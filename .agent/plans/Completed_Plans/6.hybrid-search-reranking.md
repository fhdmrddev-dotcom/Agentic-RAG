## Overview

Currently, retrieval uses **vector search only** (pgvector cosine similarity). This module adds:

1. **Keyword search** via Postgres full-text search (`tsvector` / `tsquery`)
2. **Reciprocal Rank Fusion (RRF)** to combine vector + keyword results
3. **Reranking** via API (Cohere) **or local cross-encoder** (sentence-transformers)
4. **Local model readiness** — configurable embedding dimensions, local reranker support, documented Ollama/LM Studio/vLLM switching

This is a pure retrieval-quality improvement — the chat UX stays the same.

---

## Architecture Decisions

### Keyword Search
- Use Postgres built-in full-text search (`to_tsvector('english', content)`)
- Add a `search_vector tsvector` column to `document_chunks` with a GIN index
- Populate on ingestion via a trigger (auto-updates if content changes)
- New RPC function `keyword_search_chunks` or extend existing RPC

### RRF Combination
- Reciprocal Rank Fusion: `score(d) = Σ 1/(k + rank_i(d))` where `k=60` (standard)
- Run vector + keyword searches in parallel, merge results by RRF score
- Implemented in Python (retrieval_service.py) — cleaner than SQL for rank fusion

### Reranking (API + Local)
- **Provider pattern**: `RERANK_PROVIDER` = `"api"` (Cohere) or `"local"` (cross-encoder)
- **API mode**: Cohere Rerank API via raw `httpx` POST — no SDK needed
- **Local mode**: `sentence-transformers` `CrossEncoder` — runs on CPU/GPU locally
  - Default local model: `cross-encoder/ms-marco-MiniLM-L-6-v2` (fast, ~80MB)
  - Lazy-loaded: model only downloads/loads on first rerank call
- Optional: can be disabled entirely via `RERANK_ENABLED=false`
- Applied after RRF fusion, before returning top-K results

### Local Model Readiness (LLM + Embedding + Reranking)

The app already supports local LLM and embedding via OpenAI-compatible APIs:
- **LLM**: Ollama, LM Studio, vLLM all expose OpenAI-compatible `/v1/chat/completions` — just set `LLM_BASE_URL`
- **Embedding**: Same pattern — Ollama exposes `/v1/embeddings` — just set `EMBEDDING_BASE_URL`
- **Gap: Embedding dimensions** — currently hardcoded to `vector(1536)` in DB. Local models (e.g., `nomic-embed-text` = 768, `all-MiniLM-L6-v2` = 384) need different dimensions.

**Solution:**
- Add `EMBEDDING_DIMENSIONS` config (default: 1536)
- New migration: alter `document_chunks.embedding` to use configurable dimensions via a helper RPC
- Update `match_document_chunks` to accept dynamic vector size
- **Important caveat:** Changing dimensions requires re-embedding all existing documents. This is a config-time decision, not a runtime switch.

## Tasks

### Task 1: DB Migration — Full-Text Search Column + Index

**File:** `supabase/migrations/008_hybrid_search.sql`

1. Add `search_vector tsvector` column to `document_chunks`
2. Create GIN index on `search_vector`
3. Create trigger to auto-populate `search_vector` from `content` on INSERT/UPDATE
4. Backfill existing rows: `UPDATE document_chunks SET search_vector = to_tsvector('english', content)`
5. Create new RPC function `keyword_search_chunks`:
   ```sql
   CREATE OR REPLACE FUNCTION keyword_search_chunks(
     search_query text,
     match_user_id uuid,
     match_count integer DEFAULT 20,
     metadata_filter jsonb DEFAULT NULL
   ) RETURNS TABLE (id uuid, document_id uuid, content text, rank float)
   LANGUAGE plpgsql SECURITY DEFINER AS $$
   DECLARE
     tsq tsquery;
   BEGIN
     tsq := plainto_tsquery('english', search_query);
     RETURN QUERY
     SELECT dc.id, dc.document_id, dc.content,
            ts_rank_cd(dc.search_vector, tsq) AS rank
     FROM document_chunks dc
     JOIN documents d ON d.id = dc.document_id
     WHERE dc.user_id = match_user_id
       AND dc.search_vector @@ tsq
       AND (metadata_filter IS NULL OR d.metadata @> metadata_filter)
     ORDER BY rank DESC
     LIMIT match_count;
   END;
   $$;
   ```
   - Uses `plainto_tsquery('english', search_query)` for safe query parsing
   - Ranks via `ts_rank_cd(search_vector, query)`
   - Joins with `documents` for metadata filtering
   - Filters by `user_id` for RLS
   - RLS note: SECURITY DEFINER bypasses row-level security, so `user_id` filter is explicit (same pattern as `match_document_chunks`)

**Validation:** Run migration in Supabase SQL editor. Verify existing chunks get `search_vector` populated. Test keyword search returns results.

### Task 3: Rerank Service (API + Local)

**File:** `backend/app/services/rerank_service.py` (new)

```python
def rerank(query: str, documents: list[dict], top_n: int | None = None) -> list[dict]:
```

**Provider pattern** — dispatches based on `RERANK_PROVIDER`:

#### API mode (`rerank_provider="api"`)
- Calls Cohere Rerank API via raw `httpx` POST (no SDK needed)
- Endpoint: `https://api.cohere.com/v2/rerank`
- Maps input chunks to `documents` param, returns reordered list
- Adds `relevance_score` from reranker to each result

#### Local mode (`rerank_provider="local"`)
- Uses `sentence-transformers` `CrossEncoder`
- Default model: `cross-encoder/ms-marco-MiniLM-L-6-v2` (~80MB, fast on CPU)
- **Lazy loading**: model loaded on first call, cached in module-level variable
- `CrossEncoder.predict([(query, doc["content"]) for doc in documents])` → scores
- Sorts by score descending, returns top-N

#### Common behavior
- Falls back gracefully if reranker fails (returns original order with warning log)
- Respects `RERANK_ENABLED` — if false, returns input unchanged (early return)
- LangSmith `@traceable` for observability

**Dependencies:**
- `sentence-transformers` added to `requirements.txt` (only imported when `rerank_provider="local"`)
- `httpx` already in deps (used for API mode)

**Validation:** Test with local model. Test with API key if available. Test graceful fallback on error.

### Task 4: Hybrid Retrieval — RRF Fusion in retrieval_service.py

**File:** `backend/app/services/retrieval_service.py`

Refactor `search_documents()`:

1. **If hybrid search disabled** — keep current vector-only behavior (backward compatible)
2. **If hybrid search enabled:**
   a. Run vector search (existing `match_document_chunks` RPC) — get top 20 candidates
   b. Run keyword search (new `keyword_search_chunks` RPC) — get top 20 candidates
   c. Apply RRF fusion to merge and score results
   d. If reranking enabled: pass top candidates through `rerank()`
   e. Return top-K results (from config `retrieval_top_k`)

New helper functions:
```python
def _vector_search(query, user_id, supabase, metadata_filter, top_n=20) -> list[dict]
def _keyword_search(query, user_id, supabase, metadata_filter, top_n=20) -> list[dict]
def _rrf_fuse(vector_results, keyword_results, k=60) -> list[dict]
```

- `_vector_search`: calls existing `match_document_chunks` RPC with `match_count=top_n` — returns rows with `id`, `content`, `document_id`, `similarity`
- `_keyword_search`: calls new `keyword_search_chunks` RPC — returns rows with `id`, `content`, `document_id`, `rank`
- `_rrf_fuse`: deduplicates by chunk `id` (same chunk may appear in both sets), computes RRF score, sorts descending — each result gets `rrf_score` field
- Final `search_documents()` enriches results with `filename` (same doc_map lookup as current code) before returning
- LangSmith tracing: `@traceable` on the main function still works; add metadata for search mode

**Validation:**
- Upload a document, search with a keyword-heavy query — verify keyword results appear
- Search with a semantic query — verify vector results still dominate
- Check LangSmith trace shows hybrid search execution

### Task 6: Configurable Embedding Dimensions

Currently `vector(1536)` is hardcoded in the DB schema and RPC functions. Local embedding models use different dimensions (768, 384, etc.). This task makes the dimension configurable so switching models is a one-config change.

**File:** `supabase/migrations/008_hybrid_search.sql` (extend Task 1 migration)

Add at the end of the migration:
```sql
-- Helper: recreate embedding column with different dimensions
-- Usage: SELECT resize_embedding_column(768);
-- WARNING: This drops all existing embeddings — re-ingestion required after running
CREATE OR REPLACE FUNCTION resize_embedding_column(new_dim integer)
RETURNS void AS $$
BEGIN
  -- Drop the HNSW index
  DROP INDEX IF EXISTS document_chunks_embedding_idx;
  -- Alter column type
  ALTER TABLE document_chunks ALTER COLUMN embedding TYPE vector(new_dim) USING NULL;
  -- Recreate HNSW index
  CREATE INDEX document_chunks_embedding_idx ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

**File:** `supabase/migrations/008b_dynamic_vector_match.sql` (new)

Replace the fixed `vector(1536)` parameter in `match_document_chunks` with a cast so it accepts any dimension:

**No Python changes needed** — the OpenAI SDK returns whatever dimension the model produces, and Supabase stores it. The dimension config is for documentation/validation only.

## Switching to Local Models (Reference)

The app uses OpenAI-compatible APIs everywhere, so switching to local models is a config change:

### Local LLM (Ollama example)
```bash
# Install & run: ollama run llama3.1
LLM_BASE_URL=http://localhost:11434/v1
LLM_API_KEY=ollama                  # Ollama ignores this but field is required
LLM_MODEL=llama3.1
```

### Local Embeddings (Ollama example)
```bash
# Install & run: ollama pull nomic-embed-text
EMBEDDING_BASE_URL=http://localhost:11434/v1
EMBEDDING_API_KEY=ollama
EMBEDDING_MODEL=nomic-embed-text
EMBEDDING_DIMENSIONS=768
# Then: run `SELECT resize_embedding_column(768);` in Supabase SQL editor
# Then: re-upload all documents (old 1536-dim embeddings are incompatible)
```

### Local Reranking
```bash
RERANK_ENABLED=true
RERANK_PROVIDER=local
RERANK_MODEL=cross-encoder/ms-marco-MiniLM-L-6-v2   # ~80MB, auto-downloads on first use
```

### LM Studio / vLLM
Same pattern — just change `LLM_BASE_URL` and `EMBEDDING_BASE_URL` to point at the local server.

## Rollback

If issues arise:
- Set `HYBRID_SEARCH_ENABLED=false` → falls back to vector-only search (zero code changes)
- Set `RERANK_ENABLED=false` → disables reranking
- The `search_vector` column and trigger are harmless even if unused
- `resize_embedding_column` is a manual-only function — never called automatically
