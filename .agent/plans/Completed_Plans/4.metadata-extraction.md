# Module 4: Metadata Extraction

## Complexity: ⚠️ Medium

Multiple coordinated changes across DB, backend services, agentic loop, and frontend. Each change is individually low-risk, but the end-to-end chain (LLM extraction → DB storage → RPC filtering → agentic tool → UI display) has several integration points. Completable in a single pass.

---

## Context

Documents are currently opaque — the only queryable fields are filename, size, status, and chunk count. The agentic loop can only do semantic search; it cannot scope results to specific document attributes like type, date, or author.

Module 4 fixes this by:
1. Running a structured LLM call during ingestion to extract title, author, date, document_type, topics, language, and summary from each document's first ~3000 chars.
2. Storing the result as a JSONB `metadata` column on `documents`.
3. Extending the `match_document_chunks` RPC to optionally filter by that JSONB using PostgreSQL's `@>` containment operator.
4. Updating `SEARCH_DOCUMENTS_TOOL` so the agentic LLM can pass a `metadata_filter` when the user's request implies document-level scoping.
5. Surfacing metadata in the DocumentList UI via an expandable row panel.

---

## Phase 1: Database Migration

**File:** `supabase/migrations/007_document_metadata.sql` (new)

```sql
-- Migration 007: Module 4 - Document Metadata Extraction

ALTER TABLE public.documents ADD COLUMN metadata jsonb;

-- GIN index for fast @> containment queries
CREATE INDEX documents_metadata_gin_idx ON public.documents USING gin(metadata);

-- Replace match_document_chunks RPC with metadata-filter-aware version
CREATE OR REPLACE FUNCTION match_document_chunks(
  query_embedding vector(1536),
  match_user_id   uuid,
  match_count     integer DEFAULT 5,
  match_threshold float   DEFAULT 0.3,
  metadata_filter jsonb   DEFAULT NULL
)
RETURNS TABLE (id uuid, document_id uuid, content text, similarity float)
LANGUAGE plpgsql SECURITY DEFINER AS $$
BEGIN
  RETURN QUERY
  SELECT
    dc.id,
    dc.document_id,
    dc.content,
    1 - (dc.embedding <=> query_embedding) AS similarity
  FROM document_chunks dc
  JOIN documents d ON d.id = dc.document_id
  WHERE dc.user_id = match_user_id
    AND 1 - (dc.embedding <=> query_embedding) > match_threshold
    AND (metadata_filter IS NULL OR d.metadata @> metadata_filter)
  ORDER BY dc.embedding <=> query_embedding
  LIMIT match_count;
END;
$$;
```

Notes:
- `metadata_filter IS NULL` short-circuits → zero performance impact for unfiltered calls. Existing callers continue to work unchanged.
- `exclude_none=True` on Pydantic dump means stored JSONB only contains fields that were actually extracted, so `@>` containment works correctly (no null-key false positives).

**Validation:** Run in Supabase SQL editor — unfiltered call returns same results as before; filter with `{"document_type": "impossible_xyz"}` returns empty; `SELECT metadata FROM documents LIMIT 1` returns null (expected, no extraction yet).

## Phase 3: Extraction Service

**File:** `backend/app/services/embedding_service.py`

Add `extract_metadata()` function:

```python
def extract_metadata(content: str, model: str | None = None) -> DocumentMetadata | None:
    snippet = content[:3000].strip()
    if not snippet:
        return None
    schema = DocumentMetadata.model_json_schema()
    try:
        client = get_llm_client()
        response = client.chat.completions.create(
            model=model or settings.llm_model,
            messages=[
                {
                    "role": "system",
                    "content": (
                        "Extract structured metadata from the provided document text. "
                        "Return only the JSON object matching the schema. "
                        "Use null for any field you cannot determine. "
                        "For 'date', prefer ISO 8601. "
                        "For 'topics', return 3-7 concise strings. "
                        "For 'document_type', use a simple lowercase noun: "
                        "'report', 'tutorial', 'article', 'specification', 'email', 'meeting notes', etc."
                    ),
                },
                {"role": "user", "content": f"Document text:\n\n{snippet}"},
            ],
            response_format={
                "type": "json_schema",
                "json_schema": {
                    "name": "DocumentMetadata",
                    "strict": True,
                    "schema": schema,
                },
            },
            stream=False,
        )
        return DocumentMetadata.model_validate_json(response.choices[0].message.content)
    except Exception:
        return None   # never block ingestion
```

Design notes:
- `content[:3000]` ≈ 750 tokens — enough for title/abstract/author block without waste.
- `json_schema` response format works across OpenRouter, Ollama, LM Studio (unlike `beta.parse()`).
- All exceptions swallowed — extraction is best-effort.
- No `@traceable` decorator — runs inside ingestion background task; would create confusing nested traces.

**Validation:** Test in REPL with a sample text containing a clear title and author — should return a populated `DocumentMetadata` object.

```python
def search_documents(
    query: str,
    user_id: str,
    supabase: Client,
    metadata_filter: dict | None = None,   # new

    query_embedding = embed_texts([query])[0]

    rpc_params: dict = {
        "query_embedding": query_embedding,
        "match_user_id": user_id,
        "match_count": settings.retrieval_top_k,
        "match_threshold": settings.retrieval_match_threshold,
    }
    if metadata_filter:
        rpc_params["metadata_filter"] = metadata_filter

    result = supabase.rpc("match_document_chunks", rpc_params).execute()
    # ... rest of function unchanged ...
```

`metadata_filter` omitted from `rpc_params` when `None` → SQL function receives its default `NULL` → no filtering → full backward compatibility.

```python
SEARCH_DOCUMENTS_TOOL = {
    "type": "function",
    "function": {
        "name": "search_documents",

            "Search the user's uploaded documents for relevant information. "

            "when the user's request implies a scope (e.g. 'find all 2024 reports', "

            "Supported filter keys: document_type, language, author, date."

        "parameters": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "The semantic search query.",
                },
                "metadata_filter": {
                    "type": "object",
                    "description": (
                        "Optional JSONB containment filter on document metadata. "
                        "Each key-value pair must match stored metadata exactly. "
                        "Example: {\"document_type\": \"report\"} or {\"language\": \"French\"}. "

            "required": ["query"],
        },
```

`metadata_filter` not in `required` → LLM only includes it when relevant.
