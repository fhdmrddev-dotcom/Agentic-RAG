# v2.5 — Deployment Strategy

> **Shipped:** 2026-05-09 · **Phases:** 058–067.5 (064 deferred) · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.5 rebuilt how Syrel streams answers, so a response keeps generating and can be picked up again after you refresh, switch threads, close the tab or open a second tab — the way Claude.ai and ChatGPT behave.

## Why this milestone existed

**A note on the name first.** The milestone is recorded as "Deployment Strategy" in `.planning/MILESTONES.md`, but its own requirements file calls it **"SSE Concurrency & Reconnect Stability"**, and none of its phases deploy anything to the cloud. "v2.5 Deployment Strategy (D-v2.5-11)" was the heading of a *branch-merge* decision inside the roadmap — ship the three core streaming phases together as one merge with no feature flags — and that heading appears to have been picked up as the milestone name at archive time. This page keeps the recorded name for consistency but describes what was actually built. (Cloud deployment itself is covered in later milestones and in `docs/DEPLOYMENT-PIPELINE.md`.)

The real problem: in v2.4, stream recovery after a refresh or tab switch had been attempted twice through Supabase Realtime and deferred both times. Investigation found the root cause was deeper. While one thread was streaming, a request for another thread's messages could hang for around 30 seconds, because synchronous database calls blocked the server's event loop. And the answer's lifetime was tied to the single HTTP request that started it — close the tab, and the answer either died or kept spending tokens with nobody listening. The milestone goal was to fix the concurrency blocker and ship "a correct run-backed streaming architecture (modeled on Claude/ChatGPT) so chat streaming survives tab-switches, page refreshes, concurrent thread navigation, AND multi-tab access."

## What shipped

- **Other chats stay responsive while one streams.** Opening another thread mid-stream went from roughly a 30-second wait to under one second.
- **No wasted tokens on abandoned answers.** Closing a tab cancels the agent's work promptly rather than letting it run unseen (until runs were made durable, below).
- **No cross-thread mix-ups.** Switching from a streaming thread to another never shows the first thread's messages in the second.
- **Answers survive refresh, navigation and multiple tabs.** Generation runs independently of the browser. Refresh mid-answer and it continues; leave and come back and it is still there; open the same thread in two tabs and both show the same tokens.
- **Honest time limits.** A long multi-tool task is no longer cut off by a fixed two-minute cap. Each AI call has its own budget that resets between tool calls. If a limit is hit, the run ends as "timed out" (distinct from "cancelled" by you), and the chat shows "Agent reached time limit" with a **Resume** button.
- **Context-aware progress labels.** Instead of a generic "Thinking…", the chat says what is happening: "Searching knowledge base…", "Setting up agent…", "Loading skill 'docx'…", including why a skill is being loaded.
- **Multi-step requests run end to end.** A clear request like "search, write a report, add charts, export to Word" runs the whole pipeline without stopping to ask "shall I continue?", while still confirming genuinely ambiguous or destructive actions.
- **Reliable output downloads.** Files the agent produced (Word documents, images) can be downloaded from chat history long after they were made, instead of failing after an hour.
- **Code execution shows signs of life.** While code runs, a heartbeat with an elapsed counter replaces a bare spinner.
- **Correct provider routing.** Picking a Claude model now routes through Anthropic even if your default provider is OpenAI.
- **Chat titles always appear**, even when a run fails, is cancelled or times out.
- **Follow-up suggestions render reliably** alongside the confidence indicator.

## How it works

**1. Unblocking the event loop (Phase 058).** Every synchronous `supabase-py` `.execute()` call on the streaming path was wrapped so it runs in a worker thread (`aexec` in `backend/app/utils/db.py`), and the AnyIO thread limiter was raised from 40 to 200 at startup (`backend/app/main.py`). This became a standing rule: blocking I/O must never run directly inside an async handler (decision D-v2.5-01).

**2. Clean disconnects (Phase 059).** The SSE handler moved to `sse-starlette`, with an `asyncio.Queue` producer/consumer split so a client disconnect cancels the agent task within about a second.

**3. Run-backed streaming (Phases 061, 061.1, 062, 063, 063.1).** The core change: the agent no longer writes to the HTTP response. It writes events to a durable per-run buffer, and any number of readers can attach to that buffer.

```
POST /threads/{id}/messages ──► returns {message_id, run_id} immediately
          │
          ▼
  agent task (producer) ──XADD──► Redis Stream  run:{run_id}
          │                              ▲
          ▼                              │ XREAD (replay from offset, then tail)
  public.runs row (status, timing)       │
                                 GET /runs/{run_id}/stream?since=N  ◄── browser tab(s)
  GET /threads/{id}/active-runs  ◄── on load / reconnect: "is anything still running?"
  DELETE /runs/{run_id}          ◄── Stop
```

- **Redis** holds the ephemeral event stream per run (`run:{run_id}`), plus indexes of active runs per thread (`runs_by_thread:{thread_id}`) and globally (`runs:active`). Redis was new infrastructure in this milestone, configured by a `REDIS_URL` environment variable so local and cloud differ only by configuration.
- **Postgres** holds the durable run record: migration `supabase/migrations/035_runs_table.sql` creates `public.runs` with Row-Level Security (owners can read their own runs) and an index for the active-runs lookup.
- **The browser** (Phase 063) splits "send" from "listen": it posts the message, gets a `run_id`, subscribes to the run stream, and on every load or reconnect asks `active-runs` and reattaches at the last offset it saw. Phase 063.1 added the offset cursor, de-duplication, and coalescing of reconnect triggers.
- A test-only fixture endpoint (gated by `ENABLE_TEST_FIXTURES`) allowed a failed run to be staged to prove the Resume path, and is not mounted unless that flag is set.

**4. Lifecycle states (Phase 066).** Runs end as `completed`, `failed`, `cancelled` or `timed_out`. Per-LLM-call budgets reset at tool-call boundaries; the agent loop has no hard total cap by design, matching consumer chat products.

**5. Lived-experience fixes (Phases 067–067.5).** A chain of user-driven test rounds fixed what automated checks missed: per-thread message storage (`messagesByThread`) so switching threads mid-stream keeps both renders; sandbox downloads re-signed on demand via a JavaScript blob fetch instead of a one-hour signed link; model-to-provider routing read from `MODEL_CAPABILITIES[model]["provider"]`; suggestions always emitted (even when empty) and ordered before `done`; a `code_executing` heartbeat during code runs; and finally a guard so a completed thread never renders empty until refresh.

## Key decisions

- **D-v2.5-01:** blocking I/O in async handlers must be offloaded (`run_in_threadpool` / `aexec`). Still a project rule today.
- **D-v2.5-02:** stay on a single server worker, because multiple workers would mask the concurrency bug. *Superseded in v2.6* once the bug was fixed.
- **D-v2.5-03:** Supabase Realtime is a best-effort hint, never the source of truth — always reconcile by fetching on (re)connect. Still a project rule today.
- **D-v2.5-08/09/10:** run-backed streaming using Redis Streams with replay-and-tail.
- **D-v2.5-11:** the three core streaming phases (061–063) ship as one merge, with no feature flags or dual code paths — the old "stream in the POST response" path was deleted outright.
- **Out of scope, deliberately:** multiple workers, Celery, browser `EventSource` replay, and auto-retrying an LLM call after refresh (a Resume button is the honest UX; auto-retry costs money and can duplicate answers).
