# v4.1 — Ship It & Feel It

> **Shipped:** 2026-09-13 · **Phases:** 242–246 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

A consolidation milestone that proved v4.0 was actually running in production, made the chat surface calmer and steadier, and measured, rather than papered over, a search-quality cliff for small tenants in large corpora.

## Why this milestone existed

v4.0 shipped a lot of capability. Much of it had not been proven live, and the chat surface operators use every day felt busier than it should. The goal was:

> v4.0 stops being code that exists and becomes a product a person can prove is running — and the surface the operator actually touches every day stops feeling busier than the bar it is aimed at.

The milestone added no new capability axis. All 19 requirements closed something already on record. They fell into five groups: shipping (SHIP), the thinking stream (CHAT), the chat shell (SHELL), verification debt (DEBT) and search recall (RECALL).

## What shipped

- **Settings → Search saves reliably.** The Search tab now sends only the fields you changed. The database enforces the vision-call bound itself, so an unrelated out-of-range value can no longer block a save.
- **Proof that v4.0 was deployed.** Twenty structural checks were run against the production database instead of being re-read from the deploy record. They confirmed every v4.0 migration was present.
- **One calm "thinking" line.** While a model reasons, Syrel shows one calm, structured line that expands into a timeline. It replaces a monospace block repainted on every token. Reasoning is also visible on plain-text answers, not only on turns that call tools.
- **The scroll position holds.** If you scroll up to read while an answer streams, Syrel leaves you there. This was tested with a real mouse wheel on a 60-message thread: 0 px of drift.
- **Updates repaint on a steady cadence.** Streaming text repaints every 60 ms instead of on every token, which cut scroll work from 61 scrolls to at most 14 for 60 deltas.
- **Chat scrolls inside chat.** The navigation rail stays put and no dead space opens under the conversation.
- **A paused run still leaves you something to do.** When a Deep run pauses at its spending cap, the composer stays usable or offers the next action.
- **Approvals can be answered in the thread.** Approve / Do-not-run appears in the chat itself, not only in the workflow panel, and answering in one place updates the other.
- **Attach a local file to a chat message.** The composer has an attachment chip, and a cloud import lets you choose where the file goes.
- **A broken source reaches you anywhere in the app.** A watched source that stops reading raises a signal in the app shell, so you see it without visiting the Library.
- **The search breadth on screen is the breadth in force.** Settings asks the database for the live value and shows a loading state rather than a built-in guess.

## How it works

- **Ship path (Phase 242).** Migration `177_rls_app_settings_user_settings.sql` turned on row-level security for `app_settings` and `user_settings`, which had been exposed in production. Migration `178_app_settings_vision_calls_bound.sql` moves a bound that lived in Python into a database CHECK constraint. The Settings page sends a changed-fields-only payload. Production was checked through read-only SQL using `scripts/verify-v40-cloud-migrations.sql`.
- **Streaming and scroll (Phase 243).** `frontend/src/components/chat/ThinkingBlock.tsx` is now the single thinking renderer. `frontend/src/providers/StreamsProvider.tsx` defines `DELTA_COALESCE_MS = 60`, a leading-edge coalescer: the first delta is never delayed and later ones are batched.
- **Chat shell (Phase 244).** The composer's attachment state lives in `frontend/src/components/chat/useComposerAttachments.ts` and renders through `ChatAttachmentChip.tsx` and `ConnectedFilePickerModal.tsx`. In-thread approvals reuse `PendingAskStack` from `frontend/src/components/panel/PendingAskCard.tsx`, mounted in `MessageList.tsx`. The source-health signal is wired in `frontend/src/components/layout/ChatLayout.tsx`.
- **Verification honesty (Phase 245).** Each phase record now carries a machine-readable `verification_mode` marker (`self-verified` or `peer-reviewed`), checked by `scripts/check-verification-honesty.cjs`. A self-check can no longer read as an independent review.
- **Recall (Phase 246).** `backend/app/services/retrieval_tuning.py` asks Postgres for the live search-breadth value. The recall harness (`backend/app/services/recall_eval.py`) gained execution-plan inspection and latency measurement.
- **Also in this window.** Migrations `179_model_registry_removed_tombstone.sql` (a "Remove" control for registry models) and `180_app_settings_self_hosted_endpoints.sql` (self-hosted model endpoints configurable in the UI) are counted in this milestone's migration range.

## Key decisions

- **The recall "fix" was refused.** Phase 246 found that raising `ef_search` gave good recall only because Postgres stopped using the vector index and scanned the whole table. That costs about 1.1 s per query for every tenant. The default went back to 40, and the requirement was left honestly unmet.
- **The source-health signal lives in the app shell.** This answers the open question v4.0 left (`SURF-03`): Syrel has no notification centre, so the signal sits in the shell.
- **The chat work stayed in one phase.** Streaming cadence and follow-scroll were treated as one mechanism and not split up.
- **One test row was retired, not run.** It needed a pre-migration-176 production database, which no longer existed anywhere.

## Gaps and deferred work

- **`RECALL-01` was unmet by design.** A tenant with a small share of a large corpus still didn't get good recall by default. `SEED-273` (`hnsw.iterative_scan`) was the named next step. Phase 272 later delivered a different mechanism: exact search over a filtered document set.
- **A failed attachment copy never recovers** (`SEED-272`). Phase 244 found it and deferred it by explicit decision.
- **Deployment lag at close.** Migrations 179 and 180 were not in cloud when the milestone closed, and production was 287 commits behind development. The v4.2 roadmap records that v4.1 was deployed later the same day (2026-09-13), with migrations through 180 applied.
- **The progress table was wrong at close.** The roadmap progress table showed 0/5 phases complete while all five were closed. It was repaired during the audit.
- **Some paths were never exercised.** The chat shell's fail-closed paths and the Deep-mode ask-user path were not driven live. The cross-provider check for the thinking block was attempted and abandoned, because the test driver couldn't verify which provider produced each answer.
- **Independent review was owed** for several phases. The 242 record shows a separate reviewer completed its review on 2026-09-19, after the close.
