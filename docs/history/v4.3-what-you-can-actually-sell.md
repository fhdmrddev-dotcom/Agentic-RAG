# v4.3 — What You Can Actually Sell

> **Shipped:** 2026-09-23 (deployed to production the same day) · **Phases:** 255–264 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v4.3 turned Syrel from a product that works into one that can be packaged, priced and sold to a client: every token is counted and priced, a subscription tier is enforced from one place, and "Experts" arrive as installable bundles of skills, knowledge and prompts that sit on top of the existing agent rather than beside it.

## Why this milestone existed

Before v4.3 Syrel had the features a client would pay for, but nothing that let anyone sell them:

- **No price on anything.** Workflow runs counted tokens while running but never wrote the totals down. Sub-agent usage vanished, and a chat that paused to ask the user a question lost its count. There was no per-model rate and no dollar figure anywhere.
- **No enforceable tier.** The organisation table had carried a `subscription_tier` column since migration 104, but no code read it. The feature-visibility map only told the UI what to draw; it did not stop anyone calling the endpoint (`docs/PRODUCT-PACKAGING.md` §1.2).
- **No unit to sell.** A "vertical pack" (a finance assistant, a legal assistant) had no shape. Without rules, the first pack would have been tempted to add its own engine code, which would have broken Syrel's governance guarantees.

The order was set at intake and each step depended on the one before it. First, write down what an extension may be. Then count cost, so things can be priced. Then enforce tiers, so a pack can be gated. Then build packs. Gating a pack behind a tier is what makes it a sellable product (a SKU) and not a folder anyone could copy.

## What shipped

- **A binding rule for extensions.** Anything that extends Syrel is data (skills, workflows, templates), an external process (an MCP server), or code run in the sandbox. It is never engine code. An automated guard enforces the rule.
- **Every token counted and kept.** Workflow runs store their token totals. Sub-agent usage rolls up to the run that started it. A paused or continued chat keeps its count. Hidden judge and emit calls are either counted or listed by name as known gaps.
- **Spend in dollars, with its blind spots stated.** Each model has an effective-dated rate. One conversion function turns tokens into USD. Operators get an `/admin/spend` page with spend per run and per org. A model with no rate shows as "unrated", never as $0.00.
- **Tiers that actually gate.** One check reads the org's tier against a capability map stored as data. A refusal names the plan that would allow the action. If the tier cannot be read, the check fails closed. Workflow execution and authoring writes are gated, not only two routes.
- **Experts as bundles.** An Expert is a database row listing member skills, required connections, knowledge folders, prompts and visibility. Row-level security covers the bundle and every member.
- **Using an Expert in chat.** Selecting an Expert scopes the thread and offers "Try asking…" starter prompts.
- **Authoring Experts.** Org admins create, edit, disable and delete Experts in the app. AI drafting can start from uploaded files. Access can be granted per user or per role, and who may author is itself a data setting.
- **A catalog to find them.** Normal users browse only the Experts available to them. Each card opens a detail view saying what the Expert does and when to use it, with one-click scoped chat.
- **Experts that can be given new skills.** The authoring studio proposes skills the Expert needs that do not exist yet. A human approves each one, and save refuses unknown skills. A skill created for an Expert now loads for every member of the org, not just its author. This was proven on 8 of 8 providers.

## How it works

- **Extension contract (255).** `docs/EXTENSION-CONTRACT.md` names the closed core: phase executors (`harness/phase_types.py`), emitters (`harness/emitters.py`), programmatic functions (`harness/programmatic.py`), validator kinds, and the agent tool registry (`_TOOL_REGISTRY` in `backend/app/services/tool_dispatcher.py`). `scripts/check-extension-contract.cjs`, `backend/tests/unit/test_255_extension_contract_guard.py` and a PostToolUse hook watch six trigger paths. The closed core counted **7 phase types / 1 emitter / 29 tools** when v4.3 opened and the same when it closed.
- **Token persistence (256).** Migration `182_workflow_runs_token_totals.sql` adds token columns to `workflow_runs`. The counting already existed (the circuit breaker in `harness_engine.py`). This phase made sure the totals are written down. The two judge-call sites are counted, and the remaining `forced_emit` gap is registered as `SEED-300`.
- **Pricing (257).** Migrations 183–185 build an effective-dated `model_rates` registry, insert-only so repricing never changes the cost of a past run. The single token→USD home is `backend/app/services/pricing_service.py` (`compute_token_cost_usd`, plus a generated SQL spelling `cost_usd_sql`). `backend/app/db/rates.py` and `backend/app/api/admin_spend.py` feed `frontend/src/pages/admin/AdminSpendPage.tsx`.
- **Tiers (258).** Migration `186_tier_capabilities.sql` creates `tier_capabilities(tier, capability)`, so moving a capability between tiers is a row change, not a deploy. `backend/app/services/entitlement_service.py` (`check_entitlement`, `enforce_entitlement`, `require_capability`) and `backend/app/db/entitlements.py` (`TIER_ORDER`: standard → pro → enterprise) are the one home. A fence fails if a second ad-hoc tier check appears. Migration 192 removed the anonymous role's read access to the map.
- **Expert bundle (259–260).** Migration `187_expert_bundles.sql` creates `expert_bundles` and its member tables with RLS, and seeds a first-party Financial Analyzer. Migration `188_expert_chat_scoping.sql` adds `threads.expert_id`, so each thread has at most one active Expert. Scoping is decided by `expert_service.py` and passed to the existing agent loop as data. There is no Expert-specific loop or executor.
- **Authoring, grants, catalog (261–262).** `backend/app/services/expert_authoring.py` mirrors the existing workflow-drafting seam. `backend/app/api/experts.py` serves the authoring and catalog routes. Migration 189 adds presentation fields (icon, when-to-use) and per-user and per-role grants. The UI is `frontend/src/components/experts/ExpertAuthoringStudio.tsx` and `frontend/src/components/experts/catalog/*`. The catalog opens Expert details in a modal because the app has no URL router.
- **Born-for skills (263–264).** Drafts carry a required `suggested_new_skills` list. Approval goes through the existing `POST /skills` path. Migration `191_skill_expert_provenance.sql` records which Expert a skill was born for, and `backend/app/utils/skill_visibility.py` lets org members load it.

## Key decisions

- **The pricing metric is ascending capability tiers** (`standard` → `pro` → `enterprise`), with optional extras in `organizations.add_ons` (D-258-01). This was named in advance as a one-way door and settled before any code was written. Per-seat licensing was out of scope.
- **An Expert is data, never a runtime.** No new executor, no Expert-specific agent loop, no parallel dispatcher. The closed core was re-counted at each phase.
- **Scope is declared per Expert.** An Expert is either `restricted` (confined to its own scope, the default) or `biased` (leans on its scope but keeps standard tools) (D-259-01). This later changed in v4.4; see Status today.
- **One active Expert per thread.** Two at once was refused, to avoid contradictory prompts and muddled spend attribution.
- **Fail closed for tiers.** An unreadable tier refuses the action, and that choice is recorded. The run budget loader fails open, for its own stated reasons.
- **Never auto-create or auto-publish.** AI drafting produces a draft row that a human edits and saves. A proposed skill becomes real only on human approval.
- **A modal instead of a page** for Expert details, because the app has no URL router. A per-Expert link remains owed.

## Gaps and deferred work

- **PACK-05 not met at close.** The Financial Analyzer's one document lived in a seed-only org and was never embedded. Folder sharing is org-scoped, so no real org could retrieve it. This was carried to `SEED-304` and resolved in v4.4 by copying the knowledge into each org.
- **Live checks owed at close:** a browser pass of `/admin/spend`, the three tier refusals tested from a standard-tier org, a live run of the authoring scenarios, and a re-run of the born-skill drive. All four were done in v4.4 Phase 265.
- **Review gap:** phases 255, 256, 262 and 264 were self-verified, and the fixes made during the close audit had no independent review. v4.4 Phase 265 supplied the reviews.
- **Partial items accepted:** the rate registry's SC#1 is PARTIAL by operator decision. 26 roster models are unrated by design. Several mapped capabilities (skills, code execution, custom models, connectors, audit export) are in the tier map but not yet wired to a gate. Adding a fourth tier needs a code edit to `TIER_ORDER`.
- **Records disagree:** the archived roadmap's coverage table claimed "25 / 25" requirements. The rows add up to 32, and the audit corrected this to 31 of 32 met.
- **Deploy prerequisite:** both production orgs had a NULL `subscription_tier` and needed one set before the backend shipped. Otherwise Experts and workflows would go dark for them.
- **Commercial blockers outside engineering** (no legal entity, unsettled IP position) were recorded as gating any approach to clients. Shipping was explicitly not treated as permission to pitch.
