# v2.0 — Agent Skills & Code Execution

> **Shipped:** 2026-04-04 · **Phases:** 9–17 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.0 turned Syrel from a document chat into an agent that can be taught reusable skills, remember what its tools returned, and run Python in a sandbox that produces downloadable files.

## Why this milestone existed

After v1.0 the agent could find and read documents, but every conversation started from zero. It had no way to learn a repeatable procedure, and it could not *compute* anything: no charts, no spreadsheets, no data analysis. The product's core value was restated as: the agent acts as an AI colleague that knows your knowledge base, can run code, and can be taught new behaviours (skills) that persist and can be shared.

There was also a quieter defect. Tool results were not fed back correctly on later turns, so the agent could not refer to something a tool had returned two messages earlier without running the tool again.

## What shipped

- **Tool memory across turns.** The agent can answer follow-up questions about a previous tool result without re-running the tool.
- **Skills.** Users can create, edit, delete, enable/disable and share named skills (a name, a description and instructions). A shared ("global") skill is visible to every user.
- **The agent discovers and uses skills on its own.** Each General-mode turn tells the agent which skills exist (name and description only). It loads the full instructions only when a request matches, and the chat shows a "skill activated" indicator when it does.
- **The agent can write skills.** In conversation, the agent can save a new skill or update an existing one. A seeded **skill-creator** skill walks users through building one.
- **Skill files.** Users can attach building-block files (scripts, templates, reference data) to a skill, and the agent can read them while following that skill.
- **Skills tab.** A dedicated page lists your own skills plus global ones. Global skills carry a badge, disabled ones are dimmed, and a "Try in Chat" button opens chat with a prompt that triggers the skill.
- **Portable skills.** Export a skill as a ZIP in the agentskills.io open format (a `SKILL.md` plus `scripts/`, `references/` and `assets/` folders), and import single- or multi-skill ZIPs.
- **Code execution.** With the sandbox enabled, the agent can run Python in an isolated Docker container. Variables and installed packages persist for the rest of that chat.
- **Live code output.** A Code Output panel in chat streams stdout (green) and stderr (red) as the code runs, then shows status, run time and download cards for any files the code wrote.

## How it works

**Tool memory (Phase 9).** Each tool call stored in the `messages.tool_calls` JSONB column now includes its `tool_call_id`. No schema change was needed. When the history for a new turn is loaded, `_reconstruct_history()` rebuilds proper `assistant (tool_calls)` → `tool (result)` → `assistant (text)` sequences. Stored results stay capped at 2,000 characters.

**Skills data (Phase 10).** The `skills` and `skill_files` tables have RLS, and files live in a private `skill-files` Storage bucket under `user_id/skill_id/filename`. The schema is in `supabase/migrations/017_skills.sql`. A `/skills` FastAPI router provides list, create, update, delete, `toggle-enabled` and `toggle-global`, plus file upload/list/delete with a 10 MB limit. Only owners can write; files on global skills are readable by everyone.

**Skills in the agent loop (Phase 11).** The catalog of enabled, visible skills is appended to the system prompt as `## Available Skills`. The agent gets three tools: `load_skill` (returns instructions plus file names, and emits a `skill_activated` SSE event), `save_skill` and `read_skill_file`. Explorer mode deliberately receives none of them. The design rejected injecting every skill's full instructions into every prompt, estimating 5–15k tokens per request, in favour of this catalog-then-load pattern.

**Skills UI and seed (Phases 12, 16).** The Skills page, a skill form dialog, and the `skill-creator` global skill seeded by `018_skill_creator_seed.sql`. Phase 16 added file upload/list/delete to the skill edit dialog, along with `listSkillFiles`, `uploadSkillFile` and `deleteSkillFile` in the frontend API layer.

**Open standard (Phase 13).** `GET /skills/{id}/export` and `POST /skills/import` read and write `SKILL.md` YAML frontmatter, sort files into subfolders by MIME type, and reject path-traversal filenames such as `../../etc/passwd`.

**Sandbox (Phase 14).** A session manager in `backend/app/services/sandbox_service.py` lazily imports `llm-sandbox` and keeps one container per `thread_id`, evicted after a 30-minute idle timeout. The `execute_code(code, libraries, output_files)` tool is registered only when `SANDBOX_ENABLED=true`, which defaults to off, so Docker is never contacted unless the operator opts in. Output streams as `code_execution_start`, `code_stdout`, `code_stderr` and `code_execution_complete` SSE events. Files written to `/sandbox/output/` are copied by `harvest_output_files()` into a `sandbox-outputs` bucket and recorded in `sandbox_files` with signed URLs. Every run is logged in `code_executions`. Sessions close when a thread is deleted and on app shutdown (the FastAPI lifespan handler).

**Code Output UI (Phase 15).** `ExecuteCodeBlock` inside `ToolCallPanel` rendered the interleaved output lines and the file cards.

## Key decisions

- **Progressive disclosure for skills.** The catalog carries names and descriptions only, and full instructions load on demand.
- **Skills and code execution are General-mode only.** Explorer mode stays a pure knowledge-base navigator by design.
- **Sandbox is opt-in.** `SANDBOX_ENABLED` defaults to false, so a deployment without Docker still starts cleanly.
- **One sandbox session per chat thread**, not per message, so analysis can build up over several steps.
- **`llm-sandbox` security policy, not Docker-in-Docker**, was judged sufficient isolation.
- **Python only.** Node.js and R were deferred.
- **No skill versioning in v2.0.** Saving a skill overwrites it.
- **Raw SDK calls only.** LangChain and LangGraph were explicitly excluded for skill orchestration.

## Gaps and deferred work

- **Audit gap, closed in-milestone.** The first v2.0 audit found the skill-file flow broken at step 1: the backend worked, but there was no UI to upload files. Phases 16 and 17 were added to close that gap and the procedural debt. The final audit reads `passed`, 37/37 requirements.
- **Thin test-generation coverage.** The audit marked Nyquist validation `partial` for Phases 10–15 and `missing` for Phase 9. Seven test failures that predated the milestone were carried forward.
- **Deferred to "v3":** a public skill marketplace (browse, install, ratings), multi-language sandboxes (Node.js, R), and scheduled skills.
- **Out of scope:** an admin moderation UI, real-time collaborative skill editing, and automated skill triggers.
- **Record inconsistency.** `v2.0-REQUIREMENTS.md` traceability maps most requirements to "Phase 1"–"Phase 7", which are the milestone's local numbers, while the roadmap uses global numbers 9–17. The audit body also says "7 phases (Phases 9–15)", written before 16 and 17 were added.
- **Migration provenance.** `code_executions` and `sandbox_files` were first created in the legacy `backend/supabase/migrations/` folder. They reached the canonical sequence only in `supabase/migrations/030_missing_tables.sql` ("Create missing tables never ported"), and the `sandbox-outputs` bucket in `029_storage_buckets.sql`.
