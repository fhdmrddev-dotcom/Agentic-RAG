# v2.6 — Foundation: RAG Quality + Multi-Worker + Polish

> **Shipped:** 2026-05-27 · **Phases:** 068–082 (incl. inserted phases; 082.5 deferred) · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.6 rebuilt Syrel's foundations — far better table and image extraction from documents, a server that runs on multiple workers, a single shared home for live chat streams, nine AI providers with live "show your work" streaming, and settings that live in the database instead of a file.

## Why this milestone existed

The roadmap framed it as building "the production-ready substrate the next four milestones depend on." Four concrete problems drove it:

1. **Inconsistent document extraction.** The same thesis saved as PDF and as Word produced very different table and image counts, so answers depended on file format.
2. **A single-worker ceiling.** v2.5 had deliberately kept one server worker so concurrency bugs stayed visible. With those bugs fixed, the ceiling had to go.
3. **Chat streaming logic trapped in one hook.** `useMessages` had grown to about 1,229 lines and owned every live stream, which blocked a second live surface (such as an evaluation pane) from ever streaming alongside chat.
4. **Six carry-forward issues** ("seeds") from v2.5 that would compound if left alone.

The milestone grew substantially during execution: it was planned as 16 phases and closed with 35 (including inserted phases), mostly from live cross-provider testing that surfaced streaming and UX defects.

## What shipped

- **Much better tables and images from documents.** Each part of a document — text, tables, images, equations — is extracted by its own swappable engine. The new table engine (camelot) found 53.5x more tables than the previous one on the reference document set; images use PyMuPDF.
- **Re-extract on demand.** A document can be re-extracted with the current engines, or with specific engines chosen per call, without re-uploading it.
- **Word documents read completely.** Floating shapes, headers and footers in DOCX files are now reached, and duplicate images are de-duplicated by content.
- **Duplicate uploads prevented.** Uploading the same file twice at the same moment produces exactly one document.
- **Recalibrated confidence.** Answer-confidence thresholds were re-tuned (from 0.55/0.40 to 0.54/0.38, over 121 queries) to match the new extraction output, restoring a balanced spread of high / medium / low confidence.
- **Two server workers by default.** The backend runs two workers; cancel works across workers, and code-execution sessions re-attach correctly.
- **Chat never blanks.** Switching threads, navigating away or refreshing shows the last known content instantly while fresh data loads, and an in-progress answer shows a visible pulse.
- **Nine AI providers.** OpenAI, Anthropic, Google (native SDK), DeepSeek (with thinking mode), Moonshot/Kimi, MiniMax, Zhipu/GLM, OpenRouter (generic fallback) and self-hosted Ollama, each with its own base URL, key, sub-agent default and timeout profile.
- **Watch the agent think and work.** A collapsible Thinking block shows reasoning where the provider supplies it; while the agent writes code, the code appears character by character in a highlighted editor before it runs.
- **A redesigned live-execution view.** Each assistant turn is a Run Card with a sticky header, timer and step counter that folds to a summary when finished. Each tool gets its own body: code editor with output and file preview for code runs, ranked result rows for searches, metadata for file reads. Past steps fold away while the active step stays fully visible.
- **Settings live in the database.** The old settings file was eliminated; administrators can register new models at runtime, and changes take effect within about 30 seconds without a restart.
- **Token usage recorded per run**, from the provider's own usage figures.
- **An operator backpressure signal** — a JSON endpoint reporting the server's bottleneck indicators, groundwork for a later operator dashboard.

## How it works

**Composable extraction (Phases 069–072, 076).** `backend/app/services/extraction_service.py` defines a `PdfExtractor` abstract base class and `extract_composable(raw, mime, engines=…)`, which routes each aspect through an independent engine registry. Defaults are stored in `app_settings` (migrations `045_app_settings_extraction_aspects.sql`, `047_app_settings_table_engine_default.sql`) and can be overridden per call with `?engines=` on `/upload` and `/reextract` (`backend/app/api/documents.py`). Every extraction is logged to `pdf_extraction_runs` (migration `039`), and `documents` records which extractor was used (migration `040`). Table/image rows gained bounding boxes (migrations `041`, `042`). Vision-call limits moved into `app_settings` (migration `044`). Upload races are closed by a partial unique index (migrations `043`, `051`).

**The Docling detour.** The plan was "Docling-first." Over four phases (070–071.2) a dependency conflict with the Supabase client's HTTP library was resolved, Docling shipped as primary, then live testing showed timeouts, thread starvation and weak recall on real documents. Phase 071.3 benchmarked three table engines, named camelot the winner, and removed Docling entirely (decision D-PRD-15). Phase 071.4 then fixed a camelot over-count and a silent data-corruption bug where re-ingest did not delete prior tables and images.

**Multi-worker (Phases 077–080).** Phase 077 built a validation harness (an env-gated mock LLM, 50 parallel runs) to prove cross-worker cancel via Redis, sandbox container re-attach, and a per-worker Redis singleton. Phase 079 recorded decision D-PRD-12, superseding v2.5's single-worker rule, set `WORKER_COUNT=2` as the default, and added `runs.spawned_by_worker` (migration `052_runs_worker_id.sql`) for debugging. Phase 080 corrected the deployment guides for multiple workers, a Redis container and connection-pool tuning.

**Streams provider (Phases 068, 068.5).** A Zustand store (`frontend/src/stores/streamsStore.ts`) plus a `<StreamsProvider>` context (`frontend/src/providers/StreamsProvider.tsx`) now own every run-stream subscription, mounted below the auth gate in `App.tsx`. `useMessages` shrank to a thin reader (about 130 lines today). A mocked second surface was proven to render without state collisions. v2.5's guard against the empty-thread-until-refresh bug was preserved verbatim.

**Fast database path (Phase 073).** Three hot writes on the chat path — run insert, message insert, run finalize — moved from the synchronous Supabase client to an `asyncpg` pool (`get_pg_pool()` in `backend/app/dependencies.py`), and `runs.input_tokens` / `runs.output_tokens` are now filled from the LLM `usage` field.

**Providers and live execution (Phases 075–076.2).** Each provider adapter (`openai_service.py`, `anthropic_service.py`, `google_service.py` — Google moved to its native SDK in 075.5) emits the same `tool_args_progress` event vocabulary, so one frontend renders all of them. DeepSeek `reasoning_content` is round-tripped and stored (migration `050_messages_reasoning_content.sql`). The live-execution UI lives in `frontend/src/components/chat/RunCard.tsx`, `ToolCallPanel.tsx` and `ThinkingBlock.tsx`.

**Settings unification (Phase 081.1).** Migration `053_settings_unification.sql` added 15 `app_settings` columns and a `model_capabilities_overrides` table with RLS. A one-shot startup migration moved 36 keys out of `settings_override.json`. Model capability lookups resolve in four tiers: database override, then the `LLM_CALL_TIMEOUT_OVERRIDES` environment list, then the static `MODEL_CAPABILITIES` dictionary, then a default — behind a 30-second hot-reload cache.

## Key decisions

- **D-PRD-12 — multi-worker by default** (`WORKER_COUNT=2`), superseding v2.5's single-worker rule; reverting is an environment-variable flip.
- **D-PRD-15 / D-v2.6-05 — Docling retired**, camelot tables and in-process PyMuPDF images as defaults; the "Docling-first" thesis was formally dropped.
- **D-v2.6-04 — re-extraction is opt-in** via `POST /documents/{id}/reextract`, not automatic.
- **D-v2.6-01 — Supabase client upgraded** (2.10 to 2.29.x) to resolve the HTTP-library conflict.
- **Settings in the database, secrets in the environment** — non-secret configuration moved to `app_settings` / `user_settings`; API keys stay in environment variables.
- **One event vocabulary for all providers**, so provider differences stay inside each adapter and the shared UI path never forks.

## Gaps and deferred work

- **Phase 082.5 (Error Handler Foundation) deferred to v2.7** — clean user-facing errors without SDK internals, a single log sink, and a trace ID on every error response.
- **40 acknowledged items at close:** 15 test-status fields not flipped (cosmetic), 10 verification gaps approved at project level, 11 historical quick tasks, and 4 dormant seeds (SEED-002 to SEED-005).
- **Sources disagree on scale.** The roadmap planned "16 phases, ~40 plans"; `MILESTONES.md` records 35 phases and 91 plans. The roadmap also carries a stray placeholder "Phase 83: 075.9" with no plan.
- **The agent-timeout audit (075.11) shipped no code.** Its finding was that a long-call cut-off came from a per-model timeout, fixed by raising configured timeouts rather than by a unified setting.
- **Migrations overflowed their reserved range** (039–049 reserved; 039–053 used), absorbed by the inserted phases.
