# v2.8 — Harness Engine & Workflow Mode

> **Shipped:** 2026-06-07 · **Phases:** 089–096 (including inserted 092.5 and 095.1) · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.8 gave Syrel a second way to work. Free-form chat stayed, and a new "workflow mode" was added in which the agent runs a fixed, ordered sequence of steps it cannot skip or reorder, with checks between steps and a full audit trail.

## Why this milestone existed

Free-form chat ("Deep Mode") is flexible but not repeatable. The same request can take a different path every time. For business jobs that must run the same trustworthy way each time, Syrel needed a deterministic runtime: locked, ordered phases that the backend drives and the model cannot escape. The requirements framed it as giving the agent *"a deterministic, auditable workflow runtime ... alongside today's free-form chat."*

Two structural problems had to be solved first:

- **The agent loop lived inside the chat route file.** A second runtime could not safely sit on top of it until it was extracted.
- **The first harness only worked with OpenAI.** Live testing in Phase 092 showed it ran on one of seven providers. The fix was to move all provider-specific handling into one shared "provider gateway" that both modes use.

The plugin system originally planned alongside the harness was deliberately pushed to a later milestone (decision D-v2.8-01).

## What shipped

- **Locked workflows.** A thread can run a published workflow whose phases execute in order. The backend controls each transition, and the model cannot reorder or skip steps.
- **Five kinds of step:**
  - pure code with no model call (`programmatic`);
  - a single model call (`llm_single`);
  - a bounded agent loop (`llm_agent`);
  - several helper agents in parallel, merged (`llm_batch_agents`);
  - a pause to ask the user (`llm_human_input`).
- **Checks between steps.** A step can declare validation gates: JSON schema, regex, "this workspace file exists" or a code check. A failing gate leads to a bounded retry, a jump to another step, or a failed run. It never loops forever.
- **Per-step tool limits.** Each step lists the tools it may use. Calls outside that list are refused cleanly on every provider. In normal chat nothing changes.
- **Versioned, frozen workflows.** A published workflow cannot be edited, so a rerun behaves the same way.
- **Audit trail.** Every transition, gate result and refused tool call is written to an insert-only audit log.
- **Survives restarts.** Workflow state lives in Postgres, so a run can resume after a server restart. This was tested at three kill points, including mid-question.
- **Deep / Workflow mode per thread.** A thread switches into workflow mode when a workflow starts. While the run is active the thread is locked: the server refuses a switch back. Cancel releases the lock.
- **"Continue" instead of silent truncation.** When a run hits its step limit, the user gets a Continue button that grants a bounded extra budget.
- **Live phase timeline in the workspace panel.** Current, locked and completed steps, gate badges and a transition log, meeting WCAG 2.1 AA. A failed run shows as failed with a reason.
- **Unified chat tool cards.** Tool cards share one consistent frame, with auto-scroll, details on demand, no duplicates and a working download link.
- **Run honesty across providers:**
  - Each answer shows which provider and model produced it.
  - A reloaded run shows its true duration.
  - Rate limits are no longer mislabelled as billing problems.
  - "Resume" is not offered for a run that already produced its deliverable.
- **Starter workflows.** Four seed workflows (for example Research→Summarize) shipped as examples and test fixtures.

## How it works

**Agent loop extraction (089).** The loop moved from `backend/app/api/threads.py` into `backend/app/services/agent_loop.py`. All per-provider round-trip fixes moved verbatim (Anthropic `end_turn`, Google `thought_signature`, DeepSeek `reasoning_content`, empty-retry guard), so behaviour stayed identical.

**Provider gateway (092.5).** A new package, `backend/app/services/provider_gateway/`, holds:

- an event model (`events.py`);
- `open_stream` in `dispatcher.py`;
- per-provider adapters (`anthropic.py`, `google.py`, `openai_compat.py`);
- a single chunk consumer.

Deep Mode and the harness both consume it, and the rule was that Deep must stay byte-identical. Error classification lives in `provider_gateway/errors.py` (`classify_provider_error`). It maps structured status codes: 429 is a rate limit, 401 is auth, insufficient quota is billing, and anything uncertain gets a neutral message.

**Schema (090).** Migrations `056_workflow_definitions.sql` to `062_workflow_run_claim_lease.sql` add the following tables:

| Table | What it holds |
|---|---|
| `workflow_definitions` | Workflow definitions. `UNIQUE(slug, version)`, a `BEFORE UPDATE` trigger that freezes published rows, and `ON DELETE RESTRICT` |
| `workflow_runs` | One row per run |
| `workflow_phases` | Per-phase state |
| `harness_audit` | The audit trail. Insert-only through row-level security |

The same migrations add the `threads.active_workflow_run_id` column. The seed templates came in `061_harness_seed_templates.sql`, with fixes in `065` and `066`. `063_dual_mode_continue.sql` supports Continue. Typed Pydantic models in `backend/app/models/harness.py` parse the phase config.

**Engine (091).** `backend/app/services/harness_engine.py` (`run_workflow`) is a hand-written async loop with a two-step write: mark the phase active, execute, then atomically mark it complete with its output. That is what makes resume safe. Phase executors register into `PHASE_TYPE_REGISTRY` via `backend/app/services/harness/phase_types.py`; they reuse `task_service`, `ask_user_service` and `tool_dispatcher` rather than re-implementing loops. Gates live in `backend/app/services/harness/validators.py`. Publish-time reachability lint lives in `harness/reachability.py`. The tool allowlist is enforced at the one `dispatch_tool()` choke point and when the tool list is built. Both checks do nothing when no workflow is active. No new dependencies were added.

**Mode wiring (092).** A thread is in Deep Mode when `active_workflow_run_id` is null. An illegal mode switch returns HTTP 409, and the lock is cleared in the same transaction that writes the terminal status. Continue is `POST /runs/{run_id}/continue` (`backend/app/api/runs.py`).

**Cross-provider parity (093).** A shared model resolver resolves the model from the provider without changing saved settings. Ask-user round-trips were fixed for workflow runs, and the three phase types that had never run were completed: `split_topic` now drives a real N-way batch fan-out. A live re-test passed 8/8.

**Legibility (094, 095, 095.1).**

- Phase events ride the existing `run:{run_id}` stream into a dedicated `phasesByThread` store, so phase updates do not re-render chat.
- `PhaseTimeline.tsx` and `PhaseCard.tsx` sit in `frontend/src/components/panel/`.
- The panel became the single live-execution surface for both modes (decision D-094-UNIFY).
- The todo panel fills from observed tool activity even for providers that never call `write_todos`.

**Eval and concurrency (096).**

- `scripts/eval_cross_provider.py` gained multi-phase workflow runs per provider and became the CI regression gate. `scripts/restart_smoke.py` and `scripts/longmsg_workflow_smoke.py` cover restarts and long inputs.
- Batch fan-out is capped by `max_parallel_agents` (default 5) on top of the global cap of 20.
- `StreamsProvider.tsx` keeps at most three live streams at once (the viewed thread plus recent ones). This fixed a 15–30 second hang when switching threads with six or more runs active.

## Key decisions

- **D-v2.8-01: harness and dual mode only.** The plugin contract and an operator role tier moved to v2.9, to be decided on real harness usage data.
- **GATEWAY-01: one home for provider logic.** The harness reached parity by *consuming* the shared gateway, never by re-implementing it. Deep Mode must stay byte-identical.
- **PARITY-02 over PARITY-01.** The parity that mattered was the workflow path. Deep-mode Anthropic polish was deferred again because Deep already worked on all providers.
- **D-094-UNIFY.** The workspace panel became the single live-execution surface for both Deep and workflow runs. This reversed an earlier in-chat run card for Deep.
- **D-095.1: honesty from existing data.** Run honesty is derived from data already stored: no migration and no new stream events. Provider quirks are handled at the gateway boundary.
- **Composition, not new infrastructure.** No LangChain/LangGraph/Temporal/Celery. The engine reuses the existing runs table, Redis and services.
- **Deep Mode stays the default.** Workflow mode is strictly opt-in.

## Gaps and deferred work

- **Audit status: `tech_debt`.** 24 of 25 requirements were satisfied, all 10 phases closed and 6 of 6 end-to-end flows passed.
  - The one partial is **CONC-01**. Cross-tab page loads during heavy fan-out stayed at a p95 of about 3 s, against a 50 ms target. This was 2.9 times better than before but still unmet. The cause is synchronous stream creation in the gateway dispatcher, deferred as SEED-065-B.
- **Warnings recorded by the audit:**
  - Seed workflows exist only as migration INSERTs, so an environment built from `full-schema.sql` alone has none.
  - A user-cancelled workflow could show as "failed" rather than "cancelled". Not re-checked for this document.
- **Proven in code, not watched live.** Continue at the step cap (an operator decision at close).
- **Moved to v2.9 or later:** the plugin contract (PLUGIN-01..03), the `llm_judge` validator, the visual workflow builder, and making models actually work step by step (SEED-052). PARITY-01 (Deep-mode Anthropic polish) was deferred again.
- **Open bugs at close:**
  - "Setting up agent…" hides model activity during start-up (BUG-260607-02);
  - MiniMax-M3 sends malformed tool arguments (BUG-260607-03).
- **Records disagree on the provider count.** EVAL-01 says "6 native providers", while MILESTONES.md and the 093 work say "native-7".
