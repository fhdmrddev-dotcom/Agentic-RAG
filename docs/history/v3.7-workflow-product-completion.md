# v3.7 — Workflow Product Completion

> **Shipped:** 2026-08-24 · **Phases:** 192–200.3 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v3.7 took the workflow engine Syrel had been building since v2.8 and made it usable end to end: a person can find a workflow, understand which authoring door they are walking through, build it with the right vocabulary, test-run it, stop it, and see what it produced.

## Why this milestone existed

Between v2.8 and v3.6 Syrel gained a harness engine, a Workflow Studio, a visual canvas and graded governance. A product review on 2026-08-10 found that the pieces worked but the journey did not: the Workflows page was three unlabelled shelves, identical names were indistinguishable, the two ways to start authoring looked alike, the model for a step was typed by hand, a running workflow could not be reliably stopped, and a finished run did not say what it had produced. Every requirement in this milestone traces to a seed planted during earlier testing or to a measured finding from that review. The milestone closed 20 of 20 requirements.

## What shipped

- **A searchable, filterable workflow library.** The Workflows page gained search by name, a tag filter, a findable create button, and card actions whose effect is predictable before clicking (for example, "Tweak" no longer silently opens a full edit surface).
- **Workflow identity at a glance.** When several workflows share a name, the card shows which is which, whose it is, what it was copied from and how recently it changed (for example `3 share this name · changed 2 days ago`).
- **"Does this one work?" on every card.** Each card shows when the workflow last ran and whether that run succeeded, with an honest "unknown" state and a separate state for workflows that have run, but not by the viewer.
- **Two authoring doors that explain themselves.** A person can tell the "describe it" door from the template door before choosing.
- **Templates bound at authoring time.** A document template is attached when the workflow is built, and every run fills that same template with current information. The drafting AI is told a template was provided, not merely handed placeholders.
- **A model picker backed by the live registry.** A step's model is chosen from the registered model list instead of typed as a slug.
- **Guided drafting.** Drafting from a description surfaces the decisions that actually change the result, rather than giving one shot at a prompt.
- **A Stop button that really stops, and says so.** A running workflow can be stopped at any point; the press is acknowledged on screen, and a stopped run still reads as stopped after navigating away and back.
- **The run shows its deliverable.** A workflow that produces a file shows it on the run surface using the same file card chat already uses, and a finished run names what it produced by kind (file, filled template, written answer, and so on).
- **A measurable run.** Each step shows how long it took and how much it handled; the centre column says what each step yielded while the right-hand spine says when and for how long.
- **Human-in-the-loop workflows can be published and test-run.** A workflow that asks a person for structured input mid-run can pass the publish check (the validation run auto-continues with the first configured choice) while a live run still pauses for a real person.
- **One consistent visual language across the workflow product.** Library, authoring, canvas and run were brought into the adopted design system, removing flat text dumps rather than adding features.

## How it works

- **Library facts in one query.** The last-run badge is sourced from one owner-scoped `LEFT JOIN LATERAL` across the library's feeds, so there is no per-card fetch. The card's wording decisions live in small pure modules under `frontend/src/components/workflows/library/` — `runFacts.ts` (last-run outcome, four arms plus `unknown`), `cardFace.ts` (what the card leads with), `rowIdentity.ts`, `relativeChanged.ts` and `libraryFilter.ts` — so `WorkflowCard.tsx` renders decisions rather than computing them.
- **Model picker.** The canvas phase form (`frontend/src/components/workflows/PhaseFormPanel.tsx`) uses `ModelField`, fed from the live `MODEL_CAPABILITIES` union rather than a hardcoded list.
- **Honest cancellation.** `finish_run` in `backend/app/db/workflows.py` carries a terminal-status guard, and `complete_phase` updates `workflow_phases` only `WHERE ... status IS DISTINCT FROM 'cancelled'`, so a late `completed` write cannot overwrite a `cancelled` at either the run or the step level. Migration `119_workflow_phases_cancelled.sql` adds the cancelled step state.
- **Run measurement.** Migration `121_workflow_phases_timings.sql` adds per-step timings; `122_workflow_runs_definition_snapshot.sql` stores the definition each run executed against.
- **The jsonb string-scalar repair.** `complete_phase` had been pre-encoding step output with `json.dumps` into a `$2::jsonb` parameter on a connection pool that already registers a JSON codec. The result was step output stored as a JSON *string* instead of an object on every completed row inspected (484 of 484), so the run surface's read side quietly found nothing. The fix stopped the double-encoding; migration `123_repair_definition_snapshot_string_scalars.sql` repaired the sibling snapshot column.
- **Human input.** The human-input executor was extracted to `backend/app/services/harness/human_input.py`; it auto-continues only when `ctx.is_golden_run` is set (the publish validation run), so live runs still pause.
- **Registry overrides.** Migration `120_model_capabilities_overrides_emit_tier.sql` lets the model registry carry per-model emission-tier overrides.

## Key decisions

- **Nothing new for "deterministic steps" (NODE-01).** Phase 198 counted real usage and found 0 of 264 phases across 119 definitions existed only to reshape data, so no new node type was built; the existing code-execution step remains the answer.
- **Fix the encoding, never add a cast.** The jsonb string-scalar defect was fixed by stopping the pre-encoding at the write site rather than by casting on read.
- **Golden-run auto-continue is gated at exactly one site**, so a live run can never be auto-answered.
- **Card logic extracted before it grew.** The card's "what to lead with" decision moved to `cardFace.ts`, with a characterization test committed one commit before the extraction to prove behaviour did not change.
- **Ship v3.7 together with v3.8's first three phases.** Phases 201–203 were committed before v3.7's last three, so the 2026-08-24 production release deliberately included them.

## Gaps and deferred work

- **Run answer picks the wrong step on some runs.** When a workflow's final "emit" step writes only a short status line, the run's headline answer shows that line and the real synthesis renders nowhere (`BUG-260823-04`, deferred on purpose because a naive skip would drop legitimate prose).
- **The close audit was partly wrong and corrected itself.** An independent re-audit found the backend gate quoted was a hand-picked subset and the typecheck command checked zero files; re-running the real typecheck surfaced a genuine defect (Test Run launched the last *saved* definition instead of the current draft), fixed in `2ee40c52`.
- **Three phases were uncommitted when the milestone was declared verified** (198, 200.2, 200.3); they were committed afterwards. This is why the v3.7 commit range overlaps v3.8.
- **Plan count disagrees between sources**: the milestone record measures 145 plans; the audit says 147. Neither is reconciled.
- **Owed manual testing, closed as a decision**: Phase 192.2 (0 of 10 rows driven), 197 (5 rows not driven), 199 (0 of 6 driven); Phases 198 and 200.2 have no verification report and the security review for 200.1 was never run.
- **Stop attribution wording**: three non-owner callers can cancel a run, so the UI can say "Stopped by you" about a stop the reader did not make (WR-04, open).
- **Carried forward to v3.8**: scheduled/unattended runs with spend caps, stateful workflows, CSV and email ingestion, and outbound connectors.
