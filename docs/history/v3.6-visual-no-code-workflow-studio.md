# v3.6 — Visual / No-Code Workflow Studio

> **Shipped:** 2026-08-09 · **Phases:** 181–190 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

Syrel gained a drag-and-drop canvas where a non-technical person can draw a business process, see
which steps must prove their answers from the knowledge base, watch the process run step by step,
and — for the first time — have a workflow send a real message to an outside service under approval.

## Why this milestone existed

Syrel already had a governed workflow engine (the "harness", from v2.8/v2.9) and two ways to author
workflows: "Describe & run" and "Author & govern". Both assumed a fairly technical author. The
target users — legal, HR and finance teams — think in flowcharts, not configuration forms.

The goal was to add a third, most approachable authoring door: a visual canvas on top of the same
engine. The roadmap is explicit that this was **not an engine rewrite** — the canvas had to be a pure
picture of the existing workflow definition, never a second source of truth and never a second
runtime.

A competitor review (Beam, Glean, n8n) found that none of them grade how strict a step is by whether
it is grounded in the knowledge base. That gap became the milestone's headline differentiator:
**graded governance**.

## What shipped

- **A visual workflow canvas.** Open any workflow as a node graph, then add, move, connect, configure
  and delete steps. Edits save back to the same workflow definition the engine runs.
- **"You can't draw an invalid workflow."** As you build, the server checks the structure — reachable
  steps, allowed tools, gate wiring — and each node shows a badge with the server's verdict.
- **Graded governance.** A step that reads the knowledge base is automatically *strict*: it must cite
  retrieved sources or it fails / goes to a human. A step that does not read the knowledge base stays
  *flexible*. Authors can escalate a free step to strict, but cannot loosen a step that reads the
  knowledge base. The canvas marks which steps are which.
- **Approval checkpoints.** Any step can be armed to stop and ask a person before it runs; outbound
  external-action steps are always armed.
- **Safe autosave and co-editing.** Dragging a node autosaves the draft without creating a new
  version or forcing a re-test; if two people edit the same shared workflow, the second save is
  refused with a clear "someone else changed this" message instead of silently overwriting.
- **Plain-language steps.** Nodes read as "Find documents", "Ask the AI", "Get approval", "Produce a
  report", with a reveal for technical names. Describe a workflow in plain English to get a safe,
  editable canvas draft, or start from a template in the Starter Workflow Library.
- **Watch a run on the canvas.** Each node shows pending / active / passed / failed / skipped /
  waiting-for-you, and whether it was grounded-and-cited or open. A workflow run and its finished
  deliverable got their own page instead of being dumped into chat, and remain retrievable afterwards.
- **External-action steps.** A governed step type that posts a message, creates a ticket or sends an
  email. With live sending switched off it records what it *would* have sent ("Not sent — recorded").
- **A real Slack message.** With live sending on, a Slack notification travelled the full governed
  path: approval → outbound safety checks → send → honest "completed" status → audit receipt.
- **One switch for the whole canvas layer.** Operators can turn the canvas on or off from feature
  visibility, and with it off the product behaves exactly as before.

## How it works

- **Canvas as projection.** `frontend/src/components/workflows/WorkflowCanvas.tsx` (built on
  `@xyflow/react` v12, with `zundo` for undo/redo) renders a `WorkflowDefinition`: node id = phase
  slug, edges = flow and skip branches, layout computed and **never stored** in the definition's JSONB.
  One client serializer writes edits back through the existing draft create/patch API. The engine's
  executor count was the same at the end of the milestone as at the start — no second runtime.
- **One source of validation truth.** `POST /workflows/validate` in `backend/app/api/workflows.py`
  calls the same `lint_workflow` function that publishing calls, so canvas badges and the publish
  gauntlet cannot drift. The client never invents a severity.
- **Graded governance (Phase 185).** Grounding is **derived, not stored**:
  `grounding_cause()` in `backend/app/services/harness/grounding.py` returns `detected` when a step's
  `available_tools` intersect `KB_TOOLS`, `already-set` for an explicit strict citation policy, or
  `escalated` when an author chose it — and it is recomputed on every read, so a hand-edited row
  cannot claim a grounded step is free. Strict steps get the immutable `citations_required` gate at
  run time. Approval checkpoints use `action_risk_armed` on `PhaseSpec`
  (`backend/app/models/harness.py`), built on the existing human-input phase type; migration
  `114_harness_audit_action_risk_pending.sql` records the pause in the audit log.
- **Concurrency (Phase 186).** Draft reads carry an opaque concurrency token; the client echoes it as
  `If-Match`; the server answers 409 `stale_token` / `already_published` / `draft_changed` (the last
  one if the draft changes mid-publish). No migration was needed.
- **Vocabulary + AI seed (Phase 187).** `POST /workflows/generate` produces the seed; its response
  schema *is* the strict phase-config union, so it cannot emit an unknown or unsafe node.
- **Run observability (Phase 188).** The canvas run view reads the same `usePhases(threadId)` stream
  as the developer timeline — no new events — with node state as a total function over every event
  and reconcile-on-fetch after reconnects. Runs got routes in `backend/app/api/workflow_runs.py` and a
  page at `frontend/src/pages/WorkflowRunPage.tsx`.
- **External-action node (Phase 189).** `ExternalActionPhaseConfig` in `backend/app/models/harness.py`
  maps a capability (`send_email`, `create_ticket`, `post_message`) onto the existing per-step tool
  whitelist, reusing the approval checkpoint — no new governance concept. Migration
  `115_workflow_phases_recorded_not_sent.sql` adds the honest `recorded_not_sent` outcome. The
  build-vs-platform decision was recorded as MCP-first in `docs/CONNECTOR-ARCHITECTURE.md`.
- **Live connectors (Phase 190).** Adapters in `backend/app/services/connectors/`
  (`slack_adapter.py`, `jira_adapter.py`, `smtp_adapter.py`); credentials stored encrypted per org and
  resolved server-side by reference (`116_connector_connections.sql`); an SSRF/egress guard
  (`backend/app/security/egress.py`) that runs before and independently of any credential; an
  `external_action_sent` audit receipt (`117_*.sql`); and `118_connector_secret_column_privilege.sql`,
  which closed a credential-column privilege issue found in code review. Live sending sits behind a
  separate `live_connectors` switch.
- **The off-switch.** Feature key `visual_workflow_canvas`, an ASGI-level `CanvasGateMiddleware`
  (`backend/app/middleware/canvas_gate.py`) and `backend/tests/test_revert_byte_identical.py` /
  `frontend/src/components/admin/revertByteIdentical.test.tsx` proving flag-off behaviour unchanged.

## Key decisions

- **The canvas is a projection, never a second runtime** (red line D-14). Layout is computed, not
  persisted; the harness stays the only executor.
- **The server is the single source of validation truth.** The canvas calls the same linter the
  publish gauntlet uses.
- **Grounding is enforced at run time and derived from the step's tools** (D-185-07), so an author
  cannot loosen a knowledge-base step. Note: the roadmap described an optional stored
  `grounding_mode` field; what shipped derives the mode instead, and the code contains no such field.
- **External actions add zero governance concepts** — a capability is just a tool-whitelist entry
  plus the existing approval checkpoint, always armed.
- **Connections are MCP-first and first-party-thin**, sequenced with a future Open Platform
  (`docs/CONNECTOR-ARCHITECTURE.md`).
- **Egress safety does not depend on credentials.** The outbound guard runs unconditionally, avoiding
  the "only guarded when a credential is attached" class of bug seen in other tools.
- **Pay down large files before building on them** — two dedicated refactor phases (188.1, 188.2)
  before the external-action node landed.
- **Build STRETCH 190, defer 191.** 190 was the live-proof half of an operator gate; 191 (scale
  hardening) was conditional and its condition never fired.

## Gaps and deferred work

- **CONN-02 was the one unmet requirement.** Three adapters shipped, but only Slack could actually be
  driven from a workflow at close: the step form had no fields for Jira's summary or an email's
  recipient and subject, so those runs reported `failed`. Recorded as `D-190-DEF-17` and routed to the
  connections work that followed (see v3.9).
- **SCALE-01 (Phase 191) deferred.** Real workflows sit at 5–50 steps against a ~100–150-node
  threshold, so virtualization and auto-layout were not worth adding.
- **Two accepted, tracked risks** (VALID-01 and VOCAB-02 marked partial): one low-severity
  information-disclosure concern on flag-gated routes, and the AI seed not signalling when its
  knowledge-base context was degraded (anything unsafe is still caught at validation and publish).
  Both remain open seeds.
- **Paperwork debt.** Phases 184, 188 and 189 closed without a `VERIFICATION.md`; their nine
  requirements rest on shipped code plus passing UAT. The final audit (`status: gaps_found`) scored
  CORE 19/21 satisfied, 2 partial, and STRETCH 1/3.
- **Records disagree.** `.planning/MILESTONES.md` marks CONN-03 complete; the archived
  `v3.6-REQUIREMENTS.md` checklist still shows it unchecked. The audit also notes seven Phase-190
  summaries marking CONN-02 complete, which was not true.
- **Production parity at close** required migrations up to 118 to be applied together with the
  connector code; this document does not verify cloud state.

## Video beats

1. **Visual:** A text-heavy workflow form dissolves into a clean flowchart of rounded nodes —
   "Find documents" → "Ask the AI" → "Get approval" → "Produce a report".
   **Narration:** "Syrel's Workflow Studio lets anyone draw their process instead of configuring it."
2. **Visual:** The user drags a dangling connector; a node flashes a red badge, the connection snaps
   correctly, and the badge turns green.
   **Narration:** "The server checks every edit live, so you can't draw a workflow that won't run."
3. **Visual:** A node touching a book-shaped knowledge-base icon gains a shield and a "must prove it"
   label; a neighbouring brainstorming node stays open; a lock appears when someone tries to loosen
   the shielded one.
   **Narration:** "Steps that use your knowledge base must cite their sources — and that rule can't be switched off."
4. **Visual:** The same flowchart lights up node by node — amber, green, a pause with "waiting for you".
   **Narration:** "Watch a run unfold step by step, in plain language, with its result kept on its own page."
5. **Visual:** An approval card is clicked, a message passes through a row of shield checkpoints and
   lands in a chat app with a receipt stamp; [Syrel logo placeholder] closes the scene.
   **Narration:** "And with approval and safety checks, a workflow can now act in the outside world."
