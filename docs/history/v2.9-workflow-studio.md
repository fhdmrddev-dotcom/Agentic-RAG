# v2.9 — Workflow Studio

> **Shipped:** 2026-06-15 · **Phases:** 097–104 (including inserted 101.1; STRETCH 105–109 deferred) · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.9 turned the v2.8 workflow engine into something a domain expert can use without engineering help. You describe a workflow in plain language, tie it to a project's documents and skills, and run it to produce a real, cited deliverable such as a filled-in Word report. Workflows that cannot show they produce good output are not allowed to publish.

## Why this milestone existed

v2.8 built a trustworthy workflow runtime, but only engineers could create workflows, by writing JSON or seed migrations. The v2.9 goal was to *"turn the v2.8 harness into a capability a domain expert can author, connect to their project's knowledge and skills, and run to produce a real deliverable."*

Project management was chosen as the flagship demonstration, with an explicit rule that PM must be authored content, never hard-coded logic. The milestone was planned as roughly 80–90% composition of shipped v2.8 parts. It was not to become a new runtime, and Deep (free-chat) mode had to stay byte-identical.

## What shipped

- **Projects scope the knowledge.** A workflow can be bound to a project (a folder plus its subfolders). Its searches are then limited to that project, and a single step can narrow the scope further. The server fixes the scope when the run starts, and the model cannot widen it.
- **Skills inside workflows.** A workflow step can reference a saved skill, which brings in that skill's instructions and files. The skill version is frozen into the published workflow, so editing or deleting the skill later cannot break it.
- **One-run template upload.** A user can hand a workflow a Word, PowerPoint or Excel template for a single run. The file stays in that thread's workspace, expires and is swept automatically, and is never added to the knowledge base or shown in search.
- **Template fill with citations.** The workflow fills the template from project documents. Every value carries its source (document chunk or page). The file is rendered by fixed code, not written by the model.
- **No broken files delivered.** The produced file is reopened to check its integrity before it can be marked "done". Rendering runs in a sandboxed template engine.
- **Reusable quality checks.** Any step can attach checks:
  - required citations;
  - a "check the date first" freshness preflight that asks the user when documents are stale;
  - a structure check;
  - a check that the output file is valid;
  - an AI-judge rubric.
- **A quality wall at publish time.** Each workflow declares one business requirement. Before publishing it must complete a real "golden run" that an AI judge grades. A workflow that passes structural checks but produces bad output cannot publish.
- **Workflows page.** A library filtered by project, an editor, and an 8-stage publish gauntlet (10 stages today — Grounding and the final Commit check were added later; see `frontend/src/landing/facts.ts` `GAUNTLET_STAGES`). A published workflow can be run from any chat thread.
- **Describe it in plain language.** A user describes the workflow they want, and Syrel generates a valid draft. The draft is grounded in the project folders, the available tools and skills, and any uploaded template, and it retries automatically if the first draft fails validation.
- **Read-only flow graph.** Each workflow's steps are shown as a vertical "phase spine" graph you view, not a drag-to-build canvas.
- **Project-management starter pack.**
  - Two Word templates (weekly status report and risk register).
  - Two published workflow definitions.
  - A synthetic sample project corpus ("Project Meridian").
  - All built only on the generic features.

## How it works

**Spike first (097).** A throwaway spike filled a risk register from a real knowledge-base folder on one provider. Its job was to settle the schema shape for inputs, assets and folder scope before anything was locked.

**Project binding and scope (098).** `WorkflowDefinition` gained an optional `project_folder_id` (`backend/app/models/harness.py`, `backend/app/api/workflows.py`). At run start the allowed folder IDs are resolved from the user's row-level-security context. They are then passed to every retrieval call as a bound parameter. Retrieved rows are checked against the scope; anything outside it is clipped and logged as a `scope_violation` event (`backend/app/services/harness/scope.py`, `grounding.py`). When no scope is set the check does nothing, so Deep search is unchanged.

**Skill composition (099).** Steps of type `llm_agent` and `llm_single` accept `skill_ref`, which is a resolved skill ID, not a name. `read_skill_file` is allowed automatically for that step. The skill version is snapshotted into the definition through migration `067_skill_snapshots_sibling_column.sql` and `harness/skill_snapshot.py`.

**Ephemeral templates (100).** Migration `068_workspace_template_ephemeral.sql` adds a `kind` and an `expires_at` to workspace files. `backend/app/services/template_service.py` (`sweep_expired`) and a scheduled task in `backend/app/main.py` delete expired templates. The upload control is `frontend/src/components/panel/TemplateUpload.tsx`.

**Template fill and the emission layer (101, 101.1).**

- **101.** Phase 101 added the `render_template` tool and the `docxtpl` engine to the sandbox image (`backend/Dockerfile.sandbox`, image tag `101.1`). Live testing then found that runs produced zero documents, because models would not reliably emit the data.
- **101.1.** Phase 101.1 was inserted to fix this. It added one shared "guaranteed structured emission" layer: a new phase type, `llm_emit`, built on `backend/app/services/forced_emit.py`.
  1. It *forces* the model to return a cited field map against a strict Pydantic schema.
  2. Pinned code with no model calls renders the file.
  3. The file is reopened to check its integrity.
- Forcing is tiered by each model's capabilities at the gateway boundary, with recovery for models that narrate JSON instead of calling the tool. Rendering uses Jinja's `SandboxedEnvironment` to contain template injection.

**Validation library and judge (102).** New validator kinds live in `backend/app/services/harness/validator_kinds.py`: `citations_required`, `output_file_valid`, `structure_check`, `llm_judge_rubric` and `freshness`. They use the existing gate-and-retry loop (migration `070_harness_validation_gate_library.sql`). `backend/app/services/harness/publish_service.py` runs the gauntlet: lint, then a real golden run on the project knowledge base, then the judge. It returns which stage blocked the publish and why.

**Workflows page and NL authoring (103).**

- **Pages.** `frontend/src/pages/WorkflowsPage.tsx` and `frontend/src/pages/WorkflowBuilderPage.tsx`.
- **Graph and gauntlet.** `PhaseSpineGraph.tsx` draws the read-only graph and `PublishGauntlet.tsx` shows the publish stages, both under `frontend/src/components/workflows/`.
- **Generation.** `POST /workflows/generate` (`backend/app/api/workflows.py`) calls `backend/app/services/workflow_authoring.py`. It makes one structured call against the strict `WorkflowDefinition` schema and reuses `forced_emit` and the gateway's `force_tool_name`.

**PM pack (104).** Builders and assets live under `scripts/pm-pack/`: `make_pm_corpus.py`, `make_pm_templates.py`, `templates/weekly-status-report.docx`, `templates/risk-register.docx` and a five-document sample corpus. The risk-register score (probability × impact) is computed by an inline Jinja expression in the template, so there is no PM-specific engine code.

## Key decisions

- **The red line held.** No new runtime and no re-implemented loop. Deep Mode stayed identical, and every engine addition was an additive seam.
- **One emission layer for any typed deliverable (D-101.1).** Force cited data, then render it deterministically. Template fill is the first user, not a one-off.
- **Plain-language authoring instead of a visual builder.** A drag-to-build editor was rejected as an anti-feature for the domain-expert buyer. The milestone shipped describe + form + read-only graph.
- **"Static tests would false-green."** Gates and the judge must be proven against the real endpoint on a real golden run. Phase 102's judge had never worked live until it was driven through the real publish endpoint, which surfaced six blockers that mocks had hidden.
- **Cross-provider is part of acceptance.** Every phase that runs workflows was tested across providers, with multiple tools, parallel threads and long messages. Provider-specific handling stays at the gateway.
- **The plugin contract stayed off the critical path.** It became STRETCH Phase 108.

- **Not every provider produced a document.** In the Phase 104 seven-model sweep, four models (OpenAI, Anthropic, MiniMax and GLM representatives) produced a clean cited `.docx`. DeepSeek, Gemini and Kimi failed honestly rather than producing a file. MILESTONES.md describes this as "honesty on all 7", which is accurate, but it should not be read as "reliable delivery on all 7".
- **Charter is a text deliverable, not a template.** MILESTONES.md lists charter, status-report and risk-register templates, but the 104 summaries show two `.docx` templates. The charter was proven as a plain-language-authored workflow that produces text.
- **Phase 102's records disagree.** Its VERIFICATION file reads `gaps_found` (1/3): the judge could never return a verdict live, and freshness always failed. Four follow-up plans (06–09) fixed both, and a later live re-verification (`102-UAT.md`) passed 7/7. The fixes are visible in today's code.
- **Phase 101's records point to 101.1.** Phase 101's verification closed `human_needed`, and its live findings led to the inserted 101.1 phase.
- **No formal milestone audit.** It was replaced by per-phase verification, security review and live cross-provider testing.
- **Other carry-overs.** 40 deferred items were acknowledged at close. Seven open user-reported bugs (for example a silently dropped send, a MiniMax 400 error and the "Setting up agent…" banner) rolled forward. SEED-005 (enhanced document structure) became the next milestone.
