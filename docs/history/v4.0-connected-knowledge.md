# v4.0 — Connected Knowledge

> **Shipped:** 2026-09-10 · **Phases:** 228–241 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

Syrel's knowledge base stopped depending on someone remembering to upload: a person connects a source once, previews what it would bring in, and the Library keeps reading it on a schedule, safely.

## Why this milestone existed

Before v4.0, documents entered Syrel through manual upload, plus a one-file import from Google Drive. Knowledge went stale as soon as the source folder changed. The milestone goal was:

> A person connects a source **once**, sees exactly what it would bring in **before** it brings anything, and the Library keeps reading it on a schedule, safely and at a customer's scale.

Reading from outside systems automatically introduced three new risks, and the milestone was scoped around them:

- **Deleting knowledge by accident.** A half-read listing could make the source look emptied.
- **Leaking documents across people.** One connection's files needed one clear visibility rule.
- **Prompt injection.** A document someone else wrote could now arrive without a human picking it.

## What shipped

- **Connect a source once, then let it be read on a schedule.** Map a Google Drive folder to a Library folder and Syrel checks it every N minutes. The screen says "checked every N minutes" and never claims "instantly".
- **One contract for every kind of source.** Google Drive, OneDrive (through Microsoft Graph), any MCP server that serves files, and mailboxes all plug into the same `browse / list / read / check` contract.
- **Add a new MCP file server by configuration, not code.** A GitHub MCP server was bound entirely through the UI. Its tool names and argument shapes are stored as data, and no code was committed to support it.
- **Mail as documents.** Each email message becomes one document. Messages are grouped by thread and attachments become child documents, so a 14-message thread doesn't give the same answer 14 times.
- **Preview before anything lands.** Before the first import, a person sees four labelled groups: *will be added*, *already here*, *type not supported* and *can't tell without reading it*. They also see where routing rules would file each item. Nothing is written until they confirm.
- **One visibility per connection.** Everything ingested through a connection inherits one visibility, which is enforced by the database and stated plainly on screen. Every document records which connection placed it, and that shows at retrieval and citation time.
- **Safe lifecycle behaviour.** A file removed at the source is not deleted from the Library unless someone asks. Disconnecting a connection *freezes* its documents: they stay but are left out of retrieval, with **Purge now** and **Reconnect** as named actions.
- **A durable ingestion queue.** Ingestion survives restarts and bursts, with a cap, retries and resume. Embedding calls are batched within real provider limits. When embedding fails, Syrel names the failure instead of returning empty results.
- **Per-source run history.** Each source shows what each sync actually did, with counts and errors. A source that stopped reading says when it stopped and offers the action that fixes it.
- **Write tools are fenced off from synced content.** When a turn's retrieved context includes connection-sourced content, write-capable connector tools need confirmation first.
- **One rule engine.** Watch-routing rules and classification rules share one rule language. Source facts such as source system, path and sender can be used as filter fields.

## How it works

- **Source contract.** `backend/app/services/sources/base.py` defines the adapter protocol. The adapters live in `sources/adapters/` (`google_drive.py`, `microsoft_graph.py`, `mcp_source.py`). Mail is handled as a *shape* in `sources/mail/` (`gmail.py`, `mailbox.py`) that delegates to existing adapters, not as a fourth adapter. For MCP servers, tool-name and argument mappings live in the connection's `config["source_tools"]`.
- **One ingest splice.** `backend/app/services/ingest_splice.py` creates every document row. That covers `/upload`, connector attach, watched sync and the email cascade (Phase 229).
- **Durable queue.** Migration `153_ingestion_jobs.sql` adds the queue table. `backend/app/services/ingestion_queue_service.py` claims jobs using the existing `FOR UPDATE SKIP LOCKED` pattern, so no new broker or process is needed. The queue was proven on `/upload` before any connector used it.
- **Visibility.** Migrations `154`–`156` add connection-scoped visibility (`ingest_visibility`). It is enforced in RLS on `documents` and `document_chunks` and inside the `match_document_chunks` and `keyword_search_chunks` functions.
- **Watch loop.** Migrations `168_connector_watches.sql`, `169_connector_watch_items.sql` and `170_documents_source_state.sql` hold watch state. `backend/app/services/watch_service.py` runs on the existing scheduler (`scheduler_service.py`).
- **Deletion guard.** A listing carries `SourceListing.complete`, which defaults to `False`. Syrel marks a file "missing" only when the listing's final page asserted completeness. A rate-limit error halfway through a listing can therefore never delete a corpus.
- **Preview.** `backend/app/services/sources/preview_service.py` identifies files cheaply by `(source_system, external_id, source_version)` at preview time. The existing `sha256` dedupe still runs when the file is actually ingested.
- **Sync history.** Migration `172_connector_sync_runs.sql`, served through `backend/app/api/sources.py`.
- **Rules.** Migration `173_classification_rules_scope.sql` and `classification_matcher.py` provide one rule language and one matcher, split by scope. A rule that would widen a document's visibility only produces a suggestion that a person must accept.
- **Mail grouping.** Migration `175_documents_thread_key.sql`.
- **Search breadth knobs.** Migration `176_app_settings_hnsw_knobs.sql` adds operator settings for `hnsw_ef_search` and `hnsw_iterative_scan`.
- **Injection guard.** `backend/app/services/tool_dispatcher.py` puts write tools into an "ask" posture whenever connection content is in the retrieval context.

## Key decisions

- **Freeze, don't delete, on disconnect.** This follows Microsoft's precedent. Documents stay but are left out of retrieval.
- **Four preview groups, not three.** "Already here" means matched by source file identity, not by content. A content hash would need a download, and avoiding downloads is the reason the preview exists.
- **Embedding failover only within the same vector space.** Syrel never silently switches embedding providers, because mixing vector spaces quietly degrades search.
- **Mail is a shape, not a new adapter.** This was proven by hash: `sources/base.py` stayed byte-identical while mail support landed.
- **No new scheduler, broker or OAuth scope.** The existing scheduler, queue-claim pattern and `drive.readonly` scope were reused.
- **A visibility-widening rule is only ever a suggestion.** In this schema a folder sets a document's visibility, so automatically moving a document into another folder is an access-control change.

## Gaps and deferred work

- **Recall at scale (`QUEUE-06`) was not ticked.** Phase 241 found a real recall cliff. At the shipped `ef_search = 40`, a tenant owning 0.2% of a 100,000-chunk corpus scored recall@20 of 0.040. The remedy (raising `ef_search` to 200) shipped as an operator setting with the default unchanged. v4.1 later found that remedy worked only by abandoning the index, which made each query about 1.1 s.
- **SharePoint was deferred** (`SEED-256`); only OneDrive shipped through Graph.
- **Reaching someone who isn't on the page (`SURF-03`)** was left open because Syrel had no in-app notification surface. v4.1 (Phase 244) resolved it with an app-shell signal.
- **Two debt items were blocked by decision:** an external code review of the OAuth state rework, and serving from an `app.` subdomain.
- **Three phases (238, 240, 241) closed without an independent review.** Their builder verified them.
- **Sources disagree about deployment.** The milestone entry in `.planning/MILESTONES.md` says v4.0 "has not deployed" and cloud was 15 migrations behind. The v4.1 roadmap later measured that the production push landed on 2026-09-10, the same day, with all 15 migrations applied.
- **Sources also disagree about the Microsoft tests.** The v4.0 close says all nine live Microsoft tests were blocked on an Azure app registration. Phase 245 later found they had been run live on 2026-09-07, three days before the close.
