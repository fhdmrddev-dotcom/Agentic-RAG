# v2.7 — Agent Workspace & Panel

> **Shipped:** 2026-05-30 · **Phases:** 083–088 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.7 gave the Syrel agent a desk: a private per-conversation workspace where it can write, version and diff files, keep a to-do list, hand work to helper agents and stop to ask the user a question. A right-side panel shows all of that as it happens.

## Why this milestone existed

Before v2.7 the agent's work disappeared into the chat transcript. If it drafted a document, made a plan or needed a decision, the only trace was prose in a message. The milestone goal was to *"ship a per-thread workspace filesystem and right-side panel that gives the agent a persistent scratchpad, todo management, sub-agent spawning, and user-input pausing"*. The roadmap called this the "Claude.ai artifacts" moment for a self-hosted platform that works with many model providers.

There was also a structural reason. The chat backend's tool-dispatch chain lived inside one very large file, `backend/app/api/threads.py` (about 3,800 lines). Adding five new tools to it would have made it worse, so the milestone extracted the dispatch chain first.

## What shipped

- **A per-conversation workspace.** The agent can write, read, list and delete files that belong to one thread. The files survive later turns, page reloads and new browser sessions.
- **Every save is a new version.** Each write keeps a version history, and the agent or the user can see a structured diff between any two versions.
- **A live to-do list.** The agent can publish its plan as a checklist (`write_todos`), and the panel updates as items move from pending to in progress to done.
- **Helper agents.** The agent can delegate a sub-task to a helper agent (`task`). Helpers get a restricted toolset, cannot create helpers of their own, and run under concurrency limits.
- **"Ask the user" pauses.** The agent can stop mid-run and ask a question (`ask_user`), with optional choice buttons. The run resumes with the user's answer, and this works even when the backend runs several worker processes.
- **A right-side workspace panel.** The panel sits next to the chat and can be collapsed with a button or Ctrl/⌘+. It becomes a bottom sheet on phones. It contains sections for Todos, Files (with previews of Markdown, code, CSV and images) and version diffs, plus a pinned area for pending questions.
- **Chat stays fast while the panel updates.** Panel updates arrive on the same live stream as chat but go to separate state, so they never make the message list re-render.
- **Accessible panel.** Every panel surface was brought to WCAG 2.1 AA: keyboard navigation, labels, visible focus and checked contrast in both themes.
- **Bug fixes carried in.** Fixes for Kimi/Moonshot "thinking" text leaking into answers, thread-title generation on several providers, a timer that vanished mid-run, and output files that were not persisted.

## How it works

**Tool dispatch (Phase 083).** The tool chain moved out of `backend/app/api/threads.py` into `backend/app/services/tool_dispatcher.py`, which uses a registry. All 16 existing tools moved over with no change in behaviour, and every new tool registers there. The handler map still lists `workspace_write`, `workspace_read`, `workspace_list`, `workspace_delete`, `workspace_diff`, `write_todos`, `task` and `ask_user`. Title generation picks its model by tier using the `_SINGLE_MODEL_PROVIDERS` set. A provider-gated state machine removes `<think>` blocks, and only for Moonshot and DeepSeek.

**Workspace storage (Phase 084).** Migration `054_workspace_files.sql` adds `workspace_files` and `workspace_file_versions`, with access rules that follow the thread's ownership (FK-chain row-level security) and a private storage bucket. `backend/app/services/workspace_service.py` hides a hybrid storage scheme:

- Files up to 256 KB are stored inline in Postgres; larger files go to the Supabase Storage bucket. The threshold can be changed in `app_settings`.
- Hard limits: 10 MB per file, a soft warning at 100 files, and reads capped at 8,192 characters so a large file cannot flood the model's context.
- Diffs are computed with Python's `difflib`.

Four read-only endpoints under `/threads/{thread_id}/workspace` (list, content, versions, diff) live in `backend/app/api/workspace.py`. Content is returned inline or as a signed URL that expires after 60 seconds. If you do not own the thread, the endpoints answer 404 rather than 403, so they never confirm that a thread exists. Writes and deletes publish events into the run's Redis stream (`run:{run_id}`).

**New tools (Phase 085).**

- `write_todos` stores a per-thread list (migration `055_todos_table.sql`). Each call replaces the whole list.
- `task` lives in `backend/app/services/task_service.py`. It allows one level of nesting, three concurrent helpers per run, and a global cap of 20 held in a Redis counter that is updated atomically with Lua.
- `ask_user` (`backend/app/services/ask_user_service.py`) was the codebase's first use of Redis pub/sub. The backend subscribes before it announces the question, and a cancel sentinel and a broadcast on shutdown make the pause safe when two workers are running.
- The tool registry grew from 21 to 24 entries.

**Streaming and panel state (Phase 086).** `frontend/src/providers/StreamsProvider.tsx` keeps a single connection per run and sorts events by type into dedicated Zustand keys. Panel data never passes through the chat message buckets. Per-thread hooks re-fetch on thread switch, because Realtime is treated as a hint, not a source of truth.

**Panel UI (Phases 087–088).**

- `frontend/src/components/panel/WorkspacePanel.tsx` hosts `TodosSection`, `FilesSection`, `FilePreview`, `CsvTablePreview`, `VersionDiff` / `DiffLines` / `DiffExpandOverlay` and `PendingAskCard`.
- The chat/panel split is one CSS grid in `frontend/src/components/layout/ChatLayout.tsx`: chat takes `1fr` and the panel takes `clamp(300–420px)`, or 52px as a rail.
- Chat messages carry small links into the panel (`SeamPointer`, `SeamCard`, `PausedRunCue`).
- Accessibility is held in place by vitest-axe regression tests.

**Cross-provider checks (Phase 088).** `scripts/eval_cross_provider.py` drives the real `POST /threads/{id}/messages` route for each provider and prompt, then checks tool use, argument shape and database writes. A text-only instruction in the shared system prompt encourages `write_todos`/`ask_user` without forcing any tool.

## Key decisions

- **Extract before adding.** The tool-dispatch extraction had to land before any new tool, so that the new tools did not grow the chat route further.
- **Hybrid storage behind one service.** Files at or under 256 KB are stored inline and larger ones go to the bucket. Callers never see which store a file is in.
- **404, not 403.** The workspace endpoints do not confirm whether someone else's thread exists.
- **Redis pub/sub for `ask_user`.** An in-process event cannot work when two workers run (`WORKER_COUNT=2`), so the pause goes through Redis.
- **Panel state is separate from chat state.** A panel update must cause zero chat re-renders (PANEL-06).
- **One grid, one toggle.** After live testing, the separate header toggle and the "hidden" state were dropped. A single in-panel collapse-to-rail control replaced them (087-08).
- **Tool use is encouraged, not forced.** The `write_todos`/`ask_user` guidance is plain text in the system prompt. It does not use `tool_choice`. This was judged on evidence across six providers.
- **Out of scope by design:** users editing workspace files inline, using workspace files as knowledge-base content, rendering live HTML in the panel, and opening the panel automatically on every response.
