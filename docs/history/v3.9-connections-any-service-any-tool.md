# v3.9 — Connections: Any Service, Any Tool

> **Shipped:** 2026-09-04 · **Phases:** 210–227 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v3.9 turned a connection from "a verb we wrote code for" into a service record — identity, auth, discovered tools and per-tool grants — so a person connects a service, sees every tool it offers, grants each one individually, and uses it by name in chat and as a named step on the workflow canvas.

## Why this milestone existed

v3.8 proved Syrel could reach an outside system through an MCP server, but connections still came in two incompatible shapes: three hard-coded capabilities (`send_email`, `create_ticket`, `post_message`) and MCP rows. Every surface downstream — node face, service mark, filter, chat mention, catalog, picker — had to branch on which shape it was looking at, and each new surface paid that branch again. OAuth-only services could not even be stored, because the database required either a capability or an MCP URL. The milestone was measured against one sentence: *a person connects a **service**, not a protocol, sees every tool it offers, grants each one individually, and then uses it by name in chat and as a specific step on the canvas* — with the rule that **adding a service adds rows, not code**.

It also absorbed two adjacent jobs: unifying three document pages into one **Library**, and shipping the public landing page.

At close: 34 of 39 requirements delivered, 3 partial, 2 shipped but never driven; one of the partials (cloud "Add a connection") was verified on cloud the same evening.

## What shipped

- **A connection is a service, not a verb.** Every connection is created against a service, and its actions come from that service's advertised tools. The three legacy capabilities still work, as one shape among many.
- **A catalog of services.** Settings → Connections became a searchable catalog — each service with its own mark, name and one-line purpose — with a Popular row for one-click connect and a filter on state (All / Connected / Not connected) rather than on what a connector does.
- **Paste any MCP URL and sign in to that server.** A person pastes an MCP server URL, is sent to that server's own login (OAuth 2.1 with PKCE and dynamic client registration), returns, and its tools are discovered — no token minted by hand in someone else's console. Driven live against four public servers, including one exposing 41 tools with no tool code written on Syrel's side.
- **Per-tool grants and an approval moment.** Each tool is set to Allow, Ask or Deny individually (a GitHub connection rendered 44 rows), under a connection-level default. A tool set to Ask pauses the run and asks a real person before anything leaves; a denied tool is refused with a message naming the grant that would allow it.
- **Every outbound call leaves a record.** Each call through a connection writes an audit receipt naming the connection, destination host, tool and result status, and each chat message records which connectors were active when it was sent.
- **Bring-your-own OAuth app.** A customer registers their own OAuth application and connects a first-party service with it on any deployment, including self-hosted; tokens refresh silently, and a revoked connection says so plainly.
- **Google Workspace as six applications under one token.** Drive, Gmail, Sheets, Docs, Calendar and Contacts on one Google grant, with reads and writes separated, and an application whose API is disabled shows "not available" with the remedy before anyone tries to use it.
- **Connections in chat.** A person adds a connected service to a thread by name; dismissible chips show what is active; tool calls render with the service's own mark and the tool's real name; a fresh connection offers starter prompts.
- **One file in by hand.** A person can pick a specific file from a connected source and pull it into the Library or the thread.
- **A workflow step names its service and action.** Authors pick a service, then a named action; arguments are filled in a form (from a run input, a fixed value, or an earlier step) instead of hand-written JSON; publish refuses a step whose required arguments nothing can supply; the same service-and-action identity appears on the canvas, the run spine and the run surface, including the failure reason.
- **Authors can declare workflow inputs** and source a step's argument from them.
- **The Library: one home for documents.** The document space became "Library" with tabs, upload as a real front door, the six actual ingestion stages, and stored facts finally shown in the detail panel. The separate Library Health and Governance pages retired into a Health tab and were deleted.
- **The agent's activity reads like a sentence.** Chat describes what the agent is doing in plain words, and the approval card docks above the composer with its deadline coming from the server.
- **A drawing becomes quantities (spike).** A real `.dxf` drawing and `.xlsx` rate sheet were taken end to end to a bill of quantities, with ambiguous matches escalated to a person and unitless drawings refused rather than guessed.
- **A public landing page** at the product root, rendered from facts derived from the code.

## How it works

- **Connection identity.** Migration `127_connector_connection_service_identity.sql` replaced the "capability OR MCP URL" check with a mandatory `service_id` and mutually exclusive shapes, so OAuth-only services can be stored. `backend/app/services/connectors/descriptors.py` makes a legacy capability advertise a tool descriptor byte-compatible with a discovered MCP tool, so one code path serves both.
- **Posture and grants.** Migration `128_connector_connection_posture.sql` adds the connection-level default posture; per-tool overrides live in `tool_grants` (`backend/app/services/connectors/grants.py`). Enforcement happens in the harness before dispatch (the "Gate 5.5" check), for both MCP and capability shapes.
- **OAuth.** Migrations `129_connector_oauth_tokens.sql`, `150_connector_oauth_client_secret.sql` and `151_connector_tokens_rls_policy.sql`. Secrets are AES-256-GCM encrypted at rest (`enc:v1:` prefix) and the ciphertext columns are revoked from the `anon` and `authenticated` roles. Refresh uses a lease lock so two workers produce exactly one provider refresh (`backend/app/services/oauth_refresh_service.py`). The handshake keeps its secrets on the server: `backend/app/services/oauth_state.py` issues a 43-character opaque handle (`secrets.token_urlsafe(32)`), Redis holds the secret and PKCE verifier under it, and the handle is consumed once. MCP-server OAuth discovery lives in `backend/app/services/mcp_oauth.py`.
- **Google.** `backend/app/services/google/` holds per-application modules (`gmail.py`, `calendar.py`, `docs.py`, `sheets.py`, `people.py`, `writes.py`) and `availability.py`, which probes each application's API so a disabled one reads as unavailable.
- **Audit.** Migration `152_audit_log_connector_action_types_and_message_active_connectors.sql` adds `connector.call` and `connector.grant` audit action types and a `messages.active_connector_ids` column; the receipt is written in `backend/app/services/tool_dispatcher.py`.
- **Chat.** `frontend/src/components/chat/ActiveConnectorChips.tsx`, `ConnectorsFlyout.tsx`, `ConnectedFilePickerModal.tsx`; connector tools exposed to the agent via `backend/app/services/connectors/chat_tools.py`. The approval card is `frontend/src/components/panel/PendingAskCard.tsx`; one timeout constant feeds the wait, the `expires_at`, the event and the audit string.
- **Workflow steps.** Argument sourcing in `backend/app/services/connectors/args.py`; publish-time reachability checks in `backend/app/services/harness/reachability.py` and `publish_service.py`; one `StepIdentity` element renders the service and action on the canvas, `RunSpine.tsx`, `PhaseCard.tsx` and `RunCard.tsx`.
- **Library.** `frontend/src/pages/LibraryPage.tsx` with tab components under `frontend/src/components/library/` (`IngestionTab.tsx`, `IndexingTab.tsx`, `HealthTab.tsx`, `ViewsTab.tsx`). Migrations `140_document_chunks_embedded_at.sql` and `141_checked_queries.sql` back the "embedded at" fact and per-search relevance records, so a search that could not run is distinguishable from one that found nothing.
- **Kill switch.** The `live_connectors` switch is visible and controllable from the operator Control Room (`backend/app/api/admin.py`).
- **Run frame refactor.** `ToolCallPanel.tsx` was decomposed from 1,019 to 351 lines; all eight run states were compared in a real browser against the pre-refactor build and matched.

## Key decisions

- **MCP-first, rows not code.** Follows the verdict in `docs/CONNECTOR-ARCHITECTURE.md`; a new service should never need a per-vendor adapter.
- **Keep the legacy capabilities.** They are the only external path that works with no MCP server, so they were demoted to "one shape among many", not deleted.
- **Browse by connection state, not by capability.** A competitor study concluded the earlier design had promoted an attribute to be the browse axis.
- **Bring-your-own OAuth before hosted OAuth.** A Syrel-owned OAuth app's redirect would point at the cloud and exclude self-hosted installs, and restricted-scope reviews take weeks; hosted OAuth waits for a confirmed hosted tier.
- **Defer background sync with its security work, together.** Phase 219 (a cloud drive watched on a schedule) was deferred on 2026-09-04 because shipping automatic sync without ACL mirroring and deletion propagation (`SEED-209..212`) would be a security defect, not a gap.
- **Library composition is a test, not a hope.** After the first Library build passed every gate yet was rejected against the sketch, 217.1 made a composition check of the sketch the acceptance gate (red at 40 failed, green at 47 of 47).

## Gaps and deferred work

- **Phase 219 deferred to v4.0** with `LIB-08/09/10` and `SEED-209..212`. Those three requirements never had rows in the v3.9 requirements register — only in a roadmap heading.
- **Two headline features were absent when their summaries said they shipped**, both found by driving the app, not by tests: Phase 213's approval pause fell through on "Ask" (a tool needing approval dispatched like Allow), and Phase 216's chat wiring was dead inside an exception handler despite 6,929 green tests. Both were fixed before close.
- **GRANT-03 partial:** the approval names the tool and arguments but not the service; a capability row reads as a tautology ("run post_message through post_message").
- **CHAT-06 partial at close:** the requirements archive records the armed connector set as "stored nowhere", so a page reload silently disarms. Phase 223 (inside this same milestone) added `messages.active_connector_ids`; the archive and the migration disagree, and the current code does restore the chips on reload (`MessageInput.tsx:236-249`), so the archive's "stored nowhere" is out of date.
- **CAT-05 (cloud "Add a connection")** was partial at close and verified on cloud the same evening; real sends/reads through cloud connections were not yet driven.
- **Owed verification:** Phase 210 (4 of 5 success criteria never driven — scheduling criteria could not be exercised with no schedules on the install), 211 UAT, 214's eight-provider cross-provider roster and operator drives, 217's 16 UAT rows, and a deep review for 225 skipped for lack of credits.
- **Backend unit baseline unsound to quote at close** (95 failed vs the 71 quoted all milestone) because of a test-selection difference; none of the failures were connector, OAuth, MCP or chat tests.
- **23 reported bugs open at close**, six clustered on run resume.
