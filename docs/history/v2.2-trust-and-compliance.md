# v2.2 — Trust & Compliance

> **Shipped:** 2026-04-16 · **Phases:** 26–32 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v2.2 made Syrel's answers checkable and its activity accountable: every grounded answer shows its evidence and a confidence level, documents keep a version history, every significant action is written to a tamper-resistant audit log, and each reply suggests where to go next.

## Why this milestone existed

By v2.1 Syrel answered reliably, but users still had to *trust* those answers. Teams handling real documents asked four questions the product could not yet answer:

- **"Where did that come from?"** Answers had no visible link back to the passages they were based on.
- **"How sure is it?"** A strong match and a weak guess looked the same.
- **"Which version is this?"** Uploading an updated file with the same name was rejected as a duplicate, so old content lingered or had to be deleted by hand.
- **"Who did what, and when?"** Nothing recorded uploads, deletions, searches or code runs, which is a blocker for compliance-minded buyers.

The planning record groups these as features F-01 (citations), F-05 (confidence), F-02 (versioning) and F-06 (audit log), plus F-08 (follow-up suggestions) as a usability win.

## What shipped

- **Citation cards.** Beneath each answer, collapsible cards show the exact retrieved passage, the document name and its location where known. Passages are trimmed to 400 characters with an expand control and styled as quotes, so they are visually distinct from the AI's own words. Only passages retrieved in that turn appear. A whole-document analysis shows the document name only.
- **Confidence badge.** Every answer grounded in documents carries a High / Medium / Low badge, coloured green, amber or red. Low-confidence answers add a standard disclaimer asking the user to check the sources. There is no badge on web-search, code-only or skill-only answers.
- **Document versions.** Re-uploading a file with the same name creates a new version instead of failing. The old version's chunks drop out of search as soon as the new one finishes ingesting. Updated documents show a version badge (for example "v3"), and citations name the version (for example "Report.pdf (v2)").
- **Version history and restore.** Expanding a document row lists every version with number, upload date and size. An owner can restore an older version as the active one, and the current version stays in history.
- **Audit log.** Eight kinds of action are recorded automatically: document upload, document delete, search query, code execution, skill load, thread create, thread delete and settings change. Search entries include the query and the IDs of the documents returned. Users cannot edit or delete entries.
- **Audit log in Settings.** A paginated table with date-range pills (All / 7d / 30d / 90d), an action-type filter, and CSV export of the filtered view.
- **Suggested follow-up questions.** Two or three clickable pills appear under each General-mode answer. Clicking one sends it as the next question. If generating them fails, the answer is unaffected and no pills appear.

## How it works

**Citations and confidence (Phases 26, 27).** The retrieval service was changed to return `chunk_index` and an average similarity, via the legacy migration `016_citations_chunk_index.sql`. In the canonical sequence the RPC change is `supabase/migrations/023_rpc_chunk_index.sql`. Its header records that the RPCs had been omitting `chunk_index`, so citation cards showed "Full document" instead of "Chunk N" until it was applied. The chat loop accumulates the passages used in a turn and emits a `citations` SSE event plus a `confidence` value. The original thresholds were high ≥ 0.70, medium 0.50–0.69 and low < 0.50 (including zero results). The frontend renders `CitationCard` / `CitationList` and `ConfidenceBadge` under `MessageItem`.

**Versioning (Phases 28, 29).** Migration `025_document_versioning.sql` (still `supabase/migrations/025_document_versioning.sql`) adds `version_number` and `is_latest` to `documents`, a partial index on `(user_id, filename, is_latest) WHERE is_latest`, and `is_latest` filters inside the search RPCs. On upload, the newest prior version with the same filename is found, `next_version` is computed, and siblings are retired. Phase 29 added an `is_latest` filter on the document list, `GET /documents/{id}/versions` and `POST /documents/{id}/restore`. Restore flips `is_latest` (retire all siblings, promote the target) rather than re-ingesting, which is why it is instant. In the UI, the restore button is non-destructive and owner-only, with the confirmation text "This version will become active for retrieval. The current version remains in history."

**Audit log (Phases 30, 31).** An `audit_log` table holds `user_id`, `action_type` (with a CHECK constraint listing the 8 actions), JSONB `metadata` and `created_at`, has a composite index, and RLS that allows only INSERT for users. `write_audit_entry` is an async coroutine that swallows its own errors, so a failed audit write can never break a user action. It is called through FastAPI `BackgroundTasks` on ordinary endpoints and `asyncio.create_task` inside the streaming chat generator, in `documents.py`, `threads.py` and `settings.py`. Phase 31 added the `/audit-logs` and `/audit-logs/export` endpoints and the `AuditLogSection` in Settings.

**Suggestions (Phase 32).** The stream ending was upgraded from a literal `[DONE]` to JSON events: `done`, then `suggestions` (generated by the cheapest model for the active provider), then `stream_end`. Suggestion failures are isolated in try/except. The frontend parses the new events, holds the questions as temporary state on the message, and renders `SuggestionPills`, shown only in General mode and not while streaming.

## Key decisions

- **Response-level confidence, not per-claim.** Per-claim scoring was judged too granular for this release.
- **Citation cards, not in-PDF highlighting.** In-document highlighting needs a PDF renderer and was deferred.
- **Versions are keyed on filename.** Re-uploading the same name makes a version; nothing compares content. Phase 28 notes that retiring old versions is scoped by user and filename, not by folder.
- **Restore re-activates a stored version.** The requirement allowed "re-ingest from stored file or re-upload". The build chose a flag flip.
- **The audit log is append-only by construction.** RLS allows INSERT only, and no API route modifies or deletes entries.
- **Auditing must never slow the user down.** Writes are fire-and-forget and swallow their own errors.
- **Suggestions are optional, not part of the answer.** They run after the answer, use the cheapest model, and fail silently.
- **Single-user scope.** Organisation-level audit views and SIEM export were out of scope; there was no multi-tenancy yet.

## Gaps and deferred work

- **No milestone audit file.** Unlike v2.0 and v2.1, there is no `v2.2-MILESTONE-AUDIT.md`. Phases 26–31 each have a VERIFICATION report reading `passed`. Phase 32 has none.
- **Records disagree on scope.** The archived v2.2 roadmap lists **Phase 32.5 — Retrieval Quality & Chunking Fixes**, marked complete on 2026-04-18. That is two days *after* v2.2 shipped, and the milestone record counts only 7 phases (26–32). Treat 32.5 as post-v2.2 work.
- **Restore-scope asymmetry.** Upload-time version retirement is scoped by user and filename. The restore endpoint's sibling query also filters on `folder_id`, with an explicit NULL-folder guard. These are recorded in different phase summaries, and whether they can disagree for same-named files in different folders was not checked.
- **Archived requirements file is mislabelled.** `v2.2-REQUIREMENTS.md` carries the heading "v2.3 Memory, Multimodal & Experience" because it was archived after v2.3 scope was added.
- **Deferred to v2.3:** cross-thread memory, table and image extraction, the Knowledge Health dashboard, and thumbs-up/down feedback (the last two were promoted from out-of-scope).
- **Deferred further:** group-level access control (pending a multi-tenancy decision; it arrived as organisations in v3.4), in-PDF highlighting, a version diff view, citation export, and per-claim confidence.
