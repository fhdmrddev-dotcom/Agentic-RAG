# v3.0 — Document Management

> **Shipped:** 2026-06-21 · **Phases:** 110–119 (incl. inserted 111.1) · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v3.0 turned Syrel's document store from a plain upload list into a managed library: documents carry editable metadata with honest confidence, can be grouped into saved "virtual folders", linked to each other, auto-classified (always as a suggestion), and checked for health, and the agent can use all of it in chat.

## Why this milestone existed

Before v3.0, Syrel could ingest and search documents, but anything that looked like document management happened by accident. Metadata extraction was pinned to one OpenAI model and read only the first part of a file, embeddings depended on OpenAI alone, and there was no way to say "this contract supersedes that one" or "show me every invoice from last quarter". The milestone goal was to make documents "structured, related, and trustworthy enough to power both direct use and every cited workflow deliverable".

The scope was deliberately limited to a metadata-driven "Tier A" surface. The planning records explicitly reject a full vault model (object types, classes, value lists) and reject silent automatic filing, because both conflict with Syrel's folders-plus-metadata model and its audit-and-honesty positioning.

## What shipped

- **Shared foundations, built once.** Four new tables (saved views, relationships, classification rules, custom field definitions), all user-scoped with row-level security, plus new audit action types and an on/off switch for the whole document-management capability (on by default).
- **Better metadata extraction.** Extraction now uses the model the user or admin configured instead of a hard-coded one, reads a larger head-and-tail window of each document, and supports user-defined custom fields.
- **A document detail panel.** A right-side panel shows each document's metadata with a per-field confidence chip, and lets a person correct a value inline. Human corrections are marked, audited, and protected: a later re-extraction will not overwrite them.
- **Choice of embedding provider.** Settings gained an embedding-provider picker (OpenAI, Google, Ollama, LM Studio, or any OpenAI-compatible endpoint) with model and dimension auto-fill, plus a guarded re-embed job with a destructive-change confirmation. This removed OpenAI as a single point of failure for search.
- **Virtual folders (saved views).** A no-code filter builder (equals, one of, contains, is empty, numeric and date ranges, relative dates, AND, folder scope) creates saved views that appear as a live "Views" group in the sidebar. A viewer never sees documents they cannot access.
- **Agent can query views.** In chat, the agent can run a saved view or an inline metadata query through a `query_documents_by_view` tool.
- **Document relationships.** Typed links between documents (supersedes, amends, references, attached-to), shown in the detail panel grouped by direction, with masked rows for linked documents the viewer cannot open, and a typeahead picker to create links. The agent can follow them with a `get_related_documents` tool.
- **Auto-classification as suggestions.** Rules run on upload and, on the first match, attach one visible suggestion ("move to folder X because rule Y matched"). Nothing moves until a person accepts; accepting is audited and can be undone; dismissing clears the suggestion.
- **Governance health view.** A read-only page showing three owner-scoped signals: broken relationships, unclassified documents, and low-confidence metadata. Each row links straight to the place where it can be fixed.

## How it works

- **Schema.** Migration `supabase/migrations/071_dm_foundations.sql` created `document_views`, `document_relationships`, `classification_rules` and `metadata_field_definitions`, each with RLS and a nullable `org_id` reserved for the later multi-tenancy work. It extended the `audit_log` action-type list from 11 to 19 values; a boot/CI check fails loudly if the backend's audit action list drifts from the database constraint. Later migrations added the extraction-model setting (`072`), embedding provider settings (`073`), typed view columns (`074`) and a relationship idempotency index (`075`).
- **Extraction.** Metadata extraction became a caller of the shared structured-output path (`backend/app/services/forced_emit.py`). The old OpenAI JSON-mode path was kept as a reversible `legacy` mode. User edits are stamped `_source='user'`, and the re-extraction guard (today in `backend/app/services/ingest_enrich.py`) preserves them.
- **Embeddings.** `backend/app/services/embedding_service.py` routes chunk and query embedding to the same configured provider and model; `backend/app/services/reembed_service.py` runs the background re-embed.
- **View compiler.** `backend/app/services/view_filter_compiler.py` compiles a closed registry of operators and fields into a parameterized `metadata @> $1::jsonb` query. There is no free-text query language for end users.
- **One shared read path per feature.** `backend/app/services/document_view_resolver.py` (views) and `backend/app/services/document_relationship_service.py` (relationships) are used by both the REST routes (`backend/app/api/document_views.py`, `backend/app/api/document_relationships.py`) and the agent tools in `backend/app/services/tool_dispatcher.py`. Keeping one copy means the access check cannot drift between chat and UI.
- **Classification.** `backend/app/services/classification_matcher.py` and `classification_rule_service.py` evaluate own and shared enabled rules first-match-wins and write a single `metadata._classification` suggestion. Rules are authored through `backend/app/api/classification_rules.py` and `frontend/src/components/classification/RuleBuilderPanel.tsx`.
- **Governance.** `backend/app/api/document_governance.py` reads the existing tables only. It added no migration and no write path.
- **Frontend.** `frontend/src/components/metadata/DocumentDetailPanel.tsx`, `ConfidenceChip.tsx`, `frontend/src/components/relationships/RelationshipsSection.tsx`, `frontend/src/components/ingestion/FilterBar.tsx` and `ViewsGroup.tsx`.

## Key decisions

- **Metadata-driven Tier A, not a full vault.** Syrel adopted metadata, relationships and classification basics and rejected object types, classes and value lists.
- **Classification always suggests, never files silently.** Matching rules show what they would do; a person decides.
- **A closed filter registry, never a raw query language.** Letting end users write a free-form query language was treated as both an injection risk and a usability problem.
- **Share, don't fork, the access-checked read paths.** Each sensitive read lives in one module used by both the API and the agent.
- **Gemini-safe tool schemas.** Agent tool schemas avoid `anyOf`/`oneOf` and multi-type `type: [...]` arrays. A live test in Phase 115 found that one multi-type array broke all Gemini tool use.
- **No formal milestone audit.** Instead, every phase passed its own verify, security and validation pass, including live two-user leak tests on the agent-tool phases.
