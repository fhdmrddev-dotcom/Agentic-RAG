# v4.4 — Experts That Actually Work

> **Shipped:** 2026-09-29 (deployed to production the same day) · **Phases:** 265–269 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

v4.4 made Syrel's Experts work for a real client in a real org. Installing an Expert copies its knowledge into your own workspace, inviting one only ever adds to what a thread can do, spend is attributable per Expert, and a five-Expert starter library ships ready to install. Every claim was proven by a live run as a real user, not only by tests.

## Why this milestone existed

v4.3 shipped Experts as bundles, but they were not yet useful to a client:

- **The flagship Expert could not answer from its own documents.** The Financial Analyzer's report lived in a seed-only org and was never embedded. Folder sharing is org-scoped by design, so no real org could retrieve it (v4.3's one unmet requirement, PACK-05).
- **Inviting an Expert could take tools away.** A `restricted` Expert narrowed the thread's tool list, so a user could lose web search or code execution just by adding an Expert.
- **Costs and changes were silent.** Nothing said that an Expert needed a connection you lacked. Nothing said which of your documents a restricted Expert would ignore, or that the active Expert had changed. Spend could not be split by Expert.
- **Much of v4.3 was verified only by the people who built it.** The operator required that owed live checks and independent reviews come before any new build.

The tenancy question was settled by the operator at the start: an Expert's sample knowledge is **copied into each installing org** and embedded there. No cross-tenant read path is built.

## What shipped

- **v4.3 checked before building on it.** The owed browser checks for spend, tier refusals, authoring and born-for skills were run live. Five v4.3 phases and the audit-time fix commits got independent reviews, and every finding received a written verdict.
- **Install an Expert, get its knowledge in your org.** An org admin presses Install. The Expert's sample documents are copied into that org's Library, ingested and embedded there. Re-installing creates no duplicates, and one org can never retrieve another org's copy. The Financial Analyzer now answers a revenue question by citing $124.5 million and +18.2% from the org's own copy.
- **An Expert only adds.** A thread with an Expert keeps every tool it had without one, plus the Expert's own skills and connections.
- **Honest requirements.** An Expert that needs a connection you have not set up says "Requires <Service> — not connected" on its card and in the invite dialog, and offers to connect it, rather than failing mid-run.
- **Visible changes.** Swapping or removing the active Expert writes a transcript event that says what the next turn will and will not use. The event survives reload.
- **Ask a second Expert.** From a thread, you can open a new thread scoped to a different Expert. It carries a handoff summary of the first, and each thread keeps one active Expert.
- **The cost of "restricted", stated up front.** Inviting a restricted Expert says which of the thread's documents it will not read, before the first run.
- **Spend per Expert.** `/admin/spend` groups and filters token and USD totals by Expert. Runs with no Expert get their own line.
- **Change a thread's folder scope mid-conversation.** A composer chip changes the folder scope. A transcript event records the change, and retrieval uses the new scope from the next turn.
- **A five-Expert starter library.** Financial Analyzer, Contract Reviewer, HR Policy Advisor, Operations Analyst and Security & Compliance. Each installs through the same path, and each has a recorded live conversation that cites its own corpus and refuses an out-of-scope question.

## How it works

- **Verification first (265).** No product build. Migration `194_org_plan_columns_not_client_writable.sql` came out of this phase's tier testing.
- **Per-org install (266).** Migration `195_expert_installs_and_seed_retirement.sql` adds `expert_installs` and retires the old seed-org path. Migration `196_documents_dedup_idx_org_scoped.sql` makes document dedup org-scoped, so two orgs can hold the same file. Each Expert's sample documents ship as repo data and are read by `backend/app/services/expert_corpus.py`. `backend/app/services/expert_install_service.py` claims the install, creates the folder, and mints documents into the **one existing ingest path**. It also derives an install state (Installing → Ready → Install failed). Routes are `POST /experts/{id}/install` and `GET /experts/installs` in `backend/app/api/experts.py`. Installing requires the `experts:manage` permission from v4.3.
- **Additive scope (267).** The Expert no longer computes a tool list. `run_producer` passes the Expert's skills and connections to the agent loop as neutral data, which unions them with the normal set. `backend/app/services/expert_scope.py` holds the folder rules: `restricted` means the Expert's folders only; `biased` means the thread's folder plus the Expert's. `expert_service.connection_states` is the single "is it connected" rule behind the card, modal and invite dialog. Transcript events (`expert_changed`, `expert_handoff`) are allow-listed in `backend/app/models/message.py`. The UI lives in `frontend/src/components/chat/InviteExpertDialog.tsx`, `ScopeLedger.tsx` and the catalog components.
- **Spend and scope (268).** Migration `197_runs_expert_attribution.sql` adds `runs.expert_id` / `expert_attributed`, stamped once at run insert, with sub-agent runs copying the parent's value. `backend/app/db/rates.py` uses one per-root query that prices each row and rolls up sub-agents, plus a bound `expert` filter. A `scope_changed` event and the thread PATCH (`folder_id` / `clear_folder`) commit in one transaction. A scope-effect preview route backs the composer `ScopeChip` / `ScopePicker`.
- **Starter library (269).** Migration `198_starter_expert_library.sql` seeds five org-portable Expert rows over synthetic sample corpora. A fence test proves there is no Expert-specific install code. A live run found a sibling-folder leak in `query_documents` (`BUG-260929-01`), which was fixed at `464ec8354` before the fifth Expert was promoted.

## Key decisions

- **Per-org provisioning, not shared cross-tenant knowledge.** Settles v4.3's open tenancy question (`SEED-304`).
- **Install is explicit and needs `experts:manage`** (D-266-01/02). Knowledge reaches an org only when someone presses Install.
- **An Expert stops computing a tool list** (D-267-01). The old `tool_floor_enabled` column is kept but no longer read, and its studio toggle was removed (D-267-02).
- **One active Expert per thread stays the rule.** "Ask a second Expert" opens a new thread instead.
- **Expert attribution is a column, not a second cost formula.** The token→USD conversion still has one home.
- **Starter library: five business-function Experts with verifiable cited figures** (D-269-01/02). An Expert without a live transcript is held back, and Security & Compliance was held until the leak fix.
- **Tiers stay operator-assigned** (D-269-P1). The starter library is visible to enterprise-tier orgs. A raw signup org has no tier and sees the tier-refusal sentence, not a blank page.

## Gaps and deferred work

- **Handoff across providers.** The handoff summariser can fail on 6 of 8 providers because some provider adapters drop its instructions (`SEED-327`). Eight review warnings were deferred to `SEED-328`.
- **Not driven live:** the "invite blocked while still installing" state, the not-installed view for non-managers, and a naturally reached paused-for-budget run (proven only with a seeded pause and unit and real-Postgres tests).
- **Expert attribution outside chat:** only the chat send path sets `expert_id`. Eval paths fall back to an older org guess.
- **New signup orgs have no tier**, so they cannot see the starter library until an operator assigns one (`SEED-325`).
- **Operator smoke test in production was still owed** at close: install an Expert in an enterprise org, run sandbox code in a new chat, and confirm the embedding key.
- **Verification mode.** `MILESTONES.md` records 265–269 as self-verified, because no separate reviewer was available by the close. The archived roadmap, however, notes that Phase 268 did get an outside review with no blocking findings. The two records differ on that one phase.
- **Records disagree:** the v4.4 audit file says "Nothing deployed" because it was written before the deploy, while `MILESTONES.md`, `STATE.md` and the production branch show a 2026-09-29 deploy. The audit also lists eight requirement checkboxes as stale, though the phases passed.
- **Records disagree on scope:** an early brief described this milestone as phases 265–268. The roadmap, audit and `MILESTONES.md` all include Phase 269, the starter library.
