# v3.4 — Multi-Tenancy & Org Access

> **Shipped:** 2026-07-22 · **Phases:** 160–168 · **Product:** Syrel (formerly Agentic RAG) · **Doc status:** DRAFT — generated 2026-10-04 from planning records; verify before publishing

## In one sentence

Syrel stopped being a per-user application and became an organisation-aware platform, where every
row of data belongs to an organisation and the database itself refuses to show one organisation's
data to another.

## Why this milestone existed

Before v3.4, every user was effectively an island. Data separation was real but fragile: the backend
connected to the database with a privileged "service role" that bypassed the database's own row-level
security, and the actual per-user boundary was roughly 253 hand-written `user_id` filters spread
across 32 backend files. One forgotten filter would have been a leak.

To sell Syrel to teams and companies (a co-tenant SaaS by default, with dedicated installs for
enterprises that need full isolation), the product needed three things it did not have:

- an organisation / department / role model,
- row-level security that is actually *enforced* on every request, not just declared, and
- the human-facing surfaces for it — switching organisations, inviting people, single sign-on.

The planning records call this "the load-bearing one-way RLS door": once data is org-scoped and the
database enforces it, there is no going back, so it had to be done carefully and in one atomic step.

## What shipped

- **Every user got a personal organisation, silently.** Existing users were moved into their own
  org (with a default department and org-admin role) without anything breaking; new sign-ups get one
  automatically.
- **The database enforces org isolation.** Membership-based row-level security now governs the
  user-facing tables, and request handlers talk to the database *as the signed-in user*, so a missing
  filter in code no longer means a leak.
- **Search and retrieval are org- and folder-aware.** Knowledge-base search, keyword search and skill
  matching only return content the asking user may see, including folder-level sharing rules.
- **"Global" became two clear ideas.** The old `is_global` flag was split into *shared with my
  organisation* (`is_org_shared`) and *platform content visible to everyone* (`is_system_global`),
  the latter settable only by migrations. Built-in content such as the skill-creator skill stays
  visible to all organisations.
- **An org switcher and a profile menu.** People in more than one organisation can switch between
  them from a profile menu in the sidebar footer, which also holds identity, role badge, theme and
  sign-out.
- **An org-admin console.** Org admins get a shell with Members, Audit, Settings, Invitations & Roles
  and SSO tabs (Subscription and Retention shown as honest "coming soon" placeholders at ship time).
- **Invitations.** Org admins invite people by email or shareable link, choose Member or Org-admin,
  and can resend or revoke. The invite landing page handles sign-in, sign-up, expired, revoked and
  already-a-member cases.
- **Role-based feature visibility.** The operator's per-feature visibility switch gained a third
  audience — "By role" — so a feature can be turned on for specific roles only.
- **A personal default model.** Users can pick their own default chat model from the set the
  operator/org allows, and the picker shows a lock when the operator has fixed the model.
- **SAML single sign-on.** Org admins can register a SAML 2.0 identity provider; sign-in becomes
  identifier-first (email → route to the company's IdP or reveal the password field), and first-time
  SSO users are added to the org automatically. Password sign-in always remains as a fallback.

## How it works

- **Schema (migration `104_org_dept_role_schema.sql`).** Eight membership-keyed tables (organisations,
  departments, org members, roles/permissions catalog and related), a seeded four-tier permission
  catalog, and a `current_user_org_ids()` `SECURITY DEFINER` helper. The helper exists to break
  infinite policy recursion (Postgres error 42P17) — every table's policy calls it instead of
  querying `org_members` inline.
- **Backfill (migrations 105–107).** `105_personal_org_backfill.sql` provisions personal orgs and
  backfills `org_id` across 35 tables in batched, idempotent waves before flipping them NOT NULL;
  `106_org_id_autofill_trigger.sql` fills `org_id` on inserts that omit it; `107` denormalises
  `org_id` onto the two pgvector hot tables (`document_chunks`, `skill_embeddings`) with a btree
  index so RLS does not slow vector search.
- **Enforced RLS (migrations 108–110).** `108_rls_membership_rewrite.sql` rewrites policies to
  membership predicates; `109` keeps platform/system content universally visible and blocks users
  from self-setting the system badge; `110_secdef_org_scope_audit.sql` puts an explicit org predicate
  inside the four retrieval/sharing `SECURITY DEFINER` functions and pins their `search_path`.
- **The client swap.** `backend/app/dependencies.py` provides `get_user_supabase` (per-request
  client carrying the user's JWT) and `get_user_pg_connection` (asyncpg with
  `SET LOCAL ROLE authenticated` plus JWT claims — the step that actually turns RLS on for raw SQL).
  Background writers that must bypass RLS use `get_service_role_supabase(org_id)`, which refuses to
  run without an org. The old `user_id` filters were deliberately **kept** as a second layer.
- **Refactor first.** Before the client swap, the chat run "producer" was extracted from
  `backend/app/api/threads.py` (2,444 → 1,214 lines) into `backend/app/services/run_producer.py`
  with one shared finaliser, so the risky change landed on a smaller file. Chat behaviour was proven
  unchanged across the full native provider roster.
- **Rename (migration `111_is_global_retirement_rename.sql`).** A value-preserving column rename
  (never drop-and-add) split `is_global` per table. Today `is_global` survives in `backend/app` only
  as Python's unrelated `ipaddress.is_global`.
- **Org routes.** `backend/app/api/org.py` serves `/org/me`, `/org/members`, `/org/audit`, the
  invitation endpoints (send / list / resend / revoke / accept) and the SSO provider endpoints. The
  active org arrives in an `X-Org-Id` header that the server validates against membership; admin
  actions are gated by the `current_user_has_permission` helper from migration 104.
- **Invitations** store only a hashed token; acceptance is idempotent (advisory lock +
  `ON CONFLICT DO NOTHING`) so two simultaneous first logins converge on one membership. Email
  delivery is env-switched with a log-only default.
- **SSO** relies on Supabase/GoTrue's native SAML service provider (no SAML parser of our own); a
  proxy talks to either Supabase Cloud's Management API or self-hosted GoTrue. `113_sso_configs_firming.sql`
  adds the approval gate and domain uniqueness. Sign-in fails *open* to the password field if
  domain routing errors, so no one is locked out.
- **Frontend.** `frontend/src/providers/OrgProvider.tsx` (mounted outside the streaming provider so an
  org switch tears down streams safely), `frontend/src/components/org/` (`OrgAdminShell`, `OrgBand`,
  `OrgMembersTab`, `OrgAuditTab`, `InvitationsTab`, `InviteMemberDialog`, `SsoTab`),
  `frontend/src/components/layout/ProfileMenu.tsx`, `frontend/src/pages/AcceptInvitePage.tsx`.
- **Proof.** `backend/tests/integration/test_v3_4_org_isolation.py` — the two-org exit gate covering
  tables, both database paths, the retrieval functions and header spoofing.

## Key decisions

- **Co-tenant by default, isolation by deployment for enterprise** (ADR `D-v3.4-01`). One codebase,
  one image; the four tiers (solo-local, small-team VPS, medium SaaS, enterprise/on-prem) differ only
  by environment variables, never by a code fork.
- **Policies and the client swap ship together.** Rewriting RLS without switching to per-request
  user clients would have been inert, because the service role bypasses RLS. Phase 163 did both.
- **Keep the old `user_id` filters** as belt-and-braces this milestone; their removal belongs to a
  later hardening pass.
- **Rename, never drop.** `is_global` was retired with value-preserving renames so no sharing state
  was lost.
- **Refactor before risk.** The `threads.py` producer extraction was promoted to its own phase so the
  security change landed on a paid-down file.
- **Use the platform's SAML.** Supabase/GoTrue owns SAML parsing; the dependency on a Python SAML
  library was dropped.
- **Departments ship in the schema but not in the product.** One schema serves a 5-person team and a
  2,000-person org; department-level administration was deferred.

- **STRETCH phases 169–173 were deferred, not built** (`.planning/v3.4-STRETCH-CARRYFORWARD.md`):

  cross-user document sharing ships, because that is when its risk becomes reachable.
