## 105 — Scheduled / Recurring Triggers + Budget Caps (SCHED-01)

- **Delivers:** a published workflow can run on a schedule (frequency / time / timezone) and fires
  automatically — but **only behind a spend ceiling**. REJECT-semantics per-run token ceiling plus a
  per-workflow daily cap; a run that would exceed the cap is refused, not silently overrun. Operators
  can see and cancel active schedules.
- **User value:** this is the difference between an automation product and a form. Every competitor
  in the space assumes "run this every Monday". A workflow that must be launched by hand is a tool
  the user has to remember to use.
- **Why deferred (2026-06):** the roadmap gave it a **hard, named prerequisite** — *"ship only if
  CORE lands clean AND the spend meter exists"*. It is the one v2.9 stretch item with a blocking
  dependency rather than a budget-based deferral.
- **Depends on:** Phase 104 (shipped) + the gateway spend meter.

### What changed since — measured 2026-08-10

**The prerequisite is now half-met, and that is the important news.** Token accounting exists —
`app_settings.token_capture_enabled`, and `prompt_tokens`/`total_tokens` flow through
`provider_gateway/openai_compat.py`, `api/admin.py` and `main.py`. What does **not** exist is
enforcement: a grep for `daily_cap` / `token_ceiling` / reject-on-exceed across `backend/app` returns
nothing. So the **meter** is roughly there and the **brake** is not.

**A second dependency appeared that the June text could not have known about: [[SEED-140]] — a user
cannot stop a running workflow.** Unattended scheduled execution must not ship before a human can
halt a run. Treat SEED-140 as a hard prerequisite of 105, alongside the spend cap.

Also relevant: `runs:active`, `runs_by_thread:{}` and the `cancelled` run status already exist
(Redis key conventions + `run_lifecycle.py`), so the run-control substrate 105 needs is largely
built.

### Re-open trigger

Revive when **both** are true: (1) a user asks for recurring/unattended execution — or the
connections milestone ships outbound writes, which makes "every Monday" the obvious next ask; **and**
(2) SEED-140's stop control has shipped. Do not ship the schedule before the brake and the stop.

### Build-approach note

- **Budget enforcement is the phase, scheduling is the easy half.** Cron is a solved problem; a
  REJECT-semantics ceiling that a run cannot silently overrun is not. Build the cap first and prove
  it rejects, then add the trigger.
- **Disabled-by-default, no schedule without a budget** — the original success criterion, and it
  should survive revival verbatim. It is the same fail-closed instinct the `live_connectors` gate
  uses.
- Consider a per-user active-schedule cap (the June text raised it and never resolved it).

## 106 — Citation-Traceable Grid Renderer (GRID-01)

- **Delivers:** risk register / RTM / stakeholder matrix rendered as a grid (rows = items,
  cols = attributes), backed by `llm_batch_agents` + retrieval, where **every cell carries a citation
  to its source span and uncited cells are visibly flagged**.
- **User value:** the flagship shape of this product's output. A cited grid is the artefact a
  compliance or PM audience actually wants, and per-cell citation is what makes it defensible.
- **Why deferred (2026-06):** STRETCH behind CORE; no blocking dependency recorded.
- **Depends on:** Phase 104 (shipped).

### What changed since — measured 2026-08-10

Much of the substrate now exists and this phase should be **re-scoped rather than revived as
written**: starter workflows already produce a "Risk Register" and a "Compliance Gap Report" with
per-cell grounding language ("leave a cell null where the sources do not support it"), inline
citations shipped in v3.3, and `llm_emit` + `docxtpl` produce real files.

So the gap is narrower and sharper than June assumed: **the grid is produced as a FILE, not as a
surface you can read and click.** Combine with [[SEED-148]] — a produced file is not shown anywhere
on the run surface today — because there is no point rendering a citation-traceable grid on a surface
that does not yet show outputs at all. **148 is a prerequisite, not a sibling.**

### Re-open trigger

Revive when SEED-148 has shipped (outputs are visible), AND a user asks to read or verify a matrix
in-app rather than downloading it. Also fires if per-cell citation is ever needed for an audit
conversation.

### Build-approach note

Do not build a new renderer first. Establish where a produced artefact is *displayed* (SEED-148),
then ask whether the grid is a preview mode of that surface. Note `CsvTablePreview.tsx` already
exists in the panel and may be the seam.

## 107 — Per-Run Provenance Receipt View (GOV-02)

- **Delivers:** a read-only per-run receipt surfacing the already-recorded chain —
  `definition@version` + INSERT-only run log + gate verdicts + cited sources, in the EU AI Act
  Art. 12 traceability shape. **Reconstructs from persisted data; no new runtime writes, no
  migration.**
- **User value:** the compliance artefact. For a regulated buyer, "show me what this run did and on
  what evidence" is a purchase condition, not a nice-to-have.
- **Why deferred (2026-06):** STRETCH. The roadmap's own note: *"governance is mostly surfacing, not
  building — the chain is already recorded."*
- **Depends on:** Phase 104 (shipped).

### What changed since — measured 2026-08-10

**This is the most nearly-satisfied of the four, and it may now be a small phase.** Since June:
`harness_audit` and `workflow_phases` record the chain; v3.3's Control Room shipped a two-ledger
audit browser with recorded-CSV export; v3.6's Phase 188 shipped a run receipt in chat and a phase
spine in the panel; v3.6's Phase 185 shipped governance verdicts and the "must prove it" vocabulary.

**Re-derive before planning:** the honest question is no longer "build a receipt" but "how much of
the receipt already exists across the Control Room audit tab, the run surface and the chat receipt —
and is what's missing a view, or just a print/export?" A grep for `provenance` under
`components/workflows/` finds it only as a *definition field*, not a rendered receipt, so the
consolidated view itself does not exist.

### Re-open trigger

Revive on the first customer/auditor request for a per-run evidence export, or when a compliance
question cannot be answered from the existing Control Room ledger. Cheap enough that it can also ride
along as a tail item in a governance-adjacent milestone.

### Build-approach note

**Assume it is an assembly job, not a build.** No migration was permitted by the original criteria
and none should be needed now. If a plan proposes new runtime writes, that is a signal the scope has
drifted.

## 108 — Plugin Contract Lock: `phase_type` + `file_preview` (PLUG-01)

- **Delivers:** lock the first two Plugin Contract types on real flagship telemetry — the
  `phase_type` contract via a first-class `fill_template` phase plugin, and the `file_preview`
  contract via an office/PPTX in-panel preview reference plugin (closing the SEED-037 office-viewer
  gap). The `data_source` / `secrets_adapter` seams are **named but explicitly NOT locked**.
- **Why deferred (2026-06):** STRETCH per D-v2.8-01 — the KB-grounded flagship needed zero plugins to
  ship, and locking a contract without real telemetry is guesswork.
- **Depends on:** Phase 104 (shipped).

### What changed since — measured 2026-08-10 · ⚠ THE BIGGEST DRIFT OF THE FOUR

**Half of this phase shipped, but NOT as a plugin — which changes the question rather than answering
it.**

- **`fill_template` effectively shipped as a first-class phase type.** Phase 101 (TMPL-02, D-04/D-05)
  admitted `render_template` to a harness FILL phase (`phase_types.py:332-347`). So the capability
  exists — as a **built-in executor**, not as a plugin against a locked contract.
- **This now collides with a red line drawn after v2.9.** v3.6's **D-14** held that there are exactly
  **7 harness executors** at close, same as at open, and that the canvas must never become a second
  runtime. A plugin contract for `phase_type` is, by construction, a way to add executors. **Anyone
  reviving 108 must first establish whether a `phase_type` plugin contract is still wanted at all**,
  or whether the project has effectively decided against it by building executors directly.
- **`file_preview` is genuinely still open.** Measured: `panel/FilePreview.tsx` handles code and text
  only (`py`, `ts`, `tsx`, `js`, `json`, `sh`, `sql`, `yml`), plus a separate `CsvTablePreview.tsx`.
  **No `.docx` / `.pptx` / `.xlsx` and no PDF.** SEED-037's office-viewer gap is real and unclosed.

### Re-open trigger

Split the phase; the two halves no longer share a trigger:

- **`file_preview` half:** revive when a user cannot read a produced `.docx`/`.pptx` in-app — which
  SEED-148 will make visible the moment outputs are surfaced. This half is a straightforward gap.
- **`phase_type` half:** do **not** revive on a schedule. Revive only if a deliberate decision is
  taken to allow third-party or user-authored executors, which is a milestone-level decision against
  D-14, not a stretch phase.

### Build-approach note

Treat the two contracts as unrelated work that happens to share a phase number. Bundling them was
correct in June and is not correct now.
