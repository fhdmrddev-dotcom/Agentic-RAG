<objective>
Close SEED-102: a name-collision in `_handle_load_skill` currently lets a user-owned
skill row silently shadow a same-named `is_system` built-in (e.g. `skill-creator`) at
runtime. The resolver sorts `.order("is_global")` ascending, so the owned row (is_global
False) sorts first and `skill_row[0]` picks it — the agent then executes the user's
unvetted content instead of the protected built-in. Any user can trigger this via the
Create-Skill dialog, the agent's `save_skill` tool, or an imported ZIP with a colliding
`name:`.

Fix (SEED-102 candidate #1 — the tie-break reversal): reverse the resolution ordering so
an `is_system` row (and, on a further tie, a global row) wins over an owned row — a clear
precedence hierarchy of **system > global > owned** on a name collision. Add a genuine
regression test proving the built-in wins.

Purpose: restore the trust boundary — a protected built-in must not be shadowable by an
owned same-named row for that user's own sessions.
Output: a two-line resolver change + a refreshed comment in `tool_dispatcher.py`, plus a
new regression test that fails against the old tie-break and passes against the new one.

Scope guardrails (from the task constraints):
- Touch ONLY `_handle_load_skill`'s resolution order (`tool_dispatcher.py`).
- Do NOT touch `create_skill` / `_handle_save_skill` / `import_skill` (that is candidate
  fix #2 — explicitly out of scope).
- Do NOT touch the other `.or_(...)` skill queries at lines ~749/857/869/963/975 (they are
  save/lint paths, not resolution).
</objective>
