<decision_the_matching_rule>
**Exact string equality against the presented approve label**, on the value the engine has already
`.strip()`ed at `:1136`. Not `.casefold()`, not a prefix, not a substring.

Reasoning, recorded because the plan is asked to justify it:

1. **Case-insensitive matching is strictly *more* permissive, not more careful.** Every string it
   would newly accept (`"approve and run this step"`, `"APPROVE AND RUN THIS STEP"`) is a string no
   button can ever produce — the click path resolves `choices[0]` to the exact literal, and the
   typed path is the attack surface, not the intended path. Widening the allow-list to serve a
   phrasing nobody legitimately needs is pure surface for zero benefit.
2. **Fail-closed is the tie-breaker, and the two errors are not symmetric.** Refusing an oddly-cased
   approval fails the run — recoverable, the person re-runs and clicks the button. Accepting an
   oddly-cased string runs the irreversible action. When in doubt, do not proceed.
3. **The codebase already reasons this way.** `:1123-1127`: *"a payload we could not read is not
   consent, and the only safe reading of 'we don't know what they said' is 'do not run it'."* An
   unrecognised answer is the identical epistemic situation. Quote this line in the code comment —
   it is the strongest justification available and it is the codebase's own words.

The `.strip()` at `:1136` is pre-existing and is NOT widened here — trailing whitespace on the exact
label still proceeds, exactly as it does today. Everything past that is exact.

The rule is pinned by a test: `"approve and run this step"` (lowercase) is in the falsification
table and MUST route to `fail_run`.
