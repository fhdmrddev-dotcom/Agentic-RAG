<the_decision_this_plan_takes>
## `disabled` → `aria-disabled`: TAKEN. The refused rows become focusable.

`StepTypePicker.tsx:244` renders refused rows with the NATIVE `disabled` attribute, and a natively
disabled button cannot receive focus. That contradicts the component's own stated design intent
(docblock ≈ :30-35): *"an option that vanishes teaches nothing, and an option greyed out mutely is
worse — the author is left to guess what they did wrong. So every row the definition's shape
declines is still rendered, disabled, with its sentence visible in the DOM beside it … and wired to
the row through `aria-describedby`."* The entire point is that the author LEARNS WHY — and today a
keyboard or screen-reader user can never reach the row, so they never hear the reason. WAI-ARIA APG
for `menu` says disabled items SHOULD remain focusable precisely so they stay discoverable.

**So: drop `disabled={refused}`, keep `aria-disabled={refused ? "true" : undefined}`, keep the row
in the roving order, and guard activation in the handler.**

⚠ **THE CONSEQUENCE, STATED HONESTLY: the activation guard becomes LOAD-BEARING.** Today the browser
swallows a click on a natively disabled button, so `onClick`'s `if (refused) return` has never had to
work — the shipped case *"does NOT call onChoose when a refused row is clicked"* uses
`user.click`, which does not even dispatch on a disabled button, and React's own
`shouldPreventMouseEvent` filters `onClick` for disabled buttons on top of that. After this change a
real mouse user can physically press a refused row and a real keyboard user can press `Enter`/`Space`
on one, and the ONLY thing stopping the choice is that `return`. It therefore needs its own tests
with a POSITIVE CONTROL proving the event genuinely reaches the handler now (otherwise "onChoose was
not called" is satisfied by a harness where nothing was clicked at all — the same vacuity trap that
made the shipped case green while the row was unreachable).

**Three shipped assertions must be REWRITTEN (never deleted) to the new claim**, in
`StepTypePicker.test.tsx` section 2: the `expect(row).toBeDisabled()` inside *"disables every choice
past the deliverable…"* becomes *"still `aria-disabled`, and now FOCUSABLE"*
(`not.toBeDisabled()` + `toHaveAttribute("tabindex")`). Every `not.toBeDisabled()` elsewhere stays
true unchanged. `jest-dom`'s `toBeDisabled` does NOT consult `aria-disabled`, which is exactly why
these three go RED and must be re-stated rather than left to pass by accident.

**A refused row that can hold focus MUST show that it holds it.** Refused rows carry only
`cursor-not-allowed opacity-[0.42]` today and no focus style at all; enabled rows carry
`focus-visible:bg-accent focus-visible:outline-none`. Give refused rows their own visible indicator
using EXISTING tokens only (`accent` / `ring` / `border`) — WCAG 2.4.7, and the colour budget in the
docblock spends no new hue.
</the_decision_this_plan_takes>

<the_two_traps_this_plan_is_designed_around>
## 1. `row.scrollIntoView()` CHEATS — measured, in this exact component, yesterday.

`scrollIntoView` walks up and scrolls the **nearest scrollable ancestor**, and `.react-flow` is
`overflow: hidden` — *programmatically* scrollable even though it has no scrollbar and no user
gesture can move it. Yesterday's probe used it and read a FALSE 7/7; the tell was that the
falsification control refused to swing.

**The same trap is live in `element.focus()`**: the default focus action scrolls the element into
view by walking the same ancestors. So this plan uses `focus({ preventScroll: true })` and then
scrolls the PANEL and only the panel, by assigning `panel.scrollTop` to a number computed from
`getBoundingClientRect()` deltas. `scrollIntoView` appears nowhere in the fix and nowhere in the
probe, and the driven acceptance fences all four ancestors at `0,0`.

⚠ `row.offsetTop` is NOT panel-relative here — the panel is `position: static`, so `offsetParent`
is the `absolute` wrapper in `PlaneEditingLayer` (and something else again at the `canvas-empty`
mount site, `WorkflowCanvas.tsx:1147`). Compute the row's top as
`row.getBoundingClientRect().top - panel.getBoundingClientRect().top + panel.scrollTop`. Do not add
`position: relative` to the panel to make `offsetTop` work — that changes the stacking context the
clipping fix was measured against.

## 2. Synthetic events lie about trust.

jsdom applies no CSS, computes no overflow clipping, and `dispatchEvent` bypasses hit-testing —
which is why this suite was green while row 7 was unreachable. jsdom IS adequate for the roving
half (focus and `document.activeElement` are real in jsdom), so those cases are unit tests. The
SCROLL half and the reachability half are not: drive real keys via Chrome MCP `press_key`.
`take_screenshot` times out in this estate — read DOM state with `evaluate_script`.

## 3. There are TWO mount sites for this picker, not one.

`PlaneEditingLayer.tsx:321` (the `＋` doors, via `ViewportPortal`) and `WorkflowCanvas.tsx:1150`
(the `canvas-add-first-step` empty-state door). **This is the argument for the self-contained
focus-return design below:** capturing `document.activeElement` at open time covers both openers for
free, whereas passing an opener ref down from `PlaneEditingLayer` would cover one and strand the
other. Neither caller is modified by this plan.
</the_two_traps_this_plan_is_designed_around>

```ts
// frontend/src/components/workflows/editAffordance.ts  (NEW exports)

/**
 * The APG VERTICAL-`menu` key map. Returns the next roving index, or `null` when the key
 * is not one this pattern owns — and that `null` is what keeps `Escape` working.
 */
export function nextRovingIndex(key: string, index: number, count: number): number | null

export interface RevealInput {
  /** The panel's current `scrollTop`. */
  scrollTop: number
  /** The panel's `clientHeight`. `0` (jsdom, first paint) means DO NOT MOVE. */
  clientHeight: number
  /** The row's top, ALREADY relative to the panel's scrolled content box. */
  rowTop: number
  /** The row's height. */
  rowHeight: number
}

/** The panel's NEXT `scrollTop`. Never an ancestor's, never NaN, never negative. */
export function scrollTopToReveal(input: RevealInput): number
```

The arithmetic, stated once so the executor implements it rather than re-derives it:

```
nextRovingIndex(key, index, count):
  if !Number.isFinite(index) || !Number.isInteger(count) || count <= 0 -> null
  last = count - 1
  i    = clamp(Math.trunc(index), 0, last)
  "ArrowDown" -> i === last ? 0 : i + 1        // WRAPS
  "ArrowUp"   -> i === 0 ? last : i - 1        // WRAPS
  "Home"      -> 0
  "End"       -> last
  anything else -> null                        // Escape, Enter, " ", Tab, ArrowLeft, ArrowRight

scrollTopToReveal({ scrollTop, clientHeight, rowTop, rowHeight }):
  if any of the four is non-finite -> Number.isFinite(scrollTop) ? Math.max(0, scrollTop) : 0
  if clientHeight <= 0             -> Math.max(0, scrollTop)      // unmeasured: never move
  top    = rowTop
  bottom = rowTop + Math.max(rowHeight, 0)
  if top < scrollTop                        -> Math.max(0, top)                    // reveal upward
  if bottom > scrollTop + clientHeight      -> Math.max(0, bottom - clientHeight)  // reveal downward
  otherwise                                 -> Math.max(0, scrollTop)              // already visible
```

⚠ **`ArrowLeft` / `ArrowRight` return `null` DELIBERATELY.** `ExternalActionSection` maps them
because it is a `radiogroup`, where APG defines Right/Left as synonyms of Down/Up. This is a
vertical `menu`, where Right/Left belong to submenus and menubars — neither of which exists here.
The two ARIA patterns differ, and the difference is load-bearing enough to be the driven control.

The component's own shape (Task 2), for reference — no code, the property list:

- `activeIndex` state + an `itemRefs` array; `tabIndex={index === activeIndex ? 0 : -1}`.
- ONE `onKeyDown` on the `role="menu"` container (events from the rows bubble to it) — not one
  handler per row. It calls `nextRovingIndex`; on `null` it returns WITHOUT touching the event, so
  `Escape` reaches the shipped `window` listener untouched and `Enter`/`Space` keep the button's
  native activation. On a number it calls `preventDefault()` (arrows must not scroll anything
  behind the menu), sets `activeIndex`, focuses that row with `{ preventScroll: true }`, then
  assigns the panel's `scrollTop` from `scrollTopToReveal`.
- An `open`-gated effect captures `document.activeElement` as the opener, resets `activeIndex` to
  `0` and focuses row 0 with `{ preventScroll: true }`. Its CLEANUP restores focus to the captured
  opener on the next animation frame, and ONLY IF the opener `isConnected` and
  `document.activeElement` is `null` or `document.body` — i.e. restore only when focus would
  otherwise be STRANDED, never stealing it from something the user deliberately pressed.
