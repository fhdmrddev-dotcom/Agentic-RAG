## Deviations from Plan

### 1. [Rule 1 — Bug] `Escape` left focus on `document.body`. Fifteen green jsdom cases could not see it.

- **Found during:** Task 3, by driving. The unit suite — including two dedicated
  focus-return cases — was green against the broken build.
- **Issue:** Measured across five samples out to 1000 ms, with the real `＋` still in the
  DOM and still the same node. **Instrumented rather than guessed:** `main.tsx` wraps the
  app in `<StrictMode>`, so React double-invokes the effect in dev, and the two captures
  read **`["canvas-insert-0", "step-type-choice-programmatic"]`** — the second "opener"
  being the picker's OWN first row, which the first invocation had just focused. That node
  is removed on unmount, so `isConnected` was false and the restore stood down.
- **Fix:** The capture rejects any candidate inside the panel and falls back to the
  previously captured opener. Plus a jsdom case that reproduces it.
- **⚠ The test needed fixing twice, and the second correction is the finding.** The first
  StrictMode case stayed GREEN against the exact pre-fix capture, because the harness
  toggled `open` on a mounted picker — and **React double-invokes on MOUNT, not on a
  dependency change**. Changing the harness to MOUNT/UNMOUNT (what both real callers do)
  made it go RED. A StrictMode wrapper alone proves nothing.
- **Commit:** `5562d669`

### 2. [Rule 1 — Bug] Three regressions of my own, each caught by a gate and fixed rather than absorbed

None were in the plan; all three were mine, measured against the pre-change baselines.

- **tsc 33 → 35.** Importing React's `KeyboardEvent` type under its own name SHADOWED the
  global DOM `KeyboardEvent` the shipped `window` Escape listener is typed against, so
  `addEventListener` matched no overload. Aliased to `ReactKeyboardEvent`.
- **eslint 5 → 7.** `setActiveIndex(0)` in the effect body tripped
  `react-hooks/set-state-in-effect` (moved to React's documented render-phase
  adjust-state-on-prop-change pattern), and a `role="menu"` owning a keydown handler tripped
  `jsx-a11y/interactive-supports-focus` (`tabIndex={-1}` on the container).
- **eslint 5 → 6.** Clearing `openerRef` in the render phase tripped `react-hooks/refs`.
  Removed — and clearing it in the effect cleanup instead would have broken deviation 1's
  fix outright, since StrictMode's mount-cleanup-mount would wipe the opener before the
  second mount could fall back to it.
- **Commits:** `3b952784`, `5562d669`

### 3. [Rule 1 — Bug] The `scrollIntoView` source fence, written as the plan implies, forbids the fix from explaining itself

- **Issue:** `expect(source).not.toMatch(/scrollIntoView/)` went RED against the fix's OWN
  DOCBLOCK, which names the trap three times so the next author sees why the panel is
  scrolled by hand.
- **Fix:** The fence matches the CALL spelling (`/\.scrollIntoView\s*\(/`). Both the
  positive control AND a negative control (the prose form, asserted NOT to match) are in
  the same case, so the narrowing is measured rather than asserted. A fence that forbids
  explaining itself is a fence that gets deleted.
- **Commit:** `3b952784`

### 4. [Rule 1 — Bug] The prescribed CONTROL-2 restore did not restore, and the fault was the probe's

- **Issue:** The first driven run's leg (c) read as a failure of the fix: after clearing
  `p.style.maxHeight`, the panel stayed unbounded and row 7 stayed unreachable. React had
  set that `max-height` as an **inline** style, so clearing it removed React's own
  declaration and React does not re-apply it without a re-render.
- **Fix:** The probe captures the inline values first and restores by re-assigning
  `210.612px`. The control then swung `reaches → hit:null → reaches`.
- **Recorded because** a control that appears not to swing back has exactly the shape of a
  real regression, and this is the second consecutive session on this component in which a
  probe defect nearly read as a product verdict.

### 5. [Rule 2 — Critical] A second `toBeDisabled()` lived outside the file the plan named

The plan said "three shipped `toBeDisabled()` assertions … in `StepTypePicker.test.tsx`
section 2". **Measured, that file contains exactly ONE** (inside a loop over seven types).
A second lives in `WorkflowCanvas.editing.test.tsx:872` and was found by running the suite,
not by reading. Both were **REWRITTEN in place** to `not.toBeDisabled()` +
`toHaveAttribute("tabindex")`, never deleted; both sit inside existing `it()` blocks and
change no count.
