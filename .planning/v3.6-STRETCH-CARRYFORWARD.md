## 191 — Conditional Canvas Scale Hardening (SCALE-01)

- **Delivers:**
  - React Flow `onlyRenderVisibleElements` + node memoization, for canvases past ~100–150 nodes.
  - `elkjs` auto-layout — **only** if run-visualisation must depict `llm_batch_agents` fan-out as a
    branching layout rather than the linear spine.
  - Indexed org-scoped Workflows-list reads, at many-orgs × many-workflows scale.
- **User value:** the canvas stays responsive when a workflow or an org's workflow list gets large.
  Zero value below that threshold — and possibly negative, since virtualization adds a rendering
  code path that every future canvas phase then has to reason about.
- **Why deferred — the honest reason, which is NOT "we ran out of budget":** the phase was written
  from the start as *conditional*, in the ROADMAP's own words: **"ship ONLY if a real workflow or
  org fan-out exceeds the expected small scale."** The measured reality at close is that real
  workflows sit at **5–50 phases** against thresholds of **~100–150 nodes** — an order of magnitude
  of headroom. Building it now would be optimising a bottleneck nobody has hit, and would add a
  second render path to `WorkflowCanvas.tsx`, a file that took two dedicated refactor phases
  (188.1, 188.2) to get down to 1292 lines. **Deferring is the design decision, not the fallback.**
- **Depends on:** Phases 184 (editable canvas) + 188 (run observability) — both shipped, so 191 is
  unblocked and buildable the day its trigger fires.

### Re-open trigger (concrete — do not soften this into "when it feels slow")

Revive 191 when **any one** of the following is true and **measured**, not estimated:

1. **A real workflow definition exceeds 100 phases.** Mechanically checkable — and note the
   jsonb trap this project already paid for: `workflow_definitions.definition` holds a JSON
   **string scalar**, so `definition->'phases'` silently returns zero rows. The correct query is
   `((definition #>> '{}')::jsonb)->'phases'`, and `phase_type` lives inside `phase['config']`.
   ```sql
   SELECT id, name,
          jsonb_array_length(((definition #>> '{}')::jsonb)->'phases') AS phase_count
   FROM workflow_definitions
   ORDER BY phase_count DESC NULLS LAST
   LIMIT 5;
   ```
2. **An org's Workflows list read becomes slow** — a p95 over ~500 ms on the list endpoint, or an
   `EXPLAIN` showing a sequential scan on an org-scoped workflow query.
3. **Run-visualisation must depict branching fan-out.** Today the canvas is a LINEAR spine by
   design (D-14). If `llm_batch_agents` fan-out ever has to be drawn as a branching graph, that is
   the `elkjs` half of this phase and it arrives with its own design question, not just a perf one.
4. **An operator or user reports canvas lag** on a workflow they actually authored — the only
   trigger that does not need a threshold, because it is the outcome the thresholds proxy for.

### Build-approach note

- **Do NOT bundle all three deliverables.** They are independent and have different triggers:
  virtualization answers trigger 1/4, the index answers trigger 2, `elkjs` answers trigger 3. Ship
  only the half whose trigger actually fired — the ROADMAP scoped this phase conditionally, and
  reviving it unconditionally would discard the reason it was deferred.
- **Check the G-5 hot-file ledger first.** `WorkflowCanvas.tsx` sits at 1292 L after two extraction
  refactors; adding a virtualization path is a second render concern. Per G-5, audit before adding.
- **The D-14 red line still binds.** The canvas is a projection of `WorkflowDefinition`, never a
  second source of truth and never a second runtime. Virtualization must not introduce a node
  state that exists only in the renderer.
- **Layout stays out of the definition JSONB** (`canvasModel.ts:27`). If `elkjs` is adopted, its
  output is computed, not persisted — the same rule deterministic auto-layout already follows, and
  the reason OPEN-05's `workflow_layouts` side table was never built.
