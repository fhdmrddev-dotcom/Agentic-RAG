## 1. Header

v3.1 makes the project installable, configurable, and operable by an enterprise IT operator without dev help — the load-bearing prerequisite before the first paid co-tenant or on-prem customer ships under the hybrid SaaS posture (`D-PRD-02`). Three workstreams ship together. **(1) Admin shell** — a new role tier above users (super-admin / operator) with its own UI surface that consumes v2.6's `/admin/backpressure` JSON primitive (WORKER-LIFT-04, `D-PRD-08`) plus a `MODEL_CAPABILITIES` editor that closes `SEED-009` cleanly, a migration-state UI, an audit-log browser that finally surfaces v2.2 F-06's table (`PROJECT.md:100`, `audit_log` per `PROJECT.md:188`), an active-runs admin view backed by the `runs:active` ZSET, sandbox / Redis / Supabase health rendering, secrets management, and per-org observability primitives (stub data layer; v3.2 fills RBAC). **(2) Install wizard** — a UI-driven flow that turns `RECOVERED_VPS_Deployment_Guide.md` from a copy-paste runbook into a first-run experience handling env vars, secrets store binding, Supabase + Redis container provisioning, multi-worker preset selection (now valid post-v2.6 per `D-PRD-08`), TLS / Nginx / certbot config. **(3) Deployment presets** — Solo / Team / Enterprise tier shapes encoding scale defaults (workers count, AnyIO ceiling, Redis sizing, sandbox concurrency caps) plus single-Docker-compose and Helm chart packaging. Strategically, v3.1 ships after v3.0 Skill Studio because the eval-environment-as-headline-feature is what makes the operator UI worth selling; without v3.1, the v3.2 multi-tenancy milestone has nowhere to expose org-admin primitives, the v3.3 Open Platform has no UI to issue API keys from, and every paying customer's IT team has to hand-edit `.env` and SSH into a VPS to do routine ops — a story neither Glean (closed SaaS, vendor-dependent) nor M-Files (heavy IT setup, enterprise-only) can match.

## 3. Scope

**Theme A — Admin Shell + Operator Role Tier**
- New `operator_users` table mapping Supabase auth `user_id` to a role enum `('super_admin' | 'operator')`. Distinct from the per-org `org_admin` / `dept_admin` tier coming in v3.2 (which is RBAC inside an org); these are **system-level** roles that exist even in a single-org install (per SEED-012:62-66). Defaults: bootstrap super-admin via `BOOTSTRAP_SUPER_ADMIN_EMAIL` env var on first run. *Carries: SEED-012 §1, Q-v3.1-01.*
- New `/admin` route tree in the frontend (NOT a Settings tab — operator-only, separate sidebar surface per SEED-012:64). Existing 5-tab `frontend/src/pages/SettingsPage.tsx` (PROJECT.md:231, MILESTONES.md:231) stays user-level and untouched. *Carries: SEED-012 §1, project memory `project_settings_design_guidance.md`.*
- RLS policies on `operator_users` and all admin-only tables: only `super_admin` can write; `operator` has read-only on most surfaces, write on the operational ones (cancel run, restart sandbox, edit `model_capabilities_overrides`); regular users have NO read or write. *Carries: SEED-012 §fallback-principle.*

**Theme B — Backpressure & Health Dashboard**
- Admin UI rendering of v2.6's `GET /admin/backpressure` JSON (WORKER-LIFT-04 from v2.6 PRD §3 / §5) — AnyIO threadpool depth, Redis active-runs ZSET cardinality, asyncpg pool in-use, per-worker run count. Live-polling at 5s interval; sparklines per metric over last 15 min held client-side. *Carries: SEED-001 §scope step 4 (deferred from v2.6), SEED-012 §2, partial close of SEED-001's "backpressure dashboard" remnant.*
- Health surface rendering `GET /health` (`ARCHITECTURE.md:362`): Redis OK, Supabase OK, sandbox OK (extended in v3.1 to actually probe Docker daemon when `SANDBOX_ENABLED=true` per `CONCERNS.md:668`), LangSmith reachability. *Carries: SEED-012 §2.*
- Active-runs admin view backed by `runs:active` ZSET (`ARCHITECTURE.md:140`) + `runs` table — table view with thread / user / model / elapsed / status; "Kill" affordance hits `cancel_run` (`backend/app/api/runs.py:421`); LangSmith deep-link per run (project already uses LangSmith — `INTEGRATIONS.md:107-116` per v2.6 §16). *Carries: SEED-012 §2.*
- Per-user concurrent SSE stream cap (deferred from v2.6 §15) — admin-configurable per role tier; data layer + enforcement in `backend/app/api/runs.py` stream subscribers; pairs with the dashboard UI in this milestone. *Carries: SEED-001 §scope step 5.*

**Theme C — Provider & Model Management (closes SEED-009)**
- `model_capabilities_overrides` table — admin-editable overrides on top of the static `MODEL_CAPABILITIES` registry in `backend/app/config.py` (per `STACK.md` MODEL_CAPABILITIES references and SEED-009 §likely-fix-shape Path 2). Fields: `model_key`, `provider`, `enabled`, `max_output_tokens`, `default_temperature`, `llm_call_timeout_seconds`, `native_tools`, `deprecated`, `notes`, `updated_by`, `updated_at`. Hot-reload via short TTL cache in `config.py` (mirrors existing `_TTL_CACHE` pattern at `backend/app/models/user_settings.py:27`). *Carries: SEED-009 (admin-UI surface; v2.6 shipped the underlying `max_output_tokens` field but no editor), SEED-012 §3.*
- Provider key management UI — list providers (OpenAI, Anthropic, OpenRouter, Google, Tavily, Cohere per `CONCERNS.md:81`), per-provider connection-test button (calls a tiny `/embeddings` or `/models` probe), redacted display (`sk-...****`), rotation flow (writes to chosen secrets store per Q-v3.1-02; **never** back to `settings_override.json`). Closes the `CONCERNS.md:81-83` "API keys persisted to disk as plain text" finding. *Carries: SEED-012 §3, `CONCERNS.md:81-83`.*

**Theme D — Migration & Schema State UI**
- `migration_state` view backed by Supabase migration tracking — surfaces current head, list of pending migrations against the version in the deployed image, last-applied timestamp. Status banner in the admin shell ("DB at 074, latest migration in repo is 077, 3 pending"). *Carries: SEED-012 §5.*
- "Apply pending migrations" button — gated to super-admin only, REQUIRES the operator to confirm with a typed string ("APPLY"), routes through a hardened backend endpoint that calls Supabase admin API (NOT direct SQL execution; honors CLAUDE.md "apply via SQL editor" caveat by exposing the same migration runner Supabase exposes). For deployments where direct application is blocked (managed Supabase), the button shows the SQL with a copy-to-clipboard + open-SQL-editor deep link. *Carries: SEED-012 §5, CLAUDE.md migration discipline.*
- "Regenerate full-schema.sql" button — replaces `scripts/regenerate-full-schema.sh` for the live-DB-dump path. Output is a downloadable artifact; no direct repo write. *Carries: SEED-012 §5, project memory `feedback_regen_full_schema_no_reset.md`.*

**Theme E — Audit Log Browser (finally surfaces v2.2 F-06)**
- Admin UI for the `audit_log` table (shipped v2.2 F-06, `PROJECT.md:100` + `PROJECT.md:188`). Today: per-user CSV export only. v3.1 ships: org-wide / system-wide filter, action-type filter, date-range filter, paginated table view, deep-link to user / thread / run / document, CSV export of filtered set. Read-only — table is INSERT-only RLS by design. *Carries: SEED-012 §4, v2.2 F-06 belated UI completion.*
- Audit-log retention policy — admin-configurable retention window with default per Q-v3.1-05 (recommended 90 days). Background pruner job runs daily (in-process per the no-new-scheduler-yet rule; v3.4 Automations replaces with proper scheduler). *Carries: Q-v3.1-05.*
- Operator-action audit — every admin shell action (model edit, secret rotation, run cancel, migration apply) writes to a separate `operator_audit_log` table with elevated retention (1 year default, never less than 90 days). Distinct from user `audit_log` so operator actions can't be silently pruned with user data. *Carries: SEED-012 §4 + lateral-thinking insight.*

**Theme F — User Management Primitives**
- Users list view — last-active, role (operator vs user), sign-up timestamp, disable / enable affordance. Backs onto Supabase Auth via service-role client (NOT a custom `users` mirror — sole writer to identity). v3.2 RBAC layers org membership on top of this surface. *Carries: SEED-012 §4.*
- "Sign in as user" support affordance — gated to super-admin; issues a short-lived (15 min) impersonation JWT; every action under impersonation written to `operator_audit_log` with `impersonated_user_id`. *Carries: SEED-012 §4.*
- Per-org observability primitive tables (stub data layer, v3.2 fills RBAC) — `org_id` placeholder columns on `audit_log`, `runs`, `documents`, `threads` (nullable, no enforcement until v3.2). v3.1 ships the ALTER migrations so v3.2's RLS shift is purely a policy change, not a column add. *Carries: SEED-012:52-54, `D-PRD-02` "v3.1 deployment presets must include both co-tenant and dedicated configurations" implication.*

**Theme G — Sandbox & Infrastructure Operations**
- Sandbox health probe — Docker daemon reachable? `llm-sandbox` 0.3.37 image present? recent execution failures from `runs.error`? "Restart sandbox" affordance (calls `sandbox_manager.restart()`). Closes `CONCERNS.md:666-668` startup-health-check carry-forward. *Carries: SEED-012 §6, CONCERNS.md:666-668.*
- Sandbox config UI — admin-tunable memory limits, network policy, allowed-language list (when configurable). Stored in a new `sandbox_config` row inside `app_settings` (which v2.6 finally activated per RAG-MM-LIFT-01 — extends the same wired-up read path). *Carries: SEED-012 §6.*
- Redis health detail — XLEN per `runs:active` key, memory-used vs cap per `STACK.md:104` 256MB note, eviction policy display, "Flush stale runs" affordance. *Carries: SEED-012 §2 + cross-trigger.*

**Theme H — Install Wizard**
- Browser-based first-run flow served at `setup.<domain>` (or `localhost:8000/setup` if no domain) — gates: (1) detect environment (Docker available? GPU? Postgres reachable? Redis reachable? sandbox enabled?), (2) pick deployment shape (Solo / Team / Enterprise — see Theme I), (3) bind Supabase (cloud project URL + keys, OR self-hosted CLI flow with stamped values), (4) bind Redis (container URL OR Upstash `rediss://...` per CLAUDE.md "Local-vs-cloud switch"), (5) create bootstrap super-admin user, (6) bind LLM providers (OpenAI / Anthropic / OpenRouter / Google) — at least one required, (7) optional skills bootstrap (curated starter set), (8) TLS / Nginx / certbot config (single-VPS shape only; k8s shape skips), (9) writes everything to chosen secrets store (Q-v3.1-02), provisions service files, runs migrations, smoke-tests, hands off to admin shell. *Carries: SEED-003 §scope step 2, RECOVERED_VPS_Deployment_Guide.md (everything that should move from runbook to UI), RECOVERED_Deploy_Hostinger_Supabase_Cloud.md.*
- Headless CLI variant (`agentic-rag setup`) for ops teams that won't run a browser on the server — same step graph, prompts on stdin instead. Pairs with Q-v3.1-04. *Carries: SEED-003 §scope step 2 + Q-v3.1-04.*
- Detect-and-correct existing-install upgrade flow — running the wizard on an already-installed system shows current state and only prompts for what's missing or out-of-date (e.g., new env vars added in v3.2). *Carries: SEED-003 §scope step 4.*

**Theme I — Deployment Presets & Packaging**
- **Solo preset** — single VPS / single user / single Docker compose stack. Defaults: `WORKER_COUNT=1`, AnyIO ceiling 200, sandbox enabled, no rate limits, telemetry off, Redis 256MB, `match_document_chunks` runs on Postgres-default pgbouncer. Maps to `D-PRD-10` Standard tier solo-self-host edge case. *Carries: SEED-003 §scope step 6 Tier 1.*
- **Team preset** — small org (5-50 users) self-hosted on a single beefier server or compose stack. Defaults: `WORKER_COUNT=2`, AnyIO ceiling 200, sandbox enabled with concurrency cap 4, soft rate limits, telemetry opt-in, Redis 1GB, pgbouncer transaction-mode pool 50. Maps to `D-PRD-10` Standard / Pro tiers. *Carries: SEED-003 §scope step 6 Tier 2.*
- **Enterprise preset** — k8s (Helm chart) deployment with multi-worker uvicorn pods, asyncpg pool sized per-pod, Redis cluster mode (sentinel optional), full telemetry on, sandbox concurrency cap 16, sticky sessions if Realtime returns (`AWAITING DECISION` per v2.6 §11), per-org observability primitives wired in (data-layer tables already present from Theme F). Maps to `D-PRD-10` Enterprise tier. *Carries: SEED-003 §scope step 6 Tier 3, `D-PRD-08` multi-worker default.*
- Single Docker compose reference stack (`docker-compose.prod.yml`) — Postgres + Redis + app + sandbox; complementary to existing dev `docker-compose.dev.yml`. *Carries: SEED-003 §scope step 5.*
- Prod reverse proxy (Nginx/Caddy) terminates HTTP/2 to the browser so concurrent SSE streams multiplex over a single connection, structurally removing the HTTP/1.1 6-connection-per-host cap that BUG-260530-01 documents (the Phase-096 frontend stream-cap is the per-client mitigation; HTTP/2 at the proxy is the infrastructure-layer complement). Today the app is dual-origin (UI `:5173` calls backend `:8000` directly over HTTP/1.1; uvicorn has no native HTTP/2) — the prod proxy is the substrate that addresses this. No new infra cost — it's reverse-proxy config this milestone already ships (the `docker-compose.prod.yml` + Nginx/TLS stack above, wired by WIZ-FIRST-01 / RUNBOOK-SUPER-01). *Carries: BUG-260530-01, SEED-003 §scope step 5.*
- Helm chart (`charts/agentic-rag`) with values.yaml for all three presets. Targets k8s 1.27+. *Carries: SEED-003 §scope step 5, Q-v3.1-03.*
- Deployment-runbook supersession — supersedes `RECOVERED_VPS_Deployment_Guide.md` and `RECOVERED_Deploy_Hostinger_Supabase_Cloud.md` (both partially superseded in v2.6 for Redis omission + `--workers 2` correction; v3.1 fully archives them and replaces with `OPERATOR.md` + the in-app install wizard as the canonical entry). The `_patch_postgrest_maybe_single` automation note (v2.5 Phase 058 D-058-05 made it implicit per v2.6 §9) is documented in `OPERATOR.md` so operators reading it don't think they need to apply the manual postgrest patch. *Carries: synthesis §7 RECOVERED_VPS rows, v2.6 §9 carry-forward.*

**Theme J — Secrets Management**
- Secrets store abstraction — `SecretsBackend` Python interface; v3.1 ships two implementations: (a) **encrypted-in-Postgres** (default, no new infra dependency — secrets in a `secrets` table encrypted with `pgsodium` symmetric key, key rotation supported); (b) **env-var read-only** (legacy compatibility, NEVER written to). Vault adapter deferred to v3.1.5 enterprise tier. Maps to Q-v3.1-02 recommendation. *Carries: SEED-003 §scope step 3, SEED-012 §3, `CONCERNS.md:81-83` (closes plain-text-on-disk finding).*
- Secrets rotation UI — list secrets, last-rotated, "Rotate" affordance per secret. Audit-log every rotation to `operator_audit_log`. *Carries: SEED-012 §3.*

**Theme K — Settings UI Redesign Coordination**
- The deferred Settings page redesign (per project memory `project_settings_design_guidance.md` — full redesign deferred to Skill Studio milestone) — v3.1 adds the `/admin` shell as a NEW tier ABOVE the redesigned Settings (tier separation, per SEED-012:96). v3.0 Skill Studio owns the Settings redesign itself; v3.1 is the milestone where the operator-vs-user surface separation finally exists. If v3.0 deferred the Settings redesign further, v3.1 still ships the admin shell — they're independent. *Carries: SEED-012 §7, project memory `project_settings_design_guidance.md`.*

**Theme L — Accessibility (WCAG 2.1 AA, shared scope with v3.0)**
- All new admin shell UI surfaces (Themes A-K above) meet WCAG 2.1 AA baseline: keyboard navigation across every admin route (no mouse-only paths — operator must be able to navigate the entire shell with Tab/Shift-Tab/Enter/Esc); `aria-label` / `aria-describedby` on every interactive element (model-capability rows, kill-run affordances, secret-rotation buttons, migration apply button, deployment preset cards); minimum 4.5:1 color contrast on text against Deep Midnight backgrounds; visible focus indicators via existing `:focus-visible` ring; status indicators (Redis/Supabase/Sandbox/LangSmith health) pair color with an icon + text label (no color-only conveyance). *Carries: Plan 09 SUMMARY.md §C.1 #5 routed via "small lift across v3.0 + v3.1" per user signoff 2026-05-12.*
- "Apply pending migrations" + "Sign in as user" + "Kill run" affordances all require explicit typed confirmation (already specified in Themes D + F) — confirmation modals MUST implement keyboard focus traps with escape-key dismissal per WCAG 2.4.3. *Carries: Plan 09 SUMMARY.md §C.1 #5.*
- Install wizard (Theme H) accessibility: every step navigable with Tab, every form field labeled, errors announced via `aria-live="polite"`. Critical because the install wizard runs BEFORE the user has any admin shell — accessibility issues here block setup entirely for keyboard-only operators. *Carries: lateral-thinking — install-wizard accessibility is an enterprise-procurement blocker.*
- Accessibility audit gate at milestone close: automated axe-core scan on every `/admin/*` route AND on the install wizard; manual keyboard-only walk-through documented in milestone UAT. The user-facing Settings page is OUT of v3.1 accessibility scope (owned by v3.0's Settings redesign — Theme I there). *Carries: WCAG 2.1 AA acceptance criterion, scope boundary with v3.0.*

## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** Bundle a built-in observability stack (Grafana + Prometheus + Loki) into the Enterprise deployment preset.
   **Why tempting:** Many enterprise customers want "batteries included" observability; Glean and Copilot Studio bundle dashboards. Self-host customers without an existing stack would have day-1 visibility for free.
   **Why not now:** Forces ops choices on customers — most enterprises already have Datadog / New Relic / Splunk / Honeycomb / their own Grafana / etc. and don't want a second stack. Operating a bundled stack also means we own its security patches, version drift, and resource consumption forever. v3.1 ships a Prometheus `/metrics` endpoint instead — customers bring their own stack.
   **Re-trigger:** ≥3 enterprise customers explicitly ask for a bundled stack AND none of them already have one.

2. **Idea:** Auto-update mechanism for self-hosted deployments — "agentic-rag self-update" CLI or background updater that pulls latest signed release.
   **Why tempting:** Closes the upgrade-friction gap (today: SSH + git pull + service restart + migrate). Most consumer SaaS-y apps have it.
   **Why not now:** Enterprise IT MUST control upgrade timing — auto-update during business hours is a fireable offense in regulated industries. We ship signed Docker images + Helm chart releases + migration plan; the operator runs `helm upgrade` (or wizard's upgrade flow) when their change-control window opens. v3.1's WIZ-UPGRADE-01 detect-and-correct flow is the right shape: explicit, idempotent, operator-triggered.
   **Re-trigger:** First Solo / SMB-tier customer asks for it AND we can scope it to the lowest tier without enterprise IT impact.

3. **Idea:** White-label theming — custom logo, brand colors, custom domain branding per deployment.
   **Why tempting:** Reseller / partner channels could rebrand and resell the platform. M-Files allows this for VAR partners.
   **Why not now:** Premature — no reseller channel exists; vertical packs (`D-PRD-11`) are the better-aligned monetization path. White-label adds complexity to the Aether Intelligence Deep Midnight design system (per `MILESTONES.md:147-157`) and admin shell theming surface that v3.1 doesn't need yet.
   **Re-trigger:** First reseller / partnership conversation OR vertical-pack customer needs branded UI.

4. **Idea:** Plugin / extension architecture for the admin shell — third-party tabs / panels.
   **Why tempting:** Lets customers / partners add custom admin views without forking. Glean has a "custom workflow" feature in this shape.
   **Why not now:** Out-of-scope for v3.1 — the admin shell needs to BE useful before its extension surface matters. Adds significant security surface (XSS, CSRF in plugins). Revisit if customer requests come or if the admin shell stabilizes enough to lock its API contract.
   **Re-trigger:** ≥2 customer requests for admin extensibility OR a partner ships a complementary tool that wants to integrate.

5. **Idea:** Real-time collaborative editing of admin config (multiple operators editing model_capabilities_overrides simultaneously, conflict resolution via CRDT).
   **Why tempting:** Larger ops teams might have multiple operators tuning the same config; conflict resolution would prevent overwrites.
   **Why not now:** Admin actions are low-cardinality (10s of edits per day per install). Pessimistic locking via "last-write-wins with timestamp warning" is sufficient. CRDT infrastructure is heavy and doesn't compose with the existing run-backed streaming architecture.
   **Re-trigger:** ≥10 operator-tier users on a single deployment AND observed conflict-overwrite incidents.

6. **Idea:** Build a standalone "agentic-rag-cloud" SaaS offering — fully managed, no install required.
   **Why tempting:** Lowest-friction onboarding for SMB; matches Glean's positioning; recurring revenue without per-customer ops burden.
   **Why not now:** Out of scope for v3.1 — `D-PRD-02` already commits to hybrid SaaS posture (co-tenant SMB/mid + dedicated/on-prem large enterprise). v3.2 ships the multi-tenancy required to operate the co-tenant SaaS; v3.1 is the "make on-prem painless" milestone, not the "build the SaaS" milestone. v3.2 could use v3.1's admin shell as the SaaS operator console.
   **Re-trigger:** v3.2 multi-tenancy ships AND we decide to operate a co-tenant SaaS; admin shell becomes the management plane.

## 14. Competitive positioning paragraph

v3.1 positions Agentic RAG against **Glean** (the primary enterprise-search competitor per `D-PRD-05` — closed SaaS, no on-prem, customers vendor-dependent for every operation) and **M-Files** (the secondary competitor per `D-PRD-05` — strong on-prem story but heavy IT setup, enterprise-only deployments, no co-tenant SMB tier). Three differentiators ship in this milestone, all mapping directly to scope bullets. **First: hybrid SaaS posture from one codebase** — the same release artifact serves both the Solo / Team Docker compose self-host (SMB tier) and the Enterprise Helm chart on-prem (large-enterprise tier) per Theme I, with deployment presets encoding scale defaults appropriately for each (Theme I PRESET-SOLO/TEAM/ENT-01). Glean has no on-prem story; M-Files has no co-tenant SaaS. Neither competitor can claim "evaluate as Solo today, upgrade to Enterprise on-prem when you grow" without a forklift migration. **Second: self-service operator UI — no support ticket for routine config.** The admin shell (Theme A through Theme G) means an enterprise IT operator can rotate provider keys (Theme C PROV-KEY-01), retune the `claude-haiku-4-5-20251001` max_tokens cap when Anthropic ships a new model (Theme C MOD-CAP-01 closes SEED-009 cleanly via UI, not config edit), browse the audit log that v2.2 F-06 finally surfaces (Theme E AUDIT-UI-01), kill a stuck run (Theme B BP-RUNS-01), and apply a pending migration (Theme D MIG-STATE-02) — all without filing a vendor ticket or SSH-ing into the server. Glean's customers wait on Glean's support team for these operations; M-Files customers wait on their VAR partner. **Third: web-driven install wizard — no shell access required for the IT operator** (Theme H WIZ-FIRST-01). RECOVERED_VPS_Deployment_Guide.md was a 13-step copy-paste runbook requiring SSH expertise; v3.1 replaces it with a browser-based first-run flow that detects environment, binds Supabase + Redis, provisions secrets, picks a deployment preset, configures TLS, and hands off to the admin shell — typically <30 minutes from blank Ubuntu to chatting with documents (PRESET-SOLO-01 acceptance). M-Files install requires named-IT-engineer onsite for hours-to-days; Glean is SaaS-only and not installable at all. The encrypted-in-Postgres secrets store (Theme J SEC-STORE-01) closes the `CONCERNS.md:81-83` plain-text-on-disk finding without forcing a Vault dependency on customers who don't have one — a pragmatic differentiator against the typical enterprise-software pattern of "step 1: install Vault first, step 2: figure out our app." Together these three differentiators turn the operator UX from a developer-only experience into a product an enterprise IT team can actually own day 1, day 2, and day 1000 — required before the first paid co-tenant or on-prem customer ships under `D-PRD-02`.
