# PRD: Agentic RAG — Milestone v3.2 (Multi-Tenancy — Hybrid SaaS Foundation)

**Defined:** 2026-05-10
**Author:** PRD-reset Plan 06
**Reserved migration range:** `075 – 094` (per `.planning/prd-reset/MIGRATION-RESERVATIONS.md` — largest range across all 6 PRDs because the RLS predicate rewrite touches every user-facing table)

---

## 1. Header

v3.2 is the load-bearing milestone that turns Agentic RAG from a per-user-data application into an org-aware multi-tenant platform — the existential prerequisite for the hybrid SaaS posture locked in `D-PRD-02`. Three interlocking workstreams ship together: (1) **org / department / role primitives** — new `orgs`, `departments`, `org_members`, `dept_members`, `roles`, `role_permissions`, `org_invitations`, `sso_configs` tables that take the project from a binary "private vs `is_global`" visibility model to membership-keyed authorization; (2) **a complete RLS predicate rewrite** on every user-facing table (currently 18 tables all keyed on `user_id = auth.uid()` per `supabase/full-schema.sql:1124-1493`) so org-scoped data is org-isolated by default and `is_global` becomes per-org `is_org_shared` plus a small system-skills exception list; (3) **SSO (SAML 2.0 + OIDC) via Supabase Auth providers + JIT provisioning + invitation flows** so a 500-seat enterprise customer can onboard without per-user manual signup. Concurrently, the SECURITY DEFINER RPC `match_document_chunks` (`CONCERNS.md:69-76`) is rewritten to SECURITY INVOKER with explicit RLS so the bypass class is eliminated — the most important security fix in the project's roadmap. A one-shot data migration auto-creates a personal org for every existing user, backfills `org_id` on every existing row, and preserves all data with no user action required. After v3.2: hybrid SaaS posture is real — the same codebase serves co-tenant SMB on a single Supabase instance via org_id discriminator + RLS, and dedicated/on-prem enterprise via the same codebase deployed against a customer-owned Supabase instance. v3.3 (Open Platform) and v3.4 (Automations) inherit org context natively and cannot be retrofitted; doing this milestone before them is the only correct order.

## 3. Scope

**Theme A — Org / Department / Role Schema Foundation (Wave 0)**
- New `orgs` table: `id uuid pk`, `name text`, `slug text unique`, `subscription_tier text default 'standard'` (per `D-PRD-10`), `add_ons jsonb default '[]'` (per `D-PRD-11`), `is_personal boolean default false` (auto-created personal orgs flagged), `created_at`, `updated_at`. *Carries: SEED-004 §scope-step-1, `D-PRD-02`.*
- New `departments` table: `id uuid pk`, `org_id uuid fk orgs(id) on delete cascade`, `name text`, `parent_id uuid fk departments(id)` (nesting), `retention_policy_id uuid fk` (nullable; foothold for DM Tier B per SEED-005), `created_at`. Single default dept created with each org for "small org with no departments" v1 case per SEED-004 §design. *Carries: SEED-004, `RECOVERED_PRD_Enterprise_RAG_Features_Roadmap.md F-04` (precursor groups concept, superseded).*
- New `org_members` table: `org_id uuid fk`, `user_id uuid fk auth.users(id)`, `role_id uuid fk roles(id)`, `joined_at`, `joined_via text` (`'invitation' | 'sso_jit' | 'personal_auto' | 'admin_create'`), composite PK `(org_id, user_id)`. *Carries: SEED-004 §scope-step-2.*
- New `dept_members` table: `dept_id uuid fk`, `user_id uuid fk`, `role_id uuid fk`, composite PK `(dept_id, user_id)`. A user can be in many departments within an org. *Carries: SEED-004 §scope-step-2.*
- New `roles` table: `id uuid pk`, `org_id uuid fk orgs(id)` (nullable for system roles), `name text`, `tier text` (`'super_admin' | 'org_admin' | 'dept_admin' | 'member'` per Q-v3.2-03), `is_system boolean default false`, `created_at`. *Carries: SEED-004 §scope-step-2.*
- New `role_permissions` table: `role_id uuid fk`, `permission text` (e.g., `'documents:read'`, `'documents:write'`, `'skills:share_dept'`, `'org:manage'`, `'org:audit_view'`), composite PK `(role_id, permission)`. Fine-grained permission set seeded with sensible defaults per role tier; org-admins can extend. *Carries: SEED-004 §scope-step-2 + `D-PRD-10` entitlement infrastructure.*
- New `org_invitations` table: `id uuid pk`, `org_id uuid fk`, `email text`, `role_id uuid fk`, `token_hash text unique`, `invited_by uuid`, `expires_at timestamptz`, `accepted_at timestamptz nullable`. Powers both link-based and email invite flows per Q-v3.2-07. *Carries: SEED-004 §scope-step-6.*
- New `sso_configs` table: `org_id uuid fk`, `provider_type text` (`'saml' | 'oidc'`), `idp_metadata jsonb` (SAML XML or OIDC discovery doc), `jit_provisioning_default_role_id uuid fk roles(id)`, `attribute_mapping jsonb` (claim → user field), `is_enabled boolean`, `created_at`, `updated_at`. *Carries: SEED-004 §scope-step-2 (RLS shift implications), `D-PRD-02` SSO requirement.*

**Theme B — Personal-Org Backfill Data Migration (Wave 0)**
- One-shot SQL data migration: for every row in `auth.users`, INSERT a row in `orgs` named `<email>'s Personal Workspace`, `slug='personal-<short_id>'`, `is_personal=true`, `subscription_tier='standard'`. Insert single default dept per personal org. Insert `org_members` row with `role_id=(personal-org-admin role)` and `joined_via='personal_auto'`. *Carries: SEED-004 §entry-plan-step-2 + Q-v3.2-04 recommendation.*
- Backfill `org_id` and `dept_id` columns on every user-facing table (added in Theme C migrations). UPDATE statements scoped per-table; transactional per-table; idempotent re-runs via WHERE `org_id IS NULL`. *Carries: SEED-004 §entry-plan-step-2.*
- Existing `is_global` flags on `folders` and `skills` migrate to `is_org_shared boolean` per-org. A small system-skills allow-list (the seeded `skill-creator` from migration 018, future seeded skills) gets `is_org_shared=true on every personal org` plus a new `is_system_global boolean` to preserve cross-org system-skill visibility — the only legitimate cross-org sharing in the model. *Carries: SEED-004 §scope-step-3 (`is_global` retirement), `RECOVERED_PRD_Enterprise_RAG_Features F-04` superseded.*

**Theme C — RLS Predicate Rewrite per-Table (Wave 1, parallelizable in batches)**
- Add `org_id uuid not null fk orgs(id)` and (where applicable) `dept_id uuid nullable fk departments(id)` to every user-facing table. Backfilled by Theme B migration. Tables affected (18 total per `supabase/full-schema.sql:230-524`): `audit_log`, `code_executions`, `document_chunks`, `document_images`, `document_tables`, `documents`, `folders`, `message_feedback`, `messages`, `profiles`, `runs`, `sandbox_files`, `skill_files`, `skills`, `threads`, `user_memory`, `user_settings`, `app_settings`. *Carries: SEED-004 §scope-step-3.*
- RLS policy rewrite per-table: from `(auth.uid() = user_id)` to membership-based. Standard predicate (per-table tunable):
  ```sql
  USING (
    org_id IN (SELECT org_id FROM public.org_members WHERE user_id = auth.uid())
    AND (
      user_id = auth.uid()  -- private to creator within org
      OR is_org_shared = true  -- shared with all org members
      OR (dept_id IS NOT NULL AND dept_id IN (SELECT dept_id FROM public.dept_members WHERE user_id = auth.uid()))  -- shared with creator's dept
    )
  )
  ```
  Per-table variant clauses for `audit_log` (org-admin can see all org rows via permission check), `messages` / `threads` / `runs` (private-to-user-within-org by default; no `is_org_shared`), `documents` / `folders` / `skills` (full predicate above with dept and is_org_shared variants).
- One migration per ~4-5 tables to keep PR-able sizes (~5 migrations total: documents bundle, threads/runs/messages bundle, skills bundle, audit/feedback/memory/settings bundle, profiles/sandbox/code_executions bundle). *Carries: SEED-004 §scope-step-3.*

**Theme D — SECURITY DEFINER Audit + Rewrite (Wave 1)**
- Rewrite `match_document_chunks` from SECURITY DEFINER to SECURITY INVOKER with explicit `org_id` filter inside the function body (per Q-v3.2-05 recommendation). The function currently accepts `match_user_id uuid` (`CONCERNS.md:69-76`); new signature accepts `match_user_id uuid` AND derives `org_id` from `org_members WHERE user_id = match_user_id`, applies as additional WHERE clause inside the CTE. Cross-org leak now structurally impossible because RLS on `document_chunks` enforces the same predicate independently. *Carries: SEED-004 §scope-step-3 (`SECURITY DEFINER` audit), `CONCERNS.md:69-76`, Q-v3.2-05.*
- Audit + rewrite `folder_is_globally_visible(uuid)` SECURITY DEFINER function to `folder_is_org_shared(uuid, uuid)` SECURITY INVOKER taking `(folder_id, current_user_id)` and resolving the user's orgs internally. *Carries: SEED-004 §scope-step-3, `supabase/migrations/019_global_folder_subtree_visibility.sql`.*
- Audit + rewrite `query_user_documents` RPC (text-to-SQL path, `supabase/migrations/012_query_documents_fn.sql`) — currently SECURITY DEFINER with regex-based `_inject_user_id` guard (`CONCERNS.md:36-47, 50-57`). New shape: SECURITY INVOKER + parameterized SQL via Supabase `.rpc()` proper binding (closes the regex-bypass class). *Carries: SEED-004 §scope-step-3, `CONCERNS.md:50-65`.*
- Switch backend from service-role-key Supabase singleton (`backend/app/dependencies.py:13-17`) to per-request user-JWT clients on hot paths (CONCERNS.md:36-47 critical risk). Service-role retained ONLY for explicit cross-tenant ops (audit log writes initiated by org-admin, JIT provisioning during SSO callback) — and those callsites get a hardened wrapper that requires explicit `org_id` parameter. *Carries: `CONCERNS.md:36-47`, defense-in-depth on the tenancy boundary.*

**Theme E — SSO Integration (Wave 1)**
- SAML 2.0 provider integration via Supabase Auth (Supabase ships SAML support out-of-the-box for Pro+ tier; on-prem deployments use the open `supabase-auth` lib). `sso_configs` row provides IdP metadata; redirect URL `<APP_URL>/auth/sso/saml/<org_slug>/callback`. *Carries: SEED-004 §scope-step-2, Q-v3.2-02.*
- OIDC provider integration via Supabase Auth (same path as Google/GitHub/Microsoft providers, but per-org config registered dynamically via `sso_configs` row). Redirect URL `<APP_URL>/auth/sso/oidc/<org_slug>/callback`. *Carries: SEED-004, Q-v3.2-02.*
- JIT provisioning logic on first SSO login: if `auth.users` row for the email doesn't exist, create it; insert into `org_members` with `role_id=jit_provisioning_default_role_id` and `joined_via='sso_jit'`. Attribute mapping (department from claim → `dept_members` insert) honored from `sso_configs.attribute_mapping`. *Carries: SEED-004 §entry-plan-step-2.*
- Email-and-password fallback retained for v3.2 (per §10 entry — full SSO ENFORCEMENT deferred to v3.2.5 / v3.3 add-on). Org-admin can flag `sso_configs.is_enabled=true AND email_password_disabled=false` as v3.2 default; the enforcement add-on flips the second flag.

**Theme F — Audit Log Org Discriminator + Org-Admin View (Wave 1)**
- Add `org_id uuid` column to existing `audit_log` table (NOT a new table — SEED-004 §scope-step-7 explicit). Backfill from Theme B. RLS rewrite: `org_id IN (orgs the user is a member of) AND ((user_id = auth.uid()) OR (caller has 'org:audit_view' permission on this org_id))`. *Carries: SEED-004 §scope-step-7, `CONCERNS.md:36-47` (audit-log RLS hardening).*
- Audit log retention extended with per-org override (`orgs.audit_retention_days int default 90`). v3.1's audit retention setting becomes the platform default; org-admins can extend or shorten per Q-v3.2-06 recommendation (per-tier defaults: Standard=30, Pro=90, Enterprise=unlimited; configurable per-org by org-admin). *Carries: SEED-004 §scope-step-7, Q-v3.2-06.*
- New `audit_log` action types added: `org.create`, `org.member_add`, `org.member_remove`, `org.role_change`, `org.invitation_send`, `org.invitation_accept`, `org.sso_config_change`, `org.retention_change`, `dept.create`, `dept.delete`. *Carries: SEED-004.*

**Theme G — Org-Admin / Dept-Admin UI Tier (Wave 2)**
- Org-admin shell — extends the v3.1 admin shell pattern with an org-level surface. Tabs: Members & Invitations / Departments & Roles / SSO Configuration / Audit Log (org-scope) / Subscription & Add-ons / Retention Policy / Settings. Reuses v3.1's permission-gated shell pattern; gated on `org:manage` permission. *Carries: SEED-004 §scope-step-6, SEED-012 (handed-off from v3.1), `RECOVERED_PRD_Enterprise_RAG_Features_Roadmap.md F-04`.*
- Dept-admin shell — narrower surface for dept-admins. Tabs: Dept Members / Dept Skills / Dept Retention Policy / Dept Audit Log. Gated on `dept:manage` permission. *Carries: SEED-004 §scope-step-6.*
- Settings page refactor: existing per-user settings stay user-scoped; new "Org Settings" sub-page lives behind `org:manage` permission. Per `project_settings_design_guidance.md`, Settings page redesign was deferred to Skill Studio milestone (v3.0); v3.2 lands the org-tier additions on whatever shape v3.0 produces, NOT on the v2.5 5-tab layout. *Carries: SEED-004 §scope-step-6, `project_settings_design_guidance.md`.*
- Member-facing org switcher (top-nav dropdown): a user in multiple orgs can switch context. Active org persists in localStorage + JWT custom claim; all subsequent API calls include `X-Org-Id` header (validated against `org_members` server-side). *Carries: SEED-004 §scope-step-6 implication.*

**Theme H — Invitation Flow + JIT Provisioning (Wave 2)**
- Invitation send: org-admin POST `/orgs/{org_id}/invitations` with `{email, role_id, dept_id?}`. Backend INSERTs `org_invitations` row, hashes invitation token, sends email (transactional email via existing `audit_service` pattern; provider deferred — recommend Resend or AWS SES via env var). *Carries: SEED-004 §scope-step-6, Q-v3.2-07.*
- Invitation accept: GET `/invitations/{token}` resolves to `org_invitations` row (exists + not expired + not accepted); user signs in or signs up; on auth success, INSERT `org_members` with `joined_via='invitation'`; mark invitation accepted. *Carries: SEED-004, Q-v3.2-07.*
- Link-based invite: same `/invitations/{token}` path, but org-admin can generate the link without sending email (for paste-into-Slack scenarios). Both flows share the same accept handler. *Carries: Q-v3.2-07 recommendation (both).*
- JIT provisioning per Theme E (first SSO login auto-creates membership) — covered above; called out here for the invitation-flow completeness.

**Theme I — DM Tier B Foothold (Wave 2)**
- Per-dept retention policy primitive: `retention_policies` table (`id uuid pk`, `org_id uuid fk`, `name text`, `applies_to_dept_id uuid fk departments(id) nullable` (null = org-wide), `target_resource text` (`'documents' | 'threads' | 'audit_log'`), `retain_days int`, `action_at_expiry text` (`'soft_delete' | 'hard_delete' | 'archive'`), `created_at`). Background scheduler not in scope — actual policy enforcement is a v3.4 Automations dependency. v3.2 ships only the schema + the org-admin UI to manage policies. *Carries: SEED-005 Tier B (retention policy at dept level), `D-PRD-11` implication (legal-pack precursor).*
- Per-org rate-limit primitive (data-layer only): `org_rate_limits` table (`org_id uuid fk`, `endpoint_pattern text`, `requests_per_minute int`, `created_at`). v3.3 (Open Platform) implements enforcement via Redis token-bucket reading from this table. v3.2 ships schema + org-admin UI surface. *Carries: SEED-013 dependency, `D-PRD-08` implication.*

**Theme J — Cross-Cutting Verification (Wave 4)**
- Every existing test must continue passing under the new RLS predicates, with the `org_id` backfill applied. Specifically: CONCUR-01 binding gate (`backend/tests/integration/test_058_concurrency.py`), Phase 067.x lived-experience cycles (Playwright e2e), all unit + integration tests. *Carries: regression discipline.*
- New cross-org isolation test suite: `backend/tests/integration/test_v3_2_org_isolation.py` — for each user-facing table, verify (a) user A in org X cannot SELECT/UPDATE/DELETE rows belonging to user B in org Y, (b) user A in org X cannot SELECT rows belonging to user A's other persona in org Z if such persona exists, (c) the SECURITY INVOKER `match_document_chunks` rewrite blocks cross-org returns. *Carries: SEED-004 §scope-step-3 verification, `CONCERNS.md:69-76` closure, defense-in-depth.*

## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** B2B2C — orgs invite end-customer users with bounded read access (e.g., a Legal firm invites their client to review a redlined contract).
   **Why tempting:** Strong vertical-pack play (Legal pack would benefit immediately). Closes a significant differentiator gap vs M-Files (which has external collaborators). Composes naturally with the dept-scoped visibility model.
   **Why not now:** Out-of-scope for v3.2 — the v3.2 mission is to make orgs work; B2B2C is a separate trust model (external user is in NEITHER org membership tier nor public). Adds significant complexity to RLS predicates (need a third predicate clause for "shared with external collaborators with explicit grant"). Better to ship in a vertical-pack milestone where the use case is concrete.
   **Re-trigger:** First customer in a vertical pack (likely Legal per `D-PRD-11`) explicitly requires B2B2C. Promote to its own dedicated phase under v3.5+ vertical-pack milestone.

2. **Idea:** Org-level SSO ENFORCEMENT — no email/password fallback for org members (only SSO sign-in is permitted).
   **Why tempting:** Enterprise security teams require this for compliance (SOC 2, ISO 27001 often mandate "all employees authenticate via corporate IdP"). Closes a hard requirement for some buyers.
   **Why not now:** v3.2 ships SSO + email/password fallback. Enforcement adds two failure modes: (a) org-admin enables enforcement before SSO is correctly configured → all org members locked out; (b) SSO IdP outage → org locked out with no recovery path. Both need careful UX (preview mode, break-glass admin override, recovery email). Deferred to v3.2.5 — small dedicated phase that adds the `email_password_disabled` flag to be flippable per-org with safe defaults + break-glass mechanism.
   **Re-trigger:** First enterprise customer requires SSO enforcement as a deal blocker. v3.2.5 or fold into v3.3 add-on.

3. **Idea:** Cross-org skill sharing — a user in org A authors a skill, makes it visible to org B's members.
   **Why tempting:** Compelling collaboration story; an industry-leading legal firm could publish skills consumed by its peers. agentskills.io marketplace play (per `D-PRD-03` open-peripheral standard).
   **Why not now:** **Explicit anti-feature for v3.2.** Orgs are isolated by default; cross-org sharing reopens the leak class v3.2 explicitly closes. The `is_system_global` flag exists ONLY for the seeded `skill-creator` and is set via migration (NOT user-flippable). Cross-org sharing belongs in agentskills.io ZIP marketplace flow (export from org A, import into org B) — explicit, audited, and not a runtime RLS predicate.
   **Re-trigger:** Permanent rejection. Cross-org sharing flows through ZIP marketplace, not direct RLS visibility.

4. **Idea:** Per-dept rate limiting (Redis token-bucket enforcement at the dept level).
   **Why tempting:** Enterprise governance — Finance dept gets 100 RPM; Marketing gets 500. Fine-grained spend control.
   **Why not now:** Deferred to v3.3 + Open Platform. Redis token-bucket lives in v3.3 (where the public API consumes it); v3.2 ships only the data-layer (`org_rate_limits` schema). Per-dept rate limits would also require dept-aware request routing which is meaningful only for the public API (where service-account → dept mapping matters), not the SPA.
   **Re-trigger:** v3.3 Open Platform implementation phase OR enterprise customer explicitly requests per-dept quota.

5. **Idea:** Schema choice — Supabase project per org (data-layer isolation) instead of single Supabase + org_id discriminator + RLS (application-layer isolation).
   **Why tempting:** Strongest possible isolation; data residency per-customer (valuable for GDPR / EU customers); matches the on-prem deployment shape exactly (each on-prem install = one Supabase = one org); per-org backups become trivial.
   **Why not now:** Per Q-v3.2-01 recommendation: single-Supabase + RLS for co-tenant SMB; per-org Supabase project for dedicated/on-prem enterprise. **Hybrid via DEPLOYMENT, not data-layer.** A pure per-org Supabase model would force every co-tenant SMB customer onto their own Supabase instance — operationally infeasible at SMB pricing and fights `D-PRD-10` Standard tier. The hybrid model gets both: SMB pays for shared infrastructure; enterprise customers requiring data residency get their own Supabase via dedicated/on-prem deployment of the same codebase.
   **Re-trigger:** First enterprise customer requires data residency in a specific region AND the cost of standing up a per-customer Supabase project is justified by their contract. Solved by dedicated/on-prem path, not by changing the co-tenant data-layer model.

6. **Idea:** Custom role definitions — org-admin can define new role tiers beyond super-admin / org-admin / dept-admin / member with arbitrary permission combinations.
   **Why tempting:** Flexible RBAC matches Glean's role customization. Enterprise IT often has bespoke role hierarchies (Reviewer, Auditor, Approver, etc.).
   **Why not now:** v3.2 ships 4 fixed role tiers with seeded permission sets; org-admins can extend permission grants on existing tiers but cannot define new tiers. Fixed tiers keep the RLS predicate constant time (4 tiers = 4 enum cases). Custom role definitions add a `roles.parent_role_id` recursion + permission inheritance computation that complicates RLS. Defer until enterprise customer demand validates the cost.
   **Re-trigger:** v3.3 customer feedback OR an explicit RBAC-customization deal blocker. Promote to its own phase.

7. **Idea:** SCIM provisioning (System for Cross-domain Identity Management) — automated user lifecycle from IdP (offboarding when employee leaves, role changes when promoted).
   **Why tempting:** Enterprise IT requirement for clean offboarding without manual `org_members` row management. Significant value for orgs with high turnover.
   **Why not now:** SAML+OIDC JIT provisioning covers v3.2 enterprise needs (auto-provision on first SSO login). SCIM adds an API surface and IdP-side configuration that's non-trivial. Defer until first enterprise customer requires offboarding-via-SCIM specifically.
   **Re-trigger:** First enterprise customer's IT requires SCIM as a deal blocker. Likely lands as a v3.3 add-on or v3.4 optional integration.

## 14. Competitive positioning paragraph

v3.2 positions Agentic RAG against **Glean** (org-aware closed SaaS — buyers cannot inspect or audit RLS predicates; v3.2 ships transparent SECURITY INVOKER policies you can read line-by-line in `supabase/migrations/`) and **M-Files** (org-tenancy native but heavy enterprise-only deploy with no SMB co-tenant story). Three differentiators ship in this milestone. **First: same-codebase hybrid deployment.** Per `D-PRD-02` (locked) and Q-v3.2-01, v3.2 pairs SaaS shape for SMB (single Supabase + org_id + RLS, free-tier-eligible) with on-prem isolation for enterprise (customer-owned Supabase, same codebase, full data residency). Glean is hosted-only — every customer's data sits on Glean's infrastructure with no on-prem option. M-Files is enterprise-only — no realistic SMB onboarding path. v3.2's SAML 2.0 + OIDC SSO via `sso_configs` works identically in both delivery shapes. **Second: transparent, auditable RLS.** Closed SaaS competitors require their buyers to trust opaque "RLS-equivalent" claims (which often don't survive scrutiny). v3.2's RLS predicates are readable SQL in the open `supabase/migrations/` directory — line-by-line auditable by enterprise security teams during procurement. The SECURITY INVOKER rewrite of `match_document_chunks` (`CONCERNS.md:69-76` → SECDEF-AUDIT-01) and `query_user_documents` structurally eliminates the SECURITY DEFINER bypass class — buyers can verify the absence of the highest-severity bug class by reading the function definitions. **Third: org primitives ship before automations and public API.** v3.3 service accounts inherit org context from day 1 (cannot be retrofitted); v3.4 automations (scheduled runs) inherit org context natively; v3.5+ vertical packs slot in as add-ons (per `D-PRD-11` market shape). M-Files retrofitted multi-tenancy late and the seams show in their API surface; Glean's API is org-aware but undocumented. Doing v3.2 in the right place in the roadmap is itself a competitive moat — every later milestone is org-aware by construction, not by patch. The 17 migrations + per-table RLS rewrite are the largest single architectural shift in the project's history; doing it now means v3.3 (Open Platform) ships against a clean substrate.
