# PRD: Agentic RAG — Milestone v3.3 (Open Platform: API + MCP + Service Accounts)

**Defined:** 2026-05-10
**Author:** PRD-reset Plan 07
**Reserved migration range:** `095 – 109` (per `.planning/prd-reset/MIGRATION-RESERVATIONS.md`)

---

## 1. Header

v3.3 opens the agent's capabilities to other apps via three surfaces, all sitting on the multi-worker substrate v2.6 unblocked. **Surface 1: a versioned REST API** at `/api/v1/*` mirrors the 13 existing internal route modules (`audit`, `documents`, `feedback`, `folders`, `kb`, `knowledge_health`, `runs`, `sandbox_outputs`, `settings`, `skills`, `test_fixtures`, `threads`, plus the v3.2-introduced multi-tenancy admin routes) with public-shape Pydantic schemas, explicit pagination, an OpenAPI 3.1 spec, and bearer-token auth. **Surface 2: an MCP (Model Context Protocol) server** — open-source under Apache 2.0 in a separate repo `agentic-rag-mcp` — exposing `search_documents`, `read_document`, `query_tables`, `execute_code`, `list_skills`, `run_skill`, and `chat` as MCP tools with both stdio transport (Claude Desktop / Cursor / Cline / Goose) and HTTP transport (cloud-to-cloud agent orchestration). **Surface 3: org-scoped service accounts plus webhooks plus rate limiting** — service accounts inherit v3.2's tenancy primitives, webhook deliveries are HMAC-signed with at-least-once retry semantics, and Redis token-bucket rate limiting enforces per-org-tier baselines + per-key sub-limits + per-endpoint overrides for expensive ops. Two open-source client SDKs (Python + TypeScript v1, Apache 2.0, separate repos generated from the OpenAPI spec) and a `/docs` documentation site round it out. **Strategically, v3.3 is the headline differentiator vs Glean** (closed SaaS, no public API, no MCP) **and OpenAI Assistants** (proprietary, no self-host, no MCP server) per `D-PRD-05`: after v3.3 ships, Agentic RAG is the only enterprise-grade self-hostable RAG platform that's first-class addressable from any MCP-compatible host.

## 3. Scope

**Theme A — Versioned REST API (`/api/v1/*`)**
- Public namespace `/api/v1/*` separate from the existing internal routes; the 13 internal modules each get a public-shape mirror with explicit Pydantic request/response models (separate from internal models — the public schema is a stable contract, internal models are free to evolve). *Carries: SEED-013 §Phase-1, RECOVERED_Harnessing_Agents Opportunity D, `D-PRD-03`.*
- OpenAPI 3.1 spec auto-generated by FastAPI; served at `/api/v1/openapi.json` + a Swagger-UI-rendered `/api/v1/docs` page; gated behind an "API enabled" flag per org. *Carries: SEED-013 §Phase-1.*
- URL-prefix-only versioning (`/api/v1/`); no Accept header version negotiation (Q-v3.3-06). Future `/api/v2/` would coexist for a deprecation window. *Carries: SEED-013 architectural notes.*
- Explicit pagination on all list endpoints (`page` + `per_page` + total-count header) — internal routes today are inconsistent (some paginate, some don't); the public mirror normalizes. *Carries: SEED-013 §Phase-1, lateral-thinking surface (this PRD).*
- Idempotency-key support on all mutating `/api/v1/*` endpoints (`Idempotency-Key` header → `idempotency_keys` table with 24h TTL); paired with at-least-once webhook delivery (Theme C). *Carries: lateral-thinking surface (this PRD), Q-v3.3-07.*

**Theme B — Service Accounts + API Keys**
- `service_accounts` table — per-org bearer-token-issuing entity. RLS keyed on `org_id`, scoped under `orgs` from v3.2. Org-admin can mint / rotate / revoke via the v3.1 admin shell. *Carries: SEED-013 §Phase-1, `D-PRD-02` org-aware-from-day-1 implication.*
- `api_keys` table — keys issued under a service account. Each key has a `prefix` (last 4 chars stored plain for ID) + `hash` (SHA-256 of full token). Rotation flow issues a new key, leaves old key valid for a 7-day grace period, then revokes. *Carries: SEED-013 §Phase-1.*
- **Auth model: Supabase JWT-shaped bearer** (Q-v3.3-01 recommendation) — the service account row stores a `jwt_template` payload `{sub: <service_account_id>, role: 'service_account', org_id: <uuid>, scopes: [...]}`; the issuance flow signs this payload server-side with the project's JWT secret using Supabase's HS256 — the bearer IS a Supabase JWT, so existing RLS policies (rewritten by v3.2 to be membership-keyed) apply automatically. No parallel auth path. *Carries: Q-v3.3-01 recommendation, `D-PRD-02` RLS-shift implication, lateral-thinking surface (this PRD).*
- API key scopes — capability-flags per-resource (`documents:read`, `documents:write`, `skills:execute`, `runs:create`, `kb:search`, `sandbox:execute`, `webhooks:manage`, `admin:read`) — composable; the SDK can negotiate scopes at runtime; RLS still enforces ownership. Q-v3.3-08 recommendation. *Carries: SEED-013 §Phase-1, Q-v3.3-08.*
- API key issuance UI — org-admin surface in v3.1 admin shell extended to create / list / rotate / revoke keys + view per-key usage and last-used-at. *Carries: SEED-013 §Phase-1 step 2, SEED-012 cross-ref.*

**Theme C — MCP Server (open-source, Apache 2.0, separate repo `agentic-rag-mcp`)**
- New repo `agentic-rag-mcp` under Apache 2.0; Python implementation; depends on the official `mcp` Python SDK. Talks to the closed-core backend ONLY via `/api/v1/*` REST calls — no shared internal modules per `D-PRD-03`. *Carries: SEED-013 §Phase-2, RECOVERED_Harnessing_Agents Opportunity D, `D-PRD-03`.*
- Both transports per Q-v3.3-02 recommendation: **stdio transport** for desktop hosts (Claude Desktop / Cursor / Cline / Goose / future MCP-compatible clients) — distributed as a `pip install agentic-rag-mcp` binary that reads `AGENTIC_RAG_API_BASE` + `AGENTIC_RAG_API_KEY` from env; **HTTP transport** for cloud-to-cloud agent orchestration — exposes `/mcp/v1/*` HTTP endpoints from the closed-core backend using the MCP HTTP+SSE transport spec. *Carries: SEED-013 §Phase-2, Q-v3.3-02.*
- MCP tool surface (6 tools v1, scoped narrow per SEED-013 §pitfalls "scope to 5-6 highest-value tools"): `search_documents` (semantic + filter args), `read_document` (by ID), `query_tables` (text-to-SQL bounded by user's scope), `execute_code` (sandbox; gated by `sandbox:execute` scope + `SANDBOX_ENABLED`), `list_skills`, `run_skill`. *Carries: SEED-013 §Phase-2 explicit list, RECOVERED_Harnessing_Agents Opportunity D explicit list.*
- MCP resources (read-only): `documents/{id}`, `folders/{id}`, `skills/{id}` — surfaced so MCP-aware hosts can present native browse views. *Carries: SEED-013 §Phase-2.*
- MCP prompts (pre-built workflows): `summarize_recent_uploads`, `find_documents_about`, `run_skill_with_inputs` — three v1 templates; consumers can write more. *Carries: lateral-thinking surface (this PRD).*

**Theme D — Webhooks**
- `webhooks` table — per-org outbound webhook configurations. Columns: `id`, `org_id` (FK), `url`, `secret` (HMAC signing key), `events[]` (subscribed event names), `active`, `created_at`. Org-admin manages via v3.1 admin shell. *Carries: SEED-013 §Phase-3.*
- `webhook_deliveries` table — per-delivery attempt log. Columns: `id`, `webhook_id`, `event_type`, `payload jsonb`, `status` (`pending` | `success` | `failed` | `dead_letter`), `attempt_count`, `last_attempted_at`, `last_response_code`, `last_response_body`. RLS keyed on `org_id` via FK. *Carries: SEED-013 §Phase-3.*
- Delivery semantics: at-least-once with HMAC signing + retry-with-exponential-backoff (Q-v3.3-07). Up to 5 retries (1s / 5s / 30s / 5min / 30min); after 5 failures, moved to `dead_letter` status. Consumers handle deduplication via `Idempotency-Key` header (paired with the `idempotency_keys` Theme A table). HMAC signature in `X-Agentic-RAG-Signature` header (`sha256=<hex>` of HMAC-SHA256(payload, secret)). *Carries: SEED-013 §Phase-3 architectural-notes, Q-v3.3-07 recommendation.*
- Subscribed events v1: `run.completed`, `run.failed`, `document.ingested`, `document.failed`, `skill.executed` — five event types; consumers can subscribe to any subset. *Carries: SEED-013 §Phase-3 explicit list.*
- Webhook delivery worker — background process (sibling worker per `D-PRD-08` multi-worker discipline) that consumes from a Redis Stream `webhooks:pending` and POSTs to subscriber URLs. Failed deliveries re-enqueue with TTL-based delay. *Carries: SEED-013 §Phase-3, `D-PRD-08`.*
- **Inbound webhook deferred** — only outbound in v3.3. Inbound (e.g. "ingest this S3 URL") routes through the public REST API (`POST /api/v1/documents/ingest-url`) instead of an inbound webhook. *Lean note: inbound deferred to v3.4 if signal exists.*

**Theme E — Rate Limiting (Redis token-bucket)**
- Stacked rate limit per Q-v3.3-03 recommendation: **per-org tier baseline** (Standard: 60 req/min / 1k req/day; Pro: 300 req/min / 10k req/day; Enterprise: 1000 req/min / unlimited daily — calibrated against `D-PRD-10`); **per-key sub-limit** (org-admin can set lower limits per consumer when granting keys to less-trusted apps); **per-endpoint optional override** for expensive ops (`execute_code`: 10 req/min/key, `analyze_document`: 30 req/min/key, `run_skill`: 30 req/min/key). *Carries: SEED-013 §Phase-1 step 3, `D-PRD-10`, Q-v3.3-03 recommendation, SEED-001 partial dependency.*
- Implementation: Redis token-bucket with sliding-window-counter fallback for daily caps. Keys: `ratelimit:org:{org_id}:{minute_window}`, `ratelimit:key:{api_key_id}:{minute_window}`, `ratelimit:endpoint:{api_key_id}:{endpoint}:{minute_window}`. Cross-worker safe (Redis is the source of truth — multi-worker discipline per `D-PRD-08`). *Carries: SEED-013 architectural-notes, `D-PRD-08`.*
- Standard rate-limit response headers on every `/api/v1/*` response: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. 429 response includes `Retry-After` header. *Carries: lateral-thinking surface (this PRD).*

**Theme F — CORS Policy Upgrade**
- Replace `allow_origin_regex=r"http://localhost:\d+"` (currently in `backend/app/main.py:107-109` per `CONCERNS.md:543`) with explicit per-API-key origin allow-list (Q-v3.3-04 recommendation). Each API key has an `allowed_origins text[]` column; CORS middleware decides per-request based on the bearer token's API key claim. The frontend dev origin (`localhost:5173`) is preserved as a hard-coded fallback for the React app's Supabase JWT auth path (which is not API-key-shaped). *Carries: SEED-013 architectural-notes, `CONCERNS.md:543`, Q-v3.3-04 recommendation.*

**Theme G — Client SDKs (open-source, Apache 2.0, separate repos)**
- `agentic-rag-python` repo (Apache 2.0) — Python SDK generated from OpenAPI 3.1 spec via `openapi-python-client`. Shipped as `pip install agentic-rag`. *Carries: SEED-013 §Phase-4, `D-PRD-03`, Q-v3.3-05 recommendation.*
- `agentic-rag-typescript` repo (Apache 2.0) — TypeScript SDK generated from OpenAPI 3.1 spec via `openapi-typescript-codegen`. Shipped as `npm install @agentic-rag/sdk`. *Carries: SEED-013 §Phase-4, `D-PRD-03`, Q-v3.3-05.*
- Both SDKs include: typed request/response models, automatic retry-with-backoff on 429 + 5xx, idempotency-key auto-generation on mutating calls, SSE-stream client for `/runs/{id}/stream`, MCP-tool-call helpers. *Carries: SEED-013 §Phase-4.*
- 5-minute integration guide + 3 code samples per SDK (chat, search, skill execution). Published on `/docs` site. *Carries: SEED-013 §Phase-4.*
- **Other languages: community-driven** per Q-v3.3-05 — we publish OpenAPI + MCP spec; community generates Go / Java / Ruby / Rust SDKs. *Carries: Q-v3.3-05 recommendation.*

**Theme H — Per-API-Key Observability (consumes v3.1 admin shell)**
- `runs` table grows a `service_account_id` nullable column + `api_key_id` nullable column to attribute traffic. *Carries: SEED-013 §Phase-1 step 5.*
- Audit-log entries grow same columns. *Carries: SEED-013 §Phase-1 step 5.*
- v3.1 admin shell extended with: per-key usage chart (req/min over 24h), per-key latency p50/p95/p99, per-key error rate, per-key last-used-at. Org-admin sees consumers under their org; super-admin sees all. *Carries: SEED-013 §Phase-1 step 5, SEED-012 cross-ref.*
- Per-org cost attribution surface (v1: minimal — req-count + LLM-token-count per key; full per-LLM-token-cost rollup deferred to v3.4 spend caps work per SEED-014 cross-ref). *Carries: SEED-013 §pitfalls, lateral-thinking surface (this PRD).*

**Theme I — API Documentation Site**
- Auto-generated Swagger-UI at `/api/v1/docs` (FastAPI default). *Carries: SEED-013 §Phase-1 step 4.*
- ReDoc rendering at `/api/v1/redoc` for read-friendly long-form docs. *Carries: lateral-thinking surface (this PRD).*
- Static site at `/docs` (separate path, not `/api/v1/docs`) — serves the SDK guides, MCP integration guide, webhook integration guide, "5-minute integration" tutorials. Built from Markdown sources in the closed-core repo's `backend/docs-site/` directory. *Carries: SEED-013 §Phase-4.*

## 5. Architecture & Data Model changes

**Migration numbers claimed:** `095`, `096`, `097`, `098`, `099`, `100`, `101`, `102`, `103`, `104`. Ten of the 15 reserved slots used; `105–109` remain as buffer for unanticipated phase-level discoveries. Matches `MIGRATION-RESERVATIONS.md` row for v3.3 (range `095 – 109`, width 15).

**New tables:**
- `service_accounts` — per-org service-account records. ## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** Add a **gRPC API** alongside REST + MCP for high-throughput service-to-service integration.
   **Why tempting:** gRPC has lower latency than REST (binary protobuf, HTTP/2 multiplexing) and is the canonical choice for microservice-to-microservice traffic in production-grade enterprise stacks. Some buyers may ask for it.
   **Why not now:** REST + MCP cover the platform-host integration cases (`D-PRD-05` competitive frame). gRPC is internal-service-mesh tooling — it's not something a Cursor / Claude Desktop / customer-app developer reaches for. Shipping gRPC would force a parallel implementation of every public route + a parallel SDK gen path, doubling maintenance for a marginal use case. The mid-large enterprise buyer profile (`D-PRD-01`) may want gRPC INTERNALLY but not as the agent platform's external API surface.
   **Re-trigger:** A specific enterprise customer commits and explicitly requires gRPC for their service-mesh integration AND won't accept REST + retry. Then build gRPC as an add-on under their commercial deployment.

2. **Idea:** Add a **GraphQL API** as the primary public API surface (or alongside REST).
   **Why tempting:** GraphQL gives consumers exactly the fields they want, eliminates over-fetching, and has strong tooling (Apollo Client, urql, GraphiQL). Modern consumer apps default to it.
   **Why not now:** Schema-explosion liability — every internal-route resource would need GraphQL types AND REST types AND OpenAPI mirrors AND Pydantic mirrors. OpenAPI 3.1 + REST gives consumers all the discovery they need; over-fetching isn't a real bottleneck at the request volumes v3.3 targets. GraphQL also makes per-endpoint rate limiting (`execute_code`, `analyze_document`) much harder — every query is a single endpoint that fans out internally. Opens an attack surface (query depth limits, query complexity scoring) that REST sidesteps.
   **Re-trigger:** Multiple enterprise customers ask for it specifically AND community SDK adoption stalls. Then re-evaluate whether GraphQL solves the actual integration friction.

3. **Idea:** Use **WebSocket as the alternative (or replacement) to SSE** for streaming run results from `/api/v1/runs/{id}/stream` and the MCP HTTP transport.
   **Why tempting:** WebSocket is bidirectional, has wider browser support for full-duplex flows, and supports binary frames. Some MCP clients prefer it.
   **Why not now:** SSE is already the run-streaming substrate (`D-v2.5-08`). Adding WebSocket would force a parallel implementation of run-replay-and-tail logic, double the test surface, and break the run-backed streaming invariant that disconnect/reconnect is harmless. SSE works fine for the unidirectional server→client streaming pattern v3.3 needs; bidirectionality would actually make MCP harder (the MCP spec defines its own request/response framing on top, not WebSocket-native).
   **Re-trigger:** MCP spec officially deprecates HTTP+SSE transport in favor of WebSocket. Then re-evaluate.

4. **Idea:** Ship a **plugin marketplace API** in v3.3 — endpoints for third-party developers to publish custom MCP tools / skills that consumers of our platform can install.
   **Why tempting:** Closes the loop on the open-source MCP standard story (`D-PRD-03`); creates a network effect; positions Agentic RAG as the platform-of-platforms.
   **Why not now:** Plugin marketplaces are an enormous scope of work — sandboxing third-party code, vetting + reviewing submissions, billing + revenue share, takedown / abuse handling, version compatibility tracking. Not v3.3 scope. The agentskills.io ZIP-format spec ships open per `D-PRD-03` (in v2.0 already), but the discovery / hosting / installation service is its own milestone.
   **Re-trigger:** First customer asks for a third-party-tool installation flow (vs writing their own MCP tools), OR community MCP-tool ecosystem proves real. Promote to its own dedicated milestone (~v3.5+).

5. **Idea:** **OAuth2 client_credentials** flow for service accounts (instead of long-lived bearer tokens).
   **Why tempting:** OAuth2 is the canonical enterprise API auth pattern; some customers' security teams will require it. Short-lived access tokens reduce key-leak blast radius.
   **Why not now:** Q-v3.3-01 recommendation chose Supabase JWT-shaped bearer because it inherits RLS automatically — no parallel auth path. OAuth2 client_credentials would require a separate authorization server endpoint, refresh-token machinery, and a different RLS evaluation path. All for a security improvement (short-lived tokens) that's already partially available via key rotation (SVC-ACCT-03's 7-day grace).
   **Re-trigger:** A specific enterprise customer's security review explicitly requires OAuth2 client_credentials. Then add it as a parallel auth path in v3.3.5 or a later milestone.

6. **Idea:** **String-based scopes** (`"read"`, `"write"`, `"admin"`) instead of capability-flags-per-resource (`documents:read`, `skills:execute`).
   **Why tempting:** Simpler — three strings to remember, simpler UI, simpler SDK. Matches OAuth2's typical scope shape.
   **Why not now:** Q-v3.3-08 recommendation chose capability flags because they're composable (an SDK can negotiate just the scopes it needs) and they let org-admins grant least-privilege per consumer (`documents:read` only — can't write skills, can't call execute_code). String-based scopes either over-grant (`"read"` covers everything readable, including potentially sensitive admin observability) or under-grant (force consumers to ask for `"admin"` for routine work). RLS still enforces ownership at the row level regardless of scope, but scope is a defense-in-depth layer.
   **Re-trigger:** Capability-flag-per-resource design proves cumbersome in practice (consumers always ask for the same 3-4 scope combos). Then add convenience aliases (`scopes: ["read"]` expands to `["documents:read", "folders:read", "skills:read"]`) without removing the granular form.

7. **Idea:** **Exactly-once webhook delivery** via outbox pattern (vs at-least-once + idempotency-key per Q-v3.3-07).
   **Why tempting:** Customers strongly prefer exactly-once semantics — at-least-once means consumers MUST handle deduplication on their end, which is friction.
   **Why not now:** Outbox pattern requires a transactional table write coupled to every event-emitting operation; rolling that out across 5+ event sources (run.completed, document.ingested, skill.executed, etc.) is significant scope. At-least-once + idempotency-key (sent in `Idempotency-Key` header) gives consumers a clean dedup primitive without the outbox-table cost. Most well-built consumer integrations already handle dedup; the friction is bounded.
   **Re-trigger:** Consumer feedback explicitly cites dedup pain. Then implement outbox pattern as a v3.3.x followup.

## 14. Competitive positioning paragraph

v3.3 is the milestone that makes Agentic RAG categorically different from **Glean** (the primary enterprise-search competitor per `D-PRD-05`) and **OpenAI Assistants API** (the secondary agent-capability competitor). Three differentiators ship. **First: open OpenAPI 3.1 + MCP spec means consumers can integrate in any language, today.** Glean is closed SaaS — its API is REST but proprietary, undocumented for self-host, and there's no MCP server; customers can't bring Glean's KB into Claude Desktop, Cursor, or Cline. OpenAI Assistants is proprietary endpoints, no self-host, no MCP. By shipping `/api/v1/*` REST + the open-source `agentic-rag-mcp` Apache-2.0 server + Python + TypeScript SDKs (also Apache 2.0), Agentic RAG becomes the only enterprise-grade RAG platform addressable from any MCP-compatible host AND embeddable in any customer app via SDK. **Second: self-hostable means customer keeps data sovereignty.** Glean is hosted-only; OpenAI Assistants stores user data on OpenAI's infrastructure. Both are deal-breakers for regulated-industry customers (legal, finance, healthcare) and any customer with EU data-residency or air-gapped requirements. v3.3's public API ships on the same closed-core deployment customers already self-host (`D-PRD-02` hybrid SaaS posture) — programmatic access without giving up sovereignty. **Third: MCP-native means the platform is first-class addressable from the agent host the user already chose.** When a Cursor user asks *"what does my Q4 report say about revenue?"*, Cursor connects to `agentic-rag-mcp` and runs `search_documents` against the user's KB — without that user leaving Cursor, without buying a second product, without writing integration code. No other RAG product is MCP-native today. The org-scoped service accounts (inheriting v3.2's tenancy primitives), HMAC-signed webhooks with at-least-once retry, Redis token-bucket rate limiting tied to `D-PRD-10`'s 3-tier pricing, and per-API-key observability in the v3.1 admin shell give enterprise IT the operational primitives they need to actually deploy this in production at scale. After v3.3 ships, the strategic question for Glean and OpenAI shifts from "should we add an API?" to "should we open-source our integration surface?" — which neither of their corporate structures permits.
