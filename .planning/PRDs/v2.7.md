**Defined:** 2026-05-12

## 1. Header

v2.7 ships the substrate three downstream milestones depend on. Four workstreams compose: (1) a **per-thread Workspace Filesystem** — the agent's persistent "scratchpad" of files (`/plan.md`, `/research/notes.md`, …) that survive across turns, versioned automatically, and stored hybrid (small inline / large in Supabase Storage); (2) a **Harness Engine** — a state-machine workflow runtime that constrains the LLM to locked phases for deterministic execution, with 5 phase types (`programmatic`, `llm_single`, `llm_agent`, `llm_batch_agents`, `llm_human_input`) and tool-dispatcher enforcement of per-phase tool sets so the LLM cannot skip, reorder, or escape phases; (3) a **right-side Panel UI** mirroring Claude.ai's artifact surface — todos, locked plan / phase indicator, workspace file browser with diff viewer, and pending-user-input prompts — riding the v2.6 `<StreamsProvider>` Context as a second concurrent stream consumer; (4) a **Plugin Contract** that formalizes the extension API for tools, panel renderers, phase types, file-type previews, data sources, and secrets adapters — the contract Episode 6 deliberately rejected but that our enterprise focus + D-PRD-11 vertical-pack roadmap make load-bearing. Three new General-Mode LLM tools ship alongside: `write_todos` (manage the right-side todo list), `task` (spawn delegated sub-agents — replaces ad-hoc `run_sub_agent` per skill), and `ask_user` (pause for actionable user input rendered in the panel). A dual-mode UX (Deep Mode default vs Harness Mode triggered by workflow-mode skills or user toggle) wraps everything; mid-thread switching is allowed but locks once a workflow begins. Strategically v2.7 ships BEFORE v3.0 so that Skill Studio (v3.0 Theme F Multi-Agent Orchestration) reframes as a harness workflow template, v3.4 Automations (routine_definitions) run as harness workflows by default, and v3.5+ vertical packs (legal/finance/healthcare) plug into the formal contract instead of forking core. Differentiates against **Claude.ai** (artifact panel but closed/Anthropic-only) and **ChatGPT canvas** (similar but closed/OpenAI-only, no plugin contract, no harness state machine) on three binary wins: self-hostable, multi-provider, plugin-extensible.

## 3. Scope

**Theme A — Per-thread Workspace Filesystem**
- `workspace_files` table: per-thread virtual files (`/plan.md`, `/research/notes.md`, …). Columns: `id uuid pk`, `thread_id uuid fk`, `path text` (case-sensitive, must start with `/`), `content_inline bytea nullable`, `content_storage_url text nullable` (mutually exclusive with `content_inline` — hybrid storage per Q-v2.7-01), `size_bytes bigint`, `mime_type text`, `created_by text` (`'agent' | 'user'`), `created_at timestamptz`, `updated_at timestamptz`, `org_id uuid nullable` (set in v3.2 multi-tenancy). UNIQUE on `(thread_id, path)`. RLS: `auth.uid() = (select user_id from threads where id = thread_id)`. *Carries: lateral-thinking — case-sensitive paths match POSIX expectations skill authors carry over from Unix filesystems; Q-v2.7-01.*
- `workspace_file_versions` table: per-file version history. Columns: `id uuid pk`, `workspace_file_id uuid fk`, `version int` (incrementing within file), `content_inline bytea nullable`, `content_storage_url text nullable`, `size_bytes bigint`, `delta_from_prev jsonb nullable` (efficient three-pane diff render — null on version 1), `committed_by text`, `committed_at timestamptz`. UNIQUE on `(workspace_file_id, version)`. RLS inherits via workspace_file_id FK. Auto-version every write per Q-v2.7-02 recommendation (a); explicit "publish version" deferred to v3.x. *Carries: Q-v2.7-02.*
- Hybrid storage shape (Q-v2.7-01 recommendation c): files ≤ 256KB store as `content_inline bytea`; files > 256KB upload to a NEW `workspace-files` Supabase Storage bucket with path `{thread_id}/{file_id}/v{version}.bin` and store the signed-URL in `content_storage_url`. Threshold is admin-tunable via `app_settings.workspace_inline_threshold_bytes`. The pattern mirrors Phase 067.4 sandbox-outputs bucket (`backend/app/api/sandbox_outputs.py:48-67`). *Carries: Q-v2.7-01.*
- New tools (registered General Mode only — see Theme C for the full mode-gating rules): `workspace_write(path, content)`, `workspace_read(path, version=null)`, `workspace_list(prefix='/')`, `workspace_diff(path, from_version, to_version)`, `workspace_delete(path)`. *Carries: thesis bullet 1.*
- New SSE event types ride existing `run:{run_id}` stream (per `D-v2.5-08`): `workspace_file_written{path, version, size_bytes, mime_type}`, `workspace_file_deleted{path}`. The right-side panel's file browser subscribes via the same `<StreamsProvider>` Context that chat reads from.

**Theme B — Harness Engine (State Machine)**
- `workflow_definitions` table: reusable workflow templates. Columns: `id uuid pk`, `slug text` (e.g. `contract-review-pipeline`), `name text`, `version text` (semver — mirrors `D-PRD-13` skill versioning pattern), `description text`, `phases jsonb` (ordered list of phase configs — see Theme B-phase-config sub-bullet), `entry_phase text` (slug of first phase), `created_by uuid`, `org_id uuid nullable`, `published_at timestamptz nullable`. UNIQUE on `(slug, version)`. Immutable on publish per D-PRD-13 mirror (DB trigger enforces — same shape as `skill_versions` immutable trigger). RLS: owner private + org-shared. *Carries: thesis bullet 2; `D-PRD-13` mirror.*
- `workflow_runs` table: instances of workflow execution. Columns: `id uuid pk`, `workflow_definition_id uuid fk`, `thread_id uuid fk`, `run_id uuid fk` (link to the existing `runs` Postgres row + Redis Stream — workflow runs piggyback on run-backed streaming), `current_phase_id uuid nullable`, `status text` (`'active' | 'paused' | 'awaiting_user' | 'completed' | 'failed' | 'cancelled'`), `started_at`, `completed_at`, `final_artifact_path text nullable` (workspace path of final output, e.g. `/output/report.md`), `org_id uuid nullable`. RLS via thread.
- `workflow_phases` table: per-run phase state. Columns: `id uuid pk`, `workflow_run_id uuid fk`, `phase_index int`, `phase_slug text`, `phase_type text` (`'programmatic' | 'llm_single' | 'llm_agent' | 'llm_batch_agents' | 'llm_human_input'`), `status text` (`'pending' | 'active' | 'gate_validating' | 'completed' | 'failed' | 'skipped'`), `started_at`, `completed_at`, `gate_passed bool nullable`, `output jsonb nullable`, `available_tools text[]` (canonicalized per-phase tool whitelist — enforced by dispatcher). UNIQUE on `(workflow_run_id, phase_index)`. *Carries: lateral-thinking — `available_tools` per-phase is the canonical store the dispatcher reads; refusing tools not in this set is the state-machine enforcement.*
- Phase-config jsonb shape (in `workflow_definitions.phases`): `{slug, phase_type, prompt_template, available_tools, model_override, max_steps, validators: [{kind, config}], gate_blocking: bool, on_failure: 'fail_run' | 'retry' | 'skip_to_phase:<slug>'}`.
- **5 phase types implemented:**
  - `programmatic` — backend executes a typed Python function registered in a `PROGRAMMATIC_PHASE_REGISTRY` dict; no LLM call. Use cases: deterministic data transforms, schema validation, file format conversion.
  - `llm_single` — single LLM call with curated tool set; response is the phase output. Use cases: classification, summarization, structured extraction.
  - `llm_agent` — multi-turn agent loop with curated tools; runs until self-terminates (no tool calls) or hits `max_steps` cap. Mirrors `agent_runner` (`backend/app/api/threads.py:1059`) but with the phase's `available_tools` whitelist enforced.
  - `llm_batch_agents` — N parallel sub-agents (researcher pattern from Opportunity B); each agent gets a slice of the input + the same tool whitelist. Outputs aggregated via deterministic merge (concat / dedupe / vote — `phase_config.merge_strategy`). Reuses the existing `task` tool (Theme C) for spawning.
  - `llm_human_input` — pause the run; emit `ask_user_prompt` SSE event; right-side panel renders an actionable prompt; on user response, harness resumes at the next phase.
- **Validation gates:** each phase declares `validators: [{kind, config}]`. Validator kinds v1: `json_schema` (output must match schema), `regex_match` (output text matches), `workspace_file_exists` (named file was written), `programmatic` (custom Python validator from `VALIDATOR_REGISTRY`). If `gate_blocking=true` and validators fail, phase status flips to `failed`, on_failure handler fires. *Carries: lateral-thinking — validators reuse the phase-registry pattern for symmetry with programmatic phases.*
- **State machine ENFORCEMENT** (the Episode 6 insight): the LLM cannot skip phases, reorder them, or terminate the workflow early. The tool dispatcher inside the agent loop reads `workflow_runs.current_phase_id` → `workflow_phases.available_tools` and refuses tool calls outside the whitelist with a structured `tool_not_available_in_phase` error fed back to the LLM context. Only the harness engine (a backend module, not the LLM) transitions phases. *Carries: thesis bullet 2; Episode 6's headline pattern.*
- Phase persistence (Q-v2.7-04 recommendation b): all phase state lives in Postgres (`workflow_phases` table). Workflow runs survive uvicorn restarts. Mirrors v3.4's `agent_checkpoints` pattern.
- New SSE event types: `workflow_phase_start{phase_slug, phase_type, index, available_tools}`, `workflow_phase_progress{phase_slug, detail}`, `workflow_phase_gate_check{phase_slug, validator_results}`, `workflow_phase_end{phase_slug, status, output_summary}`, `workflow_transition{from_phase, to_phase}`, `workflow_run_complete{status, final_artifact_path}`. All ride existing `run:{run_id}` Stream.

**Theme C — Three new LLM tools (`write_todos`, `task`, `ask_user`)**
- `write_todos(todos: list[Todo]) -> {accepted, version}`. Todo shape: `{id: str, content: str, status: 'pending' | 'in_progress' | 'completed' | 'cancelled', parent_id: str | None}`. Tool overwrites the thread's current todo list (full state replace, not diff — simpler invariants). Persists to a new `todos` table (Theme C-storage sub-bullet). Emits `todo_updated` SSE event; right-side panel renders live. Available in BOTH General and Explorer modes. *Carries: thesis bullet 3.*
- `task(description: str, agent_config: dict | None = None) -> {sub_run_id}`. Spawns a sub-agent for a delegated unit of work. Replaces the ad-hoc per-skill `run_sub_agent` calls (`backend/app/services/sub_agent_service.py:17`) with a single canonical entry point. `agent_config` keys: `model_override`, `system_prompt_override`, `tools` (subset of parent's available tools), `max_steps`. Sub-agent emits its events to its own `run:{sub_run_id}` Stream; parent observes via `tool_result` payload referencing the sub_run_id. Used by harness phase types `llm_agent` and `llm_batch_agents` under the hood. Available in BOTH modes. *Carries: thesis bullet 3; replaces ad-hoc per-skill sub-agent pattern.*
- `ask_user(prompt: str, options: list[str] | None = None, timeout_seconds: int | None = None) -> {response_text, choice_index}`. Pauses the agent loop; emits `ask_user_prompt` SSE event; right-side panel renders the prompt with optional choice buttons + free-text field; user response feeds back into agent context via tool_result. When called inside an `llm_human_input` harness phase, the harness drives the pause/resume; when called in Deep Mode, the agent loop pauses on its own (mechanism documented in §5 modified hot paths). Available in BOTH modes. *Carries: thesis bullet 3.*
- `todos` table (Theme C storage): `id uuid pk`, `thread_id uuid fk`, `todo_id text` (matches client-supplied id), `content text`, `status text`, `parent_id text nullable`, `created_at`, `updated_at`. UNIQUE on `(thread_id, todo_id)`. RLS via thread.
- All three tools register in the existing mode-conditional `get_tools()` site (`backend/app/services/openai_service.py` per `PROJECT.md:192-193`). Per-phase whitelist enforcement in Harness Mode wraps this — the global `get_tools()` answer is filtered by `workflow_phases.available_tools` when a workflow is active.

**Theme D — Right-side Panel UI**
- New top-level layout: chat surface (~70%) + right-side panel (~30%, collapsible). Toggleable via header button + keyboard shortcut. Default visibility: closed in Deep Mode, open in Harness Mode (auto-opens on workflow start). Mobile: panel becomes a bottom-sheet on screens <768px (per existing Aether responsive pattern).
- Panel renders 4 sections by default (Q-v2.7-06 architecture recommendation b — extend `<StreamsProvider>` Context to host both chat and panel consumers; single React tree, no iframe):
  - **Todos** — live `todos` table state with nesting (parent_id renders as indented children) and checkboxes (status flip → `write_todos` tool call from UI is OUT OF SCOPE in v1; status display is read-only). *Carries: thesis bullet 4 sub-bullet 1.*
  - **Plan / Workflow** — when a harness workflow is active: phase indicator (current/locked/completed glyphs), phase-type icon, transition log (latest 10 phases), gate-check pass/fail badges. When no workflow: section hidden.
  - **Workspace Files** — file browser for the thread's `workspace_files` rows. Click file → diff viewer (uses `workspace_file_versions.delta_from_prev` for rendering; falls back to fetch-both-versions when delta is null). File previews use the registered `file_preview` plugin renderer for the file's MIME type (Theme E); default text/markdown renderer ships in core.
  - **Pending User Input** — when an `ask_user_prompt` event arrives: actionable prompt with optional choice buttons + free-text field. Submit → POST to a thin new endpoint that pushes the response back into the producer's tool_result; harness resumes at the next phase. *Carries: thesis bullet 4 sub-bullet 4.*
- Streams Provider extension (the v2.6 lift's payoff): the existing `<StreamsProvider>` Context gains a second consumer surface (the panel). Both chat and panel subscribe to the SAME `run:{run_id}` Stream; the Context demultiplexes by event type. NO duplicate subscriptions; NO drift risk. *Carries: `D-PRD-06`; SEED-007 payoff lateral-thinking.*
- New frontend hooks: `useWorkflow(threadId)`, `useWorkspaceFiles(threadId)`, `useTodos(threadId)`, `useAskUserPrompt(threadId)`. All read from the lifted Context; reconcile via fetch on mount (per `D-v2.5-03` rule).
- New SSE event types consumed (all listed above in Themes A/B + the panel-specific ones): `workflow_phase_*`, `workflow_transition`, `todo_updated`, `workspace_file_written`, `workspace_file_deleted`, `ask_user_prompt`, `ask_user_response`.

**Theme E — Plugin Contract (D-PRD-16 candidate; see Q-v2.7-07)**
- `plugin_registry` table: installed plugins per-deployment. Columns: `id uuid pk`, `slug text unique`, `version text` (semver), `manifest jsonb`, `installed_by uuid` (super_admin user per D-PRD-14), `installed_at`, `enabled bool default false`. RLS: super_admin writes (per `D-PRD-14`); operators read; ordinary users see only the EFFECTIVE extension points exposed by enabled plugins, not the registry rows themselves. *Carries: thesis bullet 5; `D-PRD-14`.*
- `plugin_extension_points` table: extension hooks each plugin claims. Columns: `id uuid pk`, `plugin_id uuid fk`, `extension_type text` (`'tool' | 'panel_renderer' | 'phase_type' | 'file_preview' | 'data_source' | 'secrets_adapter'`), `config jsonb`, `priority int default 100` (deterministic ordering when multiple plugins extend the same point), `enabled bool default true`. UNIQUE on `(plugin_id, extension_type, config->>'name')` to prevent duplicate registrations. *Carries: thesis bullet 5.*
- **Plugin manifest schema** (JSON-Schema validated on install — schema lives at `backend/plugins/manifest_schema.json`): `name`, `slug`, `version` (semver), `description`, `author`, `agentic_rag_version` (semver constraint, e.g. `>=2.7.0,<3.0.0`), `extension_points: [...]`, `permissions: [...]` (list — what data/APIs the plugin needs; surfaced in install confirmation UI for super_admin), `assets: [...]` (list of bundled files — bundled JS for panel_renderers, bundled Python for tools/phase_types/etc.), `secrets: [...]` (named secrets the plugin needs; read via `D-PRD-15` SecretsBackend).
- **Extension types v1 (6 total):**
  - `tool` — new LLM tool registered into the agent's toolbox. Tool registration site is the existing `get_tools()` (`backend/app/services/openai_service.py` per `PROJECT.md:192-193`); plugin tools merge in. Per-phase whitelist (Theme B) still applies — plugin tools are subject to the same gating.
  - `panel_renderer` — custom right-side panel section. Plugin ships a bundled JS module exporting a React component; loaded via dynamic import. Examples: legal contract clause viewer (vertical pack), financial-model summary table (vertical pack). *Carries: lateral-thinking — vertical packs need custom panel sections; the contract is the seam.*
  - `phase_type` — custom harness phase beyond the 5 built-in. Plugin Python module registers its phase executor into `PHASE_TYPE_REGISTRY` at load. Example: `compliance_review` phase (legal pack), `pii_redaction` phase (healthcare pack).
  - `file_preview` — custom renderer for workspace files. Maps MIME type → React component. Default renderers ship in core (text, markdown, json); plugins extend (PPTX, DICOM, IFC).
  - `data_source` — custom RAG data source. Plugin implements a Python interface (`async retrieve(query, ...)`) that the existing `search_documents` tool dispatches to in addition to pgvector. Example: SharePoint connector (vertical pack), Confluence connector.
  - `secrets_adapter` — plugin implementation of D-PRD-15 SecretsBackend. Vault, Doppler, 1Password Connect, Infisical, AWS KMS BYOK. Implements `async get/set/rotate/list_keys()`. *Carries: `D-PRD-15`; SUMMARY.md §C.2 #3 BYOK clean extension point.*
- Plugin loading model (Q-v2.7-03 recommendation c — BOTH): static config via env var `PLUGINS_BOOTSTRAP=foo@1.0.0,bar@2.1.0` for self-host bootstrapping (read at lifespan startup; rows upserted into `plugin_registry`); runtime registry via super_admin UI at `/admin/plugins` (install/enable/disable/uninstall actions; the UI itself lives in v3.1 admin shell — v2.7 ships only the JSON API). *Carries: Q-v2.7-03.*
- **Skills become an IMPLICIT plugin type** — the existing `skills` table is interpreted by the contract as a plugin of extension type `tool` (the skill's instructions = tool description; the skill's tools = registered LLM tools). No re-registration required; the contract codifies what skills ALREADY are. The benefit: v3.5+ vertical packs can declare their pre-installed skills via plugin manifest, and the marketplace surface (v3.5+) sees skills and plugins through one lens.
- **MCP servers (v3.3) become an EXTERNAL plugin type** — registered via the contract but executed out-of-process (subprocess or remote HTTP). v3.3 PRD's MCP server registry rows can be reframed in v3.3 as a specialization of `plugin_registry` (single new column `delivery: 'in_process' | 'mcp_stdio' | 'mcp_http'`). v2.7 leaves this column nullable; v3.3 owns the population.
- **v3.5+ vertical packs ship as plugins through this contract.** Legal pack = manifest with custom `tool` (contract-classifier), `phase_type` (compliance_review), `file_preview` (contract-diff renderer), `data_source` (SharePoint), `panel_renderer` (clause summary). One install action; no code fork.

**Theme F — Dual-mode UX (Deep Mode vs Harness Mode)**
- **Deep Mode** (default — existing v2.6 behavior preserved unchanged): free-form chat; LLM controls flow; right-side panel hidden by default; `write_todos` / `task` / `ask_user` / workspace tools all available; no per-phase tool gating. *Carries: lateral-thinking — Deep Mode must remain the default to preserve current UX and avoid regressing existing users.*
- **Harness Mode**: triggered by (a) running a workflow-mode skill (skill metadata declares `skill_modes.harness_required: bool`), (b) user explicit "switch to plan mode" toggle in the chat input area, (c) plugin-shipped phase types that require harness (declared in plugin manifest). On entry: panel auto-opens, current workflow's phase indicator renders, tool whitelist enforced.
- **Mode-switching mid-conversation** (Q-v2.7-05 recommendation a-with-lock): allowed mid-thread; Deep → Harness spawns a new `workflow_runs` row; Harness → Deep is REFUSED until the active workflow completes or user explicitly cancels. New "Cancel workflow" affordance in panel.
- Thread metadata schema additions: `threads.deep_mode_metadata jsonb` (Deep-mode-specific state — todo list snapshot at last Deep-Mode message), `threads.active_workflow_run_id uuid fk` (nullable; populated only when a workflow is running).
- New skill metadata: `skill_modes.harness_required: bool` (default false). When set, the agent runtime auto-enters Harness Mode on skill invocation. Coordinates with v3.0's `skills.skill_modes` jsonb column — v2.7 lands the `harness_required` key shape; v3.0 already lands the column itself (Theme F of v3.0 PRD); v2.7's migration `134_skill_modes_harness_only.sql` adds the well-known key without breaking v3.0's other keys. *Carries: cross-PRD coordination — see §6 row for explicit conflict mitigation.*

## 5. Architecture & Data Model changes

**New tables:**
- `workspace_files` — per-thread virtual files (Theme A).
- `workspace_file_versions` — per-file version history (Theme A).
- `workflow_definitions` — reusable workflow templates (Theme B).
- `workflow_runs` — instances of workflow execution (Theme B).
- `workflow_phases` — per-run phase state with available_tools whitelist (Theme B).
- `todos` — per-thread todo list backing `write_todos` tool (Theme C).
- `plugin_registry` — installed plugins per-deployment (Theme E).
- `plugin_extension_points` — extension hooks each plugin claims (Theme E).
- `harness_audit` — audit-log subtype recording every phase transition + gate-check result + tool-refusal event for compliance traceability (Theme B observability — supports enterprise-grade auditable execution claim from §14).

**Modified tables:**
- `threads` — add `deep_mode_metadata jsonb nullable` (Deep-mode state snapshot) + `active_workflow_run_id uuid nullable fk` (set when a workflow is running). Migration `133_threads_deep_mode_metadata.sql`.

## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** Adopt **LangGraph** for the harness workflow orchestration.
   **Why tempting:** LangGraph is purpose-built for state-machine agent workflows. Saves implementation work — phase types, transitions, validators, parallelism all have first-class primitives.
   **Why not now:** **Project rule explicitly forbids it** (`CLAUDE.md` — "No LangChain, no LangGraph — raw SDK calls only"). The same rejection landed in v3.0 §10 for Multi-Agent Orchestration; precedent stands. The state machine v2.7 builds is intentionally simple (5 phase types, jsonb config) — well within hand-rolled scope. Adding LangGraph would also metastasize once introduced.
   **Re-trigger:** Project rule changes (would itself require a D-PRD-NN decision — this entry is the cross-reference).

2. **Idea:** Author workflows in **external YAML/CWL/Argo-style files** rather than DB rows.
   **Why tempting:** Industry-standard workflow languages (Argo Workflows, Common Workflow Language) have established tooling, syntax highlighting, version control via git, dry-run validators.
   **Why not now:** v2.7's goal is IN-PRODUCT workflow authoring — a vibe-coder edits a workflow in the app, runs it, iterates. External YAML files force file-system / git tooling and break the in-app iteration loop. The jsonb `phases` column in `workflow_definitions` is the in-product equivalent. Plugin manifests ARE external JSON/YAML — that's the right place for declarative shipped artifacts; workflows themselves are user-tunable in-product.
   **Re-trigger:** Customer demand for git-versioned workflows; v3.5+ vertical-pack workflows might ship as bundled-in-plugin YAML.

3. **Idea:** Ship a **visual workflow builder** (drag-and-drop phase composition) in v2.7.
   **Why tempting:** The harness is conceptually a graph; a visual builder would be the obvious UX. Buyers comparing to Glean's closed builder would see immediate parity.
   **Why not now:** Significant additional scope (canvas-based React component + edge-routing algorithm + drag-and-drop UX + validation overlay). v1 ships YAML/JSON `workflow_definitions` rows authored via API — operators and skill authors compose them programmatically. The visual builder is a v2.7.5 polish slot.
   **Re-trigger:** First non-developer user (operator / business analyst) needs to author workflows. v2.7's API-driven shape blocks that user shape; the visual builder unblocks.

4. **Idea:** **Real-time multi-user collaboration on workspace files** (live cursors, CRDTs).
   **Why tempting:** Workspace files are the agent's scratchpad — but a user editing alongside the agent (Google Docs-style) would be the dream UX. Pairs with v3.2 multi-tenancy where teams may co-edit.
   **Why not now:** No demand signal. CRDT infrastructure is significant complexity that doesn't compose with the existing run-backed streaming architecture. Listed in v2.6 §10 + v3.0 §10 with the same rejection — preserving the rejection here.
   **Re-trigger:** A vertical-pack customer (legal/finance) explicitly asks for it OR a competitor (Claude.ai) ships it.

5. **Idea:** **Plugin sandbox isolation via WASM** (run untrusted plugins in a sandboxed runtime).
   **Why tempting:** v3.5+ marketplace will surface community plugins; sandbox isolation is the proper trust-minimization story.
   **Why not now:** v1 plugins are first-party + community-vetted (the bootstrap-env-var path + super_admin install gate per `D-PRD-14`). Sandbox isolation is the marketplace-era concern; building it now for in-house plugins is premature optimization that locks the plugin Python API into a restricted shape.
   **Re-trigger:** v3.5+ marketplace milestone (post-vertical-pack era) or first untrusted-plugin install scenario.

6. **Idea:** Use the workspace filesystem as a **secondary RAG corpus** — index workspace files for retrieval.
   **Why tempting:** Workspace files (agent-written plans, research notes) are arguably the most relevant retrieval source for the current thread. Indexing them would let the agent reference its own past work.
   **Why not now:** Workspace files are PER-THREAD artifacts, not corpus-wide content. Indexing them would (a) explode the chunk store size linearly with thread count, (b) confuse the retrieval surface (workspace chunks would interleave with document chunks unless tagged), (c) require an opt-in user model (some users may not want their plan.md in retrieval). The `data_source` plugin extension type IS the right seam for a future "workspace-as-RAG" plugin that an opinionated user can install.
   **Re-trigger:** User demand surfaces; first vertical-pack customer asks for it.

## 14. Competitive positioning paragraph

v2.7 positions Agentic RAG against **Claude.ai** (Anthropic's flagship; closed/Anthropic-only with an artifact-side-panel surface that's the de-facto UX reference for agent-side workspaces) and **ChatGPT canvas** (OpenAI's parallel; closed/OpenAI-only, no plugin contract, no harness state machine).
