# PRD: Agentic RAG — Milestone v3.5 (Automations & Routines + Document Management Tier B)

**Defined:** 2026-05-10

## 1. Header

v3.4 ships the agent execution modes that move the product past synchronous chat. **Automations & Routines** turn the agent into a scheduled, triggered, or reactive worker against the user's KB — three modes: scheduled (cron-like — "every Monday 9am summarize last week's `/Legal/Contracts` arrivals"), triggered (event-driven — "when a doc is added to `/Legal`, run `contract-classifier`"), and reactive (webhook-driven via the v3.3 inbound webhook surface). **Agent Checkpointing** (RECOVERED_Harnessing_Agents Opportunity E) lands here too: long-running runs persist their state at tool-execution boundaries, survive disconnect, and resume mid-task — solving residual KI-001 architecturally and unblocking automations of arbitrary duration. **DM Tier B** layers the lifecycle features that make documents enterprise-manageable: per-folder/per-org retention policies, check-in/check-out for editing exclusivity, multi-step approvals, and a lifecycle audit feed. Strategically v3.4 is the moat-builder: **Glean has zero automation surface** (per `D-PRD-05`), **ChatGPT Tasks is closed and KB-blind**, and **n8n has no native KB connection** — automations against your own self-hosted KB, with org-level spend caps and arbitrary-duration agent runs, is a position no competitor occupies. The horizontal-core scope of DM Tier B (generic retention + check-in/out + linear approvals + lifecycle audit) ships here per `D-PRD-11`; vertical-pack-specific approval workflows (legal-specific routing, healthcare PHI retention) defer to v3.5+ and are explicitly carved out in §11.

## 3. Scope

**Theme A — Scheduler & Scheduled Runs**
- New `scheduled_runs` table with cron-shaped trigger (`cron_expression text`, `timezone text`, `next_run_at timestamptz`, `last_run_at timestamptz`, `org_id uuid`, `owner_user_id uuid`, `skill_id uuid` FK, `inputs_json jsonb`, `status text`, `error text`). RLS: org-members see org-routines they are allowed to see; private routines are owner-only. *Carries: SEED-014 Phase 1 scheduled-skill-runs, `D-PRD-02`.*
- New `scheduled_runs_history` table — one row per fired run, joined to `runs.id` so observability inherits run-backed streaming for free. *Carries: SEED-014 Phase 1 §observability.*
- Sibling Python process — `backend/scheduler/` — separate from the uvicorn process tree. Polls `scheduled_runs` every minute (configurable), kicks off due runs by inserting a row into `runs` and `XADD`-ing to `events:routine.scheduled_due`. Single-instance via Postgres advisory lock (`pg_try_advisory_lock`) so scaling to N uvicorn workers does NOT spawn N schedulers. *Carries: SEED-014 §architectural-notes-scheduler-choice, Q-v3.4-01.*
- Output routing: each routine has a `output_thread_id` UUID; runs that fire under the routine post their final assistant message into that thread, so users see results in chat history alongside their conversations. *Carries: SEED-014 Phase 1 §output-routing.*

**Theme B — Event Bus & Triggered Routines**
- New Redis Stream namespace `events:*` (distinct from `run:*` per SEED-014 — `events:document.ingested`, `events:run.failed`, `events:feedback.thumbs_down`, `events:confidence.low`, `events:document.checkin`, `events:document.checkout`, `events:retention.due`, `events:approval.requested`, `events:approval.completed`). Producers: ingestion pipeline (`backend/app/api/documents.py`), runs (`backend/app/api/runs.py`), feedback (existing `message_feedback` write site), DM Tier B (Theme E producers). Consumers: routine subscribers + the v3.3 webhook outbound delivery worker. *Carries: SEED-014 Phase 2, Q-v3.4-02.*
- New `event_subscriptions` table — one row per (event_type, filter_json, target_routine_id). Filter is a small JSON path expression: `{"folder_id": "uuid", "document_type": "contract"}`. Consumed by the scheduler process's secondary loop (`XREADGROUP` with consumer-group-per-subscription). *Carries: SEED-014 Phase 2.*
- New `routine_definitions` table — the canonical row backing both scheduled and triggered routines. Columns: `id, org_id, owner_user_id, name, description, mode (scheduled|triggered|reactive), trigger_config jsonb, action_skill_id uuid fk, action_inputs_json jsonb, output_thread_id uuid, version int, published_at timestamptz, created_at, updated_at, status (draft|active|paused|archived)`. Versioning: immutable on publish per Q-v3.4-07 — editing creates a new version row; old runs continue to reference their published version. *Carries: SEED-014 Phase 1+2, `D-PRD-09` skill-versioning mirror, Q-v3.4-07.*

**Theme C — Reactive Routines (Webhook-Triggered, via v3.3)**
- `routine_definitions.mode = 'reactive'` consumes the v3.3 inbound webhook surface (Phase 3 of v3.3). When a webhook lands at `POST /api/v1/webhooks/incoming/{webhook_id}`, the v3.3 webhook receiver `XADD`s to `events:webhook.{webhook_id}`; reactive routines subscribed to that key fire. Reuses the same scheduler-process consumer loop as triggered routines. *Carries: SEED-014 Phase 2 §reactive-mode, `D-PRD-03` (closed-core webhook surface), v3.3 prerequisite.*
- HMAC verification + replay-window check happens at the v3.3 receiver layer; v3.4 routines see only verified events.

**Theme D — Long-Running Run Checkpointing (RECOVERED_Harnessing_Agents Opportunity E)**
- New `agent_checkpoints` table — one row per checkpoint snapshot. Columns: `id, run_id uuid fk, thread_id uuid fk, iteration int, messages_json jsonb (compressed/truncated), tool_calls_json jsonb, pending_tool_id text, artifact_refs jsonb, created_at timestamptz`. RLS keyed on `runs.user_id` via FK. *Carries: RECOVERED_Harnessing_Agents Opportunity E, Q-v3.4-03.*
- Checkpoint emit point: at the end of every successful tool execution inside `agent_runner` (`backend/app/api/threads.py:1059` per `ARCHITECTURE.md:30-31` and `ARCHITECTURE.md:160-172`). A new `_emit_checkpoint(run_id, iteration, messages, tool_calls, pending_tool)` writes to `agent_checkpoints` BEFORE the next iteration begins. Checkpoint frequency is configurable via `CHECKPOINT_EVERY_N_TOOLS` env var (default 1 = every tool).
- Resume affordance: `POST /runs/{run_id}/resume` reads the latest checkpoint, reconstructs the `messages` list, and spawns a new `agent_runner` task that picks up at the saved iteration. Used by automations of arbitrary duration (max-24h cap with operator override per Q-v3.4-08).
- Optional context-compression strategies (per Opportunity E): summarization of older messages, token eviction beyond `trim_messages_to_fit`, artifact-reference replacement of large tool results. v3.4 ships the checkpoint primitive only; compression strategies are routed to a v3.5+ polish slot if telemetry shows checkpoint rows growing unbounded. *Carries: Opportunity E §context-compression, §11 deferral.*

**Theme E — DM Tier B: Retention, Check-in/Check-out, Approvals, Lifecycle**
- New `dm_retention_policies` table — per-folder or per-org rule. Columns: `id, org_id, folder_id uuid nullable, name, rule_expression jsonb (evaluator: document_type / metadata pattern / age threshold), action (mark_for_deletion | hard_delete | archive_storage), enforcement_mode (soft | hard), created_at, updated_at`. *Carries: SEED-005 Tier B item 5, Q-v3.4-05.*
- Scheduled cleanup job (Theme A scheduler hosts it): every night at 02:00 UTC, evaluate active retention policies, write `events:retention.due` per matching document, and either mark `documents.retention_status='due'` (soft mode) or run the configured action (hard mode). Per Q-v3.4-05 recommendation: soft default, opt-in hard for pre-classified low-risk content classes. *Carries: SEED-005 Tier B item 5 §schedule-job.*
- New `dm_check_in_out_state` table — per-document lock state. Columns: `document_id uuid pk fk, locked_by_user_id uuid, locked_at timestamptz, lock_ttl_seconds int default 86400 (24h), force_release_count int default 0`. TTL auto-release via the same scheduled cleanup job. Force-release available to `org_admin` role (visible from v3.2's governance dashboard). *Carries: SEED-005 Tier B item 4, `D-PRD-11`.*
- API: `POST /documents/{id}/checkout`, `POST /documents/{id}/checkin`, `POST /documents/{id}/force-release` (admin-only). UI: lock banner on document detail; "locked-too-long" filter on the v3.2 governance dashboard.
- New `dm_approvals` + `dm_approval_steps` tables — multi-step linear approval workflow per Q-v3.4-06 v1. Workflow definition is per-folder (every doc uploaded to that folder enters the workflow); workflow state is per-document. Linear-only in v3.4 (sequential approvers); parallel-of-N and conditional routing deferred per Q-v3.4-06. *Carries: SEED-005 Tier B item 6, Q-v3.4-06.*
- Schema: `dm_approvals (id, org_id, folder_id, document_id, status (draft|in_review|approved|rejected|cancelled), current_step int, started_at, completed_at)`; `dm_approval_steps (id, approval_id fk, step_index int, approver_user_id uuid, status (pending|approved|rejected|skipped), comment text, decided_at timestamptz)`. Producer of `events:approval.requested` / `events:approval.completed` for routine integration.
- New `dm_lifecycle_audit` table — domain-specific audit feed per document. Columns: `id, document_id, org_id, event_type (uploaded | versioned | checked_out | checked_in | approval_requested | approval_decided | retention_due | retention_executed | force_released), actor_user_id, payload jsonb, created_at timestamptz`. Distinct from the cross-cutting `audit_log` table — `dm_lifecycle_audit` is per-document and surfaces in document detail UI; `audit_log` (v2.2 F-06) stays the cross-cutting compliance feed. *Carries: SEED-005 §notes governance dashboard intersection.*

**Theme F — Spend Caps & Budget Enforcement**
- New `spend_caps` table — per-org / per-routine / global. Columns: `id, scope (global|org|routine), scope_id uuid nullable, period (daily|weekly|monthly), limit_usd numeric, hard_cap bool, alert_threshold_pct int (default 80), created_at`. Stacked enforcement per Q-v3.4-04: global hard cap (operator-set), per-org tier limit (auto-set from `D-PRD-10` tier), per-routine soft cap (member-set, must be ≤ org limit). *Carries: SEED-014 §architectural-notes-cost-runaway, RECOVERED_Harnessing_Agents §risk-analysis, `D-PRD-10`, Q-v3.4-04.*
- Enforcement layer: pre-flight check at routine-trigger time. Reads accumulated spend from `runs.input_tokens` × per-model rate (already populated post-v2.6 token-cost work) + `runs.output_tokens` × per-model rate. If projected spend exceeds the most-restrictive applicable cap, emit `events:routine.budget_exceeded` and skip the run; the routine's `last_skipped_reason` is updated. Hard-cap exceeded → routine auto-paused. *Carries: SEED-014 §risks-cost-runaway.*
- New `spend_ledger` table (per-run rollup) — denormalized cost-per-run for fast cap evaluation. Updated post-run via the existing run-finalization path at `backend/app/api/threads.py:158-255` (`_drain_stream_with_close_on_cancel`'s shielded finalize block).

**Theme G — Routine UI & Notifications**
- New `/automations` page (frontend). Org-admins see all org routines + member personal routines (if their org permits); members see their own routines. Form-driven YAML/JSON config (per §10 surprise-feature rejection of full visual no-code builder). Affordances: list, create, edit, pause, run-now, view-history. *Carries: SEED-014 Phase 1 §UI-surface, SEED-012 (handed-off — operator UI lives in v3.1's admin shell + v3.4's `/automations`).*
- Notification primitive — new `notifications` table (in-app destination only at v3.4 ship). Routine-completion / routine-failure / approval-requested / retention-due all write here. Email follow-up + outbound webhook (via v3.3) added in same milestone but as opt-in user preferences, NOT default. *Carries: SEED-014 §observability + cluster-K lateral-thinking item from synthesis (notification system landing point).*
- Realtime hint: in-app notification surface uses Supabase Realtime as a UX hint (per `D-v2.5-03`). The source of truth is the `notifications` Postgres row.

## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** Visual no-code routine builder (drag-drop steps, like n8n / Zapier).
   **Why tempting:** Lowers onboarding friction; matches buyer expectation set by n8n / Zapier / Power Automate.
   **Why not now:** Complexity vs value. The v1 path is YAML/JSON config + auto-generated form (mirrors how Skills are authored — frontmatter-driven, not GUI-driven). A full visual builder is a 4-6 phase scope on its own and risks UI sprawl. Skill-as-action means most of the routine logic IS the skill, which already has a documented authoring path; the routine layer just adds the trigger.
   **Re-trigger:** First enterprise customer trials the product and bounces on the JSON-config UX — promote a visual builder to a v3.5+ polish milestone with dedicated UI scope.

2. **Idea:** AI-suggested routines based on user activity (e.g., "I notice you summarize last week's docs every Monday — want me to schedule that?").
   **Why tempting:** Strong magical-product moment; differentiator vs n8n / Zapier (which are dumb pipes); leverages existing Knowledge Health Dashboard signal.
   **Why not now:** Deferred to a separate AI-powered admin milestone. v1 is human-authored. AI suggestions add a recommendation engine layer that's its own scope and accuracy concern (false-positives are worse than missing suggestions for trust).
   **Re-trigger:** v3.5+ AI-powered admin milestone OR first customer asks for it explicitly.

3. **Idea:** Cross-org routine sharing (one org publishes a routine, another org clones it).
   **Why tempting:** Marketplace network effect; mirrors the agentskills.io standard for skills.
   **Why not now:** **Anti-feature per `D-PRD-02`.** Orgs are isolated; cross-org sharing reopens leak class. The agentskills.io standard handles this for skills via export/import (file-mediated, no live data crossing org boundaries); routines should follow the same pattern (export/import via JSON file) NOT live cross-org references.
   **Re-trigger:** Never as live cross-org sharing. The export/import equivalent for routines may be considered in v3.5+ if the user-driven need surfaces.

4. **Idea:** Long-running runs that span multiple weeks (>24h cap raised to 30+ days).
   **Why tempting:** Some research / analysis use cases legitimately span weeks (e.g., "monitor this RSS feed forever").
   **Why not now:** v1 caps at 24h with explicit operator override to 7d. Multi-week runs reopen unbounded-token-spend risk that spend caps mitigate but don't eliminate; checkpointing primitive needs to prove stable in production before extending duration.
   **Re-trigger:** Checkpointing telemetry post-v3.4 shows ≥99% successful resume rate over 7d, AND a customer requests >7d duration.

5. **Idea:** Multi-Agent Orchestration as a routine action mode (Planner + Researcher + Analyst + Coder + Reviewer + Writer per RECOVERED_Harnessing_Agents Opportunity B).
   **Why tempting:** Strong fit with skills-as-roles framing; differentiator vs every closed competitor; composes naturally with Skill Studio (each role = a skill).
   **Why not now:** Opportunity B is its own milestone-shaped scope (RECOVERED_Harnessing_Agents §4 Implementation Roadmap Phase 3 = 3-4 weeks / one full milestone). Compressing it into v3.4 dilutes the automation primitives focus AND risks coordinator-agent complexity that's hard to debug.
   **Re-trigger:** v3.5+ vertical packs that require complex multi-role coordination (legal pack: Researcher + Reviewer + Writer; finance pack: Analyst + Reviewer).

6. **Idea:** Dedicated Background Research Agent UI surface (Anthropic-pattern initializer/coding agent split, `task_plan.json` + `task_progress.txt` user-facing).
   **Why tempting:** Matches Anthropic's published harness pattern verbatim; gives users a clear "long-running task" mental model distinct from chat.
   **Why not now:** v3.4 ships the data primitives (`agent_checkpoints` + long-running run + output thread routing) which cover the same use-cases at lower UI fidelity via `/automations` history view + checkpoint resume. The dedicated UI surface would be an additional 3-4 phases and would compete with the routine-UI surface for user attention. Better to ship the primitives, observe usage, and decide whether the dedicated UI adds value.
   **Re-trigger:** Usage telemetry post-v3.4 shows users authoring >10 long-running automations per week — promote dedicated Background Research Agent UI to v3.5+.

7. **Idea:** Per-routine LLM model override (e.g., "always use Haiku for this routine, regardless of user's default").
   **Why tempting:** Cost optimization lever — cheap models for batch / scheduled work, expensive for synthesis. Aligns with multi-provider router (Phase 067.3 v2.5).
   **Why not now:** Already covered implicitly via the skill action contract — a skill can pin its own model preference. Adding per-routine override on top creates two competing model-selection paths. v1 inherits the skill's model; if the skill defers to user-settings, the routine fires with the routine-owner's settings.
   **Re-trigger:** First customer request for "I want this scheduled summarization to always use Haiku regardless of who authored the skill" — promote to v3.4.5 polish.

## 14. Competitive positioning paragraph

v3.4 positions Agentic RAG as the open-source self-hostable agentic platform where **your skills run themselves on a schedule, react to your data, and survive arbitrary duration** — a position no competitor occupies. **Glean** (the primary enterprise-search competitor per `D-PRD-05`) has zero automation surface: it answers questions but cannot ACT on them — no scheduled runs, no triggered routines, no reactive integration with your KB. **ChatGPT Tasks** (the secondary competitor anchor) can schedule prompts but is closed-source, single-user, and entirely KB-blind — it cannot ground answers in your documents, run code, or fire on document-lifecycle events. **n8n / Zapier / Make.com** offer generic workflow automation with AI bolted on but have no native KB connection, no skill runtime, and no agent-grade observability — users must assemble agent capabilities from primitives. **OpenAI Assistants + ChatGPT scheduled actions** lock you into one provider and give no path to self-host. v3.4 differentiates on four axes that NO competitor combines: (1) **scheduled / triggered / reactive runs against your own KB self-hosted**, with skills as the action contract — "every Monday summarize last week's `/Legal` documents" actually grounds in your documents and runs the contract-classifier skill that you authored; (2) **agent checkpointing for arbitrary-duration runs** (RECOVERED_Harnessing_Agents Opportunity E shipped) — long-running automations persist their state at tool-execution boundaries, survive uvicorn restarts, and resume mid-task. No other RAG product offers this; (3) **spend-capped automation with `D-PRD-10` flat-tier enforcement** — org-admin sets the budget, per-routine soft caps, global hard ceiling — so the operationally-required cost-runaway protection is built in, not bolted on; (4) **open MCP-addressable** (per v3.3) — external orchestrators (n8n, Zapier, Cursor agents, custom) can fire Agentic RAG routines via the same webhook surface used for reactive triggers, so the moat narrows the competitive surface without locking out the ecosystem. After v3.4 ships, the competitive narrative becomes: "Glean answers; we act. ChatGPT Tasks schedules; we ground. n8n automates; we know your data." DM Tier B (retention + check-in/out + linear approvals + lifecycle audit) is the secondary positioning win — matches M-Files on the horizontal-core feature surface for vertical-pack readiness per `D-PRD-11`.
