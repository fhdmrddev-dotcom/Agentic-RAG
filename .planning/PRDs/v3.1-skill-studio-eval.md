## 1. Header

v3.0 turns the v2.0 Skills system into a proper iterative development environment — the single milestone that closes the headline-differentiator gap against **OpenAI Assistants** / **ChatGPT custom GPTs** (proprietary, untestable, no portable format) and **Glean** (closed SaaS workflows, no skill format, no agent customization). It ships five new tables (`eval_cases`, `eval_runs`, `eval_run_outputs`, `eval_feedback`, `skill_versions`), three new agent tools (`run_skill_eval`, `list_skill_evals`, `store_eval_feedback`) registered in General Mode only, dual-execution streaming so users can compare with-skill vs without-skill side-by-side, and an Evals panel addition (NOT a replacement) to the existing Skill detail view. As a second-order win it folds **Multi-Agent Orchestration** in as a Skill execution mode — Researcher / Analyst / Coder / Reviewer / Writer roles, each a configured instance of the existing agent loop with a specialized prompt + reduced tool set (Opportunity B from `RECOVERED_Harnessing_Agents_Research_Report.md`), composing naturally with eval cases per role. The eval-run SSE event types follow the existing `sub_agent_*` / `code_execution_*` taxonomy but ride the **run-backed streaming** substrate from Phase 061+ (`run:{run_id}` Redis Stream — `ARCHITECTURE.md:80-93`), NOT the legacy POST-stream pattern the recovered PRD pre-dates. Strategically v3.0 ships now because the foundation is unusually clean — Phase 065 closed the skills test infra (26/26 pass per `PROJECT.md:138`), v2.6 lifted SEED-007 (`<StreamsProvider>`) so eval streams have a clean substrate, and SKILL-01/02 catalog full-inject debt (`PROJECT.md:199`) collides with the eval mode injection question and gets resolved in the same milestone.

## 3. Scope

**Theme A — Eval Persistence Layer**
- `eval_cases` table: per-skill saved test prompt + expected-output description + tags. Reusable across iterations and across skill versions. RLS keyed on `user_id` (eval cases are user-private; global skills can have user-private eval cases). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Eval cases" infra; SEED-002 §scope-estimate; v3.2 multi-tenancy implication noted in §6.*
- `eval_runs` table: header row per executed eval — `eval_case_id`, `skill_id`, `skill_version_id`, `mode` (`with_skill | without_skill | both`), `status` (`queued | streaming | completed | failed | cancelled`), `started_at`, `completed_at`, `total_tokens`, `total_duration_ms`, `triggered_by` (`agent | user_ui`), `run_id` (link to the existing `runs` Postgres row + Redis Stream — eval runs piggyback on the run-backed streaming substrate). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Eval runs" infra; SEED-002.*
- `eval_run_outputs` table: child row per variant — one row for `with_skill` output, one row for `without_skill` output (when both are run). Columns: `eval_run_id`, `variant` (`with_skill | without_skill`), `output_text`, `output_artifacts` (jsonb of `{filename, storage_path, signed_url, mime_type}`), `tokens_used`, `duration_ms`, `model`, `provider`, `rating` (smallint 1-5, nullable), `error`. Splitting outputs into a child table (vs two columns on `eval_runs`) cleanly supports Multi-Agent Orchestration mode where >2 variants may exist (one per role). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #3 file-output-handling; lateral-thinking surface for multi-agent eval extension.*
- `eval_feedback` table: separated from `eval_run_outputs.rating` so feedback is append-only auditable history (per-output, multi-feedback). Columns: `eval_run_output_id`, `user_id`, `rating`, `feedback_text`, `created_at`. INSERT-only RLS pattern matches `message_feedback` (`PROJECT.md:183`). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "feedback" surface; lateral-thinking — multi-rater audit trail for v3.2 org review.*
- `skill_versions` table: resolves `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #5 (skill versioning). Columns: `skill_id`, `semver` (text, e.g. `1.0.0`), `instructions` (snapshot), `description` (snapshot), `created_at`, `published_at` (nullable — null = draft). Immutable on publish. Eval runs link to `skill_version_id` so iteration history is reproducible. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #5; recommendation routed to Q-v3.0-05.*
- All RLS policies follow the existing `skills`-table pattern (`user_id = auth.uid() OR is_global = true` for read; `user_id = auth.uid()` for write); eval cases of a global skill remain user-private. *Carries: `ARCHITECTURE.md:89` RLS rule.*

**Theme B — Agent Tools (General Mode only)**
- `run_skill_eval(skill_name: str, prompt: str, mode: 'both' | 'with_skill' | 'without_skill' = 'both', save_as_case: bool = false, case_description: str | None = None) -> {eval_run_id, run_id, ...}`. Spawns the eval producer (parallel sibling to the existing `agent_runner` producer in `threads.py:1059`); both with-skill and without-skill executions share a single `run_id` and emit interleaved SSE events tagged with `variant`. Returns immediately so the agent can describe what's happening to the user. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Run an eval"; `D-PRD-09`; collides with Q-v3.0-02 (target-skill-only vs full catalog).*
- `list_skill_evals(skill_id: str | None = None, skill_name: str | None = None, limit: int = 20) -> [{eval_case_id, prompt_preview, run_count, avg_rating, last_run_at, latest_versions_compared, ...}]`. Per-skill history; joins `eval_cases` × `eval_runs` × `eval_run_outputs`. The agent reads this BEFORE iterating on a skill so it knows what was tested before. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Retrieve eval history"; `D-PRD-09`.*
- `store_eval_feedback(eval_run_output_id: str, rating: int, feedback_text: str | None = None) -> {eval_feedback_id}`. Records rating + text; agent calls this after the user reviews an output verbally so the user doesn't have to navigate to the UI. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Store feedback"; `D-PRD-09`.*
- All three tools are registered in **General Mode only** — the existing `get_tools()` mode-conditional pattern in `openai_service.py` (per `PROJECT.md:192-193`) extends with three new entries gated on `calling_mode == 'general'` AND the future tier-gate (`subscription_tier in ('pro', 'enterprise')`, stub for v3.2). Explorer mode does NOT receive them. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "available only when sandbox is enabled, or always available in General Mode" — design decision LOCKED here as "General Mode only, regardless of sandbox state".*

**Theme C — Eval Execution Pipeline (run-backed streaming)**
- New `eval_runner(eval_run_id, skill_id, prompt, variant)` producer pattern, modeled on `agent_runner` (`threads.py:1059`) but specialized: builds messages = `[system_with_or_without_skill, user(prompt)]`; runs through the same `_drain_stream_with_close_on_cancel` (`threads.py:158-255`) with the same per-call timeout (`asyncio.timeout(per_call_budget)`); emits via the same `_emit(redis, run_id, type, **fields)` XADD path. *Carries: `D-v2.5-08`; `D-v2.5-11` precedent; SEED-002 §reusable-patterns ("Phase 059's pattern is a clean template for dual-execution evals").*
- New SSE event types (all ride the `run:{run_id}` Redis Stream — NO new substrate): `eval_run_start{eval_run_id, mode, variants}`, `eval_variant_start{variant}`, `eval_variant_delta{variant, content}`, `eval_variant_tool_call{variant, tool, args_preview}`, `eval_variant_done{variant, tokens, duration_ms, rating: null}`, `eval_run_done{eval_run_id, summary}`. Naming pattern follows `sub_agent_*` / `code_execution_*` per `RECOVERED_Agent_Realtime_Feedback_Assessment.md` Fix-1. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "SSE Events" with corrected substrate per synthesis §7; lateral-thinking — `eval_variant_*` granularity supports Multi-Agent Orchestration (Theme F) where N variants stream in parallel.*
- Sequential execution v1 (per Q-v3.0-01 recommendation): `with_skill` runs first, `without_skill` runs second. Parallel execution is gated to v3.0.5+ once telemetry confirms the run-backed substrate handles it cleanly under load. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #1; Q-v3.0-01.*
- Eval-mode skill injection: ONLY the target skill's `instructions` go into the system prompt — full skill catalog NOT injected. This is the ISOLATED test the recovered PRD's Open Question #2 names; the realistic-test variant is deferred (re-trigger: customer signals it's needed). Decision is independent of the SKILL-01/02 catalog dispatch question for production agent runs (Theme G). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #2; Q-v3.0-02; SKILL-01/02 from `PROJECT.md:144-145, 199`.*

**Theme D — Evals Panel UI (addition to Skill detail, not replacement)**

Existing tabs untouched. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Frontend section; `project_settings_design_guidance.md` ("Skills: align-only, full redesign deferred to Skill Studio milestone" — full redesign STILL deferred per Q-v3.0-07; v3.0 ships only the Evals panel addition).*
- Test case list: `eval_cases` rows for the skill, with prompt preview, run count, average rating, last-run-at. Empty state proposes "Ask the agent to run a test prompt" — NOT a heavy in-UI form. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Test case list".*
- Run detail view: side-by-side `with_skill` vs `without_skill` outputs from the most recent run. Multi-Agent Orchestration mode renders N columns (one per role variant). Layout aligns with Aether Intelligence Deep Midnight tonal-depth pattern (per `MILESTONES.md:147-157`). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Run detail view".*
- Lightweight inline rating + feedback (1-5 stars + optional text), saved without modal/form-submit (per Q-v3.0-04 recommendation: yes UI-driven — but inline, not modal). *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Rating and feedback"; Q-v3.0-04.*
- UI-driven test case creation: inline "+ Add test case" form within the Evals panel (Q-v3.0-04 recommendation). Form posts to a thin `POST /skills/{id}/eval-cases` endpoint that wraps `eval_cases` insert. Agent-driven creation (`run_skill_eval` with `save_as_case=true`) remains the primary path. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #4; Q-v3.0-04.*
- Iteration history: per-skill timeline showing version × eval-case × rating evolution. Visual: stacked bars per version (numeric average) — NOT a complex trend line per the recovered PRD's "design decision for the implementor" note. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Iteration history".*
- New frontend hooks: `useEvalCases(skillId)`, `useEvalRuns(evalCaseId)`, `useEvalRunStream(runId)` — last one piggybacks on the existing `subscribeToRun` SSE parser (`frontend/src/lib/api.ts:274`) per `D-v2.5-08` substrate. *Carries: existing `useX` patterns per `RECOVERED_SKILL_STUDIO_PRD.md` Frontend section.*

**Theme E — Skill Versioning (resolves Open Question #5)**
- New `skill_versions` table (Theme A) is the backing store. `skills.current_version_id uuid` FK column added. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` Open Question #5; Q-v3.0-05.*
- Publish flow: when the agent (via skill-creator) or user updates skill instructions/description, a NEW `skill_versions` row is INSERTed (with `published_at = null` if draft). The user/agent explicitly publishes by setting `published_at = now()` and updating `skills.current_version_id`. Drafts are mutable; published versions are IMMUTABLE (DB trigger enforces). *Carries: lateral-thinking on Open Question #5 — semver + immutable-on-publish.*
- Version comparison: `list_skill_evals` joins on `skill_version_id` so the agent can compare ratings across versions. The Evals panel iteration-history view groups eval runs by version. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "iteration history view requires knowing which runs belong to which 'version'".*
- Backfill: existing `skills` rows get a synthetic `1.0.0` `skill_versions` row inserted at migration time (snapshots current `instructions` + `description`). Backfill migration is idempotent — `INSERT ... ON CONFLICT DO NOTHING`. *Carries: lateral-thinking — without backfill, all existing skills would orphan their pre-v3.0 history.*

**Theme F — Multi-Agent Orchestration as a Skill execution mode**
- New skill runtime mode: a skill's `instructions` + a new `skill_modes` JSONB column on `skills` can declare `mode: 'multi_agent'` with a roster of roles (default 5: Researcher / Analyst / Coder / Reviewer / Writer per `RECOVERED_Harnessing_Agents_Research_Report.md` Opportunity B). Each role = configured instance of the existing `agent_runner` loop with a specialized system prompt + reduced tool set. *Carries: synthesis §6 differentiator #3 + #4; `RECOVERED_Harnessing_Agents_Research_Report.md` Opportunity B; project rule "no LangGraph" per `CLAUDE.md` — orchestration built directly on the existing run loop, NOT via a graph framework.*
- Orchestration topology v1: linear pipeline (Planner → Researcher → Analyst → Coder → Reviewer → Writer → Final). Parallel branches deferred (re-trigger: skill author asks for it; v3.4 Automations may also adopt this primitive). *Carries: `RECOVERED_Harnessing_Agents_Research_Report.md` Opportunity B "linear chain v1, fork v2".*
- Eval composition: a `multi_agent` skill's eval case can either (a) eval the FINAL output (single rating against the user prompt), or (b) eval EACH ROLE's output (per-role ratings — `eval_run_outputs` rows per role). Mode (b) explains why `eval_run_outputs` is a child table not two columns on `eval_runs` (Theme A). *Carries: lateral-thinking — multi-agent eval is the primary justification for the `eval_run_outputs` table shape.*
- Reused infrastructure: each role's loop emits to the same `run:{run_id}` Redis Stream with the existing per-call timeout discipline (`D-066-01..03`); cross-role messaging via standard agent-loop tool-call pattern; no new orchestration infra. *Carries: `D-v2.5-08`; `D-PRD-08` multi-worker substrate.*

**Theme H — Skill Creator Seed Skill Update**
- The `skill-creator` global seed skill (created by migration `018_skill_creator_seed.sql`) gets its instructions updated in v3.0 to reference the new eval tools. *Carries: `RECOVERED_SKILL_STUDIO_PRD.md` "Skill Creator Seed Skill — Updated Instructions".*

**Theme I — Accessibility (WCAG 2.1 AA, shared scope with v3.1)**
- All new Evals panel UI surfaces (Theme D) meet WCAG 2.1 AA baseline: keyboard navigation across rating controls + tabs + run-detail panels (no mouse-only paths); `aria-label` / `aria-describedby` on all interactive elements (rating stars, feedback textarea, "+ Add test case" form fields, run-status indicators); minimum 4.5:1 color contrast on text against Deep Midnight backgrounds (audit existing Aether tokens; bump where insufficient); visible focus indicators via the existing `:focus-visible` ring pattern; no color-only semantic conveyance (e.g., rating colors paired with stars + numeric value). *Carries: Plan 09 SUMMARY.md §C.1 #5 routed via "small lift across v3.0 + v3.1" per user signoff 2026-05-12.*
- Inline-form pattern (Q-v3.0-04 lightweight rating + feedback) MUST avoid modal/popover focus traps; if a popover is used, it MUST implement keyboard escape + focus-return per WCAG 2.4.3. *Carries: Plan 09 SUMMARY.md §C.1 #5.*
- Multi-Agent Orchestration panel (Theme F) — when multiple role variants render in side-by-side columns, ensure each column has its own landmark region (`role="region" aria-label="..."`) so screen readers can navigate between variants cleanly. *Carries: lateral-thinking — multi-column UI is a screen-reader edge case worth catching at design time.*
- Accessibility audit gate at milestone close: automated axe-core scan on all new Evals routes + manual keyboard-only walk-through documented in milestone UAT. *Carries: WCAG 2.1 AA acceptance criterion.*

- `GET /eval-runs/{id}` — fetch single eval run with all `eval_run_outputs` joined.
- `POST /eval-cases/{id}/run` — direct UI-trigger of an eval run (alternative path to the agent tool — used by the "Re-run" button in the iteration history view). Spawns `eval_runner`; returns `{eval_run_id, run_id}`.
- `POST /skills/{id}/versions/publish` — mark a draft `skill_versions` row as published (`published_at = now()`); UPDATE `skills.current_version_id`.
- `GET /skills/{id}/versions` — list versions for a skill.

**New background processes:** none. The `eval_runner` producer is an `asyncio.create_task` inside the existing FastAPI process, registered in `RUN_TASKS` (per the `agent_runner` pattern at `threads.py:2698`). Per-worker; cross-worker cancellation via the existing zombie-heal pattern at `runs.py:421` — same as production agent runs after v2.6 multi-worker enable (`D-PRD-08`).

## 10. Surprise-feature check (Gate 5)

**Rejected ideas:**

1. **Idea:** Ship a hosted skill marketplace (agentskills.io as a service) inside v3.0.
   **Why tempting:** v3.0 ships skill versioning + ZIP roundtrip with versions; the natural next step is a discovery surface where users browse and install skills published by others. Would amplify the "open standard skill format" differentiator dramatically.
   **Why not now:** agentskills.io infra is NOT v3.0 scope per `D-PRD-09`. Marketplace is its own milestone (separate hosted service, separate identity model, separate payment/auth surface, separate moderation). v3.0 ships the LOCAL-USER iterative dev loop; the marketplace is a future "vertical" once the format is proven in-house.
   **Re-trigger:** User base reaches the point where peer-to-peer skill sharing is desired (currently ~all skills are user-private or globally-injected by the operator).

2. **Idea:** Real-time collaboration on skill files (multiple users editing the same skill simultaneously, live cursors).
   **Why tempting:** Strong product differentiator; pairs with multi-tenancy (v3.2) where teams may co-author skills.
   **Why not now:** No demand signal. Complex (operational-transform / CRDT infrastructure that doesn't compose with the existing run-backed streaming architecture). Listed in v2.6 §10 with the same rejection — preserving the rejection here. Would expand v3.0 by easily 5+ phases for a feature whose ROI is unclear.
   **Re-trigger:** A vertical-pack customer (legal/finance) explicitly asks for it OR a competitor (Glean) ships it.

3. **Idea:** Use **LangGraph** for the Multi-Agent Orchestration mode (Theme F).
   **Why tempting:** LangGraph is the canonical multi-agent orchestration framework; it would handle state machines, role-routing, and inter-role messaging out of the box. Saves implementation work.
   **Why not now:** **Project rule explicitly forbids it** (`CLAUDE.md` — "No LangChain, no LangGraph — raw SDK calls only"). v3.0 builds Multi-Agent Orchestration directly on the existing run loop pattern (each role = configured `agent_runner` instance). The cost is one phase of orchestration plumbing; the win is the entire stack stays understandable and debuggable. Adding LangGraph would also be a one-way decision (the framework metastasizes once introduced).
   **Re-trigger:** Project rule changes (would itself require a `D-PRD-NN` decision — this entry is the cross-reference).

4. **Idea:** Skill auto-improvement via meta-eval — a meta-agent reads `eval_run_outputs` ratings + feedback for a skill and PROPOSES instruction updates automatically.
   **Why tempting:** Closes the iterative-dev loop completely. The eval data accumulates anyway; a meta-agent reading it is a natural extension of the skill-creator seed skill.
   **Why not now:** Too speculative for v1. Requires (a) enough eval data to be statistically meaningful (per-skill ≥10 evals × ≥3 versions); (b) trust calibration against "blind acceptance of meta-agent edits"; (c) governance (orgs may want approval workflow). All three points compound to "land this only after eval data accumulates and signal emerges from real users".
   **Re-trigger:** Production telemetry shows ≥100 skills with ≥10 evals each AND user requests for the meta-agent surface.

5. **Idea:** Promote eval cases to first-class agentskills.io ZIP standard members (export-by-default).
   **Why tempting:** Eval cases ARE part of a skill's reproducibility story; exporting them with the skill makes it portable in a stronger sense.
   **Why not now:** Eval cases are USER-PRIVATE (per RLS design — Theme A bullet 1) and may contain sensitive prompts (e.g., a finance skill's eval case might include real numbers). Default-export risks data leakage. Compromise: explicit `export_eval_cases=true` query param SHIPS in v3.0 (per SKILL-PORT-01) but default is OFF.
   **Re-trigger:** Vertical-pack workflow proves operator-shareable eval cases are the norm.

6. **Idea:** Add a "Reset to v1.0.0" button that recreates a skill from scratch with the original instructions.
   **Why tempting:** Iteration history exists; reverting to baseline is a natural action.
   **Why not now:** Skill versioning (Theme E) makes this implicit — `skill_versions` rows are the history; users navigate to the desired version and "republish" it as the current. Adding an explicit Reset button creates a footgun (data loss surprise) AND replicates functionality the version system already provides.
   **Re-trigger:** UAT shows users repeatedly asking how to revert.

## 14. Competitive positioning paragraph

v3.0 positions Agentic RAG against **OpenAI Assistants** / **ChatGPT custom GPTs** (the canonical agent-capability reference per `D-PRD-05`, proprietary with no portable skill format and no eval environment) and **Glean** (closed SaaS workflows, no agent customization, no skill format). Two differentiators ship in this milestone — both binary wins, not parity claims. **First: open ZIP-format skills + first-class eval environment + iterative dev loop.** Custom GPTs have NO testing infrastructure (you ship the first draft and pray); OpenAI Assistants has files + tools but no eval surface, no dual-execution comparison, no rating history, no version chain. v3.0 ships all of these on the agentskills.io standard ZIP format (per `D-PRD-03` open-peripheral commitment) — a skill becomes a portable artifact you can hand to a colleague, version, eval against test prompts, and re-import losslessly. Glean ships nothing comparable; its "workflow" surface is a closed builder, not a portable format. **Second: Multi-Agent Orchestration as a Skill execution mode.** Each role (Researcher, Analyst, Coder, Reviewer, Writer per `RECOVERED_Harnessing_Agents_Research_Report.md` Opportunity B) is a configured instance of the existing `agent_runner` loop with a specialized prompt + reduced tool set — built directly on the run-backed streaming substrate (`D-v2.5-08`), NOT via LangGraph (project rule per `CLAUDE.md`). The cost is one orchestration phase; the payoff is a multi-agent workflow surface that Glean's closed builder, Custom GPTs' single-agent shape, and OpenAI Assistants' tool list all lack. v3.0's silent third differentiator is **dual-execution comparison** — buyers can verify a skill's improvement by SEEING with-skill vs without-skill outputs side-by-side. Custom GPTs gives you "trust me, this is better"; v3.0 gives you proof. v3.0 is the milestone where the project earns the headline pitch "Custom GPTs that you can actually test, version, and own".
