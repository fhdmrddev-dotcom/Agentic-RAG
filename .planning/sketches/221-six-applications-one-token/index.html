Six Applications, One Token

Google Workspace stops being one undifferentiated list and becomes six applications — Drive, Gmail, Sheets, Docs, Calendar, Contacts — under a single connection, a single token, a single Revoke. Inside each application, reads and writes separate. Application is the first axis; direction is the second. One component renders both this and a single-product connector like GitHub, where there is only ever one application and the direction bands become the whole screen.

All six Google APIs now answer, and 10 of the 15 actions returned real data — a live message, the primary calendar, the system labels, a busy-block window. Four had nothing in the account to read. One is a genuine defect: read_doc handed a .docx id returns a bare HTTP 400 FAILED_PRECONDITION, and a model will do exactly that, because search_files hands back .docx and native-Doc ids side by side.

Earlier the same day, three of the six were switched off and the panel said nothing about any of them. That state is not gone — it is one console toggle away, and it is what the availability line in D4 exists to surface.

D1

Six applications — but never six authentications

Six separate connections would mean six consent screens, six refresh tokens, six rows in your list for one Google account, and six places to revoke. While the consent screen is in Testing, each of those refresh tokens expires independently every 7 days — six weekly breakages instead of one.

It would also reverse a direction already written into the code. service_tools.py records it: a gmail service id "would have meant a second row, a second consent and two places to revoke."

Recommended Keep one connection, and get the real benefit of separate auth another way — incremental consent. Grant Drive now, add Calendar later, same connection, same token. That is what the Contacts row above offers: "add it without reconnecting."
D2

Application first, direction second

Claude.ai groups Rovo purely by direction because Rovo has one axis — it is a single product surface. Google is six products, six APIs, six scopes and six independent failure modes.

This morning three of them were switched off separately, and this evening you enabled them separately. Direction cannot express "Calendar is switched off"; application can. Organise on the axis your failures actually arrive on.

Direction still earns its place one level down, where it answers a different question: not which product is this but can this action change anything.

D3

The direction band carries no bulk control

This is the one part of Claude.ai's design not to copy. Each of their groups — including Read-only tools · 22 — carries its own Needs approval dropdown, so one click sets twenty-two tools at once, keyed on direction.

Your ROADMAP forbids precisely that, in these words: "the grant-time gate must NOT key on direction, because a read is exactly where prompt injection enters." A poisoned search result is the attack; allow all reads is its front door.

Do not build A posture control on the read band. The band groups and counts; it does not grant. The bulk control lives on the application, where the axis is the product and not the direction.
D4

The availability line, and its three states

Three different things stop an application working, and today they are indistinguishable until a tool fails in chat: the Cloud API is off; the scope was never granted; or it works. The first two have opposite remedies — one is a console visit where reconnecting is useless, the other a scope grant where the console is useless.

So the panel says which. A working application says nothing at all — silence is the healthy state. Only a blocked one speaks, and it names the remedy rather than a status.

Recommended Fill it from the existing Check action, which today only verifies credentials. One check, six verdicts, cached beside last_check_verdict.
D5

Three permission levels, matching the three grouping levels

Today the ladder is action → connection default. The application becomes the middle rung: action → application → connection default. "Allow everything Drive does, ask about everything else" is the sentence people want, and it is unsayable now without setting fifteen switches.

Stored as an app:drive key inside the existing tool_grants object — no new column, no migration. resolve_effective_posture gains one lookup between its two existing steps and keeps failing closed.

Cost ~10 lines in grants.py · 1 line in the sanitizer's key filter
D6

An application's Allow never reaches its writes

When the write band lands, setting Drive to Allow must not silently arm create_file. A write starts at Ask and only an explicit per-action Allow moves it — which is also why the write rows above are drawn at Ask even though Drive's own read_file is overridden to Allow.

Building the ladder with that rule stated now is far cheaper than retrofitting it onto a shipped Allow that already cascades.

D7

One backend field, and it is not the one you'd guess

The grouping key exists in SERVICE_TOOL_SPECS but does not reach the browser. extra_descriptors_for_service strips it deliberately and says so: "the execution fields are STRIPPED here rather than carried through … none of which has any business seeing a URL path."

That reasoning is right and should not be reversed. Add a separate presentation-safe app key to each spec and emit it beside title. It carries no host, no path, no method.

Cost 1 key × 15 specs · 1 line in the projection · 1 field on McpDiscoveredTool
D8

Six product marks, or one Google glyph six times?

The sketch draws neutral monogram tiles in each product's hue, because inventing brand marks in a sketch is worse than admitting the gap. Shipped, the icon convention sources marks from @lobehub/icons via lib/connectionMark.tsx, which knows exactly one google mark today.

Recommended Six distinct marks. The premise of the split is that these read as six applications; six copies of one glyph undoes it at a glance. Any of the six lobehub lacks falls back to the monogram rather than blocking.

D9

One component, both shapes

A connector's applications are just the distinct values of the app key across its tools. Google resolves to six; GitHub, Jira, Notion and every MCP server resolve to one.

When there is exactly one, its header is redundant — the connection header already names it — so it collapses and the direction bands rise to the top. That is not a special case in the code; it is if (apps.length === 1) skipping one row. Rendering Rovo's screen costs nothing extra.

D10

Where the search box goes

The shipped list has a Search 44 actions box, and at 44 it is the only way to find anything. It stays — above the groups, filtering across all of them, with groups that match nothing hidden while the search is active.

Google at 15 does not need it and Google at 30 will. Keeping one behaviour for both beats a box that appears at a threshold nobody can predict.

D11

Direction must not be inferred where it is unknown

readOnlyHint was measured absent on the one MCP server we can reach, and the spec says an unannotated tool is to be treated as destructive. So a connector whose tools carry no hint gets no direction bands at all — one ungrouped list — rather than a silently wrong "Only reads" heading.

Fail closed Bands appear only when the direction is known. Absence is not a third band; it is the absence of banding.

D12

"Ready" stops being a lie

Google is one row with a count. Its verdict is derived, so when an API goes off again it reads Partly ready · 3 need attention without anyone maintaining a flag.

The same derived rule fixes Microsoft 365, which today shows OAuth connected · ✓ Ready with zero tools — an oauth_byo row that never completed discovery. A connection with no usable actions is Not usable, not Ready. That closes your open item #4 as a side effect rather than as its own phase.
