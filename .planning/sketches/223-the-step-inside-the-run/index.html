Three faults, one screenshot. The header counts 3 steps and the rail enumerates 2 — the third is the card below, outside the frame. The card's title is the raw tool name, uppercased by CSS. And the status sentence wears a square that reads as an unticked box because ☑ sits directly above it.

Where each string comes from

  • WRITE_TODOS — SeamCard.tsx:43 returns the raw kind; :51 applies uppercase. Nobody typed this string.
  • ☑ 1 todos — SeamCard.tsx:83. It receives counts only; rendering the raw payload is forbidden by T-087-13, so it cannot say which todo.
  • Agent reached time limit — MessageItem.tsx:799, glyph is lucide <Square> at 12px, chosen as stop.

Why it is outside the frame

  • MessageItem.tsx:841 says so in writing: "ADDITIVE ONLY — a new sibling renderer in MessageItem, never a touch of RunCard internals (G-5)."
  • The composition fault is a guardrail's residue. Moving it inside means taking the RunCard extraction the ledger already reads extraction due.

The word already exists

  • toolNames.ts:114 — write_todos: "Track its to-dos". It lives in components/workflows/ and chat never imports it. Same shape as the connectionMark move 214-08 already took.

The count becomes true by construction. Three steps in the header, three rows on the rail — the honest count is no longer a claim the renderer can contradict. The status line drops the square entirely and takes a word.

What this costs

  • Requires touching RunCard internals — the thing MessageItem.tsx:841 was written to avoid. This variant is the extraction.
  • It asserts a panel-owned pointer is a step like any other. It is not: the panel holds live state, the rail records what happened. Variant B disputes this.

What it buys

  • One rail, one grammar, one count. No second component to keep in sync.
  • open panel ↗ survives as the row's affordance — the seam is kept, not deleted.
  • The ☑ glyph moves onto the row that means todos, so the square below is free to stop looking like a checkbox.

The count stays honest a different way. Two agent steps, counted as two. The todo pointer is inside the frame — so it visibly belongs to this run — but sits in its own band, because it is a window onto live state, not a thing the agent did and finished.

The claim this makes

  • Panel = now, chat = happened — the seam rule from sketch 007. A todo list is still changing; a search that returned 6 results is over. B keeps that distinction visible.
  • The header count means agent steps, unambiguously. In A it means rows, which is a subtly different promise.

What it costs

  • Still touches RunCard — the band is inside the frame. Same G-5 obligation as A.
  • A second slot to maintain. Two grammars in one card, and the next panel-owned tool has to pick one.
  • Risk: if the band is quiet enough to read as secondary, it may read as ignorable — which is how it got missed in the first place.

The cheapest correct-shaped option. RunCard is byte-unchanged. A continuation bracket groups the run and everything that belongs to it, so the card stops reading as an orphan without anything moving.

Why this variant exists

  • The workflow asks that one variant follow the path of least resistance for the target stack. This is it: a wrapper in MessageItem, no RunCard edit, no G-5 obligation triggered.
  • The vocabulary fix (TOOL_PHRASES) and the glyph fix ship here too — they are independent of where the card sits.

What it does not fix

  • The count still disagrees unless the header is re-derived — a bracket groups visually but the run does not know the card exists.
  • It is a drawing of containment rather than containment. The next panel-owned tool lands outside again, and the bracket has to be widened by hand.
  • ⚠ It leaves both extraction due ledger rows untouched, so the debt is deferred, not paid.
  • ⭐ And it can adopt NEITHER improvement the Stitch pass found. Both the status-inside-the-frame and the right-aligned result column live inside RunCard, which this variant exists to leave alone. The orphan does not need a home. It needs deleting. Two steps, counted as two, and nothing below the frame. The todos live in the panel, where they were already live — and where they are still correct after a reload.

Why the premise for keeping it is false

  • SeamCard.tsx:3-8 justifies itself: “on thread reload the panel reconciles to current state and does NOT replay history, so the transcript must be self-contained.”
  • Measured: the panel does not need to replay. StreamsProvider.tsx:106 — useDerivedPanel is “a PURE read over the viewing thread’s persisted chat tool_calls”, and workspacePanel.ts:204 takes the latest write_todos snapshot from them.
  • Both surfaces read the same durable rows. The card is a second render of one source, not a backup for a source that disappears.

workspace_write is redundant too, by a stronger argument

  • FilesSection.tsx:158 uses useWorkspaceFiles, which fetches from the server (getThreadWorkspaceFiles via usePanelReconcile) — not a derive from the transcript at all.
  • That is more durable than the chat row, so its seam card is the weaker copy of the two.

⚠ ask_user must survive

  • Same component, different kind. You answered X is the only record that a human made a decision — the panel shows a pending question, never an answered one.
  • SeamCard.tsx:6-8 says it “CLOSES the documented ask_user reload gap”. Deleting the whole component takes that with it.

The precedent

  • MessageItem.tsx:536 — “SEED-098 Change 2: the loose write_todos / workspace_write pointers are GONE — todos live only in the right Workspace panel.” The live pointers were already deleted for this exact reason. This finishes the job.
  • ⚠ Cost, stated plainly: the panel collapses to a 52px rail, so a reopened thread shows todos only once it is open. A click, not a loss.

The answer is the message again. A hairline separates chrome from prose; the control has a surface, so it reads as pressable without shouting. Press it — it works.

Measured cause

  • MessageItem.tsx:619 passes defaultOpen={hasInRangeMarker(…)}. A grounded answer normally has markers, so in ordinary use it is open every time; the collapsed state is only ever seen on the degraded path.
  • CitationList.tsx:32-44 — the trigger is text-xs text-muted-foreground with a 12px chevron. No border, no surface, no weight, no separation from the answer body.

⚠ This reverses a shipped decision

  • CitationList.tsx:9-14 calls it the “canonical open-by-default contract (D-06/D-07)” from Phase 153, whose sketch 075-A paired numbered markers with an open footer so the two read as one object.
  • The operator’s direction supersedes it. Recorded in BUG-260902-07 so a later phase does not “restore” the old behaviour believing it was an oversight.

Why the two halves ship together

  • While it is open by default the weak trigger is invisible — nobody hunts for a control they never need. Folding it makes that trigger the only way back in, so half one without half two takes a surface that is merely noisy and makes it feel broken.
  • The count stays visible while closed. A fold that hid how many sources there are would trade one readability problem for a worse one.
