A — Dedupe harder

what ships today

Keep both renderers and make the collapse smarter. This is not a proposal so much as the status quo, drawn honestly — dedupMessages.ts already carries a runId-dedup exemption for harness rows (:20-26) and a narrow 174-04 collapse (:31-45).

Why A cannot be made reliable, measured rather than argued. The natural dedup key is the run id — and on a harness run the chat surface does not have one. runs.message_id is NULL on 587 of 607 rows whose thread owns a workflow_run (96.7 %, and all 25 most recent), so dbRunIds cannot hold it. An ordinary Deep run sets message_id and it points exactly at the row that rendered. A is asking a key that does not exist to do the work.

B — One owned slot per run

proposal needs a backend half

The thread renders exactly one assistant node for the active run, keyed on the run. Whatever arrives — the optimistic temp- row, the first SSE event, the persisted row on reconcile — fills that slot rather than mounting beside it. Two mounts collapse structurally, so it does not matter which of the three candidate mechanisms is live.

The constructibility cost, stated up front. A run-keyed slot needs a run key, and that is the 96.7 % NULL above. B implies persisting message_id for harness runs — a backend change with its own migration question, in a phase whose ROADMAP entry says it “adds no new runtime path.” B is the most correct answer and the one most likely to be out of scope. That is worth knowing before planning, not during.

C — No placeholder at all until there is something to say

proposalzero backend

No avatar, no bubble, no “Starting workflow…” shell. The run's presence is carried entirely by the status strip that never vanishes (sketch 015), which is anchored to the run rather than to a message. The assistant node appears when it has content. Two of nothing is nothing — the artefact stops being drawable without anyone needing to know which mechanism causes it.

Drive the “Slow (kimi-k2.6)” setting before judging C. That is where C is tested: several seconds where the transcript shows the prompt and no reply. The claim is that the strip covers it — the run is visibly running, it just has not spoken. If that gap feels dead rather than calm, C is wrong and the phase needs B.
C does not contradict Phase 174 D4 — it relocates it. D4 replaced the dead “Setting up agent…” with an honest live sub-state naming what the model is doing (toolMeta.ts:182 already picks “Starting workflow…” for a harness thread). C keeps that sentence and moves it into the strip, where it belongs to the run. D5 already put the activity pill, the anchored timer and the single avatar in the run-card header — C is that decision followed to its conclusion.

This is why the sketch asks the question it asks. “How do we dedupe?” cannot be answered without the measurement. “Is there one owned slot at all?” can — and both B and C make the mechanism moot, while A requires knowing it. That asymmetry is the finding, and it is available now rather than after the next live repro.
