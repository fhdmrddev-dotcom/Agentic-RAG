Drive it — two moments, three shapes of run

Today — two failures, in opposite directions

045a83dc

The operator, during Phase 194 UAT: “if the workflow is stopped, if I navigate back to the thread of this workflow that was — there is nothing showing that this workflow is stopped, it's only showing the original prompt.”

The stored truth is right in both moments. Phase 194 verified it on seven live runs — workflow_runs.status = 'cancelled', the interrupted workflow_phases row cancelled, completed phases untouched, threads.active_workflow_run_id = NULL. Only the display is wrong, and it is wrong in opposite directions at the two moments a person actually looks:

MomentWhat the screen says
Live, still on the page The run renders as Running. At +13 s the word “Stopped” appears nowhere while Postgres reads cancelled. At an approval it still offers a card that can never be honoured.
On return, after leaving and coming back The “this was stopped” signal is gone entirely — indistinguishable from a run that never started, or one that finished.

A — The dim tier, extended to the workflow thread

reuses 174 D1/D2

Phase 174 already decided what a deliberate stop looks like in chat: tier 1, dim and calm — ⊘ Response stopped as a thin mono line, or the dashed ⊘ Cancelled — no output yet body when nothing was written. Loudness earned by severity; the user did it on purpose, so it stays quiet. A applies that vocabulary, unchanged, to a workflow thread.

The honest catch, and it is the reason A may not be enough. 174's markers hang off the assistant message. A workflow stop leaves a thread whose assistant row may carry no content at all — and runs.message_id is NULL on 587 of 607 harness runs (measured, 194-MEASUREMENTS.md). Switch the driver to Nothing visible yet and judge whether A has anything to attach to.

B — A durable receipt, read from the run

proposal ★ SELECTED 2026-08-16
Selected on a measurement, not on appearance — the three variants look alike and the difference is not visual. Phase 194 verified on seven live runs that a stop sets threads.active_workflow_run_id = NULL. The thread anchor is cleared by the very event the thread now has to remember — and RunSoul and RunSeam both resolve their run from that anchor, so neither can carry the reading either. A mark that survives the return therefore must come from a workflow_runs-by-thread read. There is no cheaper construction; A and C are reading from places the stop has already emptied, or that can be absent.

⚠ One claim on this page is corrected rather than defended: variant A's note says "there is no assistant message to hang this on." That is stronger than what was measured — a NULL runs.message_id means the run cannot be joined to a message from the run side; it does not prove no assistant row exists. A's real weakness is that its mark is a message property while the thing that stopped is a run.

⚠ Converges with sketch 171. This line and 171's run-anchored kickoff line are one component in two states — see 171's README.

One line, rendered for any thread that owns a workflow run, derived from workflow_runs rather than from a message. It cannot be lost, because it is not attached to anything that can be missing: ⊘ Stopped by you · 2 of 3 steps · 2m 18s, with a seam back to the run.

It is the shipped RunCard strip's sentence — Run · {n} steps · ■ cancelled · {elapsed} — promoted from a property of the message to a property of the thread. Drive all three shapes: B reads identically in every one, which is the whole claim.

The cost, stated rather than buried. Chat does not read workflow_runs by thread today. B adds a read the chat surface does not have — and Phase 194's D-14 already examined this exact file and declined to thicken the receipt, on the grounds that the panel owns the meaningful phase spine and chat carries a thin run receipt (the 094/103 split). B is a deliberate argument against a decision made eleven days ago. If it wins, that reversal is the decision to record.

C — Chat stays thin; the panel spine carries it

honours 094/103 strictly

The strictest reading of the shipped split: the run's detail belongs to the workspace panel, and the thread carries only what a transcript needs. The spine already reads act ■ Stopped correctly after a reload — C's work is making it read that way live, and leaving chat alone.

Judge C against the actual complaint. The operator was looking at the thread. Collapse the panel — the rail is a legitimate, common state — and C has nothing. It is the cheapest variant and the one most likely to close the bug on paper while leaving the reported experience intact.

The contract

Three things bind whichever variant wins, and one of them is a decision this sketch cannot make alone.

#RuleWhy
1 The mark is derived from persisted state, never from live streaming state. Phase 174 D1 already says this — “derive it from persisted runs.status so it survives reload” — and BUG-260710-01 is the same family failing on the Deep surface, status: folded into 174 with verified_closed_by: null. A live-only badge is how this bug is two months old.
2 A pending approval must not survive the stop. The zombie card is the sharper half of BUG-260816-02: it invites an action that will silently go nowhere. ⚠ It must be retired with a sentence, not silently removed — a card that vanishes mid-read is its own small dishonesty.
3 The stop must not read as though nothing survived. Phase 194 D-13 keeps a stopped run's completed phases and explicitly rejects “collapsing to a bare cancelled that hides partial work … it discards evidence the database still holds.” Every variant here carries the step count in the same sentence as the word.

⚠ The decision this sketch cannot make alone

BUG-260710-01 and BUG-260816-02 are the same family on two surfaces, and they must be looked at together. One is a Deep chat message losing its badge; this is a harness run whose thread carries a spine, a receipt and a kickoff prompt — a different renderer over a different source of truth (workflow_runs + workflow_phases, not runs). A fix to one does not automatically fix the other. Whether 194.1 closes both or only the workflow half is a scoping call for 194.1-CONTEXT.md — and if it closes only one, the other's frontmatter must say so, because status: is the index a routing scan reads.
