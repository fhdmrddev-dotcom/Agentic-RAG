## Priority carry-forwards (build first, when triggered)

### 169 — Dept-Admin Shell (ADMIN-06)
- **Delivers:** a narrower dept-admin shell (Dept Members / Dept Skills / Dept Retention / Dept Audit) gated on `dept:manage`.
- **User value:** delegation. A department head gets their own scaled-down control panel for just their department, so an org-admin doesn't have to manage everything centrally.
- **Depends on:** 166 (org-admin shell) + 167 (roles/greenlists) — **both shipped, so the substrate is ready NOW.**
- **Why deferred:** additive UI polish; only pays off once a real org runs multiple departments needing *delegated* (non-org-admin) administration. No data-model change → zero risk in waiting.
- **Re-open trigger:** a real or prospective customer org has ≥ 2 departments that need delegated administration by someone who is *not* the org-admin.
- **Build approach when revived:** **G-2 sketch REQUIRED** (it's a visual surface). Mirror the Phase-166 `OrgAdminShell` sibling-tab pattern verbatim; add dept-scoped tabs gated on `dept:manage`; reuse the `require_*` authz pattern scoped to the department (the `dept_members` / `current_user_has_permission(org, 'dept:manage')` seam already exists from mig 104). Frontend-heavy + a thin authz router; ~1 phase. No migration expected (schema already present).

### 171 — Permission-Aware Citations (PRAG-02)
- **Delivers:** an AI answer **never cites or previews a document the asking user cannot open**.
- **User value:** closes a subtle leak — a restricted document's title/snippet can't surface through a citation to someone not allowed to read it.
- **Depends on:** 164 (PRAG-01 chunk RLS) + 167; **AND dept/role folder-sharing landing and stabilizing first.**
- **Why deferred (correct sequencing, not just convenience):** with the membership-based RLS shipped in 163/164, retrieval already runs *under the asking user's context* — so today citations only reference documents that user can already open. **The leak surface is latent.** It becomes *reachable* only once finer-grained sharing (dept/role folder-sharing, cross-user document sharing) lets a document be retrievable-in-context yet not-openable-by-the-asker. Building the guard before that surface exists = guarding a threat that can't yet occur.
- **Research-gate (do NOT skip):** a CITE-01-style leak threat model + an **unmeasured pgvector + RLS latency/recall benchmark** (permission filtering at retrieval time can hurt recall/latency — must be measured before committing an approach). **G-5 hot files:** `retrieval_service.py` + the citation renderer — do not regress the shared Deep path.
- **Re-open trigger:** **BEFORE any dept/role folder-sharing (cross-user document sharing) ships to a real tenant.** That is the exact moment the leak becomes reachable — this phase must land in the same milestone as, or immediately before, that sharing feature goes live.
- **Build approach when revived:** research-phase first (leak model + pgvector+RLS bench), then a share-don't-fork guard that filters citations/previews to the asker's *openable* set at answer-assembly time (not a fork of the Deep path — G-5). SC#10 cross-provider proof required (citations are a shared-path surface).

## Lower-priority carry-forwards (build only when the trigger fires)

### 170 — Commercial Footholds — Entitlements + Retention/Rate-Limit Data Layer (ENT-01, ENT-02)
- **ENT-01 delivers:** a real entitlement-check primitive (`require_tier()` / `require_add_on()`) reading `orgs.subscription_tier` / `add_ons`, replacing the current stub `_is_tier_pro_or_higher` that **always returns `True`** (SEED-080). Enforcement footholds only — **no billing / checkout.**
- **ENT-02 delivers:** a per-org retention + rate-limit **data layer + org-admin UI** (schema + surfaces only). **The sweeper / token-bucket *enforcement* is deferred to v3.5 / v3.6** — this ships the dials, not the engine behind them.
- **User value:** groundwork for tiered plans (features gated by Free/Pro/Enterprise) and per-org retention/rate-limit settings an org-admin can see and configure.
- **Depends on:** 161 (org schema) + 166 (org-admin shell) — substrate ready.
- **Why deferred:** premature without a near-term monetization push; a settings surface with no enforcement engine can read as "fake." Better shipped alongside the enforcement work.
- **Re-open trigger:** monetization/tiering enters the near-term roadmap, OR a real customer needs enforced per-org retention/rate limits (then pair ENT-02 with its v3.5/v3.6 sweeper/token-bucket).

### 172 — OIDC Enterprise SSO (SSO-02)
- **Delivers:** OIDC enterprise SSO via a custom Authlib service provider — the one org-SSO protocol Supabase does **not** offer natively (SAML, shipped in 168, it does).
- **User value:** customers whose identity provider speaks **OIDC** (not SAML) can also use SSO.
- **Depends on:** 168 (SSO substrate — done). Threat model: discovery-endpoint SSRF. New scope-gated dep: Authlib.
- **Why deferred:** explicitly **customer-triggered** — build only if a customer forces OIDC into scope. SAML (168) covers the common enterprise case.
- **Re-open trigger:** a real/prospective customer's IdP is OIDC-only and blocks a deal.

### 173 — Dept-Targeted Skills + Group Feature-Rollout Gating (VIS-03, VIS-04)
- **VIS-03 delivers:** department-targeted skill / automation availability (a dept sees its own skills).
- **VIS-04 delivers:** admin tiers assignable to groups + per-group beta / feature-rollout gating (turn a new feature on for one group first).
- **User value:** targeted skill visibility + gradual/controlled feature rollouts per group.
- **Depends on:** 165 (`is_global` retirement) + 167 (greenlists).
- **Why deferred:** nice-to-have; cheapest to fold in *if* skills' RLS/visibility is being rewritten anyway (don't open that surface just for this).
- **Re-open trigger:** the skills visibility/RLS layer is being reworked for another reason (fold in then), OR a customer needs per-department skill targeting or staged feature rollouts.
