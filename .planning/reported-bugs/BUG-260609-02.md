# BUG-260609-02: Sub-Results shows a phantom generic "Sub-task" for a non-batch workflow

## What we observed

On the completed "Doc Q&A (098 UAT)" workflow thread (a 3-phase, NON-batch workflow: `draft` llm_agent → `confirm` ask_user → `finalize` llm_single), the workspace panel renders a **SUB-RESULTS** section with **count 1** and one row labelled generically **"Sub-task — Done"**, disabled (not expandable, i.e. no summary). The operator asked what this section is and why it shows generic sub-task entries.

DB evidence: the thread has TWO `runs` rows — a parent (`0cfc2460…`) and a child with `parent_run_id = 0cfc2460…` (`5bf1b5b1…`, claude-haiku, completed). So a **real task-variant sub-agent was spawned** during the run (a `runs` row exists → `task_service.run_task_sub_agent` path, not the inline `analyze_document` event-only path).

## Why it matters

Minor run-honesty/labeling defect. SUB-RESULTS is meant for **batch fan-out** phases (`llm_batch_agents`) — N child agents, one per sub-question, each with a readable summary. Showing a single unlabelled, non-expandable "Sub-task" on a non-batch workflow is confusing: the operator can't tell what ran, why, or see its result. It also raises a scoping question (should a phase-internal sub-agent appear in SUB-RESULTS at all?).

## REFINED 2026-06-10 (Test 2 live UAT, gpt-5.4-mini + gemini) — NOT a phantom; a reconcile gap

Operator observed on the Test-2 multi-tool runs: the SUB-RESULTS row shows the task's **real description + details when uncollapsed DURING the run**, but after navigation it collapses to the bare generic **"Sub-task — Done"** (description + summary gone). So `tasksByThread` HAS the rich data live; it is LOST on nav.

The sub-task is REAL and structural: the harness runs each `llm_agent` phase **as a task sub-agent** (`run_task_sub_agent`) — the workspace's "1 agent" label. DB confirms a child `runs` row per run (e.g. Test-2 gpt: TOP `5aac4f77` → child `7d6ee524`; Doc Q&A: `0cfc2460` → `5bf1b5b1`). So it is the PHASE's own agent, not a batch fan-out child and not a tool-spawned analyze sub-agent.

Confirmed root cause = the SAME reconcile-gap family as BUG-260609-01/03: `tasksByThread` (the panel-only task slice) carries the live `sub_agent_start.description` + `sub_agent_done.summary`, but on navigation/reload it is NOT reconciled from a durable source — it re-hydrates a minimal/stale entry (id + status), so `BatchResultList.cleanDescription()` falls back to the literal `"Sub-task"` (`BatchResultList.tsx:41`) and the row is non-expandable (no summary). Live = rich; post-nav = bare.

Open DESIGN question (operator decision before fixing): should the phase's OWN agent appear in SUB-RESULTS at all? It is arguably redundant with the phase card in the WORKFLOW section. Options:
1. **Persist/reconcile** the task's description+summary so it survives nav (keep showing it, but honestly).
2. **Gate it out** of SUB-RESULTS — reserve SUB-RESULTS for true `llm_batch_agents` fan-out children (phaseType-gated), since a single-agent phase's task duplicates the phase card.

## Related minor observation (Test 2): 1–2s empty assistant bubble

Harness surfaces the whole answer in ONE delta at the end (`_surface_final_answer`), so the chat assistant bubble shows only the logo (empty) for the phase duration (~1–2s on a fast single-phase run), then the answer pops in. Progress is shown in the workspace panel meanwhile. Expected-by-design (not token-streamed like Deep), but a brief "is it stuck?" rough edge — low severity, polish candidate (e.g. a phase-progress hint in the bubble during harness runs).
