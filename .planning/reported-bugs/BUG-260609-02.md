# BUG-260609-02: Sub-Results shows a phantom generic "Sub-task" for a non-batch workflow

## What we observed

On the completed "Doc Q&A (098 UAT)" workflow thread (a 3-phase, NON-batch workflow: `draft` llm_agent → `confirm` ask_user → `finalize` llm_single), the workspace panel renders a **SUB-RESULTS** section with **count 1** and one row labelled generically **"Sub-task — Done"**, disabled (not expandable, i.e. no summary). The operator asked what this section is and why it shows generic sub-task entries.

DB evidence: the thread has TWO `runs` rows — a parent (`0cfc2460…`) and a child with `parent_run_id = 0cfc2460…` (`5bf1b5b1…`, claude-haiku, completed). So a **real task-variant sub-agent was spawned** during the run (a `runs` row exists → `task_service.run_task_sub_agent` path, not the inline `analyze_document` event-only path).

## Why it matters

Minor run-honesty/labeling defect. SUB-RESULTS is meant for **batch fan-out** phases (`llm_batch_agents`) — N child agents, one per sub-question, each with a readable summary. Showing a single unlabelled, non-expandable "Sub-task" on a non-batch workflow is confusing: the operator can't tell what ran, why, or see its result. It also raises a scoping question (should a phase-internal sub-agent appear in SUB-RESULTS at all?).

## Hypothesized cause (needs focused root-cause — NOT yet confirmed)

`BatchResultList.cleanDescription()` returns the literal `"Sub-task"` when `task.description` is empty (`BatchResultList.tsx:41`), and a row is only expandable when `task.summary` is non-empty. `task_service` DOES emit `sub_agent_start` WITH a `description` (`task_service.py:577`) — so the empty label means **the caller spawned the sub-agent with an empty `description`** (and no `summary` was captured into `tasksByThread`). Open questions for root-cause:
1. WHAT spawned a task sub-agent inside a `llm_agent` phase whose `available_tools` was only `["search_documents"]`? (a `spawn`/delegate path, or `analyze_document` re-routed through `run_task_sub_agent`?)
2. Should a phase-internal/tool-spawned sub-agent surface in SUB-RESULTS at all, or only true `llm_batch_agents` fan-out children?
3. If it should surface, map a real label (e.g. the doc filename + task) and capture its summary; if not, gate it out of `BatchResultList`.
