# BUG-260609-03: Workflow final answer renders twice in the UI

## What we observed

Operator reported (098 live UAT) that the FINAL result of a workflow run **renders twice** in the chat — two identical complete answer blocks stacked vertically. Evidence: `screenshots/FireShot Capture 002 - Agentic RAG - [localhost].png` (a "RPA Adoption Success Factors" literature-review workflow — the same Section/What's-in-it table answer appears twice, in full).

## Key diagnostic (DB + API + cross-browser) — CORRECTED 2026-06-09

Operator clarified the timing (cross-provider): **LIVE the answer renders ONCE (correct); the duplicate appears only AFTER navigating to another thread/page OR a full refresh, and does NOT clear on subsequent refresh.** So it is the RELOAD/fetch render path that doubles, not the live path.

Backend is exonerated: `messages` has **exactly ONE** assistant row per thread, AND `get_messages` → `_enrich_messages_with_runs` (threads.py:266-289) builds a per-message-id map and enriches IN PLACE (no JOIN fan-out) → the API returns ONE assistant message. So this is a **frontend double-RENDER on reload**, not double-persist and not an API fan-out.

KEY ASYMMETRY: a browser that NEVER streamed the run live (e.g. the MCP Chrome that only ever fetched the thread) shows ONE answer on reload; the browser that DID stream it live shows TWO after reload. → Strong signal that the **live-streamed assistant copy is cached (localStorage via `streamsCache`) with an id/key that does not dedupe against the FETCHED persisted message**, so on reload both the cached-streamed copy and the fetched copy render. Persists across refreshes because the cache isn't invalidated.

## Why it matters

Major run-honesty/correctness-of-presentation defect: a duplicated final answer makes a workflow look like it ran/answered twice, erodes trust, and doubles scroll length. Provider-agnostic (the report was on a sonnet-4-6 run; needs cross-provider confirm).

## Hypothesized cause (NOT yet confirmed — needs live repro)

Likely a frontend dedup/keying gap between (a) the LIVE streamed assistant message built from `_surface_final_answer`'s delta/grounding emit on the producer stream, and (b) the persisted/reconciled message loaded from the DB — both rendering with different keys before reconcile collapses them. The harness surfacing was explicitly consolidated to a single owner (`harness_engine._surface_final_answer`; "the live-kickoff branch no longer surfaces inline — no double-persist") so the duplication is on the RENDER side, not the persist side.

## Answered diagnostic (2026-06-09)

Reload does NOT collapse it — it SHOWS two and persists; live shows one. A never-streamed browser shows one. → The cached live-streamed copy + the fetched persisted copy both render after reload (id/key dedup gap in the streamed-vs-fetched message merge).

## CONFIRMED ROOT CAUSE + FIX (2026-06-09, commit pending)

Root-caused by an 8-agent workflow (high confidence, adversarially verified): the harness producer-shell run leaves `runs.message_id` NULL **by design** (harness_engine.py:353-357), so on reload `_enrich_messages_with_runs` (threads.py:266-289) returns the fetched harness answer with `runId=undefined`. The live-streamed copy keeps its `temp-…` id with `runId=<run_id>` (never id-swapped at terminal). The merge preserve-predicate kept a temp whenever `!dbRunIds.has(m.runId)`; since the fetched harness row has no runId, `dbRunIds` never holds the run_id → the cached temp survived next to the DB copy, and `MessageList` keyed them differently (`run-<run_id>` vs `<db-uuid>`) → two bubbles. Deep chats link `runs.message_id` (finalize_run) so they always deduped — which is why this was harness-only. The verifier also caught that the "obvious" backend fix (UPDATE runs.message_id in `_surface_final_answer`) would be **silently clobbered** by `_shielded_finalize`/`finalize_run` writing NULL afterward — so the safe fix is frontend.

FIX (frontend-only, additive, Deep untouched): in BOTH merge sites (loadMessages ~1980, reconcile ~1291) keep a runId-bearing `temp-` copy ONLY while genuinely in flight — `subscriptionsRef.current.has(runId)` OR (`!dbRunIds.has(runId)` AND `runStatus === "streaming"`). On reload there's no live subscription and a terminated (`completed`) orphan temp is dropped → the fetched DB copy renders once. The untyped-temp (`!runId`) sendInFlight branch is untouched (075.7 race protection). tsc clean; zero net-new vitest failures (combined suite 11/44 == baseline; streamPool 5/5 alone). Files: StreamsProvider.tsx. Stale 2-row buckets self-heal on the next reconcile. Live re-verify pending.
