# BUG-260718-01: Discovery panel pre-selects all ~400 new models — no opt-in, no search

## What we observed

Operator, during live UAT of Phase 159: running model discovery returns the full provider pull (~400 "new" models) with **every model pre-selected (accepted)**. There is **no text search** to find a specific model, and no way to select just one. Clicking "Apply confirmed changes" would therefore write ~400 new registry rows when the operator only wanted to add one.

Expected: adding one model from discovery should be easy — start with nothing selected, find the model, add it.
Actual: everything is pre-checked; the only path to "add one" was manually unchecking ~399 rows.

## Why it matters

Major usability defect on the operator model-registry surface: the discovery→confirm flow was effectively "add everything unless you manually deselect 400", the opposite of the curation goal Phase 159 set out to deliver. High risk of accidentally bulk-adding hundreds of unwanted (incl. utility) rows.

## Hypothesized cause

`ModelDiscoveryPanel.run()` seeded `accepted` with every `res.new` model id (accept-all-by-default, inherited from the Phase-149 "propose→confirm" panel). The Phase-159 utility filter was display-only and did not reduce the confirm payload, and there was no text search over the new-models list.

`Agentic-RAG` — this app's operator/admin discovery UI. A routing candidate.
