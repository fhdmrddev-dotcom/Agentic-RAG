# BUG-260718-04: Chat model selection resets to default on navigate/refresh — not remembered per thread

## What we observed

Operator picks a specific model for a chat. After the chat finishes, OR after navigating away, OR after refreshing the page and returning to the same thread, the model picker has **reverted to the default model** — it does not remember the model that thread was using. Desired: a thread remembers its **last-used model** (the operator may switch models mid-thread; keep the latest one used in that thread).

## Why it matters

Real workflow friction on a core control: the operator deliberately chooses a model per conversation, but the app silently reverts to the default, so a follow-up message in an existing thread can go to the wrong model unless they re-select every time. Higher than cosmetic — it affects which model actually answers. Severity: major.

## Hypothesized cause (read-only check)

`selectedModel` is ephemeral component state seeded from the GLOBAL default, never restored per-thread:
- `frontend/src/components/chat/ChatArea.tsx:63` — `const [selectedModel, setSelectedModel] = useState<string>("")`.
- `ChatArea.tsx:154-156` — on load it seeds `preferred = active_model ?? activeProvider.models[0]` (the global default), and `:201` resets to `p.models[0]` on provider change.
- `ChatArea.tsx:320` — the model IS sent per message (`sendMessage(..., selectedModel || undefined, ...)`), so each stored message already carries the model it used.
- On thread switch / remount / refresh, `selectedModel` re-initializes to the default; there is no per-thread restore.

So the data to restore from likely already exists (each message stores its model). The gap is purely the restore-on-load.

## Surface classification

`Agentic-RAG` — chat model control. Routing candidate.

## Suggested routing

- **Fold into in-flight phase:** n/a (deferred)
- **Defer to future phase / milestone:** post-v3.3. Options: (a) derive the thread's last-used model from its most recent assistant/user message's model on load and seed `selectedModel` from it (no new storage — the model is already persisted per message); (b) persist the per-thread selection explicitly (thread metadata field or localStorage keyed by thread_id); fall back to the global default only for brand-new threads or if the stored model is no longer enabled in the registry. Prefer (a) if the message model is reliably available client-side.
- **Plant as seed:** candidate if not scheduled next milestone.
- **External — note only:** no

## Workarounds

Re-select the model each time you return to a thread.
