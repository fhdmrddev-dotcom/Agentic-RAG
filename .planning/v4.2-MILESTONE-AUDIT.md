### B-2 · The phase's own resilience handler logs the credential it refused to store — `CRED-01`

`backend/app/services/connector_service.py:578-581` — confirmed in source:

```python
logger.warning(
    "connector_service._to_response: validation failed for connection %s: %s",
    d.get("id"),
    e,                      # ← the raw pydantic ValidationError
)
```

Pydantic v2's `ValidationError.__str__` echoes `input_value` on every union arm. The integration checker
drove the real model through the venv and measured **six occurrences of the secret in one message**.

⛔ **The population this fallback exists for is precisely the legacy rows that already hold a secret in
`custom_client_id`** — the code comment says so. **The phase moved the secret out of an org-readable
column and into the application log.** TM-248-06 is satisfied by the validator's own message and defeated
by a handler three files away.

**Fix:** `e.errors(include_input=False)`. One line.

### B-3 · A fourth writer bypasses the boundary and can brick a connection permanently — `CRED-01`

The `CustomClientId` validator guards three **request models**. `backend/app/api/connectors.py:1326-1352`
(RFC 7591 dynamic client registration) takes `client_id` from a **remote server's response** and hands it
to `connector_service.py:654`, which writes it unvalidated.

Two consequences, and **the second is worse than the bypass**: once a non-compliant server-issued id is
stored, every read of that connection fails `model_validate` and falls into B-2's degradation — reading
`status="error"` **forever**, with no repair path, because the operator never typed the value and cannot
type a compliant one.

⚠ **This is the exact path whose G-4 UAT scenario S2 is recorded ⛔ owed.** The one scenario not driven
is the one carrying the bypass.

### B-4 · "Sync now" reports a completed sync from a string literal — `WATCH-04`, `WATCH-06`

`frontend/src/components/sources/WatchRowCard.tsx:234-244` — confirmed in source:

```js
await onSyncNow(watch)
setSyncOutcome("✓ Synced just now (0 changes)")
```

`onSyncNow` is typed `(watch) => Promise<void> | void` — **it carries no result.** Three defects in six
lines: it claims completion where the parent's real handler only **queues**; `(0 changes)` is a literal
that renders identically for 0 or 500 changes; and there is **no `catch`**, so on a refusal the card
renders the refusal notice at `:611-613` *while* `syncOutcome` at `:380-385` reads `✓ Synced just now` —
**two contradictory statements from one click, on one card.**

⭐ SC#3's evidence is a test named *"does NOT unmount or collapse the card"* — a non-collapse assertion,
which structurally cannot see what the card **says**. This project's own recorded finding:
**presence assertions cannot see content drift.**

### Flow C, and why `BUG-260915-01` must be corrected before anyone builds its fix

The defect is real: `TodosSection.tsx:262-264` derives `isRunLive` from `streamingThreads ∪
loadingThreads`, and renders **`Not ticked` on a LIVE run** when that reads false.

⛔ **But the report's stated mechanism is measurably false, and a fixer following it would ship a no-op.**
The report says *"opening a thread triggers no reconcile."* Measured: `StreamsProvider.tsx:1936-1942` —
`setViewingThread` **does** fire `actions.reconcile(threadId)`, and `ChatArea.tsx:323-325` calls it in a
`useLayoutEffect` on `[thread?.id]`. **Fix candidate #1 is already implemented.**

**The production hole is different and wider:** on thread open `loadMessages` is never called, so
`loadingThreads` is never set and the `||` buys nothing — every open todo reads `Not ticked` for the
duration of the `/snapshot` round-trip on **every** thread open. And `reconcile`'s in-flight lock is
**global, not per-thread** (`StreamsProvider.tsx:1975`), so a dropped reconcile leaves the false state
until the user tabs away and back — which is the persistent symptom the report actually describes.
**Candidate #2 (derive liveness from the thread's own run row) is the correct fix.**

**Hole 2 — the panel's other run-state surface was never in scope.** `WorkspacePanel.tsx` mounts both
`TodosSection` (`:68`) and `PhaseTimeline` (`:72`). `PhaseCard.tsx:407` derives `isRunning` from the
SSE-driven phase status, **not from run liveness**, and drives a spinner, `aria-busy` and a forced-open
row. A run that dies without emitting its phase-terminal event leaves a phase card claiming *running*
forever. `git grep` over Phase 250's artifacts returns **zero** mentions of `PhaseCard`, `PhaseTimeline`
or `phaseStatusMeta`.

**HONEST-03's wording is *"the workspace panel"*. One of its two run-state surfaces was made honest.**
