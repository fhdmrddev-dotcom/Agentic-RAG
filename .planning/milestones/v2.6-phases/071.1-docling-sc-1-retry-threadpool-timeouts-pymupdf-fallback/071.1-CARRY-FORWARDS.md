# Phase 071.1 Carry-Forwards — Things to Investigate Later

This document is the *honest* close-out for Phase 071.1. The SUMMARY.md
reports what shipped; this file captures what we *didn't* fix, what we
discovered along the way, and what's worth investigating before the next
extraction-quality phase.

## Headline: Docling integration was a stability win, not a quality win

Phase 071's stated goal (and the v2.6 PRD § Docling-first rationale) was
extraction-quality improvement: better tables, better figures, better
multi-column handling. **What the 2026-05-15 UAT actually showed:**

| Metric | `pypdf-legacy` (pre-Phase-071) | `docling` (post-071.1) | Change |
|---|---|---|---|
| Thesis PDF `document_tables` | 4 | 4 | **0** |
| Thesis PDF `document_images` | 2 | 2 | **0** |
| Thesis PDF `document_chunks` | ~400 (estimated baseline) | **19** | **−95%** |
| Thesis DOCX `document_tables` | 39 | 39 | **0** |
| Thesis DOCX `document_images` | 0 | 0 | **0** |
| Thesis DOCX `document_chunks` | 402 | 479 | +19% |
| Thesis PDF extract time | ~1-5s typical | **125s** | **+25-100×** |
| Backend `/health` during extract | frozen for 4+ min (Phase 071 RED) | 1-2s (responsive) | structural fix |

What 071.1 actually delivered:
- ✓ The 4-min Docling stall is structurally eliminated (Plan 01's Layer 2
  wall-clock + threadpool sweep + auto-fallback)
- ✓ Backend stays responsive during in-flight extracts
- ✓ Architectural seam (Phase 069 dispatcher) lets us pick engines per-call
- ✓ Telemetry visibility (`pdf_extraction_runs` table populated cleanly)

What 071.1 did **not** deliver:
- ✗ Better PDF table extraction (same 4 tables as legacy)
- ✗ Better PDF figure extraction (same 2 images as legacy — and SEED-006
  has documented this is ~5% of what's visible in the document, since 2026-05-02)
- ✗ Closing the PDF-vs-DOCX delta (still 89.7% / 100%)
- ✗ Text-extraction parity — the PDF chunk count cratered 95%, which suggests
  Docling's `text` output is much shorter than legacy's on this PDF (regression
  candidate, see §"Open investigations" below)

User-decision 2026-05-15: **revert `EXTRACTOR_PRIMARY=legacy`** in
`backend/.env` so new uploads + `/reingest` no longer pay Docling's 25-100×
time tax for zero quality gain. Docling and PyMuPDF remain available per-doc
via `/reextract` body `{"engine": "..."}`. Restart required for the env
change to take effect.

## Open investigations (Phase 071.2 candidates)

These are diagnostic / surgical fixes, not big rewrites. Most are <1 day each.

### 1. Why did PDF chunks drop 95% under Docling? (suspected text-extraction regression)

- **Observation:** Thesis PDF chunks went from ~400 (legacy baseline) to 19
  (Docling). Same source bytes, same chunker.
- **Hypothesis A:** Docling's `result.document.export_to_markdown()` (or
  whatever the chunker reads) on this specific PDF returns much less text
  than legacy's `pypdf.extract_text() + pdfplumber` cascade.
- **Hypothesis B:** The chunker is doing something different with Docling's
  markdown output vs legacy's plain text — e.g., respecting heading
  boundaries too aggressively and producing oversize chunks that then get
  dropped or merged.
- **Hypothesis C:** Docling silently failed text extraction on some pages
  and we never noticed because the foreground extract returned successfully.
- **Diagnostic:** Call Docling directly on the thesis PDF (already wired in
  `backend/scripts/probe_docling_timeout.py`); print `len(result.document.export_to_markdown())`
  and compare to `pypdf.PdfReader(pdf).pages[i].extract_text()` summed.
  ~30 min of work. If Docling's text is much shorter, this is the bug.
- **Severity:** Likely the most impactful gap of all the items in this doc —
  retrieval relevance is bounded by chunk count + chunk content. A 95% drop
  in chunks means RAG on Docling-extracted PDFs is materially worse than
  RAG on legacy-extracted PDFs.

### 2. The 4-vs-1 table-count mismatch in /reextract telemetry

- **Observation:** Docling foreground extract on thesis PDF reports
  `table_count=1` in `pdf_extraction_runs` telemetry. But `document_tables`
  ends up with 4 rows. Where do the other 3 tables come from?
- **Hypothesis:** `ingest_document`'s `extract_and_store_tables` (called
  from the BackgroundTask after `/reextract` returns 202) runs a SEPARATE
  table-detection pass — likely still using pdfplumber's `find_tables()` —
  rather than reading Docling's `result.tables`. If true, Docling's
  table-extraction output is being **silently discarded** by the storage
  pipeline.
- **Diagnostic:** Read `backend/app/services/multimodal_service.py` and
  `backend/app/api/documents.py:ingest_document` to trace which code path
  populates `document_tables` from `extracted_doc.tables`. Compare to what
  Docling actually returns. ~1 hour.
- **Severity:** High — this means Docling's *only* potential quality gain
  on tables (better detection) is not reaching the database at all. The 4
  tables coming through are pdfplumber's, not Docling's.

### 3. `/reextract` 500s when document row has `is_latest=False`

- **Observation:** First thesis PDF retry returned 500 in 2.15s. Root cause:
  the route's first query is
  `supabase.table("documents").select("*").eq("id", id).eq("user_id", uid).eq("is_latest", True).maybe_single().execute()`.
  When `is_latest=False` (which the thesis row had from Phase 071's failed
  cascade), `.maybe_single()` raises an exception that isn't caught.
- **Fix:** Either pre-clear `is_latest=True` in the reset cascade, OR
  catch the empty-result case and return a clean 404 instead of 500.
- **Workaround applied 2026-05-15:** Manual PATCH `is_latest=True` on the
  thesis PDF row before the retry could run.
- **Severity:** Medium — silently 500s on any doc that previously failed
  ingestion. User-visible as "Re-extract didn't work, no error shown".
- **Scope:** Single-line fix.

### 4. SEED-006 still applies — multimodal storage gating bottleneck

- **Status:** SEED-006 is dormant, planted 2026-05-02, scope "Medium" (4-5 plans,

### 5. TableFormer A/B with `DISABLE_TABLE_STRUCTURE=1`

- **Question:** Does disabling TableFormer change Docling's behavior
  materially on this thesis PDF? The env knob is already wired (Plan 01).
- **Diagnostic:** Set `EXTRACTOR_DOCLING_DISABLE_TABLE_STRUCTURE=1`,
  restart uvicorn, `/reextract` the thesis pair with `engine='docling'`,
  compare telemetry table_count + duration vs the 2026-05-15 baseline.
  ~10 min of work + ~3 min of extract time.
- **Severity:** Low — informational. Tells us whether TableFormer is the
  slow path or whether Docling's slowness is layout-prediction.

### 6. Docling resource intensity — overall assessment

- **Initial model load:** ~30s on first call per process (lazy singleton).
- **Per-extract overhead:** 22-125s for PDFs (vs 1-5s legacy). DOCX is fast
  (~3-6s).
- **First-run download:** ~600 MB of TableFormer + layout models cached in
  `~/.cache/docling/`.
- **RapidOCR loads even when `do_ocr=False`** — visible in logs:
  ```
  [INFO] [RapidOCR] device_config.py:57: Using CPU device
  [INFO] [RapidOCR] download_file.py:60: File exists and is valid: ch_PP-OCRv4_rec_mobile.pth
  ```
  This is wasted boot cost. Worth investigating whether `do_ocr=False`
  should genuinely skip RapidOCR import (saves ~150 MB resident memory
  per worker).
- **Conclusion:** Docling is too expensive to be the silent default on a
  single-worker uvicorn under D-v2.5-02. Worth keeping as an *opt-in*
  per-doc engine until either (a) it earns its keep on quality, or
  (b) Phase 077's multi-worker / async architecture gives it room to run
  on a background worker without blocking interactive paths.

### 7. No frontend UI for engine switching

- **Observation:** `frontend/src/` has zero references to
  `reextract` / `extractor` / `engine`. The only way to pick an engine
  today is curl-ing `/reextract` directly.
- **Recommended:** Small dropdown on each document row: "Re-extract with
  [Docling ▾]" → POST `/reextract` body `{"engine": "..."}`. Backend
  already does the work; this is ~30-60 min of frontend work.
- **Bigger surface (deferred):** D-PRD-09 admin shell (v3.1) is the proper
  home for default-engine settings + per-user prefs + fallback chain.
- **Carry-forward note:** Without a UI, future operators will keep
  re-discovering "how do I test a different engine on doc X" as a friction
  point. Plant as SEED-016 candidate or fold into a small v2.6 polish phase.

### 8. Engine fallback chain (broader Q from this session)

- **Today's reality:** No automatic legacy → pymupdf → docling fallback
  chain. The only fallback that exists is Docling-timeout → PyMuPDF inside
  `/reextract`, wired by Plan 01.
- **Possible feature:** `EXTRACTOR_FALLBACK_ORDER=legacy,pymupdf,docling`
  env var + `get_extractor()` wrapped in a try/except chain reading the
  list. ~30 LOC + tests.
- **Decision:** User chose Option A (just flip default to legacy) over
  Option B (default + chain) on 2026-05-15. Chain is a SEED-017 candidate
  if it doesn't naturally fold into 071.2 / 072.

## What we actively chose to NOT do during this UAT

For audit purposes — these were live options that we considered and explicitly skipped:

1. **`/reingest` route threadpool sweep** (CONTEXT.md scope-bounded out).
   Same async-handler-with-sync-IO pattern as `/reextract`, but skipped
   per D-071.1-01 to keep the SC#1 retry on schedule. Re-open trigger:
   Phase 077 (multi-worker / asyncpg) is the natural place; OR earlier
   if `/reingest` is observed blocking the worker on a real upload.

2. **Full-file documents.py sync-call audit.** Plan 01 narrowly fixed only
   `/reextract`. Other async handlers in `documents.py` may have the same
   bug pattern. Re-open trigger: production observability shows event-loop
   freezes during other operations.

3. **`PYMUPDF_TIMEOUT_S` revisit** (currently 60s subprocess timeout).
   May not be long enough for thesis-class PDFs on the auto-fallback path.
   Did NOT trip during 071.1 UAT (auto-fallback never fired since Docling
   completed within budget). Re-open trigger: future UAT shows PyMuPDF
   timing out on the fallback path.

4. **Recalibrating confidence thresholds for Docling chunk distributions.**
   Phase 076 owns RAG-RECAL-01. Out of 071.1 scope.

5. **Adding `EXTRACTOR_DOCLING_TIMEOUT_S` to `app_settings`** (admin-level
   knob). Env-only for v2.6; admin shell surface is v3.1 (D-PRD-09).

6. **A binding pytest against `friendly_real.pdf`.** Would require
   committing the PDF for CI + running Docling in CI (~600 MB model
   download per run). Out of scope for v2.6. `academic_synth.pdf` (the
   reportlab-generated synthetic) remains the CI regression net;
   `friendly_real.pdf` is UAT-only.

## Honest assessment

Phase 071's v2.6 PRD justification was "Docling-first for better extraction
quality on academic PDFs." Phase 071 shipped, Phase 071.1 ironed out the
stall — but **the quality story is unfinished**. Plan 01 was honest
plumbing work. The user's intuition ("if quality didn't enhance, what is
the point of integrating Docling?") is correct on the data we have today.

Three possible resolutions:
1. **Investigate then fix** — items #1 and #2 are concrete, narrow, and
   could prove Docling's quality value if the wiring bug is real
2. **Demote Docling** — keep it as opt-in via `/reextract`, default stays
   `legacy`, accept that v2.6 PRD's Docling-first thesis is informally
   reversed (worth a brief PRD note for v2.7 reset)
3. **Defer decision** — flip default to `legacy` for now (DONE 2026-05-15),
   plan a Phase 071.2 in a future session when budget allows

User-chosen path 2026-05-15: option 3 (defer + flip default + plan later).
This carry-forwards doc is the receipt.
