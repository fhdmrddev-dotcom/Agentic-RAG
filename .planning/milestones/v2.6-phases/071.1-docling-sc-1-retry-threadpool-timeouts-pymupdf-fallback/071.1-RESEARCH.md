# Phase 071.1: Docling SC#1 retry — threadpool, timeouts, PyMuPDF fallback — Research

**Researched:** 2026-05-15
**Domain:** Docling 2.93 timeout semantics + asyncio/threadpool concurrency + PyMuPDF fallback dispatch in FastAPI
**Confidence:** HIGH (Docling API verified directly against installed 2.93.0 source; asyncio.wait_for + thread behavior verified against CPython docs)

## Summary

Phase 071.1's central unknown — *"what is the exact Docling 2.93 API surface for per-call `document_timeout` enforcement?"* — resolves to: **there is no per-call override surface in Docling 2.93's public API.** `document_timeout` is a field on `PdfPipelineOptions` (and `BasePipelineOptions`); it is applied once at `DocumentConverter` instantiation via `format_options={InputFormat.PDF: PdfFormatOption(pipeline_options=opts)}`. The `convert()` method signature does NOT accept `pipeline_options` or `timeout` per-call. **Verified by reading Docling 2.93.0 source in the project venv** at `backend/venv/Lib/site-packages/docling/`.

The reason CONTEXT.md says "the singleton-level setting did NOT trip during the 4-min UAT stall" — and why a per-call API would not have helped either — is that **Docling only checks `document_timeout` at batch boundaries inside the pipeline loop** (verified at `docling/pipeline/base_pipeline.py:289-297` and `docling/pipeline/standard_pdf_pipeline.py:660-682`). If Docling is wedged inside a single native call (TableFormer / layout-prediction model stall — the exact failure mode reported in Phase 071), the timeout check is never reached. **The fix is Layer 2 in D-071.1-02 (wall-clock `asyncio.wait_for`), not a per-call Docling API change.** D-071.1-02's Layer 1 stays as-is at singleton instantiation; the existing code already sets `opts.document_timeout = 120.0`.

**Primary recommendation:** Implement D-071.1-02 as **a single wall-clock layer at the `/reextract` route** (Layer 2 only — Layer 1 is already in place from Phase 071 Plan 04). Wrap the existing `await run_in_threadpool(extractor.extract, raw, mime_type)` with `asyncio.wait_for(..., timeout=TIMEOUT_S + 10)`. Accept the documented thread-leak trade-off under D-v2.5-02 single-worker (Python cannot kill threads in native code; uvicorn restart heals leaks). On `asyncio.TimeoutError`, dispatch PyMuPDF via the existing `get_extractor(mime, engine_override='pymupdf')` path. Three new env vars (`EXTRACTOR_DOCLING_TIMEOUT_S`, `_DISABLE_TABLE_STRUCTURE`, `_IMAGES_SCALE`) follow the existing `EXTRACTOR_PRIMARY` pattern in `_get_converter()` — read once inside the existing lock, frozen for process lifetime.

## 1. API Resolution — Docling 2.93 per-call `document_timeout`

**The central unknown the planner asked about. RESOLVED.**

### Finding (HIGH confidence — verified against installed source)

**Docling 2.93 does NOT expose a per-call `document_timeout` override on `DocumentConverter.convert()`.** The `convert()` method signature accepts only these parameters:

```python
# Source: backend/venv/Lib/site-packages/docling/document_converter.py:334-342
@validate_call(config=ConfigDict(strict=True))
def convert(
    self,
    source: Union[Path, str, DocumentStream],
    headers: Optional[dict[str, str]] = None,
    raises_on_error: bool = True,
    max_num_pages: int = sys.maxsize,
    max_file_size: int = sys.maxsize,
    page_range: PageRange = DEFAULT_PAGE_RANGE,
) -> ConversionResult:
```

There is **no `pipeline_options=` override and no `timeout=` parameter** at the call site. `document_timeout` is a field on `PdfPipelineOptions` (inherits from `BasePipelineOptions`) and is read by the pipeline class **from its own `self.pipeline_options.document_timeout`**, which is bound once at converter instantiation.

### Where `document_timeout` actually fires (and why it didn't trip in UAT)

```python
# Source: backend/venv/Lib/site-packages/docling/pipeline/base_pipeline.py:287-297
end_batch_time = time.monotonic()
total_elapsed_time += end_batch_time - start_batch_time
if (
    self.pipeline_options.document_timeout is not None
    and total_elapsed_time > self.pipeline_options.document_timeout
):
    _log.warning(
        f"Document processing time ({total_elapsed_time:.3f} seconds) exceeded the specified timeout of {self.pipeline_options.document_timeout:.3f} seconds"
    )
    conv_res.status = ConversionStatus.PARTIAL_SUCCESS
    break
```

```python
# Source: backend/venv/Lib/site-packages/docling/pipeline/standard_pdf_pipeline.py:665-682
# Check timeout
if (
    self.pipeline_options.document_timeout is not None
    and not timeout_exceeded
):
    elapsed_time = time.monotonic() - start_time
    if elapsed_time > self.pipeline_options.document_timeout:
        _log.warning(
            f"Document processing time ({elapsed_time:.3f}s) "
            f"exceeded timeout of {self.pipeline_options.document_timeout:.3f}s"
        )
        timeout_exceeded = True
        ctx.timed_out_run_ids.add(run_id)
        if not input_queue_closed:
            ctx.first_stage.input_queue.close()
            input_queue_closed = True
        # Break immediately - don't wait for in-flight work
        break
```

**Two critical implications:**

1. The check fires **only at batch boundaries** (end of each page batch in `base_pipeline`; top of each `while` iteration in `standard_pdf_pipeline`). If the pipeline is wedged **inside** a single batch — e.g., TableFormer or layout-prediction model is in a stuck native call — the timeout check is never reached. **This is exactly what happened during Phase 071's 4-minute UAT stall.**
2. On timeout, the pipeline does **NOT raise**. It sets `conv_res.status = ConversionStatus.PARTIAL_SUCCESS` and `break`s. Caller receives a `ConversionResult` with partial data and must inspect `result.status` to detect the timeout. (Compare to `ConversionStatus.SUCCESS` on a normal completion.)

## 2. asyncio.wait_for + run_in_threadpool — thread-leak pattern + trade-off

### The Python limitation (HIGH confidence — official docs)

Python **cannot interrupt a thread executing native (non-Python) code**. The `asyncio.wait_for` documentation states that on timeout it cancels the wrapped Task and raises `asyncio.TimeoutError`. But `run_in_threadpool` (which uses `anyio.to_thread.run_sync` → `concurrent.futures.ThreadPoolExecutor`) wraps a synchronous function in a thread; the awaitable returned to the event loop is cancellable, but the underlying thread is NOT.

> "Threads cannot be forcibly killed or cancelled once they're running. While you can cancel the coroutine that awaits the thread result, the actual thread function will continue executing. The cancellation only affects the waiting mechanism, not the thread itself." `[CITED: Python 3 asyncio docs — asyncio.to_thread / asyncio.wait_for]`

For Docling specifically: when the wedge is inside TableFormer / layout-prediction (PyTorch C++ inference), the thread is in native code, holding zero Python opcodes per second. Even `KeyboardInterrupt` (`Ctrl-C`) only fires at Python opcode boundaries — for the same reason, the thread keeps running until the native call returns naturally (which may never happen on a real wedge).

### Confirmed source for `run_in_threadpool`

```python
# Source: backend/venv/Lib/site-packages/starlette/concurrency.py
async def run_in_threadpool(func, *args, **kwargs):
    if kwargs:
        func = functools.partial(func, **kwargs)
    return await anyio.to_thread.run_sync(func, *args)
```

`anyio.to_thread.run_sync` uses the default `concurrent.futures.ThreadPoolExecutor`. The default pool size on Python 3.13+ is `min(32, os.cpu_count() + 4)` — so on a typical 8-core dev machine the pool is ~12 threads. Under D-v2.5-02 single-worker, leaking one thread per stuck Docling call leaves 11 usable threads for everything else (other supabase-py calls, normal Docling extracts, embedding calls, etc.). Process restart resets the pool.

### Trade-off (confirmed correct as written in CONTEXT.md D-071.1-02)

| Aspect | Reality |
|--------|---------|
| `asyncio.wait_for(coro, timeout=N)` raises `asyncio.TimeoutError` after N seconds | ✓ Yes, on the awaiter side |
| The underlying thread is killed | ✗ No — runs to natural completion of the native call (which may be never on a real wedge) |
| `/reextract` returns to the user cleanly | ✓ Yes — the route catches the TimeoutError and continues |
| Memory leak of leaked thread | ~250-500 MB per stuck Docling thread (Docling models + Python frames + Pytorch tensors) — significant on a real wedge |
| Eventual self-recovery | None — the wedge persists until process restart |
| Mitigation under D-v2.5-02 | Single worker means one process to restart; `systemctl restart` / `gunicorn` reload / dev `uvicorn --reload` all clean it |

### Mitigation patterns to be aware of (planner background)

| Pattern | Applicability to 071.1 | Why |
|---------|----------------------|-----|
| `concurrent.futures.ProcessPoolExecutor` (kill-able children) | NOT 071.1 | Would require restructuring all `run_in_threadpool` calls to use a separate pool; massive scope creep. Defer to Phase 077 multi-worker hardening. |
| Bounded thread pool size | NOT 071.1 | starlette/anyio default already bounded; further capping risks starving normal traffic. |
| Watchdog that detects wedged threads and force-restarts the worker | NOT 071.1 (per CONTEXT.md Deferred Ideas) | Premature for single-worker; healed by `--reload` / health-check restart. |
| Layer 1 timeout (Docling's own) tripping FIRST on batch-boundary stalls | ✓ Already in place | Catches batch-boundary timeouts cleanly without leaking the thread. Layer 2 only fires when Layer 1 can't (native-code wedge). |

**CONTEXT.md's trade-off statement is correct as written.** No revision needed.

### Subprocess invocation pattern (already in place — read-only context)

```python
# Source: backend/app/services/extractors/pymupdf.py:54-87 — already shipped, do NOT modify
def _run_pymupdf_subprocess(raw: bytes, mime: str) -> ExtractedDocument:
    timeout_s = int(os.getenv("PYMUPDF_TIMEOUT_S", "60"))
    child_env = {"PATH": os.environ.get("PATH", "")}
    try:
        result = subprocess.run(
            [sys.executable, "-m", "extractors.pymupdf_isolated", "--mime", mime],
            input=raw,
            capture_output=True,
            timeout=timeout_s,
            check=False,
            cwd=str(_BACKEND_DIR),
            env=child_env,
        )
    except subprocess.TimeoutExpired as e:
        raise ExtractionError(f"pymupdf timed out after {timeout_s}s") from e
    # ... rest unchanged
```

**Key facts the planner needs:**

1. `PyMuPDFExtractor.extract(raw, mime)` is synchronous and blocking on subprocess I/O. It spawns a separate process so it's safe to call from threadpool (no fitz import in the parent process — AGPL fence intact).
2. **YES, the fallback call MUST be wrapped in `run_in_threadpool`** because (a) it's blocking, and (b) `subprocess.run` releases the GIL but `_payload_to_extracted_document(json.loads(...))` after it does not. The dataclass construction is CPU-bound Python on potentially-large b64-encoded image payloads. The `/reextract` async handler stays D-v2.5-01 compliant.
3. **NO wall-clock `asyncio.wait_for` wrapper on the PyMuPDF call** (per CONTEXT.md Discretion). Reason: `PYMUPDF_TIMEOUT_S=60` is already enforced at the subprocess level via SIGKILL. The wall-clock wrapper would be redundant — and the wrapper-on-top would not solve any new failure mode because the subprocess kill is a hard process-level kill, not a thread-level "ask nicely" interrupt.
4. **`PyMuPDFExtractor.supports(mime)` is PDF-only** (D-071-03 Discretion). The thesis pair is PDF + DOCX. If `/reextract` falls back on the PDF and the body specified `engine='docling'` for the DOCX sibling, the DOCX gets its own `/reextract` call (not bundled). 071.1 fallback handles PDF-only naturally.

```python
    extractor = get_extractor(mime_type, engine_override=body.engine)
    if extractor is None:
        raise HTTPException(status_code=422, detail=f"No extractor for {mime_type!r}")

    try:
        extracted_doc = await asyncio.wait_for(
            run_in_threadpool(extractor.extract, raw, mime_type),
            timeout=wall_clock_s,
        )
        text = extracted_doc.text

    except asyncio.TimeoutError:
        # D-071.1-04 — fallback to PyMuPDF on Docling timeout ONLY.
        # Only triggered when (a) body.engine was 'docling' (or default), and
        # (b) Layer 2 wall-clock fired (Layer 1 should have fired sooner but
        # was wedged in native code per D-071.1-02 trade-off).
        # The Docling thread leaks; uvicorn restart heals it (D-v2.5-02).
        if body.engine != "docling":
            # Timeout from explicit non-Docling engine — fail loud, don't auto-fallback.
            raise HTTPException(
                status_code=422,
                detail=f"engine={body.engine} timed out after {wall_clock_s}s",
            )

        docling_duration_ms = int((time.perf_counter() - extract_start) * 1000)
        docling_error = f"docling timeout after {wall_clock_s}s (Layer 2 wall-clock)"

        # First telemetry row: Docling failed with timeout (D-071.1-04 two-row pattern).
        await run_in_threadpool(
            _write_extraction_run_row,
            supabase, document_id, current_user["id"],
            "docling", docling_duration_ms, 0, 0, docling_error,
        )

        # Attempt PyMuPDF — synchronous, subprocess-fenced, PYMUPDF_TIMEOUT_S enforced internally.
        # NOTE: Only valid for PDF (PyMuPDFExtractor.supports() returns True for PDF only).
        # The thesis DOCX path doesn't reach this fallback; Docling timeout on DOCX is
        # a separate failure mode (defer to a future phase if observed).
        pymupdf_extractor = get_extractor(mime_type, engine_override="pymupdf")
        if pymupdf_extractor is None:
            raise HTTPException(
                status_code=422,
                detail=f"Docling timed out and PyMuPDF unavailable for {mime_type!r}",
            )

        engine_used = "pymupdf-fallback"
        try:
            extracted_doc = await run_in_threadpool(
                pymupdf_extractor.extract, raw, mime_type,
            )
            text = extracted_doc.text
        except (ExtractionError, Exception) as fallback_exc:
            # Both engines failed — 422 with combined error message.
            await run_in_threadpool(
                _write_extraction_run_row,
                supabase, document_id, current_user["id"],
                "pymupdf-fallback", 0, 0, 0, str(fallback_exc)[:500],
            )
            raise HTTPException(
                status_code=422,
                detail=f"Docling timed out; PyMuPDF fallback also failed: {fallback_exc}",
            )

except HTTPException:
    raise
except Exception as e:
    raise HTTPException(
        status_code=422,
        detail=f"Could not extract text via engine={body.engine}: {e}",
    )

extract_duration_ms = int((time.perf_counter() - extract_start) * 1000)
```

## 4. `pdf_extraction_runs` two-row write pattern recommendation

### Current state (read before planning)

| Write site | Location | Triggers when |
|------------|----------|---------------|
| Happy-path single row | `backend/app/api/documents.py:893-902` (inside `ingest_document`) | Every successful ingest, regardless of trigger (`/upload`, `/reingest`, `/reextract`). Writes `engine`, `started_at`, `duration_ms`, `table_count`, `image_count`, `error=None`. |
| Failure single row | `backend/app/api/documents.py:925-934` (inside `ingest_document` `except`) | Ingest failed for any reason. Writes `error=str(exc)[:1000]`. |

### Recommendation: lightweight inline helper, no refactor of `ingest_document`

The simplest correct shape — and the one CONTEXT.md `code_context` already hints at — is to **inline a small private helper at module-scope in `documents.py`** for the fallback case's two-row write. `ingest_document`'s existing writer stays. Plan 01 adds:

```python
# Source: Phase 071.1 Plan 01 — add to backend/app/api/documents.py module scope
def _write_extraction_run_row(
    supabase: Client,
    document_id: str,
    user_id: str,
    engine: str,
    duration_ms: int,
    table_count: int,
    image_count: int,
    error: str | None,
) -> None:
    """Inline writer for pdf_extraction_runs from /reextract fallback path (Phase 071.1 D-071.1-04).

    The happy-path writer lives in ingest_document at line ~893; this helper is used ONLY
    by the /reextract route's exception handler when fallback fires (the route owns
    orchestration; ingest_document only sees the engine that actually succeeded).

    Telemetry-write failures are swallowed (consistent with T-071-02-07 pattern at line 903) —
    a telemetry hiccup must NOT block the user's extraction outcome.
    """
    try:
        supabase.table("pdf_extraction_runs").insert({
            "document_id": document_id,
            "user_id": user_id,
            "engine": engine,
            "started_at": datetime.now(timezone.utc).isoformat(),
            "duration_ms": duration_ms,
            "table_count": table_count,
            "image_count": image_count,
            "error": error[:1000] if error else None,
        }).execute()
    except Exception as exc:
        log.warning(
            "pdf_extraction_runs INSERT failed (engine=%s, doc=%s, from /reextract fallback): %s",
            engine, document_id, exc,
        )
```

**Why inline + helper (not pure inline, not factored into `extraction_service.py`):**

1. **Pure inline in the route** would duplicate the try/except telemetry-swallow pattern twice in the fallback branch — readability cost. Helper deduplicates.
2. **Factoring to `extraction_service.py`** would create a circular-ish dep (route → service → supabase client, but the service module doesn't import supabase today). Out of 071.1 scope.
3. **Refactoring `ingest_document` to take engine + counts as kwargs and call its existing writer twice** would touch the BackgroundTasks signature, ripple to `/upload` and `/reingest`, and break the existing 4 binding tests at `TestReextractDocument`. Massive scope.

The fallback path writes **two** rows:
1. Inline call to `_write_extraction_run_row(..., engine='docling', error='docling timeout after Ns')` — written from the route's exception handler BEFORE attempting PyMuPDF.
2. `ingest_document` writes the second row at its existing line 893 — with `engine='pymupdf-fallback'` (because we passed `engine_used` into `background_tasks.add_task`, see §3).

If PyMuPDF also fails, the route writes the second row explicitly with `error=str(exc)[:500]` (since `ingest_document` never gets called) — three lines of code in the `except (ExtractionError, Exception)` branch.

### Race / atomicity considerations

`pdf_extraction_runs` has no foreign-key cycle with `documents` beyond `document_id` (FK to documents.id) and `user_id` (FK to auth.users.id). Both INSERTs hit independent rows. Postgres handles them as two independent transactions; even on a server crash between them the first row (Docling-failed) is durable — the operator's audit query (`SELECT count(*) WHERE engine='pymupdf-fallback'`) still works correctly.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-call timeout enforcement on a synchronous, native-code-blocking call | Custom signal-based watchdog (e.g., `signal.SIGALRM`) | `asyncio.wait_for(run_in_threadpool(...), timeout=N)` | `SIGALRM` is Unix-only and conflicts with Windows dev (the project runs on Windows per env block). `asyncio.wait_for` is cross-platform and idiomatic; the thread leak is acceptable trade-off under D-v2.5-02. |
| Killing a stuck Python thread | `ctypes.pythonapi.PyThreadState_SetAsyncExc` (legacy hack) | Accept the leak; rely on uvicorn restart | The async-exc hack only works at Python opcode boundaries, not in native code. Docling stalls are PyTorch C++ inference — async-exc will NOT interrupt them. Documented in Python docs. |
| Wrapping every supabase-py builder chain manually | A pile of inline lambdas with subtle differences | One pattern (lambda), one PR, all 6 sites at once | Mixing wrapped + unwrapped sites would re-introduce the same D-v2.5-01 violation later. Bulk-wrap is the cheaper long-term play. |
| Detecting Docling `ConversionStatus.PARTIAL_SUCCESS` (Layer 1 fired cleanly) | Inline `result.status` check at every call site | Add a single check inside `DoclingExtractor.extract()` that emits a warning | Centralized check beats duplication; planner decides whether to include in Plan 01 scope. |
| Spawning a separate worker process to run Docling | Custom `multiprocessing.Pool` integration | Stay with threadpool + accept leak | Multi-process Docling = duplicate 600 MB model in memory per worker. Phase 077 owns this discussion. Out of 071.1. |

## Common Pitfalls

### Pitfall 1: Wrapping `.execute()` returns but not the builder chain
**What goes wrong:** `await run_in_threadpool(supabase.table("documents").select("*").eq(...).execute)` — passing the bound method `.execute` instead of evaluating the chain — means the chain itself (`.table().select().eq()`) runs synchronously in the event loop FIRST, then only the final `.execute()` runs in the threadpool. supabase-py's builder methods are pure-Python and fast (no I/O), so this is functionally correct but stylistically inconsistent.
**How to avoid:** Use the lambda form so the **entire** chain evaluates inside the threadpool. This also makes the intent visible at the call site.
**Warning signs:** Reviewer sees `run_in_threadpool(supabase.table...execute)` (no lambda) and asks "but the builder chain itself isn't wrapped".

### Pitfall 2: `asyncio.wait_for` cancellation propagation
**What goes wrong:** When `asyncio.wait_for` times out, it calls `task.cancel()` on the wrapped coroutine. For a `run_in_threadpool`-wrapped synchronous function, this means the **outer Task** gets a `CancelledError`, but the thread keeps running. If the outer code catches `CancelledError` (or `asyncio.TimeoutError`, which is what `wait_for` re-raises), it returns to the caller — but the thread is still alive holding ~250-500 MB of Docling state.
**How to avoid:** Document the leak (already in CONTEXT.md D-071.1-02), accept the trade-off, rely on uvicorn restart. Do NOT try to "wait for the thread to actually finish" after timeout — that defeats the entire point of the timeout.
**Warning signs:** Memory grows over time on a server that's seen multiple Docling timeouts. Operator runbook: `systemctl restart uvicorn` (or equivalent) once observed.

### Pitfall 3: Mixing `body.engine` and `engine_used` in fallback path
**What goes wrong:** The fallback fires; `engine_used` becomes `'pymupdf-fallback'`; but the `background_tasks.add_task(ingest_document, ..., body.engine, ...)` call still passes `body.engine = 'docling'`. `ingest_document` then writes a third `pdf_extraction_runs` row with `engine='docling'`, overwriting the actual signal. Telemetry query `SELECT count(*) WHERE engine='pymupdf-fallback'` under-reports.
**How to avoid:** Use `engine_used` (not `body.engine`) at the `background_tasks.add_task(...)` call (line 632). Three-row pattern is over-engineered per CONTEXT.md Deferred Ideas.
**Warning signs:** During UAT, query `pdf_extraction_runs` for the test doc and count rows. Should be exactly 2 on fallback, exactly 1 on happy path.

### Pitfall 4: `EXTRACTOR_DOCLING_TIMEOUT_S` parse failure
**What goes wrong:** Operator typos `EXTRACTOR_DOCLING_TIMEOUT_S=120s` (with `s` suffix). `float("120s")` raises `ValueError` inside `_get_converter()` under `_CONVERTER_LOCK`. Worker crashes on first ingest; subsequent ingests inherit the broken singleton.
**How to avoid:** Wrap each numeric env-read in `try/except ValueError` with `log.warning + fallback to default`. Or use a `_read_float_env` helper (recommended).
**Warning signs:** UAT for the env-knob test surfaces this if someone deliberately sets a garbage value.

### Pitfall 5: Docling 2.93's pipeline timeout vs wall-clock layering confusion
**What goes wrong:** Operator sets `EXTRACTOR_DOCLING_TIMEOUT_S=300` thinking it means "kill after 5 minutes." Layer 1 (Docling's own check) fires at batch boundaries within 5 min IF Docling is making progress. Layer 2 (wall-clock) fires at 5min+10s = 310s. But if Docling is wedged in native code, BOTH fire too late — the thread leaked at minute 1 of the wedge.
**How to avoid:** Document the operator-knob semantics clearly: `EXTRACTOR_DOCLING_TIMEOUT_S` is "how long are you willing to wait before falling back to PyMuPDF" — not "how long until memory is reclaimed." Memory reclamation requires process restart.
**Warning signs:** Operator complains "I set timeout to 5min and the worker is still using 2 GB after 10 min."

## State of the Art

| Old approach | Current approach | When changed | Impact |
|--------------|------------------|--------------|--------|
| Docling singleton-level `opts.document_timeout=120.0` only | Defense-in-depth: singleton-level (Layer 1) + `asyncio.wait_for` wall-clock at route (Layer 2) | 2026-05-15 (Phase 071.1) | Wall-clock catches wedge-in-native-code stalls that Docling's own check can't reach. |
| Sync supabase-py calls in async `/reextract` handler | All sync calls wrapped in `await run_in_threadpool(lambda: ...)` | 2026-05-15 (Phase 071.1; partial from 9116c2b 2026-05-14) | D-v2.5-01 compliance; backend stays responsive during long extracts. |
| `engine='docling'` on Docling failure → fail loud per D-071-11 | Narrow override for **timeout-only**: auto-fall to PyMuPDF | 2026-05-15 (Phase 071.1 D-071.1-04) | Timeout = infrastructure signal (no output produced), not quality regression. User intent preserved for non-timeout failures. |

**Deprecated/outdated (per training data):**
- "Use `signal.alarm` to interrupt long-running Python functions" — Unix-only; Windows incompatible; doesn't interrupt native code. Replaced by `asyncio.wait_for + threadpool` (cross-platform; accepts thread leak).
- "Use `ctypes.pythonapi.PyThreadState_SetAsyncExc` to kill threads" — Python folklore; only works at opcode boundaries; documented unsafe. Not applicable to Docling/PyTorch native stalls.

## Open Questions

None of these are blocking; all are micro-decisions that the planner can resolve cleanly.

1. **Whether to add `result.status == ConversionStatus.PARTIAL_SUCCESS` detection inside `DoclingExtractor.extract()`**
   - What we know: Docling's Layer 1 timeout returns partial-success silently; current code treats it as success. Telemetry under-reports timeouts.
   - What's unclear: Whether this adds value for the SC#1 retry specifically (likely the wedge happens before Layer 1 fires, so this branch wouldn't have caught it anyway), vs being telemetry hygiene for the future.
   - Recommendation: Plan 01 includes it as a 4-line addition with a `log.warning` (telemetry signal only). Cheap; doesn't affect SC#1 retry outcome either way.

2. **Whether to add a `backend/scripts/probe_docling_timeout.py` helper to reproduce stalls against a given PDF**
   - What we know: CONTEXT.md Discretion explicitly recommends YES; small file, big debugging value.
   - What's unclear: Whether the planner allocates Plan 01 time to author it OR defers it to a polish task.
   - Recommendation: Include in Plan 01 — ~30 lines, mirrors `probe_multimodal.py:probe_docling()`. Lets the operator paste a PDF path + measure stall duration end-to-end without needing the full FastAPI stack.

3. **Whether the wall-clock layer should ALSO wrap explicit `engine='pymupdf'` /reextract calls**
   - What we know: CONTEXT.md Discretion says NO — PyMuPDF's `PYMUPDF_TIMEOUT_S=60` is already a hard process-level kill.
   - What's unclear: Whether the planner wants symmetric semantics ("all engines get wall-clock") for code readability vs CONTEXT.md's recommended asymmetry.
   - Recommendation: Match CONTEXT.md — NO wrapper on explicit pymupdf. The asymmetry is justified (different kill mechanism for each engine); inline comment explains it.
