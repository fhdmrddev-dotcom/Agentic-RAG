<objective>
Rewire all settings consumers from file-based I/O to DB-backed async path.

Purpose: This is the core swap. After this plan ships, no production code reads `settings_override.json`. The `load_app_settings()` function reads from the 30s TTL DB cache (Plan 01's `_load_settings_from_db`). The Settings API writes to DB via `save_app_settings()`. The `_build_providers()` function merges DB-stored `provider_model_lists` with DB-registered models from `model_capabilities_overrides`. File-I/O code is deleted.

Output: user_settings.py fully DB-backed, settings.py API async, config.py 4-tier resolution active.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Settings API PUT -> save_app_settings | User-submitted settings validated by Pydantic then written to DB |
| DB cache -> load_app_settings | Cached DB row served to all consumers; stale data possible for 30s |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-081.1-07 | Tampering | save_app_settings sentinel bypass | mitigate | `_is_valid_api_key()` guard ported from Phase 075.4 (D-14); rejects `***`, `__KEEP__`, `••••••`, wrong-prefix, too-short keys before DB write |
| T-081.1-08 | Information Disclosure | Stale API keys in cache | accept | 30s TTL cache (D-06); single-tenant app; forward-compatible with per-user isolation in v3.2. Invalidate-on-write (D-07) ensures the writing worker sees changes immediately. |
| T-081.1-09 | Spoofing | Dynamic column names in UPDATE query | mitigate | Column names derived from `SettingsUpdate` Pydantic model fields (code-controlled set), never from raw user input; asyncpg `$N` parameterized values |
</threat_model>
