# Phase 081.1: Code Review Report

**Reviewed:** 2026-05-27
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Phase 081.1 replaces the file-based `settings_override.json` pattern with a DB-backed settings architecture: a 30 s TTL in-process cache, async `_load_settings_from_db`, `save_app_settings` via asyncpg, and a one-shot lifespan migration runner. The overall design is sound and the code is well-structured. One critical SQL injection vector was found in the migration runner where API key column names from a user-controlled JSON file are interpolated directly into a dynamically built SQL `SET` clause. Three additional warnings were found covering a missing RLS write policy, a sync/async cache dependency gap, and a test reliability issue. Three info items cover dead code and minor UX concerns.

## Critical Issues

### CR-01: SQL injection via user-controlled column names in `_migrate_settings_override`

**File:** `backend/app/main.py:146-150`

**Issue:** The migration runner categorizes JSON keys ending in `_api_key` as `api_key_updates` (line 123), then iterates `all_updates` to build the `SET` clause by interpolating column names directly into the SQL string (line 147: `f"{col} = ${i}"`). The comment on line 143 says "Column names are from code constants" — this is true for `direct_updates` (which are gated against `_DIRECT_COLUMNS`) and for `provider_model_lists` (a single fixed column name), but it is NOT true for `api_key_updates`: those column names come verbatim from the keys of the user-controlled `settings_override.json` file, gated only by `key.endswith("_api_key")`. A crafted JSON key such as `"x = $99; DROP TABLE app_settings; --_api_key"` would inject arbitrary SQL into the dynamically constructed query.

The attack surface is local (requires write access to `backend/settings_override.json`), but this is still a real injection risk: any process or user with file-system write access to the backend directory could exploit this on the next server restart.

**Fix:** Apply the same allowlist gate to `api_key_updates` that `direct_updates` has for `_DIRECT_COLUMNS`. Define a `_API_KEY_COLUMNS` allowset in `main.py` and reject any JSON key not in it before adding it to `api_key_updates`:

```python
# Add this constant alongside _DIRECT_COLUMNS and _PROVIDER_MODEL_KEYS
_API_KEY_COLUMNS: set[str] = {
    "openai_api_key", "anthropic_api_key", "google_api_key",
    "openrouter_api_key", "deepseek_api_key", "moonshot_api_key",
    "minimax_api_key", "zhipu_api_key", "ollama_api_key",
    "tavily_api_key", "embedding_api_key", "rerank_api_key",
}

# In _migrate_settings_override, change:
elif key.endswith("_api_key"):
    api_key_updates[key] = value

# To:
elif key.endswith("_api_key"):
    if key in _API_KEY_COLUMNS:
        api_key_updates[key] = value
    else:
        skipped_keys.append(key)
```

Additionally, add a final defense-in-depth validation before building the SQL, ensuring every key in `all_updates` is in the union of the three allowsets:

```python
_ALL_ALLOWED_COLS = _DIRECT_COLUMNS | _API_KEY_COLUMNS | {"provider_model_lists"}
for col in all_updates:
    assert col in _ALL_ALLOWED_COLS, f"Unexpected column in migration update: {col!r}"
```

## Warnings

### WR-01: `model_capabilities_overrides` table has no write RLS policy — runtime registration impossible via API

**File:** `supabase/migrations/053_settings_unification.sql:47-51`

**Issue:** The migration enables RLS and creates a single `SELECT` policy (`model_overrides_read_all`) for all authenticated users. No `INSERT`, `UPDATE`, or `DELETE` policies are defined. The phase design doc describes this table as enabling "runtime model registration (D-09)" implying operator-users would add rows through the UI or API. Without a write policy, all INSERT/UPDATE/DELETE from an authenticated API session will be rejected by Postgres RLS (`ERROR: 42501 new row violates row-level security policy`). Only the service-role key can write to this table. If admin-only write via service role is intentional, it should be documented explicitly in the migration comment; if self-service registration is intended, a write policy is needed.

**Fix (option A — admin-only, document the intent):**
```sql
-- After the SELECT policy, add this comment:
-- Write access is restricted to service-role (admin-only).
-- Operator must use Supabase SQL editor or a dedicated admin API
-- with service_role key to insert/update model override rows.
```

**Fix (option B — allow authenticated users to manage their own rows, if that's the intent):**
```sql
-- Add a write policy scoped to admins or all authenticated users
CREATE POLICY "model_overrides_write_admin" ON public.model_capabilities_overrides
    FOR ALL TO service_role USING (true) WITH CHECK (true);
```

### WR-02: Sync `_build_providers` reads `_model_overrides_cache` directly without guaranteeing the cache is warm

**File:** `backend/app/models/user_settings.py:373`

**Issue:** `_build_providers` is a sync function that reads `_model_overrides_cache` at line 373 to merge DB-registered models into the provider list. This cache is only populated by the async `_load_model_overrides()`. When `load_app_settings()` (sync) is called before any async request has warmed the model overrides cache — for example, during startup code paths or test fixtures that call the sync variant — `_model_overrides_cache` will be an empty dict and DB-registered models will silently be absent from the provider model lists. The caller receives no indication that the DB-registered models were skipped. This is a silent inconsistency between the sync and async paths.

**Fix:** Add a comment at the `_model_overrides_cache` read site to document the dependency and its warm/cold behavior, and consider adding a `logger.debug` trace when the cache is empty so it surfaces in logs:

```python
# D-13/D-24: merge DB-registered models from model_capabilities_overrides.
# NOTE: _model_overrides_cache is populated by async _load_model_overrides().
# In the sync load_app_settings() path (cold start), this dict will be empty
# and DB-registered models will not appear in provider lists until the first
# async request warms the cache. This is intentional (see D-06 design) but
# callers relying on the sync path should be aware.
existing_set = set(models)
db_registered = sorted(
    mid for mid, cap in _model_overrides_cache.items()
    ...
)
```

If DB-registered models are required to appear in the sync path (e.g., in provider resolution during startup), consider making `_build_providers` refuse to proceed with the sync cache and instead require callers to call `load_app_settings_async()`.

### WR-03: Unit tests for 4-tier resolution (Tests 5-8) verify the wrong negative — missing cache-miss assertion

**File:** `backend/tests/unit/test_settings_cache.py:102-197`

**Issue:** Tests 5, 7, and 8 seed `_model_overrides_cache_time = _time.time()` (TTL warm) to prevent DB calls, and assert that the returned timeout equals a specific value. However, none of these tests assert that `mock_pool.fetch` was NOT called — meaning the warm-cache bypass is never verified. If `_load_model_overrides` regresses and always hits the DB regardless of TTL, the tests would still pass as long as the final value is correct. Test 4 (`test_model_overrides_cache_warm`) correctly asserts `mock_pool.fetch.assert_not_called()` but that assertion pattern is missing from the 4-tier timeout resolution tests.

Furthermore, the `mock_pool` in tests 5-8 is a plain `AsyncMock()` with no `fetch` attribute configured. If `_load_model_overrides` reaches the DB tier and calls `pool.fetch(...)`, it would return an `AsyncMock` coroutine (truthy), not raise an exception, meaning the cache could silently appear populated with unexpected mock data. The test would then pass vacuously.

**Fix:** Add `mock_pool.fetch.assert_not_called()` after the `get_per_call_timeout_async` call in tests 5, 7, and 8 to verify the warm cache was used:

```python
# Example fix for test_timeout_async_full_resolution (Test 5):
async def test_timeout_async_full_resolution():
    ...
    mock_pool = AsyncMock()
    with patch("app.dependencies.get_pg_pool", return_value=mock_pool):
        from app.config import get_per_call_timeout_async
        result = await get_per_call_timeout_async("totally-unknown-model-xyz")

    from app.config import DEFAULT_LLM_CALL_TIMEOUT_SECONDS
    assert result == DEFAULT_LLM_CALL_TIMEOUT_SECONDS
    mock_pool.fetch.assert_not_called()  # Add this
```

## Info

### IN-01: Dead variable `migrated_count` computed but never used

**File:** `backend/app/main.py:163`

**Issue:** `migrated_count` is assigned but the `logger.info` call immediately after it uses the individual component counts (`len(data)`, `len(direct_updates)`, etc.) rather than `migrated_count`. The variable is dead code.

**Fix:** Remove the assignment:

```python
# Remove this line:
migrated_count = len(direct_updates) + len(api_key_updates) + (1 if provider_model_lists else 0)
```

### IN-02: `SettingsPage.tsx` uses `window.confirm` for cross-tab reset — inconsistent with design system

**File:** `frontend/src/pages/SettingsPage.tsx:683`

**Issue:** `handleReset` calls `window.confirm(...)` for any tab other than `"0"`. The browser's native `confirm` dialog is synchronous, blocks the main thread, cannot be styled to match the Deep Midnight design system, and is suppressed in some embedded browser contexts. This creates a jarring UX inconsistency.

**Fix:** Replace `window.confirm` with a stateful confirmation UI (e.g., a small inline prompt or a shadcn/ui `AlertDialog`) that matches the rest of the settings page styling. Since this is a minor UX improvement and this is not a streaming/provider-routing phase, it's out of scope for this phase's UAT gate but worth tracking.

### IN-03: Integration test fixture comment contradicts code behavior for `rerank_provider`

**File:** `backend/tests/integration/test_081_1_settings_migration.py:134,142`

**Issue:** `_FIXTURE_JSON` sets `"rerank_provider": "cohere"`. However, `rerank_provider` is in `_DIRECT_COLUMNS` (it is the DB column name), and the DB column's default value is `"api"` (not `"cohere"` — see `config.py` `Settings.rerank_provider = "api"`). The test comment on line 129 states the fixture uses only "routable keys" that map to "existing DB columns," which is correct, but the test never asserts the `rerank_provider` column was written to `"cohere"` after migration. If a future migration renames the column, this mismatch would go undetected. It is a minor test coverage gap, not a production bug.

**Fix:** Add an assertion for at least one `_DIRECT_COLUMN` value that has a non-default value in the fixture:

```python
# In test_migration_writes_all_keys, add:
assert row["rerank_provider"] == "cohere", (
    "rerank_provider should be 'cohere' from fixture (not the DB default 'api')"
)
```
