# Phase 081.1: Settings Architecture Unification - Research

**Researched:** 2026-05-27
**Domain:** Backend settings persistence, DB schema migration, asyncpg data access, TTL caching
**Confidence:** HIGH

## Summary

Phase 081.1 eliminates `backend/settings_override.json` (a 36-key JSON file on disk) as the primary settings persistence layer, migrating all non-secret values to the `app_settings` DB table (global knobs) and introducing a `model_capabilities_overrides` table (per-model tunables). The current `app_settings` table already has 20 columns from migrations 010-049; this phase extends it with ~12 new columns covering LLM provider/model, retrieval, context, sub-agent, and feature-toggle knobs that currently live only in the JSON file. A one-shot migration runner in FastAPI's lifespan handler reads the JSON, writes to DB via `INSERT ... ON CONFLICT DO NOTHING`, and renames the file to `.migrated`. All consumers of `_load_override()` / `save_override()` / `load_app_settings()` are rewired to an async DB-backed path through the Phase 073 asyncpg pool with a 30s TTL in-process cache.

The code surface is well-bounded: `user_settings.py` (470 lines, the main target), `settings.py` (304 lines, API endpoints), `config.py` (the `get_per_call_timeout` + `MODEL_CAPABILITIES` resolution chain), and 3-4 consumer call sites in `threads.py`, `documents.py`, `extraction_service.py`. The frontend is untouched except for one subtitle string removal at `SettingsPage.tsx:716`.

**Primary recommendation:** Execute as 4 plans per CONTEXT.md: (1) schema delta + cache, (2) migration runner, (3) consumer rewire, (4) integration tests. The schema delta is the foundation -- all subsequent plans depend on it.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** One-shot migration runs in FastAPI's lifespan handler (same place asyncpg pool initializes), before any requests are served.
- **D-02:** Multi-worker safety via `INSERT ... ON CONFLICT DO NOTHING` -- whichever worker gets there first writes, the rest no-op. No locking needed.
- **D-03:** Fail-safe rollback: if any DB write fails, log error and leave `settings_override.json` untouched. Old file-based loader stays active as fallback until next successful migration on restart. App never breaks on a DB hiccup.
- **D-04:** On success: rename file to `settings_override.json.migrated`. Log "Migrated N keys from settings_override.json".
- **D-05:** Idempotent on re-run -- if no JSON file present, migration is a no-op.
- **D-06:** 30s TTL per-worker in-process cache. Each worker has its own cache that refreshes independently from the DB. No Redis pub/sub.
- **D-07:** Invalidate-on-write for the writing worker. When the Settings API writes to the DB, it zeroes out the local cache timestamp so the response reflects the change immediately. Other workers wait for their TTL.

### Pattern 1: 30s TTL In-Process Cache (extends existing pattern)

**What:** Module-level dict + timestamp; on cache miss (age > 30s), async DB read via asyncpg pool populates cache. Invalidate-on-write zeroes timestamp for the writing worker only.

**When to use:** Every `load_app_settings()` call in the hot path (threads.py stream setup, documents.py upload).

**Example:**
```python
# Source: existing pattern at user_settings.py:175-190, extended for async DB
import asyncio
import time as _time
from typing import Any, Optional

_settings_cache: Optional[dict[str, Any]] = None
_settings_cache_time: float = 0.0
_SETTINGS_CACHE_TTL: float = 30.0


async def _load_settings_from_db() -> dict[str, Any]:
    """Read the 'global' row from app_settings via asyncpg pool."""
    global _settings_cache, _settings_cache_time
    now = _time.time()
    if _settings_cache is not None and (now - _settings_cache_time) < _SETTINGS_CACHE_TTL:
        return _settings_cache
    
    pool = await get_pg_pool()
    row = await pool.fetchrow(
        "SELECT * FROM app_settings WHERE id = 'global'"
    )
    _settings_cache = dict(row) if row else {}
    _settings_cache_time = _time.time()
    return _settings_cache


def invalidate_settings_cache() -> None:
    """Zero the cache timestamp so the next read refreshes from DB."""
    global _settings_cache_time
    _settings_cache_time = 0.0
```

### Pattern 2: 4-Tier Model Capability Resolution

**What:** For any model_id, resolve capabilities through: DB `model_capabilities_overrides` row > env CSV `LLM_CALL_TIMEOUT_OVERRIDES` > static `MODEL_CAPABILITIES` dict > safe defaults.

**When to use:** `get_per_call_timeout()`, `get_model_capability()`, `_build_providers()`.

**Example:**
```python
# Source: extends existing config.py:384-413 pattern
async def get_per_call_timeout_async(model_id: str) -> int:
    """4-tier resolution: DB > env CSV > static dict > default."""
    # 1. DB override
    db_cap = await _load_model_override(model_id)
    if db_cap and db_cap.get("llm_call_timeout_seconds") is not None:
        return db_cap["llm_call_timeout_seconds"]
    
    # 2. Env CSV override (existing path)
    overrides = _parse_llm_call_timeout_overrides(settings.llm_call_timeout_overrides)
    if model_id in overrides:
        return overrides[model_id]
    
    # 3. Static registry
    cap = MODEL_CAPABILITIES.get(model_id, {})
    if "llm_call_timeout_seconds" in cap:
        return cap["llm_call_timeout_seconds"]
    
    # 4. Default
    return DEFAULT_LLM_CALL_TIMEOUT_SECONDS
```

### Anti-Patterns to Avoid
- **Reading `settings_override.json` after migration:** After Plan 03 ships, no code path should reference `_OVERRIDE_FILE`. The verifier integration test (Plan 04) must assert zero JSON file reads.
- **Sync DB reads in async handlers:** D-20 mandates asyncpg. Do not use `run_in_threadpool(supabase.table("app_settings").select(...))` -- that pattern is Phase 073's replacement target.
- **Global cache invalidation across workers:** D-06 explicitly chose per-worker eventual consistency. Do not add Redis pub/sub for settings cache.
- **Nullable columns without code-level defaults:** Every new `app_settings` column must have a `DEFAULT` in the DDL. The `UserEffectiveSettings` Pydantic model provides a second defense layer with field defaults.

## Common Pitfalls

### Pitfall 1: Sync-to-async signature mismatch on `load_app_settings()`

**What goes wrong:** `load_app_settings()` is currently sync (returns `UserEffectiveSettings` directly). Converting to async requires updating every call site to `await`. Call sites in sync contexts (like `tool_args_progress_emit_boundary_bytes()` at user_settings.py:422) cannot await.
**Why it happens:** The function is called from both async handlers (threads.py, settings.py) and sync utility functions.
**How to avoid:** Keep a sync fallback that returns cached data without DB I/O. The async path populates the cache; the sync path reads from it. If cache is cold (first call before any async load), sync path returns Pydantic model defaults. The `tool_args_progress_emit_boundary_bytes()` helper already has a defensive `try/except` fallback (line 444) -- this pattern carries forward.
**Warning signs:** `RuntimeWarning: coroutine was never awaited` in logs.

### Pitfall 2: Migration runner timing relative to asyncpg pool init

**What goes wrong:** Migration runner runs before `get_pg_pool()` has been called, so `_pg_pool` is None.
**Why it happens:** Lifespan handler ordering is sequential but implicit.
**How to avoid:** D-01 says "after asyncpg pool initializes." Explicitly call `await get_pg_pool()` (which lazily creates the pool) before the migration runner. Or better: pass the pool reference from the lifespan handler directly.
**Warning signs:** `AttributeError: 'NoneType' object has no attribute 'acquire'` at startup.

### Pitfall 3: Multi-worker migration race with file rename

**What goes wrong:** Worker A reads JSON, worker B reads JSON, worker A writes DB + renames file, worker B tries to rename file that's already renamed.
**Why it happens:** `WORKER_COUNT=2` means two lifespan handlers run concurrently (in separate processes, since uvicorn forks).
**How to avoid:** D-02's `ON CONFLICT DO NOTHING` handles the DB side. For the file rename, use a try/except on `FileNotFoundError` -- if another worker already renamed it, silently succeed. The workers are separate OS processes so there's no in-process lock to share; the file system is the coordination mechanism.
**Warning signs:** `FileNotFoundError` in migration logs.

### Pitfall 4: asyncpg `Record` objects are not dicts

**What goes wrong:** Code assumes `pool.fetchrow()` returns a dict and tries `row["column"]` indexing -- this works, but `dict(row)` is needed for Pydantic model construction.
**Why it happens:** asyncpg `Record` supports dict-like access but is not a dict subclass.
**How to avoid:** Always convert with `dict(row)` before passing to Pydantic, or access fields individually. The Phase 073 JSONB codec (`dependencies.py:53-71`) handles jsonb->dict conversion automatically.
**Warning signs:** `TypeError: argument of type 'Record' is not iterable`.

### Pitfall 5: `app_settings` single-row assumption

**What goes wrong:** Someone adds a second row with a different `id`, or the `'global'` row gets deleted.
**Why it happens:** The table has no constraint preventing multiple rows (beyond PK uniqueness on `id`).
**How to avoid:** Always query `WHERE id = 'global'`. The migration runner uses `INSERT INTO app_settings (id, ...) VALUES ('global', ...) ON CONFLICT (id) DO UPDATE SET ...` -- this is correct. The cache loader always filters to `id = 'global'`.
**Warning signs:** Settings read returns NULL for columns that should have values.

### Pitfall 6: `provider_model_lists` JSONB merge with static registry

**What goes wrong:** DB-stored model lists completely replace static registry models, or vice versa. User-added models disappear, or removed models reappear.
**Why it happens:** The merge logic in `_build_providers()` (currently at user_settings.py:282-289) already handles this for the JSON file. The DB-backed version must replicate the same "user ordering first, then append missing registry models" logic.
**How to avoid:** Port the existing merge logic verbatim. The pattern is: `user_models + [m for m in registry_models if m not in user_set]`. The DB is the user's source of truth; the static registry is the "always available" backstop.
**Warning signs:** Models missing from picker after migration; models reappearing after user removes them.

### Pitfall 7: Forgetting to invalidate cache on Settings API write

**What goes wrong:** User saves settings, API returns updated values, but subsequent requests from the same worker still serve stale cached values.
**Why it happens:** D-07 requires invalidate-on-write for the writing worker only. If the write path doesn't call `invalidate_settings_cache()`, the TTL hasn't expired, and stale data persists.
**How to avoid:** The `update_settings` endpoint must call `invalidate_settings_cache()` after the DB write succeeds, BEFORE building the response. The current `save_override()` already does `_override_cache_time = 0.0` (line 218) -- port this pattern.
**Warning signs:** Saved settings don't appear to take effect until 30 seconds later.

```python
async def save_app_settings(updates: dict[str, Any]) -> None:
    """Write settings to app_settings row via asyncpg pool.
    
    Port of save_override() with D-14 sentinel guard preserved.
    """
    pool = await get_pg_pool()
    
    # D-14: Port _is_valid_api_key sentinel guard
    for k, v in list(updates.items()):
        if v == KEY_PLACEHOLDER:
            del updates[k]
            continue
        if k.endswith("_api_key") and v is not None and not _is_valid_api_key(k, str(v)):
            logger.warning("rejected api_key write -- sentinel/invalid format for key=%s", k)
            del updates[k]
    
    if not updates:
        return
    
    # Build SET clause dynamically
    set_parts = []
    values = []
    for i, (col, val) in enumerate(updates.items(), 1):
        set_parts.append(f"{col} = ${i}")
        values.append(val)
    values.append('global')  # WHERE clause param
    
    query = f"""
        UPDATE app_settings
        SET {', '.join(set_parts)}, updated_at = now()
        WHERE id = ${len(values)}
    """
    await pool.execute(query, *values)
    
    # D-07: Invalidate local cache
    invalidate_settings_cache()
```

## Open Questions

1. **Migration runner: asyncpg or supabase-py?**
   - What we know: D-20 locks the Settings API to asyncpg. The migration runner runs once in lifespan, not in the hot path. Claude's discretion per CONTEXT.md.
   - What's unclear: Whether there's value in using supabase-py for the one-shot migration (simpler INSERT syntax) vs asyncpg (consistency with the rest of the new code).
   - Recommendation: Use asyncpg for consistency. The migration runner runs after `get_pg_pool()` creates the pool, and asyncpg's `INSERT ... ON CONFLICT` syntax is straightforward. No reason to keep a supabase-py dependency in a code path that should be pure asyncpg.

2. **`_build_providers()` merge logic for DB-registered models (D-13)**
   - What we know: Current merge in `_build_providers()` (user_settings.py:282-289) preserves user ordering + appends missing registry models. D-13 says DB-registered models fold into provider sections alphabetically.
   - What's unclear: Whether "alphabetically" means the full combined list is sorted, or only the DB-registered additions are sorted within their insertion position.
   - Recommendation: Maintain user's saved ordering from `provider_model_lists` JSONB first, then append DB-registered models (from `model_capabilities_overrides`) and static registry models alphabetically. This preserves user preference while ensuring new models appear in a predictable position.

3. **Schema for `embedding_base_url` and `ollama_base_url` (D-16)**
   - What we know: D-16 says these go to `app_settings`. `embedding_base_url` already exists as a column in migration 010. `ollama_base_url` is new.
   - What's unclear: Whether `embedding_base_url` currently has data in the DB row (it's nullable, may be NULL if only set via JSON/env).
   - Recommendation: The migration runner handles this: if `embedding_base_url` has a value in JSON, write it to the existing DB column. Add `ollama_base_url` as a new column.
