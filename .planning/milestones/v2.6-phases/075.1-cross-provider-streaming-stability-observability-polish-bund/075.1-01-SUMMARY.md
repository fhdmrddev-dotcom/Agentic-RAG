# Phase 075.1 Plan 01: Widened Transient-Stream-End Filter + reader_done Surfacing Summary

**Defense-in-depth client-side fix: widens the SSE transient-close filter from buffer_expired-only to four trigger paths (buffer_expired error, generic error, premature done with active tools, plain reader_done) — all probe /snapshot.active_runs and re-attach when the backend says the run is still streaming, instead of mis-flipping runStatus to failed/completed.**

## Accomplishments

- Renamed `_isTransientBufferExpired` → `_isTransientStreamEnd` and widened the trigger set from 1 case (buffer_expired error) to 4 cases (buffer_expired error, any-other error, done-with-active-tools, plain reader_done) — all 4 now probe `/snapshot.active_runs` and re-attach when the backend reports the run still streaming.
- Extracted shared `_reattachAfterTransient(threadId, runId, lastSeenOffsetRef, reattach)` helper that owns the snapshot-probe + cursor-seed + re-attach flow; called from both reconcile and sendMessage onTerminal handlers (no duplication).
- Added 5th `onTerminal` kind `"reader_done"` to `StreamCallbacks` and switched `api.ts` defensive reader-close path (line ~482) from `onTerminal("done")` to `onTerminal("reader_done")`. Pre-Plan-01 this was a silent terminal that mis-flipped runStatus to `"completed"` whenever a transient network blip closed the SSE wire mid-stream.
- Both onTerminal handlers extended with: (a) tool_calls lookup from store before invoking the filter (so the kind=='done' branch can detect active tools), (b) re-attach branch that opens a fresh AbortController + reuses already-bound callbacks + adds the runId back to subscriptionsRef/subscriptionsByRunId, (c) fail-safe fall-through to the existing terminal flip if snapshot fetch fails during reattach.
- Branch D-3 streaming-bucket guard (`tid && tid !== streamingThreadIdRef.current` predicate at `StreamsProvider.tsx:455`) preserved verbatim — grep gate still returns exactly 1 match post-Plan-01.

## Decisions Made

- **Export `_isTransientStreamEnd` instead of testing via full provider render.** The existing `streamsProvider.test.tsx` baseline has 7 pre-existing waitFor-timeout failures (mock-related, not Plan 01 regressions). Adding 8 more tests through the same render pathway would inherit those flakes. A direct unit test on the exported helper gives a clean decision-matrix table and follows the established `api.test.ts` pattern.
- **Helper accepts a caller-supplied reattach callback.** Each onTerminal call site has different closure variables in scope (reconcile loop has `run`, `controller`, `callbacks`; sendMessage path has `registeredRunId`, separate `controller`, separate `callbacks`). Injecting the reattach lambda lets each site provide its own AbortController setup + subscribeToRun firing while the helper owns the snapshot-fetch + cursor-seed logic verbatim.
- **`reader_done` maps to `runStatus:"completed"` in the terminal-flip fall-through.** Pre-Plan-01 api.ts emitted `onTerminal("done")` on raw reader-close — that fell into the "completed" branch unconditionally. Plan 01 preserves that wire-level mapping for the case where the snapshot fetch confirms genuine completion (or fails fail-safe). Only when the snapshot says the run is still streaming does the new re-attach path take over.
