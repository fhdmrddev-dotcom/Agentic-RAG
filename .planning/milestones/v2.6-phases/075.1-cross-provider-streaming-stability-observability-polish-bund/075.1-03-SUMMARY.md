- **Task 1's tests pass against the CURRENT reducer without any behavior change required.** The reducer already preserves `m.content` via spread in every callback outside `onDelta`. The plan acknowledged the bug was hypothesized (most-likely-one-of-3 candidates per Step A); the audit found none of the candidates actually present in the post-Plan-01 codebase.   - Confirmed every `setMessages((prev) => prev.map((m) => ...))` return object in `makeStreamCallbacks` either omits `content:` (preserves via spread) or appends in `onDelta` (`content: m.content + delta`).
  - Confirmed `frontend/src/lib/api.ts` has ZERO `tool_args_progress` consumers — the unknown event type falls through silently in the parser's if/else-if chain with no fallback (per D-075-12).
  - Confirmed the placeholder initialization sites at StreamsProvider.tsx:673 (reconcile) and :848 (sendMessage) write `content: ""` to BRAND-NEW placeholder objects, not to existing in-progress assistant messages — those don't regress an in-progress reducer.

The actual production root-cause for B-260519-01 may live elsewhere (the SSE wire, the backend stream emission ordering, or some other surface not under Plan 03's scope). Task 3 Chrome MCP UAT is the end-to-end validation surface that determines whether reducer-invariant lock-in is sufficient or whether a follow-up fix is needed.
