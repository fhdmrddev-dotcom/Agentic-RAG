## Warnings

### WR-01: `onToolEnd` matches only the FIRST running tool with the given name — dedup collides on parallel same-name calls

**File:** `frontend/src/providers/StreamsProvider.tsx:318-328`

**Issue:** The `onToolEnd` callback finds the tool to flip to "done" with:

```ts
const updated = (m.tool_calls ?? []).map((tc) =>
  tc.name === name && tc.status === "running"
    ? { ...tc, status: "done" as const, endedAt: Date.now(), result: result ?? tc.result }
    : tc,
)
```

This matches ALL `tc.name === name && tc.status === "running"` entries — if the
same tool name appears twice in running state (e.g., two concurrent
`search_documents` calls with `parallel_tool_calls: false` disabled but
`onToolStart` fires twice before `onToolEnd` fires once), the first `onToolEnd`
will flip only the first match due to `map` semantics. However the dedup logic in
`ToolCallPanel.tsx` at line 538-548 uses `tc.id || \`${tc.name}-${tc.startedAt ?? ''}\``
as the key — a `running-${Date.now()}` id is generated in `onToolStart` at
line 300 when no preparing entry is found. That makes the IDs stable but the
`onToolEnd` match is by name + status, not ID, so it always flips the first
matching-name running tool. This is a pre-existing gap that Plan 04's dedup
does not fix and that Plan 01's `parallel_tool_calls: false` constraint
mitigates but does not eliminate (Anthropic with consecutive same-name tools
in a single message can still trigger this). The consequence is a
non-deterministic "done" stamp on the wrong tool card when two same-name tools
run in the same iteration.

**Fix:** Match by `tc.id` in `onToolEnd` — pass the tool id through the SSE
event (the backend already emits `tool_call_id` on `tool_end` events) and add
an `id` parameter to the `onToolEnd` callback:

```ts
onToolEnd: (name, result, id?) => {
  setMessages((prev) =>
    prev.map((m) => {
      if (m.id !== assistantId) return m
      const updated = (m.tool_calls ?? []).map((tc) =>
        (id ? tc.id === id : tc.name === name) && tc.status === "running"
          ? { ...tc, status: "done" as const, endedAt: Date.now(), result: result ?? tc.result }
          : tc,
      )
      return { ...m, tool_calls: updated }
    }),
  )
},
```

The `id?` fallback keeps backward compat with existing SSE frames that omit id.

### WR-02: `_isTransientStreamEnd` calls `getSnapshot` twice per transient event — once in the filter, once in `_reattachAfterTransient`

**File:** `frontend/src/providers/StreamsProvider.tsx:122-191`

**Issue:** When `_isTransientStreamEnd` returns `true`, `_reattachAfterTransient`
immediately calls `getSnapshot` again to seed the cursor. The comment on line 161
acknowledges this ("the transient filter already probed, but it could have been
called more than 100ms ago; treat that probe as 'decision' and this fetch as
'fresh cursor seed'"). The problem is that under poor network conditions the
two round-trips compound: the first probe may return `streaming` while the
second fetch (inside `_reattachAfterTransient`) could arrive after the run
terminates, returning `active_runs: []`. In that case `seedCursor` is undefined,
`since` defaults to `"0"`, and the reattach replays the full stream from the
beginning — burning Redis reads and re-firing every SSE callback against
already-committed state. While mostly harmless (SSE callbacks are idempotent in
spirit), duplicate `tool_end` events can double-flip tool status to `"done"` and
append duplicate output lines.

**Fix:** Thread the snapshot from `_isTransientStreamEnd` to
`_reattachAfterTransient` by returning it instead of just `boolean`:

```ts
// Phase 075.1 improvement: return snapshot directly to avoid second fetch
async function _isTransientStreamEnd(...): Promise<ThreadSnapshot | null> {
  // ...short-circuits return null instead of false...
  const snapshot = await getSnapshot(threadId).catch(() => null)
  if (!snapshot) return null
  const match = snapshot.active_runs.find(r => r.run_id === runId && r.status === "streaming")
  return match ? snapshot : null
}
```

This eliminates the second round-trip and removes the race window. The two-probe
pattern is low-risk in practice but worth eliminating in a follow-up.

### WR-03: `ToolCallPanel` dedup key falls back to `${tc.name}-${tc.startedAt ?? ''}` — collides for all `"preparing"` entries

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:538-548`

**Issue:** The dedup key is:

```ts
const key = tc.id || `${tc.name}-${tc.startedAt ?? ''}`
```

Preparing entries created in `onToolPreparing` receive `id: "preparing-{index}"`,
so their key is correct. However, entries created without ids (legacy paths or
Anthropic `tool_preparing` entries before the `tool_start` assigns a real id)
will use `${tc.name}-`. The fallback `${tc.startedAt ?? ''}` for a preparing
entry is always `"preparing-{index}-undefined"` truncated to just
`"${name}-"` because `startedAt` is `undefined` on preparing entries (set to
`undefined` in the `preparingEntry` at line 264). This produces the key
`"execute_code-"` for every preparing `execute_code` entry, so if two
`execute_code` tool-preparings arrive (e.g., two sequential execute_code calls
before either completes), the second one is silently dropped by the dedup.

In practice the `parallel_tool_calls: false` constraint prevents this, but the
key construction is fragile. The fix is to include the `index` in the fallback:

```ts
const key = tc.id || `${tc.name}-${tc.startedAt ?? tc.iteration ?? i}`
```

Or more robustly, use the array index `i` as tiebreaker when all else is
undefined:

```ts
for (let idx = 0; idx < toolCalls.length; idx++) {
  const tc = toolCalls[idx]
  const key = tc.id || `${tc.name}-${tc.startedAt ?? ''}-${idx}`
  ...
}
```

### IN-01: `sub_agent_service.py` `run_sub_agent` re-uses `client` after `NotFoundError` without refreshing credentials

**File:** `backend/app/services/sub_agent_service.py:105-126`

**Issue:** On `openai.NotFoundError`, the code immediately calls
`client.chat.completions.create(model=fallback, ...)` on the same `client`
instance. The client was already constructed at line 43 with the original
provider's API key and base URL. If the NotFoundError comes from OpenRouter
(where the model slug simply doesn't exist on their routing table), falling back
to a different model on the same client is fine. However if the fallback model
requires a different provider endpoint (e.g., fallback is a native Anthropic
model while the original was an OpenRouter model), the same `OpenAI`-compatible
client with an OpenRouter base URL will fail again. The `_SUB_AGENT_MODEL_DEFAULTS`
map uses provider keys so this scenario is unlikely in practice, but the
assumption is undocumented.

**Fix:** Add a comment documenting the assumption that `fallback` is always on
the same provider/base_url as the original `effective_model`. No code change
required unless the assumption is violated.

### IN-02: `harvest_output_files` double-uploads files present in `previous_files`

**File:** `backend/app/services/sandbox_service.py:113-189`

**Issue:** The delta filtering happens at lines 185-188 **after** all files are
already uploaded and `sandbox_files` rows inserted (lines 152-165). Files that
were already present in `previous_files` still get re-uploaded to Supabase
Storage (with `upsert: "true"`) and get a duplicate `sandbox_files` INSERT on
every iteration. This is wasteful (extra Storage writes + duplicate DB rows) but
functionally correct because the URL returned is deterministic (same
`storage_path` per `fname`). The `sandbox_files` table may accumulate duplicate
rows for the same `(execution_id, filename)` pair across iterations.

**Fix:** Skip upload and INSERT for files already in `previous_files`:

```python
if previous_files is not None and fname in previous_files:
    output_files.append({
        "filename": fname,
        "url": f"/sandbox-outputs/{storage_path}",
        "size": file_size,
    })
    continue  # skip re-upload and duplicate INSERT
```

This also makes the `previous_files=None` legacy path correct — it always
uploads everything, matching pre-Plan-04 behavior.

### IN-03: `MessageItem.tsx` `finalOutputFiles` panel renders filenames only — no download affordance

**File:** `frontend/src/components/chat/MessageItem.tsx:255-264`

**Issue:** The pinned "Final outputs" panel at lines 255-264 renders only
`f.filename` as text inside a `<li>`. The `Message.finalOutputFiles` type
includes `url?: string` (set by the backend's harvest), but the panel never
renders it — there is no click handler, anchor tag, or download button. The
`OutputFile` type in `types/index.ts` requires a `url: string`, but
`finalOutputFiles` uses the looser `{ filename: string; url?: string }` shape,
so the `url` can arrive but never be exposed to the user.

This is a UX gap rather than a bug, but the panel was introduced specifically to
"close the 12-download-links-for-1-desired-file cognitive-load symptom" — without
a download affordance, users cannot actually download from the pinned panel.

**Fix:** Render a download link when `url` is present, using the same
`downloadSandboxOutput` helper used in `ExecuteCodeBlock.tsx`:

```tsx
{message.finalOutputFiles.map((f) => (
  <li key={f.filename}>
    {f.url ? (
      <button onClick={() => downloadSandboxOutput(f.url!, f.filename)} className="underline hover:no-underline">
        {f.filename}
      </button>
    ) : f.filename}
  </li>
))}
```

### IN-04: `StreamsProvider.tsx` reconcile path does not set `stoppedByUserRef` to `false` after `onTerminal` fires

**File:** `frontend/src/providers/StreamsProvider.tsx:1005-1062` (sendMessage finally block)

**Issue:** The `stoppedByUserRef.current = false` reset at line 1061 lives only
in the `sendMessage` finally block. The `reconcile` path also calls `onTerminal`
but has no corresponding reset for `stoppedByUserRef`. If a user clicks Stop
during an initial `sendMessage` (setting `stoppedByUserRef.current = true`),
then navigates away and back (triggering `reconcile`), then the reconcile
`onTerminal` fires — but `stoppedByUserRef` is still `true` from the previous
send. The finally block of `sendMessage` at line 1061 will reset it only when
`sendMessage` exits its own try/finally, which it already has. So `reconcile`'s
onTerminal fires with a stale `stoppedByUserRef.current = true`.

However, inspecting the reconcile path, `stoppedByUserRef` is only read in the
`sendMessage` finally block (lines 1027-1046). The reconcile `onTerminal` does
not read it. So the stale value is harmless in practice — it will be consumed and
reset on the next `sendMessage` call. No immediate code change required, but
adding a comment noting this dependency would help future maintainers.
