## D. Content-hash output dedup (Plan 03)

### D.1 — Hash algorithm?

| Option | Description | Selected |
|---|---|---|
| SHA-256 | Project convention (documents.content_hash); stdlib; collision-free | ✓ |
| xxhash (xxh3_64) | 10× faster but adds dependency; speed gain not measurable | |
| blake3 | Even faster but another dependency; no precedent | |

**User's choice:** SHA-256.

### D.2 — Dedup data structure?

| Option | Description | Selected |
|---|---|---|
| dict[content_hash, {filename, url, size, iteration}] | Hash = canonical identity; emits `supersedes:` field on hash-change for same filename | ✓ |
| dict[filename, content_hash] | Filename-keyed; loses different-filename-same-content case | |
| set[(filename, content_hash)] | Most paranoid; spurious 'new file' events on rename | |

**User's choice:** dict[content_hash, {filename, url, size, iteration}].

### D.3 — In-flight runs at deploy time?

| Option | Description | Selected |
|---|---|---|
| Graceful empty dict on first iteration after restart | Per-run closure; cancelled runs reset; worst case = single double-emit on resume | ✓ |
| Persist dedup state to Redis run buffer | Eliminates double-emit; +50 LOC + hot-path write; overkill | |

**User's choice:** Graceful empty dict.
