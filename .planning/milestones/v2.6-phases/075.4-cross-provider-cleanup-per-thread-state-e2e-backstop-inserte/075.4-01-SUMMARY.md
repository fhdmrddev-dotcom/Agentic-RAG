- **Found during:** Task 2 (StreamsProvider write-site refactor)
- **Issue:** `frontend/src/__tests__/providers/streamsProvider.test.tsx` references the OLD store field names in 3 places: (a) beforeEach reset block at L:117-121, (b) L-068-07 test asserting `subscriptionsByRunId.has(runId)`, (c) Phase 068.5 retry-banner + Gap-01 loadingThreadId test blocks. These tests would silently use OLD field names that are no longer recognized by the new StreamsState type — Zustand v5's setState is permissive on excess properties so TypeScript doesn't flag them, but at runtime the asserts read `undefined` from the per-thread state. The plan called out migration for the test files Task 4 creates, but did NOT explicitly call out migrating the existing test file's old-field references. Per scope-boundary rule (Rule 2 — Missing Critical): these are correctness requirements; without the migration, the existing tests would falsely-RED.
- **Fix:** Migrated 4 test blocks in `streamsProvider.test.tsx` to per-thread shape: (a) beforeEach uses the 5 new field names with fresh empty Set/Map values; (b) L-068-07 asserts inner-Set-empty-then-delete-key GC behavior on `subscriptionsByThread.get("thread-A")`; (c) retry-banner tests assert `reconcileErrors.get("T1")` instead of `reconcileError.threadId`; (d) Gap-01 test renamed `loadingThreadId` describe to `loadingThreads per-thread Set` and migrated all asserts.
- **Files modified:** `frontend/src/__tests__/providers/streamsProvider.test.tsx` (modified in Task 2 commit).
- **Verification:** vitest runs the migrated tests GREEN; pre-existing failures (8 tests rooted in Phase 075 D-075-02 swap) are unchanged from HEAD baseline.
- **Committed in:** `18ee433` (Task 2 commit).

**2. [Rule 2 - Missing Critical] Module-level mutation helpers for subscriptionsByThread**

- **Found during:** Task 2 (rewriting the 6 subscriptionsByRunId write sites)
- **Issue:** The plan specified `subscriptionsByThread: copy of Map, inner Set gets new runId added via new Set(prev).add(runId)` as inline code at every write site. With 6 add + 4 remove sites that pattern would duplicate the GC logic (delete-key-when-inner-empty) 4 times — high risk of drift if a future plan only updates one site.
- **Fix:** Hoisted to module-level `_addRunToThread(current, threadId, runId)` and `_removeRunFromThread(current, threadId, runId)` helpers right before the `StreamsProvider` component declaration. Each write site calls `_addRunToThread(s.subscriptionsByThread, threadId, runId)` / `_removeRunFromThread(...)` and folds the result into a single-key setState partial. Inner-Set-empty-then-delete-key GC lives in `_removeRunFromThread` only.
- **Files modified:** `frontend/src/providers/StreamsProvider.tsx` — module-level helpers added; all 6 add/remove sites use the helpers.
- **Verification:** Task 4 Test 2 (`streamsStore_per_thread.test.ts` — "inner-Set-empty-then-delete-key GC removes the threadId entry when last run terminates") asserts the GC contract end-to-end against the runtime behavior the helpers produce.
- **Committed in:** `18ee433` (Task 2 commit).

**3. [Rule 1 - Bug] Task 4 Test 3 rewritten to avoid isSendingRef serialization**

- **Found during:** Task 4 (running the new tests)
- **Issue:** Original Test 3 ("Multi-thread parallel: A + B both streaming") tried to fire `sendMessage("thread-a", ...)` followed by `sendMessage("thread-b", ...)` to set up two parallel streams. But `sendMessage` has an early-return at L:941 (`if (isSendingRef.current) return`) that serializes per-tab — the second sendMessage call was no-oped, `mockSubscribeToRun` was called once not twice, and the test failed.
- **Fix:** Rewrote Test 3 to seed the parallel-stream state via direct store mutation (two threads in `streamingThreads`, two threads with populated `bucketsBySurface` entries) instead of going through `sendMessage`. Asserts the actual D-075.4-A1 invariant: clearThreadBucket DOES delete the active-thread bucket when no stream is alive on that ref, but `streamingThreads` Set is UNTOUCHED (the legacy `isStreaming: false` write was dropped from the setState callback). Test 3 documents the single-ref limitation (streamingThreadIdRef is single-valued; lifting it to a Set is out of scope for 075.4-01) in inline comments.
- **Files modified:** `frontend/src/__tests__/providers/streamsProvider_067_5_regression.test.tsx`.
- **Verification:** Test 3 now passes; covers the per-thread Set invariant directly without depending on undocumented sendMessage-parallel-call semantics.
- **Committed in:** `a7f2faf` (Task 4 commit).
