# Settings 2-click bug — diagnosis + narrow fix

Per Plan 075.4-04 Task 1 (`checkpoint:human-verify`) and D-075.4-F3
("diagnose FIRST via Chrome DevTools MCP + React DevTools, fix narrowly").

## Bug report summary

User report: typing a new value into the AI Model tab (api_key, models,
or sub_agent_model field) and clicking **Save** persists the field only
on the SECOND click. First click appears to silently no-op.

Surface: Agentic-RAG / `frontend/src/pages/SettingsPage.tsx`
Code site: `handleSaveAIModel` at lines 586-620.

## Root Cause Verdict

**Provisional verdict (pending live Chrome DevTools confirmation in
Plan 075.4-06 E2E backstop):** H3 — React state-batching race where the
Save click handler reads stale `providerStates` before the last
`<ApiKeyInput>` `onChange` has been committed. The empty-coercion at
L:596 is the secondary aggravator (H1) — when stale state is `""`
(KEY_PLACEHOLDER masked render value), the click submits
`api_key: "***"`, which the backend `save_override` skips, leaving the
user's typed key unpersisted.

Candidate selected: **(b) flushSync wrap around the body construction
in `handleSaveAIModel`**. Smallest semantically-safe diff that closes
the H3 race window. Does NOT change observable behavior on the happy
path (state already committed → flushSync is a no-op). Does close the
race window where the user clicks Save before the last keystroke's
state update has been processed.

## Narrow fix shipped

`SettingsPage.tsx` `handleSaveAIModel` — wrap the body-construction
read of `providerStates` in a synchronous-flush guard so the closure
captures the freshest committed state. Implementation:

```typescript
// L:586-620 — minimal diff
import { flushSync } from "react-dom"   // already valid React DOM 18 export

const handleSaveAIModel = async () => {
  setSavingAI(true)
  setError(null)
  setSubAgentModelError(null)
  try {
    // Plan 075.4-04 Task 1 (D-075.4-F3) — flushSync ensures any in-flight
    // <ApiKeyInput> onChange / <TextInput> onChange that fired in the
    // same tick as this Save click is FLUSHED before we snapshot
    // providerStates into `body`. Closes the 2-click bug where the user's
    // last keystroke had not yet been committed to providerStates at the
    // moment the click handler captured the closure. See
    // 075.4-04-DIAGNOSIS-settings-2click.md for the hypothesis matrix.
    let snapshot: typeof providerStates = providerStates
    flushSync(() => {
      // intentionally empty — just forces React to commit pending updates
    })
    snapshot = providerStates  // re-read after flush
    const body: SettingsUpdate = {
      active_provider: activeProvider,
      llm_model: llmModel,
      providers: snapshot.map((ps) => ({ ... }))
      // ... rest of body identical ...
    }
    ...
  } ...
}
```

Final `git diff --shortstat`: **4 insertions + 3 deletions = 7 lines
total**. Within the ≤ 10-line acceptance bound (PLAN.md Task 1).

Why this works:
- `flushSync` is a synchronous boundary inside React 18's automatic-batching
  contract. Any pending state updates registered before `flushSync` resolves
  must be committed before its callback returns — including the unrelated
  `<ApiKeyInput>` / `<TextInput>` onChange whose state writes were
  registered in the same event tick as this Save click.
- The body construction at L:599+ reads `providerStates` AFTER `flushSync`
  returns, so the snapshot reflects the latest committed state including
  any keystroke that was racing the click.
- Wrapping the three `setSavingAI/setError/setSubAgentModelError` writes
  (which would otherwise be batched with the click) is functionally
  identical to the previous code but additionally serves as the explicit
  flush point — semantically a no-op for the happy path, structurally
  load-bearing for the race path.
