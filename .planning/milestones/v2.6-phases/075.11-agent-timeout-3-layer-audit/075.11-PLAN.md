# Phase 075.11 — Agent Timeout 3-Layer Audit + Unification

## Goal

After this phase, the 3 layers of agent timeout (per-LLM-call SDK, agent-loop wall-clock, SSE keepalive) are unified under `app_settings` with per-model defaults that match the public Claude.ai / ChatGPT benchmarks. The operator-observed "900s hit on Anthropic during a multi-tool task" no longer fires for typical heavy-research workflows (median ~5-8 min, p95 ~18 min). Settings UI exposes the wall-clock knob so it's tunable without redeploy.

## Why no heavy ceremony

- **Root locations already found.** `backend/app/config.py:339` (`get_per_call_timeout`), `backend/app/api/threads.py:1448` (`max_iterations`), and a yet-to-find SSE-keepalive site in `app/api/runs.py` or `main.py`. No mystery code to discover.
- **Public benchmarks are the design contract.** Claude.ai ~30 min extended / ~5 min normal; ChatGPT ~10 min o3 / ~2 min 4o; Cursor 5-30 min configurable; Aider 10 min. No new ground to break — just match the median of the field.
- **G-3 lightweight commands don't quite fire** — this is more than 10 LOC + 1 file but it's audit + config-knob work, not architecture.

## Failure criteria (G-6 — how we'd know this failed)

1. **The 900s hit reproduces.** After 075.11 ships, the operator runs the same Anthropic multi-tool task that hit 900s today. If it still cuts off at the same wall-clock, the actual 900s site wasn't found (audit failure).
2. **Layers disagree mid-run.** During a long task, the per-LLM-call SDK timeout fires at 180s but the agent-loop guard is set to 1200s and SSE keepalive is at 60s. The user sees a confused state — phase fails if any two layers disagree by >2× on default config.
3. **Heavy task can't complete in default profile.** A canonical "dissertation analysis with 5+ tool calls + 2 KB synthesis output" times out under the default 1200s wall-clock with a known-fast model. Phase fails — the default is too aggressive.
4. **Settings UI knob doesn't take effect without redeploy.** Operator changes `agent_loop_max_seconds` in Settings → the next chat still uses the old value. Phase fails — settings read isn't dynamic.

## Layer audit — current state vs target

| Layer | Current site | Current default | Target default | Target source |
|---|---|---|---|---|
| **L1 — Per-LLM-call SDK timeout** | `backend/app/config.py:get_per_call_timeout(model_id)` | 180s capable / 240s agentic / 600s slow-reasoning (per-model) | unchanged values, but READ from `app_settings.agent_llm_call_timeout_default_s` if model not in `MODEL_CAPABILITIES`, else from `MODEL_CAPABILITIES.llm_call_timeout_seconds` (existing) | `MODEL_CAPABILITIES` registry + `app_settings` fallback |
| **L2 — Agent-loop wall-clock** | `backend/app/api/threads.py:1448` (`max_iterations = 8` explorer / `15` default) — **NO wall-clock guard, only iteration cap** | iteration cap only; worst-case = 15 × 180s = 45 min | NEW: `asyncio.timeout(agent_loop_max_seconds)` wrapping the iteration loop. Default `1200s` (20 min) — matches Claude.ai median × 2.5 | `app_settings.agent_loop_max_seconds INT DEFAULT 1200` |
| **L3 — SSE keepalive** | `sse-starlette` `EventSourceResponse(..., ping=N)` (Task 1 audits to find) | likely 15s or default | `60s` ping interval (browsers tolerate ~120s gap before NS_ERROR_NET_RESET); reads from `app_settings.sse_keepalive_ping_seconds` | `app_settings.sse_keepalive_ping_seconds INT DEFAULT 60` |

After audit (Task 1) confirms layer signs and L3 site, the unification work is a single migration + 3 read-site swaps.

## Tier defaults the operator chooses between

Per public-benchmark research, these are the right tiers — the Settings UI knob (Task 5) lets the operator pick:

| Profile | `agent_loop_max_seconds` | `agent_llm_call_timeout_default_s` | Use case |
|---|---|---|---|
| **Snappy** | 300 (5 min) | 120 | Quick Q&A; chat-style workflows |
| **Default** | **1200 (20 min)** | **180** | Typical multi-tool agent runs; median Claude.ai workflow |
| **Heavy research** | 2700 (45 min) | 240 | RAG over 10+ documents, complex coding, long write-ups |
| **Extended thinking** | 3600 (60 min ceiling) | 600 | o3 / Anthropic extended thinking; max acceptable spend |

Default ships as `Default`. Other tiers are documented in `Settings → Advanced` so the operator can switch without code.

```sql
ALTER TABLE app_settings
  ADD COLUMN IF NOT EXISTS agent_loop_max_seconds INTEGER NOT NULL DEFAULT 1200,
  ADD COLUMN IF NOT EXISTS sse_keepalive_ping_seconds INTEGER NOT NULL DEFAULT 60;

  'Wall-clock ceiling for the entire agent loop (preparing → running → done → next iter → ...) '

  'Default 60s — browsers tolerate ~120s before NS_ERROR_NET_RESET. Phase 075.11.';
```

Apply via Supabase SQL editor per CLAUDE.md migration rule; regen `full-schema.sql` (no `--reset`); commit both.

**Acceptance:** Migration applies cleanly; `select agent_loop_max_seconds, sse_keepalive_ping_seconds from app_settings;` returns `1200, 60`.

### Task 3: Wrap the agent loop with `asyncio.timeout(agent_loop_max_seconds)`

**File:** `backend/app/api/threads.py` near line 1733 (`for iteration in range(max_iterations):`)

Read the setting once at the top of the run handler. Wrap the iteration loop:

```python
_agent_loop_max_s = await _read_setting_int("agent_loop_max_seconds", default=1200)

try:
    async with asyncio.timeout(_agent_loop_max_s):
        for iteration in range(max_iterations):
            ...
except asyncio.TimeoutError:
    # Emit a structured system_warning event so the frontend can render
    # a "took too long, run capped" affordance instead of a silent cut.
    yield {
        "type": "system_warning",
        "kind": "agent_loop_wall_clock_exceeded",
        "ceiling_seconds": _agent_loop_max_s,
        "elapsed_seconds_estimate": int(time.time() - _loop_started_at),
    }
    # ... finalize the run as 'interrupted' status with a clear reason
```

The existing `system_warning` infrastructure from Phase 075.4 (BUG-260523 work) makes this a reload-survivable event.

**Acceptance:** Set `agent_loop_max_seconds = 30` via SQL UPDATE, send a prompt that triggers a 60s sleep tool, confirm the run terminates cleanly at ~30s with the `agent_loop_wall_clock_exceeded` system_warning visible in the chat. Frontend should NOT show "Synthesizing answer…" indefinitely.
