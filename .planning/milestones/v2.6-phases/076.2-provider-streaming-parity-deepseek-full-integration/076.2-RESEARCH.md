**Primary recommendation:** Fix DeepSeek thinking round-trip first (highest value, most code evidence), then Google Skills investigation, then streaming trace documentation for Kimi/MiniMax/GLM as smoke-test UAT.

### Pattern 1: DeepSeek reasoning_content Round-Trip in Agent Loop

**What:** When DeepSeek V4 thinking mode is enabled, `reasoning_content` must be included on assistant messages sent back to the API when tool_calls are present.

**When to use:** Every iteration of the agent loop where tool calls are buffered and the provider is DeepSeek.

**Evidence:** The DeepSeek Thinking Mode documentation states: "Between two user messages, if the model performed a tool call, the intermediate assistant's reasoning_content must participate in the context concatenation and must be passed back to the API in all subsequent user interaction turns." Community reports from multiple AI tools (OpenCode, Claude Code Router, Warp, Hermes Agent, AgentScope) confirm 400 errors without this. [VERIFIED: api-docs.deepseek.com/guides/thinking_mode + github.com/anomalyco/opencode/issues/25000]

**Current bug location:** `threads.py:2486-2512` -- the assistant message dict includes `tool_calls` and `thought_signature` but NOT `reasoning_content` or `content`.

**Fix pattern:**
```python
# threads.py:2486 -- in-memory assistant message between iterations
messages.append({
    "role": "assistant",
    "tool_calls": [
        {
            "id": tc["id"],
            "type": "function",
            "function": {"name": tc["name"], "arguments": tc["arguments"]},
            **(
                {"thought_signature": tc["thought_signature"]}
                if tc.get("thought_signature")
                else {}
            ),
        }
        for tc in tool_calls
    ],
    # Existing: content (narration before tool calls)
    **({"content": full_content} if full_content else {}),
    # NEW: DeepSeek thinking mode requires reasoning_content round-trip
    **({"reasoning_content": full_reasoning_content} if full_reasoning_content else {}),
})
```

**Critical detail:** `full_reasoning_content` must also be reset after appending (like `full_content` is reset at line 2447 in the prose-before-code path) so each iteration's reasoning is scoped correctly. Current code only initializes it at line 1577 and never resets between iterations.

**What:** Stream `reasoning_content` chunks to the frontend for real-time thinking display.

**Current state:** `_on_chunk_openai` at line 2214-2217 accumulates `delta.reasoning_content` into `full_reasoning_content` but does NOT emit an SSE event.

**Frontend handling:** StreamsProvider adds a new `onReasoningDelta` callback that accumulates reasoning text on the message. RunCard's thinking-row shell (already exists at line 254-276) renders the accumulated content in a collapsible block.

### Anti-Patterns to Avoid
- **Don't include reasoning_content for non-tool-call turns:** DeepSeek docs explicitly say "If the model did not perform a tool call, the intermediate assistant's reasoning_content does not need to participate in the context concatenation. If passed to the API in subsequent turns, it will be ignored." [VERIFIED: api-docs.deepseek.com/guides/thinking_mode]
- **Don't strip reasoning_content globally:** The old `deepseek-reasoner` model required stripping reasoning_content from history. V4 thinking mode is DIFFERENT -- it requires passing it back during tool-call turns. [VERIFIED: api-docs.deepseek.com/guides/reasoning_model vs /guides/thinking_mode]
- **Don't modify `_on_chunk_openai` for non-DeepSeek providers:** The `reasoning_content` field is DeepSeek-specific. Other OpenAI-compat providers don't emit it. The `getattr(delta, 'reasoning_content', None)` guard is already correct.
- **Don't touch the `_reconstruct_history` path:** Lines 1154/1161/1168 already correctly include `reasoning_content` on DB-loaded messages. This handles cross-conversation continuity. Only the in-memory iteration path needs fixing.

## Common Pitfalls

### Pitfall 1: reasoning_content Reset Between Iterations
**What goes wrong:** `full_reasoning_content` accumulates across ALL iterations (initialized once at line 1577, never reset). If iteration 1 produces reasoning + tool calls, and iteration 2 also produces reasoning + tool calls, the in-memory message for iteration 2 would carry BOTH iterations' reasoning content concatenated. DeepSeek expects only the current iteration's reasoning.
**Why it happens:** `full_content` has explicit resets (lines 2339, 2447) but `full_reasoning_content` does not.
**How to avoid:** Reset `full_reasoning_content = ""` immediately after appending it to the in-memory assistant message, before the tool execution round begins. Same pattern as `full_content` resets.
**Warning signs:** Second-iteration reasoning looks like doubled content; tokens grow unexpectedly.

### Pitfall 2: DeepSeek V4 vs deepseek-reasoner API Contract Difference
**What goes wrong:** Confusing the V4 thinking mode rules with the old deepseek-reasoner rules. The old model REJECTS reasoning_content in history; V4 REQUIRES it for tool-call turns.
**Why it happens:** Two different docs pages with contradictory rules for the same field name.
**How to avoid:** Gate the reasoning_content inclusion on provider being "deepseek" AND the message having tool_calls. Never add reasoning_content for non-DeepSeek providers.
**Warning signs:** 400 errors from DeepSeek API with "reasoning_content must be passed back" message.
[VERIFIED: api-docs.deepseek.com/guides/thinking_mode vs api-docs.deepseek.com/guides/reasoning_model]

### Pitfall 3: Google Skills Bug May Be Behavioral, Not Code-Level
**What goes wrong:** Assuming the bug is a code defect when it might be Gemini model behavior (Gemini may not choose to invoke `load_skill` even when the tool is registered).
**Why it happens:** Static code analysis shows the tool pipeline is correct -- `get_tools(user_settings)` includes skill tools, `stream_google` passes them through `_convert_tools_to_google`, and the schema sanitization doesn't strip simple string-parameter schemas.
**How to avoid:** First verify the tools ARE sent to the Google API (add debug logging of the converted tool declarations). Then test whether Gemini invokes `load_skill` when explicitly prompted. Only if tools are provably missing from the request is there a code bug.
**Warning signs:** LangSmith trace shows tool declarations present but model never calls them.
[VERIFIED: google_service.py:292-314 + threads.py:1976 -- tools flow correctly in code]

### Pitfall 4: MiniMax Base URL Discrepancy
**What goes wrong:** The project uses `api.minimax.chat/v1` (config.py:18) but MiniMax official docs reference `api.minimax.io/v1` as the OpenAI-compatible endpoint.
**Why it happens:** MiniMax has multiple regional endpoints and the documentation isn't always consistent.
**How to avoid:** Verify which URL actually works during UAT. If `api.minimax.chat` works (Phase 076.1 testing showed it accepting requests), leave it alone. Only change if failures occur.
**Warning signs:** Connection timeouts or 404s from MiniMax.
[CITED: platform.minimax.io/docs/api-reference/text-openai-api]

### Pitfall 5: Kimi Temperature Restriction
**What goes wrong:** Kimi API has stricter temperature requirements than OpenAI: range `[0, 1]` only, and K2.5/K2.6 require `temperature=0.6` in non-thinking mode.
**Why it happens:** The OpenAI SDK default temperature may not match Kimi's required range.
**How to avoid:** Verify the temperature parameter sent via LangSmith traces during UAT. If Kimi returns errors, add provider-specific temperature clamping.
**Warning signs:** 400 `invalid_request_error` from Kimi API.
[VERIFIED: platform.kimi.ai/docs/guide/migrating-from-openai-to-kimi]

### Pitfall 6: Kimi tool_choice="required" Not Supported
**What goes wrong:** Kimi rejects `tool_choice="required"` -- only accepts "none", "auto", and null.
**Why it happens:** The agent loop uses `tool_choice="auto"` (line 1808) and `tool_choice="none"` (force_no_tools), which are both supported. No issue expected.
**How to avoid:** Verify the agent loop never sends `tool_choice="required"` to Kimi.
[VERIFIED: platform.kimi.ai/docs/guide/migrating-from-openai-to-kimi]

## Open Questions

1. **Google Skills: behavioral vs code-level?**
   - What we know: The tool pipeline is correct in static analysis. Tools including skills are passed to `_convert_tools_to_google`. Schemas are simple and should survive sanitization.
   - What's unclear: Whether Gemini models actually receive the tools (need LangSmith trace) and whether they choose to invoke them (model behavior).
   - Recommendation: Add debug logging of converted Google tool declarations during execution. Test with explicit "use the pptx skill" prompt. If tools are confirmed present in the request and Gemini still ignores them, the fix is a system prompt adjustment for Google (out-of-scope per Deferred Ideas), not a code fix.

2. **DeepSeek "content appears all at once" (SEED-032 Gap 2)**
   - What we know: Monitoring showed 5+ minute ghost states. The streaming accumulator works correctly. This is likely DeepSeek's API behavior (slow TTFT during code generation).
   - What's unclear: Whether our chunk handler processes DeepSeek chunks differently than OpenAI chunks.
   - Recommendation: D-05 streaming trace comparison during UAT. If DeepSeek API simply doesn't emit content tokens until the full response is ready (similar to reasoning models), document as a known provider limitation.

3. **MiniMax silent failure root cause**
   - What we know: MiniMax M2.7 monitoring showed the run failing at 249s with no error message. Likely output token truncation.
   - What's unclear: Whether this is an OpenRouter issue (was tested via OpenRouter) or a MiniMax API issue.
   - Recommendation: Test via direct API (`api.minimax.chat/v1`) during UAT. If direct API also fails, document as provider limitation.
