# Phase 075.9: Code Review Report

**Reviewed:** 2026-05-24T00:00:00Z
**Depth:** standard
**Files Reviewed:** 13

## Summary

Phase 075.9 introduces a stable client-side `clientKey` identifier to decouple
React/dedup keys from the unstable provider-emitted `tc.id`, migrates
`ToolCallPanel` dedup + `panelExpanded` Record + step-summary keys to the new
fallback chain (`clientKey ?? id ?? composite`), unifies the execute_code
preparing/running editor through `ExecuteCodeEditorInset`, adds a `streaming`
prop on `ShikiCode` that wraps the code in `useDeferredValue`, closes
WR-01 (Shiki promise singleton stuck on rejection) by nulling the cached
promise inside the catch block, and adds a SECURITY CONTRACT JSDoc to the
`dangerouslySetInnerHTML` call site (WR-02). Each load-bearing invariant was
checked:

- **clientKey immutability**: Verified across all 14 reducer paths that touch
  tool_calls in `StreamsProvider.tsx`. Only the two creation sites
  (`onToolPreparing:283` and the `onToolStart` no-preparing fallback at 394)
  assign `clientKey`; every other path uses `{...tc, ...}` spread without
  overriding it. The invariant holds.
- **useDeferredValue gate**: `ExecuteCodeBody.tsx:37` correctly scopes
  `isStreaming = tc.status === "preparing" && !!tc.argsCodeText`. The running
  branch passes `streaming=false`, which short-circuits `useDeferredValue` to
  identity behavior — the inset never lags the canonical code.
- **dangerouslySetInnerHTML trust**: `html` is produced exclusively by Shiki's
  `codeToHtml`, which HTML-escapes its input before token injection. The new
  test hook does not bypass this contract.
- **clientKey ?? id ?? fallback dedup**: The composite fallback includes the
  array `idx`, so two distinct DB-loaded tools without `startedAt` cannot
  collide within one render pass.

Two warnings and four info items below — none block ship. The warnings flag
hygiene/clarity concerns that future phases should pick up, not bugs.

## Warnings

### WR-01: `__resetShikiHighlighterForTests` is exported from the production module without an environment gate

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.tsx:48`
**Issue:** The test-only reset hook is exported from the same module that
ships to production. The double-underscore prefix is convention only — it does
not prevent a caller (a future contributor, a misguided integration, or a
plugin) from invoking it in production code. Today the function only nulls a
module-level cache, so the worst-case impact is a redundant WASM init (low
severity). But the SUMMARY.md asserts "discourages production callers", which
overstates the guarantee — a hard gate would actually deliver on that promise.

Note: a `NODE_ENV === "production"` early-return inside the function body
would defeat the test (vitest runs with `NODE_ENV === "test"`, but the test
hook export gets picked up regardless). The simplest hard gate is to move the
hook into a sibling `ShikiCode.testUtils.ts` module that production bundles
never import; tree-shaking already drops it from the prod bundle, but a sibling
module makes the convention enforceable, not advisory.

**Fix:**
```ts
// Option A — gate the body so production callers no-op:
export function __resetShikiHighlighterForTests() {
  if (typeof process !== "undefined" && process.env?.NODE_ENV === "production") {
    return
  }
  highlighterPromise = null
}

// Option B (preferred) — move to a sibling module:
// frontend/src/components/chat/tool-bodies/ShikiCode.testUtils.ts
//   import * as ShikiModule from "./ShikiCode"
//   export function __resetShikiHighlighter() {
//     // Implementation detail: reach into a non-exported singleton via a
//     // narrowly-typed re-export from ShikiCode that returns a setter.
//   }
// Then drop the export from ShikiCode.tsx and import from testUtils in tests.
```

### WR-02: `makeToolKey` `provider` field is unwired — both call sites fall through to "unknown"

**File:** `frontend/src/providers/StreamsProvider.tsx:283-288`, `394-399`
**Issue:** The `makeToolKey` util accepts a `provider` field "to disambiguate
cross-provider collisions", but both StreamsProvider call sites omit it. The
`toolKey.ts` JSDoc claims `provider | messageId | name | observedAt | index`
is the collision-stable tuple; in practice every live-SSE-stamped key is
`unknown|...`. The other fields (messageId + observedAt + index) already
guarantee collision safety for a single assistant message — but the
provider-prefix story in the docstring is currently aspirational, not
load-bearing. If a future reader audits the dedup logic and trusts the
docstring's "(provider, messageId, name, observedAt)" line, they may
under-investigate cross-provider scenarios that the code does not actually
distinguish.

**Fix:** Either thread the provider through the `makeStreamCallbacks` factory
options (it already has `assistantId` + `threadId` — adding `provider` is
trivial; the snapshot reconcile path can read it from `snapshot.active_runs[i]`
if surfaced), or strike the provider field from the util signature and
JSDoc so the contract matches the reality.

```ts
// Threading-through option:
export function makeStreamCallbacks(opts: {
  assistantId: string
  threadId: string
  provider?: string        // NEW — surfaced from snapshot/sendMessage opts
  onTitleUpdate?: (title: string) => void
  setMessages: ThreadBoundSetMessages
}): StreamCallbacks {
  const { assistantId, threadId, provider, onTitleUpdate, setMessages } = opts
  // ...
  const clientKey = makeToolKey({
    provider,
    messageId: assistantId,
    name,
    observedAt: Date.now(),
    index,
  })
  // ...
}
```

## Info

### IN-01: Composite fallback `${tc.name}-${tc.startedAt ?? ''}-${idx}` can theoretically collide with a real `tc.id` or `tc.clientKey`

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:328`
**Issue:** The dedup key chain is `tc.clientKey ?? tc.id ?? composite`. If
tool A has `clientKey = "search_documents--0"` (degenerate but possible if
provider/messageId/observedAt all happen to render as empty/zero) and tool B
is a DB-loaded tool without `clientKey`/`id` that produces the same composite
`search_documents--0`, both collapse to one row. This is vanishingly unlikely
in practice — `makeToolKey` joins five segments with `|`, so a real
`clientKey` looks like `unknown|msg-X|search_documents|1700000000000|0`, which
cannot match the hyphen-joined composite. Worth a one-line comment to
explicitly disclaim cross-format collisions if a future reader audits.
**Fix:** Add an inline comment, or namespace the composite fallback to make
collision-impossibility self-evident:
```ts
const key =
  tc.clientKey ??
  tc.id ??
  `fallback|${tc.name}|${tc.startedAt ?? ''}|${idx}`
// Pipe-delimited matches clientKey's segment shape but the literal "fallback"
// prefix means a real clientKey can never be confused for a composite.
```

### IN-02: ShikiCode test "first mount: shiki init throws" asserts the fallback before the async catch fires

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.test.tsx:48-60`
**Issue:** The first assertion (`expect(screen.getByTestId("shiki-code-fallback")).toBeInTheDocument()`)
passes because the initial render shows the fallback by default (`html` is null
on first render before the useEffect resolves). The test then waits for the
mock to be invoked and re-asserts the fallback is still present. This is
correct in net behavior, but the test name implies the failure path causes
the fallback — when in fact the fallback is the initial state regardless of
shiki success/failure. A stricter test would flip the mock to succeed mid-test
and assert that the fallback transitions to `shiki-code`, then reset and
assert the fallback PERSISTS only when the mock fails. The happy-path test
(L89-97) already covers the success transition, so the gap is small.
**Fix:** Optional — sharpen the assertion to await the catch path explicitly
before re-asserting the fallback, e.g. by spying on the rejection promise.

### IN-04: `streaming={true}` ShikiCode happy-path test uses the success mock — does not actually exercise the `useDeferredValue` deferral path

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.test.tsx:99-105`
**Issue:** The test renders `<ShikiCode code="x = 1" streaming={true} />` and
asserts the highlighted DOM lands. This passes regardless of whether
`useDeferredValue` is wired, because the test doesn't change the `code` prop
in rapid succession. A behavioral test for the deferral would
need `act()` + repeated rerenders with different `code` values inside a short
window; today the `streaming` prop's correctness rests on the source-level
review of `effectiveCode = streaming ? deferredCode : code`. Not blocking —
React's `useDeferredValue` is a standard hook with documented semantics —
but flagged so a future regression that, e.g., accidentally inverts the
ternary wouldn't be caught by these tests.
**Fix:** Optional — add a behavior test that rerenders the component with
multiple code values inside the same scheduler slice and asserts the rendered
DOM matches the LATEST code value (or at minimum a stable middle one),
verifying the deferral collapses rapid updates without dropping the final one.
