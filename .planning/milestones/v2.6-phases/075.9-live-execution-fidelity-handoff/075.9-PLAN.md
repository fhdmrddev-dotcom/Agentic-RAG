# Phase 075.9 — Live-Execution Fidelity Handoff

## Goal

Close two felt-experience defects surfaced during Phase 075.8's manual UAT, plus the 3 advisory code-review warnings from 075.8. The streaming → terminal handoff should be seamless: tool identity stays stable across preparing/running/done so cards don't visually duplicate, and the `execute_code` editor view stays mounted with Shiki-highlighted code from the first streamed byte through completion (parity with Claude.ai's live-code experience).

## Failure criteria (G-6 — how we'd know this failed)

1. **Sub-agent dedup regression** — Send any prompt that triggers an `analyze` (or other) sub-agent invocation. Mid-stream Chrome MCP screenshot shows TWO cards for the same logical sub-agent call (different `tc.id` resolution between preparing and running renders). Phase fails if dup persists mid-stream.

2. **Code-stream blink** — Send `execute_code` with a >2 KB code block. Watch the editor inset: if the highlighted code disappears at `tool_start` (the preparing→running transition) and a new highlighted view re-mounts, the phase failed the seamless-handoff target. The same Shiki-highlighted view must persist across the transition without visible flash/blink/re-flow.

3. **Shiki promise singleton stuck** — Simulate a `shiki` import failure (ad-blocker, offline, throw on first init). Phase fails if subsequent mounts (after page reload OR after the user retries) still serve the plain-pre fallback because the rejected promise was cached.

## Wave 1 — 5 tasks (mostly parallelizable)

### Task 1: Stable client-side tool key util

**Files:**
- new `frontend/src/lib/toolKey.ts` (~25 lines)
- new `frontend/src/lib/__tests__/toolKey.test.ts` (~30 lines)

```ts
// toolKey.ts — stable per-tool identifier independent of provider id lifecycle
//
// Why: provider-emitted `tc.id` is unstable during the preparing→running
// transition. Some providers don't emit an id until tool_start; others change
// the id between SSE events; OpenRouter occasionally re-issues ids after
// retry. Any UI surface that uses tc.id as a Record key or dedup key suffers
// stale/duplicate state mid-stream.
//
// Stable key contract: derive from (provider, messageId, name, observedAt)
// at first observation. The streams store stamps the resulting `tc.clientKey`
// on creation and never mutates it. Reads should ALWAYS prefer tc.clientKey
// over tc.id for React keys, dedup keys, and Record keys.

export function makeToolKey(opts: {
  provider?: string | null
  messageId?: string | null
  name: string
  observedAt: number  // ms epoch — typically Date.now() at first observation
  index?: number      // per-message tool index when other fields collide
}): string {
  const parts = [
    opts.provider ?? "unknown",
    opts.messageId ?? "no-msg",
    opts.name,
    String(opts.observedAt),
    opts.index != null ? String(opts.index) : "",
  ]
  return parts.join("|")
}
```

**Acceptance:** vitest covers two tools with the same name + provider but different message ids → distinct keys; same tool observed twice (with same observedAt) → identical keys; index disambiguates collisions when all other fields match.

### Task 2: Stamp `clientKey` in the streams store at first observation

**File:** `frontend/src/providers/StreamsProvider.tsx` (or `streamsStore.ts` if the reducer lives there — audit at task start)

At every reducer code path that creates a NEW tool entry (preparing, tool_start with no prior preparing, etc.):
- Compute `clientKey = makeToolKey({ provider, messageId, name, observedAt: Date.now(), index })`
- Stamp it onto the tool object: `tc.clientKey = clientKey`
- Never mutate `clientKey` after creation — subsequent reducer updates copy it forward

The `ToolCall` type gets `clientKey: string` added (required field for newly-created entries; optional during the migration window so existing tests don't blow up).

**Acceptance:** new vitest `streamsProvider_075_9_clientkey.test.tsx` — feed a preparing event then a tool_start event for the same logical tool with a DIFFERENT `tc.id` between them; assert the resulting array has 1 entry, not 2, AND its `clientKey` is set on first observation and unchanged.

In `ShikiCode.tsx`, add a `streaming?: boolean` prop that switches re-highlight from instant to a 50ms debounce:

`useDeferredValue` (React 18+) is enough — no manual debounce loop, no lodash.

### Task 5: WR-01 + WR-02 fixes (small)

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.tsx`

WR-01 — reset singleton on failure:

```tsx
async function getHighlighter() {
  if (!highlighterPromise) {
    highlighterPromise = (async () => {
      try {
        const shiki = await import("shiki")
        const hl = await shiki.createHighlighter({ themes: ["github-dark"], langs: ["python"] })
        return { codeToHtml: (code, opts) => hl.codeToHtml(code, opts) }
      } catch (err) {
        highlighterPromise = null  // ← RESET so next mount retries
        throw err
      }
    })()
  }
  return highlighterPromise
}
```

WR-02 — JSDoc trust contract above the `dangerouslySetInnerHTML` call:

```tsx
/**
 * SECURITY CONTRACT: `code` MUST be plain text (not pre-rendered HTML or
 * markdown). Shiki's tokenizer HTML-escapes input before injecting it into
 * the styled <span> tree, so untrusted plain text is safe. Pre-rendering
 * `code` through markdown or HTML before passing here would BYPASS Shiki's
 * escape pass and allow XSS. Callers must NOT pipe through marked/MDX/etc.
 */
```

**Acceptance:** new vitest `ShikiCode.test.tsx` — mock `import("shiki")` to throw on first call, succeed on second; assert two mounts produce two getHighlighter invocations and the second renders the highlighted HTML. Existing tests stay green.
