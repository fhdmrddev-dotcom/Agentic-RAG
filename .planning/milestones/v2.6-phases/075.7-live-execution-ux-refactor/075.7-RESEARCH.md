## 1. Executive Summary

Five things the planner needs to know to make this phase land cleanly:

1. **CONTEXT.md D-11 is wrong about the scroll container.** `MessageList.tsx:91` wraps the message list in a Radix `ScrollArea`, not a page-body scroll. The Radix viewport is the actual scroll context — `position: sticky; top: 0` on the RunCard header will pin against the Radix viewport (no overflow / transform ancestor blocks it). **This is acceptable** (the sketch CSS works either way), but Plan 02 must NOT switch to page-body scroll just to honor D-11 verbatim — that would require rearchitecting MessageList. Treat D-11 as "sticky-against-the-scroll-container-already-in-use," and document the deviation as discretionary.

2. **The 9 `*Result` components are pure-function presentational components — extraction is mechanical.** Verified by reading ToolCallPanel.tsx:192-409: each takes a typed `parsed` or `result` prop and renders JSX. Only `ReadDocumentResult` (lines 306-342) carries local state (`useState(false)` for expand toggle). No other Result component reaches into `useState`, `useEffect`, refs, or the outer dispatch logic. The dispatch lives in `renderResult()` at L411-423 — a 9-line switch over tool name. Plan 01's atomic commit can lift each Result function verbatim, add a per-file `summarize()` named export, and replace `renderResult()` with a registry lookup. **Blast radius: 1 file mutated, 10 created, 1 deleted.**

3. **MessageItem's React.memo predicate is default shallow-eq, NOT custom.** Line 30: `export const MessageItem = memo(function MessageItem(...)`. No custom comparator. RunCard MUST follow the same pattern: `memo(function RunCard(...))` with default shallow-eq. The 075.4-04 invariant is structural (StreamsProvider mutates `messagesByThread` by REPLACE, so message-identity changes only when content changes) — not predicate-based.

4. **Auto-collapse trigger is `message.runStatus` (the public type-level field), NOT internal panel state.** The 5-value enum lives at `frontend/src/types/index.ts:135` — `"streaming" | "completed" | "failed" | "cancelled" | "timed_out"`. StreamsProvider writes it via `onTerminal` (lines 918-924 and 1119-1124). Terminal = any value ≠ `"streaming"` and ≠ `undefined`. RunCard derives `expanded` from this prop directly — no subscription to internal panel events needed.

5. **Anthropic terminal-frame deferral preservation is a "do not auto-collapse what the user can't see" risk.** BUG-260514-02 (deferred 3×, last 2026-05-23) describes the Anthropic-routed cycle ending with tool-call narration as the *visible body* and a short final-text block beneath it. Auto-collapse-on-completion will fold that body to a one-line summary — but click-to-expand restores full visibility per D-08. The risk: if the click-to-expand DOM order changes (e.g., narration moves above answer), the deferred bug becomes *harder* to re-litigate. **Mitigation:** Plan 02's RunCard JSX must preserve the existing tool-call → final-answer rendering order verbatim. Document this as an explicit non-goal: "do not 'fix' Anthropic block ordering as a side effect of the refactor."

## 3. Sticky Positioning Behavior (Verified Against Actual Scroll Context)

### 3.1 CONTEXT.md D-11 is partially wrong

**CONTEXT.md D-11 says:** "Sticky header uses page-body scroll, NOT an inner ScrollArea. `position: sticky; top: 0` against the document scroll (MessageList is the existing scroll container)."

**Verified actual behavior:**
- `MessageList.tsx:91` returns `<ScrollArea className="flex-1">` (Radix-UI ScrollArea — `frontend/src/components/ui/scroll-area.tsx`)
- The Radix `<ScrollArea>` renders `<ScrollAreaPrimitive.Root>` (with `overflow: hidden`) wrapping `<ScrollAreaPrimitive.Viewport>` (with `h-full w-full`)
- The Viewport — selectable as `[data-radix-scroll-area-viewport]` — IS the actual scrolling element (verified by MessageList.tsx:34 `el = containerRef.current?.closest("[data-radix-scroll-area-viewport]")`)
- The page body itself does NOT scroll the message list. The Radix Viewport does.

### 3.2 What this means for `position: sticky`

`position: sticky` pins against the **nearest scrolling ancestor**. In this case, that's the Radix Viewport, not `<body>`.

**Good news:** the Radix Viewport has no CSS `transform`, no CSS `filter`, no `overflow: hidden` on intermediate ancestors between MessageItem and the Viewport (verified by reading `scroll-area.tsx`). `position: sticky; top: 0` on a child of MessageItem WILL pin against the Viewport.

**One verified risk:** if any intermediate wrapper between RunCard's sticky header and the Viewport sets `overflow: hidden` or `transform`, sticky breaks silently (no error, just behaves as static). Current MessageList layout:

```
<ScrollArea>                             ← Radix Root, overflow: hidden
  <Viewport>                             ← scroll container, [data-radix-scroll-area-viewport]
    <div className="space-y-1 px-6 py-6 max-w-4xl mx-auto">  ← MessageList.tsx:92
      <MessageItem>                      ← memo'd
        <div className="flex gap-3 py-3 animate-fadeSlideUp">  ← MessageItem.tsx:124
          <div className="flex-shrink-0 w-8 h-8 ...">          ← avatar
          <div className="flex-1 min-w-0 pt-0.5">              ← content column (parent of RunCard)
            <RunCard>                    ← NEW
              <div className="run-frame">    ← bordered container
                <div className="run-header" style="position: sticky; top: 0">
```

The chain `Viewport → space-y-1 → MessageItem outer flex → flex-1 min-w-0 column → RunCard root → run-frame → run-header` is free of overflow/transform ancestors. Sticky will work.

**Caveat 1:** `min-w-0` (parent column) is fine. `flex` (MessageItem outer) is fine.

**Caveat 2:** Sketch CSS uses `backdrop-filter: blur(12px)` on the sticky header — this is safe across all modern browsers and does NOT create a transform context.

### 3.3 What "sticks against what" in practice

When two RunCards are visible and the user scrolls inside the Viewport:
- RunCard A's header pins at viewport-top while RunCard A's body is in view.
- When the viewport's scroll moves past RunCard A's body, RunCard A's header rolls off (sticky scope ends at the parent — RunCard A's `run-frame`).
- RunCard B's header THEN pins at top.

This is standard CSS sticky behavior. **No JS, no IntersectionObserver, no clone-and-pin trick needed** despite what live-run-container.md D2's "implementation note for React" suggests as a fallback.

## 4. React.memo Identity Preservation

### 4.1 Current MessageItem memo predicate (verified)

`MessageItem.tsx:30`:
```ts
export const MessageItem = memo(function MessageItem({ message, isStreaming, onSendMessage, onResume }: Props) {
```

**Default shallow-eq comparator.** No custom predicate is passed. The memoization works because:

1. `message` prop identity changes only when StreamsProvider replaces it in `messagesByThread` (RESEARCH-grade verified at StreamsProvider.tsx:681-695 — `setMessagesForBucket` always returns a new Map → new array → new message object).
2. `isStreaming` is a boolean from `useStreamingForThread(viewedThreadId)` (useMessages.ts:85) — flips only on stream start/end.
3. `onSendMessage` + `onResume` are stabilized via `useCallback` in ChatArea (per CONTEXT.md inferred from comment block at MessageItem.tsx:23-29).

### 4.2 RunCard memo contract

RunCard must follow the EXACT same shape:

```ts
// frontend/src/components/chat/RunCard.tsx
import { memo, useState } from "react"
import type { Message } from "@/types"

interface RunCardProps {
  message: Message
  isStreaming: boolean
}

export const RunCard = memo(function RunCard({ message, isStreaming }: RunCardProps) {
  // ... derive expanded from message.runStatus + message.tool_calls.length
  // ... mount tool bodies via TOOL_BODIES registry
})
```

**No custom comparator.** Default shallow-eq handles message identity correctly because the replace-not-mutate pattern upstream guarantees a new message object only when content actually changed.

### 4.3 Anti-patterns the planner must reject

- ❌ Custom `(prev, next) => prev.message.id === next.message.id` — breaks updates when the same message gets new tool_calls
- ❌ Spreading message destructuring at the prop boundary (`<RunCard {...message} />`) — creates a new prop object every render, defeating memo
- ❌ Passing inline-created arrays/objects as props (e.g., `tool_calls={[...message.tool_calls]}`) — same identity-break issue
- ❌ Calling `useState` for collapse state without lazy initializer — running the initializer derives expanded from runStatus, but if runStatus changes from streaming→completed and the user has already toggled, you'd reset their choice. Use lazy initializer + a separate effect to AUTO-collapse on the streaming→terminal transition

### 4.4 Recommended `expanded` derivation

```ts
const hasTools = (message.tool_calls?.length ?? 0) > 0
const isTerminal = message.runStatus && message.runStatus !== "streaming"
const shouldAutoCollapse = hasTools && isTerminal

// Lazy initializer: open by default for active runs, collapsed by default for terminal+tools
const [expanded, setExpanded] = useState(() => !shouldAutoCollapse)

// Auto-collapse on streaming → terminal transition (one-shot)
const wasStreamingRef = useRef(message.runStatus === "streaming")
useEffect(() => {
  if (wasStreamingRef.current && isTerminal && hasTools) {
    setExpanded(false)
  }
  wasStreamingRef.current = message.runStatus === "streaming"
}, [message.runStatus, hasTools])
```

This handles the live-streaming → terminal transition correctly while leaving DB-loaded messages (which mount with `runStatus = "completed"` immediately) in the auto-collapsed state.

## 5. Auto-Collapse Trigger Semantics

### 5.1 The `runStatus` lifecycle (verified against codebase)

Type definition at `frontend/src/types/index.ts:134-135`:
```ts
/** Phase 063 (D-063-04) + Phase 066 (D-066-04, 09): lifecycle status of the underlying run. */
runStatus?: "streaming" | "completed" | "failed" | "cancelled" | "timed_out"
```

5 values + `undefined` (legacy DB-loaded messages without run metadata).

### 5.2 Write sites (verified)

**Initial write (placeholder creation):**
- `StreamsProvider.tsx:834` — reconcile path, on placeholder creation for an in-flight run
- `StreamsProvider.tsx:1013` — sendMessage path, on assistant placeholder creation

Both set `runStatus: "streaming"`.

**Terminal write (run end):**

`StreamsProvider.tsx:918-924` (reconcile path) and `:1119-1124` (sendMessage path):
```ts
if (kind === "done") return { ...m, runStatus: "completed" }
if (kind === "error") return { ...m, runStatus: "failed" }
if (kind === "timed_out") return { ...m, runStatus: "timed_out" }
if (kind === "reader_done") return { ...m, runStatus: "completed" }
// kind === "cancelled"
return { ...m, runStatus: "cancelled" }
```

`StreamsProvider.tsx:1160` — failure-path catch block also sets `runStatus: "failed"`.

### 5.3 Transitions

| From | To | When | Source |
|------|-----|------|--------|
| `undefined` → `"streaming"` | placeholder created | sendMessage / reconcile | L834, L1013 |
| `"streaming"` → `"completed"` | `kind === "done"` or `"reader_done"` | onTerminal | L918, L921, L1119, L1122 |
| `"streaming"` → `"failed"` | `kind === "error"` or sendMessage catch | onTerminal / catch | L919, L1120, L1160 |
| `"streaming"` → `"timed_out"` | `kind === "timed_out"` | onTerminal | L920, L1121 |
| `"streaming"` → `"cancelled"` | `kind === "cancelled"` (user Stop or other) | onTerminal | L923, L1124 |

There is also a transient-stream-end path (`_isTransientStreamEnd` + `_reattachAfterTransient`, L859-911) — when an SSE drops mid-stream, the system re-attaches WITHOUT flipping runStatus. This means `runStatus === "streaming"` can persist through brief SSE interruptions. Auto-collapse is safe — it triggers on the structural terminal value, never on stream interruption.

### 5.4 Terminal predicate (concrete)

```ts
const isTerminal = message.runStatus != null && message.runStatus !== "streaming"
const hasTools = (message.tool_calls?.length ?? 0) > 0
const shouldAutoCollapse = hasTools && isTerminal
```

**Why `runStatus != null`?** DB-loaded historical messages with no run metadata have `runStatus === undefined`. They ALSO have `tool_calls` populated. Per SPEC.md REQ-6: "For runs that are still active (`streaming`/`queued`), the RunCard renders fully expanded as today." DB-loaded historical runs SHOULD auto-collapse (they are terminal by definition — the run finished long ago). So the predicate should be:

```ts
const isTerminal = message.runStatus !== "streaming"  // undefined → true
```

This matches the existing MessageItem precedent at line 117-121 (the sticky-label logic treats `undefined` as terminal). **Confirmed alignment.**

### 5.5 Why not internal panel state?

Today, `ToolCallPanel.tsx:565` declares `const [expanded, setExpanded] = useState(true)` — a single boolean unrelated to runStatus. Past completed runs stay expanded indefinitely. This is the current bug SPEC.md REQ-6 closes.

The new RunCard's `expanded` MUST derive from `message.runStatus`. Internal-only state would not auto-collapse on stream completion (would need an effect listening to runStatus anyway — the lazy initializer + transition effect pattern in §4.4 is the minimal correct implementation).

If the planner restructures MessageItem.tsx such that:
- `message.content` rendering moves INSIDE RunCard, OR
- The expand-click toggle reorders blocks, OR
- Auto-collapse hides the tool-call panel WITHOUT also showing the short narration outside

…then the deferred bug becomes harder to re-litigate. The 075.7 verification gate MUST include a manual UAT step:
