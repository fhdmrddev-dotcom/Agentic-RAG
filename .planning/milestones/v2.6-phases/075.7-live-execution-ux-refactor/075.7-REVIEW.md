## Warnings

### WR-01: RunCard timer `startedAtRef` is never reset on re-attach

**File:** `frontend/src/components/chat/RunCard.tsx:89-100`
**Issue:** The elapsed-time effect sets `startedAtRef.current` lazily on the
first `isStreamingNow` render and never clears it. The effect cleanup only
clears the interval. If a single `Message` instance ever transitions
`streaming → terminal → streaming → terminal` (e.g., reconcile path through
`StreamsProvider` reattaches a previously-terminal-looking run after a
`reader_done` snapshot probe — see `lib/api.ts:537` + `useMessages.ts`
reconcile chain), the second streaming cycle reuses the stale anchor from the
first cycle and the displayed `{elapsedSeconds}s` jumps to the wall-clock
delta between the two cycles, not the actual elapsed of the new attach.
This is the same class of latent bug as B-260519-07 (cross-run cache reset).
The corresponding `startedAt` on per-tool `ElapsedTimer` in `ToolCallPanel.tsx:85`
takes a `startedAt` prop, so it's immune.
**Fix:**
```tsx
useEffect(() => {
  if (!isStreamingNow) {
    // Reset anchor when leaving streaming so a future re-attach starts fresh.
    startedAtRef.current = null
    return
  }
  if (startedAtRef.current == null) startedAtRef.current = performance.now()
  const id = window.setInterval(() => {
    if (startedAtRef.current != null) {
      setElapsedMs(performance.now() - startedAtRef.current)
    }
  }, 250)
  return () => window.clearInterval(id)
}, [isStreamingNow])
```
Note this also requires removing the `(isStreamingNow || elapsedMs > 0)`
display guard at L175 if you want the elapsed badge to disappear after
terminal — current code already leaves the final value visible briefly, so
the cleanup above is the only change strictly needed.

### WR-02: Duplicate React keys inside `LsBody` / `TreeBody` parent containers

**File:** `frontend/src/components/chat/tool-bodies/LsBody.tsx:46-61`
**File:** `frontend/src/components/chat/tool-bodies/TreeBody.tsx:37-49`
**Issue:** Both bodies render two `.map(...)` calls as siblings inside the same
parent (`<div>` in `LsBody`, `<>` fragment in `TreeNodeRow`). Each map keys on
the local index `i`, so when both arrays are non-empty React sees duplicate
keys (`0, 1, ... 0, 1, ...`) among siblings — emits the
"Each child in a list should have a unique key prop" console warning and
disables reconciliation optimizations for that subtree.

This was inherited verbatim from the pre-refactor inline `LsResult` /
`TreeNodeRow` in `ToolCallPanel.tsx` (confirmed via `git show c4a7fc7:...`), so
the bug is not new — but the lines were touched by Plan 01 and the bodies are
now self-contained, so the fix is cleanly scoped here.
**Fix:**
```tsx
// LsBody.tsx
{folders.map((f: any, i: number) => (
  <div key={`folder-${i}`} ...>...</div>
))}
{documents.map((d: any, i: number) => (
  <div key={`doc-${i}`} ...>...</div>
))}

// TreeBody.tsx (inside TreeNodeRow)
{Array.isArray(node.documents) && node.documents.map((doc: any, i: number) => (
  <div key={`doc-${i}`} ...>...</div>
))}
{Array.isArray(node.children) && node.children.map((child: any, i: number) => (
  <TreeNodeRow key={`child-${i}`} node={child} depth={depth + 1} />
))}
```
Prefer a stable id (`f.id` / `d.id` / `node.id`) when the backend supplies one;
namespaced index keys are the safe back-compat.

## Info

### IN-01: `ToolCallPanel.tsx` summary fallback is dead code

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:162`
**Issue:** `const summary = tc.result ? (summarizeToolCall(tc) || "View results") : null`
— every `summarize()` in `tool-bodies/*.tsx` returns either a derived string or
a hard-coded `"View results"` (or `"no output"` / `"View search results"`),
never `""`. The `|| "View results"` branch can never fire. Not harmful, just
unreachable.
**Fix:** Drop the `|| "View results"` fallback, or keep it explicitly as
documentation of intent (current code already comments this — your call).

### IN-02: `RunCard` auto-collapse re-fires on every `streaming → terminal` cycle

**File:** `frontend/src/components/chat/RunCard.tsx:65-77`
**Issue:** `wasStreamingRef` is updated every render to mirror the current
`runStatus === "streaming"` value. If a Message goes `streaming → terminal →
(user expands) → streaming → terminal`, the second terminal arrival fires the
auto-collapse again — the "one-shot" claim in the comment is true only within
a single streaming session. The reconcile + reattach path is the most likely
producer of this scenario. Low priority because the user can re-expand; flagged
so future readers don't trust the "one-shot" comment as absolute.
**Fix:** Track whether THIS RunCard instance has ever auto-collapsed and skip
on subsequent transitions:
```tsx
const hasAutoCollapsedRef = useRef(false)
useEffect(() => {
  if (wasStreamingRef.current && isTerminal && hasTools && !hasAutoCollapsedRef.current) {
    setExpanded(false)
    hasAutoCollapsedRef.current = true
  }
  wasStreamingRef.current = message.runStatus === "streaming"
}, [message.runStatus, hasTools, isTerminal])
```

### IN-03: Effect dependency includes a derived value

**File:** `frontend/src/components/chat/RunCard.tsx:77`
**Issue:** `useEffect(..., [message.runStatus, hasTools, isTerminal])` — but
`isTerminal = !isStreamingNow = !(message.runStatus === "streaming")`, so it's
already covered by `message.runStatus`. Redundant, not buggy. Likewise
`hasTools` is derived from `message.tool_calls?.length`; including it ensures
the effect re-runs when the tools array reference changes, which is the
intended behavior.
**Fix:** Optional — drop `isTerminal` from the deps array (eslint may flag this
otherwise depending on `react-hooks/exhaustive-deps` config).

### IN-04: Playwright `selectOption({ label: RegExp })` is not in the typed API

**File:** `frontend/tests/e2e/scenario-09-cross-provider-tool-bodies.spec.ts:65,78`
**Issue:** `selectOption({ label: providerSelector })` where `providerSelector`
is a `RegExp`. Playwright's `selectOption` typed signature accepts string-only
labels; the regex shape silently relies on the immediate `.catch(...)` fallback
to recover via the role/button path. Same pattern is used in scenarios 02 /
03 / 05 — this is a project-wide convention, not a 075.7 regression, so it's
informational only. Worth normalising in a future test-infra phase to either
pass `{ label: providerSelector.source }` or use `selectOption` only with a
literal option value.
**Fix:** No action this phase. Track as a test-infra cleanup item.

### IN-05: `useEffect` in `TerminalOutput` scrolls on `lines.length` change only

**File:** `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx:34-41`
**Issue:** The effect dep array is `[lines.length]`. If the reducer ever
replaces a line's content without changing the array length (today only
append-on-stdout, so it's safe), the auto-scroll won't fire. Pre-existing
behavior — preserved verbatim from the legacy `ExecuteCodeBlock` (per Plan 01
"functional behavior preserved" contract). Flag only because the line is now
inside a renamed file.
**Fix:** No action — the contract here is intentional ("only scroll on new
line emitted").

### IN-06: Multiple IIFE re-parses of `tc.result` in `ExecuteCodeBody`

**File:** `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx:116-149`
**Issue:** Four separate IIFE blocks each call `JSON.parse(tc.result)` on every
render to derive `outputFiles` / `exitCode` / `executionDurationMs` / `lines`
for the reloaded-message path. Cheap per-call but redundant — a single
`useMemo(() => JSON.parse(tc.result ?? "null") ?? {}, [tc.result])` would
collapse the four reparses into one. Out of v1 scope per review-scope rules
(performance is non-blocking); noted because the file was touched.
**Fix:**
```tsx
const reloaded = useMemo(() => {
  try { return tc.result ? JSON.parse(tc.result) : null } catch { return null }
}, [tc.result])
const outputFiles: OutputFile[] = tc.outputFiles ?? reloaded?.output_files ?? []
const exitCode: number | undefined = tc.exitCode ?? reloaded?.exit_code
// ...etc
```
