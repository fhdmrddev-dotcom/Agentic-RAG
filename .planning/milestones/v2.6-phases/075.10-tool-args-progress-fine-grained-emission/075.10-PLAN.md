# Phase 075.10 — Fine-Grained `tool_args_progress` Emission

## Goal

Close the backend gap that 075.9's HUMAN-UAT exposed: `tool_args_progress` events either don't fire (OpenAI/OpenRouter) or fire at a 5120-byte boundary too coarse for typical code (<5 KB on Anthropic/Google). After this phase, the frontend's already-correct streaming wiring receives chunks fine-grained enough for visible character-by-character code rendering during the args-generation window — matching Claude.ai's live-code experience.

## Why no heavy ceremony

- **Root causes diagnosed.** Phase 075.9 UAT captured SSE timelines via patched `fetch` interceptor on gpt-5.4 + claude-opus-4-6. Zero `tool_args_progress` events on both. Boundary constant + service gap pinpointed at `anthropic_service.py:254`, `google_service.py:482`, and the absence of the entire emission block in `openai_service.py`.
- **Frontend already done.** Phase 075.9 + hot-fix (commit `443b4be`) shipped the architecturally-correct path: `ExecuteCodeBody` mounts during preparing across all providers, reads `tc.argsCodeText ?? tc.args.code`, and `<ShikiCode streaming={...}>` uses `useDeferredValue` to batch the re-tokenization. Zero frontend changes needed in 075.10 — just feed the path.
- **Pattern is verbatim-cloneable.** `google_service.py:367-490` is the canonical 5KB-boundary emitter. The work is "lower the boundary constant" × 2 places + "port the same block" × 1 place.

## Failure criteria (G-6 — how we'd know this failed)

1. **OpenAI silent.** After Phase 075.10 ships, send `execute_code "for i in range(10): print(i)"` on gpt-5.4. SSE intercept (patched fetch in browser console) shows **fewer than 3** `tool_args_progress` events between `tool_preparing` and `tool_start`. Phase fails — OpenAI emission isn't running.

2. **Sub-5KB code on Anthropic/Google still silent.** Send the same prompt on claude-opus-4-6 + gemini-2.5-flash. SSE intercept shows **fewer than 3** `tool_args_progress` events. Phase fails — boundary wasn't actually lowered or `tc.argsCodeText` isn't accumulating.

3. **No visible streaming on lived-experience UAT.** Eyeball test: send a ~1 KB code prompt on each of the 4 providers. If the editor inset is blank during preparing and the code appears all-at-once at `tool_start` on ANY provider, phase fails (regardless of what the SSE log says).

### Task 4: Port emission logic to OpenAI

**File:** `backend/app/services/openai_service.py`

The OpenAI Chat Completions streaming API exposes tool-call argument deltas via `chunk.choices[0].delta.tool_calls[i].function.arguments` (string fragments). Today the OpenAI service accumulates these internally but never emits them as `tool_args_progress` events.

Port the pattern verbatim from `google_service.py:367-490`:

```python
# State at the start of the streaming function
_tool_args_emit_boundary: dict[int, int] = {}
_tool_args_accumulator: dict[int, str] = {}
_tool_index_by_call_id: dict[str, int] = {}
_emit_boundary_bytes = await _read_setting_int(
  "chat_tool_args_progress_emit_boundary_bytes",
  default=256,
)

# Inside the streaming loop, when a tool_calls delta arrives with an arguments chunk:
for tc_delta in (chunk.choices[0].delta.tool_calls or []):
  if tc_delta.function is None or tc_delta.function.arguments is None:
    continue
  idx = tc_delta.index  # OpenAI provides this directly
  name = tc_delta.function.name  # may be None on deltas after the first
  _tool_args_accumulator[idx] = _tool_args_accumulator.get(idx, "") + tc_delta.function.arguments

  _bytes_total = len(_tool_args_accumulator[idx].encode("utf-8"))
  _new_boundary = _bytes_total // _emit_boundary_bytes
  _last_boundary = _tool_args_emit_boundary.get(idx, 0)
  if _new_boundary > _last_boundary and name:
    _tool_args_emit_boundary[idx] = _new_boundary
    _tail_bytes = _tool_args_accumulator[idx].encode("utf-8")[-max(5120, _emit_boundary_bytes * 4):]
    _args_so_far = _tail_bytes.decode("utf-8", errors="ignore")
    yield {
      "type": "tool_args_progress",
      "tool_index": idx,
      "name": name,
      "args_so_far": _args_so_far,
      "code_so_far": _tool_args_accumulator[idx],  # full cumulative per Req #5
      "total_args_bytes_so_far": _bytes_total,
    }
```

Also ensure `tool_preparing` fires at the first tool_call delta observation (OpenAI may skip the equivalent of Anthropic's `content_block_start` so the existing tool_start path may need a preparing-emit fallback). Audit the current OpenAI service for the tool lifecycle and add `tool_preparing` emission if missing — without it, the frontend reducer never creates the preparing entry that holds `argsCodeText`.

**Acceptance:** SSE intercept on `gpt-5.4` execute_code with a ~1 KB code body shows:
- ≥ 1 `tool_preparing` event before `tool_start`
- ≥ 3 `tool_args_progress` events between preparing and tool_start
- `code_so_far` payload that grows monotonically across the events
