## Warnings

### WR-01: `active_provider_name` rebinding inside the OpenAI-compat branch may overwrite-last-wins for Gemini routed through OpenRouter

**File:** `backend/app/api/threads.py:1853`
**Issue:** The variable `active_provider_name` is bound twice in the same scope with different semantics:
- Line 1677: `active_provider_name = getattr(user_settings, "active_provider", "") or ""` — the user's **active provider** (used to branch anthropic vs. openai-compat at line 1679).
- Line 1853 (inside the `else` openai-compat branch): `active_provider_name = (_active_cap.get("provider") or "unknown").lower()` — the **model's registry-classified provider**, read from `MODEL_CAPABILITIES[_model_id].provider`.

If a user explicitly selects provider=openrouter AND model=`gemini-2.5-flash` (registry hit, `provider="google"`), the rebinding makes `_accumulate_chunk_usage` branch on `provider="google"` and apply Google's overwrite-last-wins. The `_resolved_provider` alignment at `threads.py:1221-1228` is gated on `body.provider` being absent — so an explicit body.provider override skips the alignment but the per-chunk closure still uses the model-registry provider for accumulation.

In practice this is **safe today** because OpenRouter's compat layer per Pitfall 8 emits usage in OpenAI's final-chunk-only shape (single value = the true cumulative, so overwrite vs. += both produce the correct number). It is brittle on two axes:
1. Future OpenRouter forward-compat changes that emit usage per chunk would silently undercount if Google's overwrite branch fires on multi-chunk emission via OpenRouter.
2. The double-binding makes the closure capture surprising to readers — the variable means two different things 175 lines apart in the same try-block.

**Fix:** Rename the line-1853 local to something narrowly scoped to the accumulator, and source it explicitly from the streaming branch context rather than re-shadowing the outer name:

```python
# Phase 075.3 D-075.3-03: classify accumulator branch by the model's
# registry provider (drives Google overwrite-last-wins vs += elsewhere).
# Renamed from `active_provider_name` (shadowed the outer-scope user-settings
# active provider). Use this ONLY as the second argument to
# _accumulate_chunk_usage; keep the user-settings active_provider name
# anchored to the outer-while-loop binding.
_active_cap = get_model_capability(_model_id) or {}
_accumulator_provider = (_active_cap.get("provider") or "unknown").lower()
```

Then pass `_accumulator_provider` into `_accumulate_chunk_usage(...)` at line 1881. Optional follow-up: if the user has `active_provider="openrouter"` but the model is a registry-known Google ID, force the accumulator to `"openrouter"` (the actual streaming wire shape) rather than the model's classification. That would close the brittleness called out in (1) above. Worth a quick decision before phase close.

### WR-02: `KEY_PLACEHOLDER` sentinel is duplicated as a literal across backend and frontend with no shared source of truth or schema validation

**File:** `backend/app/models/user_settings.py:37`, `frontend/src/pages/SettingsPage.tsx:14`, `backend/app/api/settings.py:80,91,97,109`
**Issue:** The sentinel `"***"` is hand-coded in two places. The backend's `save_override` at `user_settings.py:139` uses `if v == KEY_PLACEHOLDER: continue` to skip overwrites — but any other string falls through to `current[k] = v` at line 144 and **clobbers the existing api_key with the literal sentinel string**. The orchestrator hit exactly this footgun mid-UAT (used `__KEEP__`, clobbered all api_keys). Phase 075.3's diff does not change this contract, but the diff DOES extend `SettingsUpdate` with new fields that go through the same save path (no new attack surface, just reaffirms the existing risk).

There is no defensive guard. A simple "strings starting with `*` of length ≤ 5 are sentinels, anything else is a real value" heuristic would have caught `__KEEP__`. A stronger fix would be to make the API contract explicit: use `None` for "no change" (PATCH semantics) and reserve empty string for "clear key", removing the magic-string sentinel entirely.

**Fix:** Cheapest defensive guard — log+reject any api_key save where the value looks suspicious-but-not-exactly-`***`:

```python
# backend/app/models/user_settings.py — save_override
_SENTINEL_HEURISTIC = re.compile(r"^[\*_]{1,8}$")  # ***, ___, __KEEP__, etc.

def save_override(updates: dict[str, Any]) -> None:
    current = _load_override()
    for k, v in updates.items():
        if v == KEY_PLACEHOLDER:
            continue
        # Defensive guard: any *_api_key value that looks like a sentinel
        # but isn't exactly KEY_PLACEHOLDER is almost certainly a frontend
        # bug (e.g., orchestrator wrote __KEEP__). Reject loudly rather
        # than clobber the saved key.
        if "_api_key" in k and isinstance(v, str) and _SENTINEL_HEURISTIC.match(v):
            logger.error(
                "save_override: refusing to clobber %s with suspicious sentinel %r "
                "(expected %r for keep-existing); skipping update for this key",
                k, v, KEY_PLACEHOLDER,
            )
            continue
        if v is None:
            current.pop(k, None)
        else:
            current[k] = v
    _OVERRIDE_FILE.write_text(json.dumps(current, indent=2), encoding="utf-8")
    _override_cache_time = 0.0
```

Stronger fix (post-075.3, breaking change): expose the sentinel via a shared constants endpoint or via the `FullSettingsResponse` itself so the frontend reads the canonical value from the backend rather than hard-coding it. Phase-out the sentinel pattern in favor of explicit `null` vs `""` semantics on the next settings-API revision.

### IN-04: `_accumulate_chunk_usage` docstring uses `from None` vs `(output_total or 0)` asymmetrically

**File:** `backend/app/api/threads.py:590-592`
**Issue:** The += branch in `_accumulate_chunk_usage` returns:
```python
if input_total is None:
    return _i, _o
return input_total + _i, (output_total or 0) + _o
```
The first branch assumes input_total being None implies output_total is also None (init-once). The second branch defensively guards output_total with `or 0` but does NOT guard input_total. If a caller ever threads (input_total=10, output_total=None) the function returns (10 + _i, 0 + _o) — silently dropping the input chain. The current single caller (`_on_chunk_openai`) always threads them as a pair, so this is currently unreachable, but the asymmetric defense is fragile and contradicts the assumed invariant.

**Fix:** Either remove the `or 0` (assert the pair-invariant), or guard both consistently:

```python
return (input_total or 0) + _i, (output_total or 0) + _o
```

The latter is more robust and matches the defensive-helper framing of the function.

### IN-05: Brittle accumulator branch — provider="google" classification, not wire-format classification

**File:** `backend/app/api/threads.py:550-592` + `backend/app/api/threads.py:1844-1853`
**Issue:** Related to WR-01 but worth recording separately. `_accumulate_chunk_usage` branches on the **model's registry provider** ("google" → overwrite, else → +="). This conflates "this model is from Google" with "this stream's wire is in Google's cumulative-usage shape". The two coincide today because users with provider=google use Google's direct compat, but the Phase 079 multi-worker / cross-provider-routing roadmap could introduce models that are Google-class but streamed via OpenRouter or vLLM — at which point the overwrite branch would mis-accumulate if the wire format flips.

**Fix:** Long-term, the discriminator should be **stream wire format**, not model identity. Today's shape is correct for today's wiring; capture as a deferred re-open trigger in `.planning/reported-bugs/` if a future SEED introduces a Google-class model on a non-Google wire. No code change required for 075.3 close.

### IN-06: `verified_models` payload size scales with `MODEL_CAPABILITIES` — currently small, but unbounded by API contract

**File:** `backend/app/api/settings.py:166`
**Issue:** `verified_models=sorted(MODEL_CAPABILITIES.keys())` ships the full registry on every `GET /settings` call. Current size: 33 strings × ~20 chars ≈ 700 bytes. As MODEL_CAPABILITIES grows (the user's representative-class memory feedback says this is expected on every new model surfacing live), this payload grows linearly. Settings is fetched on every Settings page open and on `hydrate()` after every save. Not a problem today; flag for revisit if the registry exceeds ~200 entries (~5KB on the wire per fetch).

**Fix:** None now. A future optimization: serve `verified_models` from a dedicated endpoint with `Cache-Control: max-age=300` so the Settings PUT round-trips don't re-fetch the constant set. Or move to a versioned schema where the frontend caches the registry against a content hash. Both deferrable past 075.3.
