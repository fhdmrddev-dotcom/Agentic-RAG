# Phase 071.4 Plan 02: Library Health infinite-fetch loop fix — BUG-260516-02 closed

**A `useRef<Set<TabKey>>` replaces the data-state inference in the tab-load useEffect. The Library Health page no longer fires `/knowledge-health/low-confidence/documents` on a tight loop when the backend returns an empty result.**

## Performance

- **Started:** 2026-05-16 (this session, inline execution)
- **Completed:** 2026-05-16
- **Tasks:** 4/4
- **Files modified:** 2 (1 code, 1 bug doc)
- **Duration:** ~30 min total (investigation ~10 min, fix ~5 min, Chrome MCP verification ~15 min)

## Accomplishments

1. **Root-caused the loop.** The offending useEffect at `KnowledgeHealthPage.tsx:233-239` had `tabData` in its deps plus an `items.length === 0` guard. When the backend legitimately returned `[]` (zero low-confidence docs for this user), the guard stayed true forever — every `setTabData` produced a new object reference, deps saw the change, effect re-fired, called `fetchTab` again, repeat.

2. **Fixed via `useRef<Set<TabKey>>`.** Replaced the data-state inference with an explicit "initialized" set tracked in a ref. The ref doesn't trigger re-renders, so a tab is fetched exactly once on first activation, regardless of the API's response shape.

3. **Preserved the Refresh button affordance.** The Refresh button now clears the ref alongside its existing `loadOverviewAndTrend(true)` call. Without this, once a tab is fetched, the only way to refetch its data was a full page reload. Now Refresh refetches the active tab too.

4. **Live-verified via Chrome DevTools MCP.** Confirmed:
   - Login → Library Health → Low Confidence tab → By Query sub-tab.
   - DevTools Network: exactly 1 request per tab activation (5 total knowledge-health requests across the 5 tabs).
   - 5 seconds of idle produced zero follow-up fetches. UI did not shake.
   - No console errors / warnings.

## Decisions Made

- **`useRef` over `useState`.** A `useState<Set<TabKey>>` would have caused the same re-render-on-set storm the bug was symptomatic of. The ref is the right primitive: tracks identity without affecting render.
- **Cleared ref on Refresh button.** Without this, the existing Refresh affordance would only refresh the overview/trend panels — tabs would be locked-in after first fetch. Small UX win bundled with the fix.
- **Did NOT change the data-shape contract.** The `TabState` shape (items / loading / error / total / offset) is unchanged. Only the trigger mechanism for fetches was rewritten. Reduces blast radius.

Probably a synthetic-event vs Radix listener quirk. Documented for future Chrome MCP UI tests on Radix surfaces.
