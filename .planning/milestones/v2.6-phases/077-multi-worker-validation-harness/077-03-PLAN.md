```python
This test only VERIFIES it works -- no new cancel logic needed (D-077-08).
```

**Infrastructure guard:** Same pattern as test_077_multi_worker.py -- `pytestmark = pytest.mark.skipif` checking Redis + Postgres availability.

**Shared subprocess fixture:** Import or duplicate the `multi_worker_server` fixture from test_077_multi_worker.py. Since pytest fixtures are module-scoped and can't be shared across files without conftest, either:
- Option A: Create a `conftest.py` in the integration folder with the shared fixture (but this risks side effects on other tests)
- Option B: Duplicate the fixture in this file (simpler, self-contained)

Choose Option B (duplicate). The fixture code is ~30 lines and self-contained.

However, for this test we need a SLOW mock -- the default mock stream completes in milliseconds, making it hard to hit with a cancel request before it completes. Solution: Add a `MOCK_LLM_SLOW_MODE=1` env var check in `_test_mock_llm.py` that makes the mock yield chunks with 0.5s delays between them. Actually, simpler approach: the harness doesn't need a slow stream -- it needs to:
1. POST a message to start a run (which inserts a `runs` row with `status='streaming'`)
2. The mock completes fast BUT -- the key insight is that with --workers 2 and round-robin, the DELETE request going to Worker B will NOT find the run_id in Worker B's `RUN_TASKS` dict even if the run is still in-flight.

Better approach per D-077-07: make the mock stream slow enough (add `time.sleep(2)` between chunks when a specific env var is set). OR: rely on the fact that after the fast mock completes, the `_shielded_finalize` path runs async (Postgres UPDATE, ZREM, etc.) -- there's a brief window where `runs.status` may still be `streaming` because finalize is shielded. But this window is unreliable.

REVISED APPROACH: The cleanest way per RESEARCH.md:
1. Start the subprocess with MOCK_LLM_MODE=1 (fast mock)
2. Use direct Redis + Postgres manipulation to SET UP a zombie state (matching the `setup_zombie_state` helper pattern from _run_helpers.py):
   - Insert a `runs` row with `status='streaming'` via asyncpg
   - ZADD to `runs:active` and `runs_by_thread:{thread_id}`
   - XADD a few entries to `run:{run_id}` stream
3. Send `DELETE /runs/{run_id}` to the subprocess (which has no RUN_TASKS entry for this run_id -- exactly the zombie-heal scenario)
4. Assert the zombie-heal outcomes

This is MORE reliable than trying to race a cancel against a fast mock. The zombie state is the EXACT scenario where cross-worker cancel matters (Worker A died, Worker B handles the DELETE).

**Test data setup fixture:** Create user `00000000-0000-0000-0000-000000000001` (same as mock auth user) + thread + runs row with `status='streaming'` + Redis sorted set entries + Redis stream entries.

**Test function `test_cross_worker_cancel_via_zombie_heal`:**
1. Setup: Insert `runs` row with `status='streaming'`, `user_id=test_user_id`, `thread_id=test_thread_id`. ZADD to `runs:active` and `runs_by_thread:{thread_id}`. XADD a content chunk to `run:{run_id}`.
2. Action: `httpx.AsyncClient` sends `DELETE /runs/{run_id}` to the subprocess base_url with auth header (mock auth).
3. Assert response status == 204
4. Assert Postgres: `SELECT status FROM runs WHERE run_id = $1` returns `'cancelled'`
5. Assert Redis: `await redis.exists(f"run:{run_id}:cancel_lock")` == True
6. Assert Redis stream: XREAD the last entry from `run:{run_id}` -- parse JSON, assert `data.type == 'cancelled'` and `data.reason == 'zombie_healed'`
7. Assert Redis: `await redis.zscore("runs:active", str(run_id))` is None (removed)

**Cleanup:** Delete the runs row, remove Redis keys.

```python
"""Sandbox Docker container re-attach verification (Phase 077 D-077-04/05/06).

Tests that SandboxSessionManager.get_or_create(thread_id):
  1. Creates a new container with name ``sandbox-{thread_id[:12]}`` on first call
  2. Re-attaches to the SAME container when _sessions dict is cleared (worker bounce)
  3. Falls back to fresh creation when no container exists (normal cold start)

Requires: Docker daemon running. Does NOT require Redis/Postgres.
"""
```

**Docker skipif guard:**
```python
def _docker_available() -> bool:
    try:
        import docker
        client = docker.from_env()
        client.ping()
        return True
    except Exception:
        return False

DOCKER_AVAILABLE = _docker_available()
pytestmark = [
    pytest.mark.skipif(not DOCKER_AVAILABLE, reason="Docker daemon not reachable"),
    pytest.mark.skipif(
        os.environ.get("SANDBOX_ENABLED", "false").lower() != "true",
        reason="SANDBOX_ENABLED not true; skipping sandbox tests",
    ),
]
```

Note: This test is only meaningful when Docker + SANDBOX_ENABLED=true. The skipif guards ensure it doesn't fail in envs without Docker.

**Test function `test_reattach_to_existing_container`:**
1. Generate a unique `thread_id = str(uuid4())`
2. Call `sandbox_manager.get_or_create(thread_id)` -- this creates a new container named `sandbox-{thread_id[:12]}`
3. Assert: `thread_id in _sessions` (in-memory entry exists)
4. Capture `container_name = f"sandbox-{thread_id[:12]}"`
5. Verify container exists via Docker SDK: `docker.from_env().containers.get(container_name)` succeeds and `.status == "running"`
6. Get the container ID: `original_container_id = container.id`
7. Simulate worker bounce: `del _sessions[thread_id]` and `_last_used.pop(thread_id, None)`
8. Assert: `thread_id not in _sessions` (simulated fresh worker)
9. Call `sandbox_manager.get_or_create(thread_id)` again
10. Assert: `thread_id in _sessions` (re-created entry)
11. Get the new session's container -- verify it's the SAME container: check `docker.from_env().containers.get(container_name).id == original_container_id`
12. Cleanup: `sandbox_manager.close_session(thread_id)` then `docker.from_env().containers.get(container_name).remove(force=True)` (wrapped in try/except)

**Test function `test_fresh_creation_when_no_container`:**
1. Generate a unique `thread_id = str(uuid4())`
2. Assert no container named `sandbox-{thread_id[:12]}` exists (docker.errors.NotFound)
3. Call `sandbox_manager.get_or_create(thread_id)`
4. Assert: container `sandbox-{thread_id[:12]}` now exists and is running
5. Cleanup: `sandbox_manager.close_session(thread_id)` then remove container
