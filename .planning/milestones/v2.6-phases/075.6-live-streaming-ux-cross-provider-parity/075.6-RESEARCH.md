## Summary

This is a narrow, surgical phase — ~80% of substrate already shipped through Phases 068 / 068.5 / 075 / 075.1. The gap is **one additive field on an existing SSE event** (uniform across 4 adapters), **one new collapsible frontend component**, and **three small frontend rendering improvements** that surface already-accumulated state.

The single largest landmine: the `backend/app/services/openrouter_service.py` file referenced in CONTEXT.md and SPEC.md **does not exist**. OpenRouter shares `_on_chunk_openai` in `backend/app/api/threads.py:2114-2200` with the OpenAI SDK path (both use the `openai==2.28.0` Python SDK, differing only by `base_url`). The SPEC-locked decision "OpenRouter aggregates upstream OpenAI-shaped deltas independently (no shared code path with OpenAI adapter)" therefore reduces to either (a) splitting the callback into two functions or (b) per-provider-branched accumulator buffers inside the existing callback. The planner needs to address this explicitly.

The second largest landmine: the OpenAI-path `tool_args_progress` emit at `threads.py:2174-2200` **explicitly skips `execute_code`** with `_tool_name != "execute_code"` — that is the exact gate Plan 01 must remove for SPEC Reqs #2 and #3. The skip was deliberate (deferred to v3.0 Skill Studio per REQUIREMENTS.md line 65) but is now obsolete given the live-panel UX.

The third landmine: existing `args_so_far` ≠ new `code_so_far`. The existing `args_so_far` is the LAST 5 KB sliding-window tail (UTF-8 truncated). The new `code_so_far` per SPEC Req #5 acceptance is the FULL cumulative text (entire concatenation, `'CHUNK_A_PLUS_B'`). They are different semantics on the same event payload, both required, both additive.

**Primary recommendation:** Plan 01 adds one additive field (`code_so_far: string` = cumulative `tool_calls_buffer[idx]["arguments"]` decoded to str) to all 4 emit sites and removes the `execute_code` skip in the OpenAI-shared path. Plan 02 extends `onToolArgsProgress` callback signature in `frontend/src/lib/api.ts:392-397` to forward `code_so_far`, extends the StreamsProvider reducer at `StreamsProvider.tsx:293-315` with a longer-string-wins update on `tc.argsCodeText`, and inserts `<ToolArgsLivePanel>` into `ToolCallPanel.tsx` near the existing byte-counter render (lines 743-746). Plan 03 narrows the sub-agent gate at line 694, adds the step-list collapse predicate inside the displayItems map at line 667, and inserts `<WorkingBadge>` into `MessageItem.tsx` between lines 140-141.

### Pattern 1: Per-tool-index closure state with per-iteration reset
**What:** A `dict[int, ...]` keyed by `tool_index` lives inside the `_on_chunk_*` callback's closure. Resets at the top of each LLM-call iteration so cross-round leakage cannot silence boundary emits.

**When to use:** Provider-uniform aggregation buffers for streaming deltas. Already used by `_tool_args_emit_boundary` (existing) and `tool_calls_buffer` (existing).

**Example (existing pattern at `threads.py:2069-2077`, extends for 075.6):**
```python
# Source: backend/app/api/threads.py:2069-2077
tool_calls_buffer: dict = {}
finish_reason: str | None = None
_announced_tools: set[int] = set()
# Phase 075 D-075-10 + Pitfall 3: per-tool_index 5KB-boundary counter
# for tool_args_progress emits. Resets alongside tool_calls_buffer /
# _announced_tools at each agent-loop iteration to prevent cross-round
# leakage.
_tool_args_emit_boundary: dict[int, int] = {}

# 075.6 Plan 01: NO new state container required — tool_calls_buffer[idx]["arguments"]
# IS the full cumulative string. New emit just decodes it to str and passes
# alongside the existing args_so_far tail.
```

### Pattern 2: Math.max-style longer-wins reducer update
**What:** When out-of-order replay events can arrive (Phase 075.2 WR-02 reattach), reducer must accept the LONGER value as truth, never overwrite with a shorter value.

**When to use:** Any monotonically-growing streaming field where SSE replay or reconnect can deliver events out of order.

**Example (existing at `StreamsProvider.tsx:307-308`, extends for 075.6):**
```typescript
// Source: frontend/src/providers/StreamsProvider.tsx:293-315 (existing)
const next = Math.max(tc.argsBytesStreamed ?? 0, totalArgsBytesSoFar)
if (next === (tc.argsBytesStreamed ?? 0)) return m

// 075.6 Plan 02 extension (longer-string-wins for argsCodeText):
const nextCode =
  codeSoFar != null && codeSoFar.length > (tc.argsCodeText ?? '').length
    ? codeSoFar
    : tc.argsCodeText
const noChange = next === (tc.argsBytesStreamed ?? 0) && nextCode === tc.argsCodeText
if (noChange) return m
const updated = calls.map((c, i) =>
  i === idx ? { ...c, argsBytesStreamed: next, argsCodeText: nextCode } : c,
)
```

### Pattern 3: Provider-uniform SSE event vocabulary (Req #9 invariant)
**What:** Adapters normalize per-provider chunk shapes into a single shared event vocabulary. Frontend NEVER branches on provider.

**When to use:** Any new streaming UI behavior. Per `feedback-provider-uniform-ux` memory + SPEC Req #9 + `git grep` audit gate.

**Example (existing pattern, extends for 075.6):**

### Anti-Patterns to Avoid

- **`if (provider === "openai") { ... }` in any frontend file:** FORBIDDEN per SPEC Req #9 + `feedback-provider-uniform-ux` memory. Audit gate: `git grep -E "provider\s*===\s*['\"]" frontend/src/components/chat/ frontend/src/providers/StreamsProvider.tsx` returns zero new matches.
- **Re-implementing a "shared" OpenRouter accumulator that points at the same buffer as OpenAI native:** Even though they share the callback function, the SPEC-locked decision requires *independent state slots*. If a future OpenRouter upstream model emits non-OpenAI-shaped chunks, the OpenAI native path must not silently break. The right shape: branch on `active_provider_name` (already captured at `threads.py:2100`) and maintain TWO separate `_tool_args_emit_boundary` dicts, or split `_on_chunk_openai` into `_on_chunk_openai_native` + `_on_chunk_openrouter`.
- **Storing `argsCodeText` in DB:** Out-of-scope per SPEC §Boundaries. Panel is in-flight only; DB-loaded historical messages render through `tc.args.code` (already-parsed final args).
- **Removing the byte-counter at `ToolCallPanel.tsx:743-747`:** Out-of-scope per SPEC §Boundaries — counter relocates inside the new panel as a small header label. The separate disposition-commit for T-260523-09 happens AFTER 075.6 ships.

### Pitfall 3: `args_so_far` ≠ `code_so_far`
**What goes wrong:** Plan 01 conflates the existing 5 KB-tail `args_so_far` field with the new `code_so_far` field. Either the wire format drops a field consumers depend on, or `code_so_far` ships as a tail instead of the full cumulative text.

**Why it happens:** The field names are similar; existing emit sites already have an `_args_so_far` local variable that's the truncated 5 KB tail (per `anthropic_service.py:263-264`, `google_service.py:468-469`, `threads.py:2192-2193`).

**How to avoid:** Plan 01 spec explicitly differentiates:
- `args_so_far` (existing, KEEP): `tb["arguments"].encode("utf-8")[-5120:].decode("utf-8", errors="ignore")` — the 5 KB sliding-window tail.
- `code_so_far` (new, ADD): `tb["arguments"]` — the FULL cumulative concatenated string (already maintained in the closure buffer). Both fields ride the same event payload.

Req #5 acceptance proves this: `onToolArgsProgress(0, 'execute_code', 5121, 'CHUNK_A')` followed by `onToolArgsProgress(0, 'execute_code', 10241, 'CHUNK_A_PLUS_B')` sets `tc.argsCodeText` to `'CHUNK_A_PLUS_B'` (entire concatenation, not a 5 KB tail of it).

**Warning signs:** Reducer test asserts `'CHUNK_A_PLUS_B'` but production reducer receives only the 5 KB tail of a 12 KB args blob → live panel shows truncated code. Or alternatively, `args_so_far` disappears from the wire and existing acceptance tests `test_args_so_far_bounded` (5 KB limit) and `test_total_bytes_monotonic` regress.

### Pitfall 5: WorkingBadge re-render thrash
**What goes wrong:** `<WorkingBadge>` placed inside MessageItem re-renders on every `tc.argsBytesStreamed` / `tc.argsCodeText` update during streaming — running the `brandPulse` 1.5s animation from scratch on each render. Visual stutter; battery drain.

**Why it happens:** MessageItem subscribes to its message, which is updated on every `onToolArgsProgress` call (per Plan 02 reducer). The Animation runs via CSS class, so adding/removing the class or remounting the element resets the animation.

**How to avoid:** WorkingBadge accepts `{ visible: boolean }` prop derived from `(activeTool || message.isPlanning) && !allDone` and renders the badge with `aria-hidden` toggled inside a stable outer wrapper (e.g., `<div className="animate-brandPulse">{ visible && <span>✦ Working</span> }</div>` — the wrapper class is stable; only the inner contents toggle). Alternatively, gate the animation class itself with `visible` and trust that React reconciliation preserves the DOM node so the CSS animation continues smoothly across content-update renders.

Belt-and-suspenders: wrap `<WorkingBadge>` in `React.memo` with a custom equality check on `(visible, label)` so reducer updates that don't change those props skip the badge re-render entirely.

**Warning signs:** Chrome DevTools Performance tab shows >60 paint events/second during a streaming response with the badge visible. The pulse animation visually "twitches" or "restarts" mid-stream.

### Pitfall 6: Step-list collapse vs iteration divider
**What goes wrong:** When 3+ completed steps collapse into one summary row, the iteration divider at `ToolCallPanel.tsx:705` (`tc.iteration !== prevToolIteration`) fires WRONG — either too many times (one per collapsed item) or zero times (because the summary row has no `iteration` field).

**Why it happens:** D-067-03 (Phase 067) renders the iteration divider above any tool item whose `iteration` differs from the prior tool item. If collapse merges 3 items spanning 2 iterations into 1 summary, the divider that would have fired between iter-N and iter-N+1 inside the collapsed group is lost. Conversely, if the summary row has `iteration=undefined`, the existing predicate `prevToolIteration !== undefined && tc.iteration !== prevToolIteration` returns `false` and skips the divider on the FIRST item AFTER the collapsed group.

**How to avoid:** Plan 03 spec for the collapse summary row:
- The summary row carries `iteration: max(iteration of collapsed items)` (i.e., the LAST iteration represented in the collapsed group).
- If the collapsed group spans MULTIPLE iterations (e.g., contains iter-1 final step + iter-2 first step + iter-2 second step), the summary row uses the EARLIEST iteration. Then the iteration divider above the FIRST item AFTER expansion (when chevron clicked) fires correctly.
- The "Step N+1" divider that would have appeared INSIDE the collapsed group is suppressed while collapsed. On expansion, the per-item rendering takes over and the divider fires correctly.
- Acceptance: 5 completed steps spanning iter-1 + iter-2 (e.g., 3 in iter-1, 2 in iter-2) + 1 active step in iter-3. Collapsed view shows 3 rows: 1 summary + 1 iteration-3 divider + 1 active step. Expanded view shows 6 tool rows + 2 iteration dividers (iter-1→iter-2 between items 3 and 4; iter-2→iter-3 between items 5 and 6).

**Warning signs:** Manual UAT shows a missing or duplicated iteration divider above the active step after step-list collapse. Vitest test for the collapse predicate doesn't assert iteration-divider count.

### Pitfall 7: `tool_args_progress` racing `tool_start`
**What goes wrong:** The LAST `tool_args_progress` event arrives AFTER `tool_start` (especially under load or with reordered async chunks). Reducer for `tool_start` runs first, clears `argsCodeText` to `undefined`, then `tool_args_progress` re-populates it — leaving stale code text rendering against a now-running tool.

**Why it happens:** Per `_drain_stream_with_close_on_cancel` semantics, the OpenAI path emits `tool_args_progress` synchronously per chunk inside `_on_chunk_openai`, and `tool_start` is emitted at the agent loop level AFTER the stream loop exits (per `threads.py:3258+` area which iterates `tool_calls_buffer` to fire `tool_start` for each completed call). Anthropic path emits `tool_start` at `content_block_stop` (anthropic_service.py:285-290) AFTER the last `input_json_delta`. Ordering is reliable per-stream, but SSE reordering on the wire isn't guaranteed if multiple events ship in one TCP packet.

**How to avoid:** Reducer `onToolStart` clears `argsCodeText` AND also stamps a `argsCodeFrozen: true` flag (or treats the transition from `preparing → running` status as a barrier in the `onToolArgsProgress` reducer). Subsequent `onToolArgsProgress` calls that target a tool already in `running` status are NO-OPS in `argsCodeText`. The existing reducer at `StreamsProvider.tsx:304` already filters on `tc.status === "preparing"` — the new `argsCodeText` write should ride the same gate. As long as `tc.status === "preparing"` precondition holds for the write, the race is closed structurally.

**Warning signs:** Vitest test simulates `onToolArgsProgress` AFTER `onToolStart` and observes `tc.argsCodeText` populated despite `tc.status === "running"`.

### Pitfall 8: OpenRouter upstream models that don't stream `function.arguments`
**What goes wrong:** Some OpenRouter-routed models (notably non-OpenAI-shaped upstreams like Gemini routed through OpenRouter, or certain open-source models) deliver tool_calls in a single non-streamed final chunk instead of progressive `delta.tool_calls[N].function.arguments` deltas. The OpenRouter path sees ZERO `tool_args_progress` events for these — the live panel never renders.

**Why it happens:** OpenRouter normalizes most providers into OpenAI-shaped chunks, but the depth of normalization varies per upstream. Some upstreams send `function.arguments` as a single complete JSON string at the end of streaming, not as incremental deltas.

**How to avoid:** Plan 01 spec accepts this gracefully — the absence of progressive chunks is NOT an error. The live panel simply doesn't render (just as it doesn't render for sub-5KB tool calls). UAT scope (per D-075.6-C2) explicitly picks an OpenRouter model that routes to an OpenAI-shaped upstream (`openai/gpt-4.1` is the SPEC-named target). UAT for non-OpenAI-shaped OpenRouter upstreams is OUT of scope; cross-provider parity is asserted ONLY for the 4 named representative routes.

**Warning signs:** UAT row for a Claude-via-OpenRouter or Gemini-via-OpenRouter model shows zero `tool_args_progress` events and panel not rendering — this is EXPECTED (acceptable) behavior, not a 075.6 failure. Document explicitly in VALIDATION.md.

## Open Questions

1. **Implementation choice: branch-inside vs split-callback for OpenAI native vs OpenRouter**
   - What we know: SPEC-locked decision says "no shared code path" but the file `openrouter_service.py` doesn't exist; both providers share `_on_chunk_openai` callback today.
   - What's unclear: planner's call between (a) branch on `active_provider_name` inside the callback with two boundary dicts, or (b) split into two named callbacks and dispatch at the `_drain_stream_with_close_on_cancel` site.
   - Recommendation: Plan 01 picks (a) — branch inside — because it preserves the single-source-of-truth chunk-parsing logic (Pitfall: silently diverging chunk parsers is worse than silently shared aggregators). The "independent" requirement is honored by two separate `_emit_boundary_*` dicts + a per-provider integration test asserting independence.

2. **Should `code_so_far` be capped at a max size?**
   - What we know: typical execute_code args are 10-40 KB; brand-new gallery prompt with extensive markdown could reach 80-120 KB.
   - What's unclear: SPEC doesn't cap. The reducer's longer-string-wins logic + the per-message Zustand store memory footprint scale linearly with code size.
   - Recommendation: NO cap in 075.6 (per SPEC out-of-scope "Backend buffering strategy redesign"). Document a re-open trigger if UAT surfaces >500 KB args text causing UI jank.

3. **Should the panel show line numbers / syntax highlighting?**
   - What we know: SPEC Req #4 says `<pre><code>` body showing `tc.argsCodeText`. No mention of highlighting.
   - What's unclear: Visual delight vs scope creep.
   - Recommendation: Plain `<pre><code>` for 075.6. The post-`tool_start` view (via existing `ExecuteCodeBlock` at `ToolCallPanel.tsx:720-721`) already has syntax highlighting; the live panel is for in-flight monitoring only and doesn't need parity.

## Landmines / Open Risks

### L1: `openrouter_service.py` is fictional (CRITICAL)
**Risk:** Plan 01 tasks reference a non-existent file. Implementation stalls; developer creates a misleading empty file just to satisfy the task description.
**Mitigation:** Plan 01 task descriptions name `backend/app/api/threads.py` as the OpenRouter emit site, with explicit comment "OpenRouter shares the OpenAI SDK chunk shape; independence is achieved via separate `_emit_boundary_openrouter` dict + branch on `active_provider_name` captured at L:2100." Optionally, Plan 01 may CREATE `openrouter_service.py` as a thin shim that wraps a callback factory function for the OpenRouter path — but this is architectural restructuring that exceeds 075.6 scope and should be a SEED for a future "OpenRouter service extraction" phase if needed.

### L2: Removing the `execute_code` skip silently changes Anthropic + Google semantics (HIGH)
**Risk:** Plan 01 also touches `anthropic_service.py:235-271` and `google_service.py:460-476` to add `code_so_far`. The existing Anthropic + Google emits already fire for `execute_code` (their D-075-11 calling_mode filter doesn't apply per the comment at `anthropic_service.py:240-242`). The OpenAI path's `execute_code` skip removal therefore brings OpenAI/OpenRouter UP to parity, not down. Sanity-check: VALIDATION.md Phase 075 baseline tests still pass with `code_so_far` added.
**Mitigation:** Plan 01 acceptance includes regression run of `backend/tests/integration/test_075_tool_args_progress.py` existing suite (6 tests). All must remain green. The new `code_so_far` assertions are additive.

### L3: Reducer race vs WR-02 reattach (MEDIUM)
**Risk:** Phase 075.2 WR-02 introduced reattach-replay of SSE events. If `tool_args_progress` replays AFTER the tool has transitioned to `running`, the new reducer's longer-string-wins update could overwrite the cached argsCodeText with stale data.
**Mitigation:** The existing `tc.status === "preparing"` filter at `StreamsProvider.tsx:304` already closes this — any reducer call targeting a non-preparing entry no-ops. Add explicit Vitest test for the post-tool_start no-op case (Wave 0 gap above).

### L4: WorkingBadge animation re-render thrash (MEDIUM)
**Risk:** `<WorkingBadge>` inside MessageItem re-renders on every reducer update during streaming; pulse animation visually restarts.
**Mitigation:** See Pitfall 5. Plan 03 wraps the badge in `React.memo` with custom equality on `(visible, label)`. Existing pattern proven at `MessageItem.tsx:136` where `animate-brandPulse` is applied conditionally to the Bot icon and runs smoothly.

### L5: Step-list collapse breaking iteration divider (MEDIUM)
**Risk:** D-067-03 iteration divider invariant collides with collapse summary row's missing `iteration` field.
**Mitigation:** See Pitfall 6. Summary row carries `iteration = min(iteration of collapsed items)`. Plan 03 acceptance test: 5 completed steps spanning iter-1 + iter-2 + 1 active step in iter-3 → expanded view has exactly 2 iteration dividers (between item 3-4 and 5-6).

### L6: Phase 067.5 D-3 guard line ref is stale (LOW)
**Risk:** SPEC.md §Constraints and CONTEXT.md §code_context both reference `useMessages.ts:572-590` for the guard, but the guard is at `StreamsProvider.tsx:692-707`. Plan tasks following the SPEC verbatim will look in the wrong file.
**Mitigation:** Plan 02 task names the CURRENT location explicitly. Existing test at `streamsProvider.test.tsx:249-321` already covers the invariant; no new guard test needed — only a new "075.6 reducer paths don't accidentally call clearThreadBucket" zero-call regression.

### L7: 12-page matplotlib gallery prompt may not reliably generate ≥10 KB args on all 4 providers (LOW)
**Risk:** UAT relies on a specific prompt to trigger the ≥5 KB cadence threshold. If a provider model generates concise code (e.g., GPT-4.1 in terse mode), `tool_args_progress` may not fire enough times to validate the panel.
**Mitigation:** SPEC Req #1 acceptance only requires ≥2 events (i.e., args reach 10 KB total). Gallery prompt is well-tested at 12 pages reaches ≥30 KB. UAT-1C / UAT-1D specify "OpenAI gpt-4.1 default" which historically generates 15-40 KB of args on this prompt per Phase 075.5 COMPARISON.md observations. If a UAT row generates <10 KB args, expand the prompt with "...and add detailed inline comments explaining each plot's purpose, axis labels, and color choices" to force verbosity.

### L8: OpenRouter upstream that doesn't stream `function.arguments` (LOW)
**Risk:** See Pitfall 8. Non-OpenAI-shaped upstream routes (Gemini-via-OpenRouter, Claude-via-OpenRouter) may deliver tool_calls non-progressively.
**Mitigation:** UAT-1D explicitly routes to `openai/gpt-4.1` (an OpenAI-shaped upstream). Non-OpenAI-shaped OpenRouter routes are documented as acceptable-no-panel in VALIDATION.md but out of UAT scope.
