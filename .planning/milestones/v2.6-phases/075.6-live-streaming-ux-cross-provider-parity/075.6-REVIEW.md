# Phase 075.6: Code Review Report

**Reviewed:** 2026-05-24
**Depth:** standard
**Files Reviewed:** 18
**Status:** issues_found

## Summary

Phase 075.6 ships a tightly-scoped feature set: an additive `code_so_far` field on
the `tool_args_progress` SSE event across all four providers (OpenAI, OpenRouter,
Anthropic, Google), a new `<ToolArgsLivePanel>` collapsible code-stream surface,
a `<WorkingBadge>` pinned top-of-turn indicator, and a step-list collapse for
runs with >=3 completed steps. The backend changes (threads.py + the two provider
adapters) are small (~68 net lines added), provider-uniform, and well-covered by
new integration tests asserting prefix-monotonic growth of `code_so_far` across
Anthropic, Google, and OpenAI/OpenRouter paths.

**No critical (security / data-loss / crash) issues were found in the changed
code.** The 4 Warnings cluster around:
1. A latent crash in the Google→threads.py SSE dispatch if a future fixture
   ever omits `code_so_far` (direct `[...]` dict access, not `.get(...)`).
2. A potentially-misleading `code_so_far` payload on the Google adapter — it
   carries the FULL JSON-encoded args dict each chunk (since Google delivers
   args atomically), so the "monotonic prefix growth" semantic intent isn't
   really exercised on the Google path the way it is on Anthropic/OpenAI. The
   integration test for Google synthesizes incremental events that don't
   match production behavior — this is documented but worth flagging.
3. A small reducer-shape concern in `<ToolArgsLivePanel>` auto-scroll behavior
   on collapse→expand transitions.
4. `ToolCallPanel.tsx` mixes a stray indentation pattern (line 563 has zero-
   indent declaration inside an indented block) that survives from a prior
   edit; pure cosmetic but contributes to the "messy" feel the user flagged.

The user's stated concern ("messy code for the last few phases") IS borne out
by the inventory: ToolCallPanel.tsx is 956 lines with 9 inline sub-components,
StreamsProvider.tsx is 1552 lines, and threads.py is 3755 lines with deep
nesting (the code dispatch path lives ~6-7 indentation levels deep). Several
Info items below catalog opportunities to extract sub-components or split
files, but none of the changes shipped in 075.6 directly worsened this. The
phase-tag-density inside reducer comments is high (Phase 067/068/075/075.4/
075.6 all referenced) but each comment is load-bearing — they document
verbatim-preservation invariants. Removing them risks breaking guard
predicates.

## Warnings

### WR-01: Google→threads.py dispatch will KeyError on `code_so_far` absent

**File:** `backend/app/api/threads.py:2007-2019`
**Issue:** The Google dispatch branch reads `_g_event["code_so_far"]` with
direct subscript:
```python
elif _etype == "tool_args_progress":
    await _emit(
        redis, run_id, "tool_args_progress",
        tool_index=_g_event["tool_index"],
        name=_g_event["name"],
        args_so_far=_g_event["args_so_far"],
        total_args_bytes_so_far=_g_event["total_args_bytes_so_far"],
        code_so_far=_g_event["code_so_far"],
    )
```
`google_service.stream_google` always populates `code_so_far` today (line 482),
so this is safe in production right now. BUT the same pattern in the Anthropic
branch (threads.py:1908-1915) uses the same direct subscript — and any future
patch to the adapter that conditionally omits the field would surface as a
`KeyError` inside the agent loop's `_on_chunk_google` closure, which would be
caught by the producer's broad `except` and surface to the user as a generic
"unexpected error" with the run already partially emitted. The fixture in
`test_075_tool_args_progress.py:301-311` ALWAYS sets `code_so_far` so the
test would never catch the regression.

The OpenAI branch is structurally different (constructed inline from
`tool_calls_buffer[idx]["arguments"]`, no dispatch dict access), so this only
applies to the Anthropic and Google pass-through dispatch branches.

**Severity rationale:** Warning, not Critical — today's adapter code always
emits the field, so no production crash; the risk is a quiet regression hiding
behind a fragile contract.

**Fix:** Use `.get()` with a safe default — `code_so_far` is additive (Plan 01
SPEC Req #1) so an absent value should not poison the dispatch:
```python
elif _etype == "tool_args_progress":
    await _emit(
        redis, run_id, "tool_args_progress",
        tool_index=_g_event["tool_index"],
        name=_g_event["name"],
        args_so_far=_g_event["args_so_far"],
        total_args_bytes_so_far=_g_event["total_args_bytes_so_far"],
        code_so_far=_g_event.get("code_so_far", ""),
    )
```
Apply the same to the Anthropic branch at threads.py:1914.

### WR-02: Google `code_so_far` semantic mismatch vs OpenAI/Anthropic

**File:** `backend/app/services/google_service.py:455-491`
**Issue:** The Google adapter emits `tool_args_progress` exactly once per
function_call part (since Google delivers `function_call.args` as a complete
dict on a single chunk — there is no streaming partial-JSON). The code
correctly notes this on line 423-424 ("the args dict may already be complete
on this single chunk since Google doesn't stream args character-by-character").

What `code_so_far` carries in this branch is `json.dumps(args, ensure_ascii=False)`
— the FULL JSON-encoded args dict. The "prefix-monotonic growth" semantic that
Anthropic + OpenAI satisfy (event N's `code_so_far` is a string prefix of event
N+1's, lengthening over time) is structurally not exercised here: Google
typically emits ONE progress event per tool_call with the complete args. The
test `test_google_path_emits_code_so_far` (test_075_tool_args_progress.py:899)
uses a synthetic fixture (`_google_events_with_big_args`) that injects fake
incremental boundaries to satisfy the >=2-events assertion — production
behavior emits only at the >=5KB boundary, which for short tool_args means
zero events.

This is documented behavior, not a bug. The concern is that the integration
test asserts an invariant the production code does NOT satisfy in practice for
the Google path. If a future maintainer relies on the test for confidence that
Gemini-3 streaming code generation will surface progress events in the UI,
they'll be surprised when real Google calls emit at most one progress event
per tool — and only when the args exceed 5KB on a single chunk.

The frontend reducer's longer-string-wins on `tc.argsCodeText` (StreamsProvider
line 316-319) is defensive against this — even one event with the full args
populates the panel correctly. But the "live code streaming" UX touted in
SPEC Req #1 is materially weaker on Google than on Anthropic/OpenAI.

**Severity rationale:** Warning, not Critical — feature degrades gracefully
(one big update vs many small ones) rather than breaking. Worth flagging
because the SPEC implies cross-provider parity that the implementation cannot
fully deliver given Google's wire format.

**Fix:** Two options:
1. **Documentation-only fix:** add a comment block at google_service.py:455
   noting that production Google calls emit at most one progress event per
   tool_call and that the integration test's incremental boundaries are
   synthetic. Update `075.6-VALIDATION.md` Google row to note the asymmetry.
2. **Behavior-only fix (more involved):** in the Google adapter, emit
   `tool_args_progress` for EVERY function_call part regardless of byte count
   (i.e., remove the 5KB boundary gate for Google specifically), so the
   `<ToolArgsLivePanel>` lights up even for sub-5KB Google tool calls. This
   makes the panel actually visible during Gemini code generation.

The phase shipped option (1) implicitly; consider option (2) as a follow-on
SEED for parity.

### WR-03: `<ToolArgsLivePanel>` auto-scroll fires on every content change including from collapsed→expanded transition

**File:** `frontend/src/components/chat/ToolArgsLivePanel.tsx:51-56`
**Issue:**
```typescript
const bodyRef = useRef<HTMLPreElement>(null)
useEffect(() => {
  if (bodyRef.current) {
    bodyRef.current.scrollTop = bodyRef.current.scrollHeight
  }
}, [contentText])
```
The effect runs whenever `contentText` changes. But:
1. When `expanded={false}`, `bodyRef.current` is `null` (the `<pre>` isn't
   mounted), so `if (bodyRef.current)` short-circuits and the scroll-to-bottom
   is skipped. That's fine.
2. When the user TOGGLES from collapsed → expanded WITHOUT a fresh
   `contentText` change, the effect does not re-run, so the panel mounts at
   `scrollTop=0`. If the content is >5KB and the user expected to see "where
   the stream is now," they'll instead see the top of the code — they have to
   manually scroll. Minor UX friction.

The fix is to also depend on `expanded` so the auto-scroll fires once on
expand. Alternative: scroll-into-view on mount in a separate effect.

**Severity rationale:** Warning, not Critical — usability regression on the
collapse→re-expand path. Easy to repro by clicking the chevron during a long
code stream.

**Fix:**
```typescript
useEffect(() => {
  if (bodyRef.current && expanded) {
    bodyRef.current.scrollTop = bodyRef.current.scrollHeight
  }
}, [contentText, expanded])
```

### IN-01: `code_so_far` shape varies across providers (raw partial JSON vs JSON-encoded dict)

**File:** `backend/app/services/anthropic_service.py:280`, `backend/app/services/google_service.py:482`, `backend/app/api/threads.py:2239`
**Issue:** What `code_so_far` carries differs across providers:
- **Anthropic:** raw partial JSON string accumulated from `input_json_delta`
  events (e.g., `{"code": "import matp` mid-stream). When the LLM is
  generating Python in `args.code`, the user sees JSON-escaped Python with
  escaped quotes / newlines (`\"` / `\n`).
- **Google:** `json.dumps(args, ensure_ascii=False)` — full JSON-encoded args
  dict.
- **OpenAI/OpenRouter:** raw streaming arguments string (same shape as
  Anthropic — JSON being typed character by character).

The `<ToolArgsLivePanel>` renders this verbatim in `<pre><code>`. For
`execute_code`, the user sees JSON syntax around the Python code, including
escaped quotes and newlines. The "Generating code…" header label oversells
this — users may expect actual Python source.

**Fix (deferred to follow-on phase):** in `<ToolArgsLivePanel>`, when
`title` mentions "code" and the body parses as `{"code": "..."}`, extract
the `code` field and display only the unescaped string. Or: rename the title
to "Generating arguments…" to set expectations. This is consistent with the
existing "non-execute_code tools also stream args" rationale.

### IN-07: Test `_anthropic_events_with_big_args` hardcodes specific chunk indexes for boundary emission

**File:** `backend/tests/integration/test_075_tool_args_progress.py:300`
**Issue:**
```python
if (i + 1) * chunk_size in (5120, 10240):
```
The condition uses a hardcoded set of byte totals (5120 and 10240) to decide
when to inject a synthetic `tool_args_progress` event. This couples the
fixture to specific values of `chunk_size=1024` and `n_chunks=12`. If a
future maintainer changes `n_chunks` to 8 or `chunk_size` to 2048, the
condition silently never matches and the test would assert "expected >=2
progress events; got 0".

**Fix:** compute the set from the boundary math:
```python
boundary = 5120
crossings = {b for b in range(boundary, n_chunks * chunk_size + 1, boundary)}
if (i + 1) * chunk_size in crossings:
    ...
```
Or, more directly, drive emission off the byte-counter modulo (matching the
production code):
```python
new_boundary = size // 5120
last_boundary = ...
if new_boundary > last_boundary:
    last_boundary = new_boundary
    yield {...}
```
The second form would mirror the production code structurally so the fixture
double-checks the production logic, not just the wire format.
