## Task 1 — the rendered-position arithmetic, DRIVEN RED against a real plant

Five cases, all pure-function arithmetic over hand-built fixtures. No DOM, no database — the
fixtures simulate the WIRE as `193.2-03`'s SQL now returns it.

### What is pinned

| Case | Property |
|---|---|
| 1 | `mergeLibrary(published, starters, drafts)` ids equal `[...starterIds, ...publishedIds, ...draftIds]`, **and each block's internal order is the order it arrived in** — the merge adds none of its own |
| 2 | `merged[SC3_STARTERS.length].id === newestPublished.id` |
| 3 | `filterLibrary(merged, {query:"", chips:[], projectId:null})` is **order-identical on the mapped ids**, and the index survives — the claim about the RENDERED list |
| 4 | **THE RESIDUAL** — the newest published row is NOT at index 0 while `starters.length > 0`, plus the counterfactual (an empty shelf puts it at index 0) |
| 5 | the rendered order is **BLOCK-WISE, never globally recency-sorted** |

### ⚠ Two fixture decisions that are the difference between an assertion and an inert one

Finding 3 in the prompt — `193.2-03` discovered a third of its own fence had been passing **before
any change**, because a bare `D-16` needle was already satisfied by a Phase 192.1 comment about a
different decision. Two fixture choices here exist specifically so that class cannot recur:

1. **The newest published row is named `Zebra quarterly board recap`, so it sorts LAST
   alphabetically** (`Annual…`, `Beta…`, `Missing…`, `Zebra…`). Under the alphabetical ordering that
   shipped *before* `193.2-03`, index `starters.length` would hold `id-p4`, not `id-p1`. **The
   premise is asserted in the case itself**, not left in a comment:
   ```ts
   const byName = [...SC3_PUBLISHED].sort((a, b) => a.name.localeCompare(b.name))
   expect(byName[byName.length - 1].id).toBe(SC3_NEWEST_PUBLISHED.id)
   expect(byName[0].id).not.toBe(SC3_NEWEST_PUBLISHED.id)
   ```
   An assertion that passed under both orderings would measure nothing.
2. **`id-d1` is the globally newest row in the whole fixture** — newer than the newest published
   row — and it still renders in the drafts block. A fixture whose blocks happened to agree with a
   global recency sort could not tell block-wise from globally-sorted.

**The index is the EXPRESSION `SC3_STARTERS.length`, never a literal `3`.** Verified: `grep -n "\[3\]"`
over the new cases returns nothing. A literal rots the moment the curated shelf grows by one —
which is exactly how `GSD_VITEST_MAX_WORKERS=4` rotted.

## Deviations from Plan

### 1. [Deviation, deliberate] the new blocks were appended at EOF, not spliced beside `describe("D-16 — the merge")`

The plan says *"join or sit beside the shipped `describe(\"D-16 — the merge\")` block; do not
restructure it"*. Splicing at line 181 would have shifted **~300 lines** of the file, invalidating
the citation `libraryFilter.test.ts:461-468` that **`rowIdentity.test.ts:96` names in prose** and
that this file's own shipped fence comment references. Appending at EOF satisfies the binding half
of the instruction (the shipped block is untouched — `git diff` shows `+229 / −0` and `+141 / −0`,
**zero deletions across both commits**) while preserving every line number a sibling module cites.

### 2. [Deviation, strengthening] TWO real plants were driven, not one

The plan specifies a plant in `libraryFilter.ts`. A second was driven in `WorkflowsPage.tsx`,
separately. Reason: the fence has two arms and the plan's single plant would have proved only one;
the unproved arm would have been the one with **no prior coverage anywhere**. This is the direct
lesson of `193.2-03`'s C-11 and 193.1's four unfirable fences.

### 3. [Addition, Rule 2] a fifth fence part — the SCOPE-2 guard

The canonical template has four parts. A fifth was added: the stripped `WorkflowsPage.tsx` must
still contain `mergeLibrary(published, starters, drafts)`, `filterLibrary(rows, { query, chips:
activeChips` and `visibleRows.map(`. Without it, a block-comment strip that survived its own
non-vacuity guard could still have removed the exact region where a sort would be written — the
fence would sweep a clean remnant and report green. This is a correctness requirement for the fence,
not a nicety.

### 4. [Structural note — the THIRD consecutive plan in this phase to report it] the `<verify>` blocks name the MAIN REPO

Both `<automated>` blocks say `cd "C:/Vibe Apps/Agentic RAG/frontend" && …` — the main repo, not
this worktree. Running them verbatim would have measured the wrong tree (the `#3099` absolute-path
hazard). **Every command was run against this worktree's root instead.** `193.2-02` §5 and
`193.2-03` §5 both recorded the same thing; it is a plan-template defect, not a per-plan slip.

### 5. [Out of scope, not fixed] the SC#3 fixtures do not re-verify the live row counts

The `109 / 28 / 78 / 3` figures come from `193.2-RESEARCH.md` §R2's live-DB measurement, which
RESEARCH itself dates as *"valid until ~7 days"*. This plan pins the **arithmetic** (index
`starters.length`), which is invariant to those counts; the specific *"4 of 109"* is a snapshot and
is labelled as such in the suite. No plan task authorises a DB read, and none was made.
