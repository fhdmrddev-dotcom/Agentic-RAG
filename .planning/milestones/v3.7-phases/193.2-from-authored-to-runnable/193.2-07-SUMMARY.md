## Is a migration needed? **NO — and here is the reason, not the assertion**

`ls supabase/migrations/ | wc -l` → **112** at the base commit and **112** at this plan's HEAD.

`definition` is a **JSONB column**. The new field is additive-optional with a `False` default, so a row
persisted before this commit `model_validate()`s clean and reads `False` — there is no column to add,
no default to backfill, no constraint to alter. This is the identical argument the two shipped
additive locks in the same class already make about themselves (`098` at `:526-533`, `143`'s `category`
at `:540-548`), and it is stated in the new field's own comment so a reader lands on it there.

**The round-trip was PROVED, including the jsonb string-scalar path**, rather than reasoned about — the
inherited finding warned that `definition->'phases'` silently returns nothing on 194 of 223 live rows
because the value is a JSON **string scalar**, so the read must go through `#>> '{}'` then parse. The
probe reproduced the whole encode/decode chain the DB layer actually uses
(`db/workflows.py:589` → `json.dumps(definition.model_dump(mode="json"))`), then the string-scalar
shape on disk, then the `#>> '{}'`-equivalent read:

| # | Property | Result |
|---|---|---|
| 1 | An OLD row (`{slug, version, name, phases}` only) validates | ✅ flag reads **`False`** |
| 2 | A dict CARRYING the new key validates (the autosave-PATCH shape) | ✅ **`True`** |
| 3 | `model_dump(mode="json")` EMITS the key | ✅ present, `True` |
| 4 | **jsonb string-scalar round trip** — `json.dumps` → string scalar → `json.loads(json.loads(...))` → `model_validate` | ✅ flag survives; **the whole re-dumped payload is equal to the original** |
| 5 | An unknown key still raises | ✅ `ValidationError`, `extra_forbidden` — **`extra="forbid"` was NOT relaxed** |
| 6 | The annotation is a plain `bool`, default `False` | ✅ not `bool \| None` — absence has ONE spelling (D-185-08) |
| 7 | `WF_SCHEMA["required"]` | ✅ **`['slug','version','name','phases']` — unchanged** |

⚠ **Row 7 carries a consequence the plan did not name, and it is recorded rather than left implicit:**
`WF_SCHEMA` is `WorkflowDefinition.model_json_schema()`, so adding the field means **the emit tool now
ADVERTISES the provenance flag to the model.** That is exactly why the payload-laundering rule is not
decoration — it is now a reachable attack surface rather than a hypothetical one. Both directions are
asserted, and one of them is defended by **nothing else in the suite** (see plant C).
