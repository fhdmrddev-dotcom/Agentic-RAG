## R2 — D-17/SC#3: where does a freshly-published row actually land in the RENDERED list?

### The rendering pipeline, end to end

**MEASURED** (all in `frontend/src/pages/WorkflowsPage.tsx` and `library/`):

```

GET /workflows/starters               →  starters    (:365)   ORDER BY name
GET /workflows/drafts                 →  drafts      (:379)   ORDER BY name
        │
        ▼  :446-449   rows = useMemo(() => mergeLibrary(published, starters, drafts), …)

        1. starters   (:145)

        3. drafts     (:147)
        │
        ▼  :458-461   visibleRows = filterLibrary(rows, {query, chips, projectId})

        │
        ▼  :1053-1055 ONE FLAT LIST — `visibleRows.map(row => <WorkflowCard …/>)`
```

- **`mergeLibrary` is pure concatenation.** `[...byId.values()]` on a `Map` returns insertion order. **MEASURED** at `libraryFilter.ts:142-148`.
- **`filterLibrary` never sorts.** **MEASURED** at `libraryFilter.ts:257-265`.

The T-7/P-4 fence at `rowIdentity.test.ts:167-181` is scoped to that module's own `source`/`code` strings and additionally requires ≥ 2 `NEVER THE ROW LIST` prose annotations. **MEASURED.**
- **No shelf grouping.** `WorkflowsPage.tsx:1045-1051` — *"ONE FLAT LIST (D-02) — No shelf, no section header, no per-shelf empty line."* **MEASURED.**

⇒ **Rendered order = `[all starters] ++ [all published] ++ [all drafts]`, each block in its server `ORDER BY`.**

### There IS a race, and it is benign — MEASURED (source) / INFERRED (timing)

| ASVS | Applies | Control here |
|---|---|---|
| V2 Authentication | no | No auth surface changes |
| V3 Session | no | — |
| **V4 Access Control** | **yes** | The three feeds run on a **service-role asyncpg pool that bypasses RLS**; the `WHERE` clause *is* the boundary (`db/workflows.py:524-525`, `:331-334`). **The `ORDER BY` change must leave every predicate byte-identical** — guarded by F-2 and the three shipped `*_predicate_is_byte_identical_*` tests |
| **V5 Input Validation** | **yes** | Pydantic `WorkflowDefinition` with `extra="forbid"` (`harness.py:41`) is the emit gate; the `ORDER BY` clauses are **static literals with no user input**, so no injection surface is added (`$N` binding is untouched) |
| V6 Cryptography | no | — |

### Concrete answers to the questions posed

**1. Can the rewritten refusal leak internal data into user-visible copy?**
- **Other users' data: no.** `_interactive_phase_failures(definition)` iterates only the definition the caller already owns; `get_definition` is owner-scoped (`db/workflows.py:361-386`), and `/validate` receives the body from the caller's own client.
- **Internal identifiers: yes, today — that is the defect.** The current literal ships `llm_human_input` and `ask_user`. F-3 turns their absence into a mechanical fence.
- **⚠ NEW surface the rewrite introduces: the phase `name` is model- or author-authored free text, and it now enters (a) a user-visible string, (b) an `aria-describedby` label, and (c) `harness_audit.metadata.named_failures`, which is persisted.** Three concrete controls a plan should carry:
  - **Length clamp.** `PhaseSpec.name` is unbounded `str | None`. A 10 KB name becomes a 10 KB refusal in a `text-[12px]` header span and a 10 KB audit row. Clamp to ~60–80 chars with an ellipsis.
  - **Whitespace/control-character collapse.** Newlines in a name would break the one-line shape on both surfaces.
  - **Rendering is already safe.** `blockedReason` reaches React as a text child (`PublishGauntlet.tsx:938`) and the tree contains **no** `dangerouslySetInnerHTML` on this path — verified. XSS is not the threat; length and honesty are.

**2. Do the list feeds carry a `user_id` scope, and does changing `ORDER BY` touch it?**
- **Yes, and no.** `list_published_workflows` binds `$1 = user_id` in both branches; `list_draft_workflows` is `WHERE status='draft' AND created_by=$1`; `list_starter_workflows` has no user scope **by design** (`is_system_global` published rows are world-readable under the mig-056 SELECT policy) and is not being changed anyway. `ORDER BY` is appended **after** the predicate and after the `$N` project-filter append (`db/workflows.py:312-316`) — it cannot widen visibility. F-2 is the guard that this stays true.
- ⚠ **`?scope=mine` is a QUERY PARAMETER, not a schema constraint** (`libraryFilter.ts:129-135` records this). The ordering change does not affect it, but a plan touching `list_published_workflows` should not be tempted to "simplify" the two branches into one.

**3. Is the AI-seeded `business_requirement` an injection surface?**
- **Rendering: already controlled.** `WorkflowSoul.tsx:22` records T-124-01 — `business_requirement` is rendered as text; the library search highlights it through `HighlightTitle` (`threadGroups.tsx:137`), which emits JSX text nodes and carries the T-156-01 control (`libraryFilter.ts:190-193`).
- **⚠ The genuinely new risk, and it is not an XSS one: this field is woven into the JUDGE's system prompt.** `publish_service.py:966-972` — `JUDGE_RUBRIC_CORE.format(business_requirement=(definition.business_requirement or "(not declared)"), …)`, and `validator_kinds.py:142-149` makes `answers_business_requirement` a graded criterion. **After this phase, a model authors the criterion that a model later grades the output against.** That is a self-grading loop introduced by SEED-163's fix.
  - **Format-string injection is NOT possible** — the value is *substituted into* `.format()`, never itself formatted, so `{}` in the requirement is inert. **MEASURED** from the call shape.
  - **The residual is a WEAKENED GATE, not code execution:** a trivially-satisfiable AI-authored requirement makes the judge stage easier to pass. **D-09 accepts this** — the visible AI mark plus the human pressing Publish is the checkpoint — but the acceptance should be *recorded in the plan's `<threat_model>` block*, not left implicit, and D-07's "durable requirement, never a copy of the describe text" is part of the mitigation: a durable requirement is a *harder* bar than a one-run instruction, not a softer one.
  - Suggested plan-level control: assert the seeded value is non-trivial (non-empty after trim, and not a byte-identical copy of `describe`) before stamping the provenance flag. This is D-07 made mechanical.

**4. Are these feeds served through the service-role pool that bypasses RLS (the q5r finding)?**
- **Yes — MEASURED.** All three take an `asyncpg.Pool` from `get_pg_pool()`. `db/workflows.py:477` and `:524-525` both state it in-source: *"the service role bypasses RLS so the WHERE is the boundary"*. This is the reason F-2 exists and the reason no plan may "tidy" a predicate while changing a sort key.

**5. Prompt-injection into the authoring prompt via `describe` / KB content?**
- Out of scope for this phase and already controlled: the grounded folder/tool/skill sets are computed **server-side** so KB content cannot whitelist itself (`workflow_authoring.py:174-178`, T-103-02-03), and `_check_grounding_fidelity` re-checks membership after the emit. The new clause adds no new data path. ⚠ It does add one more *instruction* a hostile `describe` could try to override — which is exactly why the gate stays (D-11) and why the fix is measured as a frequency reduction (D-08).
