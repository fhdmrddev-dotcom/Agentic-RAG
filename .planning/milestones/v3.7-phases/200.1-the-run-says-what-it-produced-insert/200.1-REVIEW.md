## Critical Issues

### CR-01: `phase_output_object` can raise `RecursionError` on deeply nested JSON text, violating its own "must never raise" contract

**File:** `backend/app/models/thread.py:49-124` (guard at 118-122)

**Issue:** The function's docblock states, in caps, "IT MUST NEVER RAISE (T-200.1-01)" because
it "reads model-influenced jsonb, and a parser that raises here 500s the run page for the owner
of a run whose model wrote something odd." The implementation only catches `ValueError` and
`TypeError`:

```python
if isinstance(raw, str):
    try:
        decoded = json.loads(raw)
    except (ValueError, TypeError):
        return None
    return decoded if isinstance(decoded, dict) else None
```

`json.loads` on a deeply nested JSON array or object raises `RecursionError`, which is a
`RuntimeError` subclass, not a `ValueError`/`TypeError`, and is not caught here. Verified
directly against this repo's Python:

```
$ python3 -c "
import json
s = '[' * 100000 + ']' * 100000
json.loads(s)
"
RecursionError: maximum recursion depth exceeded while decoding a JSON array from a unicode string
```

The trigger string is a few thousand `[` characters — small in bytes, well within anything a
model or a tool result could plausibly embed in an `output` dict field that gets
`json.dumps`-ed once by the (still-unfixed, by design) legacy path, or reflected from a
crafted document/tool response into a field that ends up nested inside the persisted `output`.
This is the exact "malformed input... deeply nested" case the phase's own test file claims to
rule out — `backend/tests/unit/test_200_1_phase_output_shape.py` states "No `pytest.raises`
anywhere in this file — the contract is that it CANNOT raise" but its parametrized malformed-
input list (`"not json"`, `json.dumps([1,2])`, `json.dumps("a string")`, `json.dumps(None)`,
`12`, `3.5`, `True`, `b"{}"`) never includes deep nesting, so the gap is untested as well as
unhandled.

**Blast radius:** `phase_output_object` (and `declared_phase_measure`, which calls it first)
is read on two call sites, one of them ungated: `backend/app/api/workflow_runs.py:742`
(canvas-gated `GET /workflow-runs/{id}`) and `backend/app/api/threads.py:1236`
(`for r in phase_rows: _count, _noun = declared_phase_measure(r["output"])`, inside the
UNGATED thread reconcile, with no enclosing `try`/`except` around that specific call). A single
poisoned `output` row 500s either read for every future request against that run/thread, not
just once.

**Fix:** Catch `RecursionError` alongside `ValueError`/`TypeError` (or bound decode depth):

```python
if isinstance(raw, str):
    try:
        decoded = json.loads(raw)
    except (ValueError, TypeError, RecursionError):
        return None
    return decoded if isinstance(decoded, dict) else None
```

Add a parametrized case for a deeply nested string (e.g. `"[" * 2000 + "]" * 2000`) to
`test_200_1_phase_output_shape.py`'s `test_never_raises_on_anything` so the "cannot raise"
claim is actually driven rather than asserted in prose.

### CR-02: A workflow that ends on a confirm/human-input step renders the machine's own question as "The answer this run wrote"

**File:** `frontend/src/pages/WorkflowRunPage.tsx:840-847` (root cause), interacting with
`backend/app/api/workflow_runs.py:742-748` (server ships the field with no phase-type
awareness) and the unchanged `backend/app/services/harness/human_input.py:310`
(`return {"text": prompt, "answer": answer, "tool_call_id": tool_call_id}` — every completed
`llm_human_input` phase's `output["text"]` is the PROMPT, never the answer).

**Issue:** `runAnswer` selects "the run's answer" as the last server-ordered row carrying a
non-empty `deliverable_text`, with no `phase_type` check:

```tsx
const runAnswer = useMemo<string | null>(() => {
  const rows = run?.phases ?? []
  for (let i = rows.length - 1; i >= 0; i -= 1) {
    const text = rows[i].deliverable_text
    if (typeof text === "string" && text.length > 0) return text
  }
  return null
}, [run])
```

The code's own docblock argues this is safe because "last wins": *"A `confirm` step carries
`text` too, and it is a QUESTION... A first-row-wins or a concatenating rule would print the
machine's question back at the person... Last wins, because the run's own ordering is the
argument."* That argument only holds when the confirm step is **followed by** a real answer.
It does not hold — and nothing in the code or the shipped tests considers — the case where the
confirm step **is** the last row carrying text, i.e. the workflow's terminal phase is the
confirm/approval gate itself.

This is not a hypothetical shape. The very same test file documents it as an **observed live
production run** on `doc_qa_scoped_098uat` (`WorkflowRunPage.test.tsx:2417-2419`): a 3-phase
run — `gather-contracts` (0) → `draft-letter` (1) → `final-check` (2, `llm_human_input`) — where
the confirm step is `phase_index` 2, the last phase. When that final confirm phase completes
(status flips from `active` to `completed`), its durable `output` is
`{"text": <prompt>, "answer": <user's reply>, "tool_call_id": ...}` (per
`human_input.py:310`, unchanged by this phase). The server's `deliverable_text` extraction at
`workflow_runs.py:744-748` reads `obj.get("text")` with no phase-type filter, so
`phases[2].deliverable_text` = the confirmation prompt (e.g. *"Does this draft answer your
question? Add any corrections."*), non-empty. Since it is the LAST row in `run.phases`, the
frontend's backward scan picks it before ever reaching `draft-letter`'s real answer at index 1.
The run page then renders, under the heading **"The answer this run wrote"**, the machine's own
question — not the letter the run actually drafted.

The shipped frontend test for this exact rule (`WorkflowRunPage.test.tsx:1780`, *"takes the
LAST answer when several rows carry one — a confirm's QUESTION never wins"*) only covers the
inverse ordering: confirm at index 0, real answer at index 1. It never places the confirm step
last, so it cannot catch this. The backend test
(`test_200_1_deliverable_text.py:410`, *"the server makes no judgement"*) explicitly defers the
selection rule to the client and also never exercises confirm-last.

The fix is not speculative — the field needed to exclude this case is already on the wire.
`WorkflowRunPhaseRead.phase_type` (set from `slug_to_type.get(row["slug"])`,
`workflow_runs.py:754`) is populated for every row today, including confirm/human-input ones,
so either side can filter on it cheaply.

**Fix (frontend, minimal):**

```tsx
const runAnswer = useMemo<string | null>(() => {
  const rows = run?.phases ?? []
  for (let i = rows.length - 1; i >= 0; i -= 1) {
    if (rows[i].phase_type === "llm_human_input") continue
    const text = rows[i].deliverable_text
    if (typeof text === "string" && text.length > 0) return text
  }
  return null
}, [run])
```

**Fix (backend, arguably the better home since it also protects `GET /threads/{id}/workflow`
if `deliverable_text` is ever widened there):** don't populate `deliverable_text` for a row
whose `slug_to_type` resolves to `"llm_human_input"` — that phase type's `output["text"]` is
defined, by its own executor, to be the prompt, never a deliverable.

Either way, add a test with the confirm step as the LAST row carrying text and assert the
region does not render the question (the mirror image of the already-shipped
"confirm-first" test).

### IN-01: `deliverable_text` ships whole and unclamped by deliberate, measured decision — flagged for visibility only

**File:** `backend/app/api/workflow_runs.py:175-186`, `frontend/src/lib/api.ts:4245-4267`

Not a defect: this is an explicit, data-backed decision (`D-200.1-02-B`, measured p95 15,431
chars / max 38,935 chars against the already-unbounded `definition` payload the same route
ships) rather than an oversight, and the two rejected alternatives (final-row-only,
silent-clamp) are reasoned through in the code. Noted here only because the review brief asked
that the absence of a bound be explicitly considered: nothing currently caps the size of a
single step's persisted `output["text"]`, so a future executor that stops bounding its own
generated text (unlike, e.g., `phase_types.py`'s `_EMIT_SPOTLIGHT_MAX_PASSAGE` truncation
elsewhere in that file) would inflate this response with no server-side backstop. No action
requested; re-open trigger is already named in the source (a LIST-of-runs consumer of this
field).
