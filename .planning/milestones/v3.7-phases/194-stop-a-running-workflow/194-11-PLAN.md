<objective>
SC#1's reachability half, and the fix for **the single most dangerous finding in this phase**.

`WorkflowLock.runId` carries **two different id types** depending on which code path last wrote it:
two of its five write sites store a `workflow_runs.id`, two store a producer `runs.run_id`, and its
own JSDoc asserts only the first. `DELETE /runs/{id}` accepts only the producer id, and `cancelRun`
**swallows 404**. A Stop resolved through the anchor id therefore **silently succeeds while doing
nothing** — precisely the dishonesty SC#2 exists to forbid, and a silent success is worse than a
visible failure in a phase about honesty.

The app has already solved this **twice**: `POST /runs/{id}/continue` (092-07, Facet C) and
`POST /runs/{id}/ask_user_response` (093, F10) both accept either id via an owner-scoped,
thread-anchor-confirmed fallback. **`DELETE /runs/{run_id}` is the third route on that prefix and
the only one without it.**

⚠ **But `cancel_run` cannot stop where `/continue` stops.** `_cancel_run_internals` keys `RUN_TASKS`
and `finalize_run_terminal` on the **producer** `runs.run_id`. Handing it a `workflow_runs.id`
yields: `RUN_TASKS.get(wf_id)` → miss → Step 3b → `finalize_run_terminal` updates **ZERO** `runs`
rows → **the live producer task is never cancelled while the API returns 204.** That is the same
silent success, moved server-side. **So the fallback must resolve FORWARD.**

Output: the dual-id fallback with forward resolution, and V-01 / V-02 / V-03 with F-10's two plants.
</objective>
