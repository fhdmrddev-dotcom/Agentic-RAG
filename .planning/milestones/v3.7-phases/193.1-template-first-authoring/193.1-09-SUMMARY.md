move, and the shared constant is what makes that impossible to do quietly. A companion case asserts
the non-empty bucket does **not** equal `SILENT`, so the shared value is not vacuously true.

## ⚠ Things I measured that contradict the plan, CONTEXT, the sketch or my own first reading

Every plan in this phase has found several. Here are mine, stated beside the claim rather than
silently.

### 1. The plan's corpus figures are CONFIRMED — and my own first re-measurement was the thing that was wrong

I re-measured the corpus rather than inheriting the numbers, and got **11 template-binding
definitions** and **0 rows with a non-empty input list** — flatly contradicting the plan's 74 and 3.
The plan was right. **194 of the 223 `definition` values are stored as JSON *string* scalars, not
objects** (`jsonb_typeof(definition)` → `string` 194 · `object` 29), so every `jsonb` path query and
every `@>` containment test silently reads only 29 rows. This is the trap already recorded in
project memory, re-encountered from the other direction.

Decoding the scalar first reproduces the plan **exactly**, and these are the figures the code and
the suite are written against:

| Measurement | Value |
|---|---|
| definitions | 223 |
| bind a template | **74** |
| slug ↔ placeholder overlap across all 74 | **0** |
| non-empty definition-level input list | **3**, every key `question` |
| any per-step output-key list | **0** |
| top slugs | `retrieve` 70 · `emit` 69 · `research` 12 · `summarize` 11 |
| emitters on `llm_emit` phases | `render_template` 78 · `render_docx` 1 |

**The consequence for this plan is unchanged: the degenerate case is the common case, and D-20's
degenerate-first design was not softened.**

### 2. ⚠ The 167-C action string renders NOWHERE — and the BUILD-CONTRACT's own "where" column is what is wrong

The contract's table says `reconcile.action` lives at *"rail — the button, both variants"*. **The
sketch's generated DOM says otherwise.** `body.generated.html:36` renders *"Reconcile the steps with
this template"* inside variant **B**'s stage; variant **C**'s block ends in a different button
reading **`Ask the AI to reconcile`** — which is an escalation **into 167-B**, the variant D-11
records as **REJECTED on size** ("a second model call and a diff surface is too much build for a
safety net"), with no seed planted.

So there is no honest home for a button on this surface: shipping C's own button would ship a door
onto rejected work, and shipping B's label would name an act this code does not perform (which is
precisely why D-27 reworded it). **`NAME_CHECK_ACTION` is therefore left exported and unrendered**,
with the reason in the component's docblock. It is deliberately *not* deleted — that would lower a
pinned count for a string a later phase may want.

This is a correction to the plan's implicit expectation that both ruled strings would render. The
heading (`NAME_CHECK_HEADING`) does render, and is the first line of the surface.

### 3. Two more things the approved sketch draws that this deliberately does not build

- **The lead sentence.** Variant C leads with *"Nothing in the steps names 4 of the 8 fields."* That
  sentence appears in **no** string table, so shipping it would be **inventing copy**, which D-27
  forbids — and on the measured common case it would read *"8 of the 8"*, which is the alarm the
  whole design exists to avoid.
- **Glyphs vs. labels.** The sketch draws ONE flat list where a `✓` / `○` / `◇` carries the bucket.
  The build uses the three **bucket label strings Plan 06 already shipped**
  (`BUCKET_PRODUCED` / `BUCKET_RUN_INPUT` / `BUCKET_NAMED_NOWHERE`), because a glyph legend is
  unreadable in the case that actually ships — eight rows sharing one glyph — and because the
  per-bucket cap D-11 requires needs a bucket to attach to.

### 4. `templateFirstVocabulary.ts` needed no change at all

It is listed in this plan's `files_modified`, and Task 2 says *"Add any still-missing 167-C strings"*.
**None were missing** — Plan 06 shipped all six 167-C ids plus the three bucket labels. Its diff is
**zero**, and its pinned count (21) is unmoved. Recorded so the empty diff does not later read as a
skipped step.

### 5. CONTEXT D-10's original bucket sources are confirmed wrong by direct measurement

D-10 says that at attach time the app has *"the draft's declared `output_keys`, phase slugs and
`input_keys`"*. D-20 already corrected this; my own measurement confirms it independently — **0 of
223 definitions carry any per-step output-key list**, and the per-step input-key list resolves to
`['topic', 'kickoff_prompt']` (i.e. the engine-known run inputs) on the one shape that has it, which
is a different question entirely. The classifier reads **neither**, and its suite asserts the module
does not name either token, in code or in prose, with a positive control.
