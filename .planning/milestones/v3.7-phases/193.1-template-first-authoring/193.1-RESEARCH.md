## Summary

**`template_placeholders` is NOT accepted-and-dropped. It reaches the LLM.** The mandate asked
whether the field is inert; it is not. `render_grounding_prompt`
(`backend/app/services/harness/grounding.py:576-577`) renders a
`### Template placeholder fields (if the workflow must fill a template)` section into the
authoring prompt on every `/generate` call, and the field flows there unbroken through four hops.
That is the good news and it makes the frontend half of SC#1/SC#2 cheap — `GenerateWorkflowBody`
already declares `template_placeholders?: string[]` (`frontend/src/lib/api.ts:3414`), so `onDraft`
adds one key to an object literal and nothing else on the wire changes.

**The finding that reshapes the phase is one level deeper, and neither CONTEXT nor the sketches saw
it.** `AUTHORING_SYSTEM_PROMPT` (`backend/app/services/workflow_authoring.py:82-91`) carries a rule
labelled **`DELIVERABLE RULE (CRITICAL — a wrong choice makes the workflow unpublishable)`** whose
entire condition is that grounding section: *"Use `llm_emit` with `emitter: 'render_template'`
**ONLY when the grounding explicitly lists template placeholders** … When NO template is listed in
the grounding, the final deliverable MUST be PLAIN TEXT / markdown … NEVER create a
`render_template` emit phase without a provided template — at run time it fails with
`no_template_bound` and the workflow can NEVER publish."* So sending the field does not merely show
the model eight names — **it flips the generator from the plain-text branch to the
`render_template` branch.** The draft that comes back is a draft that *requires* a bound template
to run (`phase_types.py:1263-1275`, verified). **That makes D-06's auto-bind load-bearing for
correctness, not only for AUTH-03's wording**: a draft aimed at a template that never got bound is
strictly worse than today's blind draft — today's is publishable and runs; that one is neither.

**And the three-bucket reconcile (D-10) rests on a schema field that does not exist.** CONTEXT D-10
states that at attach time the app has *"the placeholder keys, the draft's declared `output_keys`,
phase slugs and `input_keys`."* Measured: **`output_keys` is not a field on any of the seven phase
config models**, all of which subclass `_StrictBase` with `extra="forbid"`
(`backend/app/models/harness.py:38-41`), so writing one is a `ValidationError`; it survives only as
a defensive `getattr(p.config, "output_keys", [])` at `reachability.py:85` that has always returned
`[]`. **Zero of 223 live definitions carry it.** `input_keys` exists on `ProgrammaticPhaseConfig`
only (1 of 7 types, 3 phase configs live) and means keys a step *reads*, not run inputs. The real
run-input source is `WorkflowDefinition.inputs[].key` — **non-empty on 3 of 223 rows.** And across
all **74** template-binding definitions, **zero** phase slugs match any of the eight known
placeholder names: real slugs are verbs (`retrieve` ×70, `emit` ×69), placeholders are nouns
(`project_name`). On real data today the three buckets resolve to **0 / 0 / all** — which is the
exact degeneration D-10 calls a red line.

**Primary recommendation:** plan the wire and the bind as one indivisible unit (the generator's own
CRITICAL rule makes them inseparable), build the stateless read by putting `validate_upload` in
front of `parse_docx_template_variables` (that ordering is what resolves the `none`-vs-`unreadable`
ambiguity the pure parser cannot), and re-derive D-10's bucket sources from the real schema before
a single reconcile line is written.

## B. What `/generate` actually does with `template_placeholders` — the full trace

**This was the highest-value question in the mandate. Answer: it reaches the model, and it flips a
CRITICAL branch in the system prompt.**

### The four hops, each quoted with file:line

| # | Hop | Evidence |
|---|---|---|
| 1 | `GenerateRequest.template_placeholders: list[str] \| None = None` | `backend/app/api/workflows.py:1547` (class opens at **`:1539`**, not `:1541` as CONTEXT states — the docstring is at `:1540-1542`) |
| 2 | route → service, keyword-forwarded | `workflows.py:1583` — `template_placeholders=body.template_placeholders` inside `generate_workflow` (route `:1550-1585`) |
| 3 | `generate_workflow_definition` → `_assemble_grounding` → `assemble_grounding_bundle` | `workflow_authoring.py:242` (param), `:298` (forward), `:172`/`:197` (the thin delegate) → `grounding.py:345` |
| 4 | resolver → bundle → **prompt** | `grounding.py:507-513` resolves; `:288-289` returns a supplied list verbatim as `("ok")`; `:523` puts it on `GroundingBundle.placeholders`; **`render_grounding_prompt` at `:576-577` renders it** |

**The rendered section, verbatim from `grounding.py:576-577`:**

```python
"### Template placeholder fields (if the workflow must fill a template)\n"
f"{', '.join(bundle.placeholders) if bundle.placeholders else '(none)'}\n"
```

The grounded prompt is then the FIRST user message:
`base_messages = [{"role": "user", "content": grounded_prompt + "\n\n## The task to author\n" + describe}]`
(`workflow_authoring.py:301-303`).

### ⚠ The part that changes the plans — the DELIVERABLE RULE

`AUTHORING_SYSTEM_PROMPT` (`workflow_authoring.py:82-91`) is passed as `system_prompt` to
`forced_emit` (`:316`) and reads, verbatim:

> `DELIVERABLE RULE (CRITICAL — a wrong choice makes the workflow unpublishable):`
> - Use `llm_emit` with `emitter: 'render_template'` **ONLY when the grounding explicitly lists
>   template placeholders** (i.e. the user provided a .docx/.pptx/.xlsx template to fill). **When
>   NO template is listed in the grounding, the final deliverable MUST be PLAIN TEXT / markdown**:
>   end the workflow with an `llm_single` step … **NEVER create a `render_template` emit phase
>   without a provided template — at run time it fails with `no_template_bound` and the workflow
>   can NEVER publish.**

**Three consequences the plans must carry:**

1. **Today every `/generate` draft is instructed away from templates.** The frontend sends nothing,
   so the section always renders `(none)`, so the rule's second clause always fires. That is a
   sharper statement of `SEED-157` than "the AI drafts blind": the AI is *told there is no
   template* and *forbidden to build for one*.
2. **Sending the field is a branch flip, not a hint.** SC#2's proof should therefore look for the
   `render_template` `llm_emit` phase FIRST, and the placeholder-name overlap second. The former is
   binary and mechanical; the latter is the model's judgement.
3. **⚠ A `render_template` draft that never gets its template bound is UNPUBLISHABLE AND
   UNRUNNABLE.** Verified at the executor: `phase_types.py:1263-1275` — no bytes ⇒ audit
   `emit_failed`, substep `no_template_bound`, `_emit_failure_output("no_template_bound", …)`. **So
   D-06 is not "requirement-level nicety"; it is the thing that stops this phase shipping drafts
   that are worse than the ones it replaces.** CONTEXT's rule 2 ("the silent write needs an honest
   line") is right and now needs a stronger sentence: the failure is not "your template didn't
   attach", it is "your draft was built to fill a template that is not attached".

### Does anything downstream tie a phase's `output_keys` to the names?

**No — and it could not.** `output_keys` is not a schema field (§F). The only downstream consumer
of the placeholder list is the *run-time* emit path: `_exec_llm_emit` parses the BOUND template's
own bytes and builds the emit tool schema from them (`build_field_map_tool_schema`,
`template_render_service.py:115`), then `check_coverage` (`:416`) scores the emitted map against
them. **Nothing structurally connects the generated definition to the names.** The grounding text
is the entire mechanism. That is exactly why SC#2 insists on a real call.

### Which provider serves `/generate`

`resolve_authoring_model(settings)` → `settings.harness_authoring_model`;
`provider = get_model_capability(authoring_model)["provider"]`; the call goes through `forced_emit`
with `strict=False` (`workflow_authoring.py:259-266`, `:305-319`). **It is a single model resolved
from ONE app setting — not a per-request `model`/`provider` override.** See §"Validation
Architecture" for the roster ruling.

## C. The stateless read route (D-05) — a concrete recommendation

### Recommended shape

```
POST /workflows/template/placeholders
  multipart/form-data, single part named `file`
  dependencies=[Depends(require_visible("workflow_authoring"))]
  current_user: dict = Depends(get_current_user)
  → TemplatePlaceholdersResponse   # the SHIPPED model, reused verbatim
  201? no — 200. Nothing is created.
```

**Why `POST` and not `GET`:** the bytes are the input; a GET cannot carry them.
**Why this path:** it sits in the same `/workflows` router, twenty lines from its two siblings
(D-03), and the trailing `template/placeholders` reads as *the sibling of
`/{definition_id}/template/placeholders` that has no definition* — which is exactly what it is.
⚠ **Route-ordering check the plan must make:** FastAPI matches in declaration order and
`/{definition_id}/template` exists. A literal-segment path (`/template/placeholders`) declared
BEFORE the parameterised ones is unambiguous; declared after, `template` could be captured as a
`definition_id` — which is typed `UUID`, so it would 422 rather than mis-route. **Declare it before
the two `{definition_id}` template routes and assert the order in a test.**

### Parser directly, NOT through `resolve_template_placeholders` — with evidence

`resolve_template_placeholders` (`grounding.py:245-326`) is, minus its two guard clauses, entirely
a Storage round trip: build an `AssetRef`, `await resolve_template_source(...)`, take
`resolved["bytes"]`, then parse. With bytes already in hand, **only lines `:315-323` do any work**,
and reaching them requires manufacturing a fake `AssetRef` and a `pool`. Call
`parse_docx_template_variables(raw)` directly and mirror `:315-323`'s name assembly:

```python
parsed = parse_docx_template_variables(raw)
if not parsed:
    return TemplatePlaceholdersResponse(read="ok", placeholders=[])
names = list(parsed.get("scalars") or [])
for col_keys in (parsed.get("columns") or {}).values():
    names.extend(col_keys)
return TemplatePlaceholdersResponse(read="ok", placeholders=sorted(set(names)))
```

⚠ **The name assembly must be COPIED, not re-invented.** `:320-322` includes loop-column keys and
excludes `collections`; a route that returned `scalars` alone would show a different field list for
the same document than the bound-template door does, one screen apart. Consider lifting those four
lines into a shared helper in the same commit rather than duplicating — but if duplicated, pin the
two against each other with a test that runs one document through both doors.

### ⚠ The honesty problem the pure parser CANNOT solve, and the ordering that solves it

`parse_docx_template_variables` returns `None` for **two different facts**:
- `:390-391` — `except Exception: return None` (not a zip / corrupt / not a docx)
- `:407-408` — `if not scalars and not collections: return None` (a real docx with no tokens)

The shipped resolver collapses these: a successfully-downloaded but corrupt file returns
`("ok", [])` — i.e. **"we read it and found no fields"** about a document that never opened. That is
a latent instance of the exact lie `TEMPLATE_FIELDS_NONE` / `TEMPLATE_FIELDS_UNAVAILABLE` were
separated to prevent (`TemplateAttachSection.tsx:130-143`, which carries the **may never merge**
docblock). It is tolerable today because the bytes came from a Storage object that already passed
`validate_upload` at its own upload door.

**On the stateless route the file comes straight off the user's disk, so the ambiguity is live.**
The fix is ordering, and it is mechanical:

| Order | Outcome | UI arm |
|---|---|---|
| 1. declared part size > `MAX_FILE_SIZE` (before `.read()`) | `422` | error |
| 2. extension ∉ `_TEMPLATE_MIME_BY_EXT` | `422` | error |
| 3. `len(raw) == 0` or `> MAX_FILE_SIZE` | `422` | error |
| 4. `validate_upload(name, raw)` — ZIP EOCD + `[Content_Types].xml` + part marker | `422` | error |
| 5. parser returns `None` **after 4 passed** | `read="ok", placeholders=[]` | `none` (or `not-word` for pptx/xlsx) |
| 6. parser returns names | `read="ok", placeholders=[…]` | `fields` |

**With this ordering `read="unreadable"` is genuinely unreachable on this route** — a corrupt file
is a *refusal*, not a degraded read. Keep the field in the response anyway (shape parity with the
bound door), and **state the unreachability in the docblock the way `TemplatePlaceholdersResponse`
already states `"not_requested"`'s** (`workflows.py:1643-1644`) — that is this codebase's idiom.

### The security shape — what replaces the row gate

There is no row and no Storage object, so `_owned_slug_or_404` and the owner-prefix check have
nothing to attach to. What remains, and what each buys:

- **No filename is persisted or echoed**, so `WR-05`'s `safe_name` sanitisation is not needed —

**neither is a real `phase_type`** (the seven are `programmatic`, `llm_single`, `llm_agent`,

### What this does and does not mean

**It does NOT kill 167-C.** `reconcile.disclaim` already says *"a step may already gather a field
under a different name. We cannot know until the workflow runs."* — which is precisely, and
honestly, what the measurement shows. And SC#3's scenario is a template attached to a draft
generated BEFORE the template existed, i.e. one of the blind drafts; those are exactly the 74 rows
measured at zero overlap.

**It DOES mean four things the plans must settle rather than inherit:**

1. **Re-source the buckets.** *produced by a step* = phase **slugs** (`output_keys` contributes
   nothing and must not be presented as if it did). *supplied as a run input* =
   `definition.inputs[].key`, plus optionally the two engine-known keys
   `_KNOWN_RUN_INPUT_KEYS = {"kickoff_prompt", "topic"}` (`reachability.py:67`).
2. **Design for the degenerate case as the COMMON case**, not the edge. A panel whose realistic
   first render is *"8 named nowhere, 0 produced, 0 run inputs"* needs copy that survives it — and
   D-11's *"show all N"* cap will fire on essentially every real template.
3. **Do not let an empty bucket render as a claim.** This is 193's D-15/D-20 rule one surface later:
   an empty *produced* bucket must not read as *"no step produces anything"*.
4. **Consider whether the reconcile should also read post-193.1 drafts differently.** A draft
   generated WITH `template_placeholders` may name the fields (the whole point of §B). Whether it
   does is unmeasurable until SC#2 runs — **and it is a reason to sequence the reconcile AFTER the
   wire**, so its first real input is a template-aware draft rather than only the 74 blind ones.

### The jsonb string-scalar question — answered, and it is a backend-only concern

`jsonb_typeof(definition)`: **`string` 194 / `object` 29** at HEAD — Phase 193's finding CONFIRMED.
**It does NOT reach the frontend.** `_coerce_definition` (`workflows.py:105-125`) `json.loads` a
string, passes a dict through, and degrades anything else to `None`; every list/read route runs
values through it (`:360`, `:404`, `:1192`). So the page holds a real object and the reconcile can
read `meta`/`phases` client-side normally.

⚠ **The hazard is on the BACKEND**: any SQL this phase might add of the form
`definition->'phases'` or `definition->'inputs'` **silently returns zero rows on 194 of 223 rows**.
This phase should need no such query — but a plan that adds one must use `_coerce_definition`'s
posture, never raw jsonb path operators.

**Where the frontend actually holds them:** `BuilderDefinition`
(`WorkflowBuilderPage.tsx:478-486`) declares `slug/version/status/business_requirement/
project_folder_id/phases` **plus an index signature `[k: string]: unknown`**, and `DefinitionMeta`
(`builderStore.ts:178-180`) is a key-remapped mapped type that preserves it. **So `meta.inputs` and
`meta.assets` are present but UNTYPED** — the reconcile must read them defensively, exactly as
`setTemplateAsset` reads `s.meta.assets` (`builderStore.ts:700`, *"a non-array or absent `assets` is
treated as empty, never spread"*).

**What:** absence must never be readable as a claim (193's D-15/D-20; q5r's `(names, read)`).
**When:** every read this phase performs.
**The trap this phase introduces:** the underlying parser is a TWO-state function collapsing three

See §C.

### Pattern 2: Extraction before feature, baselines before the move

**What:** the cut ships in an early wave; characterization baselines are captured in a commit that
touches no source (188.1: *a baseline only proves something if it PREDATES the change*).
**When:** D-01/D-02. §D-2 names what to capture.

### Pattern 3: One writer on the definition JSONB

**What:** the backend mints descriptors and stops; the client writes `definition.assets[]` through
the existing draft save.
**Why:** 186-07's `If-Match` token. Stated in three shipped docblocks — `workflows.py:1597-1600`,
`api.ts:3543-3546`, `TemplateAttachSection.tsx:30-35`.
**Binds:** D-06's bind and D-12's reconcile. **A reconcile that edited the canvas would be a second
writer.**

### Pattern 4: Every user-visible string is an exported identifier

**What:** `GovernanceSection` / `ConnectionPicker` / `TemplateAttachSection` discipline — *"a
sentence living inline inside JSX is a sentence nobody can test for drift."*
⚠ **A runtime FUNCTION export beside a component is a `react-refresh/only-export-components` lint
ERROR** — measured, recorded at `TemplateAttachSection.tsx:164-169` and
`ExternalActionSection.tsx:77`. String constants are fine (`allowConstantExport`); helpers must stay
module-private and be driven through the rendered surface.

### Pattern 5: Fences are driven RED against a real plant, and their SCOPE is asserted first

**What:** non-vacuity BEFORE any negative — assert the source loaded, assert the needles are
non-empty, assert a planted literal IS caught, and only then assert the absence.
**Why:** the 192.1 E-2 finding — *a fence swept against the empty string passes green while
defending nothing*. Canonical example: `WorkflowDoorSwitch.test.tsx:515-550`.

### Anti-Patterns to Avoid

- **Injecting a `supabase` or `pool` dependency into the stateless route "for symmetry."** It needs
  neither, and adding one recreates the exact class q5r's docblock exists to warn about.
- **Presenting `output_keys` in the reconcile.** It is not a field. Any code path that reads it is
  reading `[]` forever.
- **Re-wording a server refusal on the client.** `TemplateAttachSection.tsx:41-48` states the rule:
  422/502 relay the server's own sentence; only 404 is worded client-side, because the server made
  not-found and not-yours deliberately indistinguishable.
- **Re-deriving sketch geometry by eye.** `SEED-155`. Consume `BUILD-CONTRACT.generated.md`.
- **Quoting a governed door word in a comment in any swept file.** The D-24(a) sweep is RAW.
- **Adding a conditional to protect SC#4.** D-08 — the absence of a read IS the absence of a gate.

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Reading a docx's placeholder names | A client-side JSZip parse, or a second server parser | `parse_docx_template_variables` | Handles run-split tokens (XML-tag stripping coalesces them), loop vars vs scalars vs `.value` columns, and headers/footers. | Validating an uploaded Office file | An extension check, or a 4-byte `PK` sniff | `validate_upload` | Validates the ZIP End-of-Central-Directory, `[Content_Types].xml`, and a per-extension part marker. A truncated file or a non-Office ZIP passes a magic sniff and fails this. |

## Common Pitfalls

### Pitfall 1: Sending `template_placeholders` and treating it as a hint
**What goes wrong:** the plan verifies "the names appear in the prompt" and stops. But the field
flips the `DELIVERABLE RULE` branch — the draft's SHAPE changes, not just its vocabulary.
**Why it happens:** the field is named after data, and its effect is on control flow inside a
prompt nobody reads at plan time.
**How to avoid:** SC#2's assertion is two-part — a `render_template` `llm_emit` phase EXISTS, and
the names are recognisable. Assert the first mechanically.
**Warning sign:** a plan that describes the change as "grounding the model better."

### Pitfall 2: Shipping the wire without the bind
**What goes wrong:** drafts come back aimed at a template that was never bound ⇒ `no_template_bound`
at run and unpublishable. **Strictly worse than today's blind draft.**
**Why it happens:** none of the four success criteria mention the fill (CONTEXT's own D-06 finding),
so a criteria-driven plan stops one step short — the exact trap Phase 193 fell into.
**How to avoid:** wire and bind in the same wave, with a test that a draft carrying a
`render_template` phase also carries a bound `assets[]` template by the time the row settles.
**Warning sign:** the wire and the bind appear in different waves with no dependency between them.

### Pitfall 3: The bind throwing synchronously out of `onDraftCreated`
**What goes wrong:** the persist loop catches it (`:657`), reports a failed save for a row that WAS
created, and a terminal refusal sets `haltedRef` — freezing autosave for the session.
**Why it happens:** `onDraftCreated` looks like a fire-and-forget notification and is not: it is
called inside the write's try block.
**How to avoid:** `void (async () => { … })()` with an internal catch. Test it with a throwing bind.
**Warning sign:** `onDraftCreated: (id) => { setDraftId(id); bindHeldTemplate(id) }` with no `void`
and no async boundary.

### Pitfall 4: Reddening a byte-exact pin by accident
**What goes wrong:** anything added INSIDE `<div class="flex flex-col items-center gap-3">` reds
`FLAG_OFF_DESCRIBE_MARKUP` (`describe.test.tsx:307`); anything that re-parents the drafted header
reds `FLAG_OFF_HEADER_MARKUP` (`header.test.tsx:382`).
**Why it happens:** the CTA region already hosts `StarterTemplatePicker`, so it *looks* like the
place additions go — but that one is gated on `canvasEnabled` and the pin is flag-OFF.
**How to avoid:** §D-2's placement rule. The approved splice is BEFORE the CTA group.
**Warning sign:** a plan that says "re-capture the describe pin" without a dated, reasoned
declaration. `header.test.tsx:377-381` states the standard explicitly: *any further re-capture is a
behaviour change to explain, not a test to update.*

### Pitfall 5: Two controls on one screen both called "template"
**What goes wrong:** sketch 165's `ctrl.label` is **"Filling in a template?"**. Shipped, ~2 inches
away inside the CTA region, is `STARTER_DOOR_LINE = "Not sure where to start? Start from a
template."` (`definitionOps.ts:857`) — which seeds the DESCRIBE BOX from a curated starter WORKFLOW
(151-C / Phase 187-14). Two meanings, one word, one screen.
**Why it happens — measured, not supposed:** **sketch 165 never rendered the starter picker.**
`grep -c "starter-door-trigger"` across `body.generated.html`, `index.html` and
`dom.generated.json` → **0**, and `"Not sure where to start"` appears nowhere in the sketch. The
mockup's dump was taken without it; the real screen has it, because
`app_settings.feature_visibility.visual_workflow_canvas.audience` is **`everyone`**, so
`canvasEnabled` is true.
**How to avoid:** decide the collision explicitly at plan time — reword one, separate them, or rule
it acceptable with a reason. **Do not discover it at UAT.**
**Warning sign:** a plan quoting `ctrl.label` verbatim with no mention of `STARTER_DOOR_LINE`.

### Pitfall 6: A reconcile that lists every field as a gap
**What goes wrong:** on real data the name check returns "all named nowhere" (§F), which is the
crying-wolf failure D-10 forbids — at maximum volume.
**Why it happens:** CONTEXT's bucket sources include a field that does not exist and one that means
something else.
**How to avoid:** re-source the buckets (§F), and design the copy for the degenerate case first.
**Warning sign:** a plan whose reconcile test fixture resembles sketch 167's (`retrieval` /
`llm_analysis` phase types, `output_keys` declared) rather than a real definition.

### Pitfall 7: A zip bomb through the new door
**What goes wrong:** a 10 MB OOXML container holding a multi-GB `word/document.xml`; the size gates
pass, `_validate_ooxml_container` only reads the central directory, and `zf.read(n)`
(`template_render_service.py:387`) decompresses it into RAM.
**Why it happens:** it is inherited from the shipped doors, so it looks pre-approved.
**How to avoid:** cap `sum(zi.file_size for zi in zf.infolist())` or bound the read.
**Warning sign:** the new route described as "the same gates as the upload door" with nothing added.

### Pitfall 8: Trusting `CLAUDE.md`'s vitest worker cap
**What goes wrong:** `GSD_VITEST_MAX_WORKERS=4` produced `failed 17 / 4 / 3` on ONE identical
commit at ~3600 cases; cap 2 produced 0 and 0. Every failure was a `STACK_TRACE_ERROR` timeout in an
untouched file.
**How to avoid:** `GSD_VITEST_MAX_WORKERS=2` in every plan. ⚠ `CLAUDE.md`'s rule table still says
`4` while the prose beneath it documents the rot.
**Warning sign:** a red suite the plan did not touch.
