<objective>
Route the harness's per-phase model through the shipped disabled-model resolver, with an honest notice.

Purpose: **D-10 is the half a picker structurally cannot fix.** Measured: `_resolve_enabled_model`
(`backend/app/services/run_model_resolution.py:35`, shipped in Phase 149 as D-149-10) exists **only** on
the chat `send_message` path. The harness's `_effective_model` (`phase_types.py:393-395`) hands the
per-phase string **straight to the provider with no check at all**. So a workflow authored before this
phase can still burn a run on a model an operator disabled, in complete silence — and no amount of
honesty in the authoring form changes that, because the author's browser is long gone by then.

⚠ **Without this plan the picker is honest and the runtime still is not.** That asymmetry is the reason
D-10 exists as a separate decision from D-01.

Output: one additive async helper, five call sites gaining `await` and a name, a user-visible sub-step,
a durable `policy_applied` receipt, and the frontend mapping that keeps the notice from rendering as the
word "Working".

**Parallel-safety:** every test in this plan stubs the harness ctx and patches
`load_all_model_overrides`; **no test creates a real `workflow_runs` row or writes any database row**,
which is what keeps this plan free of CLAUDE.md rule 4's serialisation constraint. RESEARCH.md §K.30
flags this plan as one of the two that could accidentally become DB-mutating — a `files_modified` check
cannot see a database write, so this sentence is the flag and the acceptance criteria enforce it.

**G-5, honoured by construction and said so rather than assumed.** `phase_types.py` measures
**38 commits / 15 phases / 2393 L** and G-5 FIRES; its ledger row reads *"extraction due — and
deliberately NOT taken in 190"*, with 190's clearance recorded as a test: *"190's whole change to this
file is one function … so it adds a call-out, not a concern."* This plan's change is **one function plus
