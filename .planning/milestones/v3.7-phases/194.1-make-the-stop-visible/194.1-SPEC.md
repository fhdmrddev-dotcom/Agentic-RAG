# Phase 194.1: Make the Stop Visible — Specification

**Created:** 2026-08-16
**Ambiguity score:** 0.14 (gate: ≤ 0.20)
**Requirements:** 7 locked
**Measured at:** HEAD `4bd5462a`, branch `develop` (the sketches were composed against `045a83dc`)

## Goal

A person can see the Stop they pressed: the press is acknowledged on screen within the same
frame, the surface `▶ Run workflow` lands on can stop the run it is showing, and a thread whose
workflow was stopped still says so after navigating away and back.

## Background

Phase 194 landed the **durable** half of Stop and verified it on seven live runs —
`workflow_runs.status = 'cancelled'`, the interrupted `workflow_phases` row cancelled, completed
phases untouched, `threads.active_workflow_run_id = NULL`, the producer `runs` row cancelled.
Phase 194's own UAT then found that **a person cannot perceive any of it.**

Measured at HEAD (`4bd5462a`), re-derived for this spec rather than inherited:

| The composer Stop has no pending state | `grep -c "isStopping" frontend/src/components/chat/MessageInput.tsx` | **0** |
| `Stopping…` is net-new copy | `grep -ril "stopping" frontend/src --include=*.ts{,x} \| grep -v test` | **1** file — `useDraftPersistence.ts:463`, a docblock on an unrelated subject |

⚠ **Two inherited claims are corrected here rather than repeated.**
(1) Sketch 168's provenance table states `grep -ri "stopping" frontend/src` returns **0** in
production source. It returns **1**. The conclusion — that `Stopping…` is new copy — survives
unchanged; the figure does not, and a plan quoting `0` would be quoting a number that is wrong.
(2) `BUG-260816-01` states "`WorkspacePanel.tsx:453` gates on `showTimeline`". **`:453` is where
the Stop row renders; `:354` is where the gate is defined.** They are different lines needing
different edits, and a plan aimed at `:453` would not find the gate.

**The design is already settled** by four baked sketches, and this phase does not re-open them:

| Sketch | Winner | Commitment |
|---|---|---|
| 168 | **B — the control yields** | On press the Stop control leaves its slot; `⊘ Stopping this run…` takes it. No disabled button, because no button — a double-press is impossible by construction. |
| 169 | **A — the title row** | Stop mounts in `WorkflowRunPage.tsx`'s title row opposite the seam link, gated on the component-level `isTerminal` already in scope. **Direct flip** — no sheet, no arm-to-confirm. |
| 170 | **B — the durable receipt** | The thread's reading derives from `workflow_runs`-by-thread. Not negotiable: the stop **NULLs** `threads.active_workflow_run_id`, so `RunSoul` and `RunSeam` both read from a place the stop has already emptied. |

The convergence in 171 is the reason this phase is small: **170-B and 171-C are one component with
two states**, not two features.

## Requirements

1. **The press is acknowledged**: pressing Stop replaces the control with a stopping reading in the
   same slot, on every mount that has one.
   - Current: `MessageInput.tsx:410-420`, `WorkspacePanel.tsx:453-469` and `ActiveRunsTray.tsx:126-134`
     each render `onClick={onStop}` with **no** `isStopping`, no spinner, no label change, no
     disabled-after-click. The button is byte-identical before and after the click.
   - Target: on press the control unmounts and `⊘ Stopping this run…` occupies its slot until a
     terminal event or the timeout in R2. All three shipped mounts plus R3's new one use **one**
     mechanism, per Phase 194 D-08 (*four mounts, ONE mechanism*).
   - Acceptance: for each of the four mounts, a test presses Stop and asserts (a) the stopping
     reading is present, (b) the Stop control is absent from the DOM, (c) pressing again is
     impossible because no control exists. The composer row's height/width is unchanged between
     the two states — asserted on the measured slot, not by eye.

2. **A lost stop climbs down**: a stop that never resolves returns a pressable control and says it
   was not confirmed.
   - Current: no timeout exists — there is no pending state to time out of.
   - Target: after **8 seconds** with no terminal event, the stopping reading is replaced by the
     Stop control again, accompanied by copy stating the stop was **not confirmed** and may be
     pressed again.
   - Acceptance: with a cancel mocked to never resolve, at t+8s the Stop control is pressable again
     and the copy asserts non-confirmation. At t+7s the stopping reading is still shown (the
     timeout does not fire early). A cancel that resolves at t+2s never shows the non-confirmation
     copy at all.

3. **The run surface can stop its own run**: `WorkflowRunPage.tsx` mounts a Stop in the title row.
   - Current: **0** matches for `onStop|stopThread|cancelRun|Stop` in the whole file. `▶ Run workflow`
     lands here, so the natural launch path has no working Stop.
   - Target: a Stop control in the title row opposite `Open the chat thread`, rendered only while
     the run is non-terminal (reading the `isTerminal` const already computed in that component),
     dispatching the same `stopThread(threadId)` as the other three mounts, with **no** confirmation
     guard.
   - Acceptance: the control renders on `● Running` and on `Paused for your answer`; it is **absent**
     on `✓ Complete`, `⊘ Cancelled` and `✕ Failed`. Pressing it issues exactly one cancel and shows
     R1's stopping reading. `grep -c "cancelRun(" WorkflowRunPage.tsx` is **0** — it goes through
     `stopThread`, per D-08.

4. **The thread remembers the stop**: returning to a stopped workflow's thread shows that it was
   stopped by the user, with what survived.
   - Current: the thread ends at the original prompt — indistinguishable from a run that never
     started or one that finished. The signal is not merely faint; it is absent.
   - Target: a run-anchored line at list level, derived from `workflow_runs` by thread, reading
     `⊘ Stopped by you · 2 of 3 steps · 2m 18s` with a seam to the run. Present on first paint after
     navigation, not only while streaming.
   - Acceptance: navigate away from a stopped workflow thread and back; the line is present and
     names the step count and elapsed time. It is derived from persisted state — a test with the
     live streaming store **empty** still renders it. It is absent on a thread whose workflow
     completed normally.

5. **One component, two states**: the same element carries the live kickoff reading, and no assistant
   node is rendered at harness kickoff.
   - Current: the harness kickoff mounts an optimistic assistant placeholder (`StreamsProvider.tsx:1926-1936`,
     `runStatus: "streaming"`, no `runId`), which is the surface the duplicate avatar is drawn on.
     The only always-present `RunStatusStrip` is inside `RunCard.tsx:336` — i.e. inside that very
     message. `MessageList.tsx:217`'s strip is gated on `showJumpToLive = !isPinned && isStreaming`,
     so it appears only after scrolling away.
   - Target: R4's line renders a live state (`◆ Starting workflow… · Step 2 of 3 · 2m 18s`) from
     kickoff onward, and the assistant message renders **only when it has content**. At harness
     kickoff there is no assistant node.
   - Acceptance: at kickoff on a harness thread, zero assistant nodes are in the transcript and the
     live line is present — so the artefact cannot be drawn twice **regardless of which of the three
     candidate mechanisms in `194-MEASUREMENTS.md` is live**. On a slow first-token mock there is no
     interval in which the transcript shows a prompt with no run instrument. ⚠ This does **not**
     repair the double-mount race; it removes the surface it rendered on. Stated as a boundary, not
     as a fix.

6. **A Stop the tray offers actually stops**: the run id resolves without requiring the thread to
   have been opened this session.
   - Current: `StreamsProvider.tsx:2411-2418` resolves `runId` **only** by scanning the `"chat"`
     surface bucket for a streaming assistant message. A tray row for a thread not opened this
     session finds nothing, hits the `!runId` guard at `:2454` and returns having cancelled nothing —
     the console line then states a cause (*"the run had not finished registering (the pre-stamp
     window) … press Stop again in a moment"*) that is **false** for both the tray case and the
     finished-run case, and its advice can never succeed.
   - Target: `stopThread` resolves the run id from a source that does not depend on the chat bucket
     being populated. The console string states only what has been established.
   - Acceptance: pressing Stop on a tray row for a thread never opened this session issues a real
     cancel (asserted on the network call, not on the absence of an error). The false-cause string
     is gone — `grep -c "press Stop again in a moment"` in production source is **0**. ⚠ The shipped
     re-open trigger at `StreamsProvider.tsx:2443-2452` (*"a second sighting of a Stop lost in the
     pre-stamp window"*) is **discharged** by this requirement and must be recorded as such rather
     than left reading as pending.

7. **A dead control is not offered**: the panel's Stop disappears when the run is over, and a pending
   approval does not outlive the stop.
   - Current: `WorkspacePanel.tsx:354` gates on `showTimeline = isHarness || phases.length > 0`, and
     phase rows **outlive the run** — so a finished run still renders "THIS RUN — Stop". Driven in
     194 UAT-03 on a completed run: no network request, `document.body.innerText` byte-identical
     (`diffLen: 0`). Separately, an approval card remains actionable after a stop while Postgres
     already reads `cancelled`.
   - Target: the panel's Stop renders only while the run is non-terminal. A pending approval is
     **retired with a sentence**, never silently removed.
   - Acceptance: on a completed run the panel shows no Stop control. Stopping a run waiting at an
     approval leaves the card visibly retired and non-actionable, with copy explaining it — a test
     asserts the card is still in the DOM (not removed) and that its action is not dispatchable.

## Boundaries

**In scope:**
- The pressed/stopping state on all four mounts, sharing one mechanism (R1) and one timeout (R2)
- A Stop control in `WorkflowRunPage.tsx`'s title row, direct flip (R3)
- One run-anchored, list-level component with a live state and a stopped state (R4 + R5)
- **One owner-scoped read** exposing `workflow_runs` by thread, on the existing `workflow_runs` router
- Suppression of the harness kickoff assistant placeholder (R5)
- The `stopThread` run-id resolution fix and the false console string (R6)
- The `showTimeline` gate fix at `WorkspacePanel.tsx:354` and the retired-approval sentence (R7)
- Folding `BUG-260816-01`, `BUG-260816-02`, `BUG-260709-01` (Direction A), `BUG-260610-01`
  (duplicate-avatar half) — **frontmatter flipped at discuss-phase, not claimed in prose**

**Out of scope:**
- **The Deep / plain-chat path** — the operator saw the duplicate avatar there too, but the
  mechanism is still UNMEASURED (`194-MEASUREMENTS.md`: three live candidates, no verdict) and
  Phase 174 D-14 holds Deep byte-identical. Acting on an unmeasured race on a surface this phase
  has no other business on is how a six-plan phase becomes fifteen. Deferred with the existing
  store-dump trigger, undischarged.
- **The double-mount race itself** — R5 removes the surface it drew on; it does not repair it. If
  the same race later reaches a content-bearing message the artefact returns.
- **The timer half of `BUG-260610-01`** (clock reads `28s` instead of `2m 18s` after nav-back) —
  adjacent and real, but it is a reseed-source defect in a different component, and `verified_closed_by`
  on the 128 fold was never established. Stays open with its own trigger.
- **The stopped-badge-on-nav family on Deep chat** — same family as R4, different surface, different
  source of truth (`runs`, not `workflow_runs` + `workflow_phases`). ⚠ Sketch 170 refers to this as
  `BUG-260710-01`; **no report with that id exists in `.planning/reported-bugs/`.** Whoever defers it
  must file it or correct the reference — a deferral pointing at a nonexistent id is invisible.
- **Any change to the durable half** — 194's writers, migration 119, the cancel composition. Verified
  on seven live runs; this phase reads that state, it does not write it.
- **A confirmation guard on any Stop** — settled by sketch 169: direct flip on all mounts.
- **New canvas glyph vocabulary** — `⊘` is shipped (174 D1/D2), lucide `Square` is the shipped
  control. `■` is `RunCard`'s cancelled **state** mark and is not a control; `⏹` is in no table.

## Constraints

- **Derived from persisted state, never from live streaming state** (174 D1). A live-only reading is
  precisely *why* `BUG-260610-01` is two months old. R4's acceptance test asserts this by rendering
  with the streaming store empty.
- **Four mounts, ONE mechanism** (194 D-08). Nothing may read `workflowLock?.runId` or call
  `cancelRun(` directly; `grep -cE "workflowLock\??\.runId|cancelRun\("` stays **0** in the mount
  components. Four mounts that acknowledge a press four different ways satisfies D-08 and still
  leaves the user confused.
- **R4 is a narrow amendment to Phase 194 D-14, not a repudiation.** The receipt stays thin — one
  line, no spine. What changes is D-14's clause that *"nothing here needs a new source of truth"*.
  Record the reversal; do not quietly overwrite D-14.
- **A pending approval is retired with a sentence, never removed.** A card that vanishes mid-read is
  its own small dishonesty. This is a rule across all variants, not a design choice.
- **No net-new canvas glyph.** `icon-convention.md` §4's table is `⛨ 🔒 ⤳ ＋ ✕ ↶ ↷ ◆`.
- **The stop must not read as though nothing survived** (194 D-13). Completed phases survive a stop;
  every reading carries the step count in the same sentence as the word.
- **G-5 fires on four files and a refactor recommendation is owed FIRST at discuss-phase**, before
  the feature: `RunCard.tsx` (inherits `21 / 9 / 608`), `WorkspacePanel.tsx` (inherits `14 / 9 / 580`),
  `MessageInput.tsx`, and — ⚠ **absent from the ledger entirely** — `MessageList.tsx`, measured by
  sketch 171 at **18 commits / ≥6 phases / 234 lines** against a threshold of 3. A guardrail cannot
  see what is absent from its list; add the row at discuss-phase.
- **Efficiency directive (operator, at spec time).** This phase is scoped to be built in a **single
  digit number of plans**. The convergence of 170-B and 171-C into one component is what makes that
  achievable — a plan set that treats them as two features has mis-read this spec. Recent phases ran
  to 11–29 plans; that is the failure mode to avoid, without trading away RED-first fences or
  cross-provider honesty.

## Acceptance Criteria

- [ ] Pressing Stop on each of the four mounts replaces the control with `⊘ Stopping this run…` in
      the same slot; the control is absent from the DOM while stopping
- [ ] The composer row's measured height and width are identical in the resting and stopping states
- [ ] A cancel that never resolves restores a pressable Stop at 8s with copy stating the stop was not
      confirmed; at 7s it has not fired; a 2s cancel never shows that copy
- [ ] `WorkflowRunPage.tsx` renders a Stop on `● Running` and `Paused for your answer`, and **not** on
      `✓ Complete` / `⊘ Cancelled` / `✕ Failed`
- [ ] `grep -cE "workflowLock\??\.runId|cancelRun\("` is **0** in all four mount components
- [ ] Returning to a stopped workflow thread renders the stopped line with step count and elapsed
      time, with the live streaming store empty
- [ ] The stopped line is absent on a thread whose workflow completed normally
- [ ] At harness kickoff, zero assistant nodes are in the transcript and the live run line is present
- [ ] On a slow-first-token mock there is no interval showing a prompt with no run instrument
- [ ] Stop on a tray row for a thread never opened this session issues a real cancel (asserted on the
      network call)
- [ ] `grep -c "press Stop again in a moment"` in production source is **0**
- [ ] A completed run shows no Stop control in the workspace panel
- [ ] Stopping a run waiting at an approval leaves the card present, visibly retired, and its action
      not dispatchable
- [ ] **G-4 rows driven by the operator at verification**, each with its named failure shape:
      (1) **Press** — Stop in the composer on a live run; fails if the button sits inert or the row twitches
      (2) **Canvas** — launch via `▶ Run workflow`, stop from the run surface without navigating; fails if
          there is no control, or the control persists after the run is terminal
      (3) **Return** — stop, navigate away, come back; fails if the thread ends at the original prompt
- [ ] All four claimed bug reports have `status: folded` and `folded_into: 194.1` in their
      **frontmatter** — prose claiming a fold the frontmatter does not record is worse than no claim
