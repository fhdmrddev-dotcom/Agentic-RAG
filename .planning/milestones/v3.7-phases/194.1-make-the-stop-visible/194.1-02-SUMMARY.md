## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] Two shipped mock fixtures were stale against the widened SELECTs**

- **Found during:** Task 2, and **found only because I ran a suite the plan's verification block
  does not name.** `<verification>` specifies `tests/unit`; `test_thread_workflow_endpoint.py`
  lives in `tests/` and would have been missed entirely by the stated gate.
- **Issue:** `KeyError: 'status'` / `KeyError: 'created_at'`. The conftest mocked pool answers with
  fixture dicts regardless of SQL, so a widened SELECT leaves the fixtures short of columns.
- **Proved it was MINE, not pre-existing** rather than assuming: ran the suite against
  `git checkout 86471c13 -- <the two files>` → **1 failed / 8 passed**; with my change →
  **3 failed / 6 passed**. Two genuine regressions.
- **Fix:** widened both fixtures. **Production code keeps STRICT `Record["key"]` access** — a
  `.get()` fallback would silently return `None` if someone later narrowed the SELECT, which is
  exactly the class of bug this plan's fences exist to catch. The mock was stale; the code was not.
- **Files:** `backend/tests/test_thread_workflow_endpoint.py` · **Commit:** `e3acb59d`

**2. [Rule 1 — Bug] The shipped pure-read fence was a SUBSTRING test and red on a COLUMN NAME**

⚠ **The most interesting finding of this plan.** Three loops asserted
`"UPDATE" not in sql.upper()`. My new column `updated_at` uppercases to **`UPDATED_AT`, which
literally contains `UPDATE`** — so a pure `SELECT` tripped the "this endpoint must never write"
fence.

- **The endpoint is still a pure read.** SELECTing a column named `updated_at` writes nothing.
  **The fence was mis-scoped, never the code** — and per BASELINE §9's standing rule, the correct
  response is to fix the fence, not to rename a database column to appease a regex.
- **This is the project's recurring lesson in a new place:** *a raw sweep reds on the thing it
  sweeps for* (192-05's `title=` fence had to be AST-parsed for exactly this reason;
  BASELINE §9 Trap 2 records the same shape in `PendingAskCard`).
- **Fix:** one `_assert_pure_read()` helper matching UPDATE/INSERT/DELETE as **whole words**.
  All three call sites now share it.
- **PROVED NOT WEAKER, not asserted:** a table-driven check confirmed `\b(UPDATE|INSERT|DELETE)\b`
  still catches `UPDATE … SET`, `INSERT INTO`, `DELETE FROM` **and a CTE-prefixed
  `WITH x AS (SELECT 1) UPDATE threads SET a=1`**, while no longer firing on
  `updated_at` / `inserted_at` / `deleted_at`. Then **driven RED in situ**: a real
  `UPDATE workflow_runs SET status=status;` planted in production ARM B produced
  `AssertionError: GET reconcile must not write; saw 'UPDATE'`.
- **Scope note:** all three instances were corrected, not just the one that reddened. A
  half-corrected fence would red the next widening one site at a time.
- **Files:** `backend/tests/test_thread_workflow_endpoint.py` · **Commit:** `e3acb59d`

## ⚠ The cross-user case does NOT isolate its clause — and that was MEASURED, not guessed

The plan required this be stated honestly if isolation proved impossible. **It did, and here is the
evidence rather than the claim.**

In this mocked-pool shape the conftest Supabase builder is a `MagicMock` whose `.eq()` returns
itself and whose `.execute()` returns `mock_execute_result.data` **regardless of any filter**. So
deleting `.eq("user_id", …)` from production source changes the mock's answer by exactly nothing.

**Driven, not reasoned:** plant **P4** deleted the ownership clause from `get_thread_workflow`
(scoped to that route — the identical 3-line idiom appears **3×** in `threads.py`, and my `== 1`
guard correctly refused to plant blindly the first time). Result:

- `test_another_accounts_thread_answers_404_and_never_a_run_row` → **GREEN under the plant.**
- `test_the_ownership_clause_is_applied_on_the_same_query_as_the_id` → **RED.**

That asymmetry is exactly 194-11's recorded finding — *one clause tested in a world where a sibling
clause also holds has never been tested* — reproduced here on this route. The coverage is therefore
split and each half is labelled in the module docblock for what it actually proves. **The real
access boundary is RLS plus the shipped ownership gate; a mocked unit test cannot stand in for
either**, and the docblock says so, so nobody later reads these cases as if it could.

What the 404 case *does* prove about this plan: **body parity, not status parity** — the response
body is exactly `{"detail": "Thread not found"}` and none of the three new field names (nor
`last_workflow_run_id`, nor a status value) appears anywhere in it.
