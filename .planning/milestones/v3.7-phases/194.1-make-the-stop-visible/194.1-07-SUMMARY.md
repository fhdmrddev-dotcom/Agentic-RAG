## Deviations from Plan

### 1. [Decision] The pin bump is in its own commit, not literally the same one as its cases

The plan's task-4 acceptance says *"The pin bump is in the SAME commit as the cases that raised
it"*, while the orchestrator's success criteria also require *"Each task committed
individually"*. The two conflict for tasks 2/3 versus 4, because task 3 adds cases too — so the
pin can only be measured after both.

**Committed individually, and the property the same-commit rule protects was MEASURED to hold
rather than argued:** the gate's contract is *no per-file DECREASE*, so cases-without-a-bump is
the SAFE direction (it is exactly the state `WorkspacePanel.test.tsx` sat in for twelve cases).
Runs 1 and 2 above are the tree at commit `77b51936` — cases in, pin still 89 — and both read
**`count gate OK`**. **At no commit in this plan did a pin exceed its actual**, which is the
dangerous direction the rule exists to prevent. All four commits land in one wave and merge
together.

### 2. [Rule 3 — blocking] The suite's StreamsProvider mock had to be extended in task 1

`WorkflowRunPage.test.tsx` mocks `@/providers/StreamsProvider` with five exports.
`StopControl` imports **`useStoppingForThread`** and **`useStopNotConfirmedForThread`** from
that module and dispatches through `useStreamActions().stopThread` — none of which the mock
had. **A module mock that omits an export the component under test imports does not fail
informatively:** the import resolves to `undefined` and the render dies inside React, taking
all 89 shipped cases with it. Measured, not predicted.

Task 2 owns that file; the three additions landed in task 1's commit because without them task
1's own verification could not run.

### 3. [Rule 1] `expectBandSentence` sampled where it had to wait — see the section above

The fix is in the helper's own docblock, not only here, and P1 was re-driven afterwards.

### 4. [Correction] Plan 01's `toBe(1047)` was already red at this base — see the section above

Not caused by this plan; inherited from plan 06 and invisible because the suite is ungated.
Fixed as part of the supersession the plan required anyway.

### 5. [Honest scope] What the press case proves, and what it does not

The plan asks that *"after the press the control is ABSENT and the stopping reading is
present"*. This suite mocks the provider module away, so there is no store to drive: the
stopping flag is flipped from inside the `stopThread` spy and a re-render is forced. **The case
is labelled in its own docblock as proving *"the page renders the shared slot's stopping arm in
its title row"* — not *"pressing flips the store"* (plan 03's property, pinned in
`StreamsProvider.stopping.test.ts`) and not *"stopping removes the control"* (plan 04's, pinned
in `StopControl.test.tsx`).** Three arms, each pinned where it lives; none faked here to stand
in for another.

⚠ **One measured trap on the way:** `rerender(el)` with a hoisted, referentially-identical
element renders NOTHING — React bails out — so the case first reported the control still
present while the flag was already `true`. A test that cannot re-render cannot observe a swap.
Recorded inline.

### 6. [Measurement] `getByText` on a band sentence cannot work on this surface

The page renders `band.sentence` **twice** by design (header + the `sr-only` polite band), and
**three** times on `failed` (+ the `role="alert"` region gated on
`ALERTING_STATUSES = {failed, cap_paused}`). The helper takes the count as a parameter and
asserts it, so the duplication cannot silently become a triplication — rather than reaching for
`getAllByText(...)[0]`, which would assert nothing about the second home.
