## Summary

Five findings change the plan set. Four of them make it **smaller**.

1. **The composer Stop does NOT go through `stopThread`.** It goes through `stopStream`
   (`ChatArea.tsx:361 onStop={stopStreaming}` → `useMessages.ts:118 stopStreaming: actions.stopStream`).
   `stopStream` (`StreamsProvider.tsx:2373-2404`) and `stopThread` (`:2411-2474`) are **byte-mirror
   resolvers**, and the false-cause string exists **TWICE** (`:2394` and `:2457`) — so the SPEC's
   `grep -c "press Stop again in a moment" == 0` acceptance is **not satisfiable by editing
   `stopThread` alone**. Routing `<StopControl>` at `stopThread(threadId)` retires the second
   resolver for free.
2. **R6 needs NO backend work.** `GET /threads/{id}/workflow` already returns
   `last_workflow_run_id` — the anchor-then-latest id that **survives the anchor NULL**
   (`models/thread.py:101-115`; `api/threads.py:1264-1270`). `DELETE /runs/{id}` accepts a
   `workflow_runs.id` (`api/runs.py:1212-1253`). The chain is shipped end to end.
3. **D-09's premise is measurably false, and the alternative also dodges a trap CONTEXT never
   names.** `/workflow-runs/{id}` is **canvas-gated** (`middleware/canvas_gate.py:85-93`), and
   `visual_workflow_canvas` ships **`"off"`** (`models/user_settings.py:1203`). A chat-surface
   receipt fed by that router is **invisible whenever the canvas is off**. `GET /threads/{id}/workflow`
   is **not** gated (`api/threads.py:1036`) and already resolves the same run — it is missing only
   `status` + two timestamps.
4. **R5's gate as worded silences two shipped honesty paths.** `sendMessage`'s 403 kill-switch amber
   notice (`:2260-2264`) and the network-failure `runStatus:"failed"` flip (`:2289-2293`) both write
   onto the placeholder R5 deletes. The 403 is *the harness path* (`workflow_kickoff.py:200`).
5. **The "measured slot" fence cannot be geometric.** jsdom returns 0 for all layout, and **no test
   in this tree measures real geometry** — the only `getBoundingClientRect` reference is a *negative*
   source fence (`PhaseNodeCard.test.tsx:523-527`).

**Primary recommendation:** eight plans, four waves, backend reduced to **one additive widening of a
shipped pure read** — no new route, no `CANVAS_GATED_PATHS` edit, no migration.

## Q1 — the store slice (D-05 / D-06 / D-07)

**Store technology.** Zustand v5 with `subscribeWithSelector`:
`streamsStore.ts:330` — `export const useStreamsStore = create<StreamsState>()(subscribeWithSelector(() => ({…})))`.
Not context, not `useSyncExternalStore` by hand (zustand uses it internally).

**The shipped `streamingThreads` slice — the exact idiom to mirror.**

| Property | Evidence |
|---|---|
| Type | `streamingThreads: Set<string>` — `streamsStore.ts:115` (declared), `:345` (seeded `new Set<string>()`) |
| Written by | **immutable replace only**, never `.add` in place: `new Set(s.streamingThreads).add(threadId)` (`StreamsProvider.tsx:1592`, `:1944`, `:2108`); delete arm `const next = new Set(...); next.delete(...); return { streamingThreads: next }` (`:1599-1602`, `:2307-2311`, `:3007-3010`, `:3222-3225`) |
| Selector | `export const useStreamingThreadIds = (): Set<string> => useStreamsStore((s) => s.streamingThreads)` — `:3614-3615` |
| Per-thread selector | `export const useStreamingForThread = (threadId: string \| null): boolean => useStreamsStore((s) => (threadId ? s.streamingThreads.has(threadId) : false))` — `:3605-3606` |

**Re-render risk — answered, not assumed.** `:3610-3613` records the measured property: *"Selecting
`streamingThreads` directly is reference-stable across token deltas (the Set is reassigned ONLY on
stream start/stop — tokens never touch it)."* A `stoppingThreads` sibling inherits that property by
construction **provided it is reassigned only on press / clear / timeout**. A boolean selector
(`useStoppingForThread`) returns a primitive, so Zustand's default `Object.is` equality re-renders
only the subscribing mount whose value flipped. **Never** return a fresh object/array from the
selector (`:3293` records the churn hazard).

**Where the timer must live: the PROVIDER, in a ref — not in the store.**
`streamsStore.ts:22-27` is explicit: *"AbortController must NOT live in Zustand state (not
serializable, identity churn breaks selector memoization). The provider holds the actual
`Map<runId, AbortController>` in a ref; this Set is the pure-data mirror."* The shipped pair is
`subscriptionsRef` (`StreamsProvider.tsx:1178`) ↔ `subscriptionsByThread` (`streamsStore.ts:136`).

⇒ **`stopTimersRef = useRef<Map<string, number>>(new Map())`** beside `lastEventAtRef`
(`StreamsProvider.tsx:1214`), holding `window.setTimeout` handles; **`stoppingThreads: Set<string>`**
in the store as the pure-data mirror.

**How a provider-owned timer survives component unmount.** `<StreamsProvider>` is mounted at
**`App.tsx:253`**, wrapping everything down to `:313` — above the page switch. A mount unmounting
(navigating away from the composer, collapsing the panel) does not unmount the provider, so both the
ref and the slice persist. This is the whole of D-06's *"component-local state dies on unmount"*
argument, made structural. `stopThread` / `stopStream` bodies are registered inside the provider's
mount-time `useStreamsStore.setState` (`StreamsProvider.tsx:1358`), so both refs are already in scope
at the exact line the press is handled.

**What `<StopControl threadId>` reads.** One boolean selector plus one string:

```ts
// StreamsProvider.tsx — beside :3605, alphabetical per the :3601-3603 convention
export const useStoppingForThread = (threadId: string | null): boolean =>
  useStreamsStore((s) => (threadId ? s.stoppingThreads.has(threadId) : false))
export const useStopNotConfirmedForThread = (threadId: string | null): boolean =>
  useStreamsStore((s) => (threadId ? s.stopNotConfirmed.has(threadId) : false))
```

Two `Set<string>`s beats one `Map<string, "stopping"|"unconfirmed">`: a Map selector that reads
`.get()` returns a value that is `undefined` for most threads (fine), but the three-state collapse
makes the "cleared entirely" and "unconfirmed" cases share a key, and R2's acceptance needs them
distinguishable. Two Sets keep both selectors primitive-returning. *(This is Claude's-discretion
territory per CONTEXT; the property that matters is primitive-returning selectors.)*

**⚠ D-06 correction — the composer is NOT on `stopThread` today.** `MessageInput.tsx:412`
`onClick={onStop}` ← `ChatArea.tsx:361 onStop={stopStreaming}` ← `useMessages.ts:118
stopStreaming: actions.stopStream`. Only the panel (`WorkspacePanel.tsx:461`) and the tray
(`ActiveRunsTray.tsx:107`, `:128`) call `stopThread`. **`MessageInput` already receives
`threadId?: string \| null`** (its `interface Props`), so `<StopControl threadId={threadId}>`
mounts there with zero prop churn, and routing it at `stopThread(threadId)` is behaviour-preserving:
`stopStream` resolves `activeThreadIdRef.current` (`:2378`) which **is** the composer's thread, and
the two bodies are otherwise identical (compare `:2380-2403` with `:2413-2473` — same bucket scan,
same `stoppedByUserRef` ordering, same `cancelRun`, no `abort()` in either).

## Q2 — the terminal events that clear the stopping state

**There is no single "terminal event" — there are four `streamingThreads` delete sites**, and the
honest clear point is the *slice transition*, not a handler:

| # | Site | Line | Fires on |
|---|---|---|---|
| 1 | `sendMessage`'s `finally` — *"the AUTHORITATIVE streaming-end write"* | `:2304-2311` | every send-path run end |
| 2 | reconcile-DERIVE (from `snapshot.active_runs`) | `:1599-1602` | mount / thread-switch / tab-focus |
| 3 | inactivity watchdog silent-finalize | `:3007-3010` | ~20s of no events on a probed-terminal run |
| 4 | org teardown | `:3222-3225` | org switch |

Adds: `:1591-1592` (reconcile-derive), `:1943-1945` (send), `:2101-2108` (BUG-260707-01 restore).

**Recommended clear mechanism — one place, cannot drift:** because the store carries
`subscribeWithSelector` (`streamsStore.ts:37, 330`), the provider can register **one**
`useStreamsStore.subscribe(s => s.streamingThreads, next => …)` in a mount-time effect and, for every
thread that is in `stoppingThreads` but **no longer** in `next`, clear the flag **and**
`clearTimeout(stopTimersRef.current.get(tid))`. That covers all four sites plus any future one, and
it is deterministic: R2's "never appears for a 2s cancel" is exactly "the slice lost the thread
before the timer fired."

The secondary, narrower clear is `onTerminal` — but note it is **wrapped twice** (`:1662-1663`
reconcile path, `:2057-2058` send path) and the workflow-lock clear already sits in the send-path
wrapper at **`:2202`** (`clearWorkflowLockForThread`), which is the single line a plan would otherwise
copy. Using it alone would miss the watchdog (#3) and reconcile-derive (#2) — i.e. exactly the
missed-terminal cases Phase 145 existed to close. **Do not key the clear on `onTerminal` alone.**

**⚠ L-01 on the wire — say it in the plan, do not discover it at UAT.** `finish_run` has no terminal
guard (`db/workflows.py:1458-1463`; CONTEXT deferred), so on roughly half of stops a producer on the
other worker writes `completed` over the cancel. With the clear keyed on the slice transition, the
surface will honestly show `⊘ Stopping this run…` → **`✓ Complete`**. **That is correct behaviour for
this phase.** No plan may special-case, delay, or suppress the terminal reading to hide it. The fence
for this is a *positive* one: a test that drives stop-then-`onTerminal("done")` and asserts the
stopping reading is gone and the completed reading is present.

### ⚠ The elapsed anchor — a measured trap that will otherwise produce a lie

`claimed_at` is **NOT** the anchor. `WorkflowRunPage.tsx:759-768` records the live measurement:

`claim_run`'s CAS lease is the distributed-worker path and the in-process producer never takes it.

### ⚠ D-09 IS AMENDED BY MEASUREMENT — a cheaper construction exists, and D-09's own premise is false

CONTEXT D-09/the SPEC justify a new route with *"the stop NULLs the anchor, so no cheaper
construction exists."* **Measured, that is false.** `GET /threads/{id}/workflow` already carries

> *"``finish_run`` NULLs ``threads.active_workflow_run_id`` in the same transaction as the terminal
> status … So the live anchor is absent for exactly the runs a 're-open this run' affordance exists
> to serve … This field is the anchor that survives termination."*

It is resolved at `threads.py:1187-1197` (`active_workflow_run_id` ELSE
`SELECT id FROM workflow_runs WHERE thread_id = $1 ORDER BY created_at DESC LIMIT 1`) and surfaced at

**And the frame is already the anchor-then-latest resolution D-09 wants to build.** What it is
missing is precisely three fields, because `run_status` is populated **only inside

**⚠ AND THE ROUTE CHOICE CARRIES A TRAP NEITHER SPEC NOR CONTEXT NAMES.**

> **Widen the shipped `ThreadWorkflowState` with three additive-optional fields** —

Two honest costs, stated rather than smoothed: (a) it puts run-shaped data on the threads router
rather than the `workflow_runs` router — a boundary argument, not a correctness one; (b) it needs one

### Shipped state (the defect)

**⚠ SPEC correction.** `grep -rn "press Stop again in a moment" frontend/src` returns **two** hits:

### The fix, and yes — synchronous-on-press is acceptable

```ts
let runId = streamingMsg?.runId
if (!runId) {
  const frame = await getThreadWorkflow(threadId)          // owner-scoped, NOT canvas-gated
  runId = frame.active_workflow_run_id ?? frame.last_workflow_run_id ?? undefined

```

`stopThread` is **already `async`** (`streamsStore.ts` declares `stopThread: (threadId: string) => Promise<void>`)
and already `await`s `cancelRun` (`:2470`). An awaited fetch inside it is not a new shape. And with
D-05's slice, **the press is acknowledged before the await** — `stoppingThreads.add` is a synchronous
`setState` at the top of the handler, so the fetch latency is invisible. That is the whole reason
R1 and R6 belong in the same provider change.

⚠ Keep the bucket scan **first** and the frame read as a **fallback only**. The bucket path yields the
producer `runs.run_id` (verified in `ComposerStopHarness.test.tsx`'s four-hop trace); the frame path
yields a `workflow_runs.id` and takes the slower Step-1b branch. Reversing them would change the id
type on every Deep stop — a needless behaviour change on the out-of-scope surface.

### `DELETE /runs/{id}` really does accept a `workflow_runs.id` — quoted

## Q5 — R5's kickoff gate

### The signal exists — proved, not asserted

`streamsStore.ts` `sendMessage` opts:

It is already branched on inside `sendMessage` at **`:1981`** — `if (opts?.workflowDefinitionId && run_id)`

```ts
if (!opts?.workflowDefinitionId) {

```

**Deep's path at the same line:** Deep never sets `workflowDefinitionId` (the JSDoc says *"Omitted on
