## 1. L-01 / CR-04 — the run that reports `completed` after you stopped it

**Status: a BOUNDARY STATED, not a fix. Phase 194's SC#2 is FAILED and still has no roadmap home.**

**The mechanism, restated so the next planner does not re-derive it:**

- `RUN_TASKS` is **per-process**. At the shipped `WORKER_COUNT=2`, the worker that receives
  `DELETE /runs/{id}` is only sometimes the worker holding the producer task.
- When it is not, the producer on the other worker runs to completion and calls
  `finish_run(run_id, 'completed')` (`harness_engine.py:2012`) **over** the cancel.
- `finish_run` is an unconditional `UPDATE … SET status = $2 WHERE id = $1` with **NO TERMINAL
  GUARD** (`backend/app/db/workflows.py:1458-1463`). Nothing stops `cancelled` being overwritten.

⇒ **roughly half of all stops end with the run reporting `completed`.**

**Operator decision (2026-08-16): state it as a boundary in 194.1, and insert a phase for it AFTER
194.1 lands.** 194.1 does not touch the durable half — every writer, migration 119 and the cancel
composition are Phase 194's and stay byte-untouched.

⚠ **THE INTERACTION MUST BE STATED RATHER THAN DISCOVERED AT UAT: THIS PHASE'S HONEST UI MAKES THE
L-01 LIE *MORE* VISIBLE, NOT LESS.** The stopping reading resolves on the terminal event, so on those
runs the surface truthfully shows `⊘ Stopping this run…` and then lands on **`✓ Complete`**. That is
correct behaviour for 194.1 and **no plan was permitted to "fix" it by suppressing the terminal
reading** — plan 03's **P4** is a two-armed fence that exists specifically to red against that
well-meaning suppression, and it was driven RED in exactly that direction. ⚠ Its SOURCE arm had to be
widened from one line to an **eight-line window** first, because the one-line form stayed GREEN under
the very plant it was written for.

**Cheaper repairs named at 194's verification, carried forward for whoever plans it** (all three, so
the next phase inherits options rather than one prescription):

1. an in-loop `workflow_runs.status` re-read before `mark_phase_active`, raising `CancelledError`
   when the row is already terminal;
2. **a terminal guard on `finish_run`** — the narrowest fix, and the one this entry's mechanism
   paragraph points at directly;
3. a Redis cancel channel as a cross-worker fallback.

**Re-open trigger:** ⚠ **this is not a "watch for it" deferral — it is an OWED PHASE.** Insert it as
soon as 194.1 lands. Until it ships, **RUN-01 stays UNTICKED** (see §11).

`useMessages.ts:118 stopStreaming: actions.stopStream`, and now goes through `stopThread(threadId)`

   `useState` / `useCallback`; `grep -rn "setActiveRunId\|activeRunId"` over non-test `frontend/src`

   SECOND prop on `MessageList`**, and D-03 allows the `MessageList` prop count to move by exactly one.

**Rendering the words without working navigation would be a link to a locked door — the failure this
phase exists to remove, not to add.**

⚠ **THE ABSENCE IS FENCED, NOT MERELY STATED.** A case asserts the module's stripped CODE contains
neither `Open the run` nor `onOpenRun`, **while asserting the raw source still DOES contain the
documented deferral and its re-open trigger** — so the strip can never cover for a silently deleted
decision, and a future half-built seam reds.

**Re-open trigger:** the first surface needing a chat→run jump for a reason the panel's shipped seam
does not serve, **or** an operator observation that the panel seam is not findable from a stopped
