**Gathered:** 2026-08-16

<domain>
## Phase Boundary

A person can **see** the Stop they pressed. Phase 194 landed the durable half and verified it on
seven live runs; this phase makes it perceivable — the press is acknowledged in the same slot, the
surface `▶ Run workflow` lands on can stop its own run, and a stopped thread still says so after
navigating away and back.

This phase **reads** run state. It does not write it. Every writer, migration 119 and the cancel
composition are Phase 194's and stay byte-untouched.

</domain>

### The stopping state (R1 + R2)

- **D-05: the pressed state lives in a StreamsProvider store slice, not in the mounts.**
  `stopThread` records the thread as stopping; **one 8s timer per thread lives in the store**; the
  four mounts render a shared `<StopControl threadId>` that only READS a selector. The mechanism sits
  where `stopThread` already is, which makes Phase 194 D-08 (*four mounts, ONE mechanism*) structural
  instead of a matter of discipline.
- **D-06: the discriminating argument, recorded so it is not re-litigated.** The composer Stop and
  the panel Stop can be mounted for the **same thread simultaneously**. With component-local state,
  pressing one leaves the other pressable — and R1's acceptance is that a second press is impossible
  **by construction**, not merely discouraged. Component-local state also dies on unmount, so
  navigating away mid-stop would restore a pressable Stop: a new lie, in a phase whose subject is an
  honest Stop. Both rejected alternatives (component-owned state; store state + component-owned
  timer, which gives four timers per thread that can disagree) are recorded rather than omitted.
- **D-07: the 8s climb-down is a store timer keyed by thread.** It clears on a terminal event; on
  expiry it clears the stopping state and raises a **not-confirmed** reading beside a pressable Stop.
  R2's three acceptance points (fires at 8s, has NOT fired at 7s, never appears for a 2s cancel) are
  the planner's fence set.
- **D-08: `⊘ Stopping this run…` occupies the slot the control left** (sketch 168-B). No disabled
  button, because no button. The composer row's measured height and width are identical between the
  two states — asserted on the measured slot, never by eye.

### The by-thread read (R4 + R6)

- **D-09: ONE owner-scoped route serves both requirements.** A GET on the existing `workflow_runs`
  router returning the **latest** workflow run for a thread, owner-scoped with `.eq("user_id", …)` on

  two-step check is refused). R4 reads status / step count / elapsed; **R6 takes the same row's `id`
  straight to `cancelRun`** — `194-11`'s dual-id fallback on `DELETE /runs/{id}` already accepts a
  `workflow_runs.id`, so no new cancel path is invented.

- ⚠ **D-09 IS AMENDED BY MEASUREMENT — 2026-08-16, at plan-phase, operator-decided. The original is
  left standing above rather than overwritten, per this project's habit.** D-09's stated premise was
  *"the stop NULLs the anchor, so no cheaper construction exists."* **Measured, that is false, and the
  route it chose carries a trap neither the SPEC nor D-09 names.**

  | Claim | Evidence | Verdict |
  |---|---|---|
  | The `workflow_runs` router is canvas-gated | `middleware/canvas_gate.py:85-93` (`CANVAS_GATED_PATHS`); `workflow_runs.py:169` (`Depends(require_canvas())`) | TRUE |
  | `visual_workflow_canvas` ships **off** | `models/user_settings.py:1197-1203` | TRUE |
  | ⇒ an R4 chat receipt fed from that router is **invisible at the shipped default** | R4's surface is chat, which is **not** canvas-gated | **the trap** |
  | A cheaper, ungated construction already exists | `GET /threads/{id}/workflow` is ungated (`threads.py:1036`) and already resolves anchor-then-latest via `last_workflow_run_id` (`threads.py:1187-1197`, surfaced `:1264-1270`), added by **Phase 188 CR-03 for the identical problem** and documented at `models/thread.py:101-115` | **TRUE — D-09's premise refuted** |

  **The amended decision: widen the shipped `ThreadWorkflowState` with three additive-optional
  fields** — `last_run_status`, `last_run_created_at`, `last_run_updated_at`, keyed to the **already
  resolved** `phases_source_run_id`. This is the exact shape and the exact justification Phase 188
  CR-03 used for `last_workflow_run_id`. **No new route, no `CANVAS_GATED_PATHS` edit, no migration,
  no canvas coupling, ONE round trip instead of two**, and the ownership gate is the route's existing
  one. The frame today populates `run_status` only inside `if active_workflow_run_id is not None:`
  (`threads.py:1091-1114`), so after a stop it reads `run_status = None` while `phases[]` and
  `last_workflow_run_id` both survive — that gap **is** the three fields.

  **Two honest costs, stated rather than smoothed:** (a) it puts run-shaped data on the threads
  router rather than the `workflow_runs` router — a boundary argument, not a correctness one; (b) it
  needs one extra `_rls_fetchrow` on `phases_source_run_id` **or** a widening of the two existing
  SELECTs (`:1093-1106`'s anchor arm already reads `wr.status`; `:1188-1194`'s latest arm reads `id`
  alone). **The rejected alternatives are recorded rather than omitted:** D-09's route kept and
  canvas-gated (R4 invisible at the shipped default — measured broken); D-09's route kept but
  deliberately ungated on a gated router (defensible, but a posture needing its own defence plus a
  second round trip). **Re-open trigger:** a phase that needs run history, or more than the latest
  run, in the thread — D-10 already bounds this to latest-run-only.

- ⚠ **D-09b — R6 NEEDS NO BACKEND WORK AT ALL, which D-09 did not know.** The chain is shipped end to
  end: `GET /threads/{id}/workflow` already returns `last_workflow_run_id`, the anchor-then-latest id
  that **survives the anchor NULL** (`models/thread.py:101-115`), and `DELETE /runs/{id}` already
  accepts a `workflow_runs.id` (`api/runs.py:1211-1253`, the `194-11` dual-id fallback quoted in
  RESEARCH.md Q4). ⚠ Clause (c) of that fallback requires the anchor to **still point at the run** —
  true for every live run R6 serves, including the tray row for a thread never opened this session;
  an already-stopped run 404s and `cancelRun` swallows it, which is correct and is *why* R1's
  no-button-while-stopping is load-bearing.
- **D-10: latest-run, not a list.** Nothing in this phase consumes a second row, and sketch 171's
  title is *one run, one slot*. A list would move "which run" from the server to the client for no
  consumer. Re-open trigger: a phase that shows run history in the thread.
- **D-11: fetched on mount, not polled.** R4's acceptance is *present on first paint after
  navigation*; a poll is a different capability and `WorkflowRunPage.tsx:683-731` already owns the
  polling concern for the run surface.
- **D-12: rejected alternative — a store field stamped at kickoff to serve R6.** Rejected because it
  is a live-only reading, and a live-only reading is precisely why `BUG-260610-01` is two months old
  (174 D1). Two sources of truth for one fact is the defect, not the fix.
