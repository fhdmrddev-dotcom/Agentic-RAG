## Summary

Phase 200.2 is a **re-presentation of facts that already ship**, plus one narrow new backend read. The four deliverable arms (file / answer / both / neither) were built and browser-driven in 200.1-02; the per-step count read (`step_count`/`step_noun` via `declaredCount`) shipped in Phase 200; the answer read (`deliverable_text`) shipped in 200.1. **The selection logic is done.** What this phase builds is the visual contract the operator chose in rendered sketch 202 (verdict **C, the strict single line**, 2026-08-23): a hero at the top of the centre column, a one-line-per-step "process trace" carrying each step's yield, and citation passages reachable lazily behind the yield.

The single most important structural finding for the planner is a **wiring-shape pivot**: the shipped `RunTranscript` consumes `PhaseTimingRow[]` (a duration-only read shape that deliberately does NOT carry `deliverable_text`), while the yield design (D-06) needs `deliverable_text` and `phase_type` per step. The sketch resolves this by having its card components consume the **full `WorkflowRunPhase` wire model**, not `PhaseTimingRow`. The planner must NOT widen `PhaseTimingRow` — the hot-file ledger records that widening a shared read shape to reach one field is "how a leaf stops being a leaf" — and must NOT re-derive `runAnswer` per-step. The hero region reads `run.phases` (the full wire model) directly, exactly as the current deliverable region does.

The backend half is genuinely narrow but real: one new lazy, run+step-scoped route returning citation passages with `similarity` stripped at the boundary (D-10). No migration. The existing run serializer and its written "only `text` may reach the wire" comment stay byte-unchanged.

**Primary recommendation:** Plan this as (1) a hero-region extraction/relocation on `WorkflowRunPage.tsx` reading `run.phases`, (2) a new step-card list component (the variant-C "process trace") that replaces `RunTranscript`'s mount for the Log view and consumes full `WorkflowRunPhase[]`, (3) the `RunSpine` count sub-line removal (D-05/A-02 — load-bearing, not optional), (4) one new backend route + client function for lazy citations with a set-equality fence, and (5) the sketch-202 teardown in the same commit as the executed plan.

### Recommended wiring (the load-bearing decisions)

1. **The hero reads `run.phases`, NOT `wireRows`.** This is the existing, correct pattern at `WorkflowRunPage.tsx:840` (`runAnswer`) and the deliverable region. `wireRows` is typed `PhaseTimingRow` and must NOT be widened.

2. **The new step-card list consumes `WorkflowRunPhase[]`.** This is what the sketch's `StepCard` does (`SketchRunColumn.tsx:372-491`): it passes the full wire row to `phaseRunFacts(row, …)` and `declaredCount(row)` (both only need the `PhaseTimingRow` subset — `WorkflowRunPhase` satisfies it structurally), AND reads `row.deliverable_text` / `row.phase_type` for the yield and gate logic. This is the resolution of the central wiring tension.

3. **Do NOT re-derive `runAnswer` per-step for the yield.** The hero's answer arm uses the existing whole-run `runAnswer` memo (last server-ordered non-gate row with text). The per-step "wrote an answer" yield (D-06) is a SEPARATE, per-row read of `row.deliverable_text` non-empty — a boolean fact about THAT step, not the run-level selection. Key on `phase_type` from the wire (A-03), never a slug heuristic.

### Pattern 1: Allow-list over a jsonb boundary, proved by set equality

**What:** The new citation route reads exactly the named keys it ships and nothing else.
**When to use:** Any time a jsonb column that has never been fully on the wire gets a new key exposed.
**Example (the 200.1 pattern to replicate):**

### Pattern 2: Type-level totality for the empty hero

**What:** D-16 requires the empty-hero sentence to be exhaustive over terminal statuses, enforced by the compiler.
**Example (the discriminated-union / exhaustive-switch pattern):**

### Anti-Patterns to Avoid

- **Widening `PhaseTimingRow` to carry `deliverable_text`** — the recorded "leaf stops being a leaf" defect. Consume `WorkflowRunPhase` in the new component instead.
- **Reusing `CitationCard`/`CitationPeek` against a wire that carries `similarity`** — they render `similarity.toFixed(2)` when non-null, which is literally the `Relevance: 0.94` R-2 refuses. Strip the score server-side (D-10) so the branch provably cannot fire.
- **A run-level aggregate of per-step counts** (e.g. summing `_measure` into "55 sources") — A-09 near-miss #1: the sum counts READS, not distinct sources. Forbidden.
- **Inlining citations into the polled run read** — D-09 rejects; ~300KB every poll tick.
- **A slug-regex gate detector** (`/confirm|approve|review/i`) — A-03 refutes this; `phase_type` is on the wire and clean. Key on it.

## Common Pitfalls

### Pitfall 1: The `PhaseTimingRow` widening trap
**What goes wrong:** The yield (D-06) needs `deliverable_text` and `phase_type`; the easy move is to add them to `PhaseTimingRow` so `RunTranscript`'s existing props can stay.
**Why it happens:** `PhaseTimingRow` is what the spine and log both consume; it feels like the natural shared shape.
**How to avoid:** The ledger records explicitly: "`wireRows` is typed as `phaseDuration.ts`'s `PhaseTimingRow`, which is that leaf's DURATION read shape… widening a shared read shape to reach one field on one page is how a leaf stops being a leaf." Build the new step-card list to consume `WorkflowRunPhase[]` (which satisfies `PhaseTimingRow` structurally for the shared resolvers). `phaseDuration.ts` diffs to nothing.
**Warning signs:** A `phaseDuration.ts` diff that adds a field; a `PhaseTimingRow` gaining a non-timing member.

### Pitfall 2: The 187-24 prose trap (six recorded firings on this page alone)
**What goes wrong:** `WorkflowRunPage.tsx` and `RunTranscript.tsx` both carry `?raw` WHOLE-FILE greps expecting ZERO occurrences of certain tokens (React's raw-HTML escape hatch; the sheet's icon-library class names). Naming a forbidden token inside your own comment turns the guard RED.
**Why it happens:** A whole-file grep cannot tell a refusal from an adoption.
**How to avoid:** Before writing ANY new comment in these files, read the fence's source to learn its reading mode (one is comment-stripped `codeOf(pageSource)`, one is raw `?raw` — only reading each one's source tells you which prose is safe). Describe forbidden tokens; never spell them.
**Warning signs:** A fence failing right after a docblock edit; `grep -c` reading `1` where it must read `0`.

### Pitfall 3: Re-deriving `runAnswer` per-step (and the D-17 status-line defect)
**What goes wrong:** The hero needs the run's answer; a naive per-step "last row with text" re-derivation diverges from the shipped rule AND inherits D-17's measured defect (an `llm_emit` step whose text is a 61-char filename announcement outranks a sibling's 6,133-char narrative).
**Why it happens:** The rule looks simple.
**How to avoid:** Reuse the existing `runAnswer` memo. D-17 is a locked decision: the plan must EITHER fix the rule with a measured justification across real rows OR record it as a reported bug and leave it alone — not silently inherit it. If fixing, key the skip on `phase_type === "llm_emit"` is NOT obviously correct (the sketch notes `llm_emit`'s text may be the right answer on a prose-emit workflow) — this needs a measured cross-row justification, which is why D-17 permits the bug-record path instead.
**Warning signs:** A second answer-selection memo; an unexamined `skip llm_emit`.

### Pitfall 4: Reusing citation components against a wire carrying the score
**What goes wrong:** `CitationCard`/`CitationList`/`CitationPeek` all render `citation.similarity.toFixed(2)` when non-null. Reusing them as-is on a wire that carries the score ships exactly the `Relevance: 0.94` lie R-2 refuses.
**How to avoid:** D-10 strips `similarity` at the new endpoint by not copying it. The set-equality fence proves the wire shape. With the score absent, the branch provably cannot fire and the components are reused unchanged; chat is untouched.
**Warning signs:** Any response-body key beyond the four allowed; a `similarity` field reaching the client.

### Pitfall 5: Sketch 202 uses glyphs the shipped components refuse
**What goes wrong:** The sketch's `StepCard` draws `CheckCircle2`/`XCircle`/`CircleDashed`/`ChevronDown`/`ChevronRight`/`FileText`/`Clock`/`ExternalLink` from lucide. `RunTranscript` and `RunSpine` carry ZERO-net-new-glyphs rules and refuse icon imports (the glyph budget; the spinner is a CSS ring for exactly this reason).
**Why it happens:** The sketch is the acceptance bar for LAYOUT and CONTENT, but it is a sibling Vite entry with its own imports — it is NOT bound by the shipped components' glyph fences.
**How to avoid:** The planner must reconcile this deliberately. The icon convention (`references/icon-convention.md` §4) is explicit: an icon for the same concept is byte-identical everywhere, and the shipped status marks live in `panel/phaseStatusMeta.ts` (the same characters `RunSpine` inherits). The chevron disclosure (D-12) and the status ring are the two new marks; the planner must decide whether they reuse the existing reading→face vocabulary or spend a glyph — and record it. Do NOT let the build import lucide per-sketch without reconciling against the zero-glyph invariant on the surface being replaced.
**Warning signs:** A new `from "lucide-react"` import in the run-surface component subtree; a glyph fence going red.

### Pitfall 6: The sketch surface outlives its sketch
**What goes wrong:** `frontend/sketch/` + `frontend/tsconfig.sketch.json` are a sibling Vite entry, deliberately outside `src/`. `frontend/src/__tests__/no-sketch-surface.test.ts` turns RED once Phase 200.2 has an executed plan (a `*-SUMMARY.md` exists under the phase dir).

**Warning signs:** The teardown test failing at phase close; a leftover `tsconfig.sketch.json` pointing at a deleted dir.
