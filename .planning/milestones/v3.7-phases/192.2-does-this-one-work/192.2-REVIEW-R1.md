### WR-04: `EMPTY_MATCH_REASONS`'s stated purpose is defeated at the only production call site, and the array is not frozen

**File:** `frontend/src/components/workflows/library/WorkflowCard.tsx:410-414`; `frontend/src/pages/WorkflowsPage.tsx:1104`
**Issue:** The docblock says the constant exists *"so it is ONE frozen array rather than a fresh
`[]` minted on every render of every one of the operator's 107 rows."* Both halves are wrong as
shipped:

1. `WorkflowsPage` **always** passes `matchReasons={matchReasons(row, selection)}`, and
   `matchReasons` returns a freshly-allocated array on every call — including the resting case.
   The default is therefore never taken in production; the fresh-array-per-row-per-render cost
   the comment claims to avoid is incurred anyway, and the prop identity changes on every render
   of every card.
2. The array is typed `readonly` but is not `Object.freeze`d, so *"frozen"* is a type-level
   claim presented as a runtime one.

This matters here specifically because the subtree's method is that a docblock is a contract a
later reader will act on; a claim that is measurably false is the same failure class this round
was convened to fix one layer up.
**Fix:** either return the shared empty array from `matchReasons` when there is nothing to say,
or correct the docblock to state what the constant is really for (a stable default for callers
that omit the prop). The former is the smaller change and makes the comment true:
```ts
// libraryFilter.ts
const NO_REASONS: readonly MatchReason[] = Object.freeze([])
export function matchReasons(...): readonly MatchReason[] {
  const reasons: MatchReason[] = []
  /* … */
  return reasons.length === 0 ? NO_REASONS : reasons
}
```

### IN-04: a legacy `workflow_runs` row with `user_id IS NULL` would show *Run by someone else* to the person who actually ran it

**File:** `backend/app/db/workflows.py:161-169` (lateral) + `:211-213` (`_HAS_ANY_RUN_SQL`)
**Issue:** The lateral is fail-closed on `NULL` (`NULL = $1` is never true), while the row-level
`EXISTS` counts the row regardless. So for a run whose `user_id` is `NULL`, the pair resolves to
`hasAnyRun === true` + `lastRunStatus === null` → `not-by-you`, shown to the very user who made
the run. Measured 2026-08-19 all 228 rows carry a non-`NULL` `user_id`, so this is latent, not
live — and fail-closed is the correct posture for the lateral. Recording it so the arm's
precondition is not later mistaken for a proof.
**Fix:** none now. If a backfill or a new writer can ever produce a `NULL` `user_id`, add a
`NOT NULL` constraint rather than widening the lateral.

### IN-05: `has_any_run` is a poll-observable transition, which the recorded budget's "no timestamp" does not mention

**File:** `backend/app/db/workflows.py:188-196` (DEC-08-A budget); `backend/app/api/workflows.py` (`PublishedWorkflow.has_any_run`)
**Issue:** The budget is stated as *"no count, no timestamp, no user id, no org id, no status —
`EXISTS` and nothing more."* Payload-wise that is exactly true. But on a world-readable
`is_system_global` row, a caller who polls `/starters` observes the `false → true` transition and
thereby learns **approximately when another tenant first ran that workflow**, to polling
resolution. That is inherent to any existence bit and is arguably inside the operator's locked
trade ("reveal that SOMEBODY ran a workflow the caller can already see"), so this is not a
finding against the decision — it is a finding against the *completeness of the recorded
budget*, which a future reviewer will read as the whole disclosure.
**Fix:** one clause on the budget docblock: *"and note the bit's TRANSITION is observable by a
polling client, which discloses first-run timing to polling resolution; that is inside the trade,
not outside it."*

### IN-06: `role="group"` in a `menu` owns no menu items — the note is delivered by `aria-describedby`, not by the role

**File:** `frontend/src/components/workflows/library/WorkflowCard.tsx` (fork-consequence node)
**Issue:** `DropdownMenuGroup` → Radix `Menu.Group` → `role="group"` is a permitted child of
`role="menu"` and correctly closes `aria-required-children`, and the primitive choice over
`DropdownMenuLabel` is well-evidenced (no role at all; `font-semibold` merged under our class).
Worth recording: a `group` inside a `menu` is conventionally expected to *own menuitems*, and
several screen readers prune non-`menuitem` content when arrowing a menu — so the consequence
sentence still reaches the user via the two items' `aria-describedby`, not via the group role.
The fix is correct; the mechanism is not the one the role implies.
**Fix:** none. The existing `aria-describedby` round-trip cases already pin the real delivery
path; keeping them un-deleted is the actual requirement (see WR-01).
