## 2. The headline claim, and how it is proved rather than asserted

**The claim:** the card renders identically before and after.

**The proof is an ORDERING, not an assertion.** `WorkflowCard.baseline.test.tsx` was written, run and
**committed at `b1017d20`, before `cardFace.ts` existed at all**. Its verdict at that commit,
verbatim:

```
 Test Files  1 passed (1)
      Tests  24 passed (24)
```

After Task 3, the same suite is green again — and the load-bearing measurement is not that it
passed but that it was not touched:

```
$ git diff --numstat b1017d20 HEAD -- .../WorkflowCard.baseline.test.tsx
(no output)
```

⚠ **This is the 188.1 lesson discharged rather than cited** — *a characterization baseline only
proves something if it PREDATES the change*. A pin authored after the refactor would have pinned the
refactor's output, and would have been satisfied by any behaviour the refactor happened to produce.

### Two literals in that pin were READ, not predicted

Both came out of the suite's own failing diff on its first run, and both would have made the pin
wrong in the direction that matters — asserting a card the component does not render:

1. **The AUTH-03 template mark sits ON the identity line.** The expected array was written as
   `[own, ...segs, ofN, when]`; the diff said `+ "needs a template"` at index 1. `identityParts`
   is `[...templateMark, ...segs, …]` (`WorkflowCard.tsx:568`), and every fixture row scores
   `templateAdmission(...) === "admits"` — which the pin now asserts explicitly rather than
   assuming, because *both failure tests pinned the correct branch without entering the wrong one*
   is this project's own recorded CR-01 defect.
2. **The fixture's deliverable is a FILE**, `produces: Vendor Risk Review · file`, not
   `produces: answer in chat`.

## 4. Deviations from Plan

### Auto-fixed / decided

**1. [Rule 2 - Missing critical] `./cardFace.ts` joins `LIBRARY_SUBTREE_PATHS` in the commit that created it**

- **Found during:** Task 2
- **Issue:** The plan's `files_modified` names four files and `librarySubtree.fences.test.ts` is not
  one of them. But that array is an **explicit list, not a glob** — a module absent from it is swept
  by F1, F4, F5, F6, F7 and T-192-04 **not at all**, while every one of those fences stays green.
  Its own docblock states the rule: *"a module joins the list in the same commit that creates it,
  because an unlisted module is swept by nothing at all."* This is the *"a guardrail cannot see what
  is absent from its list"* failure `CLAUDE.md` records for `WorkflowsPage.tsx` and G-5, one layer
  down — a correctness requirement, not a scope question.
- **Fix:** Added the path, then **observed** `expected [ './libraryRow.ts', …(12) ] to have a length
  of 12 but got 13` before writing the `13`. The `+5` forecast three paragraphs above that pin
  (five `it.each(LIBRARY_SUBTREE_PATHS)` sweeps × one module) **held exactly**: 118 → 123 cases.
- **Files modified:** `librarySubtree.fences.test.ts`
- **Commit:** `888dbaeb`

**2. [Rule 1 - Bug avoided] The word *t-o-k-e-n* is deliberately absent from `cardFace.ts`**

- **Found during:** Task 2 — **measured, not foreseen.**
- **Issue:** The plan says the mark should be *"a token the card maps to a glyph"*, and the first
  draft used that word throughout its prose. Adding the module to the fence corpus then turned F6's
  SCOPING CONTROL red: `+ "./cardFace.ts"` joined the enumerated list of modules that mention the
  **draft's opaque field** (D-16), which carries that exact spelling. The collision is real, not
  cosmetic — the same word would name two unrelated concepts inside one subtree, and every future
  grep of the opaque field would cost a reader one adjudication.
- **Fix:** The docblock calls it a **key** and a **plain word**; the type is `CardMark`. F6's control
  is untouched and its enumerated list is unchanged. Recorded in the module's own header so a later
  author does not "tidy" the wording back.
- **Files modified:** `cardFace.ts` (before its first commit)

**3. [Decision] The business words are IMPORTED, against the plan's letter**

- **The plan said:** *"The face's state vocabulary is the business one (`Ready to run` /
  `Still building` / `Starter`)"* — i.e. spell them here.
- **What was measured:** all three already ship, in one home, with an anti-drift fence on two of
  them: `libraryVocabulary.ts:297-307` declares `STATE_RUNNABLE = "Ready to run"`,
  `STATE_DRAFT = "Still building"` and `STATE_STARTER = "Shared starter"`, ported from sketch 163's
  **generated** build contract, and `rowIdentity.ts` consumes them today for the identity line's
  state axis.
- **Why the letter was not followed:** re-typing them in `cardFace.ts` would have created the second
  copy **T-06 exists to prevent**, and would have broken D-14's rule that a copy change is a one-line
  diff in one file. So the DECISION moved to `cardFace.ts` and the VOCABULARY stayed put.
- ⚠ **One consequence, stated rather than smoothed:** the starter word is therefore
  **`Shared starter`**, the shipped constant — not the plan's parenthetical `Starter`. `Starter` is
  the card's current *pill* text and is preserved on screen by `LEGACY_STATE_PILL`. **Wave 4 chooses
  which word the pill says, and now has exactly one place to change it.**

**4. [Decision] Absence is `null`, and the empty-name test is `=== ""` rather than a trim**

The plan requires *"an explicit unknown, never a blank string"*. `null` is that, and it renders
byte-identically to today's `""` (React emits no text node for either) — so the no-pixel constraint
holds absolutely. A `.trim()` check would additionally collapse a whitespace-only name, which is
invisible to the eye but **drops a DOM text node**, i.e. a change to the rendered output inside a
plan whose headline constraint is that there is none. What a `null` lead should SAY is a pixel
decision and belongs to Wave 4; this plan's job was to make the absence legible to whoever decides.
