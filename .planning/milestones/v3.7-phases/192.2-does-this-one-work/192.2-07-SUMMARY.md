## How the extraction is bounded — and the PROOF, not the assertion

**The cross-plan hazard:** sibling `192.2-09` edits `WorkflowCard.tsx`'s JSX in a parallel
worktree (a `matchReasons` render for WR-04). Its changes meet this fence only **after the
merge**, where nobody is watching. A line-ranged or whole-file regex extraction would sweep that
JSX's classes and go red for a reason that is nobody's defect.

**The bounding:** `blockBody(cardSource, /\bconst GUTTER_TONE\s*=\s*\{/)` finds the header, then
walks from that `{` to its **matching** `}` with a string- and comment-aware depth counter. Only
string literals inside that span are considered, and only those starting `bg-` / `text-` /
`border-` / `ring-` / `fill-` / `stroke-`. The header must match **exactly once** — zero matches
or two both throw, so a renamed map fails loudly instead of sweeping the empty string.

**The proof** is a control in the suite (`is bounded to the two map bodies`), not this paragraph.
It runs the real `allToneUtilities` over a fixture carrying `bg-nope-not-swept` in three places a
sibling plan's edit would put it — in JSX `className`, in a sibling `const`, and as a JSX child —
plus `bg-also-not-swept` inside a comment *within* a map body:

```
expect(swept).toEqual(["bg-success", "text-success"])
expect(swept).not.toContain("bg-nope-not-swept")
expect(swept).not.toContain("bg-also-not-swept")
// …and the planted literals really ARE in the fixture, so the negatives are not passing
// because the fixture forgot to carry them:
expect(CARD_WITH_CLASSES_OUTSIDE_THE_MAPS).toContain("bg-nope-not-swept")
```

**A class added outside the two map bodies is therefore provably not swept.** The last two lines
are load-bearing — a `not.toContain` over a fixture that never had the string passes vacuously.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 - Blocking] `?raw` cannot read CSS under vitest — it returns the EMPTY STRING**

- **Found during:** Task 1, at the first run of the fence.
- **Issue:** The plan specifies `@/index.css?raw`, the house idiom. It **resolves** and yields
  `""`. Four forms measured, all zero:

  | form | length |
  |---|---|
  | `import css from "@/index.css?raw"` | **0** |
  | `import css from "../../../index.css?raw"` | **0** |
  | `import.meta.glob("…/index.css", {query:"?raw"})` | key present, **0** |
  | `import css from "@/index.css?inline"` | **0** |

  `test.css` defaults to `false`, so every CSS module is replaced with an empty string and the
  `?raw` / `?inline` query is swallowed with it. **Nothing throws and nothing warns.**
- **Why this is the finding, not just an obstacle:** this is *exactly* the failure mode this
  subtree keeps recording — a fence sweeping the empty string passes green while defending
  nothing. Every `--X` lookup would have missed. It was caught **only** because the non-vacuity
  block asserts each source is non-empty *before* anything is asserted about its contents. That
  block is load-bearing, not ceremony. **Any existing or future fence in this repo that reads CSS
  via `?raw` is defending nothing while staying green.**
- **Fix:** `await vi.importActual("node:fs")` — a *runtime* module specifier, so no static
  `node:*` import exists for `tsc` to reject and the `types: ["vite/client"]` baseline is
  unmoved. This is a test file; no `src/**` product module gains a Node reach from it. The
  departure from `PublishGauntlet.test.tsx:36-46`'s "never `node:fs`" rule is **forced by
  measurement and documented at the import site**, with all four zero-length readings recorded
  there so a later reader does not re-litigate it.
- **Files modified:** `gutterTokens.fences.test.ts`
- **Commit:** `f3f750da`

**2. [Rule 3 - Blocking] `new URL(…, import.meta.url)` is statically rewritten by Vite**

- **Found during:** Task 1, second run.
- **Issue:** `fileURLToPath(new URL("../../../index.css", import.meta.url))` threw
  `TypeError: The URL must be of scheme file` at import time — a **suite-level** error, which
  does not read the same as a red fence in a gate report.
- **Note:** this confirms `PublishGauntlet.test.tsx:44-46`'s in-repo claim. It was **re-measured
  rather than inherited**, and the measurement also refutes the natural follow-on guess: bare
  `import.meta.url` *is* a perfectly good `file:///…` URL (probed). It is `new URL(…)` that Vite
  rewrites, not `import.meta.url` that is broken.
- **Fix:** derive the path from `import.meta.url` by string surgery on a `/src/components/workflows/library/`
  marker, and throw with the observed string if the marker is absent. `process.cwd()` was
  rejected too — it has no type under `vite/client`, and a cwd-derived path silently depends on
  whether the runner is `frontend/` (direct `vitest run`) or the repo root
  (`scripts/vitest-count-gate.cjs`).
- **Commit:** `f3f750da`

**3. [Rule 1 - Correctness] The plan's config-key matcher would report every compound key as undeclared**

- **Found during:** Task 1.
- **Issue:** The plan specifies matching the key as a property name at the start of a line,
  `/^\s*"?<key>"?\s*:/m`. `text-muted-foreground` strips to `muted-foreground`, and **there is no
  such line anywhere in `tailwind.config.js`** — it exists only as a `foreground:` member nested
  under `muted:`. Three of the nine unique utilities resolve through nested members. The grep
  would have reported them all unresolved, making the fence permanently red for the wrong reason.
- **Fix:** a depth-aware object parser that composes `parent` (from `DEFAULT`) and
  `parent-member` names — which is how Tailwind itself resolves them. It is **strictly stronger**
  on the property the grep was chosen for: comments are never scanned at all, so a key mentioned
  only in a comment cannot satisfy it (the 187-24 trap). **That is proven by a control**
  (`L2 does NOT count a key that appears only inside a COMMENT`), not asserted — the control
  first checks the fixture really does contain the word `ghost`, then requires the parser to
  refuse it.
- **Commit:** `f3f750da`

**4. [Rule 1 - Correctness] A false claim in the fence's own docblock, caught before commit**

- The first draft asserted L3 was red alongside L2. Measured false (see above), corrected in
  place with the correction recorded beside it rather than the original quietly deleted.
