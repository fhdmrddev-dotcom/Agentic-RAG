<decisions>
**DEC-08-A — THE OPERATOR CHOSE THE ROW-LEVEL FACT OVER THE REWORD, AND ACCEPTED AN EXPLICIT
DISCLOSURE TRADE. This is a locked input, not an option to re-litigate.**

The review offered two honest repairs: (a) reword the arm as caller-scoped (*"You haven't run
this"*), or (b) carry a non-identifying row-level `has_any_run` and add a fourth arm. **The operator
picked (b)**, against (a) presented beside it, because on a world-readable starter the caller-scoped
sentence answers a question nobody asked, and LIB-06's thesis (*does this one work*) then goes
unanswered for exactly the rows a newcomer meets first.

⚠ **THE TRADE, WRITTEN DOWN SO A FUTURE READER CAN RE-OPEN IT RATHER THAN REDISCOVER IT:**
`has_any_run` reveals that **somebody** has run a workflow the caller **can already see**. It must
**never** reveal *who*, *when*, or *with what outcome*. **`EXISTS` only — no count, no timestamp, no
user id, no org id, no status.** On a world-readable starter this disclosure is arguably the point
of the feature; on a private row the caller is the only person with runs anyway, so the bit is
self-evident. That reasoning is the whole justification, and it is recorded here rather than left
implicit. **Re-open trigger:** the first workflow row that is visible to a caller who is not entitled
to know it has been exercised at all.

**DEC-08-B — THE OWNER SCOPE IS UNTOUCHED.** `r.user_id = $1` inside `_LAST_RUN_LATERAL_SQL` stays
byte-identical. It is the correct security call — these feeds run on a service-role pool that
BYPASSES RLS, so whatever the SQL returns is what the caller gets. The new EXISTS goes in the OUTER
projection, never inside that subquery.

**DEC-08-C — `has_any_run` is typed `bool | None`, not `bool`, and the default is `None`.** A SQL
`EXISTS` is never null, so the live value is always `True`/`False`. `None` exists for exactly one
case: a future read path that omits the column. Defaulting to `False` there would manufacture the
affirmative claim *"nobody has run this"* out of an absence — which is the shape of the very bug
this plan closes, one layer down.

**DEC-08-D — ONE CONSTANT, FOUR SITES, and it is appended to the projection rather than folded into
the lateral.** Folding it into `_LAST_RUN_LATERAL_SQL` is impossible: that subquery's `WHERE` is
owner-scoped, and an `EXISTS` evaluated inside it would inherit the scope and answer the same
question twice. A second module-level constant keeps the SQL text in ONE home while leaving the
security boundary intact.

**⚠ G-7 JUDGEMENT, RECORDED RATHER THAN LEFT TO BE INFERRED.** G-7 says a closure round may never
introduce a new user-facing capability — *"that is a phase, not a gap."* The fourth arm this
backend enables does put a NEW WORD on screen, so an auditor will reasonably ask whether this round
smuggled in a feature. **It did not, and here is the argument:** the card ALREADY claims to report
run truth, and it currently claims it **falsely** on the shelf built specifically to be
world-readable. A correct claim in place of a false one is REPAIR, not new capability. The mechanical
check does not trip either — `check-gap-closure-rounds.cjs` fails `[new-capability-in-closure]` only
when a gap plan's `files_modified` names a non-test source file that did not exist when the plan was
written, and **every file here already exists**. Run it (`node scripts/check-gap-closure-rounds.cjs
192.2`) and paste the verdict into the SUMMARY. It reported `6 total · 0 gap-closure · G-7 clear` at
