# Phase 192.2 Plan 11: The Fourth Arm — CR-01 Closed On Screen — Summary

**`never` now fires only on an affirmed `has_any_run === false`, so the card has stopped telling
everybody that workflows they can see but have not personally run have never run — and the case it
used to swallow gets its own sentence, its own gutter and its own regression pin.**

## 1 · What CR-01 actually was, and where it ended

The `last_run_at` / `last_run_status` fields arrive from an **owner-scoped lateral join**. Every row
the product serves to everybody — all three `/starters` rows, every `is_system_global` published row
— therefore arrives at a non-runner with `last_run_status: null`, and the resolver read `null` as
*the backend looked and there is no run*. The product printed an **affirmative falsehood**, in
words, about somebody else's work. `192.2-08` measured it: **1 of 3 starter rows** (only
`weekly-status-report` has ever run) and **5 of 92 published rows**.

The fix is one precondition and one new arm:

| `lastRunStatus` | `hasAnyRun` | arm | word |
|---|---|---|---|
| `undefined` | *(never read)* | `unknown` | Not recorded |
| `null` | `true` | **`not-by-you`** ← NEW | **Run by someone else** |
| `null` | `false` | `never` | Never run |
| `null` | `undefined` / `null` | `unknown` | Not recorded |
| unrecognised / blank | any | `unknown` | Not recorded |
| terminal | any | `ran` | Worked / Failed / Stopped |

**The old resolver's behaviour is not inferred — it was measured.** Four pre-existing card cases went
RED the moment the precondition landed, each reading `expected 'Not recorded|…' to contain 'Never
run'` on a `status: null` row. That is direct evidence that `null` alone used to produce the
never-run sentence.

## 2 · DEC-11-B, the operator-flagged interpretation, implemented exactly

The locked four arms name `has_any_run = true` and `= false`. They **do not name ABSENT**. An absent
bit routes to the existing `unknown` arm, because *Never run* is an affirmative row-level claim and
an absent bit is not a fact we hold.

Held mechanically, not by convention:

- `row.hasAnyRun` is read **only inside** the `status === null` branch. The `undefined` branch still
  returns before anything else is read.
- The comparisons are `=== true` and `=== false`. A truthiness test folds `false`, `null` and
  `undefined` into **one** answer; DEC-11-B turns on those being **three**.
- `runFacts.test.ts` asserts the four `hasAnyRun` values reach **three** arms
  (`["not-by-you","never","unknown","unknown"]`, `new Set(...).size === 3`) and sweeps the
  comment-stripped source for both explicit comparisons — so a later truthiness rewrite reds twice.
- The `status: undefined` × four-value matrix proves rule 1 still short-circuits (T-192.2-48).

## 3 · ⚠ The cross-plan obligation: `192.2-07`'s fence RE-DERIVED, not bumped

`gutterTokens.fences.test.ts` pins an **exact** size over the literals inside `GUTTER_TONE` and
`RUN_TONE`. Adding a sixth arm to both maps moves that shape, and this plan was the only one
authorised to touch it.

**Old (measured by `192.2-07` at `d622165b`, five arms):** `{ entries: 10, unique: 9, perMap: 5 }`
**New (measured here, six arms):** `{ entries: 12, unique: 10, perMap: 6 }`

**The arithmetic, and why a `+2` guess would have been wrong on two of the three figures:**

| figure | old | new | Δ | why |
|---|---|---|---|---|
| `entries` | 10 | **12** | **+2** | raw occurrences — one new entry in each of the two maps |
| `unique` | 9 | **10** | **+1** | `new Set(all).size`. `GUTTER_TONE["not-by-you"] = "bg-muted-foreground"` is a genuinely NEW literal; `RUN_TONE["not-by-you"] = "text-muted-foreground"` is the **THIRD** occurrence of a literal `never` and `unknown` already name |
| `perMap` | 5 | **6** | **+1** | the two maps stay the same length — the design invariant `RUN_TONE`'s docblock states |

A uniform `+2` would have landed on `unique: 11` — a wrong number that still *looks* plausible.

**How it was derived, in both directions:**
1. Read the two edited object bodies back and counted: GUTTER_TONE 6 literals, RUN_TONE 6 literals;
   union = {bg-success, bg-destructive, bg-warning, bg-border, bg-muted-foreground, bg-transparent,
   text-success, text-destructive, text-warning, text-muted-foreground} = **10**.
2. Confirmed against the fence's **own failing diff**, which read verbatim:
   `AssertionError: expected [ 'bg-success', …(11) ] to have a length of 10 but got 12`.

**The assertion was NOT weakened.** It is still `toHaveLength(TONE_SHAPE.entries)`, `toBe(...unique)`
and a per-map `toBe(...perMap)` — no `>=`, no range, no tolerance, no removed check. The comment now
records *why* the numbers moved, names this plan, and tells a seventh-arm author to re-run the drill.

**`192.2-07`'s synthetic positive controls still fire.** The plan said there were two; the shipped
fence carries **five**, and all five pass — each one runs the REAL detector over an in-test source
carrying a planted violation and requires it to be caught:

| control | proves |
|---|---|
| `L2 catches a tone map naming a key nobody declared` | the undeclared-key detector fires |
| `L2 does NOT count a key that appears only inside a COMMENT` | the 187-24 trap |
| `L3 catches a declared key whose variable is missing from :root` | the dark-only half of WR-01 |
| `L3 catches a key that is a raw hex rather than a semantic token` | the token contract |
| `blockBody REFUSES a renamed map rather than sweeping the empty string` | non-vacuity |

Independently of the controls, **the fence demonstrably still goes red**: it did, on this plan's own

## 4 · WR-03 — and the correction that matters

The fork-consequence sentence was a bare `<p>` directly inside Radix's `role="menu"`.

**⚠ DEC-11-E's premise is refuted by measurement, and the departure is recorded rather than made
quietly.** Both the review's fix block and DEC-11-E named `DropdownMenuLabel` as *"the same visual
node with a valid role"*. **Both halves are false:**

1. **It carries no role at all.** Radix's `Menu.Label` is a bare `Primitive.div` with no `role` prop
   (`@radix-ui/react-menu/dist/index.mjs:356-362`). Swapping to it left the five-role sweep **still
   red** — `div[role=none]` where it had said `p[role=none]`. A renamed defect, not a fixed one.
2. **It is not the same visual node.** `DropdownMenuLabel` merges `"px-2 py-1.5 text-sm
   font-semibold"` *under* our `className`, and `MENU_NOTE_CLASSES` names no font weight — so the
   note would have rendered **semibold**, a pixel change D-03 did not sanction on a card this phase
   exists to quieten.

The shipped fix is **`DropdownMenuGroup`**, which Radix renders as `role="group"` and nothing else
(`index.mjs:348-354`): one node, a permitted role, the identical paint. It is also exactly the
review's own parenthetical alternative, reached through a shipped primitive instead of a hand-rolled
`div`. `id`, `data-testid` and `className` moved across verbatim; the `aria-describedby` round-trip
cases passed **unedited**.

### ⚠ Which of the two a11y assertions shipped, stated plainly

**Axe did NOT flag it.** The axe case was driven through the real trigger against the unedited `<p>`
and **passed green** (vitest-axe over axe-core 4.11.4, jsdom); `aria-required-children` never fired.

So **both** shipped, labelled:

- **The fence that holds WR-03 is the explicit structural sweep** — every direct element child of
  `[role="menu"]` must carry one of the five permitted roles. It was driven **RED twice** and named
  the offending node each time (`p[role=none]`, then `div[role=none]`), with a non-vacuity guard so
  an empty menu cannot satisfy it.
- **The axe case is kept as a broad regression backstop**, with its silence on this specific defect
  written into its own comment. A green-only axe assertion with no recorded failure mode is not
  evidence, and shipping it as though it were is how a fence that defends nothing gets believed.
