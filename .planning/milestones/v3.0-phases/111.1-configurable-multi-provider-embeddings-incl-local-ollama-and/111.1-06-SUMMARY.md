## Bug found live + fixed (in Plan 05's code) — `3246629e`

The confirm gate showed **1,000** chunks vs the real **1,839**. Root cause: `reembed_service.py` derived counts via `len(rows)` on a `.select()` that PostgREST caps at the default 1,000 max-rows — so the re-embed **progress denominator** was also capped (a real run would report "complete" at 1,000 of 1,839). Static tests missed it (2-row rollback fixtures); the live 1,839-chunk corpus exposed it. Fixed with `count="exact"` (head query, `.limit(1)`). Verified live: old `len()` = 1,000, fixed `.count` = 1,839 ✓. 7 reembed tests still green.
