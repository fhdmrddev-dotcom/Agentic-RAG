<objective>
Implement `_handle_query_documents_by_view` — the one new agent tool's handler — in
`backend/app/services/tool_dispatcher.py`, cloning the `_handle_search_documents` shape
(tool_dispatcher.py:173). The handler has three modes off the polymorphic `view`-XOR-`filter`
argument: CATALOG (neither field, or an unknown view name) → the caller's saved views + the
filterable fields; SAVED-VIEW (a `view` name) → own-or-global lookup → resolve; INLINE-FILTER
(a `filter` object) → `ViewFilter.model_validate` → resolve. It reuses the Plan-01 extracted
`resolve_filter` in-process (count_only=True for the TRUE total, then a capped materialization),
returns honest compact newest-N rows + the truncation note + `source_refs`, maps a `ResolveError`
to a calm `ToolResult` string (NEVER throws into the agent loop), and fires the existing
`search.query` audit tagged `via:"view"`/`via:"filter"` (D-115-10 — no new enum, no migration).
Also add the small `get_view_by_name` own-or-global lookup helper (the model never sees UUIDs).

Purpose: This is the conversational mouth of the 113/114 virtual-folders work — "open my Invoices
view" / "how many contracts expire in 90 days" answered in chat (VIEW-07). Honesty is
load-bearing (TRUE total never `len(capped_rows)`; explicit truncation note; caller-scoped only;
citable `source_refs`). The SC#1 dual-WIRING (registry + advertised schema) and the live leak
proof land in Plan 03.

Output: `_handle_query_documents_by_view` + `get_view_by_name`, with handler-mode unit tests and
the live catalog/resolve/result-shape integration tests green.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model tool-call → handler | The model supplies `view`/`filter`/`limit` — untrusted, polymorphic; validated at the handler edge |
| handler → resolve core | The handler passes caller=`ctx.current_user["id"]`; the core caller-scopes own+global (the leak boundary) |
| filter value → SQL | Untrusted literals; bound params via the reused compiler (no f-string SQL) |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-115-02-01 | Information Disclosure | cross-user leak via a seeded global view | mitigate | Handler passes ONLY `caller = ctx.current_user["id"]` into `resolve_filter`; never `view["user_id"]`; the resolver caller-scopes own+global. Proven LIVE by the Plan-03 two-user leak test (not the RLS label — the "static would false-green" lesson) |
| T-115-02-02 | Information Disclosure | view-name existence leak (probing another user's view names) | mitigate | `get_view_by_name` is own-or-global only; an unknown/unseeable name → catalog, never a 403 or a distinguishable error (D-115-6) |
| T-115-02-03 | Tampering | SQL/SSTI via an inline `filter` value | mitigate | `ViewFilter.model_validate` (Literal-op reject) + the reused `compile_filter` bound params; no f-string SQL in the handler |
