<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| router → document_view_service | The router passes caller-derived `user_id`; the service must never trust a caller-supplied `is_global` |
| service → document_views (Postgres + RLS) | RLS forces `is_global=false` on end-user writes; the service hard-sets it as defense-in-depth |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-06 | Elevation of Privilege (escalate to global) | `create_view` / `update_view` payload | mitigate | `is_global` HARD-SET to `False` in the insert payload, never read from a caller field (D-113-3); RLS WITH CHECK at migration 071 forces it too. Verified live in Plan 03's CRUD integration test (the create row is non-global). |
| T-113-07 | Information Disclosure (existence leak) | `get_view` / `update_view` / `delete_view` | mitigate | Reads gate to own-OR-global; writes gate to own-only; a miss collapses to `None`/`False` so the router returns a generic 404 (not 403). Verified live in Plan 03's `test_cross_user_miss_404`. |
| T-113-08 | DoS (blocking I/O in async handler) | every `.execute()` | mitigate | All DB calls wrapped in `aexec` (`run_in_threadpool`) per D-v2.5-01 — no blocking supabase-py call inside an async handler. |
</threat_model>
