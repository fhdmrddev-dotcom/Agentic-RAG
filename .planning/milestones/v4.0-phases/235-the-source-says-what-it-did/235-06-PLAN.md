<objective>
Compute the stopped verdict once, on the server, from the rows the loop now writes — and expose the history
the card will render.

Purpose: SC#4 says the signal must not fire for a healthy source or for a single transient failure the next
check recovered from. That rule has to live in exactly one place or the badge, the Health row and the card will
eventually disagree, and the first person to notice the disagreement will be a user. D-235-05 puts it here.

⛔ And the endpoint must not repeat, one level up, the overclaim `BUG-260906-02` is about: `main.py:571` gates
the loop on `settings.watch_process_enabled`, but `:587-589` catches a failed start, sets `_watch_service = None`
and carries on — so the flag reads `true` while nothing is running. The honest source is `app.state`.

Output: a pure verdict leaf, two GET routes on `sources.py`, and their wire models.
</objective>

  <behavior>
    - `verdict_for_runs([])` → `never_read=True`, `stopped=False`. A watch with no rows has not read yet; it is
      not broken.
    - Newest row `status="failed"`, `failure_cause="token_revoked"` → `stopped=True`, `hard=True`, on failure ONE.
    - Newest row `failure_cause="folder_gone"` → `stopped=True`, `hard=True`, on failure ONE.
    - Two consecutive `unreachable` failures → `stopped=False`. Three → `stopped=True`, `hard=False`.
      ⭐ The two-failure case is asserted explicitly and by name — SC#4's "does not fire for a single transient
      failure" is the criterion most easily satisfied by accident and most easily lost.
    - `[failed, success, failed]` (newest first) → `stopped=False`: only LEADING non-successes count, so a
      recovered blip resets.
    - `stopped_since` is the `started_at` of the OLDEST row in the leading failure streak — not the newest, which
      would make a source that has been dead a week read as stopped a minute ago.
    - `last_good_at` is the `started_at` of the newest `success` row, or `None` if there is none.
    - A `paused` run counts as a non-success for the streak but classifies as cause `unknown` unless the row
      carries one — a paused watch did tick and did not read.
    - Non-vacuity FIRST: the suite asserts `SOFT_FAILURE_THRESHOLD == 3` and that `HARD_CAUSES` is non-empty
      before any property rests on them.
  </behavior>
