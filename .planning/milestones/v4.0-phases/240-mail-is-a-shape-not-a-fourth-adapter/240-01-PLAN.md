# 240-01 — Mail is a virtual root on a connection that already exists

**Goal (SC#1 substrate, SC#4 substrate):** A person browsing their connected Google account
from the Library sees their **mail labels** beside My Drive and Shared Drives, picks one, and
gets a preview of real messages with real subjects — **without a fourth `SourceAdapter`, without
a new registry key, and without one byte of change to the contract.**

## Why this is one plan and not three

The mail module, the Gmail calls and the adapter delegation are meaningless apart: a module with
no delegation is unreachable, a delegation with no module fails import, and neither can be tested
without the other. The contract-unchanged fence belongs here too, because it is the assertion
that gives every other task its meaning. One atomic plan in Wave 1, and it shares no file with
`240-02`.

<threat_model>
<trust_boundaries>
Gmail API (third-party, returns attacker-influenced text) -> send_pinned_http (`gmail_read` egress key) -> mail/gmail.py -> mail/mailbox.py -> SourceFile -> WatchService / PreviewService / Ingestion
</trust_boundaries>
<threats>
- threat_id: TM-240-01
  category: Egress / capability confusion
  component: mail/gmail.py
  disposition: mitigated
  mitigation_plan: Every outbound call uses `send_pinned_http` with the egress key `gmail_read`, NEVER `drive_read`. `egress.py:266` pins `gmail_read` to `googleapis.com` over https only. The key is what an audit greps; a shared key would erase the Drive/Gmail separation the moment a scope was added.
- threat_id: TM-240-02
  category: Injection via attacker-controlled filename (path traversal / control bytes)
  component: mail/mailbox.py
  disposition: mitigated
  mitigation_plan: A message Subject is text a stranger chose. It is passed through the existing `sanitize_attachment_filename()` before becoming `SourceFile.name`. This Library already paid for this: a NUL byte inside a `.msg` subject produced a Postgres `22P05` in v3.7 UAT that 5,438 green tests missed.
- threat_id: TM-240-03
  category: Denial of service / memory exhaustion
  component: mail/gmail.py read path
  disposition: mitigated
  mitigation_plan: `max_bytes=source_max_file_bytes()` on the raw fetch (the single operator ceiling established in Phase 239 / SEED-258 — NOT a new module constant, which is the defect that phase removed), and a bounded `max_bytes` on every metadata and listing call.
- threat_id: TM-240-04
  category: Privilege / scope creep
  component: mail/gmail.py
  disposition: mitigated
  mitigation_plan: Reads only — `users.labels.list`, `users.messages.list`, `users.messages.get`. `gmail.compose` sits on the same token and is never called. No endpoint that mutates a mailbox appears in this module.
- threat_id: TM-240-05
  category: Disabled-connection bypass
  component: SourceRegistry
  disposition: mitigated
  mitigation_plan: Inherited, not re-implemented. Mail resolves through `SourceRegistry.get_adapter(connection)`, which is the ONE place `BUG-260907-03` is refused. A test drives it: a disabled connection must raise `SourceConnectionDisabled` before any mail call is attempted.
</threats>
</threat_model>

<action>
Create `backend/tests/unit/services/sources/test_240_mail_shape.py`. Patch `send_pinned_http`
with a fake that asserts on the URL it is given and returns canned Gmail JSON.

⚠ Phase 238's verification named its own weakness plainly: *"the fake is mine, so it agrees with
my adapter by construction."* Mitigate it here by building the canned payloads from **verbatim
field names quoted in Google's published reference** (`id`, `threadId`, `labelIds`, `snippet`,
`historyId`, `internalDate`, `sizeEstimate`, `raw`, `nextPageToken`, `resultSizeEstimate`) and
by asserting the REQUEST the adapter makes, not only the response it parses.

Cases:
1. `browse(conn, folder_id=None)` returns THREE virtual roots — `my_drive`, `shared_drives`,
   and a mail root — **with no network call at all** (the fake raises if invoked).
2. `browse(conn, folder_id="<mail root id>")` calls `users/me/labels` and maps each label to
   `SourceNode(id="mailbox:<labelId>", name=<label name>, kind="folder")`.
3. `list_files(conn, folder_id="mailbox:INBOX")` calls `users/me/messages` with
   `labelIds=INBOX`, then one `messages/{id}` per result with
   `format=metadata&metadataHeaders=Subject&metadataHeaders=Date&metadataHeaders=Message-Id`;
   maps each to `SourceFile(id="mailmsg:<id>", name="<subject>.eml",
   mime_type="message/rfc822", size=<sizeEstimate>, modified_at=<internalDate>,
   path="/<label name>")`.
4. A message with an EMPTY subject becomes `"(no subject).eml"` — never an empty name.
5. A subject containing `../`, a `\x00`, and a newline is sanitised; assert the resulting name
   contains none of them. (TM-240-02.)
6. `list_files` honours `nextPageToken` → `FilePage.next_page_token`, and passes a page size of
   **25**, not 30 (D-240-12).
7. `read_file(conn, "mailmsg:<id>")` calls `messages/{id}?format=raw`, base64url-decodes the
   `raw` field **with padding restored**, and returns
   `("<subject>.eml", <decoded bytes>, "message/rfc822")`. Use a real small RFC-822 fixture so
   the decoded bytes can be handed to `parse_eml_bytes` in the same test and produce the
   expected subject — this is the "one parser, two doors" assertion.
8. A `raw` payload whose decoded size exceeds `source_max_file_bytes()` raises `ValueError`
   naming the ceiling. (TM-240-03.)
9. Every call is made with the egress key `gmail_read`; assert the fake saw that literal and
   NEVER `drive_read`. (TM-240-01.)
10. A Drive folder id (no `mailbox:` / `mailmsg:` prefix) still takes the Drive path untouched —
    a negative control proving the delegation did not swallow Drive.
11. `SourceRegistry.get_adapter({"service_id": "google", "is_enabled": False})` raises
    `SourceConnectionDisabled` — mail inherits the refusal. (TM-240-05.)
</action>

## How we'd know this failed

- `base.py` changed — by a field, a registry key, or a mail word. The thesis is refuted and the
  phase says so instead of quietly widening the contract.
- A `GmailSourceAdapter` class exists, or `SourceRegistry` gained a mail key: mail became a
  fourth adapter after all.
- `mail/mailbox.py` imports something Google-shaped — the "provider-independent half" is a label
  rather than a fact, and the Graph arm will not be three lines.
- A Gmail call carries `drive_read`: the audit separation `egress.py` exists to preserve is gone.
- The preview lists message ids instead of subjects — Phase 233's honest labels reduced to hex.
- The fence in `240-01-01` was never driven RED, so nobody has seen it fail.
