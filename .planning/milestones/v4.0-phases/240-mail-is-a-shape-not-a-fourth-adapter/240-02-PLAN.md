# 240-02 — A conversation key that something actually reads

**Goal (SC#3, and the substrate for SC#1):** Every mail document carries a `thread_key` derived
from its own RFC 5322 headers, written by **both** ingest paths, and read by **two** things —
a view filter and (in `240-04`) a Conversation section. A reply that arrives later lands on the
same key as the message it answers.

## Why this is one plan and not four

The derivation, the column, the two write sites and the first read are one fact expressed in
four files. A column with no writer is dead; a writer on one path only is the exact defect this
phase exists to find elsewhere; and a key nothing reads is the ROADMAP's own named failure mode
for this phase. It shares no file with `240-01`, so both run in Wave 1.

## ⛔ The failure this plan is written against

ROADMAP 240, verbatim: *"`thread_key` is stored and read by nothing — the exact fate
`message_id` / `in_reply_to` / `references` already suffered here."* Those three headers are
parsed today (`email_extraction_service.py`) and copied into `metadata` at
`ingest_enrich.py:261-266`, and **nothing anywhere reads them back**. This plan does not get to
claim success by adding a fifth write.

<threat_model>
<trust_boundaries>
Attacker-authored email headers (fully untrusted) -> parse_eml_bytes -> thread_key_for() -> documents.thread_key (indexed column) -> view filter / retrieval grouping
</trust_boundaries>
<threats>
- threat_id: TM-240-06
  category: Cross-user / cross-tenant grouping
  component: documents.thread_key + its index
  disposition: mitigated
  mitigation_plan: A Message-ID is chosen by whoever sent the mail, so two unrelated users CAN be made to share one. The index and every read are keyed on `(user_id, thread_key)` and every read rides existing RLS. `thread_key` is NEVER a join key on its own. A test asserts two documents with an identical `thread_key` under different `user_id`s do not appear in one another's results.
- threat_id: TM-240-07
  category: Injection / oversized value
  component: thread_key_for()
  disposition: mitigated
  mitigation_plan: Header text is normalised (angle brackets stripped, whitespace removed, lower-cased, control characters dropped) and TRUNCATED to 512 characters before it is stored. A Message-ID is attacker-length as well as attacker-content. Bound it at the derivation, not at the column.
- threat_id: TM-240-08
  category: Wrong grouping (silent corruption of retrieval)
  component: thread_key_for()
  disposition: mitigated
  mitigation_plan: Subject is NEVER an input (D-240-05) — "Re: Budget" collides across unrelated conversations and people. Absent headers yield `None`, which reads as a thread of one: a VISIBLE degradation, never a wrong grouping. A test pins both directions.
</threats>
</threat_model>

   identical key.

   DIFFERENT keys. (TM-240-08 — subject is not an input.)
7. A `Message-ID` of 5,000 characters is truncated to 512. (TM-240-07.)
8. A `Message-ID` containing `\x00` and a newline yields a key containing neither.

*"the `References` and `In-Reply-To` headers … in compliance with RFC 2822"*.

  that was warned about it.

- Two unrelated conversations share a key because Subject leaked into the derivation.
- A message with no `References` silently joins the wrong thread instead of standing alone.
- Migration 175 was applied with `db push` / `db reset`, destroying local dev data.
