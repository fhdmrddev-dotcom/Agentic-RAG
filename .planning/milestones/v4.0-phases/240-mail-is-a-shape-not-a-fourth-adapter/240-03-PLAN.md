# 240-03 — A watched mailbox brings its attachments, and one paragraph stays one paragraph

**Goal (SC#1, SC#2):** Attachments of a message that arrived through a **watch** become documents
of their own, linked to the message both ways round — and the paragraph message 1 wrote appears in
exactly **one** document's chunks, not fourteen.

## ⛔ The defect this plan exists to close, measured before planning

`grep -n "rfc822\|attachment" backend/app/services/ingest_splice.py` returns **one docstring line
and no code**. The loop that mints an attachment as a child document and writes the `attached_to`
relationship lives **only** at `backend/app/api/documents.py:2217-2325`, inside the legacy
`ingest_document`. **Watches and `/upload` both run the queue path.** So a watched mailbox would
ingest fourteen messages and **zero attachments**, SC#2 would be false, and every unit test would
stay green — because the tests exercise the legacy path.

This is the **fourth** recorded disagreement between these two paths. `ingest_splice.py`'s own
comments narrate the first three: BUG-260905-06 (metadata never ran), the empty-chunk refusal
(*"a document that produced NO searchable content reported success"*), and the Phase 234
provenance carry. Each was found the same way — by someone going looking. The fix is the same
shape each time: **one function, both callers, never a copy.**

## Why this is one plan and not two

The extraction and the SC#1 measurement both need a real mail document ingested through the
**queue** path with attachments present. Splitting them would build that harness twice, and the
measurement would be run against a path that cannot yet produce children.
