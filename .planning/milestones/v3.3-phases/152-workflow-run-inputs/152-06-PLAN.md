<objective>
Close Warning WR-03 (backend half) on the shipped per-run folder-scope resolver, WITHOUT re-planning 152-01 (its code stays).

The A4 guard in `resolve_run_scope_root` (`backend/app/services/harness/scope.py:150-157`) drops a per-run override only when it is OUTSIDE the whole project subtree. But the per-phase narrowing at `phase_types.py:326-329` intersects EACH declared phase's `folder_scope` with the OVERRIDE's subtree — so an in-subtree override (e.g. child A of project P) can make a phase whose `folder_scope=[B]` retrieve NOTHING, silently. Membership in the project subtree is necessary but not sufficient.

Fix (152-REVIEW.md WR-03): in the `elif _definition_has_phase_folder_scope(definition)` branch, resolve the OVERRIDE's own subtree and drop the override unless EVERY declared phase `folder_scope` still intersects it.

Purpose: a folder override can never silently empty a phase's retrieval; it degrades safely to the author default instead.
Output: the corrected A4 branch + a regression test for the empty-intersection case.

NOTE: the frontend mirror of this same rule (the `overrideOptions` filter in WorkflowsPage.tsx) is closed in 152-07 — a DIFFERENT file, so there is no collision with this plan.
</objective>
