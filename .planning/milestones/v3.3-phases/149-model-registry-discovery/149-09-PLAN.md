<objective>
Close the MAJOR silent-fallback gap from the Phase-149 live UAT (Test 7, D-149-10 violation), plus its minor provider-bookkeeping wart.

The backend half of D-149-10 already works: `threads.py:1231` emits `model_disabled_fallback` into the Redis run stream with `{type, disabled_model, fallback_model, message}` (verified live on run 1c4c7b4a — the `message` string already names both models: "modelX was disabled by your administrator — this reply used modelY"). But the **frontend never consumes the event** — `rg model_disabled_fallback frontend/src` returns 0 hits; the SSE stream parser drops unknown event types silently, so the user experiences a silent model swap (the exact outcome D-149-10 bans). This plan wires the event through the existing SSE-dispatch chain (`api.ts` StreamCallbacks → `StreamsProvider` message stamp → `MessageItem` render), mirroring the `skill_activated` precedent.

Secondary (minor, same wave): after a fallback, the `runs.provider` column records the PRE-fallback provider (a MiniMax-served run recorded `provider='anthropic'`). The org-default fallback model's provider is not re-resolved before `register_run_start`. This plan re-resolves it — a small, G-5-aware `threads.py` touch (minimal diff, no refactor).

Purpose: make the disabled-model fallback honest end-to-end (never silent), and make the run's recorded provider match the model actually served.
Output: the SSE event consumed + rendered as an inline chat notice; the runs row records the effective model's provider; a component test proving the notice names both models; a backend test proving the re-resolved provider.
</objective>
