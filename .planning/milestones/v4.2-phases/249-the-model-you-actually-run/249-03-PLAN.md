<objective>
**MODEL-08 — a write the database refuses stops reporting like a write that failed to reach it.**

`save_app_settings` catches `Exception`, logs the column names, and returns `False`. Every one of its
six call sites turns `False` into a bare **HTTP 500 "Failed to save settings"**. That is true, and
undiagnosable — and for a `CheckViolationError` it is also *wrong*: a value the database refused is
a **caller error**, not a server fault.

Split the arm. **Refused → 400 naming the constraint. Unreachable → 500, unchanged.**
</objective>

<threat_model>
### Security & Reliability Invariants

1. **⛔ NEVER LOG OR RETURN A VALUE (T-081.1-04) — the load-bearing one.**
   - **Invariant:** the `app_settings` row carries **API keys**. The existing `except` says so in a
     comment and logs `sorted(clean.keys())` — **column NAMES only**.
   - The new exception and the new 400 response inherit that rule exactly: column names and the
     constraint name, never the offending value, never the row.
   - ⚠ asyncpg exceptions can carry a `detail` that echoes the rejected row. **Build the message
     from `exc.constraint_name` and the code-owned column list — never from `str(exc)`.**

2. **A settings READ must never crash a request (the reason the broad `except` exists).**
   - **Invariant:** the original broad catch was written so a pool blip cannot take down a request.
     That arm is **unchanged**: anything that is not a refusal still logs, still returns `False`,
     still becomes a 500.
   - ⛔ The new exception must not widen into an unhandled crash anywhere. Every call site is
     dispositioned in this plan — not most of them.

3. **SQL identifier integrity — unchanged.**
   - Column names reach the SET clause only via `_VALID_COLUMN_NAME`. This plan touches the
     `except`, never the filter loop or the clause builder.

4. **Encrypt-on-write — unchanged.**
   - The `SECRET_COLUMNS` loop runs before the UPDATE and is untouched. ⛔ A refusal path must not
     create a branch that skips encryption on a retry.

5. **A refused SETUP write must not read as a completed setup.**
   - `setup.py:469` writes `setup_complete: True`; `setup_service.py:342` returns the bool directly.
     If a refusal there were swallowed, the app would report itself configured when it is not.
</threat_model>

**GREEN — `backend/app/models/user_settings.py`.**

1. Add the typed exception near the top of the module:

   ```python
   class SettingsWriteRefused(Exception):
       """The DATABASE REFUSED this settings write — a caller error, not a server fault.

       ⚠ DISTINCT FROM "the write did not reach the database". `save_app_settings` returns False
       for that (a pool blip, a reset connection) and the caller answers 500, which is correct.
       A CHECK / NOT NULL / undefined-column failure is a different fact: the value, or the
       column, is wrong — and the caller can only say so if it can tell the two apart.

       ⛔ CARRIES COLUMN NAMES AND THE CONSTRAINT NAME ONLY. Never a value: these rows hold API
       keys (T-081.1-04). Built from `exc.constraint_name` and the CODE-OWNED column list, never
       from `str(exc)`, whose `detail` can echo the rejected row.
       """
       def __init__(self, columns: list[str], constraint: str | None):
           self.columns = columns
           self.constraint = constraint
           super().__init__(
               f"The database refused this settings write. columns={columns}"
               + (f" constraint={constraint}" if constraint else "")
           )
   ```

2. Split the `except`, refusal arm FIRST:

   ```python
   except (asyncpg.exceptions.CheckViolationError,
           asyncpg.exceptions.NotNullViolationError,
           asyncpg.exceptions.UndefinedColumnError) as exc:
       # THE DATABASE DID ITS JOB AND SAID NO. Distinct from "we could not reach it" below —
       # BUG-260909-01: this used to be swallowed into the same False, so three out-of-range
       # writes in a row all reported ACCEPTED while the DB rejected every one. Column NAMES
       # and the constraint name only (T-081.1-04).
       _constraint = getattr(exc, "constraint_name", None)
       logger.error(
           "save_app_settings: DB REFUSED the write; settings NOT persisted. columns=%s constraint=%s",
           sorted(clean.keys()), _constraint,
       )
       raise SettingsWriteRefused(sorted(clean.keys()), _constraint) from None
   except Exception:
       # unchanged — the write did not reach the database
       ...
       return False
   ```

⚠ `raise ... from None` is deliberate: the chained asyncpg exception's `detail` can carry the
rejected row, and a 500 handler that renders `__cause__` would leak it.
⚠ `logger.error` **without `exc_info=True`** on the refusal arm, for the same reason — the traceback
frames carry the bound values.
