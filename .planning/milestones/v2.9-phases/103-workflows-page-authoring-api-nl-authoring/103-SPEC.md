# Phase 103: Workflows Page + Authoring API + NL Authoring — Specification

**Created:** 2026-06-14
**Ambiguity score:** 0.148 (gate: <= 0.20)
**Requirements:** 7 locked

## Goal
A domain expert can describe a workflow in plain language, receive a one-shot validated `WorkflowDefinition` draft, refine it by form on a read-only vertical phase-spine graph, publish it through the existing 8-stage gauntlet (rendered verbatim from `PublishVerdict`), and launch it from a project-filtered Workflows page into a new chat thread in workflow mode — with no drag-to-build canvas, no new runtime, no router, and Deep chat byte-identical.

## Background

The v2.8 harness engine runs locked, ordered, multi-phase workflows. v2.9 Phase 103 gives that engine an **authoring + browse + launch face** — it COMPOSES the shipped engine and never re-implements it.

**Shipped today (Phase 103 composes these — do NOT re-spec as net-new):**
- **Two backend routes only** on `backend/app/api/workflows.py` (`APIRouter(prefix="/workflows")`): `GET /workflows/published` (route `get_published_workflows`, owner-scoped via `list_published_workflows`' RLS-mirroring predicate, optional `project_folder_id: UUID|None` query param) and `POST /workflows/{definition_id}/publish` (route `publish_workflow`). The file header explicitly states the publish endpoint "joins THIS router, NEVER api/threads.py."
- **The 8-stage publish gauntlet** orchestrated by `publish_service.publish` (`backend/app/services/harness/publish_service.py`): owner check → definition-valid → `business_requirement` → lint → interactive-phase → real golden run → structural-gate → judge → flip. Returns `PublishVerdict` with exactly 5 fields — `published: bool`, `version: int|None`, `golden_run_id: UUID|None`, `blocked_stage: str|None`, `named_failures: list`. The 10 real `blocked_stage` codes: `not_found`, `already_published`, `definition_invalid`, `business_requirement`, `lint`, `interactive_phase`, `golden_run_timeout`, `golden_run_error`, `structural_gate`, `judge`. HTTP mapping (verified verbatim at `workflows.py:128-143`): `not_found`→404, `already_published`→409, `business_requirement`→400-with-verdict-in-detail, every other block + success→200-with-verdict-body.

## Requirements

### REQ-1 — **Draft CRUD API + persistence (WFAUTH-01)**
A user can create, read, update, list, and delete a workflow **draft** through net-new routes on the existing `/workflows` router and DB helpers, and a publish attempt with `lint_workflow()` returning ≥1 error is blocked at `blocked_stage='lint'` (never published).
- **Current:** Only `GET /workflows/published` and `POST /workflows/{definition_id}/publish` exist. `db/workflows.py` has `get_definition`/`list_published_workflows`/`publish_definition`/`create_workflow_run`/`write_audit` but **no** `create_workflow_definition`/`update_workflow_definition`/`delete_workflow_definition`/`list_draft_workflows`. Lint already runs inside `publish_service.publish` as gauntlet stage 1.
- **Target:** Add `create_workflow_definition`, `update_workflow_definition`, `delete_workflow_definition`, `list_draft_workflows` to `db/workflows.py` and the matching `POST` (create) / `PATCH` (update) / `DELETE` (delete) / `GET` (list-drafts) routes to the **same** `APIRouter(prefix="/workflows")` in `api/workflows.py`. Create/update bind `created_by=auth.uid()`, `is_global=false`, `status='draft'`. Update of a row whose `status='published'` is rejected by the DB trigger (Postgres 23514) → surfaced as **HTTP 409 Conflict** (mirroring the existing `already_published`→409 mapping), never a silent overwrite. The publish path is unchanged — lint stays inside `publish_service.publish`.
- **Acceptance:** PASS iff: (a) `POST /workflows` with a valid draft body persists a `status='draft'` row and returns its id+version; (b) `GET` list-drafts returns only the caller's drafts (RLS owner-scope — a second user's draft is absent); (c) `PATCH` mutates a draft and round-trips the change; (d) `DELETE` removes a draft and a subsequent read 404s; (e) a `PATCH`/`DELETE` against a published row is refused with **HTTP 409** and no mutation persists (re-read shows the published row unchanged; the DB trigger raises 23514); (f) publishing a draft for which `lint_workflow()` returns ≥1 `LintError` returns `PublishVerdict.published=false`, `blocked_stage='lint'`, and `named_failures` carries the lint findings (rendered with the LOWERCASE `LintError.code` literals); (g) `backend/app/api/threads.py` is untouched.

### REQ-2 — **NL one-shot structured generation with single auto-retry + grounding fidelity (WFAUTH-02)**
A user can describe a workflow in natural language and receive a `WorkflowDefinition` that passes `model_validate()`, generated one-shot via a forced `emit_workflow_definition` tool over `WorkflowDefinition.model_json_schema()`, grounded in the project folder tree + tool/skill registry + any uploaded template; an invalid generation auto-retries **exactly once** against the validation error, then fails honestly.
- **Current:** No production NL-generation path exists (grep = 0 matches in `backend/app`). The pattern is proven only in `scripts/spike-097/authoring_feel.py`.
- **Target:** A net-new `POST /workflows/generate` route on the `/workflows` router that: forces the `emit_workflow_definition` tool with `input_schema = WorkflowDefinition.model_json_schema()`; calls the provider via the **existing provider gateway** (no new SDK path, no agent loop); runs `WorkflowDefinition.model_validate()`; on `ValidationError` retries ONCE with the validation error appended to the prompt; on a second failure returns an honest structured failure (NOT a partial/broken "draft"). The route emits a structured log/trace event `nl_generation_attempt` carrying an integer `attempt` index (1, then 2 only on first-pass `ValidationError`). Grounding context (project folder tree, tool/skill registry, uploaded template placeholders) is assembled server-side and injected into the generation prompt. The uploaded template (when present) is supplied to `/workflows/generate` by **reusing the existing Phase 101 template-asset path** (`AssetRef` / template-asset service) — i.e. the request references an already-ingested asset or passes placeholders in the body; **no net-new upload-validate endpoint is built** (see Boundaries). Confirm the template-asset supply mechanism at discuss-phase. The route returns a draft definition object the Builder renders whole; it does NOT auto-persist (persistence is REQ-1's explicit create).
- **Acceptance:** PASS iff:
  - (a) a valid NL prompt yields a definition that `model_validate()` accepts and whose `phases` are renderable; a valid first pass makes **exactly ONE** provider call (gateway call count == 1 / one `nl_generation_attempt` event with `attempt=1`) and fires **zero** retry events;
  - (b) a forced first-pass `ValidationError` (seed an unsatisfiable prompt or mock a first-pass invalid emit) triggers **exactly TWO** provider calls total (`attempt=1` then `attempt=2`) and **NO third call** — verifier asserts the count via the gateway call count / LangSmith trace span count / the `nl_generation_attempt` log sequence;
  - (c) a second-failure response never carries `published`/a runnable draft — it is an explicit structured error the UI surfaces as "could not generate," not a silent broken draft;
  - (d) **grounding fidelity (distinct from `model_validate()`, which is shape-only):** in a generated definition, every phase `folder_scope` / top-level `project_folder_id` UUID resolves within the bound project's folder subtree, and every `available_tools` / `skill_ref` is a member of the real tool/skill registry (no hallucinated folder UUID or non-registered tool/skill);
  - (e) the SC#10 cross-provider VALIDATION rows (REQ-7 / VALIDATION.md) pass — generation works on a reasoning-native provider (DeepSeek/Moonshot) and a tool-sensitive provider (GLM/MiniMax), not only OpenAI.

## How we'd know this failed (G-6)
- NL-gen emits an invalid/unparseable definition that reaches the user as a "draft" — i.e. a `model_validate()` failure surfaces as a renderable draft instead of an honest "could not generate," OR the auto-retry fires more/fewer than once (provider-call count ≠ 1 on success / ≠ 2 on first-pass invalid, or a third call appears).
- NL-gen passes `model_validate()` but the definition is ungrounded — it invents a `folder_scope` UUID outside the bound project subtree or references a non-registered tool/skill (shape-valid but grounding-broken — the exact silent-invalid-draft class G-6 exists to catch).
- A structurally-broken workflow (orphan phase / no terminal / unsatisfiable skip / bad index / unsatisfied input) publishes anyway — i.e. a `blocked_stage='lint'` verdict is treated as success.
- The graph offers any drag interaction, connection handle, `draggable=true` node, or add-node — the contract is read-only.
- Clicking Publish shows a re-derived/optimistic verdict (client recomputes `published`/`blocked_stage`) instead of the server `PublishVerdict`, OR a binary `200=ok/else=error` handler mislabels a 200-with-block as success.
- The judge block shows an enabled "publish anyway"/override, OR an absent/unproducible verdict (`named_failures` bare strings / missing `criterion`) defaults to `published=true`.
- A published definition gets mutated in place (Tweak UPDATEs the frozen row instead of INSERTing a new version; or the trigger is bypassed), OR the fork's `version` is wrong (reuses `vN` and trips `UNIQUE(slug,version)`, or hardcodes `v2`) so versioning is not actually exercised.
- `Run` leaves you on the Workflows page (renders a live run on the page) instead of creating a thread + switching to Chat, OR it switches the view but never kicks off a server-side run (no `active_workflow_run_id`), OR it uses a bespoke `/workflows/{id}/run` instead of `POST /threads/{id}/messages` with `workflow_definition_id`.
- A published-row mutation rejection returns an ambiguous/wrong HTTP code (not 409) or, worse, silently overwrites the frozen row.
- Adding the page breaks Deep chat (the named Deep functions diff non-additively, or the Deep UAT row regresses), removes the composer picker, adds `react-router`, or touches `threads.py`/`anthropic_service.py` in a breaking way.
- NL-gen works on OpenAI but silently fails on a reasoning-native provider (DeepSeek/Moonshot) or drops tools on GLM/MiniMax — i.e. the SC#10 rows are green on one provider and red/silent on another.
- The tier badge reads a stored/free-text strictness label or shows an invented "level 1/2/3"/"compliance mode" instead of being derived client-side by `deriveTier()` from the real `(citation_policy, validator-kind set)`.
