<objective>
Close gap CR-01 (verification truth #5, BLOCKER): the materializer in `skill_snapshot.py`
reads `row.get("files")` from a `skills`-table row, but the `skills` table has NO `files`
column — skill files live in the separate `skill_files` table (`017_skills.sql`). In
production `filenames` is therefore always `[]`: zero Storage copies happen, the snapshot
manifest is always empty, every `read_skill_file` in a skill-bearing phase errors with "not
in the workflow's skill snapshot", and the empty manifest is persisted to the
`workflow_definitions` JSONB and locked by the idempotency check.

Fix: query the `skill_files` table for the manifest inside `materialize_skill_snapshots`,
exactly mirroring `_handle_load_skill` in `tool_dispatcher.py:375-381`. Then de-mock the
test fakes so `_FakeSkillsDB` models the real two-table shape and can no longer carry a
`files` key the production `skills` schema lacks.

Purpose: make the file half of WFSKILL-01 functional in production — the snapshot manifest
is populated, files are physically copied, and `read_skill_file` can serve them.
Output: a corrected materializer + de-mocked tests that fail against the old (broken)
materializer and pass against the fixed one.
</objective>
