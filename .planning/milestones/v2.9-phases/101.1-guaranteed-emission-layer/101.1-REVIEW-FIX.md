### WR-01: Engine emits `phase_completed` (audit + SSE) for a phase it just marked `failed`

**Files modified:** `backend/app/services/harness_engine.py`, `frontend/src/lib/api.ts`, `frontend/src/providers/StreamsProvider.tsx`
**Commit:** b059deef
**Applied fix:** Guarded the post-completion bookkeeping on the branch taken. A
failure-bearing output now writes a `phase_transition` audit row with
`via: "emit_failed"` + the failure token (the 069 CHECK constraint has no
`phase_failed` kind; the executor's `emit_failed`/`emit_rejected` receipts carry the
detail) and emits a NEW additive `phase_failed` SSE instead of `phase_completed`.
Frontend: `api.ts` gained the `onPhaseFailed` dispatch branch (no `return` — cursor
still advances) and StreamsProvider maps it to
`setPhaseStatusForThread(threadId, phase, "failed", { error })` — required because the
finalize sweeps (`finalizeEarlierPhasesForThread` / `finalizeAllPhasesForThread`) flip
any non-terminal phase to "done"; only an explicit `failed` status survives them, which
closes the live "✓ Complete pill over the failure alert" mixed signal. The
run-continues decision is now EXPLICIT (per review: "decide explicitly"): the run
proceeds to the next phase and terminalizes `completed` — conservative per the
project's run-level-semantics constraint (the gap-4 terminal refetch keys off
`run_completed`).
**Status note:** fixed: requires human verification — semantic event-flow change;
covered by source/sweep tests but the plan-10 live re-verify should observe a failed
fill phase rendering a red card (not a green pill) live.
