# 282-04: Local models get a longer default timeout, and you can set one when adding a model

## Objective

Local (self-hosted) models are slower. One that is not registered must not run at the 300 s cloud default
with no way to change it short of a second edit. (FIX-06 follow-up; operator decision at the G-4 sign-off,
2026-10-15.)

## Tasks

### Task 1 (TDD): resolver default by provider (D-27, D-28)

1. **RED:** create `test_282_local_timeout_default.py`:
   - sync and async resolvers: `lmstudio` / `ollama` / `custom` with an unknown id → 900; `openai` / None → 300;
   - an env override and a DB row value still win;
   - async with no kwarg but a DB row whose provider is lmstudio and whose timeout is null → 900;
   - a source fence that each of the four call sites passes the provider.

   Run it and watch it fail.
2. **GREEN:**
   - Add `DEFAULT_LLM_CALL_TIMEOUT_SECONDS_SELF_HOSTED = 900` and a `provider` kwarg on both resolvers; tier 4 reads the predicate.
   - Wire the 4 call sites.

### Task 2 (TDD): Timeout on Add model by ID (D-29)

1. **RED:**
   - Backend: add-model 1801 → 422 with the PATCH sentence; 0 → 422; a legal 900 is in the upsert columns.
   - Frontend: the Timeout input exists; its placeholder flips 300 → 900 when the provider changes to lmstudio; blank omits the key; a typed 1200 is sent as a number.
2. **GREEN:**
   - One `_timeout_out_of_range_detail(lo, hi, val)` helper, used by the PATCH and the add.
   - The field joins `_ADD_MODEL_CAP_COLUMNS` and `AddModelBody`.
   - A `CapField` input in the form.

2. Run the backend baseline (≤ 71, set-equal to base).

6. Live drive, on the operator's backend after a restart:

## How we'd know this failed (G-6)

- An unregistered LM Studio model still resolves to 300.
- A cloud model's default changes.
- A stored value stops winning.
- The add accepts 1801.
- A blank Timeout writes a value.
- A second self-hosted list appears.
