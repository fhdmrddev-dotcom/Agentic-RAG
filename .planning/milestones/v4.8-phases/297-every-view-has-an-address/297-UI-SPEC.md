# Phase 297 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase is mostly plumbing (addresses, history, a router). It adds no design language.** G-2 is
not triggered, by decision (CONTEXT D-14, D-22). Three user-visible surfaces exist, and each one
reuses markup, tokens and copy the product already ships:

| # | Surface | Reuses | Decision source |
|---|---------|--------|-----------------|
| S1 | "This address doesn't open anything" state | `UnknownViewFallback`'s container (`frontend/src/components/layout/UnknownViewFallback.tsx`) + the shadcn `Button` | D-14, D-35, D-36 |
| S2 | Holding state while features / the operator probe load on a cold deep link | `WorkflowRunPage.tsx:1134-1140` loading markup and its `COPY_LOADING` sentence | D-19, D-34, D-35 |
| S3 | Unsaved-edit prompt on Back/Forward or a rail click | native `window.confirm(UNSAVED_LEAVE_PROMPT)` (`builderCopy.ts:173-174`), called through the Builder's own `canLeave()` | D-21, D-22, D-31, D-32 |

**No new tokens.** Every class below already exists in `frontend/src/index.css` /
`frontend/tailwind.config.js` (Aether Intelligence, Deep Midnight theme). No new font, colour,
spacing value, icon, animation, or shadcn block is introduced.

## Surface Contracts

### S1 — "This address doesn't open anything" (D-14, D-35, D-36)

**When it renders** (the parser's `not-found` result; never chat):
- an `/app/...` path with no known route (D-14);
- a bare path with no known prefix, e.g. `/foo` (D-36). Only bare `/` is chat;
- `/app/runs/<x>` where `<x>` is not a strict UUID (D-12);
- `/app/admin` or `/app/admin/spend` for a non-operator, once the operator probe has resolved (D-35).
  The copy is identical to an unknown address, so the state is not an existence oracle
  (RESEARCH Security, V4).

**Where it renders:** inside the layout, in the main content region, as the FIRST arm of
`AppViewSwitch`'s non-chat ternary (RESEARCH Pitfall 6). The nav rail stays visible and usable. The
chat history column and the chat grid are NOT rendered (the outer chat condition is gated
`activeView === "chat" && !addressNotFound`, and the history-column condition the same way). The app
never shows the Iris boot splash for this state.

**Component:** a new sibling of `UnknownViewFallback` in `frontend/src/components/layout/` (name is
Claude's discretion per CONTEXT; working name `AddressNotFound`). It must NOT render
`<UnknownViewFallback`, because `ChatLayout.launch.test.tsx` and `activeViewReachability` resolve that
tag's position and it must keep exactly one home, as the trailing arm.

**Markup** (`UnknownViewFallback`'s container classes verbatim, plus `gap-3 text-center` for the three stacked lines):

```tsx
<div className="flex flex-col items-center justify-center h-full p-8 gap-3 text-center">
  <h1 className="text-base font-medium text-foreground">{COPY.heading}</h1>
  <p className="max-w-sm text-sm text-muted-foreground">{COPY.body}</p>
  <Button variant="outline" size="sm" onClick={() => onNavigate("chat")}>{COPY.cta}</Button>
</div>
```

**Interaction:**
- The CTA calls the existing `onNavigate("chat")` navigator ChatLayout already receives. No new prop
  path, no `useNavigate` in the leaf (D-08).
- It is a `push` (D-15: a user-initiated top-level view change), so browser Back returns to the
  address the person opened. That is honest browser behaviour; the state renders again.
- The requested path is never echoed in the UI (RESEARCH Security: content spoofing). Fixed copy only.
- No auto-redirect, no timer, no toast.

**Accessibility:**
- The heading is an `<h1>`. It is the only heading in the main region while S1 shows.
- The CTA is a real `<button>` reachable by Tab, with the `Button` default `focus-visible:ring-2
  ring-ring ring-offset-2` ring.
- Focus is NOT moved on mount. Focus-on-navigate is app-wide and deferred to Phase 299 (CONTEXT,
  Claude's Discretion). Doing it for one state would make it behave differently from every other view.
- No `role="alert"`. This is a destination, not an interruption.

**Rail highlight:** `NavPanel.tsx` (14 phases, hot) is NOT edited. While S1 shows, the rail's current
item is whatever the derived view reports (Chat). This is accepted for 297 and recorded; 299's
`LinkNotFound` owns a corrected rail state.

### S2 — Holding state on a cold deep link (D-19, D-34, D-35)

**When it renders:**
- cold `/app/runs/<uuid>` while `featuresLoading === true` (the canvas gate has not resolved yet);
- cold `/app/admin` or `/app/admin/spend` while the operator probe is `loading`.

**Where it renders:** INSIDE `AppViewSwitch`, in the same branch as the view it is holding for (the
run hold sits in the existing `activeView === "workflow-run"` arm, so the stripped comparison count
stays 1). Never at App level, never as the Iris splash: `refetch()` flips loading back to true, and an
App-level hold would unmount `StreamsProvider` (D-34, RESEARCH Pitfall 3).

**Markup** (verbatim from `WorkflowRunPage.tsx:1134-1140`, plus `role="status"` on the wrapper):

```tsx
<div role="status" className="flex h-full flex-col items-center justify-center gap-3 px-6 text-center">
  <p className="text-sm text-muted-foreground">{sentence}</p>
</div>
```

**Copy:**
- Run hold: `Opening the run…` — the SAME sentence as `WorkflowRunPage`'s `COPY_LOADING` (export the
  const or move it to run vocabulary; one spelling, the planner's choice). Because the markup and the
  sentence are identical, the hand-off from the S2 hold to `WorkflowRunPage`'s own loading state is
  invisible: the person reads one sentence, in one position, from first paint until the run renders.
- Admin hold: `Opening…`. This is neutral by design: it names nothing, so it reveals nothing to a
  non-operator before S1 replaces it.

**Must never appear while holding** (each is a failure, see below): the chat grid, `UnknownViewFallback`
("This view has no screen: …"), S1, a refusal, the Control Room or Spend page, a skeleton spine, a
spinner ring. There is no minimum display time and no artificial delay.

**After the hold resolves:**
- run, canvas on → `WorkflowRunPage` (unchanged);
- run, canvas off → the existing trailing `UnknownViewFallback` (unchanged; pinned by
  `ChatLayout.launch.test.tsx` "a stale workflow-run view renders the UnknownViewFallback …"). The
  canvas flag is ON for everyone in production, so this is a dev or self-hosted edge;
- admin, operator → the console (unchanged); admin, non-operator → S1.

**No chat flash on normalization:** a legacy or bare address (`/app?run=<uuid>`, `/workflows`,
`/admin/spend`) is parsed into its view BEFORE first paint, and then `replace`d to canonical. The
first frame is the target view (or its S2 hold), never chat followed by a swap.

### S3 — Unsaved-edit prompt (D-21, D-22, D-30, D-31, D-32)

**Copy is unchanged, byte for byte:** `This draft has unsaved changes. Leave without saving?`
(`UNSAVED_LEAVE_PROMPT`, `frontend/src/components/workflows/builderCopy.ts:173-174`). Native
`window.confirm`, no custom dialog, no new button labels (the browser's own OK / Cancel).
`WorkflowBuilderPage.tsx` is not edited (D-31).

**Interaction:**
- Asked on browser Back, browser Forward, and any rail click away from Workflows, while the Builder
  reports dirty. The only tenant in 297 is the Workflow Builder (D-30).
- OK → the navigation completes (`proceed()`).
- Cancel → the person stays in the Builder, the edits are kept, and the address bar reads the
  Builder's address again (`reset()`). No toast, no banner.
- Asked EXACTLY ONCE per leave attempt. The in-page breadcrumb, the connect control and the golden-run
  link keep their existing in-page check, and the one-shot latch stops the app-level blocker asking a
  second time (D-32, RESEARCH Pitfall 7).
- Test Run never shows the prompt (D-32: today's behaviour kept; the latch covers its route change).
- Never asked on a clean editor (D-24).
- Never asked on a server-forced exit (the 403 visibility bounce), so Cancel can never strand a person
  on a refused surface (RESEARCH Pitfall 8; the planner records the mechanism under a `D-297-NN`).
- Refresh and tab-close stay on the existing `beforeunload` (unchanged; the browser owns that copy).

### Navigation behaviour visible to the person (no new UI)

- Back and Forward swap the main region instantly. No transition, no fade, no scroll restoration
  (CONTEXT Claude's Discretion: views scroll inside fixed containers).
- The rail's current item follows the address on Back/Forward, exactly as it follows a rail click
  today (it reads the same derived view).
- A chat answer that is streaming keeps streaming, with no gap and no re-render of the message list,
  across any number of navigations (D-10).
- `document.title` does not change per route in 297 (deferred to 299).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (S1) | `Go to Chat` ("Chat" matches the rail label in `nav-items.ts:31`) |
| Empty state heading (S1) | `This address doesn't open anything` (locked phrase, D-14) |
| Empty state body (S1) | `It may be mistyped or out of date.` |
| Holding state (S2, run) | `Opening the run…` (existing `COPY_LOADING`, reused) |
| Holding state (S2, admin) | `Opening…` |
| Error state | None new. An unopenable address is S1, not an error. Existing per-view error states are unchanged |
| Leave confirmation (S3) | Leave the Builder with unsaved edits: `This draft has unsaved changes. Leave without saving?` (existing, verbatim) |
| Destructive confirmation | None. This phase adds no destructive action |

Voice rules for the new strings (Syrel voice): plain words, sentence case, no blame ("you typed"),
no jargon ("404", "route", "URL", "not found"), no exclamation, no apology. The copy constants live in
ONE home (the S1 component module, e.g. `ADDRESS_NOT_FOUND_COPY`), and tests assert the rendered
words, not a `data-testid` alone (presence assertions cannot see content drift).

## How we'd know this failed (UI)

- Any address, known or unknown, paints chat first and then swaps.
- An unknown or malformed address renders chat, a blank region, or "This view has no screen: …".
- A cold `/app/runs/<uuid>` shows "This view has no screen: workflow-run", S1, or chat for any frame
  before the canvas flag resolves.
- A non-operator typing `/app/admin` sees the console, chat, or copy that differs from an unknown
  address.
- S1 shows the requested path, uses red/amber, or carries an icon.
- The nav rail disappears, or the Iris splash shows, on any in-app navigation.
- The leave prompt's wording differs from `UNSAVED_LEAVE_PROMPT`, appears twice for one Back press,
  appears on a clean Builder, appears on Test Run, or does not appear on browser Back with a dirty
  draft. Cancel loses the edit or leaves the address bar on the destination.
- The run hold and `WorkflowRunPage`'s loading state show two different sentences.

G-4 lived-experience scenarios are set in CONTEXT D-28 (rows 1-4); rows 1 and 4 exercise S2 and the
no-chat-flash rule, row 3 exercises S3. Add one G-4 check for S1: paste `/app/nonsense` into a fresh
tab → S1 renders inside the layout with the rail visible; "Go to Chat" opens chat; Back returns to S1.
