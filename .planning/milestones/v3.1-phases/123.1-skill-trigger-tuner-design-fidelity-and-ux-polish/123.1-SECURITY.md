## Load-bearing IDOR findings (the audit's primary directive)

**T-123.1-07-02 (the critical one) is CLOSED and NON-VACUOUS.** Two independent layers:

1. **Route guard present** — `cancel_tuner_run` (`skill_tuner.py:982-1041`) runs the checks in
   the correct order: (1) `_fetch_owned_or_global_skill` (owner gate, `:1023`), then (2) the
   run↔skill bind `redis.zscore(runs_by_thread:tuner:{skill_id}, run_id) is None → 404`
   (`:1026-1030`). The TTL'd `tuner_cancel:{run_id}` flag is set ONLY after BOTH gates pass
   (`:1038`). The same run↔skill bind is enforced on the stream route (`:800-804`) and the
   results route (`:901-925`, accepting live membership OR a durable `tuner_runs` row whose
   run_id matches), closing the shared `run:{run_id}` keyspace.

2. **Test is genuinely non-vacuous** — `test_cancel_foreign_run_id_returns_404`
   (`test_skill_tuner_routes.py:1695`) authenticates as OWNER (who CAN see the skill — the skill
   gate passes), supplies a FOREIGN `run_id` that was never ZADDed into
   `runs_by_thread:tuner:{SKILL_ID}` (membership set deliberately empty), and asserts: 404 with
   `detail=="Tuner run not found"` (the BIND 404, not the skill 404), the `tuner_cancel` flag is
   NEVER set for the foreign run_id, AND a pre-seeded unrelated in-flight claim is NOT released.
   The fake redis's `zscore` (`:66-70`) and CAS `eval` (`:93-106`) emulate real Redis semantics,
   so the gate is actually exercised — not stubbed to pass. The sibling
   `test_visible_skill_foreign_run_id_returns_404_both_routes` (`:294`) additionally plants a
   secret buffer at `tuner_result:{foreign_run_id}` and asserts the marker is NOT present in
   either the results or stream response body (`:346-349`) — proving non-exfiltration, not just
   a status code.

**T-123.1-07-01** — `test_cancel_cross_user_returns_404` (`:1655`) drives OTHER_USER against an
OWNER-only skill, asserts 404 + the owner-scope SELECT actually ran + no flag set. Non-vacuous.

## Defense-in-depth observation (non-blocking, no reopen)

`tuner_runs` RLS ships a SELECT policy only (owner OR global-skill), with writes via the
service-role client that bypasses RLS by design (mirrors `035_runs_table.sql`). The app-code
owner-scope gate (`_fetch_owned_or_global_skill`) is the SOLE read-side leak gate; the RLS is
defense-in-depth for any future RLS-respecting reader. This matches the migration's documented
intent (`077_tuner_runs.sql:17-22`) and is the established project pattern — recorded as an
observation, not a gap.
