# Phase 292.1: Code Review Report

**Reviewed:** 2026-10-24
**Depth:** standard (scoped to `git diff 9d3b77c88..HEAD`, plus the call paths the diff depends on)
**Files Reviewed:** 19
**Status:** issues_found

## Summary

The parser (`text_tool_calls.py`) is strict where it matters. A tool name outside the run's offered set refuses the whole block, and the offered set is built with the same expression the dispatcher's `available_tools` uses (`agent_loop.py:2858` and `:3207-3210`), so a call written as text cannot reach a tool the native path could not. I fed `TagHoldback` 200 random chunkings of four inputs, and `released + finish()` always equalled the input. The settings bounds agree in all three places (API 2..50, CHECK 2..50, UI clamp 2..50), and the UI never sends 0.

**The two blockers come from one wrong premise.** The new code assumes a paused Deep run's `runs.status` reads `cap_paused`. A FIRST-turn pause never reads that. The first-turn producer starts with `_terminal_status = "completed"` (`run_producer.py:729`) and has no `cap_disposition` override (only the continuation has one, at `:1166-1169`). So it finalizes the paused run as `completed` and emits the terminal `done`.

I checked this against the local database rather than inferring it:
- `SELECT count(*) FROM runs WHERE status='cap_paused'` returns **0**.
- Every `iteration_cap_paused` carrier I matched to the run that paused it (by `started_at <= carrier.created_at <= completed_at`) belongs to a run with `status='completed'`, `continues_used=0`, finalized about 5 seconds after the carrier. Examples: `5835720e…` (2026-10-03), `78784975…` (2026-10-03), `e4313e30…`, `5ec12235…`.

As a result, SEED-324's new 409 refuses the Continue button on every first pause, and the typed-continue gate can never fire on one. The new tests pin both behaviours as correct (`test_2921_continue_same_model.py:251-258` treats `completed` as refused; `test_2921_typed_continue.py:283` treats a `completed` latest run as a normal send). The tests agree with the defect.

What I drove and what I did not:
- **Drove:** the DB measurement above, the parser and holdback probes (WR-01, WR-06, IN-01) in a scratch script, and the code paths cited below by direct reading.
- **Did not drive:** a live HTTP Continue or a live typed continue against a running backend.

## Critical Issues

### CR-01: SEED-324's 409 refuses the Continue button on every first-turn Deep pause

**File:** `backend/app/api/runs.py:1251-1261` (cause: `backend/app/services/run_producer.py:729`, `:931-943`)
**Issue:** The new `elif row.get("status") in _TERMINAL_RUN_STATUSES` branch raises 409 for `completed`. A first-turn cap pause is written as `completed`: the producer's `_terminal_status` defaults to `"completed"` and, unlike the continuation (`:1166-1169`), never switches to `cap_paused`. `_finalize_producer_run` then calls `finalize_run_terminal(status="completed")` within seconds of the pause (5-6 s in the measured rows).

Failure scenario:
1. The user asks something that needs 15+ tool rounds.
2. The limit line and the Continue card appear.
3. The user presses Continue. `continue_run` reads `status='completed'` and returns 409 "This run has already finished, so there is nothing to continue."

That is the exact flow BUG-261024-03 exists to make work, and before this phase it did work: `continue_run` had no status check on the Deep side, and the measured rows with `continues_used=3` show Continue being used.

The code comment at `:1255-1257` ("the cap_paused SSE event precedes the finalizer's status write") assumes the finalizer writes `cap_paused`. It writes `completed`.

**Fix:** Pick one of these. Either way, change `test_2921_continue_same_model.py:251` so it no longer pins `completed` as refusable.
- **Preferred:** make a first-turn pause durable. In the first-turn producer's `finally`, mirror the continuation override so the single status writer records the truth:
  ```python
  # run_producer.py, first-turn finally, before _finalize_producer_run
  if _result_sink.get("cap_disposition") == "cap_paused" and _terminal_status == "completed":
      _terminal_status = "cap_paused"
  ```
  This also routes step 4 to the keep-active `finalize_run` and skips the `done` sentinel, the same way a re-pause works today. Re-check the RUN-01b gate and the boot reconciler (`run_reconciler.py:84` already treats `cap_paused` as non-terminal).
- **Otherwise:** decide "terminal" from the carrier, not from `runs.status`. Refuse only when the run is terminal AND the thread's latest `iteration_cap_paused` carrier is not newer than the run's `started_at`.

### CR-02: A typed "continue" never resumes a first-turn pause; it always starts a new run

**File:** `backend/app/api/threads.py:844`
**Issue:** The gate returns `None` unless `row["status"] == "cap_paused"`. A first-turn pause reads `completed` (CR-01's measurement), so every typed "continue" after the first limit line falls through to an ordinary new message. That breaks D-12, D-14 and G-4 row 3 ("typed continue resumes the paused run and `continues_used` increments").

The typed path only works after a continuation has re-paused, because only the continuation writes `cap_paused`. On the frontend, `shouldTryTypedContinue` (`continueWords.ts:38-45`) predicts a resume from the live lock, so it holds back the optimistic bubble. The server then answers 201 with a new run, and the bubble is inserted late (`StreamsProvider.tsx:2799`). So the user sees a delayed bubble and a fresh run instead of a resume.
**Fix:** The producer fix in CR-01 also fixes this. If the status writer is not changed, the gate has to identify a pause by its carrier (latest run terminal-`completed` AND a carrier written during that run). Re-pin `test_2921_typed_continue.py:283` against the real first-turn shape (a `completed` row that has a carrier) rather than a hand-built `cap_paused` row.

## Warnings

### WR-01: An answer that mentions `<tool_call>`, `<|tool_call>` or `<function=` in prose is truncated, and on the last round it causes a false pause

**File:** `backend/app/services/text_tool_calls.py:95-99`, `:162-174`, `:355-379`; `backend/app/services/agent_loop.py:2876-2880`, `:2020`
**Issue:** The XML and Gemma families are stripped from the opener to the closer, or to the end of the text when there is no closer. They are only skipped inside backtick code. I drove this:
- `"Qwen-style models wrap each call in <tool_call> tags, and the server parses them out. That is why you never see them."` comes back from `strip_markup` and `settle(...).visible` as `'Qwen-style models wrap each call in '`, with `kind='unparseable'`.
- `"In Gemma the marker is <|tool_call> and it closes with <tool_call|>; …"` loses its middle.

Consequences:
- **On a non-final round:** the answer is cut and replaced with "The agent's tool request was cut off or malformed, so it was not run." The text after the tag is never shown and never persisted.
- **On the forced-final round:** `_cap_markup_seen=True`, so a run that actually gave a real answer pauses with a limit line and a Continue.

This breaks D-10 ("a clean answer passes through byte-identical"). The trigger is realistic in this product: people ask about tool calling, and RAG answers quote documents verbatim.
**Fix:** For the non-DSML families, only treat a match as markup when it has the measured call shape, not just the bare opener. Two ways:
- Require the closer AND a parseable body: JSON with a `name` key for `<tool_call>`, or `<function=NAME>` with `NAME` in the offered set.
- Or require the opener to start a line or the whole message.

If the shape does not match, return `kind="none"` and leave the text byte-identical. Add the two strings above as pinned clean-answer cases.

### WR-02: Removing the adapter's DSML strip un-guards the sub-agent and harness phase paths

**File:** `backend/app/services/provider_gateway/openai_compat.py:164-169`, `:301-305`; consumers `backend/app/services/task_service.py:373-378`, `backend/app/services/harness/phase_types.py:123`
**Issue:** The deepseek-only strip lived in the adapter, so it covered every `open_stream` consumer. The phase deletes it and adds the replacement (`TagHoldback` + `settle`) only to `agent_loop`. `task_service._stream_one_iteration`, which is used by `task()` sub-agents and by harness workflow phases (`phase_types.py:123`), appends every `delta` straight into `content_parts`. So the two-bar `<｜｜DSML｜｜…` spelling the old strip caught now flows raw into:
- sub-agent results, which are fed to the parent, emitted in `tool_end`, and persisted in `messages.tool_calls`;
- harness phase outputs.

Before this phase, the two-bar spelling was suppressed on those paths. It is a regression there, and it violates D-08 / D-10's "never persisted, any route" intent.
**Fix:** In `_stream_one_iteration`, apply the same post-drain call: `settle(content, offered=set(tool names), buffer_has_calls=bool(buffer))`. Parse into `buffer` on `parsed`, use `.visible` otherwise. Or, at minimum, `strip_markup` the returned content. Add a test that drives a DSML delta through `_stream_one_iteration`.

### WR-03: Typed continue and the button can both spawn a continuation for the same pause, because `continue_run` has no compare-and-set

**File:** `backend/app/api/runs.py:1279-1298`; `frontend/src/components/chat/MessageItem.tsx:867`; `frontend/src/providers/StreamsProvider.tsx:2791-2797`
**Issue:** Step 4 reads `continues_used`, then runs `UPDATE … SET continues_used = N+1, status='streaming' WHERE run_id AND user_id`, with no `AND status='cap_paused'` and no `AND continues_used = N`. Both arms then call `spawn_continuation_run` for the same `run_id`.

The typed path adds a second door that the button's guard does not cover. `continuingThreads` is set only after the typed POST resolves, and the held-back optimistic path skips `streamingThreads`. So during the POST round trip the button is still enabled.

Failure scenario:
1. The user types "continue" and presses Continue before the POST returns.
2. Two continuation loops run on one `run_id`.
3. Each re-executes the queued tool calls (an MCP write runs twice) and both write the same Redis stream and runs row.
4. `continues_used` advances by 1 instead of 2, so the 3-Continue cap is bypassed.
5. `RUN_TASKS[run_id]` is overwritten, so the first task can no longer be stopped.

SEED-324's own stated aim ("a replayed request cannot re-drive") is also open, because `streaming` is accepted.

The `_typed_continue_or_none` docstring ("a race to the last Continue falls through") describes a refusal the code never produces. Not driven live.
**Fix:** Make step 4 an atomic claim and refuse when nothing is claimed:
```python
res = await aexec(service_supabase.table("runs")
    .update({"continues_used": _new_used, "status": "streaming"})
    .eq("run_id", str(run_id)).eq("user_id", current_user["id"])
    .eq("continues_used", continues_used))   # CAS on the counter
if not (res and res.data):
    raise HTTPException(409, "This Continue is already under way.")
```
The typed helper should map that 409 to "already continuing" rather than starting a new run. On the client, call `markContinuing(threadId)` before `postMessage` when `typedContinue` is true, and clear it on a 201 or an error.

### WR-04: `continue_run` errors escape the typed-continue gate instead of falling back to a normal send

**File:** `backend/app/api/threads.py:850-857`
**Issue:** The docstring and summary say failure modes "fall back to a normal send". Only a `refused` result does. Any `HTTPException` from `continue_run` propagates out of `send_message` and becomes the response to the user's message:
- 404 when the row is not visible;
- the new SEED-324 409, if status changes between the gate's read and `continue_run`'s read (for example, a boot reconcile sweeps `cap_paused`);
- 500 when the counter write fails.

Other exceptions are not caught either (for example, the `load_cap_paused_tool_calls` pool read or the spawn). In those cases the counter has already been incremented and the user's message is rejected.
**Fix:** Wrap the call. On `HTTPException` with status 404 or 409, return `None` (normal send). Log and re-raise only 5xx. Add tests that drive each arm.

### WR-05: AgentRoundLimits shows the defaults as the live values when the settings read fails

**File:** `frontend/src/components/settings/AgentRoundLimits.tsx:113-115`
**Issue:** `.catch(() => {})` leaves 15 / 8 on screen as if they were loaded. If the server holds 3 (the D-19 UAT setting) and the read fails, the operator sees 15. Typing 15 is then not "dirty" (`changes()` compares against the unloaded default), so it is never sent, and "✓ Saved" can appear for the other field while the cap stays at 3. The project has an explicit history with silent settings failures.
**Fix:** Track a `loadFailed` state. Render the server's error and disable Save until a successful load, or always send both fields once the user has edited either.

### WR-06: Anything after a parsed DSML block is silently dropped, including a second block's calls

**File:** `backend/app/services/text_tool_calls.py:211-214`, `:376-378`
**Issue:** `parse_dsml` parses only the first block, and `settle(kind="parsed")` returns `visible=preamble`. I drove `"Pre <DSML block> trailing prose here"`: the result is `kind='parsed'`, `visible='Pre '`, and the trailing prose is gone. Live and saved still agree because the holdback held it. But a second `…calls>` block, or a following `<tool_call>` block, is discarded with no log line and no notice. The model believes it made N calls and only the first block runs.
**Fix:** After the closer, run `settle` again on `text[close.end():]`. Append parsed calls with indices continuing from the first block. Strip and word an unparseable remainder, and keep trailing prose as visible text. At minimum, log it when the remainder is non-empty.

## Info

### IN-01: Raw DSML after an unclosed code fence is shown and persisted

**File:** `backend/app/services/text_tool_calls.py:120-123`
**Issue:** An opening fence with no closer counts as code to the end of the text, so a DSML block after it is classified `none`. I drove ```` "```\n…\n<｜DSML｜function_calls>…" ````: the result is `kind='none'`. The live holdback releases it raw at `finish`, and the save-point `strip_markup` uses the same code ranges, so the markup is persisted (D-08). This is uncommon, but it is the one route that bypasses both guards.
**Fix:** Treat an unterminated fence as code only up to the next tool-call opener at the start of a line. Or always parse DSML regardless of an unterminated fence.

### IN-02: The save-point log previews the start of the answer, not the markup, and the substituted notice was never streamed

**File:** `backend/app/services/agent_loop.py:2020-2029`
**Issue:** `preview=%r` logs `full_content[:200]`, the first 200 characters of the answer, so the line does not show the markup D-08 wants in the log. When the content is markup-only it is replaced with `FAILED_CALL_NOTICE`, which was never emitted as a delta, so live and reload differ (I-2) on this backstop path.
**Fix:** Log `full_content[detect_markup(full_content):][:200]`, and emit the notice as a delta when substituting.

### IN-03: Dead `dsml_leaked` attribute left behind

**File:** `backend/app/services/provider_gateway/openai_responses.py:277`
**Issue:** Nothing reads the flag any more (its reader at `agent_loop.py` was deleted), but `openai_responses.py` still sets it, and `test_openai_responses_adapter.py:438` still asserts it.
**Fix:** Remove the attribute and that assertion together.

### IN-04: The "chat" round cap also governs skill eval runs

**File:** `backend/app/services/agent_loop.py:1539`; `backend/app/services/eval_runner_service.py:600`
**Issue:** `eval_runner_service` calls `run_agent_loop` and so reads `chat_max_tool_rounds`. Lowering the knob for UAT (D-19), or in production, changes eval results and can produce cap-pause carrier rows in eval threads. The UI copy says "per chat turn".
**Fix:** Pass a fixed cap for eval runs (for example, via `RunContext`), or document the coupling in the hint.

### IN-05: The new tests encode CR-01 and CR-02

**File:** `backend/tests/unit/test_2921_continue_same_model.py:251-258`; `backend/tests/unit/test_2921_typed_continue.py:183-184`, `:283`
**Issue:** The fixtures hand-build a `status="cap_paused"` row that production never writes for a first pause, and they pin `completed` as "refused" and "normal send". They pass against the defect.
**Fix:** Build fixtures from the real producer shape: a `completed` row plus a carrier, or the fixed `cap_paused` row once CR-01's producer fix lands.
