## Common Pitfalls

### Pitfall 1: The reload-timer lie (D-095.1-05) is in the freeze instant, not the start baseline
**What goes wrong:** On reload of a finished run, `RunCard.tsx:111` sets `frozenEndRef.current = Date.now()` (the CURRENT clock) because `isStreamingNow` is false at first render. With `startMs = Date.parse(message.created_at)` (a day-old timestamp), `elapsedMs = Date.now() − createdAt` = a fabricated "1440m" duration. This is the exact BUG-260606-02 symptom.
**Why it happens:** The timer derives elapsed from `created_at` to current-clock, with the freeze captured at render time — correct for a LIVE streaming→terminal edge, WRONG for a run that was already terminal when the component mounted (reload).
**How to avoid:** When the message carries `startedAt` + `completedAt` (the new D-05 fields), a finished run's duration MUST be `completedAt − startedAt` (true persisted wall-clock), NOT `frozenEnd − created_at`. Live ticking stays for `runStatus === "streaming"`. A finished run with no `completedAt` shows NO duration (honesty rule), never a current-clock fabrication. Keep `created_at` as the LIVE-tick baseline only.
**Warning signs:** A reopened day-old run showing minutes/hours; the timer label growing on a terminal card.

### Pitfall 2: Panel precedence inversion (D-095.1-01)
**What goes wrong:** If the derived selector ALWAYS synthesizes from `tool_calls`, it overwrites a real `write_todos` plan (richer, the model's own statuses).
**Why it happens:** Forgetting the precedence: real `write_todos` (via `useTodos`/`todosByThread`, populated by SSE + `/todos` reconcile) wins; derivation is the FALLBACK only.
**How to avoid:** Precedence 1 = `useTodos(threadId)` non-empty → render those (today's behavior, untouched). Precedence 2 = empty AND smart gate passes → synthesize read-only. Precedence 3 = clean. Note `write_todos` is excluded from the meaningful-tool TALLY but keeps its own always-populate branch.
**Warning signs:** A real OpenAI write_todos plan replaced by generic "Run code" rows.

### Pitfall 3: `MEANINGFUL_TOOLS` drift — spike vs CONTEXT
**What goes wrong:** The spike-006 set (`{execute_code, search_documents, workspace_write, analyze_document, sub_agent}`) is NARROWER than CONTEXT's locked set and uses `sub_agent` instead of `task`.
**Why it happens:** The spike was a proof; CONTEXT broadened the set per operator ("substantive retrieval inclusive") and corrected the tool name.
**How to avoid:** Use the CONTEXT D-095.1-02 set VERBATIM as the named constant: Producers `{execute_code, workspace_write, workspace_delete, task, analyze_document, save_skill}` + Retrieval `{search_documents, query_documents, query_tables, web_search}`. Excluded-from-tally + meta lists per CONTEXT. (The actual sub-agent tool is named `task` — confirmed at tool_dispatcher.py:1090.)
**Warning signs:** A multi-step `query_tables`-only run staying clean when it should populate; a `task`-driven run not counting.

### Pitfall 4: `description` is nested in `args`, not top-level (RESEARCH FLAG #1)
**What goes wrong:** Reading `tc.description` (top-level) returns undefined — the frontend `ToolCall` type has NO top-level `description` field.
**Why it happens:** The LLM-written label is a tool PARAMETER (`execute_code.description`), so it arrives and persists inside `args`.
**How to avoid:** Read `tc.args.description` (string or undefined). For the derived label precedence: `write_todos.todos[].content` > `tc.args.description` > `infer_label(tc.args.code)` > `"Run code"`. All survive reload (FLAG #1 confirmed).
**Warning signs:** Derived panels showing only "Run code" for Anthropic runs that actually carried descriptions.

### Pitfall 5: D-03 classifier touching the gateway stream path
**What goes wrong:** Adding try/except into the adapter constructors to "classify at the boundary" mutates the byte-identical clean-move adapters and risks a Deep SSE skeleton diff across 8 providers.
**Why it happens:** Reading "classify at the gateway boundary" too literally as "inside the adapter generator."
**How to avoid:** Put a pure classifier function (`classify_provider_error(provider: str, exc: Exception) -> ErrorKind`) in a NEW `provider_gateway/errors.py` module (no event type, no generator touch). Call it from the consumer's existing `except (APIError, anthropic.APIError, google_errors.APIError)` block (agent_loop.py:2242), replacing the keyword `if` ladder at 2251-2280. The adapters stay untouched. This honors gateway separation (provider knowledge lives in the gateway package) without touching the stream.
**Warning signs:** Any diff inside `anthropic.py`/`google.py`/`openai_compat.py` generator bodies; a Deep byte-identical regression.

### Pitfall 6: Google's status signal is `.code` + `.status`, NOT `.status_code`
**What goes wrong:** A classifier that only reads `.status_code` (the OpenAI/Anthropic attribute) returns None for Google errors and falls through to "unknown".
**Why it happens:** Google's `google.genai.errors.APIError` uses a different shape: `.code` (int HTTP status, first init arg) and `.status` (string, e.g. `RESOURCE_EXHAUSTED`).
**How to avoid:** Branch the classifier by provider family. Anthropic/OpenAI-compat: prefer isinstance against SDK subclasses (RateLimitError→429, AuthenticationError→401, PermissionDeniedError→403, BadRequestError→400, InternalServerError→5xx) with `getattr(exc, "status_code", None)` fallback. Google: read `getattr(exc, "code", None)` (429→rate-limit) and optionally `getattr(exc, "status", "")` for the `RESOURCE_EXHAUSTED` confirmation. 402 (billing) is rarely a distinct HTTP code from these SDKs — treat billing as only-when-structurally-proven (e.g. `insufficient_quota` error code), else neutral.
**Warning signs:** Google 429 still reading as "billing" or "unknown".
