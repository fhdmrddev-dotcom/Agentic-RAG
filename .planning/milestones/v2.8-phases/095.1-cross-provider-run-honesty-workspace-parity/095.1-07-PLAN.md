<objective>
Close GAP-2: live attribution lag + turn-number inconsistency (RUN-HONESTY D-04
incomplete in the live moment). A just-finished run (no reload) shows run-sub
`turn 6` / `turn 4` (= iterationCount+1) with NO `provider·model`; after a reload
the SAME run shows `openai · gpt-5.4-mini · turn 1`. So (a) WHO answered is invisible
in the live moment until refresh, and (b) the turn number diverges live
(iterationCount+1) vs reload (iterationCount omitted → 1). It self-heals on any
refetch.

ROOT CAUSE (confirmed): Plan 03's enrich SELECT (`runs.model` / `runs.provider`)
runs ONLY on GET /messages (reload). The live SSE/dispatch message carries
`iterationCount` but not the enriched model/provider, so RunCard renders the
graceful `turn N` fallback (N from iterationCount). On reload, model/provider
arrive but iterationCount is dropped → turn 1. The two states disagree.

KEY ENABLER (already in code, no new resolution needed): the backend resolves
`_resolved_model` and `_resolved_provider` at `threads.py:921-954` — BEFORE
`insert_run` and BEFORE the dispatch JSONResponse returns. They are the exact same
values Plan 03's enrich SELECT reads back from `runs` on reload. So the fix is
purely additive metadata: surface those two already-resolved values onto the
dispatch response, thread them onto the live assistant placeholder, and reconcile
the run-sub turn so live and reload AGREE.

Purpose: make "which model answered" honest in the live moment and make the turn
number stable across live/reload — without touching the shared SSE chunk path
(the exact surface that caused the 075.x cross-provider cascade).

Output: additive `model`/`provider` on the dispatch response → the live message →
RunCard shows `{provider} · {model}` live; and the run-sub turn no longer reads
`iterationCount` so live == reload.
</objective>
