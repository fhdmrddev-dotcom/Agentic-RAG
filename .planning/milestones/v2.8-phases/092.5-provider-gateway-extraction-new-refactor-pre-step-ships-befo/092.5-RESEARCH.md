## Summary

The extraction surface is exactly where CONTEXT.md says it is, but **every cited line number has drifted** because CONTEXT.md was written against an old/cross-referenced map — `run_agent_loop` now lives at `agent_loop.py:826` (CONTEXT implied ~733/1317 by inheritance from the threads.py-era and task_service cross-refs). The §Line-Number Drift section is the corrected map; the planner MUST use it for `read_first` / `acceptance_criteria`.

The three provider branches are **already structurally separate** inside `run_agent_loop`'s `while True:` retry block (Anthropic `:1396–1528`, Google `:1530–1655`, OpenAI-compat `:1657–1974`). Each constructs its provider stream and defines an `async def _on_chunk_*` callback. The seam cut is clean and load-bearing: the gateway takes the **stream construction + the `_on_chunk_*` chunk→event normalization**; everything the `_on_chunk_*` callbacks MUTATE (`full_content`, `full_reasoning_content`, `input_tokens_total`, `output_tokens_total`, `_in_think_block`, `tool_calls_buffer`, the 5KB boundary dicts, `finish_reason`) is declared in `run_agent_loop` body BEFORE the loop (`:1052–1085` and per-branch) and STAYS on the consumer side. Anthropic + Google already emit a normalized event schema (their service docstrings ARE the canonical-event template); their adapters are largely a move of stream-construction. **The OpenAI adapter is the one genuinely entangled unit** — it carries STRUCTURED-mode `messages` mutation, the `<think>` state machine, `reasoning_content` routing, the per-provider 5KB boundary dicts, AND a post-stream `parse_structured_tool_calls` recovery that mutates `full_content`/`finish_reason`/`tool_calls_buffer`. That post-parse step is the trickiest seam decision (it runs AFTER the drain, reading the consumer's `full_content`) — see §OpenAI Adapter Entanglement, landmine L-3.

The Phase 089 byte-identical proof harness is **fully built and reusable as-is** — `scripts/capture_run_events.py` (capture/normalize/`diff_skeletons`), `scripts/capture_sse_baseline.py --mode before|after` (turnkey driver), `scripts/SSE_DIFF_RUNBOOK.md` (operator runbook), `scripts/eval_cross_provider.py` (native-7 scoreboard). The hard-won lesson encoded there: a RAW per-index diff is NOT a valid gate against live LLMs (same code produces 33/34/36 events run-to-run); the **structural skeleton** (`diff_skeletons`) is the SC#3 pass/fail gate. The planner reuses these verbatim; no new harness is needed for 089-style proof. The ONLY net-new test is the D-08 seam-contract test (synthetic-stream-in → canonical-events-out, fully deterministic, no live keys).

**Primary recommendation:** Extract in two provable steps — (1) the two CLEAN adapters (Anthropic + Google: stream-construction move only, since they already emit canonical events) behind a thin dispatcher, prove byte-identical; (2) the ENTANGLED OpenAI-compat adapter in isolation, with the post-stream `parse_structured_tool_calls` recovery decided explicitly (recommend: gateway yields the raw structured-mode signal but the consumer keeps owning `full_content`→parse→`tool_calls_buffer` mutation, since it touches consumer accumulators — see L-3). Run the 089 `--mode before` baseline against the PRE-extraction loop FIRST (Wave 0), `--mode after` per step.

### Pattern 1: WRAP the raw SDK boundary, do not re-derive it
**What:** Each adapter calls the existing `stream_*` / `create_adaptive_streaming_chat` and re-shapes (or passes through) the events. Anthropic + Google ALREADY yield canonical events (their docstrings are the template); their adapters are essentially `async for event in stream_anthropic(...): yield event` plus the stream-construction kwargs assembly currently inline in `agent_loop.py`.
**When to use:** all 3 adapters.
**Example (Anthropic/Google — clean):**

#   "tool_start"/"finish"/"usage"/"usage_delta", ...} — the canonical schema. No re-shaping.

### Pattern 2: ONE provider-agnostic consumer `_on_chunk` (D-02)
**What:** The three `_on_chunk_anthropic` / `_on_chunk_google` / `_on_chunk_openai` callbacks collapse into ONE handler that switches on `event["type"]` and mutates the STAY accumulators + calls `_emit`. Anthropic's and Google's handlers are ALREADY near-identical (the Google docstring at `agent_loop.py:1566-1573` literally says it's "structurally a copy of the Anthropic branch"). The OpenAI handler's body has extra logic (`<think>`, `reasoning_content`, the inline 5KB boundary computation) — that logic MOVES into the gateway's `openai_compat.py` so the OpenAI adapter EMITS the same canonical `delta`/`reasoning_delta`/`tool_args_progress`/`tool_preparing`/`tool_start` events the other two already emit. After the move, the single consumer handler is provider-agnostic.
**When to use:** the consumer side, post-extraction.

### Anti-Patterns to Avoid
- **"While-I'm-in-here" cleanup of the OpenAI branch** — the module docstring (`agent_loop.py:15-19`) warns a careless cleanup re-opens the entire 075.x cross-provider cascade. Extract VERBATIM; isolate the OpenAI adapter as its own provable step (D-04). Any behavior delta on a native-7 provider is a BLOCKER, not a thing to plan around.
- **Moving accumulation/emit into the gateway** — locked out by D-02/D-03. The gateway is a chunk→event normalizer, full stop.
- **Re-shaping Anthropic/Google events "for consistency"** — they are ALREADY the canonical template. Touching them risks a skeleton-diff on those axes for no gain.
- **Gateway importing `agent_loop`/`threads.py`** — re-creates the import cycle the callable-injection seam exists to avoid (Pitfall 4 from 089). Emit/spawn stay passed-in callables.

## Common Pitfalls

### Pitfall 1: Trusting CONTEXT.md's line numbers
**What goes wrong:** CONTEXT.md cites `stream_anthropic` ~:1396, `_on_chunk_anthropic` ~:1449, `stream_google` ~:1530/:1553, `_on_chunk_openai` ~:2294-2311, `_reconstruct_history` :733, `force_no_tools` :1367, iteration cap :1317. Several are right, several are stale, and `_on_chunk_openai` :2294-2311 is a *task_service cross-reference to the threads.py-era*, not the current location.
**Why it happens:** CONTEXT.md inherited line numbers from the 093-discuss live-code sweep (which mapped a mix of threads.py-era and post-089 locations) and from `task_service._consume_sync_stream`'s docstring comment.
**How to avoid:** Use the §Line-Number Drift table below as the single source of truth for `read_first` / `acceptance_criteria`. Re-grep before each task (the file is hot — 092 just shipped cap-pause edits into it).
**Warning signs:** A task's `read_first` points at a line that is mid-comment or in the wrong function.

### Pitfall 2: The OpenAI post-stream `parse_structured_tool_calls` recovery straddles the seam
**What goes wrong:** `parse_structured_tool_calls(full_content)` runs AFTER the drain (`agent_loop.py:1941-1962`), reading the consumer's `full_content` accumulator and mutating `full_content=""`, `finish_reason="tool_calls"`, and `tool_calls_buffer`. If you move it into the gateway, the gateway would need to OWN `full_content` — violating D-02 (events out, consumer accumulates).
**Why it happens:** Structured mode delivers tool calls as TEXT in the content stream, not as native tool-call deltas — so the "tool call" only materializes after the full text is accumulated, on the consumer's side.
**How to avoid:** Keep the post-parse on the CONSUMER side. The gateway's `openai_compat.py` returns `calling_mode` (or emits a `calling_mode` signal in the canonical event stream / a stream attribute) so the consumer knows to run `parse_structured_tool_calls(full_content)` after the drain. This keeps `full_content` mutation entirely consumer-side (D-02-compliant) while the gateway still owns chunk→event normalization. See §OpenAI Adapter Entanglement L-3 for the recommended shape.
**Warning signs:** The gateway dispatcher signature needs to return `full_content` or accept a content accumulator — that's the wrong cut.

### Pitfall 3: Dropping the `calling_mode` return value
**What goes wrong:** `create_adaptive_streaming_chat` returns `(stream, calling_mode)`. The consumer needs `calling_mode` for (a) the STRUCTURED-mode post-parse (Pitfall 2), (b) the inline `tool_args_progress` skip in STRUCTURED mode (`agent_loop.py:1878`: `calling_mode != CallingMode.STRUCTURED`), and (c) the fallback injection (`:1669`). The 2nd-copy `task_service._consume_sync_stream` ALREADY drops it (`:177` — `_calling_mode` unused) — that's exactly why the harness narrates tools as text off-OpenAI. The gateway must SURFACE `calling_mode`, not bury it.
**Why it happens:** It's tempting to make `open_stream` return just an event stream.
**How to avoid:** The dispatcher/adapter must expose `calling_mode` to the consumer (Claude's discretion on shape — a tuple, a leading `meta` event, or a stream attribute). The §Canonical Event Schema includes a `calling_mode` carrier for exactly this.
**Warning signs:** STRUCTURED-mode providers (DeepSeek/Moonshot/GLM/MiniMax when registry-missed, OpenRouter) narrate tools as text after the extraction.

### Pitfall 4: Per-provider 5KB boundary state crossing the seam wrong
**What goes wrong:** The OpenAI branch keeps `_emit_boundary_openai_native` and `_emit_boundary_openrouter` as SEPARATE dicts (`agent_loop.py:1702-1703`), branched on `active_provider_name` inside the chunk handler (`:1886-1890`). SPEC §Constraints (075.6) requires OpenRouter boundary state stay independent of OpenAI-native. If the gateway computes the `tool_args_progress` boundary, it must keep this per-provider independence; if the consumer keeps it, the gateway must emit raw arg-deltas and let the consumer compute boundaries.
**Why it happens:** The boundary computation reads the cumulative `tool_calls_buffer[idx]["arguments"]` (a consumer accumulator) AND the per-iteration `_emit_boundary_bytes` config.
**How to avoid:** Recommended cut — Anthropic and Google ALREADY compute their own `tool_args_progress` boundary INSIDE their `stream_*` adapters (anthropic_service / google_service do the 5KB walk and yield the finished `tool_args_progress` event with `args_so_far` + `total_args_bytes_so_far` + `code_so_far`). So for symmetry, the OpenAI adapter should ALSO compute the boundary internally and yield a finished `tool_args_progress` event — moving the boundary dicts + `_emit_boundary_bytes` read INTO `openai_compat.py`. The cumulative-args accumulation it needs is gateway-local (the gateway already sees every arg-delta chunk); it does NOT need the consumer's `tool_calls_buffer`. This makes all 3 adapters symmetric and removes the only inline boundary computation from the consumer.
**Warning signs:** `tool_args_progress` events with wrong `total_args_bytes_so_far` cadence, or OpenRouter/OpenAI-native boundary cross-pollution → skeleton diff on the `tool_args_progress` axis (though skeleton collapses consecutive `tool_args_progress`, a count/ordering change of `tool_preparing`→`tool_args_progress`→`tool_start` would surface).

### Pitfall 5: Forgetting the BEFORE baseline must run against the PRE-extraction loop
**What goes wrong:** The 089 proof is before/after. If you start extracting before capturing the `--mode before` baseline, you've lost the reference and can't prove byte-identical.
**How to avoid:** Wave 0 task: operator runs `scripts/capture_sse_baseline.py --mode before` against the current (pre-extraction) loop, saving `scripts/.sse_baseline/<provider>.json` for native-7. Only then begin the move.
**Warning signs:** `--mode after` reports "NO baseline ... run --mode before first".
