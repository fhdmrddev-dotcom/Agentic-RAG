## Summary

Reviewed the NEW `provider_gateway/` package (events / dispatcher / anthropic / google / openai_compat) and the `agent_loop.py` integration seam (the `open_stream` call sites at ~1558/1633 and the unified `_on_chunk` consumer at ~1382-1506). The extraction is clean and the byte-identical bar holds up under the complementary lens:

- **Concurrency (WORKER_COUNT=2):** No module-level mutable shared state. All per-stream state in `openai_compat._ClosableEventStream._normalize` (`_in_think_block`, the two boundary dicts, `_tool_args`, the usage totals) is function-local — "one stream = one tracker." Consumer accumulators (`tool_calls_buffer`, `_announced_tools_shared`, `_build_from_progress`, `_on_chunk`) are re-created per retry inside the `while True` at agent_loop.py:1352, so a provider-error `continue` (1743) gets a fresh tracker — correct idempotency.
- **Security:** No hardcoded secrets, no `eval`/`exec`/`subprocess`. API keys resolve from `user_settings`/`settings` exactly as before.
- **Resource leaks / cancel path:** `_ClosableEventStream.close()` defensively delegates to the raw stream's `.close` (handles fake test streams via `callable()` guard). On timeout, `close_fn=stream.close` closes the underlying httpx response; the producer's `for chunk in self._raw:` inside `_normalize` then terminates — behaviorally equivalent to the pre-extraction direct `stream.close`.
- **Byte-identity spot-checks (all verified faithful):** the `<think>` state machine, `reasoning_content` routing, the reasoning→visible→reasoning_content emit ORDER, `_accumulate_chunk_usage` (both Google-overwrite and OpenAI-`+=` branches), the per-provider 5KB boundary dicts, the unified usage/usage_delta consumer branch (faithful collapse of the three former handlers), and the api_key fallback chain (functionally equivalent; see IN-01).

No bugs that break correctness or the byte-identical contract were found. The findings below are maintainability/schema-completeness items in the new package — none block the phase, but WR-01 (schema drift on the seam contract) is worth closing before Phase 093 consumes the schema.

## Warnings

### WR-01: `emit_sse` field is read by the consumer but absent from the canonical `ToolArgsProgressEvent` schema

**File:** `backend/app/services/provider_gateway/events.py:60-72` (schema) / `backend/app/services/provider_gateway/openai_compat.py:348` (producer) / `backend/app/services/agent_loop.py:1472` (consumer)
**Issue:** `events.py` is explicitly declared the "source of truth for the vocabulary" and the "lossless superset" the D-02 seam contract / Phase 093 consumes (events.py:1-11). The OpenAI-compat adapter yields `"emit_sse": _crossed` on every `tool_args_progress` event (openai_compat.py:348), and the consumer reads it as `_event.get("emit_sse", True)` (agent_loop.py:1472) to gate the SSE wire cadence — it is a real, load-bearing field of the event. But `ToolArgsProgressEvent` (events.py:60-72) does not declare it. The module docstring elsewhere even calls out three fields it added "that the docstring schema omits but the consumer DOES consume" (events.py:11-20) for exactly this losslessness reason — `emit_sse` is a fourth such field that slipped the schema. A Phase 093 implementer typing against this TypedDict would not see `emit_sse` and could drop the boundary-gating behavior (reproducing the class of bug the gateway exists to prevent).
**Fix:**
```python
class ToolArgsProgressEvent(TypedDict):
    """5KB-boundary tool-args progress.

    ``code_so_far`` is 075.6-additive ... (the consumer does ``.get("code_so_far", "")``).
    ``emit_sse`` gates ONLY the SSE-emit cadence (boundary-crossed); the buffer
    update always fires. OpenAI-compat sets it; the Anthropic/Google adapters
    OMIT it (their boundary walk is internal — they only yield on boundary) and
    the consumer defaults it ``True`` via ``.get("emit_sse", True)``.
    """

    type: Literal["tool_args_progress"]
    tool_index: int
    name: str
    args_so_far: str
    total_args_bytes_so_far: int
    code_so_far: str
    emit_sse: NotRequired[bool]
```

## Info

### IN-01: api_key resolution diverges from the pre-extraction form (functionally equivalent, but the docstring claims VERBATIM)

**File:** `backend/app/services/provider_gateway/anthropic.py:59-63` and `backend/app/services/provider_gateway/google.py:61-65`
**Issue:** The pre-extraction inline was `_ant_api_key = user_settings.llm_api_key or settings.llm_api_key or ""` (agent_loop.py pre-ext :1400/:1539). The adapter rewrote it to `(getattr(user_settings, "llm_api_key", None) or "") or settings.llm_api_key or ""`. The result is identical for the live path (user_settings is always present here), and the `getattr` is strictly SAFER (it no longer `AttributeError`s if `user_settings` is `None` or lacks the attr). But the adapter docstring (anthropic.py:7, google.py:12) says the assembly is lifted "VERBATIM" — this one line is a behavioral hardening, not a verbatim copy. Not a bug; flagged only so the "VERBATIM" claim isn't taken literally during a future audit.
**Fix:** Either revert to the exact pre-extraction expression to keep "VERBATIM" honest, or update the docstring to note "api_key resolution hardened with `getattr` (defensive — original would `AttributeError` on `None` user_settings)."

### IN-02: `GatewayRequest.api_key` is a dead field — never populated, never read

**File:** `backend/app/services/provider_gateway/dispatcher.py:70`
**Issue:** `api_key: str = ""` is declared on the request envelope and listed in the docstring as one of "the union of fields the 3 stream constructions need today" (dispatcher.py:46-52). In reality no adapter reads `request.api_key` (each resolves its own key internally — anthropic.py:59, google.py:61), and neither consumer call site populates it (agent_loop.py:1548-1557, 1623-1632 omit it). A future maintainer who sets `GatewayRequest(api_key=...)` expecting it to flow through would find it silently ignored.
**Fix:** Remove the `api_key` field, or wire the adapters to honor `request.api_key` when non-empty (e.g. `request.api_key or <existing fallback chain>`) so the envelope field is actually load-bearing.

### IN-03: `GatewayRequest.max_tokens` is a dead field — never populated, never read

**File:** `backend/app/services/provider_gateway/dispatcher.py:69`
**Issue:** Same as IN-02 for `max_tokens: int | None = None`. The anthropic/google adapters call `_resolve_max_tokens(None, user_settings)` (hard-coded `None` for the explicit arg), and the openai_compat adapter never forwards `max_tokens` to `create_adaptive_streaming_chat`. No consumer call site sets it. The field is inert.
**Fix:** Remove `max_tokens` from `GatewayRequest`, or thread it through as the explicit arg (`_resolve_max_tokens(request.max_tokens, user_settings)` and `create_adaptive_streaming_chat(..., max_tokens=request.max_tokens)`) so it does what its presence implies.

### IN-04: Unused import `get_tools` in the openai_compat adapter

**File:** `backend/app/services/provider_gateway/openai_compat.py:73`
**Issue:** `get_tools` is imported from `openai_service` (line 73) but never referenced in the module — the OpenAI path delegates tool selection to `create_adaptive_streaming_chat` internally (which itself does the `tools_override if not None else get_tools()` select), so the adapter doesn't need it. Dead import. (Contrast anthropic.py/google.py, which DO use `get_tools` for their inline tool-select.)
**Fix:** Drop `get_tools` from the import on openai_compat.py:70-75:
```python
from app.services.openai_service import (
    CallingMode,
    create_adaptive_streaming_chat,
    normalize_finish_reason,
)
```

### IN-05: Return-type annotation says `AsyncIterator` but the streams are SYNC iterables

**File:** `backend/app/services/provider_gateway/dispatcher.py:78` (and the `AsyncIterator` import :29 / `events.py` references)
**Issue:** `open_stream` is annotated `-> tuple[AsyncIterator[GatewayEvent], CallingMode]`, but every adapter returns a SYNC object: `open_anthropic_stream`/`open_google_stream` return `Generator[dict, None, None]`, and `open_openai_compat_stream` returns `_ClosableEventStream` (a sync `__iter__`). This is intentional — the consumer's `_drain_stream_with_close_on_cancel` drives them with `for chunk in stream:` in a threadpool — but the `AsyncIterator` annotation is inaccurate and could mislead a Phase 093 caller into `async for`-ing the result (which would fail). The runtime behavior is correct; only the type contract is wrong.
**Fix:** Change the annotation to reflect the sync boundary, e.g. `-> tuple[Iterator[GatewayEvent], CallingMode]` (import `Iterator` from `typing`), and update the module docstring (dispatcher.py:3) which also says `AsyncIterator[GatewayEvent]`. Add a one-line note that the consumer drives the sync iterator inside a threadpool.
