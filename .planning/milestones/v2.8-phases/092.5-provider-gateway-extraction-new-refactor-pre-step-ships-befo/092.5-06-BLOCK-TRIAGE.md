## Verdict: the BLOCK is 100% ENVIRONMENTAL, not a gateway regression

**Root cause: the OpenAI account was out of credits (`429 insufficient_quota`).**
Document search is embeddings-backed and the embeddings call is **hardwired to OpenAI
with no fallback**:

- `retrieval_service.py:36` (`_vector_search`) → `openai_service.embed_texts`
- `embed_texts` (`openai_service.py:1288`, via `get_embedding_client` `:906-929`) builds a
  raw `openai.OpenAI` client and calls `client.embeddings.create()` — **no try/except, no
  alternate provider, no fallback**. Embeddings follow their own `embedding_*` settings
  (default `text-embedding-3-small`, 1536 dims), decoupled from the active CHAT provider.

So with ANY of the native-7 chat providers selected, the chat LLM streams fine, but every
`search_documents` call still hits OpenAI embeddings first → the 429 throws unguarded →
`search_documents` fails for ALL providers. The pinned proof prompt leads with
*"Search my documents…"*, so every provider's run diverges from a baseline (captured
~10:57–11:06 when OpenAI was healthy) in the same way:

1. `sources / citations / confidence` **deleted** — they only emit on usable search chunks.
2. `search_documents` **replaced** by fallback tools (`grep`, `query_documents`,
   `read_document`, `analyze_document`) — legitimate LLM tool-path non-determinism.

`openai.json` is the extreme case: the chat-completions call itself 429'd at iteration 0,
so its AFTER capture is 4 events ending in `error` (not even a terminal) — nothing ran.
