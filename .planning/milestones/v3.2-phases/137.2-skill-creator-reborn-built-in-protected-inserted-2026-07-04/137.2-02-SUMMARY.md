## Decisions Made
- **DO UPDATE vs DO NOTHING (RESEARCH Pitfall 1 / A3):** the skill row uses `ON CONFLICT (id) DO UPDATE` so a stale 018 `…0010` row on any environment is refreshed to the reborn content; the `auth.users` insert keeps `ON CONFLICT (id) DO NOTHING` (the user must never be mutated by a re-apply). On the live dev DB (row absent) both behave identically — the choice only matters on an env still holding 018's row.
- **Reuse id `…0010` (not a fresh UUID):** guarantees supersession, never a duplicate skill-creator.
- **Instructions prose:** used RESEARCH Code Example #7 as the near-complete starting draft (prose is Claude's Discretion per CONTEXT.md). Minor polish only (e.g. "there is no separate tool for this — the cases live in the Studio" in step 4; "tighten the instructions and re-run" in step 5) — all within the honesty red line and the locked 7-step shape.
- **Scope boundaries honored:** the dev-only operator private-copy rename (D-04) and `full-schema.sql` regeneration are explicitly Plan 04 work and were left untouched here.
