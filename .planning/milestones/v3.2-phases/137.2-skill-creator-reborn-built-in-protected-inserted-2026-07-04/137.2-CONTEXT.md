<decisions>
## Implementation Decisions

### Protection mechanism & "Built-in" badge
- **D-01:** Add an explicit `is_system` boolean column on `skills` (default `false`),
  set `true` ONLY by the seed migration. This column is the **badge/UI signal**
  (`skill.is_system` → a "Built-in" pill in `SkillCard.tsx`, next to the existing
  "Global" pill) — it is NOT what makes the skill protected. Protection is already
  free: every mutation route (`update_skill`, `delete_skill`, `toggle_enabled`,
  `toggle_global`) filters `.eq("user_id", current_user["id"])`, and the seed's
  system-user UUID (`00000000-0000-0000-0000-000000000001`, same one migration 018
  already seeded into `auth.users`) never matches any real user's id — every non-owner
  gets the existing 404/403 "not found or you are not the owner" response with zero
  new authorization code. Verified live against the actual route bodies during this
  discussion, not assumed.
- **D-02:** The new seed migration is idempotent (`ON CONFLICT (id) DO NOTHING`
  pattern, matching migration 018) and supersedes/refreshes migration 018's stale row
  (`00000000-0000-0000-0000-000000000010`) if present — same system user, rewritten
  platform-native instructions (per SEED-101), `is_system=true`.

### Eval-case creation during the conversation
- **D-03:** **No new agent tool.** The reborn skill's instructions have the agent
  propose 2-3 realistic eval cases as chat text, then direct the user to the skill's
  Skill Studio → Evals tab (the existing `CaseEditor` UI shipped in Phase 132) to add
  them. Chosen over a new `add_test_case` tool specifically to avoid new tool-registry
  surface — cross-provider (native-7 + OpenRouter) whitelisting and testing burden —
  that a "seed one skill" phase shouldn't be taking on.

### Operator's manual copy (skill id `7f504819-2ab6-4b12-8692-50e29696db54`)
- **D-04:** **Rename it during this phase (not delete).** Suggested new name:
  `skill-creator (imported reference)` or similar — planner/executor picks exact
  wording — so it can never be confused with the new Built-in skill in the list. It
  stays around as the user's own private reference copy (their data; ROADMAP explicitly
  says never auto-delete). Verified LIVE via psycopg2 (`:54322`) during this discussion
  (not just recalled from SEED-101): the row is owned by `d8a54002-6a29-4b88-b918-
  cff2aa4a06d5`, private (`is_global=false`), 33,103-char instructions, and carries only
  **3 of the zip's 18 files** — `agents/analyzer.md`, `agents/comparator.md`,
  `agents/grader.md` (the Claude.ai blind-A/B-comparison sub-agent prompts, SEED-101's
  SKIP-for-now bucket). The `scripts/*.py` and `eval-viewer/`/`assets/` HTML files were
  never imported — they exist only in `screenshots/skill-creator.zip` on disk, untouched
  by anything live.

### Badge + list ordering
- **D-05:** Pin `is_system` skills to the **top** of the Skills list — extend
  `list_skills`'s existing `.order("name")` to sort `is_system` first (e.g.
  `ORDER BY is_system DESC, name ASC`), so the Built-in skill is the first thing a user
  scanning the Skills tab sees, not buried mid-alphabet under "s".

### Claude's Discretion
- Exact migration number (next in sequence after 086 → likely 087).
- Whether `is_system` warrants an index (low cardinality, tiny table — likely no).
- Exact "Built-in" badge copy/styling — follow the existing "Global" pill's visual
  language (`text-[10px] text-muted-foreground bg-muted px-2 py-1 rounded-full`,
  `SkillCard.tsx:101-105`) unless a distinct treatment is clearly better.
- Full instructions prose for the reborn skill — SEED-101's "What the reborn
  skill-creator IS" section (7-step scope: interview → RAG research → draft+save →
  test → evaluate → improve → publish) is the content brief; the planner/researcher
  draft the actual wording, keeping the SEED-096 honesty constraint (never claim
  subagents/browser/`claude -p`/non-Python sandbox execution).
- Exact mechanism for renaming the operator's manual copy (one-off `UPDATE` via SQL
  editor/psycopg2 vs. folding into the same migration) — it's a single row, either
  approach is fine.
- Whether the existing "hide enabled-toggle for global skills you don't own" UI rule
  needs any adjustment for `is_system` skills — not explicitly discussed; likely
  unaffected (same owner-mismatch condition already covers it).
