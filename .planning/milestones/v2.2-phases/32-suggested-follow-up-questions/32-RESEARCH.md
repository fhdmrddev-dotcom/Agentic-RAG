## Summary

Phase 32 adds suggested follow-up question pills to every assistant response in General mode. The implementation has three tightly coupled layers: a backend SSE stream extension, a frontend SSE callback, and a UI component. All three layers follow exact patterns already established in prior phases.

The most significant implementation detail is the stream sentinel redesign. Currently `threads.py` ends the stream with the literal `data: [DONE]\n\n` string, and `api.ts` returns immediately on seeing it (line 157: `return`). Phase 32 requires the suggestions to arrive **after** the main response is complete but **before** the stream closes. The cleanest approach is to convert `[DONE]` into a JSON `{ type: "done" }` event that triggers `onDone()` without returning, then emit `suggestions` (if generation succeeds), then emit `{ type: "stream_end" }` to signal the true end of stream. The frontend `while(true)` loop already breaks on `done: true` from the reader, so the new `stream_end` event type serves as the clean termination signal.

The suggestion generation itself is a thin wrapper around the existing `sub_agent_service` model resolution logic — a single non-streaming completion call with a short system prompt requesting exactly 3 questions. Pydantic structured output is the cleanest approach for parsing the returned question list, consistent with the project's Pydantic requirement.

**Primary recommendation:** Follow the existing `onCitations`/`onConfidence` callback pattern precisely. Three changes required: (1) backend stream timeline change, (2) `onSuggestions` callback in `api.ts` + `useMessages.ts`, (3) `SuggestionPills` component + `suggestions` field on `Message` type + prop threading through `MessageList` → `MessageItem`.

### Pattern 1: Backend Stream Timeline

Current stream end sequence in `threads.py`:
```python
yield "data: [DONE]\n\n"
```

New sequence:
```python
# (1) Signal main response complete — triggers onDone() in frontend
yield f"data: {json.dumps({'type': 'done'})}\n\n"

# (2) Non-blocking suggestion generation (swallow all exceptions)
try:
    questions = _generate_suggestions(
        user_message=user_content,
        assistant_response=full_response_text,
        user_settings=user_settings,
    )
    if questions:
        yield f"data: {json.dumps({'type': 'suggestions', 'questions': questions[:3]})}\n\n"
except Exception:
    pass  # SUG-04: failure never affects main response

# (3) True stream end
yield f"data: {json.dumps({'type': 'stream_end'})}\n\n"
```

**CRITICAL:** `api.ts` currently has `if (raw === "[DONE]") { onDone(); return }`. The `return` exits the loop. Changing to JSON `done` event removes the early return — the loop must continue reading until `stream_end`. The `streamMessage` function's outer `while(true)` breaks when `reader.read()` returns `done: true` (stream closed), but the new `stream_end` JSON event is the in-band signal to call `onDone()` and return.

Wait — re-reading the CONTEXT.md diagram:
```
delta... delta... done
     └── suggestions: ["...", "...", "..."]
     └── stream_end
```

The `done` here is the semantic "main response done", distinct from `[DONE]`. The decision is to keep `onDone()` triggered at the `done` JSON event but NOT return from the loop. The `stream_end` event causes the `return`. This matches D-08 (fade-in on arrival) — pills fade in after the `done` event fires but before `stream_end`.

Revised `api.ts` SSE handler:
```typescript
// Source: extend existing event dispatch block
} else if (parsed.type === "done") {
  onDone()
  // Do NOT return — wait for stream_end to pick up suggestions
} else if (parsed.type === "suggestions" && onSuggestions) {
  onSuggestions((parsed.questions ?? []) as string[])
} else if (parsed.type === "stream_end") {
  return  // True end of stream
}
```

**Backward compatibility concern:** The literal `[DONE]` sentinel in `api.ts` line 155 is a guard against older-format responses. Replacing `[DONE]` with `{ type: "done" }` + `{ type: "stream_end" }` requires the frontend and backend to change together. Since this is a single-repo deployment with no external API consumers, this is safe.

### Pattern 2: `_generate_suggestions` function

The function is a non-streaming completion call (not a generator). It returns `list[str]` or raises on failure.

```python
# In threads.py or suggestion_service.py
from pydantic import BaseModel

class SuggestionResponse(BaseModel):
    questions: list[str]

def _generate_suggestions(
    user_message: str,
    assistant_response: str,
    user_settings: "UserEffectiveSettings | None" = None,
) -> list[str]:
    """Generate 3 follow-up questions from the last Q&A pair.
    Returns a list of question strings. Raises on any failure.
    """
    system_prompt = (
        "You are a helpful assistant. Based on the conversation excerpt below, "
        "generate exactly 3 concise, actionable follow-up questions the user might "
        "want to ask next. Return only the questions, one per line, no numbering."
    )
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": (
            f"User asked: {user_message}\n\n"
            f"Assistant replied: {assistant_response[:2000]}\n\n"  # cap to ~500 tokens
            "Generate 3 follow-up questions:"
        )},
    ]
    client = get_llm_client(user_settings)
    # Resolve cheap model using same logic as sub_agent_service
    provider = user_settings.active_provider if user_settings else ""
    effective_model = (
        settings.sub_agent_model
        or _SUB_AGENT_MODEL_DEFAULTS.get(provider, "")
        or (user_settings.llm_model if user_settings else None)
        or settings.llm_model
    )
    resp = client.chat.completions.create(
        model=effective_model,
        messages=messages,
        stream=False,
        max_tokens=200,
    )
    content = resp.choices[0].message.content or ""
    # Parse: one question per line, strip empty lines
    questions = [q.strip() for q in content.split("\n") if q.strip()]
    return questions[:3]
```

**Note on Pydantic structured output:** The project rule says "Use Pydantic for structured LLM outputs." However, a simple line-split parse is more reliable across all providers (OpenRouter/Ollama may not support JSON schema mode). Use line-split as primary, with Pydantic validation as a parsing layer if needed. Alternatively, request a JSON array and validate with Pydantic — but provider compatibility is a concern. Simple line-split is the pragmatic choice here given the minimal structure needed.

### Pattern 5: Prop threading for click-to-submit (SUG-02)

The current `MessageList` → `MessageItem` interface has no `onSendMessage` prop. The click handler must submit a message. The chain:

1. `ChatArea.tsx` has `handleSend` (already calls `sendMessage` hook)
2. `ChatArea` passes `messages` to `MessageList` — need to also pass `onSendMessage`
3. `MessageList` passes it to each `MessageItem`
4. `MessageItem` passes it to `SuggestionPills`

**Simpler alternative:** Pass `agentMode` and `onSendMessage` only to the **last assistant message** (where pills appear). `MessageList` already tracks `isLastAssistant`. Gate `onSendMessage` prop only on last assistant message to avoid unnecessary prop threading:

```tsx
// MessageList.tsx
interface Props {
  messages: Message[]
  isStreaming: boolean
  onSendMessage?: (content: string) => void  // new
}

// Pass only to last assistant message
<MessageItem
  key={msg.id}
  message={msg}
  isStreaming={isStreaming && isLastAssistant}
  onSendMessage={isLastAssistant ? onSendMessage : undefined}
/>
```

**Explorer mode gate:** `agentMode` is in `ChatArea` state. Pass it down similarly to `onSendMessage`, or simply don't pass `onSendMessage` when `agentMode === "explorer"` — pills won't render without the prop, implementing D-10 without conditional rendering logic in `MessageItem`.

Actually, cleaner: pass `agentMode` to `MessageList` (or `showSuggestions: boolean`) and gate in `MessageItem`. The `agentMode` approach is more explicit.

### Anti-Patterns to Avoid

- **Persisting suggestions to DB:** Suggestions are ephemeral (live SSE only), like `confidence`. Never store them on the `messages` table. The `Message` type field `suggestions?: string[]` is frontend-only.
- **Blocking `onDone` on suggestion generation:** `onDone()` must fire at the JSON `done` event, before suggestion generation runs. The `isStreaming` spinner must stop as soon as the main text is complete.
- **Using `stream=True` for suggestions:** The cheap model call for suggestions should be non-streaming (`stream=False`). Simple completion, no streaming needed.
- **Re-using `[DONE]` sentinel as stream_end:** The literal `[DONE]` string is not JSON-parseable and causes the current `api.ts` to `return` immediately. It must be retired in this phase.

## Common Pitfalls

### Pitfall 1: `[DONE]` vs `{ type: "done" }` — premature stream exit
**What goes wrong:** If `[DONE]` literal is kept as the stream terminator and suggestions are emitted after it, `api.ts` will `return` before reading them (line 157).
**Why it happens:** `api.ts` has `if (raw === "[DONE]") { onDone(); return }` — the `return` exits the entire `streamMessage` function.
**How to avoid:** Replace `[DONE]` with `{ type: "done" }` JSON event that calls `onDone()` but does NOT return. Add `{ type: "stream_end" }` as the true terminator that triggers the `return`.
**Warning signs:** Suggestions never arrive in the frontend despite correct backend emission.

### Pitfall 2: `isStreaming` remains true during suggestion generation
**What goes wrong:** If `isStreaming` stays true while the backend generates suggestions (~500ms–2s), the streaming cursor continues showing after the main text is fully rendered.
**Why it happens:** `onDone()` sets `isStreaming = false` in `useMessages.ts`. If `onDone()` is delayed until `stream_end`, the cursor flickers for the suggestion delay window.
**How to avoid:** Trigger `onDone()` at the JSON `done` event (not `stream_end`). This stops the cursor immediately when the main response completes, while the stream stays open for suggestions.
**Warning signs:** Streaming cursor continues showing for 1–2 seconds after last text character appears.

### Pitfall 3: `full_response_text` not captured for suggestion context
**What goes wrong:** `_generate_suggestions` needs the completed assistant response text, but `threads.py` accumulates text in a local variable that may need to be made accessible to the post-done suggestion step.
**Why it happens:** The SSE generator accumulates `full_response_text` (or `assistant_content`) inside nested loops. If the suggestion function is called outside those loops, the variable may be out of scope.
**How to avoid:** Ensure `full_response_text` (the accumulated assistant message text) is declared at a scope accessible to the post-done code block. Review `threads.py` accumulation variable name.
**Warning signs:** Suggestions generated with empty assistant response context; questions are generic/unhelpful.

### Pitfall 4: Suggestion pills appear on non-last messages after thread reload
**What goes wrong:** On page reload, `loadMessages` fetches all messages from DB. Since `suggestions` is not persisted, `message.suggestions` will be `undefined` for all loaded messages — pills correctly absent. But if there's a race between SSE finishing and `loadMessages` running, stale state could cause issues.
**Why it happens:** The `useMessages` hook already has the `isSendingRef` guard that prevents `loadMessages` from overwriting live state. Suggestions are ephemeral and not in DB, so this is safe.
**How to avoid:** No special action needed; the existing guard is sufficient. Pills simply never appear on reloaded messages.
**Warning signs:** None expected; but test that pills are absent after thread switch and return.

### Pitfall 5: Explorer mode pills suppressed only by frontend
**What goes wrong:** SUG-04 says suggestions absent in Explorer mode. D-10 says no backend change needed. If someone bypasses the frontend, the backend still emits suggestions.
**Why it happens:** By design — the backend doesn't know about agent mode for the suggestion gate.
**How to avoid:** This is correct by design. The `agentMode` gate is frontend-only. Document as intentional.
**Warning signs:** N/A.

### Pitfall 6: `max_tokens` for suggestion call not set appropriately
**What goes wrong:** Some providers error if `max_tokens` is too large for the model, or the call runs slowly if left at the default 8192.
**Why it happens:** `sub_agent_service.py` uses `_resolve_max_tokens(8192, ...)` which can return large values. Suggestion generation only needs ~200 output tokens.
**How to avoid:** Set `max_tokens=200` (or `max_completion_tokens=200` for o-series models) explicitly on the suggestion call. Use the same `_uses_max_completion_tokens(effective_model)` helper to pick the right param name.
**Warning signs:** Suggestion generation takes >2 seconds; SUG-03 timing requirement violated.

1. **`full_response_text` variable name in `threads.py`**
   - What we know: The SSE generator accumulates the assistant message text to persist to DB. The variable is needed for suggestion context.

2. **`stream_end` vs closing the stream naturally**
   - What we know: Alternatives are (a) explicit `stream_end` JSON event, (b) just let the generator return (reader's `done: true` exits the loop naturally).
   - What's unclear: Whether the `while(true)` outer loop break on `reader.read()` `done: true` is sufficient, or whether an explicit in-band signal is cleaner.
   - Recommendation: Use explicit `stream_end` JSON event (Claude's discretion, D-01). This is more robust — the generator `return` closes the HTTP response, but explicit events make frontend logic clearer and testable.

3. **`agentMode` availability in `MessageList`/`MessageItem`**
   - What we know: `agentMode` lives in `ChatArea.tsx` state. `MessageList` currently has no `agentMode` prop.
   - What's unclear: Whether to thread `agentMode` prop down or use `showSuggestions: boolean` computed in `ChatArea`.
   - Recommendation: Pass `showSuggestions={agentMode !== "explorer"}` as a boolean prop to `MessageList`, which passes it to last assistant `MessageItem`. Avoids leaking mode semantics into display components.
