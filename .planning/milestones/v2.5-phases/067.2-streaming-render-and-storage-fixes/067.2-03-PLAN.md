<objective>
Replace the hardcoded 1-hour signed URL emission in `harvest_output_files` (`sandbox_service.py:138`) with an on-demand re-sign endpoint at `GET /sandbox-outputs/{storage_path:path}`. New sandbox-output files store a relative URL (`/sandbox-outputs/{path}`) inside the assistant message; each click goes through the new endpoint which authenticates the user, performs an ownership fence (path-segment user_id match + `sandbox_files` row check, return 404 on mismatch), re-signs the Supabase Storage URL with a 60s TTL, and 302-redirects to the freshly signed URL. Closes D-067.2-03.

Purpose: stop the "InvalidJWT after 1 hour" failure mode in chat history. Output documents and chart PNGs remain clickable for the lifetime of the underlying Storage object.

<deviation_note>
## CONTEXT-vs-INVARIANT conflict resolution (D-067.2-03 acceptance #3 vs D-062-12)

**Conflict:** CONTEXT.md `### D-067.2-03` acceptance criterion #3 says "different user authenticated → click download URL of someone else's file → **403 (ownership check)**". This conflicts with the project-wide invariant **D-062-12: cross-user resource access returns 404 (NOT 403) to avoid existence leakage** (PATTERNS.md flags this as a binding invariant; runs.py:331-352 demonstrates the canonical pattern; new endpoints are expected to follow it).

**Resolution (chosen):** Implement **HTTP 404** on cross-user mismatch — adopt the project-wide invariant (D-062-12), not the phase-locked acceptance text. Justification:
1. D-062-12 is a security architectural invariant established Phase 062 and applied across runs.py, documents.py, skills.py, threads.py — every existing user-scoped endpoint returns 404. Diverging here would create the only 403-returning user-scoped route in the codebase, violating the principle of least surprise for security review.
2. The phase-acceptance text in CONTEXT.md `### D-067.2-03` was a high-level description; the locked CONTEXT does not include any user-UAT scoreboard checkbox for the cross-user IDOR case (the user UAT only covers same-user happy path + post-1h re-sign per `verification_protocol § User UAT Scoreboard`). The IDOR check becomes a developer-verified backend test, not a user-checked box — so changing 403→404 does not affect Plan 06's gate.
3. Existence leakage cost: a 403 confirms "this file exists, you just can't see it"; a 404 says "no such file from your perspective". For sandbox outputs whose names embed user-supplied prompt artifacts (e.g. `chart_FahedMrad_q3.png`), 404 is materially better.

**Implementation consequence:**
- Backend: `sandbox_outputs.py` returns 404 on path-segment mismatch AND on `sandbox_files` row miss.
- Backend test (Task 4): asserts `response.status_code == 404` for both unauth-but-valid-path and cross-user-row scenarios. The test docstring cites this deviation note.
- Plan 06 (user UAT): unchanged. No user-UAT checkbox referenced 403 in the first place.
- VERIFICATION.md (when this phase verifies): explicitly logs the 403→404 substitution under "Deviations from CONTEXT" with this rationale.
</deviation_note>
</objective>

    ```python
    """
    Sandbox-outputs re-sign endpoint (D-067.2-03).

    Replaces the legacy harvest_output_files behavior of embedding a 1-hour
    Supabase signed URL in assistant message content. Each click on a sandbox
    output now hits this endpoint, which:

      1. Authenticates the user (existing get_current_user dependency).
      2. Performs an ownership fence:
         a. Path-segment match: storage_path[0] must equal current_user["id"].
         b. sandbox_files row exists for (storage_path, user_id).
         Either failing → 404 (per project invariant D-062-12 — 404 not 403,
         to avoid leaking file existence to other users; see Phase 067.2-03
         PLAN.md <deviation_note> for rationale).
      3. Generates a fresh 60s-TTL signed URL via Supabase Storage.
      4. Returns 302 redirect to the signed URL — browser follows the redirect
         and downloads from Supabase CDN directly (no proxy bytes through
         FastAPI; keeps workers free, bandwidth light).

    D-v2.5-01: every supabase-py sync call is wrapped via aexec (Postgres) or
    run_in_threadpool (Storage). No direct .execute() inside async handlers.
    """

    from fastapi import APIRouter, Depends, HTTPException, status
    from fastapi.responses import RedirectResponse
    from starlette.concurrency import run_in_threadpool
    from supabase import Client

    from app.dependencies import get_current_user, get_supabase
    from app.utils.db import aexec

    router = APIRouter(prefix="/sandbox-outputs", tags=["sandbox-outputs"])


    @router.get("/{storage_path:path}")
    async def get_sandbox_output(
        storage_path: str,
        current_user: dict = Depends(get_current_user),
        supabase: Client = Depends(get_supabase),
    ):
        # Step 1: ownership fence — path-segment match.
        # storage_path layout (sandbox_service.py:103): "{user_id}/{execution_id}/{filename}"
        # First path segment MUST equal current_user["id"]. Reject on mismatch
        # with 404 per project invariant D-062-12 (existence-leak prevention).
        # This also structurally blocks path-traversal: parts[0] is required to
        # equal a UUID, so "../" or absolute-path tricks cannot bypass user scoping.
        parts = storage_path.split("/", 2)
        if len(parts) < 3 or parts[0] != current_user["id"]:
            raise HTTPException(
                status_code=status.HTTP_404_NOT_FOUND,
                detail="File not found",
            )

        # Step 2: defense-in-depth — verify a sandbox_files row exists for this
        # (storage_path, user_id) tuple. Mirrors runs.py:331-352 ownership-fence.
        file_resp = await aexec(
            supabase.table("sandbox_files")
            .select("id")
            .eq("storage_path", storage_path)
            .eq("user_id", current_user["id"])
            .maybe_single()
        )
        row = file_resp.data if file_resp is not None else None
        if not row:
            raise HTTPException(
                status_code=status.HTTP_404_NOT_FOUND,
                detail="File not found",
            )

        # Step 3: short-TTL re-sign. 60s is enough for the 302 → CDN fetch hop.
        # supabase.storage.from_(...).create_signed_url is a sync HTTP call to
        # the Supabase Storage API; wrap in run_in_threadpool per D-v2.5-01.
        signed = await run_in_threadpool(
            supabase.storage.from_("sandbox-outputs").create_signed_url,
            storage_path,
            60,
        )
        if isinstance(signed, dict):
            url = (
                signed.get("signedURL")
                or signed.get("signedUrl")
                or signed.get("signed_url")
            )
        else:
            url = (
                getattr(signed, "signedURL", None)
                or getattr(signed, "signedUrl", None)
            )
        if not url:
            raise HTTPException(
                status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
                detail="Failed to sign URL",
            )

        # Step 4: 302 redirect. HTTP 302 (not 307) — request is idempotent GET,
        # no method-preservation requirement. Browser follows to Supabase CDN.
        return RedirectResponse(url=url, status_code=302)
    ```

    Constraints:
    - Do NOT import `redis` — this endpoint is a pure storage-layer operation.
    - Do NOT add any caching headers; the redirect is single-use because the signed URL is short-TTL.
    - Do NOT proxy bytes through `StreamingResponse` (a 50MB CSV would block one of 40 default threadpool workers for the duration of the download — hostile under load). Redirect keeps workers free.
    - The path converter `{storage_path:path}` MUST use `:path` so `/` characters in `{user_id}/{execution_id}/{filename}` route correctly.
