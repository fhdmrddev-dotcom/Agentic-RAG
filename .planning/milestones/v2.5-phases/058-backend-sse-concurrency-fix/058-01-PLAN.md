```python
def _patch_postgrest_maybe_single():
    """Fix postgrest-py bug: maybe_single() raises APIError on 204 (no rows) instead of returning None."""
    try:
        from postgrest._sync.request_builder import SyncSingleRequestBuilder
        from postgrest.exceptions import APIError
        _orig = SyncSingleRequestBuilder.execute
        def _safe(self):
            try:
                return _orig(self)
            except APIError as e:
                if getattr(e, "code", None) == "204":
                    class _Empty:
                        data = None
                        count = None
                    return _Empty()
                raise
        SyncSingleRequestBuilder.execute = _safe
```

```python
"""Async wrapper around Supabase sync `.execute()` calls (Phase 058 — D-058-03).

Wraps `query.execute()` in `starlette.concurrency.run_in_threadpool` so the
asyncio event loop is not blocked on Postgres round-trips. This is the
SSE-path threadpool wrap referenced in research §A1–A2 — it coexists with
the existing `_patch_postgrest_maybe_single` patch in `main.py:17–40` (both
wrap `execute`; the postgrest patch handles a 204-error edge case at
import time, while `aexec` runs the call off the event loop at request
time).

Usage:
    from app.utils.db import aexec
    response = await aexec(
        supabase.table("messages")
        .select("role, content")
        .eq("thread_id", tid)
    )
    rows = response.data or []

The helper accepts a query object (NOT a callable) and calls `.execute` on
it inside the threadpool. This keeps call sites symmetric with the sync
`.execute()` they replace.
"""

import logging

from starlette.concurrency import run_in_threadpool

logger = logging.getLogger(__name__)


async def aexec(query):
    """Run a sync supabase-py query off the event loop.

    Args:
        query: A Supabase query builder (the result of
            `supabase.table(...).select(...).eq(...)` etc., before
            `.execute()` is called).

    Returns:
        The same response object `query.execute()` would have returned —
        typically with `.data` (list[dict] or dict) and `.count` (int|None).
    """
    return await run_in_threadpool(query.execute)
```

Do NOT add any other functions, classes, or constants to this module. Do NOT import `supabase.Client` (the helper is type-opaque on purpose so it works with any postgrest builder shape — table, rpc, single, etc.). Do NOT add a sync wrapper or a non-async variant.

Why these constraints (NOT decorative): D-058-03 locks the body verbatim. D-058-04 rejects "inline `await run_in_threadpool(query.execute)` everywhere" — the helper is the entire point. D-058-06 rejects monkey-patching `.execute()` to return a coroutine — that would break ~150 sync call sites outside the SSE path. Adding extra surface area to this module re-opens those rejected directions.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → FastAPI handler | Authenticated requests cross the Supabase JWT auth dependency before reaching `event_stream`. Plan 01 does NOT change this boundary — auth happens in `Depends(get_current_user)` before any code in this plan runs. |
| handler coroutine → AnyIO threadpool | NEW boundary introduced by `aexec`. The query object captures `supabase.table(...).select(...).eq(user_id)` BEFORE crossing into the worker thread; Supabase JWT context (the `current_user` dict) is closed over the query at the call site, never read inside the worker thread. RLS is enforced server-side by Supabase / Postgres on the SQL the query represents. |
| process startup ↔ AnyIO global limiter | One-time global side effect on lifespan startup. Multi-test runs that boot the app multiple times will re-set the same global. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-058-01 | D (Denial of Service) | AnyIO threadpool — 200-token ceiling | mitigate | Plan 01 sets `total_tokens = 200` (5x default). At sustained ≥200 concurrent in-flight `.execute()` calls (e.g. 200+ users streaming through a single worker simultaneously), new requests queue. Acceptable for current scale (single-user-on-laptop dev + small-team prod); CONCUR-03 (asyncpg migration) is the documented escape hatch. Reviewers should monitor logs for "queuing on AnyIO limiter" patterns post-merge. |
| T-058-02 | I (Information Disclosure) | RLS context across thread boundary | mitigate | The Supabase query object is built in the request coroutine (where `current_user["id"]` and `supabase` (a client carrying the user's JWT or the service-role key, per dependency injection) are captured into the `.eq(...)` filter). `aexec` only calls `query.execute()` in the worker thread — it never reads contextvars or auth state inside the thread. RLS is enforced by Postgres on the literal SQL the query represents. Verified by acceptance check: `aexec` body is exactly `await run_in_threadpool(query.execute)` (no contextvar manipulation, no client substitution). Plan 02 is responsible for confirming each call site builds its query with the correct user-scoped filters BEFORE awaiting `aexec`. |
| T-058-03 | T (Tampering) | `aexec` accepts arbitrary query object | accept | `aexec` is internal API only (not exposed to HTTP). All callers are first-party code in `backend/app/`. The opaque-object signature is the same trust posture as direct `.execute()` use today — Plan 01 does not expand the attack surface. |
| T-058-04 | E (Elevation of Privilege) | Service-role client leak across threads | mitigate | Each call site passes its own `supabase: Client` (via `Depends(get_supabase)` for user-scoped or via service-role import for ingestion). `aexec` does NOT close over a global supabase client — it only awaits the query the caller already built. Acceptance: `grep -c "from app.config import" backend/app/utils/db.py` returns 0; `grep -c "Client" backend/app/utils/db.py` returns 0 (helper is type-opaque). |
| T-058-05 | R (Repudiation) | Audit log writes still bind to user | accept | Plan 01 does not touch `audit_service.write_audit_entry`. Plan 02 wraps it. The user_id closure-capture pattern is unchanged. |
| T-058-06 | S (Spoofing) | JWT auth on SSE entry | accept | Auth dep `get_current_user` runs BEFORE `event_stream` is entered — Plan 01 does not move or modify auth. No SSE-path code in this plan. |

**Disposition summary:** 4 mitigate (T-058-01 via 200-token bump; T-058-02 via opaque-helper design; T-058-04 via opaque-helper design; auth boundary preserved); 2 accept (low-value internal-API surface; audit untouched).
