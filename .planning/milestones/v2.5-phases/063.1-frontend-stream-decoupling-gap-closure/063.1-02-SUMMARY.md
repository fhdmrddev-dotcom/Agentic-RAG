## Decisions Made

- **Inline reconcile rewrite over a `reconcileRun(run, threadId)` helper.** CONTEXT.md line 91 leaves this to Claude's discretion. Inline keeps the callbacks closure flat — `targetId`, `controller`, `guardedSetMessages`, `existingByRunId` all need to flow into the onTerminal override and the onCursor closure without being threaded through a helper signature. Lifting to a helper would have added 4+ ref/state captures and obscured the BL-03 cleanup flow.
- **`onCursor` fires AFTER the type-specific callback, NOT inside terminal branches.** Test 1's contract assertion (onCursor called twice for two delta events with two different ids) and the D-063.1-01/02 intent (replay cursor for paused/reconnected consumers) both require firing after content commit. Terminal branches `return` early — the cursor is irrelevant once the run has ended, and including them would also have required threading `lastEventId` into `stream_end`/`error`/`cancelled` paths, which serves no purpose.
- **`lastEventId` resets to `undefined` after each fire.** Without this, a cursor-less legacy frame following a cursor-bearing frame would inherit the prior id and fire onCursor with stale state. Test 2 (the no-id-line negative case) covers this: a single `data:` line with no preceding `id:` line must NOT fire onCursor, even if a *future* `id:`+`data:` pair will fire it correctly.
- **Reused `messagesRef.current` for the dedup lookup.** Already declared at useMessages.ts:316-319 for stopStreaming's WR-03 fix; same pattern (sync ref tracking the latest `messages` state for closures that can't depend on it without re-creating themselves on every render). Adding a parallel ref would have been clutter and PATTERNS.md explicitly called it out as the right choice (line 269).
- **sendMessage's call site continues to pass `"0"` as `since`.** Per D-063.1-02 explicit guidance: "sendMessage line 498 — start at '0' (fresh run, no offset yet)". Only RECONCILE re-attaches mid-run and benefits from the cached cursor; the wiring of onCursor in sendMessage is solely so that a *future* reconcile on the same run picks up the cached cursor.
