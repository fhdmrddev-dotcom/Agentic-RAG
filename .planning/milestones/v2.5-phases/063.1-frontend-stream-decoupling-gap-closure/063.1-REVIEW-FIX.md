## Fixed Issues

### CR-01: MERGE filter drops live SSE consumer's target during persist→stream_end window

**Files modified:** `frontend/src/hooks/useMessages.ts`
**Commit:** 8142f9a
**Applied fix:** Gated the loadMessages MERGE drop on `subscriptionsRef.current.has(m.runId)`. A temp-placeholder whose runId now also appears in the DB result is RETAINED if a live SSE consumer (sendMessage's or reconcile's) is still bound to it via that runId. Two bubbles render briefly during the persist→stream_end window; once `subscriptionsRef.delete(runId)` fires in onTerminal, the next loadMessages collapses back to one bubble. Strictly better than dropping terminal-status flips, suggestions, title, confidence and fallback_model deltas.

### CR-02: `resumeFromFailed` flips the in-flight bit AFTER synchronous early-returns

**Files modified:** `frontend/src/hooks/useMessages.ts`
**Commit:** 2a87fda
**Applied fix:** Set `resumeInFlightRef.current = true` SYNCHRONOUSLY immediately after the `if (resumeInFlightRef.current) return` guard and BEFORE the synchronous findIndex / for-loop / no-user-message early-return chain. The previous order (check → sync work → set) left a TOCTOU window where two rapid clicks both passed the guard and both called sendMessage; the second was no-op'd by sendMessage's isSendingRef and the user got no feedback. Mirrors the in-flight-first pattern that `reconcileInFlightRef` correctly applies at lines 675-676. The findIndex/loop/await all moved inside the try block so the finally still releases on every exit.

### CR-03: e2e thread-switch test captures `threadAUrl` before any message has been sent

**Files modified:** `e2e/tests/063.1-thread-switch-mid-stream.spec.ts`
**Commit:** a1dd800
**Applied fix:** Moved the `threadAUrl = page.url()` capture from immediately-after-`createNewThread` to after `sendMessageInActiveThread` + after the assistant-message bubble is visible + a 2s settle. By that point the routing has assigned the URL to `/threads/<uuid>`. Added a regex assertion `expect(threadAUrl).toMatch(/\/threads\/[0-9a-f-]{36}/)` so a future routing change that breaks this premise produces a clean failure instead of a misleading distinctRuns / bubble-count mismatch downstream.

### CR-04: Two of three e2e specs use a non-`.first()` locator for `data-testid="assistant-message"`

**Files modified:** `e2e/tests/063.1-concurrent-reconcile.spec.ts`, `e2e/tests/063.1-thread-switch-mid-stream.spec.ts`
**Commit:** bec9fe2
**Applied fix:** Added `.first()` to both post-step assistant-message visibility assertions, avoiding Playwright's strict-mode-violation throw when the locator transiently resolves to >1 elements. For `concurrent-reconcile` (where the test rationale literally is "exactly one bubble survives the concurrent reconcile") additionally added `expect(...).toHaveCount(1)` to make that the actual assertion. For `thread-switch-mid-stream`, only `.first()` was added because the single-consumer invariant for that test is the distinctRuns.size === 1 assertion, which doesn't depend on bubble count. The third spec (`063.1-refresh-no-duplicate-bubble.spec.ts`) already used `.first()` correctly.

### WR-01: `runs_by_message` dict drops collisions silently when multiple runs share `message_id`

**Files modified:** `backend/app/api/threads.py`
**Commit:** c70491c
**Applied fix:** Added `.order("started_at", desc=True)` to the runs SELECT and replaced the dict comprehension with a deterministic skip-if-already-present loop, so the FIRST (newest) run wins per message_id. `public.runs.message_id` has no UNIQUE constraint (migration 035), so collisions are possible (buffer-expired retries, partial failure paths, producer races). Newest-run-wins is also the run whose status is most likely to drive correct Resume UX.

### WR-02: `MessageResponse.run_id`/`run_status` allow `null` to leak as frontend `null` (not `undefined`)

**Files modified:** `frontend/src/lib/api.ts`
**Commit:** 13442e8
**Applied fix:** Coerced `run_id ?? undefined` and `run_status ?? undefined` in the getMessages mapper, and widened the inline response-shape type to `string | null` / enum | null so the destructured local has the right type before coercion. The frontend `Message` type declares `runId?: string` (optional, NOT `| null`), so consumers checking `m.runId === undefined` would mis-classify a `null` as "present-but-null". Existing api.test.ts assertions still pass: `"abc" ?? undefined === "abc"`, and `undefined ?? undefined === undefined`.

### WR-03: Integration tests do not exercise the `.eq("user_id", ...)` defense-in-depth filter

The mock returns the same payload regardless of how the production code chains its eq() calls, so previously a regression that dropped the user_id filter would have gone undetected.

### WR-05: `subscribeToRun` parser does not reset `lastEventId` after a JSON parse failure

**Files modified:** `frontend/src/lib/api.ts`
**Commit:** e008371
**Applied fix:** Added `lastEventId = undefined` to the parse-failure catch branch, mirroring the success-path reset. ## Skipped Issues

### WR-06: Mid-stream loadMessages can cause `runStatus: "streaming"` to be persisted from the DB even after SSE terminates

**File:** `backend/app/api/threads.py:633-654`, `frontend/src/hooks/useMessages.ts:411-419`
**Reason:** Skipped intentionally. The reviewer themselves classified this as "mostly a timing artifact and the next reconcile will resolve it" — `runs.status` flips from `streaming` to terminal AFTER `_emit_terminal` has fired, so a `loadMessages` triggered between assistant-row persist and `runs.status` UPDATE returns `run_status: "streaming"` for a run that has actually completed. The recommended fixes are non-trivial: (a) backend deferred-trigger or `completed_at IS NOT NULL` derivation (reviewer themselves marked "probably overkill"); (b) frontend forward-only state transitions on `runStatus` — would require touching every place that writes runStatus to add a "don't downgrade" gate, and risks changing observable terminal-state semantics. The orchestrator's WARNING context list (`apply where reasonable`) explicitly enumerated WR-01, WR-02, WR-03, WR-05, WR-07, WR-08, WR-09 — and notably did NOT include WR-06, suggesting this was intentional deferral. CR-01's fix (gate the merge drop on `subscriptionsRef.has(runId)`) also reduces the practical impact: while the consumer is still live the placeholder is preserved, so the consumer's onTerminal `runStatus: "completed"` flip survives even when a stale-DB `loadMessages` returns `runStatus: "streaming"` for the same row (the user keeps seeing the temp placeholder with the correct terminal flag).
**Original issue:** A `loadMessages` between assistant-row persist and `runs.status` UPDATE returns `run_status: "streaming"` for a completed run; combined with CR-01's pre-fix MERGE-drop, the UI could be stuck on a "streaming" indicator. With CR-01 fixed, the practical impact is bounded — the consumer's terminal flip on the live placeholder survives the stale read; only the persisted DB row briefly carries the stale `streaming` until the next reconcile cycle overwrites it.
