### Gap-006 — LLM agent stops mid-iteration on complex tool-calling prompts (run hard-timeout too short)

- **severity:** out-of-scope (major UX regression in its own right)
- **escalate-to:** new-phase — provisional name **"Adaptive Run Timeouts & Lifecycle States"** (numbering after 063.1, distinct from Phase 064 Validation Harness which is test infrastructure)
- **discovered:** 2026-05-04 during 063.1 close-out UAT
- **scope rationale:** Outside 063.1's frontend gap-closure boundary. The LLM streaming pipeline and timeout machinery were not modified by Phase 063.1 (only one backend READ JOIN was touched). Symptom predates 063.1 and is unaffected by Wave 2/3/4 fixes.

**Symptom (user report 2026-05-04):**
- Simple prompts ("write a 500-word poem"): mostly OK; some delays — addressed by 063.1 Wave 3+4
- Complex prompts ("search → professional report → charts → docx"): agent renders tool call, executes some iterations, then **stops** with no error in UI. User sees partial output and a frozen stream.
- LangSmith trace shows `GeneratorExit` at `langsmith/run_helpers.py:1680` (`yield from self.__ls__gen__`) — the LLM iterator's cleanup signal firing because its consuming task is being cancelled.

**Root cause (verified via Supabase + code):**
- `backend/app/config.py:251` — `run_hard_timeout_seconds: int = 120` (default)
- `backend/app/api/threads.py:842` — `async with asyncio.timeout(settings.run_hard_timeout_seconds)` wraps the entire agent loop
- When the timeout fires, `asyncio.timeout()` cancels the producer task; the cancel propagates through every nested await including the LangSmith-wrapped LLM stream iterator, which surfaces in trace as `GeneratorExit`
- Live `runs` table evidence (12-hour window, 24 runs):
  - `completed: 13` (14–50s, normal)
  - `cancelled: 11` — **5 of them clustered at 120–152s** with `error: null`
  - `failed: 0`
  - The 120s cluster matches the timeout boundary exactly; complex tool-calling agents (search + multi-iteration tool dispatch) routinely exceed 120s
- **Secondary issue 1:** `runs.error` is `null` on timeout-cancel — UI cannot distinguish "agent timed out" from "user clicked Stop"; they look identical
- **Secondary issue 2:** `cancelled` status overloaded — user-Stop and timeout share the same terminal state; should be split (`cancelled` = user intent vs `timed_out` = system limit)

**Suggested fix paths (for the new phase to triage):**
1. **Stopgap** — bump `RUN_HARD_TIMEOUT_SECONDS=600` (or 900) in `backend/.env`; restart backend. Quick and unblocks heavy tool-calling agents immediately.
2. **Per-iteration budget** — replace total-deadline `asyncio.timeout(120)` with per-LLM-call timeout that resets on each tool-call boundary. Aligns with how ChatGPT/Claude treat long agent loops (no hard total cap; each model call has its own budget).
3. **Lifecycle clarity** — capture `runs.error = "timed_out after Ns"` on timeout; introduce `timed_out` as a distinct terminal status (vs `cancelled` = user-initiated). Update frontend to render a clear "Agent reached time limit" banner with a Resume button.
4. **Multi-model awareness** — different models have different speed profiles; consider a per-model timeout (slow reasoning models like o1/Claude Opus get longer budgets than fast ones).

**User direction (2026-05-04):**
> "this is a RAG system that needs time with complex tasks and we should give it time especially if we are using different models, it was working before perfectly and complete the complex tasks and executing code but we have to restore this according to new updated architecture"

→ Path 2 + 3 (proper fix) is the user's stated preference; path 1 may be applied as immediate stopgap.
