### `useMessages.ts` — `lastSeenOffsetRef` Map (D-063.1-01)

**Analog:** existing `subscriptionsRef` Map declared next to other refs.

**Pattern to apply — declare next to subscriptionsRef:**
```typescript
// D-063.1-01 / Gap-004: per-run replay cursor. Updated as each delta
// SSE entry arrives (Redis Stream `id` field). Hook-local Map; survives
// tab switches and reconcile cycles within a page lifetime; F5 wipes it
// (back to since='0' on reload — the runId-match dedup of D-063.1-04
// handles the F5-replay flicker, not the offset cursor).
const lastSeenOffsetRef = useRef<Map<string, string>>(new Map())
```

**Update site — wherever the parser handles a delta event.** The cursor lives **in the API parser** (`api.ts:219-343`), but the parser doesn't currently read the Redis Stream `id` field per event. Two options for the planner:

1. **Plumb `id` through `subscribeToRun` callbacks** — extend `StreamCallbacks.onDelta` (and any other event types we want to cursor on) to receive the SSE event id, then update `lastSeenOffsetRef.current.set(runId, id)` in the hook-level callback. This is the cleanest path and matches how `onDelta` already accumulates content.
2. **Read it from the SSE wire** — `id:` line precedes `data:` line per Phase 062's `event_consumer` clone. Parser stores the most recent `id:` and exposes it on every callback fire.

Either way, the **hook-level usage** is read in reconcile only:

```typescript

  run.run_id,
  lastSeenOffsetRef.current.get(run.run_id) ?? "0",
  callbacks,
```

**Pattern to apply — narrow scope** (D-063.1-09 + D-063.1-04 land in the same diff because they restructure the same loop body):
```typescript
// D-063.1-09 / Gap-003: don't skip the whole iteration; only skip the
// subscribeToRun call. We still need to render the placeholder/dedup
// against existing messages on every reconcile so switching back to a
// thread re-renders the assistant bubble even though SSE is already
// streaming in the background.
//
// D-063.1-04 / Gap-001: prefer dedup-via-runId over inserting a fresh
// temp-${run_id} placeholder. If a DB row carrying runId === run.run_id
// already lives in messages (post-F5 + LEFT JOIN runs delivered it),
// reuse THAT message's id as the SSE callback target — no second bubble.
for (const run of activeRuns) {
  // Pitfall 3 cross-thread safety (UNCHANGED).
  if (activeThreadIdRef.current !== threadId) return

  // D-063.1-04: dedup-via-runId. Look in current messages state for an
  // existing row carrying this run_id; if found, route SSE to its id.
  const existingByRunId = messagesRef.current.find((m) => m.runId === run.run_id)
  const targetId = existingByRunId?.id ?? `temp-${run.run_id}`

  // Idempotent placeholder insert ONLY when no existing row found.
  if (!existingByRunId) {
    const placeholder: Message = {
      id: targetId,
      thread_id: threadId,
      user_id: "",
      role: "assistant",
      content: "",
      created_at: run.started_at,
      updated_at: run.started_at,
      tool_calls: [],
      runId: run.run_id,
      runStatus: "streaming",
    }
    setMessages((prev) => {
      if (prev.some((m) => m.id === targetId)) return prev
      return [...prev, placeholder]
    })
  }

  // D-063.1-09: short-circuit only the SUBSCRIBE call, not the whole iter.
  if (subscriptionsRef.current.has(run.run_id)) continue

  // WR-06: reserve subscription slot before firing.
  const controller = new AbortController()
  subscriptionsRef.current.set(run.run_id, controller)

  // ... existing guardedSetMessages + makeStreamCallbacks + onTerminal wrap ...
  // ... pass `targetId` as assistantId (was placeholderId) ...
  // ... subscribeToRun(run.run_id, lastSeenOffsetRef.current.get(run.run_id) ?? "0", callbacks, controller.signal) ...
}
```

**Note for planner:** the existing reconcile already uses `placeholderId` as the dedup key in the idempotent insert (line 630). D-063.1-04 swaps that key from `temp-${run.run_id}` to `existingByRunId.id` when a runId-matched row exists. This means **all downstream callbacks (`makeStreamCallbacks({ assistantId: targetId })`)** route SSE deltas to the persisted DB row, not to a parallel temp placeholder — collapsing Gap-001's "two bubbles during replay" into a single bubble. The reuse depends on D-063.1-13's backend JOIN delivering `runId` on the row; **plan ordering must lock backend JOIN BEFORE this dedup** (per CONTEXT.md suggested ordering).

**Read-from-ref note:** the dedup needs to read **current** messages, not a stale closure. Use `messagesRef.current` (already declared at `useMessages.ts:316-319` for `stopStreaming`'s WR-03 fix) — same pattern, same justification.

**Pattern to apply — MERGE preserving live placeholders** (verbatim from CONTEXT.md D-063.1-12):
```typescript
// D-063.1-12 / Gap-005: belt-and-braces protection for any code path that
// calls loadMessages while a reconcile-inserted placeholder is in flight
// (terminal-time refetch line 698, buffer_expired fallback line 493,

  // rows are sorted by created_at by the backend; live placeholders
  // belong at the tail by definition (most recent run_id). React keys
  // are stable (`id` field) so no collision risk either way.
  return [...data, ...liveTempPlaceholders]
})
```

```python
# D-063.1-13 / Gap-002: enrich each assistant row with run_id + run_status from
# public.runs via message_id FK. Migration 035 line 24 set up the FK with
# ON DELETE SET NULL — so a deleted message leaves the runs row intact (audit
# trail) but messages without a runs row return null for both fields (fine —
# pre-run-backed messages and run-less inserts don't render the Resume button).
#
# Two queries + Python merge per project convention (no PostgREST embedded
# selects used anywhere else in app/). This stays cheap because:
#   1. Both queries hit existing indexes (messages: thread_id; runs: idx_runs_history
#      on (user_id, thread_id, started_at DESC) — migration 035 line 44).
#   2. Result-set sizes are bounded by thread length — the same caller already
#      paginates client-side.
#
# RLS: messages SELECT goes through messages_select_own + the .eq("user_id", ...)
# defense-in-depth filter below; runs SELECT goes through runs_select_own +
# the .eq("user_id", ...) filter — D-063.1-14 verifies both via the
# test_063_1_messages_runs_join cross-user test.
#
# D-062-14 file-layout: this endpoint is at line 580-604, which is OUTSIDE
# the off-limits 2057-2076 region (DEF-061.1-02 producer exception classifier).
# Verify before edit by reading the off-limits markers in 062-CONTEXT.md.

@router.get("/{thread_id}/messages", response_model=list[MessageResponse])
async def get_messages(
    thread_id: str,
    current_user: dict = Depends(get_current_user),
    supabase: Client = Depends(get_supabase),
):
    # CR-01 follow-up: switch from .single() to .maybe_single() for symmetry
    # with list_active_runs — but defer that to its own commit if not in scope.
    # 063.1 keeps this line as-is to avoid feature creep.
    thread = await aexec(
        supabase.table("threads")
        .select("id")
        .eq("id", thread_id)
        .eq("user_id", current_user["id"])
        .single()
    )
    if not thread.data:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Thread not found")

    # 1. Fetch messages (UNCHANGED).
    msgs_resp = await aexec(
        supabase.table("messages")
        .select("*")
        .eq("thread_id", thread_id)
        .eq("user_id", current_user["id"])
        .order("created_at")
    )
    messages = msgs_resp.data or []

    # 2. Fetch runs for this thread keyed by message_id (NEW — D-063.1-13).
    # idx_runs_history index serves this exactly (user_id, thread_id, started_at DESC).
    runs_resp = await aexec(
        supabase.table("runs")
        .select("run_id, message_id, status")
        .eq("thread_id", thread_id)
        .eq("user_id", current_user["id"])
    )
    runs_by_message = {
        r["message_id"]: r
        for r in (runs_resp.data or [])
        if r.get("message_id") is not None
    }

    # 3. Zip — assistant rows get run_id/run_status populated when an FK match
    # exists; user rows and pre-run-backed assistant rows return null.
    for m in messages:
        run = runs_by_message.get(m["id"])
        m["run_id"] = run["run_id"] if run else None
        m["run_status"] = run["status"] if run else None

    return messages
```

**Note for planner:** the `run_status` mapping uses `runs.status` directly — the column already enforces the 4-value CHECK constraint via migration 035 line 25, so Pydantic's `Literal["streaming", "completed", "failed", "cancelled"] | None` validation aligns with the DB invariant.
