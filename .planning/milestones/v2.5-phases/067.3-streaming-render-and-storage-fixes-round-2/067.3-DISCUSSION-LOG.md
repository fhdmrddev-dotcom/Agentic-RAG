## R-2 Download Auth Approach

### Q1: Which approach?

| Option | Description | Selected |
|--------|-------------|----------|
| JS blob fetch+download (Recommended) | Frontend intercepts `<a>` click, calls `fetch('/sandbox-outputs/...')` with `Authorization: Bearer`, follows 302 to Supabase CDN, downloads as Blob. NO backend changes. Trade-off: right-click "Save link as" won't trigger JS hook. | ✓ |
| Token-rewrite at read time | Backend mints fresh short-lived (~5min) HMAC token per sandbox link in chat-history response; frontend renders `<a href='?token=jwt'>`. Native anchor + right-click work; new secret rotation surface. | |
| Both — belt-and-suspenders | JS blob primary, token-rewrite fallback. Probably overkill. | |

**User's choice:** JS blob fetch+download
**Notes:** Cleanest for current scope; right-click "Save link as" is rare in chat-history context.

### Q2: UX during the fetch?

| Option | Description | Selected |
|--------|-------------|----------|
| Disabled card + spinner (Recommended) | Card visually disables, spinner replaces Download icon, returns to normal on success or red error state on failure. | ✓ |
| Fire-and-forget | No visual state change on card; toast on completion only. | |
| Toast-only feedback | Click triggers fetch silently; toast on completion. Less intrusive but easy to miss. | |

**User's choice:** Disabled card + spinner

### Q3: Error handling?

| Option | Description | Selected |
|--------|-------------|----------|
| Toast with status-specific copy (Recommended) | 401: "Session expired"; 404: "File not found" (matches backend's existence-leak prevention); 5xx: "Download failed — try again". | ✓ |
| Generic "Download failed" toast | Single error message; loses session-expired clue. | |
| Inline error on card + retry button | Red border + Retry; more intrusive but discoverable. | |

**User's choice:** Toast with status-specific copy

## R-1 Streaming Cache Shape

### Q1 (initial): Which cache shape?

| Option | Description | Selected |
|--------|-------------|----------|
| In-memory Map (initial recommendation) | Map<threadId, deltas[]> as a sibling buffer ref; replay on switch-back. ~50-100 lines. | |
| Redis re-subscribe-on-switch | Extend reconcile-trigger to fire on thread-switch; reuse Phase 062 replay-and-tail. | |
| Hybrid | Local fast-path + Redis fallback. | |

**User's choice:** "Other — what's the most stable recommended option? how Claude.ai and ChatGPT do? did we consider scalability for future user growth? cloud or on-prem or small/medium/big organizations? we're planning to scale up later, we already made some seeds."

**Notes:** User pulled in architectural concerns (scalability, future multi-tenant, deployment topology) — re-asked the question with research-grounded options.

### Q1 (re-asked): Given scalability + ChatGPT/Claude.ai parity, which fix shape?

| Option | Description | Selected |
|--------|-------------|----------|
| Structural per-thread store (Recommended for scale) | Refactor `messages: Message[]` → `messagesByThread: Map<string, Message[]>`. Removes `guardedSetMessages` entirely. Mirrors ChatGPT/Claude.ai client architecture. ~200-400 lines touched. Aligns with v2.6+ multi-tenant + org-shared threads. | ✓ |
| Tactical Map buffer (Faster, narrower) | Sibling buffer ref preserving current state shape. ~50-100 lines. Leaves `guardedSetMessages` race intact for future features. | |
| Server re-subscribe on switch (Simplest, stalest) | 50-200ms blank state on every switch; doesn't fix client-side state shape. | |

**User's choice:** Structural per-thread store
**Notes:** Motivated by user's targeting of org-scale production (per `project_target_scale.md`) and deferred v2.6+ multi-tenant scope. ChatGPT/Claude.ai both use thread-keyed client state with server-side re-subscribe as recovery path.

### Q2: Cache key shape?

| Option | Description | Selected |
|--------|-------------|----------|
| threadId only (Recommended) | Map<threadId, Message[]>. Matches DB shape. Multi-run-per-thread appends to same bucket. | ✓ |
| threadId + runId composite | Map<threadId, Map<runId, Message[]>>. Clean separation but extra indirection. | |
| Just runId (no thread) | Map<runId, Message[]>. Awkward for the common display-this-thread's-history case. | |

**User's choice:** threadId only

### Q3: Eviction policy?

| Option | Description | Selected |
|--------|-------------|----------|
| Keep last N=5, LRU evict (Recommended) | Up to 5 thread buckets; evict LRU non-streaming on a 6th. Streaming threads pinned. Re-load from server on next view. | ✓ |
| Keep all viewed threads in session | No eviction; clear on logout. Larger memory footprint at scale. | |
| Evict immediately on stream-end + leave-thread | Aggressive cleanup; defeats stream-done-then-switch-back common case. | |

**User's choice:** Keep last N=5, LRU evict (streaming pinned)
