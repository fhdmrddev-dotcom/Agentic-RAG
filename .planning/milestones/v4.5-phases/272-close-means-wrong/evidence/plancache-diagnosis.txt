Phase 272-05 — PL/pgSQL generic-plan regression found by the SEED-273 ladder (2026-10-03)
=========================================================================================

How it was found. The first ladder run (ladder-run1-aborted.txt) printed, for the UNFILTERED
control at the global knobs, a body-statement CUSTOM plan of
  Index Scan[document_chunks_embedding_idx] · Index Scan[documents_pkey]   shared read 259
but a GENERIC plan of
  Seq Scan · Bitmap Heap Scan · Bitmap Index Scan[idx_document_chunks_document_id]   shared read 100,396
and a measured function-call p50 of 1,586.7 ms (p95 1,866.0). The 500-chunk set's INDEX branch read
p50 445.7 ms while its EXACT branch read 12.8 ms. The run was stopped and the cause isolated.

Method. recall_bench (100,000 chunks, pgvector 0.8.0), caller 7fcfb80e-… (69,805 chunks, its own
org). 12 sequential calls on ONE session (a pooled backend connection is one session), each in a
savepoint with SET LOCAL ROLE authenticated + both claim GUCs. Every DDL change (drop function,
recreate migration 170's body, drop the btree, ALTER … SET) is inside a transaction that was
ROLLED BACK. Scripts: plancache_diag_vector.py, plancache_diag_keyword.py (this directory).

Reading.
- Calls 1-5 are custom plans in every scenario; from call 6 PL/pgSQL may switch to its one generic plan.
- C vs D: the 170 body is UNCHANGED between them; only the btree differs. The btree alone makes the
  generic plan a whole-table document_id join (vector: 3-8 ms -> 0.45-1.0 s; keyword: 0.5-0.9 s ->
  12-32 s). So migration 200, as applied, regresses UNFILTERED search on every pooled connection
  after its fifth retrieval call, and makes the filtered index branch ~50x slower.
- E / G / KE: `SET plan_cache_mode = force_custom_plan` on the function removes it on both arms
  (at or below the pre-272 figures).
- Fix shipped as migration 201 (ALTER FUNCTION … SET plan_cache_mode = force_custom_plan, both RPCs).
  The btree stays: the exact branch needs it.
