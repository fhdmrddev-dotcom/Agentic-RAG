rather than a schema, an advertisement and a candidate-injection path already shipped.

What the executor does, in order:

1. Read `phase.config.capability`.
2. Resolve it against `EXTERNAL_ACTION_CAPABILITIES` imported from
   `app.services.harness.grounding`. If the name is absent, RAISE — copy `_exec_programmatic`'s
   closed-registry raise shape. **Never resolve dynamically, never `eval`, never fall back to a
   default capability.** A name not present raises; that is the rule `_TOOL_REGISTRY`,
   `PROGRAMMATIC_PHASE_REGISTRY` and `EMITTER_REGISTRY` all share.
   ⚠ In practice `ExternalActionPhaseConfig`'s `Literal` already rejects a bad name at parse time. The
   executor-level raise is the SECOND line of defence for a row that reached the engine another way,
   and it is what D-02 asks for. Say so in a comment so nobody deletes it as redundant.
3. Resolve the inputs the action WOULD have used from `phase.config` and `accumulated_outputs`, using
   the shipped conventions of the neighbouring executors.
4. Compose `output["text"]` as the NOT-SENT body — see the copy contract below.
5. Return a plain dict carrying `text` PLUS a sentinel key (for example `recorded_intent`) holding the
   structured record: the capability, the resolved inputs, and nothing else. This mirrors the shipped
   emit-failure sentinel exactly — an executor signals a non-`completed` terminal by putting a key on
   its ordinary output dict, and the ENGINE branches on that key. The engine branch is plan 189-11's.

THE OUTPUT BODY — three blocks, and the phrasing rules are binding:

- It OPENS with the negation, never with the action.
- A "what this step would have done" block naming the action in the same business words the canvas uses
  (`Sends an email` / `Creates a ticket` / `Posts a message`) plus the resolved inputs.
- A closing negation drawn from a CLOSED TABLE, never improvised: `send_email` produces "No email was
  sent."; `create_ticket` produces "No ticket was created."; `post_message` produces "No message was
  posted." Follow it with a sentence naming what the record is NOT — it is a record of an intention,
  not a receipt.
- It uses NO checkmark and NO past-tense success verb about the action itself ("done", "delivered",
  "sent to"). A recorded intent that reads like a receipt is the failure mode this whole phase exists
  to avoid, and it is the `consequence is not receipt` rule the Control Room already binds this
  codebase to.

WHAT THE EXECUTOR MUST NOT DO, each with its reason:

- **No network I/O of any kind.** SC#4. No `httpx`, no `requests`, no socket, no MCP client — there is
  ZERO MCP code in `backend/app` and this phase does not add the first line of it.
- **No agent loop.** Do not drive a streaming iteration and do not pass a tools override. Making the
  capability a callable tool would mean an LLM decides whether and how to send, which contradicts D-05
  and D-02 both.
- **Do NOT reuse the `llm_human_input` substrate.** It times out and returns NORMALLY, so the run
  ADVANCES — a fail-open shape. The armed checkpoint 189 inherits goes through a different path with an
  indefinite, shutdown-safe wait and is already fail-closed. This executor runs AFTER approval; it owns
  no waiting at all.
- **No `_TOOL_REGISTRY` entry, no `get_tools()` schema, no `*_TOOL` schema constant.** All three are
  Phase 190's, and the second opens the D-20 leak.

Then take V10 from RED to GREEN in `backend/tests/unit/test_189_no_egress.py`: with the HTTP transport
