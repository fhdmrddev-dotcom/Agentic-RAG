# Phase 189 Plan 06: Migration 115 — the Sixth `workflow_phases.status` Literal Summary

**`workflow_phases.status` now admits a sixth value, and the value it admits is a SLUG.**
The governed external action's outcome — recorded, not transmitted — is neither `completed`
(the send did not happen), nor `failed` (nothing went wrong), nor `skipped` (the step DID run
and a human DID approve it). It now has its own persisted word: `recorded_not_sent`. The
rendered sentence *"Not sent — recorded"* is **provably rejected** by the same constraint.

**Why two commits and not one.** CLAUDE.md's rule is *apply → regenerate → commit both*, but
the apply is a blocking checkpoint that must sit BETWEEN authoring and regeneration, so a
single shared SHA is impossible. The invariant that actually protects the deploy is
**directional**, and it was verified rather than assumed:

- `git ls-tree 8b8c393e supabase/migrations/115_workflow_phases_recorded_not_sent.sql` →
  the file **was already in the tree** at the regeneration commit.
- `git log --oneline -- <migration> <artifact>` → `8b8c393e` after `0e900cc8`.
- No commit anywhere carries a regenerated `full-schema.sql` without the migration present.
  Between the two commits the tree held the migration and an UNCHANGED artifact — coherent,
  with `test_migration_115.py` green-skipping, so nothing ever claimed a widening that was
  not live.

## Task 3 — the regeneration

**Exact command, run from the repo root:**

```bash
bash scripts/regenerate-full-schema.sh
```

**`--reset` was NOT passed.** Default mode dumps the live DB schema as-is. The artifact was
produced by the script and **never hand-edited**. Script output confirmed
`Latest migration on disk: 115_workflow_phases_recorded_not_sent.sql`, 5827 lines (unchanged
line count).

**The diff is ONE line — the plan's review guard passes with room to spare.** `git diff --stat`
reports `1 file changed, 1 insertion(+), 1 deletion(-)`, confined entirely to
`supabase/full-schema.sql:1932`:

```diff
-    CONSTRAINT workflow_phases_status_check CHECK ((status = ANY (ARRAY['pending'::text, ... 'skipped'::text])))
+    CONSTRAINT workflow_phases_status_check CHECK ((status = ANY (ARRAY['pending'::text, ... 'skipped'::text, 'recorded_not_sent'::text])))
```

This is the payoff of Task 1's first deliberate departure from the 114 analog: writing the
constraint as `= ANY (ARRAY[…])` with `::text` casts — matching what `pg_dump` regenerates —
rather than the more readable `IN (…)` that 114 used. Had it been written as `IN`, the dump
would have reformatted the whole constraint and the diff would have been unreviewable against
its own guard. **The guard never had to fire, because the design anticipated it.** No hunks
require explanation; there are none.

## Deviations from Plan

### 1. [Documented, not auto-fixed] The apply method differs from the plan's stated truth

- **Found during:** Task 3, while verifying Task 2's outcome.
- **Issue:** The plan's `must_haves.truths` asserts *"The operator applied the migration by
  pasting it into the Supabase SQL editor."* That is not literally what happened. The apply
  was **operator-authorised**, but executed by the orchestrator running the migration file
  verbatim in a single transaction via `psycopg2` against `127.0.0.1:54322`.
- **Why it is recorded rather than smoothed:** the substantive prohibition — CLAUDE.md's
  outright ban on `supabase db push` and `supabase db reset`, which exist to protect local dev
  data — **held completely, and is proved by surviving row counts above rather than claimed**.
  The SQL-editor instruction is the mechanism by which that ban is normally honoured, not the
  ban itself. But a `truths` entry is believed by every downstream reader and guarded by
  nothing, so silently inheriting a false one is the failure mode this project has repeatedly
  paid for.
- **Files modified:** none — this is a record, not a code change.
- **Consequence for future plans:** `test_migration_115.py`'s docstring and skip-reason string
  both still say *"operator pastes … into the Supabase SQL editor"*. Left unedited: it is
  accurate as the standing protocol and the skip branch is now unreachable in this
  environment. Worth knowing if that text is ever cited as evidence of what occurred.

### 2. Out-of-scope, untouched

`supabase/snippets/` carries ~38 modified/untracked `Untitled query *.sql` files — pre-existing
operator SQL-editor scratch artifacts, unrelated to this plan. **Not staged, not modified, not

### 3. Measured, out-of-scope: `STATE.md`'s frontmatter is not strict-YAML-parseable — and already was not

- **Found during:** the state update, while validating my own edit did not corrupt the file.
- **Measurement:** `yaml.safe_load` on the frontmatter block fails with
  `ScannerError: mapping values are not allowed here`. **It fails identically at `HEAD`**
  (`git show HEAD:.planning/STATE.md`, line 6 col 61 — inside the 189-09 `last_activity`
  prose), so this predates every edit made here. The cause is structural, not a typo: the
  long single-line `last_activity` / `stopped_at` narrative values are unquoted and contain
  `: ` sequences, which YAML reads as nested mapping keys.
- **Why it is worth recording:** the project's memory notes that several GSD state verbs
  write false records — `state.record-session` reporting success while winding `last_updated`
  backwards and deleting `stopped_at`. A frontmatter that no strict parser can read is a
  plausible mechanism for exactly that class of corruption, since a lenient line-based
  rewriter has no way to know where a value ends.
- **Action taken: none, deliberately.** Fixing it means block-quoting several very long
  narrative values across a file this plan does not own — out of scope per the scope boundary,
  and a change that would dwarf the plan's real diff. My edits followed the file's existing
  convention exactly (a non-standard `prior_activity:` key I briefly introduced was removed
  in favour of the established *"prior record follows"* inline pointer, so key shape is
  unchanged from HEAD). Logged here rather than fixed.
