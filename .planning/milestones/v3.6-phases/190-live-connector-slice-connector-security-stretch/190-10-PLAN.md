**Auth.** The username is the **email address** of the Atlassian account; the password is an
**API token**, not the account password. Atlassian states plainly: *"Authentication using
passwords has been deprecated."* `httpx` builds the header for you with
`auth=(account_email, api_token)` — **do not hand-roll the base64**, because a hand-built string
is one interpolation away from a log line.

**ADF.** *"Version 3 of the API provides support for the Atlassian Document Format (ADF),
including in issue resources."* The `description` field takes an ADF **object**:

```json
{ "type": "doc", "version": 1,
  "content": [ { "type": "paragraph", "content": [ { "type": "text", "text": "simple short description" } ] } ] }
```

**Minimal create payload:**
```json
{ "fields": {
    "project":   { "key": "PROJ" },
    "issuetype": { "name": "Task" },
    "summary":   "…",
    "description": { "type": "doc", "version": 1, "content": [ … ] } } }
```
Required: `project` (key or id), `issuetype` (name or id), `summary`. `project.key` is the
non-secret `config` field migration 116 stores.

**Error envelope.** Jira returns proper HTTP status codes (400 / 401 / 403 / 404) with a body
shaped `{"errorMessages": [...], "errors": {"<field>": "<message>"}}`. **So
`raise_for_status()` is correct for Jira and WRONG for Slack** — the adapters genuinely differ,
and the plan must not factor out a shared "check the response" helper that flattens the
difference (`190-RESEARCH.md` § Anti-Patterns; UI-SPEC §8c).

**Host rule** (research §R15): `host == "atlassian.net" or host.endswith(".atlassian.net")` —
already implemented inside `egress.validate_destination` for the `create_ticket` capability. The
adapter passes the org-configured `base_url`; it does not re-implement matching.

⚠ **A1 in the assumptions log:** the error-envelope shape is not driven against a live Jira.
Verify it on the first live UAT row (D-30) and correct the adapter if it differs.
