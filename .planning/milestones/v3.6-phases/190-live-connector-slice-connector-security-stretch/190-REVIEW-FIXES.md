## CR-01 — `secret_ciphertext` readable over PostgREST by any authenticated org member

**Severity:** Critical · **Verdict:** ✅ FIXED · **Commit:** `f64a0ebb`

### It was worse than the review stated, and that was measured before anything was changed

The review named `authenticated`. The live database held it for **`anon` too** — the
*unauthenticated* role — along with INSERT, UPDATE, DELETE and full table SELECT for both.
Measured against `127.0.0.1:54322` before any edit:

```
$ select grantee, privilege_type from information_schema.column_privileges
   where table_name='connector_connections' and column_name='secret_ciphertext';

  ('anon',          'INSERT')   ('anon',          'REFERENCES')
  ('anon',          'SELECT')   ('anon',          'UPDATE')
  ('authenticated', 'INSERT')   ('authenticated', 'REFERENCES')
  ('authenticated', 'SELECT')   ('authenticated', 'UPDATE')
  ('postgres', …)               ('service_role', …)
```

All of it comes from Supabase's stock
`GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated, service_role` default
privileges. Migration 116 simply never narrowed them — and its header cites `sso_configs`
(mig 104:372-374) as the model for its RLS shape, **a table with no secret column at all**.
The precedent did not carry.

### RED, verbatim — `tests/integration/test_190_secret_column_privilege.py`, before 118 existed

```
$ venv/Scripts/python.exe -m pytest tests/integration/test_190_secret_column_privilege.py -q

E       Failed: DID NOT RAISE <class 'psycopg2.errors.InsufficientPrivilege'>
tests\integration\test_190_secret_column_privilege.py:143: Failed
        [test_the_secret_column_is_unreadable_by_a_non_service_role[authenticated]]

E       Failed: DID NOT RAISE <class 'psycopg2.errors.InsufficientPrivilege'>
tests\integration\test_190_secret_column_privilege.py:143: Failed
        [test_the_secret_column_is_unreadable_by_a_non_service_role[anon]]

E       AssertionError: CR-01: `anon` still holds ['DELETE', 'INSERT', 'REFERENCES',
        'SELECT', 'TRIGGER', 'TRUNCATE', 'UPDATE'] on public.connector_connections.

E       AssertionError: CR-01: no migration under …\supabase\migrations revokes anything on
        connector_connections. The live grant would be undone by the next
        `regenerate-full-schema.sh --reset` and would never reach cloud.

6 failed, 2 passed, 1 warning in 0.65s
```

**GREEN after: `8 passed, 1 warning in 0.36s`.**

The suite is seven properties, and three of them exist specifically to stop the fix from being
wrong in the other direction:

| case | what it stops |
|---|---|
| `SELECT *` is refused for `authenticated` | the literal devtools one-liner |
| the safe columns still read, together **and individually** | a fix that just revoked everything |
| `authenticated` keeps INSERT/UPDATE **on the secret column** | an org admin who can no longer store a credential |
| **`service_role` still reads the secret** | the harness resolver (no user JWT) breaking every send |
| the grant is recorded in a numbered migration | a hand-applied privilege that never reaches cloud |

### The consequence the fix forces, stated rather than discovered later

With the column grant in place, **`SELECT *` fails for `authenticated`** — Postgres expands
`*` to every column and checks SELECT on each, so one missing column refuses the whole
statement. **PostgREST's default projection is `select=*`.**

This was not reasoned about; it was **driven against the live PostgREST** with a minted
`authenticated` JWT, after 118:

```
GET  ?select=*                     -> 403 {"code":"42501","message":"permission denied for table connector_connections"}
GET  ?select=secret_ciphertext     -> 403 {"code":"42501","message":"permission denied for table connector_connections"}
GET  ?select=<the safe column list>-> 200 []
POST Prefer:return=representation  -> 403 {"code":"42501","message":"permission denied for table connector_connections"}
POST …&select=<the safe list>      -> 403 {"code":"42501","message":"new row violates row-level security policy for table \"connector_connections\""}
```

Read the last two together: **without** an explicit `select`, the write is refused by the
PRIVILEGE check; **with** it, the write gets past the privilege check and is refused by the ROW
gate, which is the correct behaviour for a JWT with no org membership.

So `connector_service.py` now names its columns everywhere it runs on the user-JWT client:

* `_SELECTABLE_COLUMNS` — **derived** from `ConnectorConnectionResponse.model_fields`, never
  retyped, so a column added to the table cannot enter a projection without a model field
  appearing in a diff a reviewer reads;
* `.select(_SELECTABLE_COLUMNS)` on `list_connections`, `get_connection` and
  `update_connection`'s ownership check;
* `_project(builder)` on all four writes (insert / update / verdict / delete), because
  postgrest-py 2.29 exposes no chaining API for `?select=` on POST / PATCH / DELETE;
* `_fetch_connection_row` **keeps `select("*")`** — it is the one query that runs on the
  service-role pool and the one caller that legitimately needs the column. The docstring now
  says so, so the asymmetry reads as a decision.

`_project` is checked for **REACH, not just RED**: a case drives it against a **real**
`postgrest.SyncPostgrestClient` builder with a control asserting postgrest does *not* set
`select` by itself. Without that, every other CR-01 case would pass against a `_project` that
had silently stopped working after a library upgrade, because they all run against doubles.

## CR-04 — blocking DNS on the event loop, from three `async def` call sites

**Severity:** Critical · **Verdict:** ✅ FIXED · **Commit:** `50d058e3`

`_default_resolver` calls `socket.getaddrinfo`, a **blocking** libc call. `validate_destination`
is a plain `def`, and all three call sites are inside coroutines — `egress.py:550`
(`send_pinned_http`), `egress.py:719` (`open_pinned_smtp`) and the executor's GATE 3.

Two properties make it more than a latency note, and both are quoted from the tree rather than
argued: **`timeout=` does not bound it** (the timeout goes to the transport, not to
`getaddrinfo`; a blackholed nameserver blocks for the OS resolver's own budget with no
application-level cap), and **it is remotely triggerable with no rate limit** —
`POST /connectors/connections/{id}/check` reaches `open_pinned_smtp` on a user HTTP request.
`egress.py`'s own docstring cites SEED-065's measurement of the cost: *"a sync HTTP call left
on the event loop froze ALL request serving for the round trip."*

⚠ **The SMTP site is the sharp one:** the module has wrapped the SMTP **connect** in
`run_in_threadpool` since 190-07 and left the DNS lookup that PRECEDES it on the loop. Half a
fix reads, at a glance, exactly like a whole one.

### RED, verbatim — a THREAD IDENTITY, because nothing else can tell "off the loop" from "fast enough today"

```
E       AssertionError: CR-04: send_pinned_http resolved DNS on the event loop thread 96204.
E       assert 96204 != 96204

E       AssertionError: CR-04: open_pinned_smtp resolved DNS on the event loop thread 96204.
E       assert 96204 != 96204

E       assert 88396 != 88396          [the executor's GATE 3]
tests\unit\test_190_review_fix_executor.py:315: AssertionError
```

### What was deliberately NOT changed

`validate_destination` **stays synchronous and stays a plain module attribute**. Making it a
coroutine, or hiding it behind an `avalidate_destination` name at the call sites, would break
the D-06 ordering fence's `monkeypatch.setattr(phase_types, "validate_destination", …)` — the
exact shape RESEARCH §R10 rejected (*"a transport subclass makes the guard implicit, and
D-06's whole point is that the ordering must be assertable directly"*). **Only the thread
moved.** All five ordering cases stay green.

### Residual, named rather than smoothed

The review's second suggestion — an `asyncio.wait_for` cap so a hostile nameserver cannot hold
a **threadpool slot** either — was **not** taken. The Critical is *"blocking I/O on the event
loop"* (the D-v2.5-01 red line) and that is closed: a busy threadpool thread degrades
throughput, a blocked event loop stops every concurrent SSE stream on the worker. Adding a
lookup budget is a new behaviour with its own failure mode (a legitimately slow resolver now
fails), which is a scoping decision, not a defect repair — and D-32 fences this round to
defects. `190-15-SUMMARY.md:374` already records the worker-occupancy half.

## WR-02 — `update_connection` omitted the capability↔config validator

**Severity:** Warning · **Verdict:** ✅ FIXED · **Commit:** `f64a0ebb`

`ConnectorConnectionCreate` runs `_reject_config_capability_mismatch` in a
`@model_validator(mode="after")`. `ConnectorConnectionUpdate` **cannot** — it carries no
`capability` field, on purpose (changing it would orphan both the config shape and the stored
secret in one edit) — so the check has to happen in the service, where the stored capability is
already in hand one block above.

Without it, `PATCH {"config": {"default_channel": "#ops"}}` on a `send_email` connection
resolved through Pydantic's **smart union** to a `PostMessageConfig`, was written, and answered
**200 with the new row** (the response model has no cross-field check either, so it validated).
The SMTP host, port and from-address were **gone**, Settings rendered a blank *Sends to* cell,
and the next run of every workflow bound to it failed with `SmtpConfigInvalid` — with nothing
anywhere reporting that a valid PATCH had destroyed the destination.

### RED, verbatim — driven against a PLANT, because the fix had already landed

The validator line was removed from **production source** (`connector_service.py:619` →
`pass  # PLANT-WR02`), observed, then restored with `grep -c PLANT` → **0**:

```
E       Failed: DID NOT RAISE <class 'ValueError'>      × 6
6 failed, 3 passed, 1 warning in 0.46s
```

**The three that passed under the plant are the point:** the drive is a 3 × 3 matrix, and the
matching diagonal must still succeed. A fix that simply refused every config PATCH would
satisfy the six mismatched pairs and break the product. Two further assertions keep the six
honest — the refusal must **name the stored capability** (so an operator can tell which end is
wrong), and **no UPDATE may have been issued** before the refusal (a row already destroyed with
a cosmetic exception on top is not a fix).

The `ValueError` maps to **422** in the router, deliberately not 404: ownership is settled
before the body is interpreted, so there is no oracle to protect at that point.

## WR-05 (+ IN-03) — an entirely empty connection was accepted, and the empty secret encrypted

**Severity:** Warning · **Verdict:** ⚠ HALF FIXED (the defect is closed) · **Commit:** `f64a0ebb` · **Remainder:** `D-190-DEF-12`

No field on `ConnectorConnectionCreate` or on the three config models carried a length, format
or non-empty constraint. *Add a connection* → *Sends an email* → **Save**, with nothing typed,
produced `{host: "", port: 0, from_address: "", tls: "starttls"}` with `secret = ""`, the API
answered **201**, and `encrypt_secret("")` stored a real `enc:v1:` envelope over an empty
password. Settings then listed a connection named `""` with a blank *Sends to* column that a
workflow author could bind — and the first time anyone found out was a **failed workflow run**.

Constrained at the **model**, which is what the review's own Fix section names as the right
home (*"where both the API and any future caller are covered"*): `NonEmpty` on `name`,
`secret`, `host`, `from_address`, `base_url`, `project_key`, `account_email` and
`default_channel`; `Port = Annotated[int, Field(ge=1, le=65535)]`. The same constraints apply
on the PATCH path, where ABSENT stays legal and PRESENT-BUT-EMPTY does not.

**IN-03 is folded in here rather than deferred**, because it is the same defect wearing a
number instead of a string: an unparseable port became `0`, and `validate_destination`'s
`resolved_port = port or parsed.port or _DEFAULT_PORTS[scheme]` treats `0` as **falsy** and
substituted 465/587 — so someone who typed `four sixty five` got a working connection on a port
they never chose. `ge=1` makes it a refusal.

### RED, verbatim

```

```

**And one RED of my own test, which is recorded because it is exactly the reach problem this

## WR-01 — DEFERRED, and its false ✅ CORRECTED

**Severity:** Warning · **Verdict:** 📋 code DEFERRED `D-190-DEF-10` · **score FIXED in `190-VALIDATION.md`**

The review is right, and it was re-derived at HEAD rather than inherited.
`_pre_credential_destination` returns the step's `base_url` if one exists, else the
per-capability constant; `ExternalActionPhaseConfig` is `extra='forbid'` and carries **no
`base_url`**. So on the shipped path `post_message` validates the code constant, and
`create_ticket` / `send_email` get `destination is None` — **`validate_destination` is never
called before the resolver.**

**Not fixed, and the reason is not effort.** There is no reachable bypass (both binders call
`validate_destination` as their first statement, so no socket opens unvalidated), and the
honest repair touches `ExternalActionPhaseConfig`'s `extra='forbid'` contract and the D-13
config shape — a settlement 190-06 made deliberately and `test_190_egress_ordering.py`
asserts. Undoing a design decision to satisfy a fence is the tail wagging the dog; it belongs
