**The gate is `GROUNDING_DIAL_TYPES` exactly — `llm_agent` + `llm_batch_agents`. `llm_emit` is
DELIBERATELY EXCLUDED, on measured evidence, and the measurement contradicts a shipped docblock.**

The review said to add `llm_emit` "only if the emit executor really does bound-scope retrieval —
the `LlmEmitPhaseConfig` docblock says it does". That claim was checked in source at plan time and
it does not survive:

- `LlmEmitPhaseConfig`'s docblock (`backend/app/models/harness.py`, the "Shape-symmetry optionals"
  comment above `folder_scope`) claims the field is *"load-bearing in the executor plan — bound-scope
  retrieval + skill composition feeding the emit"*. That is a **plan-era** claim.
- The shipped executor refutes it. `_exec_llm_emit` (`backend/app/services/harness/phase_types.py`)
  is a SEALED FORCED EMIT: it never drives the agent loop, never calls `_build_phase_tool_context`,
  never reads `folder_scope` and never touches `folder_subtree_ids`. Its evidence comes from
  `_emit_evidence(accumulated_outputs)` — the retrieval PRIOR phases already performed. A grep for
  `folder_scope` / `folder_subtree` across the whole `_exec_llm_emit` body returns zero functional
  hits.
- The only run-time consumer of a phase's `folder_scope` is the per-phase narrowing inside the
  sub-agent `ToolContext` build, which serves the tool-carrying types.

So the honest predicate is the shipped two-member constant. Reusing `GROUNDING_DIAL_TYPES` — rather
than declaring a third list — is also what keeps this correct for free: it is the same "which types
can actually reach the knowledge base" question the grounding derivation already answers, and
`grounding.grounding_cause`'s own docblock gives the identical reason for not reading `folder_scope`
(*"it exists on all five LLM config members … so reading it would auto-lock steps that read nothing"*).

**`GROUNDING_DIAL_TYPES` MUST NOT BE WIDENED.** It mirrors the backend grounding rule exactly; a
third member there would change grounding semantics — a Phase-185 red line. It is READ here, never
edited.

**A second over-claim falls out of the same gate, and it is wanted.** Today an `llm_human_input`
step with a sole bound folder renders "Search {folder}" because tier (3) is reached before tier (4).
After the gate it falls to tier (4)'s "Wait for your approval", which is what that step does.
</decision_taken_at_plan_time>
