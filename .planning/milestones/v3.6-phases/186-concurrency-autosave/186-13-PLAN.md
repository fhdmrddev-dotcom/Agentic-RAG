Two calls the scope note delegated to the planner, decided here so the executor does not
re-litigate them:

**WR-04 — the flag-off Save-during-publish outcome is an HONEST HELD SENTENCE, not a disabled
button.** Rejected alternatives, with reasons:
  - *Disable the Save-draft button while a publish runs.* A disabled control with no stated
    reason is the exit hidden; the project's own R12 rule (`PublishGauntlet.blockedReason`) is
    that greying alone is never enough. It would also change the flag-off header's resting
    markup, which `WorkflowBuilderPage.header.test.tsx:305` pins as a literal.
  - *Drop the hold entirely when the flag is off, so Save writes exactly as it did pre-186.*
    Superficially the purest D-181-01 reading, and rejected on evidence: the stage-5 token guard
    shipped by 186-02 is NOT flag-gated, so a flag-off write landing mid-gauntlet now costs the
    person their entire golden run and a real provider bill. Holding is the honest protection;
    removing it would restore byte-identical CLIENT behaviour by making the SERVER refuse them.
  - *Keep the shipped sentence on both surfaces.* Forbidden by this phase's own rule: with the
    automatic flush correctly gated off, "changes will save when it finishes" is a promise the
    loop will not keep — a false receipt in the future tense.
So: the sentence becomes a function of `enabled` (promise when the loop will flush, instruction
when it will not), and it renders on both surfaces.

**WR-05 — a 404 halts the loop and states a terminal sentence; it does NOT auto-recreate the
draft.** Rejected: clearing `draftIdRef` so the next write re-creates the row. The 404-collapse
is deliberate (missing and not-owned answer identically, so no existence leaks), which means the
CLIENT literally cannot tell "deleted elsewhere" from "not yours". Silently minting a new row on
a refusal it cannot classify is a worse failure than stopping. The loop stops, the draft stays
dirty, and every leave guard therefore fires — which is the correct outcome for work that cannot
be persisted here.
</decisions_this_plan_locks>
