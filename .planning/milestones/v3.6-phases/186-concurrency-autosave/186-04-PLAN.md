guards, and retire a slot that has never been read.

**`phases`** reference change (`:585-597`), and `hasEdited` on the page explicitly *excludes*
`meta` changes. So the promoted KB chip (186-08) would write `meta.project_folder_id`,

`hasEdited`. The leave guard would not arm. That is Pitfall 4, and F14 exists for it.

`saveState` slot earn its keep? This plan exercises that call and records the answer.

Output: a `setProjectFolder` action that writes and arms in one atomic act, a retired
`saveState`, and three docblocks that stop lying.

This plan touches no wire contract and runs in Wave 1 alongside 186-01.

<decisions_taken_here>
**`saveState` is RETIRED.** (Claude's discretion per CONTEXT.md; the evidence is in
`186-RESEARCH.md` §"The store's `saveState` slot".)

1. Zero production readers — the only call site of `setSaveState` in the whole repo is
   `builderStore.test.ts:339`.
2. The store's `SaveState` (`"idle" | "saving" | "saved" | "error"`) is strictly NARROWER
   than the enum the app actually renders, `ToolbarSaveState`
   (`CanvasToolbar.tsx:78`, which adds `"dirty"`). Two enums for one concept is the exact
   failure `SAVED_STILL_A_DRAFT`'s own docblock names.
3. Phase 186's persistence state is wider still — it must represent *held* (two reasons) and
   *conflict*. A flat four-value enum cannot; 186-06 uses a discriminated union.
4. The store carries a fence forbidding it from naming the API client (D-184-03: undo never
   writes to the server). Persistence state whose one writer is a network call does not
   belong in the undo store.

**`hasEdited` is flipped at the chip's call site, not by widening the subscription** — that
half is 186-08's, and its reasoning is recorded there.
</decisions_taken_here>
