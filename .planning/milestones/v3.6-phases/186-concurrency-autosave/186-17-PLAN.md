kept the `continue`. Under the flag, `pendingRef` was armed only where a MATURED timer met an

<decisions_this_plan_locks>
**1. WR-08 IS FIXED BY SPLITTING TWO QUESTIONS, NOT BY THROTTLING.** The drain currently asks one
question ("is this superseded?") and uses the answer for two purposes. Separate them:

  - *May a receipt be filed?* — decided by PAYLOAD IDENTITY ONLY. `pendingRef` is REMOVED from
    that test. This is CR-01's property stated correctly: a queue flag is not evidence that the
    payload moved, and treating it as such is what mints the redundant PATCH WR-08's second
    instance describes (pressing Save draft while a write is outstanding, with nothing changed).
  - *May the loop issue another request IMMEDIATELY?* — decided by `pendingRef.current` ONLY.
    That flag is armed in exactly three places, and all three mean the same thing: a MATURED timer
    (or `saveNow`, or the hold release) reached `performWrite` while a write was outstanding, so
    its beat was consumed and NO live timer is guaranteed to be behind it. That is precisely the
    case where an immediate follow-up is owed. Everything else — an edit that landed mid-flight
    and is still inside its own 1000 ms debounce — has a LIVE timer, because every edit changes
    `definition` and the debounce effect reschedules on it. Those `break`, and the ordinary
    autosave beat writes them.

  Rejected alternatives, with reasons:
  - *The review's `break` in all superseded cases plus a `dirty`-gated safety re-arm.* The re-arm
    would be a SECOND timer in a module whose stated rule is "one debounce rule, one timer, one
    writer" (D-186-01), and the case it exists for is exactly the case `pendingRef` already
    identifies. Splitting the question is the same protection with no new machinery.
  - *An `await delay(...)` inside the drain before `continue`.* It keeps `inFlightRef` true for
    the whole quiet period, so the Save-draft button (`disabled={saving}`) would be disabled
    almost continuously while an author types, and `Saving…` would be on screen when nothing is
    outstanding. A rate limit that lies about the state is not an improvement.

**2. A BREAK WITHOUT A RECEIPT MUST RESOLVE THE READING.** The superseded path sets
`{kind:"saving"}` at the top of the turn. If the drain then breaks, nothing is outstanding and
`Saving…` becomes a false claim — the same class as WR-09 below, and it would be introduced BY
this fix. The break therefore sets `{kind:"idle"}` first: nothing is claimed, `dirty` is still
true, and the leave guards and the toolbar are already keyed on `dirty`.

**3. WR-09 IS FIXED BY MOVING THE RESOLUTION ABOVE EVERY GATE, NOT BY PATCHING THE `!enabled`
BRANCH.** The review proposed clearing the state inside the `if (!enabled)` arm. Two of the other
three gates have the same hazard (`haltedRef`, and the nothing-pending test), so fixing one arm
would leave the property untrue in the other two. Instead, immediately after the non-null → null
transition test, resolve `{kind:"held"}` → `{kind:"idle"}` with a functional `setState` (a no-op
for every other reading, so a `conflict` / `error` / `saved` state is untouched). The gates below
then decide only whether to WRITE, which is all any of them was ever about.

**4. `heldPendingRef` ON THE FLAG-OFF PATH IS SET TO THE STORE'S `dirty`, NOT CLEARED AND NOT
LEFT.** 186-13 deliberately did NOT clear it, so work accumulated with the flag off would still be
found if the flag came on later; the review points out the other half — left armed, it can flush a
write on the strength of a flag set minutes earlier, bypassing the `dirty` gate the debounce timer
carries precisely to stop "merely opening a draft" from PATCHing it. Both concerns are satisfied
by making the flag AGREE with the truth: `heldPendingRef.current = store.getState().dirty`. It
claims unsent work exactly when there is unsent work.
</decisions_this_plan_locks>
