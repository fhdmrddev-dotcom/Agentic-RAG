`reload()` is the exit the banner recommends FIRST. Its `catch` replaces the conflict with a
generic `error`, and the banner renders on `state.kind === "conflict" || resolving`, so on a
failed exit BOTH controls leave the DOM in the same commit that `haltedRef` becomes permanent.

`isTerminalRefusal` names only `WorkflowNotFoundError`, so every subsequent edit re-issues a
doomed PATCH for the life of the session.

<decisions_this_plan_locks>
Three calls decided here so the executor does not re-litigate them.

**1. A failed exit RESTORES the conflict; it does not invent a new state.** The catch sets
`{ kind: "conflict", currentToken: conflictTokenRef.current, note: RELOAD_FAILED_NOTE }` — the
same shape the refusal produced — and it does so ONLY while `haltedRef.current` is still true.
Rejected: (a) leaving `{kind:"error"}` and instead widening the banner's render condition to
include `error` — that would put Reload/Overwrite on screen for a 422 and a dead network too,
where neither exit means anything; (b) clearing `haltedRef` in the catch so the loop resumes —
the row genuinely moved and resuming would be the silent clobber this phase exists to prevent.
The guard on `haltedRef` matters: a `reload()` that failed while the loop was NOT halted must
keep the cause-neutral line, because claiming a conflict that did not happen is the same class of
lie in the other direction.

**2. The banner gains an EXTRA line, never a replacement (the review's own instruction).** A new
exported constant `RELOAD_FAILED_NOTE` states that the reload could not reach the server, that
nothing has changed, and that both ways out are still available. It renders inside the banner
below the locked `CONFLICT_BANNER_MESSAGE`, and both buttons stay mounted and enabled. Rejected:
putting it in the `builder-save-error` alert span — that span is for a refused WRITE, and this is
a failed READ during a resolution; two situations in one element is how a sentence stops meaning
one thing.

**3. WR-07's halt does NOT need a new "re-state the sentence" mechanism.** After a terminal
refusal `state` stays `{kind:"error", sentence: PUBLISHED_CONFLICT_MESSAGE}` for the rest of the
session — nothing overwrites it — so the sentence naming the way out (Tweak) is permanently on
screen beside the button. Pressing Save therefore does not produce a SILENT no-op: the answer is
already rendered and stays rendered. That is the material difference from GAP-4, where the
sentence was `SAVE_FAILED_SENTENCE` (a retry invitation) and the exits had vanished. Do not add a
`haltedStateRef` or any re-assertion machinery; add the predicate and the tests only.
</decisions_this_plan_locks>
