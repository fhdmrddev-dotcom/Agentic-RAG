<objective>
Close WR-10: nothing on the client refuses a gauntlet while an autosave write is outstanding.

D-186-12's hold stops NEW writes once `publishInFlight` is true, but it cannot recall one that is
already in flight. `runGauntlet` issues `publishWorkflow` immediately; the service reads
`stage0_token` and spends it minutes later at the stage-5 flip. A PATCH that commits AFTER stage
0's read makes that token dead on arrival, the flip returns `-2` → `draft_changed`, and a real
golden run has already burned wall clock and provider spend on a publish that could never have
succeeded. The author then sees a `draft_changed` refusal for an edit they made BEFORE pressing
Publish.

The trigger is gated only by `blockedReason` (the validation verdict), and the INNER Publish
button inside the modal is gated only on `goldenInput.trim().length > 0 && !loading` — so the
modal can sit open for as long as the author takes to write a golden input, and the click is
never checked against the write loop at all.

Purpose: a wasted golden run costs minutes and real money, and the refusal it produces is
confusing rather than informative. The Builder already publishes the one fact that closes the
window (`state.kind === "saving"`) and already threads a `blockedReason` into the gauntlet, so
the seam exists — it is simply not connected.

Output: a publish that will not start on top of an outstanding write, and says so on both the
trigger and inside the modal.
</objective>

<decisions_this_plan_locks>
**1. THE GATE RIDES THE EXISTING `blockedReason` SEAM. The `flushPendingWrites()` alternative is
REJECTED, and not for cost.** The review preferred having `runGauntlet` await a flush the hook
exposes, so stage 0 provably reads a current token. Two reasons that is the wrong build here:

  - *It would be an automatic write past the revert switch.* `renderPublish` — and therefore
    `PublishGauntlet` — is mounted UNCONDITIONALLY on the Builder header, on both branches of the
    flag gate (`WorkflowBuilderPage.tsx:1722` and `:1727`). A flush called from `runGauntlet`
    would therefore issue an unrequested PATCH on the flag-off surface, which is exactly the leak
    186-13 closed for the hold release and exactly what D-181-01 — this milestone's HARD gate #1 —
    exists to make impossible. It would have to be re-gated on `enabled`, at which point it is a
    conditional flush wearing a guarantee's clothes.
  - *It would need a five-hop seam.* `WorkflowBuilderPage` → `WorkflowDoorSwitch` →
    `WorkflowsPage` → `PublishGauntlet`, three of them pure pass-throughs, for a promise the
    existing seam can already carry as a fact.

  The refusal is also the vocabulary this phase already speaks everywhere else: hold, and say
  why (D-186-04 / D-186-12). Waiting one round trip and pressing again is a smaller cost to the
  person than an unrequested write is to the flag-off guarantee.

**2. THE GATE IS SOUND, NOT MERELY NARROW — say why in the code.** `performWrite` sets
`{kind:"saving"}` SYNCHRONOUSLY before the request leaves, and every automatic trigger runs from
a timer callback or an effect — a separate task from any subsequent click. So by the time a click
event is dispatched, React has already rendered the `saving` reading and `blockedReason` is
non-null. This is a real ordering property, not a hope, and it is why the fix does not need a
promise. Write that paragraph into the memo's docblock so the next reader can re-derive it.

**3. THE INNER BUTTON GETS THE REASON, NOT JUST THE DISABLE.** R12's shipped rule
(`PublishGauntlet.blockedReason`'s own docblock) is that greying alone is never enough — the
reason is rendered visibly and tied with `aria-describedby`. The trigger already does this; the
inner button is behind the modal where the trigger's reason cannot be seen, so it needs its own.

**4. WHAT THIS PLAN DOES NOT CLOSE, recorded rather than left.** A publish attempted while the
loop is in `conflict` (the server holds a different definition than the screen) or `error` is
NOT blocked here. It is arguably worse than the `saving` case, but it is a different finding, it
is not in this gap-closure round's operator-approved scope, and blocking it changes what an
author can do with a draft that has a stale sibling tab. It goes into `deferred-items.md` with a
concrete re-open trigger.
</decisions_this_plan_locks>
