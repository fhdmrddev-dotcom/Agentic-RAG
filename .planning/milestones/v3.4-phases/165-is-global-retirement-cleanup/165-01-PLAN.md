<postgres_propagation_fact>
LOAD-BEARING mechanism (why this migration is short + transcription-risk-free): PostgreSQL `ALTER TABLE … RENAME COLUMN` stores column references in RLS policies, CHECK constraints, and indexes as parsed node-trees keyed on attribute-number, so a rename AUTO-PROPAGATES to every policy USING/WITH-CHECK, the `mfd_reachable` CHECK, and all indexes with the correct new per-table name (`is_system_global` on the four write-locked tables' `is_global=true`/`is_global=false` branches; `is_org_shared` on folders/skills). Do NOT hand-re-CREATE the mig-108/109 RLS policies — that risks a transcription error that OVER-WIDENS the universal branch (the exact high-severity cross-org-leak threat T-165-01). Auto-propagation preserves mig-109 semantics VERBATIM. What does NOT auto-propagate: FUNCTION bodies (`pg_proc.prosrc` is TEXT, parsed at runtime) — trigger + DEFINER function bodies referencing `is_global` by name must be explicitly `CREATE OR REPLACE`d, and the storage-policy reconciliation is a real semantic change requiring explicit DROP+CREATE.
</postgres_propagation_fact>
