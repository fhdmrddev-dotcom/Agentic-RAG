> This is a **ratify-not-relitigate** ADR. It does not re-open the tenancy posture. It records that the posture is settled, binds the naming/renumbering decisions the downstream schema/RLS phases depend on, and pins the one genuinely-new commitment: the 4-tier deployment-flexibility contract. **No code**, no schema, no migration, and no test ship in this phase — it is a decision document.

## Context

D-PRD-02 (Hybrid SaaS posture: co-tenant SMB/mid + dedicated/on-prem large enterprise) was **ACCEPTED 2026-05-10** and is confirmed unchanged for v3.4 (D-04 — clean ratify, no changes). Nothing about the posture is being re-argued here.

One thing a reader must not be thrown by: **the version slot moved, the posture did not.** Multi-tenancy was re-slotted twice after D-PRD-02 was accepted — originally slotted **v3.2** (at 2026-05-10 acceptance), re-sequenced to **v3.3** on 2026-06-15, then to **v3.4** on 2026-06-21 (when Skill Studio split into v3.1+v3.2 and the GTM track shifted down one more slot; per `.planning/PRDs/SEQUENCE.md`). D-PRD-02's own "Consequences" section still names the ORIGINAL slots (it references v3.1/v3.2/v3.3) because it was written at acceptance and is deliberately not relitigated. Read those as historical slot labels — the multi-tenancy work is v3.4 (CORE phases 160-168, STRETCH phases 169-173). The posture is identical; only the calendar slot shifted.

Why ratify now: v3.4 is the load-bearing one-way RLS door. Every downstream phase (161-168) needs a settled foundation — the org/dept/role schema, the personal-org backfill, and the atomic RLS + user-JWT-client crux all encode assumptions about the tenancy model. Locking those assumptions in one place, once, is cheaper and safer than re-deciding them per phase.

## Decision — Ratified Tenancy Posture (SC#1)

We ratify **D-PRD-02** exactly as accepted:

- **Default = co-tenant.** A single Agentic RAG deployment serves multiple paying customer orgs on shared infrastructure, isolated by an `org_id` discriminator + membership-based RLS. This is the SMB/mid tier.
- **Enterprise = isolation-via-deployment.** Large-enterprise / regulated / data-residency customers get a dedicated single-org install (or on-prem) — a separate deployment on a customer-owned Supabase, not a second code path.
- **One codebase, one recipe matrix.** The co-tenant vs isolated difference is *configuration* (org-discriminator on/off, secrets store, identity-provider binding), never a fork. The same image serves both modes; a deploy chooses which one by environment.

A reader can see this is settled, not re-opened: it restates an ACCEPTED decision, cites the ~80% already shipped (below), and carries no open questions.

## Binding Naming & Renumbering Locks (phases 161-168) (SC#2)

The following are **binding for phases 161-168** — recorded here so the schema/migration phases never re-decide them:

1. **`skills.is_system` -> `is_system_global` reuse.** The existing write-locked `is_system` marker is reused as the cross-org visibility allow-list under the name `is_system_global`. Cross-org visibility stays migration-only (the seeded `skill-creator` is the only legitimate cross-org row); no user-facing write path may set `is_system_global`.
2. **`is_global` -> `is_org_shared` value-preserving RENAME.** The `is_global` flag becomes `is_org_shared` via a SQL `RENAME` (never drop+add — the column keeps its data). "Global" meant "visible to everyone" in the single-tenant world; "org-shared" is its correct meaning once orgs exist. This is a value-preserving rename of `is_global`, not a semantic reset.
3. **Migrations continue at slot 104+.** v3.4 migrations start at the next free numbered slot (**104**) and count up, per the repo's `<digits>_name.sql` convention (no letter suffixes — the Supabase CLI silently skips `007b`-style names).

These are stated as binding-for-161-168, not re-opened. A downstream planner cites this section rather than re-deriving the names.

## Ratify-Not-Relitigate Scope (SC#3)

This phase makes **no code** changes — it is a document. Ratification (not fresh design) is the correct move because v3.3 already shipped ~**80%** of the posture as additive stubs and presets:

- **`org_id` stubs** (migrations 095/096, live) — nullable `org_id` on the 4 owned roots + an org-agnostic `operator_users` table. The additive foundation that phase 161 extends.
- **Solo/Team/Enterprise deploy presets** (Phase 157 — `deploy/onebox.env.example`, `docker-compose.prod.yml`, `OPERATOR.md`) — make co-tenant-vs-isolated a deploy-time env choice *today*.
- **Encrypted-secrets substrate** (Phase 150, SEC-01) — the app-layer MultiFernet `enc:v1:` envelope + the DB>env `_val` precedence chain, reused (no new crypto) by the forward-compat contract below.

Because ~80% is already decided and shipped, re-litigating would be waste. The ADR records the scope and moves on. No code, no schema, no migration this phase.

## 4-Tier Deployment-Flexibility Contract (BINDING · NON-NEGOTIABLE) (SC#4 / D-01)

This is the one genuinely-new binding commitment of the phase. It has two halves; **both are binding**.

**Half 1 — the four tiers stay a `pure env-var` switch.** All four named tiers are one deployment recipe selected by environment, never a code fork:

1. **solo-local** — one user, local Docker, everything on localhost.
2. **small-team-VPS** — a handful of users on a single small VPS.
3. **medium-SaaS** — co-tenant; many orgs share one deployment, isolated by `org_id` + membership RLS.
4. **enterprise** / on-prem / BYO — isolation-via-deployment on a **customer-owned Supabase** (a dedicated single-org install).

Binding rules across all four tiers:

- The tier is a **`pure env-var`** switch — with **`no hardcoded`** URLs / keys / models / ports anywhere.
- The **local setup never breaks** — local vs cloud is a pure env-var difference, nothing more.
- The co-tenant vs isolated choice is a **deploy-time decision, never a code fork**.

**Half 2 — the forward-compat substrate (SEED-120).** The org-settings + encrypted-secrets substrate must stay forward-compatible with the three SEED-120 capabilities so that v3.5 can add them with **no schema rewrite**:

- per-org provider config,
- bring-your-own (BYO) API keys,
- per-org (including local) model selection.

This reuses the v3.3 SEC-01 `enc:v1:` MultiFernet envelope + the DB>env `_val` precedence chain (org-scoped settings as an `app_settings` analog). No new crypto — the guarantee is credible precisely because the substrate already exists and is proven.

**Per-phase enforcement clause (binding).** Every subsequent v3.4 phase (**161-173**) is verified against this contract — nothing a phase ships may make any deployment tier harder. This is a per-phase verification obligation, echoed into each phase's success criteria / verification, not a one-time milestone-exit check.

**Red-line consistency (D-14).** The contract must not imply any shared-path fork: Deep Mode stays byte-identical, provider/tier differences live at the gateway/adapter boundary, and no new runtime is introduced. Deployment flexibility is achieved by configuration + adapters, never by branching the shared path.

## Consequences + Reversal (D-03)

The one-way-door cost is small and known: **co-tenant -> isolated** is a redeploy on a **customer-owned Supabase** — a deploy-time switch, not a code fork. The expensive and unlikely direction is isolated -> co-tenant (re-tenanting separate deployments back into a shared one), which we do not commit to supporting. The named escape valve: a **paying customer** forcing isolation / integrations-first is the concrete trigger that would re-order priorities (consistent with the post-v3.4 sequencing note in `.planning/PRDs/SEQUENCE.md`). This is a short consequences note, not a re-argument of the decision.
