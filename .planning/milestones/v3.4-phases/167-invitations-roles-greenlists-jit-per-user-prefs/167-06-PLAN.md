## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| invite link → /invite page | The raw token in the URL is the only capability; the client passes it to the server accept, which validates + gates it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-167-20 | Spoofing | join without a valid invite | mitigate | Accept requires the token (server-validated pending+non-expired match, Plan 02); email-match alone never joins. The client only carries the token to the server. |
| T-167-21 | Tampering | double-accept from a re-render / confirm round-trip | mitigate | The accept is idempotent + re-runnable (Plan 02 advisory-lock + ON CONFLICT); the page guards it to fire once per authed session. |
| T-167-22 | Information Disclosure | token lingering in client storage/logs | accept | The token lives only in the URL + transient component/sessionStorage state for the accept round-trip; it is a single-use capability consumed server-side on accept. Low residual risk (client is not the boundary). |
| T-167-SC | Tampering | npm installs | mitigate | No new package — clones AuthPage + the shipped auth forms; no url router added (window.location precedent). |
</threat_model>
