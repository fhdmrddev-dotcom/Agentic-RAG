<objective>
Implement stateful and incremental workflow execution (STATE-01, STATE-02) so that recurring and manual workflow runs can read their own previous completed deliverable output across published versions, maintain living registers, and format state deltas without starting from zero on each run.
</objective>

<threat_model>
- T-205-01 (Cross-Tenant State Leakage): Because `db/workflows.py` queries via the service-role pool, failing to filter by `wr.user_id = $2 AND ($3::uuid IS NULL OR wr.org_id = $3)` on the prior run query would allow a workflow to read deliverables belonging to another tenant. Mitigation: Direct `wr.user_id` / `org_id` predicate on `workflow_runs` (no `threads` join).
- T-205-02 (JSONB String-Scalar Trap & Silent Dead Feature): Measured on live DB: 87% (532/610) of `workflow_phases.output` rows are stored as string scalars (`typeof: string`). Naive `output->>'text'` returns NULL and mimics a false cold start, silently killing the feature. Mitigation: Robust JSON deserialization unwrap (`isinstance(raw, str)` -> `json.loads`) at read time, and explicit distinction/logging between genuine cold start (`None`) and decode failures.
- T-205-03 (State Corruption from Interrupted Runs): If the query selects the latest run regardless of status, a `failed` or `cancelled` run with partial outputs would overwrite the legitimate baseline. Mitigation: Strict `status = 'completed'` predicate.
- T-205-04 (Deliverable Ambiguity & Machine Question Injection): If prior run resolution picks the literal last phase row, a closing file step (empty text) produces empty state, or a closing `confirm` step feeds the machine's own question ("Does this draft answer your question?") into the next run's baseline. Mitigation: Apply Phase 200.2's shipped rule — select the last server-ordered row with a non-empty `deliverable_text`, skipping question/confirm and file steps.
</threat_model>
