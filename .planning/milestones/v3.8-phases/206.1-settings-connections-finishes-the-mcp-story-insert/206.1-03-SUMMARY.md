# Phase 206.1 Plan 03: the MCP creation door — Summary

`Add a connection` now offers a fourth shape, gives it exactly three fields, composes a body the API
accepts on the first try, and — the defect research found while measuring it — renders the MCP shape
when you re-open an existing MCP row instead of showing you the SMTP form. **All of that is built,
tested and driven in a real browser.**

---

## ⛔ SC#1b IS NOT MET — READ THIS BEFORE ANYTHING ELSE

> **An MCP connection created by this plan CANNOT BE BOUND TO ANY WORKFLOW STEP IN THE SHIPPED
> PRODUCT.** This is the ROADMAP's first named failure mode for SC#1 verbatim — *"the form accepts an
> MCP connection but the row it creates is one the picker cannot bind"* — and Task 3's own rule says a
> failing measurement **escalates and stops**, so it is recorded as a failure and not as a note.

⚠ **THE CAUSE IS NOT IN THIS PLAN'S OUTPUT.** The row this plan creates is correct at every layer that
was measured: the API accepts it (201), returns `capability: null` and the right `mcp_server_url`, and
**`POST /connectors/connections/{id}/discover` on that row returns 3 tools**. What fails is the
BUILDER seam that D-206.1-18 assumed was already complete.

**Measured at the source, then confirmed over the wire with the org admin's own JWT:**

| Layer | Reading |
|---|---|
| `GET /connectors/connections` (no filter) | `200` · **3 rows · the MCP row PRESENT** |
| `GET ...?capability=send_email` | `200` · 0 rows · MCP absent |
| `GET ...?capability=create_ticket` | `200` · 1 row (`Jira – KAN`) · MCP absent |
| `GET ...?capability=post_message` | `200` · 1 row (`Slack-rag-test`) · MCP absent |
| `POST /connectors/connections/{id}/discover` | **`200` · 3 tools** — `ask_question`, `read_wiki_contents`, `read_wiki_structure` |

- `ConnectionPicker.tsx:271` calls `listConnectorConnections(capability)`, which always sends
  `?capability=…`. An MCP row has `capability = null`, so **it is filtered out of every read the
  picker ever performs.**
- `ExternalActionSection` offers exactly the three members of `EXTERNAL_ACTION_CAPABILITIES` — a closed
  client mirror of `ExternalActionPhaseConfig.capability`. **There is no MCP option for an
  `external_action` step.**
- `McpToolPicker` mounts only when `bound?.mcp_server_url` is set, and `bound` can only ever be a
  capability row. ⇒ **`mcp-discover-btn` has no reachable mount in the shipped product.**
- Driven in the builder: inserting an `external_action` step and opening its rail renders
  `connection-picker-empty` — *"No email connection yet — add one in Settings → Connections."*

⚠ **AND `updateConnectorGrants` HAS NO UI CALLER ANYWHERE.** `grep -rn "updateConnectorGrants" frontend/src`
outside `api.ts` returns **nothing**. `McpToolPicker` *displays* a granted/denied badge; there is no
control that flips a grant. So step 6 of Task 3 has no UI to drive either.

⚠ **THE BACKEND IS READY AND THAT IS WHAT MAKES THIS A FRONT-END GAP.**
`backend/app/models/harness.py:260` says in its own comment: *"an MCP step names a `tool_name` and has
no capability at all, which is a legitimate absence"* — `capability` is `| None`, and `connection_id` /
`tool_name` are declared. The wire contract supports the MCP shape; the authoring surface cannot
express it.

**This is the Phase-118 built-but-unreachable shape, one layer below where this phase looked.** Phase
206 shipped the client, the SSRF defense, discovery, grants, dispatch and audit; 206.1 was scoped to
add *the missing door onto the connection*. It turns out **a second door is missing too** — the one
between a connection and a step.
