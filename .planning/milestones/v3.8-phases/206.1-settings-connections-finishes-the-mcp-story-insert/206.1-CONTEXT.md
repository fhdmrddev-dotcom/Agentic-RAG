<domain>
## Phase Boundary

Phase 206 shipped a complete, working MCP connector path — client, SSRF defense, discovery,
per-tool grants, executor dispatch, audit — and **shipped no door onto it**. Live UAT on
2026-08-25 found that, and found two defects on the same surface while looking.

This phase closes all three, entirely in `frontend/src/components/settings/`.

### In Scope

1. **The creation door (NEW CAPABILITY).** `Add a connection` gains an MCP shape: a name, an
   HTTPS server URL, an optional credential. The backend already accepts this exact body —
   `ConnectorConnectionCreate` has carried `mcp_server_url` and a `capability`-less branch since
   `147f3c57`, and `frontend/src/lib/api.ts`'s `ConnectorConnectionCreate` already declares
   `capability?: ... | null` and `mcp_server_url?: string | null`. **The form is the only missing
   piece.**
2. **The row collapses when the panel opens (DEFECT).** A dense row SHAPE for the narrow column.
3. **Invented marks where real logos exist (DEFECT).** One shared per-service logo map, plus an
   honest mark for MCP, which has no capability at all.

### Explicitly Out of Scope

- **Any change to `frontend/src/lib/api.ts`.** Phase 207 exists *because* Phase 206 added two
  runtime exports there and the ledger trigger fired. The types this phase needs are already
  present; adding one more export here would re-fire a trigger that may not be re-declined.
- Backend changes of any kind. The API already accepts and returns the MCP shape.
- Migration changes. 126 is applied locally and regenerated.
- The Connections & Open Platform milestone's scope (OAuth, catalog, org sharing) — SEED-146.
- `McpToolPicker.tsx` / `ConnectionPicker.tsx` (the builder seam). Shipped and working in 206;
  this phase reads them for the shape of the mark, and does not edit them unless the shared
  logo map's adoption there is proven free (see D-206.1-08).

<decisions>
## Implementation Decisions

### Phase shape

- **D-206.1-01 (Three separable plans, not one)**: The ROADMAP requires the three items stay
  separable — *"one is a new capability and two are defects on shipped code — a closure round may
  not smuggle in a feature (G-7), and the reverse holds too, so the form must not be the reason
  the two defects go unreviewed."* Each item is therefore its own PLAN.md with its own
  `must_haves`, so one can be reverted without the others. They share a phase because G-1 caps
  repeated inserts on one hot file, not because they share a commit.
- **D-206.1-02 (Frontend-only, and `api.ts` is untouched)**: No backend file, no migration, and
  no edit to `frontend/src/lib/api.ts`. If a plan believes it needs a new `api.ts` export, that is
  a signal it has mis-read the shipped types — re-read `api.ts:6385-6426` before deviating.

### Item 1 — the MCP creation door

- **D-206.1-03 (A fourth chooser option, not a second form)**: `ConnectionFormPanel.tsx`'s
  capability chooser gains an **MCP server** option alongside the three capabilities. It is the
  same panel, the same Save, the same refusal vocabulary — the per-shape field block is what
  switches, exactly as `send_email` / `create_ticket` / `post_message` already do at
  `ConnectionFormPanel.tsx:899-993`. A second panel would fork the write path and the refusal copy.
- **D-206.1-04 (The MCP body omits `capability` and sends `config: { headers: {} }`)**: The wire
  body is `{ name, mcp_server_url, config: { headers: {} }, secret? }` with **`capability` absent
  or `null`**. Measured at the model: `ConnectorConnectionCreate._validate_connection_shape`
  branches on `mcp_server_url` FIRST and returns before the capability arm; `config` defaults to
  `McpConfig` and `McpConfig` is `extra="forbid"` with exactly one field, `headers`. Sending a
  capability alongside a URL, or a `SendEmailConfig`-shaped config, is a 422.
- **D-206.1-05 (HTTPS is refused in the panel AND at the model, and the panel is not the gate)**:
  `mcp_server_url` must start with `https://` — the model raises otherwise, and
  `validate_mcp_destination` refuses again at call time. The panel mirrors this with a disabled
  Save (*"a disabled Save is kinder than a 422"* — `models/connector.py`'s own WR-05 note), but
  the panel's check is a courtesy, never the security boundary, and the plan must say so where it
  is written.
- **D-206.1-06 (The credential is OPTIONAL for the MCP shape, and only for it)**: A capability
  connection still requires a secret (WR-05). An MCP server may be unauthenticated —
  `resolve_connection` was relaxed for the MCP shape ONLY in `147f3c57`. The panel must not
  require one, and must not present the absence as an error state.
- **D-206.1-07 (The row it creates must be one the picker can bind)**: The ROADMAP's first failure
  mode. Acceptance is not *"the POST returns 201"* — it is the driven round trip: create in the
  UI → discover → grant → a workflow step calls a granted tool. **No direct database insert
  anywhere in the evidence.**

### Item 3 — logos

- **D-206.1-08 (ONE shared map, and the shipped "never vendor logos" rule is SUPERSEDED, not
  ignored)**: `ConnectionsTab.tsx`'s header currently reads *"CAPABILITY MARKS, NEVER VENDOR LOGOS
  (§10 / U-12)"* and `CAPABILITY_MARKS` maps to generic fluent-emoji glyphs. The operator's icon
  convention (`references/icon-convention.md` §1, Running Design Decision 43, 2026-06-27) says a
  service shows its OWN mark, from one source, byte-identical everywhere — and the ROADMAP's SC#3
  makes that binding for this surface. **The old docblock is corrected AT SOURCE, beside the
  original, never deleted** (this project's standing correction rule). A reader who finds the old
  sentence and no correction will re-apply it.
- **D-206.1-09 (The dependency decision is TAKEN, not assumed away)**: Measured at HEAD —
  `@lobehub/icons@^5.10.0` is AI-provider-shaped and ships **no Slack and no Jira/Atlassian**; the
  only installed Iconify collection is `@iconify-json/fluent-emoji@^1.2.7`. `unplugin-icons` is
  wired in BOTH `vite.config.ts` and `vitest.config.ts`, so a `~icons/<set>/<slug>` import resolves
  in tests as well as in the build. The phase adds `@iconify-json/logos` (registry-verified
  present, `1.2.13`) as a devDependency, **or** bundles the SVGs — the plan states which and why.
- **D-206.1-10 (Every slug is VERIFIED to resolve, and the fallback is not blank)**: icon-convention
  §3's measured trap — `fluent-emoji:direct-hit` shipped BLANK in Phase 127. Every slug this phase
  introduces is verified against the installed package (an assertion over the collection's own JSON,
  the way `ConnectionsTab.tsx:36-41` records for its three fluent-emoji slugs), not against any
  document. The unknown-service fallback renders a **named neutral mark** — never nothing, and
  never another service's mark.
- **D-206.1-11 (The mark lookup is EXPLICIT per arm — no positional fallback)**: This is the exact
  defect `destinationFactsOf` shipped, where a trailing `return` made every MCP connection claim it
  sends to `slack.com/api` (fixed in `147f3c57`). The mark map is a total, own-property lookup with
  a named default; an MCP row resolves its own mark by its own condition (`mcp_server_url` present),
  never by falling off the end of a capability ladder.

### Item 2 — the dense row

- **D-206.1-12 (A `dense` prop threaded from the panel condition — NOT a container query)**: The
  ROADMAP offers both. Container queries are refused for two measured reasons: Tailwind is
  `^3.4.19` with **no `@tailwindcss/container-queries` plugin installed** (a second new dependency),
  and **jsdom evaluates no layout at all**, so a container-query-driven shape would be untestable in
  the suite that has to pin it. The `dense` flag is threaded from the *same*
  `panel && !isMobile` expression that opens the 400px track at `ConnectionsTab.tsx:274` — one
  condition, one home, two consequences.
- **D-206.1-13 (The dense shape REFLOWS; deleting a column is the named failure)**: *"the
  destination is the one column a person reads to approve a send, and hiding it is worse than
  truncating it."* All five columns (`Connection`, `Sends to`, `Used by`, `Credential`, `State`)
  and the ⋯ action are present in BOTH shapes — asserted by a test that queries every row testid in
  both renders, not by inspection.
- **D-206.1-14 (SC#2's geometry proof CANNOT come from vitest, and the plan must not pretend it
  can)**: jsdom reports `scrollWidth` and `clientWidth` as `0` for every element, so
  `scrollWidth <= clientWidth` is vacuously true there and proves nothing. The proof is split and
  both halves are required: **(a)** vitest pins the SHAPE — both variants render, both carry every
  column, `data-dense` reflects the flag; **(b)** a real browser measures the geometry at **1280px
  and 1536px with the panel open**, via Chrome DevTools MCP `evaluate_script` reading
  `scrollWidth`/`clientWidth` off the destination cells. A plan whose only SC#2 evidence is a green
  vitest run has not met SC#2.

### Verification & baselines

- **D-206.1-15 (Baselines are re-derived, never quoted)**: The last commit recorded *backend 68 ·
  tsc 34 · count gate 5467/0/110*. Those are that commit's readings; this phase re-derives all
  three at its own base and compares against its own reading. The count gate's contract is **no
  per-file DECREASE and zero failing**, never a fixed grand total.
- **D-206.1-16 (`tsc` is project-scoped or it measures nothing)**: `npx tsc --noEmit` checks ZERO
  files in this repo — the recorded `WorkflowBuilderPage.tsx` lesson, where the only defect v3.7
  shipped was invisible to every behavioural test and visible to the typecheck the audit did not
  run. Use `-p tsconfig.app.json`.
- **D-206.1-17 (`GSD_VITEST_MAX_WORKERS=2`, and a red gate is triaged before it is re-run)**:
  Capture failing filenames from the gate's own persisted JSON BEFORE re-running anything, check
  each against `git diff --numstat`, and only then decide flake vs. real (SEED-171; and `196-08`,
  where 249 failures were all real).

### Answered by research, 2026-08-25 — three open questions and two corrections

- **D-206.1-18 (Discover and Grant keep their existing home at the BUILDER seam — Settings gains
  neither)**: Measured — `McpToolPicker.tsx` already ships a real `Discover Tools` button
  (`data-testid="mcp-discover-btn"`, calling `discoverConnectorTools`) and the per-tool grant
  controls, mounted through `ConnectionPicker.tsx` inside the workflow builder. **SC#1's round trip
  is therefore fully UI-drivable today** once the create door exists: create in Settings → open a
  workflow's external-action step → pick the connection → Discover Tools → grant → run. Adding a
  second Discover door in Settings would be a NEW CAPABILITY inside a phase that already carries
  one, which G-7's spirit forbids. **Re-open trigger:** *the first time a person needs to inspect or
  revoke a grant without opening a workflow.*
- **D-206.1-19 (An MCP row does NOT offer `Check credential`, and the affordance is REMOVED, not
  disabled)**: The check path is capability-shaped (SMTP login / Jira auth / Slack `auth.test`) and
  has no MCP arm. This surface's shipped rule is *removed rather than disabled* — a rendered control
  the API refuses is the defect that rule exists to prevent. The reason is stated in the source where
  the arm is removed, not left to be rediscovered.
- **D-206.1-20 (The dense shape drops the COLUMN HEADER, never a cell)**: `CONNECTIONS_COLUMNS` is a
  character-identity pin and stays exported and rendered by the wide shape. In the dense shape the
  cells no longer form five aligned columns, so a five-word header would label a grid that is not
  there; it is not rendered. Every dense cell whose meaning is not self-evident (`Used by`,
  `Credential`) carries its own short inline label or accessible name, so no value loses its
  heading. D-206.1-13's *"reflows, never deletes"* is about CELLS — it is not weakened here.

- **D-206.1-21 (⚠ SC#2's PREMISE IS PARTLY FALSIFIED BY MEASUREMENT, and the correction is recorded
  rather than worked around)**: SC#2 asks for proof *"at 1280px and 1536px"*, which presumes the two
  viewports differ. Measured: `SettingsPage.tsx:861` caps this whole surface at `max-w-3xl` = 768px,
  so the list track is **718px closed and 302px open at BOTH viewports** — 1280 and 1536 produce
  identical geometry. Both are still driven and reported (the criterion is met as written, and a
  future change to that cap is exactly what the second reading would catch), but the plan must say
  in writing that they are expected to agree, so an identical pair reads as CONFIRMATION rather than
  as a copy-paste error. ⚠ **Second, decisive correction:** the destination cell is `truncate`
  (`white-space: nowrap`), so **`scrollWidth <= clientWidth` is unsatisfiable by widening alone** —
  the dense shape must let the destination **WRAP**. A dense layout that only gives the cell more
  room will still fail SC#2, and will fail it silently.
- **D-206.1-22 (The edit path is part of item 1 — a live defect found during research)**: Opening an
  existing MCP row's name renders the **SMTP form**: both `ConnectionFormPanel.tsx:714` and
  `draftFromConnection` fall back to `"send_email"` when `connection.capability` is null. Item 1 is
  not done when create works; the panel must render the MCP shape in `mode === "edit"` too, and the
  regression is pinned.
- **D-206.1-23 (A missing slug is a BUILD ERROR, not a blank render — icon-convention §3's mechanism
  is corrected beside its original)**: Driven under this repo's vitest — a non-existent
  `~icons/<set>/<slug>` import is a transform-time hard error (the suite loads zero tests), and an
  uninstalled collection behaves the same. So *"verify the slug resolves"* needs no build assertion
  here: **the import IS the fence.** What still needs a test is *resolved-but-EMPTY*, which
  `innerHTML.length > 0` per mark covers. ⚠ The bare `logos:slack` and `logos:model-context-protocol`
  are **wordmarks** (512×130, 512×69) and unusable at 16px — the square marks are
  `logos:slack-icon`, `logos:jira` (there is **no** `logos:jira-icon`) and
  `logos:model-context-protocol-icon`. **`logos` carries NO SMTP/email mark at all** — SMTP is
  vendorless, so its mark stays honest and neutral rather than borrowing a vendor's (Gmail's is the
  tempting wrong answer, and it is the `destinationFactsOf` defect in a different column).
- **D-206.1-24 (All four settings files owe a hot-file-ledger row IN THIS PHASE'S OWN COMMIT)**:
  Measured — `ConnectionsTab.tsx` `5/2/991`, `ConnectionFormPanel.tsx` `3/2/1584`,
  `connectionsCopy.ts` `2/2/477`, `connectionFormCopy.ts` `2/2/531`; **all four are absent from
  CLAUDE.md's table AND from `docs/HOT-FILE-LEDGER.md`**, and all four cross the G-5 threshold in
  this phase's own commit. `ConnectionsTab.tsx` is currently named inside another file's section
  with no row of its own — the exact drift the same-commit sync rule forbids. Rows + sections land
  together, with a named seam each.
