## Framing before the scorecard

This report is **goal-backward against two different, correctly-separated questions**, per the
phase's own ROADMAP wording and the executor's own escalation. They have different answers and
both are given rather than averaged into one number:

1. **The phase GOAL, on its own wording** ("create, see and understand an MCP connection entirely
   in the UI") — **MET.** A person can add an MCP connection via `Add a connection`, watch it
   appear in the list with its own real logo, read its destination without truncation whether the
   detail panel is open or closed, and re-open it for edit without hitting the SMTP form. All of
   that was independently re-derived below, not merely quoted from SUMMARY.md.

2. **SC#1's stronger, explicit wording** ("the round trip is driven: create → discover → grant →
   a workflow step calls a granted tool") — **NOT MET.** The row created is correct at every layer
   measured (201, `capability: null`, discover returns 3 tools over the wire) but **the authoring
   surface has no door to bind that row to a workflow step at all.** This is the ROADMAP's own
   first named failure mode, verbatim, and it is real — independently confirmed by direct code
   reading below, not merely by trusting the executor's account.

Per the task's own guidance, **this is not a gap-closure-round candidate.** Building the missing
authoring door is a NEW CAPABILITY (G-7 forbids introducing one inside a closure round), and the
phase's own three plans already correctly kept the three ROADMAP items separable — SC#1's failure
does not implicate SC#2, SC#3, SC#4 or SC#5, all of which are independently verified MET below.

## Recommendation for the operator

Per the task's explicit instruction, **do not route this to a gap-closure round.** G-7 forbids a
closure round from introducing a new user-facing capability, and binding an MCP connection to a
workflow step is exactly that — a new authoring door (a 4th `ExternalActionSection` option, an
unfiltered-or-MCP-aware `ConnectionPicker` read path, and a grant control for
`updateConnectorGrants`), not a fix to something 206.1 broke.

Three options were named by the executor and are re-affirmed here, independently verified as
accurate framings of the actual gap:

- **(A) Follow-on phase for the builder seam — recommended.** `SEED-200-mcp-connection-cannot-be-bound-to-any-step.md` already exists as the planted finding; this is the correct next phase to schedule, sized as new capability rather than defect-fix. The urgency is moderate rather than high: the MCP connector client itself was completed and driven against a real server in Phase 206, so nothing regresses by deferring — but the product currently ships a connection-creation door to a destination workflows cannot reach, which is a materially incomplete feature for anyone who tries to actually use it.
- **(B) Close 206.1 with SC#1b recorded as owed.** Defensible: the create/see/understand goal (the phase's own header wording) is genuinely met and independently verified, SC#2-5 are clean, and the gap is already planted with a re-open trigger. This is the pragmatic choice if the next milestone's sequencing does not have room for (A) immediately.
- **(C) Re-scope 206.1 to fold the builder seam in.** Not recommended — this is precisely what G-7 exists to make expensive, and it would also violate this phase's own D-206.1-01 separability design by turning a closed, verified phase back into an open one for a capability, not a defect.

**This report's own recommendation: (A), sequenced as its own phase, with (B) as the interim
close-out state for 206.1 while (A) is scheduled.** The create door alone is real, tested, and
correctly separable — closing 206.1 now with SC#1b explicitly recorded as owed (not silently
dropped) is consistent with how the phase's own plans were structured from the start.
