## Goal Achievement — headline

**The phase's own wording of the goal is MET for the runtime capability, and NOT MET for
publishing.** A person can, today, in the production build: open a step's authoring panel,
switch it to the MCP shape, see only MCP-shaped connections in the picker (never capability
rows and vice versa), discover a server's real tools, flip a real per-tool grant through the UI
(server-persisted, full-merge-safe), have the run REFUSE an ungranted tool with a real audit
receipt, and have the run CALL the tool and receive the remote server's real answer when
granted. All of that was re-derived against the current tree below, not merely quoted from the
SUMMARY. What a person **cannot** do is publish a workflow that contains that step — the
gauntlet blocks one stage after the exact stage this phase fixed, for a reason that is real,
reproducible, and NOT owned by this phase's own code.

## Independent Finding: SEED-201's causal diagnosis is contradicted by a passing regression test

This is the one piece of this verification that goes beyond re-checking the SUMMARY's own claims.

The SUMMARY and SEED-201 both assert: *"an `external_action` step ALWAYS stops for approval …
The golden run is an UNATTENDED trial run. There is nobody to press Approve this step, so it waits
until the publish service gives up. Every workflow containing any external_action step is
therefore unpublishable, whatever its shape."*

Reading `backend/app/services/harness_engine.py` (the armed-checkpoint code, lines ~860-925) shows
this is not how the golden run behaves: `if _armed and getattr(ctx, "is_golden_run", False):` the
checkpoint is **auto-continued** (logged only, no pause, no `action_risk_pending` write) — this is
the documented **D-19 / "CONFLICT 1"** fix, dated to Phase 189/190, specifically built to stop an
armed `external_action` step from hanging an unattended golden run. `ctx.is_golden_run=True` is
set explicitly in `publish_service._drive_golden_run`'s `SimpleNamespace` ctx, with an inline
comment naming exactly this failure mode as the reason it exists.

More importantly, this is not just a static-reading disagreement: `backend/tests/unit/test_publish_service.py`
contains `test_v20_an_external_action_workflow_publishes`, which drives the REAL armed checkpoint
through a REAL golden-run ctx for a **capability**-shaped (`send_email`) `external_action` step and
asserts `published is True`, `blocked_stage is None`, and `subscribe_timeouts == []` — a positive
assertion that the ask-channel was never subscribed to during the golden run. A sibling test,
`test_the_armed_checkpoint_is_not_a_validator`, is a deliberate fence (its own docstring: *"a future
reader who 'fixes' the golden-run hang by adding a case here will fail this test, which is the
intent"*) guarding specifically against re-introducing this exact hang. **Both tests were re-run
independently in this verification and PASS on the current tree** (2 passed, 0.15s).

This means: for the **capability** shape, the golden run demonstrably does NOT wait forever on
approval — it is proven, in an executable test, to publish successfully. The MCP-shaped failure
that the T4 drive found is real (driven, SQL-confirmed), but its cause is very unlikely to be the
one SEED-201 names. The likelier location is something MCP-connector-specific inside
`_drive_golden_run`'s broad `except Exception` (ctx setup, connection resolution attempted despite
the golden-run gate, or the grounding tool-names union choking on an MCP tool name) — and the
generic exception handler (`named_failures: ["golden run could not complete: {e}"]` reading literal
`None`, `golden_run_id` hardcoded to `None` even when a run row exists) is exactly what is hiding
the real cause from view.

**This does not change the verdict on SC#3b** (it is still not met — a real, reproducible defect
blocks publish for the driven case) but it does change what should happen next: SEED-201's "why it
happens" section and its scope claim should be corrected before anyone scopes a fix from it, or a
fix aimed at "the approval checkpoint" will not touch the actual bug.
