### 3 · A config write that CLEARS the other shape's keys (D-206.2-02)

> ## ⚠ NO ANALOG FOUND for the exact thing — say so plainly, per the brief.
>
> **There is no shipped example anywhere in `frontend/src` of a builder write that clears a key
> INSIDE `config`.** Measured:
> ```bash

> `patchConfig` → `patchPhaseConfig` is a **pure spread merge** over `config`
> (`definitionOps.ts:308`: `{ ...p, config: { ...p.config, ...patch } }`). There is no subtractive
> path. **The planner must author this.**

**But a PARTIAL analog exists and it is a strong one** — the D-187-07 "demote", the only sibling-key
clear in the tree. It is at the **PhaseSpec** level, not inside `config`, which is the one thing that
does not transfer:

```ts
// frontend/src/components/workflows/definitionOps.ts:295-320
export function patchPhaseConfig(
  phases: readonly PhaseSpecJSON[],
  slug: string,
  patch: Readonly<Record<string, unknown>>,
): PhaseSpecJSON[] {
  // Read the trigger off the PATCH's keys, once, before the walk: the rule is a property
  // of the edit, not of the phase.
  const invalidatesTheFace = Object.keys(patch).some((key) =>
    IDENTITY_BEARING_CONFIG_KEYS.has(key),
  )

  return phases.map((p) => {
    if (p.slug !== slug) return p
    const next: PhaseSpecJSON = { ...p, config: { ...p.config, ...patch } }
    const seededName =
      next.name_seeded_by_ai === true && typeof next.name === "string" && next.name.trim() !== ""
    if (invalidatesTheFace && seededName) {
      delete next.name
      delete next.name_seeded_by_ai
    }
    return next
  })
}
```

**WHAT TO COPY:**
- **`delete`, not `= undefined`** — and the reason is written down at `definitionOps.ts:291-293`:
  > *"The keys are `delete`d rather than set to `undefined`: a phase that carried no name must come
  > back with no name KEY, not with an explicit `undefined` the round trip would serialize
  > (`extra="forbid"` on the backend union, and R2's round-trip identity)."*
- **Clear the PAIR, never half of it** (`:283-284`): *"It clears BOTH `name` and `name_seeded_by_ai`.
  Clearing only the name would leave a provenance marker describing a name that no longer exists."*
  The MCP analog: clearing `tool_name` without `tool_args` leaves arguments for a tool that no longer
  exists. Clear `{tool_name, tool_args}` as a set; clear `capability` as its own.
- **Name the clear-trigger set as a module constant**, the `IDENTITY_BEARING_CONFIG_KEYS`
  (`:253-257`) form — never an inline condition at the call site.
- **The one-mutation-home rule** (`:272-273`): *"This is the ONE config-edit home … so the rule is
  stated once and cannot be reached around."*

**WHAT NOT TO COPY:**
- ⚠ **Its `delete` targets are PhaseSpec siblings (`next.name`), not `next.config.*`.** Copying the
  expression shape verbatim writes to the wrong object.
- ⚠ **Do NOT reach for `setPhaseGovernance` as the vehicle.** Its parameter type
  (`PhaseGovernancePatch`, `definitionOps.ts:322-325`) admits only two booleans, and
  `:337-340` says widening it into a general writer is *"a typecheck error rather than a review
  comment"* — i.e. deliberately closed.
- ⚠ **The direction of the danger is ASYMMETRIC, and the backend proves which way.** Measured at

  ```python

            derived = [self.tool_name]
        elif self.capability:
            derived = [self.capability]
        else:
            derived = []
  ```

  and at `backend/app/services/harness/phase_types.py:2288-2298` the executor branches
  `if mcp_tool_name: … elif capability not in EXTERNAL_ACTION_CAPABILITIES: raise`.
  **`tool_name` WINS.** So a stranded `capability` under an MCP step is inert; a stranded `tool_name`
  under a capability step **silently turns an email step into an MCP step**. The clear that MUST
  happen is MCP → capability. Clear both anyway (D-206.2-02 says so), but the acceptance test that
  matters is the MCP→capability direction.
- ⚠ **This is the same family as the accident `phase_types.py:2278-2286` records** —
  *"A default is not a way through a gate."* Quote it at the clear's own site.
