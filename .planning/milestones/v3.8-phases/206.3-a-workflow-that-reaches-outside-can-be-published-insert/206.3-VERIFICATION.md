## Findings

### 1. ⚠ The phase's own browser evidence was destroyed by its own session's cleanup

All three definitions named in the 206.3 audit trail (`09f1394a…`, `ed366739…`, `b97e06e4…`) and all
four golden runs (`154fdf89…`, `b388c378…`, `f6ad8f68…`, `73ec1f6a…`) return **zero rows**. They were
removed when the session cleaned out its 14 `MCP Publish Drive` test workflows. What survives is
`harness_audit` (append-only, not cascaded) — and **audit rows alone cannot prove the published
workflow was MCP-shaped**, because the metadata carries only ids.

So SC#2 was **unverifiable from the historical record** and is met only because I re-drove it. The
reproducibility came from the drive script being committed, not from the evidence being kept.

**Consequence, stated so it is not repeated:** a phase whose acceptance is *"driven in a real browser"*
must either keep its driven artifact or commit a re-runnable driver. 206.3 did the second by luck of
good practice; the first was undone in the same session.

⚠ **The workflow this pass created (`7d0eced1…`) is DELIBERATELY LEFT IN PLACE** as the verification's
own evidence. Deleting it would repeat exactly the mistake this finding records.

### 2. ⚠ The drive script does not run from the mandated `venv`

`backend/venv/Scripts/python.exe scripts/drive_phase_206_3_publish.py` dies at
`ModuleNotFoundError: No module named 'playwright'`. It runs only on system Python 3.12. The project
rule is *"Python backend must use a `venv`"*; a committed verification driver that the venv cannot
execute will read as broken to the next verifier. Either add `playwright` to the venv or say in the
script's docstring which interpreter it needs.

### 3. ⚠ The gauntlet passed a golden run whose deliverable refuses the work

The run I drove published at judge score **100**, and its final phase output was:

> *"That message looks like a system log, not a question or command. To confirm: no MCP tool was called,
> no wiki structure was retrieved, and nothing left the workflow. So there's nothing for me to act on…"*

The workflow's business requirement was *"Provide a comprehensive overview of React repository
architecture"* and the phase-1 prompt asked for JSX, lifecycle, virtual DOM and hooks. **None of that was
produced.** The downstream LLM read the `recorded_not_sent` body as a system log and derailed; the judge
scored the derailment `overall_passed: true, overall_score: 100`, summarising it as *"effectively an
acknowledgment and invitation for a follow-up."*

The three earlier drives produced genuine explanations, so this is model variance rather than a
regression — **but the hard-wall passed a non-answer, which is the property the hard-wall exists to
deny.** This is not a 206.3 defect (206.3 was scoped to make the publish possible, and it did), and it is
not fixed by weakening anything. It belongs as its own item: *a golden run's deliverable must answer the
business requirement, and the judge must be able to tell when it did not.*

⚠ **A second-order note that the fix itself creates:** the `recorded_not_sent` body is written for a
human reading a receipt, and it is then fed to the next phase as *model input*. The next phase read it as
a system log. That is a real seam between D-16's honesty and the accumulated-output contract, and it is
newly reachable because MCP steps can now publish at all.
