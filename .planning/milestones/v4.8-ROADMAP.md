#### Phase 300: Told When a Run Waits (Backend and Mailer)

**Goal**: When a workflow run starts waiting on a person, the system records one notice for its owner and, if the run is still waiting after the delay, sends exactly one content-free email linking to the run, through an app-owned sender that works from a built image; and scheduled or API-key runs that pause are launched and resumed correctly first.
**Depends on**: Phase 297 (the `/app/runs/<id>` address). Its live proof of the signed-out email journey needs Phase 299's sign-in return. The FIX-04/05 plan has no dependency and goes first.
**Requirements**: NOTE-02, NOTE-03, NOTE-04, NOTE-06, FIX-04, FIX-05
**Success Criteria** (what must be TRUE):

  1. A scheduled run whose required input is blank is refused before launch and the refusal names the input (FIX-04). A paused run started by an API key or a schedule resumes on the provider it started on, driven across the roster (FIX-05).
  2. A run that waits on a question or an approval, including a scheduled or API-key run, and is still waiting after the delay (2 minutes by default, a Settings knob) sends its owner exactly one email linking to `/app/runs/<id>`. Answering within the delay sends none. A restart, a deploy or the second worker never sends a second one, and each delivery's outcome is stored (NOTE-02).
  3. The rendered email contains only the escaped workflow name, the org name, how long the run has waited and the link: no question text, no document content, no token in the URL (NOTE-03).
  4. A user who turns notification email off in their own Settings receives no email, while the in-app notice is still recorded (NOTE-04).
  5. A built image, with nothing installed by hand, sends through Resend on cloud and SMTP on the one-box; the secret lives in env and every other knob in Settings. Invite email goes through the same sender, and a failed send is shown to the inviter, not only logged (NOTE-06).

**How we'd know this failed**: two workers or a restart send the same email twice; an email goes out after the question was answered; the body carries the question or any document text; a trigger error breaks the engine's fail-closed prompt insert; a notice takes its org from `messages.org_id` (the `LIMIT 1` autofill) instead of `workflow_runs`; the notices or outbox table is readable by `anon` or by another user, or `get_advisors(security)` shows a new ERROR; a send failure is only logged; dev mail reaches a real inbox (no redirect-all guard); a tool-round-cap pause or a chat `ask_user` produces a notice; `harness_engine.py` is edited to emit notices; the clean-image test passes only because the dev venv has the package.
