    Create `frontend/src/pages/librarySelection.ts` — zero imports, no I/O, no React.

    Export `LibrarySelection` exactly as D-217-12 locks it (four arms, the union above), and a
    `LibraryState` that additionally owns the four pieces of state that transition in lockstep and
    are NOT async results: `selection`, `editingView`, `filter`, `folderSheetOpen`.
    ⛔ `filteredDocs`, `matchCount` and `filterReqId` stay OUTSIDE the state — they are async
    results and a stale-request guard, not selection. Say so in the docblock, in the
    *"what this module cannot produce"* heading, so a later plan does not fold them in.

    Export `libraryReducer(state, action)` and an `initialLibraryState`. The actions are the five
    shipped handlers, named after them so the mapping is obvious:
    `SELECT_FOLDER {folderId}` -> `{tab:"documents", folderId}`, clears `editingView`, resets
    `filter` to EMPTY, closes `folderSheetOpen`. ⭐ This is D-217-14: the tab FOLLOWS the selection,
    so clicking a folder while a view is loaded can never leave the tab on `views`.
    `SELECT_VIEW {viewId}` -> `{tab:"views", viewId}`, clears `editingView`, sets the view's filter,
    closes `folderSheetOpen`.
    `EDIT_VIEW {view}` -> `{tab:"views", viewId}` plus `editingView`.
    `CHANGE_FILTER {filter}` -> ⚠ today `:275` clears `selectedViewId` when the filter bar is
    edited; under the union that means the selection LEAVES the views arm and becomes
    `{tab:"documents", folderId:null}`. Encode that explicitly and comment it: a tab that stayed on
    `views` while the list showed an ad-hoc filter is exactly the lie SC#5 forbids.
    `DELETE_VIEW {viewId}` -> if the deleted view is the selected one, fall back to
    `{tab:"documents", folderId:null}` and clear `editingView` and `filter`; otherwise the selection
    is unchanged.
    `SELECT_TAB {tab}` -> switches tab, preserving the arm's own payload where the arm is re-entered
    (`documents` keeps its `folderId`, `views` keeps its `viewId`).

    Export two DERIVED helpers so no consumer re-derives them and disagrees:
    `activeFolderId(state): string | null` and `activeViewId(state): string | null`, each returning
    `null` on the arms that do not carry it. ⚠ These replace the render-time ternary at
    `LibraryPage.tsx:307` — mark them in the docblock as DERIVED DISPLAY VALUES, never stored.

    The reducer is total: every action on every arm returns a valid state. No `throw`, no `as any`,
    no partial returns.
