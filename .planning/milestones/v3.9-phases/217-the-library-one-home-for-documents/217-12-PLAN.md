Purpose: `TARGETS` decides what RUNS and `BASELINE` decides what is GUARDED, and a suite can sit on
the wrong side of exactly one. At Phase 214's close twelve suites were pinned and **six more were
left unpinned**; `WorkflowScheduleModal.test.tsx` had been RUNNING while guarding nothing. Before
this phase, only ONE doc-space suite sat in both knobs.

⚠ **A deliberate planning decision, recorded so it is auditable rather than discovered:** the gate
knobs for this phase's suites land HERE rather than in each creating commit. The mechanical
constraint is only that a BASELINE key naming a file that does not yet exist makes the gate ERROR
(exit 2) — pinning after the files exist is safe, and pinning per-plan would have made
`scripts/vitest-count-gate.cjs` a shared file across six plans and forced the whole phase serial.
The cost is that each suite is unguarded for the length of the phase; the mitigation is the
mechanical completeness check in task 1, which derives the suite list from git rather than from
memory.

Output: a green gate with an attributable `+n`, a resolved bare-name collision, a seam audit, and a
signed-off VALIDATION.md.
</objective>
