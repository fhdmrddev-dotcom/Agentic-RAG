# Phase 214.1 — CONTEXT

## Why this phase exists

Phase 214 shipped three quarters of a mechanism and the operator found the missing quarter by
driving it. `BUG-260828-02`: publish correctly refuses an undeclared launch argument, the launch
forms correctly render declared inputs, the run wire correctly carries them — and **nothing can
create a declared input**. So *"Asked when this runs"* is a dead end for every author, and the only
way to send an email is to hardcode the recipient.

⚠ **The reason it survived a 16-plan phase with green gates is the whole lesson**: every test built
`definition.inputs[]` by hand. The fixtures could reach a state no human could.

## Decisions (all mine — 2026-08-28)

### D-214.1-01 · The declared-input editor lives at the DEFINITION level, not on the phase form

`inputs[]` is a property of the workflow, not of a step — several steps can source from one input,
and an input can exist before any step uses it. Putting it on `PhaseFormPanel` would make a
definition-level fact look phase-owned and would force a second copy the moment a second step used it.

**Alternative not taken:** an inline "declare this" affordance on the argument row itself, next to
*Asked when this runs*. It is friendlier — it puts the fix where the refusal happens — but it hides a
definition-level object inside a phase-level control, which is how `tool_args` became confusing in
the first place. ⚠ **If the operator prefers the inline version, the store action and the wire are
unchanged; only the mount point moves.**

### D-214.1-02 · A declared input is `{ key, label, required, description? }` and nothing more

`key` is what an argument source binds to; `label` is what the launch form shows; `required` decides
whether the launcher can proceed empty. No type system in this phase — every launch field is already
a text input on all three launchers, so a `type` field would be stored, unused, and immediately
stale. ⚠ Attachments (`SEED-225`) are the first thing that will need a type; that seed says so.

### D-214.1-03 · Reserved keys are refused AT AUTHORING TIME, with the reason

`RESERVED_RUN_INPUT_KEYS` (from 214-16) is stripped server-side. An author who declares
`kickoff_prompt` today would get a field whose value silently vanishes — 214-09 measured exactly
this trap. The editor refuses the key when it is typed and says why, rather than accepting it and
letting the strip happen invisibly.

### D-214.1-04 · `BUG-260828-04` is DIAGNOSED, not assumed

The operator saw the raw backend diagnostic (`phase 'act': the required argument 'to' is asked for
at launch, but the wor…`). `PublishRefusalList.tsx`'s own docblock forbids rendering that text, and
the verifier's hand-trace says `isArgumentRefusal` returns `true` for that exact shape — so the
composed sentence *should* have rendered.

Two live hypotheses and they need different fixes:
- **(a) classification defect** — the entry never reaches `PublishRefusalList`, or reaches it and the
  raw diagnostic is rendered anyway.
- **(b) stale bundle** — the operator's browser was serving pre-merge JS at drive time.

**The plan MUST drive the distinction** (render the real refusal shape in a test and read what comes
out) before writing a fix. ⚠ Shipping a CSS clamp against hypothesis (b) would leave (a) live and
look fixed.

### D-214.1-05 · `BUG-260828-03` is answered by a LOOKUP, never by prompting

The model wrote *"no email service is connected to this workspace"* while the SMTP connection
existed, and it was delivered to a recipient. Prompting a model not to speculate about system state
is already measured insufficient one surface over — STEP-06 enforces its vocabulary on the *emitted
definition* rather than by asking. The same shape applies: the connected-service set is a fact the
system holds, so the model must be given it rather than asked to guess it.

**Scope limit I am imposing:** this phase makes the model *aware* of the real connection set at the
point it would otherwise speculate. It does **not** add a post-hoc censor over generated text — that
is a bigger and more dangerous mechanism, and it would need the operator.

### D-214.1-06 · ⚠ G-2 IS OVERRIDDEN, NOT SATISFIED

This phase ships UI and **no operator-approved sketch exists**. The operator explicitly retained the
visual veto and authorised the build anyway. The UI is authored from the shipped design system and
