### 4. The six `RunModal` whole-`innerHTML` captures — **BYTE-IDENTICAL, and not re-baselined**

`git diff --stat 1b31f478..HEAD -- frontend/src/pages/__tests__/RunModal.test.tsx` is **EMPTY**,
and all **54** of its tests pass. The captures were therefore not moved and not re-taken — which
matters, because `214-12` re-baselined them once and its own plan said not to move them twice.

⚠ **THEY ALMOST DID MOVE, AND WHAT STOPPED IT IS A REAL FINDING RATHER THAN LUCK.** The first
implementation put the required mark inside the `<label>`. Two consequences, both measured:

1. **A testid prefix collision.** `run-input-mark-{key}` matched a shipped assertion's
   `getAllByTestId(/^run-input-/)`, turning *"the RESERVED key draws NO field"* red with
   `expected … length 2 but got 4`. **Fixed by renaming the testid to `run-field-mark-{key}`, not
   by editing the shipped count** — the assertion was right and the new id was wrong.
2. ⭐ **A REAL ACCESSIBILITY REGRESSION.** An input wrapped by a `<label>` takes the label's whole
   text content as its **accessible name**, so the mark produced
   `Expected: "Recipient email" / Received: "Recipient emailRequired"`. That is not a stale pin —
   the field's name would have stopped being the author's words, which is this component's entire
   contract. ⛔ `aria-hidden` on the mark was the cheaper fix and was **REFUSED**: it would keep
   the name clean by making requiredness a **sighted-only** signal, which is the same class of
   dishonesty the two-arm rule exists to prevent. The mark now sits **outside** the `<label>` and
   is linked by `aria-describedby`, so the label owns the NAME and the mark is a DESCRIPTION.
   The `<label>`'s own children are unchanged — face span, then input, direct siblings — because
   three shipped cases read the face as `input.parentElement.querySelector("span")` and one reads
   it as `input.previousElementSibling`. **Both shapes were driven; both went red when they were
   not honoured.**

### 5. `InputFieldSpec` at execute time — **`description` still absent, `type` still required**

Re-measured at HEAD rather than inherited (`backend/app/models/harness.py:652-660`):

```python
class InputFieldSpec(_StrictBase):          # _StrictBase => ConfigDict(extra="forbid")
    key: str
    label: str
    type: Literal["text","number","date","enum","file","kb_auto"]   # ← NO DEFAULT
    required: bool = True
    source: Literal[...] = "user"
    enum_options: list[str] = []
    folder_scope: list[UUID] | None = None
```

- **`description` does NOT exist** → emitting one would be a 422 on the first autosave. D-214.1-02's
  wording (`{key, label, required, description?}`) is **corrected by measurement**, recorded rather
  than silently obeyed.
- **`type` has NO default** → it must be written. It is the constant `"text"` and is **not
  author-editable**, which is what D-214.1-02 means by *no type system*: there is no type CHOICE,
  not that the field is absent.
- `required: bool = True` → an **absent** `required` reads `true` client-side.
- `RESERVED_RUN_INPUT_KEYS` is `frozenset({"kickoff_prompt","folder_id"})`
  (`backend/app/models/message.py:27`) and the client mirror agrees. Asserted by **iterating** the
  shipped set, so a third reserved key inherits the refusal with no edit.

**Plan `214.1-02`'s describe-door derivation can compile against `{key, label, type: "text",
required}` and must NOT emit `description`.**
