# 213-06 — gap closure round 1

**Source:** `213-POSTFLIGHT.md`. G-7 checked before writing: `check-gap-closure-rounds.cjs 213` →
**clear**, 0 prior gap-closure plans. This is round 1.

⚠ **No new capability is introduced.** Every surface, string, resolver and mount this plan needs
already shipped in waves 1–5; what is missing is the wiring between them. That is the G-7 test for
whether a closure round is legitimate, and it passes.

---

## The decision this plan implements, stated plainly because it reads like a contradiction

`D-213-09` chose **two triggers, ONE pause**, and explicitly **rejected** *"posture SUPERSEDES the
armed checkpoint"* — because a connection-level `allow` that skipped the pause *"would silently
un-arm every external step"*, disarming a guarantee `models/harness.py:517` coerces to True and calls
*"structurally armed, not disarmable"*.

**A consequence follows that must be written down rather than rediscovered as a defect:**

> On a workflow `external_action` step, `allow` and `ask` produce the SAME observable behaviour —
> both proceed *after* the armed checkpoint has asked a person. That is not the posture being inert;
> it is the author's arming being unconditional, which is the recorded decision.

So the two postures differ exactly where the armed checkpoint is **absent** — the Phase 216 chat path,
and any future non-armed caller. `ask` there must mean **"a human must have been asked"**, and if
nothing asked, the answer is **refuse**. That is what makes SC#3's *"nothing leaves until they
answer"* true rather than aspirational, and it is what this plan builds.

## Task 1 — `ask` must never mean "send" (⛔ POSTFLIGHT §1, §1b)

**Today:** Gate 5.5 refuses on `deny` and falls through on everything else, so `ask` dispatches.
Combined with migration §1's `DEFAULT 'ask'`, a **newly created connection with no grant configured
dispatches** — where the pre-213 MCP path refused, because Gate 6's removed check made a missing key
DENY.

**Change:** Gate 5.5 gains an `ask` arm keyed on whether the phase was armed.

- `phase.action_risk_armed` is **True** → the armed checkpoint has already paused and a person has
  already answered (the body runs **only** when `_resolve_failure_with_ask_user` returns `None`,
  `harness_engine.py:930`). The approval requirement is satisfied → proceed.
- `phase.action_risk_armed` is **False** → **nothing asked anyone.** Refuse, fail closed, with a
  refusal that says approval was required and never obtained.

This restores the fail-closed property to the **gate** rather than leaving it resting on a column
default, and it introduces **no second pause**.

## Task 2 — the approval prompt must name the service, the tool and the arguments (⛔ SC#3)

**Today:** `grounding._approval_sentence` states POSITION, IDENTITY and CONSEQUENCE, and names
none of the three things SC#3 requires.

**Change:** append an external-action clause composed from `phase.config` **only** — `capability`
(the service, where the row has one), `tool_name`, and `tool_args`. The composer stays **pure**;
no new I/O, and the engine is not made to resolve a connection it does not already hold.

- ⚠ Shipped assertions on this sentence use `.startswith(...)` (`test_185_engine_attachment.py:249`,
  `:525`), so appending is safe by construction. Verified before writing.
- ⚠ **Name only what is known.** An MCP row has `capability = None`, so the clause names the tool and
  the arguments and does **not** invent a service label. *Never draw a name the system cannot know.*
- ⚠ **Arguments are SHOWN, never recorded.** `D-213-14` already settled that asymmetry, and this
  keeps it: the prompt is a user-facing sentence, and `_write_send_receipt`'s D-08 metadata is
  untouched.
- The honesty rules hold: it still never says *approved*, *safe* or *proven*.

## Task 3 — the refusal names the grant that would allow it (⚠ GRANT-04 / POSTFLIGHT §2)

**Today:** the pre-existing *"Tool execution refused: Tool 'X' is not granted permission…"* — the
mechanism-naming voice the sketch deliberately replaced, naming no grant and offering no next step.

**Change:** compose from the sketch's copy, which already ships unused in `grantsVocabulary.ts:50-54`
— `REFUSED_HEADLINE`, `REFUSED_BECAUSE_DENIED`, `REFUSED_BECAUSE_UNGRANTED`, `REFUSED_NEXT`. Per
`D-213-15` the backend owns the run sentence, so the words are carried in a backend constant that
**mirrors** the vocabulary; a test pins the two in agreement so the drift the two-homes decision
accepts cannot go unnoticed.

## Task 4 — three refusal reasons, not one (▪ D-213-16)

`posture_denied` (a grant says deny) · `not_granted` (inherited a deny default — nobody granted it) ·
`approval_required` (approval was required and nothing asked). The third replaces what would
otherwise be silence about the Task-1 case. No new audit KIND — `tool_refused` already exists, so the
`_AUDIT_EVENT_TYPES` ↔ migration-CHECK lockstep is untouched.

## Task 5 — the migration must stop claiming re-paste safety it does not have (⚠ POSTFLIGHT §4)

`128_...sql`'s header says *"The whole file is RE-PASTE-SAFE"*. §3's backfill overwrites
`tool_grants` wholesale, so re-pasting after real use **discards every posture a person has set**.
Correct the claim and scope the backfill so it cannot re-fire on rows that have already been
migrated. **Comment-and-guard only — no data change to an applied migration's effect on a fresh DB.**
