## 2. The one gap — `RECALL-01`

Phase 246 set out to fix small-tenant recall by raising `hnsw_ef_search` to 200. **It proved the knob
cannot fix it**, and caught a false belief that had been shipping since Phase 241.

| `ef_search` | plan | rows | recall@20 | latency |
|---|---|---|---|---|
| 40 / 60 / 80 | **Index Scan** | **1** | ~0.05 | ~4 ms |
| 100 / 150 / 200 | **Seq Scan** | 20 | 1.000 | ~1,100 ms |

**Every genuine index walk returns ONE row; every good recall number is a table scan.** Shipping 200
would have cost every tenant ~1.1 s a query to fix a cliff only small tenants have, by a mechanism
nobody intended. The default is reverted to 40 (`521f4a025`) and the remaining path is `SEED-273`
(`hnsw.iterative_scan`).

⭐ **This is not a phase that failed to deliver — it is a phase that refused to ship a fix it had
disproved.** ⚠ Phase 241's contrary conclusion (`ef_search = 200` restores 1.000) **never inspected an
execution plan**; it measured recall alone and was right about the number and wrong about the cause.

### ⛔ INT-01 (warning, CONFIRMED — re-driven by hand, not taken on the subagent's word)

`frontend/src/pages/settingsSearchPayload.ts:76` still reads `hnsw_ef_search: data.hnsw_ef_search ?? 200`.

```

549d98ec9  feat(246-02) →  ?? 200     (the since-abandoned raise-the-default work)
521f4a025  fix(246)     →  six files, NOT this one
```

The revert's own message says *"Reverted at four sites plus the help copy"* — **this is a fifth site.**

⚠⚠ **CORRECTED 2026-09-13, IN THE SAME SESSION, BY DRIVING IT — the original is preserved below
rather than overwritten, because how the claim went wrong is the finding.**

> ~~**The sharper half, and the reason this earns a row rather than a one-line fix note: the test
> pins the refuted value.** `SettingsPage.changedFields.test.tsx:276` (FIXTURE A — the NULL-column
> fallback case) asserts `toBe(200)`. **So the fence would turn RED on the correct fix and GREEN on
> the wrong one.** *(Line 264, FIXTURE B, is correct — `NON_DEFAULT` genuinely stores 200.)*~~

⛔ **That was FALSE, and it was believed because the test's own case NAME was trusted over the
fixture it calls.** `ALL_NULL()` (line 115) nulls exactly six columns — `vision_model`,
`vision_max_pages`, `hnsw_iterative_scan`, `extraction_model`, `extraction_provider`,
`embedding_provider` — and **`hnsw_ef_search` is not among them.** It keeps `mkSettings`' base value
of **200**, so FIXTURE A reads a *stored* value here exactly as FIXTURE B does. `toBe(200)` was
**correct in both cases** and the file was restored byte-identical after the wrong edit.

⭐ **The real finding is duller and worse: `hnsw_ef_search`'s `??` fallback had NO coverage at all.**
Neither fixture reaches it, which is precisely why `?? 200` shipped through a revert and sat green.
A case named for a property it does not actually exercise is weaker than no case — it reads, to the
next person, as though the property were already fenced.

**Fixed at this audit:**
- `settingsSearchPayload.ts:76` → `?? 40`.
- A new case, `"⛔ a NULL hnsw_ef_search falls back to 40, the value the BACKEND coalesces a NULL
  column to"`, calls `mkSettings({ hnsw_ef_search: null })` directly. **Driven RED against the

The file's own header comment, eleven lines in, already stated the correct form verbatim as
`data.hnsw_ef_search ?? 40` and warned exactly what goes wrong otherwise. **The prose knew; nothing
executable did.**

**Live impact today: none.** `GET /settings` types `hnsw_ef_search` as a non-optional `int`
