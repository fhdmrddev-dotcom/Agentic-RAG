<objective>
Fix Symptom E: after switching tabs during a stream and returning, the complete assistant message is visible.

Root cause: The Realtime INSERT fires while `isStreamingRef.current = true` (backend persists before yielding `done`). The guard blocks it. `finally` runs too late — the INSERT is already gone. The 2s delayed `removeChannel` only catches INSERTs that arrive after `isStreamingRef = false`; this one arrives before.

Fix: In the `finally` block of `sendMessage`, after `isStreamingRef.current = false`, call `loadMessages(threadId)` directly. Guard with `activeThreadIdRef.current === threadId` (prevents overwriting a new thread the user navigated to) and `!stoppedByUserRef.current` (Stop is already handled by Phase 55's asyncio.shield). One extra `getMessages()` DB call per natural stream completion.

Purpose: Replace the unreliable "catch INSERT via Realtime" approach with a guaranteed DB reload on every natural stream completion.
Output: Modified `useMessages.ts` with activeThreadIdRef tracking and finally-block loadMessages call.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase Realtime → React state | Realtime events contain DB row data for the authenticated user's thread |
| sendMessage finally → loadMessages | DB reload is triggered client-side; server validates RLS on getMessages call |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-057-01-01 | Spoofing | activeThreadIdRef guard | mitigate | Guard uses threadId captured at sendMessage call time — cannot be forged by Realtime event content; ref is a React closure variable not accessible from outside |
| T-057-01-02 | Information Disclosure | loadMessages(threadId) in finally | mitigate | `getMessages(threadId)` calls the authenticated API endpoint; RLS on `messages` table ensures only the authenticated user's messages are returned regardless of which threadId is passed |
| T-057-01-03 | Denial of Service | Extra DB call per stream completion | accept | One additional `getMessages` GET per assistant response is negligible; no rate-limit risk at single-user scale |
| T-057-01-04 | Elevation of Privilege | Thread identity guard bypass | accept | Both guards (`activeThreadIdRef` and `!stoppedByUserRef`) are in-process memory — no cross-user risk; worst case is a stale reload of same user's own data |
</threat_model>
