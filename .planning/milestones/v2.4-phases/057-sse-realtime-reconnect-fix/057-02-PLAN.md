<objective>
Fix Symptom F: after pressing F5 mid-stream and waiting ~5s, the complete assistant message appears automatically.

Root cause: On fresh page load, `loadMessages` runs ~100ms after mount while the backend is still generating. The assistant message isn't in the DB yet. The backend persists it ~5s later via `asyncio.shield` — but no Realtime channel is listening. The channel is only created inside `sendMessage`, never on thread selection.

Fix: Add a persistent Realtime subscription for `messages INSERT` in `ChatArea.tsx`'s `useEffect([thread?.id])` — the effect that already calls `clearMessages()` + `loadMessages()`. Subscribe when a thread is selected; unsubscribe on cleanup. Expose `subscribeToThread`/`unsubscribeFromThread` from `useMessages`. On INSERT: call `loadMessages(thread.id)` if `!isStreaming` (SSE handles live updates when active). One persistent channel per viewed thread — negligible cost.

Purpose: Ensure any INSERT on the thread (including from a still-running backend task after refresh) is received regardless of whether a stream was active at page load time.
Output: Modified `useMessages.ts` (new subscribe/unsubscribe functions) and `ChatArea.tsx` (subscription in useEffect).
</objective>

```typescript
const subscribeToThread = useCallback((threadId: string) => {
  // Tear down any existing always-on subscription first (no-op if null)
  if (threadChannelRef.current) {
    supabase.removeChannel(threadChannelRef.current)
    threadChannelRef.current = null
  }

  const channelName = `thread-always-on-${threadId}`
  const channel = supabase
    .channel(channelName)
    .on(
      "postgres_changes",
      {
        event: "INSERT",
        schema: "public",
        table: "messages",
        filter: `thread_id=eq.${threadId}`,
      },
      (payload) => {
        // Guard: skip while SSE is active — SSE delta events handle live updates.
        // This subscription is recovery-only (for refresh/reconnect scenarios).
        if (isStreamingRef.current) return

        const newMsg = payload.new as Message
        setMessages((prev) => {
          // Replace optimistic temp-id placeholder for assistant messages
          if (newMsg.role === "assistant") {
            const tempIdx = prev.findIndex(
              (m) => m.role === "assistant" && m.id.startsWith("temp-")
            )
            if (tempIdx !== -1) {
              const next = [...prev]
              next[tempIdx] = newMsg
              return next
            }
          }
          // Deduplicate: skip if already present
          if (prev.some((m) => m.id === newMsg.id)) return prev
          // Fresh message (e.g. from a completed stream on a refreshed page)
          // Reload from DB to get canonical order and full message data
          loadMessages(threadId).catch(console.error)
          return prev // loadMessages will trigger a proper setMessages
        })
      }
    )
    .subscribe()

  threadChannelRef.current = channel
}, [loadMessages])
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase Realtime → React state | Always-on subscription receives INSERT events for the authenticated user's thread; RLS enforced at DB level |
| ChatArea useEffect → subscribeToThread | Subscription is scoped to `thread_id=eq.{thread.id}` filter; only the user's own thread events arrive |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-057-02-01 | Spoofing | thread_id filter in subscribeToThread | mitigate | Filter is `thread_id=eq.${threadId}` where `threadId` comes from the authenticated thread object; RLS on `messages` table additionally enforces user ownership — a cross-user INSERT would be blocked at the DB layer before reaching Realtime |
| T-057-02-02 | Information Disclosure | loadMessages called on Realtime INSERT | mitigate | `getMessages(threadId)` calls the authenticated API; RLS enforced per request; no raw Realtime payload data is written to state (loadMessages fetches fresh from API) |
| T-057-02-03 | Denial of Service | Double subscription (threadChannelRef + channelRef) | accept | At most two channels per active thread — one always-on, one SSE-recovery. Both scoped to same thread. Supabase free tier allows 100 concurrent connections; single-user app has negligible risk |
| T-057-02-04 | Denial of Service | loadMessages call on every INSERT | accept | INSERTs happen at most once per assistant response. One extra getMessages call per response is negligible at single-user scale |
| T-057-02-05 | Elevation of Privilege | isStreamingRef guard bypass | accept | Guard is an optimization (skip reload when SSE is live) — not a security boundary. Even if bypassed, loadMessages fetches from authenticated endpoint with RLS |
</threat_model>
