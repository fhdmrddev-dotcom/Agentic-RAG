# Phase 056.1 Plan 02: tool_preparing Frontend Wiring Summary

tool_preparing SSE event wired through frontend stack — ToolCall placeholder created with status "preparing" as soon as tool name is known, upgraded to "running" when tool_start arrives, eliminating the silence window in ToolCallPanel.

## Objective

Wire the `tool_preparing` SSE event (emitted by Plan 01 backend changes) through the frontend: add the `"preparing"` status to the ToolCall type, add `onToolPreparing` to `streamMessage()`, and implement the preparing/upgrade logic in `useMessages`.

## What Was Built

### Task 1 — ToolCall type extension

- Extended `ToolCall.status` union: `"running" | "done" | "interrupted" | "preparing"`
- Added optional `id?: string` field (second property, after `name`) for `"preparing-{index}"` placeholder ids
- Fixed pre-existing indentation inconsistency on `name` property (was missing leading spaces)

### Task 2 — api.ts onToolPreparing

- Inserted `onToolPreparing?: (name: string, index: number) => void` parameter immediately before `onToolStart` in `streamMessage` signature (line 105)
- Added SSE dispatch branch `else if (parsed.type === "tool_preparing" && onToolPreparing)` before the `tool_start` branch (line 165–166)
- Parameter is optional — all existing call sites that omit it continue to compile without changes

### Task 3 — useMessages preparing/upgrade logic

Three changes:

1. **onToolPreparing callback** — inserted before onToolStart in the streamMessage call:
   - Creates a `ToolCall` with `id: "preparing-{index}"`, `status: "preparing"`, `args: {}`, `startedAt: undefined`
   - Deduplication guard: if a preparing entry for the same tool name already exists, skip (handles SSE replay)
   - Sets `isPlanning: false` on the message

2. **onToolStart upgrade-first logic** — replaced the always-append pattern:
   - `findIndex` looks for entry with `name === name && status === "preparing"`
   - If found: upgrades in place with `args`, `status: "running"`, `startedAt: Date.now()` (preserves ordering)
   - If not found: appends new running entry (fallback for reconnect/race conditions)

3. **Finally block preparing cleanup** — changed `hasRunning` guard to `hasActiveTools`:
   - Now marks both `"running"` and `"preparing"` entries as `"interrupted"` when user stops stream
   - Prevents dangling preparing entries after user abort
