# Phase 44: SSE & Stop Reliability — Plan 01

**Date:** 2026-04-23
**Complexity:** Medium
**Estimated Duration:** 2-3 hours
**Wave:** 1 (single wave — backend changes and frontend changes are independent but should ship together)

---

## Context

The SSE streaming system has three reliability issues documented in `PROJECT.md` and the v2.4 REQUIREMENTS:

1. **STREAM-01** — Clicking "Stop" leaves "Saving response..." text visible in the UI. The backend continues processing after client disconnect (LLM calls, tool execution) until the next `yield` surfaces the `GeneratorExit`. The frontend aborts the fetch, sets `isStreaming=false`, but the optimistic assistant message retains its temp ID and shows "Saving response..." until a reload.

2. **STREAM-02** — Navigating away or refreshing during an active stream causes `socket.send() raised exception` server errors. The Starlette `StreamingResponse` does not suppress these log errors when writing to a disconnected client.

3. **STREAM-03** — Partial responses ARE persisted via the `finally` block in `event_stream()`, but the frontend never replaces the optimistic temp-ID message with the DB-persisted version after a stop. A page reload shows the partial message (because the backend saved it), but the current session shows a temp message with stale data.

---

## Root Cause Analysis

### STREAM-01: "Saving response..." linger

The `MessageItem.tsx` line 109 shows "Saving response..." when `!isStreaming && hasAnyTools && !message.content`. After `stopStreaming()`:
1. Frontend: `abortController.abort()` → `streamMessage` catches `AbortError` and returns → `finally` block sets `isStreaming=false`
2. The optimistic assistant message may have tool_calls but no `content` if the stream was stopped during tool execution
3. The `finally` block in `useMessages.ts` (lines 241-251) only reloads from DB if `!lastMsg.content`, which IS set during streaming deltas — so the reload doesn't fire for partial text
4. The optimistic message stays with its temp ID, never replaced by the DB version
5. `MessageItem` renders "Saving response..." because `!isStreaming && hasAnyTools` is true but `content` hasn't been replaced

Even when content IS present, the message is never reconciled with the DB-persisted version. The user sees whatever was streamed, which is correct behavior — but "Saving response..." should never appear after a user-initiated stop.

### STREAM-02: Socket errors

When the client disconnects mid-stream, Starlette's `StreamingResponse` continues trying to write to the response. The ASGI transport raises `AssertionError` or logs `socket.send() raised exception` when writing to a closed connection. The backend `event_stream()` generator catches `GeneratorExit` in `finally`, but standard Starlette doesn't suppress the transport-level errors.

### STREAM-03: Partial message visibility

The backend `finally` block correctly calls `_persist_assistant_message()`, so partial content IS saved to the database. But the frontend `finally` block only triggers `loadMessages()` when content is empty. When the user stops with partial text, the optimistic message stays in state. On page reload, `loadMessages()` is called fresh and the DB-persisted message (with real `id`, `created_at`, etc.) replaces it — so this is already working for reloads.

The gap is: **in the current session**, the partial message has a temp ID and lacks DB fields. This is acceptable behavior (the content is visible), but the UX should make it clear the response was interrupted rather than "Saving response...".

---

## Goals

1. **STREAM-01**: Stop terminates immediately with no "Saving response..." text — user sees partial response with clear "stopped" indicator
2. **STREAM-02**: Client disconnect is silent — no `socket.send()` errors in server logs
3. **STREAM-03**: Partial responses are preserved on stop and visible after reload (already works via `finally` block — enhance session UX)

**Problem:** When the SSE generator yields to a disconnected client, ASGI transport raises errors that appear as noisy logs. Starlette's `StreamingResponse` does not catch these.

class SSEErrorSuppressionMiddleware(BaseHTTPMiddleware):
    """Suppress noisy socket errors when SSE clients disconnect mid-stream."""
    async def dispatch(self, request, call_next):
        response = await call_next(request)

_sse_logger = logging.getLogger("uvicorn.error")

class _SilentSSEIterator:
    """Wraps an async generator to suppress socket errors on client disconnect."""
    def __init__(self, gen):
        self._gen = gen

    def __aiter__(self):
        return self

    async def __anext__(self):
        try:
            return await self._gen.__anext__()

            if "send" in err_str or "close" in err_str or "write" in err_str:

Wait — that won't help. The real fix needs to be in the ASGI send. Let me check what Starlette does...

Actually, the idiomatic Starlette fix is straightforward. The `StreamingResponse` iterates the async generator. When the client disconnects, the next `yield` raises `GeneratorExit`. The `finally` block in `event_stream()` already calls `_persist_assistant_message()`. The `socket.send()` errors appear when Starlette tries to write to a closed socket AFTER the generator has been cleaned up.

**The actual fix:** Override the response's `__call__` to wrap the body iterator send in a try/except that catches transport errors. Create a custom response class:

In `backend/app/responses.py` (new file):

```python
import logging
from starlette.responses import StreamingResponse

logger = logging.getLogger(__name__)

class SSEStreamingResponse(StreamingResponse):
    """StreamingResponse that suppresses transport errors when SSE clients disconnect."""
    async def stream_response(self, send):
        try:
            async for chunk in self.body_iterator:
                try:
                    await send({"type": "http.response.body", "body": chunk.encode() if isinstance(chunk, str) else chunk, "more_body": True})
                except (ConnectionResetError, BrokenPipeError):
                    logger.info("SSE client disconnected during send")
                    return
        except GeneratorExit:
            logger.info("SSE generator cleaned up on disconnect")
        except Exception:
            logger.debug("SSE stream ended", exc_info=True)
        finally:
            if hasattr(self.body_iterator, "aclose"):
                await self.body_iterator.aclose()
        # Send final empty body to signal completion
        try:
            await send({"type": "http.response.body", "body": b"", "more_body": False})
        except (ConnectionResetError, BrokenPipeError):
            pass  # Client already gone
```

### Task 5: Backend — Immediate cancel endpoint (STREAM-01 enhancement)

**File:** `backend/app/api/threads.py`

**Problem:** When the user clicks "Stop", the frontend aborts the fetch. The backend only detects this on the next `yield`. If the LLM is mid-response (which can take seconds), the backend continues processing — consuming tokens and generating content that the user will never see.

**Fix:** Add a lightweight cancel endpoint and an in-memory registry of active streams. When the frontend stops a stream, it also sends a POST to `/threads/{id}/cancel` to signal the backend to stop the agentic loop immediately.

Hmm, let me reconsider. The cancel endpoint approach adds complexity (a module-level dict, a new API endpoint, thread ID tracking in the stop function). The `GeneratorExit` approach in `event_stream()` already ensures partial messages are persisted.

**Reconsidering: Is a cancel endpoint worth the complexity?**

Pros:
- Backend stops LLM processing immediately, saving tokens
- No lingering tool executions after user stops

Cons:
- More code, more surface area for bugs
- Module-level dict could grow if not cleaned up properly
- Requires tracking thread ID in stop function
- `GeneratorExit` on the next yield is usually fast enough (LLM delta yields happen multiple times per second)

**Decision: Skip the cancel endpoint for v2.4.** The `GeneratorExit` mechanism works well enough for SSE streams — the backend will stop within 1-2 LLM token yields (typically <500ms). The main issues (STREAM-01, STREAM-02, STREAM-03) are all frontend-side UX problems, not backend latency problems. The cancel endpoint can be added later if latency becomes an issue.

**Revised Task 5: Remove from plan — GeneratorExit is sufficient for now.**
