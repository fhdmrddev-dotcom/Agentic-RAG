## Decisions

**D-200.1-01 — both (a) and (b) taken, no migration.** Recorded IN THE SOURCE, in
`phase_output_object`'s docblock, in the module's own voice — with two **named** re-open
triggers so neither deferral is a silence:

- **Sibling columns:** `workflow_runs.inputs` (230/230 string) and
  `workflow_definitions.definition` (261/291) are untouched, and this is **proved** by fences
  against the base blob, not promised. Trigger carried forward verbatim: *the next phase that
  touches either on the WRITE path.* `output` was repairable alone precisely because it already
  had two shapes in it (527 string vs 61 object, the object rows being
  `pending`/`cancelled`/`skipped`) and because (a) now creates migration 123's own stated
  condition — *"one reader that already accepts BOTH shapes."*
- **No migration:** the read repair reaches every historical row, so a migration buys nothing the
  read does not, while a blind `#>> '{}'`-then-`::jsonb` cast over 527 rows of model-influenced
  content is strictly more risk than the two-row case migration 123 was written for. Trigger:
  *the first phase that needs `output` queryable IN SQL* — a `->> 'text'` predicate, an index, or
  a feed's `WHERE`/`ORDER BY` — because SQL sees the raw column and never this helper.

**The F7 resume-path finding, recorded not fixed.** `load_run_phases` SELECTs `output`, and
`harness_engine.py`'s resume re-fold reads `r.get("output") or {}` into a `dict[str, dict]`. On a
string-scalar row the codec returns a Python `str`, so **the resumed run's grounding re-fold has
been folding STRINGS** — the same silent degradation in a THIRD consumer, and why downstream
`isinstance` guards have been quietly falling through. (b) repairs NEW rows only; the 527
historical ones are outside RUN-04. Written into `complete_phase`'s docstring with the trigger
*the next phase that touches the resume path or the startup sweep*, and pinned by a test so it
cannot be deleted quietly.
