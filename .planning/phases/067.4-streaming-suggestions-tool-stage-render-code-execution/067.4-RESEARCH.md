#### The OpenAI reasoning-token quirk

`gpt-5.4-mini` is in OpenAI's GPT-5+ family which uses `max_completion_tokens` as the unified budget for BOTH:
- Visible response content
- Internal reasoning tokens (chain-of-thought, NOT returned in `content`)

When the model decides to "think" before answering (which is the default for any non-trivial prompt — and even our 3-instruction system prompt with a 2000-char Q&A context qualifies), it consumes some/all of the 200 token budget on reasoning. If reasoning tokens hit the cap, the model returns with `finish_reason="length"` and `content=""` (empty visible output). [VERIFIED: openai-python SDK 2.0+ docs and OpenAI platform error-codes reference]

That is the **highest-probability sub-cause for the empty-output branch (b)** in D-067.4-R3-01. The Plan 04 instrumentation captures the empty branch via `logger.info("suggestions empty for run %s — generate_suggestions returned []", run_id)` at `threads.py:2502-2508`. The fix is to bump the budget to 2000 (OR swap to `gpt-4.1-mini` — non-reasoning, which fits in 200 tokens easily).

The 067.3 disconfirmed retest (200→800) is consistent with this: 800 tokens is still tight for a reasoning model under the right prompt — particularly when the agent's full response content is forwarded as "Assistant replied: ..." (which can include `tool_calls` traces). 2000 is the empirically-safer threshold for `gpt-5.4-mini` based on community reports. [CITED: OpenAI community discussion — multiple threads on `gpt-5.4-mini` empty-content with sub-1k `max_completion_tokens`]

#### Where R-4 likely IS

The remaining write paths in `useMessages.ts` are OUTSIDE the factory:

1. **`sendMessage` finally block (lines 834-894):** Multiple `setMessagesForThread(threadId, ...)` calls (clear `isPlanning`, mark interrupted tools, apply `stopped` flag). All correctly bucket-targeted.

2. **`sendMessage` catch block (lines 822-833):** `setMessagesForThread(threadId, prev => ...)` for `runStatus: "failed"`. Correctly bucket-targeted.

3. **`stopStreaming` callback (lines 452-470):** Reads from `messagesRef.current`; `messagesRef` is updated via the useEffect at lines 446-450 with `streamingThreadIdRef.current ?? activeThreadIdRef.current`. **Potential lag:** the useEffect fires on `messagesByThread` dep, but if `streamingThreadIdRef` hasn't been re-pointed when stop fires immediately after thread-switch, `messagesRef.current` may have wrong bucket.

4. **`reconcile` (lines 910-1106):** Uses `messagesByThreadRef.current.get(threadId)` (line 952) — that's a ref-mirror updated via the useEffect at lines 385-387. **Potential lag:** ref updates after state setter in the same React batch; on a fresh thread switch firing reconcile, the ref may be one tick behind.

5. **The reconcile-trigger useEffect in `ChatArea.tsx:163-188`:** fires on mount/focus/visibilitychange/pageshow. CONTEXT.md flags that "concurrent thread navigation earlier in the session may have left per-thread refs in a state this code path does not recover from until refetch." — meaning a sequence like (i) start Thread A code-execution, (ii) switch to Thread B mid-stream, (iii) switch back to Thread A → reconcile re-attaches subscribers, but `tool_end` events arriving in the brief window may not yet land in the bucket UI is observing.

### 3.1 OpenAI Python SDK 2.0+ exception classes

[VERIFIED via search; SOURCE: github.com/openai/openai-python + platform.openai.com/docs/guides/error-codes]

Inheritance hierarchy (simplified):
```
openai.APIError                         (base)
├── openai.APIConnectionError           (network — DNS, refused conn)
│   └── openai.APITimeoutError          (request timeout — distinct from our asyncio.timeout)
├── openai.APIStatusError               (non-2xx response wrapper)
│   ├── openai.BadRequestError          (400 — invalid params, model not supported with these args)
│   ├── openai.AuthenticationError      (401 — bad API key)
│   ├── openai.PermissionDeniedError    (403)
│   ├── openai.NotFoundError            (404 — model not found, route not found)
│   ├── openai.UnprocessableEntityError (422)
│   ├── openai.RateLimitError           (429 — quota / rps)
│   └── openai.InternalServerError      (5xx)
```

For R-3 narrowing at `threads.py:2509`, the canonical "narrow but cover real-world failure modes" tuple is:
```python
except (openai.APIError, openai.APIConnectionError, openai.APITimeoutError,
        openai.BadRequestError, openai.RateLimitError, openai.InternalServerError):
    logger.warning(...)
except Exception:
    logger.error(...)  # genuinely unexpected
```

### 3.2 OpenRouter cancellation contract (verified by Phase 067.1 Track A landing)

[VERIFIED: codebase — Phase 067.1 Plan 01 Track A `_drain_stream_with_close_on_cancel` ships GeneratorExit-safe cancellation for the OpenAI/OpenRouter compat path]

OpenRouter goes through the standard OpenAI-compat path (`create_adaptive_streaming_chat`). The provider client is a vanilla `openai.OpenAI` with `base_url=` set to `https://openrouter.ai/api/v1`. `Stream.close()` is sync and idempotent — no provider-specific cleanup needed.

### 3.3 llm-sandbox InteractiveSandboxSession streaming

[VERIFIED: vndee.github.io/llm-sandbox/api-reference/]

`InteractiveSandboxSession` does NOT support real-time `on_stdout`/`on_stderr` callbacks. The IPython kernel + file-polling architecture buffers output until completion. The callbacks are accepted as parameters for API compatibility but are no-ops.

`SandboxSession` (non-interactive) DOES support real-time streaming but has no state persistence between `run()` calls.

### 3.4 GPT-5 family `max_completion_tokens` reasoning quirk

[CITED: OpenAI community forum; VERIFIED in code: openai_service.py:690-703 and config.py:99-103]

For `gpt-5*` and `o1`/`o3`/`o4` models, `max_completion_tokens` is the unified budget for visible content + internal reasoning. At sub-1k budgets with non-trivial prompts, the model can return `finish_reason="length"` and `content=""` because reasoning tokens consumed the cap. Empirical safe-floor for `gpt-5.4-mini` on a short suggestion-generation prompt: 2000 tokens. For non-reasoning models (`gpt-4o`, `gpt-4.1-mini`), 200 tokens is plenty for 3 newline-delimited suggestions.
