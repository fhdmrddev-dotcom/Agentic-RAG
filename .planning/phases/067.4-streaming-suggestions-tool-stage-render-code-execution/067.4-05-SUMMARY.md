## What's broken (frontend — outside Plan 01's scope)

The SSE event arrives well-formed but the DOM never populates suggestion pills. This is a frontend rendering bug that Plan 01's CONTEXT.md explicitly stated should not need a frontend change ("frontend gate at MessageItem.tsx:93-98 already short-circuits empty arrays via `message.suggestions.length > 0`").

**Probable root cause** (hypothesis — needs Phase 067.5 investigation):

1. `assistantId` in `useMessages.ts:351-355` is closure-captured at run-start as `temp-${tempId}`.
2. When `loadMessages` runs (e.g., during `done` → DB-row arrival → `suggestions` window), the placeholder may be reconciled to the persisted DB row whose ID is the assistant message's UUID, not the `temp-` prefix.
3. The `setMessagesForThread(threadId, prev => prev.map(m => m.id === assistantId ? {...m, suggestions: questions} : m))` becomes a silent no-op because the `assistantId` no longer matches any message in the bucket.
4. The gate at `useMessages.ts:649` (`subscriptionsRef.current.has(m.runId)`) was designed to keep the placeholder alive while the SSE consumer still owns the runId — but it may be releasing too early, OR the live consumer's `assistantId` was bound to the placeholder ID before the reconcile fired.

**Likely fix surface for 067.5:**
- `frontend/src/hooks/useMessages.ts:351-355` (the `onSuggestions` handler) — replace the bare `m.id === assistantId` check with a runId-aware match that survives placeholder→DB-row reconciliation.
- Or: ensure the `loadMessages` MERGE logic at `useMessages.ts:639-651` doesn't reconcile away the placeholder until AFTER `stream_end` (i.e., until `subscriptionsRef.current.delete(runId)` has fired in `onTerminal`).
