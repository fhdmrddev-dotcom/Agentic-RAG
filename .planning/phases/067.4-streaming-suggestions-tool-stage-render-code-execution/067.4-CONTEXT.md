### D-067.4-R3-01 — R-3 investigation strategy (LOCKED)

**Decision:** Plan 01 starts with **uvicorn stdout capture** during a Fahed-Mrad search-only run. Read which Plan 04 log line fires:
- `logger.warning("suggestion generation failed for run X — main response unaffected", exc_info=True)` → exception-swallow path; the broad `except Exception:` at `threads.py:2509` is hiding a non-`NotFoundError` exception. Fix: narrow the exception class OR re-raise in a controlled way OR fix the underlying exception.
- `logger.info("suggestions empty for run X — generate_suggestions returned [] (no emit; not an error)")` → empty-LLM-output path; the LLM is returning `content=""`. Likely candidate causes: (a) reasoning-token starvation on `gpt-5.4-mini` (max_tokens budget consumed by chain-of-thought; the `max_tokens=200` config at `suggestion_service.py:75/92` is suspect — but **DO NOT re-explore the 200→800 budget bump alone**, which was disconfirmed live during 067.3 Plan 05); (b) JSON output parser miscount (function-call-style response wrapping); (c) prompt insufficiency (system prompt at `suggestion_service.py:15-20` may need tightening for reasoning-capable models).

**Fallback if uvicorn stdout is unavailable:** Plan 01 writes a focused integration test that calls `generate_suggestions(...)` directly with the captured 067.3 prompts/responses (`user_message="Search for any document about Fahed Mrad and summarize."`, `assistant_response=<the actual completed response from run_id 36b509e2-…>`). Assert non-empty return. If that test fails locally with the same `gpt-5.4-mini` model, the bug is fully in `suggestion_service.py` and can be fixed without SSE-pipeline involvement.

**Why this serves "systematic + clean close + flexibility":** Plan 04 already invested in this exact instrumentation specifically for this UAT cycle. Reading what we shipped is the cheapest evidence-first move. Adding more instrumentation is a sunk-cost trap. The fallback test gives us a deterministic local repro for whichever fix path we pick.

**Disconfirmed-hypothesis logged** (do NOT re-explore in 067.4): `max_tokens` budget bump from 200 to 800 in `backend/app/services/suggestion_service.py:75/92`. Retest run_id `00dcf270-3773-44e2-8181-6ee36169dc03` after the bump SSE still missing `suggestions` event. Root cause is elsewhere.

### D-067.4-R3-02 — Empty `[]` emit guarantee (LOCKED)

**Decision:** When `generate_suggestions(...)` returns `[]` (no exception, just empty), the backend should **still emit a `suggestions` event with `questions=[]`** so the frontend can distinguish "we tried and there are no suggestions" from "we never ran the suggestion service." Today at `threads.py:2497-2498`, the emit is gated by `if questions:` — change to always emit, even when empty.

**Frontend behavior on empty `suggestions`:** Render nothing visible (no empty pill row, no "no suggestions" placeholder), but the message record carries the truthful state. Useful for telemetry + future UX work that may want to show a "Why no suggestions?" affordance.

**Why this serves "systematic + clean close":** The current code path makes the SSE stream's "missing event" ambiguous between three states (emit happened with empty, emit didn't happen, exception swallowed). Always emitting when we know for sure the suggestion service ran cleanly removes one ambiguity dimension permanently.

### D-067.4-R3-03 — Plan 01 includes `run_in_threadpool` wrap (LOCKED, ADDED 2026-05-09)

**Decision:** Plan 01 wraps the synchronous `generate_suggestions(...)` call (currently invoked at `backend/app/api/threads.py:2488-2494` directly inside an async handler) in `fastapi.concurrency.run_in_threadpool`. The wrap is additive (~3 lines on the same line being edited for D-067.4-R3-01/02) and closes a pre-existing CLAUDE.md D-v2.5-01 violation ("no blocking I/O directly inside async handlers").

**Why included (research finding 2026-05-09):** `generate_suggestions` makes a synchronous `client.chat.completions.create(stream=False)` call (intentional — non-streaming sub-agent). It is currently invoked WITHOUT `run_in_threadpool`, so it blocks the uvicorn event loop for the suggestion-LLM round-trip duration. Plan 01 is the only 067.4 plan editing this exact line; including the wrap is cheaper than scheduling a follow-up tech-debt phase and lower-risk than amending 067.4 mid-flight if the violation surfaces during UAT.

**Why this serves "systematic + clean close":** The fix is on-the-line (no extra surface), it's covered by the same R-3 acceptance criteria (suggestion pills render after Fahed-Mrad search-only prompts), and it removes a latent class of "uvicorn worker stalls during slow OpenAI suggestion calls" bugs that would eventually surface as a different incident. Single uvicorn worker (CLAUDE.md D-v2.5-02) makes this violation more impactful, not less.

**Out of scope:** The phase does NOT audit other potential D-v2.5-01 violations elsewhere in the backend; only the line being edited by Plan 01 is in scope. A repo-wide audit is captured as a deferred idea for a future tech-debt phase.

### D-067.4-R5-01 — R-5 streaming granularity (LOCKED, AMENDED 2026-05-09)

**Decision (amended):** Plan 03 ships an **execution-progress heartbeat** — a `code_executing` SSE event emitted approximately once per second while sandbox code is running, carrying `tool_index` and `elapsed_seconds`. Per-line stdout/stderr continues to be emitted on completion via the existing `code_stdout` / `code_stderr` events (already in place at `backend/app/api/threads.py:2123-2128` and `frontend/src/hooks/useMessages.ts:257-282`).

**Why amended (research finding 2026-05-09):** `InteractiveSandboxSession` (chosen at `backend/app/services/sandbox_service.py:30` for **Python state persistence across multi-iteration code runs** — a documented agent pattern, see `SYSTEM_PROMPT` "split into multiple execute_code calls") **does NOT fire `on_stdout` / `on_stderr` callbacks during execution** (verified at vndee.github.io/llm-sandbox/api-reference/: "Not used in interactive sessions, accepted for API compatibility"). The interactive mode uses a file-based command/result queue that delivers output only on `exec_result` return. The original "line-by-line every `\n`" plan was therefore not feasible without breaking session-state persistence (Option B was rejected; Option C defer was rejected; Option A heartbeat was selected).

**Backend (additive only):**
- In `backend/app/api/threads.py` execute-code branch (around the `keepalive` branch at `~2110` of the existing `sandbox_queue` drain loop), add a heartbeat tick: every ~1 second elapsed since last emit, push `{"type": "code_executing", "tool_index": N, "elapsed_seconds": float}` into `sandbox_queue`; the existing drain loop emits via `_emit(redis, run_id, 'code_executing', ...)`.
- The dead `on_stdout` / `on_stderr` callbacks at `threads.py:2014-2024` MAY be deleted as part of Plan 03 (they accept-and-discard for the interactive session — non-functional clutter), but deletion is OPTIONAL and must not change any other behavior; the simpler cut is to leave them in place and add the heartbeat.
- Existing post-completion line emit at `threads.py:2123-2128` is preserved unchanged.

**Frontend (additive only):**
- Add a handler in `frontend/src/hooks/useMessages.ts` for `code_executing` events that updates `tool_calls[N].elapsed_seconds: number` on the active thread's bucket (per-thread-bucket-write pattern from D-067.4-R4-01).
- `frontend/src/components/chat/ExecuteCodeBlock.tsx` renders the elapsed counter next to the existing spinner during execution (e.g., "Executing… 2.4s"). On completion, the existing `outputLines: OutputLine[]` rendering takes over (already wired — no change).

**Strictly additive constraint** — NO changes to:
- `OutputFileCard` (R-2 surface)
- `messagesByThread` shape (R-1 surface) — only one new key `elapsed_seconds` nested under `tool_calls[N]`
- `MODEL_CAPABILITIES` router (N-01 surface)
- `suggestion_service` or its emit path (R-3 surface)
- The existing `on_stdout` / `on_stderr` queue plumbing (kept in place; the interactive session simply never invokes them)

**Why this serves "systematic + clean close + flexibility":** Heartbeat preserves the strictly-additive constraint, removes the user-perceived "silent thinking" without architectural risk, and matches the quality bar's "no full-duration spinner without feedback" criterion at the granularity the chosen sandbox session supports. **Flexibility:** if `llm-sandbox` later supports `on_stdout` for interactive sessions (or if the project decides multi-iteration session-state persistence is no longer needed), the per-line emit pathway is already in place — at that point, heartbeat is dropped and the frontend transparently renders true line-by-line. Backward-compatible upgrade path.

**Re-open trigger** (deferred follow-up, not blocking 067.4 closure): if (a) `llm-sandbox` releases real-time interactive-session streaming OR (b) the project drops session-state persistence, replace heartbeat with on_stdout-driven `code_output_line` events; the frontend bucket-write pattern is already proven in this phase.

### D-067.4-NR-01 — NR-067.2-11/12 OpenRouter provider-class timeout regression protocol (LOCKED)

**Decision:** Plan 04 runs the standard synthetic-timeout protocol for **two distinct OpenRouter models**. The model identifiers in legacy row labels (`moonshotai/kimi-k2.5`, `minimax/minimax-m2.7`) are **representative**, not literal — at execute time, substitute whichever OpenRouter models the user has currently configured in the model picker (provider routing rotates as upstream releases). What we're testing is the **OpenRouter provider-class** timeout-cancellation contract, not specific pinned models.

```bash
# Pick TWO distinct OpenRouter models from the live model picker
# (do NOT hard-code model names; read from the same source the chat composer uses).
OR_MODEL_A="<first OpenRouter model from current picker>"
OR_MODEL_B="<second distinct OpenRouter model from current picker>"

# Run the protocol for each:
LLM_CALL_TIMEOUT_OVERRIDES="${OR_MODEL_A}=10"
# restart uvicorn; submit long-form prompt with model=${OR_MODEL_A}
# expect: runs.status='timed_out', runs.error='timed_out: 10s per-call deadline exceeded at iteration N (model=${OR_MODEL_A})'
# (NOT GeneratorExit format)

LLM_CALL_TIMEOUT_OVERRIDES="${OR_MODEL_B}=10"
# (same protocol; substitute model)
```

**Acceptance:** Either of:
- ✅ GREEN: `runs.error` shows clean cancellation format (NOT `GeneratorExit`) for **both** OpenRouter models. Provider-class regression check passes.
- ⬜ n/a — provider unconfigured: if `OPENROUTER_API_KEY` rotated/missing at execute time. Honor the multi-provider availability rule from Phase 067.2 D-067.2-WAVE-03 — do NOT block phase closure on creds rotation.

**Capture:** Both run_ids in 067.4-HUMAN-UAT.md Evidence fields for future audit. Record the actual model IDs used (not just "row 11" / "row 12") so the audit trail survives upstream model rotations.

**Why "representative-not-literal":** OpenRouter is intentionally the flexible provider in the registry — the model list rotates as upstream releases. The contract we're locking is "OpenRouter timeout cancellation produces clean format", which is invariant across model rotations. A literal kimi-k2.5/minimax-m2.7 lock would silently rot when those models retire. Provider-class testing is the right granularity.
