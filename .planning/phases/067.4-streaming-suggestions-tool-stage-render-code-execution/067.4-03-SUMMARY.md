### Auto-fixed Issues

**1. [Rule 3 — Blocking issue] `tool_index` was not in scope at the drain loop**

- **Found during:** Task 2 — when applying the verbatim PATTERNS.md "Target shape for Plan 03 R-5 heartbeat" code, the heartbeat emit references `tool_index` which the planning text said was "already in scope … set inside the `for tool_call in pending_tool_calls:` loop earlier."
- **Issue:** Static audit of `threads.py` at execution time showed the loop is `for tc in tool_calls:` (no `enumerate`, no `tool_index` variable). A naive `tool_index=tool_index` reference would cause a `NameError` at runtime and a stricter Python linter would flag it before that.
- **Fix:** Changed the loop signature `for tc in tool_calls:` → `for tool_index, tc in enumerate(tool_calls):` at line 1722 (added an inline comment block explaining the deviation). The body of the loop (~600 lines) does not otherwise reference an index, so this is a minimal, additive change that makes `tool_index` available in the heartbeat scope ~400 lines downstream.
- **Files modified:** `backend/app/api/threads.py` (loop signature + 7-line comment block).
- **Commit:** `32c0343` (folded into Task 2's single cohesive feat commit per the plan's "single commit" stipulation).
- **Why this is Rule 3 (not Rule 4):** The fix doesn't restructure databases / services / architecture; it's a 1-line loop signature change preserving every other contract. The plan's stated heartbeat must-have (`code_executing` carrying `tool_index`) cannot be satisfied without `tool_index` being in scope — making it a blocking issue, not an architectural decision.

**2. [Rule 3 — Test signature alignment] sendMessage call uses 2-arg form**

- **Files modified:** `frontend/src/__tests__/hooks/useMessages.test.ts`.
- **Commit:** `804dc5a`.
- **Why this is Rule 3:** Test would not type-check / not run; trivial 1-arg → 2-arg correction; no architectural decision.
