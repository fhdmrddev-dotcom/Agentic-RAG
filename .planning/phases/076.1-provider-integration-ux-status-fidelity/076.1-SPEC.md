# Phase 076.1: Provider Integration + UX Status Fidelity — Specification

**Created:** 2026-05-25
**Ambiguity score:** 0.17 (gate: ≤ 0.20)
**Requirements:** 13 locked

## Goal

The agent run always feels alive (streaming code visible during TTFT gaps, accurate status labels, failure reasons surfaced) and DeepSeek is directly integrated as a first-class provider with its own API key, sub-agent defaults, and Settings UI tab — eliminating the OpenRouter latency/reliability tax observed during monitoring.

## Background

A 3-hour cross-provider monitoring session (2026-05-25, 6 providers) revealed two categories of issues:

**UX Status Fidelity:** The 075.x streaming phase series built solid plumbing — `tool_args_progress` events fire at 256-byte boundaries (migration 049), `argsCodeText` is cached in StreamsProvider, and `ExecuteCodeEditorInset` renders Shiki-highlighted code during `preparing` state (ToolCallPanel.tsx:717-719). But the user sees "Thinking..." at the bottom of the screen while the code preview renders above the viewport inside the tool panel. Result: 30s-267s of perceived silence per TTFT gap across all providers. The Sonnet 4.6 run (best output at 573KB/19 slides) was nearly abandoned because the UI looked stuck for 4+ minutes. Competitive UX research (Claude.ai, ChatGPT, Gemini, Kimi.ai) confirms streaming text IS the progress indicator — no major platform uses timers or progress bars during generation.

**Provider Architecture:** OpenRouter adds latency multiplier (DeepSeek: 24min/893K tokens) and reliability issues (Kimi: tool parse failure, MiniMax: output truncation). DeepSeek V4 Pro succeeded via OpenRouter but consumed 893K tokens because the sub-agent used the main model (no sub-agent default for OpenRouter). DeepSeek has an OpenAI-compatible direct API at `api.deepseek.com`. The existing architecture (`_PROVIDER_BASE_URLS` + `MODEL_CAPABILITIES` + `openai_service.py` base_url switching) already supports adding new OpenAI-compat providers mechanically.

**Prior failure context:** Commit `0dce56a` tried adding planning SSE events + system prompt narration rules + `planningHint` field — ALL REVERTED in `61e5eb1` because it caused heavy React re-renders, text/code leakage to UI, chat barely scrollable. Lesson: don't add more events/fields. Better utilize existing signals.

## Requirements

1. **Auto-scroll to active tool**: When `tool_preparing` fires for any tool (especially `execute_code`), the chat viewport auto-scrolls to keep the tool panel body visible.
   - Current: No auto-scroll on `tool_preparing`. The tool panel renders inside the RunCard body but the user's viewport stays at the bottom where "Thinking..." sits. During 30-267s TTFT gaps, the streaming code preview is invisible.
   - Target: When `tool_preparing` creates a new tool entry, the viewport scrolls to show the tool panel body (where `ExecuteCodeEditorInset` or `ToolArgsLivePanel` renders). The user watches code stream line-by-line — the moving cursor is the alive signal.
   - Acceptance: During a GPT 5.4 DBA PPTX generation run, the `execute_code` tool panel with streaming code is visible within 2s of `tool_preparing` firing. The user does NOT see static "Thinking..." for the duration of code generation.

2. **Differentiate "generating code" from "executing code"**: The status label on `execute_code` tool cards distinguishes the two states.
   - Current: Both `preparing` (model generating code args) and `running` (sandbox executing code) show similar visual treatment. Status text says "Preparing execute_code..." during generation and the pill changes at `tool_start`, but the distinction is not obvious.
   - Target: `preparing` state shows "Generating code" (or similar) with the streaming code preview as the primary visual. `running` state shows "Executing code" with stdout/stderr output. The transition from generating→executing is visually distinct.
   - Acceptance: Chrome MCP screenshot during `preparing` shows "Generating code" label. Screenshot during `running` shows "Executing code" label. Labels are different strings, not just badge color changes.

3. **Replace "queued" with elapsed indicator**: The "NEXT planning next step... queued" footer shows an active signal when the LLM call is actually in progress.
   - Current: RunCard.tsx:273-284 shows "queued" suffix on the footer during inter-iteration gaps. The word "queued" is misleading — the LLM call is ACTIVE (tokens may be streaming), not queued.
   - Target: When delta events are arriving (LLM is actively streaming), replace "queued" with an elapsed timer or active spinner. When no deltas are arriving (genuine wait), show "waiting..." or keep "queued".
   - Acceptance: During an active LLM call, the footer shows an elapsed counter (e.g., "8s") or active spinner instead of the static "queued" label.

4. **Surface failure reason on failed runs**: When a run fails, the UI shows WHY — not just "failed" with zero explanation.
   - Current: `runs.error` column stores the error string (written by `db/runs.py:finalize_run`). Frontend receives `kind === "error"` terminal event but does NOT surface the error reason. UI shows "✗ failed" badge with Resume button — no tooltip, no detail.
   - Target: Failed runs show the error category (timeout, code error, truncation, model limit) in the RunCard collapsed header or as a tooltip on the failure badge. Error read from `runs.error` via existing `/threads/{id}/messages` or `/threads/{id}/snapshot` data — no new SSE fields needed.
   - Acceptance: After a MiniMax-style failure (output truncation), the UI shows something like "failed — output truncated" instead of just "failed". After a timeout, shows "failed — timed out after Ns".

5. **Text dedup for repeated narration**: Consecutive identical paragraphs in assistant messages are collapsed to a single occurrence at render time.
   - Current: Pure `content += delta` concatenation at StreamsProvider.tsx:253. Anthropic Sonnet 4.6 and DeepSeek V4 Pro both emit the same planning text 4x between tool iterations (e.g., "Now I have all the content. Let me load the PPTX skill..." repeated verbatim). All 4 copies render in the message.
   - Target: Before rendering message content in MessageItem, consecutive identical paragraphs (split by `\n\n`) are collapsed to single occurrence. Raw data in StreamsProvider preserved — dedup is display-only.
   - Acceptance: An Anthropic Sonnet run that produces 4x repeated narration (observed in monitoring) displays each narration paragraph exactly once. The 4x repetition visible in the raw `message.content` does not appear in the rendered output.

6. **Sticky elapsed timer**: A minimal elapsed timer remains visible during active runs regardless of scroll position.
   - Current: Elapsed timer exists in RunCard header (Phase 075) but scrolls offscreen when the user reads sub-agent output or code panels below.
   - Target: During active runs, a compact elapsed indicator (timer + step count) is visible at a fixed position (e.g., above the input box, or as a sticky RunCard header) regardless of scroll position.
   - Acceptance: While scrolled to the bottom of a long sub-agent extraction panel, the elapsed timer is still visible on screen.

7. **Google atomic args honest UX**: Google's SDK delivers tool args atomically (no progressive streaming). The UI handles this honestly.
   - Current: Google runs show the same "Thinking..." / "queued" labels as progressive-streaming providers, but no `tool_args_progress` events fire (atomic delivery). The code panel "pops in" all at once when `tool_start` fires.
   - Target: For providers with atomic tool arg delivery (Google), the `preparing` state shows "Waiting for model..." with a visible elapsed counter instead of the byte-count badge. No empty code panel.
   - Acceptance: During a Google Gemini run, the `preparing` state does NOT show an empty code panel or "0.0 KB" badge. Shows "Waiting for model..." or equivalent honest label with elapsed counter.

8. **Running file count for multi-batch runs**: Multi-batch code generation (Sonnet's 4-batch pattern) shows cumulative file output count.
   - Current: Each `execute_code` call is a separate tool card. No cumulative file count across batches. User can't tell they're on "batch 2 of 4."
   - Target: When multiple `execute_code` tool calls complete in the same run, a cumulative output file count is visible (e.g., "3 files" growing to "6 files" to "11 files"). Exact batch numbering (2/4) is out of scope — the model doesn't announce how many batches it plans.
   - Acceptance: During a Sonnet multi-batch run, the RunCard header or a visible indicator shows a file count that grows as each batch completes.

9. **DeepSeek direct provider integration**: DeepSeek models route through `api.deepseek.com` directly instead of OpenRouter.
   - Current: `deepseek/deepseek-v4-pro` is in MODEL_CAPABILITIES with `provider: "openrouter"`. All DeepSeek models route through OpenRouter, which adds latency and costs 893K tokens for a single PPTX run because the sub-agent uses the main model.
   - Target: New `provider: "deepseek"` entries in MODEL_CAPABILITIES. `_PROVIDER_BASE_URLS["deepseek"] = "https://api.deepseek.com/v1"`. `_SUB_AGENT_MODEL_DEFAULTS["deepseek"] = "deepseek-chat"`. `DEEPSEEK_API_KEY` env var. OpenAI-compat routing through existing `openai_service.py`.
   - Acceptance: With `DEEPSEEK_API_KEY` set, selecting a `deepseek-*` model in Settings routes through `api.deepseek.com` (verified by backend log or LangSmith trace showing base_url). Sub-agent uses `deepseek-chat` (not the main model).

10. **DeepSeek Settings UI tab**: DeepSeek appears as a selectable provider in the Settings model picker.
    - Current: Settings UI has tabs/groups for OpenAI, Anthropic, Google, OpenRouter, Ollama. No DeepSeek entry.
    - Target: A "DeepSeek" provider option appears in the Settings UI. Selecting it shows DeepSeek-specific models and an API key field. The selected model routes through the direct API.
    - Acceptance: User can navigate to Settings → select DeepSeek as provider → enter API key → select a DeepSeek model → return to chat and use it. The model appears in the model selector dropdown.

11. **DeepSeek timeout profile**: DeepSeek models get appropriate timeout defaults reflecting observed behavior.
    - Current: `deepseek/deepseek-v4-pro` has `llm_call_timeout_seconds: 900` (set during monitoring). No other DeepSeek models registered.
    - Target: At least `deepseek-v4-pro` and `deepseek-chat` registered in MODEL_CAPABILITIES with appropriate timeouts (900s for pro, 120s for chat) and `max_output_tokens` values.
    - Acceptance: `get_model_capability("deepseek-v4-pro")` returns `provider: "deepseek"`, `llm_call_timeout_seconds: 900`, `max_output_tokens: 65536`. `get_model_capability("deepseek-chat")` returns sane defaults.

12. **OpenRouter fallback preserved**: Models not matched to a direct provider still route through OpenRouter.
    - Current: Unknown models with `/` in the ID (e.g., `moonshotai/kimi-k2.6`) route to OpenRouter via the regex inference at config.py:209-298.
    - Target: The existing OpenRouter fallback is unchanged. Models without a direct provider entry still route through OpenRouter. No regression for existing OpenRouter users.
    - Acceptance: `get_model_capability("moonshotai/kimi-k2.6")` still returns `provider: "openrouter"`. Existing OpenRouter models work without configuration changes.

13. **No new SSE event types or fields**: The UX improvements use only existing SSE vocabulary.
    - Current: SSE events include `tool_preparing`, `tool_args_progress`, `tool_start`, `tool_end`, `stream_end`, `delta`, `iteration_start`, `code_output_line`, etc.
    - Target: Zero new SSE event types. Zero new fields on existing SSE events. All UX improvements are frontend-rendering changes reading existing data, or backend config changes for provider routing.
    - Acceptance: `git diff` of backend SSE emission code (threads.py, openai_service.py, anthropic_service.py, google_service.py) shows zero new event types and zero new fields added to existing events.

## Boundaries

**In scope:**
- Auto-scroll to active tool panel on `tool_preparing` (frontend)
- Status label differentiation: "Generating code" vs "Executing code" (frontend)
- Replace "queued" with elapsed indicator when LLM is active (frontend)
- Failure reason surfacing from existing `runs.error` column (frontend read, no backend SSE changes)
- Render-time text dedup for consecutive identical paragraphs (frontend utility)
- Sticky elapsed timer visible regardless of scroll (frontend)
- Google atomic-args honest "Waiting for model..." UX (frontend)
- Running file count across multi-batch tool calls (frontend)
- DeepSeek direct provider: MODEL_CAPABILITIES + _PROVIDER_BASE_URLS + _SUB_AGENT_MODEL_DEFAULTS + env var (backend)
- DeepSeek Settings UI tab/group in model picker (frontend)
- DeepSeek timeout profile + model registry entries (backend config)

**Out of scope:**
- Kimi/Moonshot direct integration — deferred to SEED-031 follow-on (untested via direct API, failed even via OpenRouter)
- MiniMax direct integration — deferred to SEED-031 follow-on (untested via direct API, failed via OpenRouter)
- GLM/Zhipu direct integration — deferred to SEED-031 follow-on (never tested)
- Per-provider system prompt sections — separate concern, belongs in a system-prompt quality phase
- Per-provider iteration limits — current 15/8 defaults work; tuning is a separate concern
- Backend text dedup (SSE-level) — render-time dedup is sufficient; backend changes would touch 4 service files for marginal benefit
- threads.py changes — avoid G-5 hot-file debt; failure reason read from existing `runs.error` via data fetch
- New SSE event types or fields — reverted commit 0dce56a proved this approach fails
- Side panel / split-view architecture — major layout change out of scope; auto-scroll is the lightweight fix
- `batch N of M` progress indicator — model doesn't announce batch count; show cumulative file count instead

## Constraints

- **No new SSE events or fields** — hard constraint from reverted commit 0dce56a experience
- **No threads.py modifications** — G-5 hot-file guardrail fires (9+ phases); failure reason read from existing data paths
- **Reuse openai_service.py for DeepSeek** — same OpenAI-compat base_url pattern used by Google/Anthropic/OpenRouter
- **Frontend render-time dedup only** — no backend dedup (touches 4 service files), no streaming-layer dedup (fragile at token granularity)
- **DeepSeek only for provider scope** — Kimi/MiniMax/GLM deferred to reduce UAT surface

## Acceptance Criteria

- [ ] During `execute_code` tool arg generation, the viewport auto-scrolls to show the tool panel with streaming code within 2s of `tool_preparing` firing
- [ ] `execute_code` tool cards show "Generating code" during `preparing` state and "Executing code" during `running` state — different labels verified via Chrome MCP screenshot
- [ ] RunCard footer shows elapsed counter or active spinner instead of static "queued" when LLM call is active
- [ ] Failed runs display error reason from `runs.error` (e.g., "failed — timed out") instead of just "failed"
- [ ] Anthropic/DeepSeek runs with 4x repeated narration render each paragraph exactly once (dedup verified visually)
- [ ] Elapsed timer is visible on screen while scrolled to bottom of a long sub-agent panel
- [ ] Google Gemini runs show "Waiting for model..." with elapsed counter during `preparing` (no empty code panel or "0.0 KB")
- [ ] RunCard header or indicator shows cumulative file count growing during multi-batch runs
- [ ] DeepSeek models route through `api.deepseek.com` (not OpenRouter) when `DEEPSEEK_API_KEY` is set — verified via backend log
- [ ] DeepSeek sub-agent uses `deepseek-chat` (not main model) — verified via LangSmith trace or backend log
- [ ] DeepSeek appears as a selectable provider in Settings UI with API key field and model list
- [ ] OpenRouter fallback unchanged — `moonshotai/kimi-k2.6` still routes to OpenRouter
- [ ] `git diff` of backend SSE emission code shows zero new event types and zero new fields

## How we'd know this failed

- User still sees static "Thinking..." for >10s during execute_code TTFT gaps (auto-scroll didn't work or code preview isn't visible)
- DeepSeek direct API produces different behavior than OpenRouter (tool calling format mismatch, streaming chunk shape differences)
- Text dedup falsely collapses non-duplicate content (e.g., intentionally repeated code examples)
- Auto-scroll fights with user manual scrolling (user scrolls up to read, viewport yanks back down)
- Sticky timer introduces layout jank or covers content
- Failure reason shows raw exception text (e.g., Python traceback) instead of user-friendly category
