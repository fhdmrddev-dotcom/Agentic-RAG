# Phase 076.1: Code Review Report

**Reviewed:** 2026-05-25T12:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 076.1 adds four direct OpenAI-compatible LLM providers (DeepSeek, Moonshot/Kimi, MiniMax, GLM/Zhipu) to the backend registry, settings UI, and model capability tables. On the UX side, it adds a sticky timer bar above the input, error categorization for failed runs, render-time paragraph dedup, auto-scroll to preparing tool panels, a "Waiting for model..." honest UX for atomic-delivery providers, file count badges, and `runError` propagation from SSE terminals through to the RunCard display.

The changes are well-structured and consistent across all layers (backend config, settings model, Settings UI, StreamsProvider, RunCard, types). The primary concerns are a logic bug in the RunCard file count filter, a missing `FieldRow` prop type, and a potential scroll performance issue from a duplicate useEffect dependency pattern.

## Warnings

### WR-01: RunCard fileCount includes "running" status tools -- likely wrong

**File:** `frontend/src/components/chat/RunCard.tsx:100`
**Issue:** The `fileCount` reducer in RunCard filters for `tc.status === "done" || tc.status === "running"`, but the identical logic in the `StickyTimerBar` component in ChatArea.tsx:437 filters for `tc.status === "completed" || tc.status === "done"`. A "running" tool call has not completed execution yet, so parsing its `tc.result` for `output_files` is premature -- the result field is not populated until `onToolEnd` fires. This is a logic error that will not cause a crash (JSON.parse of undefined/null is caught) but represents an inconsistency between two components counting the same metric. Additionally, `StickyTimerBar` checks for `"completed"` which is not a valid `ToolCall.status` value per `frontend/src/types/index.ts:28` (the enum is `"running" | "done" | "interrupted" | "preparing"`), so that filter arm is dead code.
**Fix:**
```typescript
// RunCard.tsx:100 — change "running" to only "done"
const fileCount = (message.tool_calls ?? []).reduce((sum, tc) => {
  if (tc.status === "done" && tc.result) {
    try {
      const parsed = JSON.parse(tc.result)
      if (parsed.output_files) return sum + parsed.output_files.length
    } catch { /* not JSON or no output_files key */ }
  }
  return sum
}, 0)
```
```typescript
// ChatArea.tsx:437 — fix the dead "completed" check to match ToolCall.status enum
const fileCount = toolCalls.reduce((sum, tc) => {
  if (tc.status === "done" && tc.result) {
    // ...
  }
  return sum
}, 0)
```

### WR-02: StickyTimerBar completedCount uses invalid "completed" status value

**File:** `frontend/src/components/chat/ChatArea.tsx:430`
**Issue:** `completedCount` filters for `tc.status === "completed" || tc.status === "done"`. The `ToolCall.status` type (defined in `frontend/src/types/index.ts:28`) has four valid values: `"running" | "done" | "interrupted" | "preparing"`. The string `"completed"` never appears on a `ToolCall.status` -- it only exists on `Message.runStatus`. This means the `"completed"` arm of the filter is dead code and `completedCount` only matches `"done"`. The step number will be correct in practice (all finished tools are `"done"`), but the dead branch indicates a copy-paste error from `runStatus` logic and could mislead future maintainers.
**Fix:**
```typescript
// ChatArea.tsx:430 — remove the dead "completed" check
const completedCount = toolCalls.filter(tc => tc.status === "done").length
```

### WR-03: Duplicate useEffect with identical dependencies fires auto-scroll twice per render

**File:** `frontend/src/components/chat/MessageList.tsx:97-106`
**Issue:** The new auto-scroll useEffect (lines 97-106) has the same dependency array `[messages, isStreaming]` as the existing auto-scroll useEffect at lines 70-88. Both effects run on every `messages` change during streaming. When a `tool_preparing` event fires, both effects execute: the first scrolls `bottomRef` into view (line 80-81 or 86), and the second scrolls the `[data-tool-status="preparing"]` element into view (line 104). This produces two competing `scrollIntoView` calls on the same render cycle, which can cause visual jitter -- especially because one uses `"instant"` behavior and the other uses `"smooth"`. The intended target (the preparing panel) may be overridden by the bottom-scroll.
**Fix:** Merge the preparing-panel scroll into the existing useEffect, or add a condition to the bottom-scroll effect that defers to the preparing-panel scroll when a preparing tool exists:
```typescript
// In the existing useEffect at line 70, after the bottom-scroll logic:
// Check if there's a preparing tool panel that should get priority
if (isStreaming && isNearBottomRef.current) {
  const preparingEl = containerRef.current?.querySelector(
    '[data-tool-status="preparing"]'
  ) as HTMLElement | null
  if (preparingEl) {
    preparingEl.scrollIntoView({ behavior: "smooth", block: "nearest" })
    return  // Skip the bottom scroll
  }
}
```

### WR-04: KNOWN_PROVIDERS in user_settings.py duplicates _PROVIDER_BASE_URLS from config.py

**File:** `backend/app/models/user_settings.py:32-42`
**Issue:** `KNOWN_PROVIDERS` is a second source of truth for provider base URLs, duplicating the `_PROVIDER_BASE_URLS` dict in `config.py:10-20`. The Phase 075.4 decision D-075.4-B2 explicitly mandated that `_PROVIDER_BASE_URLS` be the "single source of truth for known providers" so "adding a new provider is a one-edit operation." With this phase adding 4 new providers, both dicts had to be updated (evidence: both now list all 9 providers with identical base URLs). If a future phase adds a provider to `config.py` but forgets `user_settings.py`, the Settings UI will silently omit it. This violates the D-075.4-B2 contract.
**Fix:** Derive `KNOWN_PROVIDERS` from `_PROVIDER_BASE_URLS` at module level, adding only the `name` display label locally:
```python
from app.config import _PROVIDER_BASE_URLS

_PROVIDER_DISPLAY_NAMES: dict[str, str] = {
    "openai": "OpenAI",
    "anthropic": "Anthropic",
    "google": "Google Gemini",
    "openrouter": "OpenRouter",
    "ollama": "Ollama (local)",
    "deepseek": "DeepSeek",
    "moonshot": "Moonshot (Kimi)",
    "minimax": "MiniMax",
    "zhipu": "GLM (Zhipu)",
}

KNOWN_PROVIDERS = {
    pid: {"name": _PROVIDER_DISPLAY_NAMES.get(pid, pid), "base_url": url}
    for pid, url in _PROVIDER_BASE_URLS.items()
}
```

### IN-03: FieldRow component accepts undeclared `tooltip` prop

**File:** `frontend/src/pages/SettingsPage.tsx:883`
**Issue:** The `FieldRow` component at line 31-38 has the interface `{ label: string; children: React.ReactNode }` but is called with a `tooltip` prop at line 883: `<FieldRow label="OpenRouter Tool Strategy" tooltip="How OpenRouter models...">`. The `tooltip` prop is silently ignored by React (passed as a DOM attribute but never rendered). This is not a bug (the description is provided in the child `<p>` tag instead) but the unused prop is misleading.
**Fix:** Remove the `tooltip` prop from the call at line 883, or add `tooltip?: string` to `FieldRow`'s interface and render it.

### IN-04: errorCategories.ts pattern for "auth" may match unrelated strings

**File:** `frontend/src/lib/errorCategories.ts:19`
**Issue:** The regex `/auth|401|403|invalid.*key/i` will match any error string containing the substring "auth" anywhere, including words like "unauthorized" (correct) but also "author" or "authenticate" in a non-error context. For display-time categorization this is low-risk since the input is always an error string, but the pattern could be tightened to `\bauth\b|401|403|invalid.*key` for precision.
**Fix:** Optional -- add word boundary `\b` around "auth" if false positives are observed in practice.
