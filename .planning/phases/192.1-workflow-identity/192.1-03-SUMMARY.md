## Deviations from Plan

### 1. [Rule 3 — Blocking] `libraryFork` must NOT join `PAGE_IMPORTED_MODULES`

- **Found during:** Task 3(a).
- **Issue:** Task 3(a) instructs *"Add `useWorkflowFork` and `libraryFork` to
  `PAGE_IMPORTED_MODULES`."* Measured: after the cut the page has **no remaining use** of
  `freshHash` or `isForkConflict` — both are consumed only by the two handlers, which left with
  them. The fence would therefore red permanently, and with `noUnusedLocals` ON, manufacturing a
  satisfying import is a **type error**.
- **Fix:** `useWorkflowFork` only. The fence's own docblock already states this rule in general
  terms for `WorkflowDeleteSheet` — *"Listing it here would assert a coupling that does not exist
  and would red on the correct architecture"* — and the reasoning is recorded at the entry so the
  next author does not "restore" the plan's version.
- **Commit:** `790ce24d`.

### 2. [Rule 2 — Correctness] Three acceptance greps are unsatisfiable as written

- **Found during:** Task 2.
- **Issue:** The criteria require `grep -n "setBuilderInitial\|setPageView"` and
  `grep -n "WorkflowsPage\|WorkflowBuilderPage\|BuilderInitial"` over `useWorkflowFork.ts` to return
  **nothing** — but the plan's own action text *requires* the module to document why those symbols
  are absent (the F4/`WorkflowBuilderPage` near-miss especially). A raw grep therefore reds on the
  prose that documents the rule it enforces. **This is the 187-24 trap, which this repo has now
  recorded four times** (F1 had to become AST-parsed; the `HighlightTitle` fence was written raw
  first and observed RED against exactly such a comment; Wave 1 scoped its `updatedAt` source fence
  to non-comment lines for the same reason).
- **Fix:** verified over **non-comment CODE lines**, which is the repo's own recorded resolution:

  | Probe | CODE lines |

  literal `createWorkflowDraft(` and pushed the raw count to 3 — the trap in miniature. The comment
  now DESCRIBES the client instead of spelling it, and says why, so the raw whole-file count is
  honestly **2**.

### 3. [Rule 1 — Bug] The two `console.error` prefixes pointed at the file the code left

- **Found during:** Task 2.
- **Issue:** both handlers log `"[WorkflowsPage] … fork failed"`. Emitted from
  `library/useWorkflowFork.ts`, that sends a debugger to the wrong file — the wrong-pointer failure
  D-37 guards against, one layer below prose, in the one line whose entire purpose is to help
  someone find the code.
- **Fix:** `[useWorkflowFork]`. Verified nothing binds to the strings first (no `console.error` spy
  anywhere in the fork arc; `grep` over `src/` finds only the two definitions). The line's PURPOSE
  is unchanged. Recorded at the call site so it does not read as an accident.
- **Commit:** `9383516e`.

### 5. [Scope] The notice's state moved; its render did not

The plan's `must_haves` lists *"the failure notice"* among what `useWorkflowFork.ts` provides, and
its `<interfaces>` block says the notice is *"rendered from the hook's state"*. Read as: state to
the hook, JSX to the page — which is what shipped, and is what Task 3(b) then instructs directly.
Moving the JSX would make the hook a `.tsx` and carry a page-LAYOUT decision into a module that
cannot see the region it belongs to. The markup is byte-identical to 192-15's; the reasoning is
recorded at both the old state site and the render site.
