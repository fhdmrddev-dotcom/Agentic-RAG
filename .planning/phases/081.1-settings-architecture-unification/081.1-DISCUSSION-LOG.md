## Migration safety

### Q1: When should the one-shot JSON→DB migration execute?

| Option | Description | Selected |
|--------|-------------|----------|
| Startup lifespan hook | Runs inside FastAPI lifespan handler before requests. Multi-worker safe via INSERT ... ON CONFLICT DO NOTHING. | ✓ |
| Management command | Separate script operator runs manually before deploying. | |
| First-request lazy trigger | Runs on first API request that hits the settings loader. | |

**User's choice:** Startup lifespan hook
**Notes:** Simplest for operators — just restart backend after deploy.

### Q2: What should happen if the migration fails partway through?

| Option | Description | Selected |
|--------|-------------|----------|
| Log error, keep JSON file, boot anyway | Old file-based loader stays active as fallback. Zero downtime risk. | ✓ |
| Block startup on failure | Raise exception preventing uvicorn from starting. | |
| Partial migration + retry | Write keys one-by-one, track which succeeded, retry on next boot. | |

**User's choice:** Log error, keep JSON file, boot anyway
**Notes:** Fail-safe fallback — app never breaks on a DB hiccup.

## Cache across workers

### Q3: How should settings cache work across multiple workers?

| Option | Description | Selected |
|--------|-------------|----------|
| 30s TTL per-worker | Each worker has its own in-process cache, refreshes independently. | ✓ |
| Redis pub/sub invalidation | Publish invalidation message to Redis channel, near-instant consistency. | |
| No cache — always read DB | Every settings access hits DB via asyncpg (~1-2ms with pooling). | |

**User's choice:** 30s TTL per-worker
**Notes:** Settings changes are rare admin actions — a few seconds of cross-worker drift is invisible.

### Q4: Should writes invalidate the writing worker's cache immediately?

| Option | Description | Selected |
|--------|-------------|----------|
| Invalidate on write | Zero local cache on write, response reflects change immediately. Other workers wait for TTL. | ✓ |
| You decide | Let Claude pick the best approach. | |

**User's choice:** Invalidate on write
**Notes:** None.

## Model overrides scope

### Q5: Which per-model fields should be overridable in the DB table?

| Option | Description | Selected |
|--------|-------------|----------|
| Timeout + context + output only | Three numeric fields. Simplest. Provider routing stays in static dict. | ✓ (initial) |
| All numeric + boolean fields | Also include native_tools, supports_streaming, supports_vision. | |
| Full model registration | Table becomes primary model registry with provider + all capability fields. | |

**User's choice:** Initially selected "Timeout + context + output only" but then clarified:

### Q6: Should the table support adding entirely NEW models?

| Option | Description | Selected |
|--------|-------------|----------|
| Override-only for now | Table only stores overrides for existing models. | |
| Allow new registrations | Admins can INSERT new models not in static dict. Needs provider column. | ✓ |

**User's choice:** Allow new registrations — "we should be able always to add new models and configure them smoothly and completely, everyday there's new model."
**Notes:** User explicitly stated that adding new models without code changes is essential. Minimum required: model_id + provider. Extended to include enabled (bool) and native_tools (bool) override. Everything else has sensible defaults.

### Q8: Does this phase touch the Settings menu and design?

**User's question:** "does this touch settings menu and design?"
**Answer:** Minimal frontend impact. Settings page talks to same API contract (backend just reads from DB instead of JSON). New JSONB columns are backend-only foundations for v3.1. Model picker auto-includes DB-registered models via data source expansion, not UI code change. ~95% backend phase.
