# Phase 081.1: Settings Architecture Unification - Context

**Gathered:** 2026-05-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Eliminate `backend/settings_override.json` — every non-secret value it holds today migrates to `app_settings` (global) or `user_settings` (per-user) DB tables, read through a single hot-reload cache. Secrets stay in `.env`. Creates `model_capabilities_overrides` table for per-model knobs (including full new-model registration without code changes). Foundation for v3.1 admin shell + v3.2 multi-tenancy — eliminates JSON-file drift before downstream milestones inherit it.

CLAUDE.md principle finally holds in code: "Settings live in `user_settings` / `app_settings` and the Settings UI; env vars are for secrets and infra only."

</domain>

<decisions>
## Implementation Decisions

### Migration strategy
- **D-01:** One-shot migration runs in FastAPI's **lifespan handler** (same place asyncpg pool initializes), before any requests are served. Simplest for operators — just restart backend after deploy.
- **D-02:** Multi-worker safety via `INSERT ... ON CONFLICT DO NOTHING` — whichever worker gets there first writes, the rest no-op. No locking needed.
- **D-03:** Fail-safe rollback: if any DB write fails, log error and **leave `settings_override.json` untouched** (no rename to `.migrated`). Old file-based loader stays active as fallback until next successful migration on restart. App never breaks on a DB hiccup.
- **D-04:** On success: rename file to `settings_override.json.migrated` (operator rollback artifact). Log `"Migrated N keys from settings_override.json"`.
- **D-05:** Idempotent on re-run — if no JSON file present, migration is a no-op.

### Cache architecture
- **D-06:** **30s TTL per-worker in-process cache.** Each worker has its own cache that refreshes independently from the DB. No Redis pub/sub — eventual consistency within 30s is acceptable for rare admin settings changes.
- **D-07:** **Invalidate-on-write for the writing worker.** When the Settings API writes to the DB, it zeroes out the local cache timestamp so the response reflects the change immediately. Other workers wait for their TTL.
- **D-08:** Cache pattern mirrors existing `_TTL_CACHE` at `user_settings.py:27` (extended from 5s file-cache to 30s DB-cache). All reads go through the cache; no direct DB reads in hot paths.

### Model capabilities overrides
- **D-09:** New `model_capabilities_overrides` table supports **full new-model registration**, not just overrides on existing models. Minimum required: `model_id` (PK) + `provider` (text). Everything else nullable with code-level defaults.
- **D-10:** Overridable fields: `llm_call_timeout_seconds` (INT), `context_window_tokens` (INT), `max_output_tokens` (INT), `native_tools` (BOOL), `enabled` (BOOL, default true).
- **D-11:** Resolution precedence: **DB row > static `MODEL_CAPABILITIES` dict > default**. Unknown models (not in DB, not in static dict) get safe defaults (300s timeout, 200K context, 32K output, tools=true).
- **D-12:** `LLM_CALL_TIMEOUT_OVERRIDES` env CSV stays as operator bootstrap fallback. Precedence: DB > env CSV > static dict. Documented in `.env.example` as "operator bootstrap only; prefer admin UI in v3.1+."
- **D-13:** DB-registered models automatically appear in the model picker under their provider's section — no visual distinction from built-in models. The `_build_providers` function merges static + DB model lists per provider.

### Forward-ref obligations (carried from prior phases)
- **D-14:** Phase 075.4 Plan 04's `_is_valid_api_key` sentinel guard (WR-02 defense-in-depth) MUST be ported to the new DB-backed write path. The guard prevents frontend placeholder values (`***`, `__KEEP__`, `••••••`) from overwriting real API keys.
- **D-15:** Phase 075.4 Plan 04's "2-click save" fix MUST be preserved — the new write path must not re-introduce the single-click save race.

### Key routing specifics
- **D-16:** `embedding_base_url` and `ollama_base_url` go to `app_settings` (not secrets — UI-writable endpoint addresses). Matches the "settings in DB" principle.
- **D-17:** Provider model lists (9 keys: `openai_models`, `anthropic_models`, etc.) stored as a single `provider_model_lists` JSONB column on `app_settings`. Shape: `{"openai": ["gpt-4o", ...], "anthropic": [...]}`. One column for all providers.
- **D-18:** `sub_agent_model` goes to `app_settings` as a top-level column (same level as `llm_model`). It's a single global default, not a per-model capability.

### API contract
- **D-19:** API keys stay in `app_settings` DB columns for now. Same UI flow, different backing store. v3.1 migrates to proper secrets vault later.
- **D-20:** Settings reads/writes go fully async via asyncpg pool (Phase 073). No `run_in_threadpool` wrapper needed for the new DB path.
- **D-21:** `GET /settings` and `PUT /settings` API contract stays unchanged — `FullSettingsResponse` / `SettingsUpdate` Pydantic models don't change shape. Pure backend swap; frontend sees no difference.

### JSONB column shapes
- **D-22:** Planner derives JSONB column shapes (`title_drafting_config`, `sub_agent_config`) from current hardcoded values in the codebase. User reviews at plan time, not at context time. Planner reads: title gen (model + prompt + max_tokens=30 + max_length=60 at `threads.py:1000-1016`), sub_agent (model + max_output_tokens + per-provider defaults at `config.py:465` + `sub_agent_service.py`).
- **D-23:** Scope stays tight — only the 34 keys already in `settings_override.json` migrate to DB. Agent behavior knobs (max_iterations, system prompts, confidence thresholds) stay hardcoded until v3.0/v3.1 builds admin UI.

### Model picker UX
- **D-24:** DB-registered models merged alphabetically with built-in models within each provider's section. No badges, no "Custom" label, no visual distinction. They're all just "models for this provider."
- **D-25:** Remove the `settings_override.json` subtitle from Settings page header (currently at `SettingsPage.tsx:717`). Replace with "Changes take effect immediately." — no implementation details leaked to users.

<specifics>
## Specific Ideas

- User explicitly wants new models to be addable without code changes — "every day there's a new model." The `model_capabilities_overrides` table MUST support full model registration (model_id + provider minimum), not just overrides.
- Custom models fold seamlessly into their provider's section in the model picker — no badges, no "Custom" section. Alphabetical merge.
- The table schema should be forward-compatible with v3.1 admin shell UI that will build forms on top of it.
- Settings subtitle removal: the user doesn't need to know the backing store. Just "Changes take effect immediately."

</specifics>
