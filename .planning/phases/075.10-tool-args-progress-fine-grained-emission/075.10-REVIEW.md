# Phase 075.10: Code Review Report

**Reviewed:** 2026-05-24
**Depth:** standard
**Files Reviewed:** 5

## Summary

Phase 075.10 lowers the hardcoded `5120`-byte `tool_args_progress` SSE emission boundary to a configurable default of `256` bytes across all four provider streaming paths (Anthropic native, Google native, OpenAI native, OpenRouter — last two via shared `_on_chunk_openai`). The implementation pattern is consistent across all three streaming sites:

1. Import `tool_args_progress_emit_boundary_bytes()` at the top of the stream-setup region (lazy import to break a potential module-load cycle).
2. Call ONCE per stream invocation; capture into a local `_emit_boundary_bytes`.
3. Compute `_emit_tail_bytes = max(5120, _emit_boundary_bytes * 4)` to widen the sliding-window tail proportionally.
4. Use both locals inside the per-chunk hot loop.
5. Defensive helper wraps `load_app_settings()` in try/except, clamps non-positive values, falls back to `5120` on any failure.

Migration 049 adds `chat_tool_args_progress_emit_boundary_bytes INTEGER NOT NULL DEFAULT 256` idempotently to `app_settings` — matches existing migrations 044/045/047. No RLS implication: `app_settings` is a singleton row with RLS already established in migration 010.

The plan deviation (modifying `threads.py:_on_chunk_openai` instead of `openai_service.py`) is structurally correct — the emission code lives in `threads.py` since Phase 075.6, and the diff is symmetric with the Anthropic/Google pattern.

All four hot focus areas check out: per-stream-invocation read (not per-chunk), no division-by-zero (helper clamps non-positive to fallback 5120), tail slice widening is correct, no leftover hardcoded `5120` divisors remain (the `5120` references that remain are intentional minimum tail-size floors or comments).

## Warnings

### WR-01: `tool_args_progress_emit_boundary_bytes()` called on event-loop thread in `threads.py` performs blocking file I/O on TTL miss

**File:** `backend/app/api/threads.py:2122`

**Issue:** The OpenAI/OpenRouter path invokes `tool_args_progress_emit_boundary_bytes()` directly inside the `async def agent_runner` coroutine (line 2122), not inside a threadpool worker. The helper chain is `tool_args_progress_emit_boundary_bytes()` → `load_app_settings()` → `_load_override()` → `_OVERRIDE_FILE.read_text(...)` (`backend/app/models/user_settings.py:177`). On a TTL cache miss (every 5 s) this performs a synchronous `Path.read_text()` from the event loop thread, which CLAUDE.md explicitly forbids (D-v2.5-01: "Do not run blocking I/O directly inside async handlers — wrap with `run_in_threadpool`").

By contrast, the Anthropic and Google service variants (`anthropic_service.py:205`, `google_service.py:376`) are called inside SYNC generator functions, whose first-`next()` invocation is driven from the threadpool producer in `_drain_stream_with_close_on_cancel` (line 287) — those reads are NOT on the event loop and are fine.

This is small-magnitude (a single ~50-100 µs JSON read in the worst case) and the file is local + cached, so the visible impact is negligible — but it formally violates a project rule and the path will pick up additional readers as the Settings UI grows.

**Fix:** Wrap with `run_in_threadpool` to match the project rule:
```python
from starlette.concurrency import run_in_threadpool  # already imported at line 12
from app.models.user_settings import tool_args_progress_emit_boundary_bytes  # noqa: PLC0415
_emit_boundary_bytes = await run_in_threadpool(tool_args_progress_emit_boundary_bytes)
_emit_tail_bytes = max(5120, _emit_boundary_bytes * 4)
```
Alternative (cheaper): mark the helper itself as the documented blocking-OK seam (it relies on a 5 s TTL cache so amortized cost is near-zero), and add a comment at the call site explaining the deliberate event-loop call. Either way, the current implementation should be reconciled with the D-v2.5-01 convention so future readers don't add unwrapped readers.

## Info

### IN-01: Docstring claims "clamps non-positive up to 1" but code returns 5120 fallback

**File:** `backend/app/models/user_settings.py:430-431`

**Issue:** The `tool_args_progress_emit_boundary_bytes()` docstring states:

> "Positive int byte boundary (minimum 1 — clamps any non-positive override up to 1 to avoid a divide-by-zero in the `// boundary` arithmetic)."

But the actual code (line 442-443) returns the 5120 fallback when `value is None or value <= 0`, not 1:
```python
if value is None or value <= 0:
    return _FALLBACK_TOOL_ARGS_EMIT_BOUNDARY_BYTES
```
This is a low-stakes documentation drift — the runtime behavior is actually safer than the docstring promises (5120 is a sane operational default; 1 would emit a SSE event on every byte and saturate the network). The docstring just lies about the contract.

**Fix:** Update the docstring to match the implementation:
```python
Returns:
    Positive int byte boundary (≥ 1). Returns the hardcoded pre-075.10
    fallback (5120) instead of raising when `load_app_settings()` fails,
    or when the configured value is None / ≤ 0 (defensive: avoids
    divide-by-zero in `// boundary` arithmetic and prevents an operator
    misconfig from saturating SSE bandwidth at 1-byte cadence).
```

### IN-02: Lazy import duplicated across 3 sites — consider hoisting to module top

**File:** `backend/app/services/anthropic_service.py:204`, `backend/app/services/google_service.py:375`, `backend/app/api/threads.py:2121`

**Issue:** All three sites carry the same lazy-import pattern:
```python
from app.models.user_settings import tool_args_progress_emit_boundary_bytes  # noqa: PLC0415 — avoid module-load-time cycle
```
The "module-load-time cycle" comment is the same justification three times — but `app.models.user_settings` does NOT import `anthropic_service` / `google_service` / `threads.py`, so no actual cycle exists. The pattern was likely copy-pasted from a real cycle elsewhere. The lazy import is harmless (the helper is invoked once per stream so the cost is negligible), but the rationale is incorrect documentation.

`threads.py` already top-imports `app.models.user_settings` heavily elsewhere; the inline import is just lazy convention.

**Fix:** Either (a) move the import to the top of each module to match prevailing convention, or (b) shorten the comment to "kept local for symmetry with sibling lazy imports" since the cycle claim is not load-bearing. Low priority — current state is correct, just over-commented.

### IN-03: `_emit_tail_bytes` floor of 5120 means lowering boundary below ~1280 has no effect on tail width

**File:** `backend/app/services/anthropic_service.py:211`, `backend/app/services/google_service.py:377`, `backend/app/api/threads.py:2123`

**Issue:** The formula `max(5120, _emit_boundary_bytes * 4)` keeps the tail at 5120 bytes for any boundary value `≤ 1280`. With the new default boundary of 256, the tail is `max(5120, 1024) = 5120` — meaning every emit ships 5 KB of cumulative tail context, ~20x the boundary increment. For an OpenRouter token-by-token stream of `execute_code` args spanning, say, 30 KB total, this produces ~120 emits each carrying a 5 KB payload — total SSE payload weight ~600 KB compared to ~7.5 KB if the tail tracked the boundary 1:1. Comments at lines 207-211 explicitly document this as intentional ("legacy 5120-byte tail still ships plenty of cumulative context per emit"), but no telemetry exists to verify SSE bandwidth doesn't spike for very long tool-arg streams.

This is NOT a bug — the additive `code_so_far` field (set at the same call site to `tb["arguments"]` / `tool_calls_buffer[idx]["arguments"]`) ALREADY ships the full cumulative buffer, so `args_so_far` is logically redundant for the live-code-panel use case (the consumer in 075.6 was switched to read `code_so_far`). The 5 KB tail floor is doing two jobs: (1) backward-compat for any consumer still reading the older field, (2) bandwidth safety belt.

**Fix:** No code change needed. Consider adding a 075.10 verification UAT row that measures total SSE byte count for a 30 KB tool-arg stream pre/post — Phase 075.9 already exercised SSE intercept tooling in Chrome MCP, so the rig is available. If bandwidth headroom turns out to be tight, the floor could drop to `max(boundary * 4, 1024)` in a follow-on phase.
