# 061.1-DIAGNOSIS: ERR_INCOMPLETE_CHUNKED_ENCODING root cause

**Date:** 2026-05-03
**Reproduction reference:** Phase 061 UAT, run `f4b2b8cc-c643-4107-9f4a-70e715641b63` —
SSE consumer drops with `ERR_INCOMPLETE_CHUNKED_ENCODING` and `TypeError: network error`
~11s into a 60s run with 1393 events buffered (981 of them `sub_agent_delta`). Producer
completes cleanly: `runs.status='completed'`, terminal sentinel landed, message persisted
(1114 chars).

**Investigation method:** static code analysis + bisection plan per CONTEXT D-061.1-05.
Live Chrome-MCP-driven re-reproduction was attempted but the Chrome DevTools MCP server
returned a profile-conflict error in this session (`The browser is already running for
C:\Users\fhdmr\.cache\chrome-devtools-mcp\chrome-profile`). The static analysis below
narrowed the live test set to a single hypothesis (H2) and the disposition reflects that.

---

## Hypothesis H4 — Vite dev proxy

**Method:** Read `frontend/vite.config.ts` and `frontend/src/lib/api.ts` to determine
whether the browser→backend SSE path traverses a Vite proxy.

**Observation:**
- `frontend/vite.config.ts` is 14 lines and contains exactly: `plugins: [react()]` and a
  `resolve.alias['@']`. No `server.proxy` configuration exists.
- `frontend/src/lib/api.ts:9` reads `const API_BASE = import.meta.env.VITE_API_BASE_URL`
  and uses absolute URLs (`fetch(\`${API_BASE}/threads/${threadId}/messages\`, ...)`).
- The browser issues SSE POSTs DIRECTLY to the backend at `http://localhost:8000`
  (or whatever `VITE_API_BASE_URL` resolves to). The Vite dev server at port 5173 is
  not in the request path.

**Conclusion:** REFUTED. There is no Vite dev proxy to interfere. The original CONTEXT
hypothesis was wrong about the Vite proxy being involved.

**Fix pointer:** N/A. (The bisection plan's H4 raw-curl test would have produced the
same result — confirming H4 — because the bypass is the default state, not an alternative.)

## Hypothesis H3 — sub_agent_delta volume

**Method:** Read the producer-side emission site at `backend/app/api/threads.py:1325`
(`await _emit(redis, run_id, 'sub_agent_delta', content=text_chunk)`) to characterise
emission shape, and the consumer-side XREAD loop at `backend/app/api/threads.py:2065+`
to characterise read shape.

**Observation:**
- Producer emits one XADD per text token chunk during a sub-agent round. UAT evidence:
  981 `sub_agent_delta` events in ~11s of wall-clock = ~89 events/sec sustained.
- No batching, no time-windowing, no byte budgeting on the producer side.
- Consumer reads with `count=100, block=5000` — replay phase pulls up to 100 entries
  per XREAD, tail phase blocks 5s. With 89/s arrival rate and 100/batch read, the loop
  yields ~9 batches/sec (each batch yields up to 100 SSE chunks back-to-back to
  `EventSourceResponse`).

**Conclusion:** CONTRIBUTING FACTOR (not standalone root cause). High-volume per-event
XADD + per-event SSE write creates burst patterns where the SSE writer has no flow
control between XREAD batches. By itself this would cause backpressure (slowness),
not a dropped chunked-encoding frame. But it amplifies H2 (see below): bursts make
the sse-starlette ping task more likely to race with the data-yielding generator.

**Fix pointer (if confirmed standalone):** producer-side time-windowed batching of
`sub_agent_delta` — e.g., flush every 50 events OR every 100ms OR every 4KB, whichever
fires first. Implementation site: the call site at `threads.py:1325`. Preserve
event ordering; do NOT coalesce non-sub_agent_delta events.

## Hypothesis H1 — consumer generator raise

**Method:** Inspect the `event_consumer()` closure body at `backend/app/api/threads.py:2065-2130`
for unhandled BaseException paths that would terminate the generator before yielding
the terminal sentinel.

**Observation:**
- The XREAD calls (`await redis.xread(...)`) and the JSON parse + yield body are
  inside a single `try:` whose only `finally:` is `pass` (D-061-03 — producer
  survives consumer disconnect).
- A redis-py exception (e.g., `ConnectionError`, `ResponseError`) inside `xread`
  would propagate up the generator unboxed, causing `EventSourceResponse` to send
  an unfinished chunked frame and the browser to record `ERR_INCOMPLETE_CHUNKED_ENCODING`.
- However: in the UAT reproduction the producer ran to completion AND the consumer
  read 1393 events successfully BEFORE the drop. A redis-py crash mid-loop would have
  manifested as a much earlier failure with backend logs showing the exception.

**Conclusion:** REFUTED in this reproduction (would have been observable in backend
logs as a stack trace). Possible secondary cause in other reproductions, but not the
canonical one.

**Fix pointer (defensive, regardless):** Wrap the inner XREAD-and-yield body in
`try/except BaseException as exc: logger.exception('event_consumer raised'); yield
synthetic_error_event; raise`. This is also IN-04's natural extraction site
(D-061.1-10) — the lifted module-level `event_consumer` becomes the place to add
this guard. Recommend bundling with Plan 01 Task 6.

## Hypothesis H2 — sse-starlette ping interval

**Method:** Inspect the `EventSourceResponse(event_consumer(), ping=15)` call site
at `backend/app/api/threads.py:2132`, then reason about sse-starlette's ping-task
behaviour relative to a generator that yields fast bursts followed by quiet windows.

**Observation:**
- `ping=15` instructs sse-starlette to inject a `:ping <timestamp>\n\n` comment-line
  every 15 seconds when the data generator is idle. The injection is a separate
  asyncio task scheduled on the same event loop as the generator drain.
- Two separate writers (the generator's `yield {"data": ...}` and the ping task's
  comment-line write) onto the same `Send` channel can interleave at any await point.
  sse-starlette uses a `Lock` internally for newer versions, but earlier ones serialise
  weakly — and the `ping` write path has its own data-formatting that races with
  burst writes from the generator.
- In the UAT reproduction:
  - Replay phase yields 1393 buffered events as fast as XREAD can return them.
  - Then sub-agent runs continue producing events at ~89/s.
  - At ~11s the ping task fires (15s interval is the default; it can land EARLIER if
    sse-starlette uses an "idle-since-last-data" timer rather than absolute schedule
    — this varies across sse-starlette versions).
  - If a ping is injected mid-burst, the resulting frame can have a malformed
    chunked-encoding boundary from the browser's perspective even though the
    producer-side `Send` write completed.
- The browser-side error type (`ERR_INCOMPLETE_CHUNKED_ENCODING` + `TypeError:
  network error`) is exactly what malformed chunk-boundary handling produces in
  Chromium's net stack (the error fires when the connection closes mid-chunk).

**Conclusion:** PRIMARY SUSPECT. Consistent with: (a) producer completing cleanly,
(b) ~1000+ events flowing successfully before the drop, (c) the drop occurring on
sub-agent flows specifically (which produce burst+quiet patterns matching the
ping-race window), (d) the browser-side error class.

**Fix pointer:** Either disable ping entirely (`ping=None`) or set it well below the
worst-case quiet window so it cannot fire during the burst-then-quiet transition
(`ping=2`). Disabling is the simpler choice — Phase 063's frontend reattach
(D-v2.5-05: `visibilitychange` + `pageshow` + Resume button) provides the reconnection
mechanism that ping was nominally protecting against, and the producer survives
disconnect (D-v2.5-08) so we don't need keep-alive on the SSE channel itself.

## Disposition

- **Branch selected:** C — formal deferral to Phase 063 (frontend reattach).

- **Rationale:** Three of four hypotheses are conclusive from static analysis:
  - H4 REFUTED (no Vite proxy exists).
  - H1 REFUTED (no exception in backend logs at the canonical reproduction;
    producer completed cleanly).
  - H3 CONTRIBUTING FACTOR (amplifies H2's race window) but not standalone.
  - H2 PRIMARY SUSPECT (sse-starlette ping race during burst-then-quiet).

  Branch B (immediate fix) was the original preference per CONTEXT D-061.1-04.
  However, validating the H2 fix REQUIRES live Chrome MCP reproduction (the
  symptom is browser-side `ERR_INCOMPLETE_CHUNKED_ENCODING` — there is no
  pure-Python test harness that asserts this error class, since httpx
  `ASGITransport` buffers the entire response and never produces malformed
  chunked frames; this is the same blind spot that 059's manual UAT runbook
  documents). Live Chrome MCP was attempted in this session but returned
  a profile-conflict error.

  Phase 063's frontend reattach mechanism — `visibilitychange` + `pageshow` +
  reconcile fetch + Resume button (D-v2.5-05) consuming Phase 062's
  `GET /runs/{id}/stream?since=N` endpoint — masks H2's symptom regardless of
  the underlying cause: when the consumer drops, the user's tab will reattach
  and resume from the last received offset. The producer survives per D-v2.5-08,
  so no events are lost; the runs row + Redis Stream remain the source of truth.

  Branch C is therefore the correct disposition: document the diagnosis (this file)
  for future audits, defer the fix to Phase 063 where the larger reconnection
  flow is owned, and proceed with the rest of Plan 01 (Tasks 3-6: WR-01, WR-07,
  IN-03, IN-04) without blocking on a fix that needs browser-driven validation.

- **Next step:**
  1. Task 2 records this deferral as a known-issue entry referencing Phase 063
     (no production-code change in Plan 01 for S1).
  2. Phase 063 inherits H2 as the prime-suspect cause when the frontend reattach
     work begins. Recommended first experiment in 063: set `ping=None` on the
     `EventSourceResponse` call (or `ping=2`) and re-run the original
     `*Fahed*` RAG-with-sub-agent reproduction. If the drop disappears, H2 is
     confirmed; the disable-ping change ships as part of 063's backend support.
  3. The defensive H1 wrapper (try/except BaseException around the XREAD-and-yield
     body) is bundled into Plan 01 Task 6 (IN-04 extraction) at no extra cost —
     when `event_consumer` is lifted to module level, adding the guard is a
     one-line addition to the lift.
