    **1. Create `supabase/migrations/032_match_skills_rpc.sql`:**
    Create a `match_skills` RPC function following the exact pattern of `match_document_chunks` in migration 008 (but simpler — no hybrid search, vector-only). The function:
    - Takes `query_embedding vector(1536)`, `match_user_id uuid`, `match_threshold float DEFAULT 0.5`, `match_count int DEFAULT 5`
    - Returns `TABLE(id uuid, name text, description text, similarity float)`
    - Queries `public.skills WHERE (user_id = match_user_id OR is_global = true) AND is_enabled = true AND embedding IS NOT NULL`
    - Computes similarity as `1 - (embedding <=> query_embedding)` (cosine similarity from distance)
    - Filters by `similarity >= match_threshold`
    - Orders by `embedding <=> query_embedding ASC` (closest first)
    - Limits to `match_count`
    - Uses `STABLE` language plpgsql
    Also add a comment header matching migration 031's style.

    **3. Create `backend/app/services/skill_match_service.py`:**
    Create a new service module with these functions:

    `compute_skill_embedding(name: str, description: str) -> list[float]`
    - Calls `embed_texts([f"{name}: {description}"])` per D-02
    - Returns the embedding vector (list of 1536 floats)
    - On failure, logs the error and returns None (callers handle None gracefully)

    `cosine_similarity(a: list[float], b: list[float]) -> float`
    - Pure Python implementation: `dot / (norm_a * norm_b)` with zero-norm guard
    - Used as fallback when RPC is unavailable (and in unit tests)

    `match_skills(message: str, user_id: str, supabase: Client) -> list[dict] | None`
    - Per D-05: First check if any enabled skill's name appears as a case-insensitive substring in the message. Query `skills` table for user's enabled + global skills (`or_(user_id.eq.{user_id},is_global.eq.true).eq(is_enabled,true)`).
    - Per D-01: If any skills have embeddings, embed the message using `embed_texts([message])` and call `match_skills` RPC. Merge RPC results with name-bypass results, deduplicating by skill ID.
    - If no skills have embeddings yet (all NULL), fall back to including all enabled skills (graceful degradation — matches D-15 philosophy).
    - Cap result at `settings.skill_match_limit` (D-04, default 5).
    - On any embedding service failure, return `None` (caller falls back to all skills per D-15).
    - On success, return matched skill dicts with `id`, `name`, `description`.

    `backfill_skill_embeddings(supabase: Client) -> dict`
    - Fetches all skills with `embedding IS NULL` (`.is_("embedding", "null")`)
    - For each: compute embedding, update skill row `embedding = computed_value`
    - Returns `{"processed": N, "errors": M}` summary
    - Logs errors and continues (never aborts the whole backfill for one failure)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → API | Untrusted user messages — injection vector for skill matching |
| API → Supabase | Service-role key used for embeddings/backfill — no user-controlled SQL |
| API → OpenAI | Embedding API calls — user skill descriptions sent to OpenAI |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation |
|-----------|----------|-----------|-------------|------------|
| T-46-01 | Information Disclosure | Skill embedding computation | mitigate | Skill name+description sent to OpenAI for embedding — same data already sent in system prompts. No PII in skill content. |
| T-46-02 | Denial of Service | match_skills RPC | accept | Single embedding call per chat request — same latency as document RAG queries. No amplification vector. |
| T-46-03 | Spoofing | Explicit name bypass | mitigate | Name matching is case-insensitive substring — simple heuristic. A deliberately crafted message could trigger unrelated skill, but the skill still needs user intent to be useful. |
| T-46-04 | Tampering | Embedding stored in skills table | accept | Embeddings are computed server-side from skill name+description. User cannot inject arbitrary vectors. |
</threat_model>
