# Phase 184.1 Plan 01: Builder Header Consolidation Summary

**The Builder's three stacked header bands collapse into one flag-gated row — ~90px handed back to the canvas — and the flag-off surface is, for the first time, structurally pinned rather than merely promised.**

## Performance

- **Duration:** ~35 min (07:20–07:55)
- **Tasks:** 3/3
- **Files modified:** 3 source + 1 net-new test
- **Commits:** 3 task commits + 1 docs commit

## Accomplishments

The operator's Phase 184 UAT report was *"the canvas space is very narrow because the header above is taking too much space… especially with the smaller screens"* — measured at 275px of chrome above a 288px canvas on a 639px window, of which 146px was three bands doing one band's job.

Those three bands are owned by three different components, at three different nesting levels:

| Band | Owner | Contents |
|---|---|---|
| 1 | `WorkflowsPage` | `← Workflows` · `Edit · <title>` · `NET-NEW` |
| 2 | `WorkflowDoorSwitch` (`door-govern`) | `‹ both doors` · `🔧 Author & govern` · `JUDGE ALWAYS-ON` |
| 3 | `WorkflowBuilderPage` (`<header>`) | `<slug>` · `draft` · `Save draft` · `◆ Publish…` |

With the flag on they are now one `BuilderHeaderBar` row. With the flag off they are exactly what shipped, reached by a branch that cannot see the new slot props at all.

**Task 1 — the pin, written first.** `WorkflowBuilderPage.header.test.tsx` mounts the real three-owner stack (open a draft through `WorkflowsPage`) and asserts three distinct, non-nesting bands plus one normalised `outerHTML` literal. It was green against the **unmodified** page before any refactor began, and it passed after the merge with **zero edits** — which is the whole evidence that the flag gate held.

**Task 2 — the merge.** `useCanvasGate()` now holds the D-183-03 rule in one place; `BuilderHeaderBar` renders `lead`/`identity`/`trail`/`actions` in one wrapping row; `WorkflowDoorSwitch` gained an additive `inline`; `WorkflowsPage` stopped drawing its band and passes its breadcrumb group down as an opaque node.

**Task 3 — the proof it cannot regrow.** Exactly one band flag-on, every control reachable by accessible name, a band-count budget measured as a relationship in a single run, and the coordinator's requested one-definition guard on the gate rule.

### Count gate — the honest reading

The gate was run three times. Runs 2 and 3 failed on `PublishGauntlet.test.tsx` **only** (2 tests, then 2 different tests, all `Error: STACK_TRACE_ERROR`) — the documented pre-existing parallel-load flake. That file passes 24/24 in isolation and imports nothing this plan touches.

Run 1 additionally reported `WorkflowBuilderPage.canvas.test.tsx :: POSITIVE CONTROL — with the flag ON the very same read finds the key`. Because the orchestrator drew the tolerance line at "PublishGauntlet only", this was investigated rather than waved through:

- The message is `AssertionError: expected 0 to be greater than 0` — a **timeout** of `railsPropOf`'s `waitFor(() => expect(seen.length).toBeGreaterThan(0))`, which runs on Testing Library's **default 1s budget** after a `vi.resetModules()` plus two dynamic re-imports. That is a module-graph re-transform under full parallel load — the same class of load sensitivity this file already documented when it widened its lazy-chunk waits to 10s.
- It did **not** reproduce in gate runs 2 or 3, and the suite passed 22/22 in three separate isolated runs after the merge.
- No assertion was edited to make it pass (editing a shipped assertion is forbidden, and would have been the wrong fix regardless).

Read: a pre-existing timing fragility in that one helper, surfaced once. Recorded rather than absorbed.

## Deviations from Plan

### 1. [Rule 4 → escalated, coordinator approved] `WorkflowsPage.tsx` added to scope; the "one flag read" instruction withdrawn

- **Found during:** Task 2, before any code was written
- **Issue:** The dispatch said *"do NOT add a second read (183-03: one call site in the whole tree is the tripwire)"*, but bands 1 and 2 are owned by **ancestors** of the only component holding the flag. A parent cannot be handed a gate value by its child without its own read or a mount-effect callback, and the callback paints the band once before removing it — the exact flash-then-shift D-183-03 forbids. The alternative (parents pass content down and stop rendering bands) re-parents bands 1 and 2 into the Builder's subtree, changing flag-off nesting and reding the Task 1 pin.
- **Escalated** as a checkpoint rather than auto-fixed, because the remedy contradicted an explicit hard constraint.
- **Resolution:** Coordinator confirmed Option A, withdrew the instruction (the 183-03 tripwire pins the *BuilderPage* to the optional accessor and greps `builderSource` alone; the single `useEffectiveFeatures` **fetch** in `App.tsx` is untouched either way), and committed the scope correction as `34ddff75`, adding `WorkflowsPage.tsx` to `files_modified` and recording **D-184.1-04**.
- **Files:** `frontend/src/pages/WorkflowsPage.tsx`
- **Commit:** `0e9466de`

### 2. [Rule 2 - Missing critical functionality] The breadcrumb would have vanished on a fresh build

- **Found during:** Task 2
- **Issue:** With the flag on, both ancestors stop drawing their bands — but the describe screen and the two-door chooser have **no header of their own**. Only the drafted Builder does. Gating naively would have left an author on a fresh build with no `← Workflows` control and no way back.
- **Fix:** `WorkflowDoorSwitch`'s describe door and chooser adopt `headerLead` when `inline` is set, and the Builder's pre-draft branch hosts a `BuilderHeaderBar` when (and only when) a slot was actually handed down. Guarded by a dedicated test.
- **Commit:** `0e9466de` (guard in `12c557b3`)

### 3. [Rule 1 - Bug, twice] My own docblocks tripped source-grep guards

- **Found during:** Tasks 2 and 3
- **Issue:** Twice, prose I wrote introduced a token a grep expects to be absent — first `PhaseFormPanel` in `WorkflowDoorSwitch.tsx` (its own suite greps that source to zero, `WorkflowDoorSwitch.test.tsx:200`), then `useCanvasGate` in the same file (the new one-definition guard).
- **Fix:** Named the concept in prose and kept the identifier out, with an inline note saying why. The guards were **not** weakened — this is the project's standing anti-drift rule working as intended, and a guard that only passes by making a comment lie is a broken guard.
- **Commits:** `0e9466de`, `12c557b3`

### 4. [Accepted, pre-existing] `npx vite build` instead of `npm run build`

`npm run build` is `tsc -b && vite build` and is unsatisfiable on an untouched checkout at 33 pre-existing errors. Consistent with the deviation accepted across all of Phase 184.
