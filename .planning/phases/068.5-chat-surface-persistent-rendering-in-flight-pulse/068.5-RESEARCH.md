### Locked Decisions

**Cache strategy (F5 / page-refresh resilience)**

- **D-068.5-01:** localStorage snapshot for F5 resilience. Persist the bucket to localStorage so a hard refresh paints cached content before the server response returns. In-memory `bucketsBySurface` alone handles in-app navigation but not F5; the bug update explicitly mentions "refresh" + "mimics the behaviour of claude" — localStorage is the closest minimal-cost match.
- **D-068.5-02:** Cache scope: 5–10 most-recent threads, LRU eviction. Typical thread sizes ~2 KB to ~40 KB (long dissertation from BUG-260513-01); 5–10 threads stay well under ~5 MB origin cap. LRU eviction by last-accessed timestamp.
- **D-068.5-03:** Write cadence: throttled trailing-edge ~500ms during streaming + immediate flush on terminal events + immediate flush on thread switch. Avoids write-storm from per-token writes; keeps snapshot within ~500ms of reality; guarantees clean snapshot at terminal boundaries.
- **D-068.5-04:** localStorage key shape is surface-agnostic. Keys SHOULD include `SurfaceId` (e.g., `agentic-rag.streams.<surfaceId>.<thread_id>`) so a future v3.0 eval-pane second surface inherits F5 resilience without restructuring. Single packed blob vs per-thread keys is Claude's discretion.

## Summary

This is a frontend-shaped phase with **zero backend code change required** — `GET /threads/{id}/messages` already returns `run_status` per-row (verified at `backend/app/api/threads.py:793-814`); the Pydantic `MessageResponse.run_status` Literal is already 5-value (`models/message.py:44`); and the frontend mapper at `lib/api.ts:67-100` already maps `run_status` → `runStatus`. **D-068.5-14's research finding closes "confirmed present, no add needed."** This eliminates one of the three plan-level uncertainties up front.

The remaining technical surface is three concentric layers, all on top of the already-shipped Phase 068 substrate:

1. **localStorage cache layer.** Add a surface-keyed JSON snapshot of `bucketsBySurface` written via throttled subscribe; hydrate synchronously before first paint on `<StreamsProvider>` mount; LRU-evict to 5–10 threads. Compose with the existing Phase 067.5 Branch D-3 guard so hydrate never clobbers a streaming bucket.
2. **In-flight pulse + skeleton.** Add a CSS keyframe (or repurpose existing `animate-pulseGlow`/`animate-shimmer` already in `index.css`) gated on `Message.runStatus === 'streaming'` (NOT `'running'` — see Finding #8 — the literal enum value is `'streaming'`). Add a `<MessageSkeleton>` placeholder that mounts when bucket is empty and reconcile is in-flight.
3. **Retry banner.** Reuse the existing `fallbackNotice` slot pattern at `ChatArea.tsx:268-272`. Track retry attempts in a Zustand state slice or local ref; silent retry once at 1s; then banner with manual Retry button.

**Primary recommendation:** Build the localStorage layer as a DIY thin wrapper (~80–120 LOC) — NOT Zustand's `persist` middleware. Reasons: (a) the existing Phase 068 store uses **post-mount action registration via `setState`** (StreamsProvider.tsx:381-869), which is incompatible with `persist`'s assumption that the store config is the source of truth; (b) the bucket shape is `Map<SurfaceId, Map<string, Message[]>>` which requires custom serialization anyway; (c) we need a Branch-D-3-aware hydrate (skip if streaming) which `persist` doesn't model; (d) LRU eviction by access-time is a write-time concern not covered by `persist`. The DIY layer is two functions (`hydrate()` + `throttledWrite()`) plus an eviction helper — simpler than configuring `persist` around the existing architecture.

### Pattern 1: Hydrate-Before-First-Paint via useEffect in <StreamsProvider>

**What:** Read localStorage synchronously inside the provider's first useEffect (which fires after first commit but before browser paint when the provider mounts in a fresh tab). For React 19 + Zustand v5 + non-SSR (this app is a pure SPA, no Next.js), `useEffect` runs AFTER React's first paint commit but BEFORE the browser displays anything in cases where there's no Suspense boundary above. The result: hydrate happens fast enough that the user perceives the cached content as the "first render".

**When to use:** Pre-paint cache hydrate on a SPA mount.

**Example:**
```typescript
// frontend/src/providers/StreamsProvider.tsx (NEW useEffect, inserted BEFORE
// the existing useEffect #1 at line 381)
//
// Source: zustand docs + React 19 + project's no-SSR architecture.

useEffect(() => {
  // PHASE 068.5: synchronous hydrate before first user interaction.
  // Branch D-3 guard (L-068.5-01): if a stream is somehow active when this
  // effect fires (impossible at mount, but defensive), skip that thread.
  const snapshot = readSnapshotFromLocalStorage()  // sync localStorage.getItem
  if (!snapshot) return
  useStreamsStore.setState((state) => {
    const merged = new Map(state.bucketsBySurface)
    for (const [surface, threadMap] of snapshot) {
      const existingSurfMap = merged.get(surface) ?? new Map<string, Message[]>()
      const newSurfMap = new Map(existingSurfMap)
      for (const [tid, msgs] of threadMap) {
        // L-068.5-01: never overwrite a streaming bucket — defensive only.
        if (tid !== streamingThreadIdRef.current) {
          newSurfMap.set(tid, msgs)
        }
      }
      merged.set(surface, newSurfMap)
    }
    return { bucketsBySurface: merged }
  })
}, [])
```

**Note on React 19 + useSyncExternalStore (Zustand's substrate):** Zustand v5 uses `useSyncExternalStore` internally. Per React 19 docs [CITED: react.dev/reference/react/useSyncExternalStore], `useSyncExternalStore` triggers a non-concurrent synchronous blocking render — the snapshot returned by Zustand must be referentially-stable across calls (Phase 068 already handles this via the `EMPTY_ARRAY` module-level constant at `StreamsProvider.tsx:81`). Calling `useStreamsStore.setState` inside a useEffect AFTER the first render is the React 19-safe pattern (avoids hydration mismatch in SSR; for this SPA it's just a second commit). The user will perceive cached content as the first visible state if the hydrate happens before the browser flushes paint — empirically this is the case for localStorage reads under ~5 ms.

### Pattern 2: Throttled Bucket Subscription Write

**What:** Subscribe to `bucketsBySurface` changes; write to localStorage on trailing-edge of 500ms (D-068.5-03), with immediate-flush hooks for terminal events and thread switches.

**Example:**
```typescript
// frontend/src/lib/throttle.ts (NEW — ~15 LOC)
//
// Trailing-edge throttle with explicit flush method.

export function makeThrottle<T extends (...args: never[]) => void>(
  fn: T,
  waitMs: number,
): T & { flush: () => void } {
  let timer: ReturnType<typeof setTimeout> | null = null
  let lastArgs: Parameters<T> | null = null
  const invoke = () => {
    timer = null
    if (lastArgs) {
      fn(...lastArgs)
      lastArgs = null
    }
  }
  const throttled = ((...args: Parameters<T>) => {
    lastArgs = args
    if (timer === null) {
      timer = setTimeout(invoke, waitMs)
    }
  }) as T & { flush: () => void }
  throttled.flush = () => {
    if (timer !== null) {
      clearTimeout(timer)
      invoke()
    }
  }
  return throttled
}

// frontend/src/providers/StreamsProvider.tsx (NEW useEffect #4)
useEffect(() => {
  const writeNow = (state: StreamsState) => {
    writeSnapshotToLocalStorage(state.bucketsBySurface)
  }
  const throttledWrite = makeThrottle(writeNow, 500)
  const unsubscribe = useStreamsStore.subscribe((state) => {
    throttledWrite(state)
  })
  return () => {
    throttledWrite.flush()  // flush pending write on unmount
    unsubscribe()
  }
}, [])
```

The `terminal-event flush` and `thread-switch flush` hooks call `throttledWrite.flush()` directly from inside the existing onTerminal callback and setViewingThread action.

### Pattern 3: LRU Eviction — Recommended Approach

**What:** Lazy eviction on write — check the snapshot size after every write; if more than 10 threads, evict the oldest by `lastAccessedAt` timestamp. Wrap the actual `localStorage.setItem` in a `try { } catch (QuotaExceededError) { evict-50-percent-and-retry-once }`.

**Why lazy over write-time always-check:** Most writes don't exceed the cap. The cheap-path is "just write"; the slow-path is "catch quota error, evict, retry". Avoids per-write size computation.

**Snapshot shape:**
```typescript
// localStorage key: "agentic-rag.streams.v1"
// Single packed JSON blob (D-068.5-04 allows either; packed is simpler for LRU)
{
  version: 1,
  threads: {
    [surfaceId]: {
      [threadId]: {
        messages: Message[],
        lastAccessedAt: number,  // Date.now()
      }
    }
  }
}
```

Single key allows atomic write; per-thread reads at hydrate are O(threads) which is trivially small (≤10).

**Example:**
```typescript
// frontend/src/lib/streamsCache.ts
const KEY = "agentic-rag.streams.v1"
const MAX_THREADS_PER_SURFACE = 10

export function writeSnapshotToLocalStorage(
  buckets: Map<SurfaceId, Map<string, Message[]>>,
): void {
  const snapshot = serialize(buckets)  // converts Maps → plain objects + adds lastAccessedAt
  try {
    localStorage.setItem(KEY, JSON.stringify(snapshot))
  } catch (err) {
    if (err instanceof DOMException && err.name === "QuotaExceededError") {
      evictOldestHalf(snapshot)
      try {
        localStorage.setItem(KEY, JSON.stringify(snapshot))
      } catch {
        // Give up — log + skip; in-memory bucket still works.
        console.warn("[streamsCache] quota exhausted after eviction; cache disabled")
      }
    } else {
      throw err
    }
  }
}
```

### Anti-Patterns to Avoid

- **Don't use Zustand `persist` middleware.** Doesn't compose with the existing post-mount `setState` action registration; doesn't support Branch-D-3-aware hydrate; needs custom storage engine for nested Maps anyway. The DIY path is simpler AND smaller for this specific architecture.
- **Don't read localStorage on every component render.** Hydrate once, into the store; subsequent reads are from in-memory state.
- **Don't write to localStorage on every token delta.** Throttle at 500ms (D-068.5-03); flush on terminal + on thread switch.
- **Don't add a new `Message.inFlight` field.** The existing `runStatus === 'streaming'` is the source of truth. Don't denormalize.
- **Don't introduce a new SSE event for "in-flight pulse".** The pulse reads message-level state already arrived via existing events.
- **Don't add a service worker, IndexedDB, or BroadcastChannel.** Explicit deferred ideas per CONTEXT.md.
- **Don't write tests that hardcode localStorage keys without a const indirection.** Use the same `KEY` const exported from `streamsCache.ts`.
- **Don't break the `streamingThreadIdRef.current` invariant during hydrate.** Even though it's null at mount, future surfaces (eval pane mid-stream) could have it set when remounted; defensive guard is required (L-068.5-01).

## Common Pitfalls

### Pitfall 1: localStorage hydrate fires AFTER first paint, defeating the purpose

**What goes wrong:** Developer puts hydrate inside a `useEffect` that fires after the first paint, expecting the user to see cached content as the first frame. Instead they briefly see the blank state, then the cached content appears as a layout shift.

**Why it happens:** React `useEffect` semantics — runs after commit. On a SPA there's no SSR initial HTML; the first paint is whatever React renders on first commit, which is empty bucketsBySurface (initial state from `streamsStore.ts:75-91`).

**How to avoid:** Two options:
1. **Initialize Zustand store state synchronously by reading localStorage in the store creator function** (the initial `create<StreamsState>()(() => ({...}))` factory at `streamsStore.ts:75`). Move the hydrate call INTO the factory — `bucketsBySurface: readSnapshotSyncOrEmpty()`. This way the store has hydrated state on its very first read.
2. Accept a one-frame layout shift and put hydrate in useEffect.

**Recommendation:** Option 1 — hydrate is synchronous, localStorage reads are <5ms even on slow devices, no need to defer. Initial value of `bucketsBySurface` becomes the deserialized Map (or `new Map()` on first ever load / parse failure). This is structurally cleaner and gives the user a true "first paint with cached content" experience required by SC#5 (<100ms paint).

**Warning signs:** Chrome DevTools Performance trace shows two paint frames within the first 200ms post-route-render — first empty, second with content. Should be ONE paint with content.

### Pitfall 2: Reading the snapshot before checking `streamingThreadIdRef`

**What goes wrong:** Hydrate writes to a bucket whose thread is currently streaming (e.g., user is on an eval pane mid-stream, browser tab unfocuses → focuses, provider remounts somehow, hydrate runs, clobbers live bucket).

**Why it happens:** L-068.5-01 says "Branch D-3 guard preserved" but hydrate is a NEW write path that wasn't covered by Phase 067.5's fix.

**How to avoid:** Per-thread guard in the hydrate body (Pattern 1 above shows it). At mount this always passes because `streamingThreadIdRef.current === null`. Defensive code; cheap to add.

**Warning signs:** A new Vitest regression test should construct the scenario: set `streamingThreadIdRef.current = 'X'` synthetically, then call hydrate with a snapshot that contains thread X, assert thread X's existing bucket survives.

### Pitfall 3: Throttle writes during streaming + crash mid-token

**What goes wrong:** Stream is mid-token, throttle has a pending write 200ms away, browser crashes / tab closed. The last 200ms of tokens are lost from the snapshot.

**Why it happens:** Throttle by design delays writes.

**How to avoid:** D-068.5-03 already addresses — immediate flush on terminal events + on thread switch. The "lose at most one delta on crash" guarantee in CONTEXT.md is precisely this — the loss is bounded to the throttle window (500ms) and is acceptable per the locked decision.

**Warning signs:** Chrome MCP timing test: kill tab mid-stream, refresh, observe the lost-token window. Should be ≤500ms of content.

### Pitfall 4: localStorage on iOS Safari private mode throws QuotaExceededError on first write

**What goes wrong:** localStorage in iOS Safari private mode has a 0-byte quota; every `setItem` throws.

**Why it happens:** Apple privacy feature.

**How to avoid:** The `try { setItem } catch` wrapper (Pattern 3) silently falls through; cache is effectively disabled in private mode, but in-memory bucket still works → same UX as today.

**Warning signs:** Console warning `[streamsCache] quota exhausted after eviction; cache disabled` in private-mode test sessions. Document as known limitation.

### Pitfall 5: Concurrent thread-switch races on the throttled write

**What goes wrong:** User switches A→B→A quickly. Throttle has a pending write for state-after-switch-1; switch-2 happens; flush triggers; write captures state-after-switch-2 (correct) BUT the snapshot's `lastAccessedAt` for thread A reflects an old visit time, so LRU eviction may target the wrong thread.

**Why it happens:** `lastAccessedAt` updates only on bucket reads, not on every `bucketsBySurface` write.

**How to avoid:** Update `lastAccessedAt` for the active thread inside `setViewingThread` action, not inside the write subscriber. Decouples access-time from write-time.

**Warning signs:** Vitest test: rapid A→B→A→C→D→...→K (12 threads), assert thread A is not evicted before the most-recently-accessed-but-stale thread.

### Pitfall 6: Pulse animation flashes on terminal SSE arrival (the "in-flight → done" transition)

**What goes wrong:** The pulse keeps animating for a few hundred ms after the SSE terminal event arrives, because React batches state updates and there's a frame where `runStatus === 'streaming'` is stale.

**Why it happens:** Zustand subscribes are synchronous, but React's render commit is async; the SSE terminal event flips runStatus to `'completed'` in the store, but the next render frame may not commit immediately.

**How to avoid:** This is actually fine — the pulse animation is 1.5s and a one-frame stale state is invisible. Don't over-engineer this.

**Warning signs:** Manual UAT: send a short prompt (1-2 tokens), watch the pulse end exactly when text appears. Should feel instantaneous.

### Pitfall 7: Cached content paints but the layout breaks because container chrome (provider/model selectors) hasn't loaded yet

**What goes wrong:** Cached messages render immediately on F5 but `getProviders()` at `ChatArea.tsx:51-66` is still loading, so the provider/model dropdowns are empty, and the user sees a weird half-loaded layout.

**Why it happens:** Different async stages — message hydrate is sync (from localStorage), provider list is async (network fetch).

**How to avoid:** This is acceptable; the chrome chrome is small and already partial-state on every F5 today. The cached messages are the user-noticed surface. If the chrome flash is too jarring, add a parallel localStorage cache for `getProviders()` response — but that's out of scope per the phase boundary (CONTEXT.md explicitly excludes "any state beyond the bucket"). Leave alone.

### Pitfall 8: Skeleton flash for already-warm threads (skeleton shown for 1-2 frames between bucket-empty-init and bucket-hydrated)

**What goes wrong:** On F5, the initial state of `bucketsBySurface` is `new Map()` (line 76 of `streamsStore.ts`). If skeleton renders on `messages.length === 0`, the user sees a brief skeleton flash before the hydrate fires.

**Why it happens:** Race between component-mount and hydrate-effect.

**How to avoid:** Either (a) hydrate synchronously in the store factory (Pitfall 1 recommendation), OR (b) gate skeleton on a separate `isHydrating` flag that goes false after hydrate completes (and never goes true again). Option (a) avoids the flag entirely. **Recommend option (a).**

**Warning signs:** Chrome MCP: F5 a thread with cached data; observe whether skeleton flashes for any frame. Should not flash if hydrate is in the store factory.

### Cache module skeleton

```typescript
// frontend/src/lib/streamsCache.ts (NEW)
import type { Message } from "@/types"
import type { SurfaceId } from "@/stores/streamsStore"

const KEY = "agentic-rag.streams.v1"
const MAX_THREADS_PER_SURFACE = 10
const VERSION = 1

interface SerializedThreadEntry {
  messages: Message[]
  lastAccessedAt: number
}

interface SerializedSnapshot {
  version: number
  surfaces: Record<SurfaceId, Record<string, SerializedThreadEntry>>
}

export function readSnapshotSyncOrEmpty(): Map<SurfaceId, Map<string, Message[]>> {
  try {
    const raw = localStorage.getItem(KEY)
    if (!raw) return new Map()
    const parsed = JSON.parse(raw) as SerializedSnapshot
    if (parsed.version !== VERSION) {
      // Version drift — drop and start fresh.
      localStorage.removeItem(KEY)
      return new Map()
    }
    const out = new Map<SurfaceId, Map<string, Message[]>>()
    for (const [surface, threads] of Object.entries(parsed.surfaces)) {
      const surfMap = new Map<string, Message[]>()
      for (const [tid, entry] of Object.entries(threads)) {
        surfMap.set(tid, entry.messages)
      }
      out.set(surface, surfMap)
    }
    return out
  } catch {
    return new Map()
  }
}

export function writeSnapshotToLocalStorage(
  buckets: Map<SurfaceId, Map<string, Message[]>>,
  now: number = Date.now(),
): void {
  const snapshot: SerializedSnapshot = { version: VERSION, surfaces: {} }
  for (const [surface, threads] of buckets) {
    const surfaceEntry: Record<string, SerializedThreadEntry> = {}
    for (const [tid, messages] of threads) {
      surfaceEntry[tid] = { messages, lastAccessedAt: now }
    }
    snapshot.surfaces[surface] = surfaceEntry
  }
  evictPerSurfaceIfOver(snapshot, MAX_THREADS_PER_SURFACE)
  try {
    localStorage.setItem(KEY, JSON.stringify(snapshot))
  } catch (err) {
    if (err instanceof DOMException && err.name === "QuotaExceededError") {
      // Drop oldest half across all surfaces and retry once.
      evictOldestHalf(snapshot)
      try {
        localStorage.setItem(KEY, JSON.stringify(snapshot))
      } catch {
        console.warn("[streamsCache] quota exhausted after eviction; cache disabled this session")
      }
    } else {
      console.warn("[streamsCache] write failed:", err)
    }
  }
}

function evictPerSurfaceIfOver(
  snapshot: SerializedSnapshot,
  maxPerSurface: number,
): void {
  for (const [surface, threads] of Object.entries(snapshot.surfaces)) {
    const entries = Object.entries(threads)
    if (entries.length <= maxPerSurface) continue
    entries.sort((a, b) => b[1].lastAccessedAt - a[1].lastAccessedAt)
    const kept = Object.fromEntries(entries.slice(0, maxPerSurface))
    snapshot.surfaces[surface] = kept
  }
}

function evictOldestHalf(snapshot: SerializedSnapshot): void {
  for (const surface of Object.keys(snapshot.surfaces)) {
    const entries = Object.entries(snapshot.surfaces[surface])
    entries.sort((a, b) => b[1].lastAccessedAt - a[1].lastAccessedAt)
    const half = Math.ceil(entries.length / 2)
    snapshot.surfaces[surface] = Object.fromEntries(entries.slice(0, half))
  }
}
```

### Known Threat Patterns for {React 19 + Zustand + localStorage frontend stack}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malformed cache → JSON.parse throws | Denial-of-Service (cosmetic; refuses to load app) | `try { JSON.parse } catch → return new Map()` fallback (Pattern 3 above) |
| Quota exhaustion → setItem throws on every write | Denial-of-Service (cosmetic; cache disabled, in-memory works) | `try { setItem } catch (QuotaExceededError) → evict-half-retry → fall through silently` |
| Version drift after a future cache shape change | Information disclosure (could deserialize wrong shape into store; corrupts state) | `if (parsed.version !== VERSION) drop + start fresh` — and bump VERSION on shape changes |
| XSS reads cache (third-party script) | Information disclosure | No new vector — XSS on this app already has access to in-memory store; localStorage doesn't broaden. Existing CSP / DOMPurify usage (`dompurify` in package.json line 32) handles the source XSS prevention. |
| Multi-tab race (Tab A clears cache, Tab B is mid-write) | Tampering (lost write) | Acceptable; multi-tab sync is explicitly deferred per CONTEXT.md. Last write wins; cached content in Tab B's in-memory store survives. |

**No new security controls required.** The cache is plaintext, scoped to the origin, and protected only by browser sandboxing — same posture as the existing in-memory store. The risk-tier matches what already ships.
