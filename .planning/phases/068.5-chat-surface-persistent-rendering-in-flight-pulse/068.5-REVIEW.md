## Summary

The phase ships a clean, well-commented localStorage substrate, a sound cold-render fix, and accurate brand-pulse + retry-banner wiring. All five locked invariants (L-068.5-01..05) verify by inspection. Two real correctness issues warrant fixing before phase close: (1) the localStorage cache is **not partitioned per Supabase user**, so on dev/test machines where two users sign in to the same browser origin, the second user momentarily sees the first user's cached thread content (privacy + correctness, since `messages` is RLS-protected server-side but the localStorage cache is not); (2) the `useStreamsStore.subscribe` listener in `useEffect #4` fires the throttled writer on **every** state mutation (reconcileError, isStreaming, subscriptionsByRunId, loadingThreadId, viewedThreadId, fallbackNotice), not just on `bucketsBySurface` changes, defeating much of the throttle's purpose and burning serialization work on hot paths.

The remaining warnings are mostly UX-consistency nits (dismiss handler clears banner state cross-thread; banner uses `role="status"` which a11y conventions suggest should be `role="alert"` for an error). Test coverage for Gap-01 is solid (real runtime tests); test coverage for Gap-02 (the cross-thread `loadMessages` fix) is a static-grep marker only — no runtime test exercises the cold-load-while-streaming-other-thread path that originally surfaced the bug.

### Blockers (must fix before phase close)

**B-01: localStorage cache is not partitioned per Supabase user — leaks chat content across user sessions on a shared origin**
- **File:** `frontend/src/lib/streamsCache.ts:29`, `frontend/src/stores/streamsStore.ts:93`
- **Severity:** blocker
- **Category:** security / privacy
- **Description:** `STREAMS_CACHE_KEY = "agentic-rag.streams.v1"` is a single origin-wide key. The Zustand factory hydrates `bucketsBySurface` **synchronously at module import time** from this key (`streamsStore.ts:93`), before any auth state is known. On a machine where user A signs in, sends messages, then signs out and user B signs in (the documented dev-test pattern — `fhdmrd@gmail.com / 123456`, plus any second account), user B's first paint will render user A's cached chat content for any thread_id whose UUID happens to overlap (rare across users) — BUT crucially, the same browser tab continues to write user B's bucket data over user A's into the same key. There is no `signOut` clearing of `localStorage[STREAMS_CACHE_KEY]`, no user-id prefix, and no on-mount predicate that compares cached payload against current `supabase.auth.getUser()`. Given CLAUDE.md explicitly mandates "All tables need Row-Level Security — users only see their own data" and the target is "production at organizational scale (few to thousands of users)" (per MEMORY.md `project_target_scale.md`), shipping a cross-user-visible client cache violates the project's stated RLS posture even though the server still enforces it. On a shared device (kiosk, family Mac, dev machine with multiple test logins) this is a real leak.
- **Suggested fix:** Two-line change in `streamsCache.ts`:
  ```ts
  // Make the key user-scoped. Resolve user_id at read/write time from the
  // current auth session (sync via Supabase client local-storage adapter).
  export const STREAMS_CACHE_KEY_PREFIX = "agentic-rag.streams.v1" as const
  export function streamsCacheKey(userId: string): string {
    return `${STREAMS_CACHE_KEY_PREFIX}.${userId}`
  }
  ```
  Plus a `signOut`-time `localStorage.removeItem(streamsCacheKey(userId))` in the auth flow, and a guard in `readSnapshotSyncOrEmpty` that returns empty Map when no auth session is present (the Zustand factory would then hydrate to empty on cold load, and a follow-up `useEffect` re-hydrates after `supabase.auth.getSession()` resolves). The trade-off vs. Pitfall 1's "synchronous first-paint" closure is one extra render cycle for the rare deep-link-to-thread case — acceptable for the privacy guarantee.

**B-02: `useStreamsStore.subscribe(listener)` fires on every state change, not on `bucketsBySurface` changes — defeats the throttle's batching purpose**
- **File:** `frontend/src/providers/StreamsProvider.tsx:998-1000`
- **Severity:** blocker
- **Category:** correctness / invariant-violation (D-068.5-03 intent)
- **Description:** The planner spec (068.5-01-PLAN.md `<interfaces>` block) and RESEARCH.md §Pattern S3 both describe useEffect #4 as a "Zustand `subscribe(state => state.bucketsBySurface, throttled-write)`" — i.e., a SELECTOR-bound subscription. The implementation at line 998 is `useStreamsStore.subscribe((state) => { throttledWrite(state) })` with **no selector argument**. In Zustand v5 the single-argument `subscribe(listener)` form fires the listener on **every** store update — including `reconcileError` setState (rare), `viewedThreadId` setState (per thread switch), `isStreaming` setState (twice per send), `fallbackNotice` setState (per fallback), `subscriptionsByRunId` setState (twice per run lifecycle — add + remove), and `loadingThreadId` setState (twice per loadMessages — start + finally). Each of these schedules a 500ms write that ultimately serializes the entire `bucketsBySurface` Map even though that field did not change. On a long active stream that flips `subscriptionsByRunId` per onTerminal and `loadingThreadId` per reconcile-triggered loadMessages, the write rate is ~1 per terminal event PLUS the desired per-token coalesce. This violates D-068.5-03's "throttled trailing-edge ~500ms during streaming" semantics: the throttle still coalesces, but the trigger fires on bookkeeping state too. More importantly, if `bucketsBySurface` is the actual source of "is there something cache-worthy to write?", subscribing without a selector means writes happen even when **nothing cache-relevant** changed — wasted CPU + localStorage churn (the very thing the cap=3 rescope was supposed to reduce).
- **Suggested fix:** Use Zustand v5's `subscribeWithSelector` middleware or the imperative `subscribe(selector, listener, options)` form:
  ```ts
  const unsubscribe = useStreamsStore.subscribe(
    (state) => state.bucketsBySurface,
    (buckets) => {
      // call the existing writeNow with current state — only fires when buckets ref changes
      throttledWrite(useStreamsStore.getState())
    },
  )
  ```
  Note: Zustand v5 requires `subscribeWithSelector` middleware to be in the store factory for the selector overload. Alternative: keep the single-arg form but compare `state.bucketsBySurface` against a ref-captured previous value inside the listener and bail when reference-equal. Either fix restores D-068.5-03's intent.

**W-02: Dismiss handler clears `reconcileError` globally — wipes an error scoped to a different thread on cross-thread switch**
- **File:** `frontend/src/components/chat/ChatArea.tsx:64-66`, `64-66`
- **Severity:** warning
- **Category:** UX / state-scoping
- **Description:** `reconcileError` is a single store slot scoped by `{ threadId, error }` payload. The render gate at ChatArea.tsx:309 correctly limits visibility to the matching thread (`reconcileError.threadId === thread?.id`). But the dismiss handler at line 64-66 (`useStreamsStore.setState({ reconcileError: null })`) clears the error unconditionally. Scenario: user is on Thread A; A's reconcile fails; user dismisses the banner on A; later user opens Thread B; B's reconcile also fails → banner appears with the NEW error. So far so good. But: user is on A; A's reconcile fails; user switches to B (banner hides via predicate, error state persists in store); B's reconcile succeeds (line 901-903 clears A's error since `state.reconcileError?.threadId === B` is false, so the predicate `=== threadId` is also false, NO clear happens). User switches back to A → A's banner reappears with the OLD error — even though A may have been silently fixed by another mount cycle in between. The interaction between "banner is thread-scoped via the render predicate" and "dismiss is store-global" is inconsistent.
- **Suggested fix:** Scope the dismiss to the current thread (and the success-clear at line 901). Either:
  ```ts
  const dismissReconcileError = useCallback(() => {
    if (!thread) return
    useStreamsStore.setState((s) =>
      s.reconcileError?.threadId === thread.id ? { reconcileError: null } : s,
    )
  }, [thread])
  ```
  Or convert `reconcileError` to a `Map<thread_id, Error>` keyed by thread — also lets multiple threads have concurrent error state.

**W-03: Recursive `setTimeout(resolve, 1000)` retry leaks across component unmount + thread switch — no AbortSignal binding on the retry timer**
- **File:** `frontend/src/providers/StreamsProvider.tsx:910`
- **Severity:** warning
- **Category:** memory / race-condition
- **Description:** `await new Promise((resolve) => setTimeout(resolve, 1000))` (the silent-1s-then-retry delay) is not bound to any AbortController or unmount cleanup. If the user navigates away from the chat surface mid-1s-wait, or switches threads (thereby triggering `loadMessages` for the new thread), the suspended Promise continues to its second `tryFetch(1)` call. The second `tryFetch(1)` then does `loadAbortRef.current?.abort()` (aborts whatever fetch the new thread just started!), creates a new AbortController, and fires `getMessages(threadId, controller.signal)` for the OLD threadId. The post-await guard at line 875 (`if (activeThreadIdRef.current !== threadId) return`) correctly bails — the result is discarded — but in the meantime the NEW thread's in-flight fetch was aborted by the old retry's `loadAbortRef.current?.abort()`. The new thread's loadMessages will throw AbortError and silently early-return; the user sees a stuck skeleton or stale content until the next mount.
- **Suggested fix:** Bind the retry delay to the same AbortController:
  ```ts
  const controller = new AbortController()
  loadAbortRef.current = controller
  // ... inside catch:
  if (attempt === 0) {
    await new Promise<void>((resolve, reject) => {
      const t = setTimeout(resolve, 1000)
      controller.signal.addEventListener("abort", () => {
        clearTimeout(t)
        reject(new DOMException("aborted", "AbortError"))
      })
    })
    return tryFetch(1)
  }
  ```
  Wrap in try/catch so the AbortError early-returns cleanly. Also clear the retry path's `loadAbortRef` before scheduling the new fetch so the next thread switch's `abort()` doesn't kill the silent retry's fresh controller.

**W-04: Retry banner uses `role="status"` for an error condition — accessibility convention prefers `role="alert"`**
- **File:** `frontend/src/components/chat/ChatArea.tsx:313`
- **Severity:** warning
- **Category:** accessibility
- **Description:** WAI-ARIA convention reserves `role="status"` for advisory, non-time-sensitive messages (e.g., "Saved"). `role="alert"` is the canonical role for error conditions like "Couldn't load latest messages" that the user should act on. Screen readers handle the two differently — `alert` interrupts the current narration; `status` waits for an idle slot. The banner's `aria-live="polite"` is also wrong for an alert (alerts should be `aria-live="assertive"` or simply rely on the `alert` role's implicit semantics).
- **Suggested fix:**
  ```tsx
  <div role="alert" aria-live="assertive" data-testid="reconcile-error-banner" ...>
  ```

**W-05: `evictOldestHalf` mutates `snapshot.surfaces` then retries write — silent failure after retry leaves cache half-cleared but unwritten**
- **File:** `frontend/src/lib/streamsCache.ts:177-184`
- **Severity:** warning
- **Category:** correctness (quota path)
- **Description:** When `setItem` throws QuotaExceededError, `evictOldestHalf(snapshot)` mutates the local `snapshot` variable in place (drops half per surface, sort-by-`lastAccessedAt`). The retry `setItem(STREAMS_CACHE_KEY, JSON.stringify(snapshot))` is wrapped in a bare try/catch with `console.warn` on a second throw. If the second `setItem` also throws (e.g., the snapshot still doesn't fit, or the user's localStorage is fully wedged in Safari private mode), the cache becomes silently desynced — the in-memory `bucketsBySurface` still has all threads, but localStorage now holds nothing (or worse, holds a stale value from a prior write that the failed retry didn't overwrite). On the next reload, the user F5s and the on-disk snapshot is from minutes ago. There's also no telemetry signal — `console.warn` in production is invisible to dev tools triage.
- **Suggested fix:** Three small improvements:
  1. Compute serialized size before the first `setItem` and pre-evict if `> SAFE_BYTES` (e.g., 1.5 MB); avoids the Safari quirk where quota errors are inconsistent.
  2. On the second throw, explicitly `localStorage.removeItem(STREAMS_CACHE_KEY)` so the next read hits the version-drift recovery path cleanly (no stale half-content).
  3. Add a one-line emit via a `cacheQuotaExhausted` callback so downstream telemetry (or a future error boundary) can surface it.

**W-06: `lastAccessedAt` is never actually "accessed-time" — it's "write-time of first appearance", so LRU degrades to FIFO under steady streaming**
- **File:** `frontend/src/lib/streamsCache.ts:107-118` (docblock notes this), `199-211`
- **Severity:** warning
- **Category:** correctness / design intent
- **Description:** The docblock at line 107-118 explicitly notes "Per-thread access-time is a future refinement." That refinement is exactly what makes LRU eviction correct under the actual usage pattern. Today: user opens thread A (gets lastAccessedAt = T0), streams a long response (writes accumulate but lastAccessedAt stays at T0 — the prior-times merge at line 162 preserves the FIRST seen timestamp). User opens thread B (T1), thread C (T2). Cap = 3, all good. Now user goes BACK to thread A (the most-relevant "recently accessed" thread). No write fires for A's bucket because nothing changed — so A's lastAccessedAt stays at T0. If a fourth thread D is opened (T3), A is evicted (oldest by lastAccessedAt) even though A is the currently-viewed thread. This converts LRU into "first-write-wins FIFO", which is the opposite of the intent.
- **Suggested fix:** Refresh `lastAccessedAt` for `streamingThreadId` and `activeThreadId` on every write (not just for new threads):
  ```ts
  for (const [tid, messages] of threads) {
    if (keepPredicate && !keepPredicate(surface, tid)) continue
    const prior = priorSurf?.get(tid)
    // If this thread IS the currently-active or streaming thread, refresh its
    // lastAccessedAt — otherwise preserve the prior stamp.
    const isHotThread = keepPredicate ? keepPredicate(surface, tid) : false
    surfaceEntry[tid] = {
      messages,
      lastAccessedAt: isHotThread ? now : (typeof prior === "number" ? prior : now),
    }
  }
  ```
  (The keepPredicate here is already used to gate persistence; piggyback its "hot thread" signal for stamp refresh.)

**IN-02: Banner success-clear predicate doesn't check `useStreamsStore.getState().reconcileError?.threadId === threadId` atomically with the success-set**
- **File:** `frontend/src/providers/StreamsProvider.tsx:901-903`
- **Severity:** info
- **Category:** race
- **Description:** Read-then-set pattern: `if (state.reconcileError?.threadId === threadId) setState({ reconcileError: null })`. In React strict mode + concurrent setState, another action could mutate `reconcileError` between the read and write. The end state is still null (which is what we want) so no real damage, but a setState with a functional updater (`useStreamsStore.setState((s) => s.reconcileError?.threadId === threadId ? { reconcileError: null } : s)`) is the more correct pattern.

**IN-03: `JSON.parse(raw) as SerializedSnapshot` lacks runtime shape verification — partial-trust input not validated**
- **File:** `frontend/src/lib/streamsCache.ts:60`
- **Severity:** info
- **Category:** robustness
- **Description:** A user (or an attacker, or a bug in a future phase that writes a different shape) could put any JSON under `agentic-rag.streams.v1`. The code checks `version === STREAMS_CACHE_VERSION` (good), then walks `surfaces` with `Object.entries`. If `parsed.surfaces` is an array, or a primitive, the code at line 73 (`Object.entries(surfaces)`) silently returns an empty iterator — no error, returns empty Map. The cache discards what was there. Not exploitable today (the cache is read-only inside the user's own browser), but worth a guarded `if (typeof parsed.surfaces !== "object")` upgrade — purely defensive.
