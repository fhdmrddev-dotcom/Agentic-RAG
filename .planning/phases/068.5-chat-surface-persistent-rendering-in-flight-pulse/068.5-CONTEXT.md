# Phase 068.5: Chat-Surface Persistent Rendering + In-Flight Pulse - Context

**Gathered:** 2026-05-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the 200–800ms blank-chat-surface window (BUG-260513-01) by rendering last-known-good messages immediately on thread switch / page navigation / page refresh, reconciling fresh server data in the background without clobbering active streaming buckets, and signaling un-terminated assistant turns with a visible in-flight pulse. Fetch failures surface an inline retry banner over the cached content instead of blanking the message list.

This phase is built directly on Phase 068's `<StreamsProvider>` substrate:
- `bucketsBySurface: Map<SurfaceId, Map<thread_id, Message[]>>` in `frontend/src/stores/streamsStore.ts:38` already provides in-app navigation persistence for free — switching threads inside an open session keeps both buckets warm.
- `Message.runStatus` (`frontend/src/types/index.ts:112`) already mirrors `public.runs.status` 5-value enum — the pulse reads this directly.
- The Phase 067.5 Branch D-3 guard at `streamsStore.clearThreadBucket` MUST be preserved verbatim.

**What this phase does NOT do:**
- Change the SSE event shape, the streams contract, or `<StreamsProvider>` action signatures (Phase 068 just shipped — those interfaces are locked).
- Add offline support, service workers, IndexedDB, or cross-tab cache sync (BroadcastChannel) — out of scope.
- Introduce per-message granular caching — the cache unit is per-thread.
- Add a "you're offline" mode — this is a load-latency / fetch-failure UX, not a network-state UX.
- Touch the v3.0 eval-pane second-surface story beyond making the localStorage cache surface-agnostic (keyed by `SurfaceId`) so a future second surface inherits resilience for free.

</domain>

<decisions>
## Implementation Decisions

### Cache strategy (F5 / page-refresh resilience)

- **D-068.5-01:** **localStorage snapshot for F5 resilience.** Persist the bucket to localStorage so a hard refresh paints cached content before the server response returns. In-memory `bucketsBySurface` alone handles in-app navigation but not F5; the bug update explicitly mentions "refresh" + "this mimics the behaviour of claude" — localStorage is the closest minimal-cost match.
- **D-068.5-02:** **Cache scope: streaming + currently-viewing thread only, LRU eviction with cap=3.** ~~Originally scoped to 5–10 most-recent threads~~ — rescoped 2026-05-14 during SC#6 UAT (user pushback: "completed chats are in DB, why cache them?"). The cache's load-bearing UX value is in two cases only:
  1. **Streaming thread on F5** — DB only has finalized terminal-state content; mid-stream accumulated tokens live only in the SSE producer + the bucket. Without cache, F5 wipes the in-flight render.
  2. **Currently-viewing thread on F5** — instant paint vs the 590ms DB roundtrip.
  Completed background threads load from DB + skeleton on demand. Cache write predicate: `threadId === streamingThreadIdRef.current || threadId === activeThreadIdRef.current`. LRU cap drops 10 → 3 (room for the active pair + brief overlap during a thread switch). Cache stays under ~200 KB at typical sizes, ~500 KB worst case.
- **D-068.5-03:** **Write cadence: throttled trailing-edge ~500ms during streaming + immediate flush on terminal events + immediate flush on thread switch.** Avoids the write-storm that per-token writes would produce (100+ writes/sec during fast streams), keeps the snapshot within ~500ms of reality, and guarantees a clean snapshot at terminal boundaries so a crash mid-typing-the-next-token loses at most one delta. Implementation note: planner should pick a throttle (lodash or DIY `setTimeout`-based) — both fine.
- **D-068.5-04:** **localStorage key shape is surface-agnostic.** Keys SHOULD include `SurfaceId` (e.g., `agentic-rag.streams.<surfaceId>.<thread_id>`) so a future v3.0 eval-pane second surface inherits F5 resilience without restructuring. Exact key encoding is Claude's discretion — single packed JSON blob vs per-thread keys both acceptable; pick whatever makes the LRU eviction reads cheap.

### In-flight pulse (un-terminated assistant turns)

- **D-068.5-05:** **Visual style: brand-mark glow + breathing pulse.** The assistant's Sparkles + gradient-primary brand mark (pattern at `ChatArea.tsx:212`) gets a soft scale + opacity breathing animation — likely a 1.5s ease-in-out keyframe with subtle scale (1.0 → 1.05) and opacity (0.85 → 1.0) cycles. CSS-only (Tailwind `animate-pulse` may be close enough; a custom keyframe gives more control over speed and subtlety). On-brand for Aether Intelligence Deep Midnight; doesn't compete with the message text content.
- **D-068.5-06:** **Pulse fires ONLY on `Message.runStatus === 'streaming'`.** NOT on terminal states (`completed` / `cancelled` / `failed` / `timed_out` — those have their own static affordances, e.g., Resume button on `failed` and `timed_out`). NOT on tool-execution stages (Phase 067 already added `tool_call_stage` SSE events with their own UI cards — double-pulsing would feel busy).
  - **Research correction (2026-05-13):** The original CONTEXT.md said `'running' || 'queued'` mirroring the ROADMAP SC#3 phrasing, but RESEARCH.md three-source verified the actual codebase enum is the 5-value `'streaming' | 'completed' | 'failed' | 'cancelled' | 'timed_out'` (`types/index.ts:113` + `models/message.py:44` + migration 035 + 038 CHECK). The intent is unchanged — pulse fires during the only non-terminal state the system actually has — but the literal gate value MUST be `'streaming'`. The roadmap SC#3 should be re-read with this substitution.
- **D-068.5-07:** **Pulse stops on terminal SSE arrival.** When the SSE terminal event (`stream_end`, `cancelled`, `failed`, `timed_out`) is replayed for a turn, the pulse animation removes immediately. If the user opens a thread mid-stream from another tab, the pulse remains until the active SSE consumer's terminal event arrives — exactly Claude.ai's behavior.

### Fetch-failure retry UX

- **D-068.5-08:** **Retry affordance: sticky banner at top of message list + manual Retry button.** Reuses the existing `fallbackNotice` banner pattern at `ChatArea.tsx:268-272` (amber-400 background, compact, sits above `<MessageList>`). Cached content remains visible underneath — the user is never blanked. Click on Retry re-fires the reconcile action.
- **D-068.5-09:** **Auto-retry policy: silent single retry at 1s, then banner.** If the first `GET /threads/{id}/messages` fails, wait 1s and try once more silently. If that also fails, surface the sticky banner. Closes the common transient-blip case (tab wake-up 5xx, brief network drop) without bothering the user. Two retries with longer backoff was considered but rejected: delays the manual affordance to ~4s, which feels broken on a real outage.
- **D-068.5-10:** **Banner is dismissable.** User can dismiss the banner manually; cached content remains, no auto-redisplay until another reconcile attempt fails. Standard banner UX.

### First-ever-load placeholder (cold cache miss)

- **D-068.5-11:** **Cold-load placeholder: ~3 skeleton message bubbles with shimmer.** For a thread with no in-memory bucket AND no localStorage entry (e.g., a thread the user clicks from a deep link in another tab, or after LRU eviction), render ~3 alternating user/assistant skeleton bubbles using shadcn `<Skeleton>` + a shimmer animation that matches the in-flight pulse's keyframe. Sets correct mental model ("messages incoming"), occupies the spatial structure the content will eventually fill, prevents layout shift, and uses the same animation vocabulary as the pulse for visual coherence.
- **D-068.5-12:** **Skeleton clears as soon as the first message renders.** Either the reconcile response arrives or a localStorage snapshot is hydrated (whichever wins the race). No "skeleton + content" overlap state.

### Locked invariants that MUST survive this phase

- **L-068.5-01:** **Phase 067.5 Branch D-3 guard** at `streamsStore.clearThreadBucket` (the per-surface adaptation of `useMessages.ts:572-590`) — refuses to wipe a bucket whose thread is `streamingThreadIdRef.current`. Phase 068 preserved it; Phase 068.5 must NOT introduce a code path that bypasses it (e.g., the localStorage hydrate path must NOT overwrite a bucket where streaming is in flight).
- **L-068.5-02:** **D-063.1-12 `loadMessages` MERGE three-clause filter** for temp placeholders — `m.id.startsWith('temp-') && m.runId && !dbRunIds.has(m.runId)`. The reconcile-merge step in this phase composes with this filter, doesn't replace it. Server response replaces non-streaming non-temp DB messages; temp placeholders pinned to active runs survive the merge; bucket of a streaming thread is never clobbered.
- **L-068.5-03:** **`bucketsBySurface: Map<SurfaceId, Map<thread_id, Message[]>>`** shape is unchanged. localStorage cache mirrors the same nested shape so hydration is a structural assign, not a transformation.
- **L-068.5-04:** **`Message.runStatus`** semantics from Phase 063 + Phase 066 (D-063-04, D-066-04, D-066-09) — Resume button still surfaces on `runStatus === 'failed' || 'timed_out'`; the pulse coexists with these terminal-state affordances without overlap (pulse only on `running`).
- **L-068.5-05:** **Reconcile-merge precedence** — server response is authoritative for non-streaming non-temp content; the Branch D-3 guard protects the streaming bucket; temp placeholders are pinned per L-068.5-02. The hydrate-from-localStorage path is "pre-paint cache" — it runs BEFORE the reconcile fetch and is OVERWRITTEN by the server response when it arrives (subject to Branch D-3 + temp-placeholder filter).

### Reconcile timing

- **D-068.5-13:** **On mount of a chat surface, the reconcile fetch fires in parallel with the localStorage hydrate.** Hydrate is synchronous (single localStorage read on the critical path); reconcile is async (network round-trip). Render order: hydrate → first paint within 100ms of route-render → reconcile resolves → server-fresh data replaces cache (subject to L-068.5-05). On a warm in-memory bucket, hydrate is a no-op and reconcile still fires as the freshness check.

### Backend touchpoint (research-driven)

- **D-068.5-14:** **RESOLVED — `runStatus` is already exposed on `GET /threads/{id}/messages`.** RESEARCH.md three-source verified: `backend/app/api/threads.py:793-814` already does the JOIN-and-merge with `public.runs`; `backend/app/models/message.py:44` `MessageResponse.run_status` is already a 5-value `Literal`; `frontend/src/lib/api.ts:67-100` `getMessages` mapper already maps snake_case `run_status` → camelCase `runStatus`. **NO BACKEND CHANGE REQUIRED.** Phase 068.5 stays pure frontend.

### Plan ordering (advisory; gsd-planner finalizes)

ROADMAP says 2 plans (placeholder, refined here). Recommended split:

1. **Plan 1 — Cache substrate + cold-render fix.**
   - Add localStorage persistence layer to `streamsStore.ts`: write throttle (~500ms) + LRU eviction + surface-keyed JSON shape (D-068.5-01..04).
   - On `<StreamsProvider>` mount, hydrate `bucketsBySurface` from localStorage BEFORE first render.
   - Resolve the in-app "blank window" by either (a) removing the unconditional `clearMessages()` call at `ChatArea.tsx:134` on thread switch (the bucket already carries the prior thread's data via `bucketsBySurface`), or (b) replacing it with a guarded variant that only clears if the bucket is genuinely stale. Planner picks; both shapes solve the in-app case.
   - Add skeleton-message placeholder component for cold-load (D-068.5-11..12).
   - Backend touchpoint: confirm or add `runStatus` per-message on `GET /threads/{id}/messages` (D-068.5-14).
   - Vitest: regression suite for L-068.5-01..05.

2. **Plan 2 — In-flight pulse + retry banner + Chrome MCP UAT.**
   - Add CSS keyframe (1.5s breathing pulse on Sparkles brand mark) + apply when `Message.runStatus === 'running'` (D-068.5-05..07).
   - Add sticky retry banner (reuse `fallbackNotice` pattern) + silent-1s-then-banner retry policy (D-068.5-08..10).
   - Chrome MCP UAT against SC#5 (cold-cache F5 → <100ms paint, <1s reconcile, no blank).
   - 5/5 lived-experience UAT cycles mirroring Phase 067.5 precedent (the SC#6 binding gate that flips BUG-260513-01 from `folded` to `closed` at `/gsd:complete-milestone`).

### Claude's Discretion

- **Throttle implementation** — lodash `_.throttle` (already a dependency? planner checks) vs DIY `setTimeout`-based vs RAF-coalesced. Pick whatever is smallest.
- **localStorage key encoding** — single packed JSON blob (`agentic-rag.streams` → `{chat: {tid: msgs[], ...}, ...}`) vs per-thread keys (`agentic-rag.streams.chat.tid` → `msgs[]`). Per-thread reads are cheaper at the LRU touch point; single-blob writes are atomic. Pick whichever keeps the hot path simpler.
- **LRU eviction trigger** — write-time only (every write checks size and evicts oldest) vs lazy (only on quota error). Lazy is cheaper and the typical case never hits the cap.
- **Skeleton component reuse** — shadcn `<Skeleton>` directly vs a custom `<MessageSkeleton>` wrapper. Wrapper is nicer for styling consistency; direct is shorter.
- **Pulse keyframe values** — exact opacity / scale / duration. The spec is "soft breathing"; planner tunes to match Aether Intelligence design feel.
- **Whether the unconditional `clearMessages()` at `ChatArea.tsx:134` stays, gets removed, or gets guarded** — both shapes solve the in-app blank window; planner picks based on regression-cost vs structural-clarity tradeoff.
- **Auto-retry counter visibility** — do we expose a tiny "retrying…" hint between the silent retry and the banner, or stay completely silent? Researcher / planner picks based on UX feel; the spec is "silent retry, then banner if still failing."

<specifics>
## Specific Ideas

- **"Mimic Claude.ai" is the load-bearing UX reference.** Cached content paints first; reconcile happens silently; the breathing brand-mark glow is the "still working" signal. The phase's design choices should pattern-match Claude.ai behavior wherever a coin-flip exists — that's the reference the user provided verbatim ("this mimics the behaviour of claude").
- **The 5/5 lived-experience UAT cycle pattern is binding (SC#6).** Phase 067.5 closed STREAM-04-correctness-round3 with literal 5/5 user-driven cycles; Phase 068.5 closes BUG-260513-01 the same way. The Chrome MCP UAT (SC#5) is the automated half; the 5/5 cycles is the manual half. Both required for milestone close.
- **Surface-agnostic by design.** The localStorage cache MUST be keyed by `SurfaceId` (D-068.5-04) so v3.0 Skill Studio's eval pane gets F5 resilience for free. This is consistent with Phase 068's D-068-04 / D-068-05 surface-agnostic store design.
- **The Branch D-3 guard is THE binding regression net.** The localStorage hydrate path is a new code path that touches bucket state; it MUST consult the same guard that `clearThreadBucket` consults. Vitest regression: hydrate during active streaming must NOT clobber the streaming bucket.
- **`runStatus` field reuse, not a new API.** Don't invent a new "in-flight" boolean on `Message`; the existing 5-value enum is the right shape and the pulse gating composes with the Resume button gating without conflict.
- **No new SSE event types.** `tool_call_stage`, `code_stdout`, `tool_args_progress` already exist; the pulse reads run-level state, not tool-level state. Do not introduce a new "in_flight" SSE event.

</specifics>

<deferred>
## Deferred Ideas

- **IndexedDB for unlimited cache + offline support.** Considered as the durable-cache backend. Rejected for v2.6 — localStorage covers the 5–10 active threads case at zero complexity cost; IndexedDB earns its place only when offline-first becomes a goal (likely v3.x / v3.4 Automations). Re-open trigger: a customer demands offline access OR localStorage quota errors start showing up in production telemetry.

- **Cross-tab cache sync via BroadcastChannel.** Considered for the case where the user opens the same thread in two tabs — Tab A's reconcile updates Tab B's cache without Tab B re-fetching. Rejected for v2.6 — BUG-260513-01 is a single-tab UX issue; multi-tab sync adds a state-machine without solving the reported bug. Re-open trigger: explicit multi-tab UX user report.

- **Per-message granular caching.** Today caching is per-thread (whole message array per thread bucket). A future optimization could cache individual messages keyed by message_id, allowing partial-update reconcile. Rejected for v2.6 — no message is large enough today to justify the complexity; per-thread caching's worst case is 40 KB. Re-open trigger: messages start carrying multi-MB embedded payloads (image dataURLs, etc.).

- **Per-token shimmer on streaming text.** Considered as an alternative to the brand-mark pulse (D-068.5-05). Rejected — visually noisier; Claude.ai uses brand-mark glow not text shimmer; user picked the brand-mark direction explicitly. Re-open trigger: A/B test data shows the brand-mark pulse is missed by users.

- **Two-retry exponential backoff (1s + 3s) before banner.** Considered as a heavier auto-retry policy (D-068.5-09 picked single 1s retry instead). Rejected — delays the manual affordance to ~4s on a real outage, which feels broken. Re-open trigger: production telemetry shows >20% of reconcile failures resolve on the second silent retry; bump to two.

- **Animated typing-dots row appended below text** (classic three-dot bounce). Considered for the in-flight pulse style; rejected in favor of brand-mark glow + breathing pulse. Re-open trigger: usability testing shows the brand-mark pulse isn't legible enough.

- **Toast notification for fetch failures.** Considered as alternative placement for the retry affordance. Rejected — bug update explicitly says "inline retry over cached content"; toast is too easy to miss. Re-open trigger: none anticipated.

- **Centered subtle spinner + "Loading conversation…" for cold-load.** Considered as an alternative to skeleton bubbles (D-068.5-11). Rejected — skeleton bubbles pre-paint the spatial structure of the eventual content, preventing layout shift; spinner doesn't. Re-open trigger: none anticipated.

- **Keep current blank-state behavior for cold-load (200–800ms is brief).** Considered as a do-nothing option for D-068.5-11. Rejected — bug report explicitly cites the blank state as the user-visible problem; even rare cold-load shouldn't reintroduce it. Re-open trigger: none anticipated.

- **sessionStorage instead of localStorage** (same-tab F5 only). Considered as a smaller-scope cache backing. Rejected — doesn't help when the user reopens the app from a fresh tab (a common pattern). localStorage's cross-tab persistence is load-bearing. Re-open trigger: privacy / tenant-isolation requirement that disallows cross-session persistence (likely v3.2 multi-tenancy concern).

- **Bigger backend touchpoint — `GET /threads/{id}/snapshot` combined endpoint** (replaces the 3-call sequential chain). That's already scoped as POLISH-SEED-008-01 in Phase 075. Phase 068.5 does NOT scope this — it consumes whatever `GET /threads/{id}/messages` gives today (possibly augmented with `runStatus`, per D-068.5-14). Re-open trigger: none — Phase 075 owns the snapshot endpoint; Phase 068.5 ships independently.

- **Pulse during 'queued' state.** Considered. Rejected — queue-state window is typically <1s; adding pulse during it creates visual churn. Re-open trigger: telemetry shows queued-state durations exceed 2s regularly (would indicate a backend producer-task starvation issue worth its own seed).
