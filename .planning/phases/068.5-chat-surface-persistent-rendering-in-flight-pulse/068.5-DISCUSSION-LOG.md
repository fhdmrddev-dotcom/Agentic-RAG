## F5 / refresh cache strategy

### Q1 — localStorage snapshot vs in-memory only

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — add localStorage snapshot | Persist last N threads' messages to localStorage; hydrate `bucketsBySurface` from localStorage before first render. Closes the F5 case explicitly called out in the bug update + matches Claude.ai behavior. Adds ~30–50 LOC + size-budget + eviction logic. | ✓ |
| No — in-app navigation only | Rely on `bucketsBySurface` alone. Thread switch and sidebar nav clicks paint instantly; F5 still shows blank/skeleton until reconcile returns. Smaller scope but doesn't close the bug-update "refresh" symptom. | |
| Yes — but sessionStorage (same-tab F5 only) | sessionStorage survives same-tab F5 but resets on tab-close / new-tab. Cheaper than localStorage but doesn't help users who reopen the app from a fresh tab. | |

**User's choice:** Yes — add localStorage snapshot (Recommended)
**Notes:** Locks D-068.5-01. The bug update explicitly mentions "refresh" + user said "mimic Claude.ai" — localStorage is the closest minimal-cost match.

### Q2 — Cache scope (how many threads)

| Option | Description | Selected |
|--------|-------------|----------|
| Most-recent thread only | ~40KB worst case. Smallest footprint; switching to any OTHER thread post-F5 falls back to skeleton + reconcile. Simple, robust. | |
| 5–10 most-recent threads (LRU) | ~200–400KB typical, ~2MB worst case. Covers the common "jump between a few active chats" pattern. Adds an LRU list + eviction logic (~20 LOC). | ✓ |
| All threads up to ~4MB budget | LRU-evict oldest by accessed-at when over budget. Best F5 coverage; biggest moving parts. | |

**User's choice:** 5–10 most-recent threads (LRU) (Recommended)
**Notes:** Locks D-068.5-02. Stays well within the ~5MB origin cap; matches Claude.ai's "few active chats" UX.

### Q3 — Write cadence

| Option | Description | Selected |
|--------|-------------|----------|
| Throttled — every ~500ms + on terminal events | Trailing-edge throttle at ~500ms during streaming, plus immediate flush on terminal events (stream_end / cancelled / failed / timed_out) and on thread switch. Keeps snapshot within ~500ms of reality; minimizes write storm. | ✓ |
| Only on terminal events + thread switch | Skip per-token writes entirely. Lightest impact; live-mid-stream content lost on F5 (but stream-resume + reconcile re-fetches it via Phase 062 replay API). | |
| Every bucket update | Simplest code; fires 100+ writes/sec during fast streams. Risks main-thread jank on mobile. Not recommended. | |

**User's choice:** Throttled — every ~500ms + on terminal events (Recommended)
**Notes:** Locks D-068.5-03. Implementation: planner picks throttle library (lodash or DIY `setTimeout`-based).

### Q2 — Pulse scope (which run states trigger it)

| Option | Description | Selected |
|--------|-------------|----------|
| Only 'running' | Pulse only when `runStatus === 'running'`. 'queued' is so brief (<1s) that pulsing during it adds visual churn. Keeps the signal precise. | ✓ |
| 'running' + 'queued' | Fire on both. Slightly more honest "work-in-progress" signal; matches ROADMAP SC#3 phrasing verbatim. | |
| 'running' + 'queued' + tool-execution stages | Also pulse while tool calls are in flight even though token streaming paused. More signal-rich but Phase 067 already added `tool_call_stage` SSE events with their own UI cards; double-pulsing may feel busy. | |

**User's choice:** Only 'running' (Recommended)
**Notes:** Locks D-068.5-06. Avoids double-signaling with Phase 067 tool-call cards; keeps the signal "the model is actively generating right now."

## Fetch-failure retry UX

### Q1 — Retry affordance placement

| Option | Description | Selected |
|--------|-------------|----------|
| Sticky banner at top of message list + manual Retry button | Compact dismissable banner pinned above cached messages: "Couldn't reload latest — [Retry]". Matches existing `fallbackNotice` pattern at `ChatArea.tsx:268-272` (amber-400 banner). Most discoverable, low visual noise. | ✓ |
| Footer pill below last message + retry | Small pill at the very bottom of the cached list. Less prominent; user might miss it on long threads. | |
| Auto-retry 2x with exponential backoff, then top banner | Silent retry at 1s + 3s; if still failing, show banner. Adds retry-state machine (~15 LOC). | |
| Toast notification + retry button | Shadcn toast bottom-right. Cleanest visual but easy to miss if user focused on chat content. | |

**User's choice:** Sticky banner at top of message list + manual Retry button (Recommended)
**Notes:** Locks D-068.5-08. Reuses the existing `fallbackNotice` styling pattern — visually matches what's already in the codebase.

### Q2 — Auto-retry policy

| Option | Description | Selected |
|--------|-------------|----------|
| Silent single retry at 1s, then banner | If first GET fails, wait 1s and retry once silently. If that also fails, show banner. Closes the common transient-blip case without bothering the user. | ✓ |
| Two retries with 1s / 3s backoff, then banner | Catches longer outages silently but delays manual affordance to ~4s, which feels broken on a real outage. | |
| No auto-retry — banner on first failure | Simplest. Every transient blip shows the banner; user clicks Retry. Honest but noisy on flaky connections. | |

**User's choice:** Silent single retry at 1s, then banner (Recommended)
**Notes:** Locks D-068.5-09. Tiny code, big UX win.

## Claude's Discretion

Areas where the planner gets to choose:

- **Throttle implementation** — lodash `_.throttle` (if already a dep) vs DIY `setTimeout`-based vs RAF-coalesced. Pick smallest.
- **localStorage key encoding** — single packed JSON blob vs per-thread keys. Per-thread reads are cheaper at LRU touch points; single-blob writes are atomic. Either works.
- **LRU eviction trigger** — write-time vs lazy (only on quota error). Lazy is cheaper and the typical case never hits the cap.
- **Skeleton component reuse** — shadcn `<Skeleton>` directly vs custom `<MessageSkeleton>` wrapper. Wrapper is nicer for styling consistency; direct is shorter.
- **Pulse keyframe values** — exact opacity / scale / duration. Spec is "soft breathing"; planner tunes to Aether Intelligence design feel.
- **Whether `clearMessages()` at `ChatArea.tsx:134` is deleted or guarded** — both shapes solve the in-app blank window; planner picks based on regression-cost vs structural-clarity tradeoff.
- **Auto-retry counter visibility** — tiny "retrying…" hint between silent retry and banner, or stay fully silent? Planner picks based on UX feel.

## Deferred Ideas

Captured fully in CONTEXT.md `<deferred>`. Summary:

- IndexedDB / offline support — overkill for v2.6; localStorage covers the case.
- Cross-tab cache sync via BroadcastChannel — out of scope (single-tab bug).
- Per-message granular caching — no message large enough today to justify.
- Per-token shimmer text — rejected in favor of brand-mark glow.
- Two-retry exponential backoff — rejected (feels broken on real outages).
- Animated typing-dots — rejected in favor of brand-mark glow.
- Toast for fetch failures — rejected (too easy to miss).
- Centered spinner / blank-state for cold-load — rejected (skeleton wins).
- sessionStorage — rejected (doesn't help fresh-tab reopen).
- Bigger backend touchpoint (`GET /threads/{id}/snapshot`) — owned by Phase 075 (POLISH-SEED-008-01); Phase 068.5 ships independently.
- Pulse during 'queued' state — rejected (sub-second window adds churn).
