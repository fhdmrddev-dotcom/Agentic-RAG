## Gaps

### Gap-01 — MessageSkeleton renders on NEW (empty, not-loading) chats
- **Cycle / SC:** SC#6 exploratory cycle 1 (user opening a new chat during SC#6 setup)
- **Failure mode:** Opening a brand-new chat (or any thread with `messages.length === 0` and no active fetch) shows the 3-bubble shimmer skeleton — implying "messages are loading" when in fact there's nothing to load.
- **Root cause:** `MessageList`'s empty-state ternary gates skeleton on `messages.length === 0` (Plan 01 Task 4-5). This conflates "loading" with "genuinely empty thread." New chats with no messages and no in-flight reconcile still trigger the skeleton.
- **Reproduction:**
  1. Click "New Chat" in the sidebar.
  2. Observe: skeleton bubbles appear with shimmer animation even though there are no messages to load.
  3. Sending a message replaces the skeleton with the new bubbles correctly, so the bug is cosmetic, not functional.
- **Fix direction:** Gate the skeleton on an explicit "loading" signal (e.g., `loadingByThread: Map<thread_id, boolean>` in `streamsStore`, set true at the top of `loadMessages.tryFetch(0)`, false on success/abort/final-failure). MessageList renders skeleton only when `loadingByThread.get(activeThreadId) === true && messages.length === 0`. New chats never trigger loadMessages, so the loading bit stays false, skeleton stays hidden.
- **Escalation:** Inline Plan 02 follow-up commit OR Plan 03 gap closure — surgical (5-10 LOC + 1 store slot + 1 Vitest test).

### Gap-02 — Cold-load thread switch mid-stream gets stuck on persistent skeleton (D/E threads)
- **Cycle / SC:** SC#6 exploratory cycle (user driving through A→B→A→C→A→D→A→E→A while A was streaming)
- **Failure mode:** While Thread A was streaming, switching to never-previously-visited Threads D and E left them stuck on the pulsing skeleton — they NEVER resolved to message content. Going back to A always worked. Previously-visited Threads B and C worked correctly (they had cached entries). Combination triggering the bug: **cold-cache target + concurrent active stream on another thread**.
- **Root cause:** `StreamsProvider.tsx:867` in `loadMessages`:
  ```ts
  if (isSendingRef.current) return
  ```
  The comment one line above states: "Protect optimistic placeholders if a send is in flight on the **same thread**." But the code does NOT check thread identity. When the user is streaming Thread A (so `isSendingRef.current === true`), and clicks Thread D (cold cache), `loadMessages('D')` runs:
  1. `tryFetch(0)` aborts the previous controller (no-op since nothing pending)
  2. `getMessages('D', controller.signal)` succeeds with D's message data
  3. Line 865 `if (activeThreadIdRef.current !== 'D') return` passes (user is on D)
  4. Line 867 `if (isSendingRef.current) return` — **returns early because A is sending**
  5. Bucket for D is never populated. MessageSkeleton renders forever.

  B and C worked because their buckets were already populated from earlier visits — the reconcile still bailed silently at line 867 but didn't matter visually since `bucketsBySurface.get('chat').get('B'/'C')` had cached content.
- **This bug pre-dates Phase 068.5** — it lives in Phase 068's `loadMessages` action. Phase 068.5 SURFACED it by adding MessageSkeleton: before, the user saw a blank window for ~1s and assumed the thread was loading; now they see a persistent shimmer that never resolves.
- **Reproduction:**
  1. Send a long prompt to Thread A. Wait for streaming to begin.
  2. While A is streaming, click on a never-previously-visited thread (D).
  3. Observe: skeleton bubbles appear and pulse indefinitely. Network tab shows the `GET /threads/D/messages` request succeeded with full message data — but the messages never reach the DOM.
  4. Click back to A: A still works.
  5. Wait for A's stream to terminate. Click D again: now D loads correctly (because `isSendingRef.current === false`).
- **Fix direction:** Change line 867 from `if (isSendingRef.current) return` to a thread-aware predicate. Two acceptable shapes:
  - Tightest: `if (isSendingRef.current && activeThreadIdRef.current === threadId) return` — but `activeThreadIdRef.current` was already verified at line 865, so this collapses to "skip merge only if the active thread is the one that's sending AND we just got its messages." Equivalent rewrite: `if (isSendingRef.current && sendingThreadIdRef?.current === threadId) return` — requires a new ref to track WHICH thread is the active sender.
  - Pragmatic: Add a `sendingThreadIdRef: useRef<string | null>(null)` set/cleared by the existing sendMessage action body. Then `if (isSendingRef.current && sendingThreadIdRef.current === threadId) return` is the correct guard.
- **Escalation:** Inline Plan 02 follow-up commit OR Plan 03 gap closure — surgical (1 new ref + 2 assignment sites in sendMessage + 1 line change at 867 + 1 Vitest test).
