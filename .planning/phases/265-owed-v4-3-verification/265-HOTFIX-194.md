# 265 hotfix — migration 194: org plan columns are not client-writable

**Finding (R265-audit-fixes-01, from `265-REVIEW-audit-fixes.md`):** `anon` and `authenticated` held TABLE-level
INSERT/UPDATE on `public.organizations`, and the only UPDATE policy is `current_user_has_permission(id, 'org:manage')`.
Any org admin could PATCH their own `subscription_tier` or `add_ons` through PostgREST and pass every v4.3 tier gate.

**Why this was fixed inside 265, against D-04:** the fix has schema surface, so D-04 would route it to a later phase.
The operator ruled it a live security hole in production and ordered it fixed now. That override is recorded here and
in `STATE.md → Guardrail overrides`.

## Why nothing legitimate broke

No app code writes `organizations`. Org creation runs through the SECURITY DEFINER functions
`create_org_with_default_dept` / `handle_new_user` (verified `prosecdef = true` on prod). The backend pool connects as
postgres / service_role. Plan changes stay a service-role / SQL-editor action.
