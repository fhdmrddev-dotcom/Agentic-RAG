<objective>
Make typing "continue" after a tool-limit pause resume the same paused run, behave exactly like the
Continue button, and make Continue resume on the run's own model, with a visible "Continuing…"
state. Backend and frontend ship together so the wire contract (`continued: true`) never exists on
one side only.

Purpose: SC#3 (typed continue resumes the paused run; production evidence: the user typed
"continue" and got a NEW run on a different capacity path) and SC#1's "Continue resumes the same
run" (orchestrator ruling 4: today a continuation runs on the operator default model).

Output: `typed_continue.py`, the one-branch gate in `send_message`, the model/provider carry in
`continue_run` → `spawn_continuation_run`, the client word list + lockstep fence, the
`continuingThreads` slice, the typed path in `sendMessage`, and the card's "Continuing…" state.

Plan shape (D-21 / G-8): its own plan because it shares no file with plan 01 (agent loop) or plan
02 (knobs, the only DB-mutating plan); it is code + mocked tests only, so it runs in wave 1 beside
them.

Why one plan at 18 files (WARNING 1, not split): the backend gate, the typed-continue frontend path
and the "Continuing…" state are ONE contract. D-14 says a typed continue must behave exactly like
the button, which is only provable when the server's `continued: true` reply, the client's
skip-the-bubble branch and the card state ship and are tested together; a split would leave one
side of the wire live without the other between waves. 8 of the 18 files are tests or fixtures,
and a fifth plan costs more in worktree / merge overhead than it saves (G-8 caps at 3-5).
</objective>
