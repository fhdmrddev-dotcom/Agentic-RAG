# Phase 292.1 Plan 03: Typed Continue and Same-Model Continue Summary

Typing a continue word (`continue`, `keep going`, `go on`, `carry on`, `resume`, `proceed`) after a tool-limit pause now resumes the same paused Deep run through `runs.continue_run`, exactly like the button. Both the typed path and the button now resume on the run's own stored model and provider. A terminal Deep run refuses Continue with a 409. The Continue card reads "Reached the tool-use limit for this turn." and shows "Continuing…" until the run pauses again or ends.

## What was built

**Task 1 (backend gate).** `typed_continue.py` holds `CONTINUE_WORDS` and `is_continue_word`, which casefolds, collapses whitespace, trims, and strips trailing `.!?…`. In `threads.py`, `_typed_continue_or_none` runs its checks cheapest first:
1. Return `None` for a workflow kickoff or a harness thread.
2. Return `None` unless the text is a continue word.
3. Read the latest run with the 244 SQL (no status predicate) over the RLS user connection. A failed read logs a warning and falls through to a normal send.
4. Return `None` unless the run is `cap_paused` and `continues_used < settings.max_continues_per_run`.
5. Lazy-import `continue_run` and await it.
6. A refused `JSONResponse` or dict falls through to a normal send. Otherwise it returns 200 `{continued: true, run_id, message_id: null, continues_used, continues_remaining}`.

`send_message` gains exactly one `if`.

**Task 2 (same-model + SEED-324).**
- `continue_run`'s Step-1 select now reads `model, provider`, and the Deep spawn passes `model=row.get("model"), provider=row.get("provider")` (None-safe).
- A new `elif row.get("status") in _TERMINAL_RUN_STATUSES` arm on the Deep side raises 409 before the counter write and the spawn.
- `spawn_continuation_run(..., model=None, provider=None)` is byte-identical when both are None. With a stored pair it calls `_resolve_continuation_model`, which takes three callables resolved late off `app.api.threads`: `override_provider`, `get_model_capability_async`, and `load_all_model_overrides`.

**Task 3 (frontend).**
- `continueWords.ts` mirrors the word list as a rendering hint. It is pinned to the backend by a `?raw` lockstep fence over `typed_continue.py` and the shared JSON fixture, which also checks that it really read those files.
- `PostMessageResponse.message_id` is now `string | null`, and the type gains `continued` and `continues_*`.
- The store gains a `continuingThreads` slice with module-level `markContinuing` / `clearContinuing` writers. It is not a `WorkflowLock` field.
- `onCapPaused` calls `clearContinuing`, and the `clearWorkflowLockForThread` action deletes the thread from `continuingThreads` in the same `setState`.
- `sendMessage` changes:
  - Its three optimistic writes now live in one `insertOptimisticTurn` closure, unchanged in order and content.
  - For a hinted word the turn is held back, then made late on a normal 201.
  - On `continued: true` it calls `markContinuing`, drops any optimistic turn this call made, and returns through the `finally`.
  - On an error it inserts the held-back turn first, so the existing error arms see what they always saw.
- `MessageItem` reads `continuingThreads` straight from the store and shows the new sentence plus `Continuing…` (button disabled, spinner). A press that is not refused marks the thread as continuing.

## Fallback checks that exist (Task 2 requirement)

- **Provider:** `override_provider` returns its input unchanged when the provider is gone or has no key. The fallback triggers when `active_provider != provider` after the override.
- **Model capability:** `get_model_capability_async(model, provider_hint)` raising triggers the fallback. In practice it swallows DB-tier errors and falls through to inference, so this is a guard against an unexpected raise.
- **Registry disabled flag:** this flag exists. `load_all_model_overrides()` is the only read that returns disabled rows, and a row with `enabled is False` triggers the fallback. Removed tombstones (`removed = true`, mig 179) are already excluded from that read and resolve by inference, so they are not a fallback case.
- On fallback, exactly one WARNING: `continuation <run_id>: stored model/provider <m>/<p> cannot be resolved; continuing on <fm>/<fp>`.

**3. [Rule 2 - Correctness] A held-back typed continue that errors gets its turn back**
- **Issue:** Not in the plan. Without this, a typed "continue" that hit a network error or a 409 would have shown a failure receipt with no user bubble and no restored draft.
- **Fix:** The `catch` calls `insertOptimisticTurn()` first when the turn was held back, so the existing rollback and receipt arms behave exactly as before.
- **Commit:** 586db841e

**4. [Rule 3] `message_id` narrowing in sendMessage**
- **Issue:** Making `PostMessageResponse.message_id` nullable broke the id swap's types.
- **Fix:** The destructured value is aliased to `postedMessageId`, and `const message_id = postedMessageId ?? userMsg.id` is set after the continued arm. The swap code is unchanged; a 201 always carries the id.
- **Commit:** 586db841e
