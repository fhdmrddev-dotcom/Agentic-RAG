## Summary

The bug has a deeper cause than the CONTEXT names, and it changes what "work still pending" can mean. **On the forced-final round the request carries no tools at all** for the OpenAI-compat path (OpenAI, OpenRouter, DeepSeek, Zhipu, MiniMax, Moonshot, self-hosted) and the Google path: `create_adaptive_streaming_chat` sends `tools` only when `tool_choice == "auto"` (`openai_service.py:2502-2570`), `google_service.py:443` sends `[]` when `force_no_tools`, and the Responses adapter does the same (`openai_responses.py:507`). Only Anthropic keeps tools with `tool_choice: {"type": "none"}` (`anthropic_service.py:206-207`). OpenRouter's own docs say *"The `tools` parameter must be included in every request ... so the router can validate the tool schema"* [CITED: openrouter.ai/docs/guides/features/tool-calling]. A DeepSeek upstream that receives tool-call history but no `tools` has no tool parser engaged, so the model's next call comes back as raw DSML text in `content`. The structured buffer is then empty, the cap check at `agent_loop.py:2849` is false, and the markup becomes the answer. Do not change what the final round sends. That would alter every provider's last turn, which is out of scope and breaks D-14 byte-identity. The parser this phase writes is the correct fix.

**The measured format set is wider than one bar vs two bars.** Production holds exactly one row (orchestrator SQL). It is DSML with one bar and a space: `<｜DSML｜ calls>`. **The local dev DB was reachable** and holds 16 assistant rows across five families. Three are DSML spellings from DeepSeek: two-bar `<｜｜DSML｜｜tool_calls>` (native `deepseek-v4-flash`, three rows), one-bar no-space `<｜DSML｜tool_calls>` (OpenRouter `deepseek/deepseek-v4-pro`, one row), and the prod one-bar plus space. Two are XML forms, and they come only from **self-hosted** models: Qwen-style `<tool_call><function=NAME><parameter=K>V</parameter></function></tool_call>` (six rows) and GLM-style `<tool_call>NAME<arg_key>K</arg_key><arg_value>V</arg_value></tool_call>` (four rows). A Gemma-style `<|tool_call>call:NAME{k:v}<tool_call|>` with non-JSON arguments also appears (three rows). **No OpenRouter-routed model has ever emitted an XML tool tag** in either DB, so the ROADMAP's "OpenRouter XML" was a guess. Recommendation: **parse DSML (every spelling: one or two fullwidth bars, block name `tool_calls` / `function_calls` / ` calls`)**. Put the **five measured families into a provider-blind detector** that strips and words, so unknown or unparseable forms never reach the answer.

The Continue path already exists and is sound: one writer of `cap_paused → streaming` (`runs.py:1281-1286`), and a carrier read by thread (`db/runs.py:179-230`). Four latent problems surface the moment text calls feed it, and the plan must handle each one. (1) An empty-queue pause (D-07) writes a carrier that `load_cap_paused_tool_calls` cannot match, so a later Continue re-runs **a previous pause's** calls. (2) The continuation resumes on the operator's **default model**, not the run's model (`run_producer.py:1051-1056`), so the per-request UAT board cannot prove "Continue resumes the same run" per provider. (3) The send door's `if` count is pinned by `test_279_org_helper.py:194-206`, so D-12's one branch must retire that fence deliberately. (4) The Continue card never shows "Continuing…" after a successful Deep continue. The lock stays `capPaused` until a terminal event (`MessageItem.tsx:853-899`, `StreamsProvider.tsx:3015`).

**Primary recommendation:** a new pure module `backend/app/services/text_tool_calls.py` owns three things: a DSML parser, a five-family markup detector/stripper, and a tag holdback. `agent_loop.py` gains a few call sites:
- one holdback `feed` in `_on_chunk`;
- one post-drain `settle` after the provider `while` loop;
- a widened cap condition;
- the knob read replacing two literals.

The adapter's deepseek-only strip in `openai_compat.py` is retired deliberately so there is one provider-blind path. Typed continue is one delegating branch in `send_message` that calls `continue_run` directly. The knobs follow the `vision_max_pages` precedent: migration 214 adds a column with DEFAULT plus a CHECK, so it is schema, not a seed.

Patterns searched that returned **0 rows** locally: `<function_calls>`, `<invoke ` (bare, non-DSML), `<tool_use>`, `[TOOL_CALLS]`, `<|python_tag|>`, `<minimax:tool_call>`, `<|tool_calls_section_begin|>`, `<｜tool` (DeepSeek-V3 legacy `tool▁call` tokens).

**DSML grammar from the vendor-side sources** [CITED: docs.vllm.ai/en/v0.22.1/api/vllm/tool_parsers/deepseekv32_tool_parser/; docs.vllm.ai/en/latest/api/vllm/tokenizers/deepseek_v4_encoding/; docs.nvidia.com Megatron-Bridge `encoding_v4`]:
- The token is `｜DSML｜`: one fullwidth bar U+FF5C on each side, no space. The block name is `function_calls` for V3.2 and `tool_calls` for V4. Invoke: `<｜DSML｜invoke name="X">…</｜DSML｜invoke>`. Parameter: `<｜DSML｜parameter name="K" string="true|false">V</｜DSML｜parameter>`.
- `string="true"` means V is raw text, inserted as-is (no JSON escaping, whitespace preserved). `string="false"` means V is `json.dumps(value, ensure_ascii=False)` (numbers, booleans, arrays, objects). The encoder emits `is_str = "true"` iff the value is a Python `str`.
- vLLM's parser regexes: `<｜DSML｜invoke\s+name="([^"]+)"\s*>(.*?)</｜DSML｜invoke>` and `<｜DSML｜parameter\s+name="([^"]+)"\s+string="(true|false)"\s*>(.*?)</｜DSML｜parameter>`, both DOTALL.
- ⚠ **The production ` calls` spelling (bar, space, `calls`) and the two-bar spelling are NOT in any published grammar.** They are measured outputs. The DeepSeek API docs now route the legacy `deepseek-v4-flash` id to **DeepSeek-V4.1-Flash-1017** [CITED: api-docs.deepseek.com/guides/function_calling]. So the native row in the UAT board serves the same model as the prod OpenRouter row. No official DeepSeek page documents DSML at all. The parser must therefore be tolerant on the opener: one or two fullwidth bars, an optional space, and any block name ending in `calls`. It should be strict on `invoke` and `parameter`.
- ASCII `|DSML|` is **not** in the measured set. The existing `test_ascii_pipe_lookalike_does_not_trigger` pins that it must not trigger. Keep it out.

**Answer to the orchestrator's question, "is an XML tool-tag form in the measured set?":** Not in production, and not from any OpenRouter-routed or native-vendor model. The XML forms F4 and F5 are real but come only from **self-hosted** endpoints (ollama / lmstudio / custom, the mig-180 path). Recommendation: the D-24 "XML" planted tests use the measured F4 shape and assert it is **caught and worded**, not executed. Parsing F4/F5 is a capability decision for local models (Open Question 1). It is not this bug.

## Root cause chain (verified in code)

1. **`agent_loop.py:2324-2325`:** the final iteration sets `force_no_tools = True`, `tool_choice = "none"`.
2. **`openai_service.py:2502`:** `elif tool_choice == "auto":` is the only branch that sets `kwargs["tools"]`. On `"none"` the request goes out **with tool-call history and no tools**. Google: `google_service.py:443`. Responses: `openai_responses.py:507`. Anthropic keeps tools and sends `{"type":"none"}`, which "prevents Claude from using any tools" [CITED: platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools].
3. OpenRouter rows resolve **NATIVE** under the default `quality` strategy (`openai_service.py:2312-2323`), so `_structured_holdback` is `None` and every delta is emitted raw (`agent_loop.py:2437-2438`).
4. `_ClosableEventStream` is built with `request.active_provider_name`, which is the **registry provider** (`agent_loop.py:2652` → `openai_compat.py:534`). For an OpenRouter row that is `"openrouter"`, so the `== "deepseek"` gate (`openai_compat.py:352`) and the `<think>` gate (`:323`) both skip. **Cause #1 (D-01) confirmed.**
5. Even on native DeepSeek, `_DSML_OPENER = "<｜｜DSML｜｜"` (`:167`) cannot match F1 or F2. **Cause #2 (D-02) confirmed.**
6. The cap check reads only `tool_calls_buffer` (`agent_loop.py:2849`). **D-04 confirmed.**

Local evidence that the **structured** cap path does fire: 7 `iteration_cap_paused` carriers exist locally. Four came from `google · gemini-3.5-flash` and two from native `deepseek-v4-flash` (those runs used all 3 Continues). So G-4 row (1) "cap hit with a structured call" is reachable on Gemini and native DeepSeek. For OpenAI / OpenRouter no structured call can arrive on the final round because no tools are sent. Expect those rows to end in prose, or in text markup (DeepSeek-family).

### Pattern 1: DSML parser (pure, measured-set tolerant on the opener, strict on the body)

**What:** `parse_dsml(text, offered: set[str]) -> DsmlResult(calls, preamble, block, ok)`.
**Rules (each is a D-07 refusal when violated):**
- Opener: `<｜{1,2}DSML｜{1,2}\s*[A-Za-z_]*calls\s*>` (fullwidth only). The first match splits **preamble** (kept) from **block** (never shown).
- Each `invoke`: name must be in **the run's offered tool list** (Pitfall 4). It must have a closer `</｜{1,2}DSML｜{1,2}\s*invoke>`. A missing closer means truncated, so unparseable.
- Each `parameter`: `string="true"` or a missing attribute means the raw value, verbatim, with no strip (vendor: "spaces for string values are not stripped"). `string="false"` means `json.loads(value)`. **On a decode failure the whole block is unparseable.** Never coerce or repair. That is the MiniMax precedent: *"never brace-balance / re-escape — that fabricates a partial dispatch"* (`agent_loop.py:173-184`).
- Output entry shape is exactly the `tool_calls_buffer` shape the loop already uses (`agent_loop.py:2767-2771`):
  ```python
  # Source: mirrors agent_loop.py:2766-2771 + tool_parser.py:125-129 (id style)
  tool_calls_buffer[idx] = {
      "id": f"call_{uuid.uuid4().hex[:24]}",   # Anthropic tool_use id-safe; same style as tool_parser
      "name": name,
      "arguments": json.dumps(args, ensure_ascii=False),
  }
  ```
**When to use:** only when the structured `tool_calls_buffer` is empty. If a provider sent structured calls AND markup, strip the markup and log it. Never double-dispatch.

### Pattern 2: one post-drain call site, not two
Both provider branches exit the `while True` at different points: the native `break` at `:2607`, and the compat path after the structured parse at `:2795`. The single common point is just after the loop (`:2833`, before the `logger.debug("Iteration %d finish_reason…")`). Put the **one** `settle(...)` call there. For the parsed case, mirror the structured branch's emits: `tool_preparing` per call (`:2775-2776`), `asyncio.sleep(0)`, and `turn_boundary` only when non-whitespace preamble was released (`:2757-2758` / `:3109`). Keep the preamble in `full_content`. The native buffer path already consumes it as the assistant turn's `content` (`:3079`) and emits `turn_boundary` at `:3109`. So for parsed calls, set `full_content = preamble` and **do not** emit `turn_boundary` yourself on that path. Pick one of the two emit sites and pin it.

The dead `dsml_leaked` block (`:2721-2746`) and `DSML_LEAK_ERROR_MESSAGE` (`:145-153`) are **replaced**. For an unparseable non-final block, use `structured_text_holdback.FAILED_CALL_NOTICE` ("*The agent's tool request was cut off or malformed, so it was not run.*") and `replace_failed_call`. That gives one copy home, already pinned against raw interpolation. The `test_dsml_leak_signal.py` cases are retired deliberately; see Pitfall 7.

### Pattern 3: provider-blind tag holdback (D-11), reusing the 273 contract
- `TagHoldback.feed(chunk) -> str` / `.finish(resolved: bool) -> str` / `.released_text`. These mirror `StructuredTextHoldback` (`structured_text_holdback.py:138-214`).
- **Openers are data** (one tuple): the measured F1-F6 openers `<｜` (then `DSML`), `<tool_call>`, `<|tool_call>`, `<function=`. Optional additions are documented vendor forms with 0 local hits: `<function_calls>`, `<minimax:tool_call>`, `[TOOL_CALLS]`, `<|python_tag|>`. Hold a trailing partial-opener suffix until the next chunk disambiguates (the 1-char split case). From a complete opener, hold to stream end (the 273 "sticky inline" rule).
- **One instance per provider call, created beside `_structured_holdback` (`:2389`) on every path.** Chain order: the tag holdback first, then the structured holdback when STRUCTURED, then emit. Accumulation stays raw: `full_content += _text` is unchanged, so `parse_structured_tool_calls` sees exactly what it saw before (273's rule).
- **Abort path:** the compat drain's `except BaseException` (`:2713-2719`) must also `drop_held` the tag holdback's held text. The native branch has no such `except` today. Add the same one-liner at the single post-drain site's error path, or document that native aborts re-raise before persist (273-REVIEW WR-06(b) parity).
- Byte-identity: concatenated deltas are identical whenever no opener appears. Chunk boundaries change only when a chunk ends in a prefix of an opener (e.g. a trailing `<`). `test_273_structured_holdback.py::test_native_delta_sequence_is_byte_identical` uses text with no `<`, so it stays green. Add a pin with `<` in prose (`a < b`, HTML) asserting **joined** deltas are identical.

### Pattern 4: cap disposition for parsed and unparseable markup
- Widen the condition at `:2849` to `if force_no_tools and (tool_calls_buffer or _cap_markup_seen):`. ⚠ `test_075_4_iteration_cap_drop.py:44-47` regex-matches the literal `if\s+force_no_tools\s+and\s+tool_calls_buffer:`. Update that fence deliberately in the same commit; see Pitfall 8.
- **Empty-queue pause (D-07):** `persist_cap_paused` with an empty buffer writes `tool_calls: []`. `load_cap_paused_tool_calls` filters `tool_calls @> '[{"kind": "iteration_cap_paused"}]'`, which an **empty array does not satisfy**. The Continue then reads the **previous** pause's carrier in that thread and re-executes stale calls. Fix: write a marker entry `{"kind": "iteration_cap_paused", "tool_call_id": null, "name": null, "arguments": null}`. Then filter name-less entries in `load_cap_paused_tool_calls` (`db/runs.py:228-230`), so the resume block (`agent_loop.py:2185`) receives `[]` and dispatches nothing. Without the filter, the resume block appends `{"role":"assistant","tool_calls":[{id:""…}]}`, and Anthropic rejects an empty `tool_use` id.
- Wording: the carrier text (`:414-416`) and the SSE message (`:433-436`) say "N tool(s) still queued". For N=0 use the limit-line copy. Recommended single line for both: **"Reached the tool-use limit for this turn."** (Claude.ai wording, BUG report). Update the card sentence at `MessageItem.tsx:857` ("Reached the iteration limit — some tools haven't run yet."), which is false for an empty queue. The copy home is the card; Claude's discretion.

### Anti-Patterns to Avoid
- **Re-gating any of this on a provider name.** That is the bug (D-10). The detector, holdback and parser run for every provider. Provider-specific handling stays only where a protocol needs it.
- **Parsing with `tool_parser._get_known_tools()`.** It is `get_tools()` with no user settings. It includes tools not offered this run (e.g. `execute_code` with the sandbox off) and excludes connector tools. Use the run's offered list: `active_tools if active_tools is not None else get_tools(user_settings)`, exactly as `available_tools` is derived (`agent_loop.py:3153-3156`).
- **Stripping markup inside a markdown code fence.** An answer explaining Qwen's `<tool_call>` format is legitimate content. The detector must skip fenced blocks and inline code; see Pitfall 6.
- **Logging the whole block.** The prod block is 12 KB of model-written code. Log length, sha256 and a bounded preview (≤ 200 chars) at WARNING. LangSmith already holds the raw output via `wrap_openai` (`openai_service.py:1615-1629`), which satisfies D-08 with no new tracing code.

## Common Pitfalls

### Pitfall 1: the forced-final round sends no tools, so "structured call at the cap" is rare by design
**What goes wrong:** the UAT board expects a structured cap call on OpenAI or OpenRouter and gets prose.
**Why:** `tools` is omitted at `tool_choice="none"` (`openai_service.py:2502`, `google_service.py:443`, `openai_responses.py:507`). Anthropic forbids tool use under `none`.
**How to avoid:** score each board row on what actually happened: structured-pause, text-pause, or prose-final (honest "no pending work"). G-4 row (1) structured should be driven on **Gemini or native DeepSeek**, where local carriers prove it happens.
**Warning sign:** a board row marked "PASS" with no `cap_paused` event.

### Pitfall 2: the empty-queue carrier resurrects an older pause's calls
`[]` does not match `@> '[{"kind":"iteration_cap_paused"}]'`, so `load_cap_paused_tool_calls` returns the previous carrier (`db/runs.py:201-227`). Use the marker entry plus the name filter (Pattern 4). Test: two pauses in one thread, the second empty, then Continue dispatches nothing.

### Pitfall 3: parsed text calls skip the offered-tool check on resume
On Continue, the resume `ToolContext` sets `available_tools=[rc["name"] for rc in _resume_calls]` (`agent_loop.py:2228`). Whatever is in the carrier is "available". `dispatch_tool` refuses only unregistered names (`tool_dispatcher.py:268-273`). Connector names (`service__action`) route to the connector handler, which re-checks posture (`tools/connector.py:40+`). So the **parser is the gate**: refuse any name not in the run's offered list *before* queuing. Test with a DSML block naming a real but not-offered tool (e.g. `execute_code` with the sandbox off), and with a connector name the composer did not switch on.

### Pitfall 4: wrong known-tool set (see Anti-Patterns)

### Pitfall 5: Continue resumes on the operator's default model, not the run's
`spawn_continuation_run` builds `user_settings = load_user_settings(...)` and `body = MessageCreate(content="", model=user_settings.llm_model, provider=user_settings.active_provider)` (`run_producer.py:1051-1056`). A per-request OpenRouter DeepSeek run therefore continues on whatever the Settings default is. This defeats SC4's per-provider proof and can replay a DeepSeek-parsed call to a different provider. It is pre-existing and not caused by this phase, but SC1 says "Continue resumes **the same run**". See Open Question 4 (recommend fixing: read `runs.model`/`runs.provider` in `continue_run` Step 1, which already selects that row at `runs.py:1174`, and pass them through). Until it is fixed, the board must set the Settings default to each row's provider before pressing Continue, or record the Continue half of that row as owed.

### Pitfall 6: false-positive stripping of legitimate answers
A user can ask "what does Qwen's tool-call format look like?". The detector strips only **outside** code fences / inline code, and only a structurally complete block (opener … closer) or an opener that runs to end of text. The holdback may still *delay* such text until stream end; `finish(False)` releases it byte-for-byte. Pin both behaviours.

### Pitfall 7: three existing tests encode the bug and must be retired deliberately
- `test_dsml_leak_signal.py::test_non_deepseek_stream_never_sets_dsml_leaked` asserts that an OpenRouter stream passes DSML through verbatim. That is cause #1, as a test.
- `test_openai_compat_dsml_strip.py` pins the two-bar opener and the deepseek-only strip (`:29-31`, `:134-140`).
- These are retired **with the reason written into the test body**, the SEED-177 / D-206-07 precedent (CLAUDE.md: "retire the fence DELIBERATELY, never trip it by surprise"). Keep `test_ascii_pipe_lookalike_does_not_trigger`'s intent: re-home it to the new module.

### Pitfall 8: two source-text fences on the exact lines this phase edits
- `test_075_4_iteration_cap_drop.py:44-47` regex-matches `if force_no_tools and tool_calls_buffer:`. Widening the condition breaks it, so update the regex in the same commit.
- `test_279_org_helper.py:194-206` (`test_send_message_gains_no_branch_relative_to_the_phase_base`, "GREEN now and forever") asserts `send_message`'s `ast.If` count equals the 279 base. D-12's branch adds one. Re-base the fence to this phase's base with the reason recorded. The ledger already records "send stays 11 `if`s (pinned) · ⛔ 0 new send-path branches". Count the gate's helper as the single new `if` and keep its logic in the helper, so `send_message` gains exactly one.

### Pitfall 9: the typed-continue response breaks the frontend's response contract
`postMessage` destructures `{message_id, run_id, model, provider}` (`StreamsProvider.tsx:2748-2753`) and stamps optimistic placeholders by `run_id`. A `continued` response has `message_id: null` and points at the **existing** run. Without the client branch (Pattern 5) the UI shows a ghost user bubble and a second assistant placeholder bound to the paused run's id.

### Pitfall 10: the composer and Continue card states
- Deep cap-pause leaves the composer **enabled**. `workflowLocked = workflowLock !== null && workflowLock.mode === "harness"` (`ChatArea.tsx:230`, 244-13), so typing works.
- The sketch skill's D5 ("composer stays disabled at cap_paused", `references/composer-and-mode.md:28-29`) is **superseded** by 244-03 / BUG-260904-05. Do not "restore" it.
- Keep `continuePending` and the new continuing slice consistent so a double press and typed-then-press cannot fire two Continues. `continue_run` increments durably but does not check status (`runs.py:1167-1292` reads no `status == 'cap_paused'` for a Deep row). A second Continue on a now-streaming run would spawn a **second** continuation. Recommend the gate (and ideally `continue_run` Step 1) refuse when `row["status"] != "cap_paused"` for Deep rows. That is a read-side check, not a new writer.

### Pitfall 11: Gemini 3 thought signatures on injected calls
Gemini 3 400s on a function call in the current turn with no `thought_signature`. The documented last-resort bypass is the literal `skip_thought_signature_validator` [CITED: docs.cloud.google.com/vertex-ai/generative-ai/docs/thought-signatures]. Carriers store no signature (`agent_loop.py:357-374`), and `google_service.py:186-205` attaches one only if present. This bites only if a DSML-parsed call is replayed to Gemini, which Pitfall 5's fix prevents. Note it; do not build the bypass this phase.

### Pitfall 12: backend unit baseline has zero headroom
The gate is `pytest tests/unit -q --continue-on-collection-errors` = **71 failed** ceiling. Retired or edited fences (Pitfalls 7-8) must stay green, not be deleted into the failed count. The seven directly related suites run in ~8 s today and are all green (93 passed, measured 2026-10-24).

| Threat | STRIDE | Mitigation |
|---|---|---|
| Prompt-injected document text makes the model **write** a tool call (now executed, D-09) | Elevation / Tampering | This was already possible for structured calls.
