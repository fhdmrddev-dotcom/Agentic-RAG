## SC#1 — "every model the product can run has an input and output rate"

### What was wrong

Measured on the live dev DB (org `22f9c615`, 1,595 real runs): **78 distinct models appear in
real runs and exactly ONE (`gpt-4o`) had a rate.** 98.3% unrated. The dashboard's headline
figure was **$0.2666**.

⚠ **A correction to the review's own wording.** `257-REVIEW.md` said the roster "was hand-typed,
not derived from `MODEL_CAPABILITIES`, which CLAUDE.md forbids". Half right, and the half that
is wrong matters: ROADMAP line 119 already recorded — correctly, and by measurement — that rates
**cannot** be derived from `MODEL_CAPABILITIES`, because it carries no structured cost field
(one prose comment, `config.py:121`). **The ROSTER should come from there. The PRICES cannot.**
Criticising 183 for not deriving prices was unfair; criticising it for covering 5 of 61 roster
models stands.

⭐ And 183's OpenAI rates were **correct** (`gpt-4o` 2.50/10.00, `gpt-4o-mini` 0.15/0.60). The
defect was coverage, not accuracy.

### What shipped

**Migration `184_model_rates_complete_roster.sql`** — 48 new rates, roster derived from
`MODEL_CAPABILITIES`, prices fetched from each vendor's own published pricing page on
2026-09-19 (provider-docs-first, per CLAUDE.md):

**Four caveats are written into the migration rather than smoothed over:** rates are applied

### The part that actually closes SC#1: a fence, not a seed

⛔ **A seed is a snapshot; the roster moves.** The next model added to `MODEL_CAPABILITIES`
would silently reintroduce the same hole. `backend/tests/unit/test_257_1_every_model_has_a_rate.py`
reads the roster **via `ast`** and the seeds from the migration files, and fails when a runnable
model has neither a rate nor a stated reason. It is deliberately **static** — a test that needs
Postgres SKIPS in CI, and a skip reads as "not failing".

Three cases, each **driven RED**:

| arm | plant | result |
|---|---|---|
| unpriced model | `"planted-unpriced-model"` into `MODEL_CAPABILITIES` | `1 failed` — `openai/planted-unpriced-model` |
| stale exemption | `"gpt-4o"` added to `UNRATED_BY_DESIGN` | `1 failed` — "…but DO now have a seeded rate" |
| empty reason | (asserted by `test_every_exemption_states_a_reason`) | green |

⚠ **`config.py` was restored md5-identical** (`3489e7baab579e09aee96bdfbc657559`) after the
plant. The first restore attempt was NOT identical — `sed -i` rewrote CRLF as LF across the
whole file. Git saw no diff (it normalises), but the bytes had moved; the line endings were
put back explicitly and the md5 re-checked. This is the trap already recorded at
`project_251_closed_v42_complete`.

⛔ **12 models are exempt, each with a written reason**: 9 OpenRouter (a router's price depends
on which upstream serves the request — one row would be a fiction), `kimi-k2.5` and
`moonshot-v1-8k` (not on Moonshot's current pricing page), `glm-5-turbo` (not on z.ai's table).

## SC#4 — "an operator can see spend in dollars for a **single run**"

### What was wrong

The badge **could never render**. All three `RunCostBadge` mounts are guarded by
`(cost_usd !== undefined || is_rated !== undefined)` and no backend route outside `/admin/spend`
emitted either key. 257-04 added the fields to `lib/api/workflows.ts` and `types/index.ts` as
**optional, with no producer** — so `tsc` was satisfied, `RunCostBadge.test.tsx` passed (it
hands the component props directly), and the product showed nothing.

### What shipped — a producer on both surfaces, in lockstep

`WorkflowRunRead`'s own docstring names the trap: **declared, selected and populated in
lockstep**, because `response_model` drops undeclared keys *silently*. Phase 210 already paid
for that once. Both wirings respect it:

**Workflow run page** — `backend/app/api/workflow_runs.py`
1. declared `model` / `cost_usd` / `is_rated` / `token_coverage` on `WorkflowRunRead`
2. widened the ownership SELECT by 4 columns (WHERE clause untouched — no widened row set)
3. computed at the return site

**Chat** — `backend/app/api/threads.py` + `backend/app/models/message.py`
1. declared `cost_usd` / `is_rated` on `MessageResponse` — ⛔ `GET /{thread_id}/messages` is
   `response_model=list[MessageResponse]`, so **omitting this step would have reproduced the
   exact dead-UI bug the review found**, silently. It was caught by checking
   `MessageResponse.model_fields`, not by a test.
2. widened `_enrich_messages_with_runs`' SELECT by 2 columns — the same additive shape Phase
   095.1-03 argued for on this file
3. stamped per message, with the rate resolved **once per distinct model** (a thread is
   routinely 50+ messages; per-message lookup would add a round trip per row)
4. mapped snake→camel in `lib/api/threads.ts`, destructured so the snake keys do not leak
   through `...rest`

⛔ **Cost is READ through the one conversion home at both sites.** Writing
`tokens * rate / 1e6` at either call site would be a 6th conversion site and the METER-02 AST
fence would fire — correctly. Both import `compute_token_cost_usd` and
`rates.get_rate_for_model` (also the one rate *resolver*).

⚠ **Both sites degrade rather than 500.** `/messages` and the run read are primary reads; cost
is an affordance on them. A failed rate lookup logs and renders the run without a figure.

### Driven end-to-end

```
model                              in     out  is_rated  cost_usd   coverage
deepseek-v4-flash              135142   10317  True      0.0529     complete
glm-5.1                          None    None  True      None       partial
gemini-3.6-flash                 None    None  True      None       partial
```

Row 1 renders **$0.0529**. Rows 2+ are the third state and now render **"No tokens recorded"**.

### Two further defects found while wiring

1. **`isRated = true` was a default.** An absent flag was being read as a positive claim, so
   `<RunCostBadge costUsd={null} />` rendered "No tokens recorded" instead of "Unrated" —
   and failed **257-04's own case**. The default is gone; only an explicit `true` is a claim.
2. **Absent coverage was scored as incomplete coverage.** `isCoverageComplete` treated
   `undefined` (caller does not track coverage) identically to partial, so the `*` lower-bound
   marker would have been stamped on **every chat message** — `token_coverage` lives on
   `workflow_runs` and chat reads `runs`. Now: `undefined` → no claim; `null`/`[]` → incomplete.
   ⭐ 257-04's test asserting `null` → asterisk was **right**, and caught the first, blunter fix.

`Message.isRated` was widened to `boolean | null` — the null is load-bearing, because
collapsing it forces the third state to masquerade as the second.

## Three defects the OPERATOR found by using the app, after the gates were green

⭐ **All three were invisible to every gate**, which is the finding. Two green gates, a clean
typecheck and 8,428 passing frontend cases said nothing about any of them.

### 1. The page was unreachable — the reachability triad, third leg missing

Operator: *"this page is not available to navigate from the app, I have to navigate manually
to /admin/spend."* Phase 257 shipped the `admin-spend` `ActiveView` (leg 1) and the
`ChatLayout` mount (leg 2) and **no entry action** (leg 3). Legs 1 and 2 typecheck; leg 3
exists in no type, so nothing failed — the surface simply could not be reached.

Fixed: an `isOperator`-gated rail entry in `NavPanel`, beside Control Room and **outside**
`NAV_ITEMS` (that array also feeds the mobile drawer, so an entry there leaks an operator
surface to every member — the D-07 contract, locked by `nav-items.test.ts`). Glyph `Receipt`,
distinct from both Shields per the icon convention.

⭐ **A third invisible suite fell out of this.** `layout/__tests__/NavPanel.test.tsx` — the
suite that owns the operator rail's non-discoverability contract — was in **neither knob**
and had been for its whole life. Measured green at 14 before adoption, 18 after the four new
reachability cases; three of the four driven RED against a relabelled entry.

### 2. The page did not scroll

Operator: *"I see a lot of information that's good but it is not scrolling down."*

Root carried `flex-1 overflow-y-auto`. But `ChatLayout` mounts it into
`<main className="flex-1 overflow-hidden">` — **and that main is not a flex container**, so
`flex-1` on its child is inert. The root therefore had no constrained height, and
`overflow-y-auto` on an element as tall as its own content never scrolls. Everything below
the fold rendered and was clipped. Fixed with `h-full min-h-0`, and fenced — driven RED
against the exact class string that shipped.

### 3. Routing was inconsistent, and a deep link 404'd on the apex

`/admin/spend` worked on `app.<domain>` (the host-scoped `/(.*)` rewrite catches it) and
**404'd on the apex**, because Vercel resolves redirects → filesystem → rewrites and there was
no `/admin` redirect entry — while `/setup` and `/invite` both had one. Added, with two cases
in `vercelRouting.test.ts`.

⭐ **And the wider answer the operator asked for is now written down**:
[`docs/APP-ROUTING.md`](../../../docs/APP-ROUTING.md) — the three layers, the three literal
`pathname` checks that constitute all URL handling, a measured reachability table for every
`ActiveView`, and the checklist for adding a surface.

⛔ **The honest headline of that document: you cannot link to a specific run, thread or
document today.** `activeRunId` is `useState` in `ChatLayout:263` and is never written to the
URL; thread selection is a bare `setState`. The URL can choose which of three homes you land
on, and nothing else. **Deep-linking is NOT built and was deliberately not built here** — it
is a decision with three costed options in that document (query params ≈ cheap and closes the
ask; a real router = a phase touching `App.tsx`, every mount, `middleware.ts` and every
`vercel.json` entry). Recommendation: query params now, a router only as its own phase.

### 4. The filters moved the ledger but not the charts

Operator: *"the filter is working but it is not working on the charts and visuals, it is
working on the entries below it."*

**Two endpoints, two dialects of one filter:**

| endpoint | parameter | what it is |
|---|---|---|
| `GET /admin/spend/runs` | `time_range` | a string — `"today"`, `"7d"`, `"30d"` |
| `GET /admin/spend/summary` | `start_time` | an ISO timestamp |

The ledger passed its chip straight through and filtered correctly. The summary was called
`getSpendSummary()` — **bare, with no arguments** — so all four KPI cards, the daily chart,
the donut and the blind-spots gauge answered about all-time while the rows beneath them
answered about the chip. Two halves of one page describing different populations.

⭐ **The backend supported it the whole way; nothing was missing there.** The figures the
charts should have been showing, driven on the live dev DB (org `22f9c615`):

```
  all    spend=24.9083  rated=851  unrated=332  daily_buckets=89
  30d    spend= 4.3543  rated=171  unrated= 97  daily_buckets=28
  7d     spend= 1.5233  rated= 40  unrated= 16  daily_buckets=6
  today  spend= 0.0000  rated=  1  unrated=  0  daily_buckets=1
```

Fixed with one `timeRangeToStartTime()` helper — the single place the chip becomes a
timestamp — and three tests, two driven RED against the exact bare call.

⚠ **THE BUG WAS IN TWO PLACES, WHICH IS WHY THIS IS NOW A SHARED CALLBACK.** A byte-identical
copy lived in a `fetchData` callback driving the refresh control and `RepriceModal`'s
`onSuccess`. Fixing one and missing the other would have left the page correct on load and
wrong again after a reprice. `loadAll` now builds the three requests once; the effect and
`fetchData` are its two consumers.

⛔ **AND I WAS WRONG ABOUT IT FIRST.** My initial pass deleted `fetchData` as "dead code,
referenced by NOTHING" — it was referenced twice, and the page broke with
`ReferenceError: fetchData is not defined`. The suite caught it on the first run. Recorded
because the claim was confident, written into a comment, and false.

⚠ **A residue named rather than papered over:** `"today"` converts to the BROWSER's midnight,
while the ledger's `CURRENT_DATE` is evaluated in the DATABASE's timezone. Same instant when
both agree; for an operator in a different zone they differ by the offset, so the charts and
ledger can disagree by a few boundary hours. Closing it properly means the ledger taking an
explicit window too — an API change, not a client-side rounding.

⚠ **Coverage chips scope the LEDGER only**, because `/summary` has no status parameter. The
ledger header now says so in words when one is active, so two honest numbers never disagree
in silence.
