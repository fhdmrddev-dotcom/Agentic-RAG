### CR-01: A run's cost is resolved at `now()` on the run page and chat, but at `started_at` in the ledger — so a reprice makes the same run report two different dollar figures

**File:** `backend/app/api/workflow_runs.py:974` · `backend/app/api/threads.py:379`
(vs `backend/app/db/rates.py:196, 260, 317, 401`)

**What is wrong.** Both SC#4 producers call `rates.get_rate_for_model(pool, model)` with no
`effective_at`, no `provider` and no `org_id`, so the resolver defaults to
`effective_from <= now()`; every `/admin/spend` query resolves `mr.effective_from <= r.started_at`
with org-over-global and provider-over-fallback preference.

**Failure scenario.** An operator uses the feature SC#1 exists for — *"repricing a model adds a
new effective-dated row"* — and corrects `deepseek-v4-flash` from `0.30/1.20` to `3.00/12.00`
effective today. A run from 2026-06-02 (28,693 in / 1,794 out) is then reported as **$0.0108** in
the spend ledger and **$0.1076** on its own run page and chat badge. The whole point of
effective-dating is that a past run keeps its past price; one of the two surfaces throws that
away. The same root cause silently ignores any **org-scoped** rate (the reprice endpoint accepts
`org_id`) on the run page while the ledger honours it.

**Evidence** — driven inside a transaction that was rolled back; `model_rates` row count 53
before and 53 after:

```
run: 0605b46f-… deepseek-v4-flash 28693 1794 2026-06-02 19:11:52+00
REPRICED deepseek-v4-flash 0.30/1.20 -> 3.00/12.00 effective now()
  ADMIN LEDGER (effective_from <= started_at) cost = $ 0.0108
  RUN PAGE / CHAT (effective_from <= now())   cost = $ 0.1076
rows after rollback: 53 (before 53 )
```

**Fix.** Pass the run's own timestamp and scope at both call sites:

```python
rate = await rates.get_rate_for_model(
    pool, run_model,
    provider=run.get("provider"),
    effective_at=run.get("started_at") or run.get("created_at"),
    org_id=org_id,
)
```

and the same in `_enrich_messages_with_runs` — note this breaks the "once per distinct model"
batching, so key the cache on `(model, provider)` and accept a per-run resolve, or resolve the
whole rate *history* per model once and pick the row per run in Python.

### CR-02: The ledger renders a confident emerald `$0.0000` for 343 runs it cannot price — the exact thing D-257-05 forbids, under a comment saying it never does

**File:** `backend/app/db/rates.py:467-472` and `:482` · `frontend/src/pages/admin/AdminSpendPage.tsx:554-556`

**What is wrong.** Every SQL cost expression wraps the token counts in `COALESCE(r.input_tokens, 0)`,
so a run whose model **has** a rate but whose tokens were **never recorded** computes to
`0.0000` rather than `NULL`; `is_rated = r["cost_usd"] is not None` (`rates.py:482`) then reads
`True`, and the ledger cell guard `run.isRated && run.costUsd !== null` renders `$0.0000` in
emerald — three lines above a comment reading *"STRICT INVARIANT: unrated runs display ▲ Unrated
badge, NEVER $0.00"*.

**Failure scenario.** 257.1's own three-state model says this state must read *"No tokens
recorded"* — and it does, on the run page and in chat, because the Python path
(`compute_token_cost_usd`) returns `cost_usd=None, is_rated=True` for it. The SQL path does not
share that behaviour. So the same run reads **"No tokens recorded"** on one surface and
**"$0.0000 · priced"** on the other, and the KPI card's *"851 runs priced"* counts 343 runs that
were priced at zero because nothing was measured.

⚠ **This is 257's defect, but 257.1 is what made it a page-wide claim.** Before migration 184
only 20 runs were rated at all; after it, 851 are — and 343 of those have no token counts.

**Evidence:**

```
RATED runs with NO token counts at all: 343
of the first 400 ledger rows, rated-but-unmeasured: 69
   model=deepseek-v4-flash      in=None out=None cost_usd='0.0000' is_rated=True
   model=glm-5.2                in=None out=None cost_usd='0.0000' is_rated=True
   model=MiniMax-M3             in=None out=None cost_usd='0.0000' is_rated=True
   model=kimi-k2.6              in=None out=None cost_usd='0.0000' is_rated=True
```

**Fix.** Make SQL agree with `compute_token_cost_usd` — a rated model with no measurement is a
third state, not a zero:

```sql
CASE
    WHEN rate.input_cost_per_million IS NULL THEN NULL          -- unrated model
    WHEN r.input_tokens IS NULL AND r.output_tokens IS NULL THEN NULL  -- unmeasured
    ELSE ROUND(...)
END AS cost_usd
```

…and carry a separate `rate_exists` boolean so `is_rated` stops being inferred from `cost_usd`,
so the ledger can render the "No tokens recorded" badge the component already has. Until then the
KPI "N runs priced" should subtract the unmeasured set.

### CR-03: SC#1 is still measurably false, and the fence that claims to enforce it reads the wrong roster

**File:** `backend/tests/unit/test_257_1_every_model_has_a_rate.py:58-91` (`_roster()`)

**What is wrong.** `_roster()` `ast`-parses `MODEL_CAPABILITIES` in `backend/app/config.py` and
nothing else. But this product's model roster is **`MODEL_CAPABILITIES` ∪ the
`model_capabilities_overrides` table** — the admin "add model" path (SEED-172: *"local models
registered BY HAND"*). That table holds **51 rows** on the dev DB. The fence is structurally
blind to every one of them, so SC#1 — *"every model the product **can run** has a rate"* — is
asserted against a subset of the models the product can run.

**Failure scenario.** An operator registers `claude-opus-5` through the Model Registry tab, runs
it, and its spend reads `▲ Unrated` forever. The fence stays green. This is not hypothetical: it
has already happened six times, with **paid, first-party providers**.

**Evidence** — live dev DB, filtered to enabled / not-deprecated / not-removed / paid providers:

```
{'model_id': 'claude-opus-5',    'provider': 'anthropic', 'enabled': True, 'removed': False, 'deprecated': False}
{'model_id': 'gemini-3.7-flash', 'provider': 'google',    'enabled': True, 'removed': False, 'deprecated': False}
{'model_id': 'gemini-3.8-flash', 'provider': 'google',    'enabled': True, 'removed': False, 'deprecated': False}
{'model_id': 'kimi-k3',          'provider': 'moonshot',  'enabled': True, 'removed': False, 'deprecated': False}
{'model_id': 'glm-5.3',          'provider': 'zhipu',     'enabled': True, 'removed': False, 'deprecated': False}
{'model_id': 'glm-5.3-flash',    'provider': 'zhipu',     'enabled': True, 'removed': False, 'deprecated': False}
```

29 override rows in total have no rate. Five of the six above appear in real `runs` rows
(`claude-opus-5` ×2, `gemini-3.7-flash` ×1, `kimi-k3` ×5, `glm-5.3` ×3, `glm-5.3-flash` via
`z-ai/glm-5.3-flash`), and the run-level model `claude-haiku-4-5` (2 runs) is unrated because
the seed uses the dated id `claude-haiku-4-5-20251001` — an **alias mismatch the fence also
cannot see**, because it compares roster keys to seed ids and never to what `runs.model`
actually records.

**Fix.** Two additions, neither of which needs Postgres at test time to be useful:
1. Add a *dynamic* arm that reads `model_capabilities_overrides` when a pool is available and
   **fails loudly rather than skipping** when it is not reachable in a non-CI context (or run it
   as a `uat_` scenario alongside `uat_257_scenarios.py`).
2. Add a static assertion that every id in the `UNRATED_BY_DESIGN` + seed set is *reachable* —
   i.e. a check that no seeded id differs from a roster id only by a date suffix.

⛔ Until (1) exists, `257.1-FIXES.md`'s claim that SC#1 is *closed* should read *"closed for
`MODEL_CAPABILITIES`; open for registered models"*.

### CR-05: Migration 184's new unique index turns the natural "I typed the wrong price" correction into an HTTP 500

**File:** `supabase/migrations/184_model_rates_complete_roster.sql:79-80` ·
`backend/app/db/rates.py:122-142` · `backend/app/api/admin_spend.py:160-189`

**What is wrong.** 184 adds `UNIQUE (model_id, COALESCE(provider,''), effective_from)` — correct
for idempotency, and it genuinely fixes F-4. But `reprice_model` issues a bare `INSERT` with no
`ON CONFLICT` and no exception handling, and `create_rate_revision` wraps nothing. `RepriceModal`
offers a `datetime-local` input (minute precision), so **two reprices at the same stated effective
time now raise `asyncpg.exceptions.UniqueViolationError` → unhandled → 500.**

**Failure scenario.** The operator reprices `gpt-5.4` to `2.50/15.00` effective
`2026-09-19 00:00`, notices they meant `25.00`, and submits again with the same effective time.
The modal renders `Failed to reprice model: 500`. Because the table is deliberately append-only
and there is no edit or delete affordance in the UI, **the wrong price is now permanent at that
timestamp with no in-product recourse** — the operator must pick a different minute or open the
SQL editor.

**Evidence** — driven inside a rolled-back transaction; row count 53 before and after:

```
rows before: 53
first insert OK
SECOND INSERT RAISED: UniqueViolationError | duplicate key value violates unique constraint "uq_model_rates_identity"
rows after rollback: 53 -> unchanged: True
```

**Fix.** Make the reprice an upsert on the identity key and return which arm ran, so the operator
sees a correction rather than a crash:

```python
INSERT INTO public.model_rates (...) VALUES ($1,$2,$3,$4,$5,$6)
ON CONFLICT (model_id, COALESCE(provider, ''), effective_from)
DO UPDATE SET input_cost_per_million = EXCLUDED.input_cost_per_million,
              output_cost_per_million = EXCLUDED.output_cost_per_million
RETURNING ...
```

⚠ An upsert weakens D-257-03's immutability claim, which is the honest trade to name explicitly;
the alternative is catching `UniqueViolationError` and returning a **409 with the existing row**
so the modal can say *"a rate already exists at that effective time"*.

### WR-02: Stale-response race — a slow refresh landing after a filter change overwrites the fresher data

**File:** `frontend/src/pages/admin/AdminSpendPage.tsx:133-141` (uncommitted)

**What is wrong.** The declarative door (the effect, `:146-162`) has an `alive` flag. The
imperative door — `fetchData`, wired to the Refresh button (`:222`) and `RepriceModal.onSuccess`
(`:636`) — does `applyAll(await loadAll())` with **no guard at all**, and `applyAll` has `[]`
deps so it never goes stale. Its `finally { setIsLoading(false) }` also clears a spinner the
effect may still own.

**Failure scenario.** Operator clicks **Refresh** (or repricess a model) while on *Last 30D*, then
immediately clicks **7D**. The 7D response lands first and renders; the slow 30D response lands
second and overwrites every KPI, both charts and the ledger — while the chip still reads **7D**.
The page shows 30-day numbers labelled as 7-day, on the honesty dashboard.

**Evidence** — probe test (created, run, deleted):

```
✓ a slow refresh landing after a filter change overwrites the fresher data
   mount(30d) -> $111.1100 ; refresh held open ; chip->7D -> $222.2200 ;
   held refresh released -> $111.1100 rendered, $222.2200 gone.
```

**Fix.** Give the imperative door the same generation guard:

```tsx
const reqId = React.useRef(0)
const fetchData = React.useCallback(async () => {
  const mine = ++reqId.current
  setIsLoading(true)
  try { const r = await loadAll(); if (mine === reqId.current) applyAll(r) }
  catch (err) { if (mine === reqId.current) setLoadError(String(err)) }
  finally { if (mine === reqId.current) setIsLoading(false) }
}, [loadAll, applyAll])
```

…and bump `reqId` in the effect too, so the two doors share one generation counter.

### WR-03: The METER-02 fence is blind to SQL-string conversions — which is how 4 of the 5 existing sites are written

**File:** `backend/tests/unit/test_257_single_token_conversion_home.py:162-174`

**What is wrong.** The detector walks Python `ast.BinOp` nodes. A conversion written inside a SQL
string literal is an `ast.Constant`, not a `BinOp`, so it is structurally invisible — and SQL is
the **dominant spelling in this codebase**: `rates.py` carries the expression verbatim eight
times across four queries. Separately, the `_MONEY_HINTS` filter on `ast.unparse(node.left)` means
a Python conversion whose operands are not named `token`/`rate`/`cost`/`price`/`usd`/`million`/
`spend` also slips through.

**Failure scenario.** Someone adds a per-user spend endpoint and copies `rates.py`'s
`ROUND((COALESCE(...)*rate/1000000.0)+...)` into `api/admin.py`. SC#3 says *"a second conversion
site added anywhere makes a fence fail"*; the fence reports `1 passed`.

**Evidence** — two plants at `backend/app/services/_plant_sqlprobe.py`, each a verbatim copy of an
existing conversion; the file was deleted afterwards and `git status backend/app/` is clean:

```
PLANT 1 (rates.py's SQL expression, inside a module-level string)   -> 1 passed, 1 warning
PLANT 2 (pricing_service's Python, vars renamed n_in/r_in/MIL)      -> 1 passed, 1 warning
```

**Fix.** Add a string-literal arm to the same walk — scan every `ast.Constant` of type `str` in a
non-allowlisted module for `/ 1000000` / `/ 1e6` / `* 0.000001` adjacent to a money word, and
report it with the same message. This costs ~15 lines and closes the spelling that actually ships.
The `_MONEY_HINTS` gate should also consider the **assignment target** name, not only the left
operand.

⛔ And `db/rates.py` is still allowlisted **wholesale**, so F-13 stands verbatim: five conversion
sites exist, the fence guards one of them, and SC#3 is not met. Confirmed by measurement —
`grep -c "1000000.0" backend/app/db/rates.py` → `8` (four `ROUND(...)` blocks).
