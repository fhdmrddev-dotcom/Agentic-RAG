<objective>
Give the chat / library / Test-Run kickoff a channel for declared input values, merge it into the
run's `inputs` dict, and mirror it onto the live run context — so `BUG-260826-01` can actually close.

Purpose: **the milestone's blocking defect survives the phase that exists to close it unless this
plan lands.** The measured chain for the library door is:

```
RunModal.onRun
  → WorkflowsPage.tsx:1351  onLaunch(target, text, { templateFile, folderId })
  → onLaunch IS doRun       (ChatLayout.tsx:711  onLaunch={doRun})
  → doRun                   (ChatLayout.tsx:269-300) → postMessage(thread.id, kickoff, {...})
  → postMessage             (lib/api/threads.ts:449-468) — options are EXACTLY
                              { model, provider, agentMode, workflowDefinitionId, folderId }
  → POST /threads/{id}/messages → MessageCreate (models/message.py:8-25) — the same five, no more
  → threads.py:917          inputs={"kickoff_prompt": body.content,
                                     **({"folder_id": str(body.folder_id)} if body.folder_id else {})}
```

⛔ **There is no `inputs` channel on that wire and no merge on the server.** Plan `214-09` asserts the
values *"reach the backend as the run's `inputs` dict"*; plan `214-12`'s `key_links` asserts a path
*"via the existing postMessage payload"*. **That payload does not exist**, and until this plan lands
neither claim is true. ⚠ Plan `214-14`'s S-5 case passes green over the hole because it hands
`run_inputs` straight to `resolve_arguments` in-process — the launcher's half supplied by the test
rather than by the product. **That is Phase 204's signature exactly.**

✅ **The schedule door is already fine** and is deliberately untouched here:
`scheduler_service.py:139-162` reads `schedule["inputs"]` and spreads `**raw_inputs` into
`run_inputs`. So without this plan SC#2 ships **one of three** named doors; with it, all three plus
Test Run.

⭐ **AND THERE IS A FIFTH FILE ON THE PATH THAT NO PLAN OWNED**, found by the mechanical
producer→consumer derivation this revision required (recorded in plan `214-14`):
`backend/app/services/workflow_kickoff.py:500` builds a **second copy** of the same dict for the LIVE
`ctx.inputs`, with its own comment saying *"Mirror EXACTLY what was persisted so live ctx.inputs ==
the durable inputs jsonb the resume builders read back."* ⚠ **Widening only `threads.py` would mean a
workflow's FIRST run sees no declared values and a RESUMED run sees them all** — a defect that
reproduces only on a resume and that no unit test in this phase would have looked for.

Output: one client option, one request field, two merges in one commit, and an integration test that
reads the database.

argument: it is owner-reachability-gated server-side (D-05) and a launcher-supplied string must not
be able to impersonate it. **Record this precedence in a comment at the merge site**, with the reason,
because a reader who sees the spread order and not the reason will "fix" it.
