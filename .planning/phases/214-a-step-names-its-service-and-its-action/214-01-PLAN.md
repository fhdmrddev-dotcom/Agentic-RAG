`backend/app/services/connectors/args.py` exports exactly:

- `ArgumentSourceKind` — `Literal["fixed", "ask", "upstream"]`
- `ArgumentGapKind` — `Literal["no_source", "ask_undeclared", "upstream_unreachable", "shape_unknown", "unrenderable"]`
  (⚠ these five strings are the SAME five the sketch-215 refusal kinds and plan `214-05`'s
  `LINT_CODES` additions use — one spelling, three consumers.)
- `class ArgumentGap(NamedTuple)` — `kind: ArgumentGapKind`, `argument: str | None`, `upstream: str | None`
- `def renderable_property(prop: Any) -> bool`
- `def resolve_arguments(*, config: Any, schema: Any, upstream_outputs: Mapping[str, Any], run_inputs: Mapping[str, Any], body_arg: str | None = None) -> dict[str, Any]`
- `def unsatisfiable_arguments(*, config: Any, schema: Any, upstream_slugs: Sequence[str], declared_input_keys: AbstractSet[str], body_arg: str | None = None) -> list[ArgumentGap]`
- ⭐ `def schema_for_bound_tool(*, capability: str | None, tool_name: str | None, discovered_tools: Any) -> dict[str, Any] | None`
  — **the ONE place a bound step's `inputSchema` is obtained, for BOTH shapes.** Returns `None` when
  the schema is not knowable, which the gate turns into `shape_unknown` rather than into a pass.

⚠ **WHY THE SEVENTH EXPORT EXISTS, AND IT IS NOT TIDINESS.** `resolve_arguments` and
`unsatisfiable_arguments` both take `schema` as a REQUIRED argument, and the resolver walks the
schema's declared `properties` — never `config.tool_args`' keys. So a **wrong or absent** schema
yields an **empty argument object on the outbound path, silently**. Two functions agreeing on one
schema object proves `f(s) == g(s)`; it cannot detect `s_gate != s_executor`, which is a
published-then-fails-at-the-send workflow — `BUG-260826-02` restated one level up, and CONTEXT
failure mode #3. **One accessor makes the two provenances identical by construction rather than by
assertion**, and plan `214-14`'s S-2b asserts it anyway.

Its two arms, stated so neither can drift:
- **native capability** — `descriptors.descriptor_for(capability)["inputSchema"]`, which is
  `_plain_json(get_adapter(capability).INPUT_SCHEMA)` (`descriptors.py:157-170`). Pure, in-process,
  no I/O. An unregistered capability raises `KeyError` there and is allowed to propagate — the
  closed set fails CLOSED at a named site (`descriptors.py:152-157`), and swallowing it here would
  turn an unimplemented action into an empty argument object.
- **MCP** — the entry in `discovered_tools` whose `name` equals `tool_name`, read from the
  connection's snapshot. `None` when the snapshot is absent, or carries no matching entry, or the
  entry carries no `inputSchema`.

Three callers, one function: the executor (`phase_types.py`, plan `214-01` Task 3), the publish gate's
`tool_schemas` builder (`publish_service.py`, plan `214-05` Task 2), and the approval pause
(`harness_engine.py`, plan `214-06` Task 2). ⛔ **No caller may read `discovered_tools` or
`INPUT_SCHEMA` for itself.**

`backend/app/models/harness.py` gains, on `ExternalActionPhaseConfig`:

- `class ArgumentSourceSpec(_StrictBase)` — `source: ArgumentSourceKind`, `ask_key: str | None = None`,
  `upstream_slug: str | None = None`
- `arg_sources: dict[str, ArgumentSourceSpec] = Field(default_factory=dict)` — keyed by the
  schema property name.

`renderable_property(prop)` returns True for a flat scalar JSON-Schema property — `type` of

`resolve_arguments` walks the schema's declared `properties` (never `config.tool_args`' keys), and
for each declared property reads `config.arg_sources[name]`:
  - `fixed` → the value at `config.tool_args[name]`, omitted when absent or empty-string.
  - `ask` → `run_inputs[spec.ask_key or name]`, omitted when absent.
  - `upstream` → `upstream_outputs[spec.upstream_slug]`, omitted when absent.
A property with NO entry in `arg_sources` falls back to `config.tool_args[name]` if present — that
is the D-214-08 read of pre-existing objects and the D-214-12 no-retroaction guarantee in one line.
`body_arg`, when given and still unfilled and `upstream_outputs` carries a `content` value, fills
exactly as `_adapter_args` does today. Undeclared `tool_args` keys are DROPPED from the returned
object (the adapters fail closed on them) but are NOT the resolver's business to report — the
editor surfaces them (D-214-08) and `unsatisfiable_arguments` never invents a gap for an optional
leftover.

`unsatisfiable_arguments` returns one `ArgumentGap` per *required* schema property that cannot be
supplied, in `schema["required"]` order, using exactly the five `ArgumentGapKind` values:
  - schema is `None` or carries no `properties` → a single `shape_unknown` gap with `argument=None`
    (⚠ sketch 215 invariant #2: this is the ONE refusal that must not name an argument).
  - the property is not `renderable_property` → `unrenderable`.
  - no `arg_sources` entry and no non-empty `tool_args` value → `no_source`.
  - `source == "ask"` and `(spec.ask_key or name)` not in `declared_input_keys` → `ask_undeclared`.
  - `source == "upstream"` and `spec.upstream_slug` not in `upstream_slugs` → `upstream_unreachable`,
    with `upstream` set to the named slug.
  - `source == "fixed"` and the `tool_args` value is absent or an empty/whitespace string → `no_source`.
An OPTIONAL property never produces a gap.
