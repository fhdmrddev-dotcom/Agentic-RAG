### R-1 — Per-Thread Streaming Cache (Structural Refactor)

- **D-067.3-R1-01:** Adopt the **structural per-thread store** pattern, mirroring ChatGPT/Claude.ai client-side architecture. State shape in `frontend/src/hooks/useMessages.ts` flips from `messages: Message[]` to `messagesByThread: Map<string, Message[]>`. The visible `messages` array is derived: `messagesByThread.get(activeThreadId) ?? []`.
- **D-067.3-R1-02:** Cache key is `threadId` only (NOT `threadId + runId`). Multi-run-per-thread (rare today) appends to the same thread bucket. Matches the DB shape (`messages.thread_id` is the only bucket key) and the natural mental model.
- **D-067.3-R1-03:** Eviction policy: **LRU N=5 with streaming threads pinned**. Hold up to 5 thread buckets; on a 6th view, drop the least-recently-viewed *non-streaming* bucket. Streaming threads are never evicted. Re-loaded from server via existing `loadMessages` flow on next view. Bounded memory; scales gracefully to power users + future v2.6+ multi-tenant.
- **D-067.3-R1-04:** **`guardedSetMessages` is REMOVED** from both call sites (`useMessages.ts:623-628` sendMessage path + `useMessages.ts:866-871` reconcile path). The guard is structurally unnecessary once deltas write to their thread's bucket regardless of `activeThreadIdRef`. Plain setState updates targeting `messagesByThread.get(streamingThreadId)`.
- **D-067.3-R1-05:** **`streamingThreadIdRef` remains** as the bucket-key for incoming deltas (the ref tells `onDelta` which thread bucket to append to). Phase 067.2 Plan 01's synchronous `setViewingThread` alignment in `ChatArea.tsx` `handleSend` and the `useLayoutEffect` placement at `ChatArea.tsx:79` are both PRESERVED — they ensure `activeThreadIdRef` is set before the first delta arrives, which now means the visible `messages` array immediately reflects the streaming bucket. No regression.
- **D-067.3-R1-06:** F5 / multi-tab recovery is UNCHANGED: Phase 062 replay-and-tail (`GET /runs/{id}/stream?since=offset`) + Phase 063 reconcile-on-(re)connect contract (`ChatArea.tsx:163-188`) still own the recovery path. The new per-thread store is the IN-TAB mechanism; cross-tab/F5 still uses the server-side stream as source-of-truth.
- **D-067.3-R1-07:** `clearMessages()` becomes "clear thread bucket for `activeThreadId`" rather than "clear single messages array." Loadmessages-on-thread-change at `ChatArea.tsx:79+` still triggers DB fetch on first view; the bucket is populated from the fetch result.
- **D-067.3-R1-08:** Cursor / dedup state (`lastEventIdRef`, `lastSeenOffsetRef`, in-flight per-thread state) needs to compose with the bucket key. Audit during planning: any per-stream cursor needs a `Map<threadId, cursor>` shape OR explicit per-bucket reset on stream-end.

## Specific Ideas

- **R-1 ChatGPT/Claude.ai parity rationale:** This phase brings the client-side state shape into alignment with how production-grade chat UIs structure their per-thread state. The user-driven concern — "we are planning later to scale it up and we already made some seeds" + targeting org-scale (per `project_target_scale.md`) — directly motivates choosing the structural over the tactical fix. Future v2.6+ multi-tenant + org-shared threads (per `project_org_level_deferred.md`) compose naturally on `Map<threadId, Message[]>`; they would force a re-do under the tactical option.
- **R-1 LRU N=5 sizing rationale:** Typical chat session views 1-3 threads. N=5 buys headroom for power users without unbounded memory growth. Streaming-pinned exemption ensures background runs (e.g., user starts a long agent run on Thread A, switches to read Thread B, returns to A) never lose their bucket. Re-load from server is acceptable cost for the rare 6th-thread case.
- **N-01 unit-test trap:** The fix is mechanically simple (~5 lines) but the test must assert auto-resolution under the WRONG `active_provider` setting. A test that hand-sets `body.provider="anthropic"` would pass without exercising the bug. Test signature: `client.post("/threads/{id}/messages", json={"content": "...", "model": "claude-sonnet-4-6"})` with a session whose `user_settings.active_provider="openai"` — assert the request reaches `Anthropic.messages.stream(...)`, NOT `openai.chat.completions.create(...)`.
- **R-2 right-click "Save link as" trade-off:** Native anchor + right-click paths break under JS blob (server returns 401 on raw anchor click). User confirmed this is acceptable for the chat-history use case. If it becomes a UX target later, switch to token-rewrite-at-read-time (option B in the original fork) — implementation surface is documented and the migration is mechanical.
- **R-3 backend log placement:** The `logger.warning` swap at `threads.py:2478-2479` is observability-first. Even if Task 1 finds the root cause is frontend (rendered-side gap), the backend log stays in — it's cheap insurance against future silent-swallow regressions in `generate_suggestions`.
- **Plan 05 UAT scope clarification:** Phase 067.2 closure depends on Plan 05's deferred-row re-tick.
