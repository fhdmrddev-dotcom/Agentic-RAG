prior-phase OUTPUT objects (`phase_types.py` prior-phase chaining), not by reading
`messages`. The ONLY history-replay consumer is the Deep `:1024` query. So the
active control is the Deep-side `neq('origin','harness')` filter; the

control (asymmetric risk: an untagged harness row defaults to 'deep' and leaks).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Deep turn → `messages` history read | Workflow (`harness`) rows are untrusted-for-Deep-replay; they must never enter a Deep turn's reconstructed history. |
| Harness phase → `messages` | A Deep row is untrusted-for-Harness-replay (harness does not read messages today, but the strict filter blocks it if it ever does). |
| User/RLS scope → history query | The owner/thread predicate (`thread_id` + `user_id`) is the access-control boundary; the origin filter must compose with it, never widen it. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-120-04 | Information Disclosure (context bleed — core security property) | Untagged HARNESS insert defaulting to 'deep' → leaks workflow context into a later Deep turn | mitigate | Exhaustive harness-site tagging (db/runs.py harness callers, phase_types.py:629, harness_engine.py:225/:439/:513/:889, api/runs.py workflow branch); test_harness_sites_tag_harness asserts each. Asymmetric-risk priority: tagging exhaustiveness IS the control. |
| T-120-05 | Elevation of Privilege / IDOR | Origin filter accidentally relaxing the owner/thread scope (broadened query) | mitigate | The origin filter is ADDITIVE — `.eq("thread_id")` + `.eq("user_id")` preserved; acceptance asserts both present. The new `.neq`/`.eq` only NARROWS within an already-owner-scoped set. |
