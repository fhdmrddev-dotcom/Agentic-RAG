# Phase 063.1: Code Review Report

**Reviewed:** 2026-05-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10 (note: lib/api.ts was reviewed in addition to the listed 9; the 10th file was reviewed because the api.test.ts and useMessages.ts changes flow through it)
**Status:** issues_found

## Summary

The implementation is largely well-considered and the contracts described in the phase context (`reconcileInFlightRef`, MERGE filter, `guardedSetMessages`, two-query backend merge with ownership-first ordering) are present and correctly wired in the happy paths. RLS / aexec / single-worker rules from `CLAUDE.md` are honored.

However, several real defects remain:

1. **The MERGE filter in `loadMessages` can silently drop terminal-time updates from a still-live SSE consumer** when `loadMessages` runs in the narrow window between assistant-row persist and `stream_end`. The closed-over `assistantId = "temp-${run_id}"` in the earlier SSE consumer's callbacks targets a row that the merge has now removed (because the DB row carries the same `runId`), so `onTerminal`'s status flip and `suggestions`/`title` deltas are silently dropped. This is the inverse-failure-mode of the bug Wave 4 was intended to fix, and it's a real BLOCKER.

2. **`resumeFromFailed` lock is set AFTER the synchronous early-return guards** — two synchronous clicks both pass the `resumeInFlightRef` check, both find the user message, both flip the bit, both call `sendMessage`. The second `sendMessage` is no-op'd by `isSendingRef`, but the user gets no feedback (the comment in the source explicitly acknowledges this is the failure mode).

3. **The Pydantic `MessageResponse.run_id`/`run_status` flow allows `null` to leak into frontend `Message.runId` / `Message.runStatus` fields** that are typed `?: string` (optional, not `| null`). The `getMessages` mapper passes `run_id`/`run_status` straight through without nullish coercion, so consumers downstream see `null` where the type contract says `undefined`. Truthy checks happen to work; explicit `m.runId === undefined` checks would silently misbehave.

4. **The `e2e/063.1-thread-switch-mid-stream.spec.ts` captures `threadAUrl` BEFORE the first message is sent** — depending on app routing, the URL may still be the generic `/` or `/new` and `page.goto(threadAUrl)` would not actually navigate back to Thread A. Combined with non-`.first()` locator usage in two of the three e2e specs, the assertions are fragile and may pass for the wrong reason.

5. The two-query backend merge silently picks an arbitrary run when `message_id` collisions exist (no UNIQUE constraint on `runs.message_id`); the dict-comprehension is last-write-wins under Python's iteration order over Supabase response.

6. The integration test for the cross-user 404 short-circuit invariant is correctly written, but the two happy-path integration tests do not exercise the `.eq("user_id", ...)` defense-in-depth filter — the mock returns the same data regardless of which `user_id` the route filters by.

Specific findings below.

## Critical Issues

### CR-01: MERGE filter drops live SSE consumer's target during persist→stream_end window

**File:** `frontend/src/hooks/useMessages.ts:411-419` (loadMessages MERGE)
**Issue:**

The backend persists the assistant message to `public.messages` BEFORE emitting `stream_end` (`backend/app/api/threads.py:2082` then `:2107` `done`, then `:2125` `stream_end`). During this narrow window:

- `loadMessages` returns an array `data` containing the assistant DB row with `runId = R`.
- The merge filter computes `dbRunIds = {R}` and removes any temp placeholder whose `runId === R`.
- BUT the still-running `subscribeToRun` consumer (e.g., the original `sendMessage` SSE) has `assistantId = temp-<makeTempId>` (line 454) baked into closures. Its `setMessages((prev) => prev.map((m) => m.id === assistantId ? ... : m))` pattern (lines 56-58, 130-141, 544-552, etc.) becomes a silent no-op once the merge drops that placeholder.
- The terminal-status flip (line 544-552), `suggestions`, `title`, `confidence`, and `fallback_model` deltas in this window are all silently dropped. The user can be left with a stuck `runStatus: "streaming"` on a run that has actually completed, until the next reconcile-driven `loadMessages` overwrites state with the terminal DB row.

For reconcile's SSE consumer (`useMessages.ts:764-769`, `assistantId: targetId` where `targetId = existingByRunId?.id ?? \`temp-${run.run_id}\``), the same problem applies: if the consumer was started when no DB row existed, `targetId === "temp-${run.run_id}"`; once the DB row appears mid-stream, the merge drops that placeholder and the consumer's `setMessages` no-ops.

The phase-context promise that "reconcile's runId-match dedup at D-063.1-04 will route SSE deltas to the DB row" only holds for the NEXT reconcile cycle's NEW `subscribeToRun` call — it does NOT retarget an already-running consumer.

**Fix:**

Two viable options:

(a) Gate the merge drop on `subscriptionsRef.has(m.runId)`. Keep the temp placeholder if a live SSE consumer is still bound to it, even when the DB row has appeared:

```ts
setMessages((prev) => {
  const dbRunIds = new Set(data.filter((m) => m.runId).map((m) => m.runId))
  const liveTempPlaceholders = prev.filter(
    (m) =>
      m.id.startsWith("temp-") &&
      m.runId &&
      // Keep if DB doesn't have it yet OR a live SSE consumer is still bound to it
      (!dbRunIds.has(m.runId) || subscriptionsRef.current.has(m.runId)),
  )
  return [...data, ...liveTempPlaceholders]
})
```

This keeps two bubbles briefly during the persist→stream_end window, but the next `loadMessages` after the consumer drops out of `subscriptionsRef` (terminal cleanup at `useMessages.ts:557` / `:788`) collapses to one. Still better than silently swallowing terminal-status flips and suggestions.

(b) When the merge identifies a `dbRunIds`-overlap-with-live-temp situation, retarget the running consumer by rewriting the temp's `id` to the DB id and rebinding via a closure-lookup table. More invasive; (a) is preferred.

### CR-02: `resumeFromFailed` flips the in-flight bit AFTER synchronous early-returns

**File:** `frontend/src/hooks/useMessages.ts:857-879`
**Issue:**

```ts
const resumeFromFailed = useCallback(async (failedMessage: Message) => {
  if (resumeInFlightRef.current) return            // (1)
  const idx = messages.findIndex(...)              // (2) sync
  if (idx < 0) return
  let userMsg: Message | undefined
  for (let i = idx - 1; i >= 0; i--) { ... }       // (3) sync
  if (!userMsg) { ... return }
  resumeInFlightRef.current = true                 // (4) set TOO LATE
  try {
    await sendMessage(...)
  } finally {
    resumeInFlightRef.current = false
  }
}, [messages, sendMessage])
```

If the user double-clicks Resume rapidly enough that React fires both handlers in the same task before either reaches `(4)`, BOTH calls pass the guard at `(1)` and BOTH call `sendMessage`. `sendMessage`'s own `isSendingRef.current` guard (line 435) silently no-ops the second one, leaving the user with no feedback — which the source comment at line 854 explicitly acknowledges as the failure mode this guard is meant to prevent.

**Fix:** Set the bit BEFORE the early-return chain so it's claimed synchronously:

```ts
const resumeFromFailed = useCallback(async (failedMessage: Message) => {
  if (resumeInFlightRef.current) return
  resumeInFlightRef.current = true                 // claim synchronously
  try {
    const idx = messages.findIndex((m) => m.id === failedMessage.id)
    if (idx < 0) return
    let userMsg: Message | undefined
    for (let i = idx - 1; i >= 0; i--) {
      if (messages[i].role === "user") {
        userMsg = messages[i]
        break
      }
    }
    if (!userMsg) {
      console.warn("resumeFromFailed: no preceding user message for", failedMessage.id)
      return
    }
    await sendMessage(failedMessage.thread_id, userMsg.content)
  } finally {
    resumeInFlightRef.current = false
  }
}, [messages, sendMessage])
```

Mirrors the in-flight-first pattern that `reconcileInFlightRef` correctly applies at `useMessages.ts:675-676`.

### CR-03: e2e thread-switch test captures `threadAUrl` before any message has been sent

**File:** `e2e/tests/063.1-thread-switch-mid-stream.spec.ts:101-118`
**Issue:**

```ts
await createNewThread(page)
const threadAUrl = page.url()                              // (a) BEFORE first message
await sendMessageInActiveThread(page, LONG_STREAM_PROMPT)  // (b) thread_id assigned/URL changes here
...
await createNewThread(page)                                // Step 2: switch to Thread B
await page.waitForTimeout(2_000)
await page.goto(threadAUrl)                                // Step 3: switch back — to the PRE-message URL
```

If the app routes a freshly-created Thread A to `/threads/<id>` only after the first POST `/threads` returns, `threadAUrl` captured at `(a)` is the `/new` (or root `/`) URL — not Thread A's eventual route. `page.goto(threadAUrl)` would land on a fresh chat surface, not Thread A, and the assertions at lines 123-156 would either trivially pass (no assistant bubble, no run-stream call → distinctRuns = {} fails .toBe(1)) or wrongly assert against a different thread.

Even if the route IS available pre-first-message (e.g., Thread A is created the moment "New Chat" is clicked), the test premise of the second `createNewThread` "switching" is suspect — `createNewThread` is not the same UX action as switching to a sibling thread; it creates Thread B while leaving Thread A's stream live.

**Fix:**

(a) Capture `threadAUrl` AFTER `sendMessageInActiveThread` returns and the URL has stabilized:

```ts
await createNewThread(page)
await sendMessageInActiveThread(page, LONG_STREAM_PROMPT)
await expect(page.locator('[data-testid="assistant-message"]').first()).toBeVisible({ timeout: 15_000 })
await page.waitForTimeout(2_000)
const threadAUrl = page.url()  // now stable, contains thread_id
```

(b) Verify `threadAUrl` matches a thread-route shape (e.g., `/threads/<uuid>`) before relying on it:

```ts
expect(threadAUrl).toMatch(/\/threads\/[0-9a-f-]{36}/)
```

(c) For the "switch to Thread B" step, prefer a sidebar click on a sibling thread rather than `createNewThread` — the latter exercises a different code path (thread creation) and may not reproduce the visibility-change-mid-stream race the test claims to cover.

### CR-04: Two of three e2e specs use a non-`.first()` locator for `data-testid="assistant-message"`

**File:** `e2e/tests/063.1-concurrent-reconcile.spec.ts:121-123`, `e2e/tests/063.1-thread-switch-mid-stream.spec.ts:123-125`
**Issue:**

```ts
await expect(page.locator('[data-testid="assistant-message"]')).toBeVisible({ timeout: 2_000 })
```

When the locator resolves to >1 elements, Playwright's `.toBeVisible()` enters strict-mode and throws `strict mode violation: ... resolved to N elements`. The refresh test (`063.1-refresh-no-duplicate-bubble.spec.ts:75`) correctly uses `.first()`; the other two omit it. In the `concurrent-reconcile` test specifically, the test rationale is "exactly one bubble survives" — but if the test is RUN before the fix lands, two bubbles could exist briefly, and the strict-mode violation would surface as a misleading failure (not "two bubbles" but "strict mode violation"). And if the test runs cleanly with one bubble, the assertion would technically pass either way — the test isn't actually counting bubbles. In `thread-switch-mid-stream` the existing implementation has it covered earlier in line 109 with `.first()`, but line 123 reuses the locator without `.first()`.

**Fix:** Use `.first()` consistently, and where the test rationale requires "exactly one", switch to `.toHaveCount(1)`:

```ts
// concurrent-reconcile.spec.ts (Assertion A — bubble visible)
await expect(page.locator('[data-testid="assistant-message"]').first()).toBeVisible({ timeout: 2_000 })
// AND assert exactly one if that's the test invariant:
await expect(page.locator('[data-testid="assistant-message"]')).toHaveCount(1)
```

## Warnings

### WR-01: `runs_by_message` dict drops collisions silently when multiple runs share `message_id`

**File:** `backend/app/api/threads.py:639-643`
**Issue:**

```py
runs_by_message = {
    r["message_id"]: r
    for r in (runs_resp.data or [])
    if r.get("message_id") is not None
}
```

`public.runs.message_id` has no UNIQUE constraint (migration 035 line 24 — only an FK with `ON DELETE SET NULL`). Multiple runs with the same `message_id` (rare but possible — buffer-expired retries, partial failure paths, or simple producer races) collapse to whichever the dict comprehension iterates last; ordering is implementation-defined for the supabase-py response with no `ORDER BY`. The route then attaches an arbitrary run's status to the assistant row, which can be e.g. an old `failed` run instead of the most recent `completed`.

**Fix:** Add `.order("started_at", desc=True)` to the runs SELECT and prefer the FIRST run per `message_id` (or the streaming one when present):

```py
runs_resp = await aexec(
    supabase.table("runs")
    .select("run_id, message_id, status")
    .eq("thread_id", thread_id)
    .eq("user_id", current_user["id"])
    .order("started_at", desc=True)
)
runs_by_message: dict[str, dict] = {}
for r in (runs_resp.data or []):
    mid = r.get("message_id")
    if mid is None or mid in runs_by_message:
        continue   # keep the first (most recent) per message_id
    runs_by_message[mid] = r
```

Or, more defensively, prefer `streaming` > `failed` > `completed` > `cancelled` so the Resume UX is correct in the rare collision case.

### WR-02: `MessageResponse.run_id`/`run_status` allow `null` to leak as frontend `null` (not `undefined`)

**File:** `frontend/src/lib/api.ts:62-90`, `frontend/src/types/index.ts:96-98`
**Issue:**

The Pydantic model uses `run_id: UUID | None = None`; the frontend mapper does `runId: run_id` without nullish coercion. The frontend `Message` type declares `runId?: string` (optional), not `runId?: string | null`. Consumers performing `m.runId === undefined` checks would mis-classify a `null` as "present-but-null" rather than "absent."

Most current call sites rely on truthy checks (`m.runId && ...` at line 416 of useMessages.ts; `m.runId === run.run_id` at line 701 — string-compare-to-null is false, no false positive). So this is currently latent.

**Fix:** Coerce in the mapper:

```ts
return {
  ...rest,
  citations: (source_refs ?? []) as Citation[],
  runId: run_id ?? undefined,
  runStatus: run_status ?? undefined,
}
```

OR widen the Message type to `runId?: string | null` and audit all usages.

### WR-03: Integration tests do not exercise the `.eq("user_id", ...)` defense-in-depth filter

**File:** `backend/tests/integration/test_063_1_messages_runs_join.py:67-69, 130-131`
**Issue:**

The mock `runs_builder.execute.side_effect` returns the same payload regardless of how the production code chains `.eq("thread_id", ...).eq("user_id", ...)`. The happy-path tests verify the merge logic shape but cannot detect a regression that drops the `.eq("user_id", current_user["id"])` filter. The `T-063.1-04` mitigation comment in the production source (lines 626-629) claims defense-in-depth via this filter, but the test suite doesn't actually verify that the chain is built.

**Fix:** Inspect `runs_builder.eq.call_args_list` after the request and assert both `("thread_id", ...)` and `("user_id", ...)` calls are present:

```py
eq_calls = runs_builder.eq.call_args_list
eq_kwargs = [(c.args[0], c.args[1]) for c in eq_calls]
assert ("thread_id", THREAD_A) in eq_kwargs
assert ("user_id", USER_ID) in eq_kwargs
```

This makes the defense-in-depth filter a tested invariant, not a comment.

### WR-05: `subscribeToRun` parser does not reset `lastEventId` after a JSON parse failure

**File:** `frontend/src/lib/api.ts:298-394`
**Issue:**

```ts
for (const line of lines) {
  if (line.startsWith("id: ")) {
    lastEventId = line.slice(4).trim()
    continue
  }
  if (!line.startsWith("data: ")) continue
  const raw = line.slice(6).trim()
  try {
    const parsed = JSON.parse(raw) as ...
    // ... dispatch ...
    if (lastEventId !== undefined && callbacks.onCursor) {
      callbacks.onCursor(lastEventId)
    }
    lastEventId = undefined
  } catch (parseErr) {
    console.warn(...)
    // lastEventId NOT reset — the stale id will be paired with the NEXT event
  }
}
```

If a malformed `data:` frame follows a valid `id:` line, the parse fails, `lastEventId` is not reset, and the NEXT (well-formed) data event fires `onCursor` with the WRONG `id`. The cursor would advance past events that haven't been dispatched, causing the next reconcile reattach to skip those events.

**Fix:** Reset `lastEventId` in the catch:

```ts
} catch (parseErr) {
  console.warn("subscribeToRun: malformed SSE line", { raw, parseErr })
  lastEventId = undefined
}
```

### WR-06: Mid-stream loadMessages can cause `runStatus: "streaming"` to be persisted from the DB even after SSE terminates

**File:** `backend/app/api/threads.py:633-654`, `frontend/src/hooks/useMessages.ts:411-419`
**Issue:**

`get_messages` returns `run_status` directly from the `public.runs` row. The producer flips `runs.status` from `streaming` to terminal AFTER `_emit_terminal` (line 2180) and AFTER the assistant message has been persisted. So a `loadMessages` triggered between assistant-row persist and `runs.status` UPDATE returns `run_status: "streaming"` for a run that has actually completed. The frontend Message gets `runStatus: "streaming"`, and combined with CR-01 (terminal flip silently dropped if MERGE removes the temp), the UI can be stuck on a "streaming" indicator until another loadMessages overwrites it.

**Fix:** This is mostly a timing artifact and the next reconcile will resolve it. Consider either:

(a) Backend: derive `run_status` from a more conservative source, e.g., infer "completed" when `runs.completed_at IS NOT NULL` regardless of the `status` field, or add a deferred trigger to update both atomically. (Probably overkill.)

(b) Frontend: when the runId-matched DB row arrives with `runStatus: "streaming"` AND `subscriptionsRef.has(runId)` is false (consumer already terminated), treat it as a stale DB read and don't downgrade local terminal state. Effectively, only allow forward state transitions on `runStatus`.

The frontend fix is cheaper.

### WR-07: `clearMessages()` is still called on thread switch, defeating part of the D-063.1-07 motivation

**File:** `frontend/src/components/chat/ChatArea.tsx:107-108`
**Issue:**

The phase context says abortStream removal "lets the in-flight sendMessage SSE consumer survive thread switch" and the `guardedSetMessages` wrapper exists so SSE deltas no-op while viewing a different thread. But `clearMessages()` (line 107) STILL runs on every thread switch, wiping the messages array. The downstream effect is that when the user navigates back, `loadMessages` re-fetches everything from the DB and reconcile re-runs, which is the very thing the design was trying to avoid the cost of (CONTEXT.md).

This is more architectural than a bug, but it conflicts with the stated invariant. If the goal is "SSE consumer survives switch and seamlessly resumes," `clearMessages()` should be conditional on whether a live subscription exists for any of the currently-displayed messages, OR the per-thread message cache should be keyed somewhere outside the hook so the next switch-back can hydrate from cache instead of doing a full re-fetch.

**Fix:** Either:

(a) Document explicitly that `clearMessages()` is intentional and the survival guarantee is "SSE keeps writing to the dropped placeholder until the user navigates back, at which point reconcile + loadMessages converge on the persisted DB row" — but acknowledge the wasted SSE writes between switch-away and switch-back.

(b) Hoist a per-thread message cache (e.g., a `Map<threadId, Message[]>`) and re-hydrate from cache on switch-back instead of `clearMessages` + `loadMessages`. This actually matches the motivation behind D-063.1-07 (avoid teardown).

Note: this is only a WARNING because the current behavior is functionally correct, just suboptimal.

### WR-08: ChatArea visibility/focus listener attaches before `reconcileRef` is updated on first render

**File:** `frontend/src/components/chat/ChatArea.tsx:127-130, 132-157`
**Issue:**

```ts
const reconcileRef = useRef(reconcile)
useEffect(() => {
  reconcileRef.current = reconcile
}, [reconcile])

useEffect(() => {
  if (!thread?.id) return
  const tid = thread.id
  reconcileRef.current(tid).catch(console.error)   // (1) initial fire
  ...
}, [thread?.id])
```

On the very first mount where `thread?.id` is set, both effects run after render. Effect order in React is declaration order for the same component, so `reconcileRef.current = reconcile` runs first (this is fine on initial mount because `useRef(reconcile)` already initialized it). But if `reconcile` changes identity AFTER the first mount (e.g., if its `useCallback` deps change), there's a brief window between when the new `reconcile` exists and when the ref is updated where the listener-effect could fire `reconcileRef.current(...)` with the OLD reconcile. Currently `reconcile`'s deps are `[loadMessages]` and `loadMessages`'s deps are `[]`, so `reconcile` is stable. But this is a fragile coupling — any future dep added to `loadMessages` or `reconcile` makes this latent bug a real one.

**Fix:** None strictly required given the current dep graph, but adding a comment documenting the ordering invariant, or restructuring to `useEffect(() => { ...; }, [reconcile])` (accept the listener re-attach cost in exchange for safety) would harden against future changes.

### WR-09: Test fixture import for side-effect (`_reset_sse_starlette_app_status`) is also imported into a route that doesn't open SSE streams

**File:** `backend/tests/integration/test_063_1_messages_runs_join.py:31`
**Issue:**

```py
from tests.integration.test_059_disconnect import _reset_sse_starlette_app_status  # noqa: F401, E402
```

The test exercises only `GET /threads/{tid}/messages`, which does NOT use sse-starlette.
