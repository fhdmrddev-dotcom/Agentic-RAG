## Decisions Made

- **Two-query merge over embedded select** — Codebase has zero precedent for PostgREST embedded selects (verified via grep audit in 063.1-PATTERNS.md line 1001). Mirroring the existing `list_active_runs` pattern (sibling route at threads.py:393-401) keeps the codebase uniform and avoids introducing a new pattern that downstream maintainers would have to reason about.
- **Snake_case on the Pydantic surface** — CONTEXT.md mentioned a "Phase 053+ camelCase contract", but PATTERNS.md line 532 confirmed that convention is NOT actually present in MessageResponse. The frontend api.ts:48-71 already does the snake→camel rename in a destructure pass that handles other fields (source_refs → citations, confidence_*). Adding a model_config alias_generator would be an inconsistent local change.
- **runs SELECT column enumeration over SELECT *** — Migration 035 includes columns like `error`, `model`, `provider`, `input_tokens`, `output_tokens` that have no business showing up in the messages-list response. Explicit `select("run_id, message_id, status")` is a structural T-063.1-04 mitigation: even if a future Pydantic refactor accidentally relaxed the response_model coercion, those fields could not leak because they were never fetched.
- **No `.maybe_single()` migration** — Per PATTERNS.md line 619, switching the `.single()` to `.maybe_single()` for symmetry with list_active_runs is a separate CR-01 follow-up. Keeping it scoped to D-063.1-13 avoids feature creep.
