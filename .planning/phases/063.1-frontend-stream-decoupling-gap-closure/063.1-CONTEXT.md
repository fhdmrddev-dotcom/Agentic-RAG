# Phase 063.1 Context — Gap closure for Frontend Stream Decoupling

## Why this phase exists

Phase 063 landed all 5 planned plans and the gsd-verifier scored 7/7 must-haves at the code level. Live UAT on 2026-05-04 against the local Supabase + Redis + backend + frontend stack covered every untested success criterion — the phase passes its core promise (POST returns immediately, SSE decoupled, reconciliation triggers fire, multi-tab fanout works, Stop sends DELETE, no tool-JSON leak), BUT 5 real gaps surfaced that block calling Phase 063 user-complete:

1. **Gap-003 (major UX)** — Switching threads mid-stream causes a blank window on switch-back, plus a duplicate `GET /runs/{rid}/stream?since=0` against the same run id (one from sendMessage, one from reconcile). The original SSE controller is aborted on React effect cleanup, the entry is removed from `subscriptionsRef`, and reconcile then opens a fresh consumer that replays the stream from offset 0.
2. **Gap-001 (cosmetic)** — Refresh-mid-stream renders the assistant bubble twice during the SSE replay window: once as `temp-${run_id}` (filled by reconcile's SSE deltas from offset 0), once as the persisted DB row (loaded by `loadMessages`). Auto-resolves on terminal event but is visible flicker.
3. **Gap-002 (unconfirmed)** — Resume button data flow uncertain: `getActiveRuns` returns only `status='streaming'`, `loadMessages` returns raw DB rows without `runStatus`. Unclear how `message.runStatus="failed"` reaches the Message object after reload. Not exercised live in 063/063.1 UAT because backend env-gate `ENABLE_TEST_FIXTURES=1` was not set.
4. **Gap-004 (architectural)** — `since="0"` is hard-coded at all 3 `subscribeToRun` call sites in useMessages.ts. The backend `event_consumer` clone already supports `last_id=since`, so the API surface is correct — the client just doesn't use it.
5. **Gap-005 (NEW — found 2026-05-04 multi-tab UAT)** — Concurrent reconcile races wipe the temp placeholder. When a passive tab gets BOTH `visibilitychange` and `focus` events on tab activation, ChatArea fires `reconcile()` twice. The two calls race: A's for-loop inserts the temp placeholder (line 615-632), then B's `loadMessages` (line 374) calls `setMessages(data)` which OVERWRITES the placeholder. B's for-loop then short-circuits because A's `subscriptionsRef.set` already executed. **Net result**: SSE is open but no placeholder bubble renders. User sees the user-message but no assistant bubble until the producer's first DB persist (which may not happen at all if the run completes/cancels via SSE only). Confirmed via React fiber introspection on tab 2 of multi-tab test: `messages` state had 18 real DB-id rows, ZERO temp- placeholders, despite SSE being open for run `a6d7114d-...`.

The 5 success criteria in ROADMAP.md for Phase 063.1, plus a passing live UAT pass:

- No duplicate bubble during refresh-mid-stream

## Architectural intent

Three complementary fixes (was two before Gap-005 surfaced):

**A. Track offset cursor on the client.**
- Each subscribeToRun call records the highest `id` seen from each delta event into a `lastSeenOffsetRef.current[run_id]`.
- On reconnect (reconcile) or resume, pass that offset as `since` instead of `"0"`.
- This eliminates Gap-001 and Gap-004 directly.

**B. Don't abort SSE on thread switch.**
- The current `subscriptionsRef` Map already supports keeping subscriptions alive across thread switches.
- The `controller.abort()` that runs on ChatArea unmount must NOT cascade to the SSE consumer — only the loadMessages fetch should abort.
- WR-05's `guardedSetMessages` is already in place to prevent cross-thread bleed of state updates.
- The existing `if (subscriptionsRef.current.has(run.run_id)) continue` short-circuit in reconcile (line 598) will then correctly skip re-subscription on switch-back.

**C. Serialize concurrent reconcile calls (Gap-005 fix).**
- Currently `ChatArea.tsx:121-146` wires reconcile to mount, visibilitychange, focus, AND pageshow. Browsers commonly fire visibilitychange + focus together when a tab is activated. If both fire reconcile, the two parallel `Promise.all([getActiveRuns, loadMessages])` chains race, and the LATER `loadMessages → setMessages(data)` wipes the EARLIER reconcile's placeholder.
- Two possible fixes:
  - **Option 1 — In-flight guard ref**: `reconcileInFlightRef.current = boolean`. If true on entry, skip. The active reconcile picks up the latest state when it finishes.
  - **Option 2 — Insert placeholder BEFORE loadMessages settles**: Restructure reconcile to fire `getActiveRuns` first, insert placeholder synchronously when it returns, THEN `loadMessages`. Use `setMessages((prev) => mergeWithPlaceholders(prev, placeholders))` inside loadMessages to preserve placeholders. This is more invasive but avoids the user-visible delay.
- Probably want both for robustness.

## Open questions for discuss-phase

1. Should `lastSeenOffsetRef` be a hook-local ref (lost on full unmount) or persisted to sessionStorage? Persisted across page reloads would help Gap-001 too.
2. For Resume button: prefer (a) `loadMessages` joins `runs.status` into the row, or (b) a separate `getRecentlyFailedRuns(threadId)` endpoint? (a) is simpler but couples concerns; (b) is cleaner.
3. Should the `subscribeToRun` controller live in a higher-level provider (App-level) so it survives ChatArea remount entirely? Or fix the abort cascade locally?
4. For Gap-005: is the cleanest fix to debounce reconcile (e.g., 50ms trailing edge) so coalesced visibility/focus events fire only one reconcile call? Or is the in-flight guard sufficient?
5. Should `loadMessages` preserve in-memory temp placeholders when merging DB results? Currently line 375 does `setMessages(data)` (replace). If we change to merge, it protects placeholders from any concurrent reconcile.
