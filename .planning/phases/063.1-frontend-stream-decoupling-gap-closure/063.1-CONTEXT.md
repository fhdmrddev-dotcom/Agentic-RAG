# Phase 063.1 Context — Gap closure for Frontend Stream Decoupling

<domain>
## Phase Boundary

Resolve the 5 UAT-surfaced gaps (Gap-001..005) so navigate-away-during-stream, refresh-mid-stream, AND multi-tab-activation flows are visually clean and Redis-efficient. Confirm Resume-button data path against a live failed run via `ENABLE_TEST_FIXTURES=1`. No new requirement added — finishes the user-visible side of STREAM-04 that Phase 063 left rough.

</domain>

## Why this phase exists

Phase 063 landed all 5 planned plans and the gsd-verifier scored 7/7 must-haves at the code level. Live UAT on 2026-05-04 against the local Supabase + Redis + backend + frontend stack covered every untested success criterion — the phase passes its core promise (POST returns immediately, SSE decoupled, reconciliation triggers fire, multi-tab fanout works, Stop sends DELETE, no tool-JSON leak), BUT 5 real gaps surfaced that block calling Phase 063 user-complete:

1. **Gap-003 (major UX)** — Switching threads mid-stream causes a blank window on switch-back, plus a duplicate `GET /runs/{rid}/stream?since=0` against the same run id (one from sendMessage, one from reconcile). The original SSE controller is aborted on React effect cleanup, the entry is removed from `subscriptionsRef`, and reconcile then opens a fresh consumer that replays the stream from offset 0.
2. **Gap-001 (cosmetic)** — Refresh-mid-stream renders the assistant bubble twice during the SSE replay window: once as `temp-${run_id}` (filled by reconcile's SSE deltas from offset 0), once as the persisted DB row (loaded by `loadMessages`). Auto-resolves on terminal event but is visible flicker.
3. **Gap-002 (unconfirmed)** — Resume button data flow uncertain: `getActiveRuns` returns only `status='streaming'`, `loadMessages` returns raw DB rows without `runStatus`. Unclear how `message.runStatus="failed"` reaches the Message object after reload. Not exercised live in 063/063.1 UAT because backend env-gate `ENABLE_TEST_FIXTURES=1` was not set.
4. **Gap-004 (architectural)** — `since="0"` is hard-coded at all 3 `subscribeToRun` call sites in useMessages.ts. The backend `event_consumer` clone already supports `last_id=since`, so the API surface is correct — the client just doesn't use it.
5. **Gap-005 (NEW — found 2026-05-04 multi-tab UAT)** — Concurrent reconcile races wipe the temp placeholder. When a passive tab gets BOTH `visibilitychange` and `focus` events on tab activation, ChatArea fires `reconcile()` twice. The two calls race: A's for-loop inserts the temp placeholder (line 615-632), then B's `loadMessages` (line 374) calls `setMessages(data)` which OVERWRITES the placeholder. B's for-loop then short-circuits because A's `subscriptionsRef.set` already executed. **Net result**: SSE is open but no placeholder bubble renders. User sees the user-message but no assistant bubble until the producer's first DB persist (which may not happen at all if the run completes/cancels via SSE only). Confirmed via React fiber introspection on tab 2 of multi-tab test: `messages` state had 18 real DB-id rows, ZERO temp- placeholders, despite SSE being open for run `a6d7114d-...`.

## What "done" looks like

The 5 success criteria in ROADMAP.md for Phase 063.1, plus a passing live UAT pass:
- No blank window on tab/thread switch
- Single SSE per run id at any time (within a tab)
- No duplicate bubble during refresh-mid-stream
- Temp placeholder renders even when reconcile fires twice in quick succession (Gap-005 fix)
- Resume button render-and-click confirmed against `ENABLE_TEST_FIXTURES=1` backend
- Cross-tab Stop verified end-to-end (single-tab Stop already verified at backend level — DELETE → 204 → "Response stopped" badge)

## Implementation Decisions

### Offset-cursor strategy (Gap-004 fix; partial Gap-001 input)

- **D-063.1-01:** Track `lastSeenOffsetRef.current = Map<run_id, ms_id>` inside useMessages. Updated as each delta event arrives (via the `id` field on each Redis Stream entry). Hook-local — survives tab switches and reconcile cycles within a page lifetime; F5 wipes it (back to `since='0'` on reload). NOT persisted to sessionStorage — refresh-mid-stream's duplicate-bubble (Gap-001) is solved by the runId-match dedup below, not by persisted offset.
- **D-063.1-02:** Thread `since` through all 3 `subscribeToRun` call sites in `useMessages.ts`:
  - `sendMessage` line 498 — start at `"0"` (fresh run, no offset yet).
  - `reconcile` line 680 — pass `lastSeenOffsetRef.current.get(run.run_id) ?? "0"`.
  - `resumeFromFailed` line 715 — irrelevant; this re-POSTs a new message and starts a fresh run, so it doesn't replay against an existing offset.
- **D-063.1-03:** Backend already accepts `since` per Phase 062 (`event_consumer` clone with `last_id=since`). No backend change needed for Gap-004.

### Refresh-flicker dedup (Gap-001 fix)

- **D-063.1-04:** When `reconcile` iterates `activeRuns`, look in current `messages` state for `m.runId === run.run_id`. If found, **reuse THAT message's id** as the `assistantId` passed to `makeStreamCallbacks`. SSE deltas update the existing DB row in-place. If not found, fall back to inserting `temp-${run.run_id}` placeholder as today (lines 615-632).
- **D-063.1-05:** Backend assistant rows MUST carry `runId` after F5/reload — wired via the `loadMessages` JOIN (D-063.1-13 below). Without that join, D-063.1-04 short-circuit can't fire. Plan must verify the JOIN lands BEFORE the dedup logic exercises it.

### Thread-switch SSE persistence (Gap-003 fix)

- **D-063.1-06:** Single message buffer architecture (no Context provider lift, no per-thread Map refactor). `messages` stays as a single React state in useMessages, scoped to the viewing thread. Cross-thread bleed is prevented by guards, not by buffer separation.
- **D-063.1-07:** Remove `abortStream()` from ChatArea's thread-change useEffect (`ChatArea.tsx:95`). The current call kills the in-flight `sendMessage` AbortController, which terminates the SSE consumer. After removal, only the `loadAbortRef.current?.abort()` inside `loadMessages` (line 364) cancels — and that's what we want.
- **D-063.1-08:** Wrap `sendMessage`'s callbacks with the same `guardedSetMessages` pattern reconcile already uses (line 642-647). Gate on `streamingThreadIdRef.current === activeThreadIdRef.current` so per-event `setMessages` calls are no-ops when the user has navigated to a different thread. State updates resume automatically when the user navigates back (the still-live SSE keeps writing through the now-active guard).
- **D-063.1-09:** Flip reconcile's `subscriptionsRef.has(run.run_id) continue` short-circuit (line 598). New behavior: ALWAYS render the placeholder/dedup against the existing message; only short-circuit the `subscribeToRun` call itself when a live subscription already exists. This way, switching back to a thread re-renders the placeholder even though SSE is already streaming in the background.
- **D-063.1-10:** Hook unmount effect (line 744-749) keeps its current behavior — abort all subscriptions on full hook unmount. Thread switches don't unmount useMessages (it's keyed to a stable parent), so this only fires on logout/route change. Verify in plan via component-tree mount audit.

### Concurrent-reconcile race fix (Gap-005)

- **D-063.1-11:** Add `reconcileInFlightRef.current: boolean` to useMessages. At top of `reconcile` (line 585): if `true`, return immediately. Set `true` before the Promise.all, set `false` in finally. The active reconcile picks up the latest state when it finishes; subsequent triggers fire a fresh reconcile after the lock releases.
- **D-063.1-12:** Change `loadMessages` from REPLACE to MERGE for temp placeholders. Current line 375 `setMessages(data)` becomes:
  ```ts
  setMessages((prev) => {
    const dbRunIds = new Set(data.filter(m => m.runId).map(m => m.runId))
    const liveTempPlaceholders = prev.filter(m =>
      m.id.startsWith('temp-') && m.runId && !dbRunIds.has(m.runId)
    )
    return [...data, ...liveTempPlaceholders]
  })
  ```
  Belt-and-braces protection for any other code path that calls loadMessages while a reconcile-inserted placeholder is in-flight (terminal-time refetch line 698, `buffer_expired` fallback line 493). NO debounce — that adds latency to single legit triggers and is fragile against pageshow firing later than 50ms.

### Resume button data flow (Gap-002 fix)

- **D-063.1-13:** Modify the existing `GET /threads/{tid}/messages` endpoint (NOT a new endpoint, NOT broadening getActiveRuns). Backend: LEFT JOIN `public.runs ON messages.id = runs.message_id`, return `runStatus` (= runs.status) and `runId` on each assistant row. Single round-trip; no UI flicker between "loaded without status" and "with status." Pre-run-backed messages (predate migration 035) get `null` — fine, Resume button only renders when `runStatus === 'failed'`.
- **D-063.1-14:** RLS already gates both tables through the same `user_id`. The JOIN piggy-backs on the existing `messages` SELECT policy; no new RLS policy required. Plan must verify this in a cross-user test (mirror `test_063_cross_user_no_runid_leak.py` shape).
- **D-063.1-15:** Pydantic response model for `MessageResponse` extends to include `run_id: Optional[str]` and `run_status: Optional[Literal["streaming", "completed", "failed", "cancelled"]]`. Frontend `Message` type already has these (`runId`, `runStatus`) — just needs backend wire-up + camelCase mapping in `api.ts`.

### Claude's Discretion

- Exact merge ordering in D-063.1-12 (whether placeholders sort before/after DB rows when interleaved by created_at — pick whatever doesn't cause React key collisions).
- Whether D-063.1-09's "always insert placeholder, conditional subscribe" gets factored into a small helper (`reconcileRun(run, threadId)`) or stays inline in the for-loop.
- Implementation choice for D-063.1-15 backend JOIN: SQLAlchemy `outerjoin` vs raw SQL, whichever matches the project's existing `app/api/threads.py` patterns.

## Existing Code Insights

### Reusable Assets
- **`guardedSetMessages` (useMessages.ts:642-647)** — Already battle-tested in reconcile (WR-05 fix). Lifted to a hook-level helper for D-063.1-08; sendMessage's makeStreamCallbacks consumes it instead of raw setMessages.
- **`subscriptionsRef.current` Map (useMessages.ts)** — Already keyed by run_id, already deduplicates concurrent SSE consumers via `.has()` short-circuit. D-063.1-09 narrows the short-circuit scope but reuses the same Map.
- **`activeThreadIdRef` + `setViewingThread` (D-060-01)** — Sole writer pattern proven across 060/063. D-063.1-08 reuses it for sendMessage's guard.
- **`reconcileRef` indirection (WR-07 fix at ChatArea.tsx:116-119)** — Prevents listener thrashing on reconcile identity change. D-063.1-11's in-flight ref slots into the same indirection.
- **Pydantic `MessageResponse`** — Existing model in `backend/app/api/threads.py`; D-063.1-15 extends it rather than introducing a parallel shape.

### Established Patterns
- **Sole writer + post-await guard (D-060-01/02)** — Every cross-thread state mutation in useMessages already uses this pattern. D-063.1-08 (sendMessage guarded callbacks) and D-063.1-11 (in-flight reconcile) both fit cleanly.
- **Subscription cleanup belongs to onTerminal, not finally (BL-03)** — Don't clean up `subscriptionsRef` in promise finally chains; the SSE reader can outlive the promise resolution. D-063.1-09 must preserve this.
- **Pydantic camelCase response (Phase 053+ contract)** — Backend snake_case `run_id` / `run_status` → frontend camelCase `runId` / `runStatus` via existing alias generator.
- **D-062-14 file-layout discipline** — Phase 062 carved out off-limits regions in `threads.py`. D-063.1-13 must respect them; the JOIN modification is in the message-list endpoint which is OUT of those regions, but verify in plan.

### Integration Points
- **Frontend ↔ backend message-list shape** — D-063.1-13/15 is the ONLY backend change in this phase. Everything else is frontend.
- **`subscribeToRun(runId, since, callbacks, signal)`** — Already accepts `since` as second arg from Phase 062; D-063.1-02 just stops hard-coding `"0"`.
- **`reconcile()` is the orchestrator** — All 4 areas converge on this function. Plan ordering must lock the diff order to avoid stepping on itself (e.g. D-063.1-09 placeholder logic depends on D-063.1-04 dedup which depends on D-063.1-13 backend JOIN).
