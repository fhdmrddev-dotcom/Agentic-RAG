<objective>
Add the propose/get/reject control surface for the loop on the existing `evals.py` `/skills` router
(the smaller diff per RESEARCH Alternatives; the `skill_tuner.py` sibling router is the compliant
fallback). POST propose owner-verifies the skill, reads the SOURCE eval run's evaluated version as the
diff base, assembles the D-02 evidence, calls `skill_proposer_service.propose`, and persists a
`status='proposed'` row. GET routes read owner-scoped; reject is a pure-audit status flip.

This plan OWNS `eval_run.py`, so it also LOCKS the response contract for the whole loop — including the
nullable `gate` field (a `PromotionGate` model of honest case-matched counts). D-13 requires those counts
"always displayed alongside the verdict"; FastAPI response models strip any field not declared on the
response model, so the field must be born here even though Plan 05 is what WRITES it (at reconcile) and
Plan 07 is what DISPLAYS it. At propose time `gate` is `None` (no re-eval has run yet).

Purpose: Let the user draft ONE improvement on demand and review/reject it — the front half of the loop —
on a contract that already carries the honest-counts surface D-13 needs downstream.
Output: the Pydantic proposal shapes (`eval_run.py`, incl. `PromotionGate` + `gate`) + 4 routes
(`evals.py`) + owner-scoping tests.

Honors D-01 (on-demand, enabled once >=1 run w/ results), D-04 (one open proposal at a time),
D-07 (owner-scoped persistence + 404-not-403), D-10 (reject = re-draft path, pure audit),
D-13 (the honest-counts `gate` field is owned + declared here so it survives serialization).
</objective>
