## Decisions Made

- **Auto-scroll-to-bottom on contentText change (Plan I-2 option a, not b).** Inside `ToolArgsLivePanel`'s body, `useEffect(() => { bodyRef.current.scrollTop = bodyRef.current.scrollHeight }, [contentText])` keeps the latest streamed line in view for the >5 KB code-stream case. Without this, `max-h-64 overflow-y-auto` would show the middle/bottom slice on first paint and the user would see static code until they manually scrolled. The plan offered (a) auto-scroll OR (b) note in UAT that screenshot may show middle/bottom slice; I chose (a) for screenshot stability per the plan's explicit recommendation.
- **Reducer noChange early-return checks BOTH fields.** The original byte-counter reducer returned early when `next === (tc.argsBytesStreamed ?? 0)`. The new reducer checks `next === (tc.argsBytesStreamed ?? 0) && nextCode === tc.argsCodeText` — if EITHER field changes, the reducer writes; if both unchanged, it's a no-op. Preserves the existing zero-write idempotency contract.
- **argsCodeText cleared atomically with the preparing→running transition.** Per CONTEXT.md §Claude's Discretion, the `onToolStart` reducer body adds `argsCodeText: undefined` to the merged tc object inside the preparing-branch spread. Single state transition; no separate `clearArgsCodeText` action needed.
- **Per-tool-id `panelExpanded` Record at component scope (not lifted to a hook or context).** Each `<ToolArgsLivePanel>` instance needs its own user-toggle bit. Lifting to `useState<Record<string, boolean>>({})` keyed by `tc.id` at the `ToolCallPanel` component scope is React-safe; `useState` inside the `displayItems.map` callback is NOT (would create new state per render). The toggle setter handles the default-for-active default value: `setPanelExpanded(prev => ({ ...prev, [id]: !(prev[id] ?? defaultExpanded) }))`.
- **`actions = useStreamsStore.getState().actions; vi.spyOn(actions, 'clearThreadBucket')` is the canonical zero-call assertion pattern.** The provider replaces the actions object exactly once at mount (`useStreamsStore.setState({ actions: {...} })` at `StreamsProvider.tsx:678`); subsequent consumers read `useStreamsStore.getState().actions.clearThreadBucket` which resolves to the SAME object reference. Spying on the function property persists across the full streaming run.
