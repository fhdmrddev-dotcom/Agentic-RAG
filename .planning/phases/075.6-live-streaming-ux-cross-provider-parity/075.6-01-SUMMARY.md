## Decisions Made

- **Per-iteration-fresh twin dicts** (not a single 2-level mapping) for the per-provider boundary state — matches the existing reset semantics verbatim and keeps the lookup branch shallow inside the chunk callback.
- **Forwarder-by-forwarder edits** for the cross-provider field — the 3 forwarders in threads.py (`_on_chunk_anthropic`, `_on_chunk_google`, `_on_chunk_openai`) all use EXPLICIT kwarg lists to `_emit`, so an additive field requires one edit per forwarder (no `**kwargs` spread).
- **Plan-deviated test fixture parameters:** T3 OpenAI execute_code test uses `chunk_size=2048, n_chunks=8` (16 KB → 3 boundaries) per the plan's `<read_first>` block, not the helper's defaults of `chunk_size=1024, n_chunks=12` (12 KB → 2 boundaries) — to satisfy the `>=3` acceptance threshold.
- **Comment rewording to satisfy static gates:** The literal strings `_tool_name != "execute_code"` and `openrouter_service.py` were removed from defensive comment blocks to satisfy `! git grep` style acceptance criteria (zero matches anywhere in the file, including comments).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Three threads.py forwarders strip the new `code_so_far` field**
- **Found during:** Task 1 verification run (`test_anthropic_path_emits_code_so_far` failed asserting `code_so_far in event`)
- **Issue:** `_on_chunk_anthropic` at L1898-1911 forwards `tool_args_progress` events to `_emit` with an EXPLICIT kwarg list, so any new field on the producer side is silently dropped. Same pattern in `_on_chunk_google` at L2003-2011.
- **Fix:** Added `code_so_far=_ant_event["code_so_far"]` to the Anthropic forwarder (T1 commit `e87b36a`); added `code_so_far=_g_event["code_so_far"]` to the Google forwarder (T2 commit `05bcdac`). The OpenAI/OpenRouter shared callback uses an inline `_emit` call (no forwarder indirection) so it was already covered by Task 3's Edit 2.
- **Files modified:** backend/app/api/threads.py
- **Verification:** All 9 tests in `test_075_tool_args_progress.py` GREEN after fix.
- **Committed in:** `e87b36a` (Task 1) and `05bcdac` (Task 2).

**2. [Rule 2 — Missing Critical] `_capture_run_events` was silently routing OpenAI tests through Google**
- **Found during:** Task 3 verification run (`test_openai_path_emits_for_execute_code` failed with `ValueError: contents are required` from `google.genai`)
- **Issue:** The test helper `_capture_run_events` did NOT patch `load_user_settings`. Dev `.env` has `LLM_PROVIDER=google`, so threads.py's agent loop took the Google branch (`elif active_provider_name == "google":`) and called `stream_google` — invalidating tests whose docstrings claim to exercise "the OpenAI accumulator". Three pre-existing baseline tests (`test_tool_args_progress_fires_on_5kb_boundary`, `test_args_so_far_bounded`, `test_total_bytes_monotonic`) were quietly RED for this reason; both new T3 tests inherited the same issue.
- **Fix:** Added `_force_openai_settings` patch on `app.api.threads.load_user_settings` inside `_capture_run_events`, mirroring `_capture_anthropic_events`. Forces `active_provider="openai"` + `llm_model="gpt-4o"` so the agent loop takes the OpenAI/OpenRouter shared chunk-handler branch.
- **Files modified:** backend/tests/integration/test_075_tool_args_progress.py
- **Verification:** 3 pre-existing baseline OpenAI tests now GREEN; both new T3 tests GREEN; full file 9/9; combined file pair 12/12.
- **Committed in:** `efa62fd` (Task 3).
