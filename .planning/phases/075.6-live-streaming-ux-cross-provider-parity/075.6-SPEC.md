# Phase 075.6: Live Streaming UX + Cross-Provider Parity — Specification

**Created:** 2026-05-23
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

During every `tool_preparing → tool_start` window for `execute_code` exceeding the 5 KB cadence threshold, the assistant turn renders a live code panel that shows the LLM-generated code text growing monotonically — on all four LLM providers (Anthropic, Google, OpenAI, OpenRouter) using one provider-agnostic frontend component fed by one normalized SSE event vocabulary.

## Background

T-260523-09 (commit `0a5a2db`, 2026-05-23) added a `(X.X KB)` byte-counter badge to the "Preparing code…" row during `tool_preparing` state. The badge ticks rapidly from ~5 KB to ~40 KB in under 1 second per execute_code call, then disappears when `tool_start` fires. The 60-120 second LLM-generation pause the user actually feels — which is what triggered T-260523-09 — remained silent: the badge appears, ticks fast, vanishes, and the user stares at a static "Executing code…" row for the rest of the pause window.

Chrome-MCP-driven comparison with Claude.ai on 3 prompts (4 recordings, ~775s analyzed in `.planning/phases/075.5-gemini-native-sdk/claude-ai-comparison/COMPARISON.md`) identified the gold-standard pattern: **live code streams into a scrollable panel during prep**, plus step-list collapse once 3+ steps accumulate, plus a pinned "Working" badge. Audit of existing wiring confirmed:

- Backend already streams raw `input_json_delta` chunks per provider (anthropic_service.py:245 area), but aggregates them on 5 KB boundaries into `tool_args_progress` events that carry ONLY `total_args_bytes_so_far` (a number), discarding the chunk text.
- Frontend already wires `onToolArgsProgress(toolIndex, name, totalArgsBytesSoFar)` → `StreamsProvider.tsx:293-315` reducer → `ToolCallPanel.tsx:743-746` badge render. The reducer slice and render path exist; only the **text payload** is missing from the event.
- Phase 068 (StreamsProvider Context lift) ✅ done; Phase 068.5 (in-flight pulse + cached snapshot render) ✅ done; Phase 075 (tool_args_progress backend event) ✅ done. ~80% of substrate is in place.
- T-260523-09 fix in commit `0a5a2db` only touched Anthropic + Google service modules. **OpenAI** (`openai_service.py`) and **OpenRouter** (`openrouter_service.py`) still never emit `tool_args_progress` for `execute_code`, violating the "one UX, four adapters" rule recorded in `feedback-provider-uniform-ux` memory.

The gap is therefore narrow: one new field on an existing event (provider-uniform across 4 adapters), one new frontend collapsible component, and three small frontend rendering improvements (sub-agent live surface, step-list collapse, "Working" badge) that surface already-accumulated state.

## Requirements

1. **`code_so_far` field on `tool_args_progress` event (backend, provider-uniform vocabulary)**: The existing `tool_args_progress` SSE event gains an additive `code_so_far: string` field carrying the cumulative tool-args text streamed from the LLM up to the 5 KB-boundary trigger point. Same 5 KB cadence; no new event type.
   - Current: event payload is `{type: "tool_args_progress", tool_index: N, name: "execute_code", total_args_bytes_so_far: N}` — text content is buffered server-side then discarded; T-260523-09 fix only emits the byte count.
   - Target: event payload gains `code_so_far: string` containing the cumulative args text up to the trigger boundary. Emitted by all 4 service adapters (`anthropic_service.py`, `google_service.py`, `openai_service.py`, `openrouter_service.py`).
   - Acceptance: For an execute_code call generating ≥10 KB of args on each of the 4 providers, the Redis run buffer contains ≥2 `tool_args_progress` events where `code_so_far` is a non-empty string AND `code_so_far` of event N is a string prefix of `code_so_far` of event N+1 (monotonic growth).

2. **OpenAI adapter emits `tool_args_progress` for `execute_code` (cross-provider parity)**: `openai_service.py` aggregates `chat.completions.chunk.choices[0].delta.tool_calls[N].function.arguments` string deltas and emits `tool_args_progress` on the same 5 KB cadence as Anthropic + Google, with `code_so_far` populated.
   - Current: `openai_service.py` never emits `tool_args_progress` for `execute_code` (or any tool). Commit `0a5a2db` only modified Anthropic + Google.
   - Target: OpenAI adapter emits the normalized `tool_args_progress` event for `execute_code` calls whose accumulated args cross each 5 KB boundary, with `code_so_far` set to the aggregated `function.arguments` text.
   - Acceptance: A Chrome MCP UAT run on OpenAI gpt-4.1 (or current default OpenAI model) submitting the 12-page matplotlib gallery prompt produces ≥3 `tool_args_progress` Redis events for the `execute_code` call where `code_so_far` is monotonically growing.

3. **OpenRouter adapter emits `tool_args_progress` for `execute_code` (cross-provider parity)**: `openrouter_service.py` aggregates upstream OpenAI-shaped `function.arguments` deltas (locked decision per Boundary Keeper round) and emits `tool_args_progress` on the same 5 KB cadence.
   - Current: `openrouter_service.py` never emits `tool_args_progress` for `execute_code`.
   - Target: OpenRouter adapter emits the normalized `tool_args_progress` event for `execute_code` calls, aggregating upstream OpenAI-shaped chunk deltas. Adapter remains independent of the OpenAI adapter (no shared code path) so upstream format divergence doesn't silently break.
   - Acceptance: A Chrome MCP UAT run on an OpenRouter model that routes to an OpenAI-shaped upstream (e.g., `openai/gpt-4.1`) submitting the gallery prompt produces ≥3 `tool_args_progress` Redis events with monotonic `code_so_far`.

4. **`<ToolArgsLivePanel>` frontend component renders during preparing state**: A new collapsible code panel renders inside `ToolCallPanel.tsx` for each tool call whose `tc.status === 'preparing'` AND `tc.argsCodeText` is non-empty. Default state: **expanded for the active (most recent) preparing tool, collapsed for any past preparing tools** (locked per Boundary Keeper round). On `tool_start` (status transitions to `running`), the panel auto-collapses; the byte counter that was the header badge moves inside the panel as a small label for at-a-glance scan.
   - Current: `ToolCallPanel.tsx:743-746` renders `(X.X KB)` text-only badge that disappears when `tool_start` flips the status from `preparing` to `running`.
   - Target: New `<ToolArgsLivePanel>` component with `<pre><code>` body showing `tc.argsCodeText`, a header row with the byte counter + chevron, default-expanded for the active preparing tool. Auto-collapses on `tool_start` (panel persists but collapsed; final args remain in `tc.args.code` and the existing post-start code-block render becomes the source of truth).
   - Acceptance: Chrome MCP screenshot taken during the `tool_preparing` window of a ≥10 KB execute_code call on any of the 4 providers shows the panel expanded with at least 5 KB of streaming code text visible; a follow-up screenshot ≥500ms after `tool_start` fires shows the panel collapsed.

5. **`argsCodeText` reducer slice (frontend state plumbing)**: `ToolCall` type gains an `argsCodeText?: string` field; `StreamsProvider.tsx` `onToolArgsProgress` reducer sets `tc.argsCodeText = codeSoFar` when `codeSoFar.length > (tc.argsCodeText ?? '').length` (string-superset replace, analogous to existing Math.max for `argsBytesStreamed`); cleared on `tool_start` transition (panel keeps the text but the new `tc.args.code` becomes the source of truth).
   - Current: `StreamsProvider.tsx:293-315` updates only `tc.argsBytesStreamed` via Math.max; no string field exists.
   - Target: Reducer also updates `tc.argsCodeText` with the new `code_so_far` payload when it's longer than what's already stored. On `onToolStart`, reducer clears or marks the field as "frozen" so post-start renders use `tc.args.code` instead.
   - Acceptance: Vitest test asserts that calling `onToolArgsProgress(0, 'execute_code', 5121, 'CHUNK_A')` followed by `onToolArgsProgress(0, 'execute_code', 10241, 'CHUNK_A_PLUS_B')` sets `tc.argsCodeText` to `'CHUNK_A_PLUS_B'` (longer string wins); reverse order keeps `'CHUNK_A_PLUS_B'` (Math.max-but-string equivalent).

6. **Sub-agent live content surfaces for ALL sub-agent kinds (drop narrow gate)**: The current rendering gate at `ToolCallPanel.tsx:694` (`tc.sub_agent ?? (tc.name === "analyze_document" ? subAgent : undefined)`) restricts live `m.sub_agent.content` rendering to the `analyze_document` tool only. Remove the name-based gate so any sub-agent run surfaces its live content.
   - Current: 323 sub_agent_delta events accumulate into `m.sub_agent.content` on a PPTX run; only the `analyze_document` tool row renders it. Sub-agents spawned by other tools see their content discarded from the UI (still accumulated in state).
   - Target: `ToolCallPanel.tsx:694` reads `tc.sub_agent ?? subAgent` (drops the name check). Any sub-agent run shows its live content in the tool row that triggered it.
   - Acceptance: A run that spawns a sub-agent from a non-`analyze_document` tool (manual UAT trigger — any tool that delegates to sub_agent_service.py) renders the streaming sub-agent text inside that tool's row in real time; verified via Chrome MCP screenshot showing >0 chars of sub-agent text during the sub-agent run.

7. **Step-list collapses when ≥3 completed tool calls precede the active step**: When the deduplicated tool-calls array contains ≥3 entries with `status === 'done'` BEFORE the active (running/preparing) tool, those completed entries render as a single summary row `▸ Completed N steps (X tools used)` with a chevron; expanding the chevron restores per-step rendering. Threshold N=3 locked per Boundary Keeper round.
   - Current: every tool call renders as its own row regardless of count; long tool chains (10+) grow the chat surface unboundedly tall.
   - Target: collapse logic in ToolCallPanel.tsx detects the count of consecutive completed steps preceding the active step; when ≥3, replaces them with one summary row + chevron. Active step always stays expanded; iteration divider semantics preserved (D-067-03 at ToolCallPanel.tsx:705 must still fire correctly across the collapsed/expanded boundary).
   - Acceptance: A run with 5 completed execute_code steps followed by a 6th active step renders 4 rows (one collapsed summary + the active step); clicking the chevron expands to 6 rows. Iteration divider between iteration-N and iteration-N+1 renders correctly in both collapsed and expanded states.

8. **Pinned "✦ Working" badge at top of active assistant turn**: Renders at the top of the assistant message bubble whenever `(activeTool || m.isPlanning) && !allDone`. Disappears on terminal (`allDone === true`). Uses the existing pink-orange brand accent.
   - Current: in-flight indicator is contextual (a spinner inside the active step row); no top-level pinned indicator at the assistant turn level.
   - Target: small `<WorkingBadge>` component at the top of `MessageItem.tsx` for assistant messages, gated on the derived condition `(activeTool || isPlanning) && !allDone`. Visual: `✦ Working` text with a subtle pulse animation (reuse the brand pulse from Phase 068.5 if present, otherwise CSS keyframe in `index.css`).
   - Acceptance: Chrome MCP screenshot during an active assistant turn shows the `✦ Working` badge at the top of the bubble; screenshot ≥500ms after terminal SSE shows the badge gone.

9. **Provider-uniform: zero per-provider UX branches**: The frontend code paths in `StreamsProvider.tsx`, `ToolCallPanel.tsx`, and any new components MUST NOT contain `if (provider === 'X')` branches for any of the new rendering behaviors. The "one UX, four adapters" invariant from `feedback-provider-uniform-ux` memory holds: any provider-specific behavior lives ONLY in the backend service adapter that normalizes into the shared event vocabulary.
   - Current: existing frontend has some provider-specific dedup logic (Phase 075.1 Plan 04 Atom B) but no provider-conditional rendering for tool prep.
   - Target: new components have zero provider-conditional rendering; adapter normalization is the sole point of provider-specific code.
   - Acceptance: `git grep -E "provider\s*===\s*['\"]" frontend/src/components/chat/` and `git grep -E "provider\s*===\s*['\"]" frontend/src/providers/StreamsProvider.tsx` return zero matches added by this phase's plans.

## Boundaries

**In scope:**
- Additive `code_so_far: string` field on existing `tool_args_progress` SSE event in all 4 service adapters
- OpenAI + OpenRouter adapter implementations of `tool_args_progress` for `execute_code` (Anthropic + Google already done in commit `0a5a2db`)
- New `<ToolArgsLivePanel>` frontend component (collapsible, default-expanded-for-active-preparing-tool)
- `argsCodeText` reducer slice in StreamsProvider
- Drop the `tc.name === "analyze_document"` narrow gate on sub-agent live rendering at ToolCallPanel.tsx:694
- Step-list collapse when ≥3 completed tool calls precede active step (N=3 locked)
- Pinned `✦ Working` badge at top of active assistant turn
- Vitest regression tests for the new reducer slice + the Phase 067.5 Branch D-3 guard preservation
- Chrome MCP UAT covering the 4-axis bandwidth mandated by CLAUDE.md (cross-provider × multi-tool × parallel-thread × long-message)

**Out of scope:**
- **File output card polish** (T-260523-10: intermediate vs final classification, thumbnails, type icons) — separate concern (file lifecycle, not streaming UX); SEED into next polish bundle
- **Live PPTX preview pane** (right-side page navigator like Claude.ai recording 2) — requires server-side PPTX-to-image conversion + a new rendering surface; significant scope; defer
- **Extended-thinking summary collapsible block** (Claude.ai Adaptive mode pattern in recording 4) — only relevant once thinking models (claude-opus-4-7 Extended Thinking, gpt-5-thinking, o3) are wired; fold into a future model-routing phase
- **Removing the T-260523-09 byte counter** — byte counter stays inside the new panel as a small header label for at-a-glance scan; the COMMIT that closes T-260523-09 with disposition "superseded" happens separately after 075.6 ships and UAT confirms the panel replaces the felt-silence problem
- **OpenAI/OpenRouter token usage parity** (separate from streaming UX) — tracked elsewhere; not in this phase
- **Provider-specific UI branches** — explicitly forbidden by Requirement #9; if a provider's adapter can't emit the normalized event, the adapter is incomplete (not the UI's problem)
- **Backend buffering strategy redesign** (e.g., variable-cadence boundaries, adaptive throttling) — stay with the existing 5 KB cadence; tune later if UAT surfaces a problem
- **Storing args text in `messages.tool_calls` JSONB for replay** — DB-loaded historical messages already have `tc.args.code`; the live panel is only for in-flight runs

## Constraints

- **Phase 067.5 Branch D-3 guard at `useMessages.ts:572-590` must survive verbatim** — the per-thread bucket invariant that refuses `clearMessages` on streaming threads has survived Phases 068, 068.5, 075, 075.1, 075.2, 075.3, 075.4 unchanged; 075.6 frontend changes MUST NOT touch that guard. Existing Vitest regression test L-068-01 must stay green.
- **Provider-uniform vocabulary is mandatory** — `feedback-provider-uniform-ux` memory rule. Backend adapters normalize; frontend has zero `if (provider === ...)` branches for new behavior.
- **No backward-compat break** — `code_so_far` is an additive field on an existing event. Any consumer that ignores unknown fields continues working. DB-loaded historical `messages.tool_calls` JSON does NOT need migration (the live panel only renders for in-flight `tc.status === 'preparing'`).
- **4-axis UAT bandwidth is mandatory** per CLAUDE.md SC#10: cross-provider (all 4) × multi-tool (≥1 row with 2+ tools in one prompt) × parallel-thread (≥1 row with Thread A streaming while Thread B accepts a new prompt) × long-message (≥1 row with ≥50 prior messages OR ≥5 KB user prompt). UAT rows live in VALIDATION.md, not PLAN.md tasks.
- **Iteration divider semantics (D-067-03)** at `ToolCallPanel.tsx:705` must still fire correctly when step-list collapse merges multiple iterations into one summary row. Plan 03 must spec the divider behavior across the collapsed/expanded boundary explicitly.
- **No new event types** — locked decision (Boundary Keeper round): additive field on existing event, not a separate `tool_args_text_delta` event. Keeps event count on the wire flat.
- **Single uvicorn worker assumption** (CLAUDE.md rule) — all backend changes assume in-process aggregation buffers; safe under current `--workers 1` config. When Phase 079 enables `--workers 2`, the per-worker aggregation is naturally isolated (no shared state needed).
