<objective>
Make the Settings judge-model knob obey. Route all four judge consumers off the env-backed
`app.config.settings` singleton and onto the DB-backed `UserEffectiveSettings` the rest of the app uses.

Purpose: `BUG-260731-01` (`severity: critical`, folded into this phase as **D-17**) reproduces exactly on
today's `develop`, re-measured this planning session:

| Source | Value |
|---|---|
| `app_settings.harness_judge_model` — what the operator set in the UI | `deepseek-v4-pro` |
| `settings.harness_judge_model` — the env singleton every consumer reads | `None` |
| `resolve_judge_model(settings)` — what the judge shot actually uses | `claude-opus-4-8` |

⚠ It fails in the **expensive** direction — the fallback is a top-tier model while the operator's stated
goal was to spend less — and the publish-gauntlet judge is a **hard wall**. This is one of the three
faces of the same defect this phase exists to remove: *a control that lies about what will actually run.*

⚠ **The report's own condition is BINDING and is not optional garnish.** The fix MUST ship a test that
sets the row and asserts the RESOLVED model changes: *"the absence of that test is why this survived
from 2026-07-31 to 2026-08-17."* This plan writes that test FIRST, drives all four cases RED, and only
then changes the consumers.

Output: four rewired consumers, one new RED-first test file with five cases, and one seed recording the
latent flag drift as a future gate.

**Parallel-safety:** every case in this plan patches `app.models.user_settings._load_settings_from_db`
and mutates **zero** database rows, so CLAUDE.md rule 4's serialisation constraint does not bind. A
`files_modified` check cannot see a database write — this sentence is the flag.
