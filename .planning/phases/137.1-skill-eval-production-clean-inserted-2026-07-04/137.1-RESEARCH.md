## Summary

This phase is a **brownfield hardening + additive-UI pass** on the eval engine shipped and battle-tested across Phases 133–137. There is **no new runtime, no new external dependency, and no new architectural tier** — every deliverable extends an existing, well-instrumented seam. The eval runner (`backend/app/services/eval_runner_service.py`, 838 lines) and its control router (`backend/app/api/evals.py`, 1908 lines) already give you: the per-arm SSE vocabulary (`eval_case_started`/`eval_case_done`/`eval_verdict`/`eval_complete`/`eval_heartbeat`), the honest verdict-state machine (`graded`/`not_measured`/`judge_error`), the Redis `SET NX` one-eval-per-skill claim, the companion `public.runs` row that makes stream/cancel reuse work with zero new stream code, and the judge evidence channel (`dd694916`, shipped 2026-07-04). The frontend homes (`EvalsTab`/`RunBar`/`RunHistory`/`RunCaseDetail`) already lift this machinery verbatim.

The work splits cleanly across three tiers. **Backend/API:** a matrix launch route (`evals.py`) that fans one skill's eval into N parallel single-provider runs under one group claim; a boot-time reconciler module mounted in the FastAPI lifespan (direct precedent: `harness_engine.resume_stranded_workflows`); a duration timer + `case_feedback` capture in the runner; the judge-model knob exposed through the settings API; and — only if a re-test still reproduces them — the two provider request-shape fixes at the gateway/adapter boundary (D-14). **Database:** exactly ONE additive migration (next number: **085**) adding matrix-group columns + gate-feeder flag on `eval_runs` and `duration_ms` + `case_feedback` on `eval_results`. **Frontend:** the matrix launcher + gate-feeder chip, the grouped matrix card + history-derived aggregation + deterministic analyst notes, the determinate progress bar (pure frontend unit math), the inline `case_feedback` block, and the Settings Engine-health card + judge picker — all bounded by the operator-locked sketches **058-A / 059-A / 060-A**.

**Primary recommendation:** Sequence the plan so the two bug re-tests (D-14) come FIRST (they gate whether any adapter fix is even needed and whether aggregation builds on trustworthy verdicts), then the additive migration, then backend matrix/reconciler/duration/case_feedback, then the sketch-bounded UI. Do not hand-roll parallel-run orchestration, verdict math, or stream re-attach — every one of those already exists and rewriting it re-introduces fixed races.

### Pattern 1: N parallel arms under ONE group claim (D-06)
**What:** A matrix run is N independent single-provider `run_eval_job` invocations, each with its own `run_id`/`eval_runs` row/companion `runs` row/Redis buffer — but gated by ONE `SET NX` claim taken once for the whole group.
**When to use:** The matrix launch route.
**Why it works:** `run_eval_job` is already fully self-contained per run (`eval_runner_service.py:678`). The existing single-run route takes the claim at `evals.py:229`. For the matrix, take the claim once (keyed by skill_id per D-06), then spawn N jobs; the group's `finally` releases the claim after ALL arms finish. N rows in the UI = N existing per-run `subscribeToRun` subscriptions (`EvalsTab.tsx:143`) — zero new stream code.
```python
# Pattern (evals.py) — sketch, not literal:
claimed = await redis.set(_inflight_key(skill_id), str(group_id), nx=True, ex=_INFLIGHT_TTL_S)
if not claimed: raise HTTPException(409, "An eval run is already in progress for this skill")
for cfg in configs:                       # one representative model per configured provider
    run_id = uuid4()
    feeds_gate = (cfg.provider == active_provider)   # D-05: exactly one True
    # insert eval_runs (matrix_group_id=group_id, feeds_gate=feeds_gate) + companion runs row
    spawn(run_eval_job(run_id=run_id, ..., provider=cfg.provider, model=cfg.model))
# release the group claim only after the LAST arm's finally (see Pitfall 3)
```

### Pattern 2: One-truth-teller gate — the chip is a LABEL, not a computation (D-05, 137 D-03)
**What:** The publish gate reads exactly the ONE run in the group whose `feeds_gate=true`. The "▣ feeds gate" chip in the UI renders off that same flag.
**When to use:** Matrix group rendering + the publish-gate read path.
**Why it works:** `promotion_gate()`/`_compute_gate()` (`evals.py:1059,1111`) already compute the gate from a single run's rows. Scope the gate read to the `feeds_gate` run; the other N−1 runs are never fed to the gate. Do NOT add a second gate computation — the plan-checker verifies tier correctness here.

### Pattern 3: Boot-time reconciliation (D-09/D-10) — mirror `resume_stranded_workflows`
**What:** On startup, sweep runs that are non-terminal in Postgres but absent from the Redis `runs:active` sorted set (the authoritative "actually streaming" set), flip them to their honest terminal, and drop their stale streams.
**When to use:** A NEW `run_reconciler.py`, mounted in the lifespan.
**Why it works:** `harness_engine.resume_stranded_workflows` (`harness_engine.py:1672`) is the exact precedent — a lifespan-spawned background task with a CAS claim so WORKER_COUNT=2 never double-runs. The lifespan already spawns `_resume_stranded` (`main.py:257-269`) and `_sweep_expired_templates` (`main.py:279-291`) this way.
```python
# main.py lifespan (mirror the existing _resume_stranded block at :257-269):
async def _reconcile_orphans():
    try:
        from app.services.run_reconciler import reconcile_orphaned_runs
        n = await reconcile_orphaned_runs(pool=await get_pg_pool(), redis=get_redis(),
                                          supabase=get_supabase())
        if n: logger.info("Run reconciler closed %d orphaned run(s)", n)
    except Exception:
        logger.exception("Run reconciler failed (app continues)")
asyncio.create_task(_reconcile_orphans())
```
Staleness predicate (D-10 / from BUG-260702-02 evidence): `status IN ('running')` for `eval_runs` (or `streaming`/`cap_paused` for `runs`) AND the run_id is absent from `runs:active`. Single-shot Redis `SET NX` guard (e.g. `run_reconcile_lock`) so only one worker performs the sweep. This is EXACTLY what the manual 2026-07-02 cleanup did (eval→`interrupted`, chat→`failed`, delete stale `run:*`).

### Pattern 4: Determinate progress is pure FRONTEND math (EVAL-05c)
**What:** `total units = case_count × 2 arms + 1 judge step`; increment on each `eval_case_done` (and optionally a judge-step unit).
**When to use:** RunHistory's running-row treatment (059-A thin bar).
**Why it works:** The per-arm events already stream — `EvalsTab.tsx:149-160` already maps `onEvalCaseStarted`/`onEvalCaseDone`/`onEvalVerdict` into a `live` status map keyed `${testCaseId}:${variant}`. The bar reads off that map. **No backend change** — do not add a progress event. The judge step has no dedicated SSE event today; treat "judge step" as one unit that completes when `eval_complete` arrives (059-A renders it as one unit; confirm at plan).

### Pattern 5: Judge-model knob = settings-API exposure, no migration (D-11/D-12)
**What:** `harness_judge_model` already exists as an `app_settings` field (`config.py:1006`) and is resolved by `resolve_judge_model(settings)` (`validator_kinds.py:58-80`), which BOTH the eval judge (`eval_runner_service.py:300`) and the publish judge (`publish_service.py:668`) call. It is DB-only with no UI.
**When to use:** The Settings judge picker.
**Why it works:** `skill_builder_model` is the exact precedent for exposing an `app_settings` model field with UI. Copy that wiring: `SettingsResponse` returns raw + resolved (`settings.py:73-78,195-196`), `SettingsUpdate.harness_judge_model` (`settings.py:143,344-345`), persisted in `save_app_settings`. D-12 registry validation = the picker offers only `get_model_capability(id)` "registry" models (the `evals.py:165-170` model-validation rule), and shows `resolve_judge_model` output when unset.

### Anti-Patterns to Avoid
- **Forking the shared agent loop for a provider fix (D-14 red line).** BUG-260701-01/-260630-01 fixes go in `provider_gateway/anthropic.py` / `openai_compat.py` (+ possibly a MODEL_CAPABILITIES flag), never in `agent_loop.py`. Deep Mode stays byte-identical.
- **A second gate computation.** The gate-feeder chip is a label; never recompute `met`.
- **Emitting mid-run verdicts.** Verdicts land only at finalize (`EvalsTab.tsx:161-164` loads the durable DB readout on `eval_complete`; T-137-04). The determinate bar shows completion, never pass/fail.
- **Counting `not_measured`/`judge_error` as fail.** The rollup denominator is with-skill `graded` arms only (`eval_runner_service.py:797-799`); aggregation must inherit this.
- **A per-click cost multiplier / repeat knob.** D-07: ×1 run per provider per click; stddev accumulates from run HISTORY (renders only at n≥2).
- **A new eval-per-arm claim.** One claim per matrix group (D-06).

## Common Pitfalls

### Pitfall 1: Releasing the group claim too early (D-06)
**What goes wrong:** If the matrix route releases the `SET NX` claim when the FIRST arm finishes, a second run can start while other arms are still live — breaking one-eval-per-skill.
**Why it happens:** Each `run_eval_job` has its OWN `finally` that CAS-releases `eval_inflight:{skill_id}` (`eval_runner_service.py:833`). For a matrix, that single-run release logic would fire N times.
**How to avoid:** The group claim value should be the GROUP id (not a per-arm run_id), and only a group-level coordinator releases it after ALL arms complete. Either (a) suppress the per-job release for matrix arms (pass a flag) and release once at the group level, or (b) use CAS-release-if-owned keyed to the group id so an early arm's release is a no-op (the existing `_release_inflight_if_owned` CAS at `eval_runner_service.py:152` already no-ops when the stored value differs — leverage that).
**Warning signs:** A 409 that clears before the matrix UI shows all arms done; a second run starting mid-matrix.

### Pitfall 2: The smoke skill has no "hidden" mechanism yet
**What goes wrong:** The `skills` table has only `is_enabled` + `is_global` (`full-schema.sql:1040-1050`) — no hidden/system flag. A seeded smoke skill would appear in the user's Skills list, contradicting D-02.
**Why it happens:** No prior phase needed a hidden system skill.
**How to avoid:** Three options for the planner (Open Question): (a) a synthesized in-memory catalog_override + case, never a DB skills row (cleanest — the matrix route for the sweep synthesizes the WITH-arm catalog and the single case directly, bypassing `_read_cases`); (b) a real seeded skill filtered from `list_skills` by a well-known system user_id / name prefix; (c) a new `is_builtin`/`is_hidden` column (larger migration — CREATE-01/137.2 may want this anyway). Coordinate with 137.2's `is_global` built-in-skill plan.
**Warning signs:** A "smoke" skill visible in the user's Skills tab.

### Pitfall 3: `case_feedback` bleeding into the verdict (EVAL-05d honesty lock)
**What goes wrong:** If `case_feedback` renders like a verdict (amber/red, in the rollup, next to PASS/FAIL), it reads as a failure signal — but it is advisory critique of the CASE, never blocking.
**Why it happens:** RunCaseDetail already renders verdict chips with amber/red tones (`RunCaseDetail.tsx:128-137`).
**How to avoid:** 059-A locks the vocabulary: violet (info), dashed-border "◇ Judge on this case" block, visually distinct from PASS/FAIL, never in rollup math. Store it separately from `verdict_*` fields.
**Warning signs:** A non-discriminating case reading as a fail; `case_feedback` changing a pass count.

### Pitfall 4: Aggregation reading as if one click bought N repeats (D-07)
**What goes wrong:** Showing mean±stddev after a single matrix click implies the run was repeated 3×.
**Why it happens:** stddev needs ≥2 samples; a first run has none.
**How to avoid:** 058-A lock: "×1 run per click — spread accumulates from history"; stddev renders ONLY at n≥2 per config; a first run shows "first run — no spread yet". The aggregation query reads accumulated `eval_runs` HISTORY per (skill, provider, model), not the single click.
**Warning signs:** stddev shown on a config's first-ever run.

### Pitfall 5: Assuming the two provider bugs still exist (D-14)
**What goes wrong:** Writing an adapter fix for BUG-260630-01 / BUG-260701-01 before re-testing wastes effort and risks touching the gateway needlessly.
**Why it happens:** `f47d6736` (reset before EACH arm) removed the replayed with-skill assistant turn that likely CAUSED the DeepSeek `reasoning_content` 400 (BUG-260630-01). BUG-260701-01 (Claude 4.6+/5 prefill 400) may be a genuinely separate request-shape trap.
**How to avoid:** The plan's FIRST eval-touching task re-tests BOTH live (the smoke sweep is the natural vehicle — it runs the without-skill arm on all 8 providers). Only if a bug reproduces does an adapter fix follow. Close BUG-260630-01 on a clean re-verify.
**Warning signs:** An adapter diff landing with no reproduction evidence.

### Pitfall 6: Reconciler flipping a legitimately-live run
**What goes wrong:** A run that IS streaming (present in `runs:active`) gets flipped to `interrupted` by an over-eager staleness predicate.
**Why it happens:** A naive "status='running'" filter without the `runs:active` cross-check.
**How to avoid:** The predicate MUST be "non-terminal in PG AND absent from `runs:active`" (the authoritative streaming set — CLAUDE.md run-buffer key conventions). Run the sweep once at boot before new runs start; the CAS guard prevents double-sweep.
**Warning signs:** An in-flight run interrupted right after a boot; `runs:active` and PG disagreeing.

## Open Questions

1. **Smoke-skill storage: in-memory synthesized vs seeded-and-filtered vs new hidden column?**
   - What we know: `skills` has no hidden flag (`full-schema.sql:1040`); the sweep must ride matrix machinery (D-01) which reads a skill's cases/version.
   - What's unclear: whether the sweep route synthesizes the WITH-arm catalog + single case directly (bypassing `_read_cases`/`_read_latest_version`), or seeds a real hidden skill.
   - Recommendation: prefer the in-memory synthesized path for the sweep (no seeded DB state, no deploy-parity burden, no Skills-list pollution) — but coordinate with 137.2 (CREATE-01) which is already introducing a seeded `is_global` built-in skill; if 137.2 adds an `is_builtin`/hidden mechanism, the smoke skill can reuse it. Flag for discuss/plan.

2. **Migration shape: nullable columns on `eval_runs` vs a new `eval_matrix_groups` table?**
   - What we know: 080/081 precedent is additive columns; a matrix needs a group id shared across N runs + a per-run gate flag.
   - Recommendation: nullable `matrix_group_id uuid` + `feeds_gate boolean DEFAULT false` on `eval_runs` (single-run rows get NULL group + false gate; a single run's gate read is unchanged). Add `duration_ms integer` + `case_feedback text` on `eval_results`. One migration (085). A separate groups table is only worth it if per-group metadata (launcher config, active-provider snapshot) needs its own row — likely not for this scope.

3. **`case_feedback` — one judge shot per arm, or a separate case-quality shot?**
   - What we know: the judge already grades per-arm (`_judge_eval_answer`); grader.md Step 6 provides the "weak assertion / non-discriminating case" criteria.
   - What's unclear: whether to add `case_feedback` to the SAME `JudgeVerdict` emission (cheaper, one shot) or a distinct shot (cleaner separation but +1 LLM call per case).
   - Recommendation: add it to the same forced emission (Code Examples above). Store once per case (it critiques the CASE, not the arm) — likely on the with-skill result row or an `eval_runs`-level per-case map. Confirm placement at plan.

4. **Where does the deterministic analyst-notes computation live (D-08)?**
   - What we know: 058-A says "backend-computed or frontend-derived — planner's call". Inputs = per-config verdicts (non-discriminating), stddev across history (flaky variance), duration+tokens (time-token tradeoff).
   - Recommendation: frontend-derived is viable since all inputs are already in the readout; but backend-computed keeps the fixed phrasing in one place and testable. Lean backend (a small pure function alongside `promotion_gate`) for testability and to keep the honesty phrasing server-authored.
