<decisions>
## Implementation Decisions

### Smoke sweep (EVAL-05a)
- **D-01 Trigger = in-app, riding the matrix machinery.** The sweep IS a matrix run
  (one representative model per configured provider) over a built-in smoke case —
  one machinery serves EVAL-05a and EVAL-05b. Results are live run rows watchable
  like any eval run.
- **D-02 Test fixture = built-in synthetic smoke skill + one case,** shipped by us,
  deterministic and token-cheap, designed to prove ENGINE health only: each arm
  completes with verdict `graded` or an honest `not_measured` carrying a REAL
  provider error — never an engine-shaped error. No user data. The smoke skill is
  HIDDEN from the Skills list (a fixture, not a usable skill).
- **D-03 Results home = an Engine-health card in Settings:** compact per-provider
  ✓/✗ board with last-sweep result + timestamp + "Run sweep" button; each provider
  links to its run detail. ~24 LLM calls/sweep is the accepted budget.
- **D-04 Cadence = on-demand only, staleness always shown** (board displays how old
  the last sweep is). No scheduler, no config-change nudge.

### Matrix runs (EVAL-05b)
- **D-05 Gate semantics = explicit gate-feeder picked at launch.** The launcher
  designates exactly ONE config as gate-feeding (default: the user's active
  provider); that run row carries a "feeds gate" chip; the other N−1 runs are
  analysis-only and never satisfy/flip the publish gate. One-truth-teller (137 D-03)
  preserved — the gate never reads an arbitrary "last to finish".
- **D-06 Lock = one claim for the whole matrix.** The existing per-skill Redis
  `SET NX` guard is acquired once per matrix group; its N arms run in parallel
  underneath it; no other run (single or matrix) can start on that skill while the
  matrix is live. 409 contract unchanged for the loser.
- **D-07 Aggregation = ×1 run per provider per click; mean±stddev/delta computed
  per config across accumulated run HISTORY** ("where run counts allow" — stddev
  appears once a config has ≥2 runs). No repeat knob, no per-click cost multiplier.
- **D-08 Analyst annotations = deterministic rules with fixed plain-language
  phrasing:** non-discriminating case (all configs pass both arms), flaky variance
  (high stddev across a config's runs), time-token tradeoffs (from the new duration
  + existing token data). No LLM analyst paragraph — the judge's `case_feedback`
  (EVAL-05d) is the LLM-side critique, per-case, never blocking.

### Ops half (EVAL-05f/g)
- **D-09 Reconciliation = boot-time sweep** in a standalone startup module (FastAPI
  lifespan): flip stale non-terminal runs to their honest terminal + drop stale
  Redis streams. Worker-safe (single-shot guard, e.g. Redis SET NX — WORKER_COUNT=2).
  No periodic watchdog this phase.
- **D-10 Sweep scope = eval AND chat runs:** eval runs → `interrupted`, chat runs →
  `failed` (exactly what the 2026-07-02 manual cleanup did). The module only writes
  DB statuses + drops streams — additive; NOT in `threads.py` (G-5), no agent-loop
  touch (D-14).
- **D-11 Judge knob = the ONE shared `harness_judge_model`** surfaced in Settings —
  it already drives the eval judge AND the harness/publish judge identically
  (`validator_kinds` resolution). No new setting, no migration, no split.
- **D-12 Judge picker = registry-validated:** reuse the existing Settings
  provider/model picker pattern offering ONLY MODEL_CAPABILITIES-known models
  (the SEED-100 picker↔registry drift lesson); shows the effective default
  (`claude-opus-4-8`) when unset.

### Folded scope extras (SEED-100 harvest)
- **D-13 IN:** (i) description-builder polish — 1024-char cap + auto-shorten retry
  in the Tuner builder; (ii) additive lint — kebab-case skill-name + description-
  length portability warnings, never blocking (D-09 posture, existing 044-A lint
  home). **OUT:** the failure-feedback iteration mode (SEED-100's own hedge — the
  one-round N-candidate design stands). Roadmap SC list stamped with these for
  traceability (SC#7).

### Locked constraints (restated — not gray areas)
- **D-14 red line:** BUG-260701-01, BUG-260630-01, and any provider fix land at the
  gateway/adapter/sanitizer boundary ONLY; the shared agent-loop/Deep path is never
  forked. Re-test BOTH bugs post-`f47d6736` before writing any fix — the baseline
  contamination fix may have closed BUG-260630-01 already; BUG-260701-01 (prefill
  400) may be a genuinely separate request-shape trap.
- **SC#10 FULL roster:** all 8 providers (OpenAI/Anthropic/Google/DeepSeek/Moonshot/
  GLM/MiniMax + OpenRouter), not representative-4. UAT rows authored in
  VALIDATION.md, never PLAN.md tasks. G-4 lived-experience scenarios on the new UI
  (watch a matrix run live, kill the backend mid-run and watch reconciliation).
- **EVAL-05h threat model:** the judge evidence channel (`dd694916`) is new
  judge-prompt surface (tool receipts can carry adversarial doc content) —
  mitigations = rubric data-posture (receipts stay DATA, T-134-02) + 4KB cap; the
  phase's PLAN threat model names both explicitly for secure-phase to verify.
- **Honest-state vocabulary** from 134/137 carries: `not_measured` excluded-never-
  failed, `judge_error` neither, `interrupted` never silent, no mid-run verdicts.
- **G-5 audit:** no ledger file is touched. `evals.py` hosts the matrix/sweep
  routes (eval home, not on ledger); the reconciler is a NEW standalone module;
  `threads.py` / `agent_loop.py` / provider gateway untouched except any
  D-14-boundary bug fix in the adapters/sanitizers.

<specifics>
## Specific Ideas

- The operator's trust bar, verbatim (SEED-100 ask #1): *"how do I know it reflects
  reality for each model without hand-running all 8."* The Engine-health board is
  the answer to that sentence — per-provider, honest, timestamped.
- Smoke sweep asserts ENGINE health, never model pass/fail — a provider whose model
  honestly fails the case but completes both arms is a HEALTHY row.
- The with/without delta became a real skill-value measurement only after
  `dd694916` (FAIL·10 → WITH PASS·72 / WITHOUT FAIL·40 live flip) — matrix
  aggregation builds on trustworthy per-run verdicts, which is why the re-tests
  (D-14) come before the aggregation UI in any plan ordering.
