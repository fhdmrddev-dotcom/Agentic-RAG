## Summary

Phase 162.5 is a pure behavior-preserving (G-5) extraction: ~1,230 LOC of
producer / finalize / kickoff / title / model-resolution logic moved out of
`backend/app/api/threads.py` (2,444 → 1,214 LOC) into 4 new service modules,
and the two near-duplicate finalize routines (`agent_runner._shielded_finalize`
+ `spawn_continuation_run._finalize`) were unified onto one shared
`_finalize_producer_run` in `run_producer.py`.

I checked out the pre-extraction baseline (`263d0b73`) and did a line-by-line
differential of every moved body against its new home, adversarially hunting
for extraction-introduced defects (flipped conditions, dropped guards, changed
gate logic, wrong-namespace resolution, lost `try/except`, altered
async/shield structure). **The core refactor is faithful:**

- **The 8 finalize invariants are preserved byte-identical** in
  `_finalize_producer_run` (persist → sys-warnings → RUN-01b gate `completed
  AND cap_disposition != cap_paused` → finalize_run_terminal / cap_paused→plain
  finalize_run → sentinel-gated-on-membership → EXPIRE 600/60 → harness-F2 gated
  on `active_workflow_run_id is not None AND != completed AND not
  is_app_shutting_down()` → `RUN_TASKS.pop` in the caller's outer finally).
- **The unification is correct.** The continuation path calls the same shared
  finalizer with `active_workflow_run_id=None` (F2 skips naturally) and a
  `cap_paused` `terminal_status` (routes to plain `finalize_run` keeping
  `runs:active`, and the `terminal_status in _RUN_STATUS_TO_TERMINAL_TYPE`
  membership guard skips the sentinel) — byte-identical to the deleted inner
  `_finalize`. The RUN-01b superset gate (`completed AND cap_disposition !=
  cap_paused`) reproduces both the producer's load-bearing two-clause gate and
  the continuation's plain `== completed` gate (the continuation's own outer
  `finally` already converts cap_paused into `terminal_status="cap_paused"`
  before the shared finalizer runs, so the extra clause is redundant-but-safe).
- **The namespace / patch surface holds.** Every moved body late-imports its
  SSE-transport + test-patched collaborators (`_emit`, `finalize_run_terminal`,
  `get_pg_pool`, `run_agent_loop`, `RunContext`, `load_user_settings`,
  `get_llm_client`, `override_provider`, `get_model_capability_async`, …) from
  `app.api.threads`, and every symbol tests import/patch off `threads`
  (`generate_thread_title`, `_ensure_skill_snapshots`, `_resolve_enabled_model`,
  `_reresolve_fallback_provider`, `_apply_fallback_to_request`) is re-exported.
  Verified against the actual usage in `test_149_fallback_notice.py` (drives the
  helpers directly + monkeypatches collaborators at `threads_mod`) and
  `test_099_skill_composition.py` (`from app.api.threads import
  _ensure_skill_snapshots`). All six modules byte-compile; no import cycle at
  module-load time.
- **Async/threadpool correctness preserved.** `asyncio.shield(...)` wraps both
  finalize call-sites; the CancelledError re-raise discipline is intact;
  `generate_thread_title` (sync, blocking SDK call) is still wrapped in
  `run_in_threadpool`. No blocking I/O introduced into an async path.

No BLOCKER defects were found. The findings below are one maintainability
defect (dead imports + now-false comments left in the hot file the phase's
whole purpose was to clean) and two benign INFO notes.

_No `<structural_findings>` pre-pass was provided with this review, so there is
no "Structural Findings (fallow)" section; all findings below are narrative._

## Warnings

### WR-01: Six dead imports + two now-false comments left behind in `threads.py`

**File:** `backend/app/api/threads.py:74-77`, `:84`, `:85`, `:86-89`
**Issue:** The extraction moved the send_message kickoff block and the
`agent_runner` harness scope-resolution block out of `threads.py`, but the
imports those blocks needed were left behind and are now **unused**. All six
symbols had functional call sites in the pre-extraction file (20 uses at
`263d0b73`) and are now referenced nowhere in `threads.py` except their import
lines. I confirmed no other module imports them from `app.api.threads` and
nothing references `threads.<symbol>`, so they are pure dead imports with no
re-export purpose (contrast `_ensure_skill_snapshots` / `generate_thread_title`,
which ARE deliberate re-exports for the test patch surface — those must stay):

- `:77` `from app.services import workflow_kickoff as _workflow_kickoff` — its
  only intended call site (the harness-run-context build) landed in
  `run_producer.py`, which imports `build_harness_run_context` directly. This
  import was added in Plan 02 and orphaned by Plan 03.
- `:84` `from app.utils.folder_utils import fetch_visible_folders` — moved into
  `workflow_kickoff.build_harness_run_context`.
- `:85` `from app.services.harness.scope import resolve_project_subtree,
  assert_folder_scopes_subset, resolve_run_scope_root` — moved into
  `workflow_kickoff.py` (preflight + run-context build).
- `:89` `from app.services.harness import skill_snapshot as _skill_snapshot` —
  moved with `_ensure_skill_snapshots` into `workflow_kickoff.py`.

Worse than the dead imports themselves, the two surviving comment blocks are now
**actively misleading**: `:74-76` asserts the identifier "appears exactly once
in this file — at its single call site in agent_runner's harness branch" (that
branch no longer exists in this file), and `:86-88` says "the kickoff helper
calls validate_skill_refs / materialize_skill_snapshots_if_needed through the
module object" (that helper is now in `workflow_kickoff.py`). These comments
will mislead the Phase 163 RLS/user-JWT crux work, which builds directly on
this exact seam. This is a real (if non-behavioral) defect on a hot file whose
stated G-5 goal was to shrink and clean it. It also leaves unnecessary eager
module-load-time imports of `harness.scope` / `harness.skill_snapshot` /
`workflow_kickoff` on the `threads.py` load path, mildly undercutting the D-A4
break-the-cycle discipline (a future top-level `import app.api.threads` in any
of those modules would now re-introduce a cycle).

**Fix:** Delete the four dead import statements and their two stale comment
blocks (lines 74-77, 84, 85, 86-89):
```python
# remove lines 74-77 entirely (comment + import):
#   from app.services import workflow_kickoff as _workflow_kickoff
# remove line 84:
#   from app.utils.folder_utils import fetch_visible_folders
# remove line 85:
#   from app.services.harness.scope import resolve_project_subtree, assert_folder_scopes_subset, resolve_run_scope_root
# remove lines 86-89 entirely (comment + import):
#   from app.services.harness import skill_snapshot as _skill_snapshot
```
Keep `create_workflow_run`, `ThreadWorkflowState`, `WorkflowPhaseState` (still
used at `:897` / `:1003` / `:1180`). Note: `list_published_workflows` (`:82`)
is ALSO unused, but it was already dead at `263d0b73` (pre-existing — out of
this phase's scope; clean it opportunistically if touching the import block).

## Info

### IN-01: `run_producer` accepts an unused `kickoff_definition_id` parameter

**File:** `backend/app/services/run_producer.py:304`
**Issue:** `run_producer(...)` declares `kickoff_definition_id` and
`send_message` passes it (`threads.py:957`), but the parameter is never read in
the function body — only `kickoff_definition` is consumed (harness branch,
`:411`). This is a faithful mirror of the old closure (the inline `agent_runner`
had `_kickoff_definition_id` in scope via closure but never used it), so it is
not a behavior change — just a dead parameter on a seam Phase 163 will extend
(`run_producer(run_id, *, ...)`), where a dangling unused kwarg sets a poor
precedent for the imminent `org_id` threading.
**Fix:** Drop `kickoff_definition_id` from the `run_producer` signature and the
`send_message` call site, or add a brief `# reserved for parity` note if it is
intentionally retained for the 163 wiring.

### IN-02: Continuation path gained a best-effort "runs.usage missing" log line

**File:** `backend/app/services/run_producer.py:174-178` (via `:589-590`, `:648-649`)
**Issue:** The old inner `_finalize` for `spawn_continuation_run` had no
missing-usage warning; the shared `_finalize_producer_run` emits one when both
token totals are `None`. On a continuation that fails before
`load_user_settings`, `resolved_provider` / `resolved_model` are `None`, so the
line logs `provider=None model=None`. This is the only observable delta from the
old continuation behavior, it is log-only (no functional change), and it is
explicitly documented at `run_producer.py:585-588`. Recording it here only
because the phase's bar is byte-identical behavior; it is benign (arguably an
observability improvement) and needs no action.
**Fix:** None required. If strict byte-identical log output is desired, guard the
warning with `if resolved_model is not None` on the continuation path.
