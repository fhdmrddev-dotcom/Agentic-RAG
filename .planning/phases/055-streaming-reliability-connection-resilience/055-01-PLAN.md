  <name>Task 1: Verify messages table in supabase_realtime publication</name>
  <what-built>Nothing yet — this is a prerequisite database check that Claude cannot perform without live Supabase credentials.</what-built>
  <how-to-verify>
    Run the following SQL against your Supabase project (use the SQL Editor in the Supabase Dashboard, or psql):

    ```sql
    SELECT tablename
    FROM pg_publication_tables
    WHERE pubname = 'supabase_realtime'
    ORDER BY tablename;
    ```

    **Expected output (messages present):**
    The result set includes a row with `tablename = 'messages'`.

    **If messages is NOT in the output:**
    Run this to add it:

    ```sql
    ALTER PUBLICATION supabase_realtime ADD TABLE messages;
    ```

    Then re-run the SELECT to confirm `messages` now appears.

    **Why this matters:** The Realtime subscription added in Plan 03 uses `supabase.channel().on('postgres_changes', { table: 'messages', ... })`. If `messages` is not in the `supabase_realtime` publication, the subscription silently connects but the callback never fires. Plan 03 removes the existing 1.5s sseDrop fallback, so a missed publication means no recovery path exists at all.

    This is the same prerequisite documented in `frontend/src/hooks/useFolders.ts` for the `folders` table.
  </how-to-verify>
  <resume-signal>
    Type one of:
    - "confirmed — messages was already in the publication"
    - "added — messages was not present, ALTER PUBLICATION executed"
    Include the tablename column output if possible.
  </resume-signal>
