## Summary

Every claim SEED-200 makes is confirmed at source at this phase's own base. `ConnectionPicker.tsx:271`
is capability-scoped, `ExternalActionSection` offers exactly three options derived from a
cross-language fence, `McpToolPicker` has no reachable mount, and `updateConnectorGrants` has zero
production callers. The backend has been ready throughout: `_exec_external_action` branches on
`tool_name` before the closed-set check, and `ExternalActionPhaseConfig.capability` is `| None` with
its own comment naming the MCP absence as legitimate.

**Three things this research found that no upstream document names, and each is a planning input
rather than a detail.** (1) **A workflow containing an MCP step CANNOT BE PUBLISHED.** Publish stage
2.6 runs `grounding._unregistered_tools`, whose admissible set is `get_tools()` ∪ the three
capabilities; an MCP step's `available_tools` is `[tool_name]` (the model validator derives it), so
`ask_question` is an `unregistered_tool` at severity **error** — driven, not reasoned (§OQ#3). The
run half of SC#3 is still reachable through **▶ Test Run**, which runs a draft and never publishes.
(2) **Both `/discover` and `PATCH /grants` require `org:manage`** while the picker's read does not —
so a plain member can bind an MCP connection and can neither discover nor grant (§OQ#4). (3)
**`ConnectionPicker.destinationPartsOf` has an un-repaired positional tail**: bind an MCP row today
and the footer reads `🔒 slack.com/api`. That is the exact defect 206.1 repaired one file over in
`connectionsCopy.destinationFactsOf` (its SC#4), left standing here because nothing could reach it.

**On D-206.2-07: the sweep as specified would have passed against the defect it exists to prevent.**
`ConnectionPicker.tsx` already imports `McpToolPicker`, today, at the defect's base. An importer
sweep proves an edge in the import graph and nothing about the props that travel it. The honest
guard is three-tier and is set out in §OQ#5 and §Validation Architecture.

**Primary recommendation:** ship the shape choice as a control BESIDE the radiogroup (never a fourth
`external-action-option`, which five shipped assertions pin at exactly 3), route the shape write
through a NEW multi-key patch prop so the clear of the other shape's keys happens in ONE place, add
the grant control inside `McpToolPicker` (the only place in this blast radius allowed to hold state),
and prove reachability with a DATA-PATH integration test plus a driven browser round trip — with the
`import.meta.glob` sweep as the cheap third leg, not the load-bearing one.

### `available_tools` is the server's, and `tool_name` OUTRANKS `capability`

```python
# harness.py — _available_tools_is_the_capability, @model_validator(mode="after")
if self.tool_name:      derived = [self.tool_name]
elif self.capability:   derived = [self.capability]

```

Driven at HEAD:

```
MCP step available_tools -> ['ask_question']
capability -> None
```
`[VERIFIED: driven in backend/venv, ExternalActionPhaseConfig instantiated directly]`

**Consequence for a STRANDED `capability` on an MCP step:** the step still executes as MCP (the
executor's `if mcp_tool_name:` arm wins) and `available_tools` is still `[tool_name]`. It is not
fatal — it is a **lie in three places**: `derivedFace` paints the node "Sends an email";
`OutsideChangeLine` prints the email consequence sentence; and
`_pre_credential_destination(config, capability)` resolves the SMTP/Jira constant and runs
`validate_destination` against a host the step will never contact. `[VERIFIED: phase_types.py:2043-2070, 2365-2367]`

**Consequence for a STRANDED `tool_name` on a capability step:** worse. `available_tools` becomes
`[tool_name]` instead of `[capability]`, and the executor's first branch takes the MCP path. The step
silently stops being an email step. **This direction is the one the clear MUST cover.**

### Where the clear must happen, and what happens instead today

`PhaseFormPanel.tsx:1011`:

```tsx
const set = (key: string) => (v: string | number) => onChange({ [key]: v })
```

`set()` is **single-key by construction**. `ExternalActionSection`'s prop is
`onChange: (value: string) => void` and it is wired as `onChange={set("capability")}`. So **there is
no seam today through which a shape switch could clear another key** — the write physically cannot
carry two.

The merge below it does not delete either:

```ts
// definitionOps.patchPhaseConfig
const next: PhaseSpecJSON = { ...p, config: { ...p.config, ...patch } }
```

A spread. It deletes ONLY `name` / `name_seeded_by_ai`, and only when the patch's keys intersect
`IDENTITY_BEARING_CONFIG_KEYS = {skill_ref, folder_scope, available_tools}` — **`capability`,
`tool_name` and `tool_args` are NOT in that set**, so a shape switch does not even invalidate an
AI-seeded step name. `[VERIFIED: definitionOps.ts:253-320]`

**What currently happens:** choose `create_ticket` on a step that had `tool_name: "ask_question"` and
the config becomes `{capability: "create_ticket", tool_name: "ask_question", …}` — which the server
accepts, whose `available_tools` derives to `["ask_question"]`, and which runs as MCP.

### The three places the clear could live — and the one that is right

| Option | Cost | Verdict |
|---|---|---|
| Inside `ConnectionPicker.bind()` | ⚠ **Trips `ConnectionPicker.test.tsx`'s T6 sweep**: `expect(Object.keys(patch)).toEqual(["connection_id"])` runs over EVERY call the driven `<select>` makes. A multi-key patch there is RED, and the sweep has a positive control so it cannot be loosened accidentally | **NO** |
| Inside `builderStore.patchConfig` / `definitionOps.patchPhaseConfig` (a shape-aware normaliser) | Puts a product rule in a pure merge that six other surfaces share; the merge's own docblock says it "deliberately does NOT renumber and does NOT reorder" — it is a mechanism, not a policy | **NO** |
| At the SHAPE-CHOICE write site, through a NEW multi-key prop on `ExternalActionSection`, forwarded from `PhaseFormPanel` as `onChange` **whole** (not through `set()`) | `PhaseFormPanelProps.onChange` is ALREADY `(patch: PhaseConfigPatch) => void` where `PhaseConfigPatch = Record<string, unknown>`. **No panel prop changes.** One new leaf prop, one new JSX argument | **YES** |

Concretely: `<ExternalActionSection capability={…} onChange={set("capability")} onPersist={onPersist}
onChangeShape={onChange} />` — where `onChangeShape` is the panel's own patch-shaped `onChange`,
so the leaf can emit `{capability: "send_email", tool_name: undefined, tool_args: undefined}` or
`{capability: undefined, tool_name: "", …}` in ONE patch. **Do not widen the existing `onChange`
prop's signature** — eight assertions in `ExternalActionSection.test.tsx` call
`expect(onChange).toHaveBeenCalledWith("create_ticket")` and would all move.

### ⚠ `undefined` vs deletion — measure this before relying on it

`{...cfg, capability: undefined}` leaves the KEY PRESENT with value `undefined`. `JSON.stringify`
drops it on the wire, so the SAVED definition is clean — but the in-memory `PhaseSpecJSON` still has
the key, and every client-side reader that does `"capability" in cfg` (rather than a truthiness or
`own()` check) will see it. `asStr(cfg.capability)` in `PhaseFormPanel` returns `""` for `undefined`,
which is the desired behaviour. **The plan should assert the SERIALIZED definition, not the store
object** — and should state explicitly whether it writes `undefined` or `""`/`null`.
`[ASSUMED — the JSON.stringify behaviour is standard, but the specific save path was not driven here]`

### The lost-update hazard — it is REAL, and here is what the UI must send

Because the endpoint REPLACES, a per-tool toggle that sends `{ [tool]: true }` alone **wipes every
other grant on the connection**. The UI must send the **full merged map**:

```ts
await updateConnectorGrants(connection.id, { ...(connection.tool_grants ?? {}), [tool]: next })
```

That is still a read-modify-write over a client snapshot: two authors in two browsers, or one author
with a stale `bound` row, will clobber each other. Three mitigations, in ascending honesty:

1. **Merge from the freshest snapshot available** — the response of the previous grant write, not the
   row captured when the picker last listed. (The response IS the row; use it.)
2. **Re-read before write** is not available without a second round trip and `getConnectorConnection`
   is already exported — but adding a read here doubles latency on a toggle.
3. **Say what it is.** The honest UI statement is that grants are per-connection and org-wide, so a
   toggle here changes what EVERY workflow bound to this connection may do. That is a governance
   fact, not a nicety, and D-206.2-05's answer-in-writing belongs beside it.

**Recommendation:** (1) + (3). Do not attempt optimistic locking — the column carries no version and
adding one is a migration.

### The authorization asymmetry — the biggest UX input in this phase

| Operation | Route | Gate | Who |
|---|---|---|---|
| `GET /connectors/connections` (the picker's read) | `:277` | none beyond auth | **any org member** (U-02) |
| `POST …/{id}/discover` | `:574` | `require_org_manage` | **org admin only** |
| `PATCH …/{id}/grants` | `:604` | `require_org_manage` | **org admin only** |

So a plain member can **bind** an MCP connection to a step and can neither **discover** nor **grant**.
Two saving graces, both measured:

- `discovered_tools` is CACHED on the row and is in `_SELECTABLE_COLUMNS`, so a member sees the tool
  list without calling `/discover`. The DeepWiki row already carries 3.
- `tool_grants` is likewise readable, so the granted/denied badge is honest for a member.

**The plan must decide** whether the grant control is hidden for a non-admin, disabled with a reason,
or shown and allowed to 403. The project's own precedent (`ConnectionPicker`'s Gate 1 docblock,
UI-SPEC §5a) is: *announce as unavailable, keep the reason as real DOM text, and let the server be the
authority.* `aria-disabled` over hard `disabled`, so the reason can render.

### `isToolGranted` — `McpToolPicker.tsx:47-57`

```ts
export function isToolGranted(
  grants: Record<string, boolean> | undefined | null,
  toolName: string | null | undefined,
): boolean {
  if (!grants || !toolName) return false
  return (
    Object.prototype.hasOwnProperty.call(grants, toolName) &&
    Boolean(grants[toolName])
  )
}
```

It is the correct own-property form (F-2), and it mirrors the server's
`grants.get(tool_name) is True` at `phase_types.py:2440`. ⚠ They are NOT identical: the client
accepts any truthy value, the server requires `is True`. `1`, `"yes"` and `[]`-truthy values would
read GRANTED in the UI and DENIED at run time. The service sanitizes on write (`bool(v)`), so this is
unreachable through the API — but a hand-edited row or a service-role writer could produce it.
Worth one line of prose; not worth a change.

### Pattern 1 — the leaf-and-one-gated-line shape (the standing G-5 order on `PhaseFormPanel.tsx`)

**Applied here:** the shape control is either a prop on `ExternalActionSection` (cheapest) or a new

### Pattern 2 — every user-visible string is an exported identifier

`ConnectionPicker.tsx:71-146` and `McpToolPicker.tsx:25-35` both do this; the suites assert
character-identity against the names. Any new sentence (the MCP shape's label, the MCP empty state,
the grant control's label, the non-admin refusal) must be a named export, not an inline literal.
⚠ `ExternalActionSection.tsx` may not declare one at all — its suite asserts the file contains none of

### Pattern 3 — `own()`, never a coalesced bracket read

`ownProperty.ts` is a zero-import leaf. Every keyed presentation table in this tree reads through it.
`CONNECTION_CAPABILITY_WORDS[capability] ?? "external"` is the outstanding exception (above).

### Pattern 4 — announce as unavailable, keep the reason as DOM text

`ConnectionPicker`'s Gate 1 uses `aria-disabled` rather than `disabled` **deliberately**, so the
refusal sentence has somewhere to render and is wired by `aria-describedby`. The non-admin grant

## Common Pitfalls

### Pitfall 1 — the fourth option that reddens five assertions at once
**What goes wrong:** the MCP choice is rendered as a fourth row in the existing radiogroup.
**Why:** it is the obvious visual answer and SEED-200's own "what a fix looks like" section says
*"A fourth option on `ExternalActionSection`"*.
**Avoid:** a different `data-testid`, outside the `radiogroup`, or as a segmented control above it.
**Warning sign:** `getAllByTestId("external-action-option")` returning 4.

### Pitfall 2 — the stranded key that typechecks and runs wrong
**What goes wrong:** a step switched from MCP to email keeps `tool_name`, and the executor's first
branch takes the MCP path. The step silently stops being an email step.
**Why:** `patchPhaseConfig` is a spread; `set(key)` is single-key; nothing normalises.
**Avoid:** the multi-key shape-choice seam of §OQ#2.
**Warning sign:** a saved definition whose `config` carries both `capability` and `tool_name`.

### Pitfall 3 — the grant toggle that wipes the other grants
**What goes wrong:** `updateConnectorGrants(id, { [tool]: true })` replaces the whole column.
**Avoid:** always send `{ ...(connection.tool_grants ?? {}), [tool]: next }`, merged from the
FRESHEST snapshot (the previous write's response body).
**Warning sign:** a second tool's badge flipping from granted to denied after an unrelated toggle.

### Pitfall 4 — the 403 nobody planned for
**What goes wrong:** a plain member sees a Discover button and a grant switch, and both 403.
**Why:** `/discover` and `/grants` carry `require_org_manage`; the picker's read does not.
**Avoid:** decide the non-admin story at plan time; the cached `discovered_tools` and `tool_grants`
are readable, so the READ half degrades gracefully on its own.
**Warning sign:** `McpToolPicker`'s `discoveryError` alert firing with a permission message.

### Pitfall 5 — an incomplete `vi.mock("@/lib/api")` factory
**What goes wrong:** a new import in `McpToolPicker.tsx` makes a one-key factory inert; 196-08
measured 249 red tests from exactly this.
**Avoid:** spend the budget in the SAME commit —
`McpToolPicker.test.tsx` (adds `updateConnectorGrants`) and the four
`WorkflowBuilderPage.*.test.tsx` suites that mock only `listConnectorConnections`.
**Warning sign:** `[vitest] No "updateConnectorGrants" export is defined on the "@/lib/api" mock`.

### Pitfall 6 — reading `tool_refused` by event_type alone
**What goes wrong:** the audit query matches the agent tool-whitelist refusals too. **Measured: the
local `harness_audit` already holds four `tool_refused` rows with metadata `{"tool": "workspace_write",
"allowed": ["search_documents"]}` — a completely different concern that reuses the name.**
**Avoid:** filter on `metadata->>'connection_id'` or `metadata->>'reason' = 'permission_denied'`.

### Pitfall 7 — claiming the round trip works because Test Run is green
**What goes wrong:** the phase closes with a green draft run and a publish path that refuses.
**Avoid:** §OQ#3's escalation, stated in the summary and in the ROADMAP row.

### Pitfall 8 — the footer that says `slack.com/api`
**What goes wrong:** an MCP row bound in the picker renders Slack's constant host.
**Avoid:** give `destinationPartsOf` an explicit `mcp_server_url` arm ABOVE the tail, exactly as
`connectionsCopy.destinationFactsOf` was repaired in 206.1.
**Warning sign:** it is not a warning sign — it is the DEFAULT today, and the browser drive will see it.

### Known threat patterns

| Pattern | STRIDE | Mitigation, and where |
|---|---|---|
| A destination fact or credential copied into `workflow_definitions.definition` (org-readable JSONB) | Information disclosure | **T6** in `ConnectionPicker.test.tsx` — only `connection_id` crosses. ⚠ This phase adds `tool_name`/`tool_args` writes to that surface: **`tool_args` is author-typed and could carry a token.** The plan should state that `tool_args` is author-owned content and is NOT covered by T6's promise — and should not extend T6 to bless it silently |
| A workflow granted a tool nobody approved | Elevation of privilege | `grants.get(tool_name) is True` at GATE 6 — a missing key DENIES. The UI never re-derives it |
| Lost-update wiping a deliberate denial | Tampering | ⚠ **LIVE** — REPLACE semantics. Send the full merged map from the freshest snapshot (§OQ#4) |
| A non-admin escalating via the UI | Elevation of privilege | route dep + RLS; the UI's job is to be honest, not to be the gate |
| Untrusted remote tool metadata rendered as UI | Tampering / XSS | `discovered_tools` is remote text. It is rendered as React children (escaped) in `<option>` and a `<p>`. ⚠ **Never introduce `dangerouslySetInnerHTML` for a tool description** — T-206-03 |

1. **Does this phase accept that MCP workflows cannot be published?**
   - **What we know:** measured — stage 2.6 blocks with `unregistered_tool` at severity `error`; the

     include the backend line; or (c) sequence the backend fix first.

     leaves a measured, one-line follow-on. ⚠ Whichever is chosen, the ROADMAP's SC#2 wording
     *"publish if required"* must be amended, not quietly reinterpreted.

2. **What does a non-admin see?**
   - **What we know:** `/discover` and `/grants` are `org:manage`; the read is org-wide; the cached
     `discovered_tools` and `tool_grants` are readable by any member.
   - **What's unclear:** hide / disable-with-reason / allow-and-403.
   - **Recommendation:** disable-with-reason, `aria-disabled`, reason as real DOM text — the shipped
     Gate 1 shape, whose docblock argues exactly this case. Falls under Claude's Discretion but the
     plan should state it as a decision.

3. **Does the canvas banner lie about a read-only MCP tool?**
   - **What we know:** `nodeEffectBanner` renders `CHANGES SOMETHING OUTSIDE` keyed on the phase TYPE,
     deliberately, and declines an `ONLY READS` banner with a two-armed re-open trigger. Neither arm
     fires: no capability is added, and the wire carries no read/write hint (measured — the DeepWiki
     payload has no `annotations`).
   - **Recommendation:** leave it, and record the near-miss in `nodeEffectBanner.ts`'s own trigger
     paragraph. Do not invent a heuristic on the tool NAME — that is the fabricated claim it refuses.

4. **Is `stepGaps`' permanent "Choose what this step changes outside the workflow" row in scope?**
   - It is a one-arm fix in `stepReadinessContext.ts` and it is a visible lie on every MCP step.
   - **Recommendation:** yes — it is part of "the step can name the MCP shape", not a separate feature.

5. **Does `destinationPartsOf`'s repair count as touching a shipped capability shape (D-206.2-08)?**
   - Adding an `mcp_server_url` arm ABOVE the tail leaves all three capability arms byte-identical and
     changes no capability row's footer. **Recommendation:** yes, in scope, and assert the three
     capability footers byte-identical to prove it.
