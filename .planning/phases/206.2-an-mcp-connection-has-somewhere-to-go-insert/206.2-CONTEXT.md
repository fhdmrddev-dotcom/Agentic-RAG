## Phase Boundary

Phase 206 shipped the MCP engine — client, SSRF defence, discovery, per-tool grants, executor
dispatch, audit. Phase 206.1 shipped the door that CREATES a connection. **This phase is the door
that USES one.**

### In Scope

1. **The step can name the MCP shape.** `ExternalActionSection` today offers exactly the three
   members of `EXTERNAL_ACTION_CAPABILITIES`; there is no way to say *"this step calls an MCP tool"*.
2. **The picker can see MCP rows.** `ConnectionPicker.tsx:271` always calls
   `listConnectorConnections(capability)`; an MCP row has `capability = null` and is filtered out of
   every read the picker performs.
3. **A grant can be flipped from the UI.** `updateConnectorGrants` exists in `api.ts` and has
   **zero production callers** — `McpToolPicker` renders a granted/denied badge and no control
   changes it.
4. **A reachability guard**, so this class of defect cannot ship green again.

### Explicitly Out of Scope

- **Any change to `frontend/src/lib/api.ts`.** Phase 207 owns that split. ⚠ **Measured: this phase
  needs no change there.** `listConnectorConnections(capability?: string)` already builds an empty
  query string when the argument is falsy (`api.ts:6469-6483`), so the unfiltered read is a
  CALL-SITE change; and `updateConnectorGrants` was already exported by Phase 206.
- ⚠ **CORRECTED — see D-206.2-19: ONE backend change IS in scope**, the publish-validator fix. The
  sentence below was written before research drove a publish attempt and is preserved because its
  reasoning was sound on what was known then: the backend's *executor* really is ready. What is not
  ready is its *publish validator*, and that is a defect Phase 206 introduced in the same commit
  that made `tool_name` outrank `capability`.
  ~~Any backend change.~~ ⚠ **Measured: the backend EXECUTOR has been ready throughout.**
  `_exec_external_action` branches on `tool_name` FIRST and an MCP step carries no capability
  (`phase_types.py:2273-2298`); `ExternalActionPhaseConfig.capability` is `Literal[...] | None`.
- Migration changes. `capability`'s CHECK constraint at migration 116 is a closed three-member set

- Settings → Connections (Phase 206.1's surface). It is done; this phase reads its output.
- The connector catalog / OAuth / org sharing — SEED-146, a milestone of its own.

<decisions>
## Implementation Decisions

### The shape, and the two ways to get it wrong

- **D-206.2-01 (The MCP option is a SHAPE choice, NOT a fourth capability — and this is the seed's
  forbidden fix, one level up)**: `EXTERNAL_ACTION_CAPABILITIES` is derived as
  `Object.keys(EXTERNAL_CAPABILITY_SENTENCES)`, and that constant is a **cross-language fence**:
  its own docblock says the suite compares the client's closed set against the server's `Literal`,
  so *"a fourth entry cannot appear on one side alone"*. The server's `Literal` has three members
  and migration 116's `CHECK` has three. **Adding a fourth key would break the fence, and would be
  exactly the fake capability SEED-200 forbids.** The MCP option is therefore a choice ABOUT WHICH
  SHAPE THE STEP IS, presented beside the capability list, never inside it.
- **D-206.2-02 (An MCP step writes `tool_name` and MUST NOT write `capability`)**: measured at the
  executor — `_exec_external_action` reads `tool_name` first and only falls to the closed-set check
  when it is absent. ⚠ **The source records that this guard was satisfied BY ACCIDENT for a whole
  phase**: `ExternalActionPhaseConfig.capability` once defaulted to `"send_email"`, so every MCP step
  arrived claiming to be an email step and passed a closed-set check it was never meant to take.
  *"A default is not a way through a gate."* The builder must write `{connection_id, tool_name,
  tool_args}` for an MCP step and leave `capability` genuinely absent — and switching a step's shape
  must CLEAR the other shape's keys, not leave them stranded.
- **D-206.2-03 (The MCP read is `listConnectorConnections()` with NO argument — a call-site change,
  not an API change)**: `api.ts` is untouched. ⚠ **The `is_enabled` filter applies to the MCP read
  too** — `ConnectionPicker` drops disabled rows because *"a DISABLED connection is not a choice"*
  (UI-SPEC §6d), and an MCP row must obey the same rule rather than inheriting a laxer one.
  ⚠ An unfiltered read returns capability rows as well; the MCP shape must show **only** rows with
  `mcp_server_url`, filtered client-side, or the two shapes' pickers start listing each other's rows.

### The grant

- **D-206.2-04 (The grant control ships in THIS phase — it is not a follow-on)**: Phase 206's
  enforcement is `tool_grants.get(tool_name) is True`, so **a missing key DENIES**. A step that can
  be bound but whose tools can never be granted is a second built-but-unreachable feature, which is
  the exact defect this phase exists to close. Binding without granting is not a smaller version of
  this phase; it is this phase's own failure mode.
- **D-206.2-05 (SEED-146's standing rule is ANSWERED IN WRITING, not assumed either way)**: the rule
  is *never add an outbound capability before the approval model exists*. The reading this phase
  takes, and which the plan must state at the control's own site: **the per-tool grant IS the
  approval model for this surface** — Phase 206 shipped enforcement plus a `tool_refused` audit
  event, and what is missing is the human-facing switch that the enforcement already reads. This
  phase adds **no new outbound capability**: the egress, the SSRF guard and the dispatch all shipped
  in 206. ⚠ If a planner or executor finds that reading does not hold, that is a STOP — escalate
  rather than shipping the control.
- **D-206.2-06 (A denied tool stays denied, and the refusal keeps its receipt)**: flipping a grant on
  must not disturb the deny path. The `tool_refused` audit event still fires for an ungranted tool,
  and the negative case is driven, not assumed.

### The guard — the whole point of the phase

- **D-206.2-07 (A REACHABILITY assertion, never another component test)**: ⚠ **Every gate was green
  while this defect shipped.** `McpToolPicker.test.tsx` is green and in the count gate because it
  mounts the component directly with a connection prop **that no production code path could
  produce**. *A component test that constructs its own props cannot see that nothing constructs them
  in production.* The guard is an `import.meta.glob` sweep proving `McpToolPicker` has at least one
  production importer whose props can carry an MCP row — the `RunReceipt.tsx` zero-importer sweep
  pointed the other way, **with a positive control** (a sweep that would pass against an empty
  codebase proves nothing).

### Scope fences

- **D-206.2-08 (The three shipped capability shapes are untouched)**: `EXTERNAL_ACTION_CAPABILITIES`
  keeps exactly its three members, and a capability step's picker behaviour is asserted
  **byte-identical** — the `CARD_HTML_BASELINE` / 206.1-02 precedent. This phase adds a shape beside
  them; it does not renegotiate them.
- **D-206.2-09 (Baselines re-derived, never quoted)**: at Phase 206.1's close the readings were
  backend `68 failed / 2605 passed`; `tsc -p tsconfig.app.json` = **34** with zero in any
  `Connection*` / `connectionMark*` file; count gate `OK — 111/111 · total 5605 · failed 0 · pinned
  total 5043`. Re-derive all three at this phase's own base. The gate's contract is **no per-file
  DECREASE and zero failing**, never a fixed total — a larger total is the gate working.
  `tsc` is project-scoped (`-p tsconfig.app.json`) or it measures nothing.
  `GSD_VITEST_MAX_WORKERS=2`; a red gate is triaged from its persisted JSON BEFORE any re-run
  (SEED-171), and a red gate is sometimes REAL (196-08: 249 failures, all genuine).
- **D-206.2-10 (This phase closes Phase 206.1's owed SC#1b, and must say so where it lands)**: the
  ROADMAP records SC#1b as owed. When the round trip is driven here, 206.1's checklist row is
  updated in the same commit — an owed criterion nobody goes back to mark is a deferral with no

- **D-206.2-11 (⚠ CLAUDE.md is past its WARN band and this phase inherits that obligation)**:

### Corrected by pattern mapping, 2026-08-25 — one of these refutes a decision above

- **D-206.2-12 (⚠ THE GUARD D-206.2-07 NAMES IS VACUOUS AT ITS OWN BASE — MEASURED, AND THIS IS THE
  MOST IMPORTANT CORRECTION IN THIS FILE)**: `McpToolPicker` **already has exactly one production
  importer** (`ConnectionPicker.tsx:61` / `:426`), so the `RunReceipt.test.tsx:249-287` sweep
  inverted from `0` to `≥1` **passes GREEN ON THE BROKEN TREE**. A guard that is satisfied by the
  defect it was written to catch is worse than no guard, because it reads as coverage. The
  unreachability is one level UP: `bound` is drawn from a capability-scoped read, so
  `bound?.mcp_server_url` is unsatisfiable regardless of the import graph. **SEED-200's own second
  clause is the escape** — *"whose props can carry an MCP row"* — and it is the load-bearing half.
  **The guard is therefore TWO-LEGGED:** (a) the inverted sweep, for the import edge, with a
  positive control; **and (b) a render through the REAL chain with only `@/lib/api` mocked,
  constructing no component prop by hand.** Leg (b) is the one that would have failed before this
  phase. A plan that ships only leg (a) has re-created the defect in the guard.
- **D-206.2-13 (⚠ TWO AUDIENCES ON ONE PANEL — `discover` and `grant` are ORG-ADMIN ONLY, and no
  workflow-builder surface reads org role today)**: measured — `PATCH /connectors/connections/{id}/grants`
  and `POST /.../discover` are `require_org_manage` (`api/connectors.py:577`, `:607` → 403 at
  `dependencies.py:906-910`), while `GET /connectors/connections` is deliberately ungated org-wide.
  So **any member may BIND a connection; only an org admin may DISCOVER or GRANT.** This surface
  would be the first in the builder to read org role. The shipped rule on the Settings side is
  **REMOVED, not disabled** — a rendered control the API refuses is the defect that rule exists to
  prevent — and the plan must decide, in writing, whether that rule transfers here or whether a
  non-admin sees an explanatory absence instead. ⚠ **Do NOT let a non-admin see a Discover button
  that 403s.**
- **D-206.2-14 (⚠ `McpToolPicker.test.tsx` IS NOT PINNED — SEED-200's "green and in the count gate"
  is half true, and the wrong half is load-bearing)**: measured — `grep -n "Mcp"
  scripts/vitest-count-gate.cjs` returns **nothing**. `src/components/workflows` is a `TARGETS`
  directory entry so the suite RUNS, but it carries no per-file pin: **it could have been deleted
  with the gate green.** This phase adopts it into both knobs, in the same commit as the code that
  makes it meaningful.
- **D-206.2-15 (The shape choice cannot go through `ExternalActionSection.onChange`)**: measured —
  `PhaseFormPanel.tsx:1011` is `set(key) => (v) => onChange({[key]: v})`, a ONE-KEY writer, and a
  shape switch is a MULTI-KEY patch (set one, clear the other). The shipped answer is the argument
  `ConnectionPicker.tsx:5-16` already makes for itself: a sibling child with store access.
- **D-206.2-16 (`updateConnectorGrants` is a whole-column REPLACE — a naive per-tool toggle is a
  lost-update bug)**: measured at `connector_service.py:791`. A `{[tool]: next}` payload **wipes
  every other grant.** The UI sends the FULL map, derived from the server-owned value, never from
  local state: the `FeatureVisibility.tsx:253-258` shape (`nextRoles` derived from the server prop,
  `if (busy) return`, **no optimistic flip**) plus `ConnectionsTab.tsx:1046-1116`'s re-fetch nonce.
- **D-206.2-17 (Nothing in `frontend/src` clears a key inside `config` — the planner authors it, and
  ONE DIRECTION IS DANGEROUS)**: measured — `patchPhaseConfig` (`definitionOps.ts:295-320`) is a pure
  spread merge and `grep -rn "delete .*\.config\[..."` returns nothing. The partial analog is the
  D-187-07 demote, which `delete`s **PhaseSpec** siblings — the *`delete`-not-`undefined`* reasoning
  transfers, the target object does not. ⚠ **The asymmetry is the finding:** the backend branches on
  `tool_name` FIRST (`phase_types.py:2288`), so a stranded `capability` is INERT, but **a stranded
  `tool_name` silently turns an email step into an MCP step.** Clearing MCP→capability is the
  direction that must not be skipped.
- **D-206.2-18 (The byte-identity pin needs a COUNTED `useId` normalization)**: `ConnectionPicker`
  calls `useId()` **twice** and both reach the DOM, so an unrelated case added above moves the ids.
  Use `ConnectionsTab.test.tsx:872-1030`'s counted form — expected replacement count **2**, or **4**

### Corrected by research, 2026-08-25 — a BLOCKER, and it changes this phase's scope

- **D-206.2-19 (⚠ A WORKFLOW CONTAINING AN MCP STEP CANNOT BE PUBLISHED TODAY — DRIVEN, AND THE
  BACKEND FIX IS IN SCOPE. THIS REVERSES THE "no backend change" FENCE ABOVE, DELIBERATELY.)**
  Measured and then re-read at source by the orchestrator:
  `ExternalActionPhaseConfig._available_tools_is_the_capability` (`models/harness.py:320-350`)
  derives `available_tools = [tool_name]` for an MCP step — Phase 206's own change, and correct.
  `_unregistered_tools` (`grounding.py:816-866`) then admits, for an `external_action` phase, only
  `EXTERNAL_ACTION_CAPABILITIES`. An MCP tool name is in neither set, so rule 2 flags it, severity
  resolves to **`error`**, and publish stage 2.6 blocks at `grounding_fidelity`.
  ⚠ **`_unregistered_tools`'s own docstring asserts *"IT COSTS `external_action` NOTHING"* and
  *"D-06 (a workflow containing the external-action node PUBLISHES) stays true by construction"* —
  both stopped being true the day Phase 206 made `tool_name` outrank `capability`, in the same
  validator.** That stale claim is corrected BESIDE its original, never over it.
  **The fix is narrow and is NOT a loosening:** when an `external_action` phase carries a
  `tool_name`, the admissible set gains **that one name** — which `available_tools` is already
  DERIVED from, so the two are equal by construction and nothing new becomes representable. The MCP
  tool is closed by a **different and stronger** mechanism than `_TOOL_REGISTRY`: the per-tool grant,
  enforced at run time as `tool_grants.get(tool_name) is True` (**a missing key DENIES**) with a
  `tool_refused` audit event. **Publishing grants nothing.** The type test already scopes this to
  `external_action`, so CR-01's measured wire-around — an `llm_agent` step naming a capability —
  stays blocked, and that must be asserted with a negative control rather than assumed.
  **Why the scope widened rather than escalating:** shipping the authoring door while publish
  refuses its result would be the **FOURTH consecutive built-but-unreachable door** in this
  feature's history — 206 shipped the engine with no create door, 206.1 the create door with no bind
  door, and 206.2 would ship the bind door with no publish. That is the exact pattern this phase
  exists to break, and G-7's "a closure round may not smuggle in a capability" does not apply: this
  is a **defect on shipped code**, not a capability.
  ⚠ **Zero backend test coverage exists for `PATCH /grants` or its service** — measured. This phase
  adds it rather than inheriting the gap.
  ⚠ SC#3 is reachable WITHOUT this fix via **▶ Test Run** (a draft path with no verdict gate), so a
  plan could have scored SC#3 green while leaving publish broken. Recorded so nobody takes that road.
- **D-206.2-20 (⚠ `ConnectionPicker.destinationPartsOf` HAS AN UN-REPAIRED POSITIONAL TAIL — the
  SAME defect 206.1 fixed one file over, and it is in scope)**: bind an MCP row and the picker's
  footer reads `🔒 slack.com/api`. That is byte-for-byte the defect `destinationFactsOf` shipped and
  206.1 repaired as its own SC#4 — the wrong host named on a surface whose whole job is *where does
  this send?*. Fix it here with an explicit arm plus a **synthetic-fifth-shape negative control**,
  the shape 206.1 used. Leaving it would mean this phase's own binding flow displays a lie.
- **D-206.2-21 (The MCP control sits OUTSIDE the capability radiogroup — five shipped assertions pin
  it at exactly 3)**: measured — five assertions pin `external-action-option` / `[role="radio"]` at
  **exactly 3**. The MCP control needs its **own testid** and must not join that radiogroup, or five
  shipped fences go red for a reason that is not a defect. This is D-206.2-01's constraint expressed
  in the DOM.
- **D-206.2-22 (Where the state may live, measured)**: `ExternalActionSection`'s source fence forbids
  `useEffect|useStore|useContext|zustand` but **allows `useState`**; `PhaseFormPanel.tsx` holds an
  ABSOLUTE-ZERO hook pin. ⇒ **grant state belongs in `McpToolPicker.tsx`.** The shape-switch write
  reaches the store through a **new multi-key prop forwarding `PhaseFormPanel`'s already
  patch-shaped `onChange`** — no panel prop changes, and **not** through `ConnectionPicker.bind()`,
  whose T6 fence pins `Object.keys(patch) === ["connection_id"]` over every driven call.
- **D-206.2-23 (Driving it: Playwright, and the 206.1 localStorage trick does NOT transfer)**:
  measured — Chrome DevTools MCP is **not** available here; Playwright + Chromium (`chromium-1223`)
  are. `activeView` is unpersisted `useState` with **no router**, so the rail must be CLICKED
  (`[aria-label="Workflows"]`). Live fixture confirmed: the MCP row `7ca5e114…` with
  `tool_grants = {}` and 3 cached tools; `live_connectors` and `visual_workflow_canvas` both
  `"everyone"`. ⚠ `tool_refused` is a **shared** `event_type` — filter on `connection_id`/`reason`,
  never on the name alone.
- **D-206.2-24 (G-2 override, recorded rather than skipped)**: G-2 says propose `/gsd:sketch` before
  planning a live-UI phase. The operator is unattended and asked for completion, so the override is
  taken and the design contract is produced by `/gsd:ui-phase --auto` instead — the workflow's own
