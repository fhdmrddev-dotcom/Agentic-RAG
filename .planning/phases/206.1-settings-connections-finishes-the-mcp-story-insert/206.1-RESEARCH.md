#### Phase shape

- **D-206.1-01 (Three separable plans, not one)**: The ROADMAP requires the three items stay
  separable — *"one is a new capability and two are defects on shipped code — a closure round may
  not smuggle in a feature (G-7), and the reverse holds too, so the form must not be the reason
  the two defects go unreviewed."* Each item is therefore its own PLAN.md with its own
  `must_haves`, so one can be reverted without the others. They share a phase because G-1 caps
  repeated inserts on one hot file, not because they share a commit.
- **D-206.1-02 (Frontend-only, and `api.ts` is untouched)**: No backend file, no migration, and
  no edit to `frontend/src/lib/api.ts`. If a plan believes it needs a new `api.ts` export, that is
  a signal it has mis-read the shipped types — re-read `api.ts:6385-6426` before deviating.

#### Item 1 — the MCP creation door

- **D-206.1-03 (A fourth chooser option, not a second form)**: `ConnectionFormPanel.tsx`'s
  capability chooser gains an **MCP server** option alongside the three capabilities. It is the
  same panel, the same Save, the same refusal vocabulary — the per-shape field block is what
  switches, exactly as `send_email` / `create_ticket` / `post_message` already do at
  `ConnectionFormPanel.tsx:899-993`. A second panel would fork the write path and the refusal copy.
- **D-206.1-04 (The MCP body omits `capability` and sends `config: { headers: {} }`)**: The wire
  body is `{ name, mcp_server_url, config: { headers: {} }, secret? }` with **`capability` absent
  or `null`**. Measured at the model: `ConnectorConnectionCreate._validate_connection_shape`
  branches on `mcp_server_url` FIRST and returns before the capability arm; `config` defaults to
  `McpConfig` and `McpConfig` is `extra="forbid"` with exactly one field, `headers`. Sending a
  capability alongside a URL, or a `SendEmailConfig`-shaped config, is a 422.
- **D-206.1-05 (HTTPS is refused in the panel AND at the model, and the panel is not the gate)**:
  `mcp_server_url` must start with `https://` — the model raises otherwise, and
  `validate_mcp_destination` refuses again at call time. The panel mirrors this with a disabled
  Save (*"a disabled Save is kinder than a 422"* — `models/connector.py`'s own WR-05 note), but
  the panel's check is a courtesy, never the security boundary, and the plan must say so where it
  is written.
- **D-206.1-06 (The credential is OPTIONAL for the MCP shape, and only for it)**: A capability
  connection still requires a secret (WR-05). An MCP server may be unauthenticated —
  `resolve_connection` was relaxed for the MCP shape ONLY in `147f3c57`. The panel must not
  require one, and must not present the absence as an error state.
- **D-206.1-07 (The row it creates must be one the picker can bind)**: The ROADMAP's first failure
  mode. Acceptance is not *"the POST returns 201"* — it is the driven round trip: create in the
  UI → discover → grant → a workflow step calls a granted tool. **No direct database insert
  anywhere in the evidence.**

#### Item 3 — logos

- **D-206.1-08 (ONE shared map, and the shipped "never vendor logos" rule is SUPERSEDED, not
  ignored)**: `ConnectionsTab.tsx`'s header currently reads *"CAPABILITY MARKS, NEVER VENDOR LOGOS
  (§10 / U-12)"* and `CAPABILITY_MARKS` maps to generic fluent-emoji glyphs. The operator's icon
  convention (`references/icon-convention.md` §1, Running Design Decision 43, 2026-06-27) says a
  service shows its OWN mark, from one source, byte-identical everywhere — and the ROADMAP's SC#3
  makes that binding for this surface. **The old docblock is corrected AT SOURCE, beside the
  original, never deleted** (this project's standing correction rule). A reader who finds the old
  sentence and no correction will re-apply it.
- **D-206.1-09 (The dependency decision is TAKEN, not assumed away)**: Measured at HEAD —
  `@lobehub/icons@^5.10.0` is AI-provider-shaped and ships **no Slack and no Jira/Atlassian**; the
  only installed Iconify collection is `@iconify-json/fluent-emoji@^1.2.7`. `unplugin-icons` is
  wired in BOTH `vite.config.ts` and `vitest.config.ts`, so a `~icons/<set>/<slug>` import resolves
  in tests as well as in the build. The phase adds `@iconify-json/logos` (registry-verified
  present, `1.2.13`) as a devDependency, **or** bundles the SVGs — the plan states which and why.
- **D-206.1-10 (Every slug is VERIFIED to resolve, and the fallback is not blank)**: icon-convention
  §3's measured trap — `fluent-emoji:direct-hit` shipped BLANK in Phase 127. Every slug this phase
  introduces is verified against the installed package (an assertion over the collection's own JSON,
  the way `ConnectionsTab.tsx:36-41` records for its three fluent-emoji slugs), not against any
  document. The unknown-service fallback renders a **named neutral mark** — never nothing, and
  never another service's mark.
- **D-206.1-11 (The mark lookup is EXPLICIT per arm — no positional fallback)**: This is the exact
  defect `destinationFactsOf` shipped, where a trailing `return` made every MCP connection claim it
  sends to `slack.com/api` (fixed in `147f3c57`). The mark map is a total, own-property lookup with
  a named default; an MCP row resolves its own mark by its own condition (`mcp_server_url` present),
  never by falling off the end of a capability ladder.

#### Item 2 — the dense row

## Summary

Every one of the eight open questions was answered by **running something** — no claim below rests
on training data about Tailwind, Iconify, jsdom or Pydantic. Three findings materially change the
shape of the plan, and each of them contradicts something a reasonable planner would otherwise have
assumed:

1. **A non-existent `~icons/` slug does NOT render empty here — it fails the build.** Measured:
   `Error: Icon \`fluent-emoji/definitely-not-a-real-icon-xyz\` not found`, and the suite that
   imports it loads **zero tests**. The same is true of a slug from an *uninstalled* collection.
   So D-206.1-10's *"verify every slug resolves"* is already enforced by the module graph; what
   still needs an assertion is the OTHER half of the §3 trap — a slug that resolves to an EMPTY
   body — and that is a one-line `innerHTML.length > 0` check, measured working (7799 chars for
   `fluent-emoji:envelope`, 3211 for `ticket`, provably different).

2. **The row's problem is not that the column got narrow — it is that the fixed columns alone are
   bigger than the whole track, and the surface is capped at 768px regardless of viewport.**
   `SettingsPage.tsx:861` wraps everything in `max-w-3xl` (= 768px). The list track measures
   **718px** panel-closed and **302px** panel-open, while the row's non-flexible budget is
   **488px** (400px of `flex-none` columns + 60px of gaps + 28px of padding). At 302px the deficit
   is 186px *before either flexible cell gets a single pixel*. The corollary the ROADMAP's SC#2
   wording does not anticipate: **1280px and 1536px produce IDENTICAL geometry on this surface**,
   because `max-w-3xl` binds at both. The real variable is panel-open vs panel-closed.
   ⚠ And because the destination cell carries `truncate` (`white-space: nowrap`),
   `scrollWidth <= clientWidth` **can only become true if the text is allowed to WRAP** — widening
   the column is not sufficient for a long URL. That is the single binding design constraint on
   item 2.

3. **The positional-fallback defect SC#4 names in `connectionsCopy.ts` is already fixed there — and
   is alive in FOUR OTHER PLACES that SC#4 does not name.** `configFromDraft` and
   `destinationFooterOf` (both `connectionFormCopy.ts`) and `typedHost` and `secretLabel` (both
   `ConnectionFormPanel.tsx`) are all ladders whose LAST arm is unguarded. An MCP draft falling
   through `configFromDraft` emits `{ default_channel: "" }` — a `PostMessageConfig` shape, which
   `NonEmpty` rejects as a 422 — and through `destinationFooterOf` renders the SMTP footer. This
   is D-206.1-11's exact failure mode, one file over from where the decision points.

A fourth finding is a live defect nobody has written down: **clicking an existing MCP row's name
opens the panel showing the SMTP form.** `ConnectionFormPanel.tsx:714` falls back to
`draft.capability`, `draftFromConnection` falls back to `EMPTY_DRAFT.capability` = `"send_email"`,
and the edit screen therefore renders *"Send an email"*, an SMTP host box and a *"App password"*
label for a row that is an MCP server. It is reachable today (the container passes `onOpen`
unconditionally). OQ#4 asked what `mode === "edit"` must do; this is the answer, and it is item 1's
unnamed sibling.

**Primary recommendation:** add `@iconify-json/logos@1.2.13` as a devDependency and use the
**square `-icon` variants** (`logos:slack-icon`, `logos:model-context-protocol-icon`) — the bare
`logos:slack` / `logos:model-context-protocol` are 512×130 and 512×69 **wordmarks** that render as
a smear in a 16px box. Introduce ONE `connectionMark.tsx` leaf modelled byte-for-byte on the
shipped `lib/phaseGlyph.tsx` idiom (own-property guard, `null` for unmapped, caller renders its own
fallback). Reflow the dense row to a **two-line stack whose destination WRAPS**, and thread `dense`
from the `panel && !isMobile` expression as D-206.1-12 requires. Take the MCP shape as a `"mcp"`
sentinel member of a widened `ConnectionShape` type — the least invasive option, because every
shipped `capability === "send_email"` guard then stays literally unchanged.

⚠ **`logos` has no honest SMTP mark, and that is a finding, not a gap to paper over.** The only
mail-shaped names it carries are vendors — `google-gmail`, `mailchimp`, `mailgun`, `mailjet`.
Rendering `logos:google-gmail` for a Fastmail SMTP connection is precisely the *"approximated"*
failure the ROADMAP's *How we'd know this failed* names. SMTP is a **protocol with no vendor**, so
the honest mark is a NEUTRAL one, which is the same category D-206.1-10 already requires for the
unknown-service fallback. Three verified neutral candidates, all **already installed**, zero new
dependency:

| Candidate | Source | Verified | Note |
|---|---|---|---|

| `lucide-react` `Mail` / `Plug` / `Server` / `Cable` | already imported across the tree | ✅ all four exported | flat line glyphs; visually consistent with the flat `logos` marks |

**Recommendation (Claude's discretion under D-206.1-08):** brand marks from `logos` where a vendor
exists (`create_ticket → logos:jira`, `post_message → logos:slack-icon`), MCP's own mark
(`logos:model-context-protocol-icon`), and a **neutral lucide glyph** for the vendorless SMTP shape
(`Mail`) and for the unmapped fallback (`Plug`). That keeps one rule stated in one sentence — *a
vendor shows its own mark; a vendorless protocol shows a neutral one* — instead of two exceptions.

**`simple-icons@1.2.93` as the alternative** `[VERIFIED: collection icons.json]`: 3,726 icons,
`24×24` monochrome. Carries `simple-icons:slack`, `simple-icons:jira`, `simple-icons:atlassian`,
`simple-icons:modelcontextprotocol`, `simple-icons:confluence`. **Smaller (4.6 MB) and complete for
this phase**, but every mark is a single-colour silhouette — a Slack row would not look like Slack,
which is the whole point of Running Design Decision 43. `logos` is the right choice; `simple-icons`
is the fallback if a future slug is missing from `logos`.

⚠ **A geometry trap worth writing into the plan.** Every icon is emitted with its `viewBox`
preserved (measured: `viewBox="0 0 32 32"` on the probe), so `preserveAspectRatio` defaults to
`xMidYMid meet` and a non-square icon **letterboxes rather than distorts** inside `h-4 w-4`. That is
safe for `model-context-protocol-icon` (256×285 — a 6% letterbox). It is NOT safe for the 512×130
and 512×69 **wordmarks**, which would shrink to an unreadable 4px-tall strip inside a 16px square.
`-icon` is not a style preference here; it is the difference between a legible mark and a smear.
`[VERIFIED: collection width/height fields + probe render]`

**Duplicate-gradient note (low risk, one line of prose):** `logos:jira` and `logos:atlassian` embed
`<linearGradient id="SVGSBI7obaC">` / `id="SVGH6PerbeJ"` — pre-randomised and unique *per icon*, so
the two never collide. Rendering the SAME icon 24 times duplicates one id 24 times; `url(#id)`
resolves to the first match, which is the identical gradient, so it is visually inert. Named so it
is not rediscovered as a bug.

### OQ#2 — HOW `unplugin-icons` RESOLVES AT TEST TIME (driven, then deleted)

**Method.** Four throwaway suites written under `frontend/src/__iconprobe__/`, run with
`npx vitest run src/__iconprobe__ --maxWorkers=2`, then **the directory was deleted and
`git status -- frontend` verified clean.** `unplugin-icons@23.0.1`, vitest `4.1.0` runner /
`4.1.11` CLI, node `v22.14.0`.

**(a) An EXISTING slug renders a non-empty `<svg>` under jsdom.** `[VERIFIED: probe run]`

```
TAG: svg | viewBox: 0 0 32 32 | w: 1.2em | h: 1.2em | childCount: 1 | innerHTMLlen: 7799
CLASSATTR: h-4 w-4
```

- The component forwards `className` (so `h-4 w-4` lands on the `<svg>`).
- `width`/`height` default to `1.2em`; the `viewBox` is preserved.
- Two different slugs give **provably different** bodies: `envelope` 7799 vs `ticket` 3211.

**(b) A NON-EXISTENT slug fails LOUDLY at transform time — it does not render empty.**
`[VERIFIED: probe run]`

```
FAIL src/__iconprobe__/bad.probe.test.tsx [ src/__iconprobe__/bad.probe.test.tsx ]
Error: Icon `fluent-emoji/definitely-not-a-real-icon-xyz` not found
 ❯ src/__iconprobe__/bad.probe.test.tsx:2:1
```
The suite loads **0 tests**. Identical behaviour for a slug from an **uninstalled** collection:
```
Error: Icon `logos/slack-icon` not found
```
(measured *before* `@iconify-json/logos` was fetched — which is also the non-vacuity control that
the collection really is absent from `frontend/node_modules` today).

**What this means for the plan — and it is a correction to a shipped document.**

> ⚠ `references/icon-convention.md` §3 records that `fluent-emoji:direct-hit` *"does not exist in
> the set and rendered EMPTY"*. **That sentence is still worth obeying and its mechanism no longer
> applies to this loading path.** Measured at HEAD: `direct-hit` is indeed **ABSENT** from the
> installed `@iconify-json/fluent-emoji` (3,174 icons; `bullseye` is PRESENT, body 12438) — so the
> §3 fact is true. But under `unplugin-icons` + a local collection, an absent slug **cannot ship**:
> it is a build error, not an empty render. The empty-render failure mode belongs to the *runtime*
> Iconify API path (`<Icon icon="..."/>` fetching from `api.iconify.design`), which this repo does
> not use on this surface. The original sentence is preserved above; the correction sits beside it.

So, concretely:

- *"Every slug resolves"* is enforceable as a **unit test**, and the test is simply
  `import Mark from "~icons/logos/slack-icon"` — if the slug is wrong the suite fails to load. No
  separate build assertion is needed.
- What a test still MUST assert is the residual half: **a resolved-but-empty body**. Measured
  working: `expect(render(<Mark/>).container.querySelector("svg")!.innerHTML.length).toBeGreaterThan(0)`,
  plus a **distinctness** assertion across the four marks so a copy-paste that maps two capabilities
  to the same import fails.
- **The `~icons` import is the non-vacuity control for the dependency itself.** If a plan adds the
  imports but forgets `package.json`, the suite goes red with `Icon \`logos/...\` not found` — which
  is exactly the loud failure this project prefers over a silent one.

### Pattern 1: the total, own-property mark lookup (`lib/phaseGlyph.tsx`, verbatim idiom)

**What:** a module-private `Record<string, PhaseMark>` + an exported KEY list + a lookup function
that guards with `hasOwnProperty` and returns `null` for anything unmapped.
**When:** any string→component map whose key comes from server data.
**Why it is not optional here:** `PHASE_GLYPH_MARKS["constructor"]` is the `Object` FUNCTION —
never nullish — so `?? null` does not fire and React receives a function as a child. That hard-crashed
a node face before `188.1-04`. `ConnectionsTab.tsx:157-162` already does this correctly for
`CAPABILITY_MARKS`; the new map must inherit it.

```tsx
// Source: frontend/src/lib/phaseGlyph.tsx:96-122 (shipped)
export const PHASE_GLYPH_MARK_KEYS: readonly string[] = Object.keys(PHASE_GLYPH_MARKS)

export function phaseGlyph(phaseType: string | undefined): PhaseMark | null {
  if (!phaseType) return null
  if (!Object.prototype.hasOwnProperty.call(PHASE_GLYPH_MARKS, phaseType)) return null
  return PHASE_GLYPH_MARKS[phaseType]
}
```

⚠ **Only the KEYS are exported, never the map** — handing the map out lets a caller bypass the guard.
The new `connectionMark.tsx` should follow that exactly.

- **Deleting a column to make the row fit.** D-206.1-13 and the ROADMAP's failure list.
- **Re-baselining a pinned assertion.** The wide render must diff byte-identical; a pin that passes

- **Inventing an `api.ts` export.** D-206.1-02; every needed type is at `api.ts:6318-6426`, read.

## Common Pitfalls

### Pitfall 1: shipping a wider truncation and calling it SC#2

**What goes wrong:** the dense row gives the destination 260px instead of 93px, the cell looks much
better, and `scrollWidth <= clientWidth` is still **false** for any URL over ~40 characters.
**Why:** `truncate` sets `white-space: nowrap`, so `scrollWidth` is the full un-wrapped text width
regardless of the column. The operator's own `scrollW 272` against a 302px track shows the margin is
razor-thin even at best.
**Avoid:** the dense destination must set `whitespace-normal break-all` (or `break-words`). Assert
the computed `white-space` in the browser snippet, not only the two numbers.
**Warning sign:** a browser reading with `cellFits: true` and `whiteSpace: "nowrap"` — that is a
short fixture, not a working shape.

### Pitfall 2: the fourth chooser option renders the SMTP config on save

**What goes wrong:** the option is added, the field block is added, Save returns 422 — or worse,
succeeds with a Slack-shaped config.
**Why:** `configFromDraft`'s last statement IS the Slack arm (`connectionFormCopy.ts:269`), so `mcp`
falls through to `{ default_channel: "" }`.
**Avoid:** add the explicit `mcp` arm AND give the Slack arm its own `if`, in the same edit.
**Warning sign:** the 🔒 footer showing `nothing yet · STARTTLS` while the MCP URL box has a URL in
it — that is `destinationFooterOf`'s trailing arm firing, and it is visible before Save is pressed.

### Pitfall 3: a `title` attribute added to explain a truncation

**What goes wrong:** two suites go red on an assertion that has nothing to do with the change.
**Why:** `container.querySelectorAll("[title]")` must be **length 0**, checked with the ⋯ menu open
and a sheet open too.
**Avoid:** real DOM text or wrapping. Never a tooltip. This surface's own header says so.

### Pitfall 4: editing an existing MCP row shows the email form (LIVE TODAY)

**What goes wrong:** already broken — see §OQ#4. If the phase adds only the CREATE door, the surface
gains a way to make rows it still cannot honestly display.
**Avoid:** seed the draft's shape from `connection.mcp_server_url`, never from
`connection.capability ?? default`.
**Warning sign:** `capabilityLabelOf` receiving `"send_email"` for a row whose `Sends to` cell reads
an MCP host — the two halves of the same screen disagreeing.

### Pitfall 5: assuming 1280 and 1536 differ

**What goes wrong:** the browser proof is run twice, produces identical numbers, and is read as a
broken measurement.
**Why:** `SettingsPage.tsx:861` `max-w-3xl` caps the page at 768px.
**Avoid:** record the invariance as the finding. Keep the `control.bodyClientW` non-vacuity check so
"identical" can be distinguished from "measured nothing".

### Pitfall 6: a new sentence written inline in the panel

**What goes wrong:** `ConnectionFormPanel.test.tsx:1549` greps `panelSource` for imported refusal
identifiers and forbids three absolute-verb phrases.
**Avoid:** every MCP string is an exported identifier in `connectionFormCopy.ts`.
⚠ **And note the gap:** the nine-banned-terms and absolute-verb fences walk **`connectionRefusalCopy`
only** (`stringsOfModule()`, `:260-298`). New strings in `connectionFormCopy.ts` are **not** swept.
The plan may close that with a new sweep — but must not assume the existing fence covers it.

### Pitfall 7: re-running a red count gate before triaging it

**What goes wrong:** D-206.1-17 / SEED-171. Capture the failing filenames from the gate's persisted
JSON first, check each against `git diff --numstat`, and only then decide flake vs real. Two of
SEED-171's five named flaky suites are `library/WorkflowCard.test.tsx` and `WorkflowsPage.test.tsx`
— **neither is in this phase's blast radius**, so a red gate here is more likely real than flaky.

## Open Questions

1. **Where do `discover` and `grants` live in the UI? (A5 — the highest-value question)**
   - *What we know:* both endpoints ship; `McpToolPicker.tsx` renders grant badges at the builder
     seam; `ConnectionPicker.tsx` mounts it. SC#1 requires the driven chain create → discover →
     grant → call.
   - *What's unclear:* CONTEXT.md's in-scope list names only the creation form, the dense row and
     the logos. It never says the Settings row gains a **Discover tools** action.
   - *Recommendation:* SC#1's chain is satisfiable today through the builder seam without any
     Settings affordance. **Plan for the round trip to be DRIVEN through the existing builder seam,
     and state in the plan that a Settings-side Discover action is deliberately NOT added** — with
     a re-open trigger (*a person cannot reach the builder seam for a connection they just made*).
     Adding one would be a new capability inside a phase already carrying one.

2. **Does an MCP row get the `Check credential` action?**
   - *What we know:* `checkConnectorConnection` is capability-shaped (SMTP login / Jira auth /
     Slack `auth.test`). `ConnectionFormPanel.test.tsx:1322-1345` asserts the check is REMOVED with
     a stated reason on a switched-off row.
   - *What's unclear:* what a check MEANS for an unauthenticated MCP server.
   - *Recommendation:* **REMOVE it for the MCP shape with a stated reason** (the surface's own
     removed-not-disabled rule). A check that cannot say anything true is worse than no check.

3. **Does the dense row keep the column HEADER?**
   - *What we know:* `connections-header` is asserted with all five `[data-column]` labels **in the
     wide render**. A stacked row has no columns to head.
   - *What's unclear:* whether hiding the header in dense mode counts as "deleting a column".
   - *Recommendation:* **it does not** — D-206.1-13 is about the row's CELLS, and a stacked row with
     a five-column header would be actively misleading. Hide the header when `dense`, and pin that
     the five **cells** are all present in both renders (which is what the decision actually says).

4. **`connectionMark.tsx` or `connectionsCopy.ts`?** (Claude's discretion)
   - *Recommendation:* **its own leaf.** `connectionsCopy.ts`'s header records the measured
     `react-refresh/only-export-components` cost of mixing components into that module (plan
     190-12), and a mark map is components. `lib/providerLogo.tsx` and `lib/phaseGlyph.tsx` are the
     two shipped precedents, both leaves.
