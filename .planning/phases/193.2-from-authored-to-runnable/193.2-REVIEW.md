### WR-02: `_clean_label`'s "no control character / one line" invariant does not hold for Unicode format characters — and the test shares the blind spot

**File:** `backend/app/services/harness/publish_service.py:556-585`
(test: `backend/tests/unit/test_publish_service.py:735-752`)
**Severity:** WARNING
**Status:** ✅ **RESOLVED — 2026-08-15, fix pass 2, commit `c4fe1066`.** See the block at the end
of this finding. ~~⬜ OPEN — deliberately not fixed in the first pass (scope was WR-01 + WR-03
only); `_clean_label` and its test are unchanged and the Unicode-Cf blind spot stands.~~ (The
superseded status line is struck through rather than deleted — this file's own habit.)

**Issue.** The scrubber collapses only two classes:

```python
scrubbed = "".join(" " if (ch.isspace() or ord(ch) < 32 or ord(ch) == 127) else ch for ch in raw)
```

Unicode **category-Cf** characters are neither `isspace()` nor `< 32`. Measured against the shipped
function:

| char | name | `isspace()` | survives `_clean_label` |
|---|---|---|---|
| `U+200B` | zero-width space | False | **yes** |
| `U+202E` | RIGHT-TO-LEFT OVERRIDE | False | **yes** |
| `U+2066` | LEFT-TO-RIGHT ISOLATE | False | **yes** |
| `U+00AD` | soft hyphen | False | **yes** |

The docstring says the function delivers *"the single-line, length-bounded form"* and the
`_LABEL_MAX_CHARS` block says *"What IS defended here is LENGTH and ONE-LINE SHAPE."* Neither holds
for these.

**Concrete failure scenario.** A phase named `Approve the draft<U+202E>` produces a refusal whose text
after the label renders right-to-left in the browser — including the actionable clause *"Remove that
step to publish."* The same string is persisted verbatim into
`harness_audit.metadata.named_failures`, so the audit ledger inherits the mangling. `U+200B` in a
name additionally makes the clamp arithmetic and any operator `grep` disagree with what is on
screen.

**Why the test cannot catch it.** `test_t193201_a_newline_bearing_name_yields_a_single_line_message`
asserts `not any(ord(ch) < 32 or ord(ch) == 127 for ch in message)` — the **identical predicate** to
the code under test. A test that restates the implementation's own condition cannot discover a class
that condition misses.

**Severity note.** Not Critical: the phase `name` is authored by the workflow's own owner or by the
authoring model on that owner's behalf, and the message is shown back to that same owner, so no
privilege boundary is crossed. It is a correctness/robustness defect in a function whose entire job
is sanitisation.

**Fix.** Use the Unicode category, not the codepoint range:

```python
import unicodedata

scrubbed = "".join(
    " " if (ch.isspace() or unicodedata.category(ch) in ("Cc", "Cf", "Cs", "Co", "Zl", "Zp"))
    else ch
    for ch in raw
)
```

and widen the test's own predicate to the same category set, then drive it RED against a planted
`"Approve<U+202E>the draft"` before trusting it.

### WR-03: `ORDER BY updated_at DESC` has no deterministic tiebreaker — 39 live published rows share one timestamp

**File:** `backend/app/db/workflows.py:368` (published) and `:660` (drafts)
**Severity:** WARNING

**Issue.** Both feeds order on `updated_at` alone. `updated_at` is not unique, and Postgres'
`now()` is **transaction-scoped**, so every row touched by one migration or one bulk update shares
an identical timestamp. Measured against the live local DB (`127.0.0.1:54322`, 225 rows):

```
published rows sharing one updated_at: 39  (2026-07-18 20:43:42.856183+00)
                                        2  (2026-07-30 20:16:20.222893+00)
draft     rows sharing one updated_at: 24  (2026-07-18 20:43:42.856183+00)
```

With no tiebreaker, the relative order of those 39 rows is **unspecified**. The previous
`ORDER BY name` was total in practice (names are near-unique); the new clause is not.

**Concrete failure scenario.** The Workflows page refetches on publish, on back-nav, and on project
re-select. Between two fetches Postgres may return the 39 co-timestamped rows in a different
sequence (the heap order the sort consumes changes whenever any row in the table is updated). The
user sees a third of their library silently reshuffle after an unrelated save. The same feed is the
composer's Harness picker, so the picker reshuffles too. The recency *goal* still works — a
just-published row has a unique fresh timestamp and lands correctly — but everything below the
recent band is unstable.

**Fix.** Make the sort total. One column, no migration, no plan-shape change (there is no index on
`updated_at` either, so nothing regresses):

```python
sql += " ORDER BY updated_at DESC, id DESC"
```

```python
f"ORDER BY updated_at DESC, id DESC",     # list_draft_workflows
```

`id` is `NOT NULL` + unique. Update F-1's needle in `test_workflows_updated_at.py:459-470` to the
new clause and re-drive its RED probe against the pre-change source.

*Unverified:* I did not reproduce an actual reshuffle — Postgres is free to be stable in practice on
a small table. The tie itself is measured; the observable reorder is a predicted consequence.

### WR-04: the F-7-extended sort fence misses every non-mutating sort form

**File:** `frontend/src/components/workflows/library/libraryFilter.test.ts:768-772`, `:810-820`
**Severity:** WARNING
**Status:** ✅ **RESOLVED — 2026-08-15, fix pass 2, commit `accf9539`.** See the block at the end
of this finding. ~~⬜ OPEN — deliberately not fixed in the first pass (scope was WR-01 + WR-03
only); the needle is unchanged and `.toSorted()` / `.reverse()` still escape both clauses.~~

**Issue.** The needle is

```js
/\brows\.sort\(|\bvisibleRows\.sort\(|\bmerged\.sort\(|\bfamily\.sort\(|\blist\.sort\(/
```

Run against realistic shapes:

| candidate | caught by needle | caught by the `.sort(` corpus check |
|---|---|---|
| `rows.sort(cmp)` | ✅ | ✅ |
| `[...rows].sort(cmp)` | ❌ | ✅ |
| `[...visibleRows].sort(cmp)` | ❌ | ✅ |
| `visibleRows.slice().sort(cmp)` | ❌ | ✅ |
| `Array.from(rows).sort(cmp)` | ❌ | ✅ |
| `visibleRows.toSorted(cmp)` | ❌ | **❌** |
| `[...rows].reverse()` | ❌ | **❌** |

`Array.prototype.sort` **mutates**, so a React developer re-ordering a memoised list will almost
certainly write `[...visibleRows].sort(...)` — i.e. the needle catches only the one form the code
style discourages. The property survives today solely because of the companion assertion
`NON-VACUITY — the swept corpus is EMPTY today` (`:810`), which forbids *any* `.sort(` in either
module. That companion has its own problem: it directly contradicts the needle's docblock, which
states *"a sort that names a narrow thing it sorts … is legal"*. The day either module legitimately
sorts something narrow, the "non-vacuity" case reds on correct code, someone relaxes it, and the
only real coverage disappears — leaving the evadable needle alone.

`.toSorted()` (ES2023, widely available in the toolchain's target) and `.reverse()` escape both.

**Fix.** Make the needle shape-based rather than receiver-name-based, and let the corpus assertion
allow annotated narrow sorts:

```js
const FORBIDDEN_ROW_SORT =
  /(\brows\b|\bvisibleRows\b|\bmerged\b|\bfamily\b|\blist\b)\s*\]?\s*\)?\s*\.(sort|toSorted|reverse|toReversed)\(|\]\.(sort|toSorted|reverse)\(/
```

and drive it RED against real plants of **each** of `[...visibleRows].sort(`,
`visibleRows.toSorted(` and `[...rows].reverse()` in production source, restoring after each — the
inline `expect(planted).toMatch(...)` controls prove the regex, only a real plant proves the fence
points at the right file.
