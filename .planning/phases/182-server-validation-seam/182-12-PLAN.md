<objective>
Close WR-05 from `182-REVIEW.md` (round 2), selected by the operator as item 7 of the
D-182-R2-03 scope, and fold in the WR-06 seed correction.

`_resolve_publish_supabase` reads `SELECT org_id FROM workflow_definitions WHERE id = $1`
specifically so the BYPASSRLS service-role client is org-scoped (Phase 163, D-05 / T-163-05b). It
then passes only `user_id` down, and `assemble_grounding_bundle` resolves visibility from
`_resolve_caller_org_ids(supabase, user_id)` — EVERY org the publisher belongs to. The `org_id` that
was just read is used to construct the client and then never consulted for the gate.

For a multi-org author, publish therefore green-lights a definition in org A whose `skill_ref`
points at an org-B skill, or whose `folder_scope` names an org-B folder, because the PUBLISHER can
see both. At run time the picture flips: `tool_dispatcher`'s skill resolution and
`fetch_visible_folders` gate on the RUNNER's org set, so an org-A colleague running the published
workflow gets an unresolvable skill or an empty folder intersection. The workflow passed the hard
gate and silently under-performs for everyone but its author. Nothing crosses a tenant boundary on
the wire, but it is a multi-tenancy correctness gap in a brand-new publish gate, and 182-06 is what
made that gate authoritative. It is the same shape as SEED-124 / SEED-125 (org-blind service-role
reads), one layer up: the read is org-gated, the SCOPE of the gate is wrong.

WR-06, folded in because it is cheap and prevents future harm: SEED-130 records "Not a security
issue" and offers, as one of two viable fixes, "Option B: retype the param as the storage path
(`str`) and drop the UUID coercion". `resolve_template_source` Branch 1 performs ZERO ownership, org
or traversal validation — `user_id` is accepted and never read — and the download is a raw
service-role bucket read. The only thing containing the exposure today is the `UUID` annotation,
which restricts the reachable key space to bare-UUID objects at the bucket root that the app never
produces. Option B applied literally turns `GET /workflows/grounding-bundle?template_asset_id=...`
into an arbitrary cross-tenant object read authenticated only by "is a canvas user".

Purpose: make the publish gate answer the question it was built to answer — is this definition
grounded in ITS OWN org — and stop a wrong security verdict from being inherited by Phase 184.
Output: one optional org restriction threaded from the definition's org to both org-gated reads, a
cross-org publish test, and a corrected seed.
</objective>
