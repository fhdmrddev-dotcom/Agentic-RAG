# Phase 095.1 Plan 06: Reachable Derived Workspace Panel (GAP-1) Summary

**Closed GAP-1 from the 095.1 live UAT: the headline activity-derived workspace panel was structurally unreachable — `WorkspacePanel.hasActivity` (`todos.length || files.length || pendingAsks.length || phases.length`) OMITTED the derived selector, so a no-`write_todos` cross-provider run short-circuited to `<PanelEmpty/>` and TodosSection (which holds Plan-02's `useDerivedPanel`) NEVER mounted. Fixed by including `derived.length > 0` in `hasActivity` via the EXISTING `useDerivedPanel` hook (reuse, no re-implemented gate), plus a guard test that exercises the real gate→derived render path the unit tests bypassed, and an honest (omitted) Todos count badge for derived-only activity.**

## Accomplishments

- **`WorkspacePanel.hasActivity` now reaches the derived panel.** Imported + called the existing `useDerivedPanel(threadId)` hook (StreamsProvider, Plan 02) and ORed `derived.length > 0` into `hasActivity`. A thread with ONLY tool-call activity that earns a derived panel (the no-`write_todos` cross-provider parity case) now renders the panel body — letting `TodosSection` (precedence 2) show the derived rows + the "derived from activity" marker — instead of short-circuiting to `<PanelEmpty/>`. The derivation was previously **structurally unreachable**; this is the single boolean fix that makes the phase's headline WORKSPACE-PARITY deliverable actually visible.
- **Reuse, not re-implementation.** WorkspacePanel does NOT call `shouldPopulate` or re-derive the gate — the hook applies the smart gate (write_todos OR ≥2 deduped MEANINGFUL tools) internally and returns the stable module-level `EMPTY_DERIVED` ref when the thread doesn't qualify, so reading `derived.length > 0` is both the correct signal AND churn-free (PANEL-06 isolation preserved by construction).
- **Honest count badge.** The Todos `PanelSection` count went from `{ done: todosDone, total: todos.length }` to `todos.length > 0 ? { done: todosDone, total: todos.length } : undefined` — so derived-only activity (where there are no real todos) omits the badge entirely instead of rendering a misleading `0/0` (PanelSection renders no badge when count is undefined — the same omission idiom the Files section uses). The rail's todos badge is untouched (it reflects real todos only — derived rows are an open-panel affordance).
- **Guard test that catches what the unit tests missed.** New `WorkspacePanel.derived.test.tsx` renders the REAL WorkspacePanel + REAL TodosSection (which calls the real `useDerivedPanel`) through the `hasActivity` gate — the exact path the existing `WorkspacePanel.test.tsx` (sentinel-mocks TodosSection) and `TodosSection.test.tsx` (mounts TodosSection directly) both bypass.
- All targeted suites GREEN: WorkspacePanel.derived (4) + WorkspacePanel (24) + TodosSection (12) + panelHooks (18) = **58/58**; consumed workspacePanel selector **31/31**.

## Decisions Made

- **Reused the existing `useDerivedPanel` hook for the gate signal** rather than calling `shouldPopulate` / re-deriving in WorkspacePanel. The hook is the single source of the smart-gate truth (Plan 02) and returns the stable EMPTY ref when ungated, so a second derivation would duplicate logic AND risk a churn regression. `derived.length > 0` reads the hook's already-gated output.
- **Honest (omitted) count badge over an invented derived-count badge.** A `0/0` on the Todos header for a derived-only thread is a lie (no real plan); a derived-count badge would imply a real plan. Omitting the badge (and leaving the "derived from activity" marker inside TodosSection to signal the state) is the locked behavior.
- **Guard test in a separate file.** `WorkspacePanel.test.tsx` globally mocks TodosSection to a sentinel (so the gate→derived path is unreachable there); a fresh `vi.mock` scope is the only way to render the REAL TodosSection through the gate. This is the structural reason the original unit tests passed while the live panel was empty.
