## Info

### IN-01: `turnNumber` is a hardcoded constant — the variable indirection is now dead

**File:** `frontend/src/components/chat/RunCard.tsx:245-248`
**Issue:** `const turnNumber = 1` is now a literal constant, so `turn ${turnNumber}` always renders `turn 1`. The variable indirection no longer carries information — the run-sub describes "ONE run = ONE turn," which is correct for the current single-run-per-card model. This is intentional and operator-accepted (live == reload was the goal, and `_mapMessageResponse` omits `iterationCount` on reload so `turn 1` is the reload-truth value). The forward-looking risk: if a future phase ever renders multiple conversation turns inside one RunCard, the hardcoded `1` is a silent correctness trap, not a compile error. The extensive comment block (L235-244) documents the rationale well, which mitigates this.
**Fix:** No change required for this phase. Optional future-proofing: inline `turn 1`, or rename to a named constant (e.g. `TURN_LABEL = 1`) to signal it is deliberately static and not a forgotten TODO. Keep the comment block in place either way — it is the load-bearing documentation that prevents a future reader from "fixing" it back to `iterationCount + 1`.

### IN-02: Gate (`threadId` prop) and body (`useViewingThread`) read the same derived signal in two components — no divergence, worth a one-line note

**File:** `frontend/src/components/panel/WorkspacePanel.tsx:90, 109`
**Issue:** The new `hasActivity` gate reads `useDerivedPanel(threadId)` where `threadId = useViewingThread()` (L90), while the body content `<TodosSection/>` independently calls `useViewingThread()` and `useDerivedPanel(threadId)` again internally. I verified these cannot diverge: WorkspacePanel sources its `threadId` from `useViewingThread()` (the `selectedThread` prop is renamed to the unused `_selectedThread`), the exact same source TodosSection uses, and `useDerivedPanel` is a pure `useMemo` over the same store slice returning the stable `EMPTY_DERIVED` ref when the gate fails. So the panel-body-opens decision and the derived-rows-render decision are guaranteed consistent — there is no "opens an empty body" race. This is correct as written; flagging only because the gate and the rendered content compute the same derived signal in two different components, a subtle coupling a future refactor could break.
**Fix:** No change required. Optional: a one-line comment on the `derived` declaration (L109) noting "same `useDerivedPanel(threadId)` TodosSection reads — keep these in lockstep" would protect the invariant against a future edit that changes the gate's thread source without changing TodosSection's.
