<objective>
Close GAP-1: the activity-derived workspace panel — the phase's headline
WORKSPACE-PARITY deliverable — never renders. Plans 01/02 built and wired a
deterministic, provider-independent derived panel (`deriveWorkspacePanel` selector
+ `useDerivedPanel(threadId)` hook + the TodosSection precedence render), proven
green by 62 unit tests. But on the live app the derived rows NEVER appear: a
14-step Google run, a 2-tool OpenAI run, and every no-`write_todos` cross-provider
thread show PanelEmpty ("No workspace activity yet").

ROOT CAUSE (confirmed, `WorkspacePanel.tsx:113-114`): `hasActivity` is computed
from `todos.length || files.length || pendingAsks.length || phases.length` — it
OMITS the derived selector. When a thread has only tool-call activity (no real
write_todos / files / asks / phases) — exactly the no-write_todos cross-provider
parity case the phase targets — `hasActivity` is `false`, the panel short-circuits
to `<PanelEmpty/>` at :131, and `TodosSection` (which holds Plan-02's
`useDerivedPanel` at :145) NEVER mounts. The derivation is structurally
unreachable. The existing unit tests passed because `WorkspacePanel.test.tsx`
mocks `TodosSection` to a thin sentinel and `TodosSection.test.tsx` mounts
TodosSection directly — BOTH bypass the `hasActivity` gate.

Purpose: make the headline parity deliverable actually reachable, so every
provider's multi-step run fills the panel with the real tasks it performed.

Output: `WorkspacePanel.tsx` consumes the EXISTING `useDerivedPanel` hook (reuse —
do NOT re-implement the gate) so `hasActivity` is true when the viewing thread
earns a derived panel; plus a guard test that exercises the REAL gate→derived
render path the unit tests missed.
</objective>
