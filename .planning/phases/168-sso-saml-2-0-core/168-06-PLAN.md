## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| login form → SSO routing | The domain lookup + redirect are the entry to the IdP; the password box must always remain reachable — even when the route lookup fails (fail open) |
| non-manager → SSO tab | The tab render-gates on canManageSso; the server require_sso_manage is the wall |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-168-07 | Denial of Service | identifier-first login | accept/mitigate | the password field reveals on any no-SSO-match AND on ANY `getSsoRoute` failure (403/network/outage — fail OPEN, never a blank form) AND the "Sign in with SSO" escape hatch + the untouched password `onSubmit` guarantee no lockout (SC#3 — enforcement deferred) |
| T-168-06 | Info Disclosure/Tampering | SSO tab visibility | mitigate | render-gated on `canManageSso` (honest-absent CTA, T-166-09); server require_sso_manage is the authority |
| T-168-04 | Info Disclosure | SsoTab render | mitigate | the tab renders only domain/provider_id/status/SP-metadata — NEVER the management token or any secret substring (UI-SPEC honesty rule) |
| T-168-01 | Spoofing/Elevation | status chip | mitigate | the chip renders server-truth status; a `pending_approval` connection visibly reads as not-yet-routing — no client override |
</threat_model>
