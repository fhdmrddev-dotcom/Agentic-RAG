<objective>
Build the deployment-config foundation + the one provider-CRUD proxy service that every SSO endpoint calls. Supabase Auth IS the SAML SP; this service makes ONE authenticated HTTP call per operation to Supabase's provider-CRUD API and returns the GoTrue provider UUID. The Cloud Management API and the self-hosted GoTrue Admin API share the SAME request/response body — only base URL + auth headers differ — so this is ONE service with TWO thin transport adapters selected by env (honoring the Phase-160 4-tier no-code-fork contract).

Purpose: Isolate the token-bearing, network-facing integration behind a single tested seam so Plan 04's endpoints are pure wiring. Fold in the D-168-05 public-domain blocklist (Control 1) and the D-168-01 encrypted-token read.
Output: `config.py` adapter settings, `secret_cipher.py` allowlist extension, `sso_provider_service.py`, `sso_domain_blocklist.py`, a unit test, and updated deploy artifacts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend → Supabase provider-CRUD API | The token-bearing HTTP call; the token must never reach the browser or logs |
| org-admin input → provider create | The metadata URL + domain are untrusted input; the domain crosses the anti-hijack gate here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-168-02 | Elevation | domain at provider-create | mitigate | `sso_domain_blocklist.is_public_domain()` rejects public/free domains before any provider call (D-168-05 Control 1) |
| T-168-04 | Info Disclosure | management token in service | mitigate | decrypt via secret_cipher ONLY at call time; backend-only; log by column name (caplog test asserts no token in logs) |
| T-168-09 | Tampering | delete path | mitigate | `delete_provider` issues the provider-CRUD DELETE first — never leaves an orphaned GoTrue provider still routing a domain |
| T-168-05a | Tampering | provider-create failure | mitigate | non-2xx fails closed (service raises) so Plan 04 never writes a `sso_configs` row for a connection that was not actually created |
</threat_model>
