## Decisions Made

1. **Aggregate Show-toggle dropped in favor of per-step summary rows.** The plan offered both options ("drop the aggregate, show per-step summaries inline; this is the sketch D3 behavior"); picked the sketch-aligned path. ToolCallPanel.test.tsx rewritten to match.
2. **ElapsedTimer preserved alongside running StatusPill.** The plan implies the pill replaces every status visual, but the running pill variant has no duration suffix by design. Keeping the live ElapsedTimer gives users a seconds-ticker during long sandbox calls. The TimeBadge (post-completion clock+duration) was the redundant one — dropped.
3. **Per-line STDERR badge dropped.** Original ExecuteCodeBody added an inline `[stderr]` chip next to each red line. With the new region-level divider (STDERR uppercase band), the per-line badge is redundant — sketch D3 mandates regions, not badges.
4. **Module-scope Shiki highlighter singleton.** Shiki 4 supports per-component highlighters, but instantiating one per `<ShikiCode>` mount would mean re-running WASM init on every new execute_code tool card. The promise-singleton pattern at module scope ensures one WASM init per page load; all subsequent codeToHtml() calls reuse the cached highlighter.
5. **Lazy() + Suspense() on ShikiCode.** Without the lazy wrapper, Vite's bundler would pull Shiki + onig WASM into the main entry chunk (~622 KB), bloating first-paint. Lazy ensures the WASM is fetched on the first execute_code render — and most chats start with a search/read tool, not code execution.
6. **github-dark theme over Aether Deep Midnight.** Sketch tool-call-panel.md L147-152 specifies GitHub-dark token palette (#ff7b72 kw, #a5d6ff str, etc.). Building a custom Shiki theme to match would have been a half-day spike on top of the editor inset itself. Plan defers any custom-theme work; github-dark on the existing #0d1117 editor frame visually integrates fine.

## Issues Encountered

### Worktree node_modules junction (resolved by sync-back pattern)

- **Problem:** Worktree at `.claude/worktrees/agent-af567364d877bb3fb/` has its own filesystem but no `node_modules`. Initial attempts to `mklink /J` a junction from the worktree's `frontend/node_modules` to the main repo's failed silently — Node's `existsSync()` returned `false` through the junction even after `mklink` reported success (probably a Windows symlink/junction quirk with Git Bash file APIs).
- **Workaround:** Run all source edits in the worktree, then `cp` the modified files into the main repo for `npx tsc` / `npx vitest` verification, then commit from the worktree. Tedious but reliable. Each task ran a sync-back step. The vite build was also run against the synced-back main repo files. Both the main repo and the worktree share the same v2.5-dev base, so the file copies don't drift from the worktree's git tree.
