# Phase 075.8: Code Review Report

**Reviewed:** 2026-05-24
**Depth:** standard

## Summary

Phase 075.8 lands clean, focused UI polish on the 075.7 RunCard architecture: a shared `<StatusPill>`, a lazy `<ShikiCode>` highlighter, active-tool glow + bottom shimmer, per-step result-summary rows in Focus Mode, a "Next:" footer, a compact thinking row, and labeled STDOUT/STDERR regions. No API/schema/provider surface is touched. Hooks usage is correct (no conditional hooks, no missing deps in `useEffect`, cleanup flags are present), and the lazy/Suspense pattern around Shiki is textbook.

Three areas merit attention before this is fully closed:

1. **Shiki innerHTML XSS surface** — Shiki output is HTML-safe by design (it serializes tokens via its own builder, escaping text), but the boundary deserves an explicit note. Today the input `code` flows from `tc.args.code` (LLM-authored Python source), so the risk surface is low; documenting this contract reduces the chance a future caller pipes user-controlled HTML through the same component.
2. **Shiki singleton init has no retry/reset path** — if the WASM init promise rejects once (offline / blocked CDN / corrupted cache), the rejected promise is cached at module scope and every subsequent mount falls through to the plain-pre fallback for the rest of the page session.
3. **`tc.id` is typed optional but used as a Record key in two places** — pre-existing pattern (075.6 Plan 02), but the new code in this phase still depends on it; worth either narrowing the type or asserting at the boundary.

The rest are info-level cleanup nits.

## Warnings

### WR-01: Shiki highlighter promise is never reset on failure — one bad init poisons the rest of the session

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.tsx:29-48`
**Issue:** `highlighterPromise` is a module-scope singleton. On the happy path this is correct — concurrent mounts share one WASM init, and subsequent mounts reuse the same highlighter. But if the first init rejects (CDN blocked by ad-blocker/proxy, transient network failure, corrupt cache), the **rejected** promise stays cached. Every subsequent `getHighlighter()` call returns the same rejected promise, so every future `<ShikiCode>` mount falls through to the plain-pre fallback for the lifetime of the page session — even after the user is back online.

```ts
async function getHighlighter() {
  if (!highlighterPromise) {
    highlighterPromise = (async () => { ... })()
  }
  return highlighterPromise   // returns rejected promise forever after first failure
}
```

**Fix:** Wire `.catch()` on the assignment so a rejection clears the singleton, allowing the next mount to retry:

```ts
async function getHighlighter() {
  if (!highlighterPromise) {
    highlighterPromise = (async () => {
      const shiki = await import("shiki")
      const hl = await shiki.createHighlighter({
        themes: ["github-dark"],
        langs: ["python"],
      })
      return {
        codeToHtml: (code: string, opts: { lang: string; theme: string }) =>
          hl.codeToHtml(code, opts),
      }
    })()
    // Reset on failure so the next mount can retry instead of being stuck
    // on the cached rejection for the rest of the page session.
    highlighterPromise.catch(() => { highlighterPromise = null })
  }
  return highlighterPromise
}
```

### WR-02: `dangerouslySetInnerHTML` boundary contract is implicit — document the trust model

**File:** `frontend/src/components/chat/tool-bodies/ShikiCode.tsx:101-107`
**Issue:** `<ShikiCode>` renders Shiki's output HTML via `dangerouslySetInnerHTML`. In Shiki's normal operation this is safe — Shiki tokenizes the input string and emits its own escaped `<span>` tree (it never reflects raw input). However the component currently accepts an arbitrary `code: string` prop with no documented trust boundary, and the comment at line 96-100 talks about CSS overrides, not the safety contract. A future caller could mistakenly pipe user-authored markdown / HTML / RCE-style strings through `<ShikiCode>` thinking it's "just a code block."

Today the only call site is `ExecuteCodeBody` with `tc.args.code` (LLM-authored Python — model-generated, not user-typed, but still untrusted by web-security defaults). The risk surface is small but the contract should be explicit.

**Fix:** Add a JSDoc note on `ShikiCodeProps.code` and a short "trust contract" header in the file:

```ts
export interface ShikiCodeProps {
  /**
   * Source code text. **Treated as untrusted plain text** — Shiki's tokenizer
   * escapes all input before emitting the highlighted HTML. Do NOT pre-render
   * the string through any markdown/HTML pipeline before passing it here.
   */
  code: string
  language?: string
  theme?: string
}
```

Optionally, add a runtime sanity check in dev to flag suspicious input (e.g. presence of `<script` or HTML entities) — but a documented contract is the minimum.

### WR-03: `tc.id` typed optional but used as a `Record<string, boolean>` key — silent collisions possible

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:660-661`
**Issue:** `ToolCall.id` is declared `id?: string` in `frontend/src/types/index.ts:30`. In `ToolCallPanel`:

```tsx
expanded={panelExpanded[tc.id] ?? (i === lastPreparingIndex)}
onToggle={() => togglePanel(tc.id, i === lastPreparingIndex)}
```

When `tc.id` is `undefined`, `panelExpanded[undefined]` is read as the string key `"undefined"`. If two preparing tools happen to both have undefined `id` (rare but possible — e.g. backend-replay edge in the same neighborhood the dedup `useMemo` exists to mitigate), they share the same toggle state. Likewise `togglePanel(undefined, ...)` mutates the `"undefined"` slot for both.

This is a **pre-existing** pattern from 075.6 Plan 02 — not introduced by 075.8 — but it intersects with the new `tc-active-wrap` glow and is worth tightening now while the file is open. Strict TS would also flag this if `noUncheckedIndexedAccess` were on.

**Fix:** Fall back to the same composite key the dedup loop already builds, so the toggle state cannot collide:

```tsx
const panelKey = tc.id ?? `${tc.name}-${tc.startedAt ?? ''}-${i}`
// ...
expanded={panelExpanded[panelKey] ?? (i === lastPreparingIndex)}
onToggle={() => togglePanel(panelKey, i === lastPreparingIndex)}
```

Or, if every preparing tool is now guaranteed to have an id via 075.2 Plan 01 Task 2 (the replay-idempotency guard), tighten the type at the boundary:

```tsx
if (!tc.id) return null  // or assert in dev
```

## Info

### IN-01: `StatusPill` should announce status changes for screen-readers

**File:** `frontend/src/components/chat/StatusPill.tsx:69-89`
**Issue:** The pill conveys important state transitions (running → done / failed / interrupted) visually but has no `aria-live` region. Screen-reader users get no announcement when a long-running tool flips to `done · 11.3s` or `failed · 800ms`. The header in `RunCard.tsx:177-183` already has `aria-live="polite"` on the elapsed timer; the pill should mirror that pattern for the terminal state transition.

**Fix:** Add `aria-live="polite"` (and optionally `role="status"`) on the outer `<span>`:

```tsx
<span
  data-testid="status-pill"
  data-status={status}
  role="status"
  aria-live="polite"
  className={cn(...)}
>
```

Note: don't make this `assertive` — that would barge in over user activity. `polite` is the right priority for tool-status changes.

### IN-03: `formatDuration` duplicated across `StatusPill.tsx`, `ToolCallPanel.tsx`, and `ExecuteCodeBody.tsx`

**File:** `frontend/src/components/chat/StatusPill.tsx:33-36`, `frontend/src/components/chat/ToolCallPanel.tsx:58-61`, `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx:31-34`
**Issue:** Three identical implementations of the same helper:

```ts
function formatDuration(ms: number): string {
  if (ms < 1000) return `${ms}ms`
  return `${(ms / 1000).toFixed(1)}s`
}
```

This is dead-code-equivalent — any future change to the format (e.g. switch to `1.23s` precision, add minute rollover for long runs) has to be made in three places.

**Fix:** Hoist into `@/lib/format` or `@/lib/toolMeta` (where `toolLabel`/`toolSummary` already live) and import everywhere. Low-risk single-line refactor.

### IN-04: `useEffect` deps in `TerminalOutput` use `lines.length` instead of `lines` — intentional but fragile

**File:** `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx:43-50`
**Issue:** The effect scrolls to bottom when the line count grows:

```tsx
useEffect(() => {
  ...
}, [lines.length])
```

This is a deliberate optimization (rerun only when length changes, not on every prop identity change), and the pre-075.8 file already used this pattern. It works under the current assumption that `lines` is append-only. If a future code path ever **mutates an existing line's content** without adding a new line (e.g. updating a partial stdout chunk in place), the autoscroll won't fire. Worth a `// length-only by design` comment so the next reader doesn't "fix" it by switching to `[lines]`.

**Fix:** Add a one-line rationale comment:

```tsx
useEffect(() => {
  const el = containerRef.current
  if (!el) return
  const isNearBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 24
  if (isNearBottom) {
    el.scrollTop = el.scrollHeight
  }
  // Intentional: depend on length, not identity — autoscroll fires only
  // when a NEW line is appended (the only producer today). Switch to
  // [lines] if a future SSE path mutates existing lines in place.
}, [lines.length])
```

### IN-05: `useMemo` for `deduplicatedToolCalls` recomputes on every parent render — but downstream `displayItems` does not

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:307-323` (memo) vs `341-344` (non-memo)
**Issue:** `deduplicatedToolCalls` is memoized on `[toolCalls]`, but the downstream `displayItems` array (lines 341-344) — which interleaves `deduplicatedToolCalls` with `activatedSkills`, maps to typed records, then `sort()`s — is **not** memoized. Since `ToolCallPanel` re-renders any time `panelExpanded` or `stepsCollapsed` changes (both internal state), `displayItems` rebuilds + re-sorts on every keystroke-equivalent state change. With realistic tool counts (≤20) this is invisible, but the work is unnecessary.

**Fix:** Wrap `displayItems` (and the derived `lastPreparingIndex` / `activeIndex` / `completedBeforeActive`) in `useMemo` keyed on `[deduplicatedToolCalls, activatedSkills]`. Low-priority — not a correctness issue, just consistency with the existing memo pattern in the same file.

### IN-06: `panelExpanded` Record grows unboundedly across the page lifetime — minor memory smell

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:365-367`
**Issue:** `panelExpanded` accumulates keys for every preparing tool the user has ever toggled on this `ToolCallPanel` instance. Since `ToolCallPanel` instances are per-message, this lives only as long as the message is mounted, which bounds the leak naturally. But the `togglePanel` updater never garbage-collects entries for tools that have transitioned past "preparing" — they linger in the Record. Cosmetic at realistic scales; mentioned only because the comment at L364 hints the lift was carefully considered.

**Fix:** None required. If a future phase wants to be tidy, prune the Record in a `useEffect` that diffs against `deduplicatedToolCalls.filter(t => t.status === 'preparing')`. Defer until measured.

## Notes (not findings)

A few patterns worth calling out as **correctly done** so future readers don't try to "fix" them:

- **`ShikiCode` `useEffect` with `mounted` flag** — correct guard against the React-18 "setState after unmount" warning during async work. The cleanup `() => { mounted = false }` is the canonical pattern.
- **`RunCard`'s pure-derivation `expanded`** — the design note at lines 56-69 documents the prior `wasStreamingRef` one-shot effect that was replaced. The current shape (`expanded = isStreamingNow || !hasTools || userExpanded`) is the safer model.
- **Active-tool glow `position: relative` + bottom shimmer `absolute`** — the shimmer at `ToolCallPanel.tsx:683-688` is positioned against `.tc-active-wrap`'s `position: relative` (index.css:275). Both render under the same `isToolActive` guard, so the positioning context is always present when needed. The wrapper's `padding-bottom: 4px` (index.css:278) leaves room for the 2px shimmer + 2px breathing room.
- **Lazy Shiki import + `<Suspense>` fallback in `ExecuteCodeBody`** — the fallback `<pre>` at line 275-277 mirrors the `ShikiCode` post-load `<pre>` text positions (same font-size, line-height, padding), so there's no visible layout shift when the highlighted HTML lands. Tested via `data-testid="shiki-code-fallback"` in `ShikiCode.tsx:88`.
- **`ToolCallPanel` body-only contract** — header / frame ownership lives in `RunCard.tsx`; the inline comments at L297-301 and L411-414 document this clearly. The `isPlanning` and `iterationCount` props remain in the `Props` interface as a no-op pass-through (RunCard still passes them) — dead receiver but kept intentionally to avoid an interface churn this phase.
