<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| builder filter → backend resolve/count | The builder sends a filter_expr AST + values; the backend validates fields against the whitelist and binds values as params (the server is the authz/validation boundary, not the client) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-05-01 | Tampering | client-composed filter_expr | mitigate | The client only assembles the AST; ALL field-whitelist validation + value binding happens server-side (validate_fields + the Fragment param binding from Plans 01/02). A hand-crafted client payload cannot inject SQL or filter on a non-whitelisted/`_`-prefixed field — the server rejects it (422) / binds it as a literal. The client is not a trust boundary. |
| T-114-05-02 | Information Disclosure | live count display | mitigate | The count reads from the count-only resolve endpoint which is caller-scoped own+global (Plan 02) — the client cannot count another user's docs; the displayed N is the caller's own resolved total. |
| T-114-05-03 | Tampering | relative-date preview readout | accept | The client-side resolved-window readout is PREVIEW-only and explicitly non-authoritative (the server derives the real window at resolve from its own clock, D-114-16) — a manipulated client readout cannot change which rows the server returns. Low risk by design. |
| T-114-05-SC | Tampering | npm/pip installs | accept | This plan installs NO packages (composes existing shadcn/lucide primitives). No supply-chain surface. |
</threat_model>
