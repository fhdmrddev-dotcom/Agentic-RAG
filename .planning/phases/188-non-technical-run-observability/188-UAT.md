# Phase 188 — UAT scoreboard

**This file is AUTHORED here and RUN by the operator gate (Plan 188-13).** Every row
below is `[pending]`. **No row is marked PASS by the plan that wrote it** — a board that
grades its own author is not evidence.

**Vocabulary — three values, and only three.** `PASS` · `⛔ + reason + blocking id` ·
`[pending]`. **Silent omission is not available.** A provider with no key, or one blocked
by a known defect, is recorded ⛔ with the reason and the blocking id — never dropped from
the table. A scoreboard that lists only what passed is not a scoreboard.

## Read this before reading any row — the three measured constraints

These were **measured** at `db086240` (188-RESEARCH.md § Open Question 1, ten-step code
trace) and re-confirmed against the live environment on 2026-08-05 by
`scripts/sc10_188_run_board.py --derive-only`. Every row below is authored on top of
them. Do not re-derive them; do not author a row that contradicts them.

1. **The per-request `model` does NOT reach a harness phase. The per-request `provider`
   DOES.** `wf_ctx.model = resolve_workflow_ctx_model(user_settings)` reads
   `user_settings.llm_model` — never `body.model` (`sub_agent_models.py:231-259`), and the
   cross-provider guard then returns `_SUB_AGENT_MODEL_DEFAULTS[active_provider]`.
   **⇒ This board measures the PROVIDER axis, not the model axis.** A passing row is
   evidence about a provider's SDK path inside the harness; it is *not* evidence about the
   id in the *Requested* column. Live proof, from the pre-flight: the `google` row requests
   `gemini-3.5-flash` and the predicted effective model is `gemini-3.6-flash` — the saved
   `llm_model`, not the requested id.

2. **`override_provider` fails SILENTLY when the target provider has no API key.** It
   returns the settings **unchanged** (`user_settings.py:957-967`), so a keyless row runs
   on the *previous* provider and looks exactly like a pass. Two defences, both wired into
   the driver: the key probe runs **before** any kickoff, and the **effective** provider is
   read back from the sub-agent `runs` rows afterwards. **A requested-vs-effective mismatch
   is ⛔ with its reason — never a pass.**

3. **`phase.config.model` beats everything** (`_effective_model = phase.config.model or
   ctx.model`, `phase_types.py:350-352`). A fixture that pins a per-phase model would
   guarantee a cross-provider mismatch on every row. The chosen fixture
   (`research_summarize`) was checked and pins none. **Corollary — OpenRouter is the one
   genuinely risky row:** `_SUB_AGENT_MODEL_DEFAULTS["openrouter"]` is `""` and openrouter
   is a `_FLEXIBLE_PROVIDER`, so the inferred-provider gate never fires and the saved
   `llm_model` passes through **unslashed** to the OpenRouter SDK — a predicted 404.

**Method.** Each row is driven with a **per-request `provider`** on
`POST /threads/{id}/messages` with `workflow_definition_id` set. **No global setting is
mutated** — the operator's environment is untouched and rows cannot contaminate each
other. Verdicts are read from the **database** (`workflow_runs` / `workflow_phases` /
`runs`), never from the UI.

**What each row asserts, and nothing more (D-188-25):** the run reaches a terminal state,
and the per-node readings the canvas would paint *at that terminal state* are correct
(`canvasReading` applied to each `workflow_phases.status`). **Not** emit quality, **not**
citation behaviour, **not** tool-call fidelity.

**Blocking-id vocabulary emitted by the driver:** `SC10-188-NOKEY` (no API key — the row
was NOT driven, because driving it would silently measure the previous provider) ·
`SC10-188-MISROUTE` (requested ≠ effective provider) · `SC10-188-NOEVIDENCE` (no sub-agent
`runs` row, so the effective provider is unreadable) · `SC10-188-RUN` (never reached
`completed`) · `SC10-188-PAINT` (a forbidden node reading at a terminal run) ·
`SC10-188-KICKOFF` (the backend refused the kickoff) · `SC10-188-NOTDRIVEN`.

**What "Node readings correct" means, precisely.** Mirror of the shipped
`frontend/src/lib/phaseState.ts` derivation applied to DB truth:
`pending→Not started` · `active→Running` · `completed→Done` · `failed→Failed` ·
`skipped→Skipped` · anything else → `Unknown`. At a **terminal** run only
`Done / Failed / Skipped / Not started` are legitimate. A `Running` reading means an
`active` row was stranded; an `Unknown` reading means a status this client does not
recognise. Either one fails the row — those are exactly the two things SPEC Req 3 forbids
the canvas to smooth over.

## 3. G-4 lived-experience rows — "I'd recognise failure here"

Carried from `188-VALIDATION.md § Manual-Only Verifications` and `188-CONTEXT.md § H`.
Chrome MCP drives these; a wire-format assertion or a single screenshot is **not**
sufficient (that is the documented UAT-gap pattern that cost the 075.x cascade).

### 12. Watch a real multi-phase run end to end, and refresh mid-run
source: VALIDATION M "G-4 lived-experience run watch" · CONTEXT §H #1, #3 · RUNVIZ-01/02/03
steps:
  1. With `visual_workflow_canvas` ON, launch a published multi-phase workflow from the Workflows page.
  2. Stay on the run surface and watch **at least 3 phase transitions** happen live.
  3. Mid-run — while a phase is `active` — **hard-refresh the page**.
  4. Let the run reach terminal, then open the deliverable.
observable: |
  No node's reading CHANGES across the refresh. A node that read Running before the
  refresh reads Running or a later state after it — never an earlier one, never Done for a
  step that had not finished, never Unknown. The panel and the canvas agree about every
  phase at every moment (§H #1). If the two disagree even once, the row fails.
result: [pending]

### 13. The skip_to_phase jump — a step that never ran must read "Not started"
source: RESEARCH Pitfall 1 (the REACHABLE fail-open) · CONTEXT §H #2 · SPEC Req 3/4
steps: |
  ⚠ No seeded fixture exists — measured: **0** rows in `workflow_definitions` contain
  `skip_to_phase`. Author one: a 3-step workflow where step 1 carries a validator with
  `on_failure: "skip_to_phase:<step-3-slug>"`, and make step 1's validator FAIL so the
  jump actually fires. Publish it, launch it, and watch step 2 — the jumped-over step.
observable: |
  Step 2 reads **Not started** while the run is live AND after a refresh. It must NEVER
  read Done. This is the fail-open `finalizeAllPhasesForThread` used to produce — it swept
  every `pending` phase to `done` on a successful `run_completed`, so a skipped-over step
  painted as Complete live and reverted to Not started on reload. It is simultaneously
  §H #2 and §H #3, and it is the highest-value observation on this board.
result: [pending]

### 14. Colour off — all seven readings separate by shape alone
source: VALIDATION M "Colour off legibility" · Sketch 153's explicit acceptance test · RUNVIZ-01
steps: |
  Get all seven readings on screen (Not started · Running · Done · Failed · Skipped ·
  Waits for you · Unknown) — a live run covers most; the rest via the canvas fixtures.
  DevTools → Rendering → **Emulate vision deficiency: achromatopsia**.
observable: |
  With colour fully removed, a person can still say which reading each node carries,
  **by shape alone**. Any two readings that become indistinguishable fail the row. A
  machine can assert the arc geometry differs; only a person can confirm it READS.
result: [pending]

### 15. The 🕐 Tomorrow moment — navigate away, come back, find the run and its file
source: VALIDATION M "The 🕐 Tomorrow moment" · D-188-13 · CONTEXT §H #6 · RUNVIZ-03
steps:
  1. Launch a workflow. Confirm you land on the **run surface** and NOT in the chat message list (§H #5) — no composer anywhere on it.
  2. Navigate away to Chat. (Simulate "tomorrow": a full reload is fine — the point is that nothing is live.)
  3. Find the run's thread in the chat history and follow **"Open the run"**.
observable: |
  The run re-opens with its full phase spine, its final state and its deliverable — all
  rendered with **no live stream**. Any elapsed number states its anchor; a run whose
  `claimed_at` is null shows **no** clock rather than a "since queued" lie (§H #7).
result: [pending]

### 16. The `.docx` deliverable is download-only, and says so
