## Read this before reading any row — the three measured constraints

These were **measured** at `db086240` (188-RESEARCH.md § Open Question 1, ten-step code
trace) and re-confirmed against the live environment on 2026-08-05 by
`scripts/sc10_188_run_board.py --derive-only`. Every row below is authored on top of
them. Do not re-derive them; do not author a row that contradicts them.

1. **The per-request `model` does NOT reach a harness phase. The per-request `provider`
   DOES.** `wf_ctx.model = resolve_workflow_ctx_model(user_settings)` reads
   `user_settings.llm_model` — never `body.model` (`sub_agent_models.py:231-259`), and the
   cross-provider guard then returns `_SUB_AGENT_MODEL_DEFAULTS[active_provider]`.
   **⇒ This board measures the PROVIDER axis, not the model axis.** A passing row is
   evidence about a provider's SDK path inside the harness; it is *not* evidence about the
   id in the *Requested* column. Live proof, from the pre-flight: the `google` row requests
   `gemini-3.5-flash` and the predicted effective model is `gemini-3.6-flash` — the saved
   `llm_model`, not the requested id.

2. **`override_provider` fails SILENTLY when the target provider has no API key.** It
   returns the settings **unchanged** (`user_settings.py:957-967`), so a keyless row runs
   on the *previous* provider and looks exactly like a pass. Two defences, both wired into
   the driver: the key probe runs **before** any kickoff, and the **effective** provider is
   read back from the sub-agent `runs` rows afterwards. **A requested-vs-effective mismatch
   is ⛔ with its reason — never a pass.**

3. **`phase.config.model` beats everything** (`_effective_model = phase.config.model or
   ctx.model`, `phase_types.py:350-352`). A fixture that pins a per-phase model would
   guarantee a cross-provider mismatch on every row. The chosen fixture
   (`research_summarize`) was checked and pins none. **Corollary — OpenRouter is the one
   genuinely risky row:** `_SUB_AGENT_MODEL_DEFAULTS["openrouter"]` is `""` and openrouter
   is a `_FLEXIBLE_PROVIDER`, so the inferred-provider gate never fires and the saved
   `llm_model` passes through **unslashed** to the OpenRouter SDK — a predicted 404.

**Method.** Each row is driven with a **per-request `provider`** on
`POST /threads/{id}/messages` with `workflow_definition_id` set. **No global setting is
mutated** — the operator's environment is untouched and rows cannot contaminate each
other. Verdicts are read from the **database** (`workflow_runs` / `workflow_phases` /
`runs`), never from the UI.

**What each row asserts, and nothing more (D-188-25):** the run reaches a terminal state,
and the per-node readings the canvas would paint *at that terminal state* are correct
(`canvasReading` applied to each `workflow_phases.status`). **Not** emit quality, **not**
citation behaviour, **not** tool-call fidelity.

## ⚠ F7 · SC#1'S GOVERNANCE HALF NEVER REACHED THE RUN SURFACE — fixed 2026-08-05 (`c50e93f4`)

**Found by checking the phase against its own success criteria, not by any row.** SC#1 reads:
*"each node shows live state (pending / active / passed / failed / skipped / waiting-for-you),
**and its grounded-cited vs open governance state**"*. Before this fix, `grep -c grounded` over
this board and over `188-VALIDATION.md` both returned **0** — no row covered the second half,
and it did not work.

### The defect

`toCanvas` resolves `grounded` through `isGrounded(phase, kbTools)`, and `canvasModel.ts:360`
defaults an omitted `kbTools` to the frozen empty `NO_KB_TOOLS`. `WorkflowRunPage` rendered
`<WorkflowCanvas>` with **no `kbTools` prop at all**, so the intersection
`available_tools ∩ kb_tools` was taken against the empty set and the **`detected`** cause could
never resolve.

The quiet shape of it, and why nobody noticed: `already-set` (an explicit `citation_policy`) and
`escalated` (the author's own flag) still resolved. So governance LOOKED correct on workflows
that declare it explicitly, while every step grounded merely by **reading the knowledge base**
painted as ungoverned. Measured: **all 8 published KB-reading fixtures in this org are
detected-only** — none carries a `citation_policy` or an escalation. The failure covered the
entire realistic population.

### Falsified live BEFORE any edit — one workflow, both surfaces

`doc_qa_scoped_098uat`, node `draft` (`available_tools: ["search_documents"]`, and
`search_documents ∈ KB_TOOLS` at `grounding.py:797`):

| Surface | `data-grounded` |
|---|---|
| Builder canvas (passes `kbTools`, `WorkflowBuilderPage.tsx:1568`) | **`"true"`** — seal renders |
| Run surface (passed nothing) | **absent** — no seal |

`useGroundingBundle`'s own docblock names this exact consumer: the kb-tool list is used *"for one
thing: the local `available_tools ∩ kb_tools` intersection that moves the dial, the
strike-through and **the canvas seal**"*. This surface never asked for it.

### The fix, and why it is the Builder's rule verbatim

`useGroundingBundle(true)` + `bundle.kind === "ready" || bundle.kind === "unavailable" ?
bundle.kbTools : []` — copied from `WorkflowBuilderPage.tsx:904-907` **for its stated reason**:
the kb-tool list is served OUTSIDE every registry read, so it survives a degraded bundle, and
carrying it only on `ready` would let an unrelated folder-registry blip silently **un-mark a
locked step**. Absent it is empty, which marks nothing — the safe direction, because the run-time
gate is server-side and unconditional either way. R11 holds: the page READS the server list and
authors none of it, fenced by a source check with a positive control.

**RED first** — both cases observed failing (`expected '' to contain 'search_documents'`; the hook
never called). Count gate re-pinned 85 → 87. **Verified live after**: the same node now reads
`data-grounded="true"` on the run surface, the **⛨ corner seal** renders at the card's top-right,
and the two non-KB steps correctly carry none.
