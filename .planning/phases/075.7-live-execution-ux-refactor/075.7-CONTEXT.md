<decisions>
## Implementation Decisions

### Plan Shape & Extraction Order
- **D-01:** **3 plans, capability-grouped.** P01 = Mechanical extraction (9 tool-bodies + `ExecuteCodeBody` rename, zero visual change). P02 = RunCard wrapper (bordered container, sticky header, brand-pulse avatar, timer, counter, narration interleave, active-state glow). P03 = Focus Mode + 4-axis UAT (wire `summarize()` into collapsed past-tool render, auto-collapse on terminal+tools>0, VALIDATION.md, Chrome MCP scenarios, Playwright specs). Each plan is one rollback boundary — P01 alone gives a refactored ToolCallPanel with zero visual change; P02 alone gives the visual frame; P03 alone gives the felt experience.
- **D-02:** **P01 ships as a single atomic commit.** Create `tool-bodies/` directory + extract all 9 `*Result` components verbatim into `*Body.tsx` files + rename `ExecuteCodeBlock` → `ExecuteCodeBody` (move into `tool-bodies/`) + delete `ExecuteCodeBlock.tsx` + update `ToolCallPanel.tsx` imports — all in one commit. Justification: `ExecuteCodeBlock.tsx` is referenced ONLY from `ToolCallPanel.tsx:12` (verified via grep); blast radius is one file. Single atomic commit means git log shows the extraction as one event; rollback boundary is clean. Matches Phase 071 Plan 02 precedent for atomic refactor commits.
- **D-03:** **Each `*Body.tsx` exports default component + named `summarize(tc: ToolCall): string`.** Plan 03 imports a per-name registry: `{ ls: LsBody.summarize, tree: TreeBody.summarize, ... }`. The Body that knows its result shape owns its derivation. New tool added → add one file, register one entry. Matches sketch findings `tool-call-panel.md` D2 verbatim.
- **D-04:** **P01 LOC bar = ≥250 LOC reduction in `ToolCallPanel.tsx`** (matches SPEC.md Requirement 2 acceptance criterion). Target: 957 → ≤707 LOC. Plan-checker enforces this gate.

### Collapse State Ownership & Persistence
- **D-05:** **`expanded` state lives inside `RunCard`**, derived from `runStatus` via `useState` initializer: default `true` if streaming/queued, default `false` if terminal AND `tool_calls.length > 0` (auto-collapse), N/A if no tool calls (no RunCard renders). RunCard owns the toggle; click on collapsed row sets `expanded=true`. Matches today's ToolCallPanel `useState` pattern.
- **D-06:** **No persistence.** Collapse state resets on every mount. Default rule applies on every render. No localStorage, no sessionStorage, no Map<run_id, bool> in StreamsProvider. Justification: matches SPEC contract; avoids unbounded storage growth across thread history; consistent with today's `useState(true)` reset behavior.
- **D-07:** **Instant fold + existing `fadeSlideUp` (0.3s) on the summary row.** No new keyframes (SPEC out-of-scope constraint). Run finishes → inner body unmounts instantly → summary row appears with the existing motion token. Sketch findings D5 explicitly describes the fold as a single-row swap, not a height transition.
- **D-08:** **Header click is a no-op while `runStatus === 'streaming'`.** Auto-collapse only fires on terminal status. User cannot fold an active run mid-stream. Matches sketch findings live-run-container.md D5 + tool-call-panel.md D7 ('Default state when active = open'). Chevron may be hidden during streaming for visual clarity.

### MessageItem Disposition
- **D-09:** **MessageItem stays the consumer; mounts `<RunCard>` for tool-bearing turns.** For assistant turns where `tool_calls.length > 0`, MessageItem renders `<RunCard message={...} isStreaming={...} />`. For turns with no tool calls (pure conversational replies), MessageItem renders the existing plain-text bubble path unchanged — NO RunCard, no border. The final answer text (MarkdownRenderer of `message.content`), ConfidenceBadge, CitationList, SuggestionPills, Resume button, MessageFeedback all stay inside MessageItem and render BELOW the RunCard. Matches sketch findings D6 verbatim: "run-card is the work; assistant message is the answer."
- **D-10:** **Props shape: whole-message + minimal extras.** `<RunCard message={message} isStreaming={isStreaming} />`. RunCard destructures what it needs (`message.tool_calls`, `message.runStatus`, `message.activatedSkills`, `message.subAgent`, `message.isPlanning`, `message.iterationCount`). Preserves the 075.4-04 `React.memo` benefit — message prop identity changes only when the message actually changed. RunCard must also be `memo()`-wrapped.
- **D-11:** **Sticky header uses page-body scroll**, NOT an inner ScrollArea. `position: sticky; top: 0` against the document scroll (MessageList is the existing scroll container). No new ScrollArea introduced. Matches sketch CSS verbatim. Standard CSS sticky behavior: when the next RunCard's header reaches `top: 0`, it pushes the previous one out. Single-column conversation reading flow preserved.
- **D-12:** **`stickyLabelRef` at MessageItem:105 STAYS in MessageItem.** The sticky BOTTOM indicator at MessageList foot (the BUG-260514-03 + B-260519-07 fix from Phase 075.1 Plan 03) is conceptually a per-message-streaming indicator at MessageList foot, NOT part of RunCard's visual frame. RunCard owns the TOP sticky header; MessageItem keeps the BOTTOM sticky indicator. Two independent sticky surfaces, two independent owners. Preserves the existing 075.1 + 075.4 bug fixes verbatim (SPEC constraint: "Phase 075.6 surface preservations").

### Vitest-Blocked Test Strategy

<specifics>
## Specific Ideas

- **Two-sticky pattern (D-12)** — RunCard owns the TOP sticky header at the run-card frame; MessageItem keeps the BOTTOM sticky indicator at the MessageList foot. These are independent surfaces with independent reset semantics. Implementation note: RunCard's `position: sticky; top: 0` and MessageItem's bottom-indicator positioning don't interact — they live at opposite ends of the message and don't compete for the same screen anchor.
- **Per-Body `summarize()` registry shape (D-03)** — Plan 01 lays the named-export plumbing; Plan 03 wires the registry into the `tc.done` collapsed past-tool render. Registry pattern (concrete):
  ```ts
  // tool-bodies/index.ts
  import { LsBody, summarize as lsSummarize } from "./LsBody"
  // ... 8 more
  export const TOOL_BODIES = { ls: LsBody, tree: TreeBody, ... } as const
  export const TOOL_SUMMARIES = { ls: lsSummarize, tree: treeSummarize, ... } as const
  ```
- **Active vs completed visual hierarchy (D-08)** — sketch findings D3 + D5: active step gets full editor open + glow border + bottom shimmer; completed steps collapse to a one-line `→ {summary}` result row (NOT args). The collapsed-summary row is what's net-new visually; the active-step rendering already mostly exists in today's ToolCallPanel.
- **Anthropic terminal-frame preservation** — `anthropic-end-of-cycle-shows-actions-not-summary` (deferred 3x) needs the current Anthropic terminal block-ordering visible so it can be re-litigated later. Plan 02's RunCard wrapping must not auto-collapse Anthropic runs in a way that hides whatever's currently visible at end-of-cycle — D-08 + D-06 together mean Anthropic runs collapse like every other provider, but the expand-on-click flow restores full visibility.

</specifics>
