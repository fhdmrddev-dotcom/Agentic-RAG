# Phase 075.7: Live-Execution UX Refactor (Run-Card + Tool-Call Panel) — Specification

**Created:** 2026-05-24
**Ambiguity score:** 0.20 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

Migrate the live-execution chat surface to the validated sketch design by (a) extracting a new `<RunCard>` wrapper component that visually brackets each assistant turn with tool calls, (b) splitting all 9 inline tool-result components out of the 957-LOC `ToolCallPanel.tsx` into their own per-tool files, (c) replacing `ExecuteCodeBlock.tsx` with a new `ExecuteCodeBody.tsx`, (d) rendering a result-summary one-liner on collapsed past tool cards, (e) making the run-card header sticky during scroll, and (f) auto-collapsing the run-card to a one-line summary on completion when tool calls were used.

## Background

The live-execution surface is the highest-traffic UX in the product and the most-touched code path. Hot-file ledger evidence (CLAUDE.md):

- `frontend/src/components/chat/ToolCallPanel.tsx` — 5+ phases of patches (067 / 067.5 / 075 / 075.4 / 075.6), now **957 LOC with all 9 tool-result components inline** (`LsResult`, `TreeResult`, `GrepResult`, `GlobResult`, `ReadDocumentResult`, `SearchDocumentsResult`, `QueryDocumentsResult`, `WebSearchResult`, `GenericResult`) plus `ToolArgsBlock`, `ToolResultBlock`, `SubAgentBlock`, `SkillRow` as nested components.
- `frontend/src/components/chat/MessageItem.tsx` — 307 LOC; today the assistant turn IS the conceptual run-card (wraps brand-pulse avatar + WorkingBadge + ToolCallPanel + final answer + Resume + suggestions) but it has no explicit bordered container or sticky header.
- `frontend/src/providers/StreamsProvider.tsx` — 1551 LOC. Phase 068 (StreamsProvider Context Lift) **has already shipped** despite the ROADMAP entry still reading `[ ]` (the file exists and `useMessages.ts` is now a 111-LOC reader, so the lift is complete).
- `frontend/src/components/chat/ExecuteCodeBlock.tsx` — 221 LOC, separate today.
- `frontend/src/components/chat/OutputFileCard.tsx` — 145 LOC, file preview cards already factored.
- `frontend/src/components/chat/ToolArgsLivePanel.tsx` — 90 LOC, 075.6 live code stream.
- `frontend/src/components/chat/WorkingBadge.tsx` — 56 LOC, pinned "✦ Working" badge.

**G-1 (Phase chain cap) and G-5 (Refactor between feature waves)** both fire — 7 prior 075.x phases (075, 075.1, 075.2, 075.3, 075.4, 075.5, 075.6) have touched these hot files. **G-2 (Sketch before plan for UX)** has been satisfied by the sketch session on 2026-05-24 (commits `10ce3a3` / `f18df4c` / `7fbe609` / `2ea3d7e`) which packaged validated visual decisions into `Skill("sketch-findings-agentic-rag")` with two reference files: `live-run-container.md` (decisions D1-D7 for the run-card frame) and `tool-call-panel.md` (decisions D1-D7 for the tool-call panel shape).

What is **missing today vs. the locked sketch findings**:
1. The result-summary one-liner (`→ yoy_q3 = 30.87%`) on collapsed past tool cards — the signature Focus Mode insight, not present today.
2. Per-tool inner-body component split — all 9 result shapes still inline in one 957-LOC file.
3. Sticky run-card header — header currently scrolls off when the body is tall.
4. Auto-collapse-on-done — `expanded` defaults to `true`; past completed runs sit fully visible by default.
5. Editor-inset polish on `execute_code` (gutter + syntax tokens + labeled STDOUT/STDERR regions) — best-effort, not a verifier gate.
6. Explicit run-card bordered container around the assistant turn — visually the work and the answer share the same surface today.

This phase IS the refactor G-1 has been demanding. After it ships, the hot-file ledger flips from "fires — refactor due" to "satisfied" on the four affected rows.

## Requirements

1. **RunCard wrapper component**: A new bordered container wraps each assistant turn that includes tool calls, with sticky header carrying timer + tool counter + bot avatar + status pill.
   - Current: `MessageItem.tsx` renders bot avatar + WorkingBadge + ToolCallPanel + answer + Resume + suggestions inline with no enclosing bordered container.
   - Target: A new `frontend/src/components/chat/RunCard.tsx` component (~150-250 LOC) wraps the work+answer for assistant turns where `tool_calls.length > 0`. Style follows `Skill("sketch-findings-agentic-rag")` reference `live-run-container.md` D1-D2: `border-radius: var(--radius-lg)`, gradient background, active-state glow border, sticky header with `position: sticky; top: 0`.
   - Acceptance: For an assistant turn with at least one tool call, the DOM contains a `<div data-testid="run-card">` element that wraps the tool-call panel, narration interleavings, and final answer. `getComputedStyle(header).position === 'sticky'`.

2. **Per-tool body component split**: All 9 inline `*Result` components are extracted from `ToolCallPanel.tsx` into their own files.
   - Current: `LsResult`, `TreeResult`, `GrepResult`, `GlobResult`, `ReadDocumentResult`, `SearchDocumentsResult`, `QueryDocumentsResult`, `WebSearchResult`, `GenericResult` are all inline functions in the 957-LOC `ToolCallPanel.tsx`. `ToolCallPanel` calls `renderResult(name, parsed, rawResult)` which switches on tool name.
   - Target: A new directory `frontend/src/components/chat/tool-bodies/` contains 9 files — `LsBody.tsx`, `TreeBody.tsx`, `GrepBody.tsx`, `GlobBody.tsx`, `ReadDocumentBody.tsx`, `SearchDocumentsBody.tsx`, `QueryDocumentsBody.tsx`, `WebSearchBody.tsx`, `GenericBody.tsx`. `ToolCallPanel.tsx` imports them and uses a per-name dispatch (object literal or switch). Each body component owns its own props interface and its own `resultSummary()` derivation.
   - Acceptance: `ls frontend/src/components/chat/tool-bodies/*Body.tsx | wc -l` returns 9 (plus `ExecuteCodeBody.tsx` from Requirement 3 = 10 total). `grep -n "function LsResult\|function TreeResult\|function GrepResult\|function GlobResult\|function ReadDocumentResult\|function SearchDocumentsResult\|function QueryDocumentsResult\|function WebSearchResult\|function GenericResult" frontend/src/components/chat/ToolCallPanel.tsx` returns 0 matches. `ToolCallPanel.tsx` LOC reduced by ≥250.

3. **ExecuteCodeBody replaces ExecuteCodeBlock**: The existing `ExecuteCodeBlock.tsx` is replaced by a new `ExecuteCodeBody.tsx` co-located with the other tool-body components.
   - Current: `frontend/src/components/chat/ExecuteCodeBlock.tsx` (221 LOC) renders the code-execution surface for `execute_code` tool calls. Imported by `ToolCallPanel.tsx` at line 12.
   - Target: A new `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx` replaces `ExecuteCodeBlock.tsx` (functional behavior ported verbatim at minimum). All callers updated; old file deleted. Editor-inset visual polish (line gutter, syntax tokens, labeled STDOUT/STDERR regions) is a **best-effort target inside Plan 02, NOT a verifier gate** — the structural file-rename + caller-migration IS gated; visual parity with sketch 002-C is best-effort.
   - Acceptance: `frontend/src/components/chat/tool-bodies/ExecuteCodeBody.tsx` exists. `frontend/src/components/chat/ExecuteCodeBlock.tsx` does NOT exist. `grep -rn "ExecuteCodeBlock" frontend/src/` returns 0 matches. All existing `execute_code` rendering behavior (code, stdout, file outputs via `OutputFileCard`, sticky bottom indicator) continues to work — Chrome MCP UAT verifies an end-to-end `execute_code` run renders identically (or better, if visual polish landed).

4. **Result-summary one-liner on collapsed past tools**: Completed tool cards collapsed within an active run show a one-line summary of their result.
   - Current: When a tool call is in the past-completed state and the panel is collapsed (or when the step-list-collapse-at-3+ rule fires), the tool's head shows name + args + status pill but no derived summary of what the tool produced. `ToolCallPanel.tsx` has a `resultSummary(name, parsed)` function at line 146 that today is used only for the active-tool head label.
   - Target: Each per-tool body component (Requirement 2 + 3) exports its own `summarize(tc: ToolCall): string` derivation. `ToolCallPanel.tsx`'s collapsed past-tool rendering calls the body's `summarize` and renders the result inline below the tool head as `→ {summary}` in muted/monospace text. Examples:
     - `execute_code` → last STDOUT line or `[chart saved to X]` if a file was produced
     - `search_documents` → `top match: {top_hit.title} ({top_hit.score})` for 1+ result; `0 results` for empty
     - `read_document` → `{N} chars · {first_50_chars}…`
     - `ls`/`tree`/`grep`/`glob` → existing logic from the current `resultSummary` extended for per-body ownership
   - Acceptance: For a completed tool call rendered inside an active run, the DOM contains a `<div data-testid="tool-result-summary">` element with text starting with `→`. Test fixture: a 3-tool run (`search_documents` + `execute_code` + `read_document`) renders 3 summary lines after the active step starts, each beginning with `→` and containing the expected derived text.

5. **Sticky run-card header**: The RunCard header (timer + counter + bot avatar + status) stays visible when the user scrolls within a tall run.
   - Current: No bordered container exists; the ToolCallPanel header scrolls with the document.
   - Target: RunCard header has `position: sticky; top: 0` (with appropriate z-index and backdrop-blur per `live-run-container.md` D2 / sketch CSS) so during a 30+ second run with 4+ tool cards, the header carrying timer + counter + bot avatar stays anchored at the top of the visible run-card area.
   - Acceptance: Vitest or Playwright test: render a RunCard with 5 tool cards (forced via fixture data so the body overflows the viewport). After scrolling the page by `body.scrollHeight / 2`, the RunCard header's `getBoundingClientRect().top` ≥ 0 and the header element is still in the visible viewport.

6. **Auto-collapse on completion when tool calls were used**: After a run reaches a terminal state with `tool_calls.length > 0`, the RunCard folds to a one-line summary; click to expand.
   - Current: `ToolCallPanel.tsx` has `const [expanded, setExpanded] = useState(true)` — past completed runs stay expanded indefinitely.
   - Target: When `message.runStatus ∈ {completed, cancelled, failed, timed_out}` AND `message.tool_calls.length > 0`, the RunCard renders ONLY a one-line summary row by default: `[bot icon] Run · {N} tool calls · ✓ {status} · {total_duration} ▸`. Click on the row expands to show the full run history. For runs where `tool_calls.length === 0` (pure conversational reply), no RunCard renders — assistant turn shows as today with no border. For runs that are still active (`streaming`/`queued`), the RunCard renders fully expanded as today.
   - Acceptance: Fixture test — message with `runStatus='completed'` and 4 tool calls renders a `<div data-testid="run-card-collapsed">` element by default and does NOT render the per-tool body components. Clicking the collapsed row sets `expanded=true` and the per-tool bodies appear. Second fixture — message with `runStatus='completed'` and 0 tool calls renders neither RunCard nor collapsed row (renders as today's plain assistant message).

7. **4-axis UAT bandwidth**: The refactored surface passes the mandatory cross-provider × multi-tool × parallel-thread × long-message scenarios per CLAUDE.md SC#10.
   - Current: 075.7 has no UAT coverage yet (phase just inserted).
   - Target: VALIDATION.md (authored at `/gsd:plan-phase`) includes ≥1 row per axis: (a) cross-provider — at least 4 rows hitting OpenAI / Anthropic / Google / OpenRouter with the new RunCard surface; (b) multi-tool — at least 1 row exercising 2+ tools in one prompt (e.g., `search_documents` + `execute_code`); (c) parallel-thread — at least 1 row with Thread A streaming the new RunCard while Thread B accepts a new prompt (composer disabled prop must NOT cross threads — preserves 075.4-01 BUG-260523-01 fix); (d) long-message — at least 1 row with ≥50 prior messages OR a ≥5 KB user prompt.
   - Acceptance: VALIDATION.md exists at `.planning/phases/075.7-live-execution-ux-refactor/075.7-VALIDATION.md` with rows covering all 4 axes; orchestrator-driven Chrome MCP runs convert each row to GREEN (or document failure with re-open trigger). Hot-file ledger in CLAUDE.md flips G-5 status from "fires — refactor due" to "satisfied" on `ToolCallPanel.tsx`, `MessageItem.tsx`, `useMessages.ts`, `StreamsProvider.tsx` rows.

## Boundaries

**In scope:**
- New `<RunCard>` component wrapping assistant turns with `tool_calls.length > 0`
- Extraction of all 9 inline `*Result` components into `frontend/src/components/chat/tool-bodies/`
- New `ExecuteCodeBody.tsx` replacing `ExecuteCodeBlock.tsx` (file/component replacement; visual polish best-effort)
- Result-summary one-liner on collapsed past tool cards
- Sticky RunCard header
- Auto-collapse-on-completion with one-line summary (only when tool calls were used)
- VALIDATION.md authored with 4-axis UAT row coverage
- Hot-file ledger update in CLAUDE.md post-merge (4 rows flip from "fires" → "satisfied")
- Test coverage: Vitest unit tests on each new component; Playwright (or Chrome MCP) scenario tests for the 4-axis UAT

**Out of scope:**
- **Cross-thread "live somewhere else" UX** — Thread A streaming while user navigates to Thread B. Sidebar pulse polish, dedicated "live somewhere else" affordance. Reason: explicitly excluded from sketch session as out-of-scope; deferred to a future phase (post-075.7, possibly v2.7 or own decimal). The composer-per-thread isolation from 075.4-01 is preserved as a regression invariant.
- **Mobile / narrow-viewport pass** — sketches built at desktop scale (~780px column). Reason: RunCard + editor-inset need a dedicated narrow-viewport sketch + plan pass; out-of-scope here so this phase doesn't expand into mobile.
- **Stress-test sketch for deliberately-borked runs** — synthetic 22-iteration loops, Gemini thought_signature artifacts, OpenRouter duplicate outputs. Reason: UAT covers normal cases per CLAUDE.md SC#10; failure-mode visual stress-testing is a follow-up exercise.
- **Editor-inset visual polish (gutter, syntax tokens, labeled STDOUT/STDERR) as a verifier gate** — explicitly de-gated in Round 3. Reason: Plan 02 ships the file rename + behavior port; visual polish ships as best-effort. A future polish bundle phase can close any visual gaps.
- **Backend / SSE event vocabulary changes** — no new SSE event fields, no provider adapter changes, no `tool_summary` field on the wire. Reason: client-side `resultSummary` derivation is the locked path (Round 2). Backend stays untouched.
- **New animation keyframes** — existing motion tokens (`fadeSlideUp`, `brandPulse`, `progressShimmer`, `dotBounce`, `toolSlideIn`, `checkPop`) are reused as-is. Reason: motion language is already locked in the brand; adding new keyframes invites style drift.
- **WorkingBadge redesign** — pinned "✦ Working" badge during silent planning gap survives as today. Reason: works correctly; not in sketch scope.
