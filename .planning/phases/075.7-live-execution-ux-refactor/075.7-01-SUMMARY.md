### Registry (`tool-bodies/index.ts`)

```ts
export const TOOL_BODIES = {
  ls, tree, grep, glob, read_document, search_documents,
  query_documents, web_search, execute_code,
} as const

export const TOOL_SUMMARIES: Record<string, (tc: ToolCall) => string> = { ...same 9 keys... }

export function summarizeToolCall(tc: ToolCall): string {
  const fn = TOOL_SUMMARIES[tc.name]
  return fn ? fn(tc) : genericSummarize(tc)
}
```

## Deviations from plan

### None functional. Below are author-discretion choices (D-03 discretion clauses) documented for transparency:

**1. Inline if/else if chain in ToolResultBlock (not `<TOOL_BODIES[tc.name] tc={tc} />`)**

The plan's `<interfaces>` block illustrated two possible dispatch shapes (verbose if/else vs. uniform `<Body tc={tc} />`). I chose the if/else chain because the per-Body prop shapes ARE NOT uniform (`{ parsed }` vs. `{ result }` vs. would-need-`{ tc }`-rewrites), and the explicit branching preserves the exact pre-refactor parsed-vs-rawResult conditionals from `renderResult`. Avoids per-Body prop-shape rewrites that would balloon the atomic commit's surface area.

**2. WebSearchBody.summarize() with `_tc` + eslint-disable**

D-03 contract requires `(tc: ToolCall) => string` signature for every Body. WebSearch result is opaque markdown today; the prior `resultSummary` returned literal `"View search results"`. Preserved that literal exactly; suppressed the unused-var lint locally rather than re-shaping the registry signature.

**3. Comment-only edits in 6 sibling files**

Plan Step 5 said "DO NOT touch MessageItem.tsx in this plan" — but the R-3 acceptance gate (`grep -rn ExecuteCodeBlock frontend/src/` returns 0) forced comment-only updates in 6 files (including MessageItem.tsx L281+288). These are comment-only no-op edits — zero behavioral change. Logged as deviation here for transparency; no functional impact.
