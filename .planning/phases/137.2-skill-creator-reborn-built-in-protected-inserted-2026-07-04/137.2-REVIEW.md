## Warnings

### WR-01: DELETE and toggle-global against the built-in are unverified, and DELETE gives a false-success response

**File:** `backend/app/api/skills.py:351-375` (`delete_skill`), `backend/app/api/skills.py:414-444`
(`toggle_global`); test gap in `backend/tests/integration/test_skills.py:284-314`
(`TestSystemSkillProtection`)

**Issue:** The phase's own validation plan explicitly scoped this protection proof to three routes.
`137.2-VALIDATION.md` row T-137.2-01: *"Non-owner update/**delete**/toggle the built-in → 404/403"*,
and `137.2-01-PLAN.md` Task 3's action text: *"assert the route raises the ACTUAL status it uses
(**update_skill/delete_skill** → 404-via-empty-result; toggle_enabled → 403)"*. What shipped is only
two tests — `test_update_nonowner_system_skill_returns_404` and
`test_toggle_enabled_nonowner_system_skill_returns_403`. There is no test for `DELETE /skills/{id}`
against the system row, and none for `toggle-global` either.

This isn't just a missing assertion — `delete_skill` actually behaves differently from
`update_skill`/`toggle_enabled`/`toggle_global`, and the untested route is the one with the
different behavior:

```python
# Step 3: Delete the skill row (skill_files cascade via FK)
supabase.table("skills").delete().eq("id", skill_id).eq("user_id", current_user["id"]).execute()
```

Unlike `update_skill` (`if not result.data: raise HTTPException(404, ...)`), `delete_skill` never
inspects `result.data`. The `.eq("user_id", current_user["id"])` clause does correctly prevent an
actual delete of a row the caller doesn't own (including the built-in) — there is no real data-loss
path here — but the endpoint unconditionally returns `204 No Content` whether zero or one rows were
actually deleted. A caller attempting to delete the built-in (or any skill they don't own) gets a
response that looks like success. Because this exact route was never exercised by the new
`TestSystemSkillProtection` tests, a future refactor that accidentally weakens or drops the
`.eq("user_id", ...)` scoping on this one query (e.g., someone "simplifies" the delete call) would
ship a real deletion of the built-in with **no test anywhere catching it** — the class whose entire
purpose is proving "read-only/undeletable... with ZERO new authorization code" doesn't actually
touch the "undeletable" route.

**Fix:**
```python
# backend/tests/integration/test_skills.py — add to TestSystemSkillProtection
def test_delete_nonowner_system_skill_is_a_noop(self, client, auth_headers, mock_builder):
    """DELETE /skills/{id} on a row the user doesn't own must not delete anything."""
    # files-lookup (empty) + the delete call itself
    mock_builder.execute.side_effect = [_make_result([]), _make_result([])]
    response = client.delete(f"/skills/{SKILL_ID}", headers=auth_headers)
    assert response.status_code == 204  # documents TODAY's behavior — see fix below
    # Once delete_skill is fixed to check result.data, change this to assert 404.

def test_toggle_global_nonowner_system_skill_returns_403(self, client, auth_headers, mock_builder):
    mock_builder.execute.side_effect = [_make_result([])]
    response = client.patch(f"/skills/{SKILL_ID}/toggle-global", headers=auth_headers)
    assert response.status_code == 403
```
And close the honesty gap at the source so the test above has something meaningful to assert:
```python
# backend/app/api/skills.py — delete_skill, step 3
result = (
    supabase.table("skills").delete()
    .eq("id", skill_id).eq("user_id", current_user["id"]).execute()
)
if not result.data:
    raise HTTPException(status_code=404, detail="Skill not found")
```

### WR-02: The built-in's name can be silently re-shadowed by any future user; only one historical instance was fixed

**File:** `supabase/migrations/087_skill_creator_reborn.sql` (reintroduces the global skill named
`skill-creator`); resolution logic in `backend/app/services/tool_dispatcher.py:665-677`
(`_handle_load_skill`, unchanged by this phase); mitigation scope in
`.planning/phases/137.2-.../137.2-04-PLAN.md:16` (one-off rename)

**Issue:** `_handle_load_skill` resolves a skill by name with:
```python
.or_(f"user_id.eq.{ctx.current_user['id']},is_global.eq.true")
.eq("name", skill_name)
.eq("is_enabled", True)
.order("is_global")   # ascending: False (owned) sorts before True (global) on a name tie
```
and then takes `skill_row[0]`. On a name collision between a user's own private skill and a global
skill, **the owned row always wins**. Migration 087 (in this review's scope) reinstates a global,
`is_system=true` skill literally named `skill-creator`. The phase's own `137.2-RESEARCH.md` names
this exact risk as **Pitfall 3** ("Name collision shadows the built-in") and found one real instance
of it on the dev/test account. The chosen fix (`137.2-04` Task 3) is a **one-off manual `UPDATE`**
renaming that one account's private copy — explicitly scoped that way in the plan text: *"targets
one specific dev user's private row that exists on no other environment."*

That fix closes the one known instance but adds no structural guard. Nothing in `create_skill`
(`skills.py:163-195`), `_handle_save_skill` (`tool_dispatcher.py:724-782`), or `import_skill`
(`skills.py:198-307`) rejects or dedupes a name that collides with an existing `is_system=true`
skill, and `_handle_load_skill`'s tie-break is untouched. Any user — today or in the future, via the
Create-Skill dialog, the agent's own `save_skill` tool, or an imported ZIP whose `SKILL.md`
frontmatter happens to say `name: skill-creator` — will silently shadow the built-in for their own
sessions: the Skills **list** still correctly shows the pinned "Built-in" badge (that part of D-01 is
sound), but the agent's `load_skill("skill-creator")` call at **runtime** will silently execute the
user's own, unvetted, non-`is_system` content instead. That is precisely the kind of gap the "+
Protected" half of this phase's title is meant to close, and it is scoped in the actual change to
exactly one already-known account rather than the general case. Given the blast radius is
self-contained (a user can only shadow the built-in for themselves, not for other accounts), this is
a Warning rather than a Blocker — but it is a real, provable, currently-open gap, not a hypothetical.

**Fix:** Either reverse the tie-break so a global/`is_system` row wins over an owned row on a name
collision in `_handle_load_skill` (`.order("is_system", desc=True).order("is_global", desc=True)`
before taking the first row), or reject/auto-suffix a create/save/import name that collides with an
existing `is_system=true` skill's name (mirrors the empty-name guard already added in Phase 123,
`skills.py:174-175`). At minimum, if neither is scheduled for this phase, file it as a tracked
backlog item (SEED) so the residual risk documented today in `137.2-RESEARCH.md` doesn't quietly
disappear once this phase's planning folder is archived.
