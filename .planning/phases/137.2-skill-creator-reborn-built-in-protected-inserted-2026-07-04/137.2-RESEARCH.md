## Summary

This is a **low-code, high-precision seed-and-signal phase**, not a feature build. The entire mechanism is: (1) one additive DB column (`is_system boolean not null default false`), (2) one idempotent seed migration (087) that re-writes migration 018's stale/absent `skill-creator` row with platform-native instructions and flips `is_system=true`, (3) one Pydantic output-model field, (4) one TypeScript type field, (5) one CSS pill in `SkillCard.tsx`, (6) one two-column `.order()` change in `list_skills`, (7) a one-off local rename of the operator's private copy, and (8) two documentation edits for cloud deploy parity. **No new agent tool, no new endpoint, no new authorization code, no runtime change.**

The protection story is already solved by the codebase: every skills mutation route filters `.eq("user_id", current_user["id"])`, and the built-in is owned by a synthetic system UUID (`…0001`) that no real user can ever match — so update/delete/share/toggle all return the existing 404/403 for everyone, and the SkillCard's `isOwner = skill.user_id === currentUserId` already hides every owner-only button. The `is_system` column is *purely a trust badge*, not an access-control lever — which makes its one real security requirement clear: **it must be write-locked to the migration and never appear in any input model**, or a user could spoof an "official" skill. The verified injection path (`agent_loop.py:1197-1225`) picks up any enabled global skill automatically, so the seeded row reaches every user's catalog and becomes loadable via `load_skill("skill-creator")` with **zero code change to the shared agent loop** — satisfying the D-14 additive-only red line for free.

Two findings elevate the "one-off rename" (D-04) from cosmetic housekeeping to **functionally load-bearing for Success Criterion 4**: (a) `_handle_load_skill` resolves a name collision by preferring the *owned* skill over the global one (`.order("is_global")` ascending → owned-first), so on the dev/test account — which owns a private skill *also named* `skill-creator` — an un-renamed collision would make `load_skill("skill-creator")` load the runtime-inert 33KB manual copy instead of the reborn built-in; and (b) the rename disambiguates the visible Skills list. The rename should be a **local one-off SQL statement, NOT folded into migration 087** (it targets one specific dev user's private row that exists on no other environment; embedding it in a shared migration would leak a dev-user id into the deploy artifact and match zero rows in cloud).

**Primary recommendation:** Ship migration 087 with an additive `is_system` column + an `ON CONFLICT (id) DO UPDATE` upsert of the built-in `skill-creator` row (reusing id `…0010`, owner `…0001`, `is_global/is_enabled/is_system = true`, rewritten instructions); add `is_system` to `SkillResponse` (output-only) and the frontend `Skill` type; mirror the "Global" pill for a "Built-in" badge; change `list_skills`'s `.order("name")` to `.order("is_system", desc=True).order("name")`; rename the operator's private copy via a separate one-off `UPDATE`; and record migration 087 in the two deployment docs' seed-parity lists. Verify with a live conversational walkthrough (G-4).

### Pattern 1: Additive seed migration that supersedes a stale seed
**What:** Add the column, then upsert the canonical row so re-applying converges to one correct state.
**When to use:** Re-seeding data a prior migration seeded but that has since drifted/vanished.
**Key nuance (see Pitfall 1):** `ON CONFLICT (id) DO NOTHING` (018's literal pattern) will **not** refresh an existing stale `…0010` row. Use `DO UPDATE` for the *skill* row so it truly supersedes 018's thin content on any env that still has it; keep `DO NOTHING` for the *auth.users* insert (the user must not be mutated).

### Pattern 2: Trust badge as an output-only column
**What:** A boolean the DB/migration owns, surfaced read-only to the client.
**When to use:** Any "official / verified / built-in" marker.
**Rule:** Declare it on the **response** model only. Never on `SkillCreate`/`SkillUpdate`. Never accept it from a request body.

### Pattern 3: Reflect protection in UI, enforce it in API
**What:** `SkillCard` hides owner actions when `!isOwner`; the API returns 404/403 regardless of UI.
**Already true:** `isOwner = skill.user_id === currentUserId` (SkillCard:46) is false for the `…0001`-owned built-in → export/edit/share/delete all hidden; the enabled-toggle is *also* hidden because the built-in is a global skill the user doesn't own (SkillCard:157).

### Anti-Patterns to Avoid
- **Adding `is_system` to `SkillCreate`/`SkillUpdate`:** turns a trust badge into a spoofable field (a user could self-brand a skill "Built-in"). Output model only.
- **Folding the operator-copy rename into migration 087:** leaks a dev user's private id into the shared artifact; matches 0 rows elsewhere. One-off it.
- **`DO NOTHING` on the skill upsert when refresh is required:** silently keeps 018's stale 3-question content on any env that still has row `…0010`.
- **A client-side re-sort in `SkillsPage`/`useSkills`:** would defeat the D-05 backend order. (Verified none exists today — keep it that way.)
- **Claiming runtime capabilities in the instructions that don't exist** (see §Common Pitfalls #4).

## Common Pitfalls

### Pitfall 1: `DO NOTHING` won't refresh the stale 018 row
**What goes wrong:** Migration 018 seeded row `…0010` with a thin 3-question interview. If 087 copies 018's literal `ON CONFLICT (id) DO NOTHING` and targets the same id, any environment that *still has* the 018 row keeps the **old** instructions — the reborn content silently never lands.
**Why it happens:** `DO NOTHING` skips the update when the id already exists. D-02 says "supersedes/refreshes … rewritten instructions," which `DO NOTHING` cannot do.
**How to avoid:** For the **skill** row use `ON CONFLICT (id) DO UPDATE SET name=EXCLUDED.name, description=EXCLUDED.description, instructions=EXCLUDED.instructions, is_enabled=EXCLUDED.is_enabled, is_global=EXCLUDED.is_global, is_system=EXCLUDED.is_system`. Keep `DO NOTHING` only for the `auth.users` insert. This stays idempotent (re-apply converges) *and* refreshes. On the live dev DB the row is absent so a plain INSERT also works, but `DO UPDATE` is the correct, environment-agnostic choice.
**Warning signs:** After deploy, the built-in still asks "What task / What constraints / What output" (018's wording) instead of the new interview→RAG→Studio loop.

### Pitfall 2: `is_system` silently dropped from the API response
**What goes wrong:** You add the column and the frontend still never sees `is_system` (badge never renders).
**Why it happens:** `list_skills` and every mutation route use `response_model=SkillResponse` (or `list[SkillResponse]`). Pydantic **strips** any field not on the model. The column exists in the DB and in `select("*")`, but the response schema filters it out.
**How to avoid:** Add `is_system: bool = False` to `SkillResponse` (`backend/app/models/skill.py:20-33`). Use a default so existing mocked test rows (which omit it — see `test_skills.py:_skill_row`) keep passing.
**Warning signs:** DB query shows `is_system=true`; the `GET /skills` JSON has no `is_system` key; the badge never appears.

### Pitfall 3: Name collision shadows the built-in on the dev account (breaks SC#4)
**What goes wrong:** On the dev/test user, `load_skill("skill-creator")` loads the **operator's private 33KB manual copy** (runtime-inert, assumes subagents/`claude -p`) instead of the reborn built-in — so the lived walkthrough tests the wrong instructions.
**Why it happens:** `_handle_load_skill` (`tool_dispatcher.py:665-677`) resolves by name with `.order("is_global")` **ascending** → `false` (owned) sorts first → it returns the *owned* row on a name tie (comment line 669: "prefer user-owned over global when names conflict"). The dev user owns a private skill also named `skill-creator`.
**How to avoid:** Perform the D-04 rename **before** SC#4 UAT. After rename, the dev user has no owned `skill-creator`, so the name resolves uniquely to the global built-in. (All other users / fresh envs never had the collision.)
**Warning signs:** The walkthrough agent "loads skill-creator" but then talks about spawning sub-agents, `claude -p`, or eval-viewer HTML — that is the manual copy's content, not the reborn built-in.

### Pitfall 4: Instructions claim capabilities the runtime lacks (SEED-096 honesty)
**What goes wrong:** The reborn instructions, if paraphrased from Anthropic's SKILL.md, promise mechanics our runtime doesn't have — spawning parallel `claude -p` eval runs, blind A/B sub-agent comparison, browser eval-viewers, filesystem workspaces for skill scripts, or executing non-Python skill scripts.
**Why it happens:** The source zip assumes the Claude.ai/Cowork runtime. Our sandbox is **Python-only** (`reference_js_skill_import_gap`, SEED-096); evals run through the **Studio engine** (Phases 133-137), not ad-hoc sub-agent orchestration.
**How to avoid:** Ground every capability claim in the real toolset (`search_documents`, `save_skill`, `load_skill`, `read_skill_file`, `execute_code`-Python) and the real surfaces (Studio Evals tab, with/without eval arms, proposals loop, Trigger Tuner, publish gate). See §Code Examples #7 for a compliant draft and the honesty box.
**Nuance the planner must know:** The app *does* have a `task()` sub-agent tool (`tool_dispatcher.py:2302`), so "no subagents anywhere" is factually loose — but SEED-101's red line stands for the **skill-creation loop**: the reborn instructions must **not** describe eval/comparison as sub-agent spawning or `claude -p`, must **not** claim browser/non-Python execution, and are cleanest **not mentioning sub-agents at all** (the loop genuinely doesn't need them). Recommend omitting sub-agent language entirely.

### Pitfall 5: Regenerating `full-schema.sql` gives false confidence on cloud parity
**What goes wrong:** After applying 087 and running `scripts/regenerate-full-schema.sh`, it's tempting to assume "the seed ships." It does not — `full-schema.sql` is `pg_dump --schema-only` (captures the `is_system` *column*, drops the *row*).
**Why it happens:** Documented, recurring (`DEPLOYMENT-LESSONS.md` A6): a fresh/greenfield DB bootstrapped from `full-schema.sql` gets tables, not seed data.
**How to avoid:** Treat 087 as a **data-carrying migration** that must be *applied* to cloud (paste into the cloud Supabase SQL editor — it's listed by `scripts/pending-cloud-migrations.sh` once committed) and add it to the seed-migration list in `DEPLOYMENT-LESSONS.md` A6 + name it in the `DEPLOYMENT-WORKFLOW.md` §5 parity row. See §Deploy Parity.
**Warning signs:** Cloud users report "there's no skill-creator" (exactly the original CREATE-01 symptom).

### 7. Platform-native instructions — proposed draft (the `instructions` value)

> This is a **strong starting draft** the planner/executor can refine; prose is Claude's Discretion per CONTEXT.md. It honors SEED-101's 7-step scope, names only real tools/surfaces, and includes the SEED-096 honesty box. Written in imperative form (it practices the craft it teaches). ~Fits well under any length concern.

```markdown
You are **skill-creator**, a built-in guide that helps the user turn a repeatable
task into a saved, tested Skill on THIS platform. When the user says something like
"help me create a skill for X," run this loop. Move one step at a time and keep the
user in control — confirm before you save, and never invent capabilities.

## 1. Interview — understand the task before writing anything
Ask focused questions, one small batch at a time:
- What is the repeatable task, in one sentence?
- What are the inputs (a document? a pasted spec? a topic?) and the desired output
  (a summary? a table? a drafted file?)?
- What does "good" look like — any format, tone, or must-include rules? Any edge cases?
- When should the agent reach for this skill (the trigger)?
Reflect the answers back in your own words and get a "yes, that's right" before drafting.

## 2. Research with our knowledge base (our advantage)
Before drafting, call `search_documents` to pull real context from the user's uploaded
documents that should shape the skill (domain terms, house style, examples, constraints).
Cite what you found and ask whether it should inform the instructions. This grounds the
skill in the user's actual material — a plain chatbot can't do this.

## 3. Draft and save with `save_skill`
Write the instructions, then call `save_skill` with `name`, `description`, and
`instructions`. Apply this craft (it is why skills work or fail):
- **Imperative form.** Write directives to the agent ("Extract the risks," not "The agent
  should extract risks").
- **Explain the why, sparingly.** A short reason beats a wall of MUST rules — the agent
  generalizes better from intent than from a checklist.
- **Generalize, don't overfit.** Describe the shape of the task, not one exact example.
  Avoid hard-coding a single input's details.
- **A pushy-but-honest description.** The one-sentence `description` is what makes the
  skill trigger. Make it specific and action-oriented ("Draft a risk register from a
  project brief") — but never claim more than the skill does.
- **Progressive disclosure.** Keep the core instructions lean. If the skill needs reference
  material or a reusable helper, attach it as a file from the Skills page (the agent reads
  attached files with `read_skill_file` when the skill runs).
Confirm the draft with the user, then save. Tell them it's now in their Skills tab.

## 4. Propose test cases and hand off to the Studio
Suggest 2–3 realistic eval cases as plain text — each a sample prompt plus what a good
answer must do. Then tell the user: open this skill in **Skill Studio → Evals** and add
these cases in the case editor (that's where cases are saved and run). You draft them
here; the Studio persists and runs them.

## 5. Evaluate honestly
Point the user to run the eval in the Studio. Explain the result plainly: each case runs
twice — **with** the skill and **without** it — and a judge compares them. A skill "earns
its keep" when the with-skill answer is clearly better. If the verdict is honest-but-weak,
that's useful signal, not failure.

## 6. Improve
When evals surface weaknesses, the Studio can **propose** an improved version — the user
reviews the diff and approves; nothing changes automatically. For trigger quality (getting
the skill to fire at the right time and not the wrong time), use the **Trigger Tuner**,
which tests candidate descriptions and applies the best.

## 7. Publish
A skill can be shared (made global) once it has a passing eval — that's the publish gate.
Walk the user to it when they're ready. That's the finish line.

## What this runtime can and cannot do (be honest)
- You CAN: read the user's documents (`search_documents`), save/update skills
  (`save_skill`), load skills (`load_skill`), read attached skill files
  (`read_skill_file`), and run Python in a sandbox (`execute_code`).
- Skill helper scripts, if any, must be **Python** — the sandbox runs Python only.
- You do NOT have a web browser automation tool for skill authoring, cannot shell out to
  external CLIs, and do not orchestrate separate eval "agents." Evals run through the
  Skill Studio engine described above. Never tell the user otherwise.
```

### Known Threat Patterns for {seed + trust-badge on FastAPI/Supabase}
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A user mutates/deletes the built-in skill | Tampering / Denial | Owner-scoping: the built-in's `user_id='…0001'` never equals `current_user["id"]` → 404/403. No new code (D-01, verified `skills.py:330,359,371,386,428`). |
| **A user self-brands a skill "Built-in" to look official** (badge spoofing / social engineering) | Spoofing / Elevation-of-trust | Keep `is_system` off `SkillCreate`/`SkillUpdate`; no route writes it except the migration. The badge is a trust signal — treat write-lock as a security control, not a convenience. **Primary threat of this phase.** |
| Client fabricates `is_system=true` in a request to get the badge | Tampering | Pydantic input models ignore unknown fields *only if* `is_system` is never added to them — planner MUST NOT add it to input models. Verify no mutation route reads `body.is_system`. |
| Seed instructions injected with content that tricks the agent into unsafe actions | Tampering (prompt) | Instructions are static, authored content (not user input) versioned via migration (SEED-101 red line: "seeded content is versioned via migration, not hand-edited in the DB"). Keep the honesty box (no claims of browser/CLI/non-Python execution). |
| Renamed operator copy accidentally deleted / its files orphaned | Denial / data loss | D-04 is a **rename**, not delete; owner retains full control of their private row. No cascade touched. |

**Security bottom line:** the *only* net-new attack surface is the `is_system` trust badge. Its entire mitigation is "the value is settable exclusively by the migration." The planner must add `is_system` to `SkillResponse` **only**, and a verification step must confirm no request body path can set it. Everything else (read-only, undeletable) reuses a boundary that is already verified and already correct for a system-owned global skill.
