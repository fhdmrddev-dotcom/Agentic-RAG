## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| client → API (request body) | Untrusted input crosses here. `is_system` must never be settable from a body — it is a trust badge, not a user field. | `SkillCreate` / `SkillUpdate` JSON bodies |
| migration → DB | The ONLY writer of `is_system` and of the seeded built-in row is migration 087 (instructions-only refreshed by gap-closure migrations 088/089). No API route writes it. | `is_system` boolean, skill row content |
| seeded instructions → agent context | The seed's `instructions` become agent system-prompt content via the existing catalog injection. Authored static content, not user input. | Skill instructions text |
| API → client | `is_system` arrives on the read `Skill`/`SkillResponse` shape only; the client never round-trips it back as a settable field. | `GET /skills` JSON response |
| operator → live DB | Migration apply + the D-04 rename mutate live dev data. Gated by a human-action checkpoint and scoped by id/owner. | SQL migration DDL/DML, one-off `UPDATE` |
| built-in row → every user's catalog | Once live, the seeded `is_global`+`is_enabled` row reaches every user via the existing catalog injection — read-only for all (owner `…0001`). | Skill catalog content (agent system prompt) |

| T-137.2-01 | Tampering / Denial | Built-in skill row — `list_skills`/`update_skill`/`delete_skill`/`toggle_enabled` (`backend/app/api/skills.py`) + `SkillCard.tsx` owner-action reflection | mitigate | Reuses the existing owner-scoped `.eq("user_id", current_user["id"])` boundary on every mutation route — the built-in's owner `…0001` never equals a real user id, so non-owner update/delete/toggle already return 404/403 with zero new authorization code. Code-verified current (`skills.py:330-338`, `:394-406`; `SkillCard.tsx:46,198`) and independently re-verified live post-apply in Plan 04 (owned `skill-creator` count = 0 for the dev user, global count = 1). | closed |
| T-137.2-02 | Spoofing / Elevation-of-trust | `is_system` trust badge — `SkillResponse`/`Skill` read type vs. `SkillCreate`/`SkillUpdate` input types; migration 087 | mitigate | `is_system` is output-only: present on `SkillResponse` (`backend/app/models/skill.py:33`) and the frontend `Skill` interface (`types/index.ts:483`) ONLY — absent from both backend and frontend Create/Update models.
