### `supabase/migrations/087_skill_creator_reborn.sql` (migration, batch DDL + data seed)

**Analog A — seed body:** `supabase/migrations/018_skill_creator_seed.sql` (the entire file, 64 lines). Reuses the SAME system-user UUID `00000000-0000-0000-0000-000000000001` and the SAME skill id `00000000-0000-0000-0000-000000000010`.

**auth.users idempotent insert** (`018_skill_creator_seed.sql:9-32`) — copy verbatim (keep `DO NOTHING` — the user row must never be mutated):
```sql
INSERT INTO auth.users (
  id, email, encrypted_password, email_confirmed_at,
  created_at, updated_at, raw_app_meta_data, raw_user_meta_data, aud, role
)
VALUES (
  '00000000-0000-0000-0000-000000000001', 'seed@system.local', '',
  now(), now(), now(),
  '{"provider":"email","providers":["email"]}', '{}',
  'authenticated', 'authenticated'
)
ON CONFLICT (id) DO NOTHING;
```

**skill insert** (`018_skill_creator_seed.sql:34-64`) — same column list, same id/owner, but **two deliberate departures from 018** (both flagged by RESEARCH pitfalls, both correct):
1. Add the `is_system` column to the insert (value `true`).
2. Use `ON CONFLICT (id) DO UPDATE SET ...` **not** `DO NOTHING` — 018's `DO NOTHING` would silently keep a stale `…0010` row's old 3-question content on any env that still has it (RESEARCH Pitfall 1). The dev DB row is absent so a plain INSERT also works, but `DO UPDATE` is the environment-agnostic choice.

**Analog B — recent header/ALTER convention:** `086_app_settings_harness_judge_model.sql` (the most recent migration). Two conventions to mirror:
- **Comment-block header** explaining the *why* (086 opens with an 8-line rationale block, then the DDL). Recent migrations lead with intent, not just a one-line title.
- **`ADD COLUMN IF NOT EXISTS ... NOT NULL DEFAULT`** (086:13-14):
```sql
ALTER TABLE public.app_settings
  ADD COLUMN IF NOT EXISTS harness_judge_model text NOT NULL DEFAULT '';
```
  → for 137.2: `ALTER TABLE public.skills ADD COLUMN IF NOT EXISTS is_system boolean NOT NULL DEFAULT false;`

**Authoring-friction reducer (RESEARCH note on Example #1):** 018 had to double every apostrophe (`user''s`) in the instructions string. Use PostgreSQL dollar-quoting (`$INSTRUCTIONS$ … $INSTRUCTIONS$`) for the long instructions body so the prose can contain raw apostrophes.

**Migration number:** confirmed `087` — live `supabase/migrations/` tops out at `086_app_settings_harness_judge_model.sql`.

## Shared Patterns

### Owner-scoped protection (the read-only/undeletable boundary — DO NOT re-implement)
**Source:** `backend/app/api/skills.py` — every mutation route filters `.eq("user_id", current_user["id"])`: `update_skill` (:330), `delete_skill` (:359, :371), `toggle_enabled` (:386, :404), `toggle_global` (:432, :505).
**Apply to:** nothing new. This IS the protection mechanism (D-01). The built-in's owner `…0001` never equals any real `current_user["id"]`, so every non-owner gets the existing 404 (or 403 for toggle_enabled). The phase adds **zero** new authorization code — the executor must resist adding any `is_system`-aware guard.
```python
# toggle_enabled owner-miss branch (skills.py:390-394) — the existing 403 boundary:
if not current.data:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="Skill not found or you are not the owner",
    )
```

### Trust badge = output-only column (the ONE net-new attack surface)
**Source pattern:** `create_skill` hard-sets `is_global` server-side and never reads it from the body (`skills.py:185` — `"is_global": False,  # HARD-SET — never from the caller`).
**Apply to:** `backend/app/models/skill.py` (add `is_system` to `SkillResponse` ONLY, never `SkillCreate`/`SkillUpdate`) and `frontend/src/types/index.ts` (add to `Skill` ONLY, never `SkillCreate`/`SkillUpdate`). `is_system` is settable exclusively by migration 087. A verification step must confirm no request-body path can set it (RESEARCH Security Domain — badge-spoofing is the primary threat of this phase).

### Idempotent seed migration (converge-on-reapply)
**Source:** `supabase/migrations/018_skill_creator_seed.sql` — `auth.users` INSERT + `skills` INSERT, both `ON CONFLICT (id) DO NOTHING`.
**Apply to:** migration 087, with the one deliberate divergence — `DO UPDATE` for the *skill* row (so a stale `…0010` is refreshed, RESEARCH Pitfall 1), `DO NOTHING` for the *auth.users* row (never mutate the user).

### Mocked-Supabase integration test harness
**Source:** `backend/tests/conftest.py` — `_supabase`/`_builder`/`_execute_result` singletons, `mock_execute_result` (single-query `.data`) / `mock_builder` (multi-query `.execute.side_effect`) fixtures, autouse `reset_mocks`. Local helpers `_skill_row` / `_make_result` in `test_skills.py`.
**Apply to:** every backend test addition. Remember the two passthrough facts: `.order()`/`.eq()` do not sort/filter in the mock, and `mock_user_data["id"] == the system UUID`.
