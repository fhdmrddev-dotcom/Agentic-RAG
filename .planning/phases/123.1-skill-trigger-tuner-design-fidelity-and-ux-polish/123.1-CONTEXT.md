# Phase 123.1: Skill Trigger Tuner — Design Fidelity & UX Polish - Context

**Gathered:** 2026-06-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Gap-closure / polish of the Phase 123 Skill Trigger Tuner. The Tuner is functionally sound (it benchmarks trigger descriptions across all configured providers, OpenRouter resolves to a concrete model, and it survives transient SSE timeouts), but live UAT surfaced design-fidelity and UX defects (filed as **BUG-260624-01**). This phase closes those — it makes the *already-built* feature read cleanly at the org's real provider count, makes the benchmark visible/editable before a run, makes a completed result durable, and lets the builder model be chosen from configured models.

**This is NOT a new capability.** No new tuner features, no new scoring math, no agent-loop/trim changes. Scope is bounded to the HIGH+MED items in BUG-260624-01. The shared chat path, the 123 backend scoring core, and the CTX-03 trim-pin are OUT of scope and must not change.
</domain>

<decisions>
## Implementation Decisions

### Scope (operator-selected: HIGH + MED; LOW deferred)
- **D-01:** Phase 123.1 delivers the **HIGH** trio (scoreboard layout, seeded-case visibility, result persistence) **plus the MED** items (builder-model = configured models, long-description clamp, restore dropped sketch elements). LOW cosmetics are deferred (see Deferred Ideas).

### Scoreboard layout (fixes the "cramped/messy" — BUG-260624-01 HIGH #1)
- **D-02:** Re-render `ProviderScoreboard` as **vertical provider rows** (each provider = a full-width row: color dot + name + model + `fires` + `no-false` + a magnitude bar), **restoring sketch 041/042's original design** that the build replaced with a fixed horizontal `repeat(N,1fr)` grid. This scales cleanly to 8+ providers. **G-2 note:** this restores the existing approved sketch, so no new sketch is required.
- **D-03:** Let the **results/candidates span full width** (or give the right column materially more room) instead of being wedged into the half-width column of the 50/50 page split (`SkillTunerPage.tsx:280`).
- **D-04:** Restore the **standalone per-provider scoreboard block** at the top of the results area showing how the CURRENT/live description scores per provider (separate from per-candidate grids) — sketch 041 right column.

### Seeded benchmark cases (fixes "0 cases" / hidden cases — BUG-260624-01 HIGH #2 / WR-05)
- **D-05:** Backend must **return the auto-seeded cases** (prompts + `should_fire` + provenance: `seeded`/`sibling`) — either on the `POST .../tuner/runs` response or via a new lightweight GET — so the editor can display them.
- **D-06:** The editor **hydrates from the seeded cases on open and they are fully editable** (edit / remove / add) **before** the run — matching the sketch's "edit & approve before running" premise. The `seeded`/`sibling`/`held` provenance tags become real (no longer dead values).

### Result persistence (fixes "lost on refresh" — BUG-260624-01 HIGH #3)
- **D-07:** **Durable DB table** (e.g. `tuner_runs` or `skill_tuner_results`) storing the **latest tuning result per skill** (scoreboard + candidates + run metadata). Survives refresh, navigation, AND server/Redis restart. Shown whenever the skill's Tuner opens; **overwritten on re-run** (latest-wins, not accumulated history). This is the operator's "show it always, overwrite on re-run" intent.
- **D-08:** Ships as a **numbered SQL migration** under `supabase/migrations/` per CLAUDE.md — must have **Row-Level Security (owner-scoped: a user sees only their own skills' runs; global skills follow the existing skills scope)**. Apply via the Supabase SQL editor (NOT `db push`/`db reset`), then regenerate `full-schema.sql` via `scripts/regenerate-full-schema.sh`. The result-store write moves from the ephemeral Redis-only path (`tuner_result:{run_id}`, TTL 600s) to also persisting the latest result to this table; Redis can remain the live-stream transport.

### Builder-model picker (BUG-260624-01 MED #4 — operator-driven)
- **D-09:** Drive the **Skill-builder model dropdown from the user's configured models** (the same per-provider `Models (comma-separated)` lists the chat picker uses) instead of the hardcoded cheap-only list (`SKILL_BUILDER_MODEL_OPTIONS`). The operator must be able to pick **strong** models (Sonnet/Opus, GPT-5.5/-pro, Gemini-Pro), not just haiku/mini/flash.
- **D-10:** Keep a sensible **cheap-but-capable default pre-selected (not forced)**; the builder needs structured-output/forced-emission, so show a **soft hint** (not a hard block) if a chosen model lacks it. Remove the placeholder local ids (folds code-review IN-02). Decoupled-from-targets stays.

### Long descriptions (BUG-260624-01 MED #5)
- **D-11:** **Line-clamp with expand** on candidate descriptions in `CandidateCard` AND in the diff-confirm strip (old + new), so a ~1500-char description (e.g. `docx`) doesn't bury the held-out score and the Use action.

### Restored sketch elements (BUG-260624-01 MED #6/#7)
- **D-12:** Restore **"Built by {builder model} · measured on N production models"** attribution on the run row, the **pre-run cost preview** ("N cases × M models × 3 repeats = X live calls", with the model count available before the first run — `targets` currently empty until a run starts), and the **per-cell colored magnitude bar + leading combined score** (`TunerCell.score`, currently unused in this view).

### Claude's Discretion
- Exact table name/columns for D-07, the precise GET vs POST-response shape for D-05, the responsive breakpoint mechanics for D-02, and the migration number — planner/researcher decide, honoring the constraints above.

### Folded Todos
- BUG-260624-01 (the full finding set) is folded into this phase — it IS the phase scope. (No `.planning/todos/` items folded; the one todo match, the NL→workflow authoring spike, is unrelated — see Deferred.)
</decisions>

### Established Patterns
- Migrations: numbered `<digits>_name.sql` under `supabase/migrations/`, RLS mandatory, apply via SQL editor, regenerate full-schema (CLAUDE.md).
- Sequential-on-main-tree execution (worktrees lack venv/node_modules) — see prior-phase pattern.
- Owner-scoping is a security boundary; cross-user leak tests required for any new route/table.

### Integration Points
- D-07 changes the result-store write in `_run_tuner_job` (add a DB upsert of the latest result per skill alongside/instead of the Redis-only stash) + a new owner-scoped `GET .../tuner/runs/latest` (or `.../result`) route.
- D-05/D-06 change the `POST .../tuner/runs` response (or a new GET) to include seeded cases, and `SkillTunerPage` to hydrate `cases` from them.

<specifics>
## Specific Ideas

- Operator observed live (skill `docx`, 8 providers): the scoreboard was cramped/illegible, the editor showed "0 cases" while the run used hidden seeded cases, and a completed result (held-out 0.61) was lost on refresh. The builder-model picker offering only cheap models was called out as wrong — strong models must be selectable.
- "Show the result always; when you re-run, update/overwrite it" — the persistence intent (D-07 latest-wins).
</specifics>
