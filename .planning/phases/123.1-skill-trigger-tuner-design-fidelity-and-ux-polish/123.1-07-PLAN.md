<objective>
Close two run-UX defects from the 123.1 live-UAT audit (backlog §2) so the live run is honest and controllable:

- **TT-07** (lanes stuck "queued"): the frontend flips a lane queued -> running only when an `onProgress` event carries `provider`, but the backend emits provider/model ONLY on `tuner_provider_done` — AFTER the column finishes. So every lane shows "queued" for the whole run, then jumps to "done". Fix: emit a `tuner_progress` event with `stage="provider_start"` carrying provider/model at the START of each target column (via the tuner's OWN `_emit_tuner` — tuner-job-local, NOT the shared runs.py consumer, which is TT-06/Wave C), and flip the lane on it in the frontend.

- **TT-08** (cancel is client-only): `cancelRun` only aborts the SSE and sets idle — the job keeps burning paid provider calls and holds the `tuner_inflight` claim for up to 1800s, so a retry 409s and the cancelled run still finishes + persists. Fix: a real `DELETE .../tuner/runs/{run_id}` route (owner-verify + run<->skill bind, mirroring the CR-01 IDOR fix already in this phase) that sets a `tuner_cancel:{run_id}` Redis flag and releases the claim; the job checks the flag at the top of each candidate AND each provider loop and stops cleanly (no durable persist of a cancelled run); the frontend awaits the DELETE before going idle.

Purpose: The live run shows honest per-provider progress and a Cancel that actually stops the work + frees the skill for a retry.
Output: A provider_start emit + lane flip, a real owner-scoped cancel route + job checkpoint + claim release, the api.ts DELETE wrapper, and non-vacuous tests (incl. the cross-user cancel 404).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → DELETE /skills/{skill_id}/tuner/runs/{run_id} | An authenticated user requests cancellation of a tuning run, supplying BOTH a skill_id and a run_id — both are caller-controlled and untrusted. |
| caller-supplied run_id → shared run:{run_id} / runs_by_thread:tuner keyspace | The tuner reuses the SAME run:{run_id} / inflight keyspace as chat + other skills' runs; a leaked/guessed run_id must not let a user cancel a run that isn't theirs. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-123.1-07-01 | Elevation of Privilege / IDOR | DELETE cancel route — cross-user skill | mitigate | The route calls `_fetch_owned_or_global_skill(supabase, skill_id, user_id)` FIRST (the SOLE owner gate; service-role client, so the app-code `.or_(user_id.eq, is_global.eq.true)` is the only barrier) — a cross-user / non-global skill 404s before any flag is set. Mirrors the CR-01 IDOR fix already in this phase. Non-vacuous test: OTHER_USER DELETE on an OWNER-only skill -> 404. |
| T-123.1-07-02 | Tampering / IDOR | DELETE cancel route — foreign run_id on a visible skill | mitigate | The skill gate only proves "you can SEE this skill" — it does NOT bind the caller-supplied run_id. The route adds the CR-01 run<->skill bind: `redis.zscore(runs_by_thread:tuner:{skill_id}, run_id) is None -> 404`, so owning/seeing a skill + a LEAKED run_id (from logs / LangSmith / runs:active) cannot cancel an arbitrary run. The cancel flag is set ONLY for a run_id bound to this skill. Non-vacuous test: a foreign run_id on a visible skill -> 404, no tuner_cancel set. |
