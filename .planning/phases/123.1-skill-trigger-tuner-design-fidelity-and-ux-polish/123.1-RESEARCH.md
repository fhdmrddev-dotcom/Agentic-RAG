# Phase 123.1: Skill Trigger Tuner — Design Fidelity & UX Polish - Research

**Researched:** 2026-06-24
**Domain:** React/Vite frontend polish + FastAPI/Supabase durable-persistence seam (gap-closure for the already-built Phase 123 Skill Trigger Tuner)
**Confidence:** HIGH (every claim about current behavior is grounded in file:line reads of the shipped Phase-123 code; net-new seams reuse established project patterns quoted verbatim)

## Summary

Phase 123.1 is a **bounded gap-closure / polish phase** for an already-functional feature. The Phase-123 Trigger Tuner works end-to-end (it benchmarks trigger descriptions across all configured providers, OpenRouter resolves to a concrete model, runs survive transient SSE timeouts). Live UAT at the org's real provider count (8) surfaced design-fidelity and UX defects, filed as BUG-260624-01 and folded into this phase as the 12 locked decisions D-01..D-12. **The scope IS those decisions** — no new tuner capability, no scoring-math change, no agent-loop/trim-pin/shared-chat-path change.

Most of the work (D-02/D-03/D-04/D-11/D-12) is **well-understood frontend polish against approved sketches 041–044** — restoring the vertical-rows scoreboard, full-width results, per-cell magnitude bars, line-clamps, and dropped attribution/cost-preview elements. The G-2 guardrail is already satisfied because the target design is the *existing approved sketch* (041's `.scoreboard` is literally `flex-direction: column` vertical rows). The three net-new infrastructure seams the operator flagged for de-risking are:

1. **D-07/D-08 durable result persistence** — a new owner-scoped `tuner_runs` table (migration **077**) storing the *latest* result per skill (latest-wins, upsert-on-rerun), plus a DB upsert at the existing Redis-stash site (`skill_tuner.py:382-389`) and a new owner-scoped GET-latest route. This is the highest-risk piece: it touches the security boundary (RLS + app-code owner-scoping) and the migration discipline (apply-via-SQL-editor, regenerate full-schema).
2. **D-05/D-06 seeded-case visibility** — the backend already seeds cases server-side (`auto_seed_cases`, `skill_tuner_service.py:234`) but never echoes them to the client; the editor inits `cases=[]` so the provenance tags `seeded`/`sibling`/`held` are dead. Recommend **augmenting the `POST .../tuner/runs` response** (or a sibling preview GET) to return the seeded cases so the editor hydrates-on-open and they become fully editable before the run.
3. **D-09/D-10 builder-model picker from configured models** — replace the hardcoded `SKILL_BUILDER_MODEL_OPTIONS` (`SettingsPage.tsx:46-54`) with the user's configured per-provider models, which `SettingsPage` *already reads* into `providerStates` from `s.providers[].models`. This is a same-file mirror of the chat picker — low risk, removes the IN-02 placeholder ids.

**Primary recommendation:** Treat the three net-new seams as the planning core (one backend/migration wave for D-07/D-08, one backend-response + frontend-hydrate wave for D-05/D-06, one Settings-only change for D-09/D-10), and the rest as a single frontend-polish wave against the sketches. The new table/route MUST carry the cross-user-404 leak test (mirror `test_skill_tuner_routes.py:164,201`) — that is the load-bearing security proof.

### Pattern 1: Owner-scoped table with service-role writes + SELECT-only RLS (D-08)

**What:** A new table written by the service-role backend (RLS bypassed) and read with app-code `.or_(user_id.eq, is_global.eq.true)` scoping. RLS is defense-in-depth; the app-code scoping is the real gate (because `get_supabase()` is service-role — `dependencies.py:16-19`).

**When to use:** D-07's `tuner_runs`. The latest-result row is keyed by `skill_id` with `UNIQUE(skill_id)` so re-runs upsert (latest-wins, never accumulate).

**The exact existing skills RLS policy to mirror (quoted verbatim from `017_skills.sql:25-41`):**
```sql
-- Source: supabase/migrations/017_skills.sql
ALTER TABLE public.skills ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own and global skills"
  ON public.skills FOR SELECT
  USING (auth.uid() = user_id OR is_global = true);

CREATE POLICY "Users can insert own skills"
  ON public.skills FOR INSERT
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can update own skills"
  ON public.skills FOR UPDATE
  USING (auth.uid() = user_id);

CREATE POLICY "Users can delete own skills"
  ON public.skills FOR DELETE
  USING (auth.uid() = user_id);
```

**The owner+global SELECT for a child table that references skills** — mirror `skill_files` (`017_skills.sql:73-82`) when the row's own `user_id` plus the parent skill's `is_global` both matter:
```sql
-- Source: supabase/migrations/017_skills.sql (skill_files SELECT — owner OR parent-skill-global)
CREATE POLICY "Users can view files on own or global skills"
  ON public.skill_files FOR SELECT
  USING (
    auth.uid() = user_id
    OR EXISTS (
      SELECT 1 FROM public.skills
      WHERE skills.id = skill_files.skill_id
        AND skills.is_global = true
    )
  );
```

**Recommended `077_*.sql` shape** (planner finalizes columns/name; this is the verified-pattern skeleton):
```sql
-- Source pattern: 035_runs_table.sql (service-role writes, SELECT-only RLS)
--                 056_workflow_definitions.sql (jsonb config + global RLS + UNIQUE)
--                 017_skills.sql (owner+global scope)
-- Apply via the Supabase SQL editor (CLAUDE.md — NEVER `supabase db push`/`db reset`).
-- Then: bash scripts/regenerate-full-schema.sh  (no --reset — live-DB dump only); commit BOTH files.

CREATE TABLE IF NOT EXISTS public.tuner_runs (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  skill_id      uuid NOT NULL REFERENCES public.skills(id) ON DELETE CASCADE,
  user_id       uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  run_id        uuid NOT NULL,                  -- the latest run that produced this result
  scoreboard    jsonb NOT NULL DEFAULT '{}',    -- candidates + cells + winner_index (the full TunerScoreboard)
  builder_model text NOT NULL DEFAULT '',       -- D-12 "Built by {model}" attribution
  target_count  integer NOT NULL DEFAULT 0,     -- D-12 "measured on N production models"
  case_count    integer NOT NULL DEFAULT 0,     -- D-12 cost-preview / run-config
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT tuner_runs_skill_unique UNIQUE (skill_id)  -- latest-wins: one row per skill, upsert on re-run
);

CREATE INDEX IF NOT EXISTS idx_tuner_runs_user_id ON public.tuner_runs (user_id);

ALTER TABLE public.tuner_runs ENABLE ROW LEVEL SECURITY;

-- Owner OR parent-skill-global SELECT (mirror skill_files); backend writes are service-role (RLS bypassed).
CREATE POLICY "Users can view tuner runs on own or global skills"
  ON public.tuner_runs FOR SELECT
  USING (
    auth.uid() = user_id
    OR EXISTS (
      SELECT 1 FROM public.skills
      WHERE skills.id = tuner_runs.skill_id
        AND skills.is_global = true
    )
  );
```
> **Note on the global case:** the existing tuner routes already 404-gate via `.or_(user_id.eq.{caller}, is_global.eq.true)` on the *skills* table (`skill_tuner.py:147`). The simplest correct latest-result read is to (a) owner-verify the skill exactly as the existing routes do, then (b) read the `tuner_runs` row by `skill_id`. The RLS `EXISTS(... is_global)` clause matches that semantics for defense-in-depth. **Decide who owns a global skill's tuner run:** if any user can tune a global skill, the row's `user_id` is whoever last ran it — the SELECT-by-skill is the same for all global viewers. Document this in the migration comment.

**Upsert at the existing write site** (`skill_tuner.py:382-389`, inside `_run_tuner_job`) — add alongside the Redis stash, wrapped in `run_in_threadpool` (CLAUDE.md / D-v2.5-01 — supabase-py is blocking):
```python
# Source pattern: existing tuner Redis stash (skill_tuner.py:382-389) + run_in_threadpool discipline.
# Add a DB upsert (latest-wins) ALONGSIDE the existing redis.set — Redis stays the live per-run-id transport.
def _upsert_latest(_supabase, _payload):
    return (
        _supabase.table("tuner_runs")
        .upsert(_payload, on_conflict="skill_id")   # UNIQUE(skill_id) → overwrite on re-run
        .execute()
    )
try:
    await run_in_threadpool(_upsert_latest, supabase, {
        "skill_id": skill_id, "user_id": user_id, "run_id": str(run_id),
        "scoreboard": scoreboard, "builder_model": builder_model,
        "target_count": len(targets), "case_count": len(cases),
        "updated_at": "now()",
    })
except Exception:
    logger.exception("tuner durable upsert failed for run %s (Redis stash still set)", run_id)
```
> `_run_tuner_job` currently receives `redis`, `run_id`, `skill_id`, `skill`, `cases`, `targets`, `n`, `user_id` — it does **not** receive the `supabase` client. The planner must thread `supabase` into the job (the route already has it via `Depends(get_supabase)` at `skill_tuner.py:415`). `builder_model` is resolved inside the job at `skill_tuner.py:239`; `cases`/`targets` are passed in.

### Pattern 2: Return seeded cases to the client (D-05/D-06)

**What:** The backend already computes the seed (`auto_seed_cases`, `skill_tuner_service.py:234-268`) and flattens it into `cases` at `skill_tuner.py:473-477`, but the POST response (`skill_tuner.py:515-521`) returns only `case_count` (int) — the editor never sees the actual prompts. `CaseEditor`'s provenance union (`seeded`/`sibling`/`held`/`you`) is dead because nothing ever sets anything but `"you"` (`CaseEditor.tsx:132`).

**When to use:** D-05/D-06 — the editor must show + edit the seeded cases BEFORE the run.

**Current seed shape** (`auto_seed_cases` returns `{"should_fire": [...], "should_not": [...]}`):
- `should_fire`: the skill's own description, an `"I need to {description}"` paraphrase, and `"Use the {name} skill."` — provenance = `seeded`.
- `should_not`: each sibling skill's description (from the owner-scoped catalog) — provenance = `sibling`; plus the fixed `_GENERIC_OFF_TOPIC` 5-prompt set (`skill_tuner_service.py:61-67`) — provenance = `seeded` (generic).
- The `held` provenance was intended to tag the held-out 40% — but the held-out split is computed at scoring time, not seed time, so `held` is best treated as a derived display tag (which 40% will be held out) rather than a per-case authored value.

**Recommended approach — a lightweight GET preview endpoint** (rationale: the editor needs cases on OPEN, before any side-effecting POST; a GET keeps the seed read idempotent and lets the author edit/approve before kickoff, matching the sketch's "edit & approve before running" premise):
```
GET /skills/{skill_id}/tuner/cases/seeded   →  { should_fire: [{prompt, provenance}], should_not: [{prompt, provenance}] }
```
The handler owner-verifies the skill (reuse `_fetch_owned_or_global_skill`), fetches siblings (`fetch_owner_scoped_siblings`, already `run_in_threadpool`-wrapped at the call site), calls `auto_seed_cases`, and returns the prompts WITH provenance tags. To do this, `auto_seed_cases` should be extended (or a sibling function added) to **carry provenance** — currently it returns bare strings; the planner should return `(prompt, provenance)` pairs so `seeded` vs `sibling` is distinguishable.

> **Alternative (also acceptable per D-05):** augment the POST response to echo the seeded `cases` with provenance. This avoids a new route but couples case-preview to run-kickoff. The CONTEXT explicitly allows either; the GET is recommended because the sketch wants edit-before-run.

When the author then runs, `SkillTunerPage` already passes its edited `cases` into the POST body (`SkillTunerPage.tsx:102-104`); because the body's `cases` is non-empty, the backend uses them verbatim and does NOT re-seed (`skill_tuner.py:466-477` — the `if body.cases:` branch). So hydrate-on-open + edit + run is a clean loop with the existing POST contract.

### Anti-Patterns to Avoid
- **Hand-rolling the held-out split or scoring math in the frontend.** The backend owns all scoring (`skill_tuner_service.py`); the frontend renders server-computed `cells`/`scores` ONLY. `ProviderScoreboard`'s own docstring states "The UI renders server-computed scores only — no client-side fabrication." Keep it that way.
- **Persisting cases to the DB.** Cases are ephemeral/client-held by design (A2 / Open-Q5 — `TunerCase` docstring `skill_tuner.py:105-114`). Only the winning description persists (via PATCH /skills). D-07 persists the RESULT (scoreboard), not the cases.
- **Touching the shared SSE consumer / agent loop / trim-pin.** Explicitly out of scope (CONTEXT). The WR-06 lesson (a tuner change reached the shared chat path → 400) is why this red line matters.
- **Forgetting `run_in_threadpool` on the new DB upsert/read.** supabase-py is blocking; calling it directly in an async handler violates D-v2.5-01. The existing tuner code wraps every supabase call (`skill_tuner.py:153, 469`).
- **`supabase db push` / `db reset`.** CLAUDE.md forbids it for local dev (wipes data). Apply 077 via the SQL editor, then regenerate full-schema with no `--reset`.
- **Hard-blocking a builder-model choice that lacks forced-emission.** D-10 says soft hint, never a hard block.

## Common Pitfalls

### Pitfall 1: Threading `supabase` into the background job for the D-07 upsert
**What goes wrong:** `_run_tuner_job` (`skill_tuner.py:200-210`) does NOT currently receive the `supabase` client — only `redis`. A naive upsert inside the job has no client.
**Why it happens:** The job was scoped Redis-only (no DB schema change in Phase 123 — A2). The route HAS the client (`Depends(get_supabase)`, `skill_tuner.py:415`) but doesn't pass it to the spawned task (`skill_tuner.py:493-504`).
**How to avoid:** Add `supabase` to the `_run_tuner_job` signature and the `asyncio.create_task(_run_tuner_job(...))` call. Wrap the upsert in `run_in_threadpool` (supabase-py is blocking; the job is async). Make the upsert best-effort (`try/except` + log) so a DB hiccup never crashes the run — the Redis stash still serves the live per-run-id GET.
**Warning signs:** `NameError: supabase` inside the job; or a blocking supabase call freezing the event loop.

### Pitfall 2: The global-skill ownership semantics for `tuner_runs`
**What goes wrong:** A global skill can be tuned by any user; if the table's `user_id` is "whoever last ran it," a different user reading the latest result reads someone else's `user_id` row. RLS `auth.uid() = user_id` alone would 0-row it for everyone but the last runner.
**Why it happens:** The skills scope is owner-OR-global, but the *run* row has a single `user_id`.
**How to avoid:** The SELECT RLS must include the `EXISTS(... skills.is_global = true)` clause (mirror `skill_files` SELECT, `017_skills.sql:73-82`) so any user who can see the global skill can see its latest run. AND the app-code read should owner-verify the SKILL (reuse `_fetch_owned_or_global_skill`) then read `tuner_runs` by `skill_id` — exactly matching the existing route gate. Document the chosen semantics in the migration comment.
**Warning signs:** A global skill's tuner result disappears for a second user who can see the skill.

### Pitfall 3: The pre-run cost preview is empty because `targets` is set only at kickoff
**What goes wrong:** `SkillTunerPage.tsx:303` renders `× ${targets.length} models` but `targets` state starts `[]` and is only populated from the POST response (`SkillTunerPage.tsx:106`) — so the preview reads "N cases × 3 repeats" with no model count until the first run.
**Why it happens:** The component derives the model count from the run, not from the configured providers.
**How to avoid:** Resolve the configured-target count client-side from `FullAppSettings.providers` with a key (mirror `configured_targets` presence logic) so the preview is populated on open. The model count is also persisted on `tuner_runs.target_count` (D-07) for the post-run attribution.
**Warning signs:** "= X live calls" preview missing the model multiplier before the first run (the exact MED #6 defect).

### Pitfall 4: `held` provenance has no per-case authored source
**What goes wrong:** `CaseEditor`'s provenance union includes `held` (`CaseEditor.tsx:22-28`), but the held-out 40% is determined at *scoring* time by `split_held_out` (per-class, `skill_tuner.py:297-301`), not at seed time. Trying to tag a case `held` at seed time is meaningless.
**Why it happens:** The split is deterministic but computed post-edit (the author can add/remove cases, shifting the 60/40 boundary).
**How to avoid:** Treat `seeded`/`sibling`/`you` as authored provenance (returned by the backend / set on add), and `held` as a *derived display tag* computed by the editor's existing 60/40 math (`CaseEditor.tsx:122-125`) — or drop `held` from the provenance union and show the train/held split only in the split bar (which already exists, `CaseEditor.tsx:191-199`). Document the decision so the tag isn't "dead" but isn't fabricated either.
**Warning signs:** A `held` tag that contradicts the split bar, or never appears.

### Pitfall 5: Forgetting to regenerate `full-schema.sql` (or hand-editing it)
**What goes wrong:** Applying 077 to the live DB but not regenerating the bootstrap artifact leaves greenfield deploys missing the table.
**Why it happens:** The two-step migration discipline (apply via SQL editor + regenerate) is easy to half-do.
**How to avoid:** After pasting 077 into the Supabase SQL editor, run `bash scripts/regenerate-full-schema.sh` (NO `--reset` — live-DB dump only), and commit BOTH files. Never hand-edit `full-schema.sql` (CLAUDE.md).
**Warning signs:** A schema-drift gate flag; or a fresh-env deploy where the Tuner's GET-latest 500s on a missing table.

```python
# Source: backend/app/api/skill_tuner.py:133-162
# get_supabase() is SERVICE-ROLE (RLS bypassed) — this .or_(...own,global) is the SOLE leak gate.
async def _fetch_owned_or_global_skill(supabase, skill_id, user_id) -> dict:
    def _read():
        return (supabase.table("skills").select("id, name, description, user_id, is_global")
                .eq("id", skill_id).or_(f"user_id.eq.{user_id},is_global.eq.true").limit(1).execute())
    resp = await run_in_threadpool(_read)
    rows = list(resp.data or [])
    if not rows:
        raise HTTPException(status_code=404, detail="Skill not found")   # 404, never 403
    return rows[0]
```

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |

### Known Threat Patterns for FastAPI + Supabase (service-role) + React

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-user read of another user's latest tuner run | Information Disclosure | Reuse `_fetch_owned_or_global_skill` 404-gate on the new GET-latest route; RLS owner+global SELECT as defense-in-depth; cross-user-404 integration test (load-bearing) |
| RLS bypass via service-role write leaking another user's data | Elevation / Disclosure | Service-role writes always stamp the correct `user_id` from `current_user["id"]`; reads go through the app-code scope, never an unscoped `select *` |
| Malformed `skill_id` leaking error shape | Information Disclosure | Existing `_fetch_owned_or_global_skill` catches PostgREST errors → 404 (`skill_tuner.py:152-158`); the new route reuses it |
| Provider API key exposure via the builder picker (D-09) | Information Disclosure | The picker reads `providers[].models` (model names only); `api_key` is never sent to the client (`LLMProvider.api_key` comment `user_settings.py:90` — "never sent to frontend"; `ProviderInfo` exposes only `has_key`) |
| Sibling-catalog leak in seeded cases (D-05) | Information Disclosure | `auto_seed_cases` consumes ONLY the owner-scoped `fetch_owner_scoped_siblings` output (`.or_(own,global)`, `skill_tuner_service.py:271-293`); another user's private skill never reaches the seed — preserve this when exposing cases to the client |
