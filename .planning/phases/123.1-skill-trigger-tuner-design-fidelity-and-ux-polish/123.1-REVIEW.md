# Phase 123.1: Code Review Report

**Reviewed:** 2026-06-24
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

This phase adds the durable `tuner_runs` table + two new owner-scoped GET routes
(`/tuner/runs/latest`, `/tuner/cases/seeded`), a `run_in_threadpool`-wrapped durable upsert,
provenance-carrying seeded cases, the vertical-rows ProviderScoreboard, the configured-models
builder picker, and the full SkillTunerPage hydrate/rehydrate/cost-preview wiring.

The security-sensitive seam the prompt flagged is, on the whole, implemented correctly:

- `_fetch_owned_or_global_skill` IS called before any `tuner_runs` read on BOTH new GET
  routes, and a cross-user miss returns 404 (not 403/500) — verified against tests 6 & 10.
- Route registration order is correct: `/tuner/runs/latest` (line 584) is declared BEFORE
  `/tuner/runs/{run_id}` (line 643), so the literal `latest` matches first instead of 422-ing
  the UUID converter.
- The durable upsert is wrapped in BOTH `run_in_threadpool` AND a best-effort try/except
  (skill_tuner.py:413-422) — a DB hiccup logs and never crashes the run.
- Seeded cases flow only from `fetch_owner_scoped_siblings` (`.or_(user_id.eq, is_global.eq.true)`).
- `077_tuner_runs.sql` has exactly ONE `FOR SELECT` policy and ZERO write policies, with
  `UNIQUE(skill_id)`.
- ProviderScoreboard renders `c.score` (the server value) and never client-recomputes
  `(fires+no_false)/2`; `getTunerLatest` maps 404→null without throwing.

However the review found one BLOCKER (an IDOR-style gap where the SSE-stream and per-run-id
results routes never bind `run_id` to the verified skill, so owning any skill + a leaked
chat-or-tuner `run_id` reads an arbitrary Redis buffer) plus several honesty/consistency
defects in the cost-preview and held-out split that surface fabricated counts to the user.

## Critical Issues

### CR-01: Stream + per-run-id results routes never bind `run_id` to the verified skill (cross-resource read)

**File:** `backend/app/api/skill_tuner.py:558-581` (`stream_tuner_run`), `643-671` (`get_tuner_results`)
**Issue:** Both routes owner-verify only the *skill* via `_fetch_owned_or_global_skill`, then
read `run:{run_id}` / `tuner_result:{run_id}` for the **caller-supplied `run_id`** with no check
that the run actually belongs to that skill (or to the caller). The owner-scope gate proves
"you can see this skill," NOT "this run_id is yours."

Consequences:
- `stream_tuner_run` hands `run:{run_id}` straight to the shared `replay_tail_consumer`. The
  tuner reuses the EXACT same `run:{run_id}` keyspace as the chat run-buffer
  (`threads._emit` / Phase-061+). A user who owns (or can see one global) skill, plus any
  leaked/observed `run_id` — including another user's **chat** run — can open the SSE stream and
  read that buffer's events. The skill the URL names is irrelevant to which buffer is read.
- `get_tuner_results` has the identical shape against `tuner_result:{run_id}`.

The only thing preventing the leak is the UUID being unguessable — but a `run_id` is surfaced in
many places (logs, LangSmith, the `runs:active` set, prior responses) and "unguessable id" is not
an authorization control. The existing cross-user tests (#2, the 404 cases) pass only because the
*skill* is not visible; they never exercise "visible skill + foreign run_id," so this gap is
untested.

**Fix:** Bind the run to the skill before reading the buffer. Persist the originating
`skill_id` alongside each run (a `runs_by_thread:tuner:{skill_id}` membership check already
exists — the start path ZADDs `str(run_id)` into it), and verify membership on read:

```python
# in stream_tuner_run / get_tuner_results, AFTER _fetch_owned_or_global_skill:
is_member = await redis.zscore(f"runs_by_thread:tuner:{skill_id}", str(run_id))
if is_member is None:
    raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Tuner run not found")
```

(Membership survives until ZREM in the job's `finally`; for the post-completion results read,
gate on the durable `tuner_runs.run_id` for that skill_id instead, or keep a short-lived
`tuner_run_skill:{run_id} -> skill_id` key and assert it equals the URL skill_id.)

## Warnings

### WR-01: Cost-preview / `target_count` over-counts local providers that are never scored

**File:** `backend/app/api/skill_tuner.py:495-496, 410` + `backend/app/services/skill_tuner_service.py:498-532`
**Issue:** `configured_targets` appends local providers (`ollama`/`lmstudio`) to `present` when
their `base_url` is set, then maps them through `_REPRESENTATIVE_MODEL.get(provider, "")` — which
has NO ollama/lmstudio entry, so they get `model: ""`. The job's scoring loop then does
`if not model: continue` (skill_tuner.py:308-309), so these lanes are NEVER measured — yet they
ARE counted in the response `targets` and persisted as `target_count: len(targets)`
(skill_tuner.py:410). The attribution then claims "measured on N models" for a model that
produced zero cells. The frontend separately filters them OUT (`has_key && models.some(...)`),
so the pre-run count and the post-run `target_count` can disagree by the number of local
providers.

**Fix:** Drop empty-model targets before counting/persisting, so `targets`, `target_count`, and
the scored lanes agree:

```python
targets = [t for t in targets if t.get("model")][:MAX_TARGETS]
```

and/or give ollama/lmstudio a real representative entry in `_REPRESENTATIVE_MODEL`.

### WR-02: Frontend cost-preview filter does not mirror the backend presence rule

**File:** `frontend/src/pages/SkillTunerPage.tsx:178-186`
**Issue:** The page computes the pre-run model count as
`settings.providers.filter(p => p.has_key && p.models.some(...))`. The backend
`configured_targets` keyed-provider rule checks **API-key presence only** (`elif pid in
_PROVIDER_KEY_ATTR and api_key:`), NOT model presence, and additionally counts **local**
providers by `base_url` with no key. So a keyed provider with an empty `models` list counts on
the backend but not the frontend (and vice-versa for locals — see WR-01). The "× N models"
preview is therefore not the count the run will actually use. The component comment even
acknowledges the local-provider mismatch but ships the divergent count anyway.

**Fix:** Either (a) expose the resolved target set from the backend (a thin GET that returns
`configured_targets(...)`) and render its length, or (b) align the client filter exactly with
the backend rule (key-presence for keyed providers; base_url for locals) AND fix WR-01 so the
backend itself stops counting unscored lanes. A user-facing count must match the work performed.

### WR-03: CaseEditor 60/40 split bar shows a count that does not match the backend's per-class split

**File:** `frontend/src/components/skills/tuner/CaseEditor.tsx:128-131, 202-204`
**Issue:** The split bar computes `trainCount = floor(total * 0.6)` over the **combined** case
list. The backend (`skill_tuner.py:298-302`) splits **per class** — `split_held_out(should_fire)`
and `split_held_out(should_not)` independently, then concatenates the held-out halves. For an
unbalanced set (e.g. 2 fire + 8 no-fire) the per-class held-out count differs from
`total - floor(total*0.6)`. The bar's "{heldOutCount} held-out (40%)" is then a fabricated number
the run never uses — the same class of honesty defect this phase was created to fix (WR-05 "0
cases"). Worse, `split_held_out` also bumps `cut = n-1` when a class would otherwise have an empty
held-out (line 366-367), which the flat frontend math never reflects.

**Fix:** Compute the displayed held-out count per class to mirror `split_held_out`
(`floor(n*0.6)` per class, with the `n>=2 -> at least 1 held-out` guarantee), summed across the
two columns — or render it as an approximate range and stop asserting an exact count.

### WR-04: `n` candidate cap is silently clamped without surfacing it; baseline can be discarded

**File:** `backend/app/api/skill_tuner.py:513` + `skill_tuner.py:270-280`
**Issue:** `n = max(1, min(int(body.n or DEFAULT), MAX_ITERATIONS))` clamps to 5, but
`bounded_candidates` is then filled with the baseline FIRST and capped at `MAX_ITERATIONS`
(5) total — so if the builder returns 5 candidates plus the baseline, the de-dupe+cap loop
breaks at 5 and the **builder candidates beyond the 4th are dropped while the baseline is kept**.
That's fine, but note the inverse: the request `n` is the candidate budget and the response
echoes the clamped `n` — yet `bounded_candidates` may contain `n+1` items (baseline + n) capped to
5, so the actual scored-candidate count is `min(n+1, 5)`, not the echoed `n`. The echoed `n`
misrepresents how many candidates were scored.

**Fix:** Either reserve a slot for the baseline (`min(n, MAX_ITERATIONS-1)` builder candidates +
baseline) so the count is honest, or compute and return the actual `len(bounded_candidates)` in
the POST response instead of the requested `n`.

### WR-05: Transient-reconnect path can re-enter `startRun`'s closure with a stale `skillId`/abort

**File:** `frontend/src/pages/SkillTunerPage.tsx:251-296`
**Issue:** `onTerminal` re-invokes `streamTunerRun(skillId, runIdForStream, callbacks, "0", controller.signal)`
on a transient timeout. `callbacks` (and thus `onTerminal`) close over the `skillId`/`controller`
captured when `startRun` first ran. If the user switches skills mid-run, the unmount effect aborts
`abortRef.current` — but a reconnect scheduled inside an in-flight `getTunerResults().catch()`
chain re-opens the stream against the **old** `controller.signal` (already aborted, so it returns
silently) OR, if `startRun` was re-invoked for the new skill, two callback closures now race on
`setScoreboard`/`setLanes`. The guard `if (controller.signal.aborted) return` covers the common
case, but the `getTunerResults(skillId, ...)` call on line 256/288 uses the **captured** `skillId`,
so a reconcile for skill A can resolve and `setScoreboard` after the user moved to skill B.

**Fix:** Capture a per-run "is current" token (e.g. compare `runIdForStream` against a
`currentRunIdRef`) and bail in every async continuation when it no longer matches, in addition to
the `controller.signal.aborted` check. Drop late `setScoreboard`/`setRunPhase` for superseded runs.

### WR-06: `_score_axis` empty→1.0 lets a vacuous class produce a fabricated cell score

**File:** `backend/app/services/skill_tuner_service.py:380-386, 389-410`
**Issue:** `_score_axis([], expected)` returns `1.0`. If, after the per-class held-out split, a
candidate's held-out set contains only should-fire cases (e.g. the author supplied zero should-NOT
cases, or `split_held_out` produced an empty no-false tail), `build_cell` reports `no_false = 1.0`
— a perfect false-fire-rail score that was never measured. The cell `score = (fires + 1.0)/2`
then inflates the held-out score and can hand the winner pick to a candidate on a vacuous rail.
The Phase-123 WR-02 comment (skill_tuner.py:290-297) claims the per-class split "guarantees BOTH
rails appear," but that only holds when BOTH source classes are non-empty; a single-class case set
(common when an author only adds should-fire cases) reintroduces the vacuous 1.0.

**Fix:** Distinguish "no signal" from "perfect" — return a sentinel (e.g. `None`) for an empty
axis and exclude it from `cell_score`/`pick_winner`, or refuse to score a candidate whose held-out
set is missing an entire rail and surface that honestly in the cell rather than as 1.0.

### WR-07: `_persist_latest` upsert sets `updated_at: "now()"` as a literal string, not a SQL function

**File:** `backend/app/api/skill_tuner.py:410`
**Issue:** The upsert payload sets `"updated_at": "now()"`. Through supabase-py/PostgREST this is
sent as the JSON string `"now()"`, not the SQL `now()` function. For a `timestamptz` column
Postgres will attempt to parse the string `"now()"` — Postgres *does* accept the special literal
`'now'`, but `'now()'` (with parens) is NOT a valid timestamp input and will raise
`invalid input syntax for type timestamp`. Because the whole upsert is wrapped in a best-effort
try/except (which is correct for resilience), this failure is **swallowed** — so the durable
persistence (the headline D-07 feature) can silently never write, and the only signal is a logged
exception. The column already has `DEFAULT now()` but defaults do not fire on UPDATE/upsert
conflict.

**Fix:** Omit `updated_at` from the payload and add a `BEFORE UPDATE` trigger (or
`updated_at` maintenance) in the migration, OR pass a real ISO timestamp computed in Python
(`datetime.now(timezone.utc).isoformat()`). Do NOT rely on the string `"now()"`. Add an assertion
in `test_latest_result_persists_after_run` that the persisted `updated_at` is a valid timestamp —
the current mock store accepts any payload, so this is invisible to the suite.

## Info

### IN-01: `_INFLIGHT_SKILLS` in-process set is dead weight now that the Redis claim is the gate

**File:** `backend/app/api/skill_tuner.py:91, 431, 477, 542`
**Issue:** Per the WR-01 (Phase 123) comment, the atomic Redis `SET NX` is the real gate and
`_INFLIGHT_SKILLS` is "ONLY a same-process fast-path hint." But nothing ever READS it as a fast
path — it is only `.add()`/`.discard()`-ed. It adds noise and a (harmless) leak risk if a task is
GC'd before `finally`. Consider removing it, or actually short-circuit on it before the Redis call
if the fast path is wanted.

### IN-02: Redundant `if description else description` ternary in `auto_seed_cases`

**File:** `backend/app/services/skill_tuner_service.py:253-254`
**Issue:** The paraphrase append is already inside `if description:`, so the inline
`... if description else description` ternary is unreachable in its false branch and just produces
a self-referential no-op. Simplify to the truthy branch only.

### IN-03: Duplicate `from app.config import get_model_capability` imports

**File:** `backend/app/services/skill_tuner_service.py:93, 167, 208` (and skill_tuner.py:56 imports it module-level)
**Issue:** `get_model_capability` is function-local-imported three times in the service (Pitfall-4
discipline is cited), but it is ALSO imported at module scope in the router (skill_tuner.py:56,
unused there since the router defers to the service). Confirm the module-level router import is
actually used; if not, drop it. The triple function-local import is acceptable per the stated
convention but could be a single module import in the service.

### IN-04: `seed_cases_with_provenance` re-derives sibling membership instead of reusing `auto_seed_cases`' decision

**File:** `backend/app/services/skill_tuner_service.py:298-321`
**Issue:** The provenance variant calls `auto_seed_cases` then RE-computes which `should_not`
entries were siblings by rebuilding `sibling_descs` and testing `p in sibling_descs`. This couples
two functions to the same membership rule (sib_desc present AND != this description); a future edit
to one will silently desync provenance. Consider having `auto_seed_cases` return the provenance
inline (or factor the membership test into one helper) so there is a single source of truth.

### IN-05: `previewModelCount` inherits the inflated persisted `target_count`

**File:** `frontend/src/pages/SkillTunerPage.tsx:336-339`
**Issue:** `previewModelCount` falls back to `latestRun?.target_count`, which (per WR-01) can be
inflated by unscored local-provider lanes. Once WR-01 is fixed at the source the preview corrects
itself; flagged here so the two are fixed together rather than masking each other.
