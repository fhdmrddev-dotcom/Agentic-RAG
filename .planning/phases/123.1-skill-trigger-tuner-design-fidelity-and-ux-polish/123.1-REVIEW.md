## Summary

Reviewed the gaps-only delta for the Skill Trigger Tuner. The honesty / unmeasured-cell work
(TT-05 / TT-12 / TT-15) is internally consistent and well-tested: `build_cell` returns the
`None` sentinel for empty axes, `cell_score` returns the stored value verbatim, `_run_tuner_job`
excludes all-error columns from `target_count`, and the frontend `TunerCell` type +
`ProviderScoreboard` render the unmeasured ("could not measure") branch faithfully. The
CR-01-class IDOR is NOT reintroduced — the new DELETE cancel route correctly orders
owner-verify → run↔skill bind before any side effect, and the tests
(`test_cancel_cross_user_returns_404`, `test_cancel_foreign_run_id_returns_404`) are non-vacuous
(they assert the cancel flag is never set and the unrelated claim is never released).

The one BLOCKER is in the in-flight-claim lifecycle: every release path blind-deletes the shared
`tuner_inflight:{skill_id}` key without checking it still belongs to the releasing run. Combined
with the cancel route releasing the claim immediately while the old job is still draining, a
dying run's `finally` can evict a *newer* run's claim — defeating the "exactly ONE in-flight job
per skill" DoS bound (T-123-04-02) the phase explicitly claims to hold. The remaining findings
are correctness/honesty edges, a type-contract gap, and consistency issues.

## Critical Issues

### CR-01: In-flight claim is released by blind DELETE — a stale run's `finally` can evict a newer run's claim (DoS-bound bypass)

**File:** `backend/app/api/skill_tuner.py:540` (also `:660`, `:925`)
**Issue:**
The in-flight guard is claimed atomically with `SET NX` and the claim VALUE is the owning
`run_id` (`skill_tuner.py:574-576`):

```python
claimed = await redis.set(_inflight_key(skill_id), str(run_id), nx=True, ex=_INFLIGHT_TTL_S)
```

But every release path deletes the key **unconditionally**, without verifying the stored value
still equals this run's id:

```python
# _run_tuner_job finally (:540)
await redis.delete(_inflight_key(skill_id))
# cancel_tuner_run (:925)
await redis.delete(_inflight_key(skill_id))
# spawn-error path (:660)
await redis.delete(_inflight_key(skill_id))
```

This is a non-owner-checked lock release. Concrete race that defeats the "exactly ONE in-flight
job per skill" bound (T-123-04-02 — the documented DoS guard, `skill_tuner.py:23-27`):

1. Run A claims the key (`= run_A_id`) and starts.
2. `DELETE …/tuner/runs/{run_A_id}` (cancel) passes both gates and `redis.delete`s the claim
   immediately (`:925`). Run A is only *cooperatively* cancelled — it keeps running until its
   next candidate/provider loop checkpoint (`:306` / `:329`).
3. Run B POSTs; its `SET NX` succeeds (key absent) → claim is now `= run_B_id`. Run B starts.
4. Run A reaches a checkpoint, observes the cancel flag, returns, and hits its `finally`, which
   `redis.delete`s `tuner_inflight:{skill_id}` — **evicting Run B's claim.**
5. Run C can now `SET NX` and start concurrently with the still-running Run B → two concurrent
   tuning runs for the same skill, each fanning out paid provider calls. The guard the whole
   `WR-01 SET NX` design exists to enforce is bypassed.

The same eviction happens without an explicit cancel: if Run A's job exceeds `_INFLIGHT_TTL_S`
(1800s) the claim expires, Run B `SET NX`-claims it, then Run A's late `finally` blind-deletes
Run B's claim. The existing tests (`test_cancel_owned_inflight_run_*`,
`test_run_stops_early_when_cancel_flag_preset`) only exercise single-run release, so they do NOT
catch the cross-run eviction.

**Fix:** Make every release a compare-and-delete so a run only releases its OWN claim. Use a Lua
CAS (atomic) — never a `GET`-then-`DELETE` (that re-introduces a TOCTOU):

```python
_RELEASE_IF_OWNED = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
"""

async def _release_inflight_if_owned(redis, skill_id: str, run_id) -> None:
    try:
        await redis.eval(_RELEASE_IF_OWNED, 1, _inflight_key(skill_id), str(run_id))
    except Exception:
        logger.exception("tuner inflight CAS-release failed (skill %s)", skill_id)
```

Call `_release_inflight_if_owned(redis, skill_id, run_id)` in the job `finally`, the cancel route
(it already knows the bound `run_id`), and the spawn-error path. Add a regression test: claim as
run A, simulate run B re-claiming, run A's `finally`, then assert run B's claim survives.

## Warnings

### WR-01: Cooperative cancel releases the claim before the job stops — a retry can run concurrently with the draining run

**File:** `backend/app/api/skill_tuner.py:920-926`
**Issue:** Even after CR-01 is fixed, `cancel_tuner_run` releases the in-flight claim
immediately, but the background job only stops at its next candidate/provider loop checkpoint —
which can be a whole provider column of paid `classify_fires` calls later (`_run_tuner_job` reads
`_cancel_key` only at the candidate-loop top `:306` and the provider-loop top `:329`, never
inside the per-case × per-repeat inner loops `:363-403`). Between the immediate claim release and
the old job actually stopping, a retry POST can start a second run for the same skill — so the
"exactly ONE in-flight job" invariant is violated for that window, and the cancelled-but-draining
run keeps burning the very paid calls the cancel was meant to stop.
**Fix:** Either (a) keep the claim until the job's `finally` actually CAS-releases it (a retry
409s briefly until the old job drains — honest), or (b) add a cancel checkpoint inside the
per-case loop so a cancel stops within one case rather than one whole column. Update the route
docstring, which currently promises "releases the in-flight claim immediately so a retry no
longer 409s" — exactly what creates the overlap.

### WR-02: `auto_seed_cases` does not de-dup sibling descriptions, so the cap count and the reported `total` can disagree

**File:** `backend/app/services/skill_tuner_service.py:313-322` vs `:389`
**Issue:** `auto_seed_cases` builds `sibling_sourced` as a plain list (no de-dup) and caps with
`sibling_sourced[:MAX_SEEDED_SHOULD_NOT]`. But `seed_cases_with_provenance` computes the "full
uncapped" `should_not_total = len(sibling_descs)` where `sibling_descs` is a **set** (de-duped,
`:364-370`). When two owner/global siblings share an identical description (common boilerplate),
the capped list counts the duplicate while `total` counts it once. The editor's honest-cap banner
math (`shownSiblingCount` vs `seededNotTotal`, `CaseEditor.tsx:171-172`) then renders an
inconsistent "showing N of M" — N can exceed the true distinct M, or the banner suppresses when
it should show. The run path (`auto_seed_cases`) and the GET-seed path therefore operate on
different effective sets.
**Fix:** De-dup `sibling_sourced` preserving order before the cap in `auto_seed_cases` (mirror
the `seen: set` de-dupe used for candidates at `skill_tuner.py:284-291`), so the run path, the
GET seed, and `should_not_total` all agree on the distinct set.

### WR-03: `previewModelCount` can over-state the scored set vs the actual run (no MAX_TARGETS clamp; hand-mirrored provider set)

**File:** `frontend/src/pages/SkillTunerPage.tsx:234-237, 472-475`
**Issue:** The pre-run cost preview counts `settings.providers.filter(p => p.has_key &&
REPRESENTATIVE_PROVIDER_IDS.has(p.id)).length`. The backend additionally caps at `MAX_TARGETS`
(8, `skill_tuner.py:67`), and `REPRESENTATIVE_PROVIDER_IDS` (`SkillTunerPage.tsx:63-72`) is a
hand-maintained frontend mirror of `_REPRESENTATIVE_MODEL` (`skill_tuner_service.py:554-571`). If
an org has >8 configured keyed providers, the preview shows the full count while the run scores
only 8 — the "× N models" line over-states what runs (the exact honesty class TT-12 closes on
the backend side). The mirror set also silently drifts if `_REPRESENTATIVE_MODEL` gains/loses a
provider.
**Fix:** Clamp the preview to `MAX_TARGETS` (`Math.min(count, 8)`), and prefer the authoritative
`started.targets.length` once a kickoff returns it (already done for the in-flight case at
`:472-475` — extend the same precedence pre-run where feasible). Consider exposing the backend
representative-provider set (or a `configured_targets` dry-run count) so the mirror can't drift.

### WR-04: `ProviderLane.score` typed `number | undefined` but assigned `cell.score` which is `number | null`

**File:** `frontend/src/pages/SkillTunerPage.tsx:291` (`score: cell.score`) vs
`frontend/src/components/skills/tuner/LiveRunCard.tsx:30`
**Issue:** `onProviderDone` writes `{ ...l, status: "done", score: cell.score }` where
`cell.score` is now `number | null` (api.ts `TunerCell.score`), but `ProviderLane.score` is
declared `score?: number` (i.e. `number | undefined`, NOT `| null`). At runtime an all-error
provider cell (`score: null`) flows into the lane as `null`; `LiveRunCard.tsx:112`
(`lane.score != null ? lane.score.toFixed(2) : "done"`) guards it, so this is not a crash today —
but the type contract is wrong, and a future `.toFixed()` without the guard would NPE on the
all-error path the TT-12 work just made reachable.
**Fix:** Widen `ProviderLane.score` to `score?: number | null` (keep the `!= null` guard), or
coerce at the assignment: `score: cell.score ?? undefined`.

### WR-05: An all-unmeasured / cancelled-then-partial run still picks and badges a "winner" from a degenerate signal

**File:** `backend/app/api/skill_tuner.py:429-435, 459-465`; `skill_tuner_service.py:541-549`;
`frontend/src/pages/SkillTunerPage.tsx:643-657`
**Issue:** When every candidate scores on zero measured columns (e.g. all providers all-error),
`held_out_score` falls back to `0.0` for every candidate (`:434`), and `pick_winner`
(`max(..., key=held_out_score)`) returns candidate index 0 (the baseline) with a 0.0 signal. The
scoreboard still sets `winner_index` / `winner_description`, and the UI badges a "winner"
(`isWinner={candidate.index === scoreboard.winner_index}`) over a wholly-unmeasured run — the
same lie TT-12 closes for cells, leaking back at the candidate/winner level. The author could
then confirm a "winner" chosen by noise via the PATCH write.
**Fix:** When no candidate has any measured cell, set `winner_index = None` (distinguish a real
0.0 candidate from an unmeasured one the way `build_cell` distinguishes cells), and have the UI
suppress the winner badge + the "Use"/confirm strip, rendering "could not measure — no winner"
alongside the per-cell unmeasured rows.

### WR-06: Frozen elapsed timer reads the last interval `now`, not the true finish time (under-reports up to ~250ms)

**File:** `frontend/src/components/skills/tuner/LiveRunCard.tsx:53-60`
**Issue:** The "never-vanishes" timer freezes by stopping the 250ms interval when
`phase !== "running"` (`:54-58`), then renders `elapsedS = (now - startTs)/1000` using the last
`now` state value — which can be up to ~250ms stale relative to the actual phase flip, so the
frozen elapsed under-reports. Minor for a tuner, but it contradicts the "honest elapsed" intent
the docstring cites (the 095 never-vanishes lesson).
**Fix:** On the running→non-running transition, capture a one-shot `frozenAt = Date.now()` and
render `(frozenAt ?? now) - startTs` while frozen, so the displayed elapsed is the actual finish
delta.

## Info

### IN-01: `except (asyncio.TimeoutError, Exception)` is redundant and masks partial-raise programming errors as did-not-fire

**File:** `backend/app/api/skill_tuner.py:275`, `:380`
**Issue:** `asyncio.TimeoutError` subclasses `Exception`, so the tuple is redundant. More
substantively, the broad catch around `classify_fires` treats most runtime errors as
"did-not-fire"; TT-12 now counts an ALL-raise case as unmeasured, but a *partial* raise is still
silently a false "did-not-fire" decision (a programming error in `classify_fires` would surface
as a benign low recall, not a failure).
**Fix:** Drop the redundant `asyncio.TimeoutError`; consider logging at WARNING when the raise
isn't a timeout so real bugs surface.

### IN-02: Cancel latency is bounded by `target_timeout × DEFAULT_REPEATS` per remaining case in the current column, not instantaneous

**File:** `backend/app/api/skill_tuner.py:888-926`
**Issue:** The docstring says "this route does not need to kill the task" — correct for the
cooperative model, but the running job keeps emitting / billing until it reaches the next loop
checkpoint. `asyncio.wait_for` bounds each call so it can't wedge forever, but the cancel is not
immediate.
**Fix:** None required; document the worst-case cancel latency in the route docstring so an
operator isn't surprised the run keeps going for a few seconds after DELETE returns.

### IN-03: `main.py` langsmith log suppression is a process-wide side effect at import time

**File:** `backend/app/main.py:33`
**Issue:** `logging.getLogger("langsmith").setLevel(logging.ERROR)` (TT-10) silences langsmith
WARNINGs process-wide, not just during tuner runs — a genuine non-429 langsmith
mis-configuration WARNING is now hidden too. The comment acknowledges the trade and points to
the `LANGSMITH_TRACING_SAMPLING_RATE` env knob.
**Fix:** None required; if finer control is wanted later, filter on the 429 message rather than
raising the whole logger's level.

### IN-04: Decorative-pane removal in SkillsPage is an unscoped visual change in a backend-heavy phase

**File:** `frontend/src/pages/SkillsPage.tsx:68-72`
**Issue:** The diff removes the decorative `w-16` left pane. Likely a deliberate layout fix for
the full-width tuner surface, but it's an unscoped layout change riding in a gap-closure phase —
it could shift the 3-pane Skills layout a lived-experience UAT would catch.
**Fix:** None required; confirm via the phase's UI UAT that the Skills list still aligns flush
against the NavPanel as the comment claims.
