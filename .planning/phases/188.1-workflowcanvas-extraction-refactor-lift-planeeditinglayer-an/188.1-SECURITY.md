## T-188.1-03 (UF-1) — the accept-and-register entry, in full

**The finding, verbatim from `188-SECURITY.md` § UF-1 and confirmed still present at HEAD:**

`last_workflow_run_id: UUID | None` is declared on `ThreadWorkflowState` at
`backend/app/models/thread.py:115` and populated at `backend/app/api/threads.py:1267`, shipping on
`GET /threads/{thread_id}/workflow` (`backend/app/api/threads.py:1036`). That path is **not** a
member of `CANVAS_GATED_PATHS` (`backend/app/middleware/canvas_gate.py:85-92`, whose three members
are `/workflows/validate`, `/workflows/grounding-bundle` and
`/workflow-runs/{workflow_run_id}`). So with `visual_workflow_canvas` OFF, an owner can still learn
that a `workflow_runs` row exists for their own thread and obtain its id, even though
`GET /workflow-runs/{id}` answers 404.

**Disposition: `accept` + register. Assessed LOW.**

1. The route is **ownership-gated first** — its own docstring at `backend/app/api/threads.py:1043-1044`
   states *"Ownership-gated FIRST (T-092-04 — 404, never leak existence)"*.
2. The id disclosed is the **caller's own**.
3. The sibling fields `latest_producer_run_id` and `phases` on the *same response model*
   (`backend/app/models/thread.py:100`, `:120+`) already disclosed workflow-run existence through
   this endpoint **before** Phase 188. No *new class* of information crosses the boundary.
4. The field is additive, optional, and sourced from a value the handler had already computed —
   `backend/app/models/thread.py:101-114` records *"no new query, no write"*, and the inline comment
   at `backend/app/api/threads.py:1262-1266` says the same at the assignment site.

**NO CODE CHANGE was made, and that is a phase gate, not a preference.** SC#6 asks for
REGISTRATION; re-gating is D7.

```
$ git diff --stat -- backend/ supabase/migrations/ frontend/package.json frontend/package-lock.json
(0 files changed)
```

**Why re-gating is deferred (D7), with its trigger.** Adding `/threads/{thread_id}/workflow` to
`CANVAS_GATED_PATHS` is a **backend behaviour change on an endpoint the client depends on** — the
frontend calls `getThreadWorkflow` on every (re)connect and thread switch to reconcile the
per-thread lock and Continue affordance, and CR-05's own commit message calls this endpoint's
un-gated status load-bearing. Gating it would 404 a read the pre-canvas product served.
**Re-open trigger:** the endpoint gains a field disclosing something the pre-canvas product did not
expose, **or** the visibility model changes. Recorded in `188.1-DEFERRED.md` as D7.

**What a verifier should check rather than take on trust:** that the field is still populated from
`phases_source_run_id` (an already-resolved value) and not from a second query, and that
`CANVAS_GATED_PATHS` still has exactly three members.
