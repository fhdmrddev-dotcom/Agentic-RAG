# Phase 188.1 Plan 02: Capture the editing affordances' pre-move rendered shape — Summary

Captured the `＋` / `✕` / picker layer's rendered `style`, `class` and `aria-*` off the tree as it
ships and committed the 12-entry literal as a baseline — so plan 188.1-03's move has something to be
*identical to*, and observed it go red against three deliberate one-unit changes to
`EDIT_AFFORDANCE` so the fence is around geometry rather than around presence.

## What Was Built

**Task 1 — the capture and its baseline** (commit `91f104c1`, 234 insertions / **0 deletions**)

A module-scope `AFFORDANCE_SHAPE(container)` selects every element matching
`[data-testid^="canvas-insert-"]`, `[data-testid^="canvas-remove-"]` and
`[data-testid="canvas-insert-picker"]`, maps each to `{ testid, class, style, ariaLabel,
ariaExpanded, ariaHaspopup }`, and **sorts by `data-testid`** before returning. The sort is the point:
it makes the result independent of jsdom's DOM traversal order by construction, which retires research
assumption **A6** outright rather than betting on the two agreeing runs alone.

One render drives the whole moved surface at once:

| Requirement | How it was met |
|---|---|
| ≥ 3 phases so `insertPointX` sees all three branches | `evalCoverage` (5 phases ⇒ 6 boundaries: index 0, four middles, tail) |
| a NON-ZERO `nudges` entry | `{ fanout: 48 }` — `verticalOffsetFor` then returns **three** distinct numbers (48 for that card's ✕, 24 for the two `＋` that straddle it and for the picker, 0 elsewhere) instead of one |
| the picker OPEN, driven per the suite's driver rule | `fireEvent.click(screen.getByTestId("canvas-insert-2"))` — a real event on a real middle-boundary `＋`, never a prop poke |

The baseline literal was produced by **running** the capture on the unchanged tree and pasting what it
printed (a temporary `console.log` probe, removed before commit). Not one number was typed from the
source. Above it sits a `//`-register docblock stating that it is a CAPTURE of the behaviour as it
stands at this commit (the tree Phase 188 closed at `7e1bff34`), that it was observed twice, and — in
so many words — that **a diff against it after Plan 03 is a behaviour change and not a test to update**.

Non-vacuity control, in the same `it(` and asserted *before* the deep-equal: the array is non-empty,
contains ≥ 1 `canvas-insert-\d+`, ≥ 1 `canvas-remove-`, and **exactly one** `canvas-insert-picker`.

The block was inserted **above** the shipped accumulated-belt describe rather than appended at EOF, so
that block keeps the property its own comment claims — declared last, therefore run last, therefore its
zero-fetch total covers this plan's render too.
