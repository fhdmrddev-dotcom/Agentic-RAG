## Summary

This phase is a **pure code move plus three bounded security fixes**. There is no new
capability, no schema, no endpoint, no glyph and no design decision. The research question is
therefore not "what should we build" but "**what will break if we move this code, and how do we
prove nothing changed**".

The good news, measured rather than assumed: **the seam is genuinely clean.** `PlaneEditingLayer`
and `EDIT_AFFORDANCE` — together with `REVEAL_ON_HOVER`, `insertPointX` and `verticalOffsetFor`,
which are used by nothing else in the tree — form a contiguous, self-contained region that
imports **nothing** from `WorkflowCanvas` and is imported **from** `WorkflowCanvas` only at one
JSX site plus one test import. The proposed new module has **no path back** to `WorkflowCanvas`
in its transitive import graph, so SC#3's ESM-cycle constraint is satisfied by construction, not
by care.

The risk is concentrated in three places nobody would find by reading the roadmap:

1. **Source fences narrow silently when code leaves the file they grep.** Ten `?raw`-based
   assertions across three suites grep `WorkflowCanvas?raw` for forbidden strings. Every one of
   them stays *green* after the move while covering *less code* — the same class of failure as
   Phase 188's F7 lesson ("an invariance fence on a shared component says nothing about
   reachability"). This is the real SC#5 hazard, and it is **not** the count gate.
2. **`noUnusedLocals: true` will red the typecheck** unless exactly three imports are dropped
   from `WorkflowCanvas.tsx` in the same commit (`CANVAS_LAYOUT`, `ViewportPortal`,
   `useStore as useFlowStore`). Every other import survives the move and must be kept.
3. **A shipped source fence forbids the obvious form of the WR-04 fix.**
   `PhaseNodeCard.test.tsx:373` is a *positive control* requiring the literal bracket-index form
   `ICON_TINT[` to exist in `PhaseNode.tsx`. Rewriting site 1 as `own(ICON_TINT, …)` turns that
   test red. There is a fix shape that keeps it green — see Pitfall 3.

One measurement corrects the roadmap in the phase's favour and one against it: `eslint` **already
errors today** at `WorkflowCanvas.tsx:365` (`react-refresh/only-export-components` on
`export const EDIT_AFFORDANCE`), which makes a **two-module split** strictly better than a
one-module split; and the `WorkflowCanvas` lazy chunk **no longer exists at all** — `vite build`
emits `[INEFFECTIVE_DYNAMIC_IMPORT]` and everything now lives in a 2,041 kB `index-*.js`.

**Primary recommendation:** extract into **two** new files —
`frontend/src/components/workflows/editAffordance.ts` (the pure geometry + helpers, a true leaf
module with zero component imports) and `frontend/src/components/workflows/PlaneEditingLayer.tsx`
(the component) — move the code **verbatim**, drop exactly three imports, extend every narrowed
source fence to the new module *in the same commit*, and prove behaviour identity with a
**rendered-DOM before/after capture** rather than with new behavioural assertions. Leave the
`WorkflowRunPage` static-import defect alone (see Open Question 1).

SC#3 is currently a *rule in a document*. Make it a test, in the house `?raw` idiom already used

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Proving "nothing changed" in the rendered output | A hand-typed list of expected DOM attributes | **Capture the rendered DOM twice from the same test run** — the 185-10 idiom (`185-10-SUMMARY.md:104-112`): render the same probe harness before-shape and after-shape in one process and compare | *"A hand-typed baseline `d` proves only what the author believed."* A captured baseline cannot encode an author's mistaken belief. |
| Detecting a deleted/relocated test | A failures-only diff, or eyeballing counts | `node scripts/vitest-count-gate.cjs` | Phase-177 lesson, encoded in the script header: a failures-only differential **cannot see a deleted test**. |
| Detecting a scope violation in the new module | A code-review checklist item | The `?raw` + grep house idiom, **with a positive control** | Ten suites in this tree already do this. A fence with no positive control can pass vacuously. |
| Prototype-key totality (WR-04) | A bespoke `if (key === "constructor" \|\| …)` deny-list | `Object.prototype.hasOwnProperty.call` / `Object.hasOwn` | `project_185_secured` memory: *"a deny-list can't be made fail-closed by extension."* `phaseState.ts:77` is the shipped precedent. |

**Key insight:** every guard this phase needs already exists somewhere in this tree. The phase's

## Common Pitfalls

### Pitfall 1: Source fences narrow silently — the real SC#5 hazard

**What goes wrong:** Ten assertions across three suites grep `WorkflowCanvas?raw` for forbidden
strings. When 311 lines leave that file, every one of them **still passes** while covering less
code. The count gate stays green, `tsc` stays at 33, and coverage has quietly shrunk. SC#5 says
*"no loss of coverage"* — this is the loss it will not see.

**Why it happens:** a `?raw` fence's scope is *the file*, not *the behaviour*. Phase 188 shipped
the same class of error and named it F7: *"an invariance fence on a shared component says nothing
about whether its output is REACHABLE on a new surface."*

**Complete inventory, measured this session:**

robust form:

```typescript
// One needle set, three sources — so a fence can never be satisfied by code simply moving.
const CANVAS_SUBTREE_SOURCE = [
  workflowCanvasSource,
  planeEditingLayerSource,
  editAffordanceSource,
].join("\n")
```

…and point every **negative** assertion at `CANVAS_SUBTREE_SOURCE` while leaving every **positive**
assertion pointed at the file that must actually contain the string. Editing an assertion's
*subject* is not a count change, so the count gate is unaffected.

**Warning signs:** a fence-bearing test file appears in the diff with **no** count change and
**no** subject change — that means a fence was moved past without being re-scoped.

### Count-gate mechanics for SC#5 — the exact answer

**Which glob does a new file at the proposed path fall under?** `TARGETS[0]` is the **bare
directory** `"src/components/workflows"` (`vitest-count-gate.cjs:403`). A new suite at
`frontend/src/components/workflows/PlaneEditingLayer.test.tsx` is therefore **inside `TARGETS`
automatically — no `TARGETS` edit is required, and none should be made.** It would report as
`new` in the `actual` column and be **unpinned**, which 188-12's doctrine calls *unguarded*, so it
would need a `BASELINE` entry at its measured `actual`.

**The recommended path avoids the whole question: add NO new test file.**

Every existing assertion over `PlaneEditingLayer` reaches it *through* `<WorkflowCanvas editable>`
— the component is not exported today, so no suite imports it directly. After the move it is still
rendered by `WorkflowCanvas` at the same JSX site, so **every existing test passes unchanged with
zero edits**. Consequently:

| Knob | Edit required? |
|---|---|
| `TARGETS` | **None.** Both new modules and any new suite live under the existing bare-directory entry. |
| `BASELINE` | **Only EXTENSIONS**, never a lowering. `WorkflowCanvas.test.tsx` 46 → measured actual (cycle fence + SC#4 re-verification); `WorkflowCanvas.editing.test.tsx` 57 → measured actual (the `AFFORDANCE_SHAPE` capture); `PhaseNodeCard.test.tsx` 105 → measured actual (WR-04 falsifications). |

**⚠ A gap in the gate script's own doctrine the planner must handle explicitly.** The script header
(`:82-86`) recognises exactly two pin movements: **LOWERED** (requires a deliberate deletion riding
the same commit) and **EXTENDED** (no deletion needed). A **RELOCATION** — the same test living in
a different file — is neither, and would present as a `[count-decrease]` on the source file
alongside a `new` file. If the plan chooses to move any test, it must (a) lower the source pin and
raise/create the destination pin **in the same commit**, keeping `BASELINE_TOTAL` constant, and
(b) add a third named case to the script's header block so the next reader is not forced to
reason it out. **The recommendation is to avoid relocation entirely** — then this gap never opens.

**Rule for every pin number:** read it from the script's own printed `actual` column across **two
agreeing runs**, never from a hand count of `it(` literals (unsound under `it.each` —
`definitionOps.test.ts` declares ~122 and runs 232) and never from a planning document.
