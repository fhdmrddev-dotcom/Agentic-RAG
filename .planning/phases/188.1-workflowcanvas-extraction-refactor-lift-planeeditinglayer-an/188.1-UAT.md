### F-1 — a *selected* card occludes its own `✕` (PRE-EXISTING, not a 188.1 regression)

Mechanism, measured:

- `✕` affordances render inside `.react-flow__viewport-portal` at `z-index: auto`.
- xyflow elevates a **selected** node to `z-index: 1000`.
- With "Fill compliance-gap-report.docx" selected (`.selected`, `z-index: 1000`),
  `elementFromPoint` at that card's `✕` centre returned
  `DIV.mx-auto block w-[248px] rounded-[22px] …` — the `PhaseNodeCard` itself,
  not the `✕`. Reachable: **false**.
- Deselecting (all nodes back to `z-index: 0`) → the same `✕` returns
  `SPAN` inside the button. Reachable: **true**.

Consequence: because clicking a card is *how* it becomes selected, the natural
flow "click the card, then click its `✕`" is not completable with a real pointer.
Note this is invisible to `.click()` (which bypasses hit-testing) and to every
unit test — it is precisely the class the `WorkflowCanvas.tsx:390-410` incident
records.

**Not introduced by this phase.** `git show 14917821^` (pre-extraction) and the
shipped `PlaneEditingLayer.tsx` both render through `<ViewportPortal>` with **no
`zIndex` set in either version**, and `188.1-02`'s `AFFORDANCE_SHAPE_BASELINE`
still deep-equals. Disposition: file as a reported bug with a re-open trigger;
it does not block this refactor.

### F-2 — affordances scale with zoom rather than holding constant size (observation)

The row's step 5 expects the affordances to "keep a constant on-screen size".
Measured, they do not — only the picker counter-scales:

| zoom | `＋` on-screen width | `✕` on-screen width |
|---|---|---|
| 1.690 | 43.9 px | 40.6 px |
| 0.472 | 12.3 px | 11.3 px |

At 0.472 the `＋` is 12.3 px, well under a 44 px tap target; at ~0.3× it would be
~8 px. Again **not a regression** — geometry is unchanged per the deep-equalling
baseline — so this is a shipped-behaviour observation, and the row's stated
expectation appears to have been wrong about the affordances (it is right about
the picker). Recorded so the next reader does not treat the mismatch as new.

### F-3 — the run surface rendered its status twice (FIXED in this phase)

Reported by the operator from the same screenshot: `✓ Complete · Ran for 2m 18s`
sat directly beneath `✓ Complete   Ran for 2m 18s — from when it was queued to
its last update`.

Cause: `band.sentence` rendered at `WorkflowRunPage.tsx:888` (the header, the
visual channel) **and** again at `:921` inside the `aria-live="polite"` region
(the announcement channel). Both blocks are `shrink-0` in a flex column, so
neither ever scrolled away — the duplication was permanent on every run surface.

Fixed under G-3 as a defect, not a layout change: the polite region became
`sr-only`, which removes the duplicate while keeping the announcement behaviour
exactly as designed. Regression guard added and **observed RED first** (reverting
`sr-only` fails with `expected [...] to have a length of 1 but got 2`). Gate
re-pinned from the run's own output: 2477/2477, 45/45, failed 0; `tsc` 33
unchanged.

### F-4 — dead space above the spine (NOT fixed; deliberately out of scope)

Same screenshot: a large empty band above and below the two step cards.

Diagnosed, not a bug: `WorkflowCanvas` uses `fitView` with `padding: 0.1` and
`maxZoom: 2`, while the run page's canvas region is `min-h-[320px] flex-1` and so
claims all leftover vertical height. A horizontal spine is inherently wide and
short (~700 × 150 for this run) inside a ~1790 × 520 container, so `fitView`
centres it with large vertical margins and the 2× cap prevents it filling.

Improving it is a **layout/density decision**, not a fix — the options (size the
canvas to content and give the height to the deliverable region, raise `maxZoom`,
pad asymmetrically) each change how the surface feels. Under **G-2** that wants a
sketch before code, and under this phase's own charter a refactor phase ships no
new user-facing capability. Deliberately left alone; carried as owed design work.
