<objective>
Teach the transport client the token and the two refusals it has been throwing away.

Purpose: `updateWorkflowDraft` currently reads `res.status === 409` and **discards the body**
(`api.ts:3353`), so a second 409 cause is invisible; and it has no 422 branch at all, so a
shape rejection becomes a generic `Error`. D-186-04 and D-186-09 both need named errors here.

Output: `token` on the draft wire types, an `If-Match` header on the PATCH, and three named
errors the hook can branch on by `name` — `WorkflowStaleTokenError` (new, carries the current
token), `WorkflowConflictError` (unchanged, now the fallback for any 409 the client cannot
classify), and `WorkflowDraftUnreadableError` (new, 422).

This plan runs in parallel with 186-02; the two share no files. Both are written against the
wire contract fixed by 186-01 — see `<interfaces>`.
</objective>

<interfaces>
The server contract this client is written against (fixed by 186-01):

| Response | Shape |
|---|---|
| `POST /workflows` 201 | `{ id, version, token }` |
| `PATCH /workflows/{id}` 200 | `{ id, version, token }` — the token is the POST-write value; chain it into the next PATCH |
| `GET /workflows/drafts` 200 | `[{ id, slug, version, name, definition, token }]` |
| `PATCH` 409 stale | `{ detail: { code: "stale_token", message: string, token: string } }` |
| `PATCH` 409 published | `{ detail: { code: "already_published", message: string } }` |
| `PATCH` 404 | `{ detail: "draft not found" }` (string) |
| `PATCH` 422 | FastAPI's own validation body |

Request: the token travels as the **`If-Match` header**, optional server-side for this
release. The client always sends it when it has one.

Shipped shapes to copy (all in `frontend/src/lib/api.ts`):

  the HTTP cause, `this.name` set explicitly (that name is what every consumer branches on)
- `WorkflowValidateUnreadableError` at `:3445-3467` — a 422 error that logs the raw body ONCE
  at the boundary and carries a FIXED business-plain message with nothing interpolated
- `publishWorkflow`'s WR-02 malformed-body guard at `:3623-3634` — verify the shape, else

internal field paths and framework phrasing; pretty-printing it onto an authoring surface
aimed at business users would leak implementation detail and still not say what to do.

Rewrite `updateWorkflowDraft`'s 409 arm to READ the body (it currently throws it away):

generic `!res.ok` arm untouched.

the rule for `Verdict.code` and it applies here: the SERVER owns the refusal vocabulary; the
client renders what arrives and fails closed on what it has never seen.
