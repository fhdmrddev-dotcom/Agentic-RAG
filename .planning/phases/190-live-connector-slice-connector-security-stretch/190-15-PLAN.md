<!-- UI-SPEC §5a, the reasoning table for door (b) — quoted because it is the part most likely
     to be "improved" back into an absolute: -->

| | |
|---|---|
| What door (b) means | A `connection_id` write naming a connection whose last check failed is **accepted** by the server. A direct API call, a picker regression, or a check→bind race can therefore produce a binding the picker itself would not have offered. |
| Why that is acceptable | **Blocking the bind prevents no send.** A bound-but-failing connection fails honestly on the next run with the host's verbatim words — the run surface, not the picker, is the surface that must not lie. The failing-verdict rule is a **quality hint**, not an authorization boundary; every actual boundary (org scoping, `is_enabled`, the egress guard, the armed approval) **is** server-enforced. |
| The decisive cost of door (a) | §2b makes **check admin-only** while **bind is org-wide**. A server bind-gate on `last_check_verdict` would hard-block a plain member holding a stale-`failed` verdict on a credential that has since been fixed — and they could not clear it themselves, because they cannot run the check. |

**Reversing to door (a)** is a one-line server change plus a one-clause copy change, and both
must land **in the same commit** (U-07a). A gate without the copy under-claims; the copy without
the gate is the §5 defect.

**What the gates deliberately do NOT do at run time:** they do **not** block a run on a stale
`last_check_verdict`. A verdict from two days ago deciding a live run is exactly the
settings-sync-staleness class this codebase has already been bitten by, and a credential rotated
since the check would be refused while working perfectly. **At run time the executor attempts
the send and reports the true outcome.**

**UI-SPEC §5c's success headline is load-bearing and verbatim:**
```
✓  Credential works — and nothing was sent
    Authenticated as {identity} at {host}:{port}. The check connected, authenticated
    and disconnected. No mail was delivered to anyone.
    Checked just now · re-checking is always safe.
```
The closing negation is picked from the **same closed table 189 §9d already ships**:
`send_email` → `No mail was delivered to anyone.` · `create_ticket` → `No ticket was created.` ·
`post_message` → `No message was posted.`

**dedicated action, not a query param on the read**, because it has a side effect: it writes
`last_checked_at` and `last_check_verdict`.

- **Org-admin only**, same `org:manage` gate as the other writes (UI-SPEC U-02). ⚠ Note in the

  decided door (b) in §5a. A reader who does not know that will "fix" Gate 2 later.

  id, org_id=<caller's org>)` — the same org-scoped resolver D-14 protects — and never accept a
  secret in the request body. No plaintext secret crosses the wire for a non-storage purpose.
- Dispatch to `registry.get_adapter(capability).check(...)`, which authenticates and
  disconnects.
- Persist the verdict: `ok` → `last_check_verdict = 'ok'`, failure → `'failed'`, and
  `last_checked_at = now()` either way.
- Return a structured result carrying `ok`, the authenticated `identity`, the destination
  `host:port`, and the provider's message **verbatim** on failure (071-A). Do NOT author a
  user-facing sentence here — the panel composes it from the exported identifiers in plan
  190-18.
- Map failures into UI-SPEC §4d's three buckets: an `EgressRefused` → `refused`, a transport
  miss → `unreachable`, an auth rejection → `rejected`. Three states, three next steps.

In `connector_service.py`, add `record_check_verdict(connection_id, org_id, verdict)` and make
`update_connection` reset `last_check_verdict` to `not_checked` in the SAME UPDATE whenever the
secret is replaced (research OQ#4 — one column, zero ambiguity). The panel says so, so the
server must do it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| typed form → the wire | The check must run on the STORED connection; a form-driven check would put a plaintext secret on the wire for a non-storage purpose |
| a stale verdict → a live run | A two-day-old verdict deciding a run is the settings-sync-staleness class this codebase has already been bitten by |
| copy → enforcement | A sentence claiming more than a gate delivers is the §5 defect this plan exists to close |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-190-15-CHK | Information disclosure | the check route | mitigate | Runs on the STORED connection through the org-scoped resolver; a source/signature assertion proves the route accepts no secret in its body |
| T-190-15-SEND | Repudiation | `check()` | mitigate | Parametrised across all three capabilities with the transport recorder armed: no `chat.postMessage`, no issue POST, no SMTP `DATA`. UI-SPEC §5c's negation is proved, and its wording comes from 189 §9d's closed table |
| T-190-15-U07a | Repudiation | Gate 2's reach | mitigate | `last_check_verdict` asserted ABSENT from the executor; door (b) asserted as a POSITIVE test so a later server bind-gate fails loudly instead of silently contradicting the copy. The reversal contract (both halves, one commit) is recorded |
| T-190-15-STALE | Denial of service | run-time gating | mitigate | A failed verdict blocks neither the bind nor the run; the executor attempts and reports the true outcome. A rotated credential is never refused by an old verdict |
