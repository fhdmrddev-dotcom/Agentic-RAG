Checked against the sketch-findings skill at plan time, which is the design contract for this
surface:

- `references/node-vocabulary-and-reveal.md` §"The derivation" lists the ladder as
  `bound skill → template → folder → **human input → "Wait for your approval"** → null`, i.e. the
  human-input sentence is a **derivation tier** in the winning variant, not a replacement for the
  type sentence.
- The sketch 148 source itself keeps BOTH strings: its `PHASE_TYPE_SENTENCES` map still spells
  `llm_human_input: 'Check with you'` while its derived-title function returns
  `'Wait for your approval'` for the same type. Fix (b) would edit a locked D-183-06 vocabulary
  value AND delete a tier the design contract names — that is changing the design to hide a
  consumer bug.
- Fix (a) leaves both strings exactly where the sketch puts them and repairs the ACTUAL defect: a
  consumer reading the map directly instead of asking the resolver.

**The change is provably confined to one row.** Traced at plan time: with no name context,
`nodeTitle` over a bare phase resolves tier 1 (no stored name) → `derivedFaceOf` (no `skill_ref`, no
`templateFilename`, no `folder_scope`) → `null` for five types, then `PHASE_TYPE_SENTENCES[type]`.
Only `llm_human_input` reaches `derivedFace` tier (4). So five of six rows must come out
byte-identical, and the tests assert that explicitly as the change's own blast-radius control.

**The picker previews the phase it will actually cause to be created.** Rather than a hand-built
literal, the row resolves `nodeTitle(definitionOps.minimalPhaseFor(type, …))` — the same builder the
picker's own docblock says the CALLER uses after `onChoose`. That makes the row a preview of the
real card rather than of an approximation of it, and it introduces no new module edge (the picker
already imports from `definitionOps`).
