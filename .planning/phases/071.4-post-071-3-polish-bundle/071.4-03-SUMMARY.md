## Accomplishments

1. **Diagnosed the actual gap.** Original bug report said "status stays on pending"; operator clarified mid-investigation that status WAS updating via Realtime — what's NOT updating in real-time are the **table/image/chunk counts**. The Realtime payload `payload.new` is exactly the `documents` table row; the aggregates (`table_count`, `image_count`, `chunk_count`) are derived server-side from joins in `listDocuments` and never appear in Realtime.

2. **Spread-merged UPDATE handler in `useDocuments.ts`.** Replaced `prev.map(d => d.id === newDoc.id ? newDoc : d)` with `prev.map(d => d.id === newDoc.id ? { ...d, ...newDoc } : d)`. The spread preserves the prior fetch's aggregate fields until the next refetch overwrites them. Without this, every UPDATE would temporarily zero out the count badges.

3. **Terminal-state refetch.** On UPDATE events where `newDoc.status` ∈ {`completed`, `failed`}, the handler calls `loadDocuments()` to pull fresh aggregates. Cheap heuristic: aggregates only change at terminal states (after the BackgroundTask finishes inserting all child rows), so refetching on intermediate states would be wasted bandwidth.

4. **Per-row Reingest button on DocumentList.** Added next to the existing Delete button. RefreshCw icon, tooltip "Re-ingest document", disabled while `status === 'pending' || status === 'processing'` or while a reingest is in flight on this row. Calls the existing `reingestDocument` API client. No confirm dialog (Documents is the primary workspace; friction would hurt UX).

5. **Live-verified via Chrome DevTools MCP.** Clicked Reingest on the user's thesis DOCX:
   - Status badge transitioned `Extracting images` → `completed` over ~39 seconds via Realtime (no manual refresh).
   - Counts stayed correctly at **39 tables / 20 imgs / 402 chunks** the entire time — never zeroed out, never doubled.
   - Combined with the BUG-260516-04 delete-cascade fix, the reingest produced clean steady-state numbers.
   - No console errors / warnings.

## Decisions Made

- **Spread-merge vs full replace.** Full replace was the original code; it zeroed out aggregates on every UPDATE event. Spread-merge `{ ...d, ...newDoc }` is one-line trivial and preserves the prior fetch's `table_count` / `image_count` / `chunk_count` until the next refetch.
- **Refetch only on terminal state.** Intermediate states (`pending` → `extracting_text` → `extracting_tables` → `extracting_images` → `chunking` → `embedding`) don't change the aggregates — those are written by the BackgroundTask AFTER extraction finishes. Refetching on every UPDATE would waste bandwidth without changing the displayed counts. Terminal state is the only event that matters for aggregates.
- **No confirm dialog on Documents page Reingest.** Library Health has a two-step confirm because that page is for quality auditing — deliberate actions are appropriate. Documents page is the operator's primary workspace; adding friction here would slow down testing and iteration. Worst case if accidentally clicked: a 30-60s extraction the user didn't want. The disabled-while-processing guard prevents accidental rapid-fire clicks.
