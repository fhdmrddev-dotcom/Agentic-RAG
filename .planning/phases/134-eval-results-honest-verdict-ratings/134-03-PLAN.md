<objective>
Add the ratings write path (EVAL-04): an owner-scoped `PUT` endpoint on the eval router that records
one thumbs up/down per (user, answer), re-ratable and clearable, plus attaching the caller's own
rating to the durable readout so the frontend can show current state. This is the first
user-initiated write in the eval domain — the IDOR gate on `eval_result_id` is the load-bearing
security control.

Purpose: The human-preference signal Phase 135 (SI-01) consumes. The high-value cue is human-judge
disagreement (thumbs-down on a judge-PASSED answer) — a minimal rating row joined to the Plan 02
verdict gives Phase 135 everything.
Output: a `PUT .../rating` endpoint (owner-verify then upsert/clear), `RateResultBody`, the rating
merge in `get_eval_run`, and a new router test file (round-trip + cross-user 404).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → ratings write | The FIRST user-initiated write in the eval domain; the request carries a `result_id` that must be owner-verified before any write |
| service-role client → eval_ratings | Writes bypass RLS; the app-code `.eq("user_id")` owner-verify is the real access gate |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-134-01 | Elevation of Privilege | IDOR — rate (or read) another user's eval result via `result_id` | mitigate | Owner-verify the `eval_results` row with `.eq("id", result_id).eq("user_id", current_user)` BEFORE writing; 404 NEVER 403 (don't leak existence — T-133-01 precedent). Owner-only RLS SELECT on eval_ratings is defense-in-depth. Unit-tested by `test_rating_cross_user_404` |
| T-134-03 | Spoofing / Tampering | forged owner in the ratings write | mitigate | `user_id` sourced from `current_user["id"]`, NEVER the request body; `RateResultBody` carries only `rating`. No client write policy on eval_ratings |
| T-134-09 | Tampering | invalid `rating` value smuggled past the app | mitigate | Endpoint rejects `rating` not in `("up","down")` with 400; the DB `CHECK (rating IN ('up','down'))` is the second gate |
| T-134-10 | Denial of Service | repeated ratings writes | accept | Bounded, idempotent (upsert on the UNIQUE constraint — one row per (user,result)); no fan-out. Low-value target, owner-scoped |
</threat_model>
