## Summary

Reviewed the full Phase 101.1 surface: the forced-emit substrate (`forced_emit.py`, `EmitFieldMap`, `EMITTER_REGISTRY`), the capability-tiered gateway forcing seam (dispatcher + 3 adapters + `create_adaptive_streaming_chat`), the `_exec_llm_emit` 6th executor with its citation/integrity gates and INSERT-only receipts, the gap-closure plans 07-10 (DeepSeek FORCE-NOTHINK, layer-6 backstop, single-owner persist, binary-delta skip, snapshot degrade, raw-download route, `phase_substep` demux, terminal workspace refetch, repair script), plus migration 069 and the test suite.

**The critical invariants hold.** Deep stays byte-identical: `RENDER_TEMPLATE_TOOL` is deliberately not in `get_tools()`, the forcing fields default safe on `GatewayRequest`, no provider branch leaked into the shared chunk/SSE path, and the `phase_substep` demux writes `phasesByThread` exclusively (never `bucketsBySurface`). The DeepSeek thinking gate lives at the service boundary (`openai_service.py:1364`). The audit kinds in `_AUDIT_EVENT_TYPES` are in exact lockstep with migration 069 (16 kinds). The raw-download route is ownership-gated, expiry-gated (`get_file_by_id` computes `is_expired`), and header-injection-safe. Single-owner persist (`_surfaced` flag) closes the duplicate-failure-message bug, and `fail_phase` flips the phase row on every honest failure. No Critical findings.

The main concerns are second-order consistency bugs in the new honest-failure path: the engine still writes a `phase_completed` audit row + SSE for a phase it just flipped to `failed` (WR-01), the "cited field-map is preserved below" promise is not actually kept anywhere durable (WR-02), and the emit-path render's live `workspace_file_written` event goes to an unsubscribed stream (WR-03 — the terminal refetch only partially masks it). Two provider-side risks need the planned live re-verification (WR-04, WR-05).

## Warnings

### WR-01: Engine emits `phase_completed` (audit + SSE) for a phase it just marked `failed`, then terminalizes the run as `completed`

**File:** `backend/app/services/harness_engine.py:996-1035`
**Issue:** The 101.1-07 gap-1 fix flips a `failure`-bearing phase output to `failed` via `fail_phase` — but the code after the branch runs unconditionally: `advance_current_phase`, a `phase_completed` audit write, a `phase_completed` SSE emit, an optional `phase_transition`, and `i += 1`. Consequences:
1. **Audit contradiction:** `harness_audit` records `phase_completed` for a phase whose `workflow_phases.status` is `failed` (and whose own `emit_failed`/`emit_rejected` receipt was just written). Phase 107 (GOV-02 / EU AI Act Art. 12) reads these rows as receipts — the trail is self-contradictory.
2. **Live rail mixed signal:** the frontend's `onPhaseCompleted` flips the failed card's status atom to "✓ Complete" (`setPhaseStatusForThread(threadId, phase, "done")`) while the `emitFailure` alert block still renders below it — a "Complete" header over a failure alert.
3. **Run semantics:** the run reaches `finish_run(pool, run_id, "completed")` + `run_completed status="completed"`, and any phases AFTER the failed emit phase still execute, chained on the failure text as their prior-output user turn. If "run completes with an honest failure message" is the intended semantic, that is defensible — but emitting `phase_completed` for a failed phase is not.
**Fix:** Guard the post-completion bookkeeping on the branch taken:
```python
if isinstance(output, dict) and output.get("failure"):
    await fail_phase(pool, phase_id, str(output.get("failure")))
    # do NOT write/emit phase_completed for a failed phase
    await write_audit(pool, run_id, user_id=_audit_user_id,
        event_type="phase_transition",  # or skip entirely
        metadata={"phase": phase.slug, "via": "emit_failed"})
else:
    await complete_phase(pool, phase_id, durable_output)
    await write_audit(pool, run_id, ..., event_type="phase_completed", ...)
    await _emit(redis, stream_run_id, "phase_completed", ...)
```
And decide explicitly whether a failed emit phase should halt the run (mirror the `fail_run` branch) or continue — today it continues silently.

### WR-02: "The cited field-map is preserved below" — it isn't, anywhere durable

**File:** `backend/app/services/harness/phase_types.py:1243-1251, 1300-1330` + `backend/app/services/harness_engine.py:996-997` + `backend/app/db/workflows.py:372-381`
**Issue:** States (b)/(c)/(d) build the failure output with `field_map=legacy_map` ("D-08: a non-opening render never loses the extracted data") and the surfaced chat message tells the user "the cited field-map is preserved below." But:
- `_surface_failure_message(ctx, run_id, msg, pool)` persists only `msg` — the message contains no field-map, so nothing is "below."
- The engine routes the failure output through `fail_phase`, which overwrites `workflow_phases.output` with `{"_failure_reason": "<taxonomy token>"}` — the in-memory `field_map` is dropped.
The extracted, cited data the model produced is durably lost on every honest failure, contradicting the D-08 design promise and the user-facing copy.
**Fix:** Persist the failure output dict (including `field_map`) on the phase row, e.g. extend `fail_phase` to accept the full output: `json.dumps({"_failure_reason": reason, **(output or {})})`, or call `complete-style` persist with status `failed` in one UPDATE. Alternatively render the field-map (or a workspace JSON fallback file) into the surfaced message. At minimum, drop "preserved below" from the message copy until it is true.

### WR-03: Emit-path render emits `workspace_file_written` on the workflow-run stream nobody subscribes to

**File:** `backend/app/services/harness/phase_types.py:1280` (post_processor call) + `backend/app/services/harness/emitters.py:160` + `backend/app/services/tool_dispatcher.py:1871-1878`
**Issue:** `_exec_llm_emit` passes the raw harness ctx bag into the post_processor; `_handle_render_template` then emits `workspace_file_written` via `ctx.emit(ctx.redis, ctx.run_id, ...)`. On the harness bag, `ctx.run_id` is the **workflow_runs id** — the frontend tails `run:{producer_run_id}` (the exact Facet-B routing problem 092-07 fixed everywhere else; compare `_emit_phase_substep`, which correctly prefers `ctx.producer_run_id`, and `_build_phase_tool_context`, which sets `run_id=_producer_id` for llm_agent tool dispatch). The live file card therefore never appears mid-run from an emit phase. The 101.1-09 terminal refetch (StreamsProvider `onRunCompleted`) heals it — but only when the run reaches `status === "completed"`; a run that ends `run_failed` after a successful render (multi-phase workflow) leaves the file invisible until panel remount.
**Fix:** Route the render handler's emit to the producer stream on the emit path — e.g. in `_exec_llm_emit`, hand the post_processor a shallow ctx clone with `run_id=getattr(ctx, "producer_run_id", None) or ctx.run_id`, or build a phase `ToolContext` (as `_build_phase_tool_context` does) for the render dispatch.

### WR-04: TIER-COERCE structurally cannot succeed on a STRUCTURED calling-mode model

**File:** `backend/app/services/forced_emit.py:216-229, 260`
**Issue:** For a coerce-tier model the substrate keeps `tool_choice="auto"` and passes `tools` on the `GatewayRequest` — but if the model resolves to `CallingMode.STRUCTURED` (registry `native_tools: False`, or OpenRouter `xml` strategy), `create_adaptive_streaming_chat` deliberately does NOT pass the tools param, the STRUCTURED system-prompt schema injection stays consumer-side in the agent loop (which `forced_emit` rightly bypasses), and the D-06 narration recovery is gated on `calling_mode == CallingMode.NATIVE` (line 260). Net: the model never sees the emit schema, and even a perfectly narrated field-map is not recovered — every STRUCTURED-mode `llm_emit` phase fails state (a). Honest, never silent, but the coerce tier is dead for that model class and the failure message blames the model ("it narrated prose") for a request that never carried the schema.
**Fix:** Either (a) extend recovery to STRUCTURED mode (`recover_narrated_emission` already handles the tool-wrapped narration shape via `parse_structured_tool_calls`) and inject the emitter schema into the coerce system prompt when `calling_mode == STRUCTURED`, or (b) fail fast with a distinct, accurate failure reason (`unsupported_calling_mode`) so receipts/UAT don't read it as a model failure.

### WR-05: Strict `response_format` on the forced path — wrong mechanism for tool args, and unverified on DeepSeek (the model class plan-10 must re-verify)

**File:** `backend/app/services/openai_service.py:1384-1403` + `backend/app/config.py:279-280`
**Issue:** Two related concerns:
1. The "token-level guaranteed schema" is implemented as `response_format={"type":"json_schema",...}` — but on OpenAI-compat APIs `response_format` constrains the assistant **content** channel, not forced **tool-call arguments**. OpenAI's strict mechanism for tool args is `"strict": true` inside the function definition. As written the flag likely buys nothing for the thing being validated (the tool args), and downstream Pydantic validation is what actually holds the line.
2. DeepSeek rows carry `strict_json_schema: True`, so every DeepSeek forced emit sends `response_format: {"type":"json_schema", ...}` alongside the named `tool_choice`. DeepSeek's documented `response_format` support has historically been `json_object` only — if the live API rejects `json_schema`, every DeepSeek TIER-FORCE emit 400s (caught honestly by the layer-6 backstop as `provider_error`, but the feature remains dead on DeepSeek even after the FORCE-NOTHINK fix). This is exactly the "docs said forceable!" trap 101.1-07 just hit. The pending plan-10 live re-verify should assert a `forced=true` + `emit_rendered` receipt on DeepSeek with this combination; if it 400s, either drop `strict_json_schema` from the DeepSeek rows or move strictness onto the tool definition.
**Fix:** Prefer `kwargs["tools"][i]["function"]["strict"] = True` for the named tool on providers that support it; gate `response_format` injection per-provider and verify DeepSeek live before declaring gap-1a closed.

### WR-06: Raw-download route 500s on a malformed `file_id`

**File:** `backend/app/api/workspace.py:370`
**Issue:** `download_workspace_file_raw` calls `UUID(file_id)` on the raw path segment. A non-UUID value (typo, crafted URL) raises `ValueError` → unhandled → 500. Every sibling route passes `file_id` to PostgREST as a string (which degrades to a 404/empty), so this route is the only one that can 500 on user input.
**Fix:**
```python
try:
    fid = UUID(file_id)
except ValueError:
    raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="File not found")
row = await get_file_by_id(pool, fid)
```
(404, matching the route's existing missing-and-IDOR-collapsed contract.)

### WR-07: Hardcoded login credentials in the committed smoke script

**File:** `scripts/smoke_101_1_06.py:46`
**Issue:** `tok = _req(AUTH, {"email": "fhdmrd@gmail.com", "password": "123456"}, ...)` hardcodes a real account email + password. The header comment says the file is "NOT committed," but it is in the working tree and in this review's scope. It is the documented local-dev seed account against localhost-only endpoints, so practical risk is low — but a committed credential pair is the pattern secret-scanners (and future copy-paste) punish, and the email is the operator's real address.
**Fix:** Read the credentials from env vars (`SMOKE_EMAIL` / `SMOKE_PASSWORD`) with a clear failure message when absent, or delete the script now that the 101.1-06 gap closure is proven (its header already declares it throwaway).

### IN-01: `definition_id` in emit receipts is always `None`

**File:** `backend/app/services/harness/phase_types.py:900-902`
**Issue:** `_emit_audit_metadata` derives `definition_id` via `getattr(definition, "definition_id", None) or getattr(definition, "id", None)` — but `WorkflowDefinition` (`models/harness.py`) has neither field, and `extra="forbid"` guarantees the parsed JSONB can never carry one. Every receipt's `definition_id` is null; the D-12 "keyed to definition@version" promise is only half met (version is real).
**Fix:** Thread the actual `workflow_runs.definition_id` onto the ctx bag (it is in scope at both ctx build sites) and read it here.

### IN-02: `emit_forced` receipt under-reports provider/model

**File:** `backend/app/services/harness/phase_types.py:1137-1144, 909-910`
**Issue:** The per-attempt `emit_forced` receipt sets `provider=getattr(ctx, "provider", None)` — no ctx build site (live `wf_ctx`, resume bag) ever sets `.provider`, so it is always null; and `model=getattr(phase.config, "model", None)` is null whenever the phase inherits the thread model. The receipt for the *forcing* transition records neither the effective model nor the resolved provider, while the later receipts (built from `result`) do carry the provider. Same `ctx.provider` dead-first-branch at line 1150 (`getattr(ctx, "provider", None) or _provider_for_model(model, ctx)` — the fallback is the only live path; harmless but misleading).
**Fix:** Record the resolved `_provider_for_model(model, ctx)` and the effective `model` variable in the receipt.

### IN-03: PhaseCard has no `llm_emit` phase-type label

**File:** `frontend/src/components/panel/PhaseCard.tsx:41-48`
**Issue:** `PHASE_TYPE_LABEL` covers the 5 original phase types; an `llm_emit` fill phase falls to `UNKNOWN_PHASE_META` and renders as generic "Step · A workflow step ran." Safe (the forward-compat fallback works as designed), but the phase this entire milestone is about renders with the least informative label.
**Fix:** Add `llm_emit: { label: "Deliverable fill", glyph: "▦", oneLiner: "A forced, cited fill of the bound template." }`.

### IN-04: DeepSeek FORCE-NOTHINK relies on omission, not explicit disable

**File:** `backend/app/services/openai_service.py:1364-1369`
**Issue:** On a forced DeepSeek call the `extra_body.thinking` enable is skipped, relying on the server default being thinking-off. If DeepSeek ever flips the default (or a reasoning-aliased model id is used), the 400 returns. Explicitly sending `{"type": "disabled"}` on the forced branch is drift-proof.
**Fix:** `kwargs["extra_body"]["thinking"] = {"type": "disabled"}` when `force_tool_name is not None` and provider is deepseek (subject to the same plan-10 live verification as WR-05).

### IN-05: Unused `exc` parameter

**File:** `backend/app/services/harness/phase_types.py:998`
**Issue:** `_emit_unexpected_failure(..., exc)` never uses `exc` (the `logger.exception` call relies on ambient exception context, which works because the call happens inside the `except` block). The parameter suggests the receipt records the error class; it doesn't.
**Fix:** Either drop the parameter or include `type(exc).__name__` in the receipt metadata (identifier-only — no message content, per T-073-04).

### IN-06: `_drain` can duplicate a tool call in its buffer on the Anthropic path

**File:** `backend/app/services/forced_emit.py:296-333`
**Issue:** Anthropic streams yield `tool_preparing` (buffered at the event index) AND `tool_start` (buffered at `len(buffer)` — a fresh slot), then the finish-fold merges `finish.tool_calls` by enumerate index. A single forced call ends up in the buffer twice (slots 0 and 1, identical). Harmless today — the executor scans for the first validating call — but the fold-by-enumerate also assumes 0-based contiguous indices and could merge into the wrong slot if a provider ever indexes from non-zero.
**Fix:** In the `tool_start` branch, merge by id/name into an existing slot when one matches instead of always appending.

### IN-07: Migration 069 `DROP CONSTRAINT` without `IF EXISTS`

**File:** `supabase/migrations/069_harness_audit_emit_kinds.sql:15`
**Issue:** A re-paste into the SQL editor (the documented apply mechanism) errors on the second run; `DROP CONSTRAINT IF EXISTS` makes the ALTER pair idempotent at zero cost.
**Fix:** `ALTER TABLE public.harness_audit DROP CONSTRAINT IF EXISTS harness_audit_event_type_check;`

### IN-08: A no-evidence emit can send an empty `messages` list

**File:** `backend/app/services/harness/phase_types.py:1122`
**Issue:** `messages = [{"role": "user", "content": user_turn}] if user_turn else []` — when there is no prior output, no kickoff prompt, no spotlight, and no oracle, `forced_emit` issues a provider call with zero messages, which most providers reject with a 400 (caught as `provider_error`). The failure is honest but the receipt blames the provider for a request the executor could have avoided or labeled.
**Fix:** Fall back to a minimal user turn (e.g. "Fill the bound template from the available sources.") or short-circuit to state (a)/(e) with an accurate reason before calling the provider.
