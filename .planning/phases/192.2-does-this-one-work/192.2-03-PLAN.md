Put the run truth on the library feeds: `last_run_at` and `last_run_status`, joined from the
`workflow_runs` rows that already exist.

Purpose: LIB-06's differentiator is *does this one work*. Measured (CONTEXT `<measurements>`),
`workflow_runs` already holds **228 rows** — 186 completed, 31 failed, 11 cancelled — and **32 of
36 published definitions have at least one**. Nothing needs to be written or migrated; the feed
simply does not read it.

⚠ **NO MIGRATION. NO NEW COLUMN. NO NEW WRITE.** A task here that adds a table or a column has
misread the plan.

<threat_model>
- **T-08 — The join drops never-run rows.** An inner join would hide 69% of the library. Mitigated
  by Task 1 assertion 1 (row set and order identical) which fails loudly.
- **T-09 — The join multiplies rows.** A definition with 24 runs rendering 24 times. Mitigated by
  `LATERAL … LIMIT 1` and by asserting the row COUNT is unchanged.
- **T-10 — Visibility widening.** ⚠ Security-bearing: `workflow_runs` carries `org_id` and
  `user_id`. A join that leaks another tenant's run onto a shared/global definition is a cross-tenant
  read. Mitigated by Task 1 assertion 4 and by leaving the WHERE untouched.
- **T-11 — The key never reaches the client.** These routes declare `response_model`, which DROPS
  undeclared keys silently — a green backend test with an unchanged UI. Mitigated by Task 3's live
  response check.
- **T-12 — SQL injection via a new binding.** Mitigated by positional binds only; no f-string in SQL.
</threat_model>
