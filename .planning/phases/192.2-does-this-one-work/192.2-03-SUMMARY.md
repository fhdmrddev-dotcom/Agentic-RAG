## 1. What shipped

### The one join (`backend/app/db/workflows.py`)

```sql
LEFT JOIN LATERAL (
  SELECT r.created_at AS last_run_at, r.status AS last_run_status
  FROM workflow_runs r
  WHERE r.definition_id = wd.id AND r.user_id = $1
  ORDER BY r.created_at DESC, r.id DESC
  LIMIT 1
) lr ON TRUE
```

Four properties, each measured rather than argued:

| Property | Why it is that way, measured |
|---|---|
| **`LEFT`** | Only **48** definitions have ANY run and **81 of 117** real rows are drafts. An inner join would hide most of the library. |
| **`LATERAL … LIMIT 1`** | One definition carries **24** runs, another **22**, another **20**. A plain join renders those workflows 24, 22 and 20 times. |
| **`r.user_id = $1`** | Five `is_system_global` published rows carry **20 / 15 / 11 / 7 / 1** runs belonging to ONE user, and these feeds run on a pool that **bypasses RLS**. Unscoped, every caller would read that activity. Scoping by `user_id` is strictly narrower than by `org_id`, so the cross-org case is excluded by construction. A legacy run with NULL `user_id` is attributed to nobody — fail-closed. |
| **`AS last_run_at` / `AS last_run_status`** | ⚠ **Not cosmetic.** `workflow_runs` also has `id`, `status` and `updated_at`, and the outer queries carry all three BARE (`WHERE status = 'published'`, `ORDER BY updated_at DESC, id DESC`). Exposing them under their own names makes every one of those clauses ambiguous and each feed raises. The rename at the subquery boundary is what keeps the shipped WHERE and ORDER BY byte-identical. |

**`, r.id DESC` is prospective, not corrective.** Measured 2026-08-19: **0** `(definition_id, created_at)` collisions across all 228 rows. It is there because `now()` is transaction-scoped and `created_at` is not unique — the WR-03 lesson applied before it costs anything, not after.

### The wire (`backend/app/api/workflows.py`)

`PublishedWorkflow` and `DraftRow` each gain `last_run_at: str | None = None` and `last_run_status: str | None = None` — additive, defaulted, so a client deployed ahead of this backend degrades to *unknown* rather than to a fabricated value. `/starters` now resolves the caller **before** the fetch and hands it to the db layer.

### Deliberate decisions that differ from the plan's letter

**5. `last_run_at` is typed `str`, not the plan's `datetime | None`.**
The plan's Task 3 says `last_run_at: datetime | None = None` and, in the next sentence, *"matching the `updated_at` precedent exactly"*. Those conflict. The precedent is `str`, and it is backed by a measurement recorded on `DraftCreateResponse.token` and `PublishedWorkflow.updated_at`: a `datetime`-typed field re-serializes through Pydantic and DROPS the fractional part when microseconds are 0, so the wire string's width varies with the clock. The measured clause wins; the suite pins `"datetime" not in` the annotation and asserts `123456` survives the JSON dump.

**6. `backend/app/models/harness.py` was NOT modified, though the plan lists it in `files_modified`.**
`PublishedWorkflow` is declared at `backend/app/api/workflows.py:146` and `DraftRow` at `:~300`. `grep -rn "class PublishedWorkflow\|class WorkflowDraftRow" backend/app` returns **one** hit, in `api/workflows.py`. There is no `WorkflowDraftRow` anywhere in the backend at all — that is the FRONTEND type name in `lib/api.ts`. Editing `models/harness.py` would have added a second, unused declaration.

**7. `/starters` was included, and it required a signature change the plan did not name.**
The plan's `<context>` says both `PublishedWorkflow` feeds need the facts, and RESEARCH C-6 makes mirroring binding. But `list_starter_workflows` took **no** user at all, and the lateral is owner-scoped — so it gained a keyword-only `user_id`, **defaulted to `None` and fail-closed** (a NULL bind matches no run), which keeps the shipped positional call in `test_starter_workflows.py` valid and can only ever REMOVE information.
