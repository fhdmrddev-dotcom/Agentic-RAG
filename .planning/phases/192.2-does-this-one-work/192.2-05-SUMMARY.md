## 5. Deviations from Plan

### **1. [Rule 3 — Blocking] `lib/phaseGlyph.tsx` was DECLINED, not obeyed — the FOURTH wrong path in this phase's plans**

- **The plan said:** Task 3's `<files>` names `frontend/src/lib/phaseGlyph.tsx`, and its action says *"Replace the emoji marks with the shared glyph path."*
- **Why that could not be done:** `phaseGlyph.tsx` is total over **PHASE TYPES** (`programmatic`, `llm_agent`, `llm_emit` …). The card's marks are a **PROVENANCE** axis (`ready` / `starter` / `building`). The `sketch-findings-agentic-rag` skill's `references/icon-convention.md` §4 forbids exactly this move **by name**: *"Using a phase-type glyph as a category icon — a workflow is its SPINE (#36), not one step's mark"*, a rule written after an audit caught four such drifts. The module additionally exports `PHASE_GLYPH_MARK_KEYS` **only** so a test can assert its key set equals `soulData.PHASE_GLYPHS`'s — adding provenance keys there would break that split-brain guard, and adding a second map would bolt an unrelated concern onto a single-concern module. ⚠ And the card **stopped consuming `phaseGlyph` altogether** when the glyph-dot spine left with D-03, so the file has no relationship to this surface any more.
- **What was done instead:** `lucide-react` — `FileText` / `Sparkles` / `SquarePen`, plus `Folder` for the chip. That is **not a fourth icon path**: `WorkflowCard.tsx` already drew `MoreHorizontal`, `Trash2` and `Loader2` from it, and the convention's two single sources (`@lobehub/icons` for providers, `PHASE_GLYPHS` for phase types) do not cover a library row's provenance at all.
- ⚠ **This is the FOURTH wrong `files_modified` entry in this phase** — after `192.2-03`'s `models/harness.py` and `192.2-04`'s `libraryRow.ts`, and after `ROW_FACE` (which does not exist).
- **Files:** none. `git diff --stat` on `phaseGlyph.tsx` is 0 lines.

### **4. [Rule 1 — avoided] The state word now renders TWICE on a name-colliding row — RECORDED, deliberately NOT fixed**

- **Found how:** measured, not foreseen. Three pin cases failed with `TestingLibraryElementError: Found multiple elements with the text: Ready to run`.
- **Why it happens:** the pin's three rows collide on one name, so `resolveIdentity` picks the **state axis** as the discriminator and emits `Ready to run` as a seg of the identity line — while D-01 now also puts it on line 2. On such a row the card reads `… | Ready to run` and then `Yours · needs a template · Ready to run · 3 share this name · …`.
- **Why it was not fixed here, and the reasoning is mechanical rather than reluctant:** D-04 states LIB-05 stays complete and *must not be re-opened*; `rowIdentity.ts` is outside `files_modified` and carries 72 pinned cases; and filtering the seg card-side would break this card's own documented discipline — *"it paints `own`, then `segs` in the order given … and it invents no part and drops none"*, which has its own `toEqual` assertions.
- **What was done:** the pin's state assertions are **scoped to their SLOT** (`within(row-answer)`), which is the correct assertion anyway — a slot, not a coincidence — and the duplication is written into the suite, STATE.md and ROADMAP.md.
- ⚠ **Re-open trigger: an operator reads the stutter on the real shelf.** It is a candidate for a follow-up seed; the honest reading is that the discrimination ranker should stop spending the state axis now that the state is unconditional on every card.
