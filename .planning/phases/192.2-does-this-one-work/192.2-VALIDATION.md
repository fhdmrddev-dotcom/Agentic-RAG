# Phase 192.2 — VALIDATION

**This file was authored BEFORE anyone claimed the phase shipped, and every `result:` below is
empty on purpose.** G-4 requires operator-defined *"I'd recognise failure here"* scenarios **at
scope-time, not post-hoc** — and the reason is mechanical rather than procedural: **a UAT row
written after the build is written to match what was built.** Two of the rows below (U4, U5) were
chosen specifically because the implementation cannot trivially satisfy them.

---

## ⚠ The rule every row here inherits

> **A machine check that bypasses the human's task does not verify the human's task.**
> Phase 192's post-fix re-drive located rows with **`getElementById`** on a known UUID. It proved
> the code and could not prove the row was *findable*. The operator, who had to find it, could not.

**NO ROW BELOW MAY LOCATE ITS TARGET BY ID.** Not `getElementById`, not a UUID, not a
`data-testid`, not the DevTools element picker. **Search for it, read the line, point at it.**
This is CONTEXT's own verification note and this project's D-27.

⚠ **And the rows must be driven on the REAL library** — the operator's own 117 rows, 96 distinct
slugs, 37 distinct names — **not on a fixture and not on the dev route.** The dev route no longer
exists (torn down by this plan's Task 1); the fixture cannot show what a shelf of 43
identically-named rows feels like, which is the entire question LIB-06 was opened for.

**The one sanctioned DevTools act** is U4's response override: it *removes* information from a
payload. It finds nothing and it locates nothing.

## The 4-axis UAT bandwidth — stated for every axis, including the ones that do not apply

⚠ **A scoreboard that lists only what passed is not a scoreboard.** An axis that does not apply is
recorded with its reason; it is never silently omitted.

| Axis | Applies? | Reason, stated rather than assumed |
|---|---|---|
| **Cross-provider** (the full native roster + OpenRouter — 8 rows) | **NO** | This phase touches **no streaming, no agent loop, no provider routing and no provider-dependent UI state.** The card renders `workflow_runs.status`, a terminal value the run lifecycle writes identically whichever provider produced the run, joined by SQL and rendered by a pure function. ⚠ **The one honest caveat, stated so it is not discovered later:** the run whose outcome a card reports *was* executed by some provider — but **this surface neither reads nor branches on `provider`**, and `grep` finds no provider identifier anywhere under `library/`. ### U3 — A never-run draft reads as never-run, and is NOT mistaken for broken

### U4 — ⚠ THE UNKNOWN ARM. Run the frontend against a backend that does not carry the new keys

**This is the row most likely to be skipped, and it guards the phase's central honesty claim.**
A frontend deployed ahead of its backend must render an explicit *unknown* — **never a tick, never
a blank, and above all never the sentence *"Never run"* about a workflow that has run.**

- **Why manual:** the unit suite proves the resolver; it cannot prove the *deployed* pair. And this
  exact skew is a real deployment state for this project, because the frontend (Vercel) and the
  backend (Coolify) build from the same branch but not in the same instant.
- **How to drive — two concrete setups, either is sufficient:**
  1. **DevTools response override (one step, no second backend).** Load the Workflows page.
     Network → right-click the `/workflows/published` request → **Override content** → delete the
     `last_run_at` and `last_run_status` keys from **every** row in the saved JSON → reload with
     overrides enabled. ⚠ **Delete the KEYS. Do not set them to `null`** — `null` is a different
     arm and it is the arm this row is not testing.
  2. **A real old backend.** Create a throwaway worktree at the phase base
     `82dd2efd13459e419d8e6036cdae19fae9ee574b`, run `bash scripts/bootstrap-worktree.sh` in it,
     start `uvicorn` from that tree on the port the frontend already points at, and reload.
     ⚠ Tear it down with `bash scripts/teardown-worktree.sh` — **never `rm -rf`**.
- **What must be true:** every card says **`Not recorded`**. No gutter colour. No tick. No blank
  slot. No time. **And no card says `Never run`.**
- **`fail:` if** any card renders a tick, an empty line 2, a fabricated time, or the words
  `Never run`.

### U7 — ⚠ CARRIED FINDING: the state word renders TWICE on a name-colliding row

**Recorded by `192.2-05`, deliberately NOT fixed, and carried here rather than buried in a summary.**

On a row whose name collides with others, `resolveIdentity` picks the **state axis** as that row's
discriminator — so the card reads `… | Ready to run` on line 2 **and** `Yours · … · Ready to run ·
43 share this name · changed 5 days ago` on line 3. It was found by `getByText` throwing *"Found
multiple elements with the text: Ready to run"*, **not by reasoning**.

- **Why it was not fixed in-phase, mechanically rather than reluctantly:** D-04 states LIB-05 stays
  complete and **must not be re-opened**; `rowIdentity.ts` sits outside this phase's
  `files_modified` carrying 72 pinned cases; and filtering the seg card-side would break the card's
  own documented discipline — *"it paints `own`, then `segs` in the order given … it invents no part
  and drops none"*, which has its own `toEqual` assertions.
- **How to drive:** open the 43-member `Compliance Gap Report` family and read one row's card top
  to bottom. Say whether the repeat reads as a stutter or passes unnoticed.
- ⚠ **RE-OPEN TRIGGER (concrete):** *an operator reads the stutter on the real shelf and says it
  reads badly* — i.e. this row failing. **The fix is in `rowIdentity.ts`, not in the card:** the
  discrimination ranker should stop spending the **state** axis now that the state is unconditional
  on every card, which frees that axis for a discriminator that actually discriminates.
- **Filed as a bug report so it is visible to the routing scan:**
  `.planning/reported-bugs/library-card-state-word-renders-twice-on-colliding-row.md`
  (**`BUG-260819-01`**, `status: open`, `surface: Agentic-RAG`). ⚠ **A record living only in a
  phase summary is invisible to every touchpoint that scans for open bugs** — that is how a live
  bug hid for two months in this project.

### U8 — ⚠ CARRIED TRADE-OFF: a search hit is no longer self-explaining

**Recorded by `192.2-05` as a knowingly-accepted consequence of D-03, not as a defect.**

The library filter **still matches on `purpose`** — `WorkflowsPage.test.tsx`'s D-07 case still
proves that a word appearing **only** in a row's purpose finds that row. But the purpose hero was
atom 11 and D-03 cut it. **So a row can match your query for a reason that is nowhere on screen.**

- **Why it was accepted:** CONTEXT measures `business_requirement` populated on **16 of 117 rows
  (14 %)** and rules that it cannot lead. Keeping a hero for one row in seven, to explain a match
  that happens rarely, is exactly the noise D-03 exists to cut.
- **Why it is not simply dropped:** the case is **pinned in that direction with the trade written
  beside it**, so a later wave restoring a why-it-matched affordance reds there and reads the note
  instead of rediscovering the reason.
- **How to drive:** search for a word you know appears only in one workflow's written purpose.
  Confirm the row comes back. Then say whether you can tell **why** it came back.
- ⚠ **RE-OPEN TRIGGER (concrete), two independent arms — either fires it:**
  1. **an operator reports a search result they cannot account for**, or
  2. **`business_requirement` population passes ~70 %** (it is 14 % today), at which point the
     deferred *"`business_requirement` as a card atom"* decision in CONTEXT re-opens on its own
     trigger and this one is answered with it.
  **The likely answer is neither a hero nor nothing: a match-reason affordance on the matched row
  only** — which costs zero pixels on the 100+ rows that did not match.

### U9 — A run happening RIGHT NOW reads *Not recorded*, and that is deliberate

**The substitute for the parallel-thread axis**, and a known limit stated rather than discovered.

`workflow_runs.status` admits six values; only the three **terminal** ones (`completed` / `failed` /
`cancelled`) map to an outcome. The three in-flight ones (`active` / `paused` / `cap_paused`) are
**deliberately absent from the map**, so they take the honest `unknown` default.

- **Why manual:** the claim under test is not *"does it say Not recorded"* (a unit test proves
  that) but *"is that acceptable to a person watching their own run"*.
- **How to drive:** start a workflow run. While it is still going, open the Workflows page in
  another tab and read that workflow's card.
- **What is true today:** it says **`Not recorded`** with no gutter colour. That is honest — no
  outcome is on record — but it says less than the surface could.
- **`fail:` if** you expected the card to show the run is live and its silence reads as a bug.
- ⚠ **RE-OPEN TRIGGER (concrete):** *the first phase that renders in-flight state on the library
  shelf.* It needs a **fourth arm** on `runFacts`, its own mark, and a decision about a live tick
  — which this project has already recorded as a defect class (the 188 tick-gate bug).
