## Summary

Phase 192.2 joins `workflow_runs.created_at` / `.status` onto the three workflow-library
feeds through one shared `LEFT JOIN LATERAL`, normalizes them onto `LibraryRow` as a
deliberately three-valued pair, resolves them to words in a new `runFacts.ts` leaf, and
re-draws `WorkflowCard.tsx` around a four-slot face. The engineering discipline is high and
most of the risk surface the brief named checks out. What it did **not** notice is that
owner-scoping the join changed the *meaning* of the fact from a row-level one to a
caller-level one, while every downstream type doc, vocabulary constant and rendered word
stayed row-level — which reproduces, on the shared shelves, the exact false claim this
phase's headline invariant (D-08) exists to prevent.

**The five areas the brief flagged, checked directly:**

1. **Owner-scoping on `/starters` — SOUND as a security control.** `list_starter_workflows`
   is keyword-only (`db/workflows.py:502-504`), so a positional caller physically cannot bind
   `user_id`; the sole call site passes it by keyword (`api/workflows.py:477`). A `None` id
   binds SQL `NULL` and `r.user_id = NULL` is never true — genuinely fail-closed, matching no
   run rather than all runs. The shelf's three-clause `WHERE` is byte-identical, so row
   visibility neither widens nor narrows. Verified.
2. **SQL correctness — SOUND.** `LEFT` preserves never-run rows; `LATERAL … LIMIT 1` caps the
   join at one row per definition, so no feed can multiply. The lateral consumes the
   already-bound `$1` and adds no placeholder, so `list_published_workflows`' `$2` project
   filter is not renumbered (`db/workflows.py:412-415`). The `AS last_run_at` /
   `AS last_run_status` renames genuinely prevent `status` / `updated_at` / `id` ambiguity in
   the outer `WHERE` and `ORDER BY`. No identifier is interpolated; the constant is a pure
   code literal (`db/workflows.py:161-169`). Verified.
3. **The three-state contract — TOTAL, but see CR-01.** `runFacts` is total over its input:
   `undefined` → `unknown` before anything reads the timestamp, `null` → `never`, an
   unrecognised or blank status → `unknown` via `Object.prototype.hasOwnProperty.call`
   (never `TABLE[k] ?? fallback`), and only the three terminal spellings reach `ran`. The
   `undefined`/`null` distinction survives `libraryFilter.ts:122-123` and `:157-158` verbatim.
   Nothing falls through to a success rendering. The **resolution** is correct; the **claim**
   the `never` arm makes is not (CR-01).
4. **The `relativeChanged` split — SOUND.** `relativeChanged` is now literally
   `CHANGED_PREFIX + relativeBand(…)`; `band()` is byte-identical, so no boundary moved and
   the prefix cannot double-apply (`relativeChanged.ts:76-83`, `:105-115`, `:124-138`).
5. **`api.ts` type-only claim — TRUE.** The `+53 / −0` diff adds interface members only; zero
   new runtime exports. The recorded architectural trigger did not fire. (But see WR-02 for a
   naming collision it introduced.)

Also verified: the `/sketch-card` dev surface and `src/dev/SketchLibraryCard.tsx` are fully
gone with zero dangling references; the live DB tests are `skipif`-gated and carry real
positive controls; the characterization pin's re-baseline is an inversion, not a loosening;
`WorkflowSoul scale="card"` is still consumed by `WorkflowDoorSwitch.tsx:451`, so removing
the card's mount left no dead branch.

The two recorded known issues (`BUG-260819-01`; the purpose-search hit no longer
self-explaining) were not re-reported — but WR-04 records that the second is **broader than
described**.

## Critical Issues

### CR-01: The owner-scoped join makes the card assert "Never run" about workflows that have run

**File:** `backend/app/db/workflows.py:161-169`, `frontend/src/components/workflows/library/libraryVocabulary.ts:436-442`, `frontend/src/components/workflows/library/runFacts.ts:163-164`, `frontend/src/lib/api.ts:1402-1421`, `frontend/src/components/workflows/library/libraryRow.ts` (the `lastRunAt` docblock)

**Issue:**
The lateral is scoped `r.user_id = $1`. That is the right security decision and it must
stand. But it changes the fact from *"this row has runs"* to *"**you** have runs of this
row"* — and nothing downstream was updated to match. Three separate places still document
the caller-scoped `null` as a row-level statement:

- `runFacts.ts:16-17` — *"THE BACKEND LOOKED AND THERE IS NO RUN … a real, affirmative fact
  about the row"*
- `api.ts:1414` — *"`null` means the backend looked and there is NO RUN"*
- `libraryVocabulary.ts:436-437` — *"THE BACKEND LOOKED AND THERE IS NO RUN. An affirmative
  statement about the row"* → `RUN_NEVER = "Never run"`

The consequence is concrete and is proved by this phase's own measurement, recorded verbatim
at `db/workflows.py:116-118`: five `is_system_global` published rows carry **20 / 15 / 11 /
7 / 1** real runs **belonging to ONE user**. `/starters` is world-readable and returns the
same rows to every caller (`db/workflows.py:522-532`). So for every caller who is not that
one user, both fields come back `NULL`, `runFacts` takes arm 2, and the card prints the
affirmative sentence **"Never run"** — with `GUTTER_TONE.never = "bg-border"`, i.e. a real,
painted, quiet bar (`WorkflowCard.tsx:495`), not an absence — about a workflow that has run
twenty times.

That is exactly the defect `runFacts.ts:20-22` names as the thing the three arms exist to
prevent: *"It makes the product state 'this has never run' about a workflow that may have run
a hundred times — a specific false claim, printed confidently."* The three arms solve the
stale-deploy case (`undefined`), which is essentially unreachable in production (see IN-04),
and leave the shared-shelf case — which every user hits on every load of the Starters shelf —
saying the false thing.

This is not a security bug; the scoping is correct. It is a truthfulness bug introduced by
the scoping, on the one shelf the phase measured as *"3 rows, exactly ONE of which has ever
been run"* (`api/workflows.py:497-500`) — i.e. two thirds of that shelf lies to every caller
but one.

**Fix:**
The cheapest honest fix needs no SQL change, because **all three feeds are now caller-scoped**
— so word the arm as caller-scoped everywhere, and amend the three docblocks that assert a
row-level fact:

```ts
// frontend/src/components/workflows/library/libraryVocabulary.ts
/**
 * D-08 arm 2 — THE BACKEND LOOKED AND *THIS CALLER* HAS NO RUN OF THIS ROW.
 * ⚠ THE JOIN BEHIND THIS IS OWNER-SCOPED (`r.user_id = $1`), so on a world-readable
 * `is_system_global` row this says nothing about whether ANYBODY has run it — five such
 * rows carry 20/15/11/7/1 runs by one user. The word must therefore name the caller, or
 * it asserts a global fact off a per-user answer.
 */
export const RUN_NEVER = "You haven't run this"
```

If a row-level answer is actually wanted on the shared shelves, the stronger fix is a second,
non-identifying column on the same lateral — a bare boolean that discloses no other tenant's
timestamps, ids or activity:

```sql
-- inside _LAST_RUN_LATERAL_SQL's outer SELECT list, NOT inside the owner-scoped subquery
EXISTS (SELECT 1 FROM workflow_runs r2 WHERE r2.definition_id = wd.id) AS has_any_run
```

with a fourth `RunFact` arm (`{ kind: "not-by-you" }`) so `never` keeps meaning *nobody ran
it* and the new arm means *you didn't*. Either way, `runFacts.ts:16-17`, `api.ts:1414` and
`libraryRow.ts`'s `lastRunAt` docblock must stop claiming the `null` is a fact about the row.

## Warnings

### WR-01: `bg-warning` / `text-warning` are not utilities in this project — the `stopped` gutter renders unpainted

**File:** `frontend/src/components/workflows/library/WorkflowCard.tsx:491-506`

**Issue:**
`GUTTER_TONE.stopped = "bg-warning"` and `RUN_TONE.stopped = "text-warning"` are new in this
phase, and the docblock above them asserts *"Deep Midnight semantic tokens only; every one of
these is already in `index.css` and none is a new hex."* Both halves of that claim are false:

- `frontend/tailwind.config.js` has **no `warning` key** anywhere under
  `theme.extend.colors` (`grep -n warning frontend/tailwind.config.js` → exit 1), while
  `success`, `destructive` and `border` all are. Tailwind ships no `warning` palette, so
  `bg-warning` and `text-warning` compile to **nothing**.
- `--warning` / `--warning-foreground` are defined **only inside `.dark`**
  (`frontend/src/index.css:116-117`); `:root` (`:17-90`) carries `--success` but no
  `--warning` at all.
- Confirmed against the built stylesheet: `frontend/dist/assets/index-*.css` contains
  `.bg-success{background-color:hsl(var(--success))}` and `.bg-border`, and **zero**
  `.bg-warning` / `.text-warning` rules.

Effect: a `cancelled` run's 3px gutter has no background — visually identical to the
`unknown` arm the same docblock says is *deliberately* unpainted so the two "cannot be
mistaken" (`:487-490`) — and the `Stopped` word falls back to inherited colour, matching the
muted tone the `never` and `unknown` arms use. The design invariant the block states is
broken in both axes for one of five arms.

It is unguarded: the suite asserts `data-run` and explicitly *not* a class
(`WorkflowCard.test.tsx:1597`, `:1631`, `:1643`), so nothing goes red.

Note this is a repo-wide latent bug (`ModelDiscoveryPanel.tsx`, `ModelRegistryTab.tsx`,
`ConnectionFormPanel.tsx` all use `bg-warning` today), so the config fix repairs those too —
but this phase is where it becomes a stated-and-violated contract.

**Fix:**
```js
// frontend/tailwind.config.js — beside `success`
warning: {
  DEFAULT: "hsl(var(--warning))",
  foreground: "hsl(var(--warning-foreground))",
},
```
```css
/* frontend/src/index.css — :root, so the token is not dark-only */
--warning: 38 92% 60%;
--warning-foreground: 240 60% 8%;
```
and correct the false sentence in `GUTTER_TONE`'s docblock. Add one class-level assertion for
the `stopped` arm so the gap cannot reopen silently.

### WR-02: Two different `last_run_status` fields now live in `api.ts`, and the same column has two wire names

**File:** `frontend/src/lib/api.ts:1337-1339` (Phase 194.1) vs `:1421`, `:1438`, `:3459-3460` (this phase)

**Issue:**
`api.ts` already carried `last_run_status?: string | null` with companions
`last_run_created_at` / `last_run_updated_at` on the thread workflow-state type. This phase
adds a second `last_run_status?: string | null` to `PublishedWorkflow` **and** to
`WorkflowDraftRow`, with a companion named `last_run_at`.

Both `last_run_created_at` (`:1338`) and `last_run_at` (`:1421`) are `workflow_runs.created_at`
— the same column, two wire names, one file. And three identically-typed
`last_run_status?: string | null` fields now sit within ~2100 lines of each other on types
that all flow through the workflow surfaces.

This is the precise hazard the file itself documents twelve lines above the collision:
*"Both are bare uuids, so a swap typechecks and then resolves nothing"* (`:1321-1322`) and
*"Both are `string | null` and a swap TYPECHECKS, exactly like the two id types warned about
above"* (`:1329-1330`). The new fields reproduce the shape that warning exists for, in the
hottest file in the repository.

**Fix:** Rename the 192.2 timestamp to match the shipped spelling for the same column
(`last_run_created_at`), or — if `last_run_at` is preferred — say so at both declarations and
cross-reference them, so a reader landing on either knows the other exists:

```ts
/** ⚠ NOT the `last_run_status` on `ThreadWorkflowState` (api.ts:1337), which is the LIVE
 *  thread's last run and is paired with `last_run_created_at`. Same type, same name,
 *  different table scope — a swap TYPECHECKS. */
last_run_status?: string | null
```

### WR-03: A bare `<p>` is rendered as a direct child of Radix's `role="menu"`

**File:** `frontend/src/components/workflows/library/WorkflowCard.tsx:1012-1019`

**Issue:**
The fork-consequence sentence moved from the resting card into `DropdownMenuContent`, which
Radix renders with `role="menu"`. ARIA's `aria-required-children` requires the children of
`role="menu"` to be `menuitem` / `menuitemradio` / `menuitemcheckbox` / `group` /
`separator`; a raw `<p>` is none of them. The comment at `:1006-1008` correctly reasons that a
`<p>` takes no focus and is skipped by roving focus/typeahead — that part is right — but that
does not make it a valid child of the menu role.

There is no axe assertion on this component (`vitest-axe` is imported only by
`ForkNameDialog.test.tsx`), so nothing catches it. The shipped `DropdownMenuLabel` primitive
already exists in `@/components/ui/dropdown-menu` for exactly this.

Secondary consequence worth stating: the sentence now exists in the DOM **only while the menu
is open**, so `aria-describedby` on the fork item resolves (both are in the same portal
subtree) but the resting card discloses the fork consequence nowhere. That is D-03's
deliberate decision, not a defect — flagged only so the a11y fix is not mistaken for a
re-litigation of it.

**Fix:**
```tsx
<DropdownMenuLabel
  id={consequenceId}
  data-testid="fork-consequence"
  className={MENU_NOTE_CLASSES}
>
  {hasExistingFork ? FORK_CONSEQUENCE_EXISTING : FORK_CONSEQUENCE}
</DropdownMenuLabel>
```
(or wrap the `<p>` in `<div role="group">`), and add one `axe()` assertion over the open menu
alongside the existing fork-consequence case.

### WR-04: Three filter chips and the search now select on facts the card no longer shows

**File:** `frontend/src/components/workflows/library/libraryFilter.ts:220-222` and `:246-247`; `frontend/src/components/workflows/library/WorkflowCard.tsx` (the removed `WorkflowSoul scale="card"` mount)

**Issue:**
The recorded known issue covers the search matching on `purpose` after the purpose hero was
cut. It is **broader than described**: D-03 also cut the **tier chip** and the **deliverable
atom**, and two of the six filter chips still select on exactly those:

```ts
"makes-a-file": (row) => soulDeliverable(row.def).kind === "file",   // deliverable atom — CUT
strict:         (row) => tierForDefinition(row.def).id === TIERS.STRICT.id,  // tier chip — CUT
```

So filtering by *Makes a file* or *Strict* now returns a set of cards carrying no visible
evidence of the property that selected them, and `chipCounts` (`:330-337`) publishes a count
for a fact the surface will not show. `WorkflowsPage.test.tsx:778-793` even asserts this
directly and calls it intended: *"the card says nothing about it, on a row whose tier is
unambiguously STRICT"* — the decision is recorded, but its interaction with the still-live
chips is not.

Three of six chips are now in this state (`makes-a-file`, `strict`, plus the search's purpose
arm); the other three (`ready-to-run`, `yours`, `still-building`, `starters`) still have a
visible carrier on line 2 or the mark.

**Fix:** Either (a) surface the selecting fact when the chip is active — e.g. render the tier
or deliverable inline on line 2 only for rows matched by that chip, mirroring the
already-shipped `HighlightTitle` pattern for the search — or (b) retire the two chips in the
same commit that removed their carriers and record the removal in `ChipId`. Leaving a filter
whose result cannot be self-explained is the same defect as the recorded purpose one, three
times over.

### IN-01: A live test's both-arms assertion depends on the dev DB happening to hold both arms

**File:** `backend/tests/unit/test_library_run_facts.py:959-981`

**Issue:** `test_the_starters_shelf_carries_run_facts_for_the_caller_who_ran_one` asserts
`any(last_run_at is not None)` **and** `any(last_run_at is None)` over the live shelf. It
passes only while the local dev database holds a starters shelf where *some but not all* rows
have been run — the docstring says so explicitly (*"the live shelf is 3 rows, exactly ONE of
which has ever been run"*). Running the second starter once turns this red on a tree with no
defect.

**Fix:** Skip the arm that is absent rather than failing:
`pytest.skip("shelf holds no unrun starter — arm unexercised")`, or seed/derive the target row
the way `_the_user_who_runs_things` derives its caller.

### IN-02: Hardcoded database credentials as the test DSN default

**File:** `backend/tests/unit/test_library_run_facts.py:716-718`

**Issue:** `postgresql://postgres:postgres@127.0.0.1:54322/postgres` is inlined as the
`POSTGRES_DSN` fallback. It is the well-known local Supabase dev pair and the tests are

### IN-03: The new non-vacuity control cannot fail for the right reason

**File:** `backend/tests/unit/test_workflows_updated_at.py:568-573`

**Issue:** The needle was correctly narrowed from `"AS token, updated_at "` to
`"AS token, updated_at"`, but the added control —
`assert "AS token, updated_at" not in "SELECT id, to_char(updated_at) AS token FROM t"` —
is a hand-written string that trivially lacks the needle. It proves the needle is not the
empty string and nothing else; it does not demonstrate the needle catching the collapse it
guards (which would require a string where `token` is derived *from* `updated_at` with both
projected adjacently).

**Fix:** Point the control at the real pre-192.1 source shape, or delete it and rely on
`test_draft_updated_at_is_not_parsed_out_of_the_token` below, which the docstring already
names as the behavioural half.

### IN-04: The `unknown` arm is unreachable from any current backend, yet it is what 107 of 111 fixture rows render

**File:** `frontend/src/components/workflows/library/__fixtures__/libraryScale.ts:765-772`; `backend/app/api/workflows.py:236-238`, `:351-353`

**Issue:** `PublishedWorkflow` and `DraftRow` declare both fields with `= None` defaults and
neither route sets `response_model_exclude_unset`, so FastAPI always emits both keys —
`undefined` cannot arrive from any backend of this version. Meanwhile the scale corpus sets
both to `undefined`, so all 107 scale rows and all four characterization-pin rows exercise
the arm that essentially never occurs live, while the arm most users will actually see on the
Starters shelf (`never`, per CR-01) is driven on a handful of hand-built rows.

The choice is defensible (the fixture predates the feed and `null` would be a claim it does
not hold), and `WorkflowCard.test.tsx:1508-1700` does drive the full matrix. Recorded so the
coverage shape is visible rather than assumed.

**Fix:** None required. If the scale corpus is ever re-baselined, give it a realistic mix
(≈69% `never`, some `worked` / `failed`, a couple `unknown`) so the 107-row perf and layout
cases exercise the arms production will actually render.

### IN-05: `_LAST_RUN_LATERAL_SQL`'s docblock makes a claim that is false for one of its three feeds

**File:** `backend/app/db/workflows.py:124-126`

**Issue:** *"⚠ IT BINDS `$1` AND NEVER A NEW PLACEHOLDER. All three feeds ALREADY bind the
caller as `$1`"* — `list_starter_workflows` bound **no parameters at all** before this phase
(its own docstring at `:514-520` still says *"NO user scope … a `$`-free literal"* two
paragraphs above the amendment). The conclusion is right (no renumbering occurs, because the
starters query had no `$2` to shift), but the stated reason is wrong for a third of the
claim's subject, and this file's whole convention is that a reason survives its author.

**Fix:** Amend to *"the two published/draft feeds already bind the caller as `$1`;
`list_starter_workflows` gains its first parameter here, which is safe because it had no other
placeholder to renumber"*, and reconcile the now-contradicted *"NO user scope"* sentence at
`:514`.
