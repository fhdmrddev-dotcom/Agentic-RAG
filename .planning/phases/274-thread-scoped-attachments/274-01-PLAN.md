<objective>
Make a chat attachment live for the life of its thread (D-05, D-06, D-21), make thread delete remove
its attachment BYTES and not only its rows (D-08), correct the agent note that says attachments expire
(D-26), and land migration 203 — the `In Library` mark columns plan 02 stamps (D-28) — applied to the
local DB.

Purpose: ATT-01 / SC#4. Today an attachment dies after 24h while the thread lives on, and a deleted
thread leaves its >256 KB attachment bytes orphaned in the `workspace-files` bucket. The mechanism is
`expires_at = NULL` chosen by the door (RESEARCH Pattern 1): every read gate already admits NULL, the
sweeper and the run pin already skip it, and the agent allow-list and the chip keep testing one string,
so the split needs NO migration. Migration 203 exists only for the promote mark.

Existing rows are forward-only (CONTEXT discretion, stated): attachments that already carry an
`expires_at` keep it, and expired rows are not resurrected, because a blanket reset would also revive
workflow template inputs. Bucket bytes of threads deleted BEFORE this phase stay orphaned — recorded as
an observation, out of scope (a sweep would be a service-role job and its own operator decision).

Output: the lifetime split and its pins, the cleanup seam and its pins, migration 203 + shape test,
local apply evidence, a regenerated `full-schema.sql`, a regenerated OpenAPI snapshot, and
`274-BASELINES.md`.
</objective>

|----------|-------------|
| browser → `POST /threads/{id}/workspace/files?lifetime=` | client chooses which lifetime its own upload gets |
| browser → `DELETE /threads/{id}` | client-supplied thread id drives a storage removal |
| API → `workspace-files` bucket | object removal with the user-JWT client |
| migration → live schema | DDL on an RLS-governed table |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-274-01 | Tampering | `upload_template` `lifetime` param | accept | A client can opt its OWN upload in its OWN thread into thread-life: same 10 MB cap, same `validate_upload`, own quota, and the bytes are now removed at thread delete. `Literal` rejects any other value (422) |
| T-274-02 | Elevation | `delete_thread` → storage remove | mitigate | Paths come only from `workspace_files`/`workspace_file_versions` rows visible to the USER-JWT client under `*_select_own` RLS; a foreign thread id yields `[]`. Paths whose first segment ≠ `current_user["id"]` are dropped and logged; storage `workspace_storage_delete_own` is the final authority. No service-role client on this path (static test) |
| T-274-03 | Denial of service | `delete_thread` | mitigate | Collect/remove failures are logged and swallowed AFTER being recorded; the thread delete itself is never blocked by storage; remove runs only after the delete returns, so a failed delete never leaves rows pointing at removed bytes |
| T-274-04 | Repudiation | removal failures | mitigate | `logger.warning` with the thread id and path count on every failure (no bare `pass`) |
| T-274-05 | Information disclosure | migration 203 | mitigate | No GRANT, no anon, RLS untouched; grants and `relrowsecurity` captured before and after the local apply and asserted identical; `get_advisors(security)` read-only baseline now, post-apply run OWED at deploy |
| T-274-06 | Denial of service | `library_document_id` FK | mitigate | `ON DELETE SET NULL` and no pairing CHECK, proven by a rolled-back document delete — a promoted document can always be deleted |
