## Plan 06 In-Scope Fixes (Task 3)

Within Plan 06's 6-8h budget, fix the FK-violation cluster ONLY:

- **4 fails in `tests/test_provider_router.py`** — `runs_thread_id_fkey`
  violations all surfaced at `app/api/threads.py:1251` (`insert_run` call
  inside `send_message`). The test mocks `supabase.table("runs").insert`,
  but Phase 073-04 routed the production path through
  `app.db.runs.insert_run` (asyncpg), which now hits the real Postgres
  pool and FKs out because the parent `threads` row was never seeded.

- **2 fails in `tests/integration/test_066_langsmith_clean.py`** —
  identical root cause (`runs_thread_id_fkey` at the same call site).

**Expected delta: 6 of 98 closed → 92 remaining.** Plan 06 ships at 92
failures (or whatever the actual post-fix count is). The remaining 92 are
documented above with explicit deferral routing.

### Fix approach (engineering note)

The plan PLAN.md suggested injecting `fk_aware_runs_factory` (Plan 05
Wave 0) to seed parent threads / auth.users rows. That fixture is correct
for tests that themselves call `_supabase.table("runs").insert(...)`.

For these 6 tests, the production code is the caller — the tests just
exercise it through ASGITransport. The cleanest in-scope fix is to **patch
`app.api.threads.insert_run` (and friends) as `AsyncMock` no-ops** within
the test's `_run_post_and_capture` helper, then assert on the AsyncMock
`call_args` directly. This:

1. Eliminates the FK violation entirely (no real DB write).
2. Preserves the test design philosophy (mock-based, no real Postgres).
3. Avoids the `fk_aware_runs_factory` skip path (which would `pytest.skip`
   under the current test conftest because `SUPABASE_URL` is the test
   placeholder and `supabase_real` isn't a wired fixture in these files).

This is a Rule-1 pragmatic call (auto-fix bug, smallest defensible diff).
The `fk_aware_runs_factory` remains the right tool for any future test
that needs a real-Postgres FK chain — e.g., a binding test that wants to
exercise the asyncpg path end-to-end against the live DB.
