## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test 1 model substitution: o1-preview → o1**

- **Found during:** Task 1 test authoring.
- **Issue:** Plan's Test 1 spec says `_uses_max_completion_tokens("o1-preview") returns True via registry (MODEL_CAPABILITIES["o1-preview"]["uses_max_completion_tokens"] == True)`. But `o1-preview` is NOT in `MODEL_CAPABILITIES` — only `o1` is. The test would have failed on a registry KeyError before reaching the assertion.
- **Fix:** Used `o1` (which IS registered) for the registry-hit test; documented the substitution in the test docstring. Added a bonus test that verifies every gpt-5+/o-series registered row carries the flag.
- **Files modified:** `backend/tests/unit/test_075_4_registry_sweep.py`
- **Verification:** Tests pass; the spirit of "registry hit returns True" is preserved.
- **Committed in:** `034552a` (Task 2 commit).

**2. [Rule 2 - Missing Critical] Caller of _reconstruct_history updated to pass active_provider**

- **Found during:** Task 3 (extending _reconstruct_history signature).
- **Issue:** The plan's Step 2 said "Update all call sites of `_reconstruct_history` to pass `active_provider=active_provider_name` (or equivalent in-scope variable)" — but at the production call site (threads.py:~1517), the variable `active_provider_name` (which is the chunk-handler-local capture from line ~1853) is NOT in scope. The closer in-scope variable is `user_settings.active_provider`.
- **Fix:** Caller passes `active_provider=(getattr(user_settings, "active_provider", "") or "").lower()` — the `.lower()` matches the chunk-handler's normalization at line 1853, and `getattr` with default protects against settings rows that predate the field.
- **Files modified:** `backend/app/api/threads.py`
- **Verification:** All 15 test_tool_memory.py cases stay green; the new test_075_4_thought_signature.py back-compat test asserts identical output across legacy 1-arg call and explicit `active_provider=""` call.
- **Committed in:** `1d13794` (Task 3 commit).

**3. [Rule 2 - Missing Critical] Empty-string signature defense in capture path**

- **Found during:** Task 3 capture-path implementation.
- **Issue:** The plan's capture shape initializes the per-tool-call slot to empty string `""`. If a chunk later arrives with `extra_content.google.thought_signature == ""` (Google's API has been known to emit empty placeholder values on the first chunk before the real signature lands), the existing slot would NOT be overwritten with garbage; but the echo + persist paths must filter out empty strings to avoid sending a no-op `extra_content` key to Google.
- **Fix:** Three layers of empty-string defense — (a) the capture-side `sig = (extra.get("google") or {}).get("thought_signature") or ""` short-circuits on falsy; (b) `if sig:` gate prevents overwriting the slot with empty; (c) echo + persist conditional spreads use `if tc.get("thought_signature")` (truthy check, excludes "").
- **Files modified:** `backend/app/api/threads.py`
- **Verification:** Test 3 (`test_capture_no_false_positive_when_empty_string_signature`) + Test 6 (`test_reconstruct_history_no_signature_no_spread`) + Test 9 (`test_persisted_tool_calls_empty_signature_skipped`) all green.
- **Committed in:** `1d13794` (Task 3 commit).
