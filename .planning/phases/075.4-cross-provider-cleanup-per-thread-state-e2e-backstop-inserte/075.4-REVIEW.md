## Summary

Phase 075.4 is a 6-plan cross-provider cleanup phase that adds: per-thread state in the frontend Zustand store (BUG-260523-01), `UnknownProviderError` + registry-driven capability inference (Plan 02), content-hash sandbox file dedup + terminal-status race fix + system_warning persistence (Plan 03), save_override sentinel allowlist + memo perf optimizations (Plan 04), Playwright E2E backstop scaffolding (Plan 05), and 6 E2E scenarios (Plan 06).

The codebase quality is generally high — extensive inline rationale, consistent test patterns, defense-in-depth error handling, and careful threading of decisions (D-075.4-*) through both source and tests. Most concerns are minor (style, error-classification ambiguity, missing assertions, security hygiene).

**One critical security issue found:** the Playwright E2E fixtures commit a real local-dev login email + password as the default value. While `reference_local_dev_app.md` memory documents this credential pair as the documented local test login, hardcoding it in `auth.fixture.ts` AND `scenario-*.spec.ts` files committed to the repo is undesirable — even for a "test password 123456". Tracked as CR-01 with the recommendation to require the env vars instead of defaulting.

Several warnings concern correctness on edge cases (empty/None model_id in provider inference, swallow-all `except: pass` paths in cleanup, JS regex selector breadth in E2E scenarios). Info items cover stylistic improvements and forward-ref hooks that may regress.

## Critical Issues

### CR-01: Real local-dev credentials hardcoded as defaults in committed E2E fixture

**File:** `frontend/tests/e2e/fixtures/auth.fixture.ts:14-15`
**Issue:** Local dev login email + password are committed as `DEFAULT_EMAIL`/`DEFAULT_PASSWORD` constants in a tracked file. While memory `reference_local_dev_app.md` documents these as the legitimate local-dev test credentials, having them in the repo permanently linked to a person's real email address creates a small but real footprint: if Supabase ever auto-routes that email or if the password is reused, the public commit history exposes the pair. This also collides with `feedback_env_secrets_handling.md` (avoid surfacing credentials).

Mitigations are already in the file (env vars override the default + db-teardown.fixture.ts has the `localhost` HARD-GATE), but the defaults themselves still ship.

**Fix:**
```ts
// auth.fixture.ts
export const test = base.extend<AuthedFixtures>({
  authedPage: async ({ page }, use) => {
    const email = process.env.E2E_USER_EMAIL
    const password = process.env.E2E_USER_PASSWORD
    if (!email || !password) {
      throw new Error(
        "E2E auth requires E2E_USER_EMAIL + E2E_USER_PASSWORD env vars. " +
        "See REDIS-SETUP.md / supabase/SETUP.md for local-dev test user setup."
      )
    }
    // ... rest unchanged
```
Then mirror the same hard-fail pattern in every `scenario-*.spec.ts` that has the `|| "fhdmrd@gmail.com"` fallback (currently lines 33, 29, 25, 31, 35, 32 across the 6 scenarios). This is also a memory-feedback gate: the user explicitly flagged credential leakage as a class of recurring footgun.

## Warnings

### WR-01: Outer `try/finally: pass` in agent_runner serves no purpose post-067.5

**File:** `backend/app/api/threads.py:3359-3545`
**Issue:** The outer `try:` opens at line 3359 (`OUTER try → finally runs shielded finalizer`), but the outer `finally: pass` at line 3544 is documented as "outer try kept structurally; classification handled by inner except branches above". The outer try has no exception handlers — all classification is in the inner exception block at 3379-3417, which runs INSIDE the inner `try:` opening at 3693 (line numbers shifted). The outer try-finally pair effectively does nothing — it could be removed for clarity, OR the comment at 3537-3545 should explain WHY it's kept structurally (e.g., for some downstream signature compatibility).

If kept, it provides zero value but readers must mentally parse it. If a future refactor accidentally adds logic to the outer finally, it would run AFTER the shielded finalizer — surprising behavior.

**Fix:** Either delete the outer `try/finally: pass` wrapper (cleanest), OR add a `# Intentional: see comment below` block that explains why the wrapper structure must stay even though the finally is empty.

### WR-02: `_is_transient_provider_error` silently swallows AttributeError on malformed body

**File:** `backend/app/api/threads.py:315-332`
**Issue:** The `try: code = e.body.get("error", {}).get("code")` block catches `(AttributeError, TypeError)` and falls through. If `e.body` is a malformed dict (e.g., string instead of object at `e.body["error"]`), the `.get("code")` raises AttributeError on the string, gets swallowed, and the function only consults the textual message. This is correct for OpenAI-shape errors but for a provider whose nested structure varies, it could miss a legitimate transient marker.

**Fix:** Add a debug log when the body-structure path is exercised so observability captures unexpected shapes:
```python
except (AttributeError, TypeError) as e:
    logger.debug("provider body inspection failed: %s", e)
```

### WR-03: `harvest_output_files` swallows ALL exceptions silently

**File:** `backend/app/services/sandbox_service.py:206-207`
**Issue:** The outer `try: ... except Exception as e: logger.error(...)` wrapper around the `tempfile.TemporaryDirectory + session.copy_from_runtime + storage upload + DB insert` block catches every exception including programmer errors (TypeError on bad args, KeyError on bad dict access). The function returns an empty `output_files` list, so the caller cannot distinguish "no files produced" from "we tried but everything broke." The agent loop emits `code_execution_complete` with `output_files=[]` either way — the user sees a successful cell with no downloads even if upload failed.

**Fix:** Split the `except Exception` into specific groups (`OSError`, `IOError`, supabase-py errors) so legitimate "no files" results stay silent but programmer errors surface. Alternatively, propagate a separate error indicator:
```python
output_files: list[dict] = []
harvest_error: Exception | None = None
try:
    # ...
except OSError as e:
    logger.error("Filesystem error during harvest: %s", e, exc_info=True)
    harvest_error = e
except Exception as e:
    logger.error("Unexpected harvest failure: %s", e, exc_info=True)
    harvest_error = e
# return (delta_files, current_files_dict, harvest_error) — extend signature
```
This is a contract change — defer to a follow-up if the lift is too disruptive, but at minimum log the FULL traceback (`exc_info=True` is already there — good) and consider whether a downstream message to the user is warranted.

### WR-04: `_extract_into_buffer` test helper diverges from production capture path

**File:** `backend/tests/unit/test_075_4_thought_signature.py:64-87`
**Issue:** The test file documents `_extract_into_buffer` as "kept in sync verbatim with the closure inside threads.py:send_message", but the production closure at `threads.py:_on_chunk_openai` lines 2016-2057 has additional behavior the test helper omits:
- The production code initializes `tool_calls_buffer[idx]["thought_signature"] = ""` ONLY when `active_provider_name == "google"` (test mirrors this).
- However, the production code reads BOTH `tc.extra_content` AND `(tc.model_extra or {}).get("extra_content")` with OR fall-through — the test helper mirrors this.
- BUT the test helper does NOT exercise tool_args_progress emit boundary logic (5KB byte counter) — leaving the closure's behavior partially untested via this proxy.

This is OK for Test 1-3's scope (provider gating), but the comment "kept in sync verbatim" overstates the parity. Future regressions in the 5KB boundary won't be caught here.

**Fix:** Either weaken the comment ("mirrors the thought_signature CAPTURE branch only") or extend the helper to drive the args-progress emit logic. The unit-test approach Phase 075.4 ships is acceptable; just clarify the scope comment.

### WR-05: Empty-key handling in `_addRunToThread` doesn't guard against null/undefined threadId

**File:** `frontend/src/providers/StreamsProvider.tsx:571-582`
**Issue:** `_addRunToThread(current, threadId, runId)` accepts `threadId: string` typed strictly, but TypeScript's `string` allows `""`. An empty-string threadId would be inserted as a Map key, leaking storage that's never collected. Today the callers all pass real UUIDs, but a regression on the call site (e.g., `streamingThreadIdRef.current` flipping to `""` instead of `null` after a refactor) would silently land.

**Fix:** Add a guard at the top of `_addRunToThread` and `_removeRunFromThread`:
```ts
if (!threadId) {
  console.warn("[StreamsProvider] _addRunToThread called with empty threadId; ignoring")
  return current
}
```

### WR-06: Provider-router test fixture lacks `_assert_finalize_status` for non-error paths

**File:** `backend/tests/test_provider_router.py:204-292`
**Issue:** The 4 test functions assert on `insert_run` payload but do NOT assert that `finalize_run` was called with `status="completed"` or `status="cancelled"`. With the asyncpg flip in Phase 073-04 + the test's deliberate cancellation in the `finally:` block (lines 280-292), it's plausible that `finalize_run` is never invoked at all (the test cancels the producer task before it can run). The assertion would catch a regression where the producer's `_shielded_finalize` doesn't fire on cancellation — a real lifecycle bug worth gating.

**Fix:** After the test's primary assertion on `payload["provider"]`, also assert `finalize_run_mock.called is True` with a status from the canonical set. Or document why the test legitimately ignores finalize.

### WR-07: `scenario-04-done-latency.spec.ts` measures POST close, not actual SSE `done` event

**File:** `frontend/tests/e2e/scenario-04-done-latency.spec.ts:65-83`
**Issue:** The scenario header docstring (line 17-22) explicitly notes the limitation ("we cannot easily intercept individual SSE events from Playwright without setting up a CDP session"). The implementation approximates SSE end via `response.finished()`, but this captures the moment the HTTP stream closes, which is AFTER the terminal sentinel + finalize_run UPDATE. The 500ms budget then measures (POST close → UI settled), which may not be the actual race window for BUG-260523-03b.

If the regression's race window is between the SSE `done` ENTRY (server-side XADD) and the HTTP stream close (could be 10-50ms apart), this scenario wouldn't catch it.

**Fix:** Either (a) accept the approximation and update the docstring + budget rationale to clarify "POST close" is the measurement boundary, OR (b) attach a CDP session to capture `Network.eventSourceMessageReceived` events for the SSE stream. Option (a) is acceptable for Phase 075.4 (the existing comment partly does this); option (b) is the rigorous fix for a future tighter bound.

## Info

### IN-01: `pkill -f` regex matches every uvicorn for "app.main:app" — could collide

**File:** `scripts/restart-backend.sh:23`
**Issue:** `pkill -f 'uvicorn.*app.main:app'` would also kill backends in OTHER repos that happen to import `app.main:app` (a common pattern). The Windows equivalent at `restart-backend.ps1:25` uses the literal regex `uvicorn.*app\.main:app` which is slightly more specific (escapes the dot) but has the same scope.

**Fix:** Narrow the regex to include the venv path or working directory in the match. Not urgent for a developer-tool script.

### IN-02: `_load_override()` cache TTL is hardcoded 5s

**File:** `backend/app/models/user_settings.py:160`
**Issue:** `_OVERRIDE_CACHE_TTL: float = 5.0` is fine for production but means a Settings UI change can take up to 5 seconds to propagate. The comment doesn't explain the choice.

**Fix:** Add a one-line comment explaining the 5s budget (e.g., "5s balances test runtime + UI responsiveness; settings_override.json edits are infrequent so cache doesn't need to be sub-second"), OR make it configurable via env var for tests.

### IN-03: Magic number `5120` (5 KB tool_args boundary) repeated in two files

**File:** `backend/app/api/threads.py:2078, 2087` and `backend/app/services/anthropic_service.py:247, 256`
**Issue:** The 5KB tool_args_progress boundary appears as the literal `5120` in 4 locations. Extracting to a module-level constant `TOOL_ARGS_PROGRESS_EMIT_BOUNDARY_BYTES = 5120` would document the magic number once and reduce drift risk if the value is tuned later.

**Fix:** Define `TOOL_ARGS_PROGRESS_EMIT_BOUNDARY_BYTES = 5120` in `app/api/threads.py` (or a shared constants module) and reference it from both call sites.

### IN-04: `useStreamSubscriptions` is O(N threads) per call

**File:** `frontend/src/providers/StreamsProvider.tsx:1479-1485`
**Issue:** The comment at line 1477 acknowledges the O(N) scan: "callers query a known runId rarely (per-message subscription gating), so the linear scan is acceptable." For now this is true — a user usually has <50 active threads. If a power user accumulates thousands of historical threads with stale entries, the scan compounds across re-renders.

**Fix:** Document a follow-up SEED or accept the current shape. Consider adding a runId-indexed Set as a secondary index if perf becomes an issue. (Filing as info because Phase 075.4 acceptance is met.)

### IN-05: Many `try/except: pass` blocks in producer cleanup paths

**File:** `backend/app/api/threads.py:937, 1282, 2713` and others
**Issue:** Several `except Exception: pass` blocks are scattered through the producer lifecycle (cleanup paths in delete_thread, _tempfile_local.unlink, runs ZREM cleanup, etc.). These are intentional best-effort cleanups (commented as such), but the broad scope swallows surprising errors.

**Fix:** Where feasible, narrow to specific exceptions (`OSError`, `RedisError`) so programmer bugs surface during dev. Acceptable as-is for production reliability.

### IN-06: Inconsistent provider name casing across config

**File:** `backend/app/config.py:215-220, 477`
**Issue:** `_INFERENCE_PATTERNS` uses lowercase provider strings (`"openai"`, `"anthropic"`), `KNOWN_PROVIDERS` in `user_settings.py:32` uses lowercase IDs, but the `chat_name=f"Chat{provider.title()}"` at `openai_service.py:551` Title-Cases the provider for LangSmith labels (yielding "Chatopenai", "Chatopenrouter"). Mixed casing is fine, but `Chatopenai` looks ungrammatical compared to LangSmith's idiomatic `ChatOpenAI` / `ChatAnthropic`.

**Fix:** Use an explicit provider-display map:
```python
_PROVIDER_LANGSMITH_LABEL = {
    "openai": "ChatOpenAI",
    "anthropic": "ChatAnthropic",
    "google": "ChatGoogle",
    "openrouter": "ChatOpenRouter",
    "ollama": "ChatOllama",
}
client = wrap_openai(client, chat_name=_PROVIDER_LANGSMITH_LABEL.get(provider, f"Chat{provider.title()}"))
```

### IN-07: Playwright scenarios use very broad selectors

**File:** `frontend/tests/e2e/scenario-*.spec.ts` (all 6)
**Issue:** Every scenario uses extremely broad selectors like `page.getByPlaceholder(/message|ask|type a message/i).or(page.getByRole("textbox").first()).first()`. The scenario header comments justify this ("future Deep Midnight redesign won't break the regression gate"), but the trade-off is: a passing test might be passing for the wrong reason (matching an unrelated text input).

**Fix:** Add data-testid attributes to the relevant DOM nodes (`MessageInput.tsx`, `Sidebar/NewChatButton.tsx`, `OutputFileCard.tsx`) and have scenarios target `data-testid="composer-textarea"` etc. Acceptable as-is for Phase 075.4 ship.

### IN-08: `test_resolve_llm_provider_raises_unknown_provider_error` reads cross-section comment

**File:** `backend/tests/unit/test_075_4_unknown_provider_error.py:86-97`
**Issue:** The test passes `_env_file=None` to `Settings(...)` to bypass `.env` file loading. The pydantic-settings docs allow this, but the kwarg name has changed between major versions. If `pydantic-settings` is updated, this could silently break. Currently passes — just be aware.

**Fix:** Pin pydantic-settings major version in `requirements.txt` and add a comment about the `_env_file` private kwarg dependency.

### IN-09: `_persist_system_messages` migration-gated failure mode could be silent for days

**File:** `backend/app/api/threads.py:1645-1687`
**Issue:** The fail-silent stance ("until migration 048 widens the role CHECK constraint") is intentional and documented. However, in production, if migration 048 was not yet applied to a target environment, every system_warning will silently fail to persist. Logged at WARNING, but operators may not surface the log signal.

**Fix:** Add a startup health-check that verifies the `messages_role_check` constraint allows `'system'` and emits a CRITICAL log if not. Operators can grep for the signal at deploy time. This is a longer-term hardening — accept the current shape for Phase 075.4.
