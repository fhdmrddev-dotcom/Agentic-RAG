### D-067.2-01 — Empty render until cycle finishes (multi-step new-thread runs)

**Failure mode:** User submits a multi-step prompt on a NEW thread (no pre-existing `thread.id`). The optimistic assistant placeholder appears empty. SSE deltas arrive but render nothing. After the run finishes server-side, the persisted DB row replaces the placeholder and the full content appears all at once.

**Root cause (line-anchored):** `frontend/src/hooks/useMessages.ts:623-628` — `guardedSetMessages` silently drops every state update when `streamingThreadIdRef.current !== activeThreadIdRef.current`.

In the new-thread `handleSend` flow at `frontend/src/components/chat/ChatArea.tsx:190-203`:
1. `await onCreateThread(scopeFolderId)` creates the thread server-side, returns object.
2. `await sendMessage(threadId, ...)` — `streamingThreadIdRef.current = threadId` set at `useMessages.ts:513`. SSE deltas begin arriving via `onDelta` callback.
3. Parent re-renders with new `thread` prop (non-deterministic React scheduling).
4. `ChatArea.tsx:79` useEffect fires → `setViewingThread(thread.id)` → `activeThreadIdRef.current = threadId` (`useMessages.ts:425`).

Steps 2 ↔ 4 are not synchronized. During the gap (50–500ms), `streamingThreadIdRef === threadId` BUT `activeThreadIdRef === null` (or stale previous), so `guardedSetMessages` no-ops every delta. Content reappears at run-end only because `_persist_assistant_message()` writes the DB row at `threads.py:2390` and a subsequent `loadMessages` (triggered by reconcile / onTerminal cleanup) replaces the empty placeholder with the persisted row.

**Fix shape:** synchronous ref alignment in `ChatArea.tsx` `handleSend`:

```ts
const handleSend = async (content: string) => {
  let activeThread = thread
  if (!activeThread) {
    activeThread = await onCreateThread(scopeFolderId)
    justCreatedThreadRef.current = activeThread.id
    setViewingThread(activeThread.id)   // ← ADD: synchronous before sendMessage
  }
  await sendMessage(activeThread.id, content, ...)
}
```

This closes the new-thread-creation race deterministically — `activeThreadIdRef.current` is set BEFORE `sendMessage` begins, so the first delta hits a passing `guardedSetMessages` guard.

**Acceptance (user-observable):** Submit Fahed-Mrad multi-step prompt on a NEW thread → assistant content streams progressively (visible delta-by-delta), NOT empty until end-of-run.

### D-067.2-02 — Mid-stream F5 / navigation empties UI (UX-067-03 broken)

**Failure mode:** User F5's mid-stream OR navigates to another thread mid-stream. UI shows blank content (only the chat title in sidebar). Backend has no failure; after the run completes, content "appears all at once" on the next interaction.

**Root cause:** Same `guardedSetMessages` pattern as D-067.2-01, applied to the reconcile path at `useMessages.ts:866-871`. On mount after F5, `activeThreadIdRef.current` is `null` until the ChatArea useEffect at `ChatArea.tsx:79` runs `setViewingThread`. The reconcile flow at `ChatArea.tsx:166` (`reconcileRef.current(tid).catch(...)`) fires from a SEPARATE useEffect at `:163`, which can run before the `setViewingThread` effect commits. Replay deltas from `subscribeToRun(run_id, "0", ...)` at `useMessages.ts:934` arrive synchronously and hit a no-op `guardedSetMessages`. The replay-and-tail backend pipe is correct (Phase 062 contract); the frontend silently discards the replayed events.

**Fix shape:** promote the `setViewingThread(thread?.id ?? null)` call from the regular `useEffect` at `ChatArea.tsx:79` to a `useLayoutEffect` so it runs synchronously after DOM mutation but BEFORE paint, ensuring `activeThreadIdRef.current === thread.id` before any reconcile / mount-effect fires.

```ts
// ChatArea.tsx — replace the existing useEffect at :79
useLayoutEffect(() => {
  setViewingThread(thread?.id ?? null)
}, [thread?.id])

// keep the existing useEffect for clearMessages + loadMessages logic
useEffect(() => {
  if (!thread) { clearMessages(); return }
  if (justCreatedThreadRef.current === thread.id) {
    justCreatedThreadRef.current = null
    return
  }
  clearMessages()
  loadMessages(thread.id).catch(console.error)
}, [thread?.id])
```

`useLayoutEffect` runs synchronously after React commits DOM mutations. The reconcile-trigger useEffect at `:163` runs AFTER all useLayoutEffect hooks have fired, so by the time `reconcileRef.current(tid)` is called, `activeThreadIdRef.current === tid`.

**Acceptance (user-observable):**
1. Submit multi-step prompt → mid-stream press F5 → page reloads → assistant content continues streaming with no blank-state period (replay from offset 0 lands in state).
2. Submit multi-step prompt on Thread A → mid-stream click Thread B → click Thread A back → content present, continuing if still streaming.

### D-067.2-03 — Storage signed URL `InvalidJWT` after 1 hour

**Failure mode:** User clicks a chart `.png` or document `.docx` link in chat history > 1 hour after generation:
```
{"statusCode":"400","error":"InvalidJWT","message":"\"exp\" claim timestamp check failed"}
```
The file is intact in storage; only the URL JWT is dead.

**Root cause (line-anchored):** `backend/app/services/sandbox_service.py:138`:
```python
supabase.storage.from_("sandbox-outputs").create_signed_url(storage_path, 3600)
```
Hardcoded 1-hour expiry. The signed URL is embedded directly in the assistant message's stored content; after `iat + 3600s`, all such URLs become dead permanently.

**Fix shape:** **Re-sign on demand** (Claude.ai/ChatGPT pattern). Add `GET /sandbox-outputs/{storage_path:path}` endpoint in `backend/app/api/` that:
1. Authenticates user (existing JWT auth dependency).
2. Verifies the requesting user owns the file (parse `user_id` from `storage_path` against `current_user["id"]`).
3. Re-signs via `create_signed_url(storage_path, 60)` — short TTL since it's a one-shot fetch, and the URL is immediately consumed.
4. Returns 302 redirect to the freshly-signed URL.

Frontend changes: `sandbox_service.py:140-143` constructs the signed URL into the message content. **Stop storing the signed URL.** Store the storage path. Frontend reconstructs the download link as `/sandbox-outputs/{storage_path}` (relative to backend host). Each click goes through the re-sign endpoint.

This requires a `tool_calls.outputFiles[i].url` shape change — likely from `https://127.0.0.1:54321/storage/v1/object/sign/sandbox-outputs/...?token=...` to `/api/sandbox-outputs/{path}` (relative). Backwards-compatible reads: if the existing assistant messages have the old long-URL form, they expire after 1h as today (no fix for already-stored URLs); only NEW outputs from this point use the re-sign endpoint. Acceptable migration cost.

**Acceptance (user-observable):**
1. Submit a docx-generating prompt → click download immediately → file downloads.
2. Wait 90 minutes (or fast-forward via short-TTL test) → click same download link in chat history → file STILL downloads (re-sign on demand worked), no `InvalidJWT`.
3. Different user authenticated → click download URL of someone else's file → 403 (ownership check).

**Failure mode:** Per `RESEARCH §` Validation Architecture and `agent_service.py` SYSTEM_PROMPT examples, the agent should surface a confidence score (low/medium/high based on similarity_scores from query_documents) and follow-up question suggestions. User reports neither is visible in the chat UI.

**Root cause (likely, requires confirmation):** Backend emits both events correctly:
- `threads.py:2387` — `_emit(redis, run_id, 'confidence', level=..., avg_similarity=..., disclaimer=...)`
- Suggestions: similar `_emit` somewhere in the post-citation block (need to grep to confirm location).

Frontend callbacks exist and update state correctly:
- `useMessages.ts:303-310` — `onConfidence` writes `message.confidence` 
- `useMessages.ts:313-316` — `onSuggestions` writes `message.suggestions`

Two possibilities:
1. **Render-side gap:** `MessageItem.tsx` doesn't render `confidence` or `suggestions` even when present on the message. (Likely the actual root cause if the events ARE arriving and the state IS being updated.)
2. **Side-effect of D-067.2-01:** the events arrive during the `guardedSetMessages` no-op window and never land in state. (Resolved automatically once D-067.2-01 fix lands.)

**Fix shape:** Plan 04 begins as INVESTIGATION (not blind code change). Verify against actual streaming runs:

2. If state IS populated but UI doesn't render: add render blocks to `MessageItem.tsx` for both fields. Check `frontend/src/types/index.ts` `Message.confidence` + `Message.suggestions` shapes.
3. If state is NOT populated: backend not emitting (re-check `threads.py` for `_emit('suggestions', ...)`); fix backend.

**Acceptance (user-observable):** After fix, on a Fahed-Mrad search-only prompt:

2. A follow-up suggestions block appears with 2-4 clickable example follow-ups derived from agent context.

### D-067.2-05 — Chat title stays "New Chat" on run failure / interruption

**Failure mode:** User submits a prompt; run fails / times out / is cancelled / hits an exception. Sidebar entry stays "New Chat" forever — even though the user message is persisted and the thread is otherwise valid. Forces the user to remember which "New Chat" was theirs.

**Root cause (line-anchored):** `backend/app/api/threads.py:2398-2408`:
```python
# Auto-title: generate on first exchange (history had exactly 1 message = first user msg)
if len(history_resp.data) == 1 and history_resp.data[0]["role"] == "user":
    first_user_msg = history_resp.data[0]["content"]
    title, title_fallback = generate_thread_title(first_user_msg, user_settings=user_settings)
    if title_fallback:
        await _emit(redis, run_id, 'fallback_model', **title_fallback)
    try:
        await aexec(supabase.table("threads").update({"title": title}).eq("id", thread_id))
        await _emit(redis, run_id, 'title', content=title)
    except Exception:
        pass
```
This runs AFTER `_persist_assistant_message()` at line 2390, which is in the success path. If the run terminates before line 2389 (TimeoutError, CancelledError, exception, user Stop), title generation never fires.

**Fix shape:** Move title generation to fire AFTER the FIRST user message is persisted, BEFORE the agent loop starts. Title is generated from the user message content alone — no dependency on assistant content.

Locate where the first user message is persisted in the agent runner (likely shortly after the run starts, near `runs.py` POST handler or top of the `_run_agent_streaming` body in `threads.py`). Hoist the title generation block up:

```python
# After first user message persisted, BEFORE agent loop starts:
if len(history_resp.data) == 1 and history_resp.data[0]["role"] == "user":
    first_user_msg = history_resp.data[0]["content"]
    title, title_fallback = generate_thread_title(first_user_msg, user_settings=user_settings)
    if title_fallback:
        await _emit(redis, run_id, 'fallback_model', **title_fallback)
    try:
        await aexec(supabase.table("threads").update({"title": title}).eq("id", thread_id))
        await _emit(redis, run_id, 'title', content=title)
    except Exception as e:
        logger.warning(f"title generation failed at run start: {e}", exc_info=True)
```

Remove the duplicate block at `:2398-2408`. Title now generates regardless of run outcome — succeeds, fails, times out, cancelled — title persists.

**Acceptance (user-observable):**
1. Submit any prompt → mid-stream click Stop → sidebar shows a generated title (NOT "New Chat").
2. Submit a prompt that triggers a synthetic timeout (`LLM_CALL_TIMEOUT_OVERRIDES=...=5`) → sidebar shows generated title even though run failed.

## Specific Ideas

- **D-067.2-01 / D-067.2-02 single-fix opportunity:** the underlying race is identical (synchronous-write requirement on `activeThreadIdRef`); a single targeted edit (move `setViewingThread(...)` into a `useLayoutEffect` AND add it synchronously in `handleSend` before `sendMessage`) closes both. Plan 01 should be ONE plan, not two.
- **D-067.2-03 ergonomic constraint:** the new `/sandbox-outputs/{storage_path}` endpoint MUST authenticate via the existing user JWT cookie/header. If the endpoint were anonymous, it would be a cross-user IDOR. Ownership check pattern: `storage_path` includes the `user_id` UUID as a path segment; verify it matches `current_user["id"]`.
- **D-067.2-04 cheap test path:** before writing any render code, paste this in browser DevTools console while the latest assistant message has confidence: `JSON.stringify($r.confidence)` (using React DevTools' `$r` selected-fiber). If it returns the populated object, render-side gap is confirmed.
- **D-067.2-05 hoist location:** the first user message is inserted in `threads.py` early in the `POST /threads/{id}/messages` handler (or its delegate). The simplest hoist is to move the title block to fire right after that insert + before the agent loop launches. Look for the pattern `await aexec(supabase.table("messages").insert({"role": "user", ...}))`.
- **D-067.2-06 model-id verification:** before UAT, verify the actual configured model ids by reading `backend/.env` `OPENAI_MODELS` and `ANTHROPIC_MODELS` (visible from earlier grep: `OPENAI_MODELS=gpt-4.1,gpt-4.1-mini,gpt-4.1-nano,gpt-4o,gpt-4o-mini,gpt-5,gpt-5.4,gpt-5.2,gpt-5.4-mini,gpt-5.4-nano` and `ANTHROPIC_MODELS=claude-opus-4-6,claude-sonnet-4-6,claude-haiku-4-5-20251001`).
