<objective>
Add the optional `retry_empty_descriptions_only=true` query param to `/reextract` (D-072-04 Shape B). When set, the handler bypasses the delete cascade + re-extract entirely and ONLY refills `document_images` rows where `description='' AND created_at < now() - 5min`. This closes the loop on D-072-03 (persist-empty-rows): operators now have a cheap way to retry the vision-LLM pass without nuking text/tables/non-empty images.

**BLOCKER 1 — schema column note:** D-072-04 CONTEXT.md uses `extracted_at` in prose; the schema column is `created_at` (confirmed: document_images table definition lives in `supabase/migrations/030_missing_tables.sql` lines 108-116 with `created_at timestamptz NOT NULL DEFAULT now()`, AND supabase/full-schema.sql:312-321 shows column is `created_at`, NOT `extracted_at`). The 5-minute retry window keys off `created_at`. There is no `extracted_at` column anywhere in the schema. All references in this plan and the helper docstring use `created_at`.

**BLOCKER 3 — DB I/O reduction:** Per checker's Option (a), the retry helper accepts `app_settings: UserEffectiveSettings` as an INJECTED parameter from the route handler. The ROUTE handler does NOT currently load `app_settings` anywhere (only the `ingest_document` BackgroundTask body does — at ~line 1128). Plan 04 Task 1 ADDS a `load_app_settings()` call INSIDE the new retry-branch fork (wrapped in `run_in_threadpool` per D-v2.5-01). The load is scoped to the retry branch — non-retry callers see no extra DB I/O. The helper itself NEVER calls `load_app_settings()` — fewer threadpool boundaries inside the loop, cleaner test mocking, aligns with how `extract_and_store_images` already accepts `app_settings`.

**WARNING 3 — D-072-02 downscale invariant for retry path:** Plan 01 ships a shared `_downscale_b64_for_vision(b64_png, max_edge=MULTIMODAL_THUMBNAIL_MAX_EDGE)` helper (extracted from the inline downscale code block in `extract_and_store_images`). Plan 04 calls the SAME helper before every `describe_image` call in the retry branch so both call sites share the invariant.

**WARNING 4 — matching key:** Use `(image_index, page)` composite key (not bare `image_index`) to dodge cross-engine misalignment when different engines assign different image_index orderings. Rows whose `(image_index, page)` pair doesn't match any freshly-extracted image stay empty (best-effort retry). Operator can fall back to full `/reextract` if needed.

    ```python
        # downscale, describe.

            b64_downscaled = _downscale_b64_for_vision(b64)
            try:
                desc = describe_image(b64_downscaled, app_settings)
            except Exception as exc:
                log.debug(
                    "retry_empty_descriptions_only: describe_image failed on row %s: %s",
                    row.get("id"), exc,
                )
                continue
            if not desc:
                continue
            # UPDATE this row (threadpool-wrapped per D-v2.5-01).
            await run_in_threadpool(
                lambda r=row, d=desc: supabase.table("document_images")
                .update({"description": d})
                .eq("id", r["id"])
                .execute()
            )
            refilled += 1

        log.info(
            "retry_empty_descriptions_only: refilled %d of %d empty rows for %s",
            refilled, len(empty_rows), document_id,
        )

        doc_resp = await run_in_threadpool(
            lambda: supabase.table("documents")
            .select("*")
            .eq("id", document_id)
            .eq("user_id", user_id)
            .single()
            .execute()
        )
        return DocumentResponse(**doc_resp.data)
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→/reextract retry-only | Authenticated request reaches the retry branch; the `retry_empty_descriptions_only` flag is a boolean — no injection surface, but RLS still gates the empty-row SELECT |
| storage→re-extract loop | Storage bytes are re-extracted server-side without the delete cascade; same trust surface as the existing /reextract; no NEW surfaces opened |
| describe_image→vision-LLM | The retry branch invokes the vision LLM with the freshly-extracted (and downscaled) b64; same trust surface as the existing extract_and_store_images path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-072-04-01 | I (Info disclosure) | retry branch SELECT against document_images might leak existence to non-owner | low | mitigate | Owner-only `.eq("user_id", user_id)` predicate preserved on the empty-row SELECT (matches the route-entry owner check at lines 786-799). Even if document_id is correct, mismatched user_id returns empty rows and the helper no-ops. |
| T-072-04-02 | D (Denial of service) | adversarial repeated /reextract?retry_empty_descriptions_only=true calls trigger unbounded vision-LLM calls | medium | mitigate | The 5-minute `created_at < now() - interval '5 minutes'` filter prevents thrashing — empty rows just-INSERTed are not retry candidates. Each refilled row removes itself from the retry pool. Multi-user multiplication is bounded by D-072-08's `multimodal_max_vision_calls` cap inherited from extract_and_store_images via describe_image. |
| T-072-04-03 | T (Tampering) | adversarial b64 returned by re-extracted PDF image triggers vision-LLM unsafe-content rejection | low | accept | OpenAI/Anthropic provider handles unsafe content rejection; describe_image catches exceptions and returns ''. The empty row stays empty (next /reextract retry will try again). Operator can manually delete the row via the Documents UI if recurring. |
| T-072-04-04 | E (Elevation of privilege) | retry branch bypasses owner-only delete cascade — could be exploited to refill rows on another user's doc? | low | mitigate | The retry-only branch INHERITS the owner-only SELECT at route entry (documents.py:786). Storage download is owner-gated. Empty-row SELECT is owner-gated. UPDATE is row-id-targeted (matched against the previous SELECT). No cross-user attack surface introduced. |
| T-072-04-05 | T (Tampering) | cross-engine misalignment via mid-flight engine swap could refill wrong rows | low | mitigate | WARNING 4 — composite `(image_index, page)` matching key. Within an engine the key is stable; cross-engine mid-flight swaps are documented operationally as "do not mix engines" in 072-HUMAN-UAT.md. Worst case: row stays empty (skipped via `if fresh is None: continue` best-effort path) — never refilled with WRONG content. |
