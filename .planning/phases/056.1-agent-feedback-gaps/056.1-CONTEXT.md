# Phase 56.1: Agent Feedback Gaps — Context

## Goal

Eliminate the 30–120 second silence window during tool argument generation, add a live elapsed timer during tool execution, and prevent pre-emptive execute_code calls via system prompt hardening.

## Background

Phase 56 improved labels and step counters **inside** ToolCallPanel — but ToolCallPanel only renders when `toolCalls.length > 0`, which requires a `tool_start` event. `tool_start` fires only after the full tool arguments are buffered (`threads.py:1031`). For `execute_code` with 50–262KB Python payloads on OpenRouter (~10 tok/s), this creates a **30–120 second silence window** where nothing appears in the UI.

Root cause confirmed via LangSmith trace analysis (see `agent_realtime_feedback_assessment.md`):

```
LLM streams tool name (instant) → arguments stream silently for 30–120s → tool_start fires → ToolCallPanel appears
                                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                   THIS ENTIRE PHASE IS INVISIBLE — Phase 56 didn't touch it
```

## Decisions (Locked)

### D-01: `tool_preparing` SSE event — emit when tool name first known

Backend: In the OpenAI streaming loop (`threads.py` lines 869–879), when `tc.function.name` is first set for a new tool index, immediately emit:
```python
{"type": "tool_preparing", "name": tc.function.name, "index": idx}
```
Use a set `_announced_tools` to emit exactly once per tool per iteration. This fires within 0.5s of the LLM's decision, before any arguments stream.

Also apply to the Anthropic path: the Anthropic SDK already delivers complete tool calls via `tool_start` events in `_ant_event["name"]` (lines 816–822), so `tool_preparing` is emitted there immediately on the `tool_start` event.

### D-02: Frontend `tool_preparing` → `status: "preparing"` on ToolCall

Three frontend changes:
1. `api.ts`: dispatch `tool_preparing` events to a new `onToolPreparing(name: string, index: number)` callback
2. `useMessages.ts`: `onToolPreparing` creates a ToolCall entry with `status: "preparing"`, `name`, and no args yet. Uses `index` field to match against later `tool_start` which carries the full args — transition from `"preparing"` to `"running"` when `tool_start` arrives for the same tool name.
3. `ToolCallPanel.tsx`:
   - Guard change: render panel when `toolCalls.length > 0 || preparingTools.length > 0` — but simpler: include `"preparing"` in the existing `toolCalls` array, the panel already maps over it
   - Status `"preparing"`: render a pulsing gradient bar instead of spinner + tool icon at reduced opacity + label "Preparing [Tool Name]…"
   - `activeTool` check: include `status === "preparing"` alongside `status === "running"`
   - `allDone`: `"preparing"` is NOT done, so it correctly keeps the panel in active state
   - `hasInterrupted`: `"preparing"` is not interrupted

### D-03: Live elapsed timer during tool execution

Frontend-only change in `ToolCallPanel.tsx`. Replace the static `TimeBadge` (which only appears after `endedAt` is set, i.e., after tool completes) with:
- While `status === "running"` AND `startedAt` exists: render a live `ElapsedTimer` component that ticks every 250ms showing `formatDuration(Date.now() - startedAt)`
- While `status === "done"` AND both `startedAt` and `endedAt` exist: render static `TimeBadge` as before (no change)
- While `status === "preparing"`: no timer (no startedAt yet)

The `ElapsedTimer` component:
```tsx
function ElapsedTimer({ startedAt }: { startedAt: number }) {
  const [elapsed, setElapsed] = useState(() => Date.now() - startedAt)
  useEffect(() => {
    const t = setInterval(() => setElapsed(Date.now() - startedAt), 250)
    return () => clearInterval(t)
  }, [startedAt])
  return (
    <span className="flex items-center gap-0.5 text-[10px] text-primary/70 font-mono tabular-nums flex-shrink-0 animate-pulse">
      <Clock className="w-2.5 h-2.5" />
      {formatDuration(elapsed)}
    </span>
  )
}
```

### D-04: System prompt — prevent pre-emptive execute_code + code size guidance

Two additions to `SYSTEM_PROMPT` in `threads.py`:

**Rule 1 (sequential tool use):** Add to the `## Rules` section:
> "**Never call execute_code in the same response as search_documents, analyze_document, read_document, or web_search.** Retrieve content first; call execute_code only in the NEXT iteration after you have received the retrieved data. Calling execute_code before reading documents produces fabricated content."

**Rule 2 (code size):** Add after Rule 1:
> "**Keep execute_code scripts under 200 lines.** Use data-driven loops and helper functions instead of hardcoding each slide, section, or page. Monolithic scripts are slow to generate and error-prone. If the task requires more than 200 lines, split into multiple execute_code calls."

These are additive — all existing PROMPT-01 Q&A/generation disambiguation rules from Phase 54 remain intact.

### D-05: `tool_preparing` for structured mode (CallingMode.STRUCTURED)

In `CallingMode.STRUCTURED`, tool calls are parsed from `full_content` AFTER the stream ends (lines 882–890) — there is no streaming tool name. The `tool_preparing` event cannot fire during streaming for this path.

For structured mode: emit `tool_preparing` events immediately after `parse_structured_tool_calls` returns, before the tool execution loop — so the user still gets near-instant feedback (0.5s after stream ends instead of after argument parsing).

```python
# After structured_calls is populated, before execution loop:
for idx, call in enumerate(structured_calls):
    yield f"data: {json.dumps({'type': 'tool_preparing', 'name': call.function.name, 'index': idx})}\n\n"
```

## Success Criteria

1. Send a query that triggers `execute_code`. Within 1 second of the LLM deciding to call it, the ToolCallPanel appears showing "Preparing Execute Code…" with a pulsing indicator — even though the 262KB Python payload hasn't finished streaming yet.
2. While a tool is executing (status "running"), the ToolCallPanel header shows a live elapsed time counter that ticks every ~250ms.
3. When the user asks the agent to "generate a PowerPoint from my dissertation", the agent calls search_documents or analyze_document first, waits for results, then calls execute_code in the next iteration — never pre-emptively.
4. Code generated by execute_code is ≤200 lines (data-driven, not hardcoded per slide).
5. Existing tool rendering (running/done/interrupted statuses, sub-agent blocks, execute_code blocks, skill rows) is unchanged.
