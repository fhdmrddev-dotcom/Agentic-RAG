# Phase 056.1: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Phase 056.1 adds three new SSE event types (`tool_preparing`, `iteration_start`/`planning`), an `ElapsedTimer` component, the `preparing` ToolCall status, and upgrades the system prompt. The core design is sound and the happy-path flow (OpenAI native tool calling) works correctly. However, several edge-case bugs exist: duplicate-named tool calls in one agent round will silently lose their `preparing` phase in the UI; the Anthropic path lacks the `_announced_tools` deduplication guard; the `finally` block over-broadly marks tools as interrupted; and the `displayItems` sort causes `preparing` entries to jump to the top of the tool list. One pre-existing design issue (double `onDone` call) is now more likely to surface because the stream is longer-lived.

## Warnings

### WR-01: Duplicate-named tool calls lose second `preparing` entry — silent UI gap

**File:** `frontend/src/hooks/useMessages.ts:188-193`

**Issue:** `onToolPreparing` deduplicates by `tc.name === name && tc.status === "preparing"`. When the model calls the same tool twice in one round (e.g., two `search_documents` calls), the second `tool_preparing` SSE event is silently dropped because a `preparing` entry for that name already exists. The backend emits distinct `index` values for each call but the frontend discards them. The second call will appear to skip the `preparing` phase entirely and jump straight to `running` (or not appear until `tool_start`).

**Fix:** Key the deduplication on `index`, not `name`. Store the `preparing-{index}` id in the entry and match on it:

```typescript
// onToolPreparing callback
(name: string, index: number) => {
  setMessages((prev) =>
    prev.map((m) => {
      if (m.id !== assistantId) return m
      const preparingId = `preparing-${index}`
      // Deduplicate on the synthetic id, not on name
      const alreadyPreparing = (m.tool_calls ?? []).some(
        (tc) => tc.id === preparingId
      )
      if (alreadyPreparing) return m
      const preparingEntry: ToolCall = {
        id: preparingId,
        name,
        args: {},
        status: "preparing",
        startedAt: undefined,
      }
      return { ...m, isPlanning: false, tool_calls: [...(m.tool_calls ?? []), preparingEntry] }
    }),
  )
},
```

### WR-02: `onToolStart` upgrade matches first `preparing` by name — wrong entry promoted for parallel same-name calls

**File:** `frontend/src/hooks/useMessages.ts:211-224`

**Issue:** `findIndex((tc) => tc.name === name && tc.status === "preparing")` returns the first match. If two `search_documents` calls are both `preparing`, the second `tool_start` event will upgrade the first entry (already `running` from the first `tool_start`) rather than the intended second entry. The fallback path (line 224) appends a new entry missing the `id` field, breaking the name-based `tool_end` match for that call.

**Fix:** After adopting `preparing-{index}` ids (WR-01), match on `tc.id === \`preparing-${index}\`` in `onToolStart`. Requires the backend `tool_start` event to carry `index`, which it currently does not. As an interim fix without a backend change, fall back to name-match but ensure the newly-appended fallback entry includes the real tool-call id when available:

```typescript
// In the fallback append path, always include an id field.
// The real id arrives in tool_end result; for now use a unique placeholder.
updatedCalls = [...existingCalls, {
  id: `running-${Date.now()}`,
  name, args, status: "running" as const, startedAt: Date.now()
}]
```

### WR-03: `finally` block marks tools on ALL assistant messages as interrupted, not only the streaming message

**File:** `frontend/src/hooks/useMessages.ts:424-441`

**Issue:** The interrupt logic iterates `prev.map((m) => { if (m.role !== "assistant") return m; ... })`. This touches every assistant message in the thread, not just the one being streamed (`assistantId`). In the normal case existing messages only have `status === "done"` tools, so the `hasActiveTools` guard prevents mutation — but this is fragile. If any prior message were re-rendered with a `running` or `preparing` tool (e.g., via Realtime UPDATE), it would be incorrectly marked `interrupted`.

**Fix:** Scope the guard to the streaming message only:

```typescript
if (wasStoppedByUser) {
  setMessages((prev) =>
    prev.map((m) => {
      if (m.id !== assistantId) return m          // ← was: m.role !== "assistant"
      const hasActiveTools = m.tool_calls?.some(
        (tc) => tc.status === "running" || tc.status === "preparing"
      )
      if (!hasActiveTools) return m
      return {
        ...m,
        tool_calls: m.tool_calls!.map((tc) =>
          tc.status === "running" || tc.status === "preparing"
            ? { ...tc, status: "interrupted" as const }
            : tc
        ),
      }
    })
  )
}
```

### WR-04: Anthropic path lacks `_announced_tools` guard — duplicate `tool_preparing` on retry

**File:** `backend/app/api/threads.py:822-827`

**Issue:** The OpenAI/OpenRouter path guards `tool_preparing` emission with `if idx not in _announced_tools` (line 890). The Anthropic path has no equivalent guard. It emits `tool_preparing` unconditionally on every `tool_start` event from the generator. The Anthropic SDK fires `tool_start` once under normal conditions, so this is currently safe. However, if the inner `while True:` retry loop re-enters the `for _ant_event in _ant_gen:` loop (after a transient error that does not raise — e.g., the generator partially replays), a second `tool_preparing` would be emitted for the same tool. After the first `tool_start` upgrades the entry to `running`, the duplicate `tool_preparing` would insert a new `preparing` entry with the same name (WR-01's dedup would catch it only while status is still `preparing`).

Additionally, the Anthropic path re-declares `tool_calls_buffer = {}` and `finish_reason = None` at lines 811-812 (inside `while True:`) but does NOT declare `_announced_tools`. This asymmetry is the defect.

**Fix:** Add `_announced_tools: set` before the Anthropic event loop, matching the OpenAI path:

```python
# Anthropic path — add before the for loop:
_announced_tools_ant: set[int] = set()
for _ant_event in _ant_gen:
    ...
    elif _etype == "tool_start":
        _idx = len(tool_calls_buffer)
        if _idx not in _announced_tools_ant:   # guard added
            _announced_tools_ant.add(_idx)
            yield f"data: {json.dumps({'type': 'tool_preparing', 'name': _ant_event['name'], 'index': _idx})}\n\n"
        tool_calls_buffer[_idx] = { ... }
```

### WR-05: `preparing` entries sort to epoch-0, jumping to top of `displayItems` list

**File:** `frontend/src/components/chat/ToolCallPanel.tsx:585-587`

**Issue:** `displayItems` is built by mapping each `ToolCall` to `{ ..., t: tc.startedAt ?? 0 }`. A `preparing` entry has `startedAt: undefined` (set in `useMessages.ts` line 199), so `t = 0` (Unix epoch). When the list is sorted by `t`, all `preparing` tools sort ahead of any already-`running` or `done` tools regardless of their actual arrival order. For a multi-tool agent round, this causes the new `preparing` entry to visually jump to the top of the panel, above the tool that is currently executing.

**Fix:** Use `Date.now()` as the fallback instead of `0`, or preserve insertion order for `preparing` entries by appending them to the end rather than sorting:

```typescript
// Option A — use current time as fallback:
...toolCalls.map((tc): DisplayItem => ({
  kind: 'tool',
  tc,
  t: tc.startedAt ?? Date.now(),   // ← was: ?? 0
})),

// Option B — stable sort: put preparing entries at the end by using Infinity for startedAt:
t: tc.status === "preparing" ? Infinity : (tc.startedAt ?? Date.now()),
```

Option B is safer because it preserves the natural append order of `preparing` entries.

### WR-06: Structured-mode `tool_preparing` emitted after buffer population — near-zero `preparing` duration

**File:** `backend/app/api/threads.py:899-913`

**Issue:** In the structured (XML) path, `tool_calls_buffer` is fully populated at lines 899-906 and then `tool_preparing` events are emitted at lines 910-911. The `tool_start` events will immediately follow in the same agent iteration before the next `yield` suspension point, meaning the frontend receives `tool_preparing` and `tool_start` for the same tool in the same SSE flush. The `preparing` state will never be visible to users in this path — it transitions to `running` before the browser can render a frame.

While not incorrect per se, this defeats the stated purpose of D-05 ("fires immediately after parse returns, before the tool execution loop"). The execution loop begins directly after the `yield` statements on lines 910-911, so there is no async gap.

**Fix:** Add an explicit `await asyncio.sleep(0)` after the batch of `tool_preparing` yields to force an event-loop yield before execution begins:

```python
for idx, call in enumerate(structured_calls):
    yield f"data: {json.dumps({'type': 'tool_preparing', 'name': call.function.name, 'index': idx})}\n\n"
await asyncio.sleep(0)   # flush to client before execution starts
full_content = ""
finish_reason = "tool_calls"
```

### WR-07: `onDone` called twice when stream ends without `stream_end` event

**File:** `frontend/src/lib/api.ts:202-222`

**Issue:** When the SSE `done` event is received (line 202-204), `onDone()` is called immediately. The code then continues reading the stream for the `stream_end` event (by design). If the backend connection drops or the ASGI process crashes after sending `done` but before sending `stream_end`, the `while (true)` loop exits via `if (done) break` and `onDone()` is called a second time at line 222.

`onDone` in `useMessages.ts` calls `setIsStreaming(false)` and clears the `isPlanning` flag. A second call is idempotent for those effects, but it re-executes `setMessages(prev.map(...))` which may cause a spurious re-render mid-`finally`-block teardown.

This is a pre-existing issue that became more likely to trigger with Phase 56.1 because the stream is now longer (more events after `done`).

**Fix:** Add a guard flag inside `streamMessage`:

```typescript
let doneFired = false
// In the SSE event handler:
} else if (parsed.type === "done") {
  if (!doneFired) { doneFired = true; onDone() }
  // Do NOT return — stream stays open for suggestions event
}
// At end of function, after the while loop:
if (!doneFired) onDone()
```

### IN-01: `ToolCall.args` typed as `Record<string, string>` — incorrect for nested args

**File:** `frontend/src/types/index.ts:32`

**Issue:** The `args` field is typed `Record<string, string>`, but tool arguments include nested objects (`metadata_filter`), arrays (`libraries`, `output_files`), and numbers (`start_line`, `end_line`). `ToolArgsBlock` in `ToolCallPanel.tsx` already works around this with `typeof val === "object"`, confirming the type is known to be inaccurate. This type lie prevents TypeScript from catching incorrect argument shapes and makes the interface misleading.

**Fix:**
```typescript
args: Record<string, unknown>
```
