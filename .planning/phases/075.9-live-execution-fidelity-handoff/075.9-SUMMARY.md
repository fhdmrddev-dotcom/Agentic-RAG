## Accomplishments

- **Stable client-side tool key** (T1+T2+T3) — `tc.clientKey` is stamped ONCE at first observation in the StreamsProvider reducer (`onToolPreparing` AND the `onToolStart` no-preparing-entry fallback). - **Single-render-path Shiki editor inset** (T4) — extracted `ExecuteCodeEditorInset` as an exported sub-component. Reads `tc.argsCodeText ?? tc.args.code`, so the same DOM mounts during preparing (cumulative SSE bytes from `tool_args_progress`) and running/done (canonical args after `tool_start`). The reducer copies `argsCodeText → args.code` at tool_start, so both fields carry identical content at the moment of swap — the visual is byte-stable. No re-mount, no flash, no re-flow.
- **`ToolArgsLivePanel.hideBody`** (T4) — new prop renders a header-only band (title + byte counter, no chevron, no body) for execute_code preparing. The Shiki inset owns the body; the panel keeps the "Generating code… (X.X KB)" affordance so the user still sees the byte counter ticking up.
- **`ShikiCode.streaming`** (T4) — uses React 18's `useDeferredValue` to batch rapid `code`-prop changes during the SSE stream. The WASM tokenizer runs at most once per scheduler idle slice; no manual debounce, no lodash.
- **WR-01: Shiki promise reset on rejection** (T5) — `getHighlighter()` now wraps the IIFE body in `try/catch`. On rejection, `highlighterPromise = null` BEFORE the `throw err` so the rethrow propagates to the caller's `.catch` (the `useEffect` path that sets `html=null` → plain-pre fallback) WHILE the singleton goes back to null. The NEXT mount sees a null singleton and kicks a fresh WASM init. Without WR-01, ONE bad init permanently degraded every future `<ShikiCode>` mount to the plain-pre fallback for the rest of the page session.
- **WR-02: SECURITY CONTRACT JSDoc** (T5, partially shipped in T4) — `ShikiCodeProps.code` JSDoc explicitly states the input MUST be plain text. A second SECURITY JSDoc above the `dangerouslySetInnerHTML` call documents that `html` originates exclusively from `hl.codeToHtml(...)`, which HTML-escapes its input before emitting the styled `<span>` tree.
- **Test hook `__resetShikiHighlighterForTests`** (T5) — exported with the double-underscore convention so production callers won't reach for it. Enables vitest cases to reset the module-scope singleton between tests, making the WR-01 "after-failure-retry" assertion order-independent.

## Decisions Made

1. **Provider field is not yet routed through `makeStreamCallbacks`.** The factory closure has access to `assistantId` and `threadId` but not the provider. The `makeToolKey` fallback to `"unknown"` is fine — `assistantId + name + observedAt + index` is collision-stable within a single assistant message, and cross-message dedup is not in scope. If a future phase needs to dedup tool calls across messages (e.g. "did the same exact analyze_document call run in two different turns?"), surface provider through the callback factory at that point.

2. **Composite fallback retained in `deduplicatedToolCalls`.** The chain is `tc.clientKey ?? tc.id ?? `${name}-${startedAt}-${idx}``. The last segment is dead code for new live-SSE tools (they always carry clientKey) but ships as defense-in-depth for DB-loaded historical messages and in-flight test fixtures that pre-date the T2 stamp. Marked with `// REMOVE after migration window` so a future cleanup phase can drop it once the window has passed.

3. **Single-render-path via extracted sub-component, not full ExecuteCodeBody rebranching.** The cleanest implementation would have been to call `<TOOL_BODIES.execute_code tc={tc} />` for ALL execute_code states (including preparing), letting ExecuteCodeBody render the "Preparing" label + editor inset + StatusPill. That would have meant duplicating the generic-tool branch's StatusPill / icon / args header machinery inside ExecuteCodeBody — significant refactor. The chosen path is smaller: extract just the editor inset (`ExecuteCodeEditorInset`, ~25 LOC), and mount it twice — once inside ExecuteCodeBody (running/done) and once in ToolCallPanel's preparing branch. The unified read of `argsCodeText ?? args.code` gives byte-stability without touching the surrounding chrome.

4. **`hideBody` prop on ToolArgsLivePanel, not a children slot.** Two patterns were on the table: (a) `hideBody: boolean` — simple flag that drops the chevron + expandable body; (b) children-injected body — caller passes the body React node. The boolean is cleaner because it keeps the panel's header logic (title + byte counter format + KB rounding) DRY across the two consumers; a children slot would have leaked rendering responsibility back into the caller and made it easy to drift the header format.

5. **`useDeferredValue` for streaming, not a manual debounce.** React 18's `useDeferredValue` returns the latest value but lets the scheduler defer re-renders that depend on it. For the WASM tokenizer, this means at most one tokenization per concurrent-mode idle slice. Manual debounce (`setTimeout` + clearout) would have meant tracking a timer ref, cleanup on unmount, and a tunable debounce window — three new failure modes. The native hook is one line.

6. **Test hook exported with double-underscore prefix.** `__resetShikiHighlighterForTests` is exported because vitest's `vi.mock` factory toggling can't reach inside the module to null the singleton between cases. The double-underscore prefix signals "test-only, not part of the public API." A `vi.resetModules()` approach was rejected because it'd force vitest to re-import the SUT between cases and lose the mocked `import("shiki")` registration.

7. **`tc.argsCodeText!` non-null assertions in the ToolCallPanel branch.** The surrounding `if` condition (`tc.argsCodeText && tc.argsCodeText.length > 0 && tc.argsBytesStreamed != null`) statically proves both fields are defined inside the closure, but TypeScript's narrow analysis doesn't flow through the IIFE pattern I used (the `(() => { ... })()` boundary breaks the narrowing). Added `!` assertions on the props pass-down lines; safe because the condition gate is right above.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing Critical] Reducer's `onToolStart` fallback branch had no clientKey stamp**

- **Found during:** Task 2 implementation
- **Issue:** The plan said "stamp clientKey at every reducer path that creates a NEW tool entry." The most obvious path is `onToolPreparing`. But the `onToolStart` reducer has a second creation path: when no preparing entry exists AND no finalized entry exists, it appends a fresh `{ id: running-${Date.now()}, ... }` entry. Some providers (older OpenAI legacy paths, certain OpenRouter models per Phase 075.2 RESEARCH) skip the preparing-state SSE event entirely and emit `tool_start` as the first observable. Without stamping there too, those providers would have ToolCall entries without `clientKey` — degrading the T3 dedup invariant.
- **Fix:** Added a parallel clientKey stamp in the `onToolStart` fallback branch, using `existingCalls.length` as the tie-break index. Also captures `observedAt = Date.now()` once and reuses it for both the clientKey and the `id`/`startedAt` so the timestamp is consistent.
- **Files modified:** `frontend/src/providers/StreamsProvider.tsx`
- **Verification:** new vitest case `when provider skips preparing event, tool_start ALSO stamps a clientKey` exercises this path directly.
- **Committed in:** `52fb1ed` (T2 commit)

**2. [Rule 2 — Missing Critical] `step-summary-row` React key also depended on `collapsedTc.id`**

- **Found during:** Task 3 sweep
- **Issue:** Beyond `deduplicatedToolCalls` and `panelExpanded`, there's a third surface where `tc.id` is used as a key-source: the `step-summary-${i}-${collapsedTc.id ?? collapsedTc.name}` React key for collapsed-mode rows in Focus Mode. If a tool's `tc.id` mutated across the dedup pass while the row was in the collapsed view, the row would re-mount mid-stream. The plan listed this as a "sweep" target ("Any other `tc.id` Record key or React key on tool surfaces — sweep + replace").
- **Fix:** Updated the React key to `step-summary-${i}-${collapsedTc.clientKey ?? collapsedTc.id ?? collapsedTc.name}` for stability across provider-id mutations.
- **Files modified:** `frontend/src/components/chat/ToolCallPanel.tsx`
- **Verification:** existing ToolCallPanel.test.tsx step-summary-row cases stay green (the test fixtures don't mutate `tc.id`, so behavior is unchanged); the new dedup test case proves the principal invariant.
- **Committed in:** `95ecbb2` (T3 commit)
