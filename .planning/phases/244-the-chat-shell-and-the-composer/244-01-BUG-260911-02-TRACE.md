## 3. The trace — C-6's three candidates, driven in order

### (a) *"`activeView` is not `"chat"` at click time, so the click landed on the drawer/palette path"*

**NOT REFUTED, and not reachable from here.** Both list surfaces call the same one-step selector —
`ChatHistoryColumn.tsx:166` and the mobile drawer row at `ChatLayout.tsx:676` — so *which* list was
clicked changes nothing about the handler. Distinguishing them needs the live surface. It is folded
into the re-open trigger below rather than left unexamined.

### (b) *"a re-render / remount discards the first `setState`"*

⛔ **REFUTED, on two driven observations.**

1. **One click, one call.** `fireEvent.click` on the row's real `<button>` calls `onSelectThread`
   **exactly once**, with that thread. There is no intermediate state to discard.
   (`ChatHistoryColumn.tsx:163-167`.)
2. **The receiver has no second step.** `useThreads.selectThread`'s `useCallback` body is
   **exactly** `setSelectedThread(thread)` — asserted against the source, because the property under
   test is *the absence of an effect beside it*, which a passing behavioural test could not see.
   (`frontend/src/hooks/useThreads.ts:35-37`.)

### (c) *"it is `ChatArea`'s own render gate (welcome vs thread), not selection"*

⛔ **REFUTED AS AN EXPLANATION — and this is the sharpest thing the trace found.**

The report observes, simultaneously, a **highlighted row** and a pane showing
*"How can I help you?"*. **Those two readings cannot both come from selection state, because they
read the same value.** Driven:

- `ChatArea.tsx:472` gates the welcome branch on `if (!thread) {`, and `thread` is
  `selectedThread`, passed straight through at `ChatLayout.tsx:804`.
- The literal `How can I help you?` occurs **exactly once** in `ChatArea.tsx` and sits inside that
  branch — so *"the welcome pane is showing"* has exactly one possible source.
- The row's highlight is `selectedThread?.id === thread.id` (`ChatHistoryColumn.tsx:150-155`).

A highlighted row means `thread` is non-null, which means the welcome branch is **not** the one
rendering. ⚠ **So the highlight the reporter saw was almost certainly the HOVER treatment, not
selection.** Driven: an un-selected row carries `hover:bg-accent/40 hover:text-sidebar-foreground`,
a selected one carries `bg-primary/15`, and the `⋯` affordance is revealed by `group-hover` — all
three appear under a resting pointer on **any** row.

⭐ **That reframes the symptom.** Not *"selected but not opened"* — **"the click did not select at
all"**, which is a different defect with a different suspect.

## 4. ⭐ A FOURTH candidate C-6 did not list — the invisible click sink

**`frontend/src/components/layout/ChatHistoryColumn.tsx:220-227`** (pre-fix line numbers).

The per-row actions container is **always rendered** and merely `opacity-0` at rest — a deliberate
A11Y-01 decision (CSS-gated, never render-gated, so a keyboard user can Tab to Stop / Rename /
Delete). Its class list, **quoted verbatim from the failing assertion**:

```
absolute inset-y-0 right-0 flex items-center gap-1 pl-10 pr-1.5
bg-gradient-to-l from-sidebar via-sidebar to-transparent rounded-r-lg
opacity-0 transition-opacity group-hover:opacity-100 group-focus-within:opacity-100
```

It is `absolute inset-y-0 right-0` with a **`pl-10` transparent scrim**, and it is painted **after**
the row `<button>` — so **it wins the hit test over the right-hand strip of every row while being
invisible.** A pointer landing there hits a `div` with **no handler**: the thread is not selected,
while the hover treatment and this very reveal both fire. **That is the reported appearance
exactly.**

⛔ **The evidence is an ASYMMETRY, not a hunch.** Its sibling — the SEED-064 resting run-dot
overlay, `ChatHistoryColumn.tsx:203-206`, with the *same* `absolute inset-y-0 right-0` geometry —
carries `pointer-events-none` and explains itself in its own comment:

> *"`pointer-events-none` keeps it click-through."*

The actions container carried no such token. **One overlay was reasoned about and the other was
not.** Both halves are now driven: a case asserts the run-dot's token (the control) and a case
asserts the actions container's (the finding, seen RED).

**And the target matters, which is what makes an overlay consequential at all.** Driven: a click
dispatched on the row *shell* never reaches `onSelectThread`, while the same click on the `<button>`
does. ⚠ The report notes that clicking *"via the element reference (`ref`)"* had the same effect and
concludes *"it is not a hit-test or pointer-target problem"* — **that inference does not hold**: a
synthetic click on a wrapper does not reach a handler bound to a child, so a ref click failing is
consistent with a target problem rather than evidence against one.

behavioural case proves the options button still opens Rename + Delete, so the click-through
container did not disarm its own controls.

⛔ **It is NOT claimed to fix the report.** jsdom cannot hit-test, so the browser confirmation is
owed and is exactly what the re-open trigger asks for.

### 6.1 What the new mechanism is

⛔ **The 503's own cause is only PARTIALLY established and is not upgraded here.** It is raised

### 6.2 The verdict: ⭐ **SECOND CAUSE**

**Both mechanisms produce the report's COMPLAINT — *"the first click does not open it, the
second one does"* — by different routes, and they are DISTINGUISHABLE ON SCREEN.**

### 6.3 The discriminator, driven against source

§3(c) established the discriminator and this section only has to apply it: the welcome branch is
gated on `if (!thread)` (`ChatArea.tsx:517`), and `thread` is `selectedThread` passed straight
through. So:

| | §4's overlay click-sink | the snapshot-503 path |
|---|---|---|
| did the click select? | **no** — `thread` stays `null` | **yes** — `thread` is non-null |
| which branch renders | the **welcome** pane | the **thread frame** |
| `"How can I help you?"` | present | ⛔ **impossible** |
| starter-prompt chips | present | ⛔ **impossible** |
| transcript | n/a | **empty** |
| after 244-11 | no banner | ⭐ **an amber banner with Retry** |

Two literals are load-bearing and were each measured to occur **exactly once** in `ChatArea.tsx`,
both inside the `!thread` branch: `How can I help you?` (`:550`) and the Phase-216 starter-prompt
chips `📁 Search connected files` / `💬 Draft a team update` (`:573-587`). **A selected thread
cannot render either of them.**

### 6.4 Why that is SECOND CAUSE and not UNRELATED

Taken **literally**, the report describes the welcome pane — *"the content pane keeps showing the
empty 'How can I help you?' state, with the model pickers and the suggestion chips"* — and the
503 path **provably cannot produce that**. Read alone, that argues UNRELATED.

⚠ **But the report's described appearance is already known to be an unreliable composite**, by
this trace's own §3(c): its two halves (*highlighted row* + *welcome pane*) read the SAME value
and cannot both be selection state, and §3(c) concluded the highlight was almost certainly HOVER.
**One half of the description was already refuted as an observation**, so "the reported
appearance" is not a single fixed target against which UNRELATED can be cleanly asserted.

What is NOT in doubt is the report's **measured** evidence, which is appearance-agnostic:
`thinking-trigger` count `0` after click 1 and `8` after click 2. **The snapshot-503 path
produces exactly that**, and the UAT driver hit exactly that — *while looking for this bug*, on
the same surface, four weeks later.

So the honest position is two mechanisms, one complaint:

- If the reporter really saw the welcome pane and the chips → **§4's overlay is the live cause**
  and the 503 is a second, independent way to reach the same complaint.
- If the reporter's "welcome state" was a reading of an empty thread frame → **the 503 path is
  the likelier single cause** and §4 was a real defect that is not this report.

⛔ **Neither branch is decided from a chair.** Both are settled by ONE browser visit, and 244-11
adds a third observable that makes the reading unambiguous: after this plan, the 503 arm renders
a **visible amber banner with Retry**, which the overlay arm never does.
