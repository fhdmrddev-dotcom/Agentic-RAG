**⛔ THE C-2 RULING — bound the READ, do not add a writer.**

C-2 offers two closures: *(a) retire the row server-side when a new run starts on the thread, or
(b) bound the read (only if it is newer than the thread's latest run).* **This plan takes (b)**, and
records (a) as the rejected arm with its reason:

- (b) is a **pure read change** on one query. It makes the lock clear the instant a newer run row
  exists, which is exactly the semantics the operator experiences, and it needs no new writer on a
  244-commit / 81-phase file.
- (a) would add a **second** writer of `runs.status` beside `continue_run`. Two writers of one status
  column is how `runs:active` and `runs.status` drift — the exact failure Phase 145 D-149-09 made one
  atomic co-write to prevent. ⛔ Rejected on that ground, not on difficulty.
- ⚠ (b) must not break `continue_run`: it looks the row up **by `run_id`**, not by scanning for
  `status='cap_paused'`, so an older paused row stays continuable. Assert this.

⚠ **D-244-09 still binds: "drive it; do not reason about it."** C-2 is a source reading — strong
evidence, still a hypothesis. The driven row lives in `244-VALIDATION.md` (post a message at
`cap_paused`, reload, assert the composer is still usable and a NEW run appeared). ⛔ Verified
**after a reload**, not only during a live stream — ROADMAP criterion 2.
