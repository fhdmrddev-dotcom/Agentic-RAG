Replace the current "blast all enabled skills" catalog injection in threads.py with embedding-based relevance matching. When skills match the user's message, only those skills appear in the system prompt and only relevant skill tools are offered. Output: Modified threads.py with skill matching, modified openai_service.py with tool filtering, unit tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User message → match_skills | User-controlled text input used for embedding — potential prompt-injection into embedding model |
| match_skills output → system prompt | Matched skills are injected into the LLM system prompt — skill descriptions could contain manipulation |
| Tool availability → LLM | Conditional tool inclusion based on matching — tool set changes per message |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation |
|-----------|----------|-----------|-------------|------------|
| T-46-05 | Tampering | User message in embedding | mitigate | Embedding model treats input as text only — no special instruction handling. User cannot influence embedding behavior. |
| T-46-06 | Information Disclosure | Skill descriptions in system prompt | accept | Skill descriptions were already visible to LLM before this change. Filtering reduces exposure, not increases it. |
| T-46-07 | Denial of Service | Embedding latency per request | accept | Single OpenAI embedding call per chat request (~50-100ms). Same latency profile as document RAG queries. Falls back gracefully on failure (D-15). |
| T-46-08 | Elevation of Privilege | Explicit name bypass | mitigate | Name bypass only includes the skill in the catalog — the LLM still must choose to call load_skill. No privilege escalation beyond what was already possible. |
</threat_model>
