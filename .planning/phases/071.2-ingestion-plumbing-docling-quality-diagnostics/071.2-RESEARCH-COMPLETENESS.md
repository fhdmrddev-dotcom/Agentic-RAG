## Summary

The existing `071.2-RESEARCH.md` correctly identifies **two plumbing bugs**: (1) `multimodal_service.extract_and_store_tables/_images` ignores `extracted_doc.tables/.images`; (2) `docling.py:198` feeds the chunker `export_to_text()` instead of `export_to_markdown()`. Fixing both is necessary. **It is not sufficient.** Even after the plumbing is correct, the *underlying detection* on the user's thesis pair is wrong on three concrete axes:

1. **DOCX images: `multimodal_service.extract_docx_images` at `multimodal_service.py:175-207` walks ONLY `doc.inline_shapes`.** Per [python-docx issue #747](https://github.com/python-openxml/python-docx/issues/747) + [#159](https://github.com/python-openxml/python-docx/issues/159) + the [Office Open XML spec for floating drawings](http://officeopenxml.com/drwPicFloating.php), `inline_shapes` is documented to be **`<wp:inline>` only** — every `<wp:anchor>` floating picture, every `<v:imagedata>` legacy VML picture, every picture in a header/footer or text box, and every picture inside an SDT/content-control is invisible to this code path. Word's clipboard-paste produces `<wp:anchor>` by default — which is exactly the "pasted pictures" the user is testing. [VERIFIED: direct source read of `multimodal_service.py:186-187`]

2. **PDF images: `multimodal_service.extract_pdf_images` at `multimodal_service.py:132-172` walks ONLY `pdfplumber.page.images`** and reads `stream_obj.get_data()` directly. Per the [PyMuPDF maintainer's discussion in PyMuPDF #2140](https://github.com/pymupdf/PyMuPDF/discussions/2140), `pdfplumber.page.images` is the same scope as PyMuPDF's `page.get_images()` *without* `full=True` — it sees top-level XObject images on the page object but **does not descend into Form XObjects**, and does not handle inline images (BI/ID/EI content-stream operators). PDFs exported from Word "Save As PDF" routinely wrap pictures in Form XObjects (one per drawing region) — exactly the pattern that produces the "PDF has 2 images but the DOCX it was exported from has more". [VERIFIED: pdfplumber 0.11.9 source `_objects.py` and PyMuPDF official docs; CITED above]

3. **PDF tables: pdfplumber's `extract_tables` is ruling-line-based** (it joins detected lines into a grid). On a thesis PDF exported from Word where most tables render as text-positioned cells *without* ruling lines (or with single-line bottom borders only), pdfplumber detects 0–4. Per the [2025 PDF data extraction benchmark](https://procycons.com/en/blogs/pdf-data-extraction-benchmark/), Docling's TableFormer (the model loaded inside `do_table_structure=True`) hit 97.9% accuracy where pdfplumber-class tools were near 0% on the same borderless inputs. [CITED: procycons benchmark]

**Critical observation that connects to SEED-006:** The PDF image count and the DOCX image count are *both wrong in different ways*. They look the same number (2 vs 2 or 4 vs 4) because of **two coincidentally-converging failure modes**, not because they're both right. The DOCX case fails at the python-docx layer (anchor blindness). The PDF case fails at the pdfplumber layer (Form XObject blindness + scope limitation vs `get_images(full=True)`). Both produce small numbers; neither is correct.

**Primary recommendation:** Plans 03 + 04 still ship as scoped. Add **Plan 05 — Detection Ceiling**, scoped to three surgical upgrades:

1. **DOCX images:** Replace the `doc.inline_shapes`-only walk with a ZIP+XPath walk over `word/document.xml` for `a:blip` (covers both `wp:inline` and `wp:anchor`) + `v:imagedata` (legacy VML), reconciled against `word/media/` for the actual image bytes. This is **exactly what Docling's `MsWordDocumentBackend` does at `venv/Lib/site-packages/docling/backend/msword_backend.py:78-83`** — we don't need to invent the pattern; we follow Docling's. [VERIFIED: direct source read]

2. **PDF images:** Always have PyMuPDF's `page.get_images(full=True)` *in the dedup-source set* (already lives in `extractors/pymupdf.py` subprocess). When `extracted_doc` comes from `pypdf-legacy`, run a supplementary PyMuPDF pass via the existing subprocess harness for the multimodal step only (no AGPL fence violation — still subprocess-isolated).

3. **PDF tables:** When `EXTRACTOR_PRIMARY=docling` AND `do_table_structure=True`, the table count comes from Docling's TableFormer. The user has these already configured (`docling.py:80-83`). The fix is purely Plan 04's wiring — *no additional detection upgrade needed*. The data we're missing today is *blocked at the persistence layer*, not at the detection layer. The "PDF tables=4, DOCX tables=39" gap should close to the DOCX number once Docling's table output stops being discarded.

**Net rescope:** Plans 01, 02, 03 unchanged. Plan 04 changes from "wire the existing pdfplumber output" to "wire Docling's output as primary, pdfplumber/python-docx as fallback only when `extracted_doc.tables/.images` is empty AND we want supplementary detection beyond what the primary extractor saw." A new **Plan 05** (image-detection upgrade) adds the DOCX `a:blip` + `v:imagedata` walk and (optionally) the PyMuPDF supplementary PDF pass.

The function name says "extract_docx_images" but the iteration **only walks `doc.inline_shapes`** — and `inline_shapes`, per the python-docx maintainers in [issue #747](https://github.com/python-openxml/python-docx/issues/747) and [#159](https://github.com/python-openxml/python-docx/issues/159), is defined as the collection of `<wp:inline>` shapes only. Picture types this code provably misses on a DOCX with pasted pictures:

| Picture type | OOXML element | Why missed | Frequency in thesis-class docs |
|---|---|---|---|
| **Floating-anchor pictures** (the user's "pasted in" pictures) | `<wp:anchor>` inside `<w:drawing>` | `inline_shapes` walks `<wp:inline>` only; `<wp:anchor>` is a sibling tag, not a descendant | **DOMINANT — most paste-from-clipboard or paste-from-PowerPoint pictures default to anchored, not inline** ([Office Open XML spec](http://officeopenxml.com/drwPicFloating.php), confirmed by `unstructured.io` issue #1615 + docx4j forums) |

| **Header/footer pictures** | `<wp:inline>` or `<wp:anchor>` inside `word/header*.xml` / `word/footer*.xml` | `Document.inline_shapes` only scans the main `word/document.xml` body | Common (logos, watermarks) |
| **Text box pictures** | Picture inside `<w:txbxContent>` (text box's content fragment) | `inline_shapes` halts at the text box boundary | Common in modern Word templates |
| **SDT / content control pictures** | Picture wrapped in `<w:sdt>` content control | Same paragraph-walk halts at SDT boundary | Less common, but real |
| **Shape-fill pictures** | `<a:blipFill>` inside `<wps:wsp>` (Office 2010+ shape) | Not a picture *shape*; a shape *with a picture fill* | Rare in academic docs |

**The user's primary failure mode (the thesis DOCX returns 0 images even though it has pasted pictures) is almost certainly floating-anchor.** This is consistent with Word's default behavior on `Ctrl+V` from another Word doc, from PowerPoint, or from a browser: anchored is the default wrap, not inline.

### Recommended minimal upgrade for DOCX image extraction

Implement a single new function `extract_docx_images_v2` that mirrors Docling's XPath pattern. **This is not novel research — we are directly porting the algorithm from the Docling source.** The function returns a list of `(b64_png, bbox_if_available)` dicts. Replace the `doc.inline_shapes` walk with the new function in `multimodal_service.extract_docx_images`:

```python
# Source: docling/backend/msword_backend.py:78-83 + :266-273 (port)
# Required imports — all already installed (lxml ships with docling/python-docx)
import zipfile
import io
from lxml import etree

_DOCX_BLIP_NAMESPACES = {
    "w":    "http://schemas.openxmlformats.org/wordprocessingml/2006/main",
    "wp":   "http://schemas.openxmlformats.org/drawingml/2006/wordprocessingDrawing",
    "a":    "http://schemas.openxmlformats.org/drawingml/2006/main",
    "r":    "http://schemas.openxmlformats.org/officeDocument/2006/relationships",
    "v":    "urn:schemas-microsoft-com:vml",
    "pic":  "http://schemas.openxmlformats.org/drawingml/2006/picture",
}
_BLIP_EMBED_ATTR = "{http://schemas.openxmlformats.org/officeDocument/2006/relationships}embed"
_VML_IMAGEDATA_ID_ATTR = "{http://schemas.openxmlformats.org/officeDocument/2006/relationships}id"


def _read_docx_relationships(zf: zipfile.ZipFile, part_path: str) -> dict[str, str]:
    """Return rId → target media path for a given DOCX part.

    part_path is e.g. 'word/document.xml'; the rels file is
    'word/_rels/document.xml.rels'. Maps r:embed/r:id attributes to
    media filenames inside word/media/.
    """
    rels_path = part_path.replace(
        part_path.rsplit("/", 1)[-1],
        f"_rels/{part_path.rsplit('/', 1)[-1]}.rels"
    )
    try:
        rels_xml = etree.fromstring(zf.read(rels_path))
    except KeyError:
        return {}
    ns = {"r": "http://schemas.openxmlformats.org/package/2006/relationships"}
    out = {}
    for rel in rels_xml.findall("r:Relationship", ns):
        rid = rel.get("Id")
        target = rel.get("Target")
        # Targets in document rels are relative to part_path's parent
        if rid and target:
            target = target.lstrip("./")
            out[rid] = f"word/{target}" if not target.startswith("word/") else target
    return out


def extract_docx_images_v2(raw: bytes, min_px: int = 50) -> list[dict]:
    """Walk DrawingML a:blip + VML v:imagedata across body, headers, footers, textboxes.

    Captures inline + floating-anchor + VML legacy images that python-docx's
    inline_shapes collection silently drops. Port of
    docling/backend/msword_backend.py:78-83 + :266-273 detection algorithm.
    Storage of the resolved bytes goes through PIL exactly as v1 does, so
    downstream code is unchanged.
    """
    from PIL import Image as PILImage  # already a project dep
    import base64

    results: list[dict] = []
    seen_blob_keys: set[str] = set()  # dedup by media filename — Word can ref the same image twice

    with zipfile.ZipFile(io.BytesIO(raw)) as zf:
        # Discover all XML parts that may carry pictures: body + headers + footers
        candidate_parts = ["word/document.xml"]
        for name in zf.namelist():
            if name.startswith("word/header") and name.endswith(".xml"):
                candidate_parts.append(name)
            elif name.startswith("word/footer") and name.endswith(".xml"):
                candidate_parts.append(name)

        for part_path in candidate_parts:
            try:
                xml_bytes = zf.read(part_path)
            except KeyError:
                continue
            try:
                tree = etree.fromstring(xml_bytes)
            except etree.XMLSyntaxError:
                continue

            rels = _read_docx_relationships(zf, part_path)

            # DrawingML pictures — covers wp:inline AND wp:anchor in one pass.
            for blip in tree.iterfind(".//a:blip", _DOCX_BLIP_NAMESPACES):
                rid = blip.get(_BLIP_EMBED_ATTR)
                media_path = rels.get(rid) if rid else None
                if not media_path or media_path in seen_blob_keys:
                    continue
                seen_blob_keys.add(media_path)
                try:
                    img_bytes = zf.read(media_path)
                    pil = PILImage.open(io.BytesIO(img_bytes))
                    if pil.width < min_px or pil.height < min_px:
                        continue
                    buf = io.BytesIO()
                    pil.convert("RGB").save(buf, format="PNG")
                    b64 = base64.b64encode(buf.getvalue()).decode("ascii")
                except Exception:
                    continue
                results.append({
                    "page": None,
                    "image_index": len(results),
                    "b64_png": b64,
                    "width": pil.width,
                    "height": pil.height,
                })

            # VML legacy pictures (older Word, embedded Visio)
            for vml in tree.iterfind(".//v:imagedata", _DOCX_BLIP_NAMESPACES):
                rid = vml.get(_VML_IMAGEDATA_ID_ATTR)
                media_path = rels.get(rid) if rid else None
                if not media_path or media_path in seen_blob_keys:
                    continue
                seen_blob_keys.add(media_path)
                try:
                    img_bytes = zf.read(media_path)
                    pil = PILImage.open(io.BytesIO(img_bytes))
                    if pil.width < min_px or pil.height < min_px:
                        continue
                    buf = io.BytesIO()
                    pil.convert("RGB").save(buf, format="PNG")
                    b64 = base64.b64encode(buf.getvalue()).decode("ascii")
                except Exception:
                    continue
                results.append({
                    "page": None,
                    "image_index": len(results),
                    "b64_png": b64,
                    "width": pil.width,
                    "height": pil.height,
                })

    return results
```

### Why pdfplumber.page.images returns so few

Per pdfplumber's source (pdfplumber 0.11.9, `pdfplumber/page.py`) and the [PyMuPDF discussion #2140](https://github.com/pymupdf/PyMuPDF/discussions/2140), `Page.images` is built by scanning page-level objects produced by pdfminer.six. It surfaces *only* top-level XObject images directly listed on the page's resource dictionary. It misses:

| Image type | Why pdfplumber misses | Why PyMuPDF `get_images(full=True)` catches it |
|---|---|---|
| **Form XObject children** (the most common miss on Word-exported PDFs) | pdfminer only scans the page-level XObject dict — Form XObjects nested as children are not descended. [CITED: pdfplumber discussion #677 + pikepdf 10.6 content-streams docs] | `full=True` explicitly walks Form XObject children: "creates an extended image list, which also checks whether it is the page itself that displays an image, or some other object ('Form XObject')" [CITED: [PyMuPDF #2759](https://github.com/pymupdf/PyMuPDF/discussions/2759) + PyMuPDF docs] |
| **Inline images** (BI / ID / EI content-stream operators) | Inline images live in the page's `/Contents` stream as operators, not in the resource dict. pdfplumber does not parse them. | PyMuPDF's `page.get_text("dict")` / `get_image_info()` includes inline images. [CITED: PyMuPDF discussion #1231 + PyMuPDF Page docs] |
| **JBIG2 / JPX / CCITT-encoded images** | pdfplumber's `stream_obj.get_data()` returns the raw filtered bytes — Pillow then can't open them (PIL doesn't read JBIG2 or JPX without optional plugins) → silent `try/except continue` at multimodal_service.py:163. | PyMuPDF's `doc.extract_image(xref)` decodes via MuPDF's filter chain and returns a sensible image format (e.g., JBIG2 → PNG conversion). |
| **Images masked / clipped by paths** | pdfplumber sees the raw image and lists it once; if the same xref is referenced multiple times with different clips, pdfplumber lists it once. | PyMuPDF's `get_images(full=True)` returns one entry per reference, including the parent xobject. |

The thesis PDF, as a Word export, almost certainly wraps each pasted picture in a Form XObject (Word's exporter does this when it needs to apply scaling / rotation / wrap-around). That's why **pdfplumber reports 2 but the original DOCX has many more pictures** — pdfplumber sees only the top-level wrapper if anything at all; the actual image is inside the Form XObject. def _supplementary_pdf_images_via_pymupdf(raw: bytes, mime: str) -> list[dict]:
```python
    """Single supplementary PyMuPDF pass via existing AGPL-fenced subprocess.

    Returns the same dict shape as extract_pdf_images. Used as union source
    when the primary extractor reports suspiciously few images.
    """
    from app.services.extractors.pymupdf import _run_pymupdf_subprocess  # noqa: PLC0415
    try:
        ed = _run_pymupdf_subprocess(raw, mime)
        return [
            {
                "page": im.page,
                "image_index": im.image_index,
                "b64_png": im.b64_png,
                "width": im.width,
                "height": im.height,
            }
            for im in (ed.images or [])
        ]
    except Exception as exc:
        log.warning("Supplementary PyMuPDF image pass failed: %s", exc)

def _dedup_by_content_hash(image_dicts: list[dict]) -> list[dict]:
    """Drop duplicate images by sha256 of the b64-decoded bytes.

    Docling layout-detection + PyMuPDF xref-walking can surface the same
    physical image twice (once per detection method). Hashing the decoded
    PNG bytes (after PIL.convert('RGB') normalization) gives a stable key.
    """
    import hashlib  # noqa: PLC0415
    seen: set[str] = set()
    out: list[dict] = []
    for d in image_dicts:
        try:
            h = hashlib.sha256(d["b64_png"].encode("ascii")).hexdigest()
        except Exception:
            h = str(id(d))
        if h in seen:
            continue
        seen.add(h)
        out.append(d)
    return out
```

**When to run Layer B (heuristic):** `len(extracted_doc.images) < expected_floor`, where `expected_floor` is a low constant like 3 — chosen because most academic PDFs >2MB have more than 3 figures, so detecting "fewer than 3" is a strong signal that the primary extractor missed something. Operator-tunable via env var (e.g., `MULTIMODAL_PDF_SUPPLEMENTARY_THRESHOLD=3`).

## Detection Ceiling — Tables

### Why the PDF/DOCX table-count mismatch (4 vs 39) is real and almost certainly closable

The DOCX has 39 tables. Those tables are explicit `<w:tbl>` XML elements — every DOCX-aware library reads them correctly. python-docx returns 39 (matches). [VERIFIED: trivial — `<w:tbl>` is the canonical DOCX table element; both python-docx and Docling's MsWordDocumentBackend iterate it.]

The PDF — same content — reports 4 tables. Two contributing factors:

1. **pdfplumber's `extract_tables` is ruling-line-based.** It joins detected horizontal+vertical lines into grid cells. Word-exported PDFs typically render table borders as 0.5pt single-line bottom borders or no borders at all. Without rulings, pdfplumber finds 0 tables on those pages. [CITED: pdfplumber README + [Mark Kramer's 2025 PDF table extraction comparison](https://medium.com/@kramermark/i-tested-12-best-in-class-pdf-table-extraction-tools-and-the-results-were-appalling-f8a9991d972e)]

2. **Docling's TableFormer (`do_table_structure=True`) is a layout-aware ML model.** It detects table regions visually (via RT-DETR) and predicts the cell grid via TableFormer. Per the [2025 benchmark](https://procycons.com/en/blogs/pdf-data-extraction-benchmark/), Docling+TableFormer hit 97.9% accuracy on complex tables where ruling-line approaches were near 0%. **Our code already enables this** at `docling.py:80-83`.

### Why the "4 PDF tables" number persists despite Docling being primary

This is the smoking gun for Plan 04: pdfplumber's pass at `multimodal_service.py:88-125` runs *unconditionally*, irrespective of what Docling produced. So when Docling foreground extract reports `table_count=1` (Phase 071.1 SUMMARY), the `document_tables` row count is 4 because **pdfplumber's separate detection pass at storage time put them there**. The 4 is pdfplumber's number, not Docling's. [VERIFIED — exactly the carry-forward #2 hypothesis.]

After Plan 04 lands (reading `extracted_doc.tables` first, falling back to pdfplumber only when empty), the expectation flips: the PDF table count will jump from the persisted-4 (pdfplumber's incorrect borderless-PDF guess) to Docling's TableFormer count, which on a 39-table thesis should be in the high-20s to low-40s range. [ASSUMED — confirm via probe in Part E.]

### Recommended minimal upgrade for PDF table detection

**No new code needed beyond Plan 04.** The required upgrade is already wired:

1. `do_table_structure=True` is already set (default, not disabled).
2. TableFormer mode is `ACCURATE` by default ([Docling advanced options](https://docling-project.github.io/docling/usage/advanced_options/) — confirmed by direct read of `docling/datamodel/pipeline_options.py` in the venv).
3. `extracted_doc.tables` is already populated by `_to_table_data` at `docling.py:99-123`.

The single thing missing is Plan 04: making `extract_and_store_tables` read `extracted_doc.tables` instead of running its own pdfplumber pass. Once that's done, PDF table count is bounded by what TableFormer detects — which the [benchmark data](https://procycons.com/en/blogs/pdf-data-extraction-benchmark/) suggests should be close to ground truth on a well-structured thesis PDF.

**Optional supplementary: Camelot or Tabula.** Both are ruling-line / template-based. For a thesis PDF without ruling lines, both will fail in the same way pdfplumber does. **Not worth adding.** Docling TableFormer is the right tool for this class of PDF; pdfplumber stays as the fallback for documents Docling fails on entirely (PARTIAL_SUCCESS or import error).

## Community Precedent

Concrete issues and threads where the community already solved (or documented) these problems:

### DOCX images (anchor + VML coverage)

- **[python-docx#747](https://github.com/python-openxml/python-docx/issues/747)** — Maintainer explicitly states python-docx only supports inline shapes; floating shapes (`<wp:anchor>`) require XML walking. Open since 2019; no resolution from upstream library — community resolves via lxml + XPath.
- **[python-docx#159](https://github.com/python-openxml/python-docx/issues/159)** — Feature request for floating image support; same resolution as #747.
- **[Unstructured-IO/unstructured#1615](https://github.com/Unstructured-IO/unstructured/issues/1615)** — Unstructured's solution: `PicturePartitioner` protocol — they walk paragraph XML with XPath to find `<wp:inline>` AND descend into `<w:drawing>` for both inline and anchor. Confirmed source pattern at [`unstructured/partition/docx.py`](https://github.com/Unstructured-IO/unstructured/blob/main/unstructured/partition/docx.py).
- **[docling/discussions/269](https://github.com/docling-project/docling/discussions/269)** — Docling DOCX backend explicitly supports `a:blip` and `v:imagedata` XPath; this is the canonical pattern we're porting.
- **[Office Open XML — Floating object spec](http://officeopenxml.com/drwPicFloating.php)** — Authoritative documentation that `<wp:anchor>` is the floating-object container; required reading to confirm the XPath descent path.

### PDF images (Form XObject + inline image scope)

- **[PyMuPDF#2140](https://github.com/pymupdf/PyMuPDF/discussions/2140)** — Maintainer Jorj X. McKie: `get_images(full=True)` descends into Form XObject children; pdfplumber doesn't.
- **[PyMuPDF#2759](https://github.com/pymupdf/PyMuPDF/discussions/2759)** — "Can't get full images list" — resolution: use `full=True` always for thoroughness.
- **[PyMuPDF#1231](https://github.com/pymupdf/PyMuPDF/discussions/1231)** — Inline image extraction (BI/ID/EI) via `page.get_text("dict")` — confirms pdfplumber doesn't handle this category at all.
- **[pdfplumber discussion #677](https://github.com/jsvine/pdfplumber/discussions/677)** — Maintainer note that Form XObject is "an endless rabbit hole" through pdfminer.six; pdfplumber doesn't fully resolve nested cases.
- **[py-pdf/pypdf#3107](https://github.com/py-pdf/pypdf/issues/3107)** — Inline image EI-sequence handling bug; symptomatic of how fragile non-PyMuPDF libraries are on inline images.

### PDF tables (borderless / model-based)

- **[Procycons 2025 PDF Data Extraction Benchmark](https://procycons.com/en/blogs/pdf-data-extraction-benchmark/)** — Numerical comparison: Docling 97.9% complex-table accuracy; ruling-line tools (pdfplumber, Camelot, Tabula) materially lower.
- **[Mark Kramer "12 best-in-class table extraction tools"](https://medium.com/@kramermark/i-tested-12-best-in-class-pdf-table-extraction-tools-and-the-results-were-appalling-f8a9991d972e)** — Independent confirmation: ruling-line tools fail catastrophically on borderless tables; ML-based tools (TableFormer family) succeed.
- **[docling/issues/2081](https://github.com/docling-project/docling/issues/2081)** — Reported TableFormer accuracy issues on specific table types; relevant for setting expectations (97.9% is the high end, not universal).
- **[Docling Advanced Options](https://docling-project.github.io/docling/usage/advanced_options/)** — Confirms `do_cell_matching=True` + `mode=TableFormerMode.ACCURATE` is the recommended config; our default already matches.

### Page-render / OCR alternative path (deferred — Phase 072)
