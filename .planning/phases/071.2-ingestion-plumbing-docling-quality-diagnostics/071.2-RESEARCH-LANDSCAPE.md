## 2. North-Star Framing — What "RAG accuracy" demands from extraction

**RAG accuracy is not "tables found." It is:**

> *"A user question about content in this document retrieves a chunk that contains that content, with enough context preserved that the LLM gives a grounded answer."*

That decomposes into five extraction-side criteria:

1. **Recall of visible content** — is every paragraph, table cell, figure caption, and equation present *somewhere* in the output bytes?
2. **Structural fidelity** — does the chunker's separator priority (in our case `\n## ` / `\n### ` / `\n\n` / `\n`) line up with semantic boundaries in the output, so chunks split where ideas split?
3. **Figure-caption proximity** — is the text "Figure 4.2: workflow diagram" emitted *adjacent* in the byte stream to figure 4.2's description/page, so a query for "workflow diagram" lands in a chunk that also references the figure?
4. **Table-cell coherence** — are table cells emitted as coherent units (markdown rows, HTML `<tr>`, or JSON arrays) that survive embedding and let a query for one cell value retrieve the whole row?
5. **Reading order** — for multi-column, sidebar, or footnote-heavy pages, does the byte order match what a human reads top-to-bottom?

**Failure mode the user observed on the thesis:** the chunker received Docling's `export_to_text()` (which strips markdown headings), so criterion #2 collapsed: the priority separators `\n## ` and `\n### ` never matched, the chunker fell through to `\n\n` then `\n` then character-level recursion, and the chunk count cratered from ~400 to 19. The content didn't disappear; the *boundaries* did.

**This north-star is what § 6 and § 9 score every candidate tool against.** Recall counts alone are a misleading proxy.

## 5. Detection Ceiling — Per Format

### 5a. DOCX images — what's missed by `python-docx.inline_shapes` (A1, A2)

`multimodal_service.extract_docx_images` at `multimodal_service.py:175-207` iterates **only** `doc.inline_shapes`. Per python-docx maintainer in [GitHub issue #747](https://github.com/python-openxml/python-docx/issues/747) + [#159](https://github.com/python-openxml/python-docx/issues/159), `inline_shapes` is **the `<wp:inline>` collection ONLY**. Picture types this misses:

| Picture type | OOXML element | Where it appears in real docs | Frequency on the thesis (predicted) |
|---|---|---|---|
| **Floating-anchor pictures** | `<wp:anchor>` inside `<w:drawing>` (DrawingML floating) | **Default for Ctrl+V from another Word doc, from PowerPoint, or from a browser** | DOMINANT — user reports "pasted in" pictures, which Word defaults to anchored |
| **Legacy VML pictures** | `<v:imagedata>` (Word 2003-era + Visio paste) | Older corporate templates | Low for thesis; high for legal/finance docs |
| **Header/footer pictures** | `<wp:inline>` / `<wp:anchor>` inside `word/header*.xml` / `word/footer*.xml` | Logos, watermarks | Possible (1-2 on thesis) |
| **Text-box pictures** | Picture inside `<w:txbxContent>` | Modern Word templates | Possible |
| **SDT / content-control pictures** | Picture wrapped in `<w:sdt>` | Forms / structured docs | Rare in academic |
| **Shape-fill pictures** | `<a:blipFill>` inside `<wps:wsp>` (Office 2010+ shape) | Decorative shapes | Rare |

**Canonical fix algorithm** — **already implemented by Docling at `venv/Lib/site-packages/docling/backend/msword_backend.py:78-83`**:

```python
# Source: docling/backend/msword_backend.py:78-83 [VERIFIED via direct source read]
self.blip_xpath_expr = etree.XPath(".//a:blip", namespaces=_BLIP_NAMESPACES)
self.vml_imagedata_xpath_expr = etree.XPath(".//v:imagedata", namespaces=_BLIP_NAMESPACES)
```

`a:blip` descends into BOTH `<wp:inline>` AND `<wp:anchor>` (both contain `<a:graphic>/<a:graphicData>/<pic:pic>/<pic:blipFill>/<a:blip>` per the [OOXML DrawingML spec](http://officeopenxml.com/drwPicFloating.php)). `v:imagedata` covers legacy VML. Docling iterates the body, headers, and footers — covering all 4 of the top picture-type categories above. Independently, [Unstructured-IO #1615](https://github.com/Unstructured-IO/unstructured/issues/1615) solver converged on the same XPath pattern. **Three independent solvers converge → consensus, not speculation.**

[VERIFIED: direct source read of installed `docling==2.93.0` MsWordDocumentBackend.]

### 5b. PDF embedded-image misses (A1, A3)

`multimodal_service.extract_pdf_images` at `multimodal_service.py:132-172` iterates **only** `pdfplumber.page.images`. Per pdfplumber 0.11.9 source + [PyMuPDF maintainer in #2140](https://github.com/pymupdf/PyMuPDF/discussions/2140), `Page.images` surfaces **only top-level XObject images on the page's resource dictionary**. Misses:

| Image type | Why pdfplumber misses | How PyMuPDF `get_images(full=True)` catches it |
|---|---|---|
| **Form XObject children** (DOMINANT miss on Word-exported PDFs) | pdfminer.six only scans page-level XObject dict | `full=True` walks Form XObject children — see [PyMuPDF #2759](https://github.com/pymupdf/PyMuPDF/discussions/2759) |
| **Inline images** (BI/ID/EI content-stream operators) | Live in `/Contents` stream as operators, not resource dict | `page.get_text("dict")` + `get_image_info()` — see [PyMuPDF #1231](https://github.com/pymupdf/PyMuPDF/discussions/1231) |
| **JBIG2 / JPX / CCITT-encoded images** | `stream_obj.get_data()` returns raw filtered bytes; PIL can't open without optional plugins → silent `try/except continue` at `multimodal_service.py:163` | `doc.extract_image(xref)` decodes via MuPDF's filter chain → PNG-convertible |
| **Page-rendered figures** (vector-only or clipped-mask images) | Not in object tree at all — must rasterize the page | Page rendering via `page.get_pixmap(clip=bbox)` |

**What Docling brings to the PDF picture problem:** `generate_picture_images=True` + the layout model detects pictures **visually** on the rendered page — this catches vector-only figures and Form-XObject-wrapped images that PyMuPDF's object-tree walk also misses. Combined source-of-truth approach: layout-detected pictures from Docling + Form-XObject + inline images from PyMuPDF, deduped by content hash. The current code uses neither path correctly.

[VERIFIED: `pymupdf_isolated.py:84-103` already iterates `get_images(full=True)` + `extract_image(xref)` — but only runs when `EXTRACTOR_PRIMARY=pymupdf` or `/reextract engine=pymupdf`. In the default `legacy` (or pre-revert `docling`) path this code never contributes images.]

### 5c. PDF tables vs DOCX tables — the 4-vs-39 structural reality (A4)

The user's thesis: DOCX has **39 tables** (every DOCX library finds them: `<w:tbl>` is an explicit OOXML element). The PDF — **same content** — reports 4 tables.

**Why this asymmetry is structural, not a bug:**

When Word exports DOCX → PDF (Word "Save As PDF" or LibreOffice), table cells render as **text-positioned strings + path objects for borders** — there is no `Table` object in the PDF tree. The PDF reader must visually re-detect the table from line+text positioning. This is a categorically harder problem than reading `<w:tbl>` XML.

| Tool | Approach to PDF tables | Result on borderless tables |
|------|-----------------------|------------------------------|
| **pdfplumber** | Ruling-line-based: detect horizontal+vertical lines, join into grid | **0 tables** on borderless pages |
| **Camelot / Tabula** | Same ruling-line approach (lattice) + stream-mode column inference | Slightly better than pdfplumber on stream-mode, still poor on borderless |
| **PyMuPDF `page.find_tables()`** | Hybrid line + column detection | Better than pdfplumber for stream-mode, but still misses borderless |
| **Docling TableFormer** | Layout-model detection (RT-DETR) + ML cell-grid prediction (TableFormer) | [97.9% complex-table accuracy](https://procycons.com/en/blogs/pdf-data-extraction-benchmark/) on the Procycons 2025 benchmark |
| **MinerU 2.5** | DocLayout-YOLO + dedicated table-recognition model | OmniDocBench v1.5 score 86.2 (pipeline backend); higher with VLM backend |
| **Marker** | Surya layout + Tatr-like table model (Surya tables) | [Strong on complex tables](https://github.com/datalab-to/marker), `--use_llm` flag boosts hard cases |

**Current state on the thesis:** `pdf_extraction_runs.table_count = 1` for Docling foreground extract (Docling's actual TableFormer output), but `document_tables` has **4 rows** because `extract_and_store_tables` runs a **separate pdfplumber pass** at storage time. The 4 is pdfplumber's number (3 of which are likely 1×1 noise per SEED-006 §Diagnostic-Findings); Docling's TableFormer found 1 in foreground mode. [VERIFIED: 071.1-CARRY-FORWARDS §2 + SEED-006 retest table.]

**The expected number after Plan 04 wires `extracted_doc.tables`:** Docling's TableFormer on a 39-table thesis should land **somewhere in the 20s to high-30s range** if TableFormer's complex-table benchmark accuracy holds. Even if it underperforms (e.g., 15-20), that's a 4× to 9× improvement over today's 4. [ASSUMED — probe-falsifiable; see §8.]

**Three knobs worth experimenting with in Plan 05 (low cost, possibly meaningful):**

1. **`do_formula_enrichment=True`** — the thesis is academic; equations live in PDF as positioned glyphs that Docling's formula model can reconstruct as LaTeX. Cost: an additional model load (~few hundred MB). [CITED: Docling pipeline_options docstring + the `CodeFormulaV2` repo reference.]
2. **`generate_table_images=True`** — for each detected table, Docling renders an image. Useful as a vision-LLM fallback when the cell-grid extraction is sparse (Phase 072 fits this naturally). Cost: more memory + b64 bytes.
3. **`force_backend_text=True`** — bypass the layout model for text and use the PDF's embedded text layer directly. On text-layer thesis PDFs this could be both faster AND more recall-correct (avoids layout model false negatives on text regions). Worth probing.

### 5e. The "both wrong" structural reality (A6)

## 10. Architectural Options

Four options, each fully scoped with downstream cross-phase impact. **Option A is the recommendation.**

### Option A — Stay Docling-primary + ship the three earlier surgical fixes + ship Plan 05 (DOCX XPath walk + PDF supplementary PyMuPDF) + optional Docling pipeline knob experiments

**Description.** Keep Docling as the registered primary engine. Ship the three plumbing/quality fixes already scoped in `071.2-RESEARCH.md` (Plans 01, 03, 04) PLUS a new Plan 05 that ports Docling's own `MsWordDocumentBackend` XPath algorithm into `multimodal_service.extract_docx_images` (catching `<wp:anchor>` floating-anchor pictures) AND adds a supplementary PyMuPDF-via-existing-subprocess pass for PDF images when Docling's `.images` count is suspiciously low. Optionally enable `do_formula_enrichment=True` and `generate_table_images=True` Docling knobs as a small experiment.

**Pros (3):**
1. **Zero new dependencies.** No license risk, no pin churn, no subprocess fence to design — everything reuses already-shipped infrastructure (Docling singleton, PyMuPDF subprocess, `ExtractedDocument` dataclass).
2. **Surgical and verifiable.** Each fix is ≤80 LOC, each has a probe-confirmable hypothesis, each plan ships green-or-revert. If Plan 03 doesn't recover chunk count, ship-stops there.
3. **Strongest cross-phase fit.** Phase 072's multimodal lift slots in cleanly on top (multimodal helpers now consume `extracted_doc.tables/.images` instead of running their own pdfplumber pass — the storage layer becomes engine-agnostic, which is what SEED-006 has been asking for since 2026-05-02).

**Cons (3):**
1. **Doesn't address Docling's 125s extract latency.** A 4 MB PDF still takes ~2 minutes. Under `--workers 2` (Phase 079) this is one of 200 ANYIO threads, but it's still a slow user experience. Mitigation: instant-201 + BackgroundTask refactor (Plan 01) means the user doesn't wait.
2. **Doesn't close the equation-rendering gap on academic PDFs.** Math equations stay as positioned glyphs unless `do_formula_enrichment=True` is enabled (which adds another model bundle).
3. **Leaves Marker / MinerU / pymupdf4llm as future SEED candidates** — if Plan 04 numbers underperform the predictions in §8, we have to circle back to a library swap anyway.

**LOC budget:** ~150 LOC implementation + ~80 LOC tests (DOCX XPath walk + PyMuPDF supplementary + tests for both) — fits the existing Plan 05 budget in `071.2-RESEARCH-COMPLETENESS.md`. Plans 01/03/04 stay as already scoped.

**Downstream cross-phase effect:**
- **Phase 072** narrows considerably: Plan 05 here delivers the `wp:anchor` floating-shape walk that 072's RAG-MM-LIFT-02 was going to do. 072 then focuses on the `_MAX_VISION_CALLS` 20→100 lift + the b64-cap lift + the empty-description-row persistence — exactly what SEED-006 named. See §11 for the precise rescope recommendation.
- **Phase 076** unaffected: Docling's chunk score distribution gets calibrated against confidence thresholds; the calibration still happens, just now against a chunker that produces ~400 chunks instead of 19 on the thesis (more rows = better-conditioned histogram).
- **Phase 077** unaffected: process model is unchanged (single Docling singleton per worker; pickleable subprocess for PyMuPDF). Multi-worker just adds per-worker singletons — already handled by D-071-06's double-checked lock.
- **v2.6 PRD Docling-first thesis: REINFORCED.** The PRD said "Docling-first because better extraction quality." The data so far is "Docling produced the same numbers because its output was discarded." Plan 04 fixes the discard. The PRD's thesis is intact; the evidence just requires the wiring to land first.
- **v3.0+ Skill Studio (D-PRD-09): no impact.** Skills don't touch ingestion path.

### Option B — Option A + add `MarkerExtractor` (GPL-fenced) to the dispatcher as opt-in

**Description.** Everything in Option A, plus: add `backend/extractors/marker_isolated.py` (GPL fence — `import marker` lives there only) + `backend/app/services/extractors/marker.py` (parent wrapper invoking subprocess child) + register `engine == "marker"` in `get_extractor`. Marker becomes available via `/reextract engine=marker` only — never the env-default primary.

**Pros (3):**
1. Gives the user a quality-leader fallback for documents Docling underperforms on (e.g., heavy math, complex multi-column layouts, scanned PDFs).
2. Reuses the proven AGPL-fence pattern from PyMuPDF Plan 03 (commit `8ae4fa3`).
3. Validates the dispatcher seam against a third engine class — proves the abstraction works.

**Cons (3):**
1. **GPU strongly recommended.** Marker on CPU is 4× slower than Docling per [Jimmy Song's 2026 review](https://jimmysong.io/blog/pdf-to-markdown-open-source-deep-dive/). Worth shipping only if the user has GPU access (production deployment may not).

3. **GPL-3 fence rigor.** Subprocess separation is sufficient for AGPL (no linkage); GPL-3 also requires no linkage of object code. Subprocess clears this, but the legal review (D-PRD-07 Appendix style) needs to be updated. Add ~1 day of legal due diligence.

**LOC budget:** Option A budget + ~350 LOC for the Marker fence + ~100 LOC of tests + 1 day legal review.

**Downstream cross-phase effect:**
- **Phase 072** same as Option A.
- **Phase 076** same as Option A.
- **Phase 077** unchanged.
- **v2.6 PRD** reinforced — adds a quality-leader option without changing the default.
- **v3.0+ Skill Studio** Marker becomes available for "pre-process this knowledge base with the best-quality engine before ingestion" workflows (D-PRD-09 fits this).
- **SEED-006** further closed — Marker on the few docs where Docling underperforms.

- Compare Marker's stored counts to Docling's predicted post-Plan-04 numbers. **Only ship Option B if Marker shows a ≥30% improvement on tables AND figures.**

### Option C — Replace Docling primary with another engine

**Description.** Demote Docling to opt-in. Pick a new primary engine: pymupdf4llm (PyMuPDF-stack, AGPL-fenced, no models) OR Marker (GPL-fenced, GPU-required) OR MinerU (Apache-based, GPU-required).

**Pros (3):**
1. May land higher quality faster than fixing Docling's wiring.
2. Forces the abstraction layer to prove itself against engine-swap stress.

### Option D — Hybrid mode: run two extractors per document, content-hash-dedup merge

**Description.** Add a `EXTRACTOR_HYBRID=docling+pymupdf` env mode. For each PDF, run Docling AND PyMuPDF in parallel (PyMuPDF in subprocess, Docling in main thread); union the resulting tables/images by content hash (sha256 of normalized PNG bytes for images; canonical-form hash for tables). Per-document opt-in via `/reextract engine=hybrid`.

**Pros (3):**
1. Maximum recall — each engine's strengths cover the other's blind spots (Docling layout-visual + PyMuPDF Form-XObject = best PDF image coverage).
2. Validates the dedup primitive that Phase 072 / SEED-006 needs anyway.
3. Acts as a built-in cross-check ("if these two engines disagree by >20%, flag for human review").

**Cons (3):**
1. **2× extraction time per call** (125s + 10s subprocess = 135s on thesis — only marginally worse than Docling alone). Under multi-worker (079) this is fine; under single-worker it's a UX hit.
2. **2× memory at peak** during the parallel phase.
3. **Dedup primitive is non-trivial.** Image dedup by content hash works; table dedup is harder (Docling's grid vs PyMuPDF's row/col layout may not normalize cleanly).

**LOC budget:** ~250 LOC + ~120 LOC tests (hybrid orchestrator + dedup helper + per-format precedence rule + new env mode + telemetry shape `engine='hybrid:docling+pymupdf'`).

**Downstream cross-phase effect:**
- Phase 072 — slightly simplified (hybrid mode already produces unified `extracted_doc.images` so the storage layer doesn't need to know about supplementary passes).
- Phase 076, 077 — unchanged.
- v2.6 PRD — additive (not reversed).
- v3.0+ — Skill Studio could expose "thorough mode" as a per-skill option.

**Probe-harness verification:** Run the hybrid mode on the thesis and confirm the deduplicated union count exceeds either engine alone by a meaningful margin.

**Recommendation:** **Defer to a future polish phase** (v2.7 or post-072). The hybrid pattern is useful but premature — first prove Docling-after-Plan-04 numbers, then decide if hybrid adds enough value to justify the dedup-primitive work.
