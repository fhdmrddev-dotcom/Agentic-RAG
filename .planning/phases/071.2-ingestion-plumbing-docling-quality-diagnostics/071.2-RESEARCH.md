# Phase 071.2: Ingestion Plumbing + Docling Quality Diagnostics — Research

**Researched:** 2026-05-15
**Domain:** RAG ingestion pipeline (FastAPI async handlers + BackgroundTask + Supabase Realtime + Docling/pdfplumber extraction wiring)
**Confidence:** HIGH (all critical claims verified by direct read of current source — exact file paths, function names, line numbers below)

## Summary

Phase 071.2 closes three operational ingestion defects that surfaced during Phase 072 discuss-phase setup, BEFORE the multimodal lift in Phase 072 lands on top of them:

1. **Sync `extractor.extract()` inside async handlers (`/upload` + `/reingest`)** — same D-v2.5-01 bug class that Phase 071.1 closed for `/reextract`, but on two more routes. The fix pattern is already proven in the codebase (`await run_in_threadpool(extractor.extract, raw, mime_type)` plus `asyncio.wait_for` Layer 2 wall-clock on Docling); 071.2 is a mechanical port of the 071.1 work to `/upload` and `/reingest`.
2. **`/upload` blocks 1–120s on foreground extract before returning 201** — `documents` row is INSERTed AFTER extraction completes. Fix is structural: extract is moved INTO the BackgroundTask along with the storage upload and ingestion pipeline; the route INSERTs the doc row with `status='pending'` first, then returns 201 within ~1s.
3. **Two Docling-quality regressions are wiring bugs in `multimodal_service` and `extractors/docling.py`** — `extract_and_store_tables`/`extract_and_store_images` **never** read `extracted_doc.tables` / `.images`; they run their own pdfplumber/python-docx passes on `raw` bytes (confirming the carry-forward Hypothesis A on item #2). The 95%-chunks-drop is almost certainly that `DoclingExtractor.extract` returns `text=doc.export_to_text()` (Docling 2.93's plain-text output strips markdown structure) — the chunker's hierarchical separators `\n## ` / `\n### ` never match, so big sections fall through to character-level recursion and merge into oversize chunks. `full_markdown` is captured on `ExtractedDocument` but never used downstream.

**Primary recommendation:** Plan 01 ports the 071.1 threadpool sweep mechanically to `/upload` and `/reingest`, plus restructures `/upload` to instant-201 + BackgroundTask (extraction moves into the task). Plan 03 changes one line in `docling.py:198` (`text = doc.export_to_text()` → `text = full_markdown or doc.export_to_text()`) — likely closes the 95% chunk-drop in <10 LOC. Plan 04 changes 2 call sites in `documents.py:1022/1032` plus the two functions in `multimodal_service.py:88-125` and `:252-...` to accept `extracted_doc` and use its tables/images when present (falling back to the existing pdfplumber/python-docx pass when None). All three are surgical; no schema changes; no migration.

### Pattern 1: Async handler + threadpool-wrapped sync I/O (D-v2.5-01)

**What:** Every sync supabase-py + storage call in an async handler MUST be wrapped with `await run_in_threadpool(...)`.

**When to use:** Every `async def` route handler in `backend/app/api/*.py` that touches the database or storage.

**Example (proven in 071.1 — `/reextract` post-fix):**
```python
# Source: backend/app/api/documents.py:618-625
doc = await run_in_threadpool(
    lambda: supabase.table("documents")
    .select("*")
    .eq("id", document_id)
    .eq("user_id", current_user["id"])
    .eq("is_latest", True)
    .maybe_single()
    .execute()
)
```

For storage:
```python
# Source: backend/app/api/documents.py:633-636
raw = await run_in_threadpool(
    supabase.storage.from_("documents").download, target["file_path"]
)
```

For extraction (Layer 2 wall-clock for Docling):
```python
# Source: backend/app/api/documents.py:695-698
extracted_doc = await asyncio.wait_for(
    run_in_threadpool(extractor.extract, raw, mime_type),
    timeout=wall_clock_s,
)
```

### Pattern 2: BackgroundTasks for fire-and-forget post-response work

**What:** Heavy or long-running work scheduled via `background_tasks.add_task(callable, *args)` runs AFTER the response is sent. Already proven in 3 spots in this file (`documents.py:333-345` upload audit, `:553-565` reingest, `:769-781` reextract).

**When to use:** Anywhere the user shouldn't wait synchronously for work to complete (storage upload, extraction, chunking, embedding, vision API calls). Required when the work blocks for >1s.

**Example signature already in use:**
```python
# Source: backend/app/api/documents.py:333-345
background_tasks.add_task(
    ingest_document,
    document_id,
    text,
    current_user["id"],
    supabase,
    raw,
    mime_type,
    file.filename,
    None,            # engine_override
    extracted_doc,
    extract_duration_ms,
)
```

**Cautionary note:** `background_tasks.add_task(callable, ...)` accepts both `async def` and `def`. `ingest_document` is `def` (sync) — runs in a thread automatically. After Plan 01, it stays `def`.

### Pattern 3: Supabase Realtime channel + INSERT/UPDATE/DELETE handler (D-v2.5-03)

**What:** Frontend subscribes to `postgres_changes` on `documents` table; receives INSERT/UPDATE/DELETE events; reconciles via fetch on (re)connect.

**When to use:** Already used for `useDocuments`. No change needed — once Plan 01 INSERTs the row BEFORE extract, Realtime will broadcast the INSERT immediately and the badge will transition `pending → processing → completed`.

**Example (existing — unchanged):**
```typescript

const channel = supabase
  .channel("documents-changes")
  .on("postgres_changes", { event: "*", schema: "public", table: "documents" }, (payload) => {
    if (payload.eventType === "UPDATE") { /* setDocuments(prev => prev.map(...)) */ }
    else if (payload.eventType === "INSERT") { /* setDocuments(prev => [newDoc, ...prev]) */ }
    else if (payload.eventType === "DELETE") { /* setDocuments(prev => prev.filter(...)) */ }
```

The optimistic add at `useDocuments.ts:81-86` already handles "Realtime INSERT may race with the upload response" — `setDocuments((prev) => { if (prev.some((d) => d.id === doc.id)) return prev; return [doc, ...prev] })`.

### Anti-Patterns to Avoid

- **Running `extractor.extract()` directly in an async handler.** This is the bug class Phase 071.1 fixed for `/reextract` and Phase 071.2 fixes for `/upload` + `/reingest`. The legacy LegacyExtractor (pypdf + pdfplumber) blocks for ~1–5s on PDFs; Docling blocks for 25–125s+ on real academic PDFs. Without `run_in_threadpool`, this freezes the single uvicorn worker (D-v2.5-02).
- **Re-extracting tables/images from raw bytes when the primary extractor already produced them.** Current `extract_and_store_tables` (multimodal_service.py:88-125) runs pdfplumber on `raw` regardless of what Docling already produced. This silently discards Docling's table+image data AND populates `document_tables` with pdfplumber's potentially-different counts → the 4-vs-1 telemetry mismatch.
- **Chunking on `export_to_text()` when `export_to_markdown()` is available.** Docling 2.93's plain-text export drops markdown structure; the chunker's `\n## ` / `\n### ` priority separators are dead code on that input. Chunks fall through to `\n\n` then `\n` then character-level recursion → catastrophic chunk-count collapse on big PDFs.
- **Using `.maybe_single()` after `.eq("is_latest", True)` without empty-result handling.** Returns 500 on a doc with `is_latest=False` rather than a clean 404 (carry-forward item #3). Single-line fix.

## Common Pitfalls

### Pitfall 1: TestClient runs BackgroundTasks synchronously after response

**What goes wrong:** A test asserting "response returns within Xms" measures total response time WITH BackgroundTasks if using FastAPI's `TestClient` — but tests asserting `mock_ingest.called` after `client.post(...)` succeed because TestClient blocks the response until BackgroundTasks finish.

**Why it happens:** Starlette's `TestClient` is synchronous and intentionally executes BackgroundTasks before returning from `.post(...)` — this is documented behavior, useful for testability.

**How to avoid:** For the "instant 201 within ~1s" success criterion: measure with `curl` against a live uvicorn instance, NOT with `TestClient`. For "ingest_document was called" assertions: use TestClient as today (verified pattern in `TestReextractDocument.test_reextract_happy_path_returns_202` at `test_documents.py:411-463` — `mock_ingest.assert_called_once()` post-response).

**Warning signs:** A passing TestClient test that fails when run against a real uvicorn server with a real PDF.

### Pitfall 2: `extract_and_store_tables` / `extract_and_store_images` modules-level `from app.services.multimodal_service import (...)` import inside `ingest_document`

**What goes wrong:** Plan 04 needs to pass `extracted_doc` into both functions, but the import lives inside `ingest_document` (line 1010-1013) and not at module level. Patching this in tests has historically required `patch("app.api.documents.extract_and_store_tables")` patterns.

**Why it happens:** Original delayed-import pattern to avoid loading `multimodal_service` at startup. Plan 04 should preserve this pattern (don't lift to module-level import) — just update the call sites to pass the new kwarg.

**How to avoid:** When updating call sites at `documents.py:1022` and `:1032`, keep the lazy import; only change the keyword arguments. Functions in `multimodal_service.py:88-125` and `:252-...` gain optional kwargs with default `None`, preserving the legacy call shape so existing tests don't break.

### Pitfall 3: Docling's `result.document.export_to_markdown()` may return `None` or raise on partial-success documents

**What goes wrong:** Phase 071's docling.py already wraps `export_to_markdown()` in try/except (`docling.py:200-203`); if it fails, `full_markdown=None`. Plan 03's one-liner `text = full_markdown or doc.export_to_text()` correctly falls back to plain text on Docling's bad days.

**Why it happens:** Docling 2.93's `PARTIAL_SUCCESS` status (logged at `docling.py:189-194`) covers documents where timeout tripped at a batch boundary — the converter returns truncated output, and markdown export may misbehave.

**How to avoid:** Keep the `or doc.export_to_text()` fallback — both are already wrapped in try/except inside `DoclingExtractor.extract`. Plan 03 should also assert via probe_docling_timeout.py that `len(full_markdown) >= len(text)` is the normal case (validates the hypothesis before shipping the swap).

### Pitfall 4: `_PRIMARY_CACHED` module-level cache freezes `EXTRACTOR_PRIMARY` per uvicorn process

**What goes wrong:** `extraction_service._PRIMARY_CACHED` (line 212) reads `os.getenv("EXTRACTOR_PRIMARY")` ONCE at first call. Changing `backend/.env` requires uvicorn restart to take effect.

**Why it happens:** Intentional per `_read_primary` docstring — a process-lifetime cache.

**How to avoid:** When Plan 01 changes /upload + /reingest to BackgroundTask flow, this is unrelated (the cache still works). But when UAT-ing Plan 03's chunks-drop fix: must `uvicorn restart` after editing `.env` to flip `EXTRACTOR_PRIMARY` from `legacy` back to `docling`. Documented in `backend/README.md` per 071.1 Troubleshooting.

### Pitfall 5: `documents.is_latest=False` raises 500 on `/reextract`

**What goes wrong:** `documents.py:618-626` filters by `.eq("is_latest", True)` AND uses `.maybe_single()`. When no row matches (because is_latest was flipped False by a prior failed cascade), the supabase-py client raises and the handler returns 500, not 404.

**Why it happens:** `.maybe_single()` is defensive against multi-row results but doesn't gracefully handle "the filter eliminated everything". This is exactly what surfaced during the 071.1 thesis UAT pre-flight — the thesis PDF row had `is_latest=False` from Phase 071 Plan 04's failed reset cascade.

**How to avoid:** Plan 04 should include the single-line fix per carry-forward item #3. Either: (a) catch the exception and re-raise as `HTTPException(404, "Document not found")`, OR (b) pre-clear `is_latest=True` in the reset cascade at `documents.py:653-664`. Option (a) is safer (doesn't change side-effect semantics). Roughly:

```python
try:
    doc = await run_in_threadpool(lambda: supabase.table("documents").select("*")...maybe_single().execute())
except Exception as e:
    # Phase 071.2: is_latest=False from a prior failed cascade silently 500s.
    # Treat empty-result-from-supabase-py as 404.
    raise HTTPException(status_code=404, detail="Document not found") from e
```
