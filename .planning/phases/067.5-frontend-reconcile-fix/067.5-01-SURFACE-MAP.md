## Diagnostic priors before runtime repro

Looking at the live shapes:

- **Branch A (cascade abort) is the LEAST likely.** `loadAbortRef` and `subscriptionsRef` controllers are demonstrably separate. The only "abort cascade" path is the indirect early-return inside reconcile's for-loop, but that doesn't touch existing SSE consumers — it only skips placeholder insertion. Existing consumers keep writing to their bucket. So Row 11's "DB has the row but UI is empty" cannot be explained by Branch A alone.

- **Branch B (stale ref-mirror) is plausible.** The `messagesByThreadRef` useEffect at lines 410-412 is a passive `useEffect` (not `useLayoutEffect`), so it lands AFTER React commits paint. If reconcile fires synchronously after a `setMessagesForThread` call (e.g., `tool_end` or `done` SSE event arrives, then ChatArea's visibilitychange listener fires reconcile in the same tick), `messagesByThreadRef.current.get(threadId)` at line 977 may return the pre-commit snapshot — missing the just-written DB row. Then `existingByRunId` is undefined → `targetId = temp-${run_id}` → idempotent placeholder insert no-ops (because the placeholder for that runId still exists OR a DB row with the same runId exists at a different id). Net: no second bubble created, but the original temp placeholder may stay empty if MERGE kept it.

- **Branch C (loadMessages MERGE strands placeholder) is the LEADING candidate.** The third clause `|| subscriptionsRef.current.has(m.runId)` keeps the temp placeholder alive while the SSE consumer is still bound. In the Row 11 scenario:
  1. User submits prompt on Thread A. `subscriptionsRef.set(runA, ctrl)` at line 748.
  2. User switches to Thread B mid-stream. `streamingThreadIdRef` is unchanged (still A).
  3. SSE `done` event arrives for A while user views B. `onTerminal` callback (line 795 / line 1045) flips runStatus to "completed" + `subscriptionsRef.delete(runA)` at line 825 / line 1076.
  4. User switches back to Thread A. ChatArea fires `reconcile(threadA)` at lines 162-188.
  5. Reconcile's `Promise.all([getActiveRuns, loadMessages])` at line 951 — getActiveRuns returns `[]` (run completed), loadMessages fetches DB row.
  6. **Critical timing:** between steps 3 and 5, was the `subscriptionsRef.delete(runA)` already committed? If `done` event was processed correctly, YES. Then MERGE filter at line 649 sees `subscriptionsRef.current.has(runA) === false` AND `dbRunIds.has(runA) === true` → predicate false → placeholder dropped → DB row wins. UI renders content. ✓
  7. **Failure case:** if `done` event fires AFTER reconcile's Promise.all dispatches loadMessages but BEFORE getMessages's response arrives, the SSE consumer is STILL in subscriptionsRef when MERGE evaluates. So the placeholder is kept (third clause `||` is true). DB row is appended. **Two messages now exist for the same runId — the empty placeholder + the DB row.** React renders both. User sees an empty bubble *plus* the populated bubble.

  But Row 11 says the user sees an EMPTY thread, not two bubbles. So Branch C as-described doesn't fully explain Row 11 by itself.

- **Branch D (divergent surface) — possible if the bug is actually two events racing.**
  - Hypothesis D-1: getActiveRuns + loadMessages both succeed, but the for-loop in reconcile (line 958) sees `activeRuns = []` (run completed), so the placeholder-insert block (lines 984-1003) NEVER fires. If MERGE dropped the placeholder AND no SSE consumer is in subscriptionsRef AND DB row is in `data`, then the `data` should appear — render should be correct.
  - Hypothesis D-2: there's a window where DB persistence happens, `subscriptionsRef.delete` happens, but `loadMessages` was triggered EARLIER (before `done` fired) and its `data` reflects the moment BEFORE the assistant row was persisted. Then `dbRunIds.has(runA) === false`, MERGE keeps the empty placeholder, `data` doesn't include the row, and the user sees an empty placeholder until the next reconcile fires (which doesn't happen unless they tab away+back, OR they F5).

  D-2 is a STRONG candidate. The trigger: `done` SSE event fires → `onTerminal` flips runStatus → `subscriptionsRef.delete` runs. But the DB persistence happens BEFORE `done` is emitted (per backend threads.py: persist → done → stream_end). So if loadMessages was triggered DURING the streaming window — before `done` — its `data` reflects the latest persisted state at that moment, which may NOT include the assistant row yet.

  **Specifically: the reconcile chain at line 1108-1121 — `subscribeToRun(...).finally(() => { loadMessages(threadId).catch... })` — fires loadMessages AT terminal. This loadMessages should pick up the row because the backend persists BEFORE done. But what if the user switched threads BEFORE this terminal-time loadMessages completes? `activeThreadIdRef.current !== threadId` early-return at line 601 fires, the loadMessages discards its response, NO setMessagesForThread call lands.** Then the user switches back and ChatArea fires reconcile(threadA), which calls loadMessages(threadA) → fetches DB row → MERGE evaluates with `dbRunIds.has(runA) === true` (DB has it now) AND `subscriptionsRef.current.has(runA) === false` (consumer cleaned up at terminal) → predicate evaluates to `(!true || false)` = `false` → placeholder dropped → DB row wins. UI renders. ✓

  Unless... the placeholder in the bucket has a runId that matches, and the DB row has a different id. In which case MERGE drops the temp placeholder, returns `[...data, ...]`, the DB row appears, render works. ✓

  Hmm. So in this analytical pass, the only way the user sees an empty thread WITHOUT F5 is if `messagesByThread.get(threadA)` is set to an array that has the placeholder but NOT the DB row, OR if it's empty. Reconcile-on-switch-back triggers loadMessages which should overwrite the bucket. **Unless reconcileInFlightRef.current is true — then reconcile early-returns at line 945 and never fires loadMessages.** That gives a working hypothesis: a previous reconcile lock got stuck (`reconcileInFlightRef = true`) due to an unhandled rejection in the inner Promise.all not flowing through finally — but the `finally` at line 1129 unconditionally resets it, so this is unlikely too.

## Recommendation for runtime repro (Task 2)

Capture in this order at the moment the empty bubble is observed:
1. **`messagesByThread.get(threadA)` contents** via React DevTools — empty? placeholder-only? populated?
2. **`subscriptionsRef.current.has(runA)`** — true means SSE consumer still bound; false means terminated.
3. **`reconcileInFlightRef.current`** — true would explain why switch-back reconcile is no-oping.
4. **Network panel `/runs/{runA}/stream?since=N` connection state** — open / closed / pending.
5. **`/threads/{threadA}/messages` Network panel response** — does the GET return the assistant row with `runId === runA`?

Based on these readings:
- Empty bucket + reconcileInFlightRef true → Branch D-3: stuck reconcile lock.
- Empty bucket + reconcileInFlightRef false + DB has the row → Branch B (stale ref-mirror suppresses re-fetch path) or Branch D-2 (loadMessages early-returned during cross-thread navigation).
- Placeholder-only bucket + DB has the row + subscriptionsRef.current.has(runA) === true → Branch C as described.
- Placeholder-only bucket + DB has the row + subscriptionsRef.current.has(runA) === false → MERGE *should* drop the placeholder; if it doesn't, MERGE filter has a bug.
