## Tooling constraint observed in Attempt 1

Chrome DevTools MCP click+snapshot roundtrip is ~1-2s. `gpt-5.4-mini` streamed Thread A's full sourdough recipe (90+ markdown nodes, see snapshot uids 90_0–90_91) in ~10-15 seconds, including the post-stream suggestion pills. This means: by the time I clicked "New Chat" to spawn Thread B, Thread A had already terminated cleanly (consumer cleaned up via `onTerminal` at line 1076; subscriptionsRef.delete(runA) fired; runStatus flipped to "completed"). There was no concurrent-streaming window in which to execute the cross-thread mid-stream nav that triggers the Row 11 race.

The Row 11 race is timing-sensitive at sub-second granularity (the user's manual UAT clicks between threads at ~250-500ms human-rate, faster than MCP). Even with heavier prompts or slower providers (Anthropic claude-sonnet-4-6 ~30-90s on multi-step prompts), the MCP click+snapshot latency stack is too coarse to deterministically reproduce a 1-of-4-frequency timing race.

This is consistent with ROADMAP risk note 524: *"If Chrome MCP cannot reproduce on a single session, Plan 01 includes a pivot decision."*

## Branch decision (which fix surface)

Based on the SURFACE-MAP diagnostic priors:

- **Branch A — SSE consumer aborted by loadMessages cascade.** Eliminated structurally. `loadAbortRef` and `subscriptionsRef` controllers are SEPARATE Controller instances (line 594 vs 1021) — direct cascade impossible. Indirect cascade via reconcile's `activeThreadIdRef` early-return at line 963 only skips placeholder insertion; it does NOT abort existing SSE consumers. So Row 11's "DB has the row but UI is empty" cannot be explained by Branch A alone.

- **Branch B — Stale ref-mirror during reconcile-on-(re)visit window.** Plausible but not exclusive. The `messagesByThreadRef` useEffect at lines 410-412 is a passive `useEffect` (not `useLayoutEffect`), so it lands AFTER React commits paint. Reconcile's `messagesByThreadRef.current.get(threadId)` read at line 977 may return a pre-commit snapshot. Effect: `existingByRunId` is undefined → `targetId = temp-${run_id}` → idempotent placeholder insert no-ops if a placeholder for that runId already exists. The empty placeholder may stay if MERGE keeps it. But this alone doesn't explain why the DB row `data` from the parallel `loadMessages` call doesn't surface — UNLESS MERGE also strands the placeholder.

- **Branch C — loadMessages MERGE strands empty placeholder. ✅ LEADING CANDIDATE.** The third clause `|| subscriptionsRef.current.has(m.runId)` at line 649 is the strand source. In the Row 11 scenario:
  1. User submits prompt on Thread A. `subscriptionsRef.set(runA, ctrl)` at line 748.
  2. User switches to Thread B mid-stream. `streamingThreadIdRef` stays A.
  3. SSE `done` event arrives for A while user views B. `onTerminal` (sendMessage path at line 795) flips runStatus to "completed" + `subscriptionsRef.delete(runA)` at line 825.
  4. **Race window:** between step 3's `subscriptionsRef.delete` and the user's switch back to A, a reconcile fires (visibilitychange/focus/pageshow listener at ChatArea.tsx:162-188). Reconcile's `Promise.all([getActiveRuns, loadMessages])` at line 951 dispatches both fetches.
  5. `loadMessages(A)` resolves with `data` from Postgres including the populated assistant row (`runId === runA`).
  6. **Critical timing:** if `loadMessages` was DISPATCHED before step 3's delete completed (i.e., reconcile fired during the streaming window), then `subscriptionsRef.current.has(runA) === true` was captured by the closure when MERGE evaluated. Even though by the time MERGE runs the entry has been deleted, JavaScript is single-threaded — the read in the filter callback is fresh at evaluation time, so... actually the closure read is fresh. Let me re-examine.
  7. **Re-examination of Branch C:** `subscriptionsRef.current.has(m.runId)` is read AT FILTER EVALUATION TIME, not closure-captured. So if `onTerminal` already deleted the entry before MERGE runs, the predicate evaluates to `(!dbRunIds.has(runA) || subscriptionsRef.current.has(runA))` = `(!true || false)` = `false`. Placeholder dropped. DB row wins. ✓
  8. **Failure case for Branch C:** the predicate stranding only happens if BOTH `onTerminal` hasn't fired yet (consumer still bound) AND `data` already includes the row. That requires:
     - Backend persists the assistant row BEFORE emitting `done` (per CLAUDE.md: persist → done → stream_end).
     - Reconcile's `loadMessages` runs AFTER persist but BEFORE `done` propagates through the SSE consumer to fire `onTerminal`.
     - This window is brief but real. During it, MERGE keeps the empty placeholder AND appends the populated DB row. Result: TWO rows for the same runId in `messagesByThread.get(A)` — `[populated_DB_row, empty_temp_placeholder]`. React renders both keyed on `id` (DB row's UUID vs `temp-${runA}`). User sees a populated bubble PLUS an empty bubble.
     - But Row 11 says ONE empty thread — not "two bubbles". So Branch C as a sole explanation may be incomplete UNLESS the populated DB row is reconciled by `existingByRunId.id ?? targetId` collapsing onto the placeholder's id, in which case all SSE deltas route to the placeholder and the DB row's content is OVERWRITTEN/IGNORED.
     - Actually re-reading reconcile line 977-979: `const existingByRunId = threadMessages.find((m) => m.runId === run.run_id); const targetId = existingByRunId?.id ?? \`temp-${run.run_id}\``.   Re-reading the code carefully: when the user switches thread A → B mid-stream, ChatArea fires `loadMessages(B)` (because the thread-selection useEffect calls it on every thread switch). `loadMessages(B)` `await`s `getMessages(B)`. ## Selected branch: D (refined as D-2-EARLY-WINDOW)

## Rationale

Three sentences citing the disambiguating evidence:
1. Branches A and C as originally framed are structurally insufficient to explain Row 11's "DB has the row, UI is empty, F5 repairs" failure mode (A: cascade-abort impossible per separate Controllers; C: third-clause `||` only strands when consumer-still-bound AND DB-already-caught-up which is a brief window that doesn't match Row 11's "minutes of empty" duration).
2. Branch B (passive useEffect ref-mirror lag) is plausible but doesn't explain why subsequent SSE `delta`/`done` events from the still-live consumer don't repair the bucket — the events DO write to `messagesByThread` regardless of ref-mirror lag.
3. Branch D-2-EARLY-WINDOW (refined): `loadMessages` fires during the postMessage in-flight window when the assistant placeholder has no `runId` stamped yet; MERGE filter at line 644-649 drops it because `m.runId` is falsy; subsequent SSE callbacks targeting the dropped placeholder's `assistantId` no-op via map; bucket stays empty until F5 (mount→reconcile→loadMessages with DB row persisted) repairs it. The fix is to narrow the MERGE filter to preserve temp placeholders without a runId (early-window state) while still dropping them when DB has caught up on a stamped runId.

**Fix scope estimate:** ~8-15 LOC at line 643-651 (narrow the predicate). Within Branch D's ≤30 LOC budget. No API surface change. No `messagesByThread` shape change.
