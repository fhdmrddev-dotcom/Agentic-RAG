# Phase 075.2: ToolCallPanel Dedup + Final Outputs Download Link - Research

**Researched:** 2026-05-22
**Domain:** Frontend reducer + presentation (StreamsProvider + ToolCallPanel + MessageItem)
**Confidence:** HIGH (all claims VERIFIED against current code at the line numbers cited)

## Summary

CONTEXT.md is exhaustive; this file answers the 7 open investigation questions raised by the planner-spawn brief. Headline findings:

1. **BUG-260521-01 is a known-shape mismatch, not an exotic race.** The backend `tool_start` SSE event carries `name` + `args` but NOT a `tool_call_id` (`backend/app/api/threads.py:2061`). The frontend `onToolStart` reducer therefore CAN'T match a preparing entry by id — it falls back to `name + status === "preparing"`. For the FIRST tool of a run on certain orderings, no preparing entry exists at the moment `onToolStart` fires, so the "no preparing found" else-branch at `StreamsProvider.tsx:298-309` runs and appends a fresh `running-${Date.now()}` entry. Then the canonical reconcile-merge lands the same tool with a backend-assigned id (Anthropic block.id or OpenAI tc.id stored in `persisted_tool_calls`) — two entries, two ids, no key collision, both render.
2. **Reuse mechanism for `OutputFileCard` is safe either way.** `ExecuteCodeBlock.tsx` does NOT import from `MessageItem.tsx` (verified via grep). The only import edge is `ToolCallPanel.tsx:12 → ExecuteCodeBlock`, and `MessageItem.tsx:5 → ToolCallPanel`. Option (a) — export from `ExecuteCodeBlock`, import into `MessageItem` — produces ZERO cycle risk because the chain stays acyclic. Option (b) — extract to `OutputFileCard.tsx` — also works. Recommend (b) for cleanliness; (a) is acceptable shortcut.
3. **WR-02 snapshot threading has exactly 2 callers, both reach the new shape via the same edit.** No test or external import consumes `_isTransientStreamEnd` as boolean — only `Promise<boolean>` is exposed via the existing test file, which mocks `getSnapshot` and asserts return value with `expect(result).toBe(true|false)`. Changing the return to `Promise<ThreadSnapshot | null>` requires updating both call sites (lines 721 and 922) AND the 9 test assertions (`expect(result).toBe(true)` becomes truthiness; `toBe(false)` becomes `toBeNull()`).

**Primary recommendation:** Plan 01 — root-cause fix is `onToolStart` else-branch hardening (key-by-`name` fallback to look back for unfinalized same-name entries OR transition the preparing→running path so the canonical id is what the panel sees). Plan 02 — extract to shared `OutputFileCard.tsx` (option b) with `url?: string` prop and internal conditional render.

## Q1 — BUG-260521-01 root-cause SSE event sequence per provider

### Wire-format facts (VERIFIED against current backend)

| Event | Carries `tool_call_id`? | Source |
|-------|------------------------|--------|
| `tool_preparing` | NO — only `name` + `index` | `threads.py:1708, 1842, 1910` and `anthropic_service.py:220` |
| `tool_start` | NO on threads.py emit (line 2061: `name` + `args`); Anthropic-internal yield includes `id` but it's stripped at the threads.py dispatch on line 1726-1731 (only `id` + `name` + `args` enter `tool_calls_buffer`, never emitted to wire) | `threads.py:2061` |
| `tool_end` | NO — only `name` + `result` (truncated to 2000 chars) | `threads.py:2838` |
| Snapshot reconcile | YES — `persisted_tool_calls` carries `tool_call_id` per entry | `threads.py:2875-2879` |

**Critical implication:** The frontend NEVER receives a backend `tool_call_id` during streaming. The id stamped on the streaming-side `ToolCall` entry is ALWAYS frontend-generated:
- `preparing-{index}` from `onToolPreparing` (`StreamsProvider.tsx:256`)
- `running-${Date.now()}` from `onToolStart` else-branch (`StreamsProvider.tsx:302`)

The canonical `tool_call_id` only appears on snapshot reconcile (which re-hydrates the assistant message from DB), and reconcile REPLACES the streaming bucket entry wholesale (`reconcile` at `StreamsProvider.tsx:642-651`: `[...snapshot.messages, ...liveTempPlaceholders]`).

### Per-provider first-tool sequence

**OpenAI gpt-4.1 native (streaming):**
1. `delta.tool_calls[].function.name` arrives → `threads.py:1840-1842` fires `tool_preparing(name, idx)` — frontend stamps `preparing-{index}` id.
2. `delta.tool_calls[].function.arguments` accumulates (no SSE emit until tool args > 5KB, which gates `tool_args_progress` not `tool_start`).
3. After model `stream` ends (`tool_calls_buffer` populated), `threads.py:2055-2061` enters the tool execution loop → fires `tool_start(name, args)` for each tool.
4. Frontend `onToolStart` finds the preparing entry by `name + status === "preparing"` → mutates in place (`StreamsProvider.tsx:286-297`).
5. After tool execution: `tool_end(name, result)` fires → flips first running same-name entry (current WR-01 gap).

**Expected outcome:** ONE card per tool. Why does the duplicate happen?

**Root-cause hypothesis path A (likely):** Snapshot reconcile fires during streaming (e.g., on visibility change, focus event, or the post-`subscribeToRun` `.finally()` triggers `loadMessages` at `StreamsProvider.tsx:818`). The new `loadMessages` data carries `tool_calls` from DB rows where `persisted_tool_calls` entries already include the canonical `tool_call_id` but the assistant message is still in `runStatus: "streaming"`. The MERGE 3-clause filter at `loadMessages` (`StreamsProvider.tsx:1152-1163`) keeps the streaming temp placeholder via `subscriptionsRef.current.has(m.runId)`, but the placeholder's `tool_calls` array (with `running-${Date.now()}` ids) does NOT get reconciled against the DB row's `tool_calls` array (with canonical ids). The downstream UI ends up rendering both: the placeholder's streaming entry AND the DB row's persisted entry (which arrived via the same merge under a different message id).

Actually re-reading: the MERGE in `loadMessages` UNIONS via `[...data, ...liveTempPlaceholders]` — but each side is a SEPARATE Message object (different `id`). The duplicate would only render if BOTH messages render. Verify against `useMessages.ts` thin reader: `useThreadMessages` returns `state.bucketsBySurface.get(surfaceId)?.get(threadId) ?? EMPTY_ARRAY`. So both message objects ARE in the array. The "duplicate tool card" is therefore likely INSIDE ONE message — the streaming placeholder accumulates a second entry directly.

**Root-cause hypothesis path B (most likely — confirm via Chrome MCP):** The WR-02 two-probe race fires `subscribeToRun` from cursor `"0"` during reattach, replaying all SSE events from the run's beginning. The first replay of `tool_preparing` is idempotent (`onToolPreparing` early-returns at `StreamsProvider.tsx:257-258` via the `alreadyPreparing` guard). BUT the second `tool_start` replay finds the preparing entry has ALREADY been mutated to `status === "running"` (first time through), so `findIndex(tc.name === name && tc.status === "preparing")` returns `-1` (line 282-284) and the else-branch fires — appending a NEW `running-${Date.now()}` entry. Now two entries: the original (preparing→running with `id: "preparing-0"`) and the duplicate (`id: "running-{ts}"`). Dedup memo sees two distinct ids → renders both.

This explains the FIRST-tool-only fingerprint: by the time subsequent tools' `tool_start` events replay, the prior tools are `status === "done"`, so subsequent `tool_preparing` for a NEW tool index creates a fresh `preparing-{new-idx}` entry that the second pass of `tool_start` correctly mutates. Only the first tool's already-running status during replay produces the else-branch append.

**Anthropic-native:** Same sequence, with the additional twist that `tool_preparing` is emitted at `content_block_start` (line 220) before any `args` JSON arrives, and `tool_start` is emitted at `content_block_stop` (line 271) after the full args block is parsed. Replay sequence is identical — `onToolPreparing` is idempotent on replay, `onToolStart` hits the running-status-not-preparing condition on replay → else-branch append.

**OpenRouter:** Routes through the OpenAI-compatible client path (`threads.py:1830-1842` block), so wire shape matches OpenAI exactly. Same replay fingerprint.

### Where exactly the second entry is created — line citation

- **The else-branch at `StreamsProvider.tsx:298-309`** is THE site that produces the duplicate. On replay of a same-name `tool_start` after the original moved to `status === "running"` (or `"done"`), the `findIndex` at line 282-284 returns `-1` and lines 299-308 append a fresh entry.

### Cases where `onToolPreparing` does NOT fire for the first tool

- **OpenAI STRUCTURED calling mode** (`threads.py:1906-1914`): `tool_preparing` fires for ALL structured calls in a loop AFTER parse completes, with `await asyncio.sleep(0)` yielding control before tool execution. Still produces `preparing` then `start` — no skip. But the `asyncio.sleep(0)` gap is what makes the preparing state actually render on the wire as a separate frame — without it, `preparing` and `start` arrive in the same TCP packet (line 1911-1914 comment confirms). For the FIRST tool of a STRUCTURED-mode run on a high-latency link, the preparing frame could be coalesced if the comment's mitigation is bypassed somehow.
- **Anthropic mixed text + tool_use:** `content_block_start` always emits `tool_preparing` (line 220). No skip path identified.
- **OpenRouter with `parallel_tool_calls: false`:** Disabled at provider level; not a skip mechanism.

**Conclusion:** `onToolPreparing` fires for every first tool on every provider in normal flow. The bug isn't "preparing missing" — it's "preparing already consumed by replay."

### Cases where `tool_start` arrives twice for the same canonical id

YES — WR-02 reattach from cursor `"0"` replays the entire Redis stream including all prior `tool_start` events. This is the primary suspected mechanism. The cursor mismatch happens because:
1. First terminal SSE (`done`/`error`) fires → `_isTransientStreamEnd` probes snapshot → returns `true`.
2. `_reattachAfterTransient` probes snapshot AGAIN → if the run ended between probe 1 and probe 2, `since_cursors[runId]` is missing → `lastSeenOffsetRef.current.get(runId) ?? "0"` falls to `"0"` → full replay.

**Recommendation for Plan 01 task ordering:** Fix WR-02 FIRST (snapshot threading eliminates the replay-from-cursor-0 trigger), then fix the `onToolStart` else-branch to be idempotent against any remaining double-fire (defense in depth). If WR-02 alone eliminates the repro on Chrome MCP across all 3 providers, the else-branch can stay defensive without a behavioral change.

### Investigation path the planner should specify

For each provider, capture the Redis stream entries for a single run via:
```bash

docker exec agentic-rag-redis-1 redis-cli XRANGE "run:{run_id}" - +
```
Confirm: (a) one `tool_preparing` entry per tool index, (b) one `tool_start` per tool index, (c) NO duplicate entries on the wire. If the Redis stream has exactly one of each, the duplicate is purely a frontend re-consumption issue (WR-02 replay path confirmed). If the Redis stream has duplicates, the bug is upstream of the frontend (unlikely given current evidence, but worth confirming).

## Q4 — Url-optional handling for Final Outputs reuse

### Current type asymmetry (VERIFIED in `types/index.ts`)

```ts
// types/index.ts:22-26
export interface OutputFile {
  filename: string
  url: string         // REQUIRED
  size: number        // REQUIRED
}

// types/index.ts:128
finalOutputFiles?: { filename: string; url?: string }[]    // url OPTIONAL, NO size
```

The pinned panel data shape is missing TWO things: `url` may be undefined AND `size` is not present at all.

### Cleanest API choice — recommendation

**`OutputFileCard` should accept a relaxed prop shape and conditionally degrade.**

```ts
// In OutputFileCard.tsx (or ExecuteCodeBlock.tsx for option a)
interface OutputFileCardProps {
  file: {
    filename: string
    url?: string         // relaxed — back-compat for finalOutputFiles
    size?: number        // relaxed — finalOutputFiles has no size field
  }
}

export function OutputFileCard({ file }: OutputFileCardProps) {
  // If no url, render plain-filename row with ghost-border + icon styling
  // but no <a> wrapper, no download handler, no size badge.
  if (!file.url) {
    return (
      <div className="flex items-center gap-2.5 rounded-md ghost-border px-3 py-2 text-xs bg-muted/30">
        <Download className="w-3.5 h-3.5 text-muted-foreground flex-shrink-0 opacity-40" />
        <span className="flex-1 min-w-0 font-mono text-foreground/60 truncate">{file.filename}</span>
      </div>
    )
  }
  // ... existing card body unchanged, but with `file.size` falsy-guard for the size badge ...
}
```

Inside the existing card body, change line 98:
```ts
{file.size != null && <span className="text-muted-foreground/50 flex-shrink-0">{formatBytes(file.size)}</span>}
```

### Why prop-level back-compat beats a wrapper

A wrapper component in `MessageItem.tsx` (e.g., `<MaybeDownloadable file={f}>` that checks `f.url` and either renders `<OutputFileCard>` or a plain `<div>`) would:
- Duplicate the ghost-border + font-mono styling (drift risk).
- Add a second site that knows about the "no url" rendering shape.

Prop-level back-compat keeps the conditional inside ONE component and the visual styling stays single-sourced.

### Backend-side check

`backend/app/services/sandbox_service.py:harvest_output_files` populates `finalOutputFiles` with URLs as a SIDE effect (per IN-02 — double-upload is wasteful but functionally correct). In practice every finalOutputFiles entry SHOULD have a url. The optional-url back-compat is purely defensive for:
- Older messages persisted before url stamping was added.
- Future backend changes that emit filename-only events (unlikely but cheap to guard against).
- The TypeScript `url?` declaration that's already in the type — the planner shouldn't tighten the type because that's a backend-contract negotiation, not a UI-component concern.

### Specific shape proposals for the D-075.2-01 edits

**Idempotency-on-replay strategy (preferred):** In `onToolStart` else-branch (`StreamsProvider.tsx:298-309`), also search for an existing same-name entry that is `status === "running"` OR `status === "done"` AND whose `args` match. If found, UPDATE that entry's startedAt/args (no-op for the running case) instead of appending. This makes `onToolStart` idempotent against WR-02 replays.

```ts
} else {
  // Look back for a previously-finalized same-name entry that this replay
  // would otherwise duplicate. If found, treat as no-op (already processed).
  const finalizedIdx = existingCalls.findIndex(
    (tc) => tc.name === name && (tc.status === "running" || tc.status === "done"),
  )
  if (finalizedIdx !== -1) {
    updatedCalls = existingCalls   // no-op
  } else {
    updatedCalls = [
      ...existingCalls,
      { id: `running-${Date.now()}`, name, args, status: "running" as const, startedAt: Date.now(), iteration: currentIteration },
    ]
  }
}
```

This is more permissive than "look back for an unfinalized same-name entry" but matches the spec's intent ("preserve dedup invariant even if WR-02 fix is incomplete").

**Caveat:** Parallel same-name tools in a single iteration would be collapsed by this — but `parallel_tool_calls: false` is enforced backend-side (CONTEXT.md `<decisions>` WR-01 §), so this is currently safe. The future-WR-01 path (passing `id` through `tool_start` and matching by id) would require backend changes outside this phase's scope; the in-place idempotency is sufficient defense for now.

### Specific shape for D-075.2-04 (WR-01)

`onToolEnd` callback signature gains `id?: string`. The SSE parser at `lib/api.ts:381-382` needs:
```ts
else if (t === "tool_end" && callbacks.onToolEnd)
  callbacks.onToolEnd(parsed.name as string, parsed.result as string | undefined, parsed.tool_call_id as string | undefined)
```
AND `backend/app/api/threads.py:2838` should pass `tool_call_id`:
```python
await _emit(redis, run_id, 'tool_end', name=tool_name, result=tool_result[:2000], tool_call_id=tc["id"])
```

**However:** CONTEXT.md `<domain>` says "Any backend changes ... Out of scope." So WR-01's wire-level id threading is partially blocked. Two options:
- **Option α (frontend-only WR-01):** Add `id?` parameter to `onToolEnd` signature with the backward-compat fallback (`id ? tc.id === id : tc.name === name`), but the `id` will always be undefined on the wire — so the change is purely a no-op preparation for a future backend change. Doable in this phase per CONTEXT.md's WR-01 inclusion.
- **Option β (wire-through):** Touch `threads.py:2838` to pass `tool_call_id` despite the backend-out-of-scope rule.

**Recommendation:** Surface this scope question to the planner. If CONTEXT.md `<decisions>` D-075.2-04 ("ships in Plan 01") truly intended frontend-only (the `id?` defaulted to undefined), then ship option α and document as "WR-01 frontend-side ready; backend wire-up deferred." If the planner reads D-075.2-04 as full wire-through, the backend-out-of-scope clause needs revisiting.

A one-line backend edit + one-line `api.ts` parser edit is a tiny, mechanically-safe change with no ripple. Worth checking with the user. This is the only thing in this phase that isn't strictly frontend.
