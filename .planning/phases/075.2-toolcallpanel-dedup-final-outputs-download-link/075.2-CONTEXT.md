## Implementation Decisions

### BUG-260521-01 — Dedup root-cause depth (Plan 01)

- **D-075.2-01: Fix root cause + harden dedup-key fallback (defense-in-depth).**
  The streaming reducer in `StreamsProvider.tsx` must update-in-place when a streaming-side
  tool entry's `id` is finalized to the backend's real `tool_call_id`. Concretely: when
  `onToolStart` cannot find a preparing entry by `name + status === "preparing"` (the path
  at `StreamsProvider.tsx:298-309` that today appends a fresh `running-${Date.now()}` id),
  it should ALSO look back for the most recent same-name entry that is awaiting id
  finalization (or key by stable `name + index` instead of generated id) and reconcile.
  Investigation goal: trace the SSE event sequence for the FIRST tool of a run and identify
  exactly which event path creates the second entry. The bug report's hypothesis (streaming-
  side id ≠ finalized id) is the leading suspect; planner verifies via Chrome MCP captured
  SSE log + reducer-state trace before locking the exact diff.

  Secondarily, tighten `ToolCallPanel.tsx:542` dedup-key fallback per 075.1-REVIEW WR-03
  to include the array index when both `id` and `startedAt` are absent:
  ```ts
  const key = tc.id || `${tc.name}-${tc.startedAt ?? ''}-${idx}`
  ```
  This is dead code once D-075.2-01 root cause is fixed, but ships as defense so the next
  edge case in this neighborhood can't produce a silent dedup.

- **D-075.2-02: Acceptance bar = ZERO duplicate, ever.**
  The first tool of a run must render exactly ONE card from the moment the first SSE event
  fires. Verified via Chrome MCP screenshots at t=0, t=2s, t=5s on all 3 providers — always
  one card. Setting the bar lower (e.g., "transient window <2s") would mean the root-cause
  fix is incomplete; this bar is what makes "root cause" the right framing.

- **D-075.2-03: WR-02 two-probe getSnapshot race fixes ship in Plan 01.**
  `_isTransientStreamEnd` returns the `ThreadSnapshot | null` instead of `boolean`, and
  `_reattachAfterTransient` consumes it directly instead of calling `getSnapshot` a second
  time. Eliminates the race window where the second probe can return `active_runs: []`
  after the run terminated, causing reattach from cursor `"0"` and duplicate SSE callbacks
  (a hypothesized contributor to BUG-260521-01 per the bug report's "Hypothesized cause" §).
  The Phase 067.5 Branch D-3 streaming-bucket guard and the D-063.1-11 `reconcileInFlightRef`
  single-bit lock are preserved verbatim.

- **D-075.2-04: WR-01 `onToolEnd` id matching ships in Plan 01.**
  Backend SSE `tool_end` events already carry `tool_call_id` per Phase 074-era plumbing.
  Thread it through the callback signature: `onToolEnd: (name, result, id?)` and match
  by `(id ? tc.id === id : tc.name === name) && tc.status === "running"`. The `id?` is
  optional for backward compat with any SSE frame that lacks id. Removes the non-deterministic
  "done" stamp risk for future parallel-tool support, lives in the same `StreamsProvider.tsx`
  reducer block as D-075.2-01.

### BUG-260521-02 — Final Outputs download link UX (Plan 02)

- **D-075.2-05: Reuse `OutputFileCard` from `ExecuteCodeBlock.tsx` verbatim.**
  The pinned "Final outputs" panel in `MessageItem.tsx:255-264` renders a stack of the
  exact same `<OutputFileCard>` components used in per-cell delta panels (icon + filename +
  size badge + ghost-border + hover state + downloading spinner + error fallback). Visual
  consistency: a user who has seen the per-cell card instantly recognizes the affordance.
  All download semantics (D-067.3-R2-03/04 programmatic blob+Bearer fetch, D-067.2-03
  relative URL + `API_BASE` resolution, 401 right-click trade-off) come along free.
  The cumulative panel is small (final outputs only, not delta-per-iteration), so the
  per-card UI weight is acceptable.

- **D-075.2-06: Planner picks the right reuse mechanism.**
  Either (a) export `OutputFileCard` from `ExecuteCodeBlock.tsx` and import into `MessageItem.tsx`,
  or (b) extract `OutputFileCard` (and its `resolveOutputUrl` + `formatBytes` helpers) into
  a shared `frontend/src/components/chat/OutputFileCard.tsx` and update both consumers.
  Both deliver visual consistency; (b) is cleaner long-term but adds refactor scope.
  Planner chooses based on import-graph / circular-dep risk inspection — no user preference.

- **D-075.2-07: Empty-state behavior unchanged.**
  Current guard `message.finalOutputFiles && message.finalOutputFiles.length > 0` at
  `MessageItem.tsx:255` stays. Panel renders only when there's at least one file; the link
  rendering is purely a swap of `<li>{f.filename}</li>` for the reused card.

### Plan structure + verification (cross-cutting)

- **D-075.2-08: Split by bug — 2 plans.**
  - **Plan 01** = BUG-260521-01 reducer-quality pass (D-075.2-01 root cause + dedup
    fallback hardening + D-075.2-03 WR-02 + D-075.2-04 WR-01). All edits in
    `StreamsProvider.tsx` + `ToolCallPanel.tsx`.
  - **Plan 02** = BUG-260521-02 Final Outputs link (D-075.2-05 + D-075.2-06). All edits
    in `MessageItem.tsx` (+ optional extraction of shared `OutputFileCard.tsx` per D-075.2-06).
  - Plans are independent (different files, different bug targets); they can ship and
    verify independently. Wave-1 parallel is acceptable.

- **D-075.2-09: Test mix — Vitest unit + Chrome MCP cross-provider UAT.**
  Match the 075.1 precedent (it's what surfaced these bugs). Unit coverage:
  - Reducer invariant: first SSE `tool_start`/`tool_call_complete` sequence produces ONE
    tool_calls entry, regardless of preparing-entry absence.
  - WR-01: `onToolEnd(name, result, id)` flips the entry whose `tc.id === id`, not just
    the first running same-name entry.
  - WR-02: snapshot threaded through transient filter; `_reattachAfterTransient` does not
    call `getSnapshot` independently.
  - WR-03 dedup fallback key includes `idx` tiebreaker.
  - MessageItem renders `<OutputFileCard>` for each `finalOutputFiles[*]` with a `url`,
    and renders plain filename when `url` is absent (back-compat).

  Chrome MCP UAT: cross-provider sleep test + primes-matplotlib test on OpenAI / Anthropic /
  OpenRouter / **Google** (4 providers — Google added 2026-05-22 post-260522-gdg hotfix, see
  the cross-provider note below). Screenshots at t=0, t=2s, t=5s confirming exactly ONE
  first-tool card on every provider. Final Outputs panel click → download confirmed on at
  least one provider.

## Specific Ideas

- **First-tool-only pattern is the fingerprint.** The bug report explicitly notes "always
  on the FIRST tool of a run, never on later ones." This rules out generic dedup failure
  and points squarely at the streaming-state vs canonical-state mismatch for the run's
  initial tool entry. Planner: capture an SSE wire log during reproduction and trace the
  id flow from `tool_call_started` → `tool_start` → `tool_call_complete` for the first
  tool specifically.
- **Cross-provider reproduction rules out "model retried."** OpenAI gpt-4.1 (45s sleep) +
  Anthropic claude-sonnet-4-6 (primes-matplotlib) both show identical fingerprint. This
  is provider-agnostic frontend behavior. **Google added to the UAT matrix 2026-05-22**
  post-quick-task-260522-gdg (Google was broken at original 075.2 scoping; the Path A
  hotfix at `openai_service.py:886-893` restores Google content delivery and surfaces
  Gemini tool-calling through the same SSE event chain — `tool_preparing` /
  `tool_start` / `tool_end`). UAT acceptance: Row 4 (Google / gemini-2.5-flash) must
  pass the same EXACTLY-ONE-first-tool-card bar at t=0/2/5/15s + Final Outputs link
  clickable on a primes-matplotlib run. Any Google-specific defect surfaced by this
  row folds into Phase 075.3 (which already touches the StreamsProvider reducer
  surface), NOT back into 075.2.
- **Snapshot reconcile WORKS today** — it correctly collapses the duplicate after 10-15s.
  Whatever the streaming reducer does wrong, the canonical-state merge does right.
  D-075.2-01 should align the streaming-state path to whatever the snapshot path produces
  (single entry keyed by canonical `tool_call_id`), not invent a new merge strategy.
- **Per-cell OutputFileCard ALREADY works correctly** for the same `url` data shape
  (BUG-260521-02 §"What we observed" confirms `primes.png 34.0 KB` is clickable in the
  per-cell card). The fix is to surface the same component on the pinned panel — no
  new data plumbing, no new download path.
- **Chrome MCP UAT shape is identical to 075.1.** Same dev login (`fhdmrd@gmail.com /
  123456`), same dev URL (`http://localhost:5173/`), same sleep + primes-matplotlib test
  prompts. Reuse the 075.1 UAT recipe; this minimizes UAT setup overhead.
