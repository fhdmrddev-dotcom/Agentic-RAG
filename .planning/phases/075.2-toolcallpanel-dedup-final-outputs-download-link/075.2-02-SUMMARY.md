## Decisions Made

- **Chose RESEARCH §Q3 Option (b).** Extracted `OutputFileCard` to a dedicated `OutputFileCard.tsx` module instead of re-exporting from `ExecuteCodeBlock.tsx`. Rationale: cleaner long-term dependency narrative (`MessageItem` no longer imports "through" the code-execution module); `resolveOutputUrl` + `API_BASE` are genuinely shared infrastructure (D-067.2-03) that a future Skill Studio surface would want; refactor scope stays bounded (one new file, two consumers updated).
- **Url-optional handled at the prop level, not the canonical type.** Per RESEARCH §Q4 + PATTERNS.md §7: the canonical `OutputFile` in `@/types/index.ts` stays STRICT (`url: string`, `size: number`). Only the `OutputFileCardProps` shape relaxes both fields with `?`. The strict type is a structural subtype of the relaxed shape, so the existing per-cell `<OutputFileCard key={i} file={file} />` call site in `ExecuteCodeBlock.tsx` keeps typechecking verbatim.
- **Hooks declared unconditionally before the url-optional early-return.** Cleaner than the alternative (conditional hooks with `eslint-disable-next-line react-hooks/rules-of-hooks`). The two `useState` calls in the url-absent branch are unused (they always return their initial values for that render), but their unconditional declaration keeps hook ordering trivially stable across all renders of the same component instance — rules-of-hooks linter is satisfied without any disable directives.

## Deviations from Plan

None — plan executed exactly as written. The plan provided literal code blocks for the extraction; both tasks landed verbatim.

The one micro-decision the plan left to the executor (hook ordering vs early-return) was resolved by declaring hooks unconditionally BEFORE the early-return (rather than the PLAN.md's suggested early-return-before-hooks pattern). Both forms work in practice (the url-ness of a given `<OutputFileCard file={f}>` instance is stable per render position, so hook order doesn't actually shift), but unconditional declaration avoids the need for any eslint-disable directive — strictly cleaner. This is a tactical detail, not a semantic deviation.
