## ⚠ The consequence that must not be read as a detail

**On a HARNESS run, the composer Stop no longer resolves the producer `runs.run_id` at all.**

R5 removes the optimistic placeholder that carried it, so there is no bucket row to scan, and R6's
fallback resolves the thread's workflow frame instead — a **`workflow_runs.id`**.

That is safe for a shipped-mechanism reason rather than an argued one: `194-11` gave
`DELETE /runs/{id}` a Step-1b dual-id fallback that accepts a `workflow_runs.id`, whose clause (c)
requires the thread anchor to still point at the run — true for exactly the LIVE runs this serves.

⚠ **`ComposerStopHarness.test.tsx`'s own header says `DELETE /runs/{id}` "accepts the PRODUCER
`runs.run_id` and nothing else". That sentence was made FALSE by `194-11` in the same phase that
wrote it**, and it is left standing with the correction beside it rather than edited away — exactly
as the plan's `<interfaces>` block instructed.

**DEEP is unaffected**, and by construction rather than by care: R5's gate keys on
`workflowDefinitionId`, which a Deep send never sets, so a Deep composer Stop still scans the bucket
and still hands `cancelRun` the producer id. The Deep positive control asserts that unchanged value.

**A second consequence, stated because it is a product fact and not only a test fact:** on a harness
run there is no chat assistant bubble left for *"Response stopped"* to render on. That is R5's
intent — the harness run's receipt is the RunCard and the panel — and it is *why* this phase's
stopping reading lives in the store rather than on a message. It is also why the `stoppedByUserRef`
positive control had to move to the Deep path: on the harness path its effect is now unobservable,
and a control asserting `undefined === undefined` is the vacuous control its own comment warns about.

transition the surface honestly shows `⊘ Stopping this run…` and then `✓ Complete`. **That is
correct behaviour for this phase**, and RUN-01 stays UNTICKED until the separate L-01 phase ships.
