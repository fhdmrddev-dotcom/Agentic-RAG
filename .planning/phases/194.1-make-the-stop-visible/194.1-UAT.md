### 6. Workspace panel still reads "Running" after the run is stopped
expected: After a stop, the panel's phase spine agrees with the chat. The chat says `⊘ Stopped by you`; the panel should not still say the run is going.
result: issue
reported: "it is But in the workspace it's still saying running"
severity: major
found_during: test 1
evidence: |
  `Screenshot 2026-08-16 213744.png`, taken AFTER the stop landed. The chat run line reads
  `⊘ Stopped by you · 0 of 5 steps · 35s`, while the panel simultaneously shows
  `gather-usage — Running`, the PHASE 1 card badged `● Running`, and its body `● Working`.
  ⚠ **The Stop CONTROL itself behaved correctly** — the `THIS RUN` row and its red Stop
  button are GONE from the panel in the after-shot, which is R3's terminal behaviour. The
  stale reading is the PHASE SPINE only, not the control.
diagnosis: |
  ⚠ **Traced, not guessed — and the backend is NOT at fault.**
  1. Phase 194's `cancel_active_phases` writes `cancelled` to `workflow_phases`, and the
     client maps it: `DB_PHASE_STATUS.cancelled → "cancelled"` (`lib/phaseState.ts:59+`,
     the 7th literal, added by migration 119). So both ends of the wire are correct.
  2. The panel's phases come from `usePhases(threadId)` → `usePanelReconcile`
     (`hooks/usePanelReconcile.ts`), whose refresh `useEffect` is keyed on **`[threadId]`
     ONLY** — *"fires ONLY on thread-switch + the manual `reconcile()` escape hatch"*
     (its own docblock, line 22).
  3. **Nothing calls that escape hatch when a stop lands.** The cancel also tears down the
     SSE stream, so no terminal phase event arrives to update the store either.
  ⇒ The panel keeps the last streamed status forever on the current thread. This is a
  MISSING REFRESH TRIGGER, not a wrong status.
prediction: |
  If this diagnosis is right, **test 3 (navigate away, come back) will show the panel
  correcting itself** — because a thread-switch is exactly the trigger that does fire.
  Test 3 is therefore also the discriminator for this issue. If the panel is STILL wrong
  after a round trip, the diagnosis above is wrong and the cause is upstream of reconcile.
prediction_outcome: |
  ✅ **CONFIRMED by test 3** (`Screenshot 2026-08-16 214524.png`). The same state that read
  `Running` indefinitely on the live thread reads `gather-usage — Stopped` / `■ Stopped`
  after a round trip. The prediction was made BEFORE the row was driven and it held, so the
  root cause is established rather than merely plausible: **the status, the wire and the
  mapping are all correct; the only thing missing is a reconcile trigger when a stop lands.**
  ⚠ This also bounds the blast radius — the defect is a STALE READING ON THE LIVE THREAD ONLY,
  self-healing on any navigation. It is not data loss and not a wrong terminal state.
fix_shape: |
  Call the existing `reconcile()` escape hatch when a thread transitions out of streaming
  (the same slice-transition subscription plan 03 already added for the stopping clear is the
  natural home). ⚠ Sizing is NOT asserted here — a one-file/≤10-line judgement is G-3's call
  and belongs to whoever writes the fix.
blast_radius: |
  ⚠ **MEASURED, and it CORRECTS this file's own earlier speculation.** An earlier draft of this
  entry asked whether the todos/files/asks panels need the same trigger and said *"if they do,
  this is one shared cause with four symptoms, not one."* **Measured: they mostly do not, and
  the narrower answer is the right one.**
  `usePanelReconcile` has FIVE consumers — `Todo`, `WorkspaceFile`, `PendingAsk`,
  `TaskRunIndexItem`, `Phase` (`StreamsProvider.tsx:3600/3655/3676/3695/3883`) — all keyed on
  `[threadId]`. But SSE keeps them live DURING a run: `todo_updated` (full-state replace),
  `workspace_file_written` / `workspace_file_deleted`, and `phase_started` / `phase_completed`
  all write to the store (`lib/api.ts:467-505`). Reconcile is the mount/thread-switch FLOOR,
  not the live path.
  ⇒ **The defect is specifically that a stop TEARS DOWN THE STREAM WITHOUT A TERMINAL PHASE
  EVENT for the phase that was running.** Files written before the stop already arrived via
  their own SSE. So the stale surface is the PHASE STATUS, and the fix is correspondingly
  narrow. **Do not scope this as a five-panel refresh problem — that would be fixing something
  nobody has observed breaking.**

### 8. ⚠ A human approval that nobody answers becomes an approval
expected: A run paused on `llm_human_input` waits for the person; if nobody answers, the outcome is distinguishable from an approval.
result: issue

severity: major
found_during: test 5
filed_as: BUG-260816-03
evidence: |
  ⚠ **The operator's reading was right, and it is NOT a mis-click.** Measured in Postgres across
  the last five runs of `doc_qa_scoped_098uat`: **four completed the `confirm` phase with
  `answer: ""`, each at exactly the 5-minute mark**; the fifth — the round the operator actually
  answered — took **24 s** and carries a real answer. `timeout_seconds` is unset on the phase, so
  `HumanInputConfig`'s default applies (`models/harness.py:135` → **300**). Measurement and
  constant agree exactly.
  Mechanism (`phase_types.py:818-856`): `subscribe_for_response` returns `None` on timeout,
  `answer` is initialised `""` and only assigned inside the `kind == "response"` branch, so the
  timeout path **falls through to a normal return** and the phase records `completed`.
  ⇒ **Nothing distinguishes "the human approved" from "nobody was there."** That is why no
  confirmation was seen — there was nothing to confirm.
why_it_is_a_defect_not_a_design: |
  ⚠ **The same codebase already answers this correctly TWICE, on the paths either side of it:**
  the validator `ask_user` gate treats an unanswered prompt as an **honest `fail_run`**; the
  armed action-risk checkpoint uses an **indefinite wait**. `llm_human_input` is the only one of
  the three that proceeds silently — and the only one whose whole purpose is to obtain a
  person's decision. The same function even defends the shutdown and choice-click routes to an
  empty answer. **The timeout is the one route nobody defended.**
blast_radius: |
  ⚠ **The armed `external_action` path is NOT affected — it waits indefinitely**, so an
  unattended timeout cannot auto-approve an outbound send. That is what bounds this at major
  rather than blocking, and it is stated so the finding is not over-read.
  ⚠ It becomes blocking the moment a human step gates a destructive or outbound action — which
  is exactly what `SEED-167` proposes (*"delete or close the open risks that were closed"*).
