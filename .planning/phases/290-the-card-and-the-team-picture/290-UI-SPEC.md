## 1. The card chip line (VIS-04)

### 1.1 Placement and what stays

- The 179 C card stays as shipped: 3px gutter, line 1 (mark, name, version), line 2 (`row-answer`: run truth, state, automation), identity line, folder chip, match reason, footer. **No purpose sentence returns** (D-02).
- The chip line is a new block inserted **between `row-answer` and `row-identity`**, exactly where the sketch's capture placed `<!--CHIPS-->`. It has `data-testid="row-steps"`.
- It renders **only when the definition has at least one step** (`row.def.phases` is an array with length ≥ 1). No steps, an absent `def`, or an unparseable definition renders **no node at all**: no empty row, no reserved space (D-01). A card without steps composes byte-identically to today.
- ⚠ Inserting it shifts `row-identity` from child index 2 to 3 **on cards with steps only**. The child-order pins in `WorkflowCard.test.tsx` move in the same commit, by decision, as they did when line 2 landed.

### 1.2 Anatomy (collapsed, the resting state)

```
[glyph Work out how to do it] → [glyph Write it up] → [glyph Reach outside] → +3 more
```

- Structure: an `<ol aria-label="Steps, in run order">` holding the chips as `<li>`, followed by the `+N more` button as a separate, non-shrinking element. The `→` joiners are `aria-hidden`.
- Layout: `mt-2 flex items-center gap-1 min-w-0`. The chip track is `flex min-w-0 flex-1 items-center gap-1 overflow-hidden flex-nowrap`. The `→ +N more` pair is `flex-none` and sits **outside** the clipped track, so it can never be cut off, including at 375px.
- Order: steps sorted by `phase_index` ascending (ties keep array order). The first **3** show (D-03).
- Chip: `inline-flex min-w-0 max-w-[170px] items-center gap-1 rounded-full border border-border bg-muted/40 py-0.5 pl-1 pr-2 text-[12px] leading-4 text-foreground`.
  - Glyph: the `phaseGlyph(phase_type)` component at 16×16, `aria-hidden`. An unknown type renders **no glyph** (no `•`, no emoji).
  - Words: `PHASE_TYPE_SENTENCES[phase_type]`, truncated with an ellipsis inside the chip (`truncate`). **Never** `phase.name`, never `nodeTitle()`, never `PHASE_TYPE_LABELS`, never the slug or the raw type id (D-04). The only exception is a `phase_type` outside the closed set of 7: it echoes its raw string, which is the shipped `nodeTitle` floor and the honest answer for a type this client does not know.
  - Each chip also carries `title={words}` as a desktop convenience. It is never the only carrier of the words.
- Joiner: `→`, `text-[11px] text-muted-foreground`, `aria-hidden`, between every pair of shown chips and before `+N more`.
- `+N more`: a `<button type="button">`, `text-[11px] text-primary`, `rounded-full border border-dashed border-border px-2 py-0.5`, `aria-expanded="false"`, accessible name `Show N more steps`. Rendered only when there are more than 3 steps; N = steps − 3.
- No hover state on chips (they are not interactive). The card root is not clickable, so the button needs no propagation guard.

### 1.3 Expanded state (`+N more` pressed)

- The line becomes `flex-wrap` with `gap-x-1 gap-y-2`, `overflow-visible`, and **every** step is shown as a chip in run order, with chip `max-width` lifted and words allowed to wrap (`whitespace-normal`). The remaining steps are now **named in visible words** with no hover (D-03, SEED-155 item 1).
- The last element is a `Show less` button, same style as `+N more`, `aria-expanded="true"`. Pressing it collapses back. Focus stays on the toggle across both states.
- State is per card, local, not persisted. It resets on remount.

### 1.4 Sizes the planner must cover

| Case | Collapsed render |
|---|---|
| 1 step | One chip, no joiner, no `+N more`. Reads as honest (sketch question 4) |
| 2-3 steps (every production definition today) | All chips, no `+N more` |
| 4-7 steps (stress) | 3 chips, `→ +1 more` … `→ +4 more` |
| 0 steps / no `def` | No `row-steps` node |
| Phone width 375px | Chips shrink and truncate; `+N more` stays fully visible; the line never wraps while collapsed |

### 1.5 New strings (all in `library/libraryVocabulary.ts`, as entries; no literal in `WorkflowCard.tsx`)

| Entry | Value |
|---|---|
| `STEP_LINE_LABEL` | `Steps, in run order` |
| `STEP_LINE_JOINER` | `→` |
| `stepLineMore(n)` | `+${n} more` |
| `stepLineMoreLabel(n)` | `Show ${n} more step${n === 1 ? "" : "s"}` (accessible name) |
| `STEP_LINE_LESS` | `Show less` |

The chip **words** are not copied into `libraryVocabulary.ts`; they are read from `PHASE_TYPE_SENTENCES` so there is one home for them. Naming note: `CHIP_WORDS` / `CHIP_ORDER` already exist in that file for the filter chips, so these use the `STEP_LINE_` prefix.

## 2. The `Steps | Team` switch (VIS-01 entry, D-06)

- **One entry point**: a two-segment switch in the **header row of `WorkflowCanvas`** (the row that already carries `👁 View only` / `✎ Editing` and the ⌥ `Technical names` toggle), placed right-aligned **immediately before** the ⌥ toggle. This is the "builder header" of sketch 290 (`.bhead`), and it keeps the team picture next to the ⌥ reveal it uses.
- It renders **only when the builder page passes the team prop**. `WorkflowRunPage` also mounts `WorkflowCanvas` and passes nothing, so the run page shows no switch (D-06: no entry from the run page or the library card).
- Markup and style: the house segmented control (`builder-view-toggle` pattern, `WorkflowBuilderPage.tsx:2099`): a `div role="tablist" aria-label="Show steps or team"` with two `button role="tab"`s, `rounded-md px-3 py-1.5 text-[13px]`; selected `bg-primary/10 font-semibold text-primary`; unselected `text-muted-foreground hover:bg-accent/40 hover:text-foreground`. `data-testid`s: `canvas-view-steps`, `canvas-view-team`. Labels: **`Steps`** and **`Team`**, no glyph.
- Default: `Steps`. The choice is local to the open builder session and is not persisted.
- **Team is always enabled**, including for 1-step and 0-step workflows (D-12 overrides the sketch's disabled segment; see §10).
- Who sees it: anyone who can open the workflow in the builder, including starters and another person's published workflow opened read-only (D-07). It reads the phases the builder already holds, so it needs no new request.
- What Team does: replaces the canvas plane, the editing toolbar and the canvas notice region **in place** with the team picture. Steps restores them exactly as they were: selection, unsaved edits and scroll position are not lost, because Team reads the same in-memory phases (including unsaved edits) and writes nothing.
- In Team mode the header's left side reads the shipped read-only vocabulary, because the editing hint ("drag a step along the lane…") would be a false promise there: `👁 View only` pill + `who does each step, and what checks it`. Steps mode restores the shipped `✎ Editing` / `👁 View only` line.
- Budget (ledger, `WorkflowCanvas.tsx` 31/9/1708 FIRES): one optional prop, one branch keyed on the switch state, one mount. Anything larger is the signal to extract first.

## 3. The team picture (VIS-01, sketch 290 winner A, org chart)

### 3.1 The one derivation (D-11)

A value-only module (no React, no API import; the `cardFace.ts` pattern), e.g. `components/workflows/teamPicture.ts`, takes `(phases, kbTools)` and returns:

- `steps[]` in `phase_index` order: index, number (1-based), slug, phase_type, title (`nodeTitle(phase, nameContext)`), role words (`PHASE_TYPE_SENTENCES`), seats (from `config.max_parallel_agents` for `llm_batch_agents`, backend default 5 when absent).
- `gates[]`: one per declared `validators[]` entry, plus the derived gates in §3.5, each with its step index, `judge` (true only for `kind === "llm_judge_rubric"`), kind, failure words, rubric text.
- `lines[]`: **every** line the picture draws, each with `kind` (`handoff` | `judge` | `check` | `jump`), `from`, `to`, and a `source` string naming the definition path it came from, for example `phases[2].validators[0].kind = "llm_judge_rubric"`.
- Totality: malformed or absent `validators`, a missing `config`, an unknown `phase_type`, an unknown `on_failure` and an unresolvable skip target all resolve without throwing.

**The SC#3 rule, enforced by construction:** the derivation has no code path that creates a line between two steps except `jump`, and `jump` exists only for a validator whose `on_failure` parses with `parseSkipTarget()` to a slug present in the definition. A planted workflow with no `skip_to_phase` returns zero step-to-step lines, asserted on `lines[]` **and** on the rendered content (no `data-line-kind="jump"` element, and the ⤳ label text absent from the DOM).

### 3.2 Layout

```
                 ┌───────────── ORCHESTRATOR ─────────────┐
                 │ Syrel runs the 3 steps in order        │
                 │ Gives each step its turn and keeps …   │
                 └────────────────────────────────────────┘
          ┌──────────────────────┼──────────────────────┐        (handoff bus, solid primary)
     ┌─ 1 [glyph] ─┐       ┌─ 2 [glyph] ─┐        ┌─ 3 [glyph] ─┐
     │ title        │       │ title        │        │ title        │
     │ role words   │       │ role words   │        │ role words   │
     └──────────────┘       └──────────────┘        └──────────────┘
                                   ┆ (dashed)
                            ┌ CHECK · STEP 2 ┐
                            │ Must match …   │
                            │ If it fails: … │
                            └────────────────┘
        Checked by rule, not by a judge.
   Built from this workflow's definition. Steps never pass work to each other.
```

- Plane: `bg-background`, padding 24px top/left/right, 72px bottom, `overflow-x-auto`. The picture keeps its natural width and scrolls horizontally rather than shrinking text.
- Orchestrator: one node, centered over the full width of the step row, 300px wide, 56px above the step row.
- Step row: a CSS grid of `repeat(N, minmax(128px, 1fr))`, 16px gap, in run order. At 7 steps the row is 7×128 + 6×16 = 992px minimum, so the stress case scrolls inside the plane in a typical builder column. That is the intended behaviour; text never drops below the sizes in Typography.
- Gate row: the same grid columns, 32px below the step row. Each column stacks the gates of the step above it, 8px apart, in validator order, derived gates last.
- Handoff lines: from the orchestrator's bottom edge down 28px to a horizontal bus, then down to the top of each step. One per step, no more.
- Gate lines: from the top of each gate card straight up to the bottom of its own step.
- ⤳ jump: from the bottom of the owning check, down to 32px below the lowest gate card, across to the target step's column, up to the target step's bottom edge, with the label `⤳ only if the check fails` centered under the horizontal run (`text-[11px] text-warning`).
- `retry` is **never** drawn as a loop; it is written in the gate's "If it fails" line (D-10).

### 3.3 Node faces

**Orchestrator** (`border-primary/45 bg-primary/10`, rounded-lg, `px-3 py-2`):
- Eyebrow (mono 10px uppercase, `text-muted-foreground`): `Orchestrator`.
- Title (13px/600, 3-line clamp): `orchestratorTitle(n)`.
- Subtitle (12px, `text-muted-foreground`): `ORCHESTRATOR_SUB` (or `ORCHESTRATOR_SUB_ONE` for a single step).
- It is drawn whenever there is at least one step. It is the engine, not a phase: it carries no number, no glyph and no gate (D-09).

**Step** (`bg-card border-border`, rounded-lg, `px-3 py-2`; `programmatic` uses `bg-muted/40`; `llm_human_input` uses `border-warning/45 bg-warning/10`):
- Row 1: step number pill (mono 10px, 18×18, `rounded-full border`) then the `phaseGlyph` mark at 24px. No corner role word (D-15).
- Row 2, title (13px/600, 2-line clamp): `nodeTitle(phase, nameContext)`, the same face the Steps view shows, so a person switching views recognises the step.
- Row 3, role (11px, `text-muted-foreground`): `PHASE_TYPE_SENTENCES[type]`, the same words as the card chip (D-15). When row 2 already equals that sentence (an unnamed step on the floor tier), row 3 shows `PHASE_TYPE_SUBTITLES[type]` instead, so the node never says one thing twice.
- ⌥ Technical names on: row 3 becomes `technicalTitle(phase)` (`AI agent step · research`). The title does not change (the shipped "swap the subtitle, not the title" convention).
- `llm_batch_agents` only, row 4: seat dots, `min(N, 8)` dots of 12px with 4px gap, then `up to N at once` (11px). N comes from `max_parallel_agents`. The words always state N, even above 8 dots (D-14).

**Gate card** (rounded-md, `px-3 py-2`, 11px):
- Check: `bg-muted/40 border-border`. Judge: `border-accent-violet/55 bg-accent-violet/10`.
- Eyebrow (mono 10px uppercase): `Judge · step N` (`text-accent-violet-text`) or `Check · step N` (`text-muted-foreground`).
- Words (`text-foreground`): the kind's words from §3.6. ⌥ on: the raw kind (`llm_judge_rubric`, `regex_match`, …).
- Judge only: the rubric from `config.rubric` as plain text in curly quotes, 3-line clamp, `text-muted-foreground`. Hidden under ⌥. Rendered as text, never HTML.
- Last line (`text-muted-foreground`): `If it fails: …` from §3.6. A resolvable jump renders `⤳ jump to step N` in `text-warning`.
- No glyph on any gate card (icon convention §4, X-2; D-16).

### 3.4 Absence, said once in words (D-12, D-13)

| Situation | What renders (in this exact place) |
|---|---|
| 0 gates (declared and derived) | Under the step row, centered, 11px italic `text-muted-foreground`: `Nothing checks this work.` No empty gate slot, no placeholder card |
| ≥ 1 gate, none is a judge | Under the gate row, centered, same style: `Checked by rule, not by a judge.` |
| ≥ 1 judge | No absence line |
| 1 step | The orchestrator, one handoff line, the one step, then centered under it (12px, `text-muted-foreground`): `One step, so there is no team to coordinate.` Its gates and the absence rule above still apply. No other node is drawn: no invented worker, no empty seat |
| 0 steps | No orchestrator. Centered in the plane: heading (13px/600) `No steps yet, so there is no team to show.` and body (12px muted) `Add a step in Steps to see who does the work.` |
| Batch step | `up to N at once`, never a headcount |

Under every non-empty picture, one caption (11px, `text-muted-foreground`, `border-t border-border/60`, 8px 12px padding): `Built from this workflow's definition. Steps never pass work to each other; each one reads what the earlier steps produced.` This is the sentence that makes "no step-to-step lines" read as true rather than broken (D-09). It does not repeat any count; absence is said only by the lines in the table above.

### 3.5 Derived gates (researcher addition, flagged for confirmation)

The engine adds a gate the definition does not list: `grounding.effective_phase()` appends a `citations_required` gate (`on_failure: fail_run`, 2 retries) to every step whose grounding cause is **detected** (it reads a knowledge-base tool). If the picture drew only `validators[]`, a grounded step would carry the line `Nothing checks this work.`, which would be false. So:

- A step where `groundingCauseOf(phase, kbTools)` returns a cause gets a derived **Check** card: words `Must prove it` (`GOVERNANCE_SEAL_LABEL`, reused, not re-spelled), `If it fails: stop the run`, source `phases[i] · grounding: <cause>` (for example `detected via search_documents`). It is computed from the definition and the same `kbTools` the canvas seal uses, so the picture and the canvas ⛨ seal cannot disagree.
- A step where `actionRiskArmed(phase)` is true gets a derived **Check** card with the words `Stops and asks you before it acts` and source `phases[i].action_risk_armed = true`.
- Derived gates are never Judges, never draw a ⤳ line, and are listed in the ⌥ ledger like every other line.
- If the operator rejects this, the fallback is to drop derived gates and change the 0-gate line to `No check is declared on this workflow.` Either way the line must stay true.

### 3.7 The ⌥ Technical names reveal

When the app-wide ⌥ toggle is on, in Team mode only:
- Step row 3 swaps to `technicalTitle(phase)`; gate words swap to the raw kind; the rubric quote hides.
- A ledger panel appears **below the caption**: heading `Every line on this picture` (mono 10px uppercase), then one row per entry in `lines[]`: a 30px line sample in that line's stroke, the plain words (`Orchestrator → step 1`, `Judge → step 3`, `⤳ step 2 → step 5, only if the check fails`), and the `source` path in mono 10px. Seat rows follow (`Step 3: up to 5 assistants`, source `phases[2].config.max_parallel_agents = 5`). It ends with `LEDGER_NO_LINKS`.
- ⌥ off: no ledger renders. The plain caption is the whole honesty surface for the business audience.

### 3.8 Interaction and accessibility

- The picture is **read-only and non-interactive**: no node is clickable, focusable or hoverable, there is no drag, no pan gesture and no selection. It is not a second canvas (no xyflow instance).
- Semantics: a `<figure aria-label="Team picture for {workflow name}">`. Inside it, the orchestrator is a paragraph, the steps are an `<ol>` in run order, and each step's gates are a nested `<ul>` inside that step's `<li>`, so a screen reader hears the structure without the lines. The SVG line layer is `aria-hidden`. The ⤳ relationship is also stated in words on the owning check (`If it fails: ⤳ jump to step N`), so no fact lives only in a drawn line.
- Lines are drawn from the rendered node rectangles. They are recomputed on resize and when ⌥ changes the node heights, and must never point at a stale position.
- Each rendered line carries `data-line-kind` and `data-line-source` (the derivation's `source`), so tests can assert the rendered line set equals `lines[]`.

## 6. G-4 lived-experience failure scenarios (operator-defined at scope time)

Each is driven in the real app with Chrome MCP at verification, with a screenshot **and** a read of the rendered text. A wire format or a testid alone does not pass a row.

1. **Chips show type ids.** Open the library with the 7-step stress workflow and a 2-step production-shaped one. Fail if any chip shows `llm_agent`, `llm_emit`, a slug, `PHASE_TYPE_LABELS` text (`AI agent step`) or an author's step name. Pass: only the seven type sentences, in run order. Also fail if `+N more` is clipped at 375px.
2. **A line appears between two steps.** Open Team on Literature review and on the 2-step workflow. Fail if any line joins two step nodes. On Vendor risk review, fail if there is more than one step-to-step line, or if the one present is not the ⤳ from the step-2 check to step 5 labelled `⤳ only if the check fails`.
3. **A 1-step workflow shows a worker that doesn't exist.** Open Team on the single-step workflow. Fail if anything other than the orchestrator, one step, its own gates and `One step, so there is no team to coordinate.` is drawn (an extra step, an empty seat, a placeholder judge).
4. **A no-judge workflow shows an empty judge slot with no words.** Open Team on the 2-step no-gate workflow and on Plan → Execute → Verify. Fail if any empty card, blank slot, dashed placeholder or unlabeled gap appears where a judge would be. Pass: `Nothing checks this work.` on the first, `Checked by rule, not by a judge.` on the second, each said once.
5. **Looks right on the sketch, breaks on real size** (ROADMAP failure line). Open Team on a real production-shaped 2-3 step workflow from the local DB **and** the 7-step stress fixture, in dark and light mode. Fail if text clips, titles overlap, lines point at the wrong node, or the picture squeezes text instead of scrolling.
