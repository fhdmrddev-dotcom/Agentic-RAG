## Root cause (DB-verified, fully diagnosed)

The restart_smoke `--kill-at programmatic` leg FAILED: after a graceful uvicorn
shutdown (Ctrl+C / SIGINT — the same path production deploys & restarts use),
the workflow went to `failed` and the boot-time resume sweep never re-claimed
it.

Mechanism:
1. `main.py` lifespan shutdown (after `yield`) cancels every producer task
   (`RUN_TASKS` loop, main.py:280-282) → `CancelledError` into the harness
   producer.
2. The producer's CancelledError branch sets `_terminal_status='cancelled'`
   (threads.py:1379) and runs the shielded finalizer.
3. The **F2 backstop** (threads.py:1531-1546) fires on ANY non-completed
   terminal status — including this shutdown 'cancelled' — and calls
   `finish_run(pool, _active_workflow_run_id, "failed")`.
4. `finish_run` (db/workflows.py:383-410) sets `workflow_runs.status='failed'`
   **and clears `threads.active_workflow_run_id = NULL`** in one txn.
5. `find_resumable_runs` (db/workflows.py:173-202) requires ALL of:
   `status IN ('active','paused')` AND `t.active_workflow_run_id = wr.id` AND an
   `active` workflow_phases row. Step 4 destroyed the first two → **never
   resumable.**

Evidence: workflow_run `432bb144` → status=`failed`, current_phase_id=NULL,
claimed_at=NULL, phase 0 `split` left `active`, only 1 audit row
(`phase_started`). Flip to `failed` timestamped at the Ctrl+C moment, BEFORE the
restart.

Note: a HARD kill (SIGKILL) runs no code → row stays `active` → resume works.
The bug is SPECIFIC to GRACEFUL shutdown, which is exactly what dev Ctrl+C and
production restart/deploy use. This is why it matters.

## The fix (proposed — provider-uniform, Deep byte-identical)

Distinguish **app-shutdown cancellation** (should stay resumable) from
**user-Stop / crash / timeout** (should terminalize, as today).

1. **main.py**: set a process-level `SHUTTING_DOWN` flag (on `app.api.threads`
   or a small `app.state`-backed module) IMMEDIATELY before the `task.cancel()`
   loop at main.py:280, and AFTER the ask_user sentinel broadcast.
2. **threads.py F2 site (~1531)**: gate the terminalize. When
   `_active_workflow_run_id is not None` AND `_terminal_status != 'completed'`:
   - if `SHUTTING_DOWN` is True → **SKIP** `finish_run` (leave workflow_runs
     `active` + anchor intact + the active phase row) so the next-boot resume
     sweep claims and re-drives it.
   - else → terminalize to `failed` (UNCHANGED — user-Stop/crash/timeout).
3. The producer-shell `runs` row may still finalize to `cancelled` (shell is
   disposable; the resume sweep mints a fresh shell). Verify the reconcile F2
   self-heal does not read the thread as wedged while workflow_runs stays active
   (the anchor, not the shell status, governs resume).

### Safety analysis (the operator's red line)
- **Deep-mode unaffected**: F2 only runs when `_active_workflow_run_id is not
  None` (harness runs). Deep runs skip F2 entirely → byte-identical. The flag
  only gates the existing harness F2 branch.
- **All 7 providers uniform**: the fix is in the shared harness finalizer, not
  any provider branch. Sub-agents are provider-specific; this machinery is not.
- **No new stranding**: runs left `active` on shutdown are exactly what
  `find_resumable_runs` + `claim_run` + the `harness_resume_lease_seconds` lease
  already handle. A genuine crash (not shutdown) still terminalizes.

## ⚠ OPEN DESIGN QUESTION (needs operator decision before coding)

The lifespan ALSO broadcasts an **ask_user shutdown sentinel** (Phase 085
D-085-07, main.py:254-273) so paused `ask_user` runs return and finalize —
explicitly to avoid stuck `streaming` rows. This INTERACTS with leaving a
harness run resumable for the **`ask_user` kill point** (restart_smoke leg 3 /
BUG-260605-01):

- For `programmatic` and `llm_agent` kill points: NO ask_user involved → the fix
  above is clean and complete.
- For the `ask_user` kill point: the sentinel could finalize the paused
  llm_human_input phase instead of leaving it resumable for the sweep's
  `resume_pending_prompt` re-emit. Need to ensure, on SHUTDOWN specifically,
  the pending prompt stays durable + the run stays `active` so resume re-emits
  it (not finalized by the sentinel).

**Options:**
- (A) On shutdown, skip the ask_user sentinel for HARNESS runs (let them stay
  pending+active for resume); keep the sentinel for Deep runs. Cleanest split.
- (B) Keep the sentinel; ensure the harness pending-prompt row stays durable and
  the resume sweep re-creates/re-emits it regardless. More moving parts.

Recommendation: **(A)** — narrowest change, matches "harness runs resume; Deep
runs finalize."
