<objective>
Put the client's half of the governance data in place: read the server's KB tool list, carry the two
`PhaseSpec` booleans in the client's definition type, and build the caller-owned write chain that will
set them.

Purpose: D-185-09 keeps the safety-defining list in exactly one home (the server) and duplicates only
the trivial set intersection client-side, so the dial, the strike-through and the canvas seal move on the
SAME render as a tool chip — no debounce lag, no network hop for a refusal reason — while the run-time
gate stays unconditional and server-side. D-185-10 routes the write through its own narrow op because
`PhaseFormPanel`'s only write seam (`onChange: (patch: PhaseConfigPatch) => void`) patches `config`, and
these fields are siblings of `validators`. That is the same reason `PhaseGateRow.onRemove` already
belongs to the caller.

Output: `kbTools` on the palette hook's state union, two optional booleans on `PhaseSpecJSON`, one pure
`setPhaseGovernance` op, one store action, and the phase's governance copy constants — one exported
const per sentence.

This plan renders nothing. It deletes nothing. `groundingFor()` still ships (plan 185-08 removes it).
</objective>
