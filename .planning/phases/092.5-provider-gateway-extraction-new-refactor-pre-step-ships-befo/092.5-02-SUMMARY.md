## Operator-run notes / deviations

- **First eval attempt crashed (ReadTimeout) at 13/23.** Root cause investigated and
  understood (not a model-quality issue): the eval's `wait_for_run` abandons a run at
  its timeout but never cancels it server-side, and `uvicorn --reload` runs a single
  worker — so two abandoned slow Moonshot (kimi) runs pinned the lone worker and
  starved the next request. Fix applied (no script change): **restart the backend** to
  clear the abandoned streams + **`EVAL_RUN_TIMEOUT_S=600`** so slow runs complete (and
  free the worker) instead of being abandoned. Second run completed all 32 cells with
  no pileup.
- **Per-model app timeouts confirmed well-calibrated** (`config.py` `llm_call_timeout_seconds`
  4-tier 180/300/600/900): 7 of 8 eval models are 300s/call; kimi-k2.6 is 600s/call.
  These are PER-CALL; a whole run = many iterations, so the eval's whole-run ceiling is
  the tight constraint, not the app. No app-side change needed. (Deferred follow-up: if
  future evidence shows the slowest providers need more whole-run room than granted,
  revisit with real completion times — out of scope for 092.5.)
- **The proper eval-harness fix** (cancel-on-timeout in `wait_for_run`) is deferred to the
  Phase 096 eval pass — NOT touched mid-refactor (proof-apparatus stability).
