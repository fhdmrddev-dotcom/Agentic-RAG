Close **F4** — the blocker found in the 092-06 lived-experience UAT that stops a Harness workflow from running end-to-end. F4 is the last thing between this phase and MODE-01/MODE-02/CONT-01 closure.

F4 is **two facets of one defect plus its resume recurrence**: the harness engine threads the **`workflow_runs.id`** as `ctx.run_id`, but two consumer classes semantically require the **producer `runs.run_id`**:
- **Facet A (the live crash):** `run_task_sub_agent` does `insert_run(parent_run_id=parent_ctx.run_id)`; `runs.parent_run_id` FKs `runs.run_id`. The workflow_run id is not a `runs` row → `asyncpg.ForeignKeyViolationError`.
- **Facet B (confirmed sibling):** every harness `_emit` and the `ask_user_prompt` emit land on `run:{workflow_run_id}` — a stream nobody watches (the frontend subscribes `run:{producer_run_id}`). Phase/gate/sub-agent/ask_user events are invisible.
- **Facet C (resume + Continue):** BOTH resume paths feed the workflow_run id into the engine ctx and mint NO producer `runs` row → the same FK recurs on resume; neither path finalizes its (would-be) producer row → a crashed resume re-wedges the thread (defeating F2); and after a page reload `workflowLock.runId` carries the workflow_run id, so the Continue button POSTs it to `/runs/{id}/continue` whose ownership SELECT (against `runs`) 404s.

Purpose: make a Harness workflow actually run, stream, resume, and Continue end-to-end — the binding criterion that closes MODE-01/MODE-02/CONT-01. The fix is **additive + harness-scoped**: introduce a second `producer_run_id` field on the harness ctx bag and a `stream_run_id` engine arg; do NOT reassign `ctx.run_id` (the workflow_run id is legitimately required by audit / terminal / definition / resume-match consumers). Deep mode stays byte-identical.
