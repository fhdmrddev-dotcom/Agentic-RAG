## The Cut List — exact source line ranges, and whether the arithmetic works

### Method

The classifier is a 60-line Node script written for this research (scratchpad
`classify.cjs`). Rules, stated so the plan can reproduce them exactly:

- **blank** — `trim() === ""` **and not inside a block comment**
- **comment** — entirely inside `/* … */` (including blank lines within it and the `{`/`}` of a
  JSX `{/* … */}` wrapper), or a whole-line `//`
- **code** — everything else. A line with code *and* a trailing comment counts as **code**
  (conservative: it can never inflate the prose figure).

Whole file: `total=797 comment=518 code=249 blank=30 prose=65.0%`.
Region sums verify: `110 + 28 + 147 + 1 + 84 + 427 = 797` ✓.

## BUG-260806-01 — the mechanism, established from source

**Report:** `.planning/reported-bugs/BUG-260806-01-selected-card-occludes-its-own-remove-control.md`
— `severity: major`, `status: folded`, `folded_into: 188.2`, `reproduces_on: develop @ 42b9cec9`.
Carries a measured `elementFromPoint` table: 4 of 5 affordances reachable; `✕ Remove step 2` returns
`DIV.mx-auto block w-[248px] rounded-[22px] …` — the card. The distinguishing variable is
**selection** (`selected: TRUE, z-index: 1000` vs `selected: false, z-index: 0`).

The report's hypothesis is **CONFIRMED, and the mechanism is now fully traced**:

### Where `z-index: 1000` comes from

| Fact | Source |
|---|---|
| The constant | `frontend/node_modules/@xyflow/system/dist/esm/index.js:1547` — `const SELECTED_NODE_Z = 1000;` |
| Its default gating | same file `:1552-1553` — `elevateNodesOnSelect: true`, `zIndexMode: 'basic'` |
| Where it is applied | same file `:1620` and `:1700` — `const selectedNodeZ = elevateNodesOnSelect && !isManualZIndexMode(zIndexMode) ? SELECTED_NODE_Z : 0;` fed into `calculateChildXYZ` → `node.internals.z` |
| How it reaches the DOM | `frontend/node_modules/@xyflow/react/dist/esm/index.js:2343` — the node wrapper's `style` object contains `zIndex: internals.z`. **It is an INLINE STYLE, not a class and not shipped CSS.** |
| Package versions | `@xyflow/react 12.11.2` · `@xyflow/system 0.0.79` (`node -p require(...).version`) |

### Why the affordance loses

| Element | Rule | Source |
|---|---|---|
| `.react-flow__viewport` | `transform-origin: 0 0; z-index: 2;` **plus an INLINE `transform`** | `@xyflow/react/dist/base.css:88-91`; the inline transform at `.../esm/index.js:3073` |
| `.react-flow__nodes` | `pointer-events: none; transform-origin: 0 0;` — **NO `position`, NO `z-index`** ⇒ static ⇒ **creates no stacking context** | `base.css:174-177` |
| `.react-flow__node` | `position: absolute;` + the inline `zIndex` above | `base.css:178-187` + `esm/index.js:2343` |
| `.react-flow__viewport-portal` | `position: absolute; width/height:100%; left/top:0;` — **NO `z-index`** ⇒ `auto` | `base.css:301-310` |
| DOM order inside the viewport | EdgeRenderer → ConnectionLine → `edgelabel-renderer` → **NodeRenderer** → **`viewport-portal` (LAST)** | `esm/index.js:3256` |

**The resolution.** `.react-flow__viewport` has a `transform`, so it establishes the stacking
context both live in. `.react-flow__nodes` is unpositioned and therefore transparent to stacking, so
each `.react-flow__node` participates **directly** in the viewport's context at its own inline
`z-index`. The portal participates at `auto`.

- **Deselected** — node `z-index: 0`, portal `auto`. Tie on z; the portal is **later in DOM order**
  ⇒ the `✕` paints on top ⇒ **reachable** ✓
- **Selected** — node `z-index: 1000` > portal `auto` ⇒ the **card paints over the `✕`** ⇒
  **unreachable** ✓

This reproduces the report's measured table exactly, from source, with no live measurement needed.

### The affordances carry no z-index today

`PlaneEditingLayer.tsx` renders three element groups inside `<ViewportPortal>` (`:144`), rendered
from `WorkflowCanvas.tsx:1266`:

- the `＋` buttons (`:146-182`) — `className` includes Tailwind `absolute`; inline `style` is
  `{ left, top, width, height, transform }` — **no `zIndex`**
- the `✕` buttons (`:186-225`) — same shape — **no `zIndex`**
- the picker wrapper (`:229-264`) — `className="pointer-events-auto absolute"` — **no `zIndex`**

### The minimal fix

Because `.react-flow__viewport-portal` is **not** a stacking context (`z-index: auto`), a positioned
child with an explicit `z-index` escapes into the viewport's context and competes directly with the
node's 1000. So the fix is **one property on the affordance elements**, not a change to the portal
container and certainly not to the card:

```ts
// editAffordance.ts — the number gets a NAMED home beside the geometry it belongs with
/** Above @xyflow's SELECTED_NODE_Z (1000, @xyflow/system:1547, applied inline at
 *  @xyflow/react:2343). The portal container carries no z-index (base.css:301) so a
 *  positioned child escapes into the viewport's stacking context and wins outright. */
export const AFFORDANCE_Z = 1002
export const SELECTED_NODE_Z_FROM_LIBRARY = 1000   // the number we must beat, named not implied
```

…then `zIndex: AFFORDANCE_Z` added to each of the three inline `style` objects in
`PlaneEditingLayer.tsx`. **Three lines of change in one file, plus two constants.** G-3 would size
that `/gsd:fast`; D-10 overrides with a recorded reason.

**Pick 1002, not 1001.** `svg.react-flow__connectionline` is pinned at **`z-index: 1001`**
(`base.css:170`). This canvas draws no connection line today, but colliding with a library layer for
no benefit is free to avoid.

**Fix all three groups, not just the `✕`.** The report's table shows the `＋` buttons reachable —
but only because no node adjacent to them was selected. A selected card would occlude a nearby `＋`
by the same mechanism. Fixing one and leaving two is fixing the symptom.

### D-11's unit half — the two numbers that must be NAMED


**jsdom cannot see occlusion** (no layout, no stacking contexts, and `.click()` bypasses

2. Assert `SELECTED_NODE_Z_FROM_LIBRARY === 1000` is still what the library uses — a positive

## Common Pitfalls

### Pitfall 1: A re-scoped fence that was never observed RED
**What goes wrong:** the fences are re-pointed at `cardSubtreeSource` and everything stays green,
so nobody notices that a typo'd path, a truncated list, or a glob that resolved to nothing has made
all seventeen vacuous.
**Why it happens:** a green negative assertion is indistinguishable from a green vacuous one.
**How to avoid:** 188.1's three non-vacuity controls, verbatim — length pin **and** per-destination
`toContain` **and** resolved-module non-empty. The substitution guard was measured RED at 188.1
precisely because a length pin alone did not catch it.
**Warning signs:** the phase's Wave 0 commit message does not name a RED observation.

### Pitfall 2: Re-pointing a *scoped* fence at the wrong haystack
**What goes wrong:** `PhaseNodeCard.test.tsx:1097` (`block.length < haystack.length / 4`) is
re-pointed at `NodeCornerMarks?raw`; the 56-line seal block is ~39 % of a ~145-line file ⇒ RED, and
the fix looks like "loosen the bound."
**How to avoid:** the haystack is the **joined subtree source**, always — the block is then ~7 %.
**Warning signs:** any proposal to change `/ 4` to `/ 2`.

### Pitfall 3: Rewriting the seal's guard shape during the move
**What goes wrong:** `NodeCornerMarks` renders the seal via an early `if (!grounded) return null`
instead of `{grounded ? ( … ) : null}`. `sealJsxBlock` anchors on those two exact literals
(`:1046-1047`) and **throws**.
**How to avoid:** the move is verbatim. 188.1's measured result was *byte-identical moved bodies*;
target the same here (see §Validation Architecture for the honest caveat about the docblock).

### Pitfall 4: The clip count satisfied by shuffling prose
**What goes wrong:** the `CLIP_UTILITY` count is re-anchored per-file rather than to the subtree, so
a later edit that moves the sentence between two files keeps every per-file count "correct."
**How to avoid:** D-08's decision — `cardSubtreeSource.split(CLIP).length - 1 === 1`. It stays 1
wherever the rule lives, and cannot be gamed by relocation.

### Pitfall 5: The D-09 control that fails for the wrong reason
**What goes wrong:** `noUnusedLocals: true` makes the unused `const three` its own error, so `tsc`
reports 34 whether or not the union is narrow.
**How to avoid:** consume the value, or `void three`. Observe the RED against the **widened union**
specifically, and confirm the count returns to exactly **33** with the union intact.

### Pitfall 6: Exporting a runtime constant from a component module
**What goes wrong:** `NodeRunOverlay.tsx` exports `RING_STROKE` "so the test can read it" ⇒
`react-refresh/only-export-components` fires ⇒ the directory's eslint count goes **5 → 6**, undoing
the only measurable lint win the phase could bank. `PlaneEditingLayer.tsx:25-30` records exactly
this, and `FlowEdge.tsx:147` and `BuilderStoreProvider.tsx:45,53,78` are four live instances of it.
**How to avoid:** the three PascalCase modules export **the component and its props type and nothing
else**. Runtime values live in camelCase `.ts` leaves. **Type-only exports are exempt** — verified
empirically: `PhaseNodeCard.tsx` exports six types plus one component and has zero eslint errors.
**Warning signs:** any `export const` in a `.tsx` file created by this phase.

### Pitfall 7: Letting the card acquire derivation on the way out (red line D-14)
**What goes wrong:** `NodeRunOverlay` "helpfully" maps a raw `workflow_phases.status` to a reading,
or `NodeCornerMarks` derives a severity. The card becomes a deriver instead of a projection.
**How to avoid:** the new modules take **already-derived** props (`reading: CanvasReading`,
`verdict: NodeVerdictMark`) exactly as the card does. The one derivation lives in
`frontend/src/lib/phaseState.ts` and is fenced by `phaseState.test.ts` (pinned at 34) as Req 8's
zero-re-derivation source fence.
**Warning signs:** any new import of `@/lib/phaseState`'s *functions* (as opposed to its `CanvasReading`
type) into the workflows tree.

### Pitfall 8: One half's UAT evidence standing in for the other's
**What goes wrong:** the driven `elementFromPoint` row for the bug fix is recorded as also proving
"the card is unchanged," because both were observed in the same browser session.
**Why it happens:** Phase 188's own failure mode (`feedback_uat_rows_need_their_own_evidence`) —
a header read COMPLETE while rows 12-17 read `[pending]`.
**How to avoid:** two boards with disjoint evidence columns; see §Validation Architecture.

### Pitfall 9: Driving the board against a stale bundle
**What goes wrong:** Vite HMR keeps the pre-move module graph; the driven row measures the old code.
**How to avoid:** hard reload before the first driven row (`reference_hmr_provider_change_stale_code`).
**Warning signs:** a driven row that passes before the fix commit was even written.

## Open Questions

1. **Does `own<T>()` get a brand-new module, or fold into `nodePresentation.ts`?**
   - Known: `nodePresentation.ts` (216 L, camelCase, `.ts`, already exports constants and
     `renderPhaseMark`) is imported by `NodeCornerMarks` anyway for `VERDICT_MARK`. Its fences
     (`:437-471`) are anchored on `ICON_TINT` / `DEFAULT_TINT` / `renderPhaseMark` / `GROUNDING_TONE`
     identifiers, so adding `own` breaks none of them. Verified.
   - Unclear: whether `NodeRunOverlay` importing from `nodePresentation` (a module about *marks*)
     just for a lookup helper is a seam anybody wants.
   - Recommendation: **a new ~35-line camelCase leaf.** D-05 already leans this way; it keeps each
     new module's import list honest about what it depends on, and 25 L of moved source does not
     justify coupling the run overlay to the presentation table.

2. **How many destination paths does `CARD_SUBTREE_PATHS` name — 5 or 6?**
   - Known: 5 if `own()` folds into `nodePresentation.ts` (already a separate, separately-fenced
     module and arguably outside the "card subtree"); 6 if it gets its own leaf.
   - Recommendation: name **exactly the files this phase creates, plus `PhaseNodeCard.tsx`** —
     do not pull `nodePresentation.ts` or `runVocabulary.ts` into the subtree. Both have their own
     fences (`PhaseNode.test.tsx:431-473`, `PhaseNodeCard.test.tsx:437-471`) and widening the
     haystack would make a negative fence go red for reasons unrelated to the card — D-07's own
     stated reason for rejecting the whole-directory sweep.

3. **Does `PhaseNodeCard.tsx` keep the `status`/`arc` derivation, or does `NodeRunOverlay` take
   `reading` and compute internally?**
   - Known: `runBorder` and `minHeight` are consumed by the CARD and must stay. `arc` is consumed
     only by the ring.
   - Unclear: whether moving `arc` inside the overlay counts as "acquiring derivation" under D-14.
   - Recommendation: **it does not** — `ringDash(ringSpecFor(reading), C)` is a pure geometry
     computation over an already-derived reading, not a run-state derivation. D-14 forbids deriving
     *what state a step is in*; the ring computing its own dasharray from a given reading is exactly
     what `runVocabulary` already exists for. Move it, and say so in the plan so a reviewer does not
     read it as a D-14 breach.

4. **Is `AFFORDANCE_SHAPE_BASELINE`'s re-capture in scope for the phase's "prove unchanged" claim?**
   - Known: the fix changes it by construction; the literal's own docblock forbids updating it.
   - Recommendation: state it in the BUG plan as **the one authorised exception**, quoting the
     docblock rule and the reason it does not apply here (the change *is* the deliberate behaviour
     change contract B exists for). Never edit it silently.
