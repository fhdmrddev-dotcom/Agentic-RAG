### WR-02: The ESM-cycle fence is evaded by an explicit `.tsx` extension, which this repo's tsconfig allows

**File:** `frontend/src/components/workflows/PhaseNodeCard.test.tsx:592-593` (and the
`it(` at `:620-635` that consumes them)

**Issue:** SC#3's only mechanical protection against the value-level cycle is:

```ts
const IMPORT_FROM_CARD = /from\s+["'][^"']*PhaseNodeCard["']/
const DYNAMIC_IMPORT_CARD = /import\s*\(\s*["'][^"']*PhaseNodeCard["']\s*\)/
```

Both require the quote to close **immediately** after `PhaseNodeCard`. `tsconfig.app.json`
sets `"allowImportingTsExtensions": true` and `"moduleResolution": "bundler"`, so
`import { PhaseNodeCard } from "./PhaseNodeCard.tsx"` typechecks, and Vite resolves it.
Measured against the two regexes:

```
CAUGHT  import { PhaseNodeCard } from "./PhaseNodeCard"
EVADES  import { PhaseNodeCard } from "./PhaseNodeCard.tsx"
EVADES  import type { PhaseNodeCardProps } from "@/components/workflows/PhaseNodeCard.tsx"
EVADES  const m = await import("./PhaseNodeCard.tsx")
EVADES  export { PhaseNodeCard } from "./PhaseNodeCard.tsx"
```

So a future editor closing the cycle with an extension-suffixed specifier gets a green
suite, a green `tsc`, a green `eslint` — and the TDZ `ReferenceError` at runtime that the
fence's own docblock (`:571-578`) says no build tool in this repo can see. The
`it("no extracted module names a PhaseNodeCard specifier in ANY import form")` title
overstates what it checks. (The 188.1 sibling fence in `WorkflowCanvas.test.tsx` has the
same shape and the same hole; fix both together.)

**Fix:** Make the extension optional in both needles, and add the evading form as an inline
positive control so the widening cannot regress:

```ts
const IMPORT_FROM_CARD = /from\s+["'][^"']*PhaseNodeCard(\.tsx?)?["']/
const DYNAMIC_IMPORT_CARD = /import\s*\(\s*["'][^"']*PhaseNodeCard(\.tsx?)?["']\s*\)/
// …in the controls block:
expect('import { PhaseNodeCard } from "./PhaseNodeCard.tsx"').toMatch(IMPORT_FROM_CARD)
expect('export { X } from "@/components/workflows/PhaseNodeCard.ts"').toMatch(IMPORT_FROM_CARD)
// the two NEGATIVE controls must still miss:
expect('import s from "./PhaseNodeCard?raw"').not.toMatch(IMPORT_FROM_CARD)
expect('import { own } from "./phaseNodeCardContract"').not.toMatch(IMPORT_FROM_CARD)
```

`"./PhaseNodeCard?raw"` still misses (`?` is not `.tsx`), so this file's own line 37 stays
legal.

### WR-03: `verticalOffsetFor` reads two author-keyed tables through the prototype chain — a sixth, unguarded WR-04 sink

**File:** `frontend/src/components/workflows/editAffordance.ts:220-224`

**Issue:** This tree treats prototype-chain reads on plain object literals as a real defect
class and guards five named sites (`ICON_TINT`, `PHASE_TYPE_LABEL`, `STATUS_META`,
`VERDICT_MARK`, `RING_STROKE`), each with a falsification observed RED. `verticalOffsetFor`
is a sixth sink of the same shape and is unguarded:

```ts
const live = overlay[slug]
if (live !== undefined) return live.y - laneY
return nudges?.[slug] ?? 0
```

`overlay` (`dragOverlay`) and `nudges` are `Record<string, …>` plain objects, and `slug` is
a workflow-definition phase slug — author-supplied JSONB with **no pattern constraint**
(`backend/app/models/harness.py:202` is a bare `slug: str`; there is no slug regex anywhere
in `backend/app`), and it is also what the AI seed door writes. With `slug === "constructor"`:
`overlay["constructor"]` is the `Object` **function** — never `undefined`, so the guard
passes — `live.y` is `undefined`, and the function returns `NaN`. `"__proto__"` behaves the
same way. The `?? 0` on the `nudges` line does not fire either, for the identical reason.

Consequence at the three call sites (`PlaneEditingLayer.tsx:176-177`, `:225`, `:256-262`):
`transform: translate(…px, NaNpx)` is an invalid CSS value, so the browser drops the whole
declaration and the `✕` / `＋` / picker for that step collapse onto the viewport origin
instead of onto their card — and, now that they carry `zIndex: 1002`, they land there
*above* the cards rather than behind them. Silent: jsdom applies no CSS, so no unit test in
this estate can see it, and the `AFFORDANCE_SHAPE_BASELINE` capture uses only well-formed
slugs.

This is pre-existing (moved verbatim by 188.1-03), but `editAffordance.ts` is a file this
phase edited and is in review scope, and it is the one remaining hole in a mitigation the
phase's own `ownProperty.ts` docblock enumerates by site.

**Fix:** Use the leaf this phase just created — it takes zero imports, so
`editAffordance.ts → ownProperty.ts` opens no cycle:

```ts
import { own } from "@/components/workflows/ownProperty"

export function verticalOffsetFor(
  slug: string | undefined,
  nudges: Record<string, number> | undefined,
  overlay: Record<string, XYPosition>,
  laneY: number,
): number {
  if (slug === undefined) return 0
  const live = own(overlay, slug)
  if (live !== undefined) return live.y - laneY
  return (nudges === undefined ? undefined : own(nudges, slug)) ?? 0
}
```

Falsify first: drive `PlaneEditingLayer` with `phaseOrder: ["constructor"]` and assert the
rendered `style.transform` contains no `NaN`; observe it RED against HEAD before the guard
lands. (`ownProperty.ts:35-38` currently lists four inline own-guards that "stay where they
are" — add this one to that list, or note it as the fifth.)

### IN-03: The z-fix rests on three premises; only one of them is guarded by a test

**File:** `frontend/src/components/workflows/editAffordance.ts:170-174`,
`frontend/src/components/workflows/WorkflowCanvas.editing.test.tsx:733-782`

**Issue:** `AFFORDANCE_Z`'s docblock says the mechanism is *"checked by machine, not by this
paragraph … so a version that changes `SELECTED_NODE_Z` turns a test red instead of silently
re-opening the bug."* The suite checks two of the three load-bearing facts — the
`1002 > 1000` relation, and the library's live elevation off a rendered selected node — but
**not** the third, which is equally load-bearing and equally version-dependent: that
`.react-flow__viewport-portal` opens **no stacking context**. I confirmed it does not today
(`@xyflow/react@12.11.2` `base.css:301-310`: `position: absolute`, no `z-index`, no

1000 while all three assertions stayed green.

**Fix:** Add a fourth case in the same block reading the property off the really-rendered
portal, so an upgrade that closes the escape hatch reds a test:

```ts
it("the viewport portal opens NO stacking context — the premise 1002 relies on", () => {
  const { container } = renderEditable(evalCoverage)
  const portal = container.querySelector<HTMLElement>(".react-flow__viewport-portal")!
  const cs = getComputedStyle(portal)
  expect(cs.zIndex).toBe("auto")   // a positioned, z-index:auto element is not a context
  expect(cs.isolation).not.toBe("isolate")
})
```

(jsdom does apply the library's own stylesheet if it is imported in the test setup; if it is
not, assert on the parsed `base.css` text instead — the point is that the premise gets a
