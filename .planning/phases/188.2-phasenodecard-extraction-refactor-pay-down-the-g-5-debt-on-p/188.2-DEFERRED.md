## D-188.2-DEF-01 — the count gate's `failed` line is not a usable regression backstop on this machine today

**Status:** LOGGED, NOT FIXED. This is a *finding of this phase*, not noise.

**What was measured.** Across two back-to-back runs of `node scripts/vitest-count-gate.cjs` in this
plan, with **identical per-file `actual` columns and an identical `total` of 2502**, the `failed`
line read:

```
run 1 (2026-08-07)   total 2502  ·  failed 1  ·  pinned total 2482   → RESULT: COUNT GATE VIOLATED [failing-tests]
run 2 (2026-08-07)   total 2502  ·  failed 0  ·  pinned total 2482   → count gate OK
```

Run 1's single failure, extracted from the gate's own JSON report rather than guessed:

```
FILE: frontend/src/pages/WorkflowBuilderPage.canvas.test.tsx
  - WorkflowBuilderPage 184-11 — with the flag OFF the panel receives NO rails key (D-14)
    POSITIVE CONTROL — with the flag ON the very same read finds the key
    AssertionError: expected 0 to be greater than 0
```

Driven in isolation immediately afterwards: **`Tests 128 passed (128)`, exit 0.** **No Phase-188.2
plan touches that file** — it appears in no `files_modified` in this phase.

**The wider evidence, from the orchestrator's own tally (2026-08-07):** across eight full runs on
this machine the TOTAL was stable and moved only by exactly what each plan added, per-file counts
intact, while the FAILURE count varied **1 → 21 → 50 → 10 → 0 → 0**. Every observed failure was
`Axe is already running` (the axe-core module singleton colliding across concurrent vitest workers)
or `Test timed out in 5000ms`, in files no 188.2 plan touches — `PhaseTimeline.test.tsx`,
`WorkflowCanvas.test.tsx`'s a11y block, `PhaseNode.test.tsx` — and every affected file passes in
isolation. This matches the pre-existing rot recorded as **SEED-056**, at a materially higher count
than the ~14–17 that seed records.

**Why deferred:** the operator decided on 2026-08-07 to **continue on SCOPED per-file gates and not
fix the flakiness in this phase**. Fixing it is a test-infrastructure change (worker isolation, or
an axe-core teardown, or `pool: "forks"`) touching a suite this phase has no other business in, and
it would be a *capability* of the test estate rather than the debt this phase was opened to pay.

**What is still sound, stated precisely so this is not read as "the gate is broken":** the gate's
**COUNT** columns — the `[count-decrease]`, `[missing-file]` and `[total-below-baseline]` reasons —
were stable across every run and remain the regression backstop the script exists to be. It is the
`[failing-tests]` reason alone that is unreliable here.

**Re-open trigger:** the gate reports `[failing-tests]` naming a file that a plan in the *current*
phase actually modified; **or** any phase with a stated CI objective (today
`.github/workflows/frontend-tests.yml` runs `lint:a11y` only, so this does not gate CI); **or** the
`failed` count is observed non-zero on a run whose per-file `actual` columns have also moved, which
would mean the two symptoms are not independent after all.
