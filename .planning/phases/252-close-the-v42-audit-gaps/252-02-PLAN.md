<objective>
Stop the credential boundary leaking in two directions at once: **out** to the application log, and
**in** past the validator via a writer that no request model guards.

Purpose: **SC#2 and SC#3.** Phase 248 tightened `custom_client_id` so a pasted secret is refused
rather than stored in an org-readable column. Two seams defeat it. `connector_service.py:578-581`
logs the raw pydantic `ValidationError`, whose `__str__` echoes `input_value` on every union arm —
**measured at six occurrences of the secret in one message** — and the population that fallback
exists for is *precisely the legacy rows that already hold a secret there*. ⛔ **The phase moved the
secret out of a readable column and into the log.** Meanwhile `connectors.py:1326-1352` takes a
`client_id` from a **remote server's response** and writes it unvalidated, and once stored it fails
`model_validate` on every read — `status="error"` forever.

⭐ **TM-248-06 is satisfied by the validator's own message and defeated by a handler three files
away.** The validator's docstring literally promises *"Does NOT echo the rejected value … to prevent
credential leakage"*, and keeps that promise.

Output: one changed log call, one validation at the single write seam, one named refusal, one
repair sentence, and four driven tests.
</objective>

`connector_service.ConnectorClientIdRefused(ConnectorError)`
  Raised by `store_oauth_client_credentials` when the `client_id` offered fails the shipped
  `_validate_custom_client_id`. ⛔ Its message NAMES THE RULE THAT FAILED and **never the value** —
  same contract as the validator it wraps (TM-248-06).

  ⚠ It subclasses `ConnectorError`, so **every existing `except ConnectorError` arm in
  `connectors.py` already catches it** (`:1063`, `:890`, `:924`). That is why the DCR block must
  catch it **by name, ahead of** those — the `ConnectorNothingToDiscover` comment at `:1060` records
  this exact ordering trap, in this exact file.
