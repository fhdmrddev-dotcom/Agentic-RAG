The `BaseException` catch is unchanged in the latest version; only a `_cleanup_traceback(e)` cosmetic call was added. **Recommendation: Plan 01 pivots to a 3-track decision tree (re-architect to bypass the wrapper for the timeout path / retire the invariant / suppress at trace-emit time).** See Plan 01 Recommended Approach below.

**STANDARD-CONFIDENCE:** Plans 02–04 are well-scoped UX/prompt work with clear surfaces (`api.ts` SSE event mapper for Plan 02; `threads.py:156-257` `SYSTEM_PROMPT` for Plan 03; `ToolCallPanel.tsx:506-525` `SkillRow` for Plan 04). Plan 05 is a UAT harness re-running two protocols with explicit Chrome MCP + Supabase MCP + LangSmith MCP capture steps.

**Primary recommendation:** Begin Plan 01 as a **time-boxed audit (≤ 2h)** that validates the architectural conclusion above against the live `_TracedStream.__iter__` source in `backend/venv/Lib/site-packages/langsmith/run_helpers.py:1678-1685`. ### Pattern 1 (Plan 01 Recommended Approach): Three-Track Decision Tree

**What:** Plan 01 must choose ONE of three tracks. Pick after a ≤2h time-boxed validation step that confirms the langsmith-py BaseException-catch behavior on the project's actual installed version.

**Track A — Re-architect (PREFERRED, MEDIUM EFFORT, HIGH PAYOFF):** Replace the inline `for chunk in stream:` with a helper that drains the stream into a list-or-generator OUTSIDE the `asyncio.timeout` window, then iterates the list under timeout. The langsmith trace closes cleanly because `_TracedStream.__iter__` runs to completion (StopIteration via the `else` branch); our timeout fires while iterating an in-memory list, so the only thing the timeout cancels is our own list iteration — no `GeneratorExit` is sent to langsmith.

```python
# Source: novel pattern derived from langsmith run_helpers.py:1678-1685 inspection
# Drain inside timeout — but consume from a wrapper that swallows mid-stream cancel
async def _drain_stream_with_close_on_cancel(stream, timeout_seconds: float, on_chunk):
    """Iterate the langsmith-wrapped stream; on cancel, call stream.close() BEFORE
    Python's implicit gen.close() runs. Trick: we own the iteration, so we can
    close the underlying object first and let `__iter__` see a clean StopIteration
    instead of GeneratorExit-from-outside.
    """
    try:
        async with asyncio.timeout(timeout_seconds):
            for chunk in stream:
                on_chunk(chunk)
    except (asyncio.TimeoutError, asyncio.CancelledError):
        # Close the underlying SDK stream BEFORE our `for` loop's implicit close
        # propagates GeneratorExit into _TracedStream.__iter__. The SDK's stream
        # ends; __iter__ sees StopIteration via `__ls__gen__` ending, takes the
        # `else: self._end_trace()` branch (no error), then raises StopIteration
        # which yields-from converts to clean exit. Our re-raise propagates the
        # TimeoutError unchanged.
        try:
            stream.close()  # OpenAI Stream — sync per openai 2.28.0
        except Exception:
            logger.debug("stream.close() raised — non-fatal", exc_info=True)
        raise
```

CRITICAL CAVEAT: this pattern is **already what threads.py:1297-1340 implements** at first glance. Why does it still produce GeneratorExit in the live trace? Because `stream.close()` is called AFTER `raise` enters the `except` block — by which point `for chunk in stream:` has ALREADY received the cancellation, ALREADY exited, and ALREADY triggered the implicit `gen.close()` on the langsmith wrapper. **The fix is to close the stream FROM INSIDE the `for` loop (e.g. via a sentinel chunk), or to abandon the `for` loop and use explicit `next(iter)` with a check between iterations** — neither is trivial.

**Track B — Retire D-066-11 (LOW EFFORT, LOWEST RISK):** Document in 067.1-CONTEXT.md and 066-HUMAN-UAT.md that langsmith-py 0.2.3..0.8.2's `_TracedStream.__iter__` records `GeneratorExit` from external generator-cleanup, by design. Update the SC#1 wording to: "LangSmith ChatOpenAI sub-trace shows the run was cancelled — exception type is `GeneratorExit` (langsmith-py library behavior on async cancellation) AND the Supabase `runs` row records `status='timed_out'` with the formatted error string." The user-facing UX is already 4-of-5 green; this is a trace-hygiene cosmetic.

**Track C — Suppress at trace-emit time (HIGH EFFORT, HIGH RISK):** Monkey-patch `_TracedStream._end_trace` to filter `error=GeneratorExit` and re-emit as `error=None`. Brittle (breaks on langsmith upgrade), opaque (future readers wonder why traces are weirdly clean), and silently masks legitimate cancellations.

**When to use:** Run the time-boxed validation (1) reproduce the failure with a synthetic test (`test_066_langsmith_clean.py` is already in tree at backend/tests/integration); (2) if Track A's "from-inside-the-loop close" pattern works in isolation, ship Track A; (3) if not, ship Track B with explicit retirement note. **Do NOT default to Track C.**

**Recommended:** **Track A primary, Track B fallback, time-box: 2h on Track A's prototype.**

## Common Pitfalls

### Pitfall 1: Track A close-from-inside-the-loop subtlety (Plan 01)

**What goes wrong:** A naive Track A implementation looks like:
```python
async with asyncio.timeout(per_call_budget):
    for chunk in stream:
        ...  # process chunk
# Cleanup is in the except block — TOO LATE
```
The `for chunk in stream:` is the loop that triggers the implicit `gen.close()` on `_TracedStream.__iter__`, regardless of whether `stream.close()` is called inside the except handler.

**Why it happens:** Python's `for` loop semantics: when the body raises, the loop's exit calls `iter.__del__` / `gen.close()` AS PART OF THE LOOP'S OWN CLEANUP. By the time control reaches `except asyncio.TimeoutError:`, `_TracedStream.__iter__` has already received GeneratorExit and already called `_end_trace(error=GeneratorExit)`.

**How to avoid:** The fix must close the underlying SDK stream BEFORE the langsmith wrapper's `__iter__` generator sees a `close()`. One pattern: drain the stream into a queue inside a separate task, and iterate the queue in the timeout-bound loop. The queue-fill task can be cancelled cleanly by us via `task.cancel()` + `await task` with explicit handling, BEFORE the langsmith generator ever sees a close. Complex. **This is why Track A is risk-flagged in the recommendation.**

**Warning signs:** First Plan 01 prototype passes locally (no GeneratorExit) but only because the test mock doesn't go through `wrap_openai`. Always validate against `test_066_langsmith_clean.py` style integration test that exercises the real langsmith path.

### Pitfall 2: Pre-streaming "Setting up agent" copy disappearing too late (Plan 02)

**What goes wrong:** "Setting up agent…" copy lingers visibly for 1-3s before first delta, then SNAPS to the next state. Users notice the snap.

**Why it happens:** State transition is event-driven (iteration_start arrives → derive new copy → setMessages). Single-frame transition.

**How to avoid:** Use the same `animate-fadeSlideUp` Tailwind class that's already on the existing placeholders [VERIFIED: MessageItem.tsx:119]. The animation is ~200ms; perceived as a smooth crossfade.

**Warning signs:** UAT screenshot shows two stacked placeholder messages mid-transition. Avoid by ensuring the outer placeholder is one element with a key tied to the active state — React replaces in place.

### Pitfall 3: System-prompt growth eroding context budget (Plan 03)

**What goes wrong:** The new "Multi-step intent recognition" section adds ~250 tokens to every chat completion. Across long conversations, this compounds against the model's context window.

**Why it happens:** The system prompt is sent on EVERY iteration (stateless completions per CLAUDE.md line 21). 250 tokens × N iterations × M turns = real token cost.

**How to avoid:** (a) Be terse — the recommended draft above is ~200 tokens, can probably be tightened to 150. (b) Verify the prompt is NOT redundantly injected per iteration (it's set once per agent_runner invocation at threads.py:1027 — verified safe). (c) Trim other parts of the existing prompt if possible — the "## Tool selection guide" section at threads.py:174-201 is dense with mostly-known information that gpt-5.4 doesn't need every turn.

**Warning signs:** Plan 05 runs hit context-window errors on long Fahed Mrad chats. Mitigation: Phase 51's context-window management already trims; the addition shouldn't tip it over.

### Pitfall 4: Skill description field empty / null (Plan 04)

**What goes wrong:** `skill.description` column is nullable; if a skill was created without a description, the SkillRow card renders `Loading skill "X" — `  (trailing em-dash, empty hint).

**Why it happens:** [VERIFIED: skills table schema allows null description per backend/app/models]. Existing skill creation paths populate it but historical rows may have empties.

**How to avoid:** Frontend conditional render: `{activation.description && <span>...</span>}` (already in the recommended snippet above). Backend additionally guards: emit description only if non-empty/non-null.

**Warning signs:** UAT run with a skill missing description shows truncated "Loading skill 'docx' —" copy.

### Pitfall 5: Plan 05 Fahed-Mrad runs hitting per-call timeout instead of validating pipeline behavior (Plan 05)

**What goes wrong:** The synthetic-timeout protocol from Phase 067 set `LLM_CALL_TIMEOUT_OVERRIDES=gpt-5.4=10`. If that env var is left in `.env` when running Plan 05's pipeline-execution test, the 5 runs will all time out and fail to verify SC#3.

**Why it happens:** `backend/.env` is gitignored; revert state depends on operator memory.

**How to avoid:** Plan 05 task list MUST explicitly check `cat backend/.env | grep LLM_CALL_TIMEOUT_OVERRIDES` and confirm it is absent (or commented out) BEFORE the SC#3 5-run sequence. The Phase 067 SUMMARY 04 confirmed this revert was done; re-verify.

**Warning signs:** First Plan 05 run terminates in <15s with `timed_out` runs.status. STOP, restore env, restart uvicorn, retry.

### Pitfall 6: SC#6 regression check missing the `data-iteration` attribute (Plan 05)

**What goes wrong:** Plan 02's copy edits accidentally remove the `data-iteration` attribute from `iteration-divider`. UX-067-05 silently regresses; Plan 05 misses it because the regression check only looks at "divider count >= 1".

**How to avoid:** Plan 05's UX-067-05 regression check copies the EXACT verification from 067-HUMAN-UAT.md SC#5: `data-iteration="1"` AND `Step 2` text AND `panel.children[0]?.getAttribute('data-testid') !== 'iteration-divider'`. Don't simplify.

### Known Threat Patterns for FastAPI + React + LangSmith

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Information disclosure via SSE payload (Plan 04) | Information Disclosure | Only emit description, not instructions. Description is short metadata; instructions can contain arbitrary content. |
| Cross-user skill description leak | Information Disclosure | Existing RLS filter + ownership-scoped query; don't change |
| Prompt injection via skill description | Tampering / Spoofing | Skill description is user-authored; rendered as text in React JSX (auto-escaped). Backend doesn't re-inject description into LLM context — only into the SSE event payload |
| Trace data leak (Plan 01) | Information Disclosure | LangSmith traces are operator-scoped (project-level API key). The GeneratorExit symptom doesn't itself leak data — it's a trace-hygiene cosmetic. Track B retirement explicitly documents this acceptance |
| System-prompt regression introducing destructive autonomy | Elevation of Privilege / Tampering | Plan 03's "EXCEPTIONS" sub-section explicitly preserves confirmation for destructive/irreversible. No destructive tools exist today (no `delete_document` etc.); guardrail is forward-looking |
