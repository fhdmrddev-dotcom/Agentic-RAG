<objective>
Surface the upcoming-skill purpose on the SkillRow tool card so users understand WHY a skill is being loaded ("Loading skill 'docx' — Generate Word documents from structured data") rather than perceiving "skill loaded but code not yet executed" as out-of-order. CONTEXT.md identifies this as a deep-UAT finding from the 2026-05-07 Fahed-Mrad multi-tool run: when `load_skill` fires before `execute_code`, the bare card stands alone without context.

Architectural constraint (RESEARCH.md § Pattern 4): At `_emit('skill_activated')` emit time (threads.py:1620), the agent has just CALLED `load_skill` and is awaiting the tool result. The "upcoming tool" is NOT YET KNOWN — the agent will see the skill instructions, then decide what tool to call next. Therefore the hint comes from skill METADATA (the `description` column already populated and RLS-filtered), NOT from upcoming-tool prediction.

Purpose: Extend the existing `_emit('skill_activated')` dispatch with a follow-up `_emit('skill_loaded', skill_name, description)` event AFTER the skills DB query, carrying the skill's description as a hint. Keep the early skill_activated emit so the card appears immediately on tool_start (no delay waiting for DB). Frontend SkillRow conditionally renders the description as an italic suffix span (Pitfall 4 guard against empty description).

Output: A backend SSE event payload extension (1 new emit call), frontend type extension (1 optional field), api.ts dispatch wiring (1 new branch), useMessages.ts handler (updates the streaming message's SkillActivation entry), and SkillRow render extension (`data-testid` + copy change + conditional description span). The `instructions` field is NEVER emitted (V7 mitigation — only `description`).
</objective>

async def _emit(redis, run_id, type: str, **fields) -> None:
    """One canonical XADD shape for all producer-side events (D-061-10)."""
    await redis.xadd(

        {"data": json.dumps({"type": type, **fields})},
        maxlen=10000,
        approximate=True,
    )
