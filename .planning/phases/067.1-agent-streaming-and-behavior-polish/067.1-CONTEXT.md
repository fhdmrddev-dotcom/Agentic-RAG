## Scope (4 plans + closing UAT)

### Plan 01 — D-066-11 stream-close-on-timeout fix (Gap-007 closure)

**Owner area:** backend/agent_runner.py + langsmith @traceable interaction
**Failure mode:** When the per-call `asyncio.timeout` fires, the LangSmith
ChatOpenAI sub-trace records `GeneratorExit` at `run_helpers.py:1680`
(`yield from self.__ls__gen__`) instead of a clean `TimeoutError`. Phase 066
D-066-11 was supposed to make `stream.close()` run cleanly *before* the
timeout cancellation propagates into the langsmith decorator's async generator
wrapper.

**Live reproducer (from Phase 067 Plan 05 Task 4 — 2026-05-07):**
- Set `LLM_CALL_TIMEOUT_OVERRIDES=gpt-5.4=10` in `backend/.env`
- Restart uvicorn
- Submit a slow long-form prompt (e.g. "Write a 5000-word essay…")
- Per-call timer fires at iteration 0
- Supabase `runs` row: `status='timed_out'`, `error='timed_out: 10s per-call deadline exceeded at iteration 0 (model=gpt-5.4)'` ✓
- LangSmith ChatOpenAI sub-trace `f40572ae-61a3-4cfd-9c19-fe88e9feaed8`:
  ```
  GeneratorExit()

  Traceback (most recent call last):
    File "C:\Vibe Apps\Agentic RAG\backend\venv\Lib\site-packages\langsmith\run_helpers.py", line 1680, in __iter__
      yield from self.__ls__gen__
  GeneratorExit
  ```

**Approach options:**
1. **Audit-and-fix** — verify D-066-11 close-before-cancel ordering in `agent_runner.py` is actually being honored; fix any ordering bug.
2. **Formally retire** — accept that langsmith-py's `@traceable` async generator wrapper records `GeneratorExit` regardless of close ordering; remove D-066-11 invariant from the SC#6 acceptance criteria. (Worth checking if newer langsmith-py versions handle this differently.)

**Acceptance:** synthetic-timeout protocol re-run produces a LangSmith trace with `TimeoutError` (or whatever clean exception) in the ChatOpenAI sub-trace exception column, NOT `GeneratorExit`. Verified via integration test that wraps a real `langsmith @traceable` with `asyncio.timeout` and asserts the trace exception type.

### Plan 02 — Context-aware in-flight UI affordance

**Owner area:** frontend (MessageItem.tsx + ToolCallPanel.tsx) + possibly api.ts SSE event mapping
**Failure mode:** Pre-streaming silence (1-3s between submit and first delta) and inter-iteration silence (between "Step N — Thinking…" divider and the next tool card appearing) feel empty because the placeholder copy is generic "Thinking" / "Working".

**Approach:** map SSE `iteration_start` and `tool_preparing` event payloads to context-aware copy. Examples:
- Pre-first-delta: "Setting up agent…" (placeholder + tool registry warming up)
- About to fire `search_documents`: "Searching knowledge base…"
- About to fire `analyze_document`: "Analyzing document…"
- About to fire `execute_code`: "Spinning up sandbox…" → "Running code…"
- About to fire skill-loaded tool: "Loading skill {name}…"

**Acceptance:** Chrome MCP submission of the Fahed Mrad multi-tool prompt shows distinct in-flight labels at each phase; Plan 04's UAT re-validates UX-067-01 still green with richer affordance.

### Plan 03 — Agent agentic-behavior overhaul (Claude.ai-like, RAG-customized)

**Owner area:** backend/agent_service.py system prompt + possibly `tool_choice` / OpenAI agent config
**Failure mode:** gpt-5.4 (and likely other models) defer multi-step pipelines to user confirmation. Example from Run 1 (deep UAT 2026-05-07): user submitted "search → report → charts/diagrams → docx" intent; agent did search + analyze, then offered "If you want, I can also turn these into a one-page thematic map or a chapter-by-chapter theme matrix" instead of executing the full pipeline.

**Approach:**
1. Audit current system prompt in `backend/app/services/agent_service.py` for "ask before doing" / "offer to" / "shall I" patterns.
2. Rewrite to instruct the agent: "When the user provides a clear multi-step intent (e.g. 'search → analyze → chart → docx'), execute the FULL pipeline without intermediate confirmation. Only ask for clarification if the intent is genuinely ambiguous."
3. Customize for RAG-nature application: "Always prefer using available tools (search_documents, analyze_document, execute_code, skill-loaded tools) over giving theoretical answers when the user's intent involves their data."
4. Possibly tune OpenAI `tool_choice` to encourage tool use earlier.

**Acceptance:** 5+ runs of the verbatim Fahed Mrad prompt (`search for research authored by Fahed Mrad → professional short report → charts/diagrams → docx`) produce all 4 deliverables (themes report + chart PNG + docx file) without any "If you want…" confirmation prompts. Verified via Chrome MCP.

### Plan 04 — Skill-load UX clarity

**Owner area:** frontend/ToolCallPanel.tsx (skill-load card variant)
**Failure mode:** When a skill loads (e.g. "Loading skill 'docx'"), the card stands alone without explaining WHY. User perceives "skill loaded but code not yet executed" as out-of-order, when actually skill-load-then-tool-fire is the correct sequence.

**Approach:** small copy/template change. Skill-load card surfaces upcoming tool context: "Loading skill 'docx' (needed for: docx generation in next step)". This requires the `skill_loaded` SSE event payload to carry a hint about the upcoming tool/operation, OR the frontend infers it from the next `tool_preparing` event.

**Acceptance:** Chrome MCP submission of a docx-generating prompt shows a skill-load card with the upcoming-tool-context affixed. Visual check + DOM assertion via `data-testid="skill-load-card"`.
