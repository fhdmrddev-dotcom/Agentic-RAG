# Plan 091-08 — Gap closure for 091-REVIEW.md (2 critical + 4 warning)

Closes the confirmed code-review defects on Phase 091's headline requirements before the phase is marked complete. Source: `091-REVIEW.md`. Cross-provider invariant + Deep-Mode byte-identical path must stay intact (Phase 089 gate).

## Task 1 — CR-01: real resume CAS via a claimed_at lease (migration 062)

**Problem (REVIEW CR-01):** `claim_run` does `SET status='active' WHERE status IN ('active','paused')`, but `find_resumable_runs` already returns `active` rows. The status never leaves the claimable set, so both WORKER_COUNT=2 workers win the claim and double-execute the run.

**Fix:**
1. Write `supabase/migrations/062_workflow_run_claim_lease.sql` — add `claimed_at timestamptz` (nullable, default NULL) to `public.workflow_runs`. No CHECK/status change. Idempotent (`ADD COLUMN IF NOT EXISTS`). Include a brief comment documenting the lease semantics. **STOP at the migration-apply checkpoint** (operator pastes into the Supabase SQL editor — never `db push`/`db reset`).
2. Rewrite `claim_run` as a lease CAS:
   ```sql
   UPDATE workflow_runs
   SET claimed_at = now()
   WHERE id = $1
     AND status IN ('active','paused')
     AND (claimed_at IS NULL OR claimed_at < now() - $2::interval)
   RETURNING id
   ```
   Winner stamps `claimed_at`; a racing loser sees a fresh `claimed_at` → 0 rows → returns False. A crash-mid-resume run becomes re-claimable once the lease (default 5 min, an engine/config constant) expires. The lease interval is a named constant (config knob, not a magic literal).
3. Ensure the resume sweep still finds runs: `find_resumable_runs` continues to anchor on `status IN ('active','paused')` (the lease column is orthogonal to status). When a run reaches a terminal status, `claimed_at` is irrelevant; no reset needed.
4. After operator applies migration 062, regenerate `supabase/full-schema.sql` via `bash scripts/regenerate-full-schema.sh` (no `--reset`) and commit the migration + regenerated artifact together (this time the schema DOES change — a new column — so full-schema.sql will have a real diff).

**Test:** two concurrent `claim_run` calls on the same run → exactly one True. A run with an expired lease → re-claimable. (Use the existing `mock_asyncpg_pool` / a fake that models the WHERE.)

## Task 2 — CR-02: never silently discard a >64 KB phase output

**Problem (REVIEW CR-02):** `_persist_output` returns `{"_spilled_path": "workspace-files://pending"}` for outputs > 64 KB, but no executor ever sets `_spilled_path` — the real content is lost from `workflow_phases.output`, and a resumed downstream phase reads the placeholder.

**Fix:** In `_persist_output` (harness_engine.py), store the full output **inline** (jsonb holds it — the 64 KB cap is an optimization, not a hard storage limit). Keep the size measurement, but when over the limit and no real `_spilled_path` is supplied, store inline (optionally log a debug/warn that spill-to-bucket is not yet wired). Never return a placeholder that drops the payload. (Bucket spill remains a future optimization, not a correctness dependency.)

**Test:** a phase output > `_OUTPUT_INLINE_LIMIT` round-trips through `_persist_output` with full content intact (no `_spilled_path` placeholder).
