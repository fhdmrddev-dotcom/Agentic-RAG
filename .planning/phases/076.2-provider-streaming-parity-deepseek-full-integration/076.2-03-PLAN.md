```python
def _convert_tools_to_google(tools: list[dict]) -> list[types.Tool]:
    declarations: list[dict] = []
    for tool in tools or []:
        fn = tool.get("function") or {}
        name = fn.get("name", "")
        description = fn.get("description", "") or ""
        raw_parameters = fn.get("parameters") or {"type": "object", "properties": {}}
        parameters = _sanitize_schema_for_google(raw_parameters)
        if not name:
            continue
        declarations.append({
            "name": name,
            "description": description,
            "parameters": parameters,
        })
    if not declarations:
        return []
    return [types.Tool(function_declarations=declarations)]
```

**Step 2: Check skill tool schema compatibility with Google**

Read the exact JSON Schema for `LOAD_SKILL_TOOL`, `SAVE_SKILL_TOOL`, `READ_SKILL_FILE_TOOL` from `skills_service.py` or `openai_service.py`. Compare each schema against `_sanitize_schema_for_google`'s strip list.

Common Google schema restrictions that could silently break:
- `additionalProperties` (stripped by sanitizer -- fine)
- `type: ["string", "null"]` arrays (converted by sanitizer -- fine)
- Empty `properties: {}` with `required: []` -- Google may reject empty object schemas
- Missing `type` on the root (Google requires `type: "object"`)

If the skill tool schema uses a pattern that `_sanitize_schema_for_google` strips to an empty or invalid schema, the tool may be silently dropped by Google or cause a 400.

**Step 3: Check response parsing for Google tool calls**

In `stream_google` (or the Google response handler in threads.py), verify that when Gemini calls `load_skill`, the response is correctly parsed into the tool dispatch path. The Google native SDK returns `Part(function_call=FunctionCall(name="load_skill", args={...}))` -- verify this flows into the same `tool_calls` list that OpenAI/Anthropic responses populate.

**Fix strategy:**

Based on investigation findings, apply the appropriate fix:

1. **If schema sanitization is stripping/breaking skill schemas:** Fix `_sanitize_schema_for_google` to handle the specific schema pattern, or fix the skill tool schemas to be Google-compatible (e.g., ensure `type: "object"` is present, ensure `properties` is non-empty).

2. **If tools reach Google but Gemini models don't invoke them:** This is behavioral. Add a comment documenting the finding and update BUG-260524-01 status. Consider whether a system prompt hint ("You have access to skills...") improves invocation rate -- but per Deferred Ideas, per-provider system prompt tuning is out of scope.

3. **If response parsing drops Google skill tool calls:** Fix the parsing to handle Google's `FunctionCall` shape for skill tools.

**Regardless of outcome, keep the debug logging** (at DEBUG level, not INFO) for future diagnosis of provider-specific tool issues. This is low-cost observability.
