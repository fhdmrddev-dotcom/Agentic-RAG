<decisions>
## Implementation Decisions

### DeepSeek Thinking Mode
- **D-01:** Render `reasoning_content` in a **collapsible "Thinking" block** matching the existing Anthropic thinking block pattern. Collapsed by default, expandable. Consistent cross-provider UX for reasoning content.
- **D-02:** Follow DeepSeek API defaults — thinking mode enabled for all DeepSeek models (`thinking.type = "enabled"`), `reasoning_effort = "high"` (DeepSeek default). No user toggle. Remove the hardcoded `thinking.type = "disabled"` guard at `openai_service.py:901-907`.
- **D-03:** `reasoning_content` already accumulates in streaming (`_on_chunk_openai`), persists to DB (migration 050 column), and is included in `_reconstruct_history`. The in-memory agent loop message assembly also includes `reasoning_content` via conditional spread at `threads.py:1154/1161/1168`. **Researcher must verify the in-memory iteration path (between tool-call iterations) actually passes `reasoning_content` — SEED-032 claims it doesn't, but the codebase scout found conditional spreads. Resolve this discrepancy.**
- **D-04:** DeepSeek's `reasoning_effort` parameter has two levels: `"high"` (default) and `"max"`. Start with `"high"` (cheaper, default). No per-model override needed this phase.

### Streaming Delta Investigation
- **D-05:** **Fix what we can, document what we can't.** For each provider, do a streaming trace comparison (log chunk-by-chunk timing/structure). Fix chunk handler issues on our side (e.g., timing-dependent progressive rendering). Document provider-side limitations (e.g., Kimi's OpenRouter tool-call parsing failure on large args) as known issues — don't build workarounds for provider bugs.
- **D-06:** **Prioritize direct Kimi API over OpenRouter.** Phase 076.1 already registered `api.moonshot.cn/v1` base URL and `kimi-k2.6` in MODEL_CAPABILITIES. Direct route avoids OpenRouter's tool-call parsing failures on large arguments. OpenRouter stays as fallback for unlisted models.
- **D-07:** DeepSeek "content appears all at once" on completion (SEED-032 Gap 2) — investigate whether the issue is chunk timing from DeepSeek's API or our chunk handler processing them differently. DeepSeek monitoring showed 5+ minute ghost states with zero visible activity between batches.

### Google Skills Bug (BUG-260524-01)
- **D-08:** Fold BUG-260524-01 (Google provider doesn't load Skills into tool surface) into this phase. Investigation + fix as part of cross-provider parity work. Three hypotheses ranked by likelihood: (1) Google adapter doesn't inject skill tool definitions, (2) Google's function_call response shape parsed differently, (3) skill JSON Schema uses features Google rejects. See `.planning/reported-bugs/google-skills-not-loading.md` for full analysis.

### Provider Model Resolution
- **D-09:** Sub-agent/title/suggestion model resolution already works correctly via `override_provider(_user_settings, body.provider)` at `threads.py:1244`. Frontend sends `selectedProvider` with every message (`ChatArea.tsx:243`). **Verify during UAT** that title gen + suggestions use the right provider for each of the 4 curated providers — don't allocate a dedicated plan for this.

### UAT Strategy
- **D-10:** **DeepSeek gets deep testing; others get smoke tests.** DeepSeek: full multi-tool + thinking mode + streaming trace investigation + title gen + suggestions. Kimi/MiniMax/GLM: quick 2-3 turn multi-tool smoke test + title gen + suggestions check.
- **D-11:** **Skills load correctly** as a UAT row for ALL providers (not just Google) — ensures no provider silently drops skills. This is BUG-260524-01's verification gate.
- **D-12:** CLAUDE.md 4-axis bandwidth mandatory:
  - Cross-provider: DeepSeek, Kimi, MiniMax, GLM (one model each)
  - Multi-tool: at least 1 row with 2+ tools per provider
  - Parallel-thread: at least 1 row with Thread A streaming + Thread B accepting
  - Long-message: at least 1 row with 50+ messages or 5KB+ prompt

### Claude's Discretion
- Frontend collapsible block component reuse vs new component for DeepSeek thinking
- Streaming trace logging approach (temporary debug logging vs persistent telemetry)
- Kimi direct API testing scope (which models beyond kimi-k2.6)
- GLM/Zhipu testing depth (minimal data from monitoring — conservative testing)

</decisions>

<specifics>
## Specific Ideas

- DeepSeek thinking collapsible block should use the same component/pattern as Anthropic thinking. Label: "Thinking" or "Reasoning" — match whatever Anthropic uses.
- SEED-032 claims in-memory reasoning_content is NOT passed between iterations, but codebase scout found conditional spreads. This discrepancy is the #1 research item.
- Kimi monitoring showed raw delimiters (`<|tool_calls_section_begin|>`) leaking through OpenRouter — switching to direct API (already registered at `api.moonshot.cn/v1`) should eliminate this.
- MiniMax monitoring showed silent failure with no error message — likely output token truncation. Document as known limitation.
- DeepSeek API docs confirm `reasoning_content` is **nullable** in assistant messages — it may not be strictly required for multi-turn, but best practice is to include it when available.

</specifics>

<deferred>
## Deferred Ideas

- **Per-provider system prompt tuning** — different tool-calling behavior per provider (Kimi leaked raw markup, MiniMax narrates between calls). Belongs in a system-prompt quality phase.
- **Backend text dedup (SSE-level)** — would prevent duplicate data reaching the client. Consider if render-time dedup proves insufficient.
- **Adaptive iteration limits per model** — hardcoded `max_iterations=15/8` should adapt per MODEL_CAPABILITIES. Separate phase.
- **Resume vs Retry UX rework** — "Resume" button re-submits the original prompt. Should be renamed "Retry" and a true checkpoint-resume (Claude.ai "Continue" style) built per SEED-029.
- **Native Google SDK split** — SEED-028 deferred to v3.1. Would eliminate OpenAI-compat layer quirks for Google.
- **Kimi/MiniMax/GLM thinking models** — these providers may add thinking/reasoning modes in the future. Current phase handles DeepSeek only.

</deferred>
