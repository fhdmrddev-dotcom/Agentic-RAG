# Phase 076.2: Code Review Report

**Reviewed:** 2026-05-26T15:00:00Z
**Depth:** standard
**Files Reviewed:** 10

## Summary

Phase 076.2 enables DeepSeek thinking mode (reasoning_content round-trip), wires
the frontend reasoning UI (collapsible Thinking block in RunCard), adds debug
logging for the Google Skills bug investigation (BUG-260524-01), updates the Kimi
base URL and sub-agent model, and adds new DeepSeek V4 model entries.

The implementation is well-structured: the backend accumulates reasoning_content
during streaming, emits `reasoning_delta` SSE events, persists the field to the
DB (migration 050 pre-exists), and the frontend accumulates deltas into
`message.reasoningContent` for display in a collapsible block. The in-memory
message chain correctly round-trips reasoning_content on tool-call turns (required
by the DeepSeek API). Accumulator resets after tool-call consumption are correct
and follow the established `full_content` reset pattern.

Two warnings are flagged: (1) thinking mode is applied unconditionally to all
DeepSeek-prefixed models including deprecated ones that may not support it, and
(2) the `onReasoningDelta` callback is optional but invoked without a guard in the
SSE dispatch, creating a silent no-op path that could mask wiring bugs.

## Warnings

### WR-01: Thinking mode applied to deprecated deepseek-chat / deepseek-reasoner models

**File:** `backend/app/services/openai_service.py:905`
**Issue:** The condition `if provider == "deepseek" or effective_model.startswith("deepseek-"):`
enables thinking mode for ALL DeepSeek-prefixed models, including `deepseek-chat` and
`deepseek-reasoner` which are deprecated legacy models (V3 API). The DeepSeek V3 API
may not support the `thinking.type=enabled` + `reasoning_effort` parameter shape that
V4 introduced. If DeepSeek's API returns a 400 for unrecognized parameters on
legacy models, users who still have `deepseek-chat` selected will get hard failures.

The config comments acknowledge the deprecation (`deprecated 2026/07/24`), but the
deprecation date is in the future -- these models are still selectable today.

**Fix:** Guard the thinking config behind a model-level check or an explicit
allowlist of thinking-capable models:
```python
_DEEPSEEK_THINKING_MODELS = frozenset({
    "deepseek-v4-flash", "deepseek-v4-pro",
})

if provider == "deepseek" or effective_model.startswith("deepseek-"):
    kwargs.setdefault("extra_body", {})
    if effective_model in _DEEPSEEK_THINKING_MODELS:
        kwargs["extra_body"]["thinking"] = {
            "type": "enabled",
            "reasoning_effort": "high",
        }
```

Alternatively, if `deepseek-chat` and `deepseek-reasoner` are confirmed to
gracefully ignore the `thinking` parameter on the DeepSeek API (returns 200
with no reasoning_content), this warning can be dismissed with a code comment
documenting the verification.

### WR-02: onReasoningDelta optional in StreamCallbacks but dispatch lacks guard in api.ts

**File:** `frontend/src/lib/api.ts:395-396`
**Issue:** The `onReasoningDelta` callback is declared as optional
(`onReasoningDelta?: (text: string) => void`) in `StreamCallbacks` (line 190),
and the dispatch at line 395-396 does check for its existence before calling:
```typescript
else if (t === "reasoning_delta" && callbacks.onReasoningDelta)
  callbacks.onReasoningDelta(parsed.content as string)
```
However, if `callbacks.onReasoningDelta` is not wired (e.g., a future caller of
`subscribeToRun` that omits it), `reasoning_delta` SSE events are silently
dropped with no logging or fallback. Since `reasoning_delta` is a new event type,
any integration point that creates `StreamCallbacks` without `onReasoningDelta`
will silently lose thinking content.

This is not a bug today (the only call site in `StreamsProvider.tsx` does wire
it), but it reduces debuggability for future callers.

**Fix:** Add the `reasoning_delta` event type to any existing "unhandled event
type" logging, or make the callback required in `StreamCallbacks` so TypeScript
enforces wiring at all call sites. The lighter fix:
```typescript
else if (t === "reasoning_delta") {
  callbacks.onReasoningDelta?.(parsed.content as string)
}
```
This uses optional chaining and keeps the event matched (not falling through
to an unhandled branch), while still being safe if the callback is absent.

### IN-02: Source-inspection tests are brittle

**File:** `backend/tests/unit/test_deepseek_thinking.py:19-30`
**Issue:** `TestDeepSeekThinkingEnable` uses `inspect.getsource()` to scan for
string literals like `'"type": "enabled"'` in the openai_service module source.
This is brittle -- any reformatting (e.g., single-quote to double-quote
normalization, line wrapping, or variable extraction) breaks these assertions
without any behavioral change.

The tests at `TestReasoningContentRoundTrip` and `TestMessageResponseExposure`
are well-structured behavioral tests. The source-inspection tests serve as
regression guards for the config change from "disabled" to "enabled", but they
duplicate the behavioral contract rather than testing it.

**Fix:** Consider replacing with a functional test that calls
`create_adaptive_streaming_chat` with a mocked client and inspects the `kwargs`
passed to `client.chat.completions.create`, verifying the `extra_body.thinking`
shape directly.

### IN-03: Debug logging in google_service.py retained for observability

**File:** `backend/app/services/google_service.py:320-325,334-338`
**Issue:** Debug-level logging was added for BUG-260524-01 investigation. The
comments note it is "retained at DEBUG level for ongoing provider-tool
observability." This is acceptable at DEBUG level and will not affect production
performance, but it does log raw parameter schemas which could be verbose.

**Fix:** No action required -- DEBUG level is appropriate. Consider adding a
structured log field (e.g., `extra={"bug": "BUG-260524-01"}`) so the logs can
be filtered easily if needed.
