it — and answering later must resume it without a server restart. The vehicle is D-13's extraction:
the human-input executor moves to its own module in the same act as its own fix.

the `kind == "response"` branch — so the timeout path falls straight through to a normal completion.

exactly the five-minute mark.** A human gate that fails OPEN is the one defect on this surface that
no amount of re-presentation can excuse.

`PhaseOutcome` kind with its own engine arm, an answer-triggered re-drive, and two new test files —
one committed before the cut, one proving the pause.

## RECORDED DEVIATION — why the ROADMAP's six-plan shape became seven

The ROADMAP folds this work into `200-02`. **RESEARCH R1 measured that the two are not additive:**
`grep -rn "'paused'" backend/app --include=*.py` returns **seven hits, all READS** — the status is
admitted by the CHECK constraint and read by three queries, and **nothing in the backend has ever
written it**. The only `UPDATE workflow_runs SET status` writer is `finish_run` (`db/workflows.py:1754`),
which **clears `threads.active_workflow_run_id` in the same transaction**, making the run permanently
unresumable because `find_resumable_runs` requires that anchor. And the only re-drive path in the whole
product is `main.py:406`'s boot-time sweep. So D-10 is a control-flow change to the engine needing its
own RED-first proof, while `200-02` is additive — and SC#5's claim that *"the extraction changes no
behaviour beyond the human-gate fix"* is unprovable if the two ride in one plan. Plans `200-04`…`200-07`
are the ROADMAP's `03`…`06`, shifted by one.
