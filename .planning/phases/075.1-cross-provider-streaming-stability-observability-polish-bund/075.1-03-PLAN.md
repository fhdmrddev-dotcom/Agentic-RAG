```python
# 1. message_start → yield {"type": "usage", ...}
# 2. content_block_start (type=tool_use) → yield {"type": "tool_preparing", id, name, index}
# 3. content_block_delta (type=text_delta) → yield {"type": "delta", "content": str}

# 6. message_delta → yield {"type": "usage", ...} (cumulative)
# Multiple text_delta and tool_use blocks INTERLEAVE — a single response can be:
# text_delta → text_delta → tool_use(start+stop) → text_delta → tool_use(start+stop) → text_delta
```

Existing makeStreamCallbacks factory in `frontend/src/providers/StreamsProvider.tsx:132-280+` handles onDelta, onDone, onToolPreparing, onToolStart, onToolEnd, etc. The contract is one assistant message accumulates content via `onDelta(text)` and tool_calls via `onToolPreparing` → `onToolStart` → `onToolEnd`.

MessageItem.tsx sticky-cache code lives at lines 59-91:
```typescript
const stickyLabelRef = useRef<string | null>(null)
const computedLabel = isStreaming
  ? outerBannerLabel(activeTool, hasAnyTools, message.isPlanning ?? false)
  : null
if (isStreaming && computedLabel !== null) {

  stickyLabelRef.current = null   // ← THE BUG: should reset on message.runStatus terminal, not isStreaming
```

The `isStreaming` prop here is provider-level (passed from MessageList/MessageItem parent). When parallel runs exist on the same surface, `isStreaming` can flip to false while THIS message is still streaming. The right signal is `message.runStatus` — terminal values are `"completed" | "failed" | "timed_out" | "cancelled"`; streaming values are `"streaming"` (or undefined for legacy/DB-loaded rows).
