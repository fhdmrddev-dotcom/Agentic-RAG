# v2.9 EXPLORATION — Consolidated Scoping Brief

**Milestone candidate:** "Make workflows REAL and domain-grounded" — project-scoped workflow
libraries, skills wired to workflows, KB-scoped retrieval, and temporary template-fill. Project
Management is the **flagship demo domain, not a hardcoded spec.**

**Synthesized from:** 6 dimension reports (A–F) under `.planning/research/v2.9-exploration/` +
adversarial verification verdicts. **Date:** 2026-06-08.

**One-line thesis (the through-line of all 6 reports):** v2.9 is **~80–90% composition of shipped
v2.8 harness primitives** — the net-new is *authoring UX + a project/scope binding + ephemeral
template upload + a small library of validation-gate kinds + a Workflows page*, NOT a new runtime
and NOT the Plugin Contract.

> **Verification downweights applied.** Two competitor-binding claims were softened: (1) Dust does
> **NOT** bind "one agent = one Space" (REFUTED) — an agent references *multiple* Spaces and a user
> must have access to **all** of them (AND-gated, admin-overridable). (2) Notion's "dedicated
> teamspace" recommended pattern is **unsubstantiated** (MIXED) — the defensible claim is only that
> Custom Agents default to **zero access** and act only on **explicitly granted** resources
> (least-privilege via granular per-resource grants). The underlying design lesson — *a
> permission-aware scope object with least-privilege explicit grants* — survives both downweights.
> All PM-taxonomy anchors (PRINCE2 baseline/record/report trichotomy, PMBOK 7's 9 non-prescriptive
> categories, risk = P×I, RTM bidirectional traceability, CPM zero-float, cost baseline excl.
> management reserve, stakeholder C→D engagement matrix, WBS tree) and the Copilot-Studio-determinism
> + TurboDocx-template-fill claims verified **supported**.

## 1. Executive summary

- **Build authoring, not runtime.** The deterministic-locked-harness-with-an-agentic-phase that
  Microsoft *sells as premium* ("same input → same output," agent delegated at a prescribed step) is
  already our shipped foundation (5 phase types, 4 validation gates + bounded retry, step/wall-clock
  caps, immutable-on-publish, Postgres-resumable, INSERT-only audit). v2.9 adds the **on-ramp** to it.
- **One unifying object: "project = folder."** A folder (+ subtree) co-owns its KB, a **library of
  workflows**, and the **skills** those workflows may load. This single binding resolves "project
  owns workflows" and "workflows scoped to the KB" at once, reusing folders + RLS that already exist.
  Modeled on permission-aware scope objects (Dust Spaces / Notion least-privilege grants) — but
  scoped to *our* folder tree, not copied wholesale.
- **The whole milestone is additive, optional config fields.** `project_folder_id`, per-phase
  `folder_scope`, `skill_ref`, and a typed `inputs`/`assets` schema all *grow* the JSONB workflow
  definition. Immutability means "no-edit-published," **not** "no-grow-format" — so old published
  workflows keep validating cleanly and nothing breaks.
- **Template-fill is the demoable wedge nobody does well.** Upload a docx/pptx/xlsx **temporarily**
  (never ingested into the KB), retrieve from the project KB, and fill *that exact template*. We
  already have the sandbox + python-docx/pptx/openpyxl/reportlab; the only new library is **docxtpl**
  for high-fidelity .docx. The LLM emits a **cited Pydantic field-map**; pinned library code renders
  the bytes deterministically.
- **PM is the flagship CONTENT pack, not hardcoded logic.** Risk register, RAID, RTM, status report,
  prob-impact matrix, stakeholder matrix, minutes-of-meeting all collapse into ~7 reusable generic
  capabilities (typed register, classify-and-route, traceability graph, scheduled template-fill
  report, generate-and-lock baseline, scored heatmap, cross-project lessons loop). Ship PM as
  template files + workflow definitions + register schemas any domain expert can re-author.
- **Author via NL-describe → strict-parse → form-edit → lint-on-publish, with a read-only live
  graph. NEVER a drag-to-build node canvas.** OpenAI is *sunsetting* its hosted visual Agent Builder
  (full shutdown 2026-11-30, ~13 months after launch) and retreating to code + NL — fresh, decisive
  market evidence for the "no canvas" call.
- **Trust is a small library of reusable gate kinds, not bespoke checks.** `citations_required`,
  `freshness` ("check the date first" as a literal guaranteed-first phase), `structure_check`,
  `output_file_valid` (re-open the file to prove it isn't corrupt), `llm_judge_rubric`. Each rides
  the harness's existing gate + bounded-retry loop. The **output-quality gate is a HARD publish
  blocker** — a lint-clean workflow can still emit garbage (the single biggest latent risk).
- **The Plugin Contract is OFF the critical path.** The KB-grounded flagship needs zero plugins.
  The flagship *does* generate real telemetry for `phase_type` (fill_template) and `file_preview`
  (office viewer) to LOCK the contract against later. Connectors (email/OneDrive/GDrive) stay
  deferred — already seeded (SEED-013/014/051) — and arrive only at the outbound "send" seam.

## 2. PM artifact catalog (the generalizable core)

PMBOK 7 deliberately ships **no fixed checklist** (9 loose, "not exhaustive or prescriptive"
categories) — which *validates* building a generic capability and expressing PM as authored content.
PRINCE2 7's **baseline / record / report** trichotomy (verified supported) is the design lens: it
maps almost 1:1 onto three harness workflow archetypes.

**Amenability legend:** EXTRACT (rows from unstructured docs) · FILL (retrieve→populate template) ·
ROLL-UP (aggregate existing structured data) · COMPUTE (deterministic math, NOT LLM) · JUDGE (human
ratifies; LLM drafts).

| Artifact | Data model (core fields) | Inputs | Cadence | Automation-fit |
|---|---|---|---|---|
| **Meeting Minutes (MoM)** — *hub input* | attendees, agenda_items, decisions[], action_items{owner,due}, risks/issues_raised[] | transcript, agenda | per-meeting | **EXTRACT (Tier 1)** — highest-leverage single extraction; feeds everything below |
| **Risk Register** — *canonical demo* | risk_id, cause→event→effect, category(RBS), P(1-5), I(1-5), score=P×I, RAG, strategy, owner, residual P/I, status, trigger | minutes, workshops, issue log, prior-project KB | high / per-standup | **EXTRACT + COMPUTE** — extract risks, dedupe, P×I score is trivial code |
| **RAID Log** | id, category(R/A/I/D), description, impact, owner, status, due, next_action | minutes, standups, emails | daily | **EXTRACT (Tier 1)** — archetypal classify-and-route into a typed register |
| **Issue Log** | issue_id, description, impact, priority, owner, status, resolution, linked_risk_id | standups, tickets, defects | daily | **EXTRACT** — same shape as RAID/risk |
| **Change Log** | change_no, type, impact_assessment{cost,sched,scope}, CCB_decision, status | CR forms, CCB minutes | event-driven | **EXTRACT + JUDGE** — impact drafted, approval is human/CCB gate |
| **RTM (Requirements Traceability)** — *most reusable* | req_id, shall_statement, source, priority, related_req_ids[], deliverable/test_case link, verification status | specs, contracts, user stories, tests | living | **EXTRACT + ROLL-UP (Tier 1)** — bidirectional graph; orphan/untested-req coverage gaps; domain-agnostic |
| **Stakeholder Register + Engagement Matrix** | power, interest, influence, classification (Power/Interest quadrant or Salience), engagement C→D across Unaware→Resistant→Neutral→Supportive→Leading | org charts, interviews, emails | periodic | **EXTRACT + JUDGE** — extract+suggest classification; C/D gap is human judgment; data often confidential |
| **Prob-Impact Matrix** | scale defs, cell_score=P×I (1-25), RAG thresholds; a *projection* of the register | risk register rows | regen on change | **ROLL-UP (pure projection)** — render, never hand-maintain; heatmap renderer candidate |
| **Status / Highlight Report** — *template-fill flagship* | overall_RAG + per-dim RAG (schedule/budget/scope/risk), accomplishments[], next[], top_risks[], milestone_status[] | schedule, cost, risk, issue records | weekly | **ROLL-UP → FILL** — read N records → compute RAG → fill branded template; THE scheduled template-fill demo |
| **Project Charter** | purpose, objectives[] (SMART), scope in/out, milestones[], budget, sponsor, high-level risks[] | business case, SOW, kickoff, prior charters | one-shot / re-baseline | **FILL + JUDGE (Tier 2)** — generate-and-lock with ask_user ratification |
| **WBS + Dictionary** | *tree*: wbs_id, parent_id, work-package leaves w/ owner, duration, cost, risks (NOT flat tabular) | scope statement, SME decomposition | planning / progressive | **FILL + JUDGE (Tier 2)** — decompose drafts; 100%-rule completeness needs human |
| **Schedule (CPM/float)** | tasks, predecessors{FS/SS/FF/SF}, computed ES/EF/LS/LF, float=LS−ES, is_critical (zero-float chain) | WBS, durations, progress | daily/weekly | **COMPUTE (Tier 3)** — deterministic; route to programmatic/execute_code; LLM only narrates |
| **Cost Baseline (EVM)** | activity→work-package(+contingency)→control-account→baseline; +mgmt reserve = budget (reserve excluded); S-curve | estimates, WBS, actuals | baseline + weekly actuals | **COMPUTE (Tier 3)** — aggregation + EVM math = code |
| **Lessons Learned → Closure** | lesson_id, category, what_happened, root_cause, recommendation; closure adds objectives-vs-actuals | retro notes, variance, risk history | continuous → one-shot | **EXTRACT + cross-project RAG** — lessons become retrieval inputs to future charters (remember/recall + KB search) |

**Three workflow archetypes (PRINCE2 lens → harness primitive):**

| Archetype | PRINCE2 type | Harness fit | LLM mode |
|---|---|---|---|
| **Generate-and-lock** | Baseline | `llm_single`/`llm_human_input` → publish → version-on-change | FILL + JUDGE |
| **Incremental register update** | Record | recurring: ingest → extract → dedupe/merge → upsert | EXTRACT |
| **Scheduled roll-up snapshot** | Report | scheduled `programmatic` + `llm_single` → render template | ROLL-UP |

**The demo spine — "standup-to-artifacts cascade":** one transcript → minutes → RAID classification →
risk register upsert → deterministic P×I/RAG recompute → prob-impact matrix re-render → weekly
status-report template-fill. This single chain exercises **every** capability v2.9 wants to prove.

**The 7 generic capabilities to BUILD (PM expressed as content on top):** (1) typed register with
lifecycle status, (2) classify-and-route free text into a register, (3) bidirectional traceability
graph, (4) scheduled roll-up into a branded template (= the template-fill requirement), (5)
generate-and-lock baseline with human ratification, (6) 2-axis scored heatmap projection, (7)
cross-project lessons→future-input loop (partly built via remember/recall). **PM-specific math
(CPM/float, EVM, S-curve) stays out of LLM phases** — candidate `phase_type` plugin, not core.

## 3. Product landscape — table stakes vs differentiators vs anti-features

Every serious "Work AI" product converged on one spine: *describe in NL → platform drafts steps +
suggests tools/knowledge → refine in fields/canvas → publish → run on triggers with HITL gates*,
knowledge **bound by a permission-aware scope object**, with the mature products separating a
**deterministic flow** from an **agentic step** inside it.

### TABLE STAKES (must-have to be credible)
1. **NL-to-draft authoring** then refine (Glean, Copilot Studio, Dust/Sidekick, monday, Asana,
   Gumloop/Gummie, Notion all ship this exact pair).
2. **An editable starter-template gallery** — never locked-prebuilt-only (ClickUp *deprecated*
   prebuilt Autopilot Agents Dec 2025 because customizable ones won).
3. **A permission-aware knowledge scope object**, least-privilege by default. *(Downweight: the
   accurate Dust/Notion lesson is "explicit grants, least privilege" — NOT "one agent = one space"
   nor "dedicated teamspace.")*
4. **Triggers: manual + scheduled (freq/time/timezone) + event.** Scheduling is expected, not
   premium; per-user active-schedule caps are common (Glean: 10).
5. **Structured deliverables** beyond chat text (native objects, a citation grid, or a filled file).
6. **HITL approval/data-input/task-complete checkpoints** that pause and resume (Relay.app is the
   gold standard; Copilot Studio ships a "Human in the loop" action type).
7. **Run history / observability** with per-step inputs/outputs + **citations to source**.
8. **Reusable, shareable definitions** with publish + versioning, scoped to a team.

### DIFFERENTIATORS (where we win)
1. **Deterministic locked harness with an agentic phase inside it** — competitors are *adding*
   determinism to agents; we *start* deterministic and add agency. The stronger stance for PM /
   legal / finance. (Already shipped.)
2. **True template-fill of an uploaded artifact** — TurboDocx is a whole product around
   `{Variable}`→KB matching; almost nobody in the Work-AI tier fills *your exact DOCX/PPTX*. We have
   the sandbox + libraries. Sharp, demoable wedge.
3. **Citation-traceable grid deliverable** (Hebbia Matrix-style: rows=items, cols=attributes, every
   cell agent-filled + source-cited) for risk register / RTM / stakeholder matrices — backed by
   `llm_batch_agents` + retrieval.
4. **Skills wired to workflow phases, scoped to the project** — a coherent story (skill = judgment,
   workflow = control) that almost nobody has cleanly assembled. Primitives exist; only the
   association is net-new.
5. **One scope object that co-owns documents + workflows + skills** under a folder boundary.
6. **Per-step bounded context passing** (Glean's "inherit only previous step's output" + `[[ ]]`
   reference) — a cheap, debuggable alternative to dumping full history into harness phases.

### ANTI-FEATURES (traps to avoid)
1. **A full visual node-graph editor** — our buyer is a domain expert, not an automation engineer;
   OpenAI's Agent Builder sunset confirms the squeezed middle. NL + a readable linear/phase view.
2. **Rigid prebuilt-only agents** — ship templates as editable seeds.
3. **Per-action metered billing surfaced to authors** — Copilot Studio's loudest complaint ("agents
   rack up pay-as-you-go before IT knows," no unified cost dashboard).
4. **Becoming a 100+ connector iPaaS** — CLAUDE.md already forbids connectors; stay KB + sandbox +
   template-fill scoped.
5. **Unbounded autonomy / "20-minute agent theater"** — our value is reliability + auditability.
6. **Heavy ALM/solutions packaging** — keep publish/version simple (immutable-on-publish + audit log
   already exist; don't gold-plate).
7. **Artificial caps** (Copilot Studio's 500-knowledge-object / 5-active-source limits) — folder
   scope bounds retrieval naturally; don't import arbitrary ceilings.

## 4. Template-fill — recommended implementation path on OUR stack

**Golden rule (verified pattern): the LLM produces DATA, deterministic code produces the FILE.** Use
a Pydantic structured-output field-map whose fields *are* the placeholder keys, each carrying
citation fields (`chunk_id`/`page`) and nullable so the model can decline rather than hallucinate;
then render with pinned library code. Matches our "Pydantic for structured outputs, raw SDK, no
LangChain" rules.

**Two strategies, support both as separate patterns:**
- **(A) Author-time placeholder templates** (project-library, trusted authors) — machine-readable
  markers, reliable + formatting-preserving. **docxtpl `{{jinja}}`** for .docx.
- **(B) Schema-discovery fill** (arbitrary user upload) — infer where values go; the "magic" path,
  but the source of nearly every formatting-loss/corruption failure. Use **non-Jinja run-replace**.

**Format-by-format on our sandbox (only docxtpl is new):**

| Format | Engine | Mode | Main risk to GATE |
|---|---|---|---|
| `.docx` | **add `docxtpl`** (jinja2+lxml come transitively) + python-docx run-replace fallback | A preferred / B | run-split silent miss; **SSTI** if author untrusted |
| `.pptx` | python-pptx (already shipped) run-level replace | B | **cannot add/remove table rows** (issue #192) → pre-size template |
| `.xlsx` | openpyxl (already shipped) in-place cell write | B | **charts/images/pivots DROPPED on load→save** → require chart-free templates |
| `.pdf` | reportlab (already shipped) generate-from-data | generate | not a true "fill" — build from context |

**Harness composition (zero changes to streaming/SSE/agent-loop hot files):**
`programmatic` (parse template → placeholder schema via `get_undeclared_template_variables()` /
marker scan) → `llm_agent` (cited Pydantic field-map, project-folder-scoped retrieval, nullable
fields) → **validation gate** (coverage + Pydantic types, bounded retry) → `llm_human_input` (review
unfilled/uncited fields) → `programmatic` (render in sandbox + **re-open output to assert integrity**)
→ **validation gate** (faithfulness).

**Ephemeral upload = a TTL'd workspace file, NOT a KB document.** Reuse the v2.7 per-thread workspace
table; add `kind='template_input'` + `expires_at` + RLS + a cron sweep. **Never** run it through
ingestion/embedding; never appears in KB search. This is an *additive storage/lifecycle change* (low
blast radius) — and keeping it out of the KB **closes the injection-via-uploaded-doc vector** at the
same time. Mirrors how OpenAI assistant-thread files auto-expire ~7d; tighten to ~24h-after-inactivity.

**Security (load-bearing, surface at spec time per G-6):** docxtpl renders Jinja2 server-side →
arbitrary uploaded template is textbook **SSTI→RCE** (the class that hit adfinis/document-merge-service,
GHSA-v5gf-r78h-55q6). **Two-layer mitigation:** pass `jinja2.sandbox.SandboxedEnvironment` to
docxtpl's `jinja_env` AND render only inside the sealed, network-less Docker sandbox. **Reserve Jinja
templates for trusted project-library authors; arbitrary uploads use the non-Jinja run-replace path.**

**Validation = 3 cheap independent layers (each a harness gate):** (a) deterministic completeness
(every placeholder present, StrictUndefined, Pydantic types) + **file integrity by re-opening the
output** with the same library; (b) faithfulness via claim-extraction + LLM-judge against cited
chunks; (c) score coverage × faithfulness × integrity **separately**, not as one number.

**Known failure modes to bake into UAT rows up front:** docx marker split across runs (silent
miss) · unescaped `&<>` XML corruption · pptx variable-row table can't grow · xlsx chart/image
stripping · merged-cell mis-write · produced-file-won't-open (the re-open-to-validate gate is
mandatory).

**Deferred (flag, don't build):** Word content controls/SDT (most robust marker, but .NET Open XML
SDK toolchain — Python has no high-level SDT API); Google Docs `replaceAllText` (cleanest
formatting-safe path, but needs OAuth + Drive connector = `data_source` plugin territory).

## 5. Workflow ↔ skill ↔ KB binding + authoring — architecture composing our harness

**Load-bearing fact:** `WorkflowDefinition` is a JSONB column parsed by a strict `extra="forbid"`
Pydantic model. **Adding *optional* fields is a zero-migration, non-breaking change** — old
published rows don't carry them and still `model_validate()` cleanly. Immutability = "no-edit-published,"
not "no-grow-format." This is what makes the whole milestone cheap.

### Four additive, optional binding fields (config, not prompt glue)
1. **`project_folder_id` on `WorkflowDefinition`** (nullable UUID). "Project" = folder + subtree. The
   Workflows page filters the library by it; run-time default KB scope = this folder's subtree
   (overrides the thread-derived default). Reuses the `folders` table + RLS. *(Consider a real column
   not a JSONB key, since the library page queries on it.)*
2. **Per-phase `folder_scope`** (nullable folder id/path). The mechanism is **already built** —
   `_build_phase_tool_context` forwards `folder_subtree_ids`/`scoped_folder_path` into the phase
   `ToolContext`, honored by `search_documents`/`ls`/`tree`/`grep`. The only change: resolve subtree
   **per phase** from `phase.config.folder_scope` (fall back to run scope). **~15 lines, no schema,
   no new tool.** (Pin "Risk register" phase → /Projects/Acme/Risk; "Stakeholders" → /People.)
3. **`skill_ref` on `llm_agent`/`llm_single` configs** (nullable skill slug). A harness phase
   *replaces* the system prompt with `phase.config.prompt`, so the skills catalog never reaches it
   today. Wire additively: load SKILL.md + referenced files, compose into the phase framing,
   auto-whitelist `read_skill_file`. **Snapshot the skill version into the locked definition** so a
   deleted/renamed skill can't break an old published workflow.
4. **Typed `inputs` + `assets` schema on `WorkflowDefinition`.** `inputs` = AI-derived launch-form
   fields (dynamic at design time, fixed at run time). `assets` = Storage-backed workflow-owned
   templates/reference docs. Distinct from the **run-time ephemeral upload** (§4) which is a run
   input — *that* upload path is the one genuinely net-new plumbing piece.

### Authoring loop (re-confirmed by OpenAI's Agent Builder sunset)
**NL-describe → strict-parse → form-edit → lint-on-publish, with a live READ-ONLY graph. NO drag
canvas.**
- **Generate:** one-shot structured call using `WorkflowDefinition` AS the response schema over our
  own provider layer. `extra="forbid"` kills hallucinated fields; `lint_workflow` kills unreachable
  graphs; auto-retry feeds the validation error back. Provider-uniform, no LangChain.
  *Authoring-time grounding* = feed the generator the KB folder tree + tool/skill registry + the
  uploaded template so it proposes correct fields/tools/scope.
- **Refine as a form:** the discriminated union IS the form schema (pick `phase_type` → reveal that
  variant's fields; whitelist = multiselect of registered tools; validators = kind+config sub-form).
  Edits stay describe + form-tweak + approve (never auto-publish).
- **Live read-only graph:** renders the `WorkflowDefinition` + the `reachability.py` nodes/edges we
  already compute. View, not drag-to-build.

### "Strictly adherent to ONE business requirement" = a 4-layer stack, each with a home
- **Structural** → `lint_workflow` (shipped): reachable, terminal, satisfiable inputs.
- **Shape** → `extra="forbid"` + discriminated union (shipped): can't emit a key the engine ignores.
- **Quality/acceptance** → **new `llm_judge` ValidatorSpec kind** + a `business_requirement` field +
  publish-time golden run. This is where "ONE requirement" becomes *enforceable*: the acceptance
  criteria ARE the judge rubric + deterministic validators.
- **Immutability** → locked-on-publish trigger (shipped).

The model **cannot publish a structurally-broken workflow** (safe by construction). The only residual
risk is *lint-clean-but-bad-output* — which the judge gate + golden run close. **This makes the
output-quality gate a HARD publish-blocking dependency.**

### Skills compose via `skill_ref` (per-step judgment bar) — preserve the distinction
**Skill = optional model-PULLED judgment** (non-deterministic, adds method). **Workflow =
author-LOCKED orchestration** (deterministic, adds control). They compose; they don't compete. The
reverse seam (a skill *triggers* a workflow) is a plugin `tool` concern — deferred.

### Library surface = almost entirely shipped
Browse (RLS + `list_published_workflows` + `project_folder_id` filter), instantiate
(`create_workflow_run` → thread-bound run, shared SSE), version (`UNIQUE(slug,version)` + immutable
trigger), share/global (`is_global` RLS). **Net-new = a Workflows PAGE** (library + builder live on
the page; **execution stays in a thread** — Run a workflow → puts *that* thread into workflow mode;
Deep is the resting default). **One authz gap:** self-serve **global** publish needs the deferred
operator/admin tier to relax the `is_global=false` INSERT check. Keep **drafts self-serve + per-user
publish** in v2.9 (RLS already enforces it); gate global behind the operator tier.

### Guardrail note
The authoring work is **greenfield** (new page, new API router, optional model fields) — it does NOT
pile onto the G-5-firing hot files (`threads.py`, `anthropic_service.py`). Engine additions are
additive seams on `harness/phase_types.py` + `models/harness.py`. **G-2 (sketch-before-plan) FIRES**
for the Workflows page / form editor / live graph — `sketch-findings-agentic-rag` already names these
surfaces. Sketch before spec.

## 7. Pitfalls & required guards

Nearly every trust failure maps to a **cheap, reusable validation-gate kind** that composes the
harness's existing gate + bounded-retry loop. Ship a *small library of gate kinds*, not bespoke
per-workflow checks.

| Failure mode | Cheapest correct guard | Gate kind |
|---|---|---|
| **Hallucinated artifacts** (invented risks/reqs) — RAG alone does NOT stop fabrication even with correct context | Every row carries `source_chunk_id`; programmatic gate deterministically rejects uncited rows (cheap substring/numeric check) BEFORE any judge call; bounded-retry re-derives or drops | `citations_required` |
| **Stale data** ("check the date first") — semantic similarity is blind to time; v1/v2/v3 retrieve equally; silent failure | Deterministic freshness-preflight phase (`SELECT max(updated_at)` over folder scope) the locked harness GUARANTEES runs FIRST; branch to `ask_user` if multiple/stale versions. **A structural win Deep-mode chat cannot offer.** | `freshness` |
| **Ungrounded template-fill** | Retrieve-then-fill: the fill phase gets only retrieved spans + parsed placeholder schema, must emit `{value, source_chunk_id}` or `[NOT FOUND IN KB]`. Template stays workspace-only | (reuses `citations_required`) |
| **File/template corruption** (python-pptx 12+ / openpyxl known offenders) | Programmatic validate-before-deliver: re-open the output with the same library + assert counts (zero-dep), or add `openxml-audit`. A corrupt file can NEVER reach the user as "done" | `output_file_valid` |
| **Over-automation / automation bias** (humans rubber-stamp; "launder" errors into false accountability) | Provenance-forward `llm_human_input` checkpoints (show value+cited-source pairs + gate flags, require a substantive action); reserve for irreversible/finalization steps only (avoid banner-blindness) | `llm_human_input` (review-with-provenance) |
| **Scope creep** | One declared `business_requirement` per workflow + publish lint (reject compound/empty) + immutable-on-publish + per-phase tool-whitelist union as the fixed capability ceiling (a risk workflow simply isn't granted web_search/email) | publish-time lint + schema field |
| **Prompt injection from ingested docs** (EchoLeak CVE-2025-32711, CVSS 9.3, zero-click email exfil) | Split "read untrusted KB content" and "act/export" into different phases via the tool whitelist (injected text reaches a phase with no exfil capability) + retrieved-text spotlighting + ingestion sanitization; future email source review-gated | tool whitelist (already owned) |
| **Cross-folder RLS leakage** (the new attack surface) — LLM-honored scope is "security theater" | Resolve `scope_folder_ids` server-side from the user's RLS context at run start; bind to every retrieval call as a parameter the model cannot widen; RLS as backstop; assert retrieved `folder_id`s ⊆ scope | server-side scope resolution |
| **Cost runaway** (agents burn 10-50× tokens; one runaway = $2,847/4h) | REJECT-semantics per-run token ceiling metered at the shared gateway + per-workflow daily caps; scheduling/fan-out ship **disabled-by-default with a mandatory budget field** (no schedule without a cap) | gateway meter + budget field |
| **Eval honesty** | Layered: programmatic structure/schema checks = correctness FLOOR; `llm_judge` analytic rubric (randomized, off hot path) = SMELL TEST (biased: self-preference/verbosity/position); human checkpoint = AUTHORITY. **A green judge must NOT auto-replace human sign-off on high-stakes artifacts** | `structure_check` + `llm_judge_rubric` |

**Governance is mostly *surfacing*, not building.** The provenance chain is already recorded:
`{immutable published def@version} + {INSERT-only run log: inputs/transitions/tool-calls/outputs} +
{per-phase gate verdicts with evidence} + {cited source spans per value}`. This matches EU AI Act
Article 12 runtime-traceability shape (append-only, ≥6-month retention; high-risk enforcement
**Aug 2, 2026**). The only add is a per-run **provenance receipt** view.

**Three claims to re-confirm against actual harness code at spec-phase:** (a) are gate
verdicts-with-evidence already persisted to the run log? (b) does in-workflow retrieval already take
a *bound* folder-scope parameter vs a prompt hint? (c) does the shared gateway uniformly capture
token usage across all 7 providers (needed as the spend meter)?

## 8. Plugin Contract relevance — which of the 6 types v2.9 exercises

The KB-grounded flagship needs **NO plugin contract at all** to ship. But it generates real telemetry
to LOCK the contract against later (D-v2.8-01's "lock on real harness telemetry" rationale). The 6
types: `tool`, `panel_renderer`, `phase_type`, `file_preview`, `data_source`, `secrets_adapter`.

| Plugin type | Exercised by v2.9? | Verdict |
|---|---|---|
| **`phase_type`** | **STRONGLY** | A first-class `fill_template` phase IS a plugin phase_type; the dispatch seam exists (`PHASE_TYPE_REGISTRY` `harness_engine.py:111` + `register_all()` `phase_types.py:573`). The single most-exercised type. *(But the 5 shipped types already cover 4/5 Anthropic patterns; orchestrator-workers is DELIBERATELY excluded to preserve determinism — do NOT add runtime-dynamic phases.)* |
| **`file_preview`** | **STRONGLY** | Viewing the filled docx/pptx/xlsx in-panel = SEED-037 office-viewer gap + the named PPTX reference plugin. A real consumer with a real gap. |
| **`tool`** | **YES** | A `fill_template`/domain tool, or the eventual `send` tool, as a registered plugin tool (existing `_TOOL_REGISTRY` closed-registry pattern). Also the home for the "skill triggers a workflow" reverse seam. |
| **`data_source`** | **PARTIAL (seam only)** | The ephemeral upload touches it; fully exercised only when connectors land. Name the "send-phase" seam now. |
| **`secrets_adapter`** | **NO (deferred with connectors)** | Only needed for outbound send / external creds. The template-fill flagship never authenticates outward. |
| **`panel_renderer`** | **LEAST** | The live read-only graph renders from data we already compute — no plugin. Specify last. |

**Recommendation:** in v2.9, **lock `phase_type` + `file_preview` (+ `tool`)** on real telemetry;
**DESIGN but do not lock** `data_source`/`secrets_adapter` (the connector/send seam); **specify
`panel_renderer` last.** Don't force all 6 types through one vision. The Plugin Contract becomes
load-bearing only at the outbound "send" phase.

## 9. PROPOSED v2.9 SCOPE

### CORE (must — the milestone is incomplete without these)
1. **Spike-first (SEED-051).** One real PM case (fill a Risk Register from a KB folder) answers the 4
   unknowns whose answers BECOME the schema: (a) can a model derive input fields from a template? (b)
   does KB-grounded docx fill produce a clean artifact? (c) what does authoring-time grounding need?
   (d) does describe→refine→publish *feel* good? **Do NOT pre-commit the `inputs`/`assets`/`folder_scope`
   schema before this.**
2. **Project = folder binding.** Optional `project_folder_id` on `WorkflowDefinition` + a
   folder-filtered library list endpoint. (V1) A thin "project" concept — NOT a heavy
   multi-tenancy entity.
3. **Workflow↔KB scope from the binding.** Source `folder_subtree_ids` from `project_folder_id`;
   add optional per-phase `folder_scope`. (V3)
4. **Workflow↔skill binding.** Optional `skill_ref` on `llm_agent`/`llm_single` configs; snapshot the
   skill version into the locked definition. (V2)
5. **Ephemeral template upload.** `POST /threads/{tid}/workspace/files` with `kind='template_input'`
   + `expires_at` + RLS + cron sweep. Workspace-only, never ingested. (V4)
6. **Template-fill capability.** Add `docxtpl` to `Dockerfile.sandbox` (bump `SANDBOX_IMAGE` tag);
   the parse→cited-field-map→validate→review→render→integrity-check composition. SandboxedEnvironment
   + sealed sandbox for SSTI. (V4)
7. **The Workflows PAGE + authoring API.** Phase A: CRUD draft definitions + lint-on-publish. Phase B:
   NL→draft one-shot structured generator over the strict schema. Live read-only graph. (V5) Sketch
   first (G-2).
8. **Output-quality gate (HARD publish blocker).** `llm_judge` ValidatorSpec kind + publish-time
   golden run + a `business_requirement` field. **NL-authoring MUST NOT ship without this.**
9. **Reusable validation-gate kinds library.** `citations_required`, `freshness`, `structure_check`,
   `output_file_valid`, `llm_judge_rubric`.
10. **PM flagship content pack.** Example templates (charter.docx, status-report.pptx,
    risk-register.xlsx) + workflow definitions + register schemas, authored on the generic
    primitives — proving domain-author-driven, not PM-hardcoded.

- **Scheduled / recurring triggers** (freq/time/timezone + optional event). The Postgres-resumable

## 11. Open questions for the operator (the decisions that most change scope)

1. **Is scheduled/recurring execution IN v2.9, or deferred?** It is table-stakes for the category but
   it is a **hard dependency on a budget/spend-ceiling system** (REJECT semantics at the gateway) that
   does not exist yet. If IN, SCHED- + the budget meter become CORE and the milestone grows
   materially. If deferred, v2.9 is purely "author + run on demand" — smaller, safer. **Recommend:
   defer scheduling to a fast-follow unless recurring reports are the headline value.**

2. **Does v2.9 include self-serve GLOBAL workflow sharing — i.e. do we build the operator/admin role
   tier now?** Today RLS cleanly allows drafts + per-user publish; global publish is reserved to seed
   migrations. If projects must be shared org-wide in v2.9, the operator tier becomes CORE (and pairs
   with multi-tenancy questions that are currently deferred). **Recommend: keep drafts + per-user
   publish in v2.9; defer the operator tier + global sharing.**

3. **How "magic" must template-fill be — trusted author-time placeholders, or arbitrary-upload
   schema-discovery?** Author-time `{{jinja}}` templates are reliable + formatting-preserving but
   require the author to mark up the template; arbitrary-upload "fill any docx you hand me" is the
   wow-demo but is where corruption/formatting-loss/SSTI risk concentrates. **Recommend: ship BOTH as
   separate patterns — project-library templates use docxtpl/Jinja (trusted); arbitrary uploads use
   non-Jinja run-replace (untrusted). Spike decides how far the arbitrary path can be pushed.**

4. **Is the citation-traceable GRID renderer (Hebbia-style) a v2.9 differentiator or a future
   polish?** It is the most visually compelling proof that PM matrices are KB-grounded + cited, but
   it is net-new UI on top of an already-large frontend deliverable (the Workflows page). **Recommend:
   STRETCH — land the page + authoring + template-fill first; add the grid if frontend budget remains.**

5. **For the PM flagship, is the headline demo the "standup-to-artifacts cascade" (one transcript →
   minutes → RAID → risk register → P×I matrix → status report) or a single template-fill (status
   report from KB)?** The cascade exercises every capability but is a much larger authored workflow;
   the single fill is the tightest, lowest-risk demo of the wedge. **Recommend: build the single
   template-fill (status report) as the spike + acceptance bar; assemble the cascade as the
   showcase content pack only after the primitives are proven.**
