# RAG Quality Investigation Report**Date**: 2026-04-18  **Triggered by**: User observed consistently low similarity scores (~0.43) when asking questions about uploaded PDF invoices  **Scope**: Chunking, embedding, retrieval pipeline, and confidence scoring---## Executive SummaryInvestigation revealed **six distinct problems** affecting retrieval quality. The most critical is a **chunking algorithm bug** that produces massive numbers of near-duplicate and broken chunks ÔÇö a 2,780-byte markdown file produced **203 chunks** instead of the expected ~4. This wastes embedding API tokens, pollutes search results with duplicate passages, and suppresses relevant chunks from appearing. Additionally, the chunker is **entirely format-agnostic** ÔÇö it ignores markdown headings, paragraph boundaries, table rows, and slide markers, splitting documents as a flat character stream. Combined with missing document context in embeddings and overly aggressive confidence thresholds, these issues explain consistently low similarity scores across all document types.---## Problem 1: Critical Chunking Algorithm Bug> [!CAUTION]> This is the **highest severity issue** ÔÇö it affects every document in the system and has compounding cost, accuracy, and performance impacts.### EvidenceA 2,780-byte markdown document (`kb_doc3_metrics_decisions.md`) produced **203 chunks**. Expected: ~4 chunks at `chunk_size=1000, overlap=200`.Sample chunks from the same document all contain the last ~110 characters but with 1ÔÇô3 character offsets:| chunk_index | content (first 30 chars) | chars ||---|---|---|| 87 | `ote work policy effective...` | ~115 || 90 | `work policy effective...` | ~110 || 91 | `work policy effective...` | ~110 || 97 | `olicy effective...` | ~105 |Chunks 90 and 91 have **bit-for-bit identical** content and **identical embedding vectors**.Similarly, the PDF invoice chunks showed the same pattern ÔÇö email addresses split mid-character across chunks: `AD85@`, `FHD.MRAD85@`, `MRAD85@`, `d FHD.MRAD85@`.### Root CauseThe bug is in [embedding_service.py, lines 10ÔÇô42](file:///c:/Vibe%20Apps/Agentic%20RAG/backend/app/services/embedding_service.py#L10-L42):```python# Sentence boundary searchfor i in range(end, search_start, -1):    if text[i - 1] in ".!?" and (i >= text_len or text[i] in " \n\r\t"):        end = i        break# Next chunk startnext_start = end - overlapif next_start <= start:    next_start = start + 1  # ÔåÉ BUG: advances only 1 character!start = next_start```**The failure cascade:**1. The sentence boundary search looks for `.!?` followed by whitespace within the overlap window `[search_start, end]`2. In structured documents (invoices, tables, numbered lists), periods appear frequently: `99.94%`, `$284,500`, `1. Approved`, `2. Pricing Change`3. When a period is found **early** in the overlap window (close to `search_start = start + overlap`), `end` gets set to approximately `start + overlap + small_offset`4. Then `next_start = end - overlap Ôëê start + small_offset` ÔÇö which can be as low as `start + 1`5. The safety guard `if next_start <= start: next_start = start + 1` fires, advancing by **one character**6. The next iteration starts just 1 char later, producing a near-identical chunk7. This repeats hundreds of times for any text with frequent periods**Why prose documents are less affected:** In regular English prose, sentences are typically 50ÔÇô150 characters. The sentence boundary is found further from `search_start`, so the overlap subtraction produces a reasonable `next_start` (~800 chars forward). But structured/tabular data with frequent short periods (decimals, numbered lists, abbreviations) hits the degenerate case.### Impact| Metric | Expected (4 chunks) | Actual (203 chunks) | Impact ||---|---|---|---|| Embedding API calls | ~4 | ~203 | **~50x cost** || Storage (1536-dim vectors) | 24 KB | 1.2 MB | **50x storage** || Search pollution | 0 duplicates in top-5 | 5/5 duplicates possible | **Wastes all retrieval slots** || Ingestion time | ~1s | ~20s+ | **20x slower** |---## Problem 2: No Document Context in Chunk Embeddings### EvidenceWhen the user asked *"what is the amount I paid on 17 Jan?"*, the top 5 retrieved chunks came from `Print Receipt for Card Payment On 17.JAN.2025.pdf` ÔÇö but the date **"17 Jan"** appears only in the **filename**, not in any chunk's `content` field.### Root CauseIn [documents.py, lines 477ÔÇô486](file:///c:/Vibe%20Apps/Agentic%20RAG/backend/app/api/documents.py#L477-L486):```pythonchunk_rows = [    {        "document_id": document_id,        "user_id": user_id,        "content": chunk,        # ÔåÉ raw text only, no filename/metadata prefix        "chunk_index": i,        "embedding": embedding,   # ÔåÉ embedding of raw text only    }    ...]```The chunk `content` is the raw extracted text. No filename, date, title, or document type is prepended. Since embeddings are computed on `content` alone, key contextual information is invisible to vector search.### Available but unused metadataThe `documents` table already stores rich metadata (extracted by the LLM during ingestion):```json{  "date": "2026-04-11",  "title": "Business Metrics & Key Decisions ÔÇö Week of April 7ÔÇô11, 2026",  "topics": ["business metrics", "product performance", ...],  "summary": "The report outlines significant product metrics...",  "language": "english",  "document_type": "report"}```None of this is injected into chunk content before embedding. A simple prefix like:```[Document: Print Receipt for Card Payment On 17.JAN.2025.pdf | Type: receipt | Date: 2025-01-17]Payment breakdown: Taxes AED 0.00, Penalties AED 0.00...```ÔÇªwould allow the query "amount paid on 17 Jan" to match the date in the embedding space, significantly boosting similarity scores.---## Problem 3: PDF Text Extraction Limitations### EvidenceThe PDF invoice chunks contained:- Email addresses split across character boundaries: `AD85@`, `FHD.MRAD85@`, `d FHD.MRAD85@`- Payment breakdowns as flat text without table structure- No visual grouping preserved from the original PDF layout### Root CauseIn [documents.py, lines 46ÔÇô48](file:///c:/Vibe%20Apps/Agentic%20RAG/backend/app/api/documents.py#L46-L48):```pythonif mime_type == "application/pdf":    reader = PdfReader(io.BytesIO(raw))    return "\n\n".join(page.extract_text() or "" for page in reader.pages)````pypdf`'s `extract_text()` is a basic layout-unaware text extractor. For structured PDFs (invoices, receipts, forms), it:- Doesn't preserve table cell boundaries- Merges columns into run-on text- Loses the visual grouping that makes data human-readable### Roadmap alignment> [!NOTE]> **Phase 35 (Multi-Modal Ingestion)** already plans to introduce `pdfplumber` for **table extraction**. However, Phase 35 focuses on extracting tables as separate structured data ÔÇö it does not address improving the base text extraction for chunking. Both improvements are complementary.---## Problem 4: Over-Aggressive Confidence Thresholds### EvidenceThe confidence scoring system in [threads.py, lines 133ÔÇô139](file:///c:/Vibe%20Apps/Agentic%20RAG/backend/app/api/threads.py#L133-L139):```pythondef _compute_confidence(avg_similarity: float) -> str:    if avg_similarity >= 0.7:        return "high"    elif avg_similarity >= 0.5:        return "medium"    return "low"```### AnalysisWith `text-embedding-3-small`, typical cosine similarity ranges are:| Content type | Typical top-5 avg similarity | What users see ||---|---|---|| Prose question ÔåÆ prose answer | 0.50ÔÇô0.70 | Medium || Natural question ÔåÆ structured data | 0.35ÔÇô0.55 | Low || Cross-language or paraphrased | 0.30ÔÇô0.50 | Low || Exact phrase match | 0.70ÔÇô0.85 | High |The 0.7 threshold for "high" confidence is almost never reached with `text-embedding-3-small` unless the query closely mirrors the chunk wording. Most correct answers will show "low" or "medium" confidence, undermining user trust.### NoteOnce Problem 1 (chunking bug) and Problem 2 (missing context) are fixed, similarity scores should increase by ~0.10ÔÇô0.20. Thresholds should be recalibrated **after** those fixes, not before.---## Problem 5: No Retrieval-Time Chunk Deduplication### EvidenceAll 5 top results from the invoice query contained effectively the same passage (payment breakdown section), with chunk indices 53, 54, 55, 61, 63. This wastes all 5 retrieval slots on identical information.### Root CauseThe `match_document_chunks` SQL function ([migration 025](file:///c:/Vibe%20Apps/Agentic%20RAG/supabase/migrations/025_document_versioning.sql#L20-L44)) returns the top-N chunks by raw similarity without any deduplication:```sqlORDER BY dc.embedding <=> query_embeddingLIMIT match_count;```There is a `_deduplicate_citations` function in [threads.py, line 142](file:///c:/Vibe%20Apps/Agentic%20RAG/backend/app/api/threads.py#L142-L151), but it deduplicates **citations for display**, not the actual retrieval results sent to the LLM. The LLM receives all 5 duplicate chunks, wasting its context window.---## Problem 6: No Structure-Aware Chunking> [!WARNING]> The chunker is **entirely format-agnostic** ÔÇö it treats all documents as
