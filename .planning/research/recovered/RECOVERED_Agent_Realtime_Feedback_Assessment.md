Root Cause Analysis### Why Gap 2 Exists (Architectural Reason)The current architecture follows this pattern:```LLM streams chunks ÔåÆ Backend accumulates tool_calls_buffer ÔåÆ Buffer complete ÔåÆ tool_start emitted ÔåÆ tool executes ÔåÆ tool_end emitted                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^                      THIS ENTIRE PHASE IS INVISIBLE TO THE USER```The backend accumulates tool call arguments in `tool_calls_buffer` (L857ÔÇôL867) inside the streaming loop, but **never emits any SSE event during accumulation**. The `tool_start` event is only emitted at L1019, **after** the stream completes and the full arguments are parsed.This is a **design-level gap** ÔÇö the architecture was built for fast tool calls (search_documents, query_documents) where argument generation takes <1 second. It was never designed for `execute_code` where arguments can be 50K+ tokens.### Why Claude Doesn't Have This ProblemClaude's architecture emits a "tool use starting" event **as soon as the tool name is known** (from the first `ToolCallInputDelta` chunk), before the arguments finish streaming. This gives the user immediate feedback: "Using [tool name]ÔÇª" appears within 0.5 seconds of the LLM's decision, even if the arguments take 60 seconds to stream.---## 6. Recommended Fix Strategy### Fix 1: Emit `tool_preparing` SSE Event During Argument Streaming (Gap 2 ÔÇö Critical)**Backend change** in `threads.py`, inside the OpenAI streaming loop (L857ÔÇôL867):```python# When a new tool call name is first detected, emit immediatelyif tc.function and tc.function.name and idx not in _announced_tools:    _announced_tools.add(idx)    yield f'data: {json.dumps({"type": "tool_preparing", "name": tc.function.name, "index": idx})}\n\n'```**Frontend change:**1. Add `onToolPreparing` callback to `streamMessage()` in `api.ts`2. In `useMessages.ts`, create a tool call entry with `status: "preparing"` (new status)3. In `ToolCallPanel.tsx`, render "preparing" status with a different animation:   ```   "Preparing Search DocumentsÔÇª" with pulsing gradient bar   ```**Impact:** Eliminates 90% of Gap 2. User sees what tool the agent chose within 0.5s, instead of waiting 30ÔÇô120s.### Fix 2: Emit `tool_args_progress` for Large Arguments (Gap 2 ÔÇö Enhancement)**Backend change:** During argument accumulation, emit periodic progress events:```python# Every 5000 characters of accumulated arguments, emit progressif len(tool_calls_buffer[idx]["arguments"]) % 5000 < len(tc.function.arguments or ""):    yield f'data: {json.dumps({"type": "tool_args_progress", "index": idx, "chars": len(tool_calls_buffer[idx]["arguments"])})}\n\n'```**Frontend change:** Show a subtle progress indicator (e.g., "Generating codeÔÇª 15KB") for `execute_code` arguments.**Impact:** Provides continuous feedback during long argument generation.### Fix 3: Add Elapsed Time Counter for Running Tools (Gap 4)**Frontend-only change** in `ToolCallPanel.tsx`:```tsxfunction ElapsedTimer({ startedAt }: { startedAt: number }) {  const [elapsed, setElapsed] = useState(0)  useEffect(() => {    const interval = setInterval(() => setElapsed(Date.now() - startedAt), 100)    return () => clearInterval(interval)  }, [startedAt])  return <span className="text-[10px] font-mono">{formatDuration(elapsed)}</span>}```Show this timer instead of a static spinner for tools in `status === "running"`.**Impact:** User sees real-time elapsed time, confirming the agent is still working.### Fix 4: Show "DecidingÔÇª" State for First Iteration (Gap 3)**Backend change:** Emit a `planning` event at the start of the loop (not just for iteration > 0):```python# Before the main loop, emit initial stateyield f'data: {json.dumps({"type": "planning", "iteration": 0})}\n\n'```**Frontend change:** The existing `onPlanning` handler would show "Planning next actionÔÇª" immediately.**Impact:** Eliminates the brief gap between "ThinkingÔÇª" and the first tool start.---## 7.
