Harness Engineering: Synthesis of Research### 2.1 Anthropic's Long-Running Agent Harness**Core insight:** Agents fail across context windows because they (1) try to one-shot too much, and (2) prematurely declare victory.**Their solution:**1. **Initializer agent**: First session sets up the environment ÔÇö `init.sh`, `feature_list.json`, `progress.txt`, initial git commit2. **Coding agent**: Every subsequent session makes incremental progress, leaves clean artifacts**Key artifacts:**- `feature_list.json` ÔÇö structured requirements, all initially "failing". Agents only change `passes` field. JSON chosen because models respect it more than Markdown.- `claude-progress.txt` ÔÇö human-readable log of what was done- Git commits with descriptive messages ÔÇö enables recovery from bad states- End-to-end testing before implementing new features (Puppeteer MCP)**Session startup ritual:**```pwd ÔåÆ read progress.txt ÔåÆ read feature_list.json ÔåÆ git log --oneline -20ÔåÆ start dev server ÔåÆ run basic E2E test ÔåÆ pick next failing feature```### 2.2 OpenAI's Harness Engineering (Codex)**Core insight:** When humans don't write code, the engineering discipline shifts from "writing good code" to "designing environments, specifying intent, and building feedback loops."**Key principles:**1. **Repository knowledge is the system of record** ÔÇö not Slack, not Google Docs, not people's heads2. **AGENTS.md is a table of contents, not an encyclopedia** ÔÇö ~100 lines, points to deeper docs3. **Progressive disclosure** ÔÇö agents start small and learn where to look next4. **Agent legibility is the goal** ÔÇö anything the agent can't access in-context effectively doesn't exist5. **Enforce invariants, not implementations** ÔÇö strict architectural boundaries with mechanical enforcement (custom linters)6. **Throughput changes merge philosophy** ÔÇö short-lived PRs, test flakes addressed with follow-up, corrections are cheap7. **Garbage collection** ÔÇö encode "golden principles" and run recurring cleanup agents**Architecture enforced mechanically:**- Layered domains: Types ÔåÆ Config ÔåÆ Repo ÔåÆ Service ÔåÆ Runtime ÔåÆ UI- Cross-cutting concerns enter through single explicit interface: Providers- Custom linters validate dependency directions, structured logging, naming conventions, file size limits### 2.3 HKUDS OpenHarness**Core insight:** An Agent Harness = Tools + Knowledge + Observation + Action + Permissions.**10 subsystems:**| Subsystem | Purpose ||-----------|---------|| `engine` | Agent Loop ÔÇö query ÔåÆ stream ÔåÆ tool-call ÔåÆ loop || `tools` | 43+ Tools ÔÇö file I/O, shell, search, web, MCP || `skills` | On-demand knowledge loading (.md files) || `plugins` | Extensions ÔÇö commands, hooks, agents, MCP servers || `permissions` | Multi-level safety ÔÇö modes, path rules, command deny || `hooks` | PreToolUse / PostToolUse lifecycle events || `commands` | 54 slash commands ÔÇö /help, /commit, /plan, /resume || `mcp` | Model Context Protocol client || `memory` | Persistent cross-session knowledge || `coordinator` | Multi-Agent ÔÇö subagent spawning, team coordination |**Notable features:**- **Auto-compaction**: preserves task state and channel logs across context compression- **Dry-run mode**: previews resolved settings, auth, skills, tools without execution- **Subprocess teammates**: headless worker mode for background agents- **Channel slash commands**: multimodal attachment support---## 3. Strategic OpportunitiesBased on the convergence of our mature codebase and the three harness research sources, here are the **highest-leverage opportunities** for harnessing agents in this application:---### Opportunity A: Background Research Agent (Anthropic Pattern)**Problem:** Current agent work is bound to the SSE connection. A user can't kick off a 30-minute research task and come back later.**Solution:** Implement a **Background Task Agent** using the Anthropic initializer/coding agent pattern.**How it would work:**1. User prompts: *"Research all my Q4 reports and build a consolidated financial summary with charts"*2. System creates a **Task Record** (`agent_tasks` table) with status `pending`3. **Initializer Agent** (first context window):   - Analyzes the request and generates a `task_plan.json` ÔÇö structured list of sub-tasks   - Example: `[{"step": 1, "action": "glob", "args": {"pattern": "*Q4*"}, "status": "pending"}, ...]`   - Commits the plan and writes a `task_progress.txt` log4. **Worker Agent** (subsequent context windows, potentially spread across hours):   - Each session reads `task_plan.json` and `task_progress.txt`   - Executes ONE step at a time   - Updates `task_plan.json` (changes `status` to `done` or `failed`)   - Appends to `task_progress.txt`   - Persists intermediate artifacts to Supabase Storage5. **Frontend**: Task dashboard showing progress, live logs, artifact downloads**Database additions:**```sqlCREATE TABLE agent_tasks (    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),    user_id uuid REFERENCES auth.users(id),    thread_id uuid REFERENCES threads(id),    status text CHECK (status IN ('pending','running','paused','completed','failed')),    plan jsonb,           -- the task_plan.json    progress_log text,    -- the task_progress.txt    artifacts jsonb,      -- list of storage paths    created_at timestamptz DEFAULT now(),    updated_at timestamptz DEFAULT now());```**Why this is powerful:**- Breaks the SSE connection barrier- Enables genuinely long-running work (hours, not seconds)- Users can review, pause, or modify tasks mid-flight- Intermediate artifacts are inspectable and reusable---### Opportunity B: Multi-Agent Orchestration (OpenHarness Pattern)**Problem:** Current architecture is single-agent with simple sub-agent delegation. facts from documents | Cheap model (Haiku/nano) || **Analyst** | Synthesizes data, identifies patterns, calculates metrics | Capable model (Sonnet/4.1) || **Coder** | Generates charts, tables, files in sandbox | Capable model + sandbox || **Reviewer** | Validates outputs for accuracy, citations, completeness | Capable model || **Writer** | Produces final prose, summaries, narratives | Capable model |**Orchestration flow:**```User Request ÔåÆ Planner ÔåÆ Task Graph                    Ôåô    ÔöîÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔö¼ÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔö¼ÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÇÔöÉ    Ôåô infrastructure for background execution- Each specialist agent is essentially a configured instance of our existing agent loop with a specialized system prompt and reduced tool set- Coordinator uses a sandbox ÔÇö the Coder agent can use it directly- We already have skills ÔÇö each agent role can be a skill- We already have SSE streaming ÔÇö coordinator streams updates from all agents---### Opportunity C: Agentic Development Harness (OpenAI Pattern)**Problem:** The codebase is ~100k+ words across 191 files. As it grows, agent developers (including Claude Code) struggle with context management.**Solution:** Apply OpenAI's harness engineering principles to make the repository maximally legible to agents.**Immediate actions:**1. **Restructure documentation as system of record**   ```   docs/   Ôö£ÔöÇÔöÇ design-docs/   Ôöé   Ôö£ÔöÇÔöÇ index.md   Ôöé   Ôö£ÔöÇÔöÇ core-beliefs.md   Ôöé   ÔööÔöÇÔöÇ architecture.md   Ôö£ÔöÇÔöÇ exec-plans/   Ôöé   Ôö£ÔöÇÔöÇ active/   Ôöé   Ôö£ÔöÇÔöÇ completed/   Ôöé   ÔööÔöÇÔöÇ tech-debt-tracker.md   Ôö£ÔöÇÔöÇ product-specs/   Ôöé   ÔööÔöÇÔöÇ ...   ÔööÔöÇÔöÇ references/       ÔööÔöÇÔöÇ api-patterns.md   ```   - Move `CLAUDE.md` content into this structure   - Keep `CLAUDE.md` as a ~100-line table of contents pointing to deeper docs2. **Encode "golden principles"**   - All tables must have RLS   - All API endpoints must have Pydantic request/response models   - All LLM calls must be traceable via LangSmith   - All frontend components must use semantic CSS variables   - Enforce via custom pre-commit hooks or CI checks3. **Progressive disclosure for agents**   - `ARCHITECTURE.md` ÔÇö top-level domain map   - `DESIGN.md` ÔÇö design system reference   - `QUALITY_SCORE.md` ÔÇö grades per domain/layer, tracked over time   - Each file has a header comment pointing to its design doc4. **Mechanical enforcement**   - Custom linter: check that new API routes have Pydantic models   - Custom linter: check that new Supabase tables have RLS policies   - Custom linter: check file size limits (e.g., no file > 500 lines without justification)   - CI job: verify all docs are cross-linked and not stale**Why this matters:**- Our development velocity is already high ÔÇö this compounds it- Future agent developers (including future versions of Claude Code) will produce higher-quality output with less human intervention- Prevents architectural drift as the codebase scales---### Opportunity D: MCP Server Exposure**Problem:** The application's agent capabilities are siloed to the web UI. External tools (Cursor, Claude Desktop, VS Code extensions) can't leverage the knowledge base or tools.**Solution:** Expose the Agentic RAG backend as an **MCP (Model Context Protocol) server**.**What this enables:**- A user in Cursor can ask: *"What does my Q4 report say about revenue?"* and Cursor queries the Agentic RAG MCP server- A user in Claude Desktop can say: *"Analyze the document I uploaded to Agentic RAG yesterday"*- External agents can use our tools: `search_documents`, `execute_code`, `query_tables`**Implementation:**- New FastAPI router: `/mcp/v1/` implementing the MCP protocol- Auth: API keys (separate from Supabase JWT, scoped per-user)- Resources: documents, folders, skills, memory entries- Tools: expose our existing 13 tools via MCP schema- Prompts: pre-built prompts for common workflows**Why now:**- MCP is gaining rapid adoption (OpenHarness, Claude Desktop, Cursor all support it)- Our tool definitions are already JSON Schema ÔÇö trivial to adapt to MCP- Our SSE infrastructure is already battle-tested- This turns our application from a product into a **platform**---### Opportunity E: Context Compression & Resumability (OpenHarness Pattern)**Problem:** KI-001 (in-flight cancellation) is a symptom of a deeper issue: the agent loop has no concept of pausing, checkpointing, or resuming. Every session is all-or-nothing.**Solution:** Implement **Agent Checkpointing**.**Design:**1. After each tool execution, the agent state is serialized to a checkpoint:   ```json   {     "checkpoint_id": "uuid",     "thread_id": "uuid",     "iteration": 3,     "messages": [...],           // truncated/compressed     "tool_calls": [...],     "pending_tool": null,     "created_at": "..."   }   ```2. Checkpoints stored in `agent_checkpoints` table or Supabase Storage3. On reconnect (SSE disconnect + reconnect):   - Load latest checkpoint   - Resume from the next yield point   - User sees: *"Resuming from step 3 of 8..."***Context compression strategies (from OpenHarness):**- **Summarization**: older messages summarized into a single "previously..." message- **Token eviction**: drop oldest messages first (already partially done via `trim_messages_to_fit`)- **Artifact references**: instead of embedding full tool results, reference artifact IDs**Why this matters:**- Solves KI-001 at the architectural level- Enables browser refresh without losing agent state- Enables true background execution (pause agent, resume later)- Foundation for the Background Research Agent (Opportunity A)---## 4. ConclusionThe Agentic RAG application is already a **sophisticated agent harness** ÔÇö arguably more advanced than many production systems. The next evolution is not adding more tools, but rather:1. **Breaking the session boundary** ÔÇö enabling long-running, resumable, background agent work2. **Specializing and coordinating** ÔÇö moving from single-agent to multi-agent orchestration3. **Platformizing** ÔÇö exposing our agent infrastructure to external tools via MCP4. **Meta-harnessing** ÔÇö making the codebase itself maximally legible and maintainable by agentsThe convergence of Anthropic's session-management patterns, OpenAI's repository-legibility discipline, and OpenHarness's modular architecture provides a clear, proven blueprint for each of these evolutions.**Recommended immediate next step:** Create a detailed plan for Phase 1 (Foundation) and execute the `docs/` restructure + `agent_tasks` schema as a proof-of-concept.---*Research compiled from live codebase audit (191 files, 1682 graph nodes, 2647 edges) and analysis of three primary sources: Anthropic Engineering (Nov 2025), OpenAI Engineering (Feb 2026), HKUDS OpenHarness (v0.1.7).*
