# PRD: Enterprise RAG Features Roadmap**Product:** Agentic RAG  **Version:** v3.0 Target  **Status:** Draft  **Date:** 2026-04-11---## OverviewThis document defines the product requirements for elevating the Agentic RAG application to enterprise-grade standards. The features below are drawn from a gap analysis against top-tier RAG products (Glean, Guru, Notion AI, Microsoft Copilot) and are prioritized by business impact, adoption risk reduction, and implementation feasibility.The app already has a strong technical foundation: hybrid search, metadata filtering, folder scoping, multi-agent KB tools, skills, code execution, and multi-format ingestion. The gaps are concentrated in **trust**, **collaboration**, **data integrity**, and **observability**.---## Priority 1 ÔÇö High Business Impact### F-01: Citation with Source Passage Highlighting**Problem**  Users receive answers they cannot verify. The app cites document names but does not show which specific passage was retrieved. This is the #1 barrier to enterprise adoption ÔÇö users cannot trust what they cannot inspect.**Goal**  Surface the exact retrieved passages in-line with the answer, clearly attributed to their source document and location.**Requirements**- Each `search_documents` result chunk must carry its source document name, page/line range, and the raw passage text- The frontend must render retrieved passages as collapsible citation cards beneath the answer, showing: document name, section (if identifiable), and the exact passage text with a character limit (e.g. 400 chars, expandable)- Passage text must be visually distinct from the AI-generated response (e.g. quoted block, different background)- Clicking a citation card opens the document in a preview panel or highlights the relevant section- Citation cards must only appear for passages that were actually retrieved in that response turn ÔÇö never fabricated- Works for `search_documents` results; `analyze_document` citations show document name only (full-doc analysis has no chunk anchor)**Out of scope (v1)**  In-document PDF highlighting, citation export, cross-thread citation linking**Success criteria**- Users can verify any factual claim in an answer by reading the source passage without leaving the app- Zero instances of a citation card appearing for a document not retrieved in that turn---### F-02: Document Versioning & Change Detection**Problem**  When a user uploads a new version of an existing document (different content, same filename), the old chunks remain in the vector store and contaminate retrieval. Answers can be based on outdated information with no indication to the user. The current duplicate detection only catches identical content (hash match) ÔÇö it does not handle updated versions.**Goal**  Track document versions explicitly. When a new version is uploaded, retire the old chunks and preserve version history for audit purposes.**Requirements**- Add a `version` integer column and `superseded_by` nullable FK to the `documents` table- On upload: if a document with the same filename exists for that user, treat the new upload as a new version ÔÇö set `superseded_by` on the old record, increment version number- Old chunks (from the superseded document) must be excluded from all retrieval and search operations immediately upon new version ingestion completing- The document library UI must show version badges (e.g. "v3") on documents that have been updated- Users can expand a document row to see its version history (version number, upload date, file size)- Users can view or re-ingest an older version (restore it as the active version)- Answers that use a versioned document must cite the version: **Report.pdf (v2)** ÔÇö Section 3- `query_documents` tool must default to active versions only; version history accessible via optional SQL filter**Out of scope (v1)**  Diff view between versions, automatic version tagging from document metadata**Success criteria**- Uploading a revised document never returns results from the previous version- Users can identify which version of a document an answer was sourced from---### F-03: Persistent Cross-Thread Memory**Problem**  Each conversation thread is fully isolated. Users must repeat context across sessions ("as I mentioned last week, my project is XÔÇª"). There is no way for the assistant to remember standing preferences, ongoing projects, or decisions made in previous conversations.**Goal**  Maintain a per-user memory layer that persists key facts, preferences, and context across threads. The assistant reads from and writes to this memory automatically.**Requirements**- New `user_memory` table: `id`, `user_id`, `key` (short label), `value` (text), `source_thread_id`, `created_at`, `updated_at`- New backend tool `remember` ÔÇö LLM calls this to store a fact: `remember(key, value)`. Examples: "current_project: Alpha redesign", "preferred_format: bullet points", "company: Acme Corp"- New backend tool `recall` ÔÇö LLM calls this to retrieve stored facts: `recall(key?)` returns all or a specific key- At the start of each conversation turn, inject a concise memory summary into the system prompt (top 10 most recently updated entries, max 500 tokens)- Users can view, edit, and delete memory entries from a new "Memory" section in Settings- Memory entries are never shared across users- The LLM must be instructed to call `remember` when the user states a persistent preference or fact, and to use recalled memory to personalize answers without being asked**Out of scope (v1)**  Memory expiry/TTL, memory categories/namespaces, memory search**Success criteria**- A user states "I prefer responses in bullet points" in thread A; in thread B the assistant responds in bullet points without being asked- A user says "my current project is X"; subsequent threads reference X when relevant---### F-04: Group-Level Access Control**Problem**  Documents are either private (user-only) or global (all users). There is no concept of teams or groups. Organizations need to share documents within a department without exposing them company-wide.**Goal**  Introduce a group/team layer that allows documents and folders to be shared with specific groups of users.**Requirements**- New tables: `groups` (`id`, `name`, `created_by`, `created_at`), `group_members` (`group_id`, `user_id`, `role` enum: admin/member)- Documents and folders gain a `group_id` nullable FK ÔÇö a document can be private, group-shared, or global (not both group and global simultaneously)- RLS policies updated: authenticated users can read documents where `user_id = auth.uid()` OR `group_id IN (user's groups)` OR `is_global = true`- Group admin can invite members by email (sends Supabase auth invite)- Group admin can upload documents directly to the group's scope- The ingestion UI shows three visibility options when uploading: Private / Group (dropdown of user's groups) / Global- Folder visibility follows the same three-tier model- `query_documents` and all KB tools respect group-scoped RLS automatically- A user leaving a group immediately loses access to group-scoped documents**Out of scope (v1)**  Per-document permission overrides, nested groups, SSO/SAML group sync**Success criteria**- A Finance group member can retrieve Finance documents; an Engineering member cannot- Removing a user from a group takes effect on the next request (no caching lag)---## Priority 2 ÔÇö Medium Business Impact### F-05: Answer Confidence Score (User-Visible)**Problem**  The app already computes similarity scores internally (0ÔÇô1 scale) but never surfaces them to the user. Users have no signal for when to trust an answer vs. when to verify it independently. This matters most in regulated industries (legal, medical, financial).**Goal**  Show a visible confidence indicator on each AI response, derived from the quality of retrieved evidence.**Requirements**- Compute a response-level confidence score from the retrieved chunks: average similarity of top-3 chunks, weighted by how many chunks were retrieved vs. requested- Map to three tiers: **High** (avg similarity ÔëÑ 0.7), **Medium** (0.5ÔÇô0.7), **Low** (< 0.5 or zero results)- Display as a small badge on each assistant message: "High confidence", "Medium confidence", "Low ÔÇö verify independently"- Badge is colour-coded: green / amber / red- When confidence is Low, append a standard disclaimer to the response: "This answer is based on limited or weakly-matched evidence. Please verify with the source documents."- Confidence score and tier are passed from the backend as an SSE event (`confidence_score`, `confidence_tier`) and stored in the message- Does not apply to web_search, execute_code, or skill-only responses (only document-grounded answers)**Out of scope (v1)**  Per-claim confidence, user feedback affecting future scoring, calibration tuning**Success criteria**- Every document-grounded response shows a confidence badge- Low-confidence responses always include the disclaimer text---### F-06: Audit Log**Problem**  There is no record of who searched for what, which documents were retrieved, or what answers were given. This is a hard requirement for SOC 2, GDPR, HIPAA, and most enterprise security reviews.**Goal**  Maintain an immutable audit trail of all significant user actions and AI retrievals.**Requirements**- New `audit_log` table: `id`, `user_id`, `action_type` (enum), `resource_type`, `resource_id`, `metadata` (JSONB), `created_at`- Logged action types: `document_upload`, `document_delete`, `document_view`, `search_query` (query text + doc IDs retrieved), `code_executed`, `skill_loaded`, `thread_created`, `thread_deleted`, `settings_changed`- Audit log entries are append-only ÔÇö no UPDATE or DELETE allowed (enforce via RLS: no delete policy)- Backend writes audit entries asynchronously (non-blocking fire-and-forget) ÔÇö never delays a response- Admin view (Settings ÔåÆ Audit Log): filterable by date range, action type, document; paginated; exportable as CSV- Audit log is per-user (users see only their own log); no cross-user audit in v1- Retention: entries kept for 90 days by default (configurable via env var `AUDIT_LOG_RETENTION_DAYS`)**Out of scope (v1)**  Organisation-level admin view, real-time alerting, SIEM integration**Success criteria**- Every document retrieval event appears in the audit log within 1 second- Audit entries cannot be deleted through any user-accessible API endpoint---### F-07: Multi-Modal: Table & Image Extraction**Problem**  PDFs containing financial tables, charts, and diagrams lose all structure on ingestion ÔÇö everything becomes flat prose. A quarterly earnings report's revenue table becomes unqueryable text. Charts lose their data entirely.**Goal**  Extract structured tables from documents as queryable data and extract images with vision-model descriptions during ingestion.**Requirements**- **Tables:** During ingestion, detect and extract tabular data from PDF and DOCX files using a table-extraction library (e.g. `pdfplumber`, `camelot`). Store extracted tables as structured JSON in a new `document_tables` table (`document_id`, `page`, `table_index`, `headers`, `rows` JSONB)- **Images:** During ingestion, extract embedded images from PDFs and DOCX. For each image above a minimum size threshold (50├ù50px), call a vision LLM to generate a description. Store descriptions in `document_images` (`document_id`, `page`, `image_index`, `description`)- Table data is indexed and queryable via an extended `query_documents` tool (or new `query_tables` tool)- Image descriptions are embedded and included in vector search results alongside text chunks- Ingestion status updates (Supabase Realtime) include table and image extraction progress- If table/image extraction fails, ingestion continues ÔÇö these are best-effort enhancements, not blockers- The document library shows a "Tables: N, Images: N" indicator on documents where these were extracted**Out of scope (v1)**  Rendering extracted tables in the UI, chart-to-data conversion, OCR for scanned PDFs**Success criteria**- A question about a specific table value in a PDF (e.g. "what was revenue in Q3?") can be answered directly from extracted table data- Image descriptions appear in search results when the user asks about diagram content---### F-08: Suggested Follow-Up Questions**Problem**  After receiving an answer, users often don't know what to ask next or don't know what else the knowledge base contains. Discovery is entirely dependent on the user already knowing what they're looking for.**Goal**  Surface 2ÔÇô3 contextually relevant follow-up questions after each assistant response to guide exploration and increase engagement.**Requirements**- After generating a response, the backend generates 2ÔÇô3 suggested follow-up questions using a fast/cheap model (not the main orchestrator model) based on: the user's question, the retrieved documents, and the assistant's answer- Suggestions are streamed as a final SSE event (`suggestions: [...]`) after the main response completes- Frontend renders suggestions as clickable pill buttons below the assistant message- Clicking a suggestion populates the message input and immediately submits it- Suggestions are regenerated fresh each turn ÔÇö not cached or repeated- Generation is non-blocking: if the suggestion call fails, the main answer is unaffected- Suggestion model defaults to the cheapest available model for the active provider (same logic as sub-agent model selection)**Out of scope (v1)**  User feedback on suggestion quality, learning from accepted suggestions, suggestions in Explorer mode**Success criteria**- Suggestions appear within 2 seconds of the main response completing- At least one suggestion per response is topically relevant to the retrieved documents---## Priority 3 ÔÇö Polish & Differentiation### F-09: Knowledge Health Dashboard**Problem**  Knowledge managers have no visibility into the state of their document library. They don't know which documents are never retrieved (dead knowledge), which are retrieved most often, or whether the library has coverage gaps.**Goal**  Provide a dashboard that surfaces library health metrics to help users maintain a high-quality knowledge base.**Requirements**- New "Library Health" view accessible from the sidebar (Knowledge Base section)- Metrics displayed:  - **Most retrieved documents** (top 10 by retrieval count, last 30 days)  - **Never retrieved documents** (uploaded but never appeared in search results)  - **Low-confidence documents** (frequently retrieved but always with low similarity scores ÔÇö content may be poorly structured or wrong format)  - **Stale documents** (not updated in > 90 days, configurable)  - **Storage breakdown** by folder and file type- Retrieval counts derived from the audit log (`search_query` events with document ID references)- Metrics refresh daily (not real-time)- Users can act directly from the dashboard: delete a document, re-ingest, or move to a folder**Out of scope (v1)**  Cross-user analytics, embedding quality scoring, automated remediation suggestions**Success criteria**- A user can identify their top 10 most-used documents and their 10 least-used within 30 seconds- "Never retrieved" list accurately reflects documents with zero retrieval events---### F-10: User Feedback Loop (Thumbs Up / Down)**Problem**  There is no mechanism for users to signal when an answer was wrong, unhelpful, or hallucinated. Poor retrieval behavior persists indefinitely with no feedback signal.**Goal**  Capture per-response quality signals that can be used to identify retrieval failures and improve the system over time.**Requirements**- Each assistant message has a thumbs-up / thumbs-down button (shown on hover)- On thumbs-down: optional short-form reason selector (Wrong answer / Not from my documents / Incomplete / Other)- Feedback stored in new `message_feedback` table: `message_id`, `user_id`, `rating` (positive/negative), `reason` (nullable), `created_at`- Feedback is visible in the Audit Log (Settings ÔåÆ Audit Log) filtered by `message_feedback` action type- Aggregate feedback stats shown in the Knowledge Health Dashboard: overall positive rate (last 30 days), most-downvoted documents- Submitting feedback does not interrupt the conversation or require confirmation- Feedback is per-user and per-message ÔÇö one rating per message per user**Out of scope (v1)**  Automated retraining from feedback, feedback-driven retrieval parameter tuning, public feedback leaderboard**Success criteria**- A user can rate any response within 2 clicks- Feedback data is queryable by the knowledge manager via the dashboard within 24 hours---## Implementation Notes### Dependencies between features- F-06 (Audit Log) is a dependency for F-09 (Knowledge Health Dashboard) and F-10 (Feedback Loop)
