# Phase 071.3 — Table Engine Comparison

**Date:** 2026-05-16
**Author:** Research pass (single sweep — desk research, no spikes)
**Context:** Docling demoted (4-min stalls + OOM at 2x render scale + httpx<0.29 pin
that already forced PyMuPDF into a subprocess fence). Interim default is
`pdfplumber`, but `page.extract_tables()` finds only 4 tables on a thesis
with 20+ visible tables. We need a non-Docling engine that recovers
borderless and layout-aligned academic tables without re-introducing
Docling-class instability.

## 2. Per-candidate detail

### 2.1 PyMuPDF `find_tables` — recommended baseline

We already ship PyMuPDF (AGPL-3.0) behind `backend/extractors/pymupdf_isolated.py`,
so adding `find_tables` is a fence extension, not a new dependency. The API
exposes four strategies — `lines`, `lines_strict`, `text`, `explicit` — and the
PyMuPDF team's own posts admit "PyMuPDF only handles simple bordered tables…
borderless, multipage and merged-cell tables need custom algorithms"
([Artifex blog](https://artifex.com/blog/extracting-tables-from-pdfs-with-pymupdf)).
That is honest. The `text` strategy uses text positions to synthesize virtual
column/row boundaries and is the right knob to try on borderless academic
tables; `lines_strict` increases precision by ignoring borderless rectangles
that masquerade as cells.

Performance-wise, the arXiv 2410.09871 comparative study (Oct 2024, "A
Comparative Study of PDF Parsing Tools Across Diverse Document Categories")
finds PyMuPDF has the **most consistent recall across categories among
rule-based tools**, and is the best rule-based parser on the `Manual`
category — but it is outperformed by TATR-class detection models on
`Scientific`, `Financial`, `Patent`, and `Law`. There is a known PyMuPDF
GitHub issue (#3156) where users find `strategy="lines"` worse than
pdfplumber on specific documents — so the `text` strategy plus tuned
`min_words_*` is what we should bench, not the default.

Stability: native C library, no OOM cliffs reported at our scale, no httpx
or torch dependency. Already subprocess-fenced for AGPL hygiene. Adapter
work is ~80–150 LOC: extend the existing isolated process to expose
`find_tables(strategy=...)` and serialize bbox+cells back. Latest release
is regularly updated (1.24.x series active through 2026).

**Bench plan:** test `strategy="lines_strict"` then `strategy="text"` with
`min_words_horizontal` / `min_words_vertical` tuned for the thesis. This is
the cheapest possible win — if it recovers 12 of 20 tables vs pdfplumber's
4, we may not even need gmft.

### 2.2 gmft — recommended ML engine

gmft is a **lightweight MIT-licensed wrapper around Microsoft's Table
Transformer (TATR)** that runs on CPU at ~1.4 s/page on Colab CPU
([PyPI](https://pypi.org/project/gmft/)). It is the "skip the Docling-shaped
hole" option: it gives us TATR's recall ceiling without dragging in
detectron2, poppler, paddleocr, or tesseract — its only runtime deps are
`pypdfium2` and `transformers`+`torch` (CPU build acceptable). License is
MIT for both the wrapper code and the upstream TATR weights, so no
subprocess fencing is required for legal reasons; we can lazy-import inside
the table-engine adapter so FastAPI startup stays clean.

TATR ground truth: in arXiv 2410.09871, TATR is reported as **the best
table-detection model on Scientific, Patent, Financial, and Law &
Regulations categories** — the exact category that matches our thesis
workload. On ICDAR-2013 it scores 75% exact-match when trained on
PubTables-1M; combined PubTables-1M+FinTabNet pushes it to 81%
([TATR paper](https://github.com/microsoft/table-transformer)). That is
materially above any rule-based parser we have benchmarked.

Active project (v0.4.3 released Feb 2026, MIT). The notable known issue is
#55 (thread safety) — fine for our async backend since we already wrap
blocking calls in `run_in_threadpool` (decision D-v2.5-01) and we are
single-uvicorn-worker (D-v2.5-02). No known OOM cliff on academic PDFs;
the failure mode is "ignores tables on rotated pages," not "stalls 4
minutes." Adapter cost is ~150–250 LOC: detect tables via
`AutoTableDetector` → render each region via `pypdfium2` → `AutoFormatter`
to extract structure → return our `ExtractedTable` shape.

**Bench plan:** run gmft on the same thesis as PyMuPDF, compare recall and
structural fidelity. Measure cold-start (transformers model load) and
per-page latency. Confirm it doesn't trip the 4-min Docling timeout on the
problematic page.

### 2.3 Camelot 1.0 — recommended dispatcher fallback

Camelot 1.0 (Aug 2025) finally dropped Ghostscript as the default backend
in favor of pdfium ([camelot-py docs](https://camelot-py.readthedocs.io/en/master/user/install-deps.html)).
That removes the historical "won't install on macOS / SIP issues / libgs
missing" tax. License is MIT. Footprint is modest (~80 MB including
opencv-python, pdfium, pdfminer.six). Lattice mode uses OpenCV morphology
on rendered pages to find ruled tables; **Stream mode is the only relevant
mode for borderless** — it uses PDFMiner character grouping and whitespace
clustering.

The arXiv 2410.09871 paper rates Camelot as best-in-class for `Government
Tenders` and competitive on `Table-BRGM`, but only mid-pack on
`Table-arXiv` (academic). It is not the right primary engine for theses,
but it **is** a useful fallback specifically because Stream and Lattice
fail in different ways than PyMuPDF and gmft — which is the point of the
per-aspect dispatcher pattern the project has already adopted
(feedback_preserve_engine_optionality).

Adapter cost ~100 LOC. No subprocess fence needed (MIT, pure Python +
opencv). No model downloads.

### 2.4 The honest losers

**Marker** is genuinely strong on `--use_llm` mode (FinTabNet 0.907), but
it is GPL-3.0 with CC-BY-NC-SA weights — would force subprocess fencing
just for licensing — *and* it is GPU-first (122 pg/s on H100; CPU
performance is not advertised, which usually means it's painful). At ~2 GB
of model weights plus Surya, it is structurally a Docling-class burden.
Skip.

**MinerU** is even further down the same road: AGPL-3.0, multi-GB model
stack (now centered on the MinerU2.5-Pro VLM), built around TableMaster +
StructEqTable + VLM. Excellent OmniDocBench scores (86.2 overall, 97.5
mAP layout) but the installation/footprint/risk profile is precisely what
we just fled. Skip.

**Tabula-py** wraps tabula-java via jpype. Strong on `Manual` and
`Scientific` per the arXiv comparison, but a JVM in the FastAPI process is
a fence-by-default situation — and once jpype has launched the JVM you
can't change JVM opts without restarting Python. That is the kind of
constraint that always bites at the wrong moment. Skip.

**PaddleOCR PP-StructureV3** has objectively excellent Chinese+English
table support including borderless, and 6% accuracy improvements landed in
2025. But: ~720 MB install (paddlepaddle 717 MB), separate `paddlepaddle`
install step, PaddlePaddle 3.x dependency, and a runtime that historically
fights other torch-based libraries on Windows. Could revisit if gmft
disappoints on borderless, but not first.

**img2table** has an explicit `borderless_tables` flag — and the docs
explicitly flag it as "alpha, requires ≥3 columns, requires external OCR."
Not production-grade for our thesis case.

**unstructured.io OSS** in `hi_res` mode brings detectron2 + layoutparser
+ ONNX + multiple model downloads. Their own benchmark reports 100% on
simple tables, **only 75% on complex structures**, and "weak structural
preservation" on nested/multi-column. The dep tree is the exact shape of
the Docling failure we just escaped. Skip.

**Microsoft TATR raw** — the model itself is what we want, but gmft is the
lightweight production wrapper. Re-implementing the crop + OCR loop from
scratch is strictly more LOC for the same accuracy.

**pymupdf4llm** wraps PyMuPDF's `find_tables`. It is a markdown
*formatter*, not a separate detection engine. Useful if we want to keep
LLM-friendly markdown output, but it cannot improve recall beyond what
PyMuPDF already finds.

## 3. Recommendation: rank the top 3 to bench

1. **PyMuPDF `find_tables` with `strategy="text"` (+ `lines_strict`)** —
   zero new dependencies, extend the existing isolated process. Cheapest
   possible win; even a partial improvement (say 8/20 vs pdfplumber's 4/20)
   buys time. **Spike first.**

2. **gmft (TATR)** — MIT, CPU-OK, lazy-importable, no httpx-style pinning.
   This is the recall ceiling among realistic candidates for academic
   borderless tables; TATR is the model arXiv 2410.09871 ranks first on
   Scientific. Bench on the same thesis page set as PyMuPDF. **Spike
   second; expected primary winner.**

3. **Camelot 1.0 Stream** — keep as a per-aspect dispatcher fallback for
   layouts that defeat both rule-based PyMuPDF and TATR (e.g. tightly-
   packed whitespace tables where character grouping wins). MIT, ~80 MB,
   no subprocess fence. **Spike third; likely role = secondary/fallback,
   not primary.**

Architectural fit: this dovetails with the dispatcher direction
(`text/tables/images/equations` swappable independently —
feedback_preserve_engine_optionality). PyMuPDF stays the cheap default;
gmft becomes the high-recall table-aspect engine; Camelot Stream sits
behind a confidence threshold as the "tables-PyMuPDF-missed" backup.
